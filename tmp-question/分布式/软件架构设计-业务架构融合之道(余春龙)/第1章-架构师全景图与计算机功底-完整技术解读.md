# 第1部分 架构师的全景视图

## 1.1 架构师的职业分类：当我们在说"架构师"时在说什么

### 1.1.1 三层架构体系

余春龙将架构分为三层，每一层对应不同的职责和技能要求：

```
┌─────────────────────────────────────────┐
│  第三层：业务系统架构                        │
│  职责：面向具体业务的系统设计与领域建模          │
│  关注：DDD（领域驱动设计）、微服务拆分、        │
│        业务建模、需求分析                     │
│  典型title：业务架构师、应用架构师              │
└─────────────────────────────────────────┘
┌─────────────────────────────────────────┐
│  第二层：中间件与大数据平台                   │
│  职责：提供通用的技术平台与工具               │
│  关注：消息队列（RocketMQ/Kafka）、           │
│        分布式缓存（Redis）、注册中心（Nacos）、 │
│        大数据平台（Spark/Flink）              │
│  典型title：中间件架构师、数据架构师            │
└─────────────────────────────────────────┘
┌─────────────────────────────────────────┐
│  第一层：基础架构                           │
│  职责：提供底层运行环境与基础设施              │
│  关注：IaaS/PaaS、网络拓扑、容器化          │
│         (K8s/Docker)、CI/CD、安全            │
│  典型title：基础架构师、运维架构师             │
└─────────────────────────────────────────┘
```

**关键认知**：三层架构不是"高级 vs 初级"的等级关系，而是**分工维度**的差异。一个优秀的业务架构师也同样需要理解基础架构的原理（否则无法设计出可靠的高可用方案）；一个基础架构师也需要理解业务的技术需求（否则会设计出"看起来很厉害但没人用"的中间件）。

### 1.1.2 架构师的四个核心能力

无论你是哪一层的架构师，以下四个能力是通用的：

| 能力 | 描述 | 如何培养 |
|------|------|---------|
| **抽象能力** | 从复杂业务中提炼出通用模式 | 多做领域建模、学习设计模式 |
| **权衡能力** | 在冲突目标中做出折中 | 理解 CAP/性能 vs 可维护性/交付速度 vs 质量 |
| **沟通能力** | 将技术方案翻译成业务语言 | 参与需求评审、写架构决策记录（ADR） |
| **预见能力** | 预测系统未来的瓶颈 | 容量规划、技术债务管理 |

> **跨书对照**：高翔龙《超大流量》从电商大促的角度给出了工程能力的具体实现（Dubbo路由、Sentinel限流、Titan压测），余春龙则从方法论层面构建了架构师的思维框架。前者是"怎么做"，后者是"为什么这样做"。两者互为补充——读完余春龙的"道"再读高翔龙的"术"，才能真正建立架构师的思维体系。

## 1.2 架构的道与术：思维方式比工具更重要

### 1.2.1 何为道，何为术

余春龙在第二章提出了全书最重要的一个框架：**道与术的辩证关系**。

| 维度 | 道 | 术 |
|------|----|-----|
| **定义** | 思维方式、方法论、原则 | 具体技术、工具、框架 |
| **特点** | 稳定、可迁移、不随技术迭代而过时 | 快速迭代、有最佳使用场景 |
| **学习难度** | 高（需要大量实践+反思） | 中（可速成，有文档和教程） |
| **价值** | 决定了你能走多远 | 决定了你当下能做什么 |
| **举例** | CAP理论、分而治之、解耦、抽象 | Dubbo配置、Nginx限流语法、Redis命令 |

**核心观点**：**道是慢变量，术是快变量**。面试官问"用过 Dubbo 吗？"表面在问术，但真正想听的其实是"你理解 RPC 框架的核心原理吗？"——这是道。道决定了你能否在 Dubbo 不能用了的时候（停更、性能不够、业务变化），快速切换到 gRPC 而不需要从零开始。

> **面试视角**："你有用过 Dubbo 吗，它和 gRPC 有什么区别？"——差的回答："我用的 Dubbo，gRPC 没用过"。好的回答："我用的 Dubbo，gRPC 也了解过。它们的核心差异在于序列化标准（Hessian2 vs Protobuf）和传输协议（自定义TCP vs HTTP/2）。如果做 Java 体系内微服务我选 Dubbo，跨语言或 Service Mesh 场景我选 gRPC。其实任何 RPC 框架解决的都是同样的三个问题：序列化、寻址、通信——掌握了这三者，框架切换只是配置变更。"

### 1.2.2 显性问题 vs 隐性问题

余春龙提出了一个非常有洞察力的分类：

| 类型 | 定义 | 表现 | 解决方式 |
|------|------|------|---------|
| **显性问题** | 不解决系统就宕机 | 高并发、高可用、数据一致性 | 分布式拆解、小步快跑、快速迭代 |
| **隐性问题** | 不解决也能运行，但效率越来越低 | 可重用性差、可扩展性差、可维护性差 | 好的架构设计、领域建模、重构 |

**为什么隐性问题比显性问题影响更大？**

- 显性问题有明确后果（宕机、P0 故障）→ 团队会优先投入资源解决
- 隐性问题没有明确后果（"开发慢一点"）→ 永远排不到优先级里
- 但隐性问题是**拖垮技术团队的慢性毒药**——每个新需求都因为糟糕的架构需要额外 3 倍的开发时间，加班成为常态，优秀人才流失
- 显性问题是"急性病"，隐性是"慢性病"。急性病让人害怕，慢性病让人死都不知道怎么死的。

> **跨书对照**：高翔龙全书都在解决"显性问题"——大促流量来了系统崩了怎么办（全链路压测、限流、削峰、多级缓存）。余春龙提醒我们，在解决显性问题的同时不要忽略隐性问题——一个能扛住百万 QPS 但每个新功能要改 50 个文件的系统，最终会死于团队的崩溃，而非流量的崩溃。

# 第2部分 计算机功底

## 1.3 编程语言：精通一门的深层含义

### 1.3.1 为什么架构师需要精通至少一门语言？

余春龙在第三章提出了一个问题："为什么架构师要精通至少一门语言？" 答案不是"因为要写代码"，而是：

1. **语言是理解的载体**：如果你不理解 Java 的 JVM 内存模型，你怎么设计一个 Java 应用的内存配置？如果你不理解 Go 的 Goroutine 调度模型，你怎么评估 Go 服务的并发瓶颈？

2. **语言影响架构选择**：Java 体系和 Go 体系在微服务框架选型、序列化方案、部署模型上有本质差异——不理解语言特性，就无法做出正确的架构决策。

3. **语言是最底层的"道"的载体**：设计模式、SOLID 原则、并发模型——这些"道"最终都是通过语言的"术"来表达的。

**精通的真正含义——三层深度**：

| 层次 | 内容 | 体现 |
|:---:|------|------|
| **语法层** | 会写能运行 | API 调用、熟练使用框架 |
| **原理层** | 理解底层机制 | JVM GC 调优、内存模型、线程模型、编译优化 |
| **哲学层** | 理解设计取舍 | 为什么 Java 不用指针？为什么 Go 没有异常？为什么 Rust 需要所有权？ |

大多数有 3-5 年经验的开发者停留在语法层→原理层的过渡中。真正精通，需要达到哲学层——能站在"语言设计者"的角度思考问题。

> **面试视角**：面试官问"你最擅长什么语言？"——不要只答"Java"。要答："Java。我关注 JVM 层面的内存管理，在工作中做过 GC 调优把 Full GC 频率从每小时 3 次降到每天 1 次；理解 JMM（Java Memory Model，Java 内存模型）的 happens-before 规则，设计了线程安全的数据结构。也了解 Go，它的 CSP（Communicating Sequential Processes，通信顺序进程）并发模型和 Java 的线程+锁模型是两种不同的哲学..."

## 1.4 操作系统：架构师必须深入理解的六个概念

余春龙在第四章选取了六个对架构师最关键的 OS 概念，每一个都直接影响系统架构决策。

### 1.4.1 缓冲 I/O vs 直接 I/O

**核心问题**：一次 `fread(buf, 1MB, fp)` 到底经历了什么？

```
应用程序内存(buf) ←→ 标准C库缓冲区(stdio buffer) ←→ 内核页缓存(Page Cache) ←→ 磁盘
    用户态                                          内核态                      硬件
```

缓冲 I/O（标准 C 库的 `fread`/`fwrite`）在用户态多了一层 stdio buffer。好处：
- 减少系统调用次数（多次小写 → 一次 `write()`）
- 提升吞吐

代价：
- 多一次内存拷贝（stdio buffer → 内核 Page Cache）
- 数据可能滞留在 stdio buffer 中 → 进程崩溃时丢数据

直接 I/O（`open()` + `O_DIRECT`）跳过 Page Cache，直接从磁盘读写。场景：自建缓存的应用（如 MySQL InnoDB、RocksDB），因为已经有了自己的缓存层（Buffer Pool），再用 OS 的 Page Cache 是浪费。

> **架构意义**：为什么 MySQL 的 `innodb_flush_method` 要选 `O_DIRECT`？因为 InnoDB 有 Buffer Pool，不需要 OS 再做一次缓存——让磁盘 I/O 和内存缓存各司其职。

### 1.4.2 零拷贝（Zero Copy）

**核心问题**：Web 服务器从磁盘读取文件发送给用户，数据在内存中拷贝了几次？

```
传统路径（4 次拷贝）：
磁盘 → 内核缓冲区 → 用户缓冲区 → 内核 Socket 缓冲区 → 网卡

sendfile() 优化（2 次拷贝）：
磁盘 → 内核缓冲区 → 网卡（DMA，Direct Memory Access + scatter-gather）
```

`sendfile()` 是 Linux 2.1 引入的系统调用，直接把数据从文件描述符传给 Socket 描述符，完全在**内核态完成**，不经过用户态。对 Web 服务器、文件服务器、Kafka 等大量发送静态数据的场景，零拷贝是吞吐量的关键优化。

> **面试视角**："Kafka 为什么这么快？" → 三点：顺序写磁盘 + Page Cache + `sendfile()` 零拷贝。消息先写入 Page Cache（内存），消费者读取时通过 `sendfile()` 直接从 Page Cache 传给网卡，全过程不经过用户态，不产生额外的拷贝。这也是为什么 Kafka 被称为"磁盘存储、内存速度"。

### 1.4.3 网络 I/O 模型：select/poll/epoll

这是架构师理解"为什么 Nginx 比 Apache 快"的基础。

| 模型 | 原理 | 复杂度 | 并发上限 |
|------|------|:---:|:---:|
| **select** | 遍历所有 fd（文件描述符）检查状态，内核→用户态拷贝整个 fd_set | O(n) | 默认 1024（FD_SETSIZE 宏限制） |
| **poll** | 与 select 类似，但用链表管理 fd，无数量限制 | O(n) | 无硬限制（但效率随 n 线性下降） |
| **epoll** | 事件驱动，只返回就绪的 fd（红黑树 + 就绪链表） | O(1)（就绪事件数） | 数十万 fd |

**epoll 的两种触发模式**：

| 模式 | 行为 | 风险 | 适用 |
|------|------|------|------|
| **LT（Level Triggered，水平触发）** | 缓冲区有数据就持续通知 | 可能重复通知 | 简单、可靠 |
| **ET（Edge Triggered，边沿触发）** | 仅在数据到达时通知一次 | 必须读到 EAGAIN，否则丢事件 | 高性能（Nginx 默认） |

> **跨书对照**：这个主题在高翔龙和唐伟志的书中没有被系统地讲解，但它是理解 Tomcat、Netty、Nginx、Redis 等所有高性能网络程序的基础。一个不了解 epoll 的架构师，看到 Nginx 能撑 10 万并发，只能归结为"它写了 C"，而不明白背后是 epoll + 非阻塞 I/O + 事件驱动架构的组合。

### 1.4.4 Reactor 与 Proactor 模式

**Reactor 模式**（同步 I/O 多路复用）：一个主线程负责 I/O 事件的分发，工作线程负责业务处理。

```
Reactor 线程: epoll_wait() → 检测到 I/O 就绪 → 分发给 Handler
Handler 线程: read()（同步等待数据）→ 处理业务逻辑 → write()
```

代表：Netty（基于 NIO）、Redis（单线程 Reactor）、Nginx（多进程多 Reactor）。

**Proactor 模式**（异步 I/O）：I/O 操作完全由内核完成，完成后通知应用。

```
应用程序: 发起异步读 → 继续做其他事
内核: 等待数据 → 拷贝到用户缓冲区 → 通知应用"读完了"
应用回调: 直接使用已就绪的数据
```

代表：Windows 的 IOCP（I/O Completion Port，I/O 完成端口）、Linux AIO（但因 Linux AIO 实现限制，生产环境仍以 Reactor 为主）。

### 1.4.4a 生产级的服务器编程模型：1+N+MReactor/Proactor 回答的是"事件怎么分发"，但生产级的服务器还需要回答"线程怎么分工"。余春龙在书中提出的 **1+N+M 模型** 是一个优雅的工程框架：```                ┌──────────────┐                │ 1 Listener   │ ← 主线程：accept() 接收新连接                │ (Acceptor)   │                └──────┬───────┘                       │ 分发连接         ┌─────────────┼─────────────┐         ▼             ▼             ▼   ┌──────────┐ ┌──────────┐ ┌──────────┐   │ Worker-1 │ │ Worker-2 │...│ Worker-N │ ← N 个 I/O Worker：epoll_wait 处理网络 I/O   └────┬─────┘ └────┬─────┘ └────┬─────┘        │            │            │        │  耗时业务逻辑交给 M 线程池        ▼            ▼            ▼   ┌──────────────────────────────────────┐   │         M Business Workers           │ ← M 个业务线程：处理具体业务逻辑   │  (ThreadPool / EventLoop blocking)   │    避免阻塞 I/O Worker   └──────────────────────────────────────┘```**为什么 1+N+M 比纯 Reactor 更实用？**纯 Reactor（单线程事件循环）的一个致命缺陷：**如果某个请求的业务逻辑耗时长（如数据库查询），所有其他请求都会被阻塞**。1+N+M 通过将"I/O 处理"和"业务处理"分到不同的线程池中来解决这个问题——I/O Worker 只负责网络事件的分发和编解码，业务处理交给独立的 M 个业务线程。**生产中的对照**：| 系统 | Listener | I/O Worker | Business Worker ||------|:---:|:---:|:---:|| **Netty** | BossGroup(1) | WorkerGroup(N) | 用户自定义线程池(M) || **Tomcat NIO** | Acceptor(1) | Poller(≤2) | Executor线程池(M) || **Nginx** | master(1) | worker(N) | worker自身处理(N=M) |> **关键洞察**：Nginx 的 M=N（Worker 同时做 I/O 和业务，因为它的业务就是静态文件/代理转发，极短），Netty/Tomcat 的 M>N（业务逻辑时间长，必须分离）。选择 1+N+M 的具体参数不是理论决定的，而是**业务处理时长决定的**——业务越重，M 越大。### 1.4.5 进程、线程与协程

| 概念 | 调度者 | 切换成本 | 资源隔离 | 适用场景 |
|------|:---:|:---:|:---:|------|
| **进程** | OS 内核 | 高（页表/TLB 刷新） | 强 | 多核并行计算 |
| **线程** | OS 内核 | 中（仅寄存器/栈） | 弱（共享地址空间） | Java/Go 并发模型 |
| **协程** | 用户态调度器 | 极低（< 100ns） | 无（共享线程） | 高并发 I/O（Go goroutine / Kotlin coroutine） |

> **架构意义**：为什么 Go 语言能轻松撑起百万并发？因为 goroutine 是协程（用户态调度），初始栈只有 2KB，创建开销几乎为零。而 Java 线程是内核线程，创建一个线程约需默认 1MB 栈空间（HotSpot JVM on Linux x64 的 `-Xss` 默认值，可通过 JVM 参数调整），创建 1000 个线程就需要约 1GB 内存。Go 的 G-M-P 调度模型（G=Goroutine、M=Machine即OS线程、P=Processor逻辑处理器——俗称 M:N 模型）是协程思想的工程化实现。

### 1.4.6 无锁编程：内存屏障与 CAS

**内存屏障（Memory Barrier/Fence）**：防止编译器和 CPU 对内存操作的乱序执行。

```c
// 假设两个线程
int flag = 0;
int data = 0;

// 线程1                    线程2
data = 42;                  while (flag == 0) { }
// store barrier ← 关键!      // load barrier ← 关键!
flag = 1;                   print(data);
```

如果没有内存屏障，CPU 或编译器可能重排线程 1 的写顺序（先写 flag 再写 data），导致线程 2 读到 flag==1 但 data==0。内存屏障的代价是**限制硬件优化**——每多一个 barrier，CPU 就少一个乱序执行的机会。

**x86 的 `lock cmpxchg` vs ARM 的 `LDREX/STREX`**：x86 的 `lock` 前缀锁定缓存行（Cache Line），单指令原子完成；ARM 使用 Load-Exclusive/Store-Exclusive 双指令，通过 Exclusive Monitor 检测并发修改。两者的核心差异在于：x86 是硬件自动处理原子性（`lock` 前缀），ARM 需要软件循环重试（`LDREX` → 修改 → `STREX` → 失败则重试）。这是为什么 Java 的 `AtomicInteger` 在不同平台上由 JIT 编译为不同的指令序列——JVM 屏蔽了底层的 ISA（Instruction Set Architecture，指令集架构）差异。
- x86：`lock cmpxchg`，单指令原子
- ARM：`LDREX/STREX`，双指令配合 + Exclusive Monitor

架构师需要理解 CAS 的核心原因：**无锁数据结构（`ConcurrentLinkedQueue`、`Disruptor`、LMAX）的基石**。在高并发场景下，锁竞争是吞吐量的天花板，CAS 是突破这个天花板的关键。

## 1.5 网络协议栈：从 HTTP 1.0 到 QUIC 的演进逻辑

余春龙在第五章将网络协议的发展按照"每一代解决了什么核心问题"来组织，而非简单地罗列协议特性。

### 1.5.1 协议演进的推动力

| 版本 | 核心问题 | 解决方案 | 新问题 |
|------|---------|---------|--------|
| **HTTP/1.0** | 一个请求建立一个连接 | Keep-Alive（复用连接） | 连接不能并发 |
| **HTTP/1.1** | 连接不能并发 | Pipeline（管道化）+ Chunked Transfer | HoL（Head-of-Line，队头阻塞） |
| **HTTP/2** | 队头阻塞 | 二进制分帧 + 多路复用（Stream） | TCP 层面的队头阻塞 |
| **HTTP/3（QUIC）** | TCP 队头阻塞 | 基于 UDP + 独立 Stream | 生态尚未完全成熟（2026年） |

**HTTP/1.1 Pipeline 的根本缺陷——队头阻塞**：

```
发送: Request-1, Request-2, Request-3（管道化发送，一个连接）
响应: Response-1（慢！50ms处理时间）, Response-2, Response-3
        ↑
      Response-2 和 Response-3 必须等待 Response-1 完成后才能返回
      即使它们已经处理完了！
```

HTTP/2 的解决方式：**二进制分帧**——将多个请求/响应拆分为帧（Frame），在同一 TCP 连接上交错发送，每个 Stream 独立，不再互相阻塞。

**HTTP/3（QUIC，Quick UDP Internet Connections）的核心创新**：

- **基于 UDP**：避免 TCP 连接的握手开销（0-RTT 连接建立）
- **独立 Stream**：一个 Stream 丢包不影响其他 Stream（解决 HTTP/2 的 TCP 层队头阻塞）
- **连接迁移**：客户端 IP 变化（WiFi→4G）时不需要重新建立连接（Connection ID 保持不变）

> **架构意义**：为什么 gRPC 选择了 HTTP/2 而不是 HTTP/1.1？因为 gRPC 需要双向流（Bidirectional Streaming）——客户端和服务端可以同时发送多条消息。这在 HTTP/1.1 的请求-响应模型下不可能实现。选协议就是选架构的能力边界。

### 1.5.2 SSL/TLS 握手——安全协议的性能代价

TLS 1.2 **完整握手**需要 2-RTT（开启 Session Resumption 时缩短握手仅需 1-RTT）：

```
Client → Server: ClientHello (支持的加密套件+随机数)
Server → Client: ServerHello + Certificate
Client → Server: ClientKeyExchange (用公钥加密的Pre-Master Secret)  ← 2-RTT
Server → Client: Finished
应用数据开始传输  ← 共消耗 2-RTT + TCP握手 1-RTT = 3-RTT
```

TLS 1.3 优化的核心：**减少 RTT**
- 握手简化为 1-RTT（绝大多数情况）
- 支持 0-RTT 恢复（客户端缓存上一会话的 PSK（Pre-Shared Key），二次访问时在首次握手中直接发送数据——**存在重放攻击风险**，仅对幂等 GET 请求安全，对 POST/PUT 需应用层做重放防护）
- 去掉不安全的加密算法（RC4、DES、MD5等）

> **生产陷阱**：TLS 握手是 Web 服务的一大性能开销。优化方向：(1) 使用 TLS 1.3（减少 1-RTT），(2) 开启 Session Resumption（会话恢复），(3) CDN/反向代理负责 HTTPS 卸载（SSL Termination），内网通信走 HTTP。但注意：内网零信任（Zero Trust）趋势下，内网也需要 mTLS（Mutual TLS，双向认证）。

## 1.6 数据库：从范式到分库分表的演进

### 1.6.1 数据库三范式的适用边界

余春龙对数据库范式的讨论精准地聚焦了一个核心问题：**范式在什么场景下不应该遵守？**

| 范式 | 要求 | 违反的理由 | 违反场景 |
|------|------|-----------|---------|
| **1NF** | 字段不可分 | 存储 JSON 方便查询 | 用户标签、灵活属性 |
| **2NF** | 非主属性完全依赖主键 | 减少 JOIN，提升查询性能 | 订单快照（冗余用户地址） |
| **3NF** | 非主属性不依赖其他非主属性 | 避免多次关联查询 | 大宽表（数据仓库） |

**核心原则**：范式是**数据一致性**的最优解，但不是**查询性能**的最优解。在多数 To-C 互联网场景下（社交、内容、电商浏览），适当违反范式是可接受的（因为一致性可以通过定时对账、MQ 兜底等最终一致性手段补充）；但电商核心交易、支付链路以及对账链路仍须一致性优先。传统金融系统则相反——一致性优先，宁愿慢也不能错。

### 1.6.2 索引优化：从 B+树到覆盖索引

B+树（B-Plus Tree）是 MySQL InnoDB 的默认索引结构：

```
B+树结构：
       [30 | 60]            ← 非叶子节点只存索引值（不存数据）
      /    |    \
[10|20] [40|50] [70|80|90]  ← 叶子节点：双向链表 + 全量数据（聚簇索引）
```

**B+树 vs B树的核心差异**：
- B树的非叶子节点也存数据 → 非叶子节点能存的索引键少 → 树更高 → 查询更深
- B+树的非叶子节点只存索引 → 每个节点能存更多键 → 树更矮 → 查询更快（2-4 层即可覆盖数十亿数据）
- B+树叶子节点是双向链表 → 范围查询（`BETWEEN`, `>`, `<`）极快（不需要回到父节点）

**覆盖索引（Covering Index）**：索引中包含了查询需要的所有字段，不需要回表。

```sql
-- 普通查询：idx_user_id → 找到主键ID → 回表取所有字段
SELECT * FROM t_order WHERE user_id = 123;

-- 覆盖索引查询：idx_user_order(user_id, order_id, status) → 全部命中，无需回表
SELECT order_id, status FROM t_order WHERE user_id = 123;
```

> **生产陷阱**：`SELECT *` 是覆盖索引的死敌。即使索引包含了所有必要字段，`*` 也会强制回表。在分库分表场景下，回表意味着两次跨库查询——第一次通过分片键定位到分区，第二次用主键找到全行。

## 1.7 框架与中间件：为什么需要它们，如何选择它们

### 1.7.1 框架的"控制反转"

余春龙对框架的定义非常精炼：**框架 = 骨架 + 扩展点**。框架通过 IoC（Inversion of Control，控制反转）将程序的控制权从业务代码转移到框架代码中。

```
传统方式：                           框架方式：
main() {                            SpringApplication.run()
    connectDB();                     ↓
    initCache();                     // 框架自动完成：
    startServer();                   // 连接池初始化 → 缓存初始化 → HTTP Server 启动
    // 处理请求...                   // 注册 Controller → 注入 Service → 管理 Bean 生命周期
    stopServer();                    // 开发者只需要写 @Controller / @Service
}
```

**控制反转的本质**：不是"你调用框架"，而是"框架调用你"。你的代码成为框架的一个可插拔组件——框架定义何时调用你、传递什么参数、如何返回结果。

### 1.7.2 框架与中间件的选型原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **够用原则** | 不要为不需要的功能引入重量级组件 | 一个 10 人团队用 K8s 部署 3 个微服务 |
| **社区活性** | 选活跃社区的产品，避免"孤儿项目" | 2018年后仍用 Eureka（已停维护） |
| **技术栈统一** | 避免引入异质技术增加运维成本 | Java 体系内用 Python 写的消息队列 |
| **性能边界明确** | 了解组件的性能极限和适用场景 | 用 ZooKeeper 做大规模注册中心（高翔龙 Ch1 已论证） |
| **可替换性** | 通过接口/抽象层隔离框架依赖 | 直接硬编码 Dubbo API（无法切换 gRPC） |

### 1.7.3 2026 年中间件生态概览

| 领域 | 主流产品 | 备注 |
|------|---------|------|
| **RPC** | Dubbo / gRPC | 同构选 Dubbo，跨语言选 gRPC |
| **注册中心** | Nacos / etcd | Nacos 同时支持 AP（服务发现，Distro 协议）和 CP（配置管理，Raft 协议）；需独立 CP 协调时亦可选 etcd |
| **消息队列** | RocketMQ / Kafka | 交易选 RocketMQ，日志/流选 Kafka |
| **缓存** | Redis Sentinel / Cluster / Caffeine | 高可用选 Redis Sentinel（主从+自动故障转移），分片选 Redis Cluster，本地选 Caffeine |
| **数据库** | MySQL + ShardingSphere / TiDB | 单表大选 ShardingSphere，分布式事务选 TiDB |
| **流控** | Sentinel / Resilience4j | 平台级选 Sentinel，轻量选 Resilience4j |
| **网关** | APISIX / SCG / Envoy | 高性能/HTTP选 APISIX，Spring 体系选 SCG，Service Mesh 数据面选 Envoy |
| **Service Mesh** | Istio + Envoy | 治理下沉到基础设施层的云原生方案 |
| **容器编排** | Kubernetes | 生产必选 K8s；轻量级场景可选 K3s 或 Nomad |

## 本章核心观点总结

1. **架构师有三层：基础架构、中间件、业务系统**。不是等级关系，是分工维度的差异。优秀架构师需要理解所有三层，但专精一层。

2. **道与术不可偏废**：道（方法论）是慢变量，决定了你能走多远；术（具体技术）是快变量，决定了你当下能做什么。用道来学习术，用术来印证道。

3. **显性问题和隐性问题的区别**：高并发、高可用是显性问题（不解决崩），可扩展性、可维护性是隐性问题（不解决拖）。架构师要在解决显性问题的同时，不制造隐性债务。

4. **精通的三个层次**：会写（语法层）→ 懂机制（原理层）→ 明取舍（哲学层）。精通的标志是能站在语言设计者的角度理解"为什么 Java 做这个选择而不是那个"。

5. **操作系统六概念**：缓冲I/O、零拷贝、epoll、Reactor/Proactor、进程/线程/协程、内存屏障/CAS——每一个都直接影响架构决策。不了解 epoll 就无法解释 Nginx 为什么比 Apache 快。

6. **HTTP 协议的演进在解决同一个问题——减少 RTT**：Keep-Alive、Pipeline、复用、0-RTT——每一次演进都在减少从请求到响应的时间。理解这个驱动力的架构师，才能做出正确的协议选型。

7. **范式是数据一致性的最优解，不是查询性能的最优解**。互联网场景下适当违反范式是合理的（冗余字段、大宽表），传统金融系统则相反。

8. **框架选型的核心原则**：够用、社区活、技术栈统一、性能边界明确、可替换。最贵的框架不一定最好——"20 人团队用 K8s 部署 3 个微服务"是过度设计的经典反例。

> **跨书学习建议**：
> - 余春龙的操作系统功底讲解与 C 语言 stage4 系统编程（epoll/sendfile/零拷贝/mmap/协程）深度互补——一个从架构师视角讲解"为什么"，一个从 C 语言实践讲解"怎么写"
> - HTTP 协议演进与高翔龙第3章 MQ 解耦形成对照——HTTP 解决同步请求的效率问题，MQ 解决异步解耦的可靠性问题
> - 框架选型原则与第1章（高翔龙）的注册中心选型一致——ZooKeeper 被淘汰不是因为技术不好，而是因为选错了应用场景
