## 引言：为什么"业务架构"是本书的核心？

我们已解读的 8 本参考书有一个共同特征：**全部是技术架构的书**。它们教你共识算法怎么写、缓存怎么搭、限流怎么配——但没一本告诉你"这个系统应该拆成几个服务""服务之间的边界画在哪""如何让技术服务于业务而不是反过来"。

余春龙的独创性在于——**他把"业务架构"和"技术架构"放在了同一本书里，而且明确告诉你前者比后者更重要**。

> 技术架构错了好改（换个中间件、加层缓存），业务架构错了——边界画错、模型建错——改的成本是推翻重来。

## Ch13 业务意识：架构师为什么必须懂业务？

### 13.1 产品经理 vs 需求分析师 vs 架构师

| 角色 | 关注点 | 产出 | 典型问题 |
|------|--------|------|---------|
| 产品经理 | 用户价值、商业目标 | PRD、用户故事 | "用户为什么要用这个功能？" |
| 需求分析师 | 功能规格 | 需求规格说明书 | "这个功能具体怎么交互？" |
| **业务架构师** | **业务本质、领域边界** | **领域模型、限界上下文** | **"这个业务的本质是什么？边界在哪里？"** |
| 技术架构师 | 技术方案、非功能需求 | 架构设计文档 | "用什么技术栈？怎么扛住并发？" |

**关键区分**：产品经理想的是"做什么"，架构师要想的是"什么是这个业务的本质"——后者比前者更深一层。产品经理可以说"用户需要一个下单功能"，架构师要想的是"下单是一个动作还是一个状态迁移？从哪个状态到哪个状态？涉及哪些领域对象？"

### 13.2 什么叫一个"业务"？

余春龙的定义：**一个"业务"是一组具有内聚性的活动，向特定利益相关者交付价值。**

拆解这个定义：
- **内聚性**：相关活动聚集在一起，与外部活动的耦合小
- **利益相关者**：不只有用户，还有运营、商家、客服、财务
- **交付价值**：不是交付功能，是交付价值——功能是手段，价值是目的

**一个经典误区**：把"功能列表"当"业务"。你列了 100 个功能点，但如果你说不清楚这 100 个功能点如何协同完成一个完整的业务流程——那你就还没理解这个业务。

### 13.3 "业务架构"的双重含义

| 含义 | 内容 | 产出 |
|------|------|------|
| **业务自身的架构** | 业务流程、业务规则、业务角色 | 业务流程图、用例图、利益相关者地图 |
| **支持业务的技术架构** | 服务拆分、数据模型、接口设计 | 领域模型、限界上下文、微服务拓扑 |

余春龙的书名就是"技术架构与业务架构融合"——他要讲的是**如何从业务自身的架构推导出技术的架构**，而不是凭空画一个技术架构图。

## Ch14 业务架构思维：九个思维工具

余春龙提出了九种业务架构思维，每一种都是"道"的层面：

### 14.1 "伪"分层

> "不是所有'分层'都是好的分层。如果一层做的事情和另一层完全重叠，那就是'伪分层'。"

经典的反例：Controller → Service → ServiceImpl → DAO。这种"分层"只是一种编码惯例，不是真正的架构分层。真正的分层意味着**每一层有独立的抽象级别和职责边界**。

DDD 的四层架构就是一个好的分层：

```
接口层（用户界面）→ 应用层（用例编排）→ 领域层（核心业务逻辑）→ 基础设施层（技术支撑）
```

### 14.2 边界思维

> "架构的本质是在画边界——把边界内的复杂度控制住，边界外的交给别人。"

判断边界是否合理的三问：
1. **内聚性**：边界内的东西是不是经常一起变化？
2. **耦合度**：跨边界的交互是不是最少？
3. **独立部署**：能不能独立部署这个边界内的东西？

这就是 DDD 中**限界上下文（Bounded Context）**的核心思想——不是按技术分层，而是按业务含义分上下文。同一个"用户"，在"订单上下文"里是买家，在"商品上下文"里是浏览者，在"营销上下文"里是受众——**同一个词在不同上下文里有不同含义**。

### 14.3 系统化思维

> "不能割裂地看问题。一个改动在 A 模块是对的，在 B 模块可能引发连锁反应。"

三层反问法：
1. 这个改动在**当前上下文**里对不对？
2. 它影响的**上游和下游**有哪些？
3. 它对**整个系统的长期演化**有什么影响？

### 14.4 利益相关者分析

> "你的系统不只是给用户用的。还有运营、客服、财务、风控——他们的需求往往被忽略，但他们的投诉往往是最大的。"

| 利益相关者 | 对系统的核心诉求 |
|-----------|----------------|
| C 端用户 | 快、稳、好用 |
| 运营/BD | 灵活配置，不要每个活动都找研发 |
| 客服 | 能查订单、能退款、有完整日志 |
| 财务 | 钱不能错、账要对平 |
| 风控/合规 | 审计日志、权限隔离、数据脱敏 |

**架构师的职责**：在技术方案中为每一个利益相关者留出接口和通路。

### 14.5 非功能性需求（以终为始）

> "性能、安全、可用性——这些不是'锦上添花'，而是'入门条件'。以终为始，从系统最终运行在什么环境下倒推架构设计。"

| 非功能维度 | 架构启示 |
|-----------|---------|
| 性能 | 缓存策略、异步化、数据库分片 |
| 可用性 | 冗余、故障切换、降级方案 |
| 安全 | 鉴权、加密、审计 |
| 可扩展 | 接口设计、插件化、业务配置化 |
| 可维护 | 日志、监控、调用链 |

### 14.6 架构视图（4+1 视图）

余春龙引用了业界经典的架构视图方法论：

| 视图 | 回答什么问题 | 受众 |
|------|------------|------|
| **逻辑视图** | 系统有哪些功能组件？ | 开发人员 |
| **进程视图** | 系统运行时怎么协作？ | 集成/运维 |
| **开发视图** | 代码怎么组织？ | 开发人员 |
| **物理视图** | 部署在哪些机器上？ | 运维/DBA |
| **场景视图(+1)** | 关键场景怎么走？ | 所有利益相关者 |

**核心原则**：不同的受众看不同的视图，**没有一个视图能展示架构的全貌**。

### 14.7 抽象

> "在不丢失关键信息的前提下，忽略不重要的细节。"

抽象的三个层次：
1. **数据抽象**：把"手机号、邮箱、微信"抽象为"联系方式"
2. **流程抽象**：把"下单、退款、换货"抽象为"订单状态机"
3. **架构抽象**：把"Nginx→Gateway→Service→MQ→DB"抽象为"接入→编排→处理→异步→持久化"

### 14.8 建模

> "模型是对现实的简化，用来回答特定的问题。"

好的模型三标准：
1. **准确**：反映真实业务规则
2. **完整**：涵盖所有必要的概念和关系
3. **可执行**：能直接映射到代码和数据库

### 14.9 正交分解

> "把一个复杂问题分解为几个互不重叠的子问题。"

这也是微服务拆分的理论基础——**如果两个服务的职责可以清晰分开、不相互重叠，那它们就是正交的，应该拆开。**

**检验正交性的方法**：问"修改 A 的需求会导致修改 B 的代码吗？" 如果答案是"从来不会"，那 A 和 B 就是正交的。如果答案是"经常"，那它们的边界画错了。

**反例**：把"订单创建"和"库存扣减"放在同一个微服务——修改库存规则（如加预售库存）必然要改订单服务的代码，这不是正交的，应该拆开。

## Ch15 技术架构与业务架构的融合

### 15.1 为什么"领域驱动"？

> "因为业务的复杂性不在技术，而在业务本身。"

DDD 的核心不是那些战术模式（Entity、ValueObject、Repository），而是**战略设计**——用**限界上下文**划分业务边界，用**上下文映射**定义上下文之间的关系。

**为什么 DDD 和微服务是天作之合？**

| DDD 概念 | 微服务对应 |
|---------|-----------|
| 限界上下文 | 一个微服务 |
| 聚合根 | 微服务内的核心实体，事务边界 |
| 领域事件 | 微服务之间的异步消息 |
| 上下文映射 | 微服务之间的调用/消息关系 |
| 反腐层 | 调用外部服务时的适配层 |

### 15.2 "业务流程"不等于"系统流程"

这是余春龙最重要的洞察之一：

> "用户看到的业务流程是一件事，系统内部的处理流程是另一件事。"

**例子**：用户"下单"这件事。

```
用户视角（业务流程）：
选商品 → 填地址 → 确认订单 → 支付 → 等待收货

系统视角（系统流程）：
库存校验 → 价格计算 → 优惠匹配 → 生成订单 → 扣库存 → 
  写订单库 → 发 MQ → 异步通知物流 → 更新缓存 → 记录埋点
```

**架构师的翻译工作**：把"用户语言"翻译成"系统语言"，同时保证翻译不丢失业务含义。这就是为什么 DDD 强调**统一语言（Ubiquitous Language）**——业务和技术必须使用同一套语言。

### 15.3 为何很难设计一个好的领域模型？

**三个根本原因**：

1. **业务专家和开发人员的语言不同**：业务说"客户等级"，开发写成 `user_level`——翻译过程中信息丢失
2. **业务规则分散在代码各处**：`if vip` 写在 Controller 里、`if (amount > 1000)` 写在 Service 里——没有集中的领域逻辑
3. **技术框架绑架了业务模型**：用 JPA/Hibernate 的 `@Entity` 直接映射表结构，表结构决定了模型结构，而不是业务决定了模型结构

**解法**：
- 先建模，后建表——让业务概念决定模型，模型再决定表结构
- 领域层的代码不应该依赖任何框架（Spring、Hibernate）——只依赖纯 Java 对象
- 用 DDD 的**聚合**来保证事务边界内的一致性

### 15.4 DDD 战术模式速览

| 模式 | 一句话 | 例子 |
|------|--------|------|
| **Entity（实体）** | 有唯一标识的对象，生命周期可变 | Order（订单号是标识，状态可变） |
| **Value Object（值对象）** | 没有唯一标识，不可变 | Address（地址改了就是新地址） |
| **Aggregate（聚合）** | 一组关联对象的集合，通过聚合根访问 | Order（聚合根）+ OrderItem（实体）+ Address（值对象） |
| **Domain Event（领域事件）** | 领域内发生的重要事情 | OrderPlaced（订单已下单） |
| **Repository（仓库）** | 聚合的持久化抽象 | OrderRepository.save(order) |
| **Domain Service（领域服务）** | 不属于任何实体的领域逻辑 | PricingService.calculate(order) |

### 15.5 CQRS：读写分离在业务架构层的体现

```
Command Model（写模型）          Query Model（读模型）
  ↓ 领域模型、事务一致性              ↓ 宽表、缓存、搜索索引
OrderService.create()              OrderReadService.find()
```

CQRS 的本质：**写操作需要强一致性和完整的业务规则校验，读操作只需要快速返回数据**——两者使用不同的数据模型和存储策略。这就是高翔龙 Ch5 中讲的"订单冗余表按 buyer_id 和 seller_id 双写"的理论基础。

**CQRS 的进阶：Event Sourcing（事件溯源）**

CQRS 常和 Event Sourcing 搭配使用——不存储当前状态，而是存储**所有导致状态变化的事件序列**：

```
传统：Order { id=123, status="paid", amount=100 }
Event Sourcing: [OrderCreated→OrderPaid→OrderShipped]
                    ↓ 重放事件序列
                Order { id=123, status="shipped", amount=100 }
```

**好处**：天然审计日志、可以回溯任意时刻的状态、Bug 修复后重放事件即可修复数据。**代价**：事件版本管理复杂、查询需要建立物化视图（读模型）、事件数量会无限增长需要快照。

### 15.6 状态机：最被低估的架构模式

> "80% 的业务系统，本质上都是一个状态机。"

| 业务 | 状态流转 |
|------|---------|
| 订单 | 待支付 → 已支付 → 已发货 → 已完成 → 已取消 |
| 退款 | 申请 → 审核中 → 已退款 → 已拒绝 |
| 审批 | 草稿 → 审批中 → 已通过/已驳回 |
| 库存 | 可用 → 锁定 → 已扣减 → 已回补 |

**为什么状态机模式重要？**
- 状态转移明确了"什么操作在什么状态下允许"
- 杜绝了 `if status == xxx` 散落在代码各处的混乱
- 天然支持事件溯源（Event Sourcing）

## 面试高频题

**Q1：DDD 的限界上下文和微服务的关系是什么？**

DDD 的限界上下文是"业务语言的边界"，微服务是"技术部署的边界"。理论上**一个限界上下文对应一个微服务**——但实践中，"对应"不一定是 1:1：一个大的限界上下文可能需要拆成多个微服务（比如订单上下文拆成订单服务和结算服务），几个小的限界上下文有时也需要合并在一个服务里（团队组织约束）。关键是：限界上下文回答了"为什么这么拆"，而不是"拆多细"。

> **追问**："如果用 DDD 来设计一个电商系统，你如何划分限界上下文？"
>
> 核心上下文：商品、订单、支付、用户、营销、物流、库存。支持上下文：评价、推荐、搜索。通用上下文：权限、通知。判断标准：两个上下文之间如果"同样的词有不同含义"（比如商品上下文里的"价格"是指原价，营销上下文里的"价格"是活动价）——那它们就应该是独立的上下文。

**Q2："业务流程"和"系统流程"的区别到底在哪？举一个具体的反例。**

业务流程是用户视角的、"应该发生什么"。系统流程是代码视角的、"实际上怎么做到的"。反例：用户看到的"立即退款"是一个动作，系统内部却要经历：校验退款条件→解冻金额→生成退款单→调用支付网关→写退款流水→发退款通知→更新订单状态——7 个步骤，任何一个失败都要回滚。架构师的职责是让这 7 个步骤对外表现为"一个业务动作"。

> **追问**："这 7 个步骤中，哪些可以异步，哪些必须同步？"
>
> 校验退款条件、调用支付网关——必须同步（失败则退款失败）。写退款流水、发退款通知——可以异步（成功后补发，不影响退款结果）。这就是 CQRS 和 Saga 模式的实践：核心路径同步 + 附加路径异步。

**Q3：如何设计一个好的聚合？DDD 聚合设计的四个原则。**

聚合是 DDD 面试最高频的考点。四个原则：
1. **在聚合边界内保护业务不变量（Invariant）**——比如"订单总额 = 所有订单项的金额总和"，这条规则必须在同一个聚合内保证
2. **设计小聚合**——一个聚合只包含一个聚合根和它直接关联的最小实体集合。大聚合拖慢事务、增加锁竞争
3. **通过 ID 引用其他聚合，而非对象引用**——`order.setUserId(userId)` 而不是 `order.setUser(user)`。ID 引用降低了跨聚合的耦合
4. **在聚合边界内使用强一致性，跨聚合使用最终一致性**——聚合内可以靠数据库事务，聚合间靠领域事件 + MQ

> **追问**："订单和订单项是同一个聚合吗？用户和订单是同一个聚合吗？"
>
> 订单和订单项是同一个聚合——因为"订单总额 = 各订单项之和"这个不变量必须在事务内保证。用户和订单是两个独立的聚合——用户状态的变化（如被封号）不应该阻塞订单的创建，订单的创建也不应该修改用户的数据。它们之间通过 UserId（ID 引用）关联即可。

## 业务架构的常见陷阱

技术架构的陷阱会宕机，业务架构的陷阱不会——它会让你半年后才发现"这个系统没法加新功能了"。

| # | 陷阱 | 后果 | 识别信号 |
|---|------|------|---------|
| 1 | **贫血模型**：Service 里全是业务逻辑，Entity 只剩 getter/setter | 同样的校验逻辑散落在 10 个 Service 里，改一个规则要翻遍所有代码 | "我要加一个下单校验，改了几个文件？" 如果 >3 个，就是贫血模型 |
| 2 | **错误的上下文划分**：把"商品价格"和"活动价格"放在同一个上下文 | 两个团队频繁冲突，改一个影响另一个 | 同一个字段在不同需求中被反复修改，每次都怕影响另一方 |
| 3 | **按表结构建模而非按业务建模** | 数据库迁移成本巨大，因为所有业务逻辑都直接绑定了表结构 | 需求文档里的"用户等级"在代码里叫 `user_level INT`，没人记得 3 代表什么 |
| 4 | **没有状态机**：`if status == "paid"` 散落各处 | 加一个新状态（如"部分退款"）需要在 20+ 个地方加判断，极易遗漏 | 群里经常出现"这个状态加了吗？那个地方改了吗？" |
| 5 | **过度 DDD**：一个日活 1000 的系统，上了聚合、领域事件、Event Sourcing | 代码复杂度远超业务复杂度，3 人团队维护一套 DDD 架构比业务代码还重 | 新增一个 CRUD 功能需要创建 Entity→VO→Repository→DomainService→ApplicationService→Controller 六个文件 |

**核心教训**：DDD 不是银弹。Eric Evans 明确说过——**DDD 适用于"复杂业务领域"**。如果你的业务就是简单 CRUD，DDD 是过度设计；如果你的业务复杂到"业务专家都说不清楚规则"，DDD 才是正解。

## 本章小结

余春龙 Part 4 的价值不在技术细节，而在**思维框架**。他告诉你的不是"微服务怎么拆"的步骤，而是"为什么这么拆"的方法论——这就是"道"。

> 技术架构告诉你"怎么做"，业务架构告诉你"为什么这么做"——前者是成本中心，后者是价值中心。
