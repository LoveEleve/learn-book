## 2.1 系统设计：从模型到架构的映射

### 2.1.1 为什么系统设计是"翻译"而非"创造"？

郭进在第四章提出了一个打破常见认知的观点：**好的系统设计不是从零"创造"出来的——它是从第1章的领域模型中"翻译"出来的。** 

这意味着：在你开始画架构图之前，领域模型已经定义了什么模块做什么事。系统设计的核心工作不是"设计功能"，而是**为领域模型中的每个概念分配计算资源、通信方式和物理位置**。

```
领域模型（第1章）           →        系统设计（第2章）
┌─────────────────┐                ┌─────────────────────┐
│ Order (领域实体)  │               │ OrderService (微服务) │
│ - create()       │               │ - POST /orders       │
│ - pay()          │     翻译      │ - PUT /orders/:id/pay │
│ - ship()         │  ───────→    │ - PUT /orders/:id/ship│
│ - cancel()       │               │ - DELETE /orders/:id  │
│ -状态机封装       │               │ - MySQL Orders库      │
└─────────────────┘                └─────────────────────┘
```

**如果跳过领域建模直接做系统设计会发生什么？**

你会根据"功能列表"来划分模块——产品说要做"登录注册"，你就创建一个 `UserController`；产品说要做"下单"，你就创建一个 `OrderController`。这种方式的致命缺陷：**模块划分跟随的是"产品需求"，而不是"业务概念"**。当需求变化时（如"登录注册"变成了"OAuth统一认证"），整个模块的边界需要重新划分，而基于领域模型的模块划分不受单一需求变化的影响。

### 2.1.2 系统设计的三个核心决策

| 决策 | 问题 | 选项 | 决策依据 |
|------|------|------|---------|
| **模块划分** | 系统拆成几个模块？每个模块负责什么？ | 单体/垂直拆分/微服务 | 领域模型中的聚合根和限界上下文 |
| **接口设计** | 模块之间怎么通信？ | REST/gRPC/MQ/共享数据库 | 同步/异步、实时/延迟、强一致/最终一致 |
| **技术选型** | 用什么技术实现？ | Spring Boot/Go/Node.js | 团队能力、生态成熟度、性能要求 |

**为什么模块划分是系统设计的第一步？**

因为模块划分决定了后续所有决策的边界——接口设计是在模块之间定义通信协议，技术选型是为每个模块选择合适的工具。如果模块划分不合理（如把支付和物流放在同一个模块里），后续的接口设计和技术选型都会被这种不合理的耦合绑架。

> **跨书对照**：高翔龙第1章从"单机→集群→垂直拆分→服务化→微服务"的演进路径讲解了模块划分的工程实践，余春龙第3章从DDD限界上下文的角度讲解了"怎样正确拆分微服务"。郭进的独特贡献是**将模块划分定位为"系统设计的第一步"**——在高翔龙的框架中，模块划分是"架构演进的一个阶段"；在余春龙的框架中，模块划分是"领域建模的结果"。郭进整合了二者：先建模（余春龙），再设计（郭进），再落地（高翔龙）。

### 2.1.3 接口设计的三个层次

郭进将接口设计分为三个递进的层次：

| 层次 | 内容 | 常见问题 |
|:---:|------|---------|
| **协议层** | 通信协议（HTTP/gRPC/MQ）和数据格式（JSON/Protobuf） | "所有接口都用REST"——不适合异步通知 |
| **语义层** | 接口的业务语义（幂等性、同步/异步、错误码） | "POST /pay 调了两次扣了两次钱"——没有幂等性设计 |
| **演化层** | 接口的版本管理和向后兼容 | "改了返回字段后所有客户端都崩了"——没有版本管理 |

**接口设计的语义层——幂等性的正确理解**：

```java
// 错误：POST 语义 + 非幂等实现
@PostMapping("/orders/{id}/pay")
public Result pay(@PathVariable Long id) {
    // 如果客户端因为超时重试，这个接口被调用两次 → 扣两次钱！(已在高翔龙Ch1详细讨论)
    orderService.pay(id);
    return Result.success();
}

// 正确：使用幂等Token保证最多执行一次
@PostMapping("/orders/{id}/pay")
public Result pay(@PathVariable Long id, @RequestHeader("Idempotent-Key") String idempotentKey) {
    // 1. 检查Redis中是否已处理过这个幂等Key
    if (redis.exists("idempotent:" + idempotentKey)) {
        return Result.success(redis.get("result:" + idempotentKey)); // 返回第一次的结果
    }
    // 2. 执行业务逻辑
    Result result = orderService.pay(id);
    // 3. 记录幂等Key + 结果
    redis.setex("idempotent:" + idempotentKey, 3600, "1");
    redis.setex("result:" + idempotentKey, 3600, JSON.toJSONString(result));
    return result;
}
```

**幂等性的三个层次**：

| 层级 | 机制 | 防线 |
|:---:|------|------|
| L1（协议层） | `Idempotent-Key` HTTP Header + Redis去重 | 5秒内重复请求 |
| L2（业务层） | 数据库唯一约束（订单号UNIQUE KEY） | 5秒外重复请求 |
| L3（对账层） | 定时任务对账 + 人工处理 | 绕过L1/L2的异常 |

## 2.2 数据设计：从实体关系到数据存储

### 2.2.1 为什么数据库设计不能直接从"建表"开始？

郭进在第五章提出了与第1章一脉相承的观点：**数据库设计必须从领域模型推导出来，而不是从"功能列表"推导出来。**

很多工程师做数据设计的方式是：
1. 产品说"做一个用户系统"→创建`user`表
2. 产品说"用户需要关注功能"→创建`follow`表
3. 产品说"用户需要收藏功能"→创建`favorite`表

这个方式产生的数据库结构是**对产品需求的直接映射**，而不是对业务概念的映射。当产品说"把关注和收藏合并为'互动关系'"时，你面临的是两个独立的表需要合并的重构。

郭进的正确方式是：
1. 从领域模型出发：`用户`、`关注关系`、`收藏`是三个不同的领域概念
2. 分析它们的相似性："关注关系"和"收藏"在本质上都是"用户A与资源B的关系" → 可以抽象为`user_relationship`表（type字段区分关注/收藏）
3. 分析它们的差异性："收藏"需要冗余存储资源的快照信息（收藏夹展示），"关注"不需要 → 如果差异不可调和，才分表

### 2.2.2 从领域模型到数据库设计的三个步骤

| 步骤 | 做什么 | 输出 |
|:---:|------|------|
| **实体→表** | 领域模型中的每个聚合根映射为一张表 | `Order`实体→`t_order`表 |
| **值对象→字段** | 聚合根的值对象映射为表的字段 | `Money totalAmount`→`amount DECIMAL(10,2)` |
| **关联→外键/冗余/聚合** | 实体间的关联关系映射为数据库的关联方式 | `Order.userId`→外键约束 |

**关联关系的三种映射策略**：

| 策略 | 做法 | 适用场景 | 代价 |
|------|------|---------|------|
| **外键** | `FOREIGN KEY (user_id) REFERENCES t_user(id)` | 强数据一致性要求 | 跨库分表时不可用 |
| **冗余存储** | 把关联实体的关键字段冗余到主表中 | 读多写少，关联查询频繁 | 数据一致性问题（需兜底） |
| **应用层聚合** | 不存关联，在应用代码中分别查两张表再合并 | 关联关系稀松、对延迟不敏感 | 增加代码复杂度 |

> **跨书对照**：《性能之道》第2章从"查询性能 vs 数据一致性"的角度讨论了冗余存储的取舍——冗余存储加速了查询但引入了一致性问题，需要定时对账兜底。郭进从"领域模型的关联关系如何翻译到数据库"的角度出发，给出了更系统化的三步法。两者是同一个决策的不同视角。

### 2.2.3 索引设计的三个反直觉原则

郭进对索引设计提出了三个容易违反的原则：

**原则一：索引不是越多越好**

每个索引都有代价——写入时需要更新所有索引（索引数量 × 写入次数），占用额外的磁盘空间，增加查询优化器的决策复杂度。一个常见的反模式：

```sql
-- 反模式：为所有查询字段都建索引
CREATE INDEX idx_user_id ON t_order(user_id);
CREATE INDEX idx_status ON t_order(status);
CREATE INDEX idx_created_at ON t_order(created_at);
CREATE INDEX idx_user_status ON t_order(user_id, status);
CREATE INDEX idx_user_time ON t_order(user_id, created_at);
-- 5个索引 → 每次INSERT都要更新5个索引！
```

**正确的做法**：分析最高频的查询模式，只为前3-5个最频繁的查询建立联合索引。其他的偶尔查询可以用慢查询日志监控，如果发现某个查询频率上升再追加索引。

**原则二：联合索引的列顺序等于查询的过滤精细度**

```sql
-- 假设最频繁的查询：
SELECT * FROM t_order WHERE user_id = ? AND status = ? ORDER BY created_at DESC LIMIT 20;

-- 正确的联合索引：最精确的过滤条件在前，排序字段在后
CREATE INDEX idx_user_status_time ON t_order(user_id, status, created_at);
-- user_id 等值 → status 等值 → created_at 排序 — 索引覆盖全查询！
```

**原则三：覆盖索引比回表快一个数量级**

```sql
-- 查询A：需要回表
SELECT order_id, amount FROM t_order WHERE user_id = 123;
-- 索引 (user_id) → 找到主键 → 回表取 order_id, amount（2次I/O）

-- 查询B：覆盖索引
SELECT order_id, amount FROM t_order WHERE user_id = 123;
-- 索引 (user_id, order_id, amount) → 索引中就有所有字段（1次I/O）
-- 但如果把amount也加到索引里，索引变大→其他查询的扫描变慢——trade-off!
```

> **生产陷阱**：在MySQL中，`EXPLAIN`结果的`Extra`字段如果显示`Using index`，说明使用了覆盖索引（最快）；如果显示`Using index condition`，说明使用了ICP（Index Condition Pushdown，索引条件下推——次快）；如果显示`NULL`，说明只是普通索引查找（需要回表）。

## 2.3 非功能性设计：性能、可用性与安全性

### 2.3.1 为什么非功能性需求容易被忽略？

郭进指出，非功能性需求被忽略的根本原因是：**功能性需求有明确的产品文档，非功能性需求没有。** 产品经理会说"做一个秒杀功能"，但不会说"秒杀功能的P99延迟<200ms，支持5000QPS/秒的写入，数据一致性为最终一致"。这些非功能性需求需要**服务端工程师自己提出、定义和量化**。

**非功能性需求没有标准答案**——"P99<200ms"对电商秒杀是一个合理的目标，对日志分析系统则完全没必要（日志分析批处理，延迟10分钟都可以）。非功能性需求的正确值=**业务特征×成本约束×技术可行性**的折衷。

### 2.3.2 性能设计：从目标到实现

郭进将性能设计拆解为"目标设定→瓶颈预判→方案选择"三个步骤：

**步骤一：目标设定——SLA倒推法**

```
用户体验目标：页面加载 < 2秒
→ 服务端处理时间预算： < 100ms（前端渲染+网络=1900ms预算）
→ 按照处理环节拆分预算：
   - API网关：5ms
   - 业务逻辑：20ms
   - RPC调用：50ms
   - 数据库查询：20ms
   - 序列化/反序列化：5ms
总预算：100ms
```

这个拆分让每个环节都有一个明确的性能目标，而不是笼统的"系统要快"。

**步骤二：瓶颈预判**

| 环节 | 典型瓶颈 | 优化方向 |
|------|---------|---------|
| API网关 | 规则匹配O(n) | 用Trie树匹配URL规则（第1.2节的DFA同理） |
| 业务逻辑 | 复杂计算 | 异步化、Cache结果、算法优化 |
| RPC调用 | 序列化开销、网络延迟 | Protobuf替代JSON、合并调用、连接池复用 |
| 数据库 | 慢查询、行锁竞争 | 索引优化、读写分离、分库分表 |

**步骤三：方案选择——性能优化决策矩阵**

| 方案 | 成本 | 效果 | 风险 |
|------|:---:|:---:|------|
| 加索引 | 低（ALTER TABLE） | SQL层：2-100x | 写入性能下降 |
| 加缓存 | 中（Redis集群） | 读请求：10-100x | 缓存一致性 |
| 异步化 | 中（MQ+消费者） | 削峰：5-50x | 数据延迟 |
| 分库分表 | 高（数据迁移） | 写入：N倍 | 跨库查询复杂 |

> **跨书对照**：《性能之道》第1章的点线面体方法论是性能优化的"在哪里"（在哪个维度优化），高翔龙第2-5章是"怎么做"（具体的技术实现），郭进的SLA倒推法是"目标在哪"（优化到什么程度算达标）。三者组合形成完整的性能设计链路：SLA倒推（目标）→点线面体分析（定位）→具体方案（实现）。

### 2.3.3 可用性设计：从故障分级到容错机制

郭进将可用性设计分为两步：**故障分级**和**对应的容错机制**。

**故障分级矩阵**：

| 级别 | 描述 | 响应时间 | 容错机制 |
|:---:|------|:---:|------|
| **P0（致命）** | 核心交易链路不可用 | <5分钟 | 自动故障转移（热备+MHA/Orchestrator） |
| **P1（严重）** | 部分用户受影响 | <30分钟 | 自动摘除故障节点（Nacos健康检查） |
| **P2（一般）** | 非核心功能异常 | <4小时 | 手动恢复 |
| **P3（轻微）** | 仅影响个别用户 | <24小时 | 下次迭代修复 |

**容错机制的分层部署**：

```
接入层：限流 → Nginx令牌桶 → 超出阈值直接拒绝（保护下游）
    ↓
应用层：熔断 → Sentinel → 下游错误率超50% → 熔断→快速失败
    ↓       降级 → 返回兜底数据（如缓存中的旧数据）
数据层：主从切换 → 主库故障 → Semi-Sync Slave自动提升为Master
    ↓       定时对账 → 每天凌晨对比主从数据 → 发现不一致→告警
```

### 2.3.4 安全性设计：从OWASP到API安全

郭进将安全性设计分为三个防御环：

| 环 | 威胁 | 防护 |
|:---:|------|------|
| **外层（传输层）** | 网络窃听、中间人攻击 | HTTPS + TLS 1.3、HSTS |
| **中层（认证授权）** | 未授权访问、越权操作 | JWT/OAuth2.0、RBAC |
| **内层（输入校验）** | SQL注入、XSS、CSRF | 参数校验、SQL参数化、CORS |

**生产陷阱——API安全中的常见漏洞**：

```java
// 漏洞：水平越权——用户A可以查看用户B的订单
@GetMapping("/orders/{orderId}")
public Order getOrder(@PathVariable Long orderId) {
    // ❌ 没有校验这个订单是否属于当前登录用户！
    return orderService.findById(orderId);
}

// 修复：从Token中提取当前用户ID，校验归属关系
@GetMapping("/orders/{orderId}")
public Order getOrder(@PathVariable Long orderId, @AuthenticationPrincipal User user) {
    Order order = orderService.findById(orderId);
    if (!order.getUserId().equals(user.getId())) {
        throw new AccessDeniedException("无权访问此订单");
    }
    return order;
}
```

> **面试视角**："你们系统的安全是怎么做的？"——不要只说"用了Spring Security"。要从三个层次回答：(1) 传输层——TLS 1.3 + HSTS强制HTTPS；(2) 认证授权层——JWT+RBAC，每个请求校验Token有效性和权限；(3) 业务层——水平越权校验（每查一个资源都验证归属关系）、SQL参数化（绝不用字符串拼接SQL）。

## 2.4 本章核心观点总结

1. **系统设计是"翻译"**：从领域模型（第1章）映射到系统架构——模块划分来自聚合根和限界上下文，接口设计来自实体的行为方法。

2. **接口设计的三个层次**：协议层（HTTP/gRPC）、语义层（幂等性/错误码）、演化层（版本管理）。大多数人只关注协议层，语义层的缺失是生产事故的主要原因。

3. **数据设计三步法**：实体→表、值对象→字段、关联→外键/冗余/聚合。索引设计遵循"不是越多越好、联合索引列顺序=过滤精细度、覆盖索引比回表快一个数量级"。

4. **非功能性需求的代价**：需要服务端工程师自己提出和量化——用SLA倒推法设定性能目标，用故障分级矩阵选择容错机制，用三层防御环设计安全体系。

5. **存储架构演进是不可逆的**：单机→读写分离→垂直分库→水平分表，每一步解决上一阶段的瓶颈，同时引入新的复杂度。分库分表不是"要不要做"，而是"什么时候做"。

6. **资损防控是电商系统最重要的非功能性需求**：可用性故障导致"暂时不可用"，资损故障导致"你在赔钱"。事前预防（幂等+校验+精度）+事中监控（实时对账+阈值告警）+事后止损（冻结+冲正+赔付）三部曲缺一不可。

7. **安全性解释必须深入原理**：SQL注入不是"过滤危险字符"——PreparedStatement在查询编译阶段将SQL结构与参数分离；XSS防御的本质是确保用户输入被渲染为"文本"而非"HTML代码"；CSRF防御的核心是浏览器会自动附上Cookie。

### 本章面试高频题

**Q1: 什么是战术编程？为什么它比需求变更更危险？**

> **面试官意图**：考察候选人是否有"从编码决策到长期维护成本"的系统思维——不是只会实现需求。

**回答要点**：
- 战术编程：每次编码只考虑"当前功能怎么快速实现"，不考虑长期可维护性
- 三大特征：复制粘贴（类似逻辑重复出现）、全局状态（状态散落无法追踪）、隐式耦合（改A模块B模块挂）
- 比需求变更更危险的原因：需求变更至少是"明的"——你知道要改什么。战术编程是"暗的"——你以为没改东西，实际已经埋了雷

> **追问到第二层**："你怎么说服团队不要做战术编程？"→ 用数据说话：计算技术债务的复利成本。当前功能战术实现省2小时→但导致3个月后5个相关功能各多花2小时调试→5×2-2=净亏8小时。把成本算清楚，比讲道理更有效。

**Q2: 数据库设计为什么不能直接从"建表"开始？CDM→LDM→PDM的顺序为什么不能颠倒？**

> **面试官意图**：考察数据建模的系统方法论。

**回答要点**：
- 直接从"建表"开始=表结构是对功能列表的映射，不是对业务概念的映射
- CDM（概念数据模型）→LDM（逻辑数据模型）→PDM（物理数据模型）的顺序不能颠倒的原因是：每一层是在上一层基础上的"不可逆抽象跳跃"。CDM定义"业务中有哪些核心概念"（与数据库无关），LDM定义"这些概念的数据结构"（逻辑上的表结构），PDM定义"在具体数据库中的物理实现"（索引/分区/存储引擎）

> **追问到第二层**："如果项目很紧，是否可以跳过CDM直接做LDM？"→ 可以，但有代价。跳过CDM意味着你放弃了"与产品/业务方对齐业务概念"的机会。当后续发现"订单"这个概念产品方和开发方的理解不一致时，已经在LDM层面写死了→改动的代价远大于一开始就在CDM层面解决。

**Q3: 资损防控的三部曲中，哪一步最重要？为什么？**

> **面试官意图**：考察对"预防>检测>止损"的工程优先级理解。

**回答要点**：
- 最重要的永远是第一步：事前预防。因为一旦资损发生，钱已经损失了。第二步和第三步只能减少损失或止损，不能挽回已发生的损失
- 幂等性是事前预防中最容易被忽略的一项——多扣钱通常不是因为算法错，而是因为同一笔请求处理了两次

> **追问到第二层**："如果幂等性防不住（如数据库唯一约束也没拦住），怎么办？"→ 第二步（事中监控）兜底——实时对账会检测到"对方账户多了钱、自己账户少了同样多的钱→不平账→触发告警→人工确认→第三步止损（冻结+冲正+赔付）。三层防线，一层失守还有下一层。
