## Ch10 在线聊天与直播系统

### 10.1 高并发在线聊天系统

> 从交互设计到集成到性能调优，三个阶段

**业务特征**：
- 消息量：百万级 DAU → 千万级消息/天
- 延迟要求：消息收发 <100ms 端到端
- 在线状态：需要准实时感知用户上下线

**三阶段调优**：

| 阶段 | 核心工作 | 性能关键 |
|------|---------|---------|
| **前期：交互设计** | 定义消息模型、确定推送模式（长轮询 vs WebSocket）、设计离线消息存储 | **WebSocket 长连接比 HTTP 短轮询节省 90% 带宽和 95% 延迟** |
| **中期：集成** | 接入 IM 服务、用户状态管理、消息路由、多端同步 | 消息路由需要**一致性 Hash** 保证同一用户的消息发到同一 IM 节点 |
| **后期：性能调优** | 连接数优化、消息积压处理、冷热数据分离 | 单机 WebSocket 连接数上限取决于文件描述符和内存，C10M 需要内核调优 |

#### WebSocket 连接数优化

```
单个 TCP 连接占用：~4KB 内核缓冲区 × 2（收发）
100 万连接 = 4KB × 2 × 1M ≈ 8GB 内存

内核参数调优：
net.ipv4.tcp_mem          # TCP 内存限制
net.ipv4.ip_local_port_range = 1024 65535  # 端口范围
fs.file-max = 2000000                         # 文件描述符上限
fs.nr_open = 2000000
```

**群消息扩散的优化**：

```
10 万人的群，发一条消息：
  简单方案：WebSocket 遍历 10 万个连接 → 10 万次系统调用 → 几百 ms
  优化方案：用 epoll 的 EPOLLET + sendfile 批量推送，或改用消息队列 → 
           每个用户从收件箱拉取 → 推拉结合
```

### 10.2 高并发直播系统

**业务特征**：
- 并发量：千万级同时在线，峰值流量是平时的 100 倍
- 延迟：直播延迟 1-3s 可接受（基于 HLS/FLV），互动（弹幕/点赞）要求 <100ms
- 数据流：视频流（大带宽）+ 互动流（高 QPS、小数据包）

**三层优化**：

| 层次 | 瓶颈 | 优化手段 |
|------|------|---------|
| **推流端** | 编码性能、上行带宽 | 硬件编码（GPU NVENC）、自适应码率（ABR） |
| **CDN 分发** | 带宽成本、边缘节点覆盖 | 就近回源、P2P 分发（WebRTC）分担带宽 |
| **互动层** | 弹幕风暴、礼物并发 | Redis 排序 + 本地缓存 + 按直播间分片 |

**弹幕风暴处理**：

```
某直播间 100 万人在线，每秒 5 万条弹幕：
  直接推给所有人 = 100W × 5W 次推送 = 不可能
  
  正确做法：
  1. 后端只做"弹幕过滤 + 敏感词审核 + 写入消息队列"（高吞吐）
  2. 前端定时拉取（每秒 2-3 次）最近 N 条弹幕（低压力）
  3. 弹幕不要求 100% 送达——丢几条用户根本感觉不到
```

**直播点赞（类似红包雨）**：

```
Redis 存储：key = live:room:12345:likes, value = 累计点赞数
并发点赞：INCRBY atomic → 单机 10万 QPS
前端展示：每 1-2 秒 GET 一次，不实时——用户只看个数字变化
```

## Ch11 自动驾驶系统的异构计算优化

> 本书最独特的案例——将分布式性能优化方法论应用到物理世界的系统

### 11.1 自动驾驶的性能挑战

自动驾驶是**硬实时系统**——延迟不是体验问题，是安全问题：

| 子系统 | 延迟要求 | 后果 |
|--------|:---:|------|
| **感知**（摄像头/激光雷达） | <20ms | 延迟超过 20ms → 距离误判 1m+（100km/h 下 20ms = 0.56m） |
| **融合**（多传感器数据融合） | <50ms | >50ms → 不同传感器的数据来自不同时刻→融合结果错误 |
| **规划**（路径规划） | <100ms | >100ms → 车辆反应延迟 |
| **控制**（刹车/转向） | <10ms | 这是安全关键——10ms 的延迟在 100km/h 下约 28cm |

### 11.2 异构计算架构

```
CPU（通用计算）
  ↓ 调度 + 逻辑控制
GPU（并行计算）
  ↓ 深度学习推理（目标检测/语义分割），比 CPU 快 50-100 倍
FPGA（低延迟）
  ↓ 传感器数据预处理、信号处理——微秒级响应
DSP（信号处理）
  ↓ 雷达/激光雷达点云处理
```

**关键架构决策**：

| 决策点 | 方案 | 性能影响 |
|--------|------|---------|
| 推理引擎 | TensorRT（NVIDIA）/ OpenVINO（Intel）| 量化（FP32→INT8）延迟降 70%，精度损失 <1% |
| 模型部署 | 多模型并行（检测+分割+跟踪） | GPU 显存管理是关键——显存不足会触发 swap → 延迟暴涨 |
| 通信中间件 | DDS/ROS2/SOME/IP | 零拷贝共享内存 > Unix Socket > TCP |

### 11.3 分布式训练优化

自动驾驶模型需要不断迭代——每天产生 TB 级驾驶数据：

| 优化维度 | 手段 | 收益 |
|---------|------|:---:|
| **数据** | 联邦学习（车端训练、云端聚合） | 带宽节省 90%+（只传梯度不传数据） |
| **通信** | NCCL（GPU 间）、RDMA（跨节点） | 比 TCP 快 10-50 倍 |
| **计算** | 混合精度训练（FP16 + FP32） | 速度翻倍，显存减半 |
| **调度** | 优先级队列——安全关键模型优先训练 | 紧急 Bug 修复 10 分钟上线 |

> **这是 12 本参考书中唯一覆盖 AI 应用优化的章节**

### 12.1 RAG 系统优化

RAG（Retrieval-Augmented Generation，检索增强生成）是当前 LLM 应用最主流架构——先检索相关文档，再让 LLM 基于文档生成回答。

**RAG 的性能瓶颈**：

```
用户问题 → Embedding 模型(100-500ms) → 向量检索(10-50ms)
    → Reranker 重排序(50-200ms) → LLM 生成(1-10s)
                       ↑
                 总延迟 = 嵌入 + 检索 + 重排序 + 生成
```

| 优化点 | 手段 | 延迟降幅 |
|--------|------|:---:|
| **语义路由** | 先判断问题类型（事实查询/推理/闲聊），简单问题跳过大模型 | 50-80%（简单查询秒级返回） |
| **向量检索** | 使用量化索引（IVF + PQ），牺牲 1% 召回换 10 倍速度 | 检索从 50ms→5ms |
| **缓存语义相似结果** | 两个语义相近的问题共享缓存结果 | 20-30% 命中率 |
| **流式输出** | LLM 生成时边生成边返回，用户感知延迟降为第一个 token 的时间 | 首字节 <500ms |

#### 语义路由：分类器不是魔法

```python
# 实际生产中用轻量分类器而非规则判断
from sentence_transformers import CrossEncoder

class QueryRouter:
    def __init__(self):
        self.classifier = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')
        self.labels = ["fact_lookup", "simple_qa", "complex"]
    
    def route(self, query: str) -> str:
        # 将问题与标签做语义匹配，选最匹配标签
        scores = self.classifier.predict([(query, label) for label in self.labels])
        return self.labels[scores.index(max(scores))]
```

#### 语义缓存的更新与淘汰

```python
# 简单方案：LRU + 定期全量重建索引（适合小规模，<10万缓存项）
# 生产方案：分层 — 高频缓存用 Faiss，低频缓存回退到传统 KV

class ProductionSemanticCache:
    def __init__(self, max_items=100000):
        self.hot_cache = SemanticCache()     # Faiss 向量检索（<10万条）
        self.cold_cache = {}                  # 传统 KV（低频）
        self.access_count = Counter()
    
    def evict_if_needed(self):
        if len(self.cache) > self.max_items:
            # 淘汰访问频率最低的 10%
            victims = self.access_count.most_common()[-self.max_items//10:]
            for key, _ in victims:
                del self.cache[key]
```

**语义缓存的致命坑**：Embedding 模型升级（如 BGE-small → BGE-large）后，所有缓存的向量**全部失效**——因为同一个文本的 embedding 变了，cosine similarity 不再匹配。升级 embedding 模型 = 清空整个语义缓存。

### 12.2 Agent 系统优化

Agent 系统比 RAG 更复杂——LLM 不仅要回答问题，还要**调用工具、执行多步推理**：

```
用户："帮我查一下北京的天气，如果明天下雨就帮我设置一个提醒"
  → LLM 计划：1) 调用天气 API  2) 判断是否下雨  3) 调用提醒 API
  → 每一步都需要等待前一步的结果 → 多步延迟叠加
```

| 优化手段 | 说明 | 收益 |
|---------|------|:---:|
| **异步 API 调用** | 用 async/await 将 LLM 调用从同步阻塞改为异步非阻塞 | 吞吐量提升 70%+ |
| **并行工具调用** | 无依赖的工具调用（查天气 + 查日历）并行执行 | 延迟减半 |
| **结构化输出** | 用 Instructor 库强制 LLM 输出 JSON Schema，减少重试和解析失败 | 可靠性提升 30%+ |
| **PII 过滤** | 用 Presidio 在 LLM 调用前过滤个人身份信息 | 安全合规，不牺牲性能 |

#### 异步 API 带来的吞吐提升

```python
# ❌ 同步：每个请求阻塞直到 LLM 返回
for query in queries:
    result = llm.generate(query)  # 阻塞 3s

# ✅ 异步：提交后立即处理下一个
async def process_batch(queries):
    tasks = [llm.agenerate(q) for q in queries]
    return await asyncio.gather(*tasks)

# 100 个请求：同步 300s → 异步 ~10s（取决于并发限制）
```

### 12.3 语义缓存

> 传统缓存用 key 精确匹配，语义缓存用向量相似度匹配

```
传统缓存：query_hash → cached_result
  问题"什么是微服务" → 命中
  问题"微服务是啥" → 未命中（一字之差！）

语义缓存：embedding(query) → 找最相似的缓存项
  问题"什么是微服务" → embedding [0.1, 0.3, ...]
  问题"微服务是啥" → embedding [0.09, 0.31, ...]
  cosine_similarity = 0.98 → 命中！
```

**实现架构**：

```python
class SemanticCache:
    def __init__(self, similarity_threshold=0.92):
        self.vector_index = faiss.IndexFlatIP(768)  # 768 dim embedding
        self.cache = {}
        self.threshold = similarity_threshold
    
    def lookup(self, query_embedding):
        scores, indices = self.vector_index.search(query_embedding, k=1)
        if scores[0] > self.threshold:
            return self.cache[indices[0]]  # 语义命中
        return None  # 未命中
```

**适用场景**：
- 客服系统（大量相似问题："怎么退款" vs "如何申请退款"）
- FAQ 系统
- 文档问答

**不适合**：
- 需要实时数据的查询
- 每次答案都可能不同的创造性问题

## 面试高频题

**Q1：RAG 系统的性能瓶颈在哪？怎么优化？**

四个瓶颈从耗时高到低：1) LLM 生成（1-10s）→ 流式输出 + 语义缓存；2) Embedding 计算（100-500ms）→ 小模型（如 BGE-small）替代大模型 Embedding；3) Reranker 重排序（50-200ms）→ 阈值过滤减少 Reranker 调用量；4) 向量检索（10-50ms）→ 量化索引 IVF+PQ 牺牲 1% 召回换 10 倍速度。

> **追问**："语义缓存和传统缓存的本质区别是什么？"
>
> 传统缓存是**精确匹配**——key 差一个字符就 miss。语义缓存是**相似度匹配**——将问题转为向量，找最相似的已缓存结果。适合客服/FAQ 场景（"怎么退款"和"如何申请退款"在语义上等价），不适合需要个性化/实时性的查询。代价：需要额外存储向量索引 + 计算相似度。

**Q2：自动驾驶系统和互联网系统的性能优化有什么区别？**

根本区别是**实时性**。互联网系统 P99<200ms 就够了，自动驾驶是**硬实时**——感知<20ms、控制<10ms，超时不是体验差是安全事故。技术差异：1) 互联网用 HTTP/gRPC TCP 协议，自动驾驶用 DDS/共享内存等零拷贝协议；2) 互联网用弹性扩容，自动驾驶用**静态资源预留**——GPU/CPU 核心预分配给关键任务；3) 互联网关注"平均吞吐量"，自动驾驶关注**最坏情况延迟**（WCET）。

> **追问**："为什么自动驾驶要用 FPGA 而不是全靠 GPU？"
>
> FPGA 的延迟是**确定性的**——我们知道一个传感器数据预处理必须 < 1ms，GPU 可能更快（并行度更高），但 GPU 有调度抖动（kernel launch overhead + warp scheduling），延迟不可预测。在安全关键场景中，**确定性比平均性能更重要**。
