## Ch3 架构优化：选对架构比优化代码重要 100 倍

> "架构决定了性能的上限，代码优化决定的是下限。"

### 3.1 五种架构的性能对比

| 架构 | 典型 QPS 上限 | 最大瓶颈 | 优化方向 |
|------|:---:|------|---------|
| **单体** | 几千 | 单机资源 + 数据库 | 垂直拆分、读写分离 |
| **SOA** | 1-5 万 | 服务间 RPC 延迟叠加 | 异步化、合并调用 |
| **微服务** | 5-20 万 | 网络开销 × 服务数量 | 服务网格、就近调用 |
| **事件驱动** | 10-50 万 | 消息积压 | 分区、批量、流控 |
| **无服务器** | 弹性伸缩 | 冷启动延迟 | 预热、预留实例 |

**选型铁律**：不是越新的架构性能越好。单体架构在数据量可控时效率最高——没有网络开销。微服务在拆分过度时性能反而更差——100 个服务之间的 RPC 延迟叠加。

### 3.2 微服务十大设计模式的性能影响

| 模式 | 对性能的影响 | 建议 |
|------|------------|------|
| **API 网关** | 聚合请求减少客户端往返 | 网关本身是单点，需要水平扩展 |
| **服务注册** | 订阅模式减少实时查询 | 本地缓存一份服务地址列表 |
| **断路器** | 快速失败保护系统，不浪费连接等超时 | 与限流配合，防止重试风暴 |
| **舱壁** | 线程池隔离防止级联阻塞 | 核心服务用专用线程池 |
| **Saga** | 牺牲强一致性换高吞吐 | 不是所有业务都能接受补偿 |
| **CQRS** | 读写分离，读路径不经过领域模型 | 写路径仍要保证一致性 |
| **事件源** | 追加写比更新快，天然可回溯 | 查询需要物化视图 |
| **绞杀榕** | 渐进式迁移，新旧两套并行有额外开销 | 迁移完成后及时下线旧系统 |

**关联阅读**：余春龙 Ch15（DDD 与微服务融合）、高翔龙 Ch1（服务化架构）。

### 3.3 跨境电商云服务架构优化案例

> 本书 Ch3 的独家案例

**场景**：跨境电商，国内用户访问海外商品库。原有架构：国内 WebServer → 直接连海外数据库。单次查询 RTT 200ms+。

**优化方案**：
1. **静态数据**（商品信息、类目）→ 国内 Redis 缓存，定时同步
2. **动态数据**（库存、价格）→ 国内 MySQL 只读副本，通过专线同步
3. **搜索** → 国内 ES 集群，商品上下架时异步同步索引

**优化结果**：P99 从 800ms 降到 120ms，跨境专线带宽使用率从 80% 降到 20%。

**核心方法论**：**数据前置**——把用户需要的数据"搬"到离用户近的地方。

## Ch4 网络优化：所有的快都始于网络不慢

### 4.1 网络优化的四个层次

| 层次 | 技术手段 | 收益 | 成本 |
|------|---------|:---:|:---:|
| **拓扑优化** | 星型→网状、跨地域就近接入 | P99 降 30-50% | 中（需专线/多机房） |
| **CDN/边缘** | 静态资源下沉、边缘渲染 | 首屏时间降 50-80% | 低（CDN 已非常便宜） |
| **负载均衡** | L4/L7 均衡、会话保持、故障剔除 | 吞吐量线性扩展 | 低 |
| **协议升级** | HTTP/1.1→HTTP/2→QUIC | 延迟降 30%+ | 低（应用层改造） |

### 4.2 BFE 大规模负载均衡实践

> 百度开源的企业级七层负载均衡，这是本书的独家案例

BFE (Baidu Front End) 的核心设计决策：

| 设计点 | BFE 的做法 | 性能收益 |
|--------|-----------|---------|
| **纯 Go 实现** | 协程模型，单机百万连接 | 比 Nginx+Lua 在多核场景高 30% |
| **插件化路由** | 条件表达式匹配 + 分级转发 | 规则变更毫秒级生效 |
| **健康检查** | 主动探测 + 被动（根据失败率） | 故障剔除<1秒 |
| **限流** | 集群限流 + 单实例限流 | 比纯 Nginx 精确 |

**选型建议**：Nginx 适合简单场景（静态文件 + 基础反向代理），BFE/APISIX 适合需要大量自定义路由规则、动态配置、多数据中心调度等场景。

**关联阅读**：高翔龙 §1.2.4（服务治理）、§3.2.3（Nginx+Lua 限流）。

## Ch5 通信优化：连接池不是开了就行

### 5.1 HTTP → gRPC：不只是协议升级

| 维度 | HTTP/1.1 + JSON | gRPC + Protobuf |
|------|----------------|-----------------|
| **连接模型** | 短连接/长连接池 | HTTP/2 多路复用单连接 |
| **序列化** | JSON（文本，可读但大） | Protobuf（二进制，紧凑） |
| **头部开销** | 每次请求 KB 级 | HPACK 压缩，几字节 |
| **多路复用** | 不支持，队头阻塞 | 支持，独立 Stream |
| **微服务内网 RPC** | P99 ~5-10ms | P99 ~1-3ms |

**选型判断**：内网服务间通信默认 gRPC。对外 API 如果客户端是浏览器，HTTP+JSON 仍然是主流（浏览器的 gRPC-Web 还不够普及）。

### 5.2 连接池的四个致命参数

```yaml
# 连接池不是"越大越好"
datasource:
  hikari:
    maximum-pool-size: 20        # ❌ 拍脑袋定
    minimum-idle: 5
    connection-timeout: 30000    # 30s 超时太长
    idle-timeout: 600000
    max-lifetime: 1800000

# ✅ 正确做法：从压测数据推导
# pool-size = 核心数 * 2 + 磁盘数（MySQL官方推荐）
# connection-timeout = P99 * 3（1s合适）
# max-lifetime < 数据库 wait_timeout（避免被服务端断开）
```

**连接池满的排查**：
```
1. 看 active_connections 是否持续等于 max
2. 看 pending_acquire 是否 > 0
3. 如果持续满 → 要么扩大池（下游扛得住），要么限流（下游扛不住）
4. 如果偶尔满 → 检查是否有慢查询占着连接不释放
```

### 5.3 异步通信的正确姿势

| 手段 | 正确用法 | 错误用法 |
|------|---------|---------|
| **MQ 削峰** | 写 MQ 后立即返回，下游异步消费 | 写入 MQ 后同步轮询结果——"伪异步" |
| **异步 RPC** | 无依赖的三个调用并行 | 有依赖的调用强行异步 |
| **批量** | 累积到一定量或一定时间再发 | 永远凑不够量一直不发 |

**关联阅读**：高翔龙 §3.4（MQ 削峰的正确/错误案例）。

## Ch6 缓存优化：六个提命问题

### 6.1 五种缓存策略的取舍

| 策略 | 读流程 | 写流程 | 一致性 | 性能 |
|------|--------|--------|:---:|:---:|
| **Cache-Aside** | 读缓存→miss→读 DB→写缓存 | 先写 DB→删缓存 | 弱 | 最优 |
| **Read-Through** | 缓存层自动查 DB | — | 弱 | 好 |
| **Write-Through** | — | 同时写缓存和 DB | 中 | 中 |
| **Write-Behind** | — | 先写缓存→异步写 DB | 弱 | 最优（写） |
| **Write-Around** | — | 写 DB→不写缓存 | 弱 | 好 |

**Cache-Aside 是 90% 场景的首选**——简单、高性能、写入时只删缓存不更新（避免并发写问题）。

#### 缓存策略决策树

```
你的写操作是否需要"即时"看到？
  ├─ 是 → 读写比 > 10:1？
  │        ├─ 是 → Cache-Aside（先写 DB，再删缓存）
  │        └─ 否 → Write-Through（同时写）
  └─ 否 → 能接受丢失少量写入？
           ├─ 是 → Write-Behind（异步批量写 DB，性能最高）
           └─ 否 → Write-Through
```

**为什么不能只用一种策略？** 电商商品详情（读多写少）用 Cache-Aside；广告计费（写密集）用 Write-Behind；支付交易（强一致）用 Write-Through。

### 6.2 六个提命问题

| 问题 | 触发条件 | 后果 | 解决方案 |
|------|---------|------|---------|
| **缓存穿透** | 查不存在的数据 | 每次都打到 DB | 布隆过滤器 / 缓存空值 |
| **缓存击穿** | 热点 key 过期 | 瞬间大量请求打 DB | 互斥锁回源 / 永不过期 |
| **缓存雪崩** | 大量 key 同时过期 | DB 瞬时压力爆炸 | 过期时间+随机偏移 |
| **热 Key** | 单个 key 被大量访问 | 单节点 CPU 100% | 本地缓存 + 多副本 |
| **大 Key** | 单个 key 的 value 太大 | 带宽打满 + 阻塞 | 拆分 / 压缩 |
| **数据不一致** | 先删缓存再写 DB 失败 | 读到旧数据 | 延迟双删 / Canal 订阅 binlog |

**关联阅读**：高翔龙 §4.3-4.5（多级缓存 + 穿透/击穿/雪崩 + 布隆过滤器原理）。

## Ch7 事务优化：不能为了强一致性无限牺牲性能

### 三种事务方案的性能-一致性谱

```
强一致性 ←———————————————→ 高性能
2PC/3PC > TCC > Saga > 最大努力通知 > 异步补偿(不保证)
```

| 方案 | 一致性 | 性能/吞吐 | 适用场景 |
|------|:---:|:---:|------|
| **2PC/3PC** | 强 | 低（同步阻塞） | 资金类核心操作、银行转账 |
| **TCC** | 强（业务保证） | 中 | 有 Try-Confirm-Cancel 的业务 |
| **Saga** | 最终 | 高 | 长事务、多服务协调（下单流程） |
| **最大努力通知** | 不保证 | 最高 | 通知类、非核心流程 |
| **事务消息** | 最终（MQ 保证） | 高 | 写操作→发消息的可靠性 |

**核心取舍**：
> 如果一个业务能接受"30秒内数据不一致"，那 Saga 比 2PC 吞吐量高 10 倍——选 Saga。如果一笔钱错了一定会被告上法庭，那用 2PC，吞吐量低就扩容——钱的问题不是性能问题。

#### TCC 走查：为什么比 2PC 快？

```
2PC 流程（同步阻塞）：
Coordinator → 所有参与者：PREPARE
             ↓ 等待所有参与者回复（最慢的决定了速度）
             ↓ 所有回复 YES → COMMIT（又一个同步等待）
             
TCC 流程（业务层面拆解）：
Try（预留资源）→ 快速返回，资源已锁定
Confirm（确认执行）→ 异步执行，不需要等所有参与者
Cancel（取消）→ 只在异常时执行

关键差异：TCC 不需要"等所有参与者都准备好再提交"——Try 阶段只预留资源不真正执行。
```

**关联阅读**：释慧利第3章（2PC/3PC详解）、唐伟志第5章（Saga/Percolator）、高翔龙 §5.3（订单最终一致性）。

## 生产陷阱清单（含可复现实验）

### 实验：连接池配置错误

```yaml
# ❌ 危险配置：连接池 200 + 超时 30s
# 后果：200 个连接全部被慢查询占满 → 201 个请求开始等 → 30s 后才发现超时
# 30s × 阻塞线程数 → 级联雪崩

# ✅ 正确：连接池 20 + 超时 1s
# 并发 > 20 → 立即排队失败 → fast fail → 熔断 → 保护下游
# 1s 超时快速释放 → 不浪费线程等死连接
```

### 实验：缓存过期时间的雪崩效应

```java
// ❌ 所有 100 个热点商品同时过期
redis.setex("product:1", 3600, data);
redis.setex("product:2", 3600, data); // ... 全 3600s

// ✅ 加上随机偏移：3600 ± 300s
for (int i = 1; i <= 100; i++) {
    redis.setex("product:" + i, 3600 + ThreadLocalRandom.current().nextInt(600) - 300, data);
}
```

| # | 陷阱 | 后果 | 正确做法 |
|---|------|------|---------|
| 1 | 连接池配置过大 + 超时过长 | 所有连接被慢查询占满→级联雪崩 | 池大小=核心×2+磁盘数，超时=P99×3 |
| 2 | 缓存永不过期无清理 | 内存打满→OOM→服务重启→冷启动雪崩 | 设置合理 TTL + 淘汰策略 |
| 3 | gRPC 没有设置 deadline | 下游慢→上游线程枯竭→链式雪崩 | 每个 gRPC 调用必设 deadline |
| 4 | 大 Key 存整个对象列表 | Redis 单线程处理 10MB key 阻塞所有请求 | 拆分存储 + 压缩 |
| 5 | 锁粒度过大 | 锁住整个商品表→并发能力退化为单线程 | 锁住单个 SKU/行 |

**关联阅读**：释慧利第3章（2PC/3PC详解）、唐伟志第5章（Saga/Percolator）、高翔龙 §5.3（订单最终一致性）。

## Ch8 分布式锁优化：锁住的是正确性，但别锁住性能

### Redis 锁 vs ZK 锁：性能对比

| 维度 | Redis（Redisson） | ZooKeeper（Curator） |
|------|------------------|---------------------|
| **加锁延迟** | 1-2ms（单次 Redis） | 10-50ms（ZK 写 + 同步） |
| **可靠性** | 时钟跳跃可能出问题 | 基于会话，更可靠 |
| **公平性** | 非公平（先到先抢） | 公平（按顺序排队） |
| **适用场景** | 高性能、可容忍极低概率异常 | 高可靠性要求（资金、配置变更） |

### 四个设计要素

| 要素 | 做法 | 反面案例 |
|------|------|---------|
| **互斥性** | SET NX + Lua 原子释放 | 非原子操作导致俩客户端同时持有锁 |
| **防死锁** | 设置过期时间 + 看门狗续期 | 锁永不过期，客户端挂了资源永远锁着 |
| **高性能** | 锁粒度尽量小（锁行不锁表） | 库存扣减锁整个商品而不是单个 SKU |
| **可重入** | 同一个客户端可重复获取 | 递归调用时死锁 |

**直播排行榜案例**：多个用户同时点赞 → 用 Redis 锁保护排序更新。锁粒度设计为"每个直播间一把锁"而非"全局一把锁"——不同直播间之间并行，吞吐量线性扩展。

## Ch9 分布式存储优化：存得快才能读得快

### 数据分布的三种策略

| 策略 | 原理 | 随机读 | 范围读 | 扩容代价 |
|------|------|:---:|:---:|:---:|
| **Hash 分片** | hash(key) % N | 最快 | 不支持 | 全量迁移 |
| **范围分片** | 按 key 范围分段 | 快 | 最快 | 分裂即可 |
| **一致性 Hash** | 哈希环 + 虚拟节点 | 快 | 不支持 | 低 |

### 复制的三种模式

| 模式 | 一致性 | 写入延迟 | 丢数据风险 |
|------|:---:|:---:|:---:|
| **同步复制** | 强 | 高（等所有副本） | 无 |
| **异步复制** | 弱 | 低（不等待） | 主库宕机可能丢失 |
| **半同步** | 中 | 中（等一个副本） | 极低 |

**题库系统案例**：800 万道题、10 万 QPS 查询。分片策略：按学科（数学题库、英语题库）+ 难度等级做二级分片。热数据（近一周新增题目）放 SSD 副本，冷数据（一年前的题目）放 HDD 副本。

## 面试高频题

**Q1：微服务拆分粒度如何影响性能？有没有"最优粒度"？**

粒度与性能不是线性的——拆得太粗（大单体）效率最高但可维护性差，拆得太细（每个接口一个服务）网络开销爆炸。没有绝对最优粒度，规则是：**一个服务内的 RPC 是函数调用（纳秒级），跨服务的 RPC 是网络调用（毫秒级）**。所以一起变化的东西放在同一服务内减少网络调用，分别变化的东西拆开做到独立部署。DDD 的限界上下文是最好的指导边界。

> **追问**："一个电商订单服务，是否应该拆成订单、结算、物流三个微服务？"
>
> 看业务规模。日订单量 <10 万：一个订单服务足够——拆开的 RPC 开销不值得。日订单量 >100 万：拆——结算和物流的逻辑复杂度已经需要独立团队维护，拆开的团队效率提升远超 RPC 开销。判断标准不是技术指标，是**团队规模**和**变更频率**。

**Q2：Redis 分布式锁在高并发下有什么性能陷阱？**

三个陷阱：1) 锁的范围太大——锁一个商品列表而不是单个商品，其余商品的请求全被阻塞。2) 锁的持有时间太长——在锁内做复杂计算或调用外部服务。3) 重试风暴——获取锁失败后自旋重试，数百个线程疯狂轮询 Redis。正确做法：锁粒度最小化 + 锁内只做必要的互斥操作 + 用信号量（Semaphore）替代自旋。

> **追问**："Redisson 的看门狗（Watchdog）机制是什么？有什么坑？"
>
> 看门狗是自动续期机制：如果业务逻辑执行时间超过锁的过期时间（默认 30s），看门狗会每 10s 把过期时间延长到 30s，防止锁提前释放。坑：如果业务代码死循环或卡住了，看门狗会持续续期→锁永不释放→其他节点全部在等→除非手动重启。解决方案：给业务逻辑加超时（如 CompletableFuture.orTimeout），超时后主动释放锁。

**Q3：五种缓存策略（Cache-Aside/Read-Through/Write-Through/Write-Behind/Write-Around），电商商品详情页和广告计费系统各应该用哪种？**

商品详情（读多写少、允许短暂不一致）→ **Cache-Aside**：先写 DB 再删缓存最简洁。广告计费（写密集、不能丢）→ **Write-Behind**：先写缓存快速响应，异步批量写 DB 提升吞吐。如果计费系统严格要求不丢写入→加 WAL（如 Redis AOF）作为 Write-Behind 的持久化保障。

> **追问**："Write-Behind 的风险是什么？怎么兜底？"
>
> 最大风险：缓存宕机→尚未写入 DB 的数据全部丢失。兜底：1) Redis AOF 持久化（性能下降但可接受）、2) 同时写一份到本地日志文件（更可靠但增加 IO）、3) 对账任务定期核对缓存和 DB 的数据差异。

## 本章小结

七个维度有一个共同规律：**性能瓶颈总是出现在"跨边界"的地方**——跨机器（网络）、跨服务（RPC）、跨数据节点（分片一致性）、跨存储介质（缓存→DB）。好的性能优化就是尽量减少跨边界次数，优化每一次跨边界的代价。

> 性能优化的终极公式：**数据前置 × 减少跨边界 × 批量代替单次 × 异步代替同步**。
