## 引言：这本书解决什么问题

市面上讲 Dubbo/Spring Cloud 的书大多是"这个框架怎么用"——配置怎么写、注解怎么加。郑天民这本书反过来——**抛开具体框架讲原理，再用框架源码验证原理**。

## Ch1 认识分布式系统

### 1.1 从单块系统到分布式系统的三个技术组件分类

郑天民把分布式系统开发所需的技术组件分成三类，这个分类角度和唐伟志、江峰的"理论视角"完全不同——是**工程实现视角**：

| 分类 | 解决什么问题 | 典型组件 |
|------|------------|---------|
| **远程过程调用组件** | 让跨进程调用像本地调用一样简单 | Dubbo、gRPC、Thrift |
| **微服务构建组件** | 服务治理的全套基础设施 | 注册中心、配置中心、网关、熔断器 |
| **通用技术组件** | 非分布式专属，但分布式场景下更重要 | 缓存、连接池、消息队列、动态代理 |

**为什么这个分类有意义？** 当你面对一个新的分布式系统需求时，可以按这三类去盘点技术选型清单——而不是想到什么用什么。比如你要做一个新的微服务系统：

```
Step 1: 选 RPC 组件——团队 Java 为主选 Dubbo，多语言异构选 gRPC
Step 2: 补齐微服务构建组件——注册中心(Nacos)、配置中心(Nacos/Apollo)、网关(Spring Cloud Gateway)
Step 3: 补齐通用技术组件——缓存(Redis)、连接池(HikariCP)、消息队列(RocketMQ)
```

### 1.2 分布式系统的四大核心设计要求

| 要求 | 核心问题 | 与其他要求的张力 |
|------|---------|----------------|
| **性能** | 响应时间、吞吐量能不能达标？ | 追求性能往往牺牲一致性（缓存的最终一致） |
| **可用性** | 部分节点故障时系统还能不能用？ | 追求高可用往往增加复杂度（容错逻辑） |
| **可扩展性** | 未来需求变了，改动成本大不大？ | 过度设计可扩展性会拖慢当前开发速度 |
| **服务治理** | 服务多了怎么统一管理？ | 治理体系本身也是一套需要维护的系统 |

**这四个要求两两之间几乎都存在张力**——这也是为什么"架构设计没有完美方案，只有权衡"（余春龙 Ch2 的核心观点，两本书在这一点上高度一致）。

### 1.3 主流开发套件速览

| 套件 | 定位 | 核心能力 |
|------|------|---------|
| **Spring Boot** | 应用开发基础框架 | 自动配置、约定优于配置——本书 Ch15 会深度剖析其扩展机制 |
| **Spring Cloud** | 微服务治理全家桶 | 注册发现(Eureka/Consul)、负载均衡(Ribbon)、熔断(Hystrix)、网关(Gateway)、配置(Config) |
| **Dubbo** | 高性能 RPC + 服务治理 | 阿里开源，国内互联网公司主力 RPC 框架 |
| **MyBatis** | 持久层框架 | 半自动 ORM，SQL 可控性强——本书用它讲透缓存/连接池/动态代理三大通用组件 |

**2026年补充视角**：Spring Cloud 生态在 2022 年后经历了较大变化——Netflix 系组件（Eureka/Ribbon/Hystrix）已停止维护，被 Spring Cloud LoadBalancer（负载均衡）、Resilience4j（熔断）替代；Dubbo 演进到 3.x，支持 Triple 协议（gRPC 兼容）；注册中心/配置中心逐渐向 Nacos 一体化收敛。本书的架构原理不变，但具体框架名称需要做现代映射（见后续章节的"关联阅读"表格）。

## Ch2 剖析框架代码结构的系统方法论

> 这是全书最有独创性的一章——不讲具体技术，讲"怎么学习一个陌生框架"的方法。

### 2.0 问题的起点：为什么读源码总是"迷路"

> "很多开发人员在学习开源框架源码时普遍存在一个问题——一不小心就扎进细节，没办法把握代码的整体结构。"

这句话精准描述了几乎所有工程师读源码的痛点。你打开 Dubbo 源码，点进 `DubboInvoker`，又跳到 `AbstractInvoker`，又跳到 `Filter` 链，半小时后你忘了自己一开始想搞懂什么问题。

郑天民给出的解法：**在扎入细节之前，先带着 5 个具体问题去框架的顶层结构中找答案**——这 5 个问题构成了一套"框架源码分析检查清单"。

### 2.1 主题一：基于组件设计原则剖析代码结构

**核心问题**："为什么代码结构要这么设计？"

#### 组件设计的两个基本维度

任何软件系统都可以看作一系列组件的集合。良好设计的核心是两个维度：

- **内聚**：组件内各元素彼此结合的紧密程度
- **耦合**：不同组件之间的互连程度

对应两类原则：
- **组件内聚原则**：指导如何把类划分到包中
- **组件耦合原则**：处理包与包之间的关系

#### 三条组件耦合原则

| 原则 | 全称 | 核心要求 |
|------|------|---------|
| **ADP** | 无环依赖原则（Acyclic Dependencies Principle） | 组件之间不应该存在循环依赖 |
| **SAP** | 稳定抽象原则（Stable Abstractions Principle） | 组件的抽象程度应与其稳定程度一致——稳定的组件应该也是抽象的 |
| **SDP** | 稳定依赖原则（Stable Dependencies Principle） | 被依赖者应该比依赖者更稳定 |

**为什么这三个原则关注的都是"稳定性"？** 一个包如果被很多其他包依赖，它就应该是稳定的——因为它一旦改动，所有依赖它的包都要跟着改。反过来，一个不被任何人依赖、但自己依赖很多东西的包，改动起来代价最小。

#### 量化组件稳定度的公式

这是本章最硬核的内容——把"稳定性"这个模糊的定性概念**变成可计算的量化指标**：

```
I = Ce / (Ca + Ce)

Ca（向心耦合）= 依赖该组件的外部组件数量
Ce（离心耦合）= 该组件依赖的外部组件数量
I（Instability，不稳定性）∈ [0, 1]
```

**两个极端案例**：

```
组件 X：Ca=3（被3个组件依赖），Ce=0（不依赖任何外部组件）
  → I = 0/(3+0) = 0  → 完全稳定

组件 Y：Ca=0（没人依赖它），Ce=3（依赖3个外部组件）
  → I = 3/(0+3) = 1  → 完全不稳定
```

**稳定性传递性**：沿着依赖方向，组件的不稳定性应该逐渐降低——**已经处于稳定状态的组件不应该依赖处于不稳定状态的组件**。这是一条重要的架构评审检查项：如果你发现一个"核心稳定组件"依赖了一个"边缘不稳定组件"，这就是架构上的一个警报信号。

#### 用 Dubbo 和 MyBatis 验证原则

Dubbo 的代码结构（common、remoting、rpc、cluster、registry、monitor、config、container 八大包）不是随意划分的——`common` 包被几乎所有其他包依赖（高 Ca），自身几乎不依赖别人（低 Ce）——所以 `common` 的不稳定性 I 接近 0，这正是"公共基础包应该最稳定"的架构常识的量化体现。

MyBatis 的包结构更复杂（十余个核心包），但同样遵循这个规律——越底层的包（如 `type` 类型处理包）越稳定，越上层的包（如 `session` 会话管理包）越不稳定。

#### SAP 和 SDP 容易混淆——辨析清楚

这两个原则名字很像，容易记混：

| 原则 | 关注什么 | 一句话记忆 |
|------|---------|-----------|
| **SAP**（稳定抽象原则） | 组件自身的**抽象程度**和**稳定程度**要匹配 | "越稳定的组件，应该越抽象（更多接口少实现）" |
| **SDP**（稳定依赖原则） | 组件**之间**的依赖方向 | "箭头应该指向更稳定的地方，不能反过来" |

举例：`common` 包（稳定，I≈0）应该主要放接口和抽象类（符合 SAP），而具体的业务实现包（不稳定，I≈1）应该依赖 `common`，不能反过来让 `common` 依赖具体实现（这是 SDP 的要求）。

#### 公式的现实局限——不要神化它

`I = Ce/(Ca+Ce)` 是一个**结构性指标**，只看依赖数量，不看依赖的"重要性"和"变化频率"：

- 一个组件可能只被 1 个外部组件依赖（Ca=1，看起来不稳定），但那 1 个依赖方是系统的核心链路——实际影响远大于公式暗示的"低稳定性"
- 一个组件可能被 20 个组件依赖（Ca=20，看起来极其稳定），但如果这 20 个依赖方都是遗留代码即将下线——它的真实"稳定性"意义不大

**正确用法**：把这个公式当作**发现问题的信号**，而不是**唯一的判断依据**——发现 I 值异常（比如核心包却很不稳定）时，去进一步分析原因，而不是直接下结论。

### 2.2 主题二：基于架构演进过程剖析代码结构

**核心问题**："框架是怎么从简单演化到复杂的？"

任何成熟框架的当前形态都不是一开始设计出来的，而是**逐步演进**的结果。理解这个演进过程，比直接看最终形态更容易抓住设计意图。

以 Dubbo 为例，其架构演进大致遵循"由易到难"的拆解路径——先解决最核心的 RPC 调用问题（能调通），再逐层叠加集群容错、负载均衡、服务治理能力。这和第 1 章"分布式系统架构演变"（张伟洋《实战派》）的思路高度一致——**架构总是问题驱动的渐进式演化，不是一次性设计出来的**。

**读源码的实用技巧**：面对一个复杂框架，试着去查它的早期版本（GitHub 的 tag 历史），你会发现早期版本的代码结构简单得多，更容易理解设计的初始意图。理解了"为什么加这一层"，比直接看最终的复杂结构更容易建立心智模型。

### 2.3 主题三：基于核心执行流程剖析代码结构

**核心问题**："怎么抓住主流程做分层剖析？"

大型框架的代码库往往有成百上千个类，但**核心执行流程通常只涉及其中的一小部分**。找到主流程，沿着主流程一层一层剖析，比试图理解"全部代码"高效得多。

书中以 MyBatis 的主流程为例：一次 SQL 执行大致经过 `SqlSession → Executor → StatementHandler → ParameterHandler/ResultSetHandler` 这条链路——**先把这条主链路的每一环搞清楚，再回头看外围的插件机制、缓存机制、类型处理机制**，会发现原本"复杂"的框架突然变得清晰了。

**这个方法论的本质**：先建立骨架（20% 的核心代码承载 80% 的核心功能），再填充细节（其余 80% 的代码是对核心流程的增强/扩展/优化）。

### 2.4 主题四：基于基础架构组成剖析代码结构

**核心问题**："框架怎么从通用基础架构扩展到具体实现？"

很多框架不是从零设计的，而是在一个**通用基础架构**之上做特化。书中给出的例子是：从"RPC 基础架构"（通用的远程调用抽象）扩展到 Dubbo 的具体实现。

**为什么这个视角重要？** 如果你理解了 RPC 的通用基础架构（寻址、序列化、网络传输、容错这几个必备环节），那么面对任何一个新的 RPC 框架（gRPC、Thrift、Dubbo3），你都能快速定位"这个框架在哪个环节做了什么特殊设计"——因为骨架都是一样的，差异都在具体实现细节上。

**类比**：这就像学会了"操作系统进程调度"的通用原理后，去看 Linux CFS 调度器和 Windows 调度器，你能快速抓住"它们解决同一个问题，但用了不同的具体算法"。

### 2.5 主题五：基于可扩展性设计剖析代码结构

**核心问题**："框架怎么预留可扩展点？"

成熟框架的一个共同特征——**几乎所有核心流程上都预留了扩展点**，让使用者可以在不修改框架源码的前提下定制行为。

书中以 MyBatis 的 **TypeHandler 机制**为例：MyBatis 需要把 Java 类型和数据库类型互相转换（比如 Java 的 `Boolean` 对应 MySQL 的 `TINYINT`），这个转换逻辑通过 `TypeHandler` 接口抽象出来——内置了几十种常见类型的 Handler，同时留了扩展点，让用户可以自定义类型转换逻辑（比如把一个 JSON 字符串自动转成 Java 对象）。

**常见的可扩展性设计方法**（书中总结的通用模式）：

| 模式 | 原理 | 典型应用 |
|------|------|---------|
| SPI（Service Provider Interface） | 通过配置文件动态加载实现类 | Java 原生 SPI、Dubbo 的扩展点加载机制 |
| 策略模式 | 定义接口，运行时选择具体实现 | 负载均衡策略、序列化策略 |
| 模板方法模式 | 定义流程骨架，子类实现具体步骤 | MyBatis 的 `BaseExecutor` |
| 拦截器/过滤器链 | 在核心流程前后插入自定义逻辑 | Dubbo Filter、Spring Interceptor |

**架构师视角的关键判断**：预留扩展点是有代价的——每一个扩展点都增加了框架的复杂度和维护成本。**好的框架设计不是扩展点越多越好，而是恰好在"高频定制需求"的地方留口子**（比如序列化协议因为业务场景差异很大，值得做成扩展点；而消息传输的字节序几乎没人需要定制，不值得开放扩展）。

## 生产实践中的应用：如何用这套方法论评审新代码

这套方法论不只用于读别人的源码，也能用于**评审自己团队的代码架构**：

```
Code Review Checklist（基于本章方法论）：
1. 这个新模块的包结构是否符合内聚原则？（相关的类是否聚在一起？）
2. 计算一下关键组件的不稳定性指数 I——核心组件是否足够稳定（I 接近 0）？
3. 是否存在循环依赖？（用 IDE 插件如 IntelliJ 的 Dependency Structure Matrix 检测）
4. 这个模块的主流程是否清晰？（能否用一句话说清楚核心执行路径？）
5. 未来最可能变化的地方，是否预留了合理的扩展点？
```

## 生产陷阱：不遵循组件设计原则的真实后果

| # | 陷阱 | 场景 | 后果 |
|---|------|------|------|
| 1 | **循环依赖** | 模块 A 依赖 B 的工具类，B 又依赖 A 的常量类 | 无法独立编译测试任一模块，重构举步维艰 |
| 2 | **核心组件不稳定** | "公共工具包"里塞了很多业务专属逻辑 | 每次业务变更都要改公共包，牵连所有依赖它的模块 |
| 3 | **扩展点开得太随意** | 每个方法都加 SPI 扩展点"以防将来需要" | 框架复杂度爆炸，实际使用的扩展点不到 10% |
| 4 | **没有主流程意识** | 新人直接从入口类逐行读到底 | 半天时间陷在一个次要分支的异常处理逻辑里，没有摸清核心链路 |

### 可复现的循环依赖实验

```java
// 模块 order 的类
package com.company.order;
import com.company.user.UserUtils;  // 依赖 user 模块

public class OrderService {
    public void createOrder() {
        UserUtils.validateUser();  // 调用 user 模块的工具类
    }
}

// 模块 user 的类——反向依赖了 order 模块！
package com.company.user;
import com.company.order.OrderConstants;  // ❌ 循环依赖产生

public class UserUtils {
    public static void validateUser() {
        // 用到了 order 模块的常量
        if (OrderConstants.MAX_ORDER_COUNT > 0) { ... }
    }
}
```

**后果**：Maven/Gradle 构建系统虽然能编译通过（因为是类级别的循环，不是模块级别），但语义上 `order` 和 `user` 已经耦合成了一个整体——你无法单独理解或测试其中一个模块。**检测方法**：用 IDEA 的 Dependency Structure Matrix 或 `jdeps` 工具扫描包依赖图，寻找环。

**正确做法**：把 `MAX_ORDER_COUNT` 这类跨模块共享的常量下沉到一个双方都依赖的 `common` 包——让依赖关系变成 `order → common ← user`，消除环。

### 可复现的扩展点滥用实验

```java
// ❌ 每个字段都开 SPI 扩展点——过度设计
public interface FieldValidator {
    boolean validate(Object value);
}
public interface FieldFormatter {
    String format(Object value);
}
public interface FieldSerializer {
    byte[] serialize(Object value);
}
// ... 一个简单的用户表单字段，硬是拆出 8 个可扩展接口
// 结果：新人加一个字段需要理解 8 个接口的关系，实际用到自定义实现的字段 <5%

// ✅ 只在真正需要变化的地方开口子
public class UserFormField {
    private final FieldType type;      // enum 已覆盖 95% 场景
    private CustomValidator customValidator; // 仅在 enum 不够用时才需要传入
}
```

**判断标准**：统计线上代码里"某个扩展点接口"被自定义实现的次数——如果 6 个月内只有 0-1 个自定义实现，这个扩展点大概率是过度设计。这条经验规则可以直接写进架构评审清单。

## 面试高频题（含二层追问）

**Q1：你如何评价一个开源框架的代码结构设计得好不好？**

不是凭感觉说"设计得优雅"，而是用具体标准检验：1）包结构是否遵循高内聚低耦合——相关的类是否聚在一起；2）是否存在循环依赖（用工具扫描包依赖图）；3）核心稳定组件（如公共工具包）是否真的足够稳定——用 `I = Ce/(Ca+Ce)` 简单估算；4）主流程是否清晰可追踪；5）扩展点设计是否恰到好处，不多不少。

> **追问**："如果发现两个包之间存在循环依赖，你有几种重构思路？"
>
> 三种：1）**抽取公共依赖**——把两者都需要的部分下沉到一个新的更底层的包；2）**依赖倒置**——让其中一方依赖另一方的接口而不是实现，把实现通过依赖注入传入；3）**合并模块**——如果两个包耦合到"事实上就是一个模块"的程度，干脆合并，承认它们本来就该在一起。选择哪种取决于耦合的性质——是"业务上天然相关"还是"设计失误导致的意外耦合"。

**Q2：面对一个上万个类的陌生框架源码，你会怎么开始阅读？**

不会从入口类逐行读下去——那样会迷失在细节里。按本章的方法论：第一步先看包结构，理解组件划分（对应主题一）；第二步找到一次典型请求的主执行流程，只沿着这条链路读（对应主题三）；第三步理解框架预留了哪些扩展点，这往往揭示了框架设计者认为"最可能变化"的地方（对应主题五）。三步做完，你对框架已经有了骨架级的理解，之后再按需深入某个具体子系统。

> **追问**："你怎么快速定位一个框架的'主流程'，而不是一头扎进某个分支？"
>
> 从**最外层的公开 API 入口**开始，用 IDE 的 Call Hierarchy（调用层次结构）功能往下追，但**只追那些没有被 catch 吞掉、且返回值参与了最终结果的调用路径**——遇到日志记录、监控埋点、异常处理这类"旁路逻辑"直接跳过，只沿着"业务主链路"走。另一个技巧是看框架的官方文档或测试用例里的"最简示例"（Hello World 级别），从这个最简单的例子反向调试，通常就是主流程。

## 本章小结

> "如何快速把握开源框架的代码结构，是我们需要梳理的一套系统方法。"

Ch1 建立了分布式系统的工程分类视角（RPC组件/微服务构建组件/通用组件），Ch2 给出了一套**可迁移到任何框架**的源码分析方法论——五个主题、一个量化公式、三条设计原则。这套方法论的价值不在于让你记住 Dubbo 或 MyBatis 的具体实现，而在于**下次遇到一个新框架（哪怕是 2030 年才出现的框架），你依然知道怎么系统性地读透它**。

下一章进入具体的服务治理组件——网络通信、远程调用、负载均衡，用 Dubbo 和 Spring Cloud 的真实源码对照验证前面提到的原理。
