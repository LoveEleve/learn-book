## Ch12 动态代理：为什么 RPC 可以"像调本地方法一样"？

### 代理模式的两大类型

| 类型 | 原理 | 典型应用 | 何时选择 |
|------|------|---------|---------|
| **JDK 动态代理** | 基于接口，运行时生成 `$Proxy` 类 | Spring AOP（接口代理） | 目标类有接口 |
| **CGLIB 代理** | 基于继承，运行时生成目标类的子类 | Spring AOP（类代理）、Hibernate 延迟加载 | 目标类无接口（或需要代理具体类） |

### Dubbo 中的代理：为什么 Consumer 拿到的只是一个接口引用？

```java
// Consumer 端只看到接口，却能发起远程调用——
// 因为 Dubbo 在运行时为这个接口动态生成了一个 Proxy 对象
UserService userService = context.getBean(UserService.class);  // 实际拿到的是 $Proxy
User user = userService.getUser(1L);  // $Proxy.invoke() → 网络请求 → Provider
```

**Dubbo 的代理生成链**：

```
Consumer 获取 Bean → Dubbo 的 ReferenceBean（FactoryBean）
  → 调用 getObject() → 触发 createProxy()
  → 为 UserService 接口动态生成 $Proxy 类
  → $Proxy.invoke() 内部：组装 RPC 请求 → Netty 发送 → 等待响应 → 反序列化返回
```

**核心技术点**：Dubbo 的代理对象做了三件事——**序列化参数**（Java 对象→字节流）、**发送网络请求**（Netty Client）、**反序列化返回值**（字节流→Java 对象）。对 Consumer 代码而言，这三步完全透明——这就是 RPC 能"像调本地方法一样"的底层真相。

#### JDK 动态代理的 `$Proxy` 类到底长什么样？

把这个反编译出来是理解动态代理的最好方式：

```java
// JDK 为 UserService 接口生成的 $Proxy0 类（反编译简化版）
public final class $Proxy0 extends Proxy implements UserService {
    // invoke 方法：所有接口方法调用都走到这里
    public final User getUser(Long id) {
        return (User) h.invoke(this, m3, new Object[]{id});
        //                    ↑  h 就是 InvocationHandler，内部的逻辑是：序列化→网络→反序列化
    }
    
    public final void updateUser(User user) {
        h.invoke(this, m4, new Object[]{user});
    }
    // 每一个接口方法，$Proxy 里都生成一个对应的 final 方法，统一委托给 h.invoke()
}
```

看到了吗？**`$Proxy.getUser()` 内部就一行 `h.invoke()`**——所有魔法都在 `InvocationHandler` 里。Dubbo 的 `InvocationHandler` 做了网络通信，MyBatis 的做了 SQL 执行。**同一个代理机制，不同的 Handler 实现，就是两种完全不同的功能**——这正是"代理模式+策略模式"组合的经典运用。

### MyBatis 中的代理：为什么只写接口就能执行 SQL？

```java
// 你只写了一个接口，MyBatis 却能让它"执行 SQL"——因为动态代理
public interface UserMapper {
    @Select("SELECT * FROM user WHERE id = #{id}")
    User getUser(Long id);
}

// MyBatis 在运行时为 UserMapper 接口生成了 MapperProxy
// getUser(1L) → MapperProxy.invoke() → 解析 @Select → 创建 PreparedStatement → 执行 SQL → 映射结果
```

**延迟加载与动态代理**：MyBatis 的一对多关联查询中（如查询用户及其所有订单），`List<Order>` 字段被赋值的不是真实列表，而是一个代理对象——只有当代码真正访问 `user.getOrders()` 时，代理才触发第二条 SQL 查询。这就是"延迟加载"的代理实现。

## Ch13 应用缓存：MyBatis 两级缓存的设计哲学

### 一级缓存（SqlSession 级别）

| 特性 | 说明 |
|------|------|
| **作用范围** | 同一个 SqlSession 内，相同的查询只执行一次 SQL |
| **生命周期** | 与 SqlSession 同生共死——session 关闭，缓存清空 |
| **默认状态** | 默认开启，无法关闭（只能通过 `sqlSession.clearCache()` 手动清） |
| **脏数据风险** | 两个 SqlSession 各自独立缓存——一个 session 修改了数据，另一个 session 的缓存不会感知 |

### 二级缓存（Mapper 级别）

| 特性 | 说明 |
|------|------|
| **作用范围** | 跨 SqlSession，同一个 namespace 下的所有 session 共享 |
| **生命周期** | 跟随 SqlSessionFactory |
| **默认状态** | 默认关闭，需手动在 mapper.xml 中加 `<cache/>` |
| **更新策略** | 执行 INSERT/UPDATE/DELETE 后自动清空该 namespace 的二级缓存 |

### 两级缓存的触发流程

```
查询请求 → 二级缓存（跨 session）→ 命中？→ 返回
                                    ↓ miss
                                一级缓存（当前 session）→ 命中？→ 返回
                                                          ↓ miss
                                                      执行 SQL → 写入一级缓存 → 返回
```

**为什么二级缓存默认关闭？** 跨 session 共享缓存在分布式环境下有严重的脏数据风险——如果两个应用节点各自有二级缓存（本地内存），节点 A 更新了数据，节点 B 的二级缓存不会感知。只有单机+读写分离的简单场景才适合开二级缓存。分布式环境下数据一致性靠 Redis 之类的集中式缓存。

**关联阅读**：高翔龙 Ch4（多级缓存架构 + 穿透/击穿/雪崩）已深度覆盖 Redis 分布式缓存，本章聚焦 MyBatis 本地缓存的特定场景。

## Ch14 资源管理：连接池怎么设计才不浪费也不撑爆

### 连接池的五个核心要素

| 要素 | 含义 | 设小了 | 设大了 |
|------|------|--------|--------|
| **最大连接数** | 池中最多多少个连接 | 并发不够，请求排队 | 数据库扛不住（MySQL 默认 max_connections=151） |
| **最小空闲连接** | 池中保持多少空闲连接 | 请求来时需临时创建→延迟 | 浪费数据库连接资源 |
| **连接超时** | 等多久拿不到连接就报错 | 误杀正常排队请求 | 请求长期阻塞→线程池耗尽 |
| **空闲回收** | 空闲多久的连接被回收 | 连接频繁创建销毁 | 占着数据库连接不用 |
| **最大生命周期** | 连接最多活多久 | 连接永不刷新→可能持有过期凭证 | 连接频繁重建→性能开销 |

### Connection 对象的获取过程（HikariCP 为例）

```
1. ConcurrentBag.borrow() — 从并发安全集合中借一个连接
2. 有空闲连接？→ 直接返回
3. 无空闲连接 + 当前总数 < maxPoolSize？→ 创建新连接
4. 无空闲连接 + 已达上限？→ 等待（connectionTimeout 以内）
5. 超时未获取 → 抛出 SQLException（而非阻塞到死）
```

**HikariCP 的 ConcurrentBag 为什么比 BlockingQueue 快？**

传统连接池用 `ArrayBlockingQueue` ——借还都加锁。HikariCP 的 `ConcurrentBag` 用无锁设计：每个线程先从自己 ThreadLocal 缓存的"最近归还连接"借，90% 的请求在这里命中（无锁）；只有 miss 时才走共享队列（CAS 无锁竞争）。这就是 HikariCP 在 JMH 基准测试中比 Druid/C3P0/DBCP2 快 2-3 倍的底层原因——**不是"更快地创建连接"，而是"更少地争抢锁"**。

### 连接池参数的推导公式

```
maxPoolSize = CPU 核数 × 2 + 有效磁盘数  （MySQL 官方推荐）
  ↓
实际容量的上限不是这个公式，而是：maxPoolSize × 节点数 ≤ MySQL max_connections × 0.8
  ↓
示例：4核机器 → 公式建议 maxPoolSize=9，4个应用节点 → 4×9=36 < 151×0.8=120 ✅
```

**注意**：数据库连接数到了上限不代表数据库就崩了——MySQL 的 max_connections 默认 151，但每个连接占约 256KB 内存（栈 + 缓冲区），1000 个连接 = 256MB 额外内存。如果设置 `maxPoolSize=200`、10 个节点 → 2000 个连接 → 数据库内存被吃满。

## Ch15 框架集成：Spring Boot 自动配置是怎么发现你的？

### Spring 的三大启动扩展点

| 扩展点 | 何时触发 | 典型用途 |
|--------|---------|---------|
| **InitializingBean** | Bean 属性设置完成后 | 初始化连接池、预热缓存 |
| **DisposableBean** | Bean 销毁前 | 关闭连接池、释放资源 |
| **Aware 接口** | 在 Bean 创建过程中注入 Spring 容器对象 | `ApplicationContextAware` 获取容器引用 |

```java
// Dubbo 的 ServiceBean 就同时实现了这三个接口
public class ServiceBean<T> extends ServiceConfig<T> 
    implements InitializingBean, DisposableBean, ApplicationContextAware {
    
    // ApplicationContextAware: 获取 Spring 容器引用
    @Override
    public void setApplicationContext(ApplicationContext ctx) { ... }
    
    // InitializingBean: 属性设置完后 → 执行服务导出
    @Override
    public void afterPropertiesSet() {
        export();  // 这里触发了第4章讲的"五阶段服务发布流水线"！
    }
    
    // DisposableBean: 容器关闭时 → 注销服务
    @Override
    public void destroy() {
        unexport();
    }
}
```

### Spring Boot 自动配置的魔法

自动配置的核心是 `spring.factories` 文件：

```
// META-INF/spring.factories
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
com.alibaba.dubbo.spring.boot.DubboAutoConfiguration
```

**启动时发生了什么**：
1. `@SpringBootApplication` → 包含了 `@EnableAutoConfiguration`
2. `@EnableAutoConfiguration` → 触发 `AutoConfigurationImportSelector`
3. 扫描所有 jar 包中的 `META-INF/spring.factories` 文件
4. 加载文件中声明的所有 `@Configuration` 类
5. 这些配置类中的 `@ConditionalOnClass`/`@ConditionalOnMissingBean` 等条件注解决定是否生效

**这就是为什么你加了 `dubbo-spring-boot-starter` 依赖后，Dubbo 自动就配置好了——不需要任何手动配置代码**。

#### 2026年重要更新：Spring Boot 3.x 已废弃 `spring.factories`

Spring Boot 2.x → 3.x 中，自动配置的注册方式从 `META-INF/spring.factories` 迁移到了 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`——文件格式从 key-value 改为每行一个类名。如果你的项目从 Boot 2.x 升级到 3.x，但某个老 starter 还用 `spring.factories`——自动配置会静默失效（Spring 不再扫描那个文件里的声明）。迁移检查清单：`grep -rn "spring.factories"` → 每个结果都需要迁移到新文件。

## Ch16 架构模式：比微服务更底层的设计思想

### 微内核模式——插件化系统的理论基础

```
微内核（MicroKernel）
  ↓ 只提供最核心的功能：插件管理 + 生命周期管理
插件（Plugin）
  ↓ 通过扩展点向微内核注册自己的功能
  
核心设计：内核不懂任何业务，所有业务都是插件——内核只管加载/卸载插件
```

**应用案例——Dubbo 的扩展点机制就是微内核模式**：
- Dubbo 内核（Protocol、ProxyFactory、Registry 等核心 SPI 接口）= 微内核
- Dubbo 插件（dubbo:protocol="dubbo" → DubboProtocol 实现，改成 "rest" → RestProtocol 实现）= 插件
- Dubbo 的 `ExtensionLoader` = 插件管理器

### 管道-过滤器模式

```
输入 → Filter A → Filter B → Filter C → 输出
          ↓            ↓           ↓
      鉴权校验      参数转换     日志记录
```

**应用案例——MyBatis 的插件机制**：
```java
// MyBatis 的 Interceptor 就是一个过滤器
@Intercepts({@Signature(type = Executor.class, method = "query", args = {...})})
public class MyPlugin implements Interceptor {
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        // 执行前做处理
        Object result = invocation.proceed();  // 调用下一个过滤器
        // 执行后做处理
        return result;
    }
}
```

这个模式在 Spring MVC 的 `HandlerInterceptor`、Dubbo 的 `Filter` SPI、Servlet 的 `Filter` 中也都在用——**过滤器链是框架设计中复用率最高的扩展模式**。

### 两种模式的核心差异

| 维度 | 微内核 | 管道-过滤器 |
|------|--------|------------|
| **关注点** | 如何组织功能模块 | 如何处理数据流 |
| **扩展方式** | 添加/移除插件 | 添加/移除/重排过滤器 |
| **典型应用** | Eclipse IDE、VS Code、Dubbo SPI | Spring Interceptor、MyBatis Plugin、Servlet Filter |
| **适用场景** | 产品需要第三方开发扩展 | 请求/数据需要多阶段处理 |

**微内核 vs 微服务——名字相似但完全不同**：

| 维度 | 微内核 | 微服务 |
|------|--------|--------|
| **关注点** | 一个进程内部的功能模块怎么组织 | 一个系统内部的服务怎么拆分和协作 |
| **通信方式** | 进程内方法调用（Java 接口） | 网络 RPC/HTTP/MQ |
| **部署方式** | 所有插件共存在同一个进程 | 每个服务独立部署 |
| **典型例子** | Dubbo SPI、Eclipse IDE、VS Code | 电商系统拆成订单/用户/支付服务 |

**一个框架里两种模式共存的经典案例——Dubbo**：Dubbo 的 SPI 机制（`ExtensionLoader`）是微内核模式——不同的 Protocol 实现作为"插件"被加载；同时 Dubbo 的 Filter 链是管道-过滤器模式——请求依次经过 CacheFilter、MonitorFilter、ExceptionFilter 等过滤器。**微内核管理**"用什么组件"，**过滤器链处理**"请求经过组件的什么顺序"。两者协同工作，互不冲突。

## 生产陷阱清单

| # | 陷阱 | 场景 | 后果 | 正确做法 |
|---|------|------|------|---------|
| 1 | **CGLIB 代理 `final` 方法不生效** | AOP 切了一个 `final` 方法 | 切面静默失效，日志/权限/事务全部不生效 | Code Review 检查 `@Transactional` 等注解的方法是否 `final` |
| 2 | **二级缓存未配置清除策略** | `cache.xml` 开了 `<cache/>` 没配任何过期策略 | 缓存无限增长→内存溢出→OOM | 必须配 `size`、`flushInterval` 或 `eviction` 之一 |
| 3 | **连接池设满数据库上限** | `maxPoolSize=50`、20 个节点→1000 连接→DB 崩 | 全站不可用 | 提前计算：节点数 × maxPoolSize ≤ DB max_connections × 0.8 |
| 4 | **Boot 3.x 升级后自动配置失效** | 老 starter 还用 `spring.factories` | 所有自动配置静默失效，排查半天找不到原因 | 升级前 `grep spring.factories` 找到所有需要迁移的文件 |
| 5 | **微内核模式误用** | 每个业务逻辑都做 SPI 扩展点 | 框架复杂度爆炸，没人知道哪个扩展点在生产中实际被自定义 | 只在高频定制需求上开口子 |

## 面试高频题

**Q1：JDK 动态代理和 CGLIB 代理的本质区别是什么？各有什么限制？**

JDK 动态代理基于**接口**——运行时生成 `$Proxy` 类实现目标接口，只能代理有接口的类。CGLIB 基于**继承**——运行时生成目标类的子类，可以代理没有接口的类，但 `final` 类和方法无法被代理。Spring AOP 的默认策略：如果目标类有接口→用 JDK 代理，没有→用 CGLIB。Dubbo 只用 JDK 代理（因为 RPC 调用本身就是基于接口的）。

> **追问**："为什么 JDK 代理不能代理无接口的类？"
>
> 因为 JDK 的 `Proxy.newProxyInstance()` 需要传入接口列表作为参数。生成的 `$Proxy` 类通过实现这些接口来拦截方法调用——没有接口就没有"实现"的途径。CGLIB 走的是继承路线——生成子类、重写方法、在重写的方法里加入拦截逻辑。所以 CGLIB 的限制是 `final`（类不能被继承、方法不能被重写）。

**Q2：MyBatis 的一级缓存和二级缓存在分布式环境下分别有什么坑？**

一级缓存的坑：同一个 SqlSession 内，先查到数据缓存在一级，然后另一个 SqlSession 改了同一条数据——一级缓存不会感知，返回脏数据。但因为一级缓存生命周期极短（一次数据库操作后就关了），影响面小。二级缓存的坑更严重：跨 SqlSession 共享，节点 A 更新了数据，节点 B 的二级缓存完全不知情——多个应用节点本地缓存的"数据不一致窗口"比一级缓存大得多。这就是为什么分布式环境下不推荐开启二级缓存——用 Redis 这种集中式替代。

> **追问**："如果非要用 MyBatis 二级缓存，怎么降低脏数据风险？"
>
> 三个控制手段：1) 只在"读多写极少"的 namespace 上开二级缓存（如字典表、省市区表）；2) 配置 `<cache>` 的 `flushInterval` 定时清空（如每隔 60 秒强制刷新）；3) 更新操作后的 `flushCache=true` 保证写操作触发清空同一 namespace 的二级缓存。核心原则：**把不一致窗口控制在可接受的范围内，而不是企图消除它。**

**Q3：Spring Boot 的自动配置如果遇到冲突（两个 starter 都提供了同一个 Bean），怎么排查？**

先看 `/actuator/beans` 端点——能看到所有已注册的 Bean 及其来源的 `@Configuration` 类。如果确实有冲突，排除不需要的：`@SpringBootApplication(exclude = {XxxAutoConfiguration.class})`。如果是你自己写的 Bean 和 starter 的冲突，用 `@ConditionalOnMissingBean` 控制——"starter 提供的默认 Bean 在用户自定义了同类 Bean 时自动失效"。这就是 Spring Boot 的"约定优于配置"同时保留了"配置覆盖约定"的弹性。

> **追问**："两个 starter 都用了 `@ConditionalOnMissingBean`，两个都没自定义——Spring 选谁？"
>
> 看加载顺序。Spring Boot 的自动配置类有 `@AutoConfigureOrder` 和 `@AutoConfigureBefore/After` 注解来控制加载先后。如果两个 starter 都没有明确排序，Spring 按类路径扫描顺序决定——结果是不确定的。生产环境应该避免这种设计：**同一个 Bean 只能有一个"权威来源"**。
