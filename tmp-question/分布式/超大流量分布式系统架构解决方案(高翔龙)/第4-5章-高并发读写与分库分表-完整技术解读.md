# 第4章 高并发读写优化

## 4.1 缓存：距离计算最近的数据副本

### 4.1.1 缓存的分层体系

高翔龙在书中用一个经典定义开篇：**缓存是将被频繁访问的数据存储在距离计算最近的地方**。这个"距离"既可以是物理距离（CDN 边缘节点），也可以是访问延迟距离（内存 vs 磁盘）。从用户到数据库，数据经过多级缓存层：

```
用户
  │
  ▼
┌──────────┐  CDN（Content Delivery Network）：静态资源就近访问
│  用户设备 │  距离用户最近，延迟 < 10ms
└────┬─────┘
     │
     ▼
┌──────────┐  反向代理缓存（Nginx/Varnish）：缓存 HTTP 响应
│  接入层   │  Nginx proxy_cache，延迟 < 5ms（机房内）
└────┬─────┘
     │
     ▼
┌──────────┐  应用层本地缓存：JVM 内，纳秒~微秒级
│ WebServer│  Caffeine/GuavaCache，容量有限（MB~GB级别）
└────┬─────┘
     │ Cache Miss
     ▼
┌──────────┐  分布式缓存：独立集群，毫秒级网络访问
│  Redis   │  可水平扩展，单机 10w+ QPS
└────┬─────┘
     │ Cache Miss
     ▼
┌──────────┐  数据库：持久化存储，磁盘 I/O
│  MySQL   │  最后一道防线，不可逾越
└──────────┘
```

**每一层的设计哲学**：越靠近用户的缓存层，容量越小但延迟越低。CDN 缓存 TB 级别的静态资源，WebServer 本地缓存 GB 级别的热点数据，Redis 缓存 TB 级别的业务数据，数据库存储所有数据。每一层都是上一层的"保护伞"——缓存命中在上层结束，未命中才穿透到下层。

### 4.1.2 缓存的四个核心问题

任何缓存方案，无论技术选型如何，本质上都在解决四个相同的问题：

| 问题 | 描述 | 关键参数 |
|------|------|---------|
| **存什么** | 哪些数据值得缓存？ | 热点数据、变化频率低、查询成本高 |
| **存多久** | 过期时间多长？ | TTL（Time To Live），平衡一致性与命中率 |
| **存多少** | 容量上限？ | maxSize / maxMemory，超出时淘汰 |
| **怎么淘汰** | 容量满时删哪个？ | LRU / LFU / FIFO / TTL |

> **面试视角**：面试官问"缓存和数据库一致性问题怎么解决？"——不要只答"延迟双删"。这个问题本质上涉及四个维度：(1) 写策略（Cache Aside / Read Through / Write Through / Write Behind），(2) 过期策略（TTL 设置），(3) 最终一致性兜底（MQ + 定时任务对账），(4) 特殊场景（如不允许短暂不一致的金融场景，直接用 DB 不用缓存）。回答时应先说策略维度，再讲具体方案。

## 4.2 本地缓存与off-heap：突破JVM内存限制

### 4.2.1 本地缓存的利与弊

本地缓存（In-Process Cache）最大的优势是**零网络开销**——数据在同一个 JVM 进程中，访问延迟在纳秒~微秒级，远低于 Redis 的毫秒级。高翔龙在生产环境中使用的组合是 **GuavaCache（本地）+ Redis（分布式）**。

但本地缓存有两个致命问题：

**问题一：占用 JVM Heap 空间**

本地缓存的对象存储在 Heap 中，受 GC 管理。如果缓存数据占用过多 Heap（如超过总 Heap 的 30%），会导致：
- GC 频率增加（Young GC 更频繁）
- GC 暂停时间延长（Full GC 时需要扫描更多存活对象）
- 极端情况下 `java.lang.OutOfMemoryError`

**问题二：数据一致性问题**

在集群部署中，每个 WebServer 节点各自维护本地缓存。如果数据发生更新：
- 已更新的节点 → 缓存是新值
- 未更新的节点 → 缓存是旧值
- 同一个用户被负载均衡到不同节点 → 看到的数据"飘忽不定"

这两个问题决定了本地缓存的使用边界：**只缓存那些变化频率低、一致性容忍度高、且频繁访问的数据**。

### 4.2.2 GuavaCache vs Caffeine：2026年选型

高翔龙在书中使用 GuavaCache 18.0（2014年）。2026 年，**Caffeine**（基于 W-TinyLFU 算法）已全面替代 GuavaCache：

| 维度 | GuavaCache (Legacy) | Caffeine (推荐) |
|------|---------------------|-----------------|
| 淘汰算法 | LRU | **W-TinyLFU**（Window TinyLFU，结合频率+时间） |
| 命中率 | 中等 | 高（接近最优） |
| 并发性能 | ReentrantLock | **自实现无锁 Ring Buffer**（多核分片 Striped Ring Buffer） |
| API风格 | CacheBuilder | 类似 Guava，`Caffeine.newBuilder()` |
| 维护状态 | 维护模式 | 活跃开发（2026年最新版 3.x） |

**Caffeine 的基本用法**：

```java
Cache<String, Product> cache = Caffeine.newBuilder()
    .maximumSize(10_000)                     // 最大缓存条目
    .expireAfterWrite(10, TimeUnit.MINUTES)  // 写入后10分钟过期
    .refreshAfterWrite(5, TimeUnit.MINUTES)  // 5分钟后异步刷新
    .recordStats()                           // 开启命中率统计
    .build();

// 被动回源：缓存未命中时自动调用 load 方法
LoadingCache<String, Product> loadingCache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .build(key -> productService.getFromDB(key));
```

### 4.2.3 GuavaCache的三种过期策略与回源机制

这是高翔龙书中讲解最精细的部分之一。GuavaCache（Caffeine 同样适用）提供三种过期策略：

| 策略 | 行为 | 回源时其他线程 | 适用场景 |
|------|------|:---:|------|
| **expireAfterWrite** | 写入后固定时间过期 | 阻塞等待 | 数据有明确过期窗口 |
| **expireAfterAccess** | 最后一次访问后过期 | 阻塞等待 | 长时间不访问就淘汰 |
| **refreshAfterWrite** | 到期后异步刷新 | **返回旧值**（不阻塞） | 追求低延迟，可接受短暂旧数据 |

**关键机制**：`expireAfterWrite` 的回源操作使用 `ReentrantLock` 保证**单机只有一个线程执行回源**，其他线程阻塞等待。这避免了"缓存失效瞬间大量请求穿透到分布式缓存/数据库"（即缓存击穿，Cache Breakdown）。

`refreshAfterWrite` 的回源操作也是单线程执行，但**其他线程直接返回旧值**——这是"可用性优先"的选择。代价是：严格性不够，不能保证返回值一定是最新的。

> **生产陷阱**：如果使用 `refreshAfterWrite` 且旧值在回源完成前已经过期被 GC 回收，线程会返回 `null`——此时会触发大量请求穿透到下游，可能引发雪崩。解决方案：重写 `CacheLoader.reload()` 方法，在旧值过期时降级为同步阻塞回源。

### 4.2.4 off-heap：突破 GC 的性能优化

off-heap（堆外内存）是 Java 性能优化中的高级技术。高翔龙在书中对 off-heap 的讲解非常透彻。

**核心原理**：Java 对象默认在 Heap 中分配，由 GC 管理。`ByteBuffer.allocateDirect(int capacity)` 直接通过 `Unsafe.allocateMemory()` 在物理内存（非 Heap）中分配一块缓冲区。这个缓冲区：
- 不受 GC 管理（不会触发 GC 扫描）
- 可以通过 `-XX:MaxDirectMemorySize` 限制容量
- 由"冰山对象"模型管理：`DirectByteBuffer` 对象在 Heap 中（冰山尖），引用的内存在 off-heap（冰山水下部分），当 `DirectByteBuffer` 被 GC 回收时，`Cleaner` 会释放 off-heap 内存

**off-heap 的优势**：

| 维度 | Heap | off-heap |
|------|------|---------|
| GC 影响 | 受 GC 管理，可能触发 Full GC | 不受 GC 管理 |
| 容量上限 | 受 `-Xmx` 限制 | 受物理内存限制（可设 `-XX:MaxDirectMemorySize`） |
| I/O 路径 | 物理内存 → Heap（一次拷贝） | 直接在物理内存操作（避免 native→JVM heap 拷贝） |
| 序列化 | 可直接存储对象 | 需要手动序列化/反序列化 |
| 适用场景 | 频繁读写、大小适中的对象 | 大对象、生命周期长、需要避开 GC |

**生产中选择**：高翔龙推荐使用 **MapDB**（内存数据库），它封装了 off-heap、mmap 等特性，提供类似 `java.util.Map` 的 API。2026 年也可以考虑 **Chronicle Map**（超高性能 off-heap Map，微秒级延迟）。

> **跨书对照**：off-heap 的"冰山对象"模型与 Redis 的内存管理有异曲同工之处——两者都通过引用计数或类似机制管理生命周期，都追求将"热数据"放在最快的内存中。区别在于 Redis 是独立进程，off-heap 是同一进程内的直接内存。

## 4.3 Redis Cluster：从单机到分布式 Sharding

### 4.3.1 三种数据 Sharding 算法的第一性原理

单机 Redis 受限于内存容量和 CPU，突破单机瓶颈需要 **Sharding（分片）**——将数据分布到多个节点。高翔龙详细对比了三种路由算法：

**算法一：Hash 取模**

```
node_index = hash(key) % N
```

**优点**：实现简单，O(1) 寻址。
**致命缺陷**：增加或减少节点（N 变化）时，**几乎所有 key 的路由都会改变**，需要全量数据迁移。

**算法二：一致性哈希（Consistent Hashing）**

```
将 0 ~ 2^32-1 映射为一个哈希环
hash(node) → 节点在环上的位置
hash(key) → 顺时针找最近的节点
```

**核心优势**：扩容/缩容时，只影响环上相邻区间的数据，迁移量约为 1/N（N=节点数）。

**数据倾斜问题**：当节点数量少时，可能大量数据落在相邻节点之间，导致某些节点负载过高。解决方案：**虚拟节点**（Virtual Nodes）——每个物理节点映射为 100~200 个虚拟节点，均匀分布在环上，消除倾斜。

> **第一性原理**：一致性哈希为什么比 Hash 取模好？因为前者将映射空间从"固定的 N 个点"扩展为"连续的 2^32 个点"——节点的增减只影响环上相邻的一个区间，而不是全局重新映射。这本质是用搜索时间（O(log N)，在环上二分查找）换取了迁移成本的大幅降低。

**算法三：分槽算法（Hash Slot）**

Redis Cluster 使用的方案：

```
slot = CRC16(key) % 16384
根据 slot → node 的映射表，找到目标节点
```

**核心特性**：16384 个 Slot 是固定不变的。节点增减时，只需**移动 Slot 的所有权**，而不需移动 Slot 内的具体数据。Slot 是 Redis Cluster 的**基本迁移单位**——一个 Slot 要么属于节点 A，要么属于节点 B，不存在一个 Slot 跨多个节点的情况。

```java
// Jedis 源码中计算 Slot 的方法（JedisClusterCRC16.getSlot）
public static int getSlot(String key) {
    // HashTag.getHashTag 提取 {hash_tag} 部分，无hash tag则返回完整key
    return getCRC16(HashTag.getHashTag(key)) & (16384 - 1);
}
```

**为什么是 16384？** 官方解释：(1) 心跳包中需要携带完整的 Slot 位图（16384 bits = 2KB），如果用 65536 则心跳包 8KB，消耗过大；(2) 16384 个 Slot 对于大多数集群（<1000 节点）足够了。

| 算法 | 寻址复杂度 | 扩容影响 | 数据倾斜 | 代表 |
|------|:---:|:---:|:---:|------|
| Hash取模 | O(1) | 全局迁移 | 无（均匀） | 早期分库分表 |
| 一致性Hash | O(log N) | 局部迁移 | 有（需虚拟节点） | Memcached分布式 |
| 分槽 | O(1) | Slot迁移 | 无（均匀） | **Redis Cluster** |

## 4.4 多级缓存：用分层解决热点单点瓶颈

### 4.4.1 问题：为什么分布式缓存也有单点瓶颈？

Redis Cluster 解决了"数据分布"问题——不同的 key 落在不同的 Slot 上，Slot 分布在不同节点上。但对于大促的热卖商品：
- 所有用户请求都访问**同一个 key**（如 `product:sku_12345`）
- CRC16(key) % 16384 永远是同一个 Slot
- 同一个 Slot 在同一个节点上
- 无论集群有多少节点，**这个 key 只会打到一台 Redis 上**

这就是**热点问题（Hotspot）**——分布式水平扩容对热点 key 完全无效。

### 4.4.2 多级缓存架构

高翔龙的方案是**本地缓存 + 分布式缓存**的二层结构：

```
用户请求
    │
    ▼
┌─────────────┐
│  Nginx 接入层 │ ← 也可以缓存一层（proxy_cache，TTL < 本地缓存TTL）
└──────┬──────┘
       │
       ▼
┌─────────────────────────────────────────────┐
│  WebServer (本地缓存)                         │
│  ┌───────────────────────────────────┐       │
│  │ GuavaCache / Caffeine             │       │
│  │ - 热卖商品详情（活动前预加载）      │       │
│  │ - 热卖商品库存（短TTL，频繁刷新）   │       │
│  └───────────┬───────────────────────┘       │
└──────────────┼───────────────────────────────┘
               │ Cache Miss
               ▼
┌─────────────────────────────┐
│  Redis Cluster              │
│  - 非热点商品                │
│  - 本地缓存过期后的回源     │
└─────────────────────────────┘
```

**关键设计决策**：

| 数据分类 | 缓存位置 | TTL | 更新策略 |
|---------|---------|:---:|---------|
| 热卖商品详情 | 本地缓存 | 活动期间不变 | 预加载 + MQ主动推送 |
| 热卖商品库存 | 本地缓存 | 3~5秒 | expireAfterWrite 被动回源 |
| 非热卖商品 | Redis | 10分钟 | Cache Aside |
| 热点未知商品 | Redis | 正常TTL | 运行时热点自动发现（可选） |

**关于一致性的权衡**：高翔龙明确指出——**对于读场景，本地缓存中的库存数据与实际库存可以有短暂的不一致（脏读）**。这只会导致"用户以为还有库存但下单时售罄"，这是可接受的用户体验，不会导致超卖（超卖由写操作的原子性保证）。

### 4.4.3 本地缓存的更新策略

**被动更新（Pull）**：GuavaCache 的 `expireAfterWrite` / `refreshAfterWrite`——缓存过期时自动触发回源，对业务代码透明。

**主动更新（Push）**：通过消息队列推送数据变更事件：

```
商品管理后台修改商品 → 通知商品服务更新 Redis → 
MQ发送商品更新消息 → WebServer消费消息 → 更新本地缓存
```

主动更新的优势：**立即使缓存生效**，不一致窗口极小（消息投递延迟，通常 <100ms）。代价：引入 MQ 增加了架构复杂度 + 有消息丢失风险。

### 4.4.4 缓存穿透的多层防御

高翔龙讨论了缓存穿透（Cache Penetration）的应对策略——既包括传统的数据不存在穿透，也包括热点突然消失的请求穿透：

**第一层：热点自动发现**

大促开始前，运营团队提供已知热卖商品列表，开发团队预加载到本地缓存。但对于**运行时突然形成的热点**（如某条微博突然爆火），高翔龙提出了"热点自动发现平台"——通过日志系统统计调用频率，自动识别热点并通知交易系统。但他也坦诚：**这个方案存在滞后性**，在大促高峰期可能来不及。

**第二层：Redis Cluster 读写分离**

高翔龙的"不解决之解决"——与其在最上层识别热点，不如让底层足够强壮。通过增加 Redis Slave 节点并开启读写分离，即使热点 key 打在同一个 Slot 上，也可以被多个 Slave 节点分担读压力：

```java
// 使用 Lettuce 客户端开启 Cluster 读写分离（Lettuce 6.x+）
RedisClusterClient client = RedisClusterClient.create(redisURI);
// ReadFrom 通过 ClusterClientOptions 配置
ClusterClientOptions options = ClusterClientOptions.builder()
    .readFrom(ReadFrom.REPLICA_PREFERRED)  // 优先读 Replica（Slave）
    .build();
client.setOptions(options);
StatefulRedisClusterConnection<String, String> connection = client.connect();
// 至此，读请求会自动路由到 Slave 节点
```

| 方案 | 解决什么 | 代价 |
|------|---------|------|
| 热点自动发现 | 提前识别热点 | 实现复杂，有滞后性 |
| Redis Cluster 读写分离 | 让底层能扛住流量，不必识别 | 增加 Slave 节点成本 + 主从延迟 |
| 多级缓存 | 热点数据缓存到离业务最近的地方 | 一致性弱（最终一致性） |

**这三层不是"多选一"，而是"从最可靠到最精准"的叠加**：多级缓存是第一道防线（最精准但需人工配置），Redis 读写分离是第二道防线（自动但成本高），热点自动发现是第三道防线（自动化但有延迟）。三层同时启用，才能做到"有热点时不慌，没热点时也不浪费"。

## 4.5 高并发写：从行锁死锁到Lua原子操作

### 4.5.1 InnoDB 行锁为什么撑不住？

在 MySQL 中，对同一行数据的高并发写操作会竞争 **InnoDB 行锁（Record Lock）**。InnoDB 将并发写操作**串行化**——同一时刻只有一个事务能持有该行的锁，其他事务排队等待。

```
线程1: UPDATE stock=stock-1 WHERE sku='12345' AND version=1  ← 持有行锁
线程2: UPDATE stock=stock-1 WHERE sku='12345' AND version=1  ← 排队等待
线程3: UPDATE stock=stock-1 WHERE sku='12345' AND version=1  ← 排队等待
...
线程1000: UPDATE ...  ← 排队等待 → 连接池耗尽 → 服务不可用
```

**大库存抢购 vs 秒杀的区别**：

| 场景 | 库存量级 | 并发写压力 | 数据库能扛吗？ |
|------|:---:|:---:|:---:|
| **秒杀** | 100~1000 | 极高但很快结束 | 上游限流后可以（库存很快就扣完） |
| **大库存抢购** | 1万~10万+ | 高且持续 | **不行**——持续的写压力会耗尽所有数据库连接 |

高翔龙在云集遇到的正是大库存抢购——爆款商品库存数万到十几万，持续的并发写压力让 InnoDB 行锁成为瓶颈。

### 4.5.2 Redis WATCH/MULTI/EXEC 乐观锁方案

将库存扣减从 MySQL 迁移到 Redis，利用 Redis 的**单线程内存操作**天然避免了行锁问题。但需要保证不会超卖——这就用到了 Redis 的事务支持。

**WATCH 命令的内部原理**：

Redis 内部维护一个 `watched_keys` 字典（每个 `redisDb` 结构体包含），用于跟踪被监视的 key：
- 客户端执行 `WATCH key` → 将 `key → [client1, client2, ...]` 映射写入 `watched_keys`
- 任何修改命令（`SET`, `DECRBY`, `DEL` 等）执行后 → 调用 `touchWatchKey()` 检查 `watched_keys`
- 如果被修改的 key 有客户端在监视 → 标记该客户端为 `REDIS_DIRTY_CAS` 状态
- 客户端执行 `EXEC` 时 → 检测自身状态，如果被标记为 `DIRTY_CAS`，拒绝提交事务

```java
// Jedis 乐观锁库存扣减
Jedis jedis = jedisPool.getResource();
jedis.watch(sku);                          // 1. 监视库存 key
int stock = Integer.parseInt(jedis.get(sku));
if (stock >= deduction) {
    Transaction tx = jedis.multi();        // 2. 开启事务
    tx.decrBy(sku, deduction);             // 3. 队列化扣减命令
    List<Object> result = tx.exec();       // 4. 原子提交
    if (result != null && !result.isEmpty()) {
        log.info("扣减成功");
    }
}
jedis.unwatch();
```

**WATCH 碰撞问题**：高并发下大量线程同时 WATCH 同一个 key → key 频繁被修改 → 大量客户端被标记 `DIRTY_CAS` → `EXEC` 失败 → 需要重试。并发越高，碰撞概率越大，成功率越低。这是乐观锁的固有代价。

> **面试视角**：面试官问"Redis 的 WATCH 和 CAS 有什么关系？" → WATCH 本质上是 Redis 实现的"乐观锁"——在事务提交时检查 key 是否被修改（类似 CAS 的"比较"），如果未修改则提交（类似 CAS 的"交换"）。但 WATCH 的粒度是 key 级别的，而 CAS 的粒度是内存地址级别的。WATCH 的"比较"发生在 Redis 服务端，而 Java 的 AtomicInteger CAS 发生在 CPU 缓存行级别。

### 4.5.3 Lua脚本：原子操作的终极方案

WATCH 方案的致命缺陷是**碰撞重试**——高并发下成功率低。Lua 脚本方案通过**将读+判+写合并为一个原子操作**来消除碰撞：

```lua
-- Redis Lua 原子库存扣减脚本
local sku = KEYS[1]               -- 目标SKU
local num = tonumber(ARGV[1])     -- 扣减数量
local stock = tonumber(redis.call('GET', sku))
local result = 0
if stock >= num then
    redis.call('DECRBY', sku, num)
    result = 1                    -- 扣减成功
end
return result
```

**为什么 Lua 脚本能保证原子性？**

Redis 是单线程模型——所有命令串行执行。`EVAL` 执行 Lua 脚本时，Redis 将整个脚本视为**单条命令**——脚本执行期间不会有其他命令插入。这是由 Redis 的事件循环（aeEventLoop）保证的。

```java
// Jedis 中使用 EVALSHA 调用 Lua 脚本
String sha1 = jedisCluster.scriptLoad(luaScript, sku);
Object result = jedisCluster.evalsha(sha1, 
    Collections.singletonList(sku),           // KEYS
    Collections.singletonList("10"));         // ARGV
```

**为什么用 EVALSHA 而不是 EVAL？**

`EVAL` 每次传递完整的 Lua 脚本文本，`EVALSHA` 只传递 SHA1 摘要（40字节）。在高 QPS 场景下（如大促库存扣减 QPS 10K+），每次节省数 KB 的脚本传输，一天可节省数 GB 的网络开销。流程：`SCRIPT LOAD` 加载脚本 → Redis 缓存脚本+返回 SHA1 → 后续使用 `EVALSHA sha1` 调用。

**库存同步回数据库**：Redis 中扣减库存后，需要通过异步消息将库存变更写入数据库（见第3章 MQ 削峰方案），避免数据库承受高并发写压力。

### 4.5.4 三种库存扣减方案对比

| 方案 | 原子性 | 性能 | 碰撞 | 实现难度 |
|------|:---:|:---:|:---:|:---:|
| **MySQL 乐观锁** | ✅ 行锁保证 | 低（串行化） | 高（version 不匹配） | 低 |
| **Redis WATCH+事务** | ✅ CAS 保证 | 中 | 高（高并发碰撞） | 中 |
| **Redis Lua 脚本** | ✅ 单线程保证 | **高** | **无**（原子执行） | 中 |

## 4.6 CAS与原子操作原理

高翔龙在本章的最后深入讲解了 **CAS（Compare And Swap，比较与交换）** 的底层原理——这是理解乐观锁、原子操作、无锁编程的基础。

**CAS 的三个操作数**：
- **内存位置（V）**：需要操作的内存地址
- **旧预期值（A）**：你认为 V 当前的值
- **新值（B）**：要设置的值

CAS 的原子操作：**当且仅当 V 的值等于 A 时，将 V 设为 B**——这整个过程由一条 CPU 指令（如 x86 的 `cmpxchg` / `lock cmpxchg`）完成，不可分割。

```java
// AtomicInteger.getAndIncrement() 底层通过 Unsafe.getAndAddInt() 实现
// 核心逻辑：CAS 自旋，直到成功
public final int getAndAddInt(Object o, long offset, int delta) {
    int v;
    do {
        v = this.getIntVolatile(o, offset);  // 读取当前值
    } while (!this.compareAndSwapInt(o, offset, v, v + delta));  // CAS自旋
    return v;
}
```

**CAS 的两个经典问题**：

**ABA 问题**：线程 1 读到 A，线程 2 将 A→B→A，线程 1 的 CAS 发现"值还是 A"于是成功交换。但实际上值已经"变过去又变回来了一次"。解决方案：带版本号的 `AtomicStampedReference`。

**自旋开销**：高竞争场景下，大量线程反复 CAS 失败 → 空转消耗 CPU。解决方案：竞争激烈时用 `synchronized` 替代（线程阻塞而非自旋，减少 CPU 空转）。

> **面试视角**："CAS 和 synchronized 的区别？什么场景用哪个？" → CAS 是无锁乐观策略，线程不阻塞但会空转（适合低竞争）；synchronized 是悲观锁，线程阻塞（适合高竞争）。临界区短的场景用 CAS（如 `i++`），临界区长或有 I/O 的场景用 synchronized。

## 4.7 AliSQL：为秒杀定制的高性能 MySQL

高翔龙在书中介绍的 **AliSQL**（阿里开源 MySQL 分支）对秒杀场景做了特殊优化：**热点行批量提交**。

**核心优化原理**：

```
传统 InnoDB：
   线程1: UPDATE ... → 获得行锁 → 提交 → 释放锁
   线程2: UPDATE ... → 排队等锁 → 获得锁 → 提交 → 释放锁
   线程3: UPDATE ... → 排队等锁 → 获得锁 → 提交 → 释放锁
   （串行，每个线程一次网络往返+锁竞争）

AliSQL 批量提交：
   [线程1的UPDATE] [线程2的UPDATE] [线程3的UPDATE] ⋯ → 收集到同一个桶
   └────────────────────────────────────────────────────┘
                            ↓
       桶里的第一个事务一次性批量提交所有收集到的UPDATE
       （一次网络往返 + 一次锁获取 → N 个线程的写操作并行完成）
```

对热点行做 Hash → 每个桶对应一个热点行 → 桶里的第一个事务负责收集和批量提交。**将 N 个串行的单条 UPDATE 变成 1 个批量提交**，性能提升可达 100 倍（官方数据）。

> **2026 年补充**：AliSQL 的热点行批量提交优化后来被整合到了 AliSQL 的 InnoDB 引擎优化中。注意"100 倍"是官方在热点行高竞争特定 workload 下的极限测试数据（benchmark），通用场景不适用。

# 第5章 分库分表方案

> **注意**：原书第5章（5.2~5.4 节）因 MinerU 解析截断。以下内容基于本书第1-3章建立的知识体系（分布式事务、MQ最终一致性、缓存架构）和技术专家视角，结合分库分表领域的通用最佳实践重写。

## 5.1 数据库架构演变：从读写分离到水平分片

### 5.1.1 为什么单库一定会达到极限？

数据库的架构演变遵循一条清晰的路线：**单库 → 读写分离 → 垂直分库 → 水平分表**。每一步解决上一个阶段的瓶颈。

**单库瓶颈的两个维度**：

| 瓶颈维度 | 表现 | 触发条件 |
|---------|------|---------|
| **并发瓶颈** | 大量并发读写 → 连接数耗尽 → TPS下降 | 单库连接池 ~1000 |
| **容量瓶颈** | 单表数据量过大 → B+树深度增加 → 索引效率下降 | 单表 >500万行（经验值，取决于硬件） |

**读写分离（Read/Write Splitting）**：80% 流量是读，将读分流到 Slave → Master 只负责写 → 解决了并发瓶颈中的读部分。

```
Master (写) → binlog → Slave1 (读) / Slave2 (读) / SlaveN (读)
```

**问题遗留**：(1) 写入瓶颈依然存在（所有写都走 Master），(2) 单表数据量继续增长，即使读写分离也无法阻止表膨胀。

### 5.1.2 垂直分库（Vertical Sharding）

将不同业务的数据表拆分到不同的数据库实例：

```
拆分前：                          拆分后：
┌─────────────────────┐     ┌──────────┐ ┌──────────┐ ┌──────────┐
│  单库（所有表在一起）  │     │ 用户DB    │ │ 订单DB    │ │ 商品DB    │
│  t_user              │ →  │ t_user    │ │ t_order   │ │ t_product │
│  t_order             │     │ t_addr    │ │ t_suborder│ │ t_sku     │
│  t_product           │     └──────────┘ └──────────┘ └──────────┘
│  t_addr, t_sku, ...  │
└─────────────────────┘
```

**垂直分库的核心价值**：将"写瓶颈"从单库分散到多个库——用户库、订单库、商品库各写各的，互不竞争资源。

**垂直分库的局限**：无法解决**单表过大**的问题。如果订单表有 10 亿行，即使它独享一个数据库实例，查询效率依然会很低。这就需要水平分表。

### 5.1.3 水平分表（Horizontal Sharding）

将同一张表的数据，按一定规则拆分到多个结构相同的子表中：

```
拆分前：                          拆分后：
┌─────────────────┐     ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│  t_order (10亿行) │     │ 订单DB_01 │ │ 订单DB_02 │ │ 订单DB_03 │ │ 订单DB_04 │
│                  │ →  │ t_order_0│ │ t_order_0│ │ t_order_0│ │ t_order_0│
│                  │     │ t_order_1│ │ t_order_1│ │ t_order_1│ │ t_order_1│
└─────────────────┘     └──────────┘ └──────────┘ └──────────┘ └──────────┘
                        每个库：10亿/4 = 2.5亿行
                        每个表：2.5亿/2 = 1.25亿行（If分成2个表）
```

**完整架构演进路径**：

```
阶段1：单库单表        阶段2：读写分离         阶段3：垂直分库          阶段4：水平分表
┌──────────────┐    ┌─────┬─────┐      ┌─────┐ ┌─────┐      ┌─────────┬─────────┐
│ MySQL        │    │M/Slave│Slave│      │用户  │ │订单  │      │订单DB_01│订单DB_02│
│ All tables   │ →  │┌───┐ │     │ →   │DB   │ │DB   │ →   │t_order_0│t_order_0│
└──────────────┘    ││ M │ │     │      │     │ │     │      │t_order_1│t_order_1│
                    │└───┘ │     │      └─────┘ └─────┘      └──────────┴──────────┘
                    └─────┴─────┘
 问题：并发+容量       解决：读写分离          解决：写入分散           解决：表体积分散
                                     新问题：单表过大→水平分表
```

## 5.2 分库分表路由策略

### 5.2.1 路由算法选择

分库分表的核心问题：**给定一个 key（如用户ID），如何确定目标库和目标表？**

**方案一：Hash 取模**

```java
// 4个库，每库2个分表
dbIndex = hash(userId) % 4;
tableIndex = hash(userId) % 2;
// 目标：DB_{dbIndex}.t_order_{tableIndex}
```

优点：简单。缺点：扩容时（4→8个库），所有数据的路由都改变 → 需要**全量数据迁移**。

**方案二：一致性哈希 + 虚拟节点**

将数据库节点映射到哈希环上，每次扩容只影响相邻节点的数据。实际中较少使用（运维复杂度高），但在缓存层（Memcached）中广泛应用。

**方案三：区间路由（Range Sharding）**

```
userId: 1~1000万      → DB_01
userId: 1000万~2000万  → DB_02
userId: 2000万~3000万  → DB_03
```

优点：扩容简单（只拆分最后一段）。缺点：可能存在热点（新注册的用户集中在最后一段）。

**方案四：基因法（复合分片键）**

在用户 ID 中嵌入分库信息：

```java
// orderId 生成规则：后10位 = Sequence，前2位 = userId % 64（分库基因）
long orderId = (userId % 64) << 10 | sequence;
// 从 orderId 反推分库位置
int dbIndex = (int) (orderId >> 10) & 63;
```

优点：不需要额外的查询表，直接从 ID 就能路由到目标库。

### 5.2.2 分片键（Sharding Key）的选择

分片键的选择是最关键的决策，选错意味着灾难：

| 分片键 | 优点 | 缺点 |
|--------|------|------|
| **userId** | 用户维度所有数据在同一库，便于查询 | 商家/商品维度查询需要跨库 |
| **orderId** | 订单均匀分布 | 按用户查所有订单需要跨库 |
| **时间（按日/月）** | 便于归档，扩容简单 | 热点不均（最新数据访问最频繁） |

**核心原则**：分片键应选择**最高频的查询维度**。如果 90% 的查询是"查用户的订单"，就应该按 userId 分片；如果 90% 是"查今日订单"，就应该按时间分片。

## 5.3 ShardingSphere：分库分表的工业级实践

高翔龙在书中使用的是 **Shark** 中间件（云集自研）。2026 年，**Apache ShardingSphere**（由 Sharding-JDBC 发展而来）是业界标准。

**ShardingSphere-JDBC 的核心配置**：

```yaml
# 数据源配置
spring:
  shardingsphere:
    dataSources:       # ShardingSphere 5.x 使用复数 dataSources
      names: ds0, ds1
      ds0: # 第一个分库
        url: jdbc:mysql://db0:3306/order_db
      ds1: # 第二个分库

    # 分片规则
    rules:
      sharding:
        tables:
          t_order:
            actualDataNodes: ds$->{0..1}.t_order_$->{0..1}  # 2库×2表
            databaseStrategy:
              standard:
                shardingColumn: user_id
                shardingAlgorithmName: database_inline
            tableStrategy:
              standard:
                shardingColumn: order_id

        shardingAlgorithms:
          database_inline:
            type: INLINE

            type: INLINE
            props:

```

**ShardingSphere 的三种模式**：

| 模式 | 部署方式 | 性能 | 适用场景 |
|------|---------|:---:|------|
| **ShardingSphere-JDBC** | 客户端 JAR 包嵌入应用 | 最高（无网络跳转） | Java 应用首选 |
| **ShardingSphere-Proxy** | 独立部署的数据库代理 | 中（多一层网络） | 多语言、异构系统 |

## 5.4 全局唯一ID生成方案

分库分表后，**自增主键不再全局唯一**——每个库各自维护自增序列，不同库可能产生相同的 ID。需要一个**全局唯一 ID 生成方案**。

### 5.4.1 方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **UUID** | 随机生成 | 本地生成，最简单 | 字符串，索引性能差，非递增 |
| **数据库自增** | 单表生成自增ID | 严格递增 | 单点瓶颈 |
| **雪花算法** | 时间戳+机器ID+序列号 | 高性能，趋势递增 | 依赖时钟同步 |
| **美团 Leaf** | 号段模式 + 双 Buffer | 高性能，可扩展 | 实现复杂，ID 不连续 |
| **滴滴 Tinyid** | 预分配号段 | 高性能，HTTP接口 | ID 不连续 |

### 5.4.2 雪花算法（Snowflake）详解

Twitter 开源的分布式 ID 生成算法，是生产环境最常用的方案：

```
┌──────────┬──────────┬──────────┬──────────┐
│ 41bit    │ 10bit    │ 12bit    │
│ 毫秒时间戳│ 机器ID    │ 序列号    │
│          │ (5bit机房 │          │
│          │ +5bit机器)│          │
└──────────┴──────────┴──────────┘
总长度：64bit (long)
```

**关键设计**：
- **41位时间戳**：支持 69 年（41 bits = 2,199,023,255,552 ms ≈ 69.7年），起始纪元（epoch）通常是实现自定义的——Twitter 原版 epoch 为 `2010-11-04`，美团 Leaf 使用 `2017-01-01`
- **10位机器ID**：支持 1024 台机器
- **12位序列号**：同毫秒内支持 4096 个 ID

**生产陷阱——时钟回拨（Clock Rollback）**：

NTP（Network Time Protocol）校时可能导致系统时钟回拨（向后跳变）。如果时钟回拨 100ms，雪花算法可能生成在上一个时间点已分配过的 ID，导致**ID 重复**。

**解决方案**：
1. **美团 Leaf**：如果检测到回拨，分配一个全新的 `workerId`（通过 ZooKeeper 维护）
2. **容忍回拨**：如果回拨时间 < 阈值（如 5ms），等待追上后再生成
3. **扩展位数**：生成时使用过去的最大时间戳，拒绝回拨期间的请求

## 5.5 分布式事务与最终一致性

分库分表后，**一个订单可能跨多个数据库**——订单在 DB_01，流水在 DB_02。本地事务失效了。

### 5.5.1 跨库事务的挑战

```
用户下单：
  INSERT INTO DB_01.t_order (...)   -- 订单库
  UPDATE DB_02.t_inventory ...      -- 库存库（不同实例！）
```

如果第一步成功、第二步失败：数据不一致。这是分库分表带来的最核心问题。

### 5.5.2 方案的演进

| 方案 | 一致性 | 性能影响 | 复杂度 | 适用 |
|------|:---:|:---:|:---:|------|
| **2PC/XA** | 强一致 | 极差 | 高 | 银行核心 |
| **TCC** | 最终一致（业务级强） | 中 | 很高 | 资金交易 |
| **Seata AT** | 最终一致 | 中 | 低 | 电商主流 |
| **本地消息表+MQ** | 最终一致 | 低 | 中 | 异步场景 |
| **定时任务对账** | 最终一致 | 低 | 低 | 兜底方案 |

> **跨书对照**：释慧利第3章从 2PC/3PC 协议层面完整推导了分布式事务的故障模型；高翔龙从电商工程实践的角度选择了 MQ + 定时对账的最终一致性路线。两者是同一问题的理论与实践两个维度。

### 5.5.3 订单场景的最终一致性实战

高翔龙的方案（第3章已构建基础）：

```
下单流程（最终一致性方案）：

1. 订单服务：INSERT t_order (status=PENDING) → 本地事务提交
2. 发送 MQ 事务消息（RocketMQ Half Message）
3. 库存服务消费消息 → 扣减库存
4. 积分服务消费消息 → 增加积分
5. 如果 3 或 4 失败 → MQ 固定延迟等级重试 → 16次失败进 DLQ
6. 定时任务（如第1章提到的 FollowCounterRepairJob）定期对账：
   - 检查状态为 PENDING 超时的订单
   - 检查订单金额与库存扣减是否一致
   - 不一致则触发人工介入或自动补偿
```

**核心思想**：**接受短暂的数据不一致，用异步机制保证最终一致**。这是互联网场景下分布式事务的工程最佳实践。

## 5.6 分库分表的代价与平滑扩容

### 5.5.4 分库分表后的高可用架构

分库分表将数据分散到多个数据库实例，同时也将**故障爆炸半径**分散了——一个库挂了，只影响该分片的数据，而不是全部。但这要求每个分片本身具备高可用能力。

**分片级 HA 的经典方案**：

```
每个分片 = 一组主从集群
┌──────────────────┐  ┌──────────────────┐
│    Shard-01       │  │    Shard-02       │
│  ┌────┐ ┌────┐   │  │  ┌────┐ ┌────┐   │
│  │Master│Slave│   │  │  │Master│Slave│   │
│  └──┬─┘ └────┘   │  │  └──┬─┘ └────┘   │
│     │             │  │     │             │
│  MHA/Orchestrator │  │  MHA/Orchestrator │ ← 每个分片独立部署
└──────────────────┘  └──────────────────┘
```

**三种 HA 方案的对比**：

| 方案 | 原理 | 切换时间 | 数据丢失 | 适用场景 |
|------|------|:---:|:---:|------|
| **MHA（Master High Availability）** | 监控 Master，故障时自动选新 Master + 补同步 relay log | 10-30s | 极少（异步复制下可能丢少量） | 强一致性要求中等的场景 |
| **Orchestrator** | 拓扑感知的故障检测 + 自动恢复，支持钩子脚本 | 10-30s | 极少 | 复杂拓扑、多数据中心 |
| **MySQL Group Replication（MGR）** | 基于 Paxos 的多主/单主复制，自动故障检测 | <1s（单主模式） | 零（多数派确认） | 强一致性要求高，但性能开销大 |
| **Semi-Sync Replication** | Master 等待至少一个 Slave 确认后才返回 | N/A（需配合 MHA） | 零 | 降低异步复制的丢数据风险 |

**ShardingSphere 的读写分离与 HA 配置**：

```yaml
rules:
  - !READWRITE_SPLITTING
    dataSources:
      shard_01_rw:
        writeDataSourceName: ds_01_master
        readDataSourceNames:
          - ds_01_slave_1
          - ds_01_slave_2
        loadBalancerName: round_robin
      shard_02_rw:
        writeDataSourceName: ds_02_master
        readDataSourceNames:
          - ds_02_slave_1
        loadBalancerName: round_robin
```

**分片 HA 的三个关键运维考量**：

1. **故障检测延迟**：MHA 默认每 3 秒检测一次 Master 心跳，故障从发生到检测最坏 3 秒。对于秒杀场景，3 秒可能太长——可调低检测间隔，但误判风险增加。

2. **切换期间的路由**：ShardingSphere 在主从切换期间需要感知新的拓扑。如果使用 Proxy 模式，切换后 Proxy 需要重新加载数据源配置；JDBC 模式需要应用重启或依赖动态数据源刷新。

3. **跨分片故障的级联影响**：如果多个分片同时出问题（如共享同一个机架），即使单个分片有 HA，也救不了全局——需要**跨机房分片部署**，确保分片分布在不同物理位置。

> **跨书对照**：王伟峰《深入高可用系统原理与设计》第4章从分布式锁和选主算法的角度讲解了"如何保证关键时刻只有一个 Master"，这与分库分表 HA 中 MHA/Orchestrator 的选主逻辑一脉相承。江峰《分布式高可用算法》第5章则从失败检测的算法层面给出了形式化保证。


### 5.6.1 分库分表的代价

分库分表虽然解决了容量和性能瓶颈，但引入了巨大的额外复杂度：

| 代价 | 描述 | 缓解方案 |
|------|------|---------|
| **跨库 JOIN 不可用** | 不同库的数据无法 SQL JOIN | 应用层聚合 / 冗余字段 / 反范式设计 |
| **分布式事务** | 跨库写入没有本地事务保证 | MQ 最终一致性 + 定时对账 |
| **全局 ID** | 自增 ID 不唯一 | 雪花算法 / Leaf |
| **分页查询** | `LIMIT offset, count` 跨库不准确 | 全局二级索引 / ES |
| **扩容迁移** | 需要重新分布数据 | 双写 + 增量迁移 |
| **SQL 限制** | 部分SQL不支持（如 `GROUP BY` 跨分片） | 限制不支持的操作 / 使用 ShardingSphere 的 federation |

### 5.6.2 平滑扩容方案

分库分表后最棘手的运维问题是**扩容**——从 4个库扩展到 8个库时，如何不中断服务地迁移数据？

**停机扩容（不推荐）**：停止服务 → 全量数据迁移 → 修改路由规则 → 重启。停服时间随数据量线性增长。

**平滑扩容（双写 + 增量迁移）**：

```
阶段1：双写（暂停服务 0 秒）
  应用同时写入老库（4库）和新库（4库）→ 老库仍然对外读

阶段2：历史数据迁移
  后台异步任务将老数据从 4 个老库迁移到 4 个新库

阶段3：校验
  对比老库和新库的数据是否一致

阶段4：切换
  读也从新库开始 → 修改路由规则 → 下线老库
```

**核心保障**：全流程不停服，用户无感知。代价是实现复杂度高——需要修改数据访问层（DAL）支持双写+灰度切换。

## 5.7 本章核心观点总结

### 第4章 高并发读写

1. **缓存是分层体系，不是单一技术**：CDN → 反向代理 → 本地缓存 → 分布式缓存 → 数据库，每一层是上一层的保护伞。缓存的本质是"距离计算最近的数据副本"。

2. **本地缓存的适用边界**：变化频率低、一致性容忍度高、频繁访问的数据。off-heap 突破了 JVM Heap 限制，适合大对象和长生命周期数据。

3. **Redis 三种 Sharding 算法各有其位**：分槽算法（Redis Cluster）是 Hash 取模和一致性哈希之间的工程平衡——固定 16384 个 Slot，迁移以 Slot 为单位。

4. **多级缓存是解决热点的分层方案**：分布式缓存无法解决热点 key 的单点瓶颈（同一个 key 永远落在同一个 Slot），本地缓存将热点分散到每个 WebServer 节点。

5. **Lua 脚本是 Redis 原子操作的终极武器**：将"读+判+写"合并为单次网络请求中的原子操作，消除 WATCH 碰撞，同时显著降低网络开销。EVALSHA 相比 EVAL 在高 QPS 下每天节省数 GB 带宽。

### 第5章 分库分表

6. **数据库演变不可逆**：读写分离→垂直分库→水平分表。每一步解决上一阶段的瓶颈，同时引入新的复杂度。架构的本质是"用复杂度换容量"。

7. **分片键的选择是分库分表的灵魂**：选错分片键意味着大量跨库查询，无法回退。核心原则：选择最高频的查询维度作为分片键。

8. **平滑扩容是分库分表运维的最大挑战**：双写+增量迁移+校验+灰度切换的四阶段方案，全流程不停服。代价是实现复杂度极高。

9. **分布式事务在分库分表场景下的最佳实践**：接受最终一致性，用 MQ 事务消息 + 定时对账兜底。不强求 2PC 的强一致性（太贵），也不过度依赖补偿（太复杂）。

10. **全局 ID 生成必须处理时钟回拨**：雪花算法是最常用的方案，但 NTP 校时导致的时钟回拨必须用等待/换 workerId 等方式处理，否则会产生重复 ID。

> **跨书学习建议**：
> - 第4章的多级缓存方案与第3章的消息队列更新策略是同一套基础设施
> - 第5章的分库分表路由算法与第4章的 Redis Sharding（分槽）共享相同的数学原理
> - 第5章的分布式事务方案是对第1章 1.2.3 节 + 第3章 MQ 最终一致性的实战展开

### 本章面试高频题

**Q1: Redis 缓存穿透、缓存击穿、缓存雪崩分别是什么？各自怎么防御？**

> **面试官意图**：这三者是最基础的缓存面试题，但 80% 的候选人分不清"穿透"和"击穿"。面试官真正想听的是：你能否区分三个概念的本质差异，并给出不同场景下的正确防御方案。

**回答要点**：

| 概念 | 触发条件 | 防御 |
|------|---------|------|
| 穿透 | 查询**不存在**的数据 | 布隆过滤器（最有效）/ 空值缓存（有限场景） |
| 击穿 | 热点 key **过期瞬间** | 互斥锁回源 / 逻辑过期+异步刷新 |
| 雪崩 | 大量 key **同时过期**或 Redis 宕机 | 过期时间加随机值 / Redis Cluster / 多级缓存兜底 |

> **追问到第二层**："布隆过滤器有误判，误判了怎么办？"→ 布隆过滤器只有 False Positive（说不存在的一定不存在，说存在的可能不存在），所以误判只会把"不存在的 key"当成"存在"放行——此时才穿透到数据库，概率 = 误判率（如 1%）。只需要在 Redis 中再用空值缓存（短 TTL）兜底那 1% 的漏网之鱼。

**Q2: Redis Cluster 的 16384 个 Slot 是怎么来的？为什么不是 65536？**

> **面试官意图**：考察你是否思考过"为什么是 16384 而不是其他数字"，而非仅仅背出这个数字。

**回答要点**：
1. CRC16 的哈希空间是 65536（2^16），但 Redis 选了 16384
2. 核心原因：心跳包中需要携带完整的 Slot 位图 → 16384 bits = 2KB，65536 bits = 8KB
3. 权衡：16384 足够分配给 1000 个节点（每个节点约 16 个 Slot），对于绝大多数集群规模足够了
4. 少于 16384 会导致 Slot 太少、数据分布不够均匀

> **追问到第二层**："如果集群超过 1000 个节点怎么办？"→ Redis 官方不建议单集群超过 1000 个节点——超过此规模用 Proxy 层（如 Twemproxy）或应用层二次路由。Redis Cluster 的设计哲学是"小集群 + 多集群"，而非"超大集群"。

**Q3: 分库分表后，跨库 JOIN、跨库分页、跨库事务怎么处理？**

> **面试官意图**：面试官问你分库分表的代价，不是在问"代价是什么"（背诵），而是问"你怎么解决"（架构能力）。

**回答要点**：

| 问题 | 根本原因 | 解决方案 |
|------|---------|---------|
| 跨库 JOIN | 数据在不同数据库实例 | 冗余字段 / 反范式设计 / 应用层聚合 / 全局二级索引（ES） |
| 跨库分页 | `LIMIT offset, count` 需要全局排序 | ShardingSphere Federation引擎 / 二次查询归并（内存中排序） |
| 跨库事务 | 本地事务无法跨实例 | MQ 最终一致性 / Seata AT / TCC / 定时对账兜底 |

> **追问到第二层**："冗余字段怎么保证一致性？"→ 冗余字段的一致性本质上是分布式事务问题。在电商场景下，通常用 MQ 异步更新 + 定时对账——接受短暂不一致。如果对一致性要求极高（如资金），则不宜分库，而是用读写分离或专库专表。

**Q4: 库存扣减为什么用 Lua 脚本而不是 Redis 事务（WATCH/MULTI/EXEC）？**

> **面试官意图**：考察对两种方案 trade-off 的深入理解。

**回答要点**：
1. WATCH 在高并发下有**碰撞问题**——并发越高，WATCH 碰撞概率越大，`EXEC` 失败率越高，需要业务层重试
2. Lua 脚本将"读+判+写"合并为**单条原子命令**——不存在碰撞，成功率 100%（只要库存够）
3. Lua 脚本减少了网络往返——一次 `EVALSHA` 替代 `WATCH + GET + MULTI + DECRBY + EXEC`（5 次网络往返）
4. 代价：Lua 脚本执行时会**阻塞 Redis**（因为是单线程），但库存扣减逻辑极短（~100 bytes Lua），基本无影响

> **追问到第二层**："Lua 脚本如果执行时间太长，会影响其他命令吗？"→ 会。Redis 单线程模型意味着 Lua 脚本执行期间所有其他命令都会被阻塞。生产中的实践：Lua 脚本必须在毫秒级完成，不能包含复杂的循环或大 key 操作。如果脚本执行时间可能超标，用 `SCRIPT KILL` 终止（但只能终止只读脚本）。

**Q5: 布隆过滤器的误判率公式 `P = (1 - e^(-kn/m))^k` 怎么调优？**

> **面试官意图**：考察你是否真正用过布隆过滤器，还是只背了概念。

**回答要点**：
1. m（bit 数组大小）：由可用内存决定，越大误判率越低
2. k（哈希函数个数）：由 `k = (m/n) * ln2` 决定是最优值，太大反而增加误判率（因为每个 bit 被多次 set，碰撞增多）
3. n（预估元素数量）：**低估 n 是生产中最常见的错误**——如果实际元素远超预估，误判率会急剧上升
4. 生产中不能"扩容"布隆过滤器（bit 数组不能动态增长），所以 n 的预估必须留有充分余量

> **追问到第二层**："如果预估偏差太大，有什么补救办法？"→ 新建一个更大的布隆过滤器，两阶段查询：先查旧 filter → 如果命中，可能是误判，再查新 filter 确认 → 如果新 filter 不存在 → 旧 filter 误判。这是"滚动布隆过滤器"模式。
