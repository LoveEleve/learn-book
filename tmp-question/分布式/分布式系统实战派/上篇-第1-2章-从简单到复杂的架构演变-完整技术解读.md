# 第1-2章 从简单到复杂的架构演变 — 技术专家深度解读

> **原著**：张伟洋《分布式系统实战派》(2024) 第1-2章
> **本章定位**：建立"问题驱动"的架构成长地图——不是教你怎么建系统，是教你在每个阶段面临什么问题时做何决策

---

## 引言：这本书为什么不是"又一本分布式入门书"

市面上 90% 的分布式入门书都是"辞典式"组织——Ch3 讲缓存、Ch4 讲消息、Ch5 讲事务——每章独立，看完不知道这些技术是什么关系、什么时候该用哪个。

张伟洋的独特之处在于**"问题驱动"的顺序**：

```
单体够用 → 什么时候不够？→ 集群 → 什么时候不够？→ 读写分离
→ 什么时候不够？→ 分库分表 → 什么时候不够？→ 微服务
→ 什么时候不够？→ 消息队列 → ... → 最终形态
```

每一章开头都是一句"**当你遇到 X 问题时，就需要 Y 技术**"。这是工程成长的真实轨迹，不是教材的目录结构。

## Ch1 从单体到微服务：一个系统的"长大"过程

### 1.1 演变全貌

```
单体(1台机器) → 集群(N台相同机器) → 读写分离(主从)
    → 分库分表(水平拆分) → 微服务(业务拆分)
    → 中间件(缓存/MQ/搜索) → 容器化(Docker/K8s)
    → 高可用(多活/备份/容灾) → 持续交付
```

**关键问题**：每一步的触发条件是什么？

| 阶段 | 之前的状态 | 触发条件 | 做什么 |
|------|----------|---------|--------|
| 单体 | 代码+DB 在同一台机器 | 用户增长，CPU/内存告警 | 独立部署 WebServer + DB |
| 集群 | 一台 WebServer | 单机 QPS 到达上限 | Nginx 反向代理 + 多节点 |
| 读写分离 | 单库扛所有 | 读 QPS 超过单库容量 | 主写从读 + 主从同步 |
| 分库分表 | 单表千万行+ | 写入变慢、索引失效 | 按分片键水平拆分 |
| 微服务 | 单体应用几十万行代码 | 团队>10人、不同模块变更频率差异大 | 按业务域拆服务 |
| 消息队列 | 同步调用链路过长 | 上下游处理速度不匹配 | 异步解耦 + 削峰 |
| 异地多活 | 单机房容灾能力不足 | 机房断电/光纤挖断等极端场景 | 多机房同时提供服务 |

**每一步的"不做的代价"**：架构决策不只是"加了会更好"，更重要的是**"如果不加，后果是什么"**：

| 阶段 | 如果跳过 | 会怎样 |
|------|---------|--------|
| 不集群 | 单机继续扛 | QPS 到顶 → 请求排队 → P99 暴涨 → 用户流失 |
| 不读写分离 | 单库扛所有流量 | 读 QPS 10万+ → 数据库 CPU 100% → 写入也被拖慢 |
| 不分库分表 | 单表 5000万行 | B+Tree 深度 4层 → 磁盘 IO 翻倍 → 单条查询从 5ms→50ms |
| 不微服务 | 单体 50万行代码 | 改一行编译 10分钟 → 10个人同时改 → 每天至少一次冲突 |
| 不异地多活 | 只有单机房 | 机房断电 → 全站不可用 → 每分钟损失 XX 万 |

### 1.2 每一步的正确决策

#### 单机 → 集群

```
❌ "系统慢了，加机器" — 没分析慢在哪
✅ 先看瓶颈：是 CPU 还是 IO？是应用层还是数据库？
   → 应用层瓶颈 → 集群（水平扩容有效）
   → 数据库瓶颈 → 读写分离、索引优化（加机器没用）
```

#### 集群 → 读写分离

**关键参数**：主从延迟决定读的一致性窗口

```sql
-- 查看主从延迟
SHOW SLAVE STATUS\G
-- Seconds_Behind_Master: 0  ← 理想
-- Seconds_Behind_Master: 30 ← 半分钟延迟，读从库可能看不到刚写入的数据
```

**决策**：能接受 N 秒的读延迟吗？
- 能 → 读写分离（主写从读）
- 不能 → 读主库（或半同步复制）

#### 读写分离 → 分库分表

**分片键选择是第一关**：

| 分片键 | 优点 | 缺点 |
|--------|------|------|
| user_id | 用户维度查询全命中单库 | 跨用户查询（如运营统计）需全库扫描 |
| order_id | 订单均匀分布 | 按用户查订单需跨库 |
| time | 天然范围查询 + 归档方便 | 最近时间的热库压力集中 |

**没有完美分片键**——只能为最高频的查询模式选。

#### 微服务拆分的真实难题

> "我已经按业务拆了 10 个微服务，为什么系统反而更慢了？"

拆得太碎的三宗罪：
1. **RPC 延迟叠加**：一个用户请求经过 8 个服务 → 8 次网络往返 → P99 从 50ms 变成 200ms
2. **分布式事务成本**：原来一个本地事务搞定，现在要 Saga/TCC
3. **运维复杂度**：10 个服务的日志、监控、部署、配置各有各的问题

**反模式识别**："微服务 = 一个接口一个服务" → 立刻停手，你的拆分粒度错了。

## Ch2 后端系统全景图：几张图看懂一个系统

### 2.1 从请求到响应的完整路径

```
用户浏览器
  ↓ DNS
CDN（静态资源）
  ↓ 源站
Nginx/LVS（接入层）
  ↓ 反向代理
API Gateway（网关层）
  ↓ 路由 + 鉴权 + 限流
WebServer / BFF（聚合层）
  ↓ RPC
Service Layer（服务层：用户/订单/商品/支付...）
  ↓ 读写
Cache（Redis） + DB（MySQL 主从、分库分表） + MQ（RocketMQ）
  ↓ 异步
Search（Elasticsearch） + Big Data（Hadoop/Spark/Flink）
  ↓
Monitoring（Prometheus + Grafana + SkyWalking）
```

### 2.2 每一层的核心组件

| 层 | 核心组件 | 解决的问题 | 详细出处 |
|----|---------|-----------|---------|
| **CDN** | 阿里云 CDN / CloudFront | 静态资源加速，离用户最近 | 高翔龙 §1.1.2 + 本书 Ch4 |
| **接入** | Nginx / LVS / BFE | 负载均衡、SSL 卸载、简单限流 | 高翔龙 §3.2.3 |
| **网关** | Spring Cloud Gateway / APISIX | 鉴权、路由、灰度、聚合 | 高翔龙 §1.1.8 |
| **服务** | Dubbo / Spring Cloud | RPC 通信、服务治理 | 高翔龙 §1.2 |
| **缓存** | Redis Cluster | 热点数据加速、分布式锁 | 高翔龙 Ch4 + 本书 Ch6 |
| **数据库** | MySQL（主从+分库分表） | 持久化 + 事务 | 高翔龙 Ch5 + 余春龙 Ch6 |
| **消息** | RocketMQ / Kafka | 异步解耦、削峰、最终一致性 | 高翔龙 §3.4 + 本书 Ch8 |
| **搜索** | Elasticsearch | 全文检索、日志分析 | 本书 Ch6 |
| **监控** | Prometheus + SkyWalking | 可观测性三支柱 | 性能优化 Ch1 |

### 2.3 系统的"成长基因"：不管多复杂，核心就四件事

> 任何一个分布式系统，不管多复杂，拆开来看就四件事。

```
存储（数据放哪）  ←→  计算（谁处理数据）
    ↕                  ↕
通信（怎么传数据） ←→ 协调（谁来做决策）
```

| 核心 | 一句话 | 对应的技术栈 |
|------|--------|-------------|
| **存储** | 数据持久化在什么地方 | MySQL/Redis/ES/HDFS/TiDB |
| **计算** | 如何处理业务逻辑 | Dubbo 服务、Flink 流计算、MapReduce 批处理 |
| **通信** | 服务和数据之间怎么传递消息 | HTTP/gRPC/MQ/WebSocket |
| **协调** | 多个组件如何达成一致 | ZK/etcd/Nacos、共识算法、分布式锁 |

**面试金句**："当你接触一个新的分布式系统，第一件事不是看它用了什么技术——而是找到它的存储模型、计算模型、通信协议、协调机制。"

## 架构决策的常见陷阱

| # | 陷阱 | 真实后果 | 案例 |
|---|------|---------|------|
| 1 | **过早分库分表** | 日活 1000 分了 32 个库——跨库 JOIN 全废、运维成本暴涨 | 创业公司半年后 DAU 5000，32 个库 90% 空闲 |
| 2 | **盲目加机器不解瓶颈** | DB CPU 100% 还加 WebServer——请求排队更严重 | 加了 10 台机器，P99 从 200ms 涨到 2000ms |
| 3 | **微服务 = 一个接口一个服务** | 用户下单一次经过 12 次 RPC——P99 300ms+ | 80% 的请求降级才能正常返回 |
| 4 | **异步消息当成同步 RPC 用** | 发 MQ 后同步轮询等结果——线程池全被阻塞 | 1000 并发 → 1000 个线程在轮询 → OOM |

## 面试高频题

**Q1：一个日活 10 万的电商系统，预期半年后日活 1000 万，你会如何规划架构演变？**

不是一口气设计 1000 万 DAU 的最终架构。分三步：第一步，先看当前瓶颈——是数据库撑不住还是 WebServer QPS 不够？第二步，接下来 3 个月的目标：读写分离 + Redis 缓存 + CDN 静态加速 → 预期能撑到 50 万 DAU。第三步，半年后：分库分表 + 微服务拆分 + 消息队列削峰 → 1000 万 DAU。关键是**每一步做完了验证数据，再决定下一步的触发时间**，不是按计划表走。

> **追问**："为什么不一开始就做分库分表？"
>
> 分库分表是不可逆的——做了就回不去。一旦分了，跨库 JOIN 不能用了、事务变复杂了、扩容数据迁移需要专项工具。日活 10 万就分库分表，等于为了未来的可能性，现在就开始承担全部的维护代价。**架构的复杂度是有成本的——只在必要的时候引入。**

**Q2：你如何判断一个系统该不该拆成微服务？**

三个硬指标：1) 团队人数 >10 且不同小组负责不同业务模块；2) 不同模块的变更频率差异大——商品详情页一周改一次、结算一个月改一次；3) 某个模块的故障频繁影响其他模块——因为代码耦合导致的连锁故障。三个中满足两个就该拆。

> **追问**："如果三个指标都不满足，但老板说'我们要做微服务'呢？"
>
> 先不要反驳。拿出当前系统的数据——"目前团队 5 人、日活 5 万、QPS 500，微服务化后需要增加 2 个运维编制 + 全链路监控 + 分布式事务处理，成本每年增加 ~50 万。如果我们半年后日活到 50 万，到时再做——成本一样，但这半年的时间可以用来做更多业务需求。" 用数据说话，不是用"我觉得"。

## 本章小结

> "从简单到复杂，不是一个技术栈堆叠的过程，而是一个问题驱动的决策链条——先遇到问题，再引入解决方案。"

张伟洋这本书的前两章不做技术深度，做的是**路线图**——告诉你分布式系统的全貌长什么样，以及你是先到哪一站、再到哪一站。这张地图的价值在于：你不会再困惑"学了 Redis 之后该学什么"，因为你知道每一步的选择是解决什么问题。
