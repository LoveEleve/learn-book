## Ch3-4 微服务交互与通信机制

### 同步 vs 异步：不是二选一，是组合

| 通信模式 | 什么时候用 | 什么时候不用 | 典型技术 |
|---------|----------|------------|---------|
| **同步 RPC** | 需要立即拿到结果（查询余额） | 调用链路过长（5+ 个服务串联） | Dubbo/gRPC/Feign |
| **异步消息** | 通知类、解耦类（发送邮件、更新搜索索引） | 需要实时反馈的业务（支付确认） | RocketMQ/Kafka |
| **事件驱动** | 数据变更需要多个下游感知（商品下架→清缓存+更新搜索+通知卖家） | 只有单一消费者的场景 | Spring Event/MQ |

### 通信选型速查

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 内网微服务间调用 | gRPC + Protobuf | 延迟 1-3ms，多路复用 |
| 对外 HTTP API | REST + JSON | 浏览器兼容，调试友好 |
| 实时推送 | WebSocket | 服务端主动推，延迟 <50ms |
| 异步削峰 | RocketMQ / Kafka | 亿级堆积，顺序写磁盘 |
| 不需要响应的通知 | Kafka（高吞吐）| 日志、埋点、监控数据 |

**关联阅读**：高翔龙 §1.2（Dubbo 实战）、余春龙 Ch5（网络原理）、性能优化 Ch5（通信优化）

## Ch5 分布式数据库

### 分库分表决策树

```
单表数据量 > 2000万行 或 写入 QPS > 1000？
  ├─ 是 → 能接受主从延迟 < 1s？
  │        ├─ 是 → 先读写分离（成本低）
  │        └─ 否 → 需要分库分表
  └─ 否 → 优化索引 + 加缓存 → 还能撑
```

### 分片键选择速查

| 查询模式 | 推荐分片键 | 理由 |
|---------|-----------|------|
| 90% 按用户 ID 查 | user_id | 命中单库，查询最优 |
| 按时间范围查询（报表） | 时间（年/月） | 天然分区 + 归档方便 |
| 订单查询（买家和卖家都要查） | 冗余双写（buyer_id + seller_id 各一份） | 一个维度主写，另一个维度异步同步 |

### 分库分表后的五个衍生问题

| 问题 | 解法 | 出处 |
|------|------|------|
| 全局唯一 ID | Snowflake / 号段模式 | 李琛轩 Ch4 |
| 跨分片查询 | 禁止跨分片 JOIN，应用层聚合 | — |
| 跨分片事务 | 放弃强一致 → 最终一致性 | 高翔龙 §5.3 |
| 分页 | 禁止深分页，强制游标分页 | — |
| 扩容 | 双写 + 灰度切换 | 高翔龙 Ch5 |

**关联阅读**：高翔龙 Ch5（分库分表实战）、余春龙 Ch6（数据库原理）、唐伟志 Ch3（分区与复制）

## Ch6 典型的分布式存储系统

### NoSQL 选型速查

| 系统 | 数据模型 | 核心优势 | 适用场景 |
|------|---------|---------|---------|
| **Redis** | KV + 数据结构 | 极低延迟（<1ms），原子操作 | 缓存、分布式锁、计数器 |
| **MongoDB** | 文档 | Schema 灵活，JSON 原生 | 快速迭代、内容管理 |
| **HBase** | 宽列 | 按 RowKey 范围扫描极快 | 时序数据、日志存储 |
| **Elasticsearch** | 倒排索引 | 全文搜索、聚合分析 | 搜索、日志分析 |
| **HDFS** | 文件 | 海量文件存储，批处理 | 数据仓库、离线分析 |

### 什么时候换掉 MySQL？

| MySQL 不够用的时候 | 换什么 | 典型数据量 |
|-------------------|--------|:--:|
| 全文搜索太慢 | Elasticsearch | >100万文档 |
| 写 QPS 单机到顶 | 分库分表 / TiDB | QPS > 5000 |
| 数据量大但查询模式简单 | HBase / Cassandra | >10亿行 |
| 需要灵活 Schema | MongoDB | 字段经常变 |

**关联阅读**：唐伟志 Ch7（GFS/HDFS/Bigtable/Cassandra/Spanner 全案例）

## Ch7 分布式事务：什么时候放弃强一致性

### 决策树

```
这个操作涉及多少钱？
  ├─ 涉及钱（转账/支付）→ 强一致性（2PC/TCC 或数据库事务）
  │    └─ 涉及的钱很多？→ 金融级强一致（2PC + 审计日志）
  └─ 不涉及钱 → 能接受 30 秒内数据不一致？
                 ├─ 是 → Saga / 事务消息
                 └─ 否 → 先分析为什么"不能"——是不是伪需求？
```

### 方案速查

| 方案 | 一致性 | 吞吐量 | 一句话 |
|------|:---:|:---:|------|
| 2PC | 强 | 低 | 所有参与方都要准备好才提交 |
| TCC | 强（业务保证） | 中 | Try 预留→Confirm 执行→Cancel 回滚 |
| Saga | 最终 | 高 | 每步独立提交 + 失败逆补偿 |
| 事务消息 | 最终 | 高 | MQ 保证至少消费一次，消费端幂等 |
| 最大努力通知 | 不保证 | 最高 | 通知完就完了，没收到不重试 |

**关联阅读**：释慧利 Ch3（2PC/3PC详解）、唐伟志 Ch5（Saga/Percolator）

## Ch8 消息中间件

### 三巨头一句话

| MQ | 一句话 |
|----|--------|
| **RocketMQ** | 阿里双11验证，事务消息 + 顺序消息 + 亿级堆积 |
| **Kafka** | 日志流处理之王，百万 QPS 写入 |
| **RabbitMQ** | 路由灵活，小规模首选 |

### 选型速查

| 场景 | 选谁 | 理由 |
|------|:--:|------|
| 订单削峰 | RocketMQ | 事务消息保证"先扣库存→再发消息"不丢 |
| 日志采集 | Kafka | 顺序写 + 零拷贝，吞吐碾压级 |
| 业务通知（邮件/短信） | RabbitMQ / RocketMQ | 路由灵活，管理界面友好 |
| 流计算（Flink/Spark） | Kafka | 天然支持 replay |

### MQ 使用的三个铁律

1. **消费端必须幂等**：MQ 的"至少一次"语义意味着消息可能重复——用唯一 ID 去重
2. **写 MQ 后立即返回，不要轮询**："伪异步"是性能杀手——参见高翔龙 §3.4 真实事故
3. **死信队列必须有人看**：消费失败进入 DLQ 的消息不会自动处理，需要监控告警

**关联阅读**：高翔龙 §3.4（MQ 削峰的正确/错误案例）、性能优化 Ch5（通信调优）

## Ch9-10 冗余备份与高可用

### 备份策略

| 策略 | RPO（丢多少） | RTO（停多久） | 成本 |
|------|:---:|:---:|:---:|
| **冷备** | >24h | 数小时 | 最低 |
| **热备** | <1min | 秒-分钟 | 中 |
| **多活** | 接近 0 | 秒级自动切换 | 最高 |

### 高可用层级

```
L1: 进程级（主从切换、自动重启）        ← 解决单进程故障
L2: 机器级（集群冗余、自动故障转移）    ← 解决单机故障
L3: 机房级（异地多活、流量切换）        ← 解决机房故障
L4: 全局级（多云多活、DNS 切换）        ← 解决云厂商故障
```

**每一层的成本是指数级增长的**——99.9% 可用到 99.99% 的成本增加 3 倍，到 99.999% 再增加 10 倍。只为你需要的 SLA 付费。

| SLA | 年宕机时间 | L1进程级 | L2机器级 | L3机房级 | L4全局级 |
|------|:---:|:---:|:---:|:---:|:---:|
| 99.9% | 8.7 小时 | ✅ 够 | — | — | — |
| 99.99% | 52 分钟 | ❌ 不够 | ✅ 够 | — | — |
| 99.999% | 5 分钟 | ❌ | ❌ | ✅ 够 | — |
| 99.9999% | 31秒 | ❌ | ❌ | ❌ | ✅ 必须 |

### 降级方案速查

| 故障 | 降级策略 | 业务影响 |
|------|---------|---------|
| 推荐服务挂了 | 返回热门商品列表 | 用户体验略降，核心购买不受影响 |
| 缓存挂了 | 直接查数据库 + 限流保护 | 性能下降，但还能用 |
| 数据库主库挂了 | 从库提升为主库 + 短暂只读 | 几分钟内不能写入 |
| 消息队列挂了 | 本地日志暂存 + 恢复后重放 | 异步链路暂时中断 |

**关联阅读**：高翔龙 Ch2（全链路压测）、王伟峰 Ch4-6（高可用与负载均衡）、唐扬 Ch2（容错六法）

## 生产陷阱清单

| # | 陷阱 | 表面现象 | 根因 | 正确做法 |
|---|------|---------|------|---------|
| 1 | **分库后跨分片查询** | "加了这个需求后接口慢了 50 倍" | 分片键选错，查询必须扫全库 | 分片键必须覆盖 90%+ 的查询模式 |
| 2 | **消息队列当成同步 RPC** | 线程池满，请求全部超时 | 发 MQ 后 `while(true) { pollResult() }` | 发 MQ 后立即返回，消费端异步处理 |
| 3 | **不设幂等直接用 MQ** | 用户投诉"怎么扣了两次钱" | 消息重试 + 消费端没做去重 | 每条消息写入前查 Redis SETNX |
| 4 | **用 2PC 做非资金类操作** | 整个下单链路变慢 10 倍 | 强一致性用在了错误场景 | Saga + 定时对账够用 |
| 5 | **99.99% SLA 只有单机房** | 机房断电 → 全站宕机 | SLA 承诺和架构能力不匹配 | 99.99%+ 至少需要同城双活 |

> **决策树 vs 真实场景**：理论说"涉及钱用 2PC"，但电商下单（涉及钱的）用 Saga + MQ 补偿更普遍。区别在哪？—次性大额转账（银行）→ 2PC，小额高频交易（电商）→ Saga。"涉及钱"是必要条件，但不是充分条件——**还要看钱多大、量大不大、能不能补偿**。

## 面试高频题

**Q1：分库分表后，如何实现跨分片的分页查询？**

答案是**尽量不要跨分片分页**。如果一定要：1) 禁用大偏移量分页（`LIMIT 100000, 20`），强制使用游标分页（`WHERE id > last_id LIMIT 20`）；2) 如果必须跨分片全局排序，在每个分片上取 Top N，汇总到应用层再排序取 Top N——这叫"查询聚合"，N 要足够大（通常取 limit×分片数）。性能代价：分片越多代价越大。

> **追问**："游标分页为什么能解决深分页的问题？"
>
> 传统分页 `LIMIT 100000,20` 需要数据库扫描前 100000 行再丢弃——分库后每个分片都要扫这么多。游标分页 `WHERE id > 100000 LIMIT 20` 直接走主键索引定位——每个分片只扫描 20 行。代价是只能逐页翻不能跳页——但真实用户行为就是逐页翻。

**Q2：MQ 消费失败后，怎么保证消息不丢且不重复处理？**

"不丢"靠死信队列 + 监控——消费失败 N 次后进入 DLQ，由人工或定时任务兜底。"不重复"靠消费端幂等——用唯一消息 ID（如 msgId + 业务主键）在 Redis 或 DB 中记录已处理的消息。两者结合：MQ 保证"至少一次"送达，幂等保证"精确一次"效果。

> **追问**："如果幂等表本身挂了怎么办？"
>
> 三层降级：1) Redis 幂等表（高性能，有丢失风险）→ 2) Redis 挂了降级到 DB 幂等表（更可靠但慢）→ 3) 两个都挂了 → 允许消息重复 + 业务侧人工对账。没有完美的幂等方案，只有多层兜底。
