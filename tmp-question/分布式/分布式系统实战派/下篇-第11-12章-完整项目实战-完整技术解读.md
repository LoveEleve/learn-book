## Ch11 短视频系统：5000 万用户同时在线的架构设计

### 11.1 业务分析

**核心特征**：
- 用户量：5000 万同时在线
- 核心操作：刷视频（读）、发视频（写）、点赞/评论/关注（读写混合）
- 数据特征：视频文件巨大（大 IO 带宽），元数据小而多（高 QPS）
- 流量特征：热点视频流量高度集中（二八定律极端版——头部 1% 的视频占 80% 的播放量）

**一个用户刷 10 分钟视频涉及的操作**：
```
10 次 Feed 流刷新 × 每次返回 5 个视频 = 50 个视频的元数据查询
5 次视频播放 = 5 次大文件读取
3 次点赞 + 1 次评论 = 4 次写操作
```

5000 万用户同时在刷 → QPS 估算：
```
每个用户每秒触发约 2-3 次操作（刷新/播放/点赞）
5000万 × 2.5 = 1.25亿次/秒 ≈ 1.25亿 QPS
```
这不是精确数字，但量级是对的——**百亿级/秒**。这意味着：任何单点组件（单 Redis 节点、单 Kafka broker）都不可能扛住——必须分区。

### 11.2 架构总览

```
客户端 App
  ↓ CDN（视频文件分发，核心带宽消耗在这里）
接入层（Nginx + API Gateway）
  ↓
视频 Feed 服务 → Redis 缓存（Feed 流，预聚合）
  ↓ miss
视频元数据服务 → MySQL（主）+ MongoDB（标签）+ ES（搜索索引）
  ↓
视频文件存储 → HDFS（大文件）+ HBase（文件索引）
  ↓ 异步
推荐引擎 → Spark/Flink → 离线计算用户画像 + 实时更新推荐模型
```

**为什么视频文件不用 MySQL？** 一个 30MB 的短视频存 MySQL BLOB → 数据库的缓冲池被打爆、备份恢复慢 100 倍。HDFS 就是为大文件设计的。

### 11.3 存储分层设计

| 存储层 | 存什么 | 为什么选它 | 数据量级 |
|--------|--------|-----------|:--:|
| **MySQL** | 视频元数据（标题/描述/作者/时长） | 结构化数据需要事务和关联查询 | 亿级 |
| **MongoDB** | 视频标签/话题 | Schema 灵活，标签体系经常变 | 亿级 |
| **Redis** | 热门 Feed 流 + 点赞计数 + 评论缓存 | 极低延迟，数据结构丰富 | TB 级 |
| **Elasticsearch** | 视频全文搜索索引 | 倒排索引，毫秒级全文搜索 | TB 级 |
| **HBase + HDFS** | 视频原文件 | 海量大文件存 HDFS，快速元数据检索用 HBase | PB 级 |

#### MySQL 与 Elasticsearch 的数据同步

```
用户发布视频
  → 写 MySQL（元数据主表）
  → 发 MQ 消息 {video_id, action: "create"}
  → 消费端：构建 ES 索引文档 → 写入 ES
  → 定时对账：MySQL 全量导出 vs ES 文档数对比
```

**为什么不用 Binlog 同步（如 Canal）？** Binlog 同步更适合"复制一份"的场景。如果 ES 的索引结构和 MySQL 的表结构差异大（字段映射复杂、需要做文本分词），**应用层双写 + 对账**更灵活。

### 11.4 CDN 与视频带宽优化

> 5000 万用户在线的最大成本不是计算，是**带宽**。

```
一个用户看 10 分钟视频 ≈ 150MB 流量
5000 万用户 × 150MB = 7.5PB/天 → 带宽费 = 天价

CDN 方案：
  L1: 热门视频推送到 CDN 边缘节点（用户从最近的 CDN 拉）
  L2: 非热门视频从源站拉取 + CDN 自动缓存
  L3: P2P 分发（用户之间共享视频数据，减少 CDN 成本 30-50%）
```

**编码优化**：
- H.264 → H.265/AV1：压缩率提升 40%，同等画质带宽省一半
- 自适应码率（ABR）：WiFi 下 1080p，4G 下 720p，弱网下 480p
- 预加载：滑动到下一个视频前 2 秒开始预加载（用户无感知）

### 11.5 推荐系统的实时链路

```
离线层（每天）：用户画像计算 → 召回模型训练 → 排序模型训练
  ↓
近线层（分钟级）：热门视频统计 → 新视频快速冷启动
  ↓
在线层（毫秒级）：召回（2000个候选）→ 粗排（200个）→ 精排（20个）→ 返回5个
```

**推荐系统的性能瓶颈**：在线层必须在 <50ms 内完成从 2000 到 5 的筛选——这意味着：
- 召回用向量检索（Faiss/Milvus），不查 DB
- 特征数据全放 Redis 或本地内存
- 模型推理用 GPU（TensorRT 优化）

## Ch12 外卖系统：日均 8000 万订单的架构设计

### 12.1 业务特征：比电商更复杂

| 维度 | 电商 | 外卖 | 外卖的额外复杂度 |
|------|------|------|-----|
| **地域** | 全国统一 | **按城市分** | 每个城市是一套独立的供需匹配 |
| **时效** | 几天到货 | **30 分钟送达** | 实时性要求极高 |
| **库存** | 预置库存 | **动态（商家随时接单/关店）** | 库存状态实时变化 |
| **物流** | 统一配送 | **骑手实时调度** | 需要实时位置 + 路径规划 |

### 12.2 微服务拆分

```
┌─────────────┐  ┌──────────┐  ┌──────────┐
│  用户服务    │  │ 商家服务  │  │ 订单服务  │
└─────────────┘  └──────────┘  └──────────┘
┌─────────────┐  ┌──────────┐  ┌──────────┐
│  支付服务    │  │ 骑手服务  │  │ 推荐服务  │
└─────────────┘  └──────────┘  └──────────┘
┌─────────────┐  ┌──────────┐  ┌──────────┐
│  营销服务    │  │ 搜索服务  │  │ 评价服务  │
└─────────────┘  └──────────┘  └──────────┘
```

**外卖和电商拆分最大的区别**：添加了**骑手服务**和**实时地理服务**——这是电商没有的。

### 12.3 数据库设计

| 数据 | 存储 | 分片策略 |
|------|------|---------|
| 订单 | MySQL（分库分表） | 按 city_id + order_id 联合分片——同城订单在同一组库 |
| 商家 | MySQL（主从） | 按 city_id 分库——每个城市一套 |
| 商品 | MySQL（主从）+ Redis | 高频读——Redis 缓存 + 本地缓存 |
| 骑手位置 | **Redis GEO + MongoDB** | 实时位置用 Redis GEO，历史轨迹用 MongoDB |
| 用户 | MySQL（分库分表） | 按 user_id |

**为什么按 city_id 分片？** 外卖是地域性极强的业务——北京用户永远不会点上海的菜。按城市分区，90% 的查询都在单分片内完成。

### 12.4 缓存架构

```
L1: 本地缓存（Caffeine） — 商家基础信息，变化极少的元数据
L2: Redis Cluster — 商品库存、价格（按城市分片）
L3: Redis + Memcached 组合 — Redis 做主缓存，Memcached 做旁路热点缓存
```

**为什么 Redis + Memcached 组合？** Redis 数据结构丰富但单线程——举个例子：一个 `ZRANGEBYSCORE` 扫了 10 万条数据，花了 100ms，这 100ms 内所有其他请求（包括最快的 `GET`）都在排队。Memcached 多线程、极简 KV——不会有这个问题。两者分层：Redis 存需要数据结构的（排行榜、GEO），Memcached 存纯 KV（商品详情缓存）。

### 12.5 骑手派单系统

> 这是整本书最有技术含量的子系统

**核心挑战**：
- 用户下单后，要在 **<5 秒**内找到最合适的骑手
- 正在配送的骑手有数千个——需要实时位置 + 配送状态
- 派单不是简单的"谁最近就派给谁"——要考虑骑手当前订单数、预计完成时间、回程空驶率

#### 实时位置存储

```
Redis GEO：
  GEOADD riders:shanghai 121.47 31.23 rider_1001
  GEORADIUS riders:shanghai 121.47 31.23 5 km  # 方圆 5km 内的骑手
```

Redis GEO 底层是 **ZSet + GeoHash**——将经纬度编码为字符串，按前缀范围查询。方圆 5km 的查询是 O(log N + M)，N 是总骑手数，M 是范围内骑手数。

#### 派单算法

```
1. 候选池：GEORADIUS 找出商家 5km 内可用骑手
2. 过滤：去掉评分过低、当前订单已满、方向不符的
3. 排序：综合评分 = 距离分 × 0.4 + 空闲度 × 0.3 + 完成率 × 0.2 + 随机 × 0.1
4. 推单：Top 3 骑手同时推送——谁先接算谁的
5. 抢单兜底：推单 30 秒无人接 → 进入抢单池 → 广播给更多骑手
```

**为什么推单 + 抢单结合？** 推单精准但慢——系统选的骑手不一定在线。抢单快但质量不可控——可能骑手抢了远单。先用推单保证质量，推不出去再用抢单兜底保证时效。

**推单的 30 秒是固定的吗？** 不，高峰期应该动态调整——午晚高峰时订单密度高，推单时间缩短到 15 秒（快速流转），凌晨低谷时延长到 45 秒（骑手少，多等等）。推单时间本质是**"质量 vs 时效"的权衡参数**，应该放在配置中心内动态调整。

**评分权重的设计逻辑**：`距离×0.4 + 空闲度×0.3 + 完成率×0.2 + 随机×0.1` — 距离是大头（用户体验），空闲度第二（平衡骑手负载），完成率做质量分层，随机打破局部最优。但这些权重不是一劳永逸的——需要 AB 测试验证：改一下权重，看接单率/投诉率/平均配送时间怎么变。

## 生产陷阱与兜底思考

| # | 陷阱 | 场景 | 后果 | 解法 |
|---|------|------|------|------|
| 1 | **推荐挂了无降级** | 算法模型服务全挂，Feed 流返回空 | 用户打开 App 一片空白 | 降级为"热门视频列表"——不依赖推荐模型 |
| 2 | **ES 索引延迟过大** | 发视频后 10 秒搜不到 | 用户以为没发成功，重新发→重复视频 | 同步消息 + 监控 MQ 消费延迟 < 1s |
| 3 | **骑手位置全部丢失** | Redis Cluster 全挂 | 所有骑手不可见，订单无法派发 | Master-Slave + Sentinel + 骑手端补报 |
| 4 | **HDFS NameNode 成为瓶颈** | 千万级文件，单 NameNode 内存不够 | 文件上传/读取全部超时 | HDFS Federation（多 NameNode） |
| 5 | **外卖商家关店导致已下单用户无人接** | 商家接单中突然关店 | 订单挂起，用户一直等 | 关店前检查未完成订单→强制走取消+退款流程 |

### 专题：PB 级 HDFS 的运维复杂度

> HDFS 不是"丢进去就不用管了"——它是需要专门团队维护的。

| 运维维度 | 关键问题 | 解法 |
|---------|---------|------|
| **NameNode 瓶颈** | 千万级小文件（视频缩略图）→ NameNode 内存 OOM | HDFS Federation 拆多 NameNode，或小文件合并存 HBase |
| **副本策略** | 三副本 = 3 倍存储成本，PB 级意味着 P 级的额外开销 | 冷数据用纠删码（EC，1.4 倍冗余替代 3 倍），热数据保留三副本 |
| **机架感知** | 如果三副本全在同一机架→机架断电→数据全丢 | 强制至少一个副本在其他机架 |
| **小文件问题** | 视频缩略图/字幕/元数据 JSON——百万级小文件 | 合并为 SequenceFile 或直接存 HBase |

## 面试高频题

**Q1：短视频系统的 Feed 流怎么设计？5000 万用户每个人都实时生成吗？**

不，这是"重写轻读"的典型应用（参见高翔龙 §8.2.3 微博 Feeds 流）。热门用户的视频用"推"（预先扩散到粉丝的收件箱），长尾用户的视频用"拉"（用户刷 Feed 时实时聚合）。关键设计是**推拉阈值**——粉丝 >10 万的用户只推给**在线粉丝**，离线粉丝下次登录时拉取。

> **追问**："推拉结合的过程中，怎么保证 Feed 流的时序正确？"
>
> 推和拉的数据来源不同，时序靠统一的逻辑时钟（毫秒级时间戳 + 序列号）。客户端收到推和拉两部分数据后合并排序。如果客户端看到"回复出现在了帖子前面"——就是因果顺序出了问题，需要用向量时钟或 Lamport 时间戳来修复。

**Q2：外卖骑手的位置数据，为什么用 Redis GEO 而不是 MySQL GIS？**

MySQL GIS 能存空间数据（POINT 类型 + SPATIAL INDEX），但外卖骑手的位置每秒更新一次——一个骑手一天 8 万次写入。MySQL 的 B+Tree 索引在这么高的写入频率下会严重性能下降。Redis GEO 的 ZSet 在内存中操作，GEOADD 是 O(log N)，10 万骑手的每秒位置更新轻松搞定。MySQL GIS 适合"查询附近的商家"这种低频更新场景。

> **追问**："Redis 挂了，骑手位置全丢怎么办？"
>
> 骑手位置是瞬时状态——丢了也就丢几秒的位置数据，不影响核心订单。但为了防止丢位置导致所有骑手都不可见：1) Redis 主从 + Sentinel 自动故障转移（恢复 <30 秒）；2) 骑手端每秒上报位置 + 重试机制（Redis 恢复后立刻补上最新位置）；3) 极端情况下，降级为骑手手动确认位置——虽然体验下降但不影响接单。

## 项目实战的设计方法论总结

两个项目看下来，能提炼出四步设计法：

```
1. 理解业务特征 → 这个系统是什么类型的？
   （读多还是写多？实时还是离线？地域相关吗？）
        ↓
2. 确定数据模型 → 数据长什么样？怎么存？
   （结构化？大文件？需要全文搜索？需要实时位置？）
        ↓
3. 画调用链路 → 一次用户操作经过哪些服务？
   （关键路径是什么？哪里可能成为瓶颈？）
        ↓
4. 设计降级方案 → 每个组件挂了怎么兜底？
   （缓存挂了→查 DB、推荐挂了→热门列表、MQ 挂了→本地暂存）
```
