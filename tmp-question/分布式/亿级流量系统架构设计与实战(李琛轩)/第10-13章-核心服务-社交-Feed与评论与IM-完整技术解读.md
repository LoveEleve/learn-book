## 1. 用户关系服务

### 1.1 关系链的核心需求

| 操作 | QPS 量级 | 数据特征 |
|------|---------|---------|
| 关注/取关 | 千-万级 | 写操作 |
| 查询关注列表 | 万级 | 读操作 |
| 查询粉丝列表 | 万级 | 读操作 |
| 是否已关注 | 十万级 | 读操作（高频） |
| 共同关注 | 千级 | 读操作（低频但复杂） |

### 1.2 关注关系的存储

**MySQL 存储**：
```sql
CREATE TABLE user_relation (
    id BIGINT PRIMARY KEY,
    follower_id BIGINT NOT NULL,      -- 关注者（粉丝）
    followee_id BIGINT NOT NULL,      -- 被关注者
    status TINYINT DEFAULT 1,        -- 1=关注 0=取关
    created_at TIMESTAMP,
    UNIQUE KEY uk_follow (follower_id, followee_id),
    KEY idx_followee (followee_id)
);
```

**Redis 缓存**（加速高频查询）：
```
我关注的：SADD user:following:me userB
我的粉丝：SADD user:follower:userB me
是否已关注：SISMEMBER user:following:me userB
```

**为什么分库分表？**
- 用户关系表数据量极大（1 亿用户 × 平均 100 关注 = 100 亿条记录）
- 按 `follower_id` 哈希分片（查询"我的关注"可直接定位到分片）
- 查询"我的粉丝"需要扫所有分片 → **冗余存储**：关注表 + 粉丝表双写

### 1.3 大 V 的关注/粉丝优化

**问题**：粉丝 1000 万的大 V 发一条动态 → 需要 Fanout 给 1000 万粉丝 → 任务太大。

**解决方案**（统一用第 2.4 节的三档分类）：
- 普通用户（粉丝 < 1000）：实时 Push 到粉丝的 Feed
- 大 V（粉丝 ≥ 1000）：不 Push，粉丝 Pull 时从大 V 的主页拉取（注：中等 V 和大 V 的细化在第 2.4 节展开）

**大 V 的新粉丝**：
- 新关注时 Push 大 V 的最近 N 条内容到新粉丝的 Feed
- 之后不再 Push（走 Pull 模式）

### 1.4 共同关注

**查询"我和 userB 的共同关注"**：
```redis
SINTER user:following:me user:following:userB
```
Redis Set 的交集运算，O(N) 复杂度（N = 较小集合的大小）。

**大 V 的共同关注优化**：
- 大 V 的关注列表缓存到本地（关注数通常远小于粉丝数）
- 计算交集时优先用小集合

### 1.5 本节小结

用户关系服务的核心：MySQL 分库分表（100 亿条）+ Redis Set 缓存（SADD/SISMEMBER/SINTER）+ 大 V 特化（不 Push，Pull 模式）。

## 2. Timeline Feed 服务

### 2.1 Feed 流的本质

**Feed 流** = 用户关注的所有人发布的内容按时间聚合排列。

**Feed 流的三个核心问题**：
1. **实时性**：关注的用户发布了新内容，Feed 流要多久更新？
2. **完整性**：用户刷 Feed 时，是否能看到所有关注的人的新内容？
3. **排序**：按时间倒序还是按热度排序？

### 2.2 Push 模式的 Feed 流

**核心思想**：用户发布新内容 → 直接推送到所有粉丝的 Feed 列表。

```
发布者发帖 → 查粉丝列表 → 逐个 Push 到粉丝的 Feed Redis List
  → 粉丝打开 App → 拉取 Feed List（已预填充）
```

**优势**：实时性好，粉丝打开 App 直接拉取即可（读延迟低）。
**劣势**：大 V 发布 → 粉丝百万级 → Push 任务可能超时。

**Redis 存储**：
```
LPUSH user:feed:userA "{postId: 123, time: 1620000000}"
LTRIM user:feed:userA 0 999    # 只保留最近 1000 条
```

### 2.3 Pull 模式的 Feed 流

**核心思想**：不预推送。粉丝每次打开 App → 查关注列表 → 逐个拉最新内容 → 聚合排序。

```
粉丝打开 App → 查关注列表 → 对每个关注者：
  ZREVRANGE user:posts:followee 0 10（拉最新 10 条）
→ 合并所有关注者的最新内容 → 按时间排序 → 返回
```

**优势**：不浪费存储（不需要为每个粉丝建 Feed 列表）。
**劣势**：关注人多时拉取慢（100 个关注者 → 100 次 Redis 查询 → 聚合排序 → 几百 ms）。

### 2.4 Push + Pull 混合（生产方案）

**核心思想**（第三篇第 1.4 节已提到，此处细化到工程参数）：

| 用户类型 | 判断条件 | Feed 模式 | 存储 |
|---------|---------|----------|------|
| 普通用户 | 粉丝 < 1000 | Push | Redis List |
| 中等 V | 1000 ≤ 粉丝 < 10 万 | Push（离线任务） | Redis List |
| 大 V | 粉丝 ≥ 10 万 | Pull（不 Push） | MySQL + Redis 缓存 |

**工程实现的关键细节**：
- Push 任务用 MQ 异步处理（RocketMQ，支持海量消息）
- 粉丝列表分页拉取（每次 1000 条，避免 OOM）
- Push 失败重试（最多 3 次，失败后丢弃——允许部分粉丝延迟看到内容）

### 2.5 热度排序

**按时间倒序**（微博模式）：简单，适合实时性要求高的场景。
**按热度排序**（抖音/小红书模式）：需要计算每个内容的"热度分数"。

**热度分数的计算**（简化版 Reddit 算法）：
```
热度分数 = log(点赞数 + 评论数×2 + 分享数×3) + 发布时间偏移
```
- 新内容：分数高（时间偏移大）→ 即使点赞少也能出现在前面
- 老内容：分数低（时间偏移衰减）→ 需要很多点赞才能翻上来

**热度 Feed 的工程实现**：
- 定时任务（每 5 分钟）重新计算所有内容的分数
- Redis Sorted Set 维护热度排序（ZADD score contentId）
- 用户拉取时 ZREVRANGE 获取 TOP N

### 2.6 本节小结

Feed 流的三级方案：普通用户 Push（实时）、大 V Pull（省资源）、中等 V 离线 Push（平衡）。热度排序用 Sorted Set + 定时重算。

## 3. 评论服务

### 3.1 评论系统的核心需求

| 需求 | 说明 | 难度 |
|------|------|------|
| **楼中楼** | 回复评论的评论，形成树形结构 | 中 |
| **分页** | 评论太多需要分页 | 中 |
| **折叠** | 低质量评论自动折叠 | 高 |
| **热评** | 按点赞数排序的热门评论 | 中 |
| **高并发** | 热门内容的评论 QPS 极高 | 高 |

### 3.2 评论的树形结构（楼中楼）

**问题**：一条评论可能有多条回复，每条回复可能还有回复——形成树状结构。

**存储方案**：
```sql
CREATE TABLE comment (
    id BIGINT PRIMARY KEY,
    post_id BIGINT NOT NULL,     -- 被评论的内容 ID
    parent_id BIGINT DEFAULT 0,  -- 父评论 ID（0=一级评论）
    reply_to_id BIGINT DEFAULT 0,-- 回复的目标评论 ID
    user_id BIGINT NOT NULL,
    content TEXT,
    like_count INT DEFAULT 0,
    created_at TIMESTAMP,
    KEY idx_post (post_id),
    KEY idx_parent (parent_id)
);
```

**查询一级评论**（父评论）：
```sql
SELECT * FROM comment WHERE post_id = ? AND parent_id = 0
ORDER BY created_at DESC LIMIT 20;
```

**查询二级评论**（回复）：
```sql
SELECT * FROM comment WHERE parent_id = ?
ORDER BY created_at ASC LIMIT 10;
```

**查询"回复的回复"**：通过 `reply_to_id` 追踪——每条回复记录自己回复的是谁。前端组装时按 `parent_id` 分组 + `created_at` 排序，不依赖数据库递归查询（MySQL 递归 CTE 在大量数据下性能差）。

**展示逻辑**（前端）：
```
一级评论 1
  ├─ 回复 1.1
  │    └─ 回复 1.1.1
  ├─ 回复 1.2
  └─ 查看全部 5 条回复
一级评论 2
  └─ ...
```

### 3.3 评论的缓存策略

**一级评论**：缓存到 Redis，TTL=1 小时
- 热门内容（评论 > 1000）：全量缓存
- 普通内容：缓存前 50 条

**二级评论**：不缓存（查询频率低，每次拉取时实时查 DB）

**评论数缓存**：
```
comment:count:post:123 = 500  # Redis 计数
```
- 每增加一条评论：INCR
- 不要每次展示都 COUNT(*) 查 DB

### 3.4 高并发评论的挑战

**问题**：热点文章发布后，瞬时评论 QPS 可能达数万。

**应对**：
1. **评论异步写入**：先写 Redis List + 立即返回，后台异步写入 MySQL
2. **评论数用 Redis 计数**（第三篇第 2 节）
3. **限流**：同一用户对同一内容的评论间隔限制（如 10 秒内只能发一条）

### 3.5 本节小结

评论服务的核心：树形结构（parent_id + reply_to_id）+ 一级缓存 Redis + 二级实时 DB + 评论数 Redis 计数 + 限流防刷。

## 4. IM 即时通讯

### 4.1 IM 的核心挑战

**挑战 1：消息可靠性**
- 发送方发出消息 → 服务端收到 → 接收方在线 → 实时推送
- 接收方离线 → 消息不能丢失 → 离线存储 → 下次上线拉取

**挑战 2：长连接管理**
- 千万级用户同时在线
- 第二篇第 3 节讲了推送系统的长连接，IM 的场景与之类似

**挑战 3：群聊消息扩散**
- 群里 500 人 → 发一条消息 → 需要推送给 500 人
- 超级群 10000 人 → 需要更高效的扩散机制

### 4.2 消息的可靠投递

**发消息的完整流程**：

```
发送方 → 服务端
  ├─ 1. 存储消息（MySQL/Redis）
  ├─ 2. 检查接收方在线状态（Redis）
  ├─ 3. 在线 → 实时推送到接收方的长连接
  └─ 4. 离线 → 存入离线消息队列
  └─ 5. 返回发送方 ACK（消息已送达服务端）
```

**消息的 ACK 三级**：

| ACK 级别 | 含义 | 发送方看到 |
|---------|------|----------|
| 已发送 | 消息已到达服务端 | 单勾（WhatsApp 的 ✓） |
| 已送达 | 消息已推送到接收方 | 双勾（✓✓） |
| 已读 | 接收方已打开对话 | 蓝色双勾 |

**离线消息的存储**：
- Redis List：`user:offline_msg:{userId}` 按时间倒序
- 接收方上线 → 拉取离线消息 → 批量推送 → 清空 List

### 4.3 群聊的消息扩散

**500 人群**：写扩散——每条消息写入 500 个用户的收件箱。
- 优势：读取快（每用户只需要读自己的收件箱）
- 劣势：写入量大（500 倍写放大）

**10000 人群**：读扩散——每条消息只存一份，用户拉取时读群消息。
- 优势：写入小
- 劣势：读取时需要去群里拉（每个用户的读取上限也是群消息的总数）

**混合方案**：小群（< 500 人）写扩散，大群（≥ 500 人）读扩散。

### 4.4 IM 的在线状态管理

（详见第二篇第 3 节推送系统的在线状态管理）

- Redis 存 `user:online:{userId}` = `{gateway_ip}`
- TTL = 心跳超时（如 180s）
- 用户上线 → SET + 拉取离线消息
- 用户下线 → TTL 过期自动清除

### 4.5 本节小结

IM 的核心：消息可信投递（三级 ACK + 离线存储）、群聊扩散（小群写扩散 + 大群读扩散）、在线状态（Redis + 心跳 TTL）。

## 结语：社交服务的四根支柱

回顾本篇，四个社交核心服务：

- **用户关系**：MySQL 分库分表 + Redis Set（SADD/SINTER）+ 大 V 不计入 Fanout
- **Feed 流**：普通用户 Push + 大 V Pull + 中等 V 离线 Push + 热度 Sorted Set
- **评论系统**：树形结构（parent_id）+ 一级缓存 + 二级实时 + 限流
- **IM 即时通讯**：三级 ACK + 离线 Redis List + 群聊写扩散/读扩散混合

**第四篇的核心论断**：社交服务是亿级流量系统最具挑战性的场景——Feed 流的 Push/Pull 混合、IM 的群聊扩散、用户关系的海量数据存储，每个都是架构师面试的高频考点。它们的共性是：**没有银弹，只有分层方案**——根据用户规模动态调整策略（普通用户 Push / 大 V Pull / 小群写扩散 / 大群读扩散）。
