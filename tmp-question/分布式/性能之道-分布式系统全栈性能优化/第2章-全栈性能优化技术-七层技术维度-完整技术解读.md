## 2.1 网络性能：被忽视的"中间网络"瓶颈

### 2.1.1 为什么网络是分布式系统的第一大瓶颈？

《性能之道》以一个反直觉的视角开篇：**当你看到系统响应慢，第一反应是查数据库、查缓存、查JVM——但如果把100ms的响应时间拆开，可能有40ms消耗在你完全无法控制的"中间网络"上。**

互联网的"中间网络"是指由数以万计互相竞争的ISP（Internet Service Provider，互联网服务提供商）组成的对等交换网络。它有几个致命特征：

| 特征 | 对性能的影响 |
|------|------------|
| **不可控** | 服务端基础设施你可以优化，中间网络你无法控制 |
| **无优化动力** | 对等节点在经济上没有动力去扩大产能 |
| **长路径** | 跨洋/跨地域的数据包可能经过数十个路由跳变 |
| **拥堵风险** | 对等节点通常负载过重，导致丢包和服务质量下降 |

**核心优化起点**：既然中间网络不可控，就把数据从"中间网络"上移走——**CDN（Content Delivery Network，内容分发网络）和边缘计算**的本质都是"把数据放在离用户更近的地方"。

### 2.1.2 网络性能优化的四个方向

### 2.1.3 TCP拥塞控制的深层机制——为什么Cubic不如BBR？

TCP 拥塞控制经历了三个时代的演进：

**第一代：Tahoe/Reno（基于丢包）**——以丢包作为拥塞信号，丢包→减半拥塞窗口。问题：(1) 丢包不一定等于拥塞（无线网络丢包更可能是信号干扰），(2) 一旦丢包就暴力减半，链路吞吐量剧烈波动。

**第二代：Cubic（基于丢包+数学优化）**——Linux 默认算法，用三次函数曲线而非线性增长来寻找最佳窗口。相比 Reno 在高 BDP（Bandwidth-Delay Product，带宽延迟积）链路上有显著改善。**但核心缺陷未变**：仍然以丢包作为拥塞信号。在有一定丢包率的链路上（如跨洋光纤 0.1-1% 丢包），Cubic 持续触发窗口减半，导致带宽利用率极低。

**第三代：BBR（基于带宽+延迟测量）**——Google 2016年贡献。核心思想：

```
Cubic 的模型：          BBR 的模型：
丢包 = 拥塞 → 减少发送  测量最大带宽 + 最小RTT → 计算最优发送速率
                        ↑ 不依赖丢包作为信号！
```

BBR 在链路 1% 丢包率下的表现：
```
Cubic：有效吞吐 = 理论带宽 × 0.3（丢包触发减半 × 多次）
BBR：  有效吞吐 = 理论带宽 × 0.95（丢包不影响发送速率）
```

**生产配置**：

```bash
# 查看当前拥塞控制算法
sysctl net.ipv4.tcp_congestion_control

# 开启 BBR（Linux 4.9+）
echo "net.core.default_qdisc=fq" >> /etc/sysctl.conf
echo "net.ipv4.tcp_congestion_control=bbr" >> /etc/sysctl.conf
sysctl -p

# 验证 BBR 已启用
sysctl net.ipv4.tcp_congestion_control  # 应输出 bbr
lsmod | grep tcp_bbr                    # 确认内核模块已加载
```

**BBR 的局限性**：(1) BBRv1 对自身流量的竞争性不够公平，可能抢占 Reno/Cubic 流的带宽；(2) BBRv2 做了改进但在某些场景下吞吐量不如 v1。选择 BBR 时需要评估你的网络环境是否有丢包容忍度的需求。

### 2.1.4 HTTP/2 多路复用的真实收益——不仅仅是"快了一点"

HTTP/1.1 的一个连接只能串行处理一个请求（Pipeline 机制因队头阻塞问题几乎被浏览器禁用）。实际优化是**多连接并发**——浏览器为同一域名开启 6 个连接，并行发送请求。但每个连接都需要独立的 TCP 握手（3次握手 = 1.5 RTT）+ TLS 握手（2 RTT）。6 个连接 = 6 × 3.5 RTT。

HTTP/2 的多路复用改变了这个模型：

```
HTTP/1.1 + 6连接:                     HTTP/2 单连接多路复用:
连接1: TCP握手 + TLS握手 + 请求+响应    单连接: TCP握手 + TLS握手
连接2: TCP握手 + TLS握手 + 请求+响应    ↓
连接3: TCP握手 + TLS握手 + 请求+响应    Stream1: 请求+响应
连接4: TCP握手 + TLS握手 + 请求+响应    Stream2: 请求+响应
连接5: TCP握手 + TLS握手 + 请求+响应    Stream3: 请求+响应
连接6: TCP握手 + TLS握手 + 请求+响应    ...
                                       6个请求共享1个连接，并行发送！
总RTT开销: 6 × 3.5 = 21 RTT           总RTT开销: 1 × 3.5 = 3.5 RTT
```

**实际数字**：假设 RTT = 50ms（同城 4G 环境）
- HTTP/1.1：6 连接 × 3.5 RTT × 50ms = 1050ms（仅连接建立，不含数据传输）
- HTTP/2：1 连接 × 3.5 RTT × 50ms = 175ms

**多路复用的收益不仅仅来自"减少连接数"**——更来自 **TCP 慢启动的优化**。TCP 每建立一个新连接都需要从慢启动开始（初始 cwnd=10 个 MSS），逐步增加到链路的真实带宽。6 个 HTTP/1.1 连接意味着 6 次从零开始的慢启动，而 HTTP/2 的单一连接一直在"热"状态——慢启动早已完成，cwnd 已稳定在最优值。


| 方向 | 策略 | 实现 |
|------|------|------|
| **减少传输数据量** | 压缩、精简协议、避免冗余字段 | Gzip/Brotli 压缩、Protobuf 替代 JSON |
| **减少往返次数（RTT）** | 连接复用、批量传输、减少握手 | HTTP/2 多路复用、TLS 1.3 1-RTT |
| **缩短物理距离** | CDN、边缘计算、同城多活 | 静态资源推到 CDN、动态数据推到边缘节点 |
| **提高传输效率** | TCP参数调优、QUIC替代TCP | TCP拥塞窗口调优、QUIC 0-RTT连接建立 |

**TCP 参数调优的关键项**：

```bash
# Linux 内核 TCP 参数优化
net.core.rmem_max = 134217728      # 接收缓冲区最大值(128MB)
net.core.wmem_max = 134217728      # 发送缓冲区最大值(128MB)
net.ipv4.tcp_slow_start_after_idle = 0  # 空闲后不重置拥塞窗口
net.ipv4.tcp_congestion_control = bbr   # 拥塞控制算法（BBR优于Cubic）
```

**BBR（Bottleneck Bandwidth and Round-trip propagation time，瓶颈带宽与往返时间）** 是 Google 开发的拥塞控制算法，相比传统的 Cubic 算法，BBR 的核心理念是：**不以丢包作为拥塞信号**（丢包不一定是拥塞造成的，可能是链路噪声），而是直接测量带宽和 RTT 来判断真正的网络容量。在生产环境中，BBR 在有一定丢包率的链路上比 Cubic 快数倍。

### 2.1.3 CDN与边缘计算的性能本质

```
传统架构：                          CDN架构：
用户 → 中间网络 → 源服务器(北京)    用户 → CDN边缘节点(就近) → (必要时才回源)
延迟：50-500ms                      延迟：5-50ms（大部分命中边缘）
```

CDN 和边缘计算本质上都是**空间换时间**——用大量的边缘存储（空间开销）来减少数据在网络上的传输时间。区别在于：CDN 主要缓存**静态内容**（图片、JS、CSS），边缘计算可以执行**动态逻辑**（如 API 鉴权、A/B 测试分流）。

> **跨书对照**：高翔龙第4章讨论了 CDN 作为多级缓存的最外层，余春龙第1章讨论了 HTTP 协议演进对 RTT 的影响。《性能之道》的独特视角是把网络层当作"不可控但可优化的变量"——你不需要成为网络工程师，但需要知道哪个参数能显著影响性能。

## 2.2 通信性能：RPC与服务间调用的效率

### 2.2.1 RPC 调用的性能开销拆解

一次 RPC 调用的总耗时可以拆解为：

```
总耗时 = 序列化 + 网络传输(2×RTT) + 服务端处理 + 反序列化
         (5-10ms)  (1-50ms)         (5-100ms)     (1-3ms)
```

**序列化开销对比**：

| 序列化方案 | 编码速度 | 解码速度 | 数据体积 | 适用 |
|-----------|:---:|:---:|:---:|------|
| **JSON** | 中 | 慢 | 大（文本） | 可读性好，适合对外API |
| **Protobuf** | 快 | 很快 | 极小（二进制） | 内部RPC首选 |
| **Hessian2** | 快 | 快 | 小（二进制） | Dubbo内部默认 |

**关键优化策略**：

1. **连接复用**：避免每次 RPC 调用都建立新的 TCP 连接（3次握手 = 1.5 RTT）。Dubbo 默认使用 Netty 长连接池，每个 Provider 维护一个长连接，连接数 = Consumer数 × Provider数。

2. **批量传输**：将多个小请求合并为一个大请求发送（Kafka 的 RecordAccumulator 就是典型实现）

3. **避免序列化不必要的数据**：不要返回整个 DO 对象给前端——用 DTO（Data Transfer Object，数据传输对象）只包含前端需要的字段

### 2.2.2 通信错误的两个方向

《性能之道》还深入讨论了通信性能优化的两个容易被忽略的方向：

**前向纠错（FEC，Forward Error Correction）** vs **重传纠错（Retransmission）**：

| 策略 | 原理 | 延迟 | 带宽开销 | 适用 |
|------|------|:---:|:---:|------|
| **重传纠错** | 丢包后重新请求 | 高（重传等待） | 低 | 有线网络、低丢包率 |
| **前向纠错** | 发送时附加冗余数据，允许接收方自行恢复少量丢包 | 低（无需等待重传） | 高（冗余数据开销 10-40%） | 无线网络、高丢包率、实时通信 |

## 2.3 客户端/前端性能：用户感知的第一道门

### 2.3.1 性能的用户感知链

《性能之道》强调了客户端性能优化中一个经常被后端工程师忽略的维度：**用户感知的性能（Perceived Performance）**。

```
用户点击 → 浏览器渲染 → 网络请求 → 服务端处理 → 数据库查询 → 返回 → 浏览器渲染
├──────────────── 用户等待 ────────────────┤
├─ 前端渲染延迟 ─┤├── 网络传输延迟 ──┤├──── 后端处理延迟 ────┤
     （最影响感知）                                          （后端最关注）
```

**关键量化指标**：

| 指标 | 简称 | 含义 | 目标 |
|------|------|------|:---:|
| **首次内容绘制** | FCP（First Contentful Paint） | 页面上第一个元素渲染的时间 | <1.8s |
| **最大内容绘制** | LCP（Largest Contentful Paint） | 页面上最大元素渲染的时间 | <2.5s |
| **首次输入延迟** | FID（First Input Delay） | 用户首次交互到浏览器响应的时间 | <100ms |
| **累计布局偏移** | CLS（Cumulative Layout Shift） | 页面视觉稳定性（元素移动） | <0.1 |

**核心优化策略**：

- **关键渲染路径优化**：将首屏必需的 CSS/JS 内联到 HTML 中（避免额外请求），非关键资源延迟加载（`defer`/`async`）
- **骨架屏（Skeleton Screen）**：在数据加载期间显示页面轮廓，降低用户感知的等待时间
- **预加载（Preload/Prefetch）**：提前加载用户可能访问的下一个页面资源

## 2.4 单服务实体性能：从JVM到代码级优化

### 2.4.1 服务端性能的瓶颈定位

这是"点"和"线"级优化的核心战场。当压测发现单服务 QPS 达不到预期时，需要逐层排查：

```
排查链路：
QPS低 → 
  ├── CPU高吗？ → 是 → 算法复杂度？热点代码？序列化开销大？
  ├── 内存高吗？ → 是 → 内存泄漏？缓存过大？GC频繁？
  ├── I/O高吗？ → 是 → 磁盘读写？网络传输？数据库查询慢？
  └── 线程状态？ → BLOCKED多 → 锁竞争 → 优化锁粒度 / 无锁化
                   WAITING多 → 线程池不够 → 加大线程池 / 异步化
```

### 2.4.2 JVM 层面的优化要点

| 优化方向 | 策略 | 典型参数 |
|---------|------|---------|
| **选择合适GC** | 低延迟用 G1/ZGC，高吞吐用 Parallel GC | `-XX:+UseG1GC` |
| **调整Heap大小** | 根据实际使用情况设定，避免频繁GC | `-Xms4g -Xmx4g` |
| **设置GC暂停目标** | G1的期望最大暂停时间 | `-XX:MaxGCPauseMillis=200` |
| **开启GC日志** | 可观测性：记录GC事件用于分析 | `-Xlog:gc*`（Java 9+统一日志） |

> **面试视角**："G1和ZGC的区别？"→ G1是分代收集（Young/Old），ZGC是不分代的并发收集。G1的暂停时间目标通常在100-200ms级别，ZGC的暂停时间在亚毫秒级（<1ms）。G1适合Heap 4-32GB的常规应用，ZGC适合16GB+且对延迟极度敏感的场景（如交易系统）。**选型不是"哪个更新用哪个"，而是"哪个更适合你的延迟目标和内存规模"。**

### 2.4.3 API 的性能约定

《性能之道》提出了一个重要的工程实践：**API的性能约定**——即在API设计阶段就明确性能承诺，而不是等上线后再优化。

```java
/**
 * 获取商品详情
 * 
 * 性能约定：
 * - P50响应时间: < 50ms
 * - P99响应时间: < 200ms  
 * - 支持QPS: 5000/s per instance
 * - 不缓存: 调用方需自行处理缓存
 * - 幂等性: GET请求天然幂等
 */
ProductDetail getProductDetail(String productId);
```

性能约定的价值在于：当调用方抱怨"你的接口慢了"时，有明确的判断标准——是1ms变2ms的抱怨（不需要优化），还是50ms变200ms的故障（需要立即修复）。

## 2.5 数据库性能：从SQL到存储引擎的全链路

### 2.5.1 数据库性能瓶颈的三层定位

| 层次 | 瓶颈表现 | 优化方向 |
|:---:|---------|---------|
| **SQL层** | 慢查询、全表扫描、索引未命中 | EXPLAIN分析、索引优化、SQL改写 |
| **连接层** | 连接池耗尽、连接超时 | 连接池参数调优、读写分离 |
| **存储层** | 磁盘I/O瓶颈、Buffer Pool命中率低 | 增大Buffer Pool、SSD/Pmem升级、归档冷数据 |

**Buffer Pool命中率**是 MySQL 最重要的性能指标之一：

```
命中率 = 1 - (磁盘读取次数 / 总读取次数)
目标：> 99%（OLTP场景）
如果命中率 < 95%，说明 Buffer Pool 太小，需要加大 innodb_buffer_pool_size
```

### 2.5.2 SQL 写入优化

| 优化 | 策略 | 收益 |
|------|------|:---:|
| **批量写入** | 用 `INSERT INTO ... VALUES (v1),(v2),...` 替代逐条INSERT | 10-50x |
| **事务合并** | 多个小事务合并为一个事务（减少 fsync 次数） | 2-5x |
| **顺序写入** | 避免随机UPDATE导致页分裂 | 取决于场景 |
| **延迟写入** | 先写内存+日志，异步落盘（LSM树的核心思想） | 极大，但有宕机丢数据风险 |

> **跨书对照**：高翔龙第4章讨论了在Redis中扣减库存以避免InnoDB行锁瓶颈，《性能之道》则从"为什么InnoDB行锁会成为瓶颈"的更深层原理出发——B+树的随机写入需要页分裂、undo log写入、redo log刷盘，每一步都是串行的。

### 2.5.3 数据库的异步化：LSM树 vs B+树

### 2.5.4 InnoDB行锁的物理实现——为什么1000个并发UPDATE同一行这么慢？

这个问题在高翔龙第4章已经讨论过，但《性能之道》从物理层面给出了更底层的解释。

InnoDB 的行锁不是"锁住一行"那么简单。它的实现涉及三个层次：

```
层次1：事务层锁（Lock Manager）
  → lock_rec_lock() → 在行记录上设置隐式锁或显式锁
  → 锁信息存储在 lock_sys->rec_hash 哈希表中
  → 每个锁占用约 50 字节内存

层次2：互斥量层（Mutex）
  → lock_sys->mutex 保护整个锁系统的并发访问
  → 所有获取/释放行锁的操作都需要先获取这个全局互斥量！
  → 这就是为什么高并发行锁竞争时性能急剧下降——不是"每个连接在等行锁"，而是"每个连接在排队获取 lock_sys->mutex"

层次3：等待队列
  → 等待同一行锁的事务按 FIFO 排队
  → 但等待检测不是实时的——默认死锁检测每 1 秒运行一次（innodb_deadlock_detect=ON）
  → 1000 个等待的事务 → 死锁检测需要遍历 1000×999 对事务组合 → O(n²) 复杂度！
```

**生产优化——关闭死锁检测**：

```sql
-- 如果确定应用层不会引入死锁（如单表更新），可以关闭死锁检测
SET GLOBAL innodb_deadlock_detect = OFF;

-- 配合使用锁等待超时替代死锁检测
SET GLOBAL innodb_lock_wait_timeout = 2;  -- 2秒后自动放弃
```

**为什么 MySQL 8.0 的 CATS（Contention-Aware Transaction Scheduling）能改善这个问题？**

CATS 修改了 InnoDB 的等待队列调度策略——不再是 FIFO，而是**基于锁竞争压力的动态调度**：
- 检测哪些事务持有"大家都要的锁"→ 优先调度这些事务完成→快速释放热点锁
- 检测哪些事务在等锁→先调度那些等待时间短的事务→减少整体排队时间

这相当于银行的"快速窗口"机制——把办事快的人先处理掉，不要让所有人排队等一个复杂业务。


```
B+树（InnoDB - OLTP优化）：           LSM树（RocksDB - 写优化）：
写入 → 直接更新磁盘页                 写入 → 内存有序表(MemTable) → 返回
         ↕ 随机写（慢）                         ↕ 纯内存操作（快）
      读取 → B+树查找（快）                   ↓ 后台异步合并(SSTable)
                                           读取 → 先查MemTable → 再查SSTable（慢）
```

**核心权衡**：B+树优化读（适用于OLTP——大量随机读+少量写），LSM树优化写（适用于日志存储、KV存储——大量顺序写+少量随机读）。

## 2.6 缓存：性能优化的王牌手段

### 2.6.1 缓存的性能收益计算

《性能之道》给出了缓存收益的精确计算框架：

```
缓存命中时的延迟 = Cache_Latency (Redis: ~1ms)
缓存未命中时的延迟 = Cache_Latency + DB_Latency (Redis: ~1ms + MySQL: ~10ms = ~11ms)
有效延迟 = P(命中) × Cache_Latency + P(未命中) × (Cache_Latency + DB_Latency)

假设命中率 = 95%：
有效延迟 = 0.95 × 1ms + 0.05 × 11ms = 0.95 + 0.55 = 1.5ms

vs 不使用缓存：延迟 = 10ms
提升：10ms → 1.5ms = 6.7x
```

**关键洞察**：缓存的收益不是固定的"加缓存快10倍"——它取决于**命中率**。如果一个缓存的命中率只有 50%，收益只有 2x，而且还需要付出缓存一致性的额外复杂度。**在决定加缓存之前，先估算命中率**。

### 2.6.2 缓存的两种更新策略

### 2.6.4 缓存一致性的四种模式——不止Cache Aside

Cache Aside 是最常用的模式，但不是唯一的。四种模式各有适用场景：

**Cache Aside（旁路缓存）**——应用自己管理缓存

```
读：查缓存 → 未命中 → 查DB → 写缓存
写：更新DB → 删除缓存
```

适用：读多写少，一致性能容忍短暂不一致。电商商品详情页、用户信息。

**Read Through（读穿透）**——缓存层代理读操作

```
应用 → 缓存层 → 未命中 → 缓存层查DB → 写缓存 → 返回应用
```

优势：应用对缓存无感知，缓存层统一管理。适用：缓存产品有内置的 Read Through 支持（如 Redis + RedisGears）。

**Write Through（写穿透）**——缓存层代理写操作

```
应用 → 缓存层 → 更新缓存 → 同步更新DB → 返回
```

优势：缓存和DB始终保持一致。代价：每次写都是同步操作（缓存+DB），写入延迟翻倍。适用：对一致性要求极高、写入频率低的场景（如配置数据）。

**Write Behind（写后异步）**——缓存先写，异步刷DB

```
应用 → 缓存层 → 更新缓存 → 立即返回
                     ↓ 异步
                 批量写入DB
```

优势：写入延迟极低（只写缓存）。代价：缓存宕机会导致未刷入DB的数据丢失。适用：写入频率极高、能容忍少量数据丢失的场景（如计数器、访问日志）。

**四种模式的选择决策树**：

```
你对一致性的要求？
├── 极高（金融核心） → Write Through
├── 高（电商交易） → Cache Aside（删除缓存，非更新）
├── 中（内容/社交） → Cache Aside + 短TTL
└── 低（计数/日志） → Write Behind
```

> **发散思考**：这四种模式与 CAP 理论的关系。Write Through 是 CP 模型（强一致，但写入性能差），Write Behind 是 AP 模型（高可用，但一致性弱）。Cache Aside 是它们之间的折中——读未命中时从 DB 回源保证最终一致，写时删除缓存避免并发写入冲突。选择缓存模式本质上是 CAP 在缓存层的映射。


| 策略 | 流程 | 一致性 | 实现复杂度 |
|------|------|:---:|:---:|
| **Cache Aside** | 读：查缓存→未命中→查DB→写缓存 | 最终一致 | 低 |
| **Read/Write Through** | 缓存层代理所有读写，应用只与缓存交互 | 取决于实现（单机强一致，分布式需额外保证） | 中 |
| **Write Behind** | 写缓存→异步批量写DB | 最终一致（有丢数据风险） | 高 |

**Cache Aside 的典型代码**：

```java
public Product getProduct(String id) {
    // 1. 查缓存
    Product p = redis.get("product:" + id);
    if (p != null) return p;
    
    // 2. 缓存未命中，查数据库
    p = db.query("SELECT * FROM product WHERE id = ?", id);
    if (p != null) {
        // 3. 写入缓存
        redis.set("product:" + id, p, 300, TimeUnit.SECONDS);
    }
    return p;
}

public void updateProduct(Product p) {
    // 1. 更新数据库
    db.update("UPDATE product SET ... WHERE id = ?", p);
    // 2. 删除缓存（而非更新缓存——避免并发写入导致的缓存不一致）
    redis.del("product:" + p.getId());
}
```

> **生产陷阱——为什么写操作删缓存而不是更新缓存？** → 如果两个并发写入分别更新缓存和数据库，可能出现"线程A先更新数据库、线程B后更新数据库、线程B先更新缓存、线程A后更新缓存"的乱序——导致缓存中是线程A的旧数据，数据库中却是线程B的新数据。而删除缓存没有这个问题——删除后下一次读会触发 Cache Aside 回源，读到的始终是最新的数据库数据。

## 2.7 消息队列：异步化的基础设施

### 2.7.1 MQ 的性能模型

| 指标 | 含义 | Kafka 典型值 | RocketMQ 典型值 |
|------|------|:---:|:---:|
| **吞吐量** | 单位时间处理的消息数 | 100w+/s | 10w+/s |
| **延迟** | 从生产到消费的时间 | ms~s级 | ms级 |
| **持久化** | 消息是否写入磁盘 | ✅（Page Cache + 顺序写） | ✅（CommitLog 顺序写） |

**Kafka高性能的秘密——五个要素**：

1. **顺序写磁盘**：充分利用磁盘的顺序写性能（HDD 100MB/s+，比随机写快数百倍）
2. **Page Cache**：消息先写入OS页缓存，由OS负责刷盘——相当于"内存写、磁盘兜底"
3. **sendfile()零拷贝**：消费者读取时，通过 `sendfile()` 从 Page Cache 直推到网卡
4. **批量发送**：Producer 端 RecordAccumulator 批量打包，减少网络往返
5. **分区并行**：每个 Partition 独立处理，天然支持横向扩展

### 2.7.2 MQ 的削峰模型

```
同步模式：                          异步模式（MQ缓冲）：
请求进入 → 立即处理 → 返回           请求进入 → 写入MQ → 立即返回
QPS > 处理能力 → 拒绝/排队           后台消费者按照自己能处理的速率消费
                                    QPS > 处理能力 → MQ堆积（磁盘缓冲）
```

**MQ削峰的能力 = MQ可堆积的消息数 = 磁盘容量 / 单条消息大小**

以 Kafka 为例：1TB 磁盘，单条消息 1KB → 可堆积 10亿条消息。在消费速率 10000 TPS 下，10亿条消息 = 100000 秒 ≈ 27 小时——这意味着即使下游暂停 27 小时，MQ 也能缓冲所有消息不丢失。

## 2.8 本章核心观点总结

1. **网络延迟是大头**：中间网络不可控，优化方向是"把数据从中间网络上移走"——CDN、边缘计算、压缩、减少RTT。

2. **RPC 优化的关键在序列化和连接管理**：Protobuf 替代 JSON（速度+体积）、长连接池避免TCP握手、DTO 精简减少序列化数据量。

3. **客户端优化的核心是感知性能**：FCP/LCP/FID/CLS 比服务端 QPS 更直接影响用户体验。骨架屏、预加载、关键渲染路径优化。

4. **单服务优化从JVM开始**：选择合适GC（低延迟→ZGC，高吞吐→ParallelGC）、GC日志可观测性、API性能约定。

5. **数据库优化三层递进**：SQL层（EXPLAIN+索引）→连接层（连接池+读写分离）→存储层（Buffer Pool+SSD）。优化顺序从最便宜的开始（SQL改写，0成本）到最贵的（升级硬件，有成本）。

6. **缓存的收益取决于命中率**：命中率 95% = 6.7x 提升，命中率 50% = 2x。在加缓存前先估算命中率。

7. **MQ=异步化的基础设施**：Kafka高性能=顺序写+Page Cache+sendfile()+批量+分区。削峰能力=磁盘容量。
