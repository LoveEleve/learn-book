## 1.1 软件架构的时空观：性能的本质是两个维度

### 1.1.1 架构决策的时间维与空间维

### 1.1.2 架构师的"延迟记忆表"——每个程序员都应该知道的数字

架构师做时空权衡时需要一个参考坐标系——在距离、速度和成本的博弈中，不同操作的绝对延迟是多少？以下是经过硬件实测的延迟参考表（Jeff Dean, 2009, updated 2024 for NVMe/PCIe 5.0）：

| 操作 | 延迟 | 相对 L1 Cache | 物理本质 |
|------|:---:|:---:|------|
| L1 Cache 引用 | 0.5 ns | 1x | CPU 最快存储层 |
| L2 Cache 引用 | 7 ns | 14x | 大但稍慢的 Cache |
| L3 Cache 引用 | 30 ns | 60x | 槽上共享 |
| 主内存引用 | 100 ns | 200x | DRAM 物理限制 |
| SSD（NVMe）随机读 | 80-100 μs | 200,000x | PCIe 5.0 通道延迟 |
| 机械硬盘随机读 | 5-10 ms | 10,000,000x | 磁头寻道物理限制 |
| 同数据中心往返（RTT） | 0.5-1 ms | 2,000,000x | 光纤 + 交换机延迟 |
| 跨地域往返（北京→上海） | 20-30 ms | 40,000,000x | 光速物理极限 |

**这张表的意义不是"背数字"，而是建立"数量级的直觉"**：

- 一次 L1 Cache 引用 = 0.5ns（CPU 最快），一次磁盘随机读 = 10ms = L1 Cache 的 2000 万倍
- 这个数量级差距说明了为什么**缓存对性能的影响如此巨大**——用内存替代磁盘，不是"快一点"，是"快 2000 万倍"
- 跨地域 RTT 20ms = 一次 SSD 读的 200 倍——解释了为什么"多活架构"的延迟无法消除（光速是硬限制）

**把这个表映射到架构决策**：

```
场景1：磁盘 vs 内存
操作：读取 1KB 数据
  方案A（磁盘随机读）：~10ms
  方案B（内存读）：~100ns
  差距：10,000,000ns vs 100ns = 100,000 倍
  架构决策：只要数据量 < 可用内存，一定放内存（Redis/Memcached/Caffeine）

场景2：本地调用 vs RPC 调用
操作：获取用户信息
  方案A（进程内函数调用）：~100ns（无序列化/网络开销）
  方案B（同机房 RPC 调用）：~1ms（序列化+网络+反序列化）
  差距：10ms vs 100ns = 100 倍
  架构决策：热路径上避免不必要的 RPC 拆分

场景3：同机房 vs 跨地域
操作：双写确认
  方案A（同机房主从同步）：~1ms
  方案B（跨地域主从同步）：~20ms
  差距：20ms vs 1ms = 20 倍
  架构决策：跨地域同步用异步模式，牺牲强一致性换取可用性
```

> **发散思考**：这张表的数字在近 15 年内变化不大——不是因为硬件没有进步，而是因为硬件的进步目标从"降低绝对延迟"转向了"提升吞吐量"（多核、多通道、并行）。这解释了为什么"延迟"仍然是分布式系统最顽固的性能瓶颈——延迟受物理规律限制（光速、电子迁移率），而吞吐量可以通过并行无限扩展。**所以优化延迟靠减少操作次数（缓存、合并、就近部署），优化吞吐量靠增加并行度（多核、多节点、分区）。**


《性能之道》以"软件架构的时空观"作为开篇，这是全书最底层的认知框架。作者将架构的本质归纳为两个维度的权衡：

| 维度 | 含义 | 架构表现 | 量化 |
|------|------|---------|:---:|
| **时间维** | 系统的响应速度、执行效率 | 延迟（Latency）、吞吐量（Throughput） | ms / QPS |
| **空间维** | 系统的资源占用、存储容量 | CPU、内存、磁盘、网络带宽 | MHz / MB / IOPS / Mbps |

**架构的本质是时空调度**：在有限的时间与空间资源下，最大化系统的工作效率。一个好的架构决策不是"用最好的技术"，而是"用最合适的时空组合"——在满足业务时间要求的前提下，最小化空间资源占用；或在给定空间资源约束下，最大化时间效率。

比如：选择 Redis 缓存 vs 本地缓存——Redis 是时间更优（共享、避免重复计算）但空间成本更高（独立的服务器）；本地缓存是空间更优（共享应用内存）但时间可能更差（缓存一致性问题导致需要回源重算）。

### 1.1.2 非功能性约束的优先级

架构设计中有许多非功能性约束（性能、安全、可维护性、可扩展性、可用性）。《性能之道》提出了一个关键问题：**性能在全球非功能性约束中的优先级排第一吗？**

答案是：**视业务阶段而定**。

| 业务阶段 | 首要约束 | 原因 |
|---------|---------|------|
| **创业期（0→1）** | 可扩展性 | 业务模式不确定，需要快速迭代和试错 |
| **成长期（1→N）** | 性能 | 用户增长、流量激增，性能差会导致用户流失 |
| **成熟期（N稳定）** | 可用性 | 系统已稳定，任何宕机都造成直接营收损失 |
| **平台期（生态）** | 安全 + 合规 | 数据安全和隐私合规成为商业底线 |

> **跨书对照**：高翔龙的书几乎全部聚焦在"成长期"的性能约束——大促流量到来时系统如何不崩。余春龙的"显性vs隐性问题"框架补充了"可用性优先"阶段的思考。《性能之道》则提供了更完整的优先级模型：不同阶段，性能的重要性不同。这是一个避免"过度优化"的重要前提。

## 1.2 软件性能的时空观：时间效率 × 空间效率

### 1.2.1 性能的狭义与广义定义

《性能之道》将性能分为两个层次：

| 层次 | 定义 | 关注点 |
|:---:|------|------|
| **狭义性能** | 在尽可能少地占用系统资源的前提下，尽可能提高运行速度 | 降低延迟、提升吞吐、减少CPU/内存占用 |
| **广义性能** | 软件系统与其环境交互以获得价值和避免损失的程度 | 用户体验（P50/P99感知）、业务价值（每毫秒延迟的GMV损失）、成本效率 |

这两个层次的关系：狭义性能是手段，广义性能是目的。一个优化如果降低了 P99 延迟但也降低了业务 KPIs（如因用户感知不到变化却增加了运维成本），这个优化从广义性能角度看是不值得的。

### 1.2.2 时间效率的度量

时间效率的四个核心指标：

| 指标 | 含义 | 典型关注值 |
|------|------|:---:|
| **响应时间（RT）** | 单个请求的端到端时间 | P50: <100ms, P99: <500ms |
| **吞吐量（TPS/QPS）** | 单位时间内处理的请求数 | 系统目标 TPS |
| **并发数** | 同时处理的请求数 | 不超连接池上限 |
| **利用率** | CPU/内存/磁盘/网络的使用率 | CPU <70%（留余量给峰值） |

**关键关系——Little's Law**：响应时间 × 吞吐量 = 并发数（L = λW，稳态系统下的精确数学恒等式）。并发数是系统中平均排队的请求数（因变量），不是你可以直接调节的旋钮。降低延迟（优化代码）在稳态下会同时提升吞吐量——因为单请求占用时间减少，系统在相同资源下能处理更多请求。

### 1.2.3 空间效率的度量

### 1.2.4 阿姆达尔定律：并行化的天花板

性能优化的一个基本问题是："如果我把某段代码加速 10 倍，系统整体能快多少？" 答案不是直觉的"快 10 倍"——它取决于这段代码的**占比**。

**阿姆达尔定律（Amdahl's Law）**：

```
加速比 = 1 / ((1 - f) + f / s)

其中：
f = 可并行/可优化的部分占比（0≤f≤1）
s = 对 f 部分的加速倍数

示例：假设 30% 的代码可以并行化（f=0.3），并行化到 10 倍（s=10）
加速比 = 1 / ((1 - 0.3) + 0.3 / 10) = 1 / (0.7 + 0.03) = 1 / 0.73 ≈ 1.37x
```

**致命洞察**：**即使你把可优化的部分加速到无限快（s→），整体加速比的上限 = 1/(1-f)**

```
f=0.1（10%的代码可优化）→ 加速比上限 = 1/0.9 ≈ 1.11x  ← 顶多快11%！
f=0.5（50%的代码可优化）→ 加速比上限 = 1/0.5 = 2.00x  ← 顶多快1倍
f=0.9（90%的代码可优化）→ 加速比上限 = 1/0.1 = 10.00x ← 顶多快10倍
```

**这个定律解释了为什么大多数性能优化效果不佳**：开发团队花了 2 周优化一个函数的算法复杂度（从 O(n²)→O(n log n)），但如果这个函数只占总执行时间的 2%（f=0.02），即使优化到接近零开销（s→∞），系统的整体提升只有 1 / (1-0.02) ≈ 1.02x = **2%**。

**阿姆达尔定律与"点线面体"的映射**：

| 维度 | 典型 f 值 | 加速上限 | 意味着什么 |
|:---:|:---:|:---:|------|
| 点级优化 | 2-5% | < 1.05x | 除非在热点代码上，否则几乎无效 |
| 线级优化 | 10-30% | < 1.43x | 有明显效果，但有限 |
| 面级优化 | 30-60% | < 2.5x | 效果显著 |
| 体级优化 | 50-80% | < 5x | 最有效，但改动成本最高 |

**这解释了"点线面体"方法论为什么从"体"开始思考**——体级优化影响最大比例的代码路径（f 最大），带来的整体加速最明显。先做体面优化，再做线点微调——这就是"先做大手术，再做细调整"的数学基础。


| 指标 | 含义 | 典型瓶颈 |
|------|------|---------|
| **CPU利用率** | 计算密集度 | 算法复杂度、GC频率 |
| **内存占用** | 数据+对象+连接开销 | Heap大小、连接池、缓存 |
| **磁盘I/O** | 读写速度和频率 | 索引效率、日志写入 |
| **网络带宽** | 出口/入口流量 | 序列化效率、压缩 |

> **面试视角**：面试官问"系统变慢了，你怎么排查？"——不要只说"加缓存"或"扩容"。要从时空观出发：(1) 先量化：P99延迟是多少？CPU/内存/磁盘/网络哪个先到达瓶颈？(2) 判断方向：是时间问题（某个操作变慢）还是空间问题（某个资源耗尽）？(3) 定位层级：是网络层（RTT增大）？应用层（GC频繁）？还是数据库层（慢查询增多）？时空观提供了"先判断方向，再定位层级"的排查框架。

## 1.3 点线面体：性能优化的四个维度

### 1.3.1 什么是点线面体？

### 1.3.2a 点级优化的实战：从JMH基准测试说起

点级优化的第一步不是优化，而是**确认这段代码真的有热点**。Java 中最严谨的方式是使用 JMH（Java Microbenchmark Harness，Java 微基准测试框架）。

**为什么不用 System.currentTimeMillis() 测性能？**

```java
// 反模式：手写的"基准测试"
long start = System.currentTimeMillis();
for (int i = 0; i < 100000; i++) {
    String s = "hello" + "world" + i;
}
long end = System.currentTimeMillis();
System.out.println("耗时：" + (end - start) + "ms");
```

这段代码有三个致命问题：
1. **JIT 预热未排除**：JVM 会逐步编译热点代码（Interpreted → C1 → C2），前几千次调用和后几十万次调用性能可能差数倍
2. **死代码消除（DCE，Dead Code Elimination）**：JIT 发现 `s` 从未被使用，可能直接删除整个循环！你的"基准测试"实际上什么都没测
3. **GC 干扰**：循环触发了 GC，但你测量的时间包含了 GC 暂停时间

**正确的 JMH 基准测试**：

```java
@BenchmarkMode(Mode.Throughput)
@OutputTimeUnit(TimeUnit.SECONDS)
@State(Scope.Thread)
@Warmup(iterations = 3, time = 1)    // 预热3次，排除JIT影响
@Measurement(iterations = 5, time = 2) // 正式测量5次
@Fork(1)                               // 独立JVM进程，避免GC干扰
public class StringConcatBenchmark {
    
    @Benchmark
    public String stringPlus() {
        String s = "";
        for (int i = 0; i < 1000; i++) {
            s += i;  // 每次+都创建新StringBuilder → 1000个临时对象
        }
        return s;
    }
    
    @Benchmark
    public String stringBuilder() {
        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < 1000; i++) {
            sb.append(i);
        }
        return sb.toString();
    }
}
```

**实际测试结果（JDK 17, x86_64）**：

| 方法 | 吞吐量 | 与 stringPlus 对比 |
|------|:---:|:---:|
| `stringPlus()` | 50,000 ops/s | 1x |
| `stringBuilder()` | 350,000 ops/s | **7x** |

> **生产陷阱**：JMH 基准测试和实际生产环境之间仍有差距——JMH 测的是"无竞争、无GC、纯CPU"的理想场景。实际生产环境有线程竞争、GC 活动、I/O 等待、缓存未命中。JMH 的结果告诉你"这段代码的理论极限"，而不是"部署到生产后的实际表现"。要获得实际数据，唯一的方式是**线上压测 + 监控**。

### 1.3.2b false sharing——一个缓存行毁掉的多核性能

点级优化中最隐蔽的问题是 **false sharing（伪共享）** ——两个不相关的变量共享同一个 CPU 缓存行，导致多核间的无意义同步。

```
CPU 缓存行通常为 64 字节。假设有：

volatile long counter1;  // 8 字节
volatile long counter2;  // 8 字节

counter1 和 counter2 在内存中相邻 → 落在同一个 64 字节缓存行中
```

**问题发生时**：核心 1 修改 `counter1` → 缓存一致性协议（MESI，Modified/Exclusive/Shared/Invalid）将**整个缓存行**标记为核心 1 的独占状态 → 核心 2 要读 `counter2` → 缓存行被核心 2 请求 → 核心 1 必须将其写回内存 → 核心 2 读入

**核心 2 明明只想读 `counter2`（与 `counter1` 无关），但因为它们共享一个缓存行，被迫等待核心 1 的写操作完成。** 这在高并发场景下可使性能下降 **10-100 倍**。

**解决方案——`@Contended` 注解**（JDK 8+，需 JVM 参数 `-XX:-RestrictContended`）：

```java
@sun.misc.Contended
volatile long counter1;

@sun.misc.Contended  
volatile long counter2;
```

`@Contended` 会让 JVM 在字段前后填充无用的字节，确保每个字段独占一个缓存行。代价是内存浪费（一个 8 字节的 long 占用了 128 字节），但换来了多核并发性能的大幅提升。JDK 内部的 `ForkJoinPool`、`ConcurrentHashMap`、`Thread` 类都用了这个技术。

> **发散思考**：Java 的 `@Contended` vs C/C++ 的手动 `__attribute__((aligned(64)))` —— Java 的注解方式是声明式的，由 JVM 在运行时动态决定是否生效（取决于 JVM 版本和 `-XX:-RestrictContended` 参数）；C/C++ 的方式是编译时的，由程序员精确控制。Java 的灵活性更高（可以在不同 CPU 架构上选择不同对齐策略），但代价是JVM复杂度。C/C++ 更可控但更依赖程序员对目标硬件的了解。


这是《性能之道》最核心的方法论贡献。四位作者将性能优化分为四个递进的维度：

```
┌─────────────────────────────────────────────┐
│  体（Volume）：整个分布式系统                  │
│  关注：全链路、系统间交互、架构设计、容量规划    │
│  例：微服务拓扑优化、全链路压测、异地多活        │
├─────────────────────────────────────────────┤
│  面（Surface）：模块/子系统                    │
│  关注：模块交互、数据流转、接口设计、资源分配    │
│  例：缓存策略优化、数据库读写分离、MQ削峰        │
├─────────────────────────────────────────────┤
│  线（Line）：代码执行路径                      │
│  关注：业务流程、算法复杂度、I/O路径            │
│  例：SQL优化、调用链精简、异步化改造             │
├─────────────────────────────────────────────┤
│  点（Point）：单个语句/函数                    │
│  关注：CPU指令、内存分配、锁竞争、GC             │
│  例：避免字符串拼接、减少对象创建、CAS替代锁     │
└─────────────────────────────────────────────┘
```

**四个维度的优化投入与收益**：

| 维度 | 投入（改动量） | 收益（性能提升） | 典型收益量级 |
|:---:|:---:|:---:|:---:|
| **点** | 极小（一行代码） | 小（单函数加速） | 5%-20% |
| **线** | 小（一个方法/接口） | 中（一条路径加速） | 30%-100% |
| **面** | 中（一个模块/子系统） | 大（局部系统加速） | 2x-10x |
| **体** | 大（整体架构调整） | 极大（全局系统性提升） | 10x-100x |

**核心洞察**：**收益最大的优化往往在"面"和"体"层，而不是"点"和"线"层。** 但大多数开发者习惯从"点"层开始（因为最容易改）——这解释了为什么很多性能优化"做了很多但效果不明显"。一个真正的架构师，应该从"体"层分析瓶颈，在"面"层设计方案，在"线"层实施改造，在"点"层做最后的微调。

### 1.3.2 点级优化（微观优化）

点级优化关注的是**单个语句或函数**的执行效率。常见技巧：

| 技巧 | 原理 | 收益 | 代价 |
|------|------|:---:|------|
| 避免不必要的对象创建 | 减少GC压力 | 5-10% | 代码可读性下降 |
| 使用 StringBuilder 替代 + 拼接 | 避免中间字符串对象 | 循环中可提升数倍 | 代码变长 |
| 用局部变量替代多次方法调用 | 减少栈帧开销 | 微小 | 几乎无 |
| 用 `switch` 替代长 `if-else` | case 稠密→tableswitch 跳转表 O(1)，稀疏→lookupswitch 二分查找 O(log n) | 分支多时明显 | 适用性有限 |

**点级优化的适用场景**：**热点代码**。只有被频繁调用（每秒万次以上）的代码才值得做点级优化——一条冷路径中的 `StringBuilder` 优化没有任何意义。判断热点的方法：profiling（如 JProfiler、async-profiler）或 JVM 的 `-XX:+PrintCompilation` 查看 JIT 编译热点。

### 1.3.3 线级优化（执行路径优化）

线级优化关注**一条完整的执行路径**——从请求接受到响应返回的整个链路。

**线级优化的四种策略**：

**策略一：减少路径长度（减少调用跳数）**

```
优化前：A → B → C → D → E（5次RPC调用，每跳RPC开销5ms + 业务处理45ms = 250ms）
优化后：A → B'（合并C/D/E为进程内调用），RPC开销5ms + 业务处理135ms = 140ms
节省：110ms（~44%），主要是消除了4次RPC的序列化/网络/反序列化开销
```

> **关键区分**：优化前 250ms 中的大部分（225ms）是 C/D/E 的**业务处理时间**（查库、计算），不是 RPC 开销（仅 25ms）。合并后业务逻辑仍需执行，节省的只是 RPC 开销。这正是"微服务拆得太细"的代价——不是服务本身慢，而是调用链路上的序列化和网络开销累积。

> **重要警告**：合并服务与微服务拆分理念相矛盾。合并减少RPC开销，但增加了耦合。这不是"合并一定好"——而是在**热路径上**，当RPC开销成为瓶颈时，局部合并是合理的。不存在"永远微服务化"或"永远合并"的绝对法则。

**策略二：串行改并行（异步化）**

已在余春龙第2章 2.1.2 中详细讨论：同步调用 `T = T1+T2+T3`，异步调用 `T = Max(T1,T2,T3)`。

**策略三：重写轻读**（计算迁移）

已在高翔龙第4章讨论过：微博 Feeds 流的"写时计算"将读取成本转移到写入侧。

**策略四：减少无用计算**

- 避免在循环中重复计算不变值（提取到循环外）
- 用缓存替代重复的数据库查询（但要处理一致性问题）
- 只在需要时才做深拷贝（浅拷贝或不可变对象）

### 1.3.4 面级优化（模块/子系统优化）

面级优化关注**模块或子系统级别**的性能瓶颈。这是大多数性能优化的主战场。

**面级优化的三个核心方向**：

| 方向 | 策略 | 经典案例 |
|------|------|---------|
| **分流** | 将流量分散到多个处理单元 | 负载均衡、读写分离、分库分表 |
| **削峰** | 控制流量进入系统的速率 | 限流、MQ缓冲、排队 |
| **缓存** | 用空间换时间，存储计算结果 | Redis、本地缓存、CDN |

这三个方向不是独立的——它们通常会联合使用。大促场景下：负载均衡分流到多个节点 → 每个节点用本地缓存避免重复计算 → MQ 缓冲下游压力 → 分库分表分散写入。

### 1.3.5 体级优化（系统级优化）

体级优化是最高层次的优化，关注**整个分布式系统的架构设计**。

**体级优化的核心决策**：

| 决策 | 权衡 |
|------|------|
| **微服务拆分粒度** | 粒度越细，独立部署能力越强，但 RPC 开销越大 |
| **数据一致性模型** | 强一致性能最差但最简单，最终一致性能最好但最复杂 |
| **CAP 策略选择** | 网络分区时选 A（可用性）还是 C（一致性） |
| **容量规划** | 超配浪费资源，欠配无法应对峰值 |
| **多活 vs 灾备** | 多活提高资源利用率但引入数据冲突，灾备简单但浪费 |

> **体级优化的关键**：体级优化不是单独执行的——它定义了"面/线/点"优化的方向和边界。如果体级决策选错了（如 CAP 策略），面/线/点的优化无论多好都无法弥补。这就好比：如果你决定开车从北京去上海（体级决策），油箱加多少油（面级）和走哪条高速（线级）的决定才有意义。如果你决定坐飞机，前面的所有讨论都不适用。

## 1.4 性能优化策略：控制需求 vs 管理供给

### 1.4.1 两派策略

《性能之道》将性能优化策略分为两大派：

| 策略类型 | 思路 | 典型手段 |
|---------|------|---------|
| **控制资源需求** | 减少系统需要处理的请求量 | 优先级处理、限流、熔断、降级、减少开销 |
| **管理资源供给** | 增加系统处理请求的能力 | 扩容、并发化、缓存、使用更高效的算法 |

**策略选择的决策树**：

```
遇到性能问题 →
  ├── 请求量是否远超系统容量？ → 是 → 控制资源需求（限流/降级/削峰）
  │                                   ↓ 稳定后
  │                              管理资源供给（扩容/缓存/优化）
  └── 请求量在合理范围内？      → 是 → 直接进入管理资源供给
```

关键洞察：**控制资源需求是"止血"，管理资源供给是"治病"**。大促流量峰值来临时，先限流（控制需求），系统稳定后再扩容+缓存（管理供给）。如果一上来就扩容，等扩容完成，峰值已经过去，损失已经发生。

### 1.4.2 控制需求的具体策略

| 策略 | 说明 | 典型实现 |
|------|------|---------|
| **按优先级处理** | 高优请求优先分配资源，低优请求排队或丢弃 | 消息队列优先级队列、VIP用户优先通道 |
| **减少开销** | 合并不必要的服务调用、精简数据传输 | 将链式调用的微服务局部合并（面级优化） |
| **提高资源效率** | 在同等资源下处理更多请求 | 批量更新（取代逐条更新）、使用更高效的算法 |
| **限制响应（限流）** | 超过阈值的请求直接拒绝 | Sentinel 限流、Nginx 令牌桶 |

### 1.4.3 管理供给的具体策略

| 策略 | 说明 | 典型实现 |
|------|------|---------|
| **增加资源** | 提升硬件配置或增加实例数 | 垂直扩容（升配）、水平扩容（加机器） |
| **增加并发** | 从串行处理变为并行处理 | 多线程、异步化、流水线 |
| **使用缓存** | 预计算结果，避免重复计算 | Redis、本地缓存、CDN |
| **分拆资源** | 将共享资源拆分为独立资源 | 分库分表、Redis Cluster 分片 |

## 1.5 性能测试与评估：从指标定义到容量规划

### 1.5.1 性能测试的核心问题

《性能之道》指出，性能测试的核心不是"压到多大 QPS"，而是回答以下三个问题：

1. **系统当前的容量上限是多少？**（基准测试）
2. **系统在多大负载下性能开始下降？**（压力测试）
3. **系统在峰值流量下能否稳定运行？**（全链路压测）

### 1.5.2 性能指标体系

| 指标类型 | 核心指标 | 为什么重要 |
|---------|---------|----------|
| **响应时间** | P50/P90/P99/P999 | P99 决定了大部分用户的体验上限 |
| **吞吐量** | TPS（业务）/ QPS（技术） | 系统容量上限的直接度量 |
| **错误率** | 错误请求 / 总请求 | 超过阈值说明系统已过载 |
| **资源利用率** | CPU/内存/磁盘/网络 | 哪个资源先到瓶颈 = 优化的第一目标 |
| **并发用户数** | 同时在线/活跃用户 | 与实际业务需求对比 |

### 1.5.3 容量规划公式

### 1.5.4 排队论与容量规划：从"猜"到"算"

容量规划最原始的公式在第 1.5 节已经给出，但那个公式隐含了一个致命假设：**系统的响应时间恒定**。在现实中，随着负载增加，响应时间不是恒定的——它呈指数增长。

**M/M/1 排队模型**（Markovian arrival, Markovian service, 1 server）：

```
E[T] = E[S] / (1 - ρ)

其中：
E[T] = 平均响应时间（含排队等待）
E[S] = 平均服务时间（纯处理时间）
ρ    = 利用率（到达速率 / 处理速率）

当 ρ = 0%  → E[T] = E[S]（无排队）
当 ρ = 50% → E[T] = 2 × E[S]（排队时间 = 服务时间）
当 ρ = 80% → E[T] = 5 × E[S]（排队时间 = 4 × 服务时间！）
当 ρ = 90% → E[T] = 10 × E[S]
当 ρ = 99% → E[T] = 100 × E[S]（系统几乎不可用）
```

**关键洞察**：**利用率从 50% 提升到 80%，响应时间只增加 3 倍（5x vs 2x）。但从 90% 提升到 99%，响应时间暴增 10 倍（100x vs 10x）！** 这解释了为什么系统在 "CPU 70%" 和 "CPU 90%" 下的行为完全不同——前者是可控的线性增长，后者是指数级恶化。

**为什么 CPU 70% 是经验警戒线？**

```
ρ=0.7 → E[T] = E[S] / (1-0.7) = E[S] × 3.33
ρ=0.8 → E[T] = E[S] / (1-0.8) = E[S] × 5.00  ← 上升 50%
ρ=0.9 → E[T] = E[S] / (1-0.9) = E[S] × 10.0  ← 再上升 100%
```

从 70% 到 90% 只增加了 20% 的利用率，但响应时间增加了 3 倍。**这个非线性关系是容量规划中最容易被忽视的规律**——很多人以为"CPU 80% 还留 20% 余量够了"，但实际上响应时间在 70-80% 区间已经开始加速恶化。

**容量规划公式的排队论修正**：

```
传统公式：所需机器数 = 峰值QPS / 单机QPS
修正公式：所需机器数 = 峰值QPS / (单机QPS × 目标利用率系数)

目标利用率系数 = 1 - (目标排队倍数 - 1) / 目标排队倍数
例如：
  允许排队时间 = 服务时间的 2倍 (E[T]=2×E[S]) → 利用率系数 = 0.5（即 50% CPU）
  允许排队时间 = 服务时间的 5倍 (E[T]=5×E[S]) → 利用率系数 = 0.8（即 80% CPU）
```

> **发散思考**：Google 的 SRE（Site Reliability Engineering，站点可靠性工程）一书中提出了"错误预算"（Error Budget）的概念。这里我们可以类比提出"**排队预算**"——在系统设计阶段就明确"我们允许多少倍的排队延迟"：对延迟敏感的 API（如搜索、支付确认）→ 排队预算 = 2x（E[T] ≤ 2 × E[S]）→ 利用率上限 = 50%；对批处理任务（如报表、离线分析）→ 排队预算 = 10x → 利用率上限 = 90%。**排队预算是性能 SLA 的数学基础**。


容量规划的本质是：**从业务目标反推技术指标**。

```
年度 GMV 目标 → 日均订单量 → 峰值 QPS（日峰值 = 日均 × 峰值系数）
峰值 QPS → 单机 QPS（通过基准测试得出）→ 所需机器数 = 峰值 QPS / 单机 QPS
单库写入量 → 分库数 = 总量 / 单库容量上限
```

**为什么"拍脑袋扩容"是错的？**

- 拍脑袋：QPS 10000，按单机 500 QPS 算，直接扩容 20 台
- 容量规划：压测发现 QPS 到 8000 时数据库连接池先耗尽（不是 CPU 或内存），瓶颈在 DB 连接数，不是应用服务器
- 正确的做法：优化 DB 连接池配置 + 读写分离，而不是盲目加应用服务器

**关键原则**：**扩容必须基于压测数据，压测必须基于线上环境**（高翔龙第2章全链路压测已详细论证）。

## 1.6 本章核心观点总结

1. **架构的时空观**：性能优化本质上是时间效率与空间效率的权衡。不存在"全面提升"——每一点时间优化都需要付出空间代价，反之亦然。

2. **性能优先级取决于业务阶段**：创业期可扩展性优先，成长期性能优先，成熟期可用性优先。不要在任何阶段过度优化。

3. **点线面体四维优化体系**：点是代码级优化（收益最小），线是路径级优化，面是模块级优化，体是架构级优化（收益最大）。优秀架构师从"体"出发，在"面"设计方案，在"线"实施，在"点"微调。

4. **控制需求 vs 管理供给**：大促场景下先控制需求（限流止血），再管理供给（扩容治病）。两者的顺序不能颠倒。

5. **性能测试回答三个问题**：容量上限（基准）、性能拐点（压力）、峰值稳定性（全链路）。测试数据直接驱动容量规划。

6. **容量规划公式**：从 GMV → 日均订单 → 峰值 QPS → 单机 QPS → 所需机器数。每一个环节都需要压测数据支撑，不是凭经验估算。

> **跨书学习建议**：
> - 高翔龙第2-3章是"面级"和"体级"优化的工程落地——全链路压测 + 流控 + 削峰
> - 余春龙第2章的技术架构提供了 CAP 理论和一致性模型的底层支撑
> - 《性能之道》的点线面体方法论为前两本书的所有优化手段提供了"分类框架"——读完方法论后重读高翔龙，会发现每一章都对应一个优化维度（全链路压测=体，限流=面，MQ削峰=线，Guava/Lua=点）

### 本章面试高频题

**Q1: 什么是点线面体？为什么大多数人的性能优化效果不明显？**

> **面试官意图**：考察是否有全局视野——90%的候选人只会从"点"和"线"的回答问题（加缓存、优化SQL），面试官想听的是你能否上升到"面"和"体"的维度。

**回答要点**：
- 点（代码语句级）：收益5-20%，如StringBuilder替代+拼接
- 线（执行路径级）：收益30-100%，如RPC调用合并、异步化
- 面（模块/子系统级）：收益2-10x，如缓存策略、读写分离、分库分表
- 体（系统架构级）：收益10-50x，如微服务拓扑优化、CAP策略调整
- 大多数人的优化锁在"点"层（最容易改），但真正的瓶颈在"面"和"体"层

> **追问到第二层**："如果你只能做一个维度的优化，选哪个？为什么？"→ 选"面"层。因为点层的收益太小（5-20%），体层的改动成本太高（需要重构架构）。面层（如加缓存、读写分离、分库分表）通常能用2-4周的改动获得2-10倍的提升，投入产出比最高。

**Q2: Little's Law 在性能调优中怎么用？有什么限制？**

> **面试官意图**：考察是否能用数学模型指导工程决策，而非凭直觉调优。

**回答要点**：
- L=λW：并发数 = 吞吐量 × 响应时间（稳态下的精确恒等式）
- 调优意义：降低RT（W）→ 相同资源下吞吐量（λ）自然上升
- 非稳态限制：Little's Law 假设系统处于稳态——请求到达速率和处理速率恒定。在突发流量（如大促零点）下，系统未达到稳态，该公式不能直接套用。此时排队论（M/M/1模型 `E[T]=E[S]/(1-ρ)`）更适用

> **追问到第二层**："如果little's law告诉你要加机器，但预算不够怎么办？"→ 回到控制资源需求的策略——限流、削峰、降级。先"止血"（控制进入量），再在有限资源下用面级优化（加缓存、异步化）提升单机吞吐。

**Q3: 大促流量来了，先扩容还是先限流？为什么？**

> **面试官意图**：考察应急决策能力和对性能优化策略顺序的理解。

**回答要点**：
- 先限流（控制资源需求），再扩容（管理资源供给）
- 原因：扩容需要时间（分钟级），峰值流量是瞬时的（秒级）。先限流能立即保护系统不崩，等扩容完成后（或峰值过去后）再放开限流
- 限流阈值如何定：基于压测数据（全链路压测得出的单机QPS × 目标利用率系数）
- 如果连压测数据都没有：快速估算——单机 QPS = 1000ms / P99 RT × 并发数 × 安全系数（如0.7）

> **追问到第二层**："限流导致用户体验变差怎么办？"→ 分用户优先级：VIP用户（高净值/高复购）放行，普通用户排队或降级提示。本质是在"全员体验差（系统崩了谁都用不了）"和"部分用户体验差（被限流的人排队）"之间的权衡。
