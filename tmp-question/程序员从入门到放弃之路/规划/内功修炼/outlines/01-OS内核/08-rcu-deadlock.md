### 1. RCU — 读零开销、写复制替换

场景提示: nf_conntrack 连接表——每个包都要查，读者比写者多几个数量级；读者加锁的开销不可接受。 [写作时展开]

关键设计: RCU（Read-Copy-Update）的核心：**读完全无锁，写者负责等读者离开**：

```[pseudocode]
读:  rcu_read_lock/rcu_read_unlock（空操作，仅关内核抢占）→ 遍历链表零成本
写:  复制对象 → 修改副本 → 原子替换指针（wmb 保证可见）→ call_rcu 注册回调
    → 等待 Grace Period（所有旧读者离开）→ 释放旧数据
```

- **读无锁**: 遍历链表/radix tree 不需要锁——读者不会阻塞写者
- **写复制替换**: 写不修改原对象，而是复制-改-替换指针——旧读者继续用旧副本
- **Grace Period 关键**: 每个 CPU 经历一次 **quiescent state（QS）**——不在任何 RCU 读临界区的时刻（空闲/用户态/退出临界区；上下文切换是检测 QS 的机制之一）→ `rcu_gp_kthread` 据 QS 推进 GP → 所有旧读者必然离开 → 旧数据可安全释放 [内核: RCU 回调在 softirq 上下文执行——与 09 篇 softirq 关联]
- **GP 加速**: `CONFIG_RCU_BOOST`（提升 reader 优先级防被抢占拖延 GP）/ `rcu_nocbs`（offload 回调到 kthread 避免软中断延迟）

Why: 为什么读者"无锁"是安全的？——读者访问的数据被写者**替换**而非修改：旧读者持旧指针（旧副本仍在），写者等"所有人都离开旧版本"（GP）后才释放。锁的哲学是"你等我"；RCU 的哲学是"我不等你，我等你走"——读者永远不用等，等待成本全部由写者承担。

比喻锚点: RCU=图书馆闭馆清场——读者（读）随时进出（无锁），管理员（写）不赶人，等所有人都离开（Grace Period）才换书架上的书（释放旧数据）；清场期间新读者看新书、旧读者看完手上的旧书。 [写作时展开]

### 2. lockdep 死锁检测 — 内核内置的运行时测试

场景提示: 内核加锁顺序错了（ABBA）——不是每次都会死锁，是特定交错才触发；怎么提前发现？ [写作时展开]

关键设计: lockdep（kernel/locking/lockdep.c）跟踪**每次锁获取的顺序**，构建依赖图，运行时检测潜在回路：

```[pseudocode]
每个锁类(lock class)赋序号 → 每次获取记录 class1→class2 边
图中已有 class2→class1 边 → 存在潜在回路 → 报告
"possible circular locking dependency detected"
```

- **死锁 4 条件**: 互斥 + 持有等待 + 不可剥夺 + 循环等待（ABBA）
- **检测 > 预防**: 内核预防（规范加锁顺序）+ lockdep 检测（违规立即报告，即使这次没死锁）
- **诊断实战**: `echo t > /proc/sysrq-trigger` → dmesg 输出所有任务栈 → 分析锁持有者 → 定位死锁现场

Why: 为什么 lockdep 在"没死锁时"也能报错？——死锁是**交错时序**问题：ABBA 只有在恰好同时发生的窗口才死锁，平时"看起来正常"。lockdep 检测的是**顺序违规**（图中出现环），不是实际死锁——把概率性事故变成确定性报告，这是它价值所在。

比喻锚点: lockdep=交警查违章记录——没出事故（没死锁）也能从行车路线（加锁顺序）发现"两条路互相逆行"的隐患，提前开罚单（报告潜在回路）。 [写作时展开]

### 3. 活锁 — 活跃但无进展

场景提示: 两个线程互相谦让——各自"你有你先来"，结果谁也进不去。 [写作时展开]

关键设计: 活锁 = 线程**不断改变状态但都无法进展**——与死锁对比：

| | 死锁 | 活锁 |
|------|------|------|
| 状态 | 停止（都在等） | 活跃（都在动） |
| 示例 | ABBA 互相持锁等待 | 两线程抢锁失败互让（trylock 回退再试） |
| 检测 | lockdep/栈分析 | **无工具**（比死锁更难发现） |
| 解决 | 规范顺序 | 随机退避 + 超时 + `cpu_relax()` 指数回退 |

活锁示例: 两线程 `trylock` 都失败 → 各自"你先来"让位 → 又同时重试 → 再次失败——循环往复，CPU 忙但无进展（典型：锁竞争下的退避无随机化）。

Why: 为什么活锁比死锁难检测？——死锁时任务栈是静态的（明显卡住）；活锁时 CPU 占用 100% 且任务在跑，没有"卡住"的迹象——只能从"进展为零但 CPU 忙"推断。

### 4. per-CPU + 内核抢占 — 免锁的另一种路径

场景提示: 每核独立的统计计数器——每核只写自己的副本，为什么需要锁？ [写作时展开]

关键设计: **per-CPU 变量**——每个 CPU 一份独立副本，本核只操作自己的 → 天然无竞争免锁：

```[pseudocode]
DEFINE_PER_CPU(type, name) → 每核独立实例
get_cpu_var/put_cpu_var（关抢占保护）→ this_cpu_inc（%gs 偏移寻址）
适合: 统计计数器/per-CPU 缓存
```

内核抢占模式: CONFIG_PREEMPT_NONE（自愿抢占）/ CONFIG_PREEMPT（可抢占）/ CONFIG_PREEMPT_RT（完全可抢占）→ `preempt_count` 跟踪 → **自旋锁自动关抢占**（持锁期间不可被调度走，07 篇已述）→ `preempt_disable/enable`。

Why: per-CPU 与锁的关系——**把"共享"变成"不共享"**：每个核有独立副本，写操作零竞争。代价是数据可能不同步（读到的是本核副本）；适用"每核独立累加、偶尔汇总"的场景（如 /proc/stat 的 CPU 计数器）——这是比 RCU 更激进的免锁：连读都不用锁，因为根本不共享。 [内核: preempt_count 跟踪嵌套抢占/软中断状态——自旋锁持锁期间 preempt_count 非零防调度]

比喻锚点: per-CPU=每人自己的储物柜——各写各的（零竞争），月底（汇总）才把各柜记录合起来；钥匙（%gs 偏移）永远是自己的，不用等别人。 [写作时展开]

### 5. 经典软件互斥 (🟢)

场景提示: 硬件原子操作（LOCK 前缀）出现之前——纯软件怎么实现互斥？ [写作时展开]

关键设计: 三个历史方案 (B1 皮特森, B6 Ch13§1-3, Ch12§2-4)：

- **皮特森算法**: `flag[i]=true; turn=j` 两变量——教学意义（忙等+顺序保证的范式）
- **Dekker 算法**: 四步 flag 握手——历史意义（硬件原子之前的最后纯软件方案）
- **事件计数/定序器**: 非阻塞原语 `await(E,V)/advance(E)`——生产者-消费者计数同步

Why: 为什么这些被硬件原子取代？——纯软件互斥依赖**内存访问的即时可见性**假设（单核成立，多核缓存下不成立）；硬件原子（LOCK 前缀）在指令层保证不可分割，不再依赖软件推理。理解历史是为了理解"为什么需要硬件支持"。

比喻锚点: 经典软件互斥=没有锁的教室——靠"眼神确认"（flag）和"轮流让位"（turn）约定谁用讲台；人少（单核）可行，人多（多核）就乱了——后来直接给讲台装了物理锁（硬件原子）。 [写作时展开]

### 6. 收束

回到"读者必须等写者吗"：
- RCU = 读者零开销（写者等读者走）
- lockdep = 锁验证（运行时检测顺序违规）
- 活锁 = 锁失败的另一种形态（活跃但无进展）
- per-CPU = 免锁的极致（根本不共享）
- 经典互斥 = 硬件原子之前的历史

**Aha Moment**: "锁的哲学是'你等我'，RCU 是'我等你走'，per-CPU 是'我们根本不见面'——同步不是只有锁一条路。而 lockdep 把死锁从'概率性事故'变成'确定性报告'，这是内核工程最聪明的部分。"
**回答读者三问**: ①读者极多写者极少=RCU（读者零开销）；②死锁怎么提前发现=lockdep 运行时检测顺序环；③统计计数器怎么免锁=per-CPU 每核副本。
