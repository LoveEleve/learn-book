# 基准测试与测量 — 如何证明一个性能数字可信

> Cluster B: 5 KPs | 依赖: 01-methodology-foundation | 读者基线: Amdahl/Little、USE/RED、会运行 `perf stat`
> 读者处境: 01 篇建立了性能分析坐标系；本篇回答更基础也更容易被忽略的问题：一次 benchmark 的数字，究竟测到了目标机制，还是被编译器、缓存、频率和计时器骗了？

### 1. 基准分类 — 先说清楚要外推到哪里

场景提示: 一个函数微基准快了 20%，能否直接断言线上服务快了 20%？ [写作时展开]

关键设计: 不同基准回答不同层次问题：

```[pseudocode]
微基准:
  测一个函数/系统调用/小操作
  → 可控、定位细
  → 外推到真实系统风险高

仿真/工作负载基准:
  模拟请求比例、数据规模、并发和 I/O
  → 更接近目标场景
  → 模型偏差仍需说明

标准基准:
  SPEC/数据库/网络基准等固定规则
  → 便于横向比较
  → 不一定代表自己的 workload

生产回放/压测:
  真实流量或脱敏 replay
  → 相关性高
  → 成本、风险和可重复性更难控制
```

Why: 为什么 benchmark 类型本身就是结论的一部分？——**因为可控性和代表性永远存在取舍**：微基准能告诉你某个函数的机制变化，却不能自动预测缓存、锁、调度和 I/O 叠加后的服务收益。报告必须写清输入规模、并发、数据分布和“能否外推”。 [内核: `perf`/sysbench/iperf 等工具测量的是不同层次，工具名本身不代表实验有效]

比喻锚点: 微基准像测发动机台架功率，生产压测像带真实载重上高速；台架结果重要，但不能直接当作整车油耗。 [写作时展开]

### 2. 统计检查 — 预热、重复与分布比单次结果重要

场景提示: 同一程序连续跑十次，为什么第一次特别慢、P99 偶尔跳高，均值却看不出来？ [写作时展开]

关键设计: benchmark 至少要区分启动、预热、稳态和异常样本：

```[pseudocode]
实验阶段:
  1) 校验环境/输入
  2) warm-up: 让 JIT、缓存、连接池等进入目标状态
  3) measurement: 重复采样
  4) 记录异常与环境变化

报告:
  中位数/P50: 典型样本
  P95/P99: 长尾
  min/max: 边界与异常线索
  不只报告均值

记录:
  CPU频率/DVFS、CPU affinity、NUMA、内存状态、内核/编译器版本
```

Why: 为什么不能只跑三次然后取中位数？——**重复次数要由噪声大小、置信目标和成本决定**：三次只能是很弱的初筛；样本应先看分布和异常，再决定是否需要更多运行。预热也不是“永远丢掉第一次”，冷启动本身可能就是业务关心的指标。 [man 1 perf: 计数器结果需要结合运行时间、multiplexing 和系统干扰解释]

比喻锚点: 测量像体检，不是量一次体温就下诊断；要知道是晨起、运动后还是稳定状态，还要看异常波动。 [写作时展开]

### 3. 编译器、缓存与硬件 — 先证明实验没有被优化掉

场景提示: 代码里明明调用了 `work()`，benchmark 却显示耗时接近零，可能发生了什么？ [写作时展开]

关键设计: 编译器可能删除无副作用结果、常量折叠、循环展开/向量化；缓存和频率又会改变真实运行成本：

```[pseudocode]
编译器检查:
  结果未使用 → dead-code elimination
  输入/输出可推导 → constant folding
  循环可证明 → 外提/展开/向量化
  → 查看汇编/反汇编确认工作仍存在

缓存状态:
  cold cache ≠ warm cache
  → 先声明要测冷启动还是稳态
  → 不要把 drop_caches 当作无代价的“标准预热”

硬件状态:
  DVFS/turbo/C-state
  CPU affinity/NUMA
  THP/TLB/cache capacity
  → 记录或控制, 不要事后猜
```

Why: 为什么 `volatile` 不能成为所有 benchmark 的万能防优化工具？——**它改变的是编译器对访问的语义，可能引入额外内存访问和改变被测程序**；更好的做法是使用受控的 black-box/编译器 barrier、检查汇编，并让 harness 的防优化成本与目标工作分离。`-O0` 也不是“真实运行”，只能用于对照。 [内核: cache/TLB/THP 状态会改变内存路径；perf 事件能帮助验证实际执行特征]

比喻锚点: 测跑步速度前要确认跑步者真的在跑，而不是编译器把整段路删了；还要说明是在空跑道、逆风还是拥挤赛道。 [写作时展开]

### 4. 计时器与 PMU — 精度、开销和语义要匹配

场景提示: 纳秒级函数、毫秒级请求、CPU 周期和硬件 cache miss，应该用同一个计时 API 吗？ [写作时展开]

关键设计: 不同工具测量的对象不同：

```[pseudocode]
clock_gettime(CLOCK_MONOTONIC/RAW)
  → 单调时间基准, 适合 wall-clock 延迟
  → 具体时钟是否受校准/频率调整影响需查文档和环境

gettimeofday
  → wall-clock 时间, 不应作为严格单调延迟计时首选

rdtsc/rdtscp
  → 读取 TSC 周期
  → 需考虑序列化、CPU affinity、虚拟化和 TSC 语义

perf stat
  → cycles/instructions/cache-misses 等计数
  → 适合解释“为什么慢”, 不只是测 elapsed time

PMU/rdpmc
  → 低开销读取硬件计数器
  → 权限、计数器 multiplexing、CPU 支持和事件定义必须核对
```

Why: 为什么“精度越高”不等于“测量越好”？——**计时器有分辨率、调用开销、可迁移性和语义差异**：纳秒显示不代表误差是纳秒；TSC 周期也不直接等于固定 CPU 指令周期。Wall-clock、CPU time、cycles、instructions、cache miss 应分别回答不同问题。 [man 2 clock_gettime: `CLOCK_MONOTONIC`/`RAW` 的语义；[man 1 perf stat: PMU 事件与权限/复用信息]]

比喻锚点: 计时器像不同刻度的尺子：秒表量比赛总时长，转速表量发动机转速，故障灯量异常；刻度更细不代表它能回答别的问题。 [写作时展开]

### 5. 收束

可信 benchmark 的闭环：

```[pseudocode]
定义问题/外推边界
  → 固定输入与环境
  → 预热或明确冷态
  → 重复采样并看分布
  → 检查汇编确认代码未消失
  → 选择匹配的时钟/PMU
  → 报告中位数、长尾、异常与环境
  → 复现实验并验证回归
```

**Aha Moment**: "性能数字可信，不是因为计时器显示了很多小数，而是因为你能回答：**测的是什么、代码是否真的执行、环境是否可比、分布是否稳定、结论能外推到哪里**。"
**回答读者三问**: ①微基准快了能否代表线上快了=要看 workload 和外推边界；②为什么多次运行不同=缓存、预热、频率、调度和噪声；③如何避免测到假工作=检查汇编、控制输入、分离 harness 开销。
