# 性能方法论基础 — 用 USE、RED、60 秒分析和排队理论找到真正瓶颈

> Cluster A: 6 KPs | 依赖: 无 | 读者基线: Linux 基础命令、吞吐量/延迟概念
> 读者处境: 阶段 5 开篇；读者已经能看到 CPU、磁盘、网络指标，但线上“慢”很少直接告诉你是哪一种资源慢。本篇建立一套从症状到证据的性能分析方法

### 叙事顺序

1. 问题引入——用户说“接口变慢”，你应该先看 CPU、P99、磁盘 await 还是错误率？（**Aha: 性能排障需要两个坐标系：USE 找资源，RED 找服务；不能用一个指标包打天下**）
2. USE——资源的使用、饱和、错误
3. RED——服务的速率、错误、延迟
4. 60 秒分析——现场第一张系统画像
5. Amdahl/Little/排队——优化上限与容量关系
6. workload、下钻与可视化——从资源定位到代码
7. 收束——方法论闭环

### 1. USE — 对每个资源连续问三遍

场景提示: CPU 90% 时，究竟是有效工作、锁竞争，还是排队导致的忙等？ [写作时展开]

关键设计: USE 对每类资源都问三个问题：

```[pseudocode]
对 CPU / memory / disk / network / interconnect:
  Utilization:
    资源有多忙? 忙的是哪种工作?
  Saturation:
    是否有任务排队、等待或被限流?
  Errors:
    是否已经出现错误、丢包、重试或硬件异常?

例: 磁盘
  U: busy/time, IOPS, throughput
  S: queue depth, await, 请求排队
  E: I/O error, timeout, medium error
```

Why: 为什么只看 utilization 很容易误判？——**100% 忙可能代表高效吞吐，也可能代表队列已经失控；30% 忙也可能因锁、单线程或外部依赖而慢**。Saturation 把“资源忙”和“请求等资源”区分开，Errors 则帮助解释异常重试与性能抖动。 [内核: `/proc`、sysfs、块层、网络统计提供不同资源的观测面，不能把所有 `%util` 直接横向比较]

比喻锚点: USE 像检查收费站：看车道是否忙（U）、车辆是否排队（S）、是否发生事故（E）；只看车道灯亮不亮无法判断堵车原因。 [写作时展开]

### 2. RED — 对服务而不是机器问三个问题

场景提示: 机器 CPU 很空闲，但 API P99 从 50ms 升到 2s；该从哪个服务指标开始看？ [写作时展开]

关键设计: RED 从请求视角观察服务：

```[pseudocode]
Rate:
  每秒处理多少请求/消息/事务?

Errors:
  失败率、超时率、重试率、状态码/业务错误?

Duration:
  请求延迟分布，至少看 P50/P95/P99
  不用平均值掩盖长尾

USE vs RED:
  USE → 哪台机器/哪个资源可能饱和?
  RED → 哪个服务/哪个端点的请求变慢或失败?
```

Why: 为什么平均延迟经常不够？——**长尾用户体验由高分位决定，平均值会把少量极慢请求稀释掉**；但 P99 也必须结合请求量、样本数、时间窗口和直方图桶解释。RED 找到服务症状后，还要回到 USE 找底层资源因果。 [man 7 prometheus: Histogram/Summary 的分位数语义和聚合方式需要区分]

比喻锚点: RED 像医院急诊看诊：今天来了多少患者（Rate）、多少误诊/失败（Errors）、从挂号到处理花了多久（Duration），而不是只看医院总耗电量。 [写作时展开]

### 3. 60 秒分析 — 先建立现场画像，再深入下钻

场景提示: 线上告警刚发生，你只有一分钟和一台 Linux 主机，第一轮应该收集什么？ [写作时展开]

关键设计: 60 秒分析不是固定命令清单，而是一组快速覆盖 CPU、内存、I/O、网络和错误的现场检查：

```[pseudocode]
1. uptime / load average
   → 系统是否有持续排队趋势
2. dmesg -T
   → 内核错误、OOM、I/O、网卡异常
3. vmstat 1
   → 运行队列、上下文切换、内存、swap、I/O
4. mpstat -P ALL 1
   → CPU 是否单核热点/软中断偏斜
5. pidstat 1
   → 哪个进程/线程消耗 CPU 或 I/O
6. iostat -xz 1
   → 设备利用、队列、await、吞吐
7. free -m / memory.stat
   → 可用内存、回收、swap/cgroup
8. sar -n DEV,TCP,ETCP 1
   → 网络吞吐、连接、重传
9. top 或等效汇总
   → 快速确认进程级画像
```

Why: 为什么这些命令不能机械地“跑完就下结论”？——**它们的采样窗口、容器视角、虚拟化环境和权限都会影响含义**：load average 不是 CPU 百分比，iostat `%util` 不是所有设备的真实饱和度，`free` 也不能直接代表 cgroup 可用内存。60 秒分析的产物是“假设列表”，不是最终根因。 [内核: `/proc/stat`、`/proc/meminfo`、块设备和网络计数器是许多工具的底层数据源]

比喻锚点: 60 秒分析像急诊分诊：先测生命体征，决定下一步做心电图、影像还是化验，不是在一分钟内完成最终诊断。 [写作时展开]

### 4. Amdahl、Little 与排队 — 把指标变成可计算的约束

场景提示: 你把并行部分优化了 10 倍，为什么整体程序可能只快 1.5 倍？ [写作时展开]

关键设计: 三个模型回答不同问题：

```[pseudocode]
Amdahl:
  固定问题规模下
  speedup <= 1 / ((1-P) + P/S)
  P = 可优化/可并行部分占比

Little:
  L = λW
  平均系统内请求数 = 到达率 × 平均停留时间

排队直觉:
  利用率越接近 100%
  → 等待时间对抖动越敏感
  → 小的到达率/服务时间变化也可能放大尾延迟
```

Why: 为什么优化前必须先问“这部分占总时间多少”？——**Amdahl 把不可优化部分变成硬上限**：即使并行部分无限快，串行部分也仍在。Little 定律则把吞吐、并发数和延迟绑在一起，帮助容量规划；排队模型提醒我们高利用率通常伴随更高等待，但真实系统未必是理想 M/M/1。 [内核: run queue、I/O queue、socket queue 都体现“请求等待服务”的排队现象，但不能直接套一个理想分布]

比喻锚点: Amdahl 像修路时发现有一座不能拓宽的桥；Little 像数餐厅桌子、进店率和用餐时长；排队理论解释为什么餐厅接近满座后，等位时间会突然变长。 [写作时展开]

### 5. workload、drill-down 与可视化 — 从“资源高”走到“函数慢”

场景提示: USE 发现磁盘饱和，如何判断是哪个请求、哪个文件、哪个代码路径造成的？ [写作时展开]

关键设计: 性能分析必须保留工作负载上下文，再逐层下钻：

```[pseudocode]
workload:
  who  → 谁产生负载
  why  → 为什么产生
  what → CPU/I/O/网络/锁/内存组成
  how  → 随时间、并发和输入规模如何变化

drill-down:
  系统 → 子系统 → 进程/线程 → 组件 → 模块 → 函数

可视化:
  线图: 时间趋势
  热图: 时间 × 延迟/计数分布
  散点: 并发/输入与延迟关系
  火焰图: CPU、内存或 off-CPU 调用栈
```

Why: 为什么“CPU 高”还不够指导优化？——**没有 workload，就无法区分正常吞吐增长和异常退化；没有 drill-down，就无法把资源指标连接到代码责任**。可视化也不是装饰：热图能展示长尾时间分布，火焰图能展示采样期间的调用栈占比，但它们都需要正确的采样窗口和解释边界。 [内核: perf/ftrace/BPF 等工具把系统事件或调用栈连接到后续函数级分析]

比喻锚点: 下钻像从城市拥堵地图一路追到道路、路口、车道和具体事故车辆；只知道“城市红了”无法修一条正确的路。 [写作时展开]

### 6. 日志、指标与仪表板 — 把一次排障变成持续观测

场景提示: 性能问题过去后，为什么只保留一张截图远远不够？ [写作时展开]

关键设计: 可观测平台把一次性命令输出变成可关联、可留存、可比较的数据：

```[pseudocode]
日志:
  时间戳 + request_id/trace_id + 结构化字段
  → 还原单次请求路径

指标:
  counter / gauge / histogram
  → 观察速率、资源、错误和延迟分布

仪表板:
  主机资源 → 实例 → 服务 → 端点 → 健康检查
  → 同一时间窗口对齐比较

持续观测 ≠ 一次性 perf:
  平台负责发现变化和关联
  专项工具负责深入证明根因
```

Why: 为什么日志、指标和仪表板不能互相替代？——**指标适合趋势和聚合，日志适合单次事件上下文，追踪/请求 ID 适合跨服务关联**；高基数标签、采样、保留周期和时钟同步都会影响平台成本与结论。观测系统本身也消耗 CPU、网络和存储，不能无限采集。 [内核: 观测工具最终读取计数器、tracepoint、调用栈或应用埋点，各自有采样偏差]

比喻锚点: 指标是城市仪表盘，日志是每辆车的行车记录，追踪是从起点到终点的路线单；三者拼起来才有全景。 [写作时展开]

### 7. 收束

性能分析闭环：

```[pseudocode]
用户症状/告警
  → RED 找服务 Rate/Errors/Duration
  → USE 找资源 Utilization/Saturation/Errors
  → 60秒分析建立现场画像
  → workload + drill-down 找到组件/函数
  → Amdahl 判断优化上限
  → Little/排队理论做容量与尾延迟解释
  → 日志/指标/仪表板持续验证回归
```

**Aha Moment**: "性能方法论不是一串命令，而是一套从**症状 → 资源/服务 → 假设 → 证据 → 模型 → 修复 → 持续观测**的闭环；USE 和 RED 负责定位坐标，Amdahl/Little/排队理论负责约束直觉。"
**回答读者三问**: ①CPU/磁盘/网络先看什么=USE 三问；②接口变慢看什么=RED 的速率、错误和长尾延迟；③优化有没有上限=Amdahl，容量是否撑得住用 Little 和排队关系验证。
