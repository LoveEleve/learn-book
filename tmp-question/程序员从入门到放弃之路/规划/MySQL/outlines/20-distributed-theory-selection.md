### 1. CAP — 先定义故障模型，再谈一致性与可用性

场景提示: 跨机房网络断开时，系统应该继续接受写入，还是宁可拒绝部分请求？ [写作时展开]

关键设计: CAP 讨论的是存在网络分区时，系统对一致性和可用性的取舍，不是平时“三选二”的产品标签：

```[pseudocode]
C(Consistency):
  读取满足系统定义的最新/线性化语义

A(Availability):
  每个非故障请求最终得到响应

P(Partition tolerance):
  网络分区/消息丢失时系统仍需做选择

发生 P:
  选择更强 C
    → 可能拒绝/等待部分请求
  选择更高 A
    → 可能返回旧值/冲突值
```

Why: 为什么“CAP 三者不可兼得”不能直接拿来给数据库贴标签？——**它针对特定一致性、可用性和分区模型，实际系统还有延迟、故障恢复、读写路径、业务补偿和一致性级别**；网络不分区时也可能在 C/A 之间做性能选择。CAP 是约束和问题框架，不是产品排名。 [分布式理论: 一致性需要明确是线性化、一致性读、因果还是最终一致]

比喻锚点: 两座城市断桥时，必须决定是暂停售票保证两边账本一致，还是继续售票并接受稍后对账；不存在“断桥时两边都立即知道全部最新交易”的免费方案。 [写作时展开]

### 2. 垂直与水平拆分 — 把容量/业务边界变成数据边界

场景提示: 单库变大后，是把用户、订单、库存拆成不同库，还是把同一张订单表按 tenant/id 分片？ [写作时展开]

关键设计: 两种拆分解决不同问题：

```[pseudocode]
垂直拆分:
  按业务域/列/表拆分
  user/order/inventory → 不同库或服务
  → 边界清晰、单域扩展
  → 跨域 JOIN/事务变复杂

水平拆分:
  同一逻辑表按 shard key 分区
  tenant_id/user_id/hash/range
  → 单分片数据与流量下降
  → 跨分片查询、排序、聚合、迁移变复杂
```

Why: 为什么分库分表不能只看单表行数？——**真正的边界还包括访问模式、事务范围、热点 key、跨域 JOIN、扩缩容和数据迁移**；错误 shard key 会把所有热点集中到一个分片，垂直拆分也可能把一个强事务拆成分布式事务。 [MySQL: ProxySQL/ShardingSphere/客户端分片的路由和事务能力不同，不应抽象成同一产品]

比喻锚点: 垂直拆分像把超市按商品类别分店，水平拆分像把同一类商品按顾客区域分仓；顾客需要跨店购买时，结账和配送都会变复杂。 [写作时展开]

### 3. 客户端与中间件分片 — 路由、事务和查询代价

场景提示: 分片后应用如何知道数据在哪，跨分片 JOIN 和全局排序又怎么办？ [写作时展开]

关键设计: 路由责任可以放客户端、代理/中间件或独立服务，但成本不会消失：

```[pseudocode]
客户端分片:
  应用根据 shard key 选择节点
  → 延迟低/控制直接
  → 每个服务都要理解拓扑、迁移和重试

中间件分片:
  ProxySQL/ShardingSphere 等解析/路由
  → 应用接入简单
  → 代理状态、SQL改写、跨分片事务和单点治理成本

跨分片查询:
  fan-out 到多个分片
  → 各自过滤/排序/聚合
  → coordinator merge
  → 延迟受最慢分片和数据量影响
```

Why: 为什么分片后“单库查询优化经验”会失效？——**网络往返、最慢分片、分布式排序/聚合、全局唯一 ID、事务和重试都加入了成本模型**；中间件能隐藏路由，却不能消除跨分片语义。设计时要明确哪些查询必须跨片、哪些可异步最终一致。 [分布式理论: 分片路由与事务边界必须由业务访问模式驱动]

比喻锚点: 分片查询像向多个仓库同时询价，最后还要等最慢仓库返回并合并报价；中间件只是帮你拨电话，不会让远端仓库瞬间完成。 [写作时展开]

### 4. 数据库全景 — 先按数据模型和访问模式分类

场景提示: 关系型、KV、列式、文档、图、时序和搜索数据库各自解决什么问题？ [写作时展开]

关键设计: 数据库类别应从访问语义和物理组织理解，而不是从产品名记忆：

```[pseudocode]
关系型/行存:
  事务、约束、JOIN、点查/更新

KV:
  key → value, 简单低延迟访问

列式/分析:
  批量扫描、压缩、聚合

文档:
  半结构化对象、灵活 schema

图:
  节点/边/路径遍历

时序:
  按时间追加、窗口聚合、降采样

搜索:
  倒排索引、分词、相关性
```

Why: 为什么“通用数据库”经常在某个专用场景不如专用系统？——**数据模型、索引、写入路径、压缩、查询并行和一致性语义都是围绕 workload 优化的**；选择专用系统也会引入运维、同步、团队技能和数据重复成本。 [MySQL: HTAP/LSM/全文/CDC 等扩展专题展示了同一数据在不同访问模型下的结构变化]

### 5. 五维选型 — 把技术选择落到组织现实

场景提示: 两个数据库 benchmark 接近，为什么团队最终可能选择性能稍低但更容易运维的那个？ [写作时展开]

关键设计: 选型至少同时评估五维：

```[pseudocode]
业务场景:
  事务/分析/搜索/时序/图/缓存/实时性

数据规模与增长:
  容量、吞吐、热点、扩缩容、保留周期

开发能力:
  SQL/SDK/生态/迁移/调试/招聘

运维能力:
  备份恢复、监控、升级、故障切换、SLA

组织与管理:
  合规、供应商、成本、云/本地、责任边界

决策:
  先写不可妥协约束
  → 设计候选 workload
  → benchmark + 故障演练
  → 评估总拥有成本与退出路径
```

Why: 为什么“性能最高”不等于“最适合生产”？——**真实系统还要支付备份、迁移、监控、人才、故障恢复和供应商锁定成本**；选型报告必须记录假设、基准场景、失败模式、数据迁移路径和回滚方案。 [系统性能: benchmark 必须使用代表性 workload；高可用专题要求把故障演练纳入验收]

### 6. 收束

从理论到选型：

```[pseudocode]
故障模型/一致性需求
  → CAP/事务/复制语义
  → 垂直/水平拆分边界
  → 客户端/中间件路由与跨片查询
  → 数据模型分类
  → 业务/规模/团队/运维/组织五维评估
  → workload benchmark + 故障演练 + 迁移退出方案
```

**Aha Moment**: "数据库选型不是找一个永远最快的产品，而是**在一致性、可用性、数据模型、扩展、团队与运维成本之间做可验证的决策**；理论负责指出约束，实验和组织能力决定最终答案。"
**回答读者三问**: ①CAP 是什么=分区发生时一致性与可用性的取舍框架；②分库分表代价=跨片查询、事务、迁移和热点；③如何选数据库=五维约束加代表性 benchmark、故障演练和退出路径。
