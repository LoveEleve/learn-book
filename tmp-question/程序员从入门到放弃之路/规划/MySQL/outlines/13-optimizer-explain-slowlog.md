### 1. 优化器 — 规则重写只是第一步，代价模型才决定最终计划

场景提示: 写了索引后，为什么优化器仍然可能不用它？ [写作时展开]

关键设计: 优化器通常先做语义保持的重写，再在候选访问路径中比较代价：

```[pseudocode]
输入 SQL
  → 语法/语义解析
  → 规则重写
      常量折叠/条件化简/部分外连接消除/范围改写
  → 生成候选访问路径
      表访问方法/索引/连接顺序/连接算法
  → 结合统计与成本模型估算
  → 选择当前最优计划
```

Why: 为什么有索引不等于成本更低？——**优化器比较的是预计总成本，不是“是否走索引”这一个开关**：低选择性索引、回表成本、排序、临时表、覆盖与并发 I/O 都会影响结论。规则重写能缩小问题空间，最终计划仍由代价模型和统计信息主导。 [MySQL: engine_cost/server_cost、optimizer_switch、hint 和版本优化器行为需按目标版本核对]

比喻锚点: 优化器像导航软件：先把无效路线删掉，再估算时间、拥堵和收费，最后选“当前看起来最便宜”的路，而不是只看地图上有没有近路。 [写作时展开]

### 2. 访问方法与联接算法 — 同样是查表，路径可能完全不同

场景提示: EXPLAIN 里的 `const/ref/range/index/all` 和 `Nested Loop/Hash Join` 到底意味着什么？ [写作时展开]

关键设计: 单表访问方法和多表联接算法是两层决策：

```[pseudocode]
单表访问方法(示意):
  const   → 常量主键/唯一值快速定位
  ref     → 通过索引等值匹配若干行
  range   → 索引范围扫描
  index   → 顺序扫描索引
  all     → 全表扫描

多表联接:
  Nested Loop / Block Nested Loop / Hash Join 等
  → 外表驱动内表
  → 可配合索引、缓冲区、物化结果或哈希表
```

Why: 为什么 `type=ref` 不一定比 `all` 更快，Hash Join 也不一定总优于 Nested Loop？——**访问方法和联接算法只有在给定数据分布、返回行数、索引、内存预算和排序需求下才有意义**；Hash Join 会增加内存与构建成本，Nested Loop 在高选择性索引下可能更好。EXPLAIN 字段是症状描述，不是性能结论排名。 [MySQL: 访问方法、Hash Join 可用性与版本/开关相关]

比喻锚点: 访问方法像进仓库拿货的路线，联接算法像两张订单如何对账；最短走路路线不一定是最低总时间。 [写作时展开]

### 3. EXPLAIN 与 EXPLAIN ANALYZE — 估算和事实是两张表

场景提示: EXPLAIN 说只扫描 100 行，真实却跑了几秒钟、扫了几十万行，哪一层出了问题？ [写作时展开]

关键设计: EXPLAIN 给出优化器视角的计划与估算，ANALYZE 给出执行期的实际统计：

```[pseudocode]
EXPLAIN:
  id/select_type/type/possible_keys/key/rows/filtered/Extra
  → “优化器以为会发生什么”

EXPLAIN FORMAT=JSON/TREE:
  → 更完整的计划树/代价/附加信息

EXPLAIN ANALYZE:
  → “实际发生了什么”
  → 行数、循环次数、耗时等运行期观测
```

Why: 为什么只看 EXPLAIN 不够？——**因为它受统计信息和成本模型驱动，估算错时计划会看起来合理、跑起来很糟**；ANALYZE 能揭露某个节点的真实行数和耗时，但也会执行语句本身（按语句类型/环境谨慎使用）。计划树好看不代表线上在相同参数、并发和缓存状态下也快。 [MySQL: EXPLAIN ANALYZE 支持范围与输出格式随版本演进]

比喻锚点: EXPLAIN 像导航预估时间，ANALYZE 像实际行驶记录；两者偏差大时，说明地图或拥堵模型失真。 [写作时展开]

### 4. 慢查询日志 — 从线上症状切进优化器问题

场景提示: 线上用户只说“接口慢”，如何在海量 SQL 中先抓出最值得分析的那一批？ [写作时展开]

关键设计: 慢查询日志把“超过阈值”的 SQL 收集为入口样本，再交给聚合工具归一化：

```[pseudocode]
慢日志配置:
  long_query_time
  min_examined_row_limit
  log_output(FILE/TABLE)

日志内容:
  query time / lock time / rows examined / rows sent / SQL 文本

工具:
  mysqldumpslow / pt-query-digest
  → 归一化模板
  → 统计 TOP N、分位、样例
```

Why: 为什么慢日志不是“调低 long_query_time 就万事大吉”？——**阈值过低会放大量短但频繁语句，阈值过高会漏掉关键尾延迟；rows_examined 高也不一定等于磁盘 I/O 高**。慢日志是问题入口，不是根因结论，还要继续结合计划、事务等待和系统指标。 [MySQL: 慢日志输出字段、采样和 TABLE/FILE 模式的成本需要按部署环境评估]

比喻锚点: 慢日志像急诊分诊单，先把“超时病人”集中起来；真正病因还要靠影像、化验和病史。 [写作时展开]

### 5. 从 digest 到计划验证 — 日志、sys schema 与系统观测要闭环

场景提示: pt-query-digest 找到一条 TOP SQL，下一步是直接加索引，还是先看等待与资源？ [写作时展开]

关键设计: 慢 SQL 的分析闭环应跨越 SQL 模板、执行计划和系统资源：

```[pseudocode]
慢日志 / digest
  → 找出高频/高总耗时/高尾延迟 SQL 模板
  → EXPLAIN/ANALYZE 看访问路径和行数偏差
  → 结合锁等待、I/O、Buffer Pool、CPU
  → 判断是估算错、索引缺失、数据倾斜还是事务阻塞

辅助:
  sys schema / Performance Schema 摘要
  → statement digest / lock waits / file I/O
```

Why: 为什么“定位到 SQL”仍然不能证明问题就在 SQL 文本本身？——**同一模板可能因参数、统计、并发事务和系统状态产生完全不同成本**；有时慢的是锁等待、复制追赶、磁盘抖动或缓存冷启动，而不是优化器算法。优化动作必须和 workload、尾延迟、资源观测一起复测。 [系统性能: MySQL 优化与 Linux CPU/I/O/锁观测要在同一时间窗口对齐]

### 6. 收束

SQL 优化诊断闭环：

```[pseudocode]
慢日志/告警
  → digest 聚合/找模板
  → EXPLAIN 看优化器估算
  → EXPLAIN ANALYZE 看实际执行
  → 对照统计信息/索引/数据分布
  → 再对齐锁/I/O/CPU/缓存证据
  → 调整索引/SQL/统计/参数并回归验证
```

**Aha Moment**: "优化器不是数据库里的神谕，它只是基于统计和成本模型的预测器；**慢查询日志给你症状，EXPLAIN 给你假设，ANALYZE 给你事实，系统观测告诉你副作用**。"
**回答读者三问**: ①有索引为什么不用=成本估算认为不划算；②EXPLAIN 和 ANALYZE 差在哪=前者估算，后者执行时事实；③慢日志怎么用=抓入口样本，再做计划和资源闭环验证。
