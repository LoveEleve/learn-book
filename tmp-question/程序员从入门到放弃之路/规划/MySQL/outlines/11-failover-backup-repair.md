### 1. Planned Switchover — 在受控窗口内平稳切主

场景提示: 需要升级主库或迁移机房时，如何在尽量不丢事务的前提下把业务切到另一台实例？ [写作时展开]

关键设计: 计划切换的核心是先让候选副本追平、再冻结旧主写入、最后切换流量：

```[pseudocode]
准备:
  检查复制健康/GTID/Relay/applier 状态
  → 选择候选副本

追平:
  确认候选副本赶上主库事务集合

冻结旧主写入:
  read_only/super_read_only 或业务层写门禁
  → 确保不再产生新事务

切换:
  提升候选为新主
  → 修改应用/代理/Router 指向
  → 验证读写
```

Why: 为什么“追平后立刻切流”仍然不够？——**还要确认应用写入已被正确拦截、连接池是否有旧主长连接、外部任务是否继续写旧主、只读标志是否真正生效**；planned switchover 追求的是可控边界，不是只比秒级速度。 [MySQL: GTID 集合、只读开关和业务写入口要同时验证]

比喻锚点: 平稳切主像电力检修切换：先确认备用线路承载正常，再停旧线路供电，最后让全楼改接新线路。 [写作时展开]

### 2. Emergency Failover — 先隔离旧主，再选“最接近真相”的副本

场景提示: 主库宕机或网络分区时，如何快速恢复服务又避免脑裂？ [写作时展开]

关键设计: 紧急故障转移优先判断旧主是否仍可能写入，再选择事务集合最完整且语义合适的副本：

```[pseudocode]
事故:
  主库失联/不可写/网络分区

第一步:
  尽可能隔离旧主
  → 防止旧主恢复后继续写(脑裂)

第二步:
  评估候选副本
    GTID executed/Relay/applier/只读状态/过滤或延迟属性
  → 选择“最接近完整真相”的副本

第三步:
  晋升并切流
  → 其他副本重新指向新主
  → 记录可能缺失事务和补偿策略
```

Why: 为什么“延迟最小的副本”不总是最佳主库候选？——**它可能是过滤副本、延迟副本、未完全回放副本，或在故障窗口失去部分事务**；failover 首要目标是正确性和防脑裂，其次才是恢复时间。自动化工具只能执行策略，不能替代事务集合判断。 [MySQL: GTID、Relay、半同步边界和主从拓扑共同决定候选资格]

比喻锚点: 紧急切主像灾后迁移总配电柜：先切断疑似带电的旧线路，再选最完整、最安全的新线路供电。 [写作时展开]

### 3. 复制中断与数据不一致修复 — 先分辨“断了”还是“错了”

场景提示: 复制线程停止、GTID 不匹配、主键冲突或 binlog 缺失时，怎样判断是配置错误、单条事务异常还是全局数据漂移？ [写作时展开]

关键设计: 故障分成链路中断、位点/GTID 问题和数据内容不一致三类：

```[pseudocode]
链路/配置:
  server_id 冲突
  包大小/网络/认证/权限问题

复制逻辑:
  binlog 缺失
  GTID 集合不匹配
  主键冲突/DDL 不兼容/依赖对象不存在

数据一致性:
  pt-table-checksum 校验差异
  → pt-table-sync 或重建副本/补数据

原则:
  先确认事务集合和拓扑状态
  再决定 skip、补数据、重拉或重建
```

Why: 为什么“跳过一条报错事务”常常是危险捷径？——**复制错误可能是更大数据漂移的症状**：盲目 skip 让副本继续前进，但一致性裂缝被永久保留。checksum/sync 工具也只是修复手段，前提是明确差异范围和业务可接受性。 [MySQL: GTID/位点修复、checksum 和跳过事务的具体流程依赖版本和拓扑]

比喻锚点: 复制修复像校账：线路断了先恢复通讯，金额不对要先查明哪几笔账缺失，而不是随手跳过一页。 [写作时展开]

### 4. 备份与时间点恢复 — 逻辑导出、物理热备与 binlog 回放

场景提示: 误删数据后，应该用 mysqldump、XtraBackup，还是直接回放 binlog？ [写作时展开]

关键设计: 备份关注的是“保存哪一层状态”，恢复关注的是“恢复到哪个时间点”：

```[pseudocode]
逻辑备份(mysqldump/mydumper 等):
  导出 SQL/表数据
  → 可跨版本/按对象恢复
  → 恢复速度受逻辑导入限制

物理热备(XtraBackup 等):
  拷贝 InnoDB 文件/日志
  → 准备并恢复到可启动状态
  → 通常更适合大库全量恢复

PITR:
  全量备份
  + binlog 按时间/位置/GTID 回放
  → 恢复到误操作前某个时间点
```

Why: 为什么“有全量备份”还不等于“能恢复到误删前 5 分钟”？——**全量只提供某个基线，时间点恢复还要依赖连续 binlog、正确时间边界和经过演练的回放流程**；逻辑/物理备份的恢复粒度、跨版本兼容、空间和恢复时长都不同。 [MySQL: mysqldump、mydumper、XtraBackup、binlog2sql 等能力与版本兼容需实测]

比喻锚点: 全量备份像整座仓库某天的快照，binlog 像之后每天的出入库流水；想回到某个具体时刻，必须两者结合。 [写作时展开]

### 5. 基准测试与恢复后验收 — 数据回来了，不等于服务就恢复了

场景提示: 切主或恢复完成后，为什么还要跑 sysbench、检查 open_files_limit 和连接上限，而不是直接宣布恢复成功？ [写作时展开]

关键设计: 数据一致只是恢复第一层，性能和容量验收是第二层：

```[pseudocode]
恢复后检查:
  只读/写入路由是否正确
  复制/GTID/只读标志是否符合新角色
  慢查询/错误日志/复制状态是否异常

容量与性能:
  sysbench 或代表性 workload
  → QPS/TPS/P95/P99
  → 检查连接数、open_files_limit、ulimit、IO/CPU/锁等待

回归:
  基线对比
  → 性能下降? 新主硬件/参数/索引/缓存热度是否不同
```

Why: 为什么“故障恢复成功”必须包含性能验收？——**新主缓存是冷的、参数可能不同、复制角色变更可能影响读写路径，恢复后的系统可能正确但很慢**；只验证数据不验证吞吐和尾延迟，等于把事故从一致性问题变成可用性问题。 [系统性能: 01-08 篇的方法论、benchmark、观测与 tracing 要在恢复后再次应用]

### 6. 收束

运维闭环：

```[pseudocode]
planned switchover
  或 emergency failover
  → 防脑裂/选副本
  → 检查 GTID/Relay/延迟/角色
  → 必要时 checksum/sync/重建
  → 用全量备份 + binlog 做 PITR
  → 恢复后压测/验收/监控
```

**Aha Moment**: "故障处理不是“把服务先拉起来”就结束，而是**在事务集合正确、角色切换清晰、复制语义明确、性能重新达标**之后，系统才算真正恢复。"
**回答读者三问**: ①planned 与 emergency 差在哪=一个追求平滑边界，一个先控风险与脑裂；②复制报错怎么办=先分链路/位点/数据三类，再决定修复或重建；③备份为什么还要配 binlog=只有这样才能做时间点恢复。
