### 1. ARIES — Analysis、Redo、Undo 如何从崩溃现场重建状态

场景提示: 数据页和日志只写了一半，恢复算法怎样知道哪些操作要重放、哪些事务要回滚？ [写作时展开]

关键设计: ARIES 用 WAL、LSN、模糊检查点和三阶段恢复建立可重复的恢复路径：

```[pseudocode]
Analysis:
  从 checkpoint 开始扫描日志
  → 重建 transaction table / dirty page table
  → 判断哪些事务在崩溃时仍未完成

Redo:
  从最早需要的 LSN 开始
  → 按日志重做历史修改
  → 重做必须可重复/幂等地恢复页状态

Undo:
  对 loser transactions 反向遍历日志
  → 撤销未提交修改
  → 写 compensation log record(CLR)
  → 直到事务完成回滚
```

Why: 为什么 ARIES 要“先 Redo、后 Undo”，而不是先把未提交事务找出来删除？——**Redo 先把磁盘恢复到崩溃前的日志状态，Undo 才能在完整状态上按日志链反向撤销 loser transaction**；模糊检查点不阻塞所有事务，LSN 把页、日志和恢复边界连接起来。ARIES 与 InnoDB 的具体字段/日志格式不同，不能把理论伪代码当成 MySQL 源码流程。 [数据库理论: WAL/LSN/CLR 是 ARIES 的核心概念；MySQL/InnoDB 有自己的实现映射]

比喻锚点: 灾后先按施工日志恢复现场，再撤销未验收工程；撤销动作本身也要记进新的施工记录，避免再次断电后无从继续。 [写作时展开]

### 2. OCC — 冲突少时，把锁等待换成提交验证

场景提示: 读多写少、冲突低的事务为什么可能不想一开始就持有大量锁？ [写作时展开]

关键设计: 乐观并发控制把事务分成读、验证、写三个阶段：

```[pseudocode]
Read phase:
  读取数据/计算结果
  → 记录 read set / write set
  → 不长期持有写锁

Validation phase:
  检查与已提交/并发事务的集合是否冲突
  → 向后/向前/并行验证策略
  → 冲突? abort/retry

Write phase:
  验证成功
  → 应用写集合
  → 提交
```

Why: 为什么 OCC 不是“无锁且一定更快”？——**冲突事务会在验证阶段回滚并重试，重复计算可能比等待锁更贵**；高冲突热点、长事务和大 write set 会让 OCC 退化。OCC 的价值在于把锁等待换成冲突检测，适合冲突概率和重试成本可控的 workload。 [并发控制: OCC 正确性依赖验证规则；应用还要处理重试、幂等和副作用]

比喻锚点: 多人先各自填表，最后交给柜台核对；没有冲突就一起提交，冲突了其中一些人要重填。 [写作时展开]

### 3. 时间戳排序 — 用全序决定冲突先后

场景提示: 两个事务访问同一数据但没有锁，系统怎样判断哪一个读写顺序合法？ [写作时展开]

关键设计: Timestamp Ordering 为事务建立时间顺序，并用数据项读/写时间戳检查操作是否违反顺序：

```[pseudocode]
事务 T 带 timestamp TS(T)
数据项 X 维护 read_TS(X) / write_TS(X)

T 读 X:
  若 TS(T) < write_TS(X)
    → 读违反时间顺序, abort/restart
  否则更新 read_TS(X)

T 写 X:
  若 TS(T) < read_TS(X)
    → 写违反顺序, abort
  若 TS(T) < write_TS(X)
    → 可拒绝、回滚或按 Thomas Write Rule 忽略过时写
  否则更新 write_TS(X)
```

Why: 为什么 Thomas Write Rule 可以忽略某些过时写？——**如果该写已经被一个更晚时间戳的写覆盖，旧写可能不再影响最终等价序列**；但它只适用于满足特定时间戳协议条件的过时写，不能泛化成“旧写都能丢”。时间戳排序减少锁等待，代价是冲突回滚和重启。 [数据库理论: Thomas Write Rule 是时间戳排序的特定优化，不等同于一般 last-write-wins]

### 4. SSI — 快照读如何检测危险结构

场景提示: 快照隔离能减少读写阻塞，却为什么仍可能出现两个事务各自读到旧快照、最后共同破坏业务约束？ [写作时展开]

关键设计: Serializable Snapshot Isolation 在快照读之上跟踪读写依赖，检测可能导致非串行化的危险结构：

```[pseudocode]
事务读快照
  → 记录 rw-conflict

事务写入/提交
  → 维护事务依赖图

检测:
  出现可能形成环的危险结构?
  → abort/延迟提交其中一个事务
  → 保证可串行化目标
```

Why: 为什么 SSI 不等于“所有读都加锁”？——**它通过依赖关系检测换取更少的读阻塞，但需要保存冲突信息，并可能在提交时回滚事务**；有向序列化图/危险结构的定义是理论核心，工程实现会做优化和近似。SSI 与普通 Repeatable Read/MVCC 也不是同一个隔离级别名。 [并发控制: snapshot isolation、serializable 和 SSI 的实现/保证边界必须区分]

比喻锚点: SSI 允许多人先读旧版文件，但记录“谁读了谁将修改的内容”；如果关系图显示可能互相矛盾，就让一方重做，而不是一开始封锁所有读者。 [写作时展开]

### 5. Shadow Paging、MARS 与 WBL — WAL 之外的恢复路线

场景提示: 如果不采用传统 Undo/WAL，数据库还能怎样保证崩溃后有一个完整版本？ [写作时展开]

关键设计: 不同恢复路线把成本放在不同位置：

```[pseudocode]
Shadow paging:
  写新页/新页表
  → 提交时原子切换根指针
  → 旧页保留为旧版本/回收候选

MARS/WBL 等研究路线:
  → 通过多核/落后写日志/版本结构重新组织恢复
  → 目标仍是降低同步或写放大

对比:
  WAL/ARIES: 原地页 + 日志 + replay/undo
  Shadow/COW: 新页/新根 + 指针切换
```

Why: 为什么替代路线没有统一取代 WAL？——**它们改变了写放大、空间回收、并发、恢复和元数据复杂度的分布**；根指针切换适合某些页组织，WAL 适合顺序日志和原地页更新。学术方案的名称和实现不能直接当作 MySQL/InnoDB 生产能力。 [数据库理论: 恢复算法比较应同时看写放大、空间放大、并发和故障模型]

### 6. 收束

理论对照：

```[pseudocode]
崩溃恢复:
  ARIES = Analysis → Redo → Undo

并发控制:
  OCC = 读 → 验证 → 写
  T/O = 时间戳全序 + 冲突检查
  SSI = 快照读 + 依赖图危险结构检测

替代恢复:
  Shadow/COW = 新版本写好 → 原子切根
```

**Aha Moment**: "数据库理论始终在回答两件事：**崩溃后怎样恢复一个可解释状态，并发事务怎样避免形成不可串行化结果**；日志、版本、时间戳、冲突图和根指针只是不同答案的工程化表达。"
**回答读者三问**: ①ARIES 为什么三阶段=先重建现场，再重做日志，最后撤销未提交；②OCC 为什么会重试=冲突在验证阶段才暴露；③SSI 为什么还要图=快照读不阻塞，但读写依赖可能形成危险结构。
