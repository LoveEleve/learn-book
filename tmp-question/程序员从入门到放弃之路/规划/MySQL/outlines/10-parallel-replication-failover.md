### 1. 并行复制模式 — 按库、按组提交、按写集合冲突

场景提示: 同样是主库 1000 TPS，为什么有的副本能并行追上，有的副本只能单线程慢慢放？ [写作时展开]

关键设计: 并行回放的核心是证明事务彼此不冲突：

```[pseudocode]
DATABASE:
  按数据库/Schema 分桶
  → 不同库事务可并行
  → 同库内仍偏串行

LOGICAL_CLOCK:
  利用主库组提交/commit 顺序信息
  → 同一批次内满足条件的事务可并行

WRITESET:
  根据事务写集合(键/行冲突摘要)判断依赖
  → 冲突小于 DATABASE 粒度时可获得更高并行度
  → 无法提取有效写集合时可能退化
```

Why: 为什么“并行复制”不等于“任意两个事务都能并行回放”？——**副本必须在不破坏提交依赖和可见性顺序的前提下并行**：跨库也可能因外键、全局资源或提交顺序约束而影响；WRITESET 还依赖主键/唯一键和冲突提取策略。并行度来自证明独立性，不是盲目开更多线程。 [MySQL: `slave_parallel_type`/`replica_parallel_type`、WRITESET 提取和依赖元数据按版本文档核对]

比喻锚点: 并行回放像仓库拆单：不同楼层的订单、同一批同时付款的订单、彼此不抢同一货架的订单，可以交给不同工人；真正抢同一货架的仍得排队。 [写作时展开]

### 2. MTS — Coordinator 分发、Worker 回放与提交顺序

场景提示: 并行复制打开后，哪些线程在做协调，哪些线程在执行事务？ [写作时展开]

关键设计: Multi-Threaded Slave/Replica 通常由协调线程和多个工作线程组成，并维护检查点和提交顺序：

```[pseudocode]
Coordinator:
  读取 Relay Log / 事务边界
  → 判断依赖/分配到 worker

Workers:
  并行回放可独立事务
  → 执行 SQL/row events
  → 上报完成进度

Checkpoint/low watermark:
  记录哪些事务已安全完成
  → 崩溃恢复/重启后决定从哪里继续

提交顺序:
  可按配置要求保持主库提交顺序
  → 约束部分并行收益
```

Why: 为什么 worker 数量增加后，吞吐有时不升反降？——**Coordinator 分发、提交顺序、依赖图不均匀、事务大小差异和锁竞争会让部分 worker 空闲、部分 worker 堵塞**；并行复制不是 CPU 核数越多越好。`slave_preserve_commit_order`/对应新变量名能改善可见顺序，却可能降低并行度。 [MySQL: MTS 线程、检查点与提交顺序实现按版本核对，8.0 名称和行为与旧版本不同]

比喻锚点: MTS 像总调度员给多个工位发工单，工位数量变多并不保证整体更快；如果所有工单都依赖同一前置步骤，其他工位仍会空转。 [写作时展开]

### 3. Seconds_Behind_Master 与 Relay 基础设施 — 延迟不止一个数字

场景提示: `Seconds_Behind_Master = 0` 时，副本真的和主库完全一致了吗？ [写作时展开]

关键设计: 延迟至少有四段：主库生成、网络传输、Relay 落盘、applier 执行；SBM 只是一个近似投影：

```[pseudocode]
主库 binlog timestamp
  → 网络传输
  → IO thread 写 Relay Log
  → applier/worker 执行
  → 副本提交可见

SBM:
  利用主从时间戳/当前执行点估算
  → 可能在空闲时归零
  → 大事务执行中可能突然跳大再归零

Relay 基础设施:
  relay log files
  master/relay info state
  relay_log_recovery 等恢复策略
```

Why: 为什么 SBM 不能作为流量切换的唯一依据？——**它依赖时钟、执行点和观察窗口，不能直接证明 GTID 集合完全一致、事务全部可见或没有长事务正在回放**；应结合 GTID executed、Relay 累积、worker 状态、apply lag 和业务一致性检查。 [MySQL: SHOW REPLICA STATUS 字段与旧 SHOW SLAVE STATUS 语义/命名差异需注意]

比喻锚点: SBM 像航班预计晚点分钟数；归零不代表行李、乘客和清洁都同步完成，只表示当前估算看起来已经追平。 [写作时展开]

### 4. 多源、过滤与延迟复制 — 复制拓扑的运维扩展

场景提示: 一个副本同时从多个来源拉数据，或者故意延迟 1 小时应用事务，它和普通主从的风险点有什么不同？ [写作时展开]

关键设计: 多源、过滤和延迟复制改变了复制“看见哪些事务、何时应用”的边界：

```[pseudocode]
多源复制:
  channel A / channel B / ...
  → 各自维护来源和进度
  → 共享实例资源, 需防冲突与观测混淆

复制过滤:
  do_db/ignore_db/do_table 等
  → 副本只应用部分事务/对象
  → 影响一致性判断与故障切换可用性

延迟复制:
  人为推迟应用一段时间
  → 形成误删/误操作恢复窗口
  → 同时引入更大的正常读延迟和切换复杂度
```

Why: 为什么复制过滤和延迟复制很危险？——**它们改变了“副本是否代表主库”的含义**：过滤副本不一定可直接晋升，延迟副本对实时业务不可替代。多源复制还会放大冲突、资源争用和排障复杂度。 [MySQL: channel、过滤项与 failover 可用性需要明确标注，不能把所有副本等价看待]

比喻锚点: 普通副本像主仓镜像，多源副本像几个仓库汇总报表，延迟副本像保险箱里的历史快照；用途不同，不能互相替代。 [写作时展开]

### 5. Failover 与复制恢复 — 选对副本比“最快切”更重要

场景提示: 主库故障后，哪台副本可以安全晋升？只看 SBM 最小那台够吗？ [写作时展开]

关键设计: 故障切换要先确认事务集合、提交边界和角色，再处理新的复制拓扑：

```[pseudocode]
故障发生
  → 冻结/隔离原主(避免双主写)
  → 检查候选副本:
      GTID executed 集合
      Relay/worker 状态
      半同步/提交边界
      只读/过滤/延迟属性
  → 选择最完整且语义合适的副本晋升
  → 其他副本重新指向新主
  → 校验缺失事务/补偿/业务一致性
```

Why: 为什么“复制延迟最小”不等于“最适合晋升”？——**副本可能是过滤副本、延迟副本、回放中的副本，或拥有不同的事务集合**；故障切换核心是事务正确性和防脑裂，其次才是切换速度。GTID 让集合对比更容易，但仍要处理 purged、并行回放和故障窗口中的边界情况。 [MySQL: 高可用组件(MHA/Orchestrator/MGR 等)只是自动化，不替代事务边界判断]

### 6. 收束

复制扩展闭环：

```[pseudocode]
主库提交
  → binlog/GTID
  → Dump/IO/Relay
  → Coordinator/Worker 并行回放
  → GTID executed/Relay state 推进
  → SBM 等近似指标观测
  → 多源/过滤/延迟改变语义
  → failover 以事务集合和边界为准
```

**Aha Moment**: "复制延迟和并行复制的本质，不是“多开几个线程”，而是**在不破坏提交依赖与事务集合的前提下，最大化独立事务并行度，并在故障时准确判断谁最接近完整真相**。"
**回答读者三问**: ①并行复制为什么有限=事务依赖和提交顺序约束并行度；②SBM 为什么不可靠=只是一种时间戳近似；③故障切换怎么选副本=看 GTID/Relay/角色语义，不只看延迟。
