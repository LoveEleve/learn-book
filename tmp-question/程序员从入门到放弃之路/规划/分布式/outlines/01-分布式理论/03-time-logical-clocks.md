# 用户在北京下单, 服务器显示纽约时间 — 机器时间不同步怎么办?

> Cluster A: 12 KPs | 依赖: 02-故障模型(已知时钟不可信) | 读者基线: 了解Unix timestamp

---

### 1. 物理时钟的困境 — NTP为什么不靠谱
  你记录了"用户下单时间: 2026-08-09 15:00:00", 但不同服务器的15:00:00可能差了300ms — 时间戳排序全乱了。
  - B1 Ch6 §1: 物理时钟 — 石英振荡器(主板RTC, 漂移~1秒/天) + 原子钟(GPS/铯原子, 漂移~1秒/300万年)
  - NTP网络时间协议: 客户端向NTP服务器发4个时间戳(t1发送→t2服务器收到→t3服务器回复→t4客户端收到) → 计算偏移offset=((t2-t1)+(t3-t4))/2 — 但不对称延迟导致误差(上行ping≠下行ping)
  - 关键设计: NTP精度极限 — 广域网~10ms, 局域网~1ms — 现代数据中心用PTP(精确时间协议)可达微秒级
  - 时间倒退陷阱: NTP可能把时钟往后调(offset>128ms→slew而非step, 但大偏移会jump) — 数据库事务时间戳/分布式锁的超时计算不能依赖单调性

### 2. Lamport逻辑时钟 — 不靠物理时钟也能排序
  Lamport说"不在乎绝对时间, 只在乎事件间的因果关系" — 怎么做到?
  - B1 Ch6 §2: happens-before(→)关系 — 同进程内a先于b→a→b; 消息发送在接收之前→send(m)→recv(m); 传递性→a→b且b→c则a→c
  - Lamport时钟算法: 每个进程维护C; 本地事件时C=C+1; 发消息时附上C; 收消息时C=max(C_local, C_msg)+1 — 保证a→b ⇒ C(a) < C(b)
  - 关键设计: Lamport时钟的"偏序到全序": C(a)=C(b)时(并发)用进程ID打破平局→全序<C, PID> — 但这是任意序非因果序
  - Lamport时钟不能检测并发: C(a)<C(b)不能推出a→b(可能并发) — 这是Lamport时钟的根本局限

### 3. 向量时钟 — 检测真正并发
  两个用户同时编辑一段文字, 谁先谁后? Lamport时钟回答不了的问题, 向量时钟能回答。
  - B1 Ch6 §3: 向量时钟 — 每个节点维护VC=[c1,c2,...,cN]; 本地事件→VC[i]++; 发消息附VC; 收消息→逐位max
  - 比较规则: VC1≤VC2(逐位且存在<)=VC1 happens-before VC2; VC1与VC2互不能比较=并发
  - 关键设计: Dynamo/Riak用向量时钟检测版本冲突 — 读取返回兄弟版本(siblings), 客户端合并或LWW(Latest Write Wins)解决
  - 瓶颈: N节点→O(N)大小向量 — 大型集群不实用 → Dynamo用版本向量(只存活跃节点) + 定期修剪

### 4. 分布式快照 — 怎么给一个运行中的分布式系统拍照?
  你要知道"某一时刻"所有账户的余额总和 — 但交易还在进行中, 账户间的钱正在飞。
  - B1 Ch6 §4: Chandy-Lamport快照算法 — 发起者记录自身状态→向所有出channel发marker→收到marker: 如果是第一次收到则记录状态并转发marker, 否则停止记录该channel→收齐所有marker后快照完成
  - 关键设计: Marker是"快照边界" — 发出marker前的消息属于拍摄前, 收到marker后但还没记录状态时的消息要单独计入channel状态
  - 工程应用: Kafka的偏移量/死信队列位置/Flink checkpoint底层都用分布式快照 — Chandy-Lamport是基准

### 5. TrueTime — Google怎么让全球数据中心的时间"一致"
  你部署了三个数据中心的Spanner, 跨洲延迟100ms+ — 怎么实现"外部一致"(比线性一致还强)?
  - B1 Ch6 §5: TrueTime = GPS(卫星原子钟)+原子钟(地面备份)+ε(不确定性窗口)
  - 关键设计: TrueTime保证TT.now()返回[earliest, latest]即绝对时间落在这个区间 — 用wait(2ε)确保时间戳单调
  - Spanner的外部一致: 事务提交时用TrueTime时间戳 — 等2ε后保证T1.commit_ts < T2.start → T1的修改对T2可见 — 实现"读己之写"在全球范围
  - HLC混合逻辑时钟: 物理时钟+逻辑计数器 — 不需要硬件(GPS/原子钟), 适合普通数据中心(B1 Ch6 §6)

### 6. 收束 — 回到时间戳排序的困境
  - 物理时钟不可靠(NTP有误差/可跳回) → Lamport逻辑时钟给出因果序(偏序) → 向量时钟检测并发 → TrueTime给全球范围内的"绝对序"
  - 分布式快照是Chandy-Lamport经典算法, Checkpoint/Flink/Kafka都受此影响
  - 不是所有场景需要TrueTime(GPS+原子钟很贵) — HLC是务实选择
