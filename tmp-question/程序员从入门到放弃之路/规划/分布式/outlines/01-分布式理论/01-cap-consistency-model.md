### 1. CAP — 网络分区发生时，系统必须暴露取舍

场景提示: 库存节点和订单节点之间网络断开，系统应该继续接单，还是拒绝请求等待一致状态？ [写作时展开]

关键设计: CAP 讨论的是在分区容忍前提下，一致性与可用性的选择：

```[pseudocode]
网络正常:
  系统可能同时提供较强一致与较高可用

发生 Partition:
  C: 继续保证定义好的单一最新视图
      → 可能拒绝/阻塞部分操作
  A: 非故障请求继续得到响应
      → 可能返回旧值/冲突值

CP/AP:
  不是产品永久标签
  而是特定故障期间、特定操作语义的取舍
```

Why: 为什么 CAP 不是“C/A/P 三选二”的产品排行榜？——**P 是故障模型中的网络分区，讨论重点是分区发生时 C 与 A 的冲突**；系统平时也可能在延迟、成本、读新鲜度和一致性之间取舍。CAP 中的 C 还要明确是线性一致等哪一种语义。 [分布式理论: CAP 的反证直觉是分区时一侧无法同时观察另一侧最新写入]

比喻锚点: 两座城市断桥时，要么停止售票等待两边账本一致，要么继续售票并接受稍后对账；断桥状态下两者不能同时无条件保证。 [写作时展开]

### 2. PACELC 与 BASE — 正常网络下也有延迟/一致性取舍

场景提示: 网络没有分区，为什么系统仍会在“更快返回”和“等待副本确认”之间做选择？ [写作时展开]

关键设计: PACELC 把 CAP 的分区情况扩展到正常运行时的延迟与一致性，BASE 则描述许多最终一致系统的工程取舍：

```[pseudocode]
P:
  Partition 时 → Availability vs Consistency

Else:
  正常无分区时 → Latency vs Consistency

BASE:
  Basically Available
  Soft State
  Eventually Consistent
  → 允许中间状态, 通过异步复制/修复最终收敛
```

Why: 为什么“最终一致”不等于“随便读，最后总会好”？——**必须定义收敛条件、冲突解决、读己之写、单调读、修复和不可用窗口**；最终一致描述时间性质，不自动提供业务正确性。支付/库存这类操作通常需要更强的幂等、顺序和确认语义，而商品浏览可能接受短暂旧读。 [分布式工程: 一致性选择必须落到操作级语义，而不是整个系统贴一个 AP/CP 标签]

比喻锚点: BASE 像多地库存账本允许短暂不同，但必须有补账、冲突处理和最终对平流程；“以后会一致”不是没有流程。 [写作时展开]

### 3. 一致性模型 — “读到什么”不是 0/1 问题

场景提示: 客户刚付款，刷新页面却看不到订单；这是 bug，还是读路径的一致性承诺？ [写作时展开]

关键设计: 一致性模型从全局顺序到客户端体验形成不同强度：

```[pseudocode]
Linearizability:
  每个操作看起来在某个真实时间点原子发生
  → 读不能返回已被覆盖的旧值(满足实时顺序)

Sequential consistency:
  存在一个全局操作序列符合各线程自身顺序
  → 不一定满足真实时间顺序

Causal consistency:
  有因果关系的操作保持顺序
  → 无因果操作可并行/不同序

Eventual consistency:
  没有新写入后, 副本最终收敛

客户端中心:
  read-your-writes / monotonic reads / monotonic writes
  → 从用户视角补强体验
```

Why: 为什么线性一致不是“所有副本永远同时相同”？——**它是操作级可观察语义，通常需要协调/共识/路由机制；实现还要说明读写路径、故障时是否拒绝和线性化点在哪里**。Paxos/Raft 可以用于构建强一致复制状态机，但不是所有使用它们的系统都自动让任意业务查询线性化。 [分布式理论: 一致性模型描述可观察结果，协议只是实现手段]

比喻锚点: 线性一致像银行柜台有一条严格时间线，因果一致像聊天消息按回复关系排序，最终一致像各分店账本稍后对齐。 [写作时展开]

### 4. 分片、复制与读写分离 — 扩展之后旧读和冲突从哪里来

场景提示: 主库刚写入库存，读请求被路由到延迟副本，为什么又显示旧库存？多主同时改同一商品怎么办？ [写作时展开]

关键设计: 数据扩展常同时使用分片与复制，但每层都增加一致性边界：

```[pseudocode]
分片:
  Range/Hash/一致性哈希等
  → 降低单机容量/流量
  → 跨片查询/事务/聚合变复杂

复制:
  同步/半同步/异步
  → 读可扩展/容灾
  → 延迟副本可能旧读

读己之写:
  关键读回主
  或等待副本追上位点/GTID
  或携带 session consistency token

多主冲突:
  LWW/版本向量/CRDT/应用合并
  → 选择取决于业务是否允许丢失/合并
```

Why: 为什么读写分离不是简单“写主、读从”？——**路由还要考虑事务上下文、读己之写、延迟、故障切换和连接池缓存**；多主冲突也不能用 LWW 无条件解决，时间戳相同/时钟偏差/业务字段合并都可能造成数据损失。 [MySQL: 09-12 篇复制/GTID/故障切换说明了副本进度与切换边界]

### 5. 分布式隔离与并发控制 — `@Transactional` 为什么跨不了服务

场景提示: 订单服务和库存服务各自有本地事务，Spring 的 `@Transactional` 能否自动把两次数据库提交绑成一个原子动作？ [写作时展开]

关键设计: 本地事务边界不会自动穿过网络；跨服务需要显式协调或业务补偿：

```[pseudocode]
单机:
  BEGIN → 多条 SQL → COMMIT/ROLLBACK
  → 同一资源管理器可统一控制

跨服务:
  Service A 本地提交
  → RPC Service B
  → B 可能超时/重试/已提交但响应丢失
  → 需要幂等、状态机、Outbox/Saga/2PC 等方案

并发控制:
  悲观全局锁 → 协调器瓶颈
  乐观版本/CAS → 冲突重试
  MVCC/时间戳 → 读版本与提交顺序
```

Why: 为什么分布式事务不是给本地注解加一层就结束？——**网络超时让“调用失败”和“远端未提交”无法直接等价，多个资源管理器也有独立日志和故障状态**；2PC 提供协议协调但增加阻塞/可用性成本，Saga/Outbox 则把原子性改成步骤补偿与最终一致。 [MySQL: 本地 ACID/Undo/Redo 与分布式协调器的边界必须分开]

比喻锚点: 本地事务像一个柜台一次盖完所有章，分布式事务像多个城市分别盖章；快递可能丢回执，所以要有编号、幂等和补偿流程。 [写作时展开]

### 6. 收束

分布式理论落地链：

```[pseudocode]
故障模型
  → CAP/PACELC 选择一致性/可用性/延迟
  → 一致性模型定义读写承诺
  → 分片/复制决定数据放置与副本进度
  → 分布式事务/并发控制决定跨服务修改
  → 业务幂等/补偿/监控把理论落地
```

**Aha Moment**: "分布式架构没有一个脱离场景的“最强一致”答案；**先定义故障、读写语义和业务可接受的不确定性，再选择复制、分片、事务和补偿方案**。"
**回答读者三问**: ①CAP 怎么用=先声明分区故障下的操作承诺；②读写分离为何旧读=副本延迟与路由语义；③跨服务事务为什么难=网络超时让本地提交无法自动构成全局原子性。
