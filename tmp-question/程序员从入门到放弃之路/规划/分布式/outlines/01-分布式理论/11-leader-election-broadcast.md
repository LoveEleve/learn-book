# Leader挂了20秒才检测到 — 怎么更快知道? 怎么选出新Leader?

> Cluster D: 13 KPs | 依赖: B(已知共识协议) | 读者基线: 理解选举和共识的基本概念

---

### 1. 失败检测 — "到底谁挂了?"
  心跳超时3秒就把节点标记为dead — 但万一是网络抖动呢? 误判导致无谓的Leader切换。
  - B3 Ch5 §1: 完美失败检测(P) — 强完备(最终每个故障被检测) + 强精确(不误判) — 只能在同步系统中实现
  - B3 Ch5 §2-4: 部分同步下的失败检测 — ◊P(最终完美, 最终不误判) → Ω失败检测(输出一个正确的Leader, 但不保证所有节点同意谁被怀疑)
  - 关键设计: heartbeat+超时是失败的近似 — 超时阈值: 太小→误判多(网络抖动触发选举), 太大→检测慢(Leader真挂等太久) — 自适应超时(如φ-accrual: 用概率模型动态调整阈值)
  - B3 Ch5 §5: 噪声失败检测 — 现实系统中心跳可能丢包 — 基于"怀疑级别": N次连续丢心跳→增加怀疑度→超过阈值才标记故障

### 2. 选主 — 三种算法, 一个目标
  谁当Leader? 三个候选者怎么选出一个?
  - B3 Ch5 §6: 霸凌算法(Bully) — 节点ID最大者当选 → 发现自己比当前Leader ID大→发起选举→给所有更高ID节点发消息→无响应则自封Leader
  - 轮转算法(Round-Robin): 硬件FIFO队列→队首为Leader→故障后出队→自动切换到队下首 — 简单但需要FIFO硬件
  - 最终选主: 基于Ω失败检测→所有正确节点最终认同同一个Leader — Raft/ZAB/Paxos都内建了Leader Selection
  - 关键设计: Leader租约(Lease) — 当选后获得为期T的租约→Follower承诺T时间内不接受其他Leader → Leader在T到期前续约 → 解决"老Leader没死但被隔离后又回来"的Brain Split

### 3. 可靠广播 — 从"尽力"到"全序"
  广播一个消息, 怎么保证所有节点都收到, 且按相同顺序?
  - B3 Ch6 §1-2: 广播层级 — 尽力广播(可能丢)→正则可靠广播(所有正确节点传递或都不传递)→统一可靠广播(故障节点也保证一致)
  - B3 Ch6 §5: Gossip/概率广播 — 每轮随机选k个邻居传播 → O(log N)轮覆盖所有节点 — HashiCorp Serf(成员管理)/Consul/Redis Cluster都用Gossip
  - B3 Ch6 §6-7: FIFO可靠广播(同一源有序) + 因果可靠广播(happens-before有序)
  - B3 Ch9 §1: 全序广播(Total Order Broadcast) = 所有节点收到完全相同顺序的消息 → 等价于共识(全序广播↔共识可互相实现) — 全序广播→确定所有节点apply相同命令序列

### 4. 复制状态机 — 广播+状态的统一
  前面讲了博客, 这里把它们串起来: 全序广播 + 确定性状态机 = 副本一致的分布式系统。
  - B3 Ch9 §2: 复制状态机 = 全序广播(输入顺序一致) + 确定性状态机(相同输入→相同输出) = 所有副本状态一致
  - 关键设计: 确定性是前提 — apply()必须是确定函数(相同输入必须相同输出) → 不能依赖随机数/实时/本地文件 → 随机数种子必须通过日志传递
  - Raft/Paxos本质: 用共识实现全序广播 → 用全序广播驱动复制状态机 → 副本一致 → 这就是分布式共识的工程目标

### 5. 收束 — 基础设施三件套
  - 失败检测 + 选主 = 自动故障转移的基础 — 自适应超时+Lease防脑裂
  - 可靠广播(Gossip/全序广播) = 信息在集群中的传播机制 — Gossip for成员, 全序for状态
  - 复制状态机 = 全序广播 + 确定性apply → 所有副本一致 = 共识的终局
