### 1. Saga — 长事务拆成短事务，但中间态会暴露

场景提示: 旅游订单里先订机票、再订酒店、再支付；支付失败时，怎样把前面的成功动作撤回？ [写作时展开]

关键设计: Saga 为每个本地事务配一个补偿动作，失败后按约定方向重试或回滚：

```[pseudocode]
T1: 订机票   ↔ C1: 取消机票
T2: 订酒店   ↔ C2: 取消酒店
T3: 扣库存   ↔ C3: 恢复库存
T4: 支付     ↔ C4: 退款/关闭支付单

执行:
  T1 → T2 → T3 → T4
  任一步失败:
    前向恢复(重试当前/后续)
    或向后恢复(按 Cn...C1 补偿)
```

Why: 为什么 Saga 的难点不在“写几条补偿 SQL”，而在中间态和并发可见性？——**子事务已经分别提交，其他请求可能读到“机票已订、支付未完成”的中间状态**；这要求业务显式设计状态机、语义锁、可重试补偿和人工兜底。补偿也不总是数学逆操作，例如外部支付退款、优惠券回滚都可能有副作用。 [分布式事务: Saga 解决的是长流程最终一致，不提供全局瞬时原子视图]

比喻锚点: Saga 像旅行社分步下单，每一步都单独确认，失败时靠一张逆序撤销清单把前面订单逐个取消。 [写作时展开]

### 2. 本地消息表 — 同库同事务，把“发消息资格”先写进数据库

场景提示: 下单成功后要异步通知库存/营销，但应用在订单提交与发 MQ 之间宕机了，如何避免“订单有了、消息没了”？ [写作时展开]

关键设计: 把业务数据与待发送消息放进同一个本地事务：

```[pseudocode]
本地事务:
  INSERT order(...)
  INSERT outbox_message(msg_id, payload, status=INIT)
COMMIT

后台投递器:
  扫描 status=INIT
  → 发送 MQ/HTTP
  → 成功: 标记 SENT
  → 失败: retry_count++ / 下次重试 / 告警

消费者:
  按 msg_id 做幂等去重
```

Why: 为什么本地消息表“简单”却很常用？——**它把原子性问题缩回单库事务：订单写成功时，消息资格一定存在**；代价是需要额外轮询/投递器、状态表清理、幂等表和重试策略。它解决“消息是否应该发”，不保证消费者业务自动成功。 [分布式事务: Outbox 模式的核心是同库同事务，不是“发消息更快”]

比喻锚点: 本地消息表像订单系统给快递室留下一张待发货单；只要订单入账成功，这张单就一定存在，哪怕快递员稍后再来取。 [写作时展开]

### 3. 事务消息 — 让 MQ 参与“是否可见”的决策

场景提示: 本地消息表要自己写轮询器、清理器和重试器；MQ 能不能把这部分责任包进去？ [写作时展开]

关键设计: 事务消息把消息先写成对消费者不可见的半消息，再等待生产者报告本地事务结果：

```[pseudocode]
Producer:
  发送 half message(消费者不可见)
  → 执行本地事务
  → COMMIT message 或 ROLLBACK message

Broker:
  若生产者迟迟未决
  → 发起事务回查
  → 询问生产者本地事务状态
  → 决定提交或回滚消息
```

Why: 为什么事务消息不是“万能 outbox 替代品”？——**它把一部分可靠投递逻辑内建到 MQ，但也把系统绑定到特定消息中间件语义和回查协议**；本地事务状态查询、幂等消费、顺序要求和异常恢复仍需业务参与。half message 只保证“消息在 broker 的可见性决策”，不直接解决下游处理成功。 [MQ: 事务消息语义、回查次数和可见性窗口依赖具体产品实现]

比喻锚点: 事务消息像快递站先收下一件“暂存包裹”，只有商家确认订单成功后才放上配送带；确认超时则由快递站回拨商家问状态。 [写作时展开]

### 4. 最大努力通知 — 接收方也要参与对账

场景提示: 银行回调商户支付结果时，商户系统偶尔不可达；这种场景为什么常用“通知 + 查询接口”而不是严格消息事务？ [写作时展开]

关键设计: 最大努力通知假设发送方会重复通知，但不能保证一定送达；接收方需要支持幂等处理和主动查询校对：

```[pseudocode]
发送方:
  发送通知
  → 失败/超时则重试 N 次
  → 保留状态与告警

接收方:
  幂等处理通知
  → 若没收到/不确定
     主动 queryOrder/queryStatus
     与发送方对账

双通道:
  push 通知
  + pull 查询校对
```

Why: 为什么最大努力通知不适合“必须一次提交完成”的核心事务？——**它接受短期不一致，把补偿压力转移到重试和查询通道**；适合外部合作方、回调、账单通知等“最终知道结果即可”的场景，不适合要求严格同步原子提交的内部扣款链路。 [分布式事务: “通知成功”与“业务已处理成功”仍需幂等和状态查询桥接]

比喻锚点: 最大努力通知像快递员多次敲门并留电话，收件人不确定时再主动打电话确认；它尽力而为，但不承诺第一次一定交付。 [写作时展开]

### 5. 收束

最终一致路线对照：

```[pseudocode]
Saga:
  本地事务 + 补偿动作
  → 暴露中间态, 需要业务状态机

本地消息表:
  单库事务 + 后台投递
  → 最朴素稳健, 需要自建投递器/清理器

事务消息:
  MQ half message + 回查
  → 降低自建轮询成本, 增加中间件耦合

最大努力通知:
  push + query
  → 适合外部回调/对账场景
```

**Aha Moment**: "最终一致方案的关键不是‘异步’两个字，而是**如何把失败显式变成状态，并给出重试、补偿、幂等和对账路径**；越少阻塞数据库，越多复杂度会转移到业务和运维。"
**回答读者三问**: ①Saga 为什么复杂=中间态暴露且补偿不是简单逆操作；②本地消息表保证什么=业务记录与待发消息同库同事务；③最大努力通知为什么要查询接口=通知可能丢失，必须靠双通道对账。
