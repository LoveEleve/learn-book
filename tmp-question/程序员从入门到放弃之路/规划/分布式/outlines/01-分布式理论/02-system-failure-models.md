### 1. 故障模型 — “没响应”不是一种故障

场景提示: 服务心跳超时，节点到底崩了、丢了消息、变得很慢，还是在恶意撒谎？ [写作时展开]

关键设计: 不同故障模型决定协议需要的防御深度：

```[pseudocode]
crash-stop:
  进程停止后不再发送/执行
  停止前行为符合协议

crash-recovery:
  停止后可能恢复
  → 需要持久化状态/恢复协议

omission:
  丢失发送或接收事件

performance/timing:
  进程或消息没有故障, 但慢到违反系统假设

Byzantine:
  任意错误/恶意行为
  → 需要更强认证/冗余/共识假设
```

Why: 为什么数据中心协议常以 crash-stop/crash-recovery 为基础，而不是直接按 Byzantine 设计？——**BFT 需要更高冗余、认证和消息开销，且故障假设必须与威胁模型匹配**；同一管理员控制的内部节点通常不需要防御任意恶意节点，但安全边界外的系统不能盲信 crash 模型。`3f+1` 是特定 BFT 模型和条件下的容错下限，不是所有共识/复制系统的通用公式。 [分布式理论: 故障模型是协议正确性证明的前提，不是部署后再补的配置]

比喻锚点: 心跳像给远方朋友打电话：没接通可能是手机坏了、信号断了、人在隧道里，也可能只是忙到无法接听；你只能根据模型和证据做判断。 [写作时展开]

### 2. 网络模型 — TCP 可靠不等于业务请求一定完成

场景提示: RPC 超时后重试，第一次扣款可能已经成功但响应丢了，怎样避免重复扣款？ [写作时展开]

关键设计: 网络模型从“不丢不重有序”到“任意丢失/延迟”，工程系统必须把请求完成与响应到达分开：

```[pseudocode]
发送请求
  → 网络延迟/丢包/重复/乱序
  → 服务端可能已执行
  → 响应可能丢失
  → 客户端超时并重试

幂等策略:
  request_id/idempotency_key
  → 服务端持久化处理结果
  → 重试命中同一 ID 时返回原结果/拒绝重复执行

TCP:
  提供连接内可靠有序字节流
  不保证对端进程仍活着
  不保证业务操作只执行一次
```

Why: 为什么“RPC 超时”不能等于“服务端没执行”？——**超时只说明客户端在规定时间内没获得足够证据**；请求可能在服务器执行、网络回程丢失或服务端正在提交。重试必须配合幂等键、状态查询或业务去重，不能把 TCP 的可靠传输当作业务 exactly-once。 [网络: 01-04 篇的 TCP/重试/粘包与 MySQL 复制说明了传输层可靠和业务层完成语义的区别]

比喻锚点: 快递查询超时不代表包裹没送到；再次下单前要用订单号查询状态，而不是盲目再寄一件。 [写作时展开]

### 3. 时间模型 — 同步、异步与部分同步

场景提示: 分布式锁 lease 是 30 秒，但 JVM Full GC 暂停 40 秒；恢复后旧持有者和新持有者会发生什么？ [写作时展开]

关键设计: 时间模型决定协议能否用“超时”推断对方状态：

```[pseudocode]
同步模型:
  消息延迟/处理时间/时钟偏差有已知上界

异步模型:
  不假设固定上界
  → 慢与故障不可区分

部分同步模型:
  最终进入一个有界/相对稳定时期
  → 之前可能任意慢
  → 现实协议常以此获得 eventual liveness

lease 风险:
  进程暂停/GC/调度延迟 > lease
  → 旧持有者恢复后仍可能继续写
  → 需要 fencing token/版本检查/合理续租
```

Why: 为什么“给超时加大 buffer”不是租约安全的完整方案？——**你无法只凭历史 GC 最大值证明未来暂停不会更长**；更稳妥的设计需要 fencing token、服务端版本校验和恢复后重新认证。部分同步不是假设“网络永远正常”，而是假设系统最终出现足够好的时期。 [分布式理论: 超时是故障检测线索，不是事实证明]

比喻锚点: 租约像停车票：过期后旧司机回来不能只凭“我记得车位是我的”继续开走，必须检查新的票号/围栏标记。 [写作时展开]

### 4. FLP 与两将军 — 共识的“不可能”到底限制什么

场景提示: 01 篇说 Paxos/Raft 可以达成共识，本篇却说异步系统共识不可能，矛盾在哪里？ [写作时展开]

关键设计: FLP 针对异步系统、确定性算法和至少一个 crash failure，说明不能同时保证所有执行都终止并达成共识：

```[pseudocode]
异步系统:
  没有消息最大延迟上界
  没有处理时间上界

FLP 结论(直觉):
  某些配置下, 对手可以持续延迟关键消息
  → 让系统无法区分“节点慢”与“节点坏”
  → 保持不确定/阻塞
  → 无法保证所有执行最终决定

工程协议:
  timeout/randomized election/leader
  + 部分同步或概率假设
  → 追求高概率终止, 不声称消灭理论条件
```

Why: 为什么 Raft/Paxos 并没有“打败 FLP”？——**工程协议通过超时、随机化、领导者和部分同步假设获得实践中的活性，但仍可能在网络长期异常时阻塞**；FLP 说的是无条件、所有执行的确定性终止不可能，不是说正常网络下共识系统完全不能工作。两将军问题则说明不可靠信道上双方无法获得无限确定的共同确认。 [分布式理论: 安全性/活性与故障假设必须分别陈述]

比喻锚点: FLP 像一个可以无限延迟信件的对手；工程协议不是证明对手不存在，而是利用超时和选主，在现实中把对手的窗口压到可接受范围。 [写作时展开]

### 5. 工程防御 — 把故障假设写进系统设计

场景提示: 已知网络、时钟和进程都可能异常，生产系统应该怎样降低错误重试和错误切换？ [写作时展开]

关键设计: 防御策略应覆盖检测、隔离、幂等和恢复：

```[pseudocode]
检测:
  heartbeat/timeout/health probe
  → 只能生成怀疑, 不能直接证明故障

隔离:
  quorum/fencing/leader lease
  → 防止旧节点继续写

幂等:
  request ID / dedup table / compare-and-set
  → 重试不重复执行

恢复:
  WAL/checkpoint/snapshot/replay
  → 节点恢复后重新加入并追平

观测:
  区分网络慢、进程暂停、CPU/GC、真实 crash
  → 不用一个 timeout 覆盖所有情况
```

### 6. 收束

故障模型闭环：

```[pseudocode]
允许的故障
  → 选择网络/时间模型
  → 定义一致性与活性保证
  → 设计 timeout/quorum/fencing/idempotency
  → 故障后恢复/重试/重新加入
```

**Aha Moment**: "分布式协议的第一行不是算法，而是故障假设；**如果你没有声明节点、网络和时间如何失败，‘一致性’和‘可用性’的承诺就没有可验证边界**。"
**回答读者三问**: ①心跳超时能证明节点宕机吗=不能，只能产生怀疑；②TCP 可靠能保证扣款一次吗=不能，业务需要幂等；③FLP 与 Paxos 矛盾吗=不矛盾，工程协议依赖超时/部分同步/随机化获得实践活性。
