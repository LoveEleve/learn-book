# 缓存穿透穿过了Redis, 击穿打穿了Redis, 雪崩埋了Redis — 三个问题, 三套解法

> Cluster C: 2 KPs | 依赖: 域4-03(Bloom Filter), 域3-05(缓存优化), 域2-04(分布式缓存架构) | 读者基线: 面试背过三概念, 线上一出问题分不清是哪个, 不知怎么验证

### 1. 缓存穿透 — 攻击者用不存在的key反复查询, Redis条条miss
  用户查到每个ID都不在缓存, 200万请求条条打穿Redis到DB — 就这么简单, 就这么致命。
  - 布隆过滤器(预防): 在缓存层之前加一层 — BF判断key不在→直接返回空→不查Redis, 更不查DB — 域4-03已讲布隆原理, 此处是工程应用 (B1 Ch5 §5.5)
  - 缓存空值(兜底): 第一次查DB返回null→把null也缓存(TTL短, 30-60秒)→检查到空值返回null — 缺陷: 内存会充满null key(需控制 + 不同IP不同null) [工程: 空值TTL = 攻击者尝试的速度 — 如果用户5秒能尝试100个不存在的key, TTL=60秒还不够 — 需要辅以IP限流]
  - IP限流第二道防线: 即使穿透了布隆, 同一IP每秒查100次不存在的key → 直接封IP或限制(令牌桶) — 布隆是过滤, 限流是防御, 双保险 (B1 Ch5 §5.5)
  - 关键设计: 穿透的根因是"不存在=不在缓存" — Redis不能存"不存在" — 只有布隆过滤器能以极小空间(误判率)表示"一定不存在" — 布隆是数学, 不是缓存

### 2. 缓存击穿 — 热点key过期瞬间, 10万个请求一起打向DB
  明星新微博, Redis TTL=5分钟 — 过期瞬间22万个请求全到DB — DB只有200个连接。
  - 互斥锁(SET NX): SET lock:hotkey:refresh NX PX 5000 → 拿到锁的做DB查询+回种 → 未拿到return旧缓存或sleep retry → 保证只有1个请求查DB (B1 Ch5 §5.5) [工程: 双重检查: 在获取锁成功后再次检查缓存 — 因为等锁的时候别的线程可能已回种]
  - 逻辑过期: 缓存不设物理TTL→value里多存一个expire_time字段 → 客户端读缓存检查是否过期 → 若逻辑过期→异步拉DB+更新value+更新expire_time → 旧缓存还在, 请求不阻塞 (B1 Ch5 §5.5)
  - SingleFlight(合并请求): 同key的并发请求合并成一个→只有第一个请求做真实查询→其他等结果 — 适合极高并发下, 省掉DB查询数 (B1 Ch5 §5.5) [工程: 参考Go singleflight/Java Striped64思想]
  - 关键设计: 击穿和穿透的区别 — 穿透(数据不在DB), 击穿(数据在DB但在缓存过期) — 穿透需过滤, 击穿需排队

### 3. 缓存雪崩 — 多个热点key同时过期, 或者Redis集群同时宕了
  你设的缓存过期时间都是整点(每小时) — 恰好在14:00所有热点key同时过期。
  - 随机TTL: expire = base + random(0, 300) — 离散化过期时间 — 30个key的过期从同秒变成散在5分钟内 (B1 Ch5 §5.5)
  - 多级缓存降级: Redis挂整个层→降级读本地Caffeine缓存 — 本地缓存数据可能旧, 但服务不停 (B1 Ch5 §5.5) [案例: S08的大促线上 — Redis集群网络故障→本地缓存扛了15分钟→Redis恢复后一致性通过对账修复(域3-05的多级协同)]
  - 限流+熔断: Redis不可用→触发限流(控制进入的请求量)+熔断(标记Redis短时间不用)→保护DB不被冲垮 (B1 Ch5 §5.5)
  - 关键设计: 雪崩的根因是"同时" → 解决方案是"离散" — 随机TTL离散时间, 多级离散空间(不同层不同老化速度)

### 4. 缓存一致性 — 你修改了数据库, 缓存还是昨天数据
  用户下单后查库存——查出来还是旧的10个。这是更新策略的问题。
  - Cache-Aside(旁路缓存): 写(更新DB→删缓存)→读(查缓存→miss查DB→回写缓存→返回) — 最被验证的模式 (B1 Ch5 §5.6)
  - 顺序之争: 先删缓存后写DB(读线程可能在删和写之间读旧值回种→覆盖DB新值) vs 先写DB后删缓存(写完后删缓存——极端场景延迟极低) — 后者更好但仍有并发风险 (B1 Ch5 §5.6) [工程: 先写后删→延迟双删(写完等1-2秒再删一次) + 失效消息(Canal监听到Binlog变更→MQ→删缓存) — 两个手段叠加]
  - CDC方案: Canal解析MySQL Binlog→提取变更行→MQ发给缓存更新服务→删/更新Redis — 异步最终一致性 — 比"写完DB手动删缓存"更可靠(不受应用代码bug影响) (B1 Ch5 §5.6)
  - 关键设计: 没有"100%一致的缓存" — CAP说一致和可用是矛盾 — 你的选择: 读主库保证强一致(成本高), 还是用缓存+最终一致(成本低) — 选哪个根据业务

### 5. 收束 — 三个问题, 三套解法, 一个真理
  - 穿透: 布隆(不存在→不查), 击穿: 锁(独家查→不重复), 雪崩: 离散(不同时过期→不集中) — 都是"许多人一起做同一件事"的不同表现形态
  - 一致性: 最终一致(CDC异步通知)是大多数业务的答案 — 强一致(直接读DB)只有金融交易等少数场景需要 — 选错了方案的代价可能是生产事故
