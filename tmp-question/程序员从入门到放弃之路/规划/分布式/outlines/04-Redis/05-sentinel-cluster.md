# 主节点挂了, 3个哨兵在"争吵"谁当新领导 — 他们怎么选出新主的?

> Cluster B: 3 KPs | 依赖: 域4-04(持久化+主从复制), 域1-01(CAP一致性←Raft) | 读者基线: 部署过哨兵或集群, 看过CLUSTER NODES, 遇到MOVED错误

---

### 1. 哨兵 — 三个节点监视一个Redis, 谁来决定它死了?
  你设了3个哨兵监控主节点 — 第三个哨兵网络断了, 它声明"主挂了!"但其他两个没挂 — 到底以谁为准?
  - 主观下线(SDOWN): 一个哨兵PING主超时→标记SDOWN — 这是主观判断(自己网络可能有问题) — 不能说给其他哨兵 (B1 Ch3 §3.3)
  - 客观下线(ODOWN): 哨兵向其他哨兵发送SENTINEL is-master-down-by-addr→收到≥quorum个确认→判定ODOWN — 多数派确认, 消除单哨兵网络分区误判 (B1 Ch3 §3.3) [理论: quorum投票 = 分布式一致性共识的轻量版本 — 不是Raft的完整共识, 只是达成"它死了"这个事实的多数确认]
  - 关键设计: SDOWN→ODOWN之间的quorum参数 — quorum太小(1)会误判, 太大(等于哨兵数)可能永远无法确认 — 哨兵数的多数(如5个设quorum=3)最合理

### 2. 哨兵Leader选举 — 从3个哨兵里选出一个指挥官
  判定ODOWN后不能三个哨兵都去做故障转移 — 必须选出Leader。
  - Raft简化: 哨兵给其他哨兵发选票→收到多数确认+epoch(纪元)最大→成为Leader — 拉票时先到先得, 没选出的重来+epoch递增 (B1 Ch3 §3.3)
  - 故障转移: Leader选择最优从(优先级/复制偏移量/replication ID)→SLAVEOF NO ONE→更新其他从→通知客户端(PUB/SUB +sentinel channel) (B1 Ch3 §3.3) [工程: 最优从判断: replication ID相同(同一主)→offset最大(数据最新)→priority最小 — 三个条件AND链接]
  - 关键设计: 哨兵不是Redis的一部分 — 哨兵是独立的进程(redis-sentinel) — Redis不知道自己被监控 — 这样的解耦让哨兵可以同时监控多个Redis实例

### 3. Redis集群 — 16384个槽, 一致性哈希的精致替代
  你加到第4个节点时, 数据需要迁移 — 一致性哈希算出的迁移量太大, Redis集群怎么让每次迁移只动1/n的数据?
  - 槽位分片: 16384个hash slots — CRC16(key)%16384→slot→节点 — 每个节点负责一部分槽 — 扩容: 新节点从每个旧节点分几个槽(不是重新分配) — 迁移量=1/n而不是全量 [理论: 16384槽 vs 一致性哈希 — 槽是预分片, 扩容只转移少量槽(不是rehash), 数据量确定, 负载可以规划]
  - 为什么是16384: 节点数×槽是心跳包大小权衡 — 心跳包包含槽位图(bitmap)→65536槽=8KB/心跳×几千节点→带宽爆炸 — 16364是2KB/心跳, 合适 (B1 Ch3 §3.4)
  - gossip协议: 节点通过cluster bus(PORT+10000)交换信息 — Meet(新节点加入)→Ping(心跳+携带1/10的节点信息)→Pong(回复)→Fail(标记某节点下线需要过半主节点确认) (B1 Ch3 §3.4)
  - MOVED vs ASK: MOVED(槽永久归属新节点)→客户端更新槽路由表 — ASK(槽迁移中, 临时指向新节点)→客户端只对当前命令去新节点, 路由表不变 (B1 Ch3 §3.4) [案例: 扩容时12001槽从旧节点迁到新节点→迁移中查slot 12001→旧节点reply ASK→客户端ASKING+命令→新节点处理→迁移完12001在新节点→超时后MOVED]
  - 关键设计: ASK不是重定向 — ASK是"这次迁移的特殊情况去新节点", MOVED是"以后这个槽永远在新节点" — 混淆两个会导致客户端缓存错误路由

### 4. 集群的代价 — 不是所有Redis都适合Cluster模式
  - 多key操作必须同一槽: 用{hashtag}强制所有key进同一槽 — `SET {user:1}:name "zhang"` 和 `SET {user:1}:age 25` 都在同一槽 (B1 Ch3 §3.4)
  - 事务限制: MULTI/EXEC只能在单节点执行 — Lua脚本也不能跨槽操作(multi-key script) — 这不是Redis不会, 是分布式事务的代价 (B1 Ch3 §3.4)
  - cluster-require-full-coverage: 一个槽不可用→整个集群不可用? — yes保证一致性, no牺牲一致性换可用 — 又是CAP的体现
  - 客户端复杂度: 集群客户端必须维护槽映射表→处理MOVED/ASK→重试逻辑→连接池为每个节点一个 — 不是简单的`redis-cli -h host`了 (B1 Ch3 §3.4)
  - 关键设计: 集群模式是为"水平扩展+自动分片"设计的 — 如果只有1-2个节点+手动分片, 哨兵+主从更适合、客户端更简单

### 5. 收束 — 哨兵+集群 = 两层的"不死设计"
  - 哨兵: 解决"谁来升新主" — 少数哨兵+选举+故障转移, 适合几台机器的中等部署
  - 集群: 解决"数据放哪"+"集群大了怎么管理" — 槽分片+gossip+重定向, 适合几十台机器的大规模部署
  - 两者组合: 集群的每个分片可以用哨兵+主从做高可用 — 集群是外层分片, 哨兵是内层故障转移 — 两层不死
  - 域1的Raft一致性在这个场景简化成了哨兵选举 — 不需要强一致日志复制, 只需要"选一个指挥官"和"通知大家"
