### 1. CAP 在工程里不是系统标签，而是操作级 SLA

场景提示: 库存扣减、商品列表、订单状态和配置中心，为什么不能统一选“强一致”或“高可用”？ [写作时展开]

关键设计: 同一系统可以为不同数据定义不同一致性承诺：

```[pseudocode]
库存扣减:
  不允许超卖/重复扣减
  → 强一致/串行化/幂等优先

商品列表:
  短暂旧读可接受
  → 可用性/缓存命中优先

配置中心:
  变更顺序/单一视图重要
  → CP 协调服务

订单状态:
  需要状态机/幂等/最终收敛
  → 按操作分别定义读写语义

PACELC:
  分区时看 C/A
  正常时看 Latency/Consistency
```

Why: 为什么一个架构同时出现 CP 和 AP 不是矛盾？——**CAP 约束的是具体系统/操作在分区故障下的保证，架构可以把不同不变量放在不同子系统**；真正要记录的是每个数据的最新性、可用性、丢失/重复容忍和补偿策略。 [分布式理论: §01 的 CAP/PACELC 从抽象定理落到数据级 SLA]

比喻锚点: 城市交通不是所有道路都追求同样规则：消防通道优先可靠，商业街优先可达，临时停车区允许最终清理；关键是标明每条路的约束。 [写作时展开]

### 2. ZooKeeper/etcd — 强一致协调服务不是缓存

场景提示: 注册中心、配置中心和选主为什么常用 ZK/etcd，而不是 Redis 或普通 DNS？ [写作时展开]

关键设计: ZK/etcd 用共识/会话/租约/Watch 提供协调状态，但它们的操作语义和部署模型不同：

```[pseudocode]
注册:
  instance → key/ephemeral/lease
  → session/lease 失效后可清理

配置:
  write → 有序提交
  → watch/读取当前版本

选主/锁:
  lease/临时节点 + fencing/版本
  → 不能只依赖客户端本地超时

etcd/ZK:
  都可提供 CP 类协调语义
  → 具体线性读、watch、租约和成员管理以版本为准
```

Why: 为什么 Redis 的高可用缓存不能自动替代 ZK/etcd 的协调语义？——**协调需要顺序、版本、租约、成员和故障边界，缓存的复制/故障切换语义可能允许旧读或双持有**；强一致协调服务也不适合存大数据和高吞吐业务缓存。 [分布式理论: 协调服务自身仍受 quorum/分区/租约边界约束]

### 3. 分布式锁 — SET NX、ZK 顺序节点与 fencing token

场景提示: Redis `SET lock NX EX 30` 的客户端暂停 40 秒后恢复，为什么可能和新持有者同时写资源？ [写作时展开]

关键设计: 锁的安全等级不只取决于“是否互斥”，还取决于旧持有者能否继续影响下游：

```[pseudocode]
Redis lease:
  SET key NX EX
  → 简单/低延迟
  → 主从切换、暂停、过期与脑裂边界需评估

ZK/etcd:
  版本/临时节点/租约
  → 顺序竞争与 watch
  → 仍需正确处理会话和重连

fencing:
  每次获取锁得到递增 token
  → 下游资源验证 token
  → 旧持有者即使恢复也不能覆盖新写
```

Why: 为什么 Redlock/多节点锁争议不能用“成功多数节点”一句话结束？——**关键是锁过期、GC 暂停、网络分区、时钟和下游是否验证 fencing**；如果下游只看客户端“自称持锁”，租约过期后的旧写仍可能造成破坏。金融/关键资源应把 fencing 或版本校验放到真正资源端。 [分布式理论: 02 时间模型的 lease 风险在锁场景中具体化]

比喻锚点: 锁像仓库钥匙，租期结束后旧钥匙必须被门禁拒绝；仅仅发一把新钥匙、却不检查钥匙版本，旧管理员仍可能回来开门。 [写作时展开]

### 4. Paxos/Raft 在架构中的角色 — 共识是底座，不是业务语义

场景提示: etcd、TiKV、Kafka、ZooKeeper 都可能使用共识/多数派，但它们对业务暴露的语义为什么不同？ [写作时展开]

关键设计: Paxos/Raft 等共识通常提供复制日志/状态机底座，上层再定义配置、元数据、消息或数据服务语义：

```[pseudocode]
共识层:
  quorum + term/ballot + ordered log
  → 复制一致状态

上层:
  etcd → key/value/lease/watch
  ZooKeeper → znode/session/watch
  Kafka → partition log/offset/ISR
  TiKV → region/raft/transaction

注意:
  共识日志一致
  ≠ 业务查询永远最新
  ≠ 跨系统事务自动原子
```

Why: 为什么不能说“用了 Raft 就实现了强一致数据库”？——**共识只保证它复制的状态机输入/提交语义，上层读路径、缓存、异步索引、事务和故障路由仍决定用户看到什么**；Kafka ISR 也有自己的 ack、min.insync 和消费者语义。 [分布式理论: 共识、复制状态机、业务可见性三层必须分开]

### 5. 分层一致性与 Quorum — 架构是多个模型的叠加

场景提示: 配置用 CP、数据库副本有延迟、Kafka 分区有序、Redis 最终一致，系统如何写出整体一致性承诺？ [写作时展开]

关键设计: 把每一层的保证显式写出来，再声明跨层边界：

```[pseudocode]
配置层:
  强顺序/版本/租约

数据库层:
  本地事务/复制延迟/读己之写

消息层:
  分区内顺序/至少一次/重复消费

缓存层:
  失效/双写/异步刷新/最终一致

NWR类模型:
  R/W 与副本数的组合影响读写交集
  → 不脱离副本拓扑/故障/读修复定义强一致
```

Why: 为什么不能把 `R+W>N` 直接等同于全局强一致？——**交集只说明某些读写会相遇，真正语义还取决于副本版本、读修复、故障节点、并发写、冲突策略和线性化定义**；架构文档必须标注每层的最新性、重复、丢失、顺序和补偿边界。 [分布式理论: 一致性不是全局开关，而是每个操作/数据路径的合同]

### 6. 收束

架构一致性决策：

```[pseudocode]
业务不变量
  → 数据/操作级一致性 SLA
  → 选择 CP/AP/最终一致/客户端一致
  → 协调服务/数据库/消息/缓存各自承诺
  → 读写路由、重试、幂等、fencing、补偿
  → 故障演练验证用户可见结果
```

**Aha Moment**: "架构中的 CAP 不是“全系统选 CP 还是 AP”，而是**每个数据、每个操作和每个故障窗口都在选择一致性、延迟、可用性与补偿成本**。"
**回答读者三问**: ①为什么系统同时用 ZK/Redis/MySQL/Kafka=不同数据 SLA；②分布式锁最关键什么=旧持有者必须被 fencing；③共识是否等于业务强一致=不等，上层读写/缓存/事务仍决定可见语义。
