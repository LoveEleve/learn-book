### 1. 单体与独立主机 — 架构的第一刀是资源隔离

场景提示: 100 用户的论坛把 Apache、应用和 MySQL 放在一台机器上，增长后为什么先拆数据库/静态资源，而不是立刻微服务化？ [写作时展开]

关键设计: 从单机到独立主机，先解决资源争用和部署耦合：

```[pseudocode]
单体:
  web + app + database + static
  → 简单/低运维
  → 资源和故障共享

独立主机:
  database 独立
  → app server 独立
  → static/cache 独立
  → 按 CPU/内存/I/O/流量分别扩展

读写分离:
  primary write + replicas read
  → 扩展读
  → 引入复制延迟/读己之写
```

Why: 为什么架构演进通常从资源隔离开始？——**资源争用是最直接、最可测的瓶颈，独立主机还能保留单体事务和部署简单性**；过早引入微服务会把一个资源问题升级成网络/运维/一致性问题。 [系统性能: 先用 USE/RED/benchmark 证明瓶颈，再引入新边界]

### 2. 垂直拆分与 SOA — 业务/数据/团队边界开始分离

场景提示: 电商的商品、订单、用户、库存全在一个数据库，为什么继续加机器仍无法解决团队互相阻塞？ [写作时展开]

关键设计: 垂直拆分把业务域、数据所有权、服务部署和团队责任逐步分开：

```[pseudocode]
order/user/product/inventory
  → 业务域/数据库边界
  → 服务 API/RPC
  → 独立部署/扩容/发布

代价:
  跨服务 join/事务
  → RPC/消息
  → 最终一致/补偿
  → 观测与故障治理
```

Why: 为什么接口边界比数据库表边界更重要？——**服务如果仍然共享表、强依赖同批发布，垂直拆分只是物理搬家，不是自治边界**；真正的 SOA/微服务边界要同时拥有数据、规则和发布责任。 [分布式架构: 07 微服务设计的内聚/数据 owner 原则在演进中验证]

### 3. 水平分片与单元化 — 扩容量，也缩小故障半径

场景提示: 单表/单库到达容量和并发边界后，为什么按 user_id 分片又会带来跨片查询和迁移问题？ [写作时展开]

关键设计: 水平分片和单元化把同一业务数据/流量分到多个可独立运行的单元：

```[pseudocode]
水平分片:
  shard_key → DB/table
  → 单片容量/流量降低
  → 跨片查询/全局事务/迁移复杂

单元化:
  user/tenant routing
  → 每单元包含 app/cache/mq/db 等闭环
  → 用户请求尽量在一个单元内完成
  → 故障影响缩小到部分单元

扩容:
  re-sharding/迁移/校验/切流
  → 不是简单加节点
```

Why: 为什么单元化不只是“更多分片”？——**它把请求、数据、缓存、消息和服务实例按同一归属聚合，减少跨单元调用并缩小爆炸半径**；代价是跨单元聚合、全局运营、热点迁移和数据复制更加复杂。单元数量和 shard 数必须由容量/故障/运维模型验证。 [分布式架构: 06 存储分片与 08 韧性/10 编排共同构成单元化基础]

### 4. 多机房与多活 — 从服务不宕到站点故障也能承受

场景提示: 一个机房完全不可用，系统如何把流量切到另一个机房，数据又如何保持可接受的一致性？ [写作时展开]

关键设计: 冷备、热备、同城多活、异地多活分别在 RTO/RPO、成本和一致性上取舍：

```[pseudocode]
冷备:
  备用资源未持续服务
  → 成本低, RTO 长

热备:
  备用已运行/同步
  → 切换更快, 资源闲置

多活:
  多站点同时承载流量
  → 资源利用率高/故障影响小
  → 路由、数据同步、冲突和演练复杂

流量:
  DNS/GSLB/Anycast/网关
  → 健康与容量感知路由
```

Why: 为什么多活不是“两个机房互相同步”这么简单？——**多写会产生冲突、跨地域延迟和故障分区；就近路由也可能把用户固定到不可用/过载区域**。多活必须定义数据归属、冲突策略、切流条件、RPO/RTO 和回切流程。 [分布式理论: CAP/PACELC/时间模型决定多活的一致性与延迟边界]

### 5. 演进方法 — 每增加一层复杂度，都要留下测量和回滚

场景提示: 从单体拆到微服务、从单库分片、从单机房做多活，如何避免“迁移成功但系统更难维护”？ [写作时展开]

关键设计: 架构演进是可观测、可迁移、可回滚的连续实验：

```[pseudocode]
发现:
  指标/日志/trace/容量/故障半径

设计:
  明确瓶颈、SLA、数据 owner、失败模式

迁移:
  双写/影子流量/灰度/校验
  → 分阶段切换

验证:
  workload benchmark + chaos/failover
  → 检查 P99/错误/一致性/成本

回滚:
  保留旧路径/数据补偿/配置开关
  → 发现不符合预期立即退回
```

Why: 为什么架构选择“今天正确”明天可能变成负担？——**容量、组织、业务、流量和故障模式会变化；每个新层都有维护、网络、数据和认知成本**。演进不是追逐最新架构，而是用测量和小步迁移解决当前约束，并为下一个阶段保留选择权。 [系统性能: 架构变更必须回到同 workload 基线和 P99 验收]

### 6. 收束

大型系统演进链：

```[pseudocode]
单体/单机
  → 资源分离/读写分离
  → 垂直业务拆分/SOA
  → 水平分片/微服务
  → 单元化/故障隔离
  → 多机房/多活

每一步:
  解决当前瓶颈
  + 引入新的分布式成本
  + 需要新的观测/迁移/回滚
```

**Aha Moment**: "大型架构不是从零跳到‘终极形态’，而是**每次用一个新边界解决当前瓶颈，再用测量、演练和组织能力偿还新复杂度**。"
**回答读者三问**: ①为什么不一开始就微服务=早期复杂度超过收益；②单元化解决什么=局部闭环与故障半径；③多活最难什么=数据归属、冲突、切流、回切和演练。
