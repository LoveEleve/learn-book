# 一个从0到10亿用户的系统, 架构经历了哪些"大手术"? — 大型网站架构演进全景

> Cluster E: 16 KPs | 依赖: 域2全11篇, 域1-分布式理论 | 读者基线: 已学习域2的全部中间件和架构知识

---

### 1. 单体型时代 — 一切从一台服务器开始
  你的用户=100人, 业务=一个论坛 → 一台服务器(MySQL+Tomcat+Apache全在上面) → 用户到1000→数据库撑不住了
  - B3 Ch4 §2: 架构推演路径 — Stage 1: 单体(All-in-one, 1台VM LAMP架构)→Stage 2: 独立主机(DB独立→App Server独立→静态资源独立) — 这是水平扩展前的基础 (B3 Ch4 §2.2) [案例: Amazon从单体C++应用拆分为微服务, 2002年Bezos的API化命令"所有团队必须通过service接口通信"是微服务史上最重要的架构决策之一]
  - B3 Ch5 §4.1-4.3: 存储分离 + 读写分离 — 数据库独立→主从(主写从读)→备库指数扩展(只能读不可写)→读远大于写时效果显著 (B3 Ch5 §4.2-4.3)
  - 工具进化: 单机MySQL→读写分离中间件(ShardingSphere有读写分离功能)→主库故障秒切(Orchestrator/MHA)
  - 关键设计: 独立主机拆分是架构的第一刀 — 让CPU密集型/IO密集型/内存密集型各司其职, 资源隔离是第一课

### 2. 垂直拆分时代 — 你从1个系统变成5个系统
  用户=10万, 业务=电商(商品+订单+用户+库存+支付) → 但是所有表都在同一DB
  - B3 Ch5 §4.4: 垂直拆分(Schema拆分) — 订单库+商品库+用户库+库存库分别独立, 各自独立→独立团队+独立部署+独立技术选择
  - B1 Ch9 §1: 服务化(SOA) — 订单→订单服务, 提供RPC→拆数据库+独立部署+独立团队, 消除单表热点 (B1 Ch9 §2)
  - 单元化思想萌芽: 用户归属哪个库? 按user_id Range[1-9999→DB0, 10000-19999→DB1] → 用户数据全在同类库→不变形关联 → 单KEY关联
  - 关键设计: 垂直拆分=按业务边界分离 — 订单服务不触碰商品表, 商品服务不触碰用户表 → 接口即边界

### 3. 水平拆分时代 — 单库3000万行, 必须分片
  你从10万用户到100万 → 单库单表抵不住
  - B4 Ch5 §5.3: 分片演进 — Shard 1(旧独立库)→ 按user_id散列→user_id MOD 64=分片号 → 128片→每片独立实例
  - B3 Ch5 §4.5: 水平拆分 — 按时间/范围/散列/一致性Hash → 常见: user_id散列+商品ID散列(商品ID=user_id无关→跨分片查询常见→ES索引辅助)
  - B4 Ch5 §6: 单元化 — 用户维度路由, 用户分片+全局空间→每个分片(单元)=一个微缩电商(DB+Redis+MQ+App全在), 单元内调用同机房无延迟(LAN<1ms) (B4 Ch5 §6) [案例: 阿里电商单元化—将全量用户散列到100+单元，每个单元封闭处理本单元的全部请求，故障隔离从"影响1%用户"降为"影响1/100用户"→每个单元有机房级容错]
  - B3 Ch11 §4: 秒杀系统单元化 — 秒杀单元的独立库存(DN=1000, 每单元分配?100) → 单元封闭→单元快速处理→汇总→归还剩余 (B3 Ch11 §4.3-4.6)
  - 关键设计: 水平拆分=数学工程 — 128分片, user_id MOD 128, 查询必须带user_id, 无法跨分片关联 → 必要的trade-off: 散列均匀但查另一维度爆炸

### 4. 多云/多活时代 — 不只服务不宕, 连机房都不宕
  你从单机房→两地三中心(同城2+异地1)→同城多活(两个机房同时服务, 互为热备)→异地多活(上海+北京+深圳全服务, 就近路由, 100%资源利用率)
  - B4 Ch5 §6.1-6.3: 数据中心扩展 — 容灾级别: 冷备(不运行, 故障时启动→几小时恢复) vs 热备(运行但无流量, 故障时切换→分钟级恢复) vs 多活(全流量, 故障无感→秒级)
  - 多活的关键: 用户路由(就近, DNS/GSLB返回最近DC IP) + 数据同步(主主复制→多写冲突→LWW/CRDT/业务层解决 + 最终一致) + 服务治理(流量自动计算每个DC的百分比)
  - B2 Ch9.4: 监控告警(单DC降级→自动切到可用DC, 告警→人工判定→切流量) — 多活不只是技术, 也需要组织协调/演练 (B2 Ch9 §4)
  - 关键设计: 多活的"活"不是"互相同步" — 是"互不干扰但数据冗余", 一个DC宕机≠其他DC停

### 5. 架构演进启示 — 每个阶段的选择都在前阶段选型中埋下伏笔
  你永远不会从0跳到单元化 — 架构演进=逐步响应+抗压
  - B1 Ch9 §3: DIY分布式集群实践 — 从系统建设→首次架构问题→限流降级→微服务重组→容量规划→持续优化的全历程 (B1 Ch9 §3)
  - 长期性能优化方法论: 监测→分析(CPU/内存/磁盘)→改→重测 — 性能优化不是想出来的, 是测量+循环改出来的
  - 域间桥接: 域2=架构层, 域3(高并发与性能)=P98优化层 — 10万QPS架构问题 vs 500/10万/100万 QPS 机械问题 (B2 Ch8 §4)
  - 关键设计: 架构演进永无止境 — 每次水平扩展都不只是"分片", 是所有后端系统重新验证+结构完整性检查+部署验证+压测的圆

### 6. 收束 — 回到0到10亿用户的演变
  - 1服务器→读写分离→垂直拆分→SOA→微服务→分片→单元化→多活 — 每个阶段都在前阶段基础上加新层
  - 架构选择=时间和代价 — 今天正确的选择明天可能成为负担, 但每个选择都为下一个阶段预留扩展能力
  - 12篇文章从网络到缓存到消息到存储到微服务到容器到云原生到架构演进 — 体系完整, 域2从这里结束
