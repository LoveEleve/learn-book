# 用户说"我下单了, 为什么订单不存在?" — 分库分表后的事务、查询和扩容

> Cluster B: 14 KPs | 依赖: 05-message-driven, 域1-分布式事务 | 读者基线: 用过MySQL, 了解单机事务ACID

---

### 1. 单表5000万行 — 索引失效、查询30秒 — 分库分表触发点
  用户量从100万涨到1000万, 订单表5000万行, 按user_id查询走索引也要扫描50万行 — 该分了
  - B2 Ch6 §2: 分库分表判据 — 数据量(单表>2000万行→B+树高度>=4→影响查询), 并发量(单库连接数上限~2000→CPU/内存/磁盘瓶颈), 业务隔离(核心交易独立库, 不和非核心查询竞争)
  - B3 Ch5 §4: 存储架构演进 — 单机(所有表共库)→读写分离(主写从读)→垂直拆分(不同业务不同库)→水平拆分(单表分散多库多表) — 每一步引入更高复杂度 (B3 Ch5 §4.1-4.6)
  - 垂直拆分vs水平拆分: 垂直(不同表到不同库, 订单/用户/商品 → 各自独立实例) = 业务边界隔离; 水平(同一表按某键拆分到多库, order_0/order_1/.../order_63) = 容量扩展 (B2 Ch6 §2)
  - 关键设计: 拆分不是"能多大就多大" — 2000万行/表是经验值, 背后是B+树高度: 2000万=>H≤4, 单次查询<4次磁盘I/O

### 2. 分片键 — 选对了后面全对, 选错了重组数据
  你按user_id分片, 运营要查"过去7天下单金额>10000的用户" — 遍历所有分片, 收集再聚合, 爆炸
  - B4 Ch5 §5.4: 拆分键选择 — 业务主键(按user_id→同用户订单在一处,查询聚合简单→但按时间/金额查需跨库), 关联键(多个表使用相同拆分键→支持Join→但可能热点不均)
  - B2 Ch6 §2.3-2.4: Join问题 — 单库Join→分库后无法跨库Join → 反范式化(冗余数据), 应用层Join(先查所有行的订单→用所有user_id批量查用户信息), 搜素引擎(ES)来辅助复杂查询
  - 全局ID: UUID(无序→索引性能差)→Snowflake(单调递增, 1bit未用+41bit时间+10bit机器+12bit序号) → 时钟回拨问题(等待/用备用算法/手动处理) (B4 Ch3 §9.2) [工程: Twitter Snowflake在毫秒内用12bit序号支持4096个ID/ms, 时钟回拨时直接抛异常拒绝服务]
  - 关键设计: 分片键=你的数据模型的"重力中心" — 所有非分片键查询都需要额外架构(ES索引/全局二级索引)

### 3. 分布式事务在存储层的落地 — 2PC/TCC/Saga/可靠消息怎么选?
  用户下单=订单表(order_db_0)+库存表(inventory_db_1)+积分表(point_db_2), 三个库三个事务
  - 域1引用: 2PC(协调者+准备+提交, 同步阻塞, 性能差), TCC(Try预留+Confirm确认+Cancel回滚, 业务侵入但非阻塞), Saga(长事务拆分+补偿操作, 适合微服务) (B1 Ch2 §6.2-6.3)
  - B2 Ch10 §2: 业界的务实选择 — 2PC(Seata XA→适合单体遗留/金融), TCC(Seata TCC+业务实现→适合资金操作), 本地消息表+MQ(幂等+重试→适合通用场景) (B2 Ch10 §2.5-2.7)
  - 最终一致性实践: 订单创建→本地事务写订单表+发MQ"OrderCreated"消息→MQ at-least-once→库存消费(幂等)→积分消费(幂等) → 所有步骤都重试直到成功 (B2 Ch10 §2.3)
  - 关键设计: 分布式事务的实质=Saga补偿+幂等+对账 — 无全局一致方案, 只有不同失败率方案; 2PC=最重/最一致, 消息=最轻/最终一致

### 4. 分片后的扩容(re-sharding) — 你问"再分一次够吗?"
  从4库32表扩到8库64表 — 双倍, 数据迁移怎么做? 不停机怎么办?
  - B4 Ch5 §5.6: re-sharding挑战 — 数据迁移(老4→新8, 按新分片键散列), 停写停机(不可接受), 双写(新老同时写, 迁移期间→确保一致性→最终切读新)
  - 实操流程: (1)双写新老库 (2)历史数据批量迁移(离线任务→全量+增量, Binlog重放) (3)校验一致(逐行checksum) (4)切流量只读新→关双写→清理老 (B4 Ch5 §5.5-5.7)
  - 路由策略: 中间件代理(ShardingSphere-Proxy/MyCAT, 应用不感知分片) vs 客户端SDK(ShardingSphere-JDBC, 性能好但耦合)
  - 关键设计: 为什么不能"一次性分到位"? — 分片数=集群成本, 分太多造成空表开销+连接数膨胀, 但数据迁移成本极高 → 初始分128片(未来扩展到128节点无需再迁移, 只需加节点+移动部分数据)

### 5. 收束 — 回到"订单不存在"
  - 订单可能真的创建成功了 — 在order_db_3里, 但你的查询走了order_db_0(因为没带user_id, 跨片扫全失败)
  - 分库分表后: 所有查询必须带分片键 + 跨库Join不可能(应用层Join/反范式) + 分布式事务=最终一致(幂等+Saga+对账)
  - 数据一旦分片, 就永远没办法像单库一样写得舒服 — 这是CAP在存储层的体现
