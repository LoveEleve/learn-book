> Cluster B: 14 KPs | 依赖: 05-message-driven、分布式事务理论 | 读者基线: MySQL、单机事务 ACID、消息幂等

### 1. 单库瓶颈 — 拆分解决什么，不解决什么

场景提示: 订单表、用户表、库存表持续增长，单库的容量、I/O、连接和维护窗口先在哪里撞墙？ [写作时展开]

关键设计: 存储演进通常从共享单库到读写分离、垂直拆分，再到水平分片：

```[pseudocode]
单库:
  所有表/读写/资源共享

读写分离:
  主库写 + 副本读
  → 扩展读
  → 引入复制延迟/读己之写问题

垂直拆分:
  order/user/inventory → 业务域/实例边界
  → 隔离资源与团队边界
  → 跨域 join/事务变复杂

水平分片:
  同一逻辑表按 shard key
  → 多库多表
  → 单片容量/流量下降
  → 路由、跨片聚合和迁移复杂
```

Why: 为什么“单表超过某个固定行数就必须分片”是错误规则？——**真正瓶颈取决于索引、行宽、访问模式、缓存、I/O、并发和维护窗口**；行数只是信号，不是通用阈值。分片前要先确认优化器、索引、归档、读写分离和硬件是否已到合理边界。 [系统性能: 分片是架构变化，不能用一个行数阈值替代容量和 workload 测量]

比喻锚点: 单库像一座中央仓库，拆分不是因为货物超过某个神奇箱数，而是因为道路、货架、进出货和维护已经互相堵住。 [写作时展开]

### 2. 分片键 — 数据模型的“重力中心”

场景提示: 按 `user_id` 分片后，查询“最近 7 天金额超过阈值的用户”为什么要扫很多分片？ [写作时展开]

关键设计: 分片键同时决定路由命中、数据局部性、热点和跨片查询：

```[pseudocode]
选择候选:
  user_id → 同用户订单聚合方便
  tenant_id → 租户隔离/路由清晰
  time/range → 范围归档友好, 可能热点
  hash → 分布均匀, 范围查询困难

跨片查询:
  无 shard key
  → fan-out
  → 各片过滤/排序/聚合
  → coordinator merge
  → 延迟受最慢分片和返回量影响

关联表:
  共享 shard key → 可能保留局部 join
  不同 key → 反范式/应用聚合/搜索索引
```

Why: 为什么分片键一旦选错，后面很难补救？——**它嵌入路由、主键、索引、事务和查询模型**：非分片键查询需要全片扫描或额外全局索引，热点键会让单片先饱和。全局 ID（UUID/Snowflake/数据库号段）也要考虑有序性、时钟回拨、唯一性和迁移。 [分布式理论: 分片键是数据放置与一致性边界，不只是一个 hash 输入]

比喻锚点: 分片键像仓库分区规则；按客户分仓方便查某客户，按日期分仓方便清理历史，但跨规则查询都要跨仓找货。 [写作时展开]

### 3. 分布式事务 — 订单、库存、积分如何落地

场景提示: order_db、inventory_db、point_db 各自本地提交，怎样避免只成功其中两个？ [写作时展开]

关键设计: 分片后的事务方案要按强度、锁、侵入和补偿选择：

```[pseudocode]
XA/2PC:
  多资源 prepare/commit
  → 原子边界更直接
  → 阻塞/锁/协调恢复成本

TCC:
  Try 预留
  → Confirm/Cancel
  → 业务侵入、重试/幂等/空回滚

Saga:
  本地步骤
  → 失败逆序补偿
  → 中间态可见

本地消息表 + MQ:
  本地事务写业务+消息
  → 消费者幂等/重试/对账
  → 最终一致
```

Why: 为什么分库分表后很难保留单库事务的舒适性？——**资源管理器不再共享一个本地提交点，网络超时和部分成功必须显式建模**；真正的选择是业务不变量、允许的中间态、恢复方式和运维能力，而不是只看框架注解。 [分布式事务: 08-10 篇的协议/幂等/补偿边界在存储架构中具体化]

### 4. Re-sharding — 数据迁移比第一次分片更难

场景提示: 4 库 32 表要扩到 8 库 64 表，怎样在不停机时搬迁历史和增量？ [写作时展开]

关键设计: 在线 re-sharding 需要建立新旧路由并处理迁移期间的并发写：

```[pseudocode]
准备:
  定义新 shard map/双读策略

全量:
  批量迁移历史数据
  → 控制速率/校验/记录进度

增量:
  双写、CDC/binlog 捕获或变更日志
  → 补齐全量迁移期间新增修改

校验:
  行数/checksum/业务抽样/版本

切换:
  灰度读新
  → 停止旧写/完成尾差
  → 只读新路由
  → 观察后清理旧数据
```

Why: 为什么不能一次停写、拷贝、再启动？——**生产通常不能接受停机窗口，而且迁移期间仍有并发写**；双写会带来失败重试、顺序、重复和双边不一致，CDC 会带来延迟和回放边界。分片数量也不是越多越好，连接、元数据、空表和迁移成本都会增长。 [系统性能: 迁移任务本身会消耗 I/O/网络/锁资源，必须限速和观测]

比喻锚点: Re-sharding 像营业中的仓库换分区：旧仓继续接单，新仓同步搬货，最后要对账、切换门牌，再拆旧仓。 [写作时展开]

### 5. 代理与客户端路由 — 隐藏复杂度不等于消除复杂度

场景提示: ShardingSphere-Proxy、MyCAT 或客户端 SDK，谁来决定 SQL 发到哪一个分片？ [写作时展开]

关键设计: 路由责任可放代理或应用客户端：

```[pseudocode]
Proxy:
  应用连接统一入口
  → 代理解析 SQL/分片键
  → 路由/改写/聚合
  → 统一治理
  → 增加网络跳数与代理状态

Client SDK:
  应用/驱动本地路由
  → 少一跳/控制直接
  → 所有服务必须升级/理解 shard map

共同限制:
  无 shard key 的查询、跨片 join、分页、排序、事务
  → 都需要额外策略
```

Why: 为什么“中间件让应用无感”通常只是短期体验？——**分片边界最终会暴露在事务、分页、排序、错误重试、迁移和运维中**；代理能集中策略，但也可能成为新的容量/故障/版本兼容边界。 [分布式架构: 路由层的透明性必须以可解释的 SQL/事务限制为代价说明]

### 6. 收束

分库分表闭环：

```[pseudocode]
容量/并发/维护瓶颈
  → 垂直或水平拆分
  → 选择 shard key/global ID
  → 重新设计查询/事务
  → 代理或客户端路由
  → re-sharding/校验/切流
  → 监控跨片延迟/热点/复制/一致性
```

**Aha Moment**: "分库分表不是把一个库复制成很多小库，而是**重新定义数据在哪里、请求如何路由、事务如何完成、查询如何聚合和数据如何迁移**；一旦拆分，数据库便利性会转化为应用和平台责任。"
**回答读者三问**: ①为什么订单会查不到=路由缺 shard key 或读副本延迟；②分片键为什么重要=它决定局部性、热点和跨片代价；③扩容为什么难=全量、增量、校验和切流必须同时正确。
