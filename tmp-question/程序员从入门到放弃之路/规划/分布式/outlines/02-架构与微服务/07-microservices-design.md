# 你拆了20个微服务, 改一个接口要通知3个团队 — 微服务拆分的边界到底在哪里?

> Cluster C: 13 KPs | 依赖: 06-storage-architecture | 读者基线: 用Spring Boot写过多个服务, 理解RPC调用

---

### 1. 单体还是微服务 — 这不是二选一, 是"什么时候该拆"的问题
  创业团队3个人, 老板要求微服务架构 — 3个人维护20个微服务, 每天Debug网络超时的次数比写代码还多
  - B1 Ch8 §1.1: 微服务兴起原因 — 单体困境(代码膨胀/部署耦合/技术锁定) vs 微服务红利(独立部署/技术多态/弹性扩容/团队自治)
  - B4 Ch2 §2.2: 什么时候开始 — 团队>5人/模块间出现依赖冲突/部署频率不一致(支付服务一天发5次, 基础服务一个月发1次)/某模块需要独立扩容(B4 Ch2 §2.2)
  - B4 Ch2 §2.6: 微服务划分反模式 — 共享数据库(多个服务连接同一DB→耦合), 分布式单体(表面拆分但强依赖部署顺序), 纳米服务(过度拆分→1个函数一个服务→调100次RPC) [案例: Uber早期微服务泛滥—司机、乘客、行程、支付各自独立但改为行程必须调全部→最终合并为行程聚合服务—证明"服务越多越独立"是错误理念]
  - 关键设计: "先从单体开始, 再拆分"的绞杀者模式 — 新功能写新微服务, 旧单体逐步迁移, 而不是一步到位把所有东西重写成微服务 (B4 Ch2 §5.4)

### 2. 拆分方法论 — DDD / 数据驱动 / 按变化频率, 选哪个?
  你拆了订单服务和库存服务, 然后发现每个功能修改都需同时改两个服务 → 拆错了
  - B4 Ch2 §5.1-5.3: 三种拆分方法 — 业务复杂度(简单CRUD→DDD不够必要), 数据驱动(按数据边界分, 同一数据归属一个服务), DDD(限界上下文+聚合根+领域事件, 适合复杂业务) [工程: DDD的限界上下文天然映射微服务边界 — 聚合是事务单元的抽象而非服务边界的唯一依据, 服务可以包含多个聚合但跨聚合的事务需最终一致性]
  - DDD与微服务: 限界上下文→微服务边界, 聚合(保证事务一致性)→微服务粒度, 领域事件(OrderCreated, InventoryDeducted)→服务间通信 (B2 Ch15 §5)
  - B2 Ch15 §3: 业务流程≠系统流程 — DDD的第一步不是建模, 是区分业务域(业务专家语言)和技术域(开发者实现), 统一语言是关键
  - 拆分合理性度量: 服务是否可独立部署? 是否可独立扩容? 是否由独立小团队维护? 3个全满足→拆分合理 (B4 Ch2 §5.6)
  - 关键设计: 用内聚度判断而不是用户量 — 修改订单状态是否不需改动库存服务? 如果"改A必然改B"那A和B就不该拆

### 3. 微服务框架选型 — Spring Cloud vs Dubbo 的23个维度
  你的团队Spring全家桶经验丰富, 但新来的架构师坚持要切Dubbo — 这不是技术分歧, 是生态分歧
  - B1 Ch8 §2.2: Spring Cloud — Eureka(注册)+Ribbon(LB)+Feign(声明式RPC)+Hystrix(熔断)+Zuul/Gateway(网关)+Config(配置), 全家桶但部分组件已进入维护模式
  - B4 Ch2 §9-10: Dubbo — Provider/Consumer/Registry(Nacos/ZK)+Monitor+Config, 纯Java生态/私有协议/性能优/阿里开源社区活跃; 支持多注册中心/多协议/多序列化
  - Spring Cloud Alibaba: Nacos(注册+配置)+Sentinel(熔断限流)+Seata(分布式事务)+RocketMQ — 阿里技术栈统一 (B4 Ch2 §10)
  - 关键设计: 选框架=选生态, 不是选代码 — Dubbo/Spring Cloud在功能上重叠但生态绑定不同; 阿里云→Dubbo+Nacos+Sentinel, 海外面向→Spring Cloud(Netflix组件)+Consul

### 4. API设计与网关 — 外部调一个接口, 内部分解成7次RPC
  前端看到POST /api/orders → 网关要拆成创建订单+扣库存+发积分+记录日志4次内部调用
  - B4 Ch2 §7: API设计原则 — RESTful(资源导向, GET/POST/PUT/DELETE), RPC(操作导向, 自定义方法), gRPC(基于HTTP/2+Protobuf, 双向流)
  - API网关: 路由(根据path→服务), 聚合(1个外部API后台调用多个微服务→BFF), 认证(JWT校验, 网关统一验证), 限流(保护后端) (B1 Ch8 §1.3)
  - 网关聚合(BFF): 每个前端(Web/Android/iOS)各自聚合需求, 1个BFF=1个前端专用聚合层→减少前端HTTP调用数 (B4 Ch2 §8)
  - 关键设计: API版本兼容 — 你不能因为一个微服务改API强制所有上游服务改 → /api/v1和/api/v2并存 + 灰度切换

### 5. 收束 — 回到20个微服务的边界
  - 微服务数量不是KPI — 以"独立部署+独立扩容+独立团队维护"三个条件检验, 不合格的服务应合并
  - 拆分是主观判断, 不是客观公式 — 关键是在业务理解基础上的内聚治理, 而非"按表拆分"
  - DDD是方法论, 但最终输出的是统一语言和聚合边界 — 不是图论完就够

### 核心悬念
**"你设计20个微服务, 测试环境全都正常——上线后订单服务挂了, 库存服务等了3秒超时, 然后10个服务像多米诺骨牌一样全挂了——为什么一个服务能搞垮整个集群?"**

→ 引出 韧性模式: 限流/熔断/降级/超时重试/舱壁隔离/优雅关闭 — 微服务的8个防守手段 (08-resilience-patterns)
