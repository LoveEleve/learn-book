### 1. 熔断 — 防止失败沿调用链传播

场景提示: 下游变慢后，上游线程池全部阻塞；熔断器如何把“等待对方恢复”变成“本地快速失败”？ [写作时展开]

关键设计: 熔断器按失败/延迟信号切换状态，并在半开阶段探测恢复：

```[pseudocode]
CLOSED:
  正常调用
  → 统计失败率/慢请求/窗口

OPEN:
  达到阈值
  → 不再调用下游
  → 快速返回 fallback/error

HALF_OPEN:
  等待冷却窗口
  → 放少量探测请求
  → 成功 → CLOSED
  → 失败 → OPEN
```

Why: 为什么熔断不是“把慢服务下线”这么简单？——**它是调用方的本地保护状态，不等于服务真实健康状态**：阈值、窗口、探测量、fallback 和恢复都会影响误判。熔断保护的是失败传播和本地资源，不保证业务请求成功。 [分布式架构: 熔断必须与 timeout、retry、fallback 和指标窗口共同设计]

### 2. 限流 — 令牌桶、漏桶与队列背压

场景提示: 每秒平均 1000 请求看起来正常，但一秒内突然来了 1 万请求，固定窗口为什么会被打穿？ [写作时展开]

关键设计: 限流算法决定平均速率、突发容量和排队行为：

```[pseudocode]
固定窗口:
  计数到阈值拒绝
  → 边界处可能双窗口突发

滑动窗口:
  多时间片统计
  → 更平滑, 有存储/计算成本

漏桶:
  固定出水速率
  → 平滑处理, 突发通常被排队/拒绝

令牌桶:
  按速率产生 token
  → 桶容量允许有限 burst
  → 没 token 时等待/拒绝
```

Why: 为什么 Guava RateLimiter 不能直接解决分布式限流？——**它是进程内状态，多实例之间不会自动共享额度**；Redis/Lua、网关或 Sentinel 可做分布式协调，却增加网络、可用性和热点成本。限流还要定义按用户、租户、接口、优先级还是全局资源。 [系统性能: 限流改变入口排队和尾延迟，不能只看 QPS]

### 3. 降级 — 熔断后不能简单返回 null

场景提示: 库存服务挂了，订单还能创建吗？推荐、积分、库存数量分别能降级到什么程度？ [写作时展开]

关键设计: 降级要按业务重要性定义可接受结果：

```[pseudocode]
核心:
  支付/扣库存/订单状态
  → 不能静默返回成功
  → 排队/失败/补偿/人工处理

非核心:
  推荐/评分/画像
  → 静态默认/缓存旧值/关闭模块

降级范围:
  全量/部分用户/部分区域/部分功能
  → 明确恢复条件和状态提示
```

Why: 为什么 fallback 返回空对象很危险？——**调用方可能把空值当成成功或继续执行，造成数据错误**；降级结果必须包含语义、状态、可重试性和用户提示。熔断保资源，降级保业务核心，两者不是同一动作。 [分布式事务: 核心不变量与最终一致/补偿路径必须优先于“接口返回 200”]

### 4. 超时、重试、舱壁与优雅关闭 — 四个机制必须配套

场景提示: 3 秒超时重试两次，慢下游会怎样把一次请求放大成三次，并进一步打满线程池？ [写作时展开]

关键设计: 防御组合应共享 deadline，并按资源和操作语义控制：

```[pseudocode]
Timeout:
  每次调用/整条链共享 deadline
  → 不让下游无限占用线程

Retry:
  只重试明确幂等/可安全重试操作
  → exponential backoff + jitter
  → 次数/总预算受限

Bulkhead:
  每个下游/优先级独立线程池、信号量或连接池
  → 坏邻居不能耗尽全部资源

Graceful shutdown:
  摘除流量
  → 停止新请求
  → 等待/取消进行中任务
  → 关闭连接池/线程池/消息消费者
```

Why: 为什么重试是最容易被滥用的韧性手段？——**它把下游错误放大，并可能重复非幂等副作用**；超时过短制造无谓重试，过长又耗尽资源。舱壁只是隔离资源，不自动解决业务失败；优雅关闭也要与注册中心、消息 offset 和连接池生命周期一致。 [分布式架构: 超时/重试/幂等三角与 02 RPC 篇一致]

### 5. 容量规划与混沌演练 — 证明防御而不是相信配置

场景提示: 你给每个服务都配了限流和熔断，怎样知道级联故障真的被挡住？ [写作时展开]

关键设计: 容量和故障演练把防御策略从配置变成可验证假设：

```[pseudocode]
容量:
  QPS/并发/响应时间
  → 估计线程、连接、队列和下游容量
  → 压测寻找饱和点与 P99

依赖清单:
  DB/Redis/MQ/RPC/外部 API
  → 宕机、慢、错误、部分可用
  → 对应 timeout/retry/fallback/bulkhead

混沌:
  kill pod/延迟/丢包/限速/依赖错误
  → 观察错误率、队列、恢复和用户语义
  → 验证回滚与告警
```

Why: 为什么“加机器”不能代替容量模型？——**瓶颈可能在数据库、单锁、队列、连接池、网络或单分片，扩展错误层级只会增加成本**；混沌实验也必须有范围、停止条件、观测和恢复计划，不能把生产用户当实验样本。 [系统性能: 用 Little/排队/USE/RED 和 workload 压测定义容量边界]

### 6. 收束

韧性体系：

```[pseudocode]
入口限流/背压
  → timeout 控制等待
  → retry 仅处理安全失败
  → circuit breaker 阻断传播
  → bulkhead 隔离资源
  → fallback 保核心语义
  → graceful shutdown 保护生命周期
  → capacity/chaos 验证边界
```

**Aha Moment**: "韧性不是把每个服务都加上八个组件，而是**让流量、等待、失败、资源和业务语义在正确层级被限制与恢复**；错误的重试和错误的 fallback 可能比没有防御更危险。"
**回答读者三问**: ①熔断和限流差在哪=前者阻断失败依赖，后者控制进入速率；②为什么降级不能返回 null=必须保核心业务语义；③如何证明有效=容量压测加有边界的混沌演练。
