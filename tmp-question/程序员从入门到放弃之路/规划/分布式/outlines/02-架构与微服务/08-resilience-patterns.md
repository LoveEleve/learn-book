# 微服务的"一个挂了全挂了" — 限流/熔断/降级/隔离, 8个防御手段的对比与协作

> Cluster C: 14 KPs | 依赖: 07-microservices-design, 05-message-driven | 读者基线: 部署了微服务, 遇到过度网络调用失败

---

### 1. 熔断器 — 你调用库存服务, 3次超时后直接在本服务判定"下线"
  库存服务开始变慢(p99从50ms→5s), 你的订单服务一直在等响应→线程池耗尽→订单服务崩溃→然后所有调用订单的服务也崩溃 —— 多米诺骨牌效应(级联失败)
  - B4 Ch4 §3.7: 熔断器三状态 — CLOSED(正常, 统计失败次数)→OPEN(判定故障, 直接返回降级逻辑, 不再调真实服务)→HALF_OPEN(等N秒后探测1次, 成功→CLOSED, 仍失败→OPEN)
  - B2 Ch9 §2: Hystrix/Sentinel — Hystrix(Netflix, 线程池隔离+信号量隔离+fallback回退, 已停止维护) → Sentinel(阿里, 基于滑动窗口统计, 流量控制+熔断+系统保护) (B2 Ch9 §2)
  - Sentinel核心: 基于QPS/响应时间/异常比率+滑动窗口(真实实时数据), 而非Hystrix的固定窗口; 支持热点参数流控(qps per user_id) [案例: Sentinel在双十一支撑阿里上万服务的流量防护, 用滑动窗口保证单机流控精度]
  - 关键设计: 熔断不是防"慢", 是防"传播" — 快速检测→快速拒绝→给下游恢复时间, 拒绝"等待对方好人"的心态

### 2. 限流 — 令牌桶/漏桶/滑动窗口, 为什么Guava RateLimiter适用场景有限?
  你下单时设了限流策略"每秒1000请求" → 但刷子用户卡在00:00:00秒发送1万个请求(00:00:01秒恢复正常) → 你的计数器限流拍死在墙上
  - B4 Ch4 §4.1: 限流算法演进 — 计数器(最大问题=时间窗口边界瞬时暴增: 00.99秒+01.01秒→2s内超过限制2倍) → 滑动窗口(细分为N个小窗口, 滑动计算, 更平滑) → 漏桶(平缓处理, 溢出=拒绝, 不可burst) → 令牌桶(生成速率恒定=平均QPS, 桶容量=突发Burst)
  - B4 Ch4 §4.3-4.4: 限流实现 — Guava RateLimiter(令牌桶, JVM内, 适合单机→但不适合分布式), Nginx limit_req_zone+limit_req(漏桶, 网关层, Nginx层面→返回503), Sentinel(分布式限流, 按调用方/出口/热点参数)
  - 分布式限流: Redis + Lua脚本实现令牌桶(原子操作) → 单次限流需要一次Redis网络调用, 性能取舍
  - 关键设计: Burst处理 — 令牌桶允许积累令牌(桶容量=Burst上限), 能处理短期脉冲而不瞬时拒绝所有——这是计数器/漏桶不具备的

### 3. 降级 — 库存服务挂了, 订单还能继续吗?
  你把所有依赖的服务都加了熔断, 熔断OPEN后返回了null → 订单创建函数NullPointerException → 下单流程整个炸
  - B2 Ch9 §2: 降级设计 — 核心链路(必须成功, 无法降级) vs 非核心(可降级); 降级手段: 静态兜底(返回缓存数据/默认值), 简化逻辑(关闭精彩推荐/积分计算), 跳转(排队等待页)
  - B3 Ch6 §1.5-1.6: 降级策略 — full-degrade(所有非核心关闭) vs partial-degrade(按用户/区域/功能维度降级); B3 Ch6 §1.5
  - 服务分级: 0级(登录=不可降级), 1级(下单=VITALS), 2级(评分/推荐=可降级), 3级(用户在线状态=可完全关闭) (B3 Ch6 §1.5)
  - 关键设计: 降级不是"返回空" — 是返回用户可接受的兜底 — 商品详情/库存数量不可降级可静态兜底(回退Redis), 用户等级积分可降级(不计算), 产品推荐可降级(关闭模块)

### 4. 超时/重试/隔离 — 这三个经常被低估
  你设了3s超时, 重试2次 → 库存服务p99=2.8s → 第一次超时→重试→库存实际上第一次成功但响应慢→第二次也成功→扣了两次库存
  - B4 Ch4 §3.5: 超时重试 — 超时=(p99 + 50%*p99) 或 经验值(500ms~3s), 重试=指数退避(100ms→200ms→400ms)+jitter(±随机, 防止惊群); 重试前必须检查幂等(幂等号)
  - B4 Ch4 §3.6: 隔离策略 — 线程池隔离(每个下游有独立的线程池, 一端满了不影响另一, Hystrix默认) vs 信号量隔离(轻量, 适合高频调用, 但无法超时); 舱壁隔离=为每个下游制造独立容器
  - B3 Ch6 §1.5: 优雅关闭 — 先摘流量(注册中心注销)→等待处理中请求(N秒)→释放资源(数据库连接池/线程池)→进程退出
  - 关键设计: 超时+重试+幂等是三角关系 — 有重试就必须有幂等, 没有幂等的重试就是欺骗自己

### 5. 容量规划与混沌工程 — 你怎么知道你撑不撑得住?
  "加机器解决一切"是微服务最大的谎言 — 加机器前不知道瓶颈在哪=随机加
  - B2 Ch8 §4: 容量模型 — QPS = 并发数/响应时间, 容量规划=压测(找到最大值)+线上监控(当前距上限的距离)+弹性扩容(自动触发)
  - B4 Ch4 §5-6: 压测与演练 — 全链路压测(生产环境影子库, 标记压测请求不污染真实数据), 混沌工程(注入故障: 随机杀Pod/延迟注入/丢包, 验证系统稳定性) (B4 Ch4 §5-6)
  - B3 Ch6 §1.2-1.4: 风险识别 — 列出所有外部依赖(DB/Redis/MQ/下游服务)→每个依赖的故障分析(完全宕机/部分可用/延迟高)→对应的降级措施
  - 关键设计: 容量规划的终极目标=知道跑多少命就断 — 不是无限加机器, 而是知道系统极限在哪+在用户打到你之前启动弹性

### 6. 收束 — 回到一个服务挂全挂的级联失败
  - 熔断阻止传播, 限流挡住脉冲, 降级保住核心链路, 隔离不让坏邻居影响好邻居 — 四个机制各司其职
  - 韧性=设计而非响应 — 在上线前设计好每个依赖的故障预案, 不是一个服务挂了后"紧急开会讨论怎么搞"
  - 容量+熔断+限流+降级+隔离+超时+重试+优雅关闭 — 8个是防御体系不是技术清单

### 核心悬念
**"你给每个服务都加了限流/熔断/降级, 但每个服务实现的逻辑都不一样——Spring Cloud Gateway加了限流, Sentinel做了熔断, 每个服务内还有自己的重试逻辑, 怎么统一?"**
