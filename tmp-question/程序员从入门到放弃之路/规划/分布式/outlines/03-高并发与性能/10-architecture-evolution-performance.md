# 拆成微服务后, 一个下单要调5个服务 — 原来单体200ms, 现在800ms

> Cluster D: 8 KPs | 依赖: 域2-01/07/12(通信/RPC/微服务架构) | 读者基线: 经历过单体→微服务拆分, 感受过分布式带来的性能开销

---

### 1. 单体的性能天花板 — 不是"单体太慢", 是"写代码的方式打不赢物理定律"
  你曾经有一个单体应用, 从1000 QPS到10000 QPS加机器就解决 — 直到数据库成瓶颈。
  - 单体的天然优势: 进程内调用(纳秒级)→无序列化开销→无网络RTT→事务本地ACID → 单体性能优化的三件套: 缓存/异步/读写分离 (B4 Ch1 §1.1-1.2, B5 Ch3 §3.1)
  - 单体的天然劣势: 垂直扩容有上限(CPU/内存/IO)→全量部署(改一个字全量上线)→数据全部耦合(一个慢查询影响所有业务) (B4 Ch1 §1.2, B3 Ch10 §10.1)
  - 单体的性能拐点: 当数据库成为瓶颈(单库连接数/写入量)且缓存+读写分离都不够用 → 必须拆分数据库 → 数据库拆分驱动业务拆分 (B4 Ch1 §1.6, B5 Ch3 §3.2)
  - 关键设计: 单体的性能优化和微服务的性能优化是两个世界 — 单体优化在代码层(减少对象分配/优化算法), 微服务优化在架构层(减少网络调用/数据一致性折中)

### 2. 拆分的第一刀 — 从单体到垂直拆分, 性能先降后升
  你把订单和用户拆成两个服务, RT从200ms变成400ms — 你拆分错了吗?
  - 拆分引入的开销: 序列化(JSON→Protobuf, 1-5ms)+网络RTT(内网0.5-2ms)+反序列化(1-5ms)+线程切换+Tomcat连接 — 一次RPC额外开销5-15ms (B2 Ch1 §1.6, B5 Ch6 §6.1)
  - Amdahl定律的分布式代价: 串行部分(P) = 不能并行的逻辑, 在分布式系统里P还包括网络调用 — 分布式Amdahl: speedup = 1/((1-P) + P/N + C×N) — C=通信开销, N越大通信开销越大 [理论: Gunther的通用可扩展性定律(USL) — 加入一致性延迟和串行化竞争, 解释了"加机器→性能下降"的现象]
  - 拆分后的优化方向: 合并调用(网关聚合多个服务返回, 减少客户端调用次数)→异步化(非关键链路的调用异步化, 不增加主链路RT)→连接池复用(RPC长连接, 避免每次建立连接) (B5 Ch6 §6.6-6.7, B2 Ch2 §2.7)
  - 关键设计: 拆分的"最优粒度" — 不是说拆越细越好, 服务粒度=业务功能内聚度×数据耦合度×网络开销容忍度

### 3. 微服务的性能陷阱 — 你以为的弹性, 其实是深坑
  你给每个微服务配了独立的数据库(独享数据库模式) — 一个查询需要跨3个数据库, 放弃数据一致性?
  - 分布式事务的性能代价: 2PC(两次提交+等待协调者, 同步阻塞5-10x慢)→TCC(Try阶段检资源+Confirm/Cancel, 异步但有补偿逻辑)→Saga(长事务编排, 每步有补偿, 最终一致) (B6 Ch7 §7.4-7.7, B5 Ch11 §11.2)
  - 服务间调用链爆炸: 下单→查用户→查商品→查库存→扣库存→创建订单→发消息 — 7次RPC=7×(5-15ms)=35-105ms, 还不算处理时间 [案例: 单体拆微服务前后性能对比 — 某电商下单: 单体200ms(MySQL查询为主)→拆5个微服务400ms(4次RPC+1次MQ)→优化后250ms(批量合并2次RPC+异步化通知+缓存用户信息)]
  - Service Mesh的代价: Sidecar代理(Envoy)→每条请求多一次代理转发(0.5-2ms)→Istio的Mixer每次请求调Policy+Telemetry(已废弃, Istio 1.5改为WASM) → 轻度使用服务网格=5-10%性能开销 (B5 Ch17 §17.3)
  - 关键设计: 微服务不是性能解决方案, 是组织扩展方案 — 性能视角下微服务引入了更多开销, 优势只在于更细粒度的独立扩容

### 4. 云原生的性能杠杆 — K8s弹性伸缩+Serverless按需付费
  K8s的HPA说CPU>80%就扩容, 但从80%到扩容到Pod就绪要1分钟 — 你的服务已经崩了。
  - HPA vs VPA: HPA(水平扩展, 增减Pod数)→VPA(垂直扩展, 调Pod资源)→KEDA(事件驱动, 基于MQ堆积数/Prometheus指标扩展) — 按场景选: HPA适合无状态web, KEDA适合消息队列消费者 (B5 Ch17 §17.1)
  - 弹性伸缩的冷启动: 新Pod调度(0.5s)→拉镜像(<30s)→应用启动(3-5s JIT+连接池)→健康检查(3×5s=15s) → 总计30-120s → 需要提前预热或过量冗余 (B5 Ch17 §17.3)
  - Serverless冷启动: 无流量→缩容到0→新请求→冷启动(镜像/初始化/GraalVM Native Image可<1s) → 适合低频非延迟敏感场景 (B5 Ch17 §17.3, B6 Ch3 §3.1)
  - 关键设计: 云原生的性能优化重心从"代码优化"转向"资源调度" — 你能用HPA在流量来前提前扩容吗? 能预测峰值还是反应式扩容?

### 5. 架构演进的性能视角 — 每个阶段的最优解不同
  1000 QPS→1万 QPS→10万 QPS→100万 QPS, 你的架构能跟上吗?
  - Phase 1(1000 QPS): 单体+缓存+读写分离 — 问题在数据库, 不是架构
  - Phase 2(1万 QPS): 垂直拆分+异步化+MQ削峰 — 问题在网络调用, 需要合并和异步
  - Phase 3(10万 QPS): 水平拆分+多级缓存+CQRS — 问题在单点瓶颈, 需要分片
  - Phase 4(100万 QPS): 单元化+异地多活+全链路异步 — 问题在地理和物理极限 [工程: 每10x流量增长不是渐进优化的累加, 而是结构性的变化 — 1000→1万改缓存, 1万→10万拆服务, 10万→100万拆数据中心]

### 6. 收束 — 架构选择的本质是"用空间换时间"的不断迭代
  - 单体→微服务: 用网络开销换独立扩展能力
  - 微服务→云原生: 用资源冗余换弹性调度
  - 没有最好的架构, 只有最匹配当前流量级别的架构
  - 域1的CAP+域2的微服务架构→域3的性能实践→下一步是深入具体技术栈
