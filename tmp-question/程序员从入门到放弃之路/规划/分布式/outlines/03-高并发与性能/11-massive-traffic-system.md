# 老板说双11要扛1000万QPS — 你用什么证明你的系统扛得住?

> Cluster D: 8 KPs | 依赖: 10-architecture-evolution-performance, 域2-06(存储架构) | 读者基线: 参与过大促保障但不清楚全链路压测和异地多活细节

---

### 1. 容量规划 — "能扛多少"不是拍脑袋说的
  你说"我们的系统能扛10万QPS", 老板问"怎么证明?" — 你说"上限没崩过"。
  - 容量规划的输入: 业务预估(运营给的目标QPS)+历史数据(去年峰值×增长系数)+单机容量(压测得单实例最大QPS) → 输出: 需要多少台机器 (B3 Ch9 §9.1-9.3, B1 Ch1 §1.4)
  - 单机QPS测算: 压测(从低QPS递增, 找到TPS饱和点+RT拐点)→冗余系数(2-3x, 覆盖单机故障+流量尖刺+日常波动) — 不是单机最大QPS, 是"安全QPS" [工程: 二八原则容量评估 — "20%的接口消耗80%的容量" → 找到Top 20%的热点接口, 优化它们, 效果最显著]
  - 容量评估的陷阱: 只算CPU(80%→预估QPS=单机QPS*(80%/当前CPU%))→没算内存/网络/磁盘→实际瓶颈在IO (B3 Ch9 §9.4, B5 Ch4 §4.4)
  - 关键设计: 容量规划=单机QPS(实测)×机器数(公式)×冗余系数(经验) — 但最关键的变量是"业务预估的准确性"

### 2. 弹性伸缩 — 流量来了才扩容, 来得及吗?
  双11零点, 流量从1000突然跳到100000 — K8s HPA检测到CPU>80%, 开始新Pod调度→拉镜像→启动→就绪...2分钟后, 服务已经崩了。
  - 预测式扩容 vs 反应式扩容: 反应式(CPU>80%扩容, 滞后30-120s)→预测式(基于历史, 提前扩容, 如双11提前30分钟扩容)→定时式(每天8点扩容, 22点缩容) (B5 Ch17 §17.1, B3 Ch11 §11.2)
  - 扩容速度 vs 稳定性: 快速扩容(拉新Pod)→快速缩容(节省成本但可能导致震荡) → HPA的stabilizationWindowSeconds(缩容前观察300s, 避免抖动) (B5 Ch17 §17.3)
  - 弹性策略: 多指标HPA(CPU+内存+自定义指标)→KEDA(基于事件: Kafka lag>1000→扩容消费者) → 复杂的系统是"组合弹性": Web层按CPU, Worker层按队列深度 (B5 Ch17 §17.1)
  - 关键设计: 弹性伸缩不是万能的 — 如果你的数据库不支持水平扩展, 应用层扩容100倍也无用; 容量短板在最下面一层

### 3. 全链路压测 — 模拟双11的流量打进生产环境
  你预发布环境压测20000QPS没问题 — 双11当天上线, 8000QPS就崩了。
  - 预发布vs生产: 数据量不同(生产3年数据), 下游服务版本不同(预发布联通全部最新版), 硬件不同(生产大内存/SSD) — 导致压测结果完全不可信 (B1 Ch6 §6.3, B5 Ch16 §16.1)
  - 全链路压测核心: 在生产环境压测(压测流量+真实流量共存)→流量染色(Header加压测标识)→数据隔离(影子库/影子表/影子缓存)→下游改造(识别压测标识, 写入影子存储) (B1 Ch6 §6.3, B5 Ch16 §16.3-16.4) [理论: 全链路压测的本质是"在不影响用户的情况下, 用生产环境的全部组件来发布负载" — 不是技术问题, 是隔离问题]
  - 流量构造: 录制线上流量(TCPCopy/Goreplay)→修改参数(影子化)→放大(单条录制成多条)→回放 → 逼真度远高于手动构造压测脚本 (B5 Ch16 §16.3)
  - 关键设计: 压测停止判断 — TPS不再增长(QPS+但TPS不涨=到达容量上限)→错误率陡升→RT曲线变陡 — 三点任一点触发表示到了容量瓶颈

### 4. 异地多活 — 一个机房挂了, 流量怎么切到另一个?
  你的服务部署在北京+上海双机房 — 北京机房故障, 流量切到上海, 但上海QPS翻倍扛不住。
  - 多活vs冷备: 冷备(一个机房工作/一个闲着, 切过去需要启动服务+恢复数据, 小时级)→多活(两个机房同时接流量, 秒级切换, 但双倍成本) (B1 Ch3 §6, B2 Ch1 §14, B4 Ch4 §4.12)
  - 单元化: 用户按UID路由到固定机房(uid%2=0→北京/uid%2=1→上海)→避免跨机房数据库写冲突 — 每单元有完整能力(独立处理用户全部请求) (B4 Ch4 §4.4-4.5, B2 Ch1 §14)
  - 数据同步: MySQL DRC(数据复制中心, 异步同步)→Redis DRC(AOF同步)→MQ跨机房复制 → 同步延迟50-200ms取决于物理距离 (B2 Ch1 §14.4-14.5) [案例: 异地多活流量切流 — GSLB(DNS解析到存活机房)→HTTP-DNS(客户端感知机房状态)→流量控制台(一键切流, 灰度放量1%→5%→50%→100%)→DB角色切换(原从库提升为主库)]
  - 关键设计: 多活的真正挑战不是"切流", 是"数据一致性" — 一个用户先后访问两个机房(切流/客户端漂移), 数据能否看到全局一致性

### 5. 秒杀系统的性能极致 — 从100万QPS中让100人抢到100件
  你说"秒杀用Redis减库存就行" — 但Redis的热点key问题让你整台Redis机器CPU打到100%。
  - 秒杀的三层缓冲: CDN(静态页面, 按钮灰掉)→Nginx限流/排队(99%流量挡在网关外)→应用层内存标记(商品售罄标记, 0数据库查询) (B4 Ch7 §7.1-7.3, B5 Ch13 §13.3)
  - Redis预扣+TCC: 预扣库存(Redis DECR, 不落DB)→抢到后异步创建订单+DB扣减→超时未支付回滚库存 — 并发竞争在Redis层(CAS), 不是在DB层(行锁) (B4 Ch7 §7.4-7.5, B5 Ch13 §13.3)
  - 削峰手段: 答题验证码(人机识别→过滤机器流量)+排队(服务端队列, 101万人排前面100人抢到)→分时秒杀(10:00/14:00/20:00三场, 分散压力) (B4 Ch7 §7.4, B1 Ch2 §2.5)
  - 关键设计: 秒杀架构的核心不是"让系统更快", 是"让大部分请求不接触核心系统" — 越早拒绝, 系统越稳

### 6. 收束 — 亿级流量的核心能力不是代码, 是"验证+兜底+恢复"
  - 全链路压测: 验证你的架构能扛多少
  - 容量规划: 知道你需要多少资源
  - 弹性伸缩: 流量来之前扩容
  - 异地多活: 流量出问题时切流
  - 没有银弹, 只有一环扣一环的保障体系
