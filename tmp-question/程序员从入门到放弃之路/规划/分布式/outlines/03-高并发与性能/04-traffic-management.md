### 1. 容量边界 — 流量治理首先不是放大吞吐，而是承认瓶颈

场景提示: 大促零点流量瞬间涌入，入口层还能收请求，但数据库连接池、下游 RPC、线程池和队列很快堆满；读者常见误判是“CPU 还没满，为什么系统已经崩了”。 [写作时展开]

关键设计: 系统吞吐取决于最慢、最脆弱且最难扩展的那一层，流量治理要在请求抵达瓶颈前就做削峰、排队、拒绝和降级：

```[pseudocode]
请求到达
  → 网关/代理层先做粗粒度限流
  → 应用层按资源/调用方/接口做细粒度限流
  → 只有被放行的请求才能继续占用线程池、连接池、下游配额
  → 某层处理不过来
       → 排队增加
       → 超时变多
       → 线程占满
       → 上游继续等待/重试
       → 级联雪崩
```

关键设计: 限流的目标不是“证明前端能扛住更高 QPS”，而是保护真正的瓶颈资源；入口能承受的请求数、应用线程数、数据库连接数和下游容量并不相等，不能把前面的高吞吐误当作整个链路的高吞吐。

Why: 为什么不能靠“加机器”“开更多线程”硬扛？——因为很多瓶颈根本不在线性扩容路径上：数据库写能力、热点行锁、下游第三方 API 配额、缓存回源、网络排队都可能先达到上限；更多线程还会把等待放大成更长队列。 [分布式架构: 端到端容量由最短板决定，不是前端容量简单外推] [JVM: 线程池和队列把流量问题转成等待时间与内存占用]

比喻锚点: 流量治理像商场消防限流——楼外排队并不代表收银台、试衣间和电梯都能无限接人；真正重要的是别让最窄的通道先被踩塌。 [写作时展开]

### 2. 限流算法 — 你不是在选“最强算法”，而是在选怎样约束突发与精度

场景提示: 面试或线上讨论里常把固定窗口、滑动窗口、漏桶、令牌桶排成优劣榜，但真实问题其实是：你要限制平均速率、平滑输出、还是允许短时突发。 [写作时展开]

关键设计: 四类常见算法控制的对象不同：

```[pseudocode]
固定窗口:
  一个时间窗一个计数器
  到窗边界清零
  优点: 简单
  风险: 窗口交界处可能出现双倍突刺

滑动窗口:
  大窗切成多个小桶
  统计最近一段时间的总量
  优点: 比固定窗口更平滑
  代价: 需要维护多个桶/时间片

漏桶:
  请求先进入桶/队列
  按稳定速率流出
  优点: 输出平滑, 适合保护下游
  风险: 到达长期高于流出时, 等待或丢弃不可避免

令牌桶:
  以稳定速率产出令牌
  请求拿到令牌才放行
  优点: 允许在令牌积累后短时突发
  风险: 令牌配置不当会把突发压给下游
```

关键设计: 固定窗口的问题不在于“算法错了”，而在于它只知道本窗口，不知道窗口边界前后的连续性；滑动窗口通过分桶降低边界突刺，但桶越细，统计与内存成本越高。像 Sentinel 这类实现常用环形桶维护 pass/block/rt/exception 等统计，核心是降低统计更新和读取成本，而不是把“滑动窗口”神化成绝对最优。

Why: 为什么不能说“令牌桶一定优于漏桶”或“滑动窗口一定最精确”？——因为不同算法在保护目标、突发容忍度、时延分布、实现复杂度和分布式一致性成本上都不一样；允许突发的令牌桶更适合入口吸收抖动，追求稳定输出的漏桶更适合贴近受保护资源。 [分布式架构: 限流算法的好坏依赖放置位置与被保护对象] [系统性能: 平均速率、突发峰值、排队时延不是同一个指标]

比喻锚点: 固定窗口像按整点放行的闸机，滑动窗口像持续滚动统计客流，漏桶像只有固定出水口的水箱，令牌桶像先发号再入场。 [写作时展开]

### 3. 限流规则落地 — 从资源、入口到分布式计数，重点是限哪里而不是只会配阈值

场景提示: 读者常见困惑不是不会背算法，而是“规则配上去了，为什么有时对某接口生效、有时只对某入口生效、重启后规则又丢了”。 [写作时展开]

关键设计: 限流落地要先定义“被保护的资源”以及“从哪个维度统计”：

```[pseudocode]
Resource:
  一个方法、一个接口、一个下游调用、一个热点参数维度

Entry:
  请求进入资源
  → 经过统计链与规则链
  → 通过则继续执行
  → 被拦截则走 block handler / fallback

常见规则维度:
  直接:
    当前资源自己到阈值就限自己
  关联:
    关联资源繁忙时, 当前资源主动让路
  链路:
    同一资源从不同入口进入, 配不同阈值
```

关键设计: 资源模型、统计链和规则链把“算法”变成“调用链中的判断点”；像 Sentinel 这类实现会把统计、流控、降级等规则串在责任链里，便于在同一个资源入口上同时叠加 pass/block/rt/exception 的判断。

关键设计: 单机计数器和分布式限流不是一回事。单机限流只对本实例视角成立；一旦多实例部署，是否需要“每实例独立预算”还是“全局共享预算”，会直接决定实现方式：
- 每实例限流适合先做粗糙削峰，配置简单，但总量会随实例数变化。
- 分布式共享限流需要借助 Redis、网关或集中式控制面做全局计数与配额分配，但必须处理时钟漂移、网络分区、存储故障、热点 key 和计数误差。
- 控制台下发规则若只保存在应用内存，实例重启后会丢失；生产环境通常需要配置中心或持久化存储来保存规则状态。

Why: 为什么“把 Redis 计数器一加”不等于分布式全局限流？——因为你不仅在做计数，还在做全局时间窗、一致性、失败恢复和性能折中；网关故障、Redis 抖动或跨机房延迟都会改变限流的真实行为。 [分布式架构: 全局限流要面对一致性与可用性的权衡] [网络: 远程计数把本地 O(1) 判断变成一次网络往返]

比喻锚点: 资源和规则像城市交通管制——有的是路口本地红绿灯，有的是全城车牌限行；同样是“限车”，单路口计数和全城总量控制不是一套系统。 [写作时展开]

### 4. 熔断与降级 — 下游已经不健康时，重点不是继续赌成功，而是停止放大故障

场景提示: 服务 A 调 B，B 再调 C；如果 C 响应变慢，A 和 B 往往会一起堆满线程池。很多系统不是死于错误率高，而是死于所有请求都在等待“也许下一个会成功”。 [写作时展开]

关键设计: 熔断和降级处理的是不同问题：熔断负责在异常或慢调用达到阈值后主动断链，降级负责给被断掉的请求一个可以接受的退路。

```[pseudocode]
熔断器状态机:
  closed:
    正常放行并统计慢调用/异常比例/异常数
  open:
    直接拒绝, 不再把请求送给不健康下游
  half-open:
    放少量探测请求
      成功 → 回到 closed
      失败 → 回到 open

降级策略:
  读降级 → 缓存/默认值/空结果
  写降级 → 异步落队列/延迟处理/稍后补偿
  功能降级 → 暂时关闭非核心链路
```

关键设计: 慢调用比例、异常比例、异常数这类熔断条件本质上都依赖时间窗与最小样本量；如果统计窗口过短、样本太少，系统会对偶发抖动过敏；如果窗口过长，又会对真实故障反应太慢。具体实现的窗口大小、最小请求数、熔断时长是实现参数，不应被写成所有系统通用的定律。

关键设计: blockHandler、fallback、默认值、缓存回退都属于“失败后怎么回复用户”的范畴，但它们和熔断触发条件不是同一层概念；熔断是是否还要继续尝试访问下游，降级是既然不继续访问，下一个返回方案是什么。

Why: 为什么熔断不等于降级？——因为熔断解决“要不要继续打这个下游”，降级解决“这次不打了，用户看到什么”；把两者混写，会导致系统既没有及时断链，也没有准备可接受的回退路径。 [分布式架构: 断路器控制失败传播，降级控制用户感知] [JVM: 慢调用不及时切断会把线程和连接长期占住]

比喻锚点: 熔断像电路里的断路器，检测到短路就先切断电源；降级像停电后的应急灯，不解决供电问题，但让人不至于立刻陷入黑暗。 [写作时展开]

### 5. 隔离、超时与重试 — 故障真正可怕的不是一次失败，而是失败被无限传播和放大

场景提示: 某个接口因为慢查询变慢，结果整个服务所有接口都开始超时；或者下游抖一下，上游统一开启三次重试，最终把对方彻底打垮。 [写作时展开]

关键设计: 隔离决定故障能传播多远，超时决定等待能持续多久，重试决定失败后是否再次施压：

```[pseudocode]
隔离:
  线程池隔离
    不同依赖/接口用不同执行资源
    好处: 故障边界清晰
    代价: 线程切换、队列和内存成本更高

  信号量隔离
    限制同时进入的请求数
    好处: 轻量
    代价: 不解决已占用线程的等待问题

超时预算:
  总 deadline
    → 拆给上游/中间层/下游
    → 越往下游预算越短
    → 不能每一层都各等一遍完整超时

重试:
  只对适合重试的失败做有限重试
  → 退避
  → 抖动
  → 限制重试比例
  → 避免和排队、熔断、全链路超时互相打架
```

关键设计: 线程池隔离和信号量隔离并不是谁先进谁落后，而是分别在“独立执行资源”和“并发许可控制”两个层面划边界；有些场景需要独立线程池隔离某个高风险依赖，有些场景只需要用信号量限制同时进入的数量。线程池、连接池、队列和 Semaphore 也不能混为一谈：它们都能形成背压，但控制的资源对象不同。

关键设计: 超时应当以端到端 deadline 为中心，而不是每一跳都随意配置一个看起来“合理”的固定值；否则上层早就不需要结果了，下层还在继续执行、占着连接和线程。重试也必须和幂等性、失败类型、限流和熔断策略一起设计，否则最容易形成重试风暴。

Why: 为什么很多系统不是被原始故障打垮，而是被自己的重试和排队打垮？——因为额外重试会把失败请求重新复制一遍，队列会把短时故障拖成长时间积压，而过长超时会让无效等待持续占据资源。 [分布式架构: 恢复策略设计错误会把局部抖动放大成系统性雪崩] [JVM: 线程池、Future 和队列把失败表现成大量等待线程]

比喻锚点: 隔离像船舱舱壁，漏水时先限制进水范围；超时像氧气瓶倒计时，必须知道还值不值得继续潜；重试像二次敲门，敲得太急只会把对方已经卡住的门彻底撞坏。 [写作时展开]

### 6. 收束

把流量治理放回一条完整调用链，可以看到它不是单个组件的功能，而是一组协作边界：

```[pseudocode]
入口限流:
  控制总体来水量, 防止瞬时峰值直接压到核心资源

应用层限流:
  按资源/调用方/热点维度做细粒度配额控制

熔断:
  下游不健康时主动断链, 避免继续占用资源

降级:
  断链后给出缓存/默认值/延迟处理等兜底方案

隔离 + 超时 + 重试:
  限制爆炸半径, 控制等待时长, 约束恢复节奏
```

**Aha Moment**: "高并发系统的稳定性不是来自把每个请求都处理完，而是来自**明确哪些请求该立即拒绝、哪些可以等待、哪些需要降级、哪些必须停止重试**。"
**回答读者三问**: ①限流是在限制能力吗=不是, 它是在保护真正的瓶颈资源; ②熔断和降级差在哪=前者决定还要不要打下游, 后者决定不打后怎么回复; ③为什么重试会把系统打崩=因为它会复制失败流量, 与排队和超时一起放大过载。
