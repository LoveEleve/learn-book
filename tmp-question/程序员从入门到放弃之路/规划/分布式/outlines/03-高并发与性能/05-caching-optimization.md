# 缓存优化 — Redis 把读请求挡住之后，为什么数据库仍会被打穿

### 1. 缓存边界 — 每一份副本都在用一致性换延迟

场景提示: 订单接口加上 Redis 后读取很快，但用户刚完成支付，订单状态仍显示“待支付”；与此同时，热点 key 过期又让大量请求一起回到数据库。 [写作时展开]

关键设计: 缓存把昂贵的读取路径复制到更靠近请求的位置，用内存空间和副本管理换取更短的访问路径，但副本天然可能落后于源数据：

```[pseudocode]
请求读取:
  浏览器/客户端缓存
    → CDN/边缘缓存
    → 反向代理缓存
    → 进程内本地缓存
    → Redis 等分布式缓存
    → 数据库/源服务

命中:
  在更靠前的层返回

未命中或失效:
  继续向后访问
  → 读取源数据
  → 按一致性策略回种副本
```

关键设计: 缓存层越靠近用户，通常越能减少网络和源站压力，但副本数量、失效传播路径和一致性成本也会增加。浏览器、CDN、Nginx、本地 Caffeine/HashMap、Redis 并不是“越多越好”的固定五层，而是可按数据类型和故障目标组合的不同缓存位置；域 2 已覆盖 Redis 集群、哨兵和分片，本篇聚焦读路径、淘汰、一致性与失效保护。

关键设计: 不是所有数据都适合缓存。实时性和正确性要求很高的数据可能需要读主库或专门的一致性方案；体积大但访问稀疏的数据可能不值得占用热缓存；变化频繁且写入压力大的计数器会带来频繁失效和更新成本。

Why: 为什么缓存不能被当作数据库的“透明加速器”？——因为它引入了独立的容量上限、淘汰决策、失效时序和故障恢复路径；从 CAP/BASE 的视角看，缓存副本往往是在可用性、分区容忍和读延迟与强一致之间做业务选择，而不是免费获得更高吞吐。 [分布式架构: 缓存是副本，副本就必须定义新鲜度和失效语义] [网络: 越靠近用户的缓存越能减少回源距离，但也增加失效传播层次]

比喻锚点: 多级缓存像城市周边的仓储网络——家门口的小仓库最快，但库存最少、补货最复杂；中央仓库更完整，却需要更长运输路径。 [写作时展开]

### 2. 本地缓存淘汰 — Caffeine 为什么要防止一次扫描污染整个缓存

场景提示: 本地缓存容量没明显增加，但从 Guava Cache 切换到 Caffeine 后命中率改善；问题不是“缓存能不能存”，而是一次性访问的大量冷数据是否会把真正热点挤出去。 [写作时展开]

关键设计: 只按最近访问淘汰的 LRU 很容易受到扫描污染：一次全表扫描会让大量只访问一次的数据短暂变成“最近使用”，挤掉长期热点；频率信息可以帮助淘汰策略区分偶尔访问和反复访问。

```[pseudocode]
W-TinyLFU:
  新进入的数据
    → 先进入 Window 区

  Window 满
    → 选择候选者与 Main 区受害者比较访问频率
    → 候选者更有价值? 晋升
    → 否则淘汰候选者

频率统计:
  多组哈希映射到计数器
  → 用较少空间估计访问频率
  → 只用于淘汰决策, 不作为业务事实
```

关键设计: W-TinyLFU 将新数据的短期机会和长期频率分开处理，目标是降低扫描污染；Count-Min Sketch 以概率型、近似的频率统计节省空间，估计值可能偏高，但用于“谁更值得留下”时通常比维护精确访问表更划算。它不是业务计数器，也不能拿来表达精确访问次数。

Why: 为什么不直接维护每个 key 的精确频率？——因为精确统计会增加内存、更新和并发维护成本，而淘汰只需要相对排序；近似统计把资源留给缓存数据本身，用可接受的误差换取更好的空间效率。 [算法: Count-Min Sketch 的误差边界适合淘汰判断，不适合精确报表] [JVM: 本地缓存的命中率提升仍受堆内存、GC、对象大小和 workload 影响]

比喻锚点: LRU 像只看“谁刚刚进过店”，W-TinyLFU 像同时看“谁刚进过”和“谁经常来”；一次旅游团经过，不应立刻赶走每天都来的老顾客。 [写作时展开]

### 3. Cache-Aside — 缓存和数据库怎样协作才不会互相覆盖

场景提示: 面试题常问“先删缓存还是先写数据库”，但线上真正危险的是并发读写交错：一个线程正在从数据库回种旧值，另一个线程已经完成了更新和失效。 [写作时展开]

关键设计: Cache-Aside 把缓存当作旁路副本，应用显式负责读 miss 的回种，以及写操作后的失效：

```[pseudocode]
读:
  查缓存
  命中 → 返回
  未命中 → 查数据库
          → 按策略写入缓存
          → 返回

写:
  更新数据库
  → 删除缓存
  → 后续读 miss 时重新加载
```

关键设计: “更新数据库后删除缓存”通常比“更新数据库后直接更新缓存”更容易保持简单边界：删除是幂等动作，不需要在缓存层复制完整的写入并发逻辑；直接更新缓存则可能出现多个写者乱序覆盖。但删除并不自动等于强一致，读回种、删除失败、消息延迟和多级缓存都会留下窗口。

关键设计: 典型竞态是：读线程先 miss，写线程完成数据库更新并删除缓存，读线程随后把此前读到的旧值回种。可以使用重试删除、消息/CDC 驱动失效、版本号或读主库等方式缩小窗口，但每种方式都有延迟、吞吐、可靠投递和恢复成本；不能把“延迟双删”写成绝对保证。

关键设计: 一致性策略要服从业务语义：强一致读取可能绕过缓存访问主库或使用带版本校验的方案；允许最终一致的内容可以通过 CDC、消息和 TTL 修复；弱一致内容可以接受短期旧值，但必须明确用户可见边界。

Why: 为什么常见答案不是“缓存更新”和“数据库更新”二选一？——因为真正的问题是副本更新顺序、并发读回种、失效消息可靠性和业务可接受的新鲜度；缓存只提供性能路径，数据库或其他权威存储仍应承担业务事实的最终归属。 [分布式架构: 副本同步只能定义一致性边界，不能凭一个删除动作消除所有并发窗口] [数据库: 写入提交时序与读路由决定用户看到哪一版数据]

比喻锚点: 数据库像总账，缓存像柜台旁的便签；改账时先撕掉便签通常比同时改两本账更简单，但撕便签和重新贴便签之间仍可能有人看到旧信息。 [写作时展开]

### 4. 穿透、击穿与雪崩 — 缓存失效时，先判断是哪一种空

场景提示: 线上发现数据库请求突然暴增，不能只说“缓存失效了”；是请求的数据根本不存在、一个热点 key 失效，还是大量 key 同时失效，防线完全不同。 [写作时展开]

关键设计: 三类问题的共同结果是“请求回到了源站”，但根因和保护对象不同：

```[pseudocode]
穿透:
  请求的数据不存在
  → 每次都 miss
  → 反复访问数据库
  防线:
    布隆过滤器先挡确定不存在的 key
    缓存空值并设置合适的短 TTL

击穿:
  一个热点 key 失效
  → 大量请求同时加载同一份数据
  防线:
    分布式锁或 SingleFlight 合并加载
    逻辑过期 + 后台刷新
    配合限流和超时保护源站

雪崩:
  大量 key 在相近时间失效
  → 大量回源同时发生
  防线:
    TTL 加随机扰动, 分散失效时间
    多级缓存/旧值兜底
    限流、熔断和分批刷新
```

关键设计: 布隆过滤器的“否”可以用来排除不存在的 key，但“是”只代表可能存在，仍需回源或查询更准确的索引；空值缓存可以降低重复穿透，但需要控制容量、TTL 和恶意 key 造成的占用。

关键设计: 击穿的关键是把并发加载合并，而不是简单地把 TTL 设得很长；分布式锁要处理持有者崩溃、锁超时、重复加载和回源失败，SingleFlight 更适合在同一进程内合并请求，跨实例时不能假设它自动具有全局效果。逻辑过期允许读到旧值换取稳定，但必须明确刷新失败后的旧值上限。

关键设计: 雪崩的随机 TTL 只是在时间上离散化，不能替代源站保护；如果缓存集群故障、网络分区或批量刷新任务同时运行，仍可能发生大规模回源，因此要和限流、熔断、多级兜底及分批恢复一起设计。

Why: 为什么“三个经典问题”不能共用一个固定答案？——穿透是不存在的数据反复进入源站，击穿是单个热点的并发加载，雪崩是大量副本同时失效；它们分别需要过滤、合并和离散化，错误匹配方案只会增加复杂度而不减少回源。 [分布式架构: 故障分类决定防线位置，不能把所有回源都归结为缓存容量不足] [系统性能: 回源峰值、锁等待和刷新队列会把缓存问题转成新的排队问题]

比喻锚点: 穿透像不断问仓库不存在的货号，击穿像一件爆款只剩一个取货员，雪崩像所有分店同时停电；三种拥堵的入口不同，处理方式也不同。 [写作时展开]

### 5. 多级缓存与热点 — 本地、Redis、消息和 TTL 怎样形成一条可恢复的读链路

场景提示: 你把 Caffeine 放在 L1、Redis 放在 L2，读延迟和源站压力都下降了；但一次更新发生时，L2 已经变了，某些实例的 L1 仍保留旧值，热点 key 又可能把单个 Redis 节点压满。 [写作时展开]

关键设计: 多级缓存必须同时设计读路径、更新路径、过期路径和故障路径：

```[pseudocode]
读:
  查 L1 本地缓存
  miss → 查 L2 Redis
  miss → 查数据库/源服务
        → 回种 L2
        → 回种 L1

更新:
  源数据提交
  → 删除或更新 L2
  → 发布失效/更新消息
  → 各实例处理 L1
  → TTL 与对账任务作为兜底

故障:
  L2 不可用或热点过载
  → 旧 L1/本地兜底?
  → 限流/降级?
  → 是否允许回源?
```

关键设计: Caffeine 的容量上限、写后过期、访问后过期和异步刷新表达的是不同策略：过期会让读请求 miss，刷新可以在后台尝试更新并在条件允许时继续返回旧值；具体效果取决于刷新执行器、加载耗时、对象大小和访问模式，不能用固定延迟替代验证。

关键设计: 缓存更新可以组合推、拉和定时三种方式：消息或 CDC 推送变化并广播本地失效，TTL 让没有收到消息的副本最终淘汰，周期性刷新或对账修复丢消息、消费失败和人工操作造成的偏差。消息更新 L2 后，L1 异步失效并不等于瞬时一致；必须定义消息积压、重复消费、乱序和实例重启后的恢复行为。

关键设计: 热点 key 的处理可沿“发现 → 分散 → 缓存”展开：先通过访问统计找出热点，再用多副本、请求合并或本地短 TTL 分摊单 key 压力；但拆分 key 会增加更新和读取组合复杂度，热点检测本身也要考虑采样、延迟和统计开销。

Why: 为什么两级缓存不是“L1 快、L2 稳”的简单叠加？——因为每增加一层就增加一份副本和一条失效路径；真正的系统设计必须回答更新消息丢了怎么办、L1 旧值能留多久、L2 挂了是否回源、热点是否被分散以及恢复时如何避免二次洪峰。 [分布式架构: 多级副本需要明确传播、重放、对账和回切语义] [JVM: L1 的对象数量、刷新线程和堆压力会成为新的性能边界]

比喻锚点: L1 是每家门店的货架，L2 是区域仓库，数据库是总仓；广播是补货通知，TTL 是过期盘点，对账是库存审计，任何一条链路失灵都不能让所有门店同时冲向总仓。 [写作时展开]

### 6. 收束

缓存的完整价值链不是“命中就快”这么简单，而是要同时管理命中、未命中、更新、过期和故障：

```[pseudocode]
缓存收益:
  用空间与副本管理换取更短读路径

缓存代价:
  淘汰、旧值、失效竞态、容量上限和故障恢复

稳定读链路:
  命中 → 快速返回
  miss → 合并回源
  更新 → 可靠失效/刷新
  故障 → 旧值/降级/限流/受控回源
```

**Aha Moment**: "缓存优化的核心不是把命中率推到最高，而是**让命中时足够快、失效时不击穿、更新时说得清允许多旧、故障时不把源站当最后一个无限容量的缓存**。"
**回答读者三问**: ①缓存为什么会带来旧数据=它保存的是独立副本，副本必须经过失效或更新才能追上源数据; ②穿透、击穿、雪崩怎么区分=不存在的数据、单个热点失效、大量副本同时失效; ③两级缓存最难的地方是什么=不是多放一层，而是定义 L1/L2 的更新、失效、故障和恢复顺序。
