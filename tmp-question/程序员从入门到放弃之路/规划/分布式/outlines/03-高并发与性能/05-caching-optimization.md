# 1万QPS的读请求打到DB — 加一层Redis就万事大吉了吗?

> Cluster B: 10 KPs | 依赖: 域1-01/02(CAP/BASE), 域2-04(分布式缓存架构) | 读者基线: 用过Redis缓存, 遭遇过缓存穿透/击穿/雪崩

---

### 1. 缓存不是魔法 — 你加的每一层都在引入新问题
  你给接口加了Redis缓存, RT从200ms降到2ms — 但用户投诉"明明下单了, 查订单状态还是待支付"。
  - 缓存本质: 用空间(内存)换时间(磁盘/网络)+用延迟(最终一致)换吞吐 — 存储"副本"就意味着"副本可能过时" (B5 Ch10 §10.1, B6 Ch6 §6.1)
  - 五层缓存架构: 浏览器缓存(Cache-Control, ETag)→CDN缓存(边缘节点)→反向代理缓存(Nginx proxy_cache)→本地缓存(Caffeine/HashMap)→分布式缓存(Redis) — 离用户越近越快, 一致性越难保证 (B5 Ch10 §10.2-10.5, B3 Ch10 §10.6)
  - 域2引用: 域2-04已讲Redis集群/哨兵/分片架构 — 域3聚焦缓存性能优化与一致性 (B2 Ch2 §2.4)
  - 关键设计: 不是所有数据都适合缓存 — 实时性要求高(库存)、数据量大但访问少(历史日志)、数据变化频繁写入压力大(计数器)不应缓存

### 2. W-TinyLFU — Caffeine凭什么比Guava Cache快?
  你从Guava Cache切到Caffeine, 内存占用差不多但命中率高了 — 发生了什么?
  - Guava的LRU缺陷: 只记录"最近用过", 无法区分"用过1次的冷数据"和"用过1000次的热数据" — 一次全表扫描把整个缓存冲掉 (B2 Ch2 §2.3.2)
  - W-TinyLFU: Window(1%空间暂存新数据)+Main(99%空间用TinyLFU频率统计) — 新数据先过Window, 频率超过Main里的受害者才晋升 (B2 Ch2 §2.3.2)
  - Count-Min Sketch: 概率型频率统计算法 — 4bit计数器×多组哈希 — 节省内存但有微小误差(只为淘汰决策, 可以接受) [理论: Count-Min Sketch用O(k)空间存储频率估计 — point query总是高估, 低估概率为0, 适合"最不常用=淘汰"场景]
  - 关键设计: W-TinyLFU解决了LRU的"扫描污染" — 扫描大量一次性的数据不会把热点数据从缓存中挤出去

### 3. 缓存一致性 — 你删缓存先还是写数据库先?
  面试官: "先删缓存再写DB, 或者先写DB再删缓存, 哪个对?" — 你说都可以, 面试官追问: "什么情况下都不对?"
  - Cache-Aside: 读(先查缓存, miss则查DB回种)→写(更新DB→删缓存) — 最通用模式, 适合读多写少 (B6 Ch6 §6.2)
  - 为什么是"删"不是"更新"? — 删缓存是幂等的, 更新缓存有并发覆盖风险(写1更新→写2更新→写2被写1覆盖)
  - 并发不一致: 先写DB后删缓存 — 线程A读miss→线程B写DB+删缓存→线程A回种旧数据 → 概率极低(缓存miss窗口极窄)但理论上存在 [工程: 延迟双删 → 写DB→删缓存→sleep(等读线程回种)→再删一次; 或CDC → 监听MySQL Binlog→MQ→删缓存, 保证最终一致]
  - 关键设计: 强一致场景不用缓存(读主库), 最终一致场景用CDC方案, 弱一致场景用过期TTL兜底

### 4. 缓存穿透/击穿/雪崩 — 三个"经典问题"各自的根因
  你面试背过这三个概念, 但线上同时出现了 — 你怎么判断当前是哪个问题?
  - 穿透(数据不存在): 查一个永远不存在的数据→每次穿透到DB, 缓存形同虚设 → 布隆过滤器(判断"一定不存在")+缓存空值(短TTL 60s) (B2 Ch2 §2.4.3, B6 Ch6 §6.9.2)
  - 击穿(热点key过期): 热点数据过期→瞬间大量请求打到DB → 分布式锁(第一个去加载)→SingleFlight(合并请求)→逻辑过期(不设过期, 异步刷新) [案例: 千万粉丝博主的首页 — 缓存击穿→每秒百万请求→DB瞬间炸→方案: 永不过期+后台异步刷新]
  - 雪崩(大量key同时过期): 几十个热点缓存同一时刻过期 → 过期时间加随机扰动(如3600+random(0,300)), 多级缓存降级(本地Caffeine兜底), 限流熔断 (B2 Ch2 §2.4.4, B6 Ch6 §6.9.4)
  - 关键设计: 三个问题的本质区别 — 穿透(数据不存在, 需要过滤), 击穿(数据存在但缓存空了, 需要锁), 雪崩(大量数据同时空, 需要离散化)

### 5. 多级缓存实战 — 本地+Redis两级怎么协同?
  你设计了Caffeine(L1)+Redis(L2)两级缓存, Caffeine命中=0.5ms, Redis=2ms, DB=100ms。
  - 缓存更新策略: 推(Canal监听到变化→MQ→广播更新本地缓存)+拉(TTL过期自然淘汰)+定时(每X分钟全量刷新) — 三者组合 (B5 Ch10 §10.7, B1 Ch3 §3.3)
  - Caffeine配置要点: maximumSize(上限)→expireAfterWrite/expireAfterAccess→refreshAfterWrite(异步刷新, 不阻塞读) — refresh比expire好的地方: 后台刷新, 读到旧值≠读miss穿透 (B2 Ch2 §2.3)
  - 热点缓存处理: 热点发现(统计QPS TopN key)→多副本(热点key分10份, key_0~key_9散列)→本地短TTL缓存(1-3s)分摊读压力 (B2 Ch2 §2.4, B6 Ch6 §6.9.1)
  - 关键设计: 两级缓存一致性 — 消息更新L2→L1异步失效(本地TTL短)+全量兜底(Binlog对账每5min)

### 6. 收束 — 缓存是高并发读的法宝, 也是高并发问题的源泉
  - 缓存将O(DB-IO)变成O(memory), 代价是引入了"数据可能不同"这一根本问题
  - 从CAP视角看缓存: 缓存=AP(可用+分区容忍)→数据最终一致(BASE) → 这就是域1理论的落地
  - 没有银弹: 不同业务(金融/社交/电商)对一致性要求不同 → 选不同的缓存架构
