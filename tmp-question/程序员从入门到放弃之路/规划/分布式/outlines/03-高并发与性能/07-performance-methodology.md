# 性能方法论 — 系统偶发变慢时，怎样从猜测走到证据

> Cluster C: 9 KPs | 依赖: 06-database-concurrency、01-分布式理论/01-cap-theorem | 读者基线: 遇到过线上性能问题，但常常只能凭经验猜测哪里慢
> 读者处境: 缓存、分片、锁和线程池都已经调过，系统却仍然会偶发性抖动；读者通常知道 CPU、RT、慢 SQL 这些词，却不知道该先看哪一个、怎样把现象一路追到原因
> 打开新视角: 性能优化的核心不是“马上去改代码”，而是**先建立指标、再定位排队点、最后用证据验证假设**；工具只是放大镜，方法论才决定你会不会看错方向

### 叙事顺序

1. 问题引入——线上偶发变慢时，为什么“拍脑袋猜数据库慢”常常会越修越错
2. 定义与测量——性能问题到底是什么，为什么先要定义 SLO 和排队点
3. USE 与 RED——机器资源视角和服务体验视角怎样互补
4. 工具链——CPU、Off-CPU、内存和线程栈怎样把猜测变成证据
5. 压测——如何找到拐点、退化方式和线上不可见的风险
6. 全链路观测——Trace、Metrics、Logs 怎样串成一次完整下钻
7. 收束——性能优化不是一次技巧，而是一轮轮假设与验证

### 1. 先测量，再优化 — 性能问题本质上是需求在某处形成排队

场景提示: 接口响应时间偶尔飙高，团队第一反应是“加索引”“扩线程池”“换序列化库”，但改完之后问题要么没变，要么换了一个地方继续慢。 [写作时展开]

关键设计: 性能问题不是抽象的“代码写得不好”，而是资源供给和请求需求在某个环节不匹配，最终表现为等待、排队、超时、错误率上升或吞吐不再增长：

```[pseudocode]
请求到达
  → 消耗 CPU/内存/磁盘/网络/连接/锁/下游配额
  → 某资源供给不足
       → 队列增长
       → 等待时间变长
       → RT 上升 / timeout / error
       → 上游重试或堆积
```

关键设计: 在动手优化前，必须先定义“什么叫慢”。同一个接口在后台批处理、用户交互、内部链路和第三方回调里，对 RT、吞吐、错误率和新鲜度的容忍完全不同；没有目标，就无法判断优化是否真的有效。

关键设计: Little's Law 可以把外部看到的吞吐、响应时间和系统内平均并发联系起来，但它描述的是稳定条件下的平均关系，不是瞬时毛刺、长尾延迟或多级队列的万能解释器。它适合帮助读者建立“RT 上升往往意味着系统里堆了更多未完成请求”的直觉，而不是替代追踪与采样。

```[pseudocode]
性能优化循环:
  Plan:
    定义 SLO / 关键指标 / 假设瓶颈
  Do:
    监控、压测、采样、抓取证据
  Check:
    对比结果与假设是否一致
  Act:
    若假设错误则重建分析
    若假设正确则做有针对性的优化
```

关键设计: 常见反模式不是“少用了某个工具”，而是破坏了问题定义和验证闭环：
- 把性能问题拖到项目结束才处理
- 没有基线就开始优化
- 测量环境、数据或流量模型与线上不一致
- 只比较平均值，不看长尾和错误率
- 还没定位瓶颈就做低级代码优化
- 只看单个接口，不看共享资源和下游
- 只看 CPU，不看等待、队列和 I/O
- 只修复表面症状，不追踪根因
- 只做一次压测，不验证峰值后的退化与恢复
- 优化后不复测、不对比，也不持续观察回归

Why: 为什么“先测量再优化”不是一句空话？——因为没有基线就分不清问题是偶发、持续还是只出现在峰值；没有假设就会把工具输出当成噪声；没有验证就不知道优化是否只是把瓶颈从一个队列移到另一个队列。 [系统性能: 端到端延迟是多级队列叠加结果，不是单个函数耗时的简单总和] [分布式架构: 上游重试、下游限流和网络抖动都可能把局部问题放大成全链路慢]

比喻锚点: 性能排查像医院分诊——先知道病人哪里不舒服、什么指标异常，再决定做血检、拍片还是手术；不能一进门就直接开刀。 [写作时展开]

### 2. USE 与 RED — 一套看资源，一套看用户感知

场景提示: 服务 RT 升高时，有时是 CPU 打满，有时是线程在等锁、等磁盘、等网络；如果只盯着一类图表，很容易把“机器没满”误判成“服务没问题”。 [写作时展开]

关键设计: USE 和 RED 分别回答两类问题：资源出了什么状况，以及用户/调用方究竟感受到了什么：

```[pseudocode]
USE:
  Utilization 资源使用情况
  Saturation  队列/等待是否堆积
  Errors      资源本身是否出错

RED:
  Rate        请求量/吞吐
  Errors      错误率/失败数
  Duration    延迟, 尤其长尾
```

关键设计: USE 更适合回答“CPU、磁盘、网络、连接池、线程池是不是已经被占满或排队”，RED 更适合回答“业务请求有没有变慢、变少或变错”。两者不是替代关系：CPU 正常不代表没有问题，因为线程可能在等锁、等 I/O、等下游；RT 高也不自动说明服务本机有问题，因为瓶颈可能在依赖项。

关键设计: RED 看长尾比只看平均值更重要。平均 RT 可能稳定，但少量请求的排队、GC、冷数据回源、锁等待和网络重传会把 P95/P99 拉高；如果只看平均值，最影响用户体验的抖动会被掩盖。

Why: 为什么 USE 和 RED 要一起看？——因为一套指标只告诉你“资源是否忙”，另一套指标才告诉你“忙这件事有没有让用户受伤”；只有把二者对上，才能区分是资源饱和、依赖异常，还是请求模型本身变了。 [系统性能: 平均值容易掩盖长尾问题] [网络: 丢包、重传和下游抖动常常通过 RED 暴露，再回到 USE 查资源等待]

比喻锚点: USE 像看厨房后场——灶台、冰箱、传菜口是否拥堵；RED 像看前厅——来了多少客人、上菜有多慢、退单有多少。只看厨房或只看前厅，都解释不完整。 [写作时展开]

### 3. 定位工具链 — 先找到慢在哪一类时间，再去找哪一行代码

场景提示: 团队常说“看火焰图就行”，但 CPU 不高时火焰图可能什么都看不出来；也有人一看到线程栈就怀疑死锁，结果只是正常阻塞。 [写作时展开]

关键设计: 工具链要围绕“线程时间花在哪里”展开，而不是围绕某个工具品牌展开：

```[pseudocode]
CPU 高:
  先定位进程
  → 再定位热点线程
  → 再关联线程栈/方法热点
  → 判断是业务循环、序列化、锁竞争还是 GC/JIT 等开销

CPU 不高但 RT 高:
  看 Off-CPU / 锁等待 / I/O 等待 / 网络等待
  → 判断线程是在工作还是在等资源

内存异常:
  看堆使用趋势、分代回收、对象分布、GC Roots
  → 判断是正常缓存、对象堆积、泄漏还是回收跟不上
```

关键设计: 对 Java 服务，常见路径是先用系统级工具确定进程和线程，再结合 JVM 线程栈、采样和堆信息判断热点；例如用 `top` 看进程，再用 `top -Hp` 找线程，最后把线程标识关联到 `jstack` 的栈信息。这里的重点不是机械背命令，而是先区分“CPU 正在忙”还是“线程正在等”。

关键设计: CPU 采样可以沿 `perf record` → `perf script` → FlameGraph 的路径展开，火焰图适合观察 CPU 热点；Off-CPU 视角适合观察锁等待、阻塞 I/O、网络等待和 park 状态。看到宽平台不等于它就是唯一根因，它可能只是某个更上层队列的受害者；采样频率、时长、环境权限和负载代表性都会影响结果，不能把一次采样当作绝对真相。

关键设计: 内存排查不能只看“堆大不大”。可以用 `jmap` 获取堆信息，再通过 MAT 的 Dominator Tree 和 Path to GC Roots 分析大对象与持有链；大对象、缓存膨胀、引用链没释放、队列堆积、线程局部对象未清理，都可能让堆看起来一直高。抓取 dump 的目标，是找出“谁还持有它”，而不是只找“哪个对象最大”。

Why: 为什么定位工具链必须先分类时间？——因为 CPU 时间、等待时间和 GC/内存压力的优化方向完全不同；如果把等待误当成 CPU 热点，或者把缓存常驻误当成泄漏，优化动作不仅无效，还可能制造新问题。 [JVM: 线程栈、堆、GC 与 JIT 共同决定 Java 服务的热点表现] [系统性能: 采样与追踪工具看到的是不同维度的时间，不应互相替代]

比喻锚点: 工具链像刑侦流程——先判断是案发现场正在打斗，还是门口排长队，还是仓库货物堆积；不同案情要找不同证据，不能所有案件都先做指纹。 [写作时展开]

### 4. 压测 — 不是证明系统“能跑多快”，而是找出它从哪里开始不优雅

场景提示: 预发环境压测看起来很好，上线后在大促和长时间运行场景仍然崩；问题往往不在“压没压”，而在“压得像不像真实系统”。 [写作时展开]

关键设计: 不同压测回答不同问题：

```[pseudocode]
基准测试:
  看单组件/单场景的基本性能特征

负载测试:
  逐步增加压力
  → 找吞吐与延迟的拐点

压力测试:
  超过正常容量
  → 看系统如何拒绝、排队、限流和恢复

稳定性测试:
  持续运行
  → 看内存、连接、日志、GC、线程是否累积问题
```

关键设计: 压测结果最有价值的不是一个漂亮的 QPS 数字，而是“在什么流量形态下，哪个指标开始不可接受，以及系统会以什么方式退化”。有的系统吞吐还能增长，但长尾 RT 已经不可用；有的系统平均指标还行，但错误率和重试开始放大。

关键设计: 单接口压测、冷启动压测、小数据集压测、无思考时间压测都可能与线上差异巨大。真实系统还有缓存预热、JIT 预热、连接池状态、数据分布、热点 key、下游限流、网络抖动和共享资源竞争；如果这些没有进入模型，压测就更像“测工具”而不是“测系统”。

关键设计: 全链路压测并不总是必须，但当容量受限于接入层、缓存、数据库、MQ、第三方服务或网关规则时，只测单个接口无法识别瓶颈在何处；而全链路压测本身也有环境隔离、数据污染、流量标记和回滚保护要求。

Why: 为什么压测不能只问“能不能到某个 QPS”？——因为系统容量从来不是单点数字，而是一组随流量形态、数据分布和依赖状态变化的边界；真正有价值的是知道它从哪里开始变坏，以及坏掉时是否可控。 [分布式架构: 峰值流量会暴露跨组件瓶颈与退化路径] [系统性能: 拐点前后的 RT、错误率和队列变化比单一吞吐值更重要]

比喻锚点: 压测像演练商场疏散——不是看平时能进多少人，而是看人一多时电梯、楼梯、收银台和出口会先堵哪，堵住后会不会踩踏。 [写作时展开]

### 5. 全链路观测 — 从告警到 Trace，再到日志和代码，才算真正定位完成

场景提示: 用户说“下单很慢”，日志只显示 Controller 正常返回；如果没有请求级上下文，团队只能在数据库、缓存、MQ 和下游服务之间来回猜。 [写作时展开]

关键设计: 一次完整定位通常需要把聚合指标、请求轨迹和事件明细串成一条链：

```[pseudocode]
告警触发:
  看到 Rate / Error / Duration 异常
  → 找到受影响时间窗与服务范围
  → 打开对应 Trace
  → 看哪一段耗时明显异常
  → 用日志/线程栈/采样继续下钻
  → 回到代码与配置验证假设
```

关键设计: TraceID、SpanID、父子关系和时间线解决的是“这一个请求去了哪、在哪些环节停了多久”；Metrics 解决的是“这个问题影响了多少请求、持续了多久、是否已恢复”；Logging 负责保留参数、错误码、上下文和关键事件。Prometheus/Grafana 可用于指标采集与展示，ELK 可用于日志检索，SkyWalking/Jaeger 可用于分布式追踪；工具选择可以变化，但三类信号之间要能从一个入口跳到另一个入口。

关键设计: 观测系统本身也有代价。全量日志会增加 I/O 和存储，Tracing 采样率会影响覆盖度，过多标签会提高指标成本；因此要围绕关键路径、异常事件和调试需求有选择地采集，避免观测系统本身成为性能问题。

关键设计: 从监控下钻到代码并不总是线性的。一次 RT 毛刺可能先在 Metrics 上出现，再通过 Trace 发现慢在某个远程调用，然后再回到那台机器的火焰图或线程栈；也可能先从日志中的超时错误看到异常，再去补看同时间窗的指标和采样。方法论要求的是闭环，而不是固定顺序。

Why: 为什么“有监控”不等于“能定位问题”？——因为孤立的图表、日志或 Trace 只能描述一个侧面；真正能定位的是从告警开始，逐层缩小范围，最后拿到足以指导修改的证据。 [分布式架构: 请求跨服务传播时，缺少统一上下文就无法还原真实路径] [网络: 一次慢调用可能由链路、DNS、连接复用、重试或下游排队共同造成]

比喻锚点: 全链路观测像机场行李追踪——Metrics 告诉你今天丢了多少件，Trace 告诉你这件行李经过了哪些传送带，日志告诉你在哪个节点被拦下以及原因。三者缺一，就只能继续猜。 [写作时展开]

### 6. 收束

性能优化应回到一条稳定的工作流，而不是某个流行工具：

```[pseudocode]
定义目标:
  SLO / 用户体验 / 关键业务指标

发现异常:
  RED 看服务影响
  USE 看资源状态

定位原因:
  线程 / 采样 / GC / Trace / 日志 / SQL / 队列

验证与修复:
  压测或回放验证假设
  → 修改
  → 再观测是否真正改善
```

**Aha Moment**: "性能问题最难的部分不是怎么优化，而是**先分清它到底是 CPU 在忙、线程在等、内存在堆、依赖在慢，还是系统只是被错误的流量模型击中了**。"
**回答读者三问**: ①为什么不能凭经验直接改代码=因为没有证据时，最常见的结果是把瓶颈从一个地方搬到另一个地方; ②USE 和 RED 分别看什么=前者看资源是否饱和与出错，后者看服务是否让用户变慢和变错; ③压测和线上监控怎么配合=压测负责找边界与退化模式，线上监控负责发现真实异常并验证优化是否生效。
