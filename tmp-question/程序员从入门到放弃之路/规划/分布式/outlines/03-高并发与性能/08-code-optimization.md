# 代码优化 — 已经定位到热点之后，怎样真正让系统做更少的事

> Cluster C: 8 KPs | 依赖: 07-performance-methodology | 读者基线: 能读懂 Java 代码，知道 GC、序列化和网络 I/O，但缺少系统化的代码级优化方法
> 读者处境: 上一篇已经告诉读者如何从指标、采样和 Trace 中找到瓶颈，现在真正困难的是：哪些修改是在减少工作，哪些只是把成本从 CPU 挪到内存、从延迟挪到复杂度
> 打开新视角: 代码优化不等于“换个更快的 API”，而是**先减少不必要的工作，再减少做这件事的次数，最后才是把剩下的工作做得更便宜**

### 叙事顺序

1. 问题引入——已经知道哪里慢了，为什么直接“换个快库”常常只能局部变快
2. 减少工作——少做、少争抢，比把同样的事做快更有效
3. 零拷贝——数据路径里哪些复制和上下文切换是可以删掉的
4. 对象池——分配和回收是否真的值得换成复用
5. 批量与异步——怎样减少网络往返、提交次数和同步等待
6. 预热与序列化——为什么第一次慢，以及编码格式怎样影响 CPU 与带宽
7. 收束——代码优化是一笔资源账，而不是若干孤立技巧

### 1. 减少工作与竞争 — 最好的优化经常是少做一次、少抢一次

场景提示: 火焰图显示热点在 JSON 序列化、计数器 CAS 和列表遍历上；如果只盯着“哪个库更快”，很容易忽略根本问题是字段传多了、操作做多了或共享状态竞争过于集中。 [写作时展开]

关键设计: 优化通常可以沿三层顺序思考：先减少工作，再减少次数，最后减少单次开销。

```[pseudocode]
减少工作:
  不读取、不计算、不序列化、不发送不需要的数据

减少次数:
  批量代替逐条
  合并请求代替重复查询
  缓存或复用代替重复构造

减少单次开销:
  更合适的数据结构、编码方式或算法
```

关键设计: “减少并发冲突”也属于减少工作。把所有线程都逼到一个共享变量上做 CAS，会让 CPU 时间花在竞争和重试上；如果能让线程处理自己的数据分区、使用线程私有副本，或把热点更新分散到多个槽位，系统做的无效竞争就会减少。

关键设计: ThreadLocal、按分片并行再汇总、LongAdder 这类方案，本质上都在减少对单个共享点的争抢：
- ThreadLocal 适合线程内可复用、无须跨线程共享的状态。
- 数据分片适合把大任务拆成彼此独立的子区间，再做最终汇总。
- LongAdder 把高并发累加分摊到多个槽位，读时再汇总，降低单一 AtomicLong 上的竞争。

关键设计: LongAdder 并不总优于 AtomicLong。高竞争写入下，分散热点通常更有优势；低竞争、频繁读取、要求精确瞬时值或内存更敏感的场景，AtomicLong 可能更直接。LongAdder 的 `sum()` 也不是一个全局冻结点，不应误写成精确原子快照。

Why: 为什么代码优化的第一步不是“把一段代码写得更快”？——因为真正昂贵的通常不是那几条指令，而是根本不该发生的重复计算、重复序列化、无效 CAS、自旋竞争和共享状态争抢。 [JVM: CAS、自旋、对象分配和缓存行竞争都会把看似简单的代码放大成热点] [系统性能: 减少工作量往往比微调单条指令更能改变端到端延迟]

比喻锚点: 代码优化像搬家——最省力的做法不是练出更强的臂力，而是先扔掉不必搬的箱子，再把零散物品装箱，最后才考虑怎么走得更快。 [写作时展开]

### 2. 零拷贝 — 数据搬运慢，不一定是磁盘慢，而可能是路径太绕

场景提示: 文件下载、日志传输或消息发送的热点不在业务逻辑，而在“数据从哪拷到哪”；读者常把“零拷贝”理解成完全没有复制，但系统里仍然可能发生 DMA、页缓存和协议栈相关的数据移动。 [写作时展开]

关键设计: 传统 I/O 路径往往让数据多次跨越内核态与用户态边界，并伴随上下文切换：

```[pseudocode]
传统路径:
  磁盘/设备 → 内核缓冲区
  → 用户缓冲区
  → Socket 缓冲区
  → 网卡/设备

优化路径:
  尽量绕过用户态中转
  或减少 CPU 参与的数据复制
```

关键设计: `sendfile` 类接口的价值通常在于减少用户态参与和 CPU 拷贝，而不是把所有数据移动都神奇消除；DMA 仍然可能存在，协议栈和网卡发送也仍要工作。它更适合“文件内容基本不用改、只是尽快发出去”的场景。

关键设计: `mmap + write` 把页映射到用户空间，适合需要在发送前查看或修改数据的场景，但它并不天然优于 `sendfile`；映射生命周期、页错误、地址空间占用和脏页管理也都是代价。Kafka 这类系统常利用页缓存与 `sendfile` 一类能力减少用户态中转，从而提升吞吐，但收益依赖工作负载、操作系统和网络栈实现。

Why: 为什么零拷贝不该被理解成“零成本传输”？——因为它优化的是数据路径中的部分复制和上下文切换，而不是消灭磁盘、页缓存、网络协议或校验的全部成本；如果应用层必须解密、压缩、过滤或改写数据，绕过用户态的空间反而会变小。 [内核: DMA、页缓存、系统调用与上下文切换共同构成 I/O 路径成本] [网络: 发送路径是否需要重组、加密或协议编码，会改变零拷贝可用性]

比喻锚点: 零拷贝像把货物直接从仓库传送带送到装车口，而不是先卸到办公室地上再搬回去；省下的是人工倒手，不是卡车和路程本身。 [写作时展开]

### 3. 对象池与分配 — 复用对象之前，先确认你真的在为分配付费

场景提示: 服务高峰期 GC 频繁，读者第一反应往往是“把对象都池化”；但对象池本身会增加借还协议、并发访问、清理责任和内存滞留。 [写作时展开]

关键设计: 对象创建的成本不只在 `new` 这一行，还包括初始化、逃逸、缓存局部性、生命周期管理和后续 GC 回收；如果大量短命对象快速进入年轻代，系统可能在吞吐和停顿上付出代价。

```[pseudocode]
对象池收益来自:
  降低昂贵对象的重复创建成本
  减少部分 GC 压力

对象池代价来自:
  借还协议
  状态重置
  池内常驻内存
  借还竞争
  误用导致脏数据/泄漏
```

关键设计: 像 Netty `Recycler` 这类实现，会把 `FastThreadLocal`、线程内栈式缓存以及跨线程归还队列（如 `WeakOrderQueue` 一类机制）组合起来，尽量减少对象复用时的共享竞争；但这类设计成立的前提，是对象的状态重置、生命周期和线程语义都能被严格约束。池化不是“只要频繁 new 就值得做”。

关键设计: 对象池要和 JIT 的逃逸分析、标量替换和栈上分配一起看。某些小对象若不逃逸出方法或线程上下文，JIT 可能已经把其分配成本压得很低；这时手动池化反而可能增加代码复杂度和内存滞留。真正适合池化的通常是创建昂贵、体积较大、构造成本高或底层资源稀缺的对象，如连接、大缓冲区、编解码器状态等。

Why: 为什么“频繁 new 对象”不自动等于“应该对象池化”？——因为分配成本、逃逸行为、GC 策略、对象大小和线程访问模式会共同决定真实开销；池化只是在某些约束下把分配成本换成协议复杂度和常驻内存。 [JVM: TLAB、逃逸分析、年轻代回收和栈上分配会改变对象创建的真实成本] [系统性能: 池化优化的是总成本，不是某一行 `new` 的表面时间]

比喻锚点: 对象池像共享工具柜——重型设备值得借还登记，小螺丝刀人人都去领再归还，管理成本可能比直接买新的还高。 [写作时展开]

### 4. 批量与异步 — 让系统少走几次来回路，比每次走快一点更重要

场景提示: 一条条写数据库、一条条发 Redis、一条条远程调用时，热点常常不在业务判断，而在网络往返、事务提交、fsync 和同步等待。 [写作时展开]

关键设计: 批量优化的是“次数”，异步优化的是“等待位置”，二者可以结合，但不是一回事：

```[pseudocode]
批量:
  多个同类操作合并后一次发送/一次提交
  → 减少 RTT、协议开销、提交次数

异步:
  请求先返回或先入队
  → 真实处理在后续阶段完成
  → 把等待从主路径挪走
```

关键设计: JDBC 批量、`rewriteBatchedStatements` 一类能力、Redis Pipeline、批量日志写入，本质上都在减少网络往返和协议封装次数；收益大小取决于数据量、批次大小、驱动行为、事务边界和错误处理策略。批得过大又可能带来长事务、内存峰值、锁持有时间和单次失败回滚成本。

关键设计: Redis Pipeline 不是事务，也不是自动保证所有命令独立成功；它减少的是网络 RTT，不改变命令语义。MQ 削峰则是把生产速度和消费速度解耦，让消费者按自己的节奏处理，但代价是引入队列堆积、重试、顺序、幂等和可见性延迟。

关键设计: 异步不等于“更快完成”，只是让调用方更早摆脱同步等待；如果异步链路仍被同一个数据库、线程池或下游容量限制，系统只是把排队位置后移。批量与异步结合得好，能减少 RTT 与主路径等待；结合得不好，则会把毛刺变成批量洪峰。

Why: 为什么批量与异步看起来都能提吞吐，却不能混成一个概念？——因为批量靠的是空间聚合，异步靠的是时间重排；一个减少请求次数，一个改变等待位置。混淆它们会让读者误把“用户更早收到响应”当成“系统实际做完得更快”。 [数据库: 批量提交会改变事务范围、锁持续时间和失败回滚代价] [分布式架构: MQ 让削峰成为可能，也让幂等、顺序和补偿成为新问题]

比喻锚点: 批量像把零散包裹装成整车再发，异步像先给顾客发取件号、货物稍后出库；一个少跑几趟，一个把等待从柜台移到仓库。 [写作时展开]

### 5. 预热与序列化 — 很多“第一次慢”不是故障，而是系统还没进入热态

场景提示: 服务刚启动时延迟偏高，热点代码还没编译、缓存还没填满、连接池还没准备好；另一些接口则在稳定运行中长期被 JSON 编解码拖慢。 [写作时展开]

关键设计: 预热的目的不是制造“假流量”，而是让 JIT、缓存、连接池、元数据和下游依赖在正式承压前进入较稳定状态：

```[pseudocode]
启动阶段:
  热点代码未编译
  缓存未命中
  连接尚未建立
  常用数据未加载

预热路径:
  回放代表性请求
  预填热点缓存
  建立连接/线程/对象池
  达到稳定状态后再接入正式流量
```

关键设计: JIT 预热、缓存预热和连接池预热各自解决不同问题。JIT 预热面向热点方法编译与分层优化，缓存预热面向冷启动回源洪峰，连接池预热面向第一次连接建立和认证成本；像 HikariCP 这类连接池常通过 `minimumIdle` 等配置提前准备部分连接，但是否立即创建、创建多少以及是否适合预热，仍取决于连接池实现、初始化策略和真实流量模型。预热对象、流量样本和接入时机都要接近真实工作负载，否则容易把错误路径也一并“预热”。

关键设计: 序列化优化通常沿三条路展开：减少字段、选择更合适的编码格式、减少重复编解码。JSON、Protobuf、Kryo 等方式没有跨场景绝对优劣：JSON 调试友好、兼容广，Protobuf 更强调紧凑和 schema，Kryo 更偏向特定语言生态；最终选择取决于跨语言需求、演进成本、对象图复杂度、安全限制和 CPU/带宽权衡。

关键设计: 序列化层的“更快”有时只是把成本转移到兼容性或可观测性上。例如字段裁剪减少了 CPU 与带宽，却要求上下游协商更严格的契约；二进制协议可能更紧凑，却降低了问题排查时的可读性。优化应与上一章的方法论闭环验证，而不是只看微基准分数。

Why: 为什么“第一次慢”和“序列化慢”不能靠一个参数统一解决？——因为前者通常是系统尚未热身，后者更多是编码路径长期消耗 CPU 与带宽；一个侧重运行时状态进入稳定区，一个侧重协议与字段设计。 [JVM: JIT 编译、类加载和连接建立会决定冷启动热态过程] [网络: 编码格式直接影响报文大小、带宽占用和下游解析成本]

比喻锚点: 预热像餐厅开门前先把灶台点热、食材备好；序列化优化像决定菜单写得多详细、菜品装多大盒子。前者解决开门第一波手忙脚乱，后者决定后续每单出餐有多费劲。 [写作时展开]

### 6. 收束

代码级优化可以回到一张统一的资源账上理解：

```[pseudocode]
减少工作:
  少算、少传、少争抢、少分配

重组工作:
  批量、异步、分片、局部复用

降低单次成本:
  更短的数据路径
  更合适的编码格式
  更少的对象生命周期压力
```

**Aha Moment**: "代码优化最有效的部分，不是把同一段逻辑榨出最后几条指令，而是**看清哪些工作根本不必做、哪些竞争本来可以分散、哪些等待只是被放错了位置**。"
**回答读者三问**: ①为什么少做比做快更重要=因为重复计算、重复序列化和无效竞争经常比单次执行速度更贵; ②对象池什么时候值得用=当对象创建或底层资源真正昂贵，且生命周期、状态重置和借还边界可控时; ③批量和异步差在哪=批量减少次数，异步改变等待位置，二者可以配合但不是同一种优化。
