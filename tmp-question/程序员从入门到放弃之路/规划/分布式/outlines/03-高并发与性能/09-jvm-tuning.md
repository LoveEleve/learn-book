# JVM 调优 — 代码已经更省了，为什么 GC、堆外内存和 JIT 仍会制造毛刺

> Cluster C: 8 KPs | 依赖: 08-code-optimization | 读者基线: 配过 `-Xmx`、`-Xms` 一类参数，看过 GC 日志，但还不清楚应该根据什么现象调什么
> 读者处境: 代码热点已经通过上一章优化过，但线上仍会出现 Young GC 频繁、直接内存告警、启动后前一段时间偏慢，或者某次去优化导致 P99 抖动

### 1. GC 不是敌人 — 它是在用运行时成本换内存安全与可管理性

场景提示: 读者看到 GC 停顿就 instinctively 把问题归咎于 JVM，但如果没有 GC，内存回收错误、悬空引用和生命周期管理本身也会成为更大的系统风险。 [写作时展开]

关键设计: GC 的核心价值不是“让内存免费”，而是把对象生命周期管理从业务代码中抽离出来，用额外的 CPU、内存布局和停顿控制换取更高的内存安全性与开发效率。

```[pseudocode]
没有 GC:
  业务代码负责申请/释放内存
  → 容易出现忘记释放、过早释放、重复释放

有 GC:
  运行时追踪可达对象
  → 回收不再可达的对象
  → 代价转化为扫描、复制、标记、整理与屏障开销
```

关键设计: 分代收集背后的直觉来自弱分代假说、强分代假说和跨代引用较少的经验规律：很多对象会很快死亡，活得越久的对象越可能继续存活，而跨代引用虽然存在，但通常不是所有对象都高度互相指向。这里的“假说”是工作负载经验，不是每个应用的数学公理；缓存、对象池和长生命周期集合会显著改变对象分布。

关键设计: JVM 调优经常落在吞吐、延迟和内存占用三者的张力上：更大的堆可能减少回收频率，却增加某些阶段的扫描与整理成本；更激进的并发收集可以降低停顿，却可能带来更多 CPU 与元数据开销。不存在对所有服务同时最优的固定组合。

Why: 为什么要先把 GC 看成“成本交换”而不是“纯副作用”？——因为只有承认 GC 在替你管理对象生命周期，读者才会去思考：是对象分配模式不合理、堆配置不匹配，还是收集器目标和业务 SLO 不一致，而不是一看到停顿就盲目加大堆或关闭某些机制。 [JVM: 标记、复制、整理、屏障和 root 扫描共同构成 GC 成本] [系统性能: GC 毛刺通常是对象分配模式、内存规模和延迟目标冲突后的表现]

比喻锚点: GC 像写字楼的保洁和物业系统——它不是免费服务，会占用人力和时间；但如果完全没有保洁，垃圾和安全问题会更早让整栋楼无法使用。 [写作时展开]

### 2. GC 选型 — 不是选“最先进”的收集器，而是选与你的目标一致的账本

场景提示: 同一套业务在 JDK 版本升级后默认 GC 可能变化，团队常把“默认值”误当成“最佳值”；实际上批处理、后台任务、低延迟 API 和超大堆服务关心的指标并不相同。 [写作时展开]

关键设计: 常见 GC 的差异，首先体现在它们把成本放在哪：

```[pseudocode]
Serial:
  简单, 单线程回收
  适合小规模、低资源场景

Parallel:
  更强调吞吐
  允许用停顿换总处理量

G1:
  把堆切成 Region
  尝试在可预测停顿与吞吐之间平衡

ZGC:
  更强调低停顿
  用并发阶段、屏障和额外元数据降低停顿时间
```

关键设计: G1 的关键不是“新默认所以一定更好”，而是 Region 化堆布局、年轻代与 Mixed GC 的组合，以及基于历史信息去逼近停顿目标。像 `-XX:MaxGCPauseMillis` 这样的目标参数，表达的是 JVM 试图靠 Region 选择和回收节奏去接近的停顿预算，而不是对每次停顿的硬保证；它通过选择一部分回收收益较高的 Region 来控制单次回收工作量，但是否接近目标仍取决于对象分布、存活率、分配速度和应用线程压力。

关键设计: ZGC 依赖并发标记、重定位及染色指针/读屏障一类机制来降低停顿，但这类机制也带来额外的元数据与运行时开销。对超低延迟敏感的服务，它可能非常有价值；对 CPU 紧张或业务不要求极低毛刺的服务，收益未必大于成本。CMS 则属于某些旧版本 JVM 的重要低延迟路线，但要注意版本演进和弃用边界，不能把老版本经验直接套到新版本默认行为上。

关键设计: 选型必须和 JDK 版本、业务目标以及运行环境一起讨论。默认 GC、生产可用性、实验状态、停顿目标和堆规模边界都与版本强相关；任何“某 GC 永远最好”或“某 GC 一定只适合大堆”的说法都过于绝对。

Why: 为什么 GC 选型不能只看“谁停顿更短”？——因为更低停顿通常意味着更多并发工作、更多 CPU 占用或更复杂的元数据路径；如果服务真正关心的是吞吐、成本或资源稳定性，仅看最短停顿会把问题简化错。 [JVM: G1 的 Region/Mixed GC 与 ZGC 的屏障/并发迁移代表不同账本] [系统性能: 低停顿、低 CPU 与低内存占用通常不能同时极致]

比喻锚点: GC 选型像选交通工具——高速列车、地铁、货车和摩托车各有优势；看起来最快的工具，不一定适合你要运的货、走的路和付得起的成本。 [写作时展开]

### 3. 堆与直接内存 — 参数不是魔法按钮，而是在分配不同的风险预算

场景提示: 服务把 `-Xms` 设得很小、`-Xmx` 设得很大，启动时看起来省内存，但运行中堆逐渐扩张；另一边，堆还没满却出现了直接内存告警或 OOM。 [写作时展开]

关键设计: `-Xms` 和 `-Xmx` 决定了堆初始规模与上限。把两者设为相同，常见目的不是“玄学更快”，而是减少运行时动态扩缩堆带来的不确定性；但是否相等、设多大，仍要看容器限制、同机部署、峰谷差异和预留空间。

```[pseudocode]
堆配置关注点:
  初始堆太小
    → 预热期扩张, 行为波动更大
  堆上限过大
    → 回收扫描与停顿风险可能放大
  新生代/老年代比例不匹配
    → 短命对象或长命对象分布失衡
```

关键设计: 新生代、老年代比例与对象年龄分布密切相关。短生命周期请求型服务通常更关注 Eden 与 Survivor 行为，长生命周期缓存/会话则更容易把对象推向老年代；但这些都要结合 GC 日志和对象分布看，不能把某个比例当作所有 I/O 密集或计算密集服务的固定答案。

关键设计: 直接内存不在 Java 堆里，却会影响总进程内存和 OOM 行为。NIO、Netty、文件传输和大量连接场景都可能更多依赖堆外缓冲；`MaxDirectMemorySize`、Cleaner/引用处理、对象生命周期与本地库行为会一起决定直接内存是否成为问题。堆够大不代表整个进程就安全。

关键设计: 排查堆外内存时，`jcmd VM.native_memory detail` 这类入口可以帮助观察 Native Memory Tracking 视角下的内存分类，定位增长更像出现在堆外缓冲、线程、代码缓存还是其他本地分配；但前提是相关能力已按环境要求启用，且你理解输出展示的是归因线索，不是自动根因。

关键设计: NMT（Native Memory Tracking）之类能力的价值，在于把堆内、堆外、线程栈、代码缓存、元空间等内存放到一张图里看。它比只看 `jmap` 更全面，但也有额外开销和粒度限制；是否长期开启要结合环境目标评估。

Why: 为什么 JVM 内存问题不能只盯着堆使用率？——因为真正把进程压垮的，可能是直接内存、线程栈、元空间或本地库分配；而真正让停顿变差的，也可能是对象年龄分布、堆扩张过程或老年代压力，而不仅是“堆看起来用了多少”。 [JVM: 堆、堆外、元空间和代码缓存共同构成进程内存账本] [系统性能: 参数配置改变的是风险分布，不是凭空消灭内存成本]

比喻锚点: JVM 内存像企业预算——堆是最显眼的总预算项，但真正让公司出问题的，也可能是隐藏在其他科目里的长期租约、外包费用和备用金消耗。 [写作时展开]

### 4. JIT 与去优化 — 代码为什么会越跑越快，也会偶尔突然变慢

场景提示: 服务启动后前一段时间延迟更高，跑稳之后明显改善；另一些毛刺则出现在系统运行很久以后，像是某条原本很快的路径突然变慢。 [写作时展开]

关键设计: HotSpot 并不是一上来就把所有代码编译到最高优化级别，而是在解释执行、C1、C2 以及分层编译之间逐步收集运行时信息，再对热点路径做更激进的优化。

```[pseudocode]
执行路径:
  初始阶段更多依赖解释执行或较轻编译
  → 收集 profiling 信息
  → 热点方法升级到更高优化层级
  → 运行稳定后热点代码成本下降
```

关键设计: C1 更强调快速编译与较低启动成本，C2 更强调基于 profiling 的深度优化。方法内联、逃逸分析、锁消除、标量替换和循环优化，都是让“越跑越快”成为可能的核心机制；但前提是热点稳定、分支行为可预测、对象逃逸模式明确。

关键设计: 去优化（Deoptimization）说明 JIT 的优化不是静态真理，而是基于过去观测做出的假设。当分支分布、类型形态、类加载或内联前提被打破时，JVM 可能回退到解释执行或较低层级重新编译，这就是某些偶发 RT 毛刺的来源之一。不能把所有抖动都怪到 GC 上。

Why: 为什么 JIT 会让同一段代码表现出“热了之后更快，偶尔又突然回退”的现象？——因为它不是一次性编译，而是在持续根据运行时行为下注；下注正确时能换来极高收益，下注失效时就要回退和重建假设。 [JVM: 分层编译、profiling 与去优化共同构成热点代码的生命周期] [系统性能: 冷启动与长稳态的延迟形态不同，不能用同一组样本解释]

比喻锚点: JIT 像经验丰富的厨师——先按通用流程做，观察顾客口味后逐步简化动作；但如果突然来了一批完全不同口味的顾客，原来的预判就得撤回重做。 [写作时展开]

### 5. GC 日志与在线诊断 — 没有证据的 JVM 调优，通常只是参数试错

场景提示: 线上 GC 频繁、内存飙高或线程异常时，团队最容易做的事是直接改参数重启；但如果不知道回收类型、触发原因、内存变化和线程热点，重启只是在抹掉现场。 [写作时展开]

关键设计: GC 日志至少要回答几类问题：什么时候发生、发生了哪类回收、回收前后内存怎样变化、停顿持续多久、为什么触发、是否频繁晋升或出现大对象/Humongous 压力。日志格式会随 JDK 版本变化，但“时间、类型、前后内存、总量、耗时、原因”这些观察维度是稳定的。

```[pseudocode]
GC 诊断问题单:
  时间窗是什么?
  Young / Mixed / Full / Concurrent 哪类回收异常?
  回收后是否真正释放内存?
  晋升是否过快?
  是否出现大对象、碎片或分配失败?
```

关键设计: GCEasy、gcviewer 一类工具适合把 GC 日志转成趋势图，帮助回答“回收是否异常频繁”“停顿是否超预算”“老年代是否持续抬升”。它们给的是解释辅助，不是自动处方；最终仍要回到业务分配模式、对象生命周期和参数配置上判断。

关键设计: Arthas 之类在线工具的价值，在于不重启 JVM 就能查看线程、方法调用、参数和局部热点。`dashboard`、`thread`、`trace`、`watch` 这些命令分别对应系统概览、热点线程、调用耗时链路和运行时观测，但线上使用也要控制采样范围与持续时间，避免诊断本身制造额外负担。

关键设计: Arthas 背后依赖 Attach API、Java Agent/Instrumentation 以及字节码增强能力，这解释了它为什么能在目标 JVM 上热插拔观察点，也解释了为什么某些环境对 attach 权限、容器隔离和安全策略更敏感。

Why: 为什么 JVM 调优必须先看日志和在线证据，而不是先改参数？——因为同样表现为“GC 频繁”或“内存上涨”的现象，可能来自短命对象风暴、缓存常驻、直接内存泄漏、晋升过快、配置过小或去优化叠加；没有证据就无法判断该调对象、调参数，还是调业务行为。 [JVM: GC 日志、NMT、线程视图与字节码观察点是不同层次的证据] [系统性能: 重启会暂时掩盖现场，但不会解释毛刺真正来自哪里]

比喻锚点: JVM 诊断像飞机故障排查——黑匣子、仪表盘、机组通话和发动机检测各看一个侧面；只看其中一个，就很容易把真正的问题错判成别的部件。 [写作时展开]

### 6. 收束

JVM 调优不是一张参数速查表，而是一条从现象回到运行时账本的路径：

```[pseudocode]
现象:
  GC 毛刺 / OOM / 冷启动慢 / P99 抖动

定位:
  看 GC 日志、线程、堆外内存、JIT 热点、在线诊断

判断:
  是对象分配模式、内存配置、收集器目标、直接内存还是去优化问题

修复:
  调整对象生命周期、GC 选型、堆与堆外参数、预热与观测策略
```

**Aha Moment**: "JVM 调优真正要做的，不是把参数调成某个流行模板，而是**搞清楚运行时到底在为哪一种业务行为买单：分配太快、对象活太久、堆外用太猛，还是热点代码的假设突然失效**。"
**回答读者三问**: ①GC 为什么不是单纯坏事=它是在用运行时成本换取对象生命周期管理与内存安全; ②为什么不能只盯默认 GC 或某个流行参数=因为 JDK 版本、业务目标、堆规模和延迟预算都会改变最合适的选择; ③线上 JVM 问题先看什么=先保留日志和运行时证据，再区分是 GC、内存区域、JIT 还是直接内存导致的毛刺。
