# 1亿条订单里查"我的订单" — MySQL怎么不快也不崩?

> Cluster B: 9 KPs | 依赖: 域2-06(存储架构) | 读者基线: 写过SQL, 知道索引和慢查询, 数据量到千万级时遇到瓶颈

---

### 1. 单库单表的极限 — 什么时候必须拆分?
  你的订单表从100万涨到5000万, SELECT带时间范围走索引但还是超2秒 — 加索引无效了?
  - 单表性能拐点: 500万(B+Tree 3层)→5000万(4层)→5亿(5层) — 层数增加=每次查询多一次磁盘IO=RT翻倍 (B5 Ch9 §9.3, B1 Ch4 §4.1)
  - 读写分离: 主写从读, 1主N从 — 从库数据有延迟(主从同步) → 问题: 刚写入查不到? 方案: 写后立即读走主库, 非关键读走从库 (B2 Ch2 §2.2, B3 Ch10 §10.4)
  - 垂直拆分: 订单主表(频繁更新)+订单详情表(大字段, 较少查) — 减少行宽度, 一个数据页能放更多行 → 减少IO (B2 Ch2 §2.6, B1 Ch4 §4.1)
  - 关键设计: 读写分离+垂直拆分是"延迟拆分" — 能扛10x~50x, 但到了1亿级必须上水平拆分

### 2. 水平分库分表 — 1亿数据拆成256个表, 怎么路由?
  你决定按用户ID取模分16库每库16表=256个分片 — 那按订单号查怎么办?
  - 拆分方式: 按范围(M_00: ID 1-1000W)+按哈希(MD5(user_id)%256) — 哈希均匀但扩容困难, 范围容易扩容但热点不均 (B1 Ch4 §4.1, B2 Ch2 §2.6) [理论: 分库分表的CAP视角 — 单库ACID→分库BASE妥协，跨分片JOIN=在分区下无法保持强一致]
  - 基因法解决跨维度查询: order_id = Snowflake(用户ID后6位+时间戳+序号) → 用order_id也能反推分片 — 但只能解决一对一映射 (B1 Ch4 §4.1, B2 Ch2 §2.6)
  - 扩容方案: 停服扩容(简单粗暴, 不可接受)→双写(新老同时写, 迁移老数据)→一致性哈希(增加虚拟节点, 减少迁移量) [工程: ShardingSphere — 配置分片规则(sharding.yaml)→路由引擎→改写SQL→执行→结果归并 — 对应用透明]
  - 关键设计: 分片键选择第一原则 — 大部分查询的单表维度是什么? 订单系统90%查询带user_id, 用user_id分片; 管理后台查所有订单走ES搜索

### 3. 分布式ID生成 — 为什么Snowflake的时钟回拨能让你丢数据?
  你用Snowflake生成订单号, 某天运维调了服务器时钟 — 然后订单被覆盖了?
  - Snowflake: timestamp(41bit,69年)+workerId(10bit,1024节点)+sequence(12bit,4096/ms) — 趋势递增, 不依赖DB (B2 Ch4 §4.3)
  - 时钟回拨: NTP同步导致时间倒退→同一个毫秒内sequence重复→ID冲突 → 方案1: 等(阻塞到时钟追上, 美团Leaf-snowflake方案), 方案2: 扩展位(用扩展位记回拨次数), 方案3: 提前(回拨前记录"最后生成时间"不准倒退) (B2 Ch4 §4.3)
  - Leaf方案: 号段模式(TinyID, 从DB批量拿号段, 用完再拿)→可设置步长(step=1000, 拿一次用1000次) — 号段用完时从DB拿需要等DB (B2 Ch4 §4.5)
  - 关键设计: 为什么不用UUID? — 非递增, 插入B+Tree随机位置→页分裂→碎片→性能差; 趋势递增ID顺序插入是InnoDB最优写入模式

### 4. 乐观锁 vs 悲观锁 — 扣库存你用哪个?
  100万人抢100件商品 — 你用SELECT FOR UPDATE一锁一个准, 但QPS只有几百。
  - 乐观锁: UPDATE stock SET count=count-1 WHERE id=1 AND count>0 → 行锁极短只有UPDATE瞬间 → 但大量回滚(>0失败) (B1 Ch5 §5.3, B6 Ch8 §8.3)
  - 悲观锁: SELECT...FOR UPDATE→扣减→UPDATE→COMMIT → 行锁从SELECT到COMMIT → 只有1个线程扣, 其他等待 → QPS极低 (B6 Ch8 §8.3)
  - 乐观锁+重试: UPDATE失败→重试(最多3次)→还失败返回"已抢光" — 短事务+重试>长事务等待 [案例: 秒杀扣库存三层优化 — L1: 内存Redis标记(商品被抢光, 直接拒绝99.99%的请求)→L2: Redis DECR库存(预扣, 毫秒级)→L3: DB乐观锁最终落盘(异步, 保证正确)]
  - 关键设计: 为什么不在Redis扣然后不写DB? — Redis挂了, 超卖不可恢复; DB是source of truth, Redis是性能层

### 5. 死锁 — 两个事务互相等锁, 你的订单系统莫名其妙假死
  监控看到数据库连接打满, 所有活跃事务都在"waiting for lock" — 谁锁了谁?
  - 死锁四条件: 互斥+持有等待+不可剥夺+循环等待 → 破任一条即可 (B1 Ch5 §5.3, B6 Ch8 §8.2)
  - MySQL死锁检测: innodb_deadlock_detect=ON → 等待图(wait-for graph)→检测到环→回滚持有最少undo的事务→ERROR 1213 Deadlock → 应用层重试 (B1 Ch5 §5.3)
  - 避免死锁: 按固定顺序加锁(SELECT id=1 FOR UPDATE然后id=2, 所有线程一致)→降低事务粒度(拆长事务)→降低隔离级别(RC下Gap Lock不会导致死锁) (B1 Ch5 §5.3, B5 Ch9 §9.3)
  - 关键设计: 分布式系统中的死锁比单机复杂 — 涉及多个数据库实例+Redis+MQ → 需要全局超时+补偿+告警

### 6. 收束 — 数据库高并发的核心矛盾
  - 读多→读写分离+缓存, 按ID查询→分库分表
  - 写多→乐观锁+异步+MQ削峰, 热点写→分散(分桶/Redis预扣)
  - 安全vs性能: 悲观锁安全但慢, 乐观锁快但可能回滚 — 没有最优方案, 只有适合业务的折中
