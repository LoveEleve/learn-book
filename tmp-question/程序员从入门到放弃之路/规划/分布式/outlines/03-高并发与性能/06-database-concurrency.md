# 数据库并发 — 订单数据越多、抢购请求越集中，MySQL 如何不快也不崩

> Cluster B: 9 KPs | 依赖: 05-caching-optimization、02-架构与微服务/06-storage-architecture、01-分布式理论/01-cap-theorem | 读者基线: 写过 SQL，知道索引、事务和慢查询，在数据量增长或热点写入时遇到过瓶颈
> 读者处境: 缓存已经挡住了大部分读流量，但秒杀、订单状态更新和库存扣减仍然会把写请求集中到少数行、少数分片和少数数据库连接上
> 打开新视角: 数据库高并发不是单纯把 SQL 写快，而是把数据规模、路由、ID、锁、事务和失败恢复一起设计；**减少竞争比让每个竞争者更快更重要**

### 叙事顺序

1. 问题引入——订单表变大、读写变多，为什么“再加一个索引”仍不能解决所有问题
2. 单库与纵向拆分——读写分离、垂直拆分解决什么，解决不了什么
3. 水平分库分表——分片键、路由、跨维度查询与扩容迁移
4. 分布式 ID——为什么 ID 生成器会影响分片、索引写入和数据安全
5. 热点写入——乐观锁、悲观锁、Redis 预扣与数据库最终落盘怎样配合
6. 死锁与恢复——数据库如何发现锁环，应用为何需要有限重试和补偿
7. 收束——容量、竞争和正确性之间没有脱离业务的最优解

### 1. 单库边界 — 加索引之前先确认瓶颈到底是什么

场景提示: 订单表持续增长，带时间条件的查询已经使用索引，却仍然出现高延迟；同时写入、复制、连接池和大字段读取互相争抢同一套资源。 [写作时展开]

关键设计: 单库单表的瓶颈不只由数据行数决定，还取决于索引层级、缓存命中、磁盘和网络 I/O、行宽度、并发写入、锁等待以及查询是否需要扫描大量范围；不能把某个数据规模或 B+Tree 层数当作跨机器、跨存储引擎都成立的性能拐点。

```[pseudocode]
读多:
  主库写入
  → 从库承担读请求
  → 明确复制延迟
  → 写后读/强一致读路由到主库

行太宽:
  订单核心字段保留在主表
  → 大字段和低频详情垂直拆分
  → 减少单次读取的数据页与传输量

仍然受限:
  评估水平分片
  → 重新设计分片键、路由和跨片查询
```

关键设计: 读写分离把读压力分散到副本，但副本存在复制延迟；写后立即读取、需要新鲜数据的读取和允许短暂旧值的读取，必须有不同路由策略。读写分离也不会自动提升主库写能力，更不会消除热点行锁和事务竞争。

关键设计: 垂直拆分把频繁访问的核心列与大字段、低频详情分开，减少行宽和无关 I/O；代价是查询需要额外关联或多次读取，事务边界、数据归属和故障恢复也更复杂。

Why: 为什么“加索引”不是数据库扩容的统一答案？——索引只改变部分访问路径；当瓶颈转移到写放大、复制、锁等待、连接池或数据页 I/O 时，继续加索引可能增加维护成本而不解决端到端延迟。 [数据库: 查询计划、索引维护和事务锁共同决定实际代价] [系统性能: 局部 SQL 优化不能替代端到端容量分析]

比喻锚点: 单库像一座中央仓库；加索引是给货架贴更好的标签，读写分离是增设分拣窗口，垂直拆分是把大件货物搬到另一间库房，但所有货物最终仍可能争同一条装卸通道。 [写作时展开]

### 2. 水平分库分表 — 数据拆开之后，查询和扩容谁来负责

场景提示: 单库继续增长，团队决定按用户维度拆到多个库表；用户订单查询很顺利，但运营后台按订单号、时间范围和全量条件查询时，原来的单库假设全部失效。 [写作时展开]

关键设计: 水平分片的核心不是“分成多少张表”，而是为主要查询选择稳定的分片键，并让写入和读取尽量命中少量分片：

```[pseudocode]
按范围分片:
  key 落入某个连续范围
  优点: 范围查询与迁移边界直观
  风险: 数据分布不均、热点集中

按哈希分片:
  hash(key) → 分片
  优点: 通常更容易把点查分散
  风险: 范围查询困难、扩容会改变映射

请求路由:
  业务请求携带分片键
  → 路由到目标库/表
  → 改写 SQL
  → 执行
  → 必要时跨片归并
```

关键设计: 范围分片便于按时间或范围管理，也可能把最新数据和热点集中在一个分片；哈希分片通常有利于均匀分布，但改变分片数量会带来大量数据迁移和路由变化。分片键应优先由主要查询维度决定，而不是只追求理论上的均匀；如果订单大多数查询按 user_id，按 user_id 分片比只看订单号分布更符合访问路径。

关键设计: 跨维度查询可以通过让 ID 携带路由信息、维护映射表、冗余索引或把搜索职责交给专门的检索系统来处理；所谓“基因法”只能在 ID 与分片规则稳定绑定时解决特定的一对一反推，不能替代通用查询路由。

关键设计: 扩容有停服迁移、双写/增量迁移、影子读、校验切换等路径；一致性哈希或虚拟节点可以减少部分映射变化，但不能自动迁移数据、保证双写顺序或处理回滚。以 ShardingSphere 这类中间件为例，应用通常通过分片规则、路由、SQL 改写、执行和结果归并获得相对透明的分片体验，但跨片事务和跨片 JOIN 的代价仍然存在。

Why: 为什么分库分表通常意味着更弱的跨片事务语义？——因为原本由单库事务统一协调的写入，被拆到多个资源和多个故障域；跨片 JOIN、排序、聚合和一致性提交都要付出额外网络与协调成本。CAP/BASE 不是“分片后绝对不能一致”，而是提醒读者：分区和可用性约束会改变强一致方案的成本与边界。 [分布式架构: 分片把容量问题转化为路由、协调和恢复问题] [数据库: 分片键不只是存储布局，也决定事务和查询范围]

比喻锚点: 分片像把图书馆按借阅者分到多个馆；按会员号找书很快，但按书名查全城所有馆就需要广播、汇总和去重。 [写作时展开]

### 3. 分布式 ID — 一个订单号同时影响排序、路由与故障安全

场景提示: 订单号生成服务平时工作正常，时钟同步或节点故障后却出现重复、倒序或分片路由异常；ID 并不是简单的“换成 Long 就完事”。 [写作时展开]

关键设计: Snowflake 类 ID 通常将时间、节点标识和序列号组合为趋势递增标识，以减少数据库中心化生成的压力，并让写入大致保持时间局部性；具体位宽、时间跨度、节点上限和每时间单位序列容量取决于实现，不能脱离方案写成通用常数。

```[pseudocode]
生成 ID:
  now = 当前时间
  若 now < last_timestamp:
    进入回拨策略
  若 now == last_timestamp:
    sequence++
  否则:
    sequence = 起始值
  组合 timestamp + worker_id + sequence
  last_timestamp = now

回拨策略:
  等待时钟追上
  或使用额外逻辑区分回拨区间
  或拒绝生成并报警
```

关键设计: 时钟回拨的危险不只是“时间变小”，而是生成器可能重新使用已经出现过的时间区间；如果节点标识和序列空间又被复用，就可能造成 ID 冲突、排序异常或依赖 ID 唯一性的业务错误。等待、扩展逻辑、拒绝服务和切换到其他生成路径各有可用性与安全性代价。

关键设计: 号段模式把一段可用 ID 从数据库或中心服务批量领取到本地，再在本地分配，降低每个 ID 都访问中心存储的成本；号段耗尽、中心服务不可用、号段重复领取和多实例并发领取都必须有明确的租约、唯一性和告警机制。

关键设计: UUID 等随机 ID 不必然“不能用”，但在某些 B+Tree 索引写入场景中，随机插入可能增加页分裂、缓存局部性变差和维护成本；趋势递增 ID 也可能带来热点尾部、可推测性或跨机房排序语义问题。ID 方案要同时看唯一性、可排序性、隐私、路由和存储引擎行为。

Why: 为什么 ID 生成器属于数据库并发设计，而不只是工具组件？——因为 ID 的局部性影响索引写入，ID 携带的路由信息影响分片查询，时钟回拨影响正确性，中心化取号又会形成新的依赖瓶颈。 [分布式架构: 时间、节点和故障恢复共同决定全局唯一性] [数据库: 索引键分布影响页分裂、缓存局部性和写放大]

比喻锚点: 分布式 ID 像多座工厂共同发出的带时间和工厂编号的货单；编号既要不重复，还要方便找到来自哪座工厂，工厂时钟倒退时更不能重新发出旧货单号。 [写作时展开]

### 4. 热点写入 — 乐观锁、悲观锁与分层扣减怎样保护库存正确性

场景提示: 大量用户同时抢同一件商品，悲观锁让请求排队，乐观锁让大量更新失败；缓存能挡住读请求，却不能直接把数据库库存扣减变成正确的并发操作。 [写作时展开]

关键设计: 乐观锁和悲观锁是在“冲突发生前是否先占住资源”上的不同选择：

```[pseudocode]
悲观锁:
  BEGIN
  SELECT stock FOR UPDATE
  → 读取并检查库存
  → 更新库存
  → COMMIT
  其他事务等待锁释放

乐观条件更新:
  UPDATE stock
  SET count = count - 1
  WHERE id = ? AND count > 0
  → 根据影响行数判断成功/失败
  → 失败请求可有限重试或直接返回不可用
```

关键设计: 悲观锁把检查和更新放在持锁事务内，适合冲突成本高、需要明确串行化的场景，但长事务会扩大锁等待和连接占用；乐观条件更新把锁持有时间压缩到更新语句附近，冲突时由数据库拒绝不满足条件的更新，适合短事务和可接受失败/重试的场景，但高竞争下会产生大量失败尝试。

关键设计: 重试不是乐观锁的默认必选项，必须受到幂等性、总 deadline、失败原因和重试预算约束；库存已经耗尽时继续重试只会浪费数据库资源。Redis 预扣、热点商品标记和异步落库可以把大量竞争挡在数据库前，但 Redis 仍是性能层，最终库存事实、补偿和对账必须有权威存储与业务流程支撑。

```[pseudocode]
高竞争写入的分层保护:
  L1 本地/边缘快速拒绝明显无货请求
  → L2 Redis 等性能层做预扣或排队
  → L3 数据库用条件更新做最终校验和落盘
  → 异步结果按订单幂等键确认、补偿和对账
```

Why: 为什么不能只在 Redis 里扣库存而不落数据库？——因为缓存或性能层可能丢失、回滚、重复消费或与订单状态分离；只要数据库仍是业务事实的归属，就必须设计预扣与最终落盘之间的幂等、失败补偿和对账。 [数据库: 条件更新把正确性判断放进原子写路径] [分布式架构: 多层扣减需要处理消息重复、超时、回滚和最终一致]

比喻锚点: 悲观锁像把最后一件商品放进柜台后只让一个顾客验货，其他人排队；乐观锁像大家先拿取货券，到付款时由库存系统确认，失败者不用一直占着柜台。 [写作时展开]

### 5. 死锁与恢复 — 数据库能发现锁环，但业务必须决定怎样回到可用状态

场景提示: 连接池逐渐打满，监控显示大量事务在等待锁；两个事务分别拿着对方需要的锁，单纯增加连接数只会让等待队列变长。 [写作时展开]

关键设计: 经典死锁依赖互斥、持有并等待、不可剥夺和循环等待等条件；工程上通常通过统一加锁顺序、缩短事务、减少锁范围、避免不必要的交叉资源持有来降低形成环的机会，但不能假设“只要代码看起来顺序一致就永远不会死锁”。

```[pseudocode]
事务 A: 持有资源 1 → 等待资源 2
事务 B: 持有资源 2 → 等待资源 1

等待图:
  A → B
  B → A
  出现环 → 选择事务回滚

应用处理:
  捕获死锁错误
  → 释放本地状态
  → 仅对可重试、幂等的操作有限重试
  → 仍失败则返回/转补偿队列/告警
```

关键设计: MySQL/InnoDB 可以通过死锁检测和等待图发现环，并回滚某个事务解除循环；具体牺牲哪一个事务由实现的代价判断决定，不能简单写成所有版本都“回滚 undo 最少”的固定规则。应用收到死锁错误后也不能无条件重试：事务外部副作用、非幂等请求、超时预算和重试风暴都要先处理。

关键设计: 固定顺序加锁、缩小事务粒度和减少持锁期间的外部调用是常见预防手段；降低隔离级别可能改变间隙锁和冲突行为，但不是通用的“死锁开关”，必须重新验证读一致性、幻读和业务正确性。

关键设计: 分布式业务中的“死锁”还可能跨数据库、Redis、消息队列和远程服务，单个数据库的等待图看不到完整环。此时要用全局 deadline、租约、状态机、补偿和告警处理跨资源等待，不能把分布式锁或超时简单当作数据库死锁检测的替代品。

Why: 为什么死锁发生后“重试一次”不是完整方案？——数据库回滚只撤销了本次事务内的修改，应用可能已经调用外部服务、发送消息或占用其他资源；恢复必须同时考虑幂等、补偿、重复执行和全链路超时。 [数据库: 死锁检测负责打破局部锁环，不负责恢复业务副作用] [分布式架构: 跨资源故障需要状态机和补偿，而不是只靠本地事务]

比喻锚点: 死锁像两辆车分别堵住一条单车道，交通警察可以让其中一辆倒车恢复通行，但倒车后货物是否已经卸下、订单是否已经通知，还需要业务系统自己核对。 [写作时展开]

### 6. 收束

数据库高并发的设计选择可以按瓶颈类型回看：

```[pseudocode]
读多:
  缓存 + 读写分离
  → 接受并管理复制延迟

数据量大:
  垂直拆分 + 水平分片
  → 用路由和迁移复杂度换容量

写多/热点写:
  条件更新、有限重试、异步削峰、预扣与分桶
  → 把竞争分散, 保留数据库最终校验

锁冲突:
  缩短事务、统一顺序、限制等待
  → 死锁检测 + 幂等重试 + 补偿恢复
```

**Aha Moment**: "数据库高并发的核心不是找一个更快的锁或更多的分片，而是**先减少会同时争抢同一资源的请求，再让剩下的竞争在明确的事务、路由和恢复边界内完成**。"
**回答读者三问**: ①什么时候从单库走向分片=当读写、数据规模或故障边界已经超过单库可接受范围，并且能承担路由与迁移复杂度; ②乐观锁和悲观锁怎么选=看冲突率、事务时长、失败成本和一致性要求，不看抽象的快慢排名; ③死锁检测后为什么还要业务补偿=数据库只能回滚局部事务，不能自动撤销外部副作用和跨资源状态。
