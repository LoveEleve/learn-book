### 第1章：计算机系统概述

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| 冯·诺依曼结构 | 程序和数据在同一内存中，CPU按序取指→译码→执行→访存→写回 | 哈佛结构(指令/数据分离)在DSP中仍用——实时性：可同时取指和取数 |
| 程序转换四阶段 | 预处理(展开宏+include)→编译(语法树→IR→汇编)→汇编(.s→.o)→链接(多个.o+库→可执行文件) | 预处理后的.i文件比.c大很多——所有`#include`的头文件都被展开了。编译阶段最耗时，汇编和链接很快 |
| 计算机层次结构 | 应用→语言处理系统→OS→ISA→微架构→数字逻辑，每层对上层隐藏实现 | C语言的`+`不关心CPU是Ripple Carry还是Carry-Lookahead |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| 程序和数据共用存储 | 简化硬件，一套总线一条存储 | 哈佛结构(分离)：可取指和取数并行但无法做JIT编译 |
| 分层抽象 | 各层独立演进，写C代码不关心CPU型号 | 取消分层：换个CPU就要重写OS和应用 |

### 第2章：数据的机器级表示与处理

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| 补码表示 | 负数=取反加一。优势：加减法共用一个加法器，无±0歧义 | `abs(INT_MIN)`是UB——-128的补码=10000000，没有正数形态 |
| 无符号/有符号混用 | C的隐式转换规则：有符号→无符号 | `-1 < 0U`结果是false——因为-1转无符号=UINT_MAX |
| IEEE 754浮点数 | 符号(1)+阶码(8单/11双)+尾数(23/52)，阶码用移码 | 0.1+0.2≠0.3——二进制中0.1和0.2是无限循环，截断带来舍入误差 |
| 大端/小端 | 小端(x86)：低字节在低地址；大端(网络字节序)：低字节在高地址 | `htonl()`只是字节序转换，不是什么神秘操作 |
| 整数溢出 | 有符号溢出=UB(编译器可做激进优化)；无符号溢出=定义好的模运算 | 编译器可利用"有符号溢出=UB"假设`x+1 > x`恒成立来优化循环 |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| 补码而非原码/反码 | 统一加减法为一个加法器，无±0二义 | 原码：10000000和00000000都是0，浪费编码+两套电路 |
| IEEE 754隐藏位 | 规格化数尾数最高位总是1，省略不存多出一位精度 | 不隐藏：23位尾数精度少一位 |
| C不规定有符号溢出行为 | 编译器可做循环展开/向量化等优化 | 规定wrap-around：`x+1 > x`不能假设，优化空间大缩 |

### 第3章：程序转换与指令系统

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| 指令集体系结构(ISA) | 软件与硬件的"合同"——上面是编译器，下面是CPU微架构 | 同一份x86二进制在Skylake和Zen4上性能天差地别——ISA不规定微架构 |
| CISC vs RISC | x86：变长指令，功能复杂；ARM：定长，简单指令 | RISC代码体积更大——同功能需要更多条简单指令 |
| x86-64寄存器组织 | 16个64位通用寄存器，rip指令指针，rflags标志 | rsp是硬件约定的栈指针；rbp是软件约定，`-fomit-frame-pointer`可以不用 |
| 寻址方式 | `[基址+变址×比例+偏移]`，一条指令完成数组访问+结构体字段计算 | 这一条指令能替代多条RISC指令 |
| 条件码机制 | ZF/SF/OF/CF，由算术指令自动设置，由条件跳转读取 | `cmp %rax,%rbx`=做减法→扔结果→留标志位 |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| x86寄存器有隐含用法 | 8086→x86→x86-64逐步扩展的历史包袱 | 纯通用寄存器(MIPS R0-R31)：干净但没有今天的生态 |
| 条件码而非条件寄存器 | 一条cmp为后续多条条件跳转服务 | 每条算术指令输出(结果+条件码)：更浪费但更灵活 |

### 第4章：程序的机器级表示

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| 栈帧机制 | 每次函数调用分配栈空间：返回地址+保存的寄存器+局部变量。x86-64前6个参数走寄存器(rdi/rsi/rdx/rcx/r8/r9) | x86-64栈帧不一定有rbp——编译器优化后用rsp+偏移，省一个寄存器 |
| 调用约定 | System V AMD64 ABI：caller-saved(rax/rcx/rdx/rsi/rdi/r8-r11) vs callee-saved(rbx/rbp/r12-r15) | 同一套ISA可有不同调用约定(Windows x64 ABI用rcx/rdx/r8/r9传前4参数) |
| 传值 vs 传址 | C只有传值——"传指针"是传"地址值"的拷贝 | C没有真正的传引用(C++的引用才是别名)，指针模拟的是另一回事 |
| 缓冲区溢出 | 越界写入覆盖栈上的返回地址→攻击者将返回地址改为恶意代码地址 | 编译器可能重排局部变量布局——溢出攻击不等于"按声明顺序覆盖" |
| 栈金丝雀(Stack Canary) | 编译器在返回地址前插随机值，函数返回前检查 | 防顺序溢出但防不了"跳过金丝雀直接改其他数据"的定向写入 |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| 栈向低地址增长 | 堆和栈从两端向中间增长，最大化地址空间 | 栈向高：堆反向增长，逻辑等价但历史约定往低 |
| 递归调用独立栈帧 | 每次调用新栈帧，局部变量互不干扰 | 共享栈帧：递归时后一次覆盖前一次的局部变量 |
| 结构体对齐 | 对齐到成员最大对齐的整数倍地址 | 不强制对齐：SPARC等架构访问未对齐地址直接bus error |

### 第5章：程序的链接与加载执行

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| ELF格式三种形态 | 可重定位文件(.o)、可执行文件、共享库(.so)。链接视角看Section，加载视角看Segment | 同一个ELF section，链接器和加载器看到的含义不同 |
| 符号表与符号解析 | 记录每个名字→地址+类型+作用域。强符号覆盖弱符号 | 链接顺序重要！`gcc main.c -la -lb`，如果a依赖b，b必须放a后面 |
| 重定位 | 把符号引用替换为实际地址。R_X86_64_PC32(PC相对)和R_X86_64_32(绝对) | 位置无关代码(PIC/fPIC)用PC相对寻址，所以.so可加载到任意地址 |
| PLT/GOT延迟绑定 | PLT是跳板，GOT存实际地址。首次调走PLT→解析→写GOT；后续直接走GOT | 这就是"第一次调用printf比后续慢"的原因 |
| 动态链接 vs 静态链接 | 动态：多个进程共享libc.so物理页，安全更新只换so | Go语言选择静态链接是完全相反的取舍——部署简单但每个binary都带一份lib |
| 库打桩 | 编译时(宏)、链接时(`--wrap`)、运行时(`LD_PRELOAD`)三种方式 | LD_PRELOAD是jemalloc替代默认malloc等工具的基础机制 |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| 动态链接而非全静态 | 节省磁盘和内存，更新CVE不用重链所有程序 | 全静态：无.so依赖但更新libc要重编整个系统 |
| 延迟绑定而非启动全量解析 | 启动快，不解析永远不用的符号 | 全量绑定：首次调用不慢但启动慢+浪费解析 |
| .interp段委托动态链接器 | 内核只加载可执行文件，动态链接由ld-linux.so做 | 内核做动态链接：复杂度暴增，违背"内核只做最少的事" |

### 第6章：存储器层次结构

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| 存储金字塔延迟量级 | Reg~0.3ns < L1~1ns < L2~4ns < L3~12ns < DRAM~100ns < SSD~100μs < HDD~10ms | 缓存比主存小100-1000倍但命中率>95%——全靠局部性原理 |
| 缓存映射方式 | 直接映射(每块1个位置)、组相联(每块E个位置)、全相联 | 实际CPU用8/16路组相联——直接映射冲突多，全相联硬件太贵 |
| 缓存替换策略 | LRU(最久未使用)、伪LRU(Tree-PLRU)、随机 | 真LRU跟踪所有访问顺序太贵——Tree-PLRU近似模拟就够了 |
| 写策略 | write-through(同时写缓存和主存)、write-back(只写缓存，脏块被替换时才写回) | write-back性能更好但miss时如果块是脏的要先写回再读入→这次miss代价更大 |
| 局部性原理 | 时间局部性(刚用的可能再用)、空间局部性(附近数据可能一起用) | 这不是硬件特性——是程序行为特性，你可以写出局部性极差的代码 |
| VIPT寻址(虚拟索引物理标签) | 索引用虚拟地址的低位bit=可和TLB查找并行进行(高性能)；标签用物理地址=保证正确(不同虚拟地址映射同一物理地址也能正确区分) | VIPT的精妙之处：大多数设计必须在"正确(VIVT→别名问题)"和"快(PIPT→等TLB)"之间二选一——VIPT用虚拟索引+物理标签巧妙把两者兼得 |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| 缓存行64字节 | 利用空间局部性，一次加载整个cache line | 128字节：顺序访问好但false sharing更严重——两个核写同一cache line不同位置互相invalidate |
| VIPT设计 | 索引用虚拟地址的低位可与TLB并行，标签用物理地址保证正确 | PIPT：慢(VIPT + TLB查找并行化的收益没了)；VIVT：快但需处理别名 |

### 第7章：虚拟存储器

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| 虚拟地址空间 | 每个进程看到独立/连续的虚拟空间。用户空间0x0~0x7FFFFFFFFFFF，内核在高端 | 32位系统4GB虚拟空间但物理内存可能512MB——靠Swap+mmap文件实现 |
| 多级页表(x86-64 4级) | PGD→P4D→PUD→PMD→PTE，每级9bit索引 | 不用多级？4KB页的48位空间一级页表要512GB——利用"大部分地址未映射"节省空间 |
| TLB | 页表查找的缓存。Intel L1 TLB约64条(4KB页)+32条(2MB) | TLB特别小，同一进程的线程共享。上下文切换可flush TLB(或用PCID/ASID避免) |
| 页面大小与大页 | 4KB(标准)、2MB(THP)、1GB。大页减少TLB miss但增加内部碎片 | 数据库喜欢大页——大量随机访存容易TLB miss，2MB页覆盖面积是4KB的512倍 |
| Copy-on-Write | fork()后父子共享物理页标记只读，任何一方写时触发缺页→分配新页+复制 | fork()快的秘密——不是真复制了整个地址空间，只是标记了COW+复制页表 |
| mmap vs read | mmap：映射文件到虚拟空间，访问像数组(read触发缺页)；read：系统调用+内核拷贝 | mmap随机访问好(缺页按需加载)，read大文件顺序读好(预读+无缺页中断) |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| 多级页表 | 利用虚拟空间稀疏性——只给被用的部分分配中间页表 | 一级大页表：512GB页表不可接受 |
| 按需分页 | 启动不加载全部代码，按需触发缺页加载 | 启动全量加载：极慢+浪费内存 |
| 内核空间放在高段 | 方便区分用户地址(高位0)和内核地址(高位1) | 内核在低段：原理等价，惯例在高端 |

### 第8章：进程与异常控制流

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| 进程上下文 | 寄存器集+rip+rsp+cr3(页表基址)+打开文件表+信号屏蔽字 | 上下文切换不保存L1/L2缓存→新进程上来时缓存全miss，间接开销远大于直接开销 |
| 上下文切换开销 | 直接~1-5μs(存/复寄存器+页表)；间接：冷缓存+TLB flush | 直接开销(μs)远小于间接开销(可使后续操作慢10-100倍) |
| 异常 vs 中断 | 异常=同步(CPU执行指令触发，如缺页/除零/系统调用)；中断=异步(外设触发，时钟/网卡) | "缺页中断"其实是page fault exception——同步的、指令触发的 |
| 系统调用 | 用户态→内核态的"受控入口"，syscall指令+sys_call_table索引找内核函数 | 开销~100-1000ns——非内核代码复杂，而是模式切换+页表切换+可能的TLB flush |
| 信号机制 | 异步通知：内核"发"信号→进程可注册handler或默认行为 | 信号handle中能安全调的函数极少(async-signal-safe列表)——printf都不在其中(内部调malloc=有锁→死锁) |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| 用户态/内核态分离 | 保护内核=限制用户程序 | 单一特权级(MS-DOS)：任何程序做任何事，无安全可言 |
| 信号是异步的 | 进程随时被"打断"处理信号，不需轮询 | 轮询检查：浪费CPU+无法处理紧急情况(进程Segfault自己坏了没法轮询) |
| 信号不排队 | 同一信号处理期间到达的被丢弃(除实时信号) | 所有信号都排队：OOM风险(每个排队信号占内核内存) |

### 第9章：I/O操作的实现

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| MMIO vs PIO | MMIO：外设寄存器映射到物理地址，mov指令访问；PIO：专用in/out指令 | 现代PCIe设备全用MMIO——PIO只残留在老设备(PS/2键盘) |
| 中断驱动I/O vs 轮询 | 中断：设备完成后触发CPU中断→被动响应；轮询：CPU循环检查设备状态 | NVMe SSD百万IOPS场景轮询比中断快——中断上下文切换太贵但浪费CPU |
| DMA | 设备直接读写主存，CPU不需搬数据，完成后通知 | DMA和CPU共享内存带宽——海量DMA影响CPU核的访存速率 |
| Page Cache | 文件I/O经内核缓冲：预读(预取后续数据)、写回(批量写入) | 绕过Page Cache(O_DIRECT)：降低CPU开销，减少一次内存拷贝，但失去预读/写回 |
| 标准I/O缓冲 vs 直接I/O | glibc FILE结构在用户态维护缓冲(全缓冲/行缓冲/无缓冲) | printf输出到终端是行缓冲(\n触发flush)，输出到文件是全缓冲——重定向到文件可能看不到即时输出 |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| Page Cache(默认)而非O_DIRECT | 预读+写回提升吞吐 | 绕过内核：应用自己管缓存=失去了全局缓存协调 |
| "一切皆文件"抽象 | 普通文件/设备/socket/管道统一fd+read/write | 每种资源不同API：接口爆炸 |

### 第10章：程序性能的优化

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| 编译器优化的边界 | 受语言语义限制：不能改变可观察行为。最大约束：指针别名、函数副作用 | 两个指针"可能指向同一内存"→编译器不敢做很多优化(如向量化) |
| `restrict`关键字 | 承诺"该指针是访问此内存的唯一途径"，编译器据此激进优化 | 违反restrict=UB——可能出正确结果也可能crash |
| 内联的代价 | 嵌入函数体=省call/ret+更多优化空间，但代码膨胀可能让I-cache失效 | L1指令缓存只有32KB——代码膨胀超过这个阈值=cache miss增加 |
| PGO | 先跑profiling收集分支频率/热点，再基于此重新编译(代码布局/内联分支预测) | PGO效果取决于profiling workload的代表性——benchmark做PGO跑生产可能负优化 |
| 编译器优化的限制 | 有符号溢出=UB是编译器优化的燃料——可以假设`x+1 > x` | Java所有行为精确定义→无UB→编译器优化空间更小——这是C快于Java的一个底层原因 |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| UB给编译器优化空间 | 不定义溢出行为=编译器可假设"绝不溢出"→做死代码消除等优化 | 所有行为精确定义(Java)：安全但丢性能 |
| 指针别名是C的性能之痛 | 两个不同类型的指针可能指向同一地址→编译器不能做优化 | 禁止指针别名(Fortran)：可做更激进优化——但C失去与硬件的亲密 |

### 第11章：网络编程

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| IP地址+端口=通信端点 | 网络层IP定主机，传输层端口定进程 | 127.0.0.1通信经loopback网卡不经过物理网卡 |
| TCP三次握手 | SYN→SYN-ACK→ACK，建立状态同步+协商初始序列号 | 三次不是四次(多余)、不是两次(历史连接不安全) |
| socket API生命周期 | socket()→bind()→listen()→accept()→read/write→close() | 每个步骤创建了哪些内核对象？listen的backlog含义是等待accept的队列长度 |
| 阻塞/非阻塞/异步I/O | 阻塞(进程挂起等数据)→非阻塞(立即返回EAGAIN，需轮询)→I/O多路复用(select/poll/epoll，一个线程监听多个fd) | 非阻塞不是异步——非阻塞还要自己轮询，异步是OS完成后通知你(如POSIX AIO) |
| I/O多路复用三种方案 | select(bitmap，最多1024个fd，O(n)扫描)→poll(动态数组，无上限，但仍是O(n))→epoll(事件驱动+红黑树，O(1)获取就绪fd) | epoll只在Linux有——跨平台的libuv/libevent封装了这层差异 |
| 并发服务器三种模型 | fork-per-client(简单但重)、pre-fork(进程池)、事件驱动(单线程I/O复用) | 线程切换有开销——几千个线程就扛不住，nginx选事件驱动非偶然 |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| 端口用16位整数 | 固定长度+整数比较极快+语言无关 | 字符串进程名：需字符串匹配(更慢)、名字可能冲突 |
| 网络分层 | 每层只管自己的事——换物理层(铜线→光纤)不影响上层 | 不分层：改任何一个细节都要重写整个协议栈 |

### 第12章：并发编程

| 知识点 | 需要理解到什么程度 | 反直觉/易错点 |
|:---|:---|:---|
| 进程 vs 线程 | 进程有独立地址空间；线程共享地址空间→通信快(共享内存)但容易竞态 | Python GIL使多线程在CPU密集型上更慢——不是所有"多线程"都等价于"并行" |
| 互斥量(Mutex) | 保证同时只有一个线程进入临界区。粒度决定并发度 | 一把大锁保护整个结构→多线程等价于单线程；细粒度锁提高并发但增加死锁风险 |
| 死锁四条件 | 互斥/持有等待/不可抢占/循环等待——破坏任一即可 | 最实用：给所有锁编号，按编号顺序加锁→破坏循环等待 |
| 信号量 vs 条件变量 | 信号量=计数器型同步(资源池/生产者-消费者)；条件变量=等待某个条件成立 | 条件变量wait必须在while循环中(防虚假唤醒spurious wakeup) |
| 锁破坏并行性 | 锁的本质=串行化——Amdahl定律：临界区5%→最多20x加速 | 无锁数据结构：CAS循环低竞争好，高竞争CPU空转浪费 |

**设计决策背后的"为什么":**

| 决策 | 设计动机 | 如果反过来呢？ |
|:---|:---|:---|
| 需要锁——硬件不能保证 | 硬件只保证单指令原子性(如LOCK CMPXCHG)，但"检查余额→扣款"两步整体不原子 | 只有原子指令没有锁：任何多步状态修改都要实现复杂无锁协议 |
| 互斥量 vs 信号量分离 | 互斥=所有权(谁锁谁解)、信号量=计数(不记谁hold) | 只有互斥：无法实现生产者-消费者；只有信号量：无所有权概念，易忘释放 |
