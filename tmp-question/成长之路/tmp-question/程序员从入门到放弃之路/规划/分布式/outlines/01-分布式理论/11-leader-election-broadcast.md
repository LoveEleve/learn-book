### 1. 失败检测 — 超时只能产生怀疑

场景提示: 心跳 3 秒没有响应，如何区分节点崩溃、网络分区、GC 暂停和临时负载？ [写作时展开]

关键设计: 完美失败检测需要强完备和强精确，但现实系统只能在时间/网络假设下产生逐步增强的怀疑：

```[pseudocode]
heartbeat/probe
  → 在 timeout 内得到响应?
      是: 维持健康
      否: 增加 suspicion

故障检测目标:
  Completeness: 最终发现故障节点
  Accuracy: 不把正确节点误判为故障

现实:
  timeout 太短 → 抖动误判
  timeout 太长 → 切换慢
  φ-accrual/自适应模型 → 用历史延迟估计怀疑度
```

Why: 为什么生产系统通常输出“suspect”而不是立即输出“dead”？——**异步/部分同步环境里，网络慢与节点死不可从一次超时区分**；检测器的精确度和完备性取决于最终网络假设。误判还可能触发错误选主、重复任务和脑裂。 [分布式理论: 完美失败检测在现实异步系统不可直接获得，Ω 关注最终选出一个正确 Leader 的能力]

比喻锚点: 心跳像给朋友打电话，没接不是死亡证明；连续多次无人接听、周边观测和历史延迟才让怀疑逐步升高。 [写作时展开]

### 2. 选主与 Lease — 选出新 Leader 还要防旧 Leader 写入

场景提示: 旧 Leader 只是网络隔离但进程仍活着，新节点已经选出 Leader；怎样防止两个节点同时接受写请求？ [写作时展开]

关键设计: 选主算法提供候选与多数认可，Lease/fencing 负责限制旧角色继续产生副作用：

```[pseudocode]
Bully/优先级选举:
  候选者按 ID/优先级竞争
  → 适合简单模型, 需要可靠成员视图

共识内建选主:
  term/ballot + quorum vote
  → Leader 身份与日志/决定绑定

Lease:
  Leader 在时间窗口内拥有领导资格
  → 周期续约
  → 失去多数/无法续约时停止服务

fencing:
  新 epoch/token
  → 下游资源拒绝旧 token 的写入
```

Why: 为什么只靠 Lease 时间还不够防脑裂？——**旧 Leader 可能因暂停、时钟误差或网络恢复在过期后继续执行本地代码**；安全设计需要服务端 epoch/fencing token 验证，而不是让旧进程自觉退出。Lease 的正确性依赖时钟/延迟边界和续约协议。 [分布式理论: 02 篇的时钟模型与 05 篇的 term/选举限制在此汇合]

比喻锚点: 租约不是“旧管理员自己记得离职”，而是门禁系统换了 epoch；旧工牌即使还在手里，仓库也拒绝它改货架。 [写作时展开]

### 3. 可靠广播 — 成员消息、顺序消息与共识不是同一层

场景提示: 广播一条配置变更，怎样保证节点不会有人收到、有人没收到、有人顺序不同？ [写作时展开]

关键设计: 广播语义从尽力传递到全序传递逐步增强：

```[pseudocode]
Best-effort:
  尝试发送, 可丢失/重复/乱序

Reliable broadcast:
  若一个正确节点 deliver
  → 其他正确节点最终也 deliver
  同时避免错误节点单独制造不一致

FIFO/causal:
  同一发送者顺序
  或遵守 happens-before

Gossip:
  每轮随机传播给若干邻居
  → 概率扩散/最终覆盖
  → 需要 anti-entropy/去重/版本与失败处理

Total-order broadcast:
  所有正确节点按相同顺序 deliver
  → 可驱动复制状态机
```

Why: 为什么 Gossip 不能替代全序广播？——**Gossip 擅长成员信息和最终传播，不天然决定所有命令的同一全局顺序**；全序广播与共识在一定模型下可以相互实现，但代价是 quorum、排序和故障处理。成员状态传播和状态机命令传播应分开设计。 [分布式理论: 消息可靠性、因果顺序和全序是不同保证层级]

比喻锚点: Gossip 像邻居口耳相传公告，最终大家可能都知道；全序广播像总账编号，大家不仅知道，还必须按同一编号顺序记账。 [写作时展开]

### 4. 复制状态机 — 全序输入加确定性 apply

场景提示: 多个副本收到同一批命令后，怎样保证最终内存状态完全一致？ [写作时展开]

关键设计: 复制状态机要求相同初始状态、相同输入顺序和确定性执行：

```[pseudocode]
client command
  → total-order broadcast/consensus log
  → every replica receives same ordered entries
  → deterministic apply(command, state)
  → same next state

禁止直接依赖:
  本地随机数
  当前墙钟
  不同步的本地文件/环境变量

需要:
  将随机种子/时间戳/外部结果纳入日志或协议
```

Why: 为什么“收到相同日志”还不保证副本相同？——**apply 函数若读取本地时间、随机数、非确定性遍历或外部状态，输入相同也可能输出不同**；复制状态机的确定性是协议正确性的组成部分，不是业务代码默认具备的性质。 [分布式理论: Paxos/Raft 的共识日志只保证输入序列，状态机确定性负责输出一致]

比喻锚点: 多家分店拿到完全相同的操作手册和订单，但如果各自用不同汇率/随机抽奖规则，库存仍会分叉；所以规则和外部输入也要统一。 [写作时展开]

### 5. 收束

基础设施闭环：

```[pseudocode]
heartbeat/probe
  → failure suspicion
  → quorum/term/lease/fencing 选主
  → Gossip 传播成员状态
  → total-order broadcast 传播状态命令
  → deterministic state machine
  → replicas converge
```

**Aha Moment**: "自动故障转移不是“超时后换个节点”，而是**怀疑故障、隔离旧角色、选出新 Leader、传播一致命令并确定性应用**的一整条安全链。"
**回答读者三问**: ①超时能证明节点死吗=不能，只产生怀疑；②Lease 如何防旧 Leader=需要 epoch/fencing，而非只靠本地时钟；③Gossip 能替代共识吗=能传播成员信息，不能天然提供全序决定。
