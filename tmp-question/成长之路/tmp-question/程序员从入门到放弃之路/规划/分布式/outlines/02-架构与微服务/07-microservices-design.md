### 1. 单体与微服务 — 不是二选一，而是组织和变化问题

场景提示: 三个人的团队维护 20 个服务，每天忙于网络超时和部署协调；什么时候应该先保留模块化单体？ [写作时展开]

关键设计: 微服务的收益来自独立发布、扩容、技术和团队边界，代价是网络、运维和一致性复杂度：

```[pseudocode]
模块化单体:
  一个部署单元
  → 进程内调用/本地事务
  → 运维简单
  → 独立扩容/发布边界较弱

微服务:
  多部署单元/独立数据边界
  → 独立发布/扩容/团队自治
  → RPC/监控/配置/故障/分布式事务成本

绞杀者迁移:
  新功能先落在新服务
  → 旧单体边界逐步替换
  → 避免一次性重写/大爆炸迁移
```

Why: 为什么“服务越多越先进”是错的？——**每个服务都增加部署、监控、网络、权限、版本和故障边界**；若服务间强同步依赖、共享数据库、必须同批发布，就只是分布式单体。服务数量应服从变化边界和团队交付能力。 [分布式架构: 绞杀者模式把迁移风险拆成可回滚的小步]

比喻锚点: 微服务拆分像把一座工厂分成多个车间；车间能独立换班和扩容，但原料、运输和总装协调会变复杂。 [写作时展开]

### 2. DDD、数据边界与变化频率 — 以高内聚而不是用户量拆分

场景提示: 订单和库存分别成服务后，每次订单状态变化都要改库存服务，说明边界可能哪里出了问题？ [写作时展开]

关键设计: 拆分要同时观察业务语言、事务边界、数据所有权和变化频率：

```[pseudocode]
DDD:
  bounded context → 业务语言/规则边界
  aggregate → 一致性与修改边界
  domain event → 跨边界通知

数据驱动:
  一个核心数据由一个服务拥有
  → 其他服务通过 API/event 访问

变化频率:
  高频独立发布/扩容模块
  → 有理由成为独立服务

合理性检查:
  能否独立部署?
  能否独立扩容?
  是否有清晰数据/团队 owner?
  跨服务调用是否会形成强同步链?
```

Why: 为什么 DDD 聚合不等于“一聚合一个服务”？——**服务边界还要考虑部署、团队、数据和运行依赖；一个服务可以包含多个聚合，跨聚合事务是否最终一致要看业务不变量**。按用户量/数据库表机械拆分，通常会制造跨服务 join 和事务。 [分布式架构: 统一语言比画出类图更关键，事件 Schema 也是边界契约]

### 3. Spring Cloud、Dubbo 与生态选择 — 选的是运行体系

场景提示: 团队在 Spring Cloud、Dubbo、Nacos、Consul、Sentinel 之间选择，为什么不能只比较 RPC QPS？ [写作时展开]

关键设计: 框架选择包括注册、配置、路由、容错、协议、序列化、观测和团队生态：

```[pseudocode]
Spring Cloud 体系:
  HTTP/RPC + Gateway/Config/Discovery/Resilience
  → 更贴近 Spring/Web 生态

Dubbo 体系:
  Provider/Consumer/Registry/Protocol/Serialization
  → Java RPC/服务治理能力集中

Alibaba/其他组件:
  Nacos/Sentinel/Seata/RocketMQ 等
  → 统一生态也带来供应商/组件耦合

选择维度:
  语言/协议/延迟/治理/生态/运维/迁移
```

Why: 为什么“性能更高”不能独立决定框架？——**网络协议只是调用成本的一部分，注册发现、序列化、线程模型、重试、追踪、升级和人才成本会长期累积**；历史组件进入维护模式、生态替换和供应商锁定也必须纳入决策。 [分布式架构: 生态选择是组织能力与技术协议的联合选择]

### 4. API、网关与 BFF — 外部一个接口，内部不必暴露七个服务

场景提示: 前端调用 `/api/orders`，后台需要订单、库存、积分和配送数据；网关聚合会不会变成新的业务中心？ [写作时展开]

关键设计: API 网关/BFF 可承担路由、认证、限流和面向客户端的聚合，但领域规则不能无限上移：

```[pseudocode]
Gateway:
  path/host → route
  → JWT/auth/rate limit
  → protocol/observability

BFF:
  Web/Android/iOS 各自需要的聚合视图
  → 调多个服务
  → 组合结果/适配字段

API evolution:
  additive change first
  → v1/v2 或兼容字段
  → 灰度/迁移/弃用窗口
```

Why: 为什么 API 版本兼容是服务边界的一部分？——**服务无法强迫所有调用方同时升级，破坏性变更会沿调用图扩散**；BFF 能减少前端调用，但如果把领域编排全部放进网关，网关会变成难以拆分的分布式单体。 [分布式架构: API 契约、超时/重试和事件 Schema 都是跨服务边界]

### 5. 收束

微服务设计闭环：

```[pseudocode]
业务语言/数据 owner
  → bounded context/aggregate 边界
  → 独立部署/扩容/团队验证
  → RPC/event/API 契约
  → 网关/BFF 适配
  → 观察同步依赖、事务和故障传播
  → 不满足边界时合并服务
```

**Aha Moment**: "微服务拆分的成功标准不是服务数量，而是**边界内聚、数据归属清晰、独立交付和可控制的跨服务依赖**；不满足这些条件，合并往往比继续拆更健康。"
**回答读者三问**: ①什么时候不该拆=团队/变化/数据/部署仍强耦合；②DDD 如何帮助=统一语言与边界，不是机械一聚合一服务；③网关有什么风险=聚合和认证有价值，但过度编排会制造新单体。
