## 三、阅读方法论

### 3.1 问题驱动，不要线性阅读

不要去"读完一本书再读下一本"。应该：

```
提出问题 → 在4-5本书中同时找答案 → 串成知识网络 → 写代码验证
```

**示例问题链：**
1. `malloc(1024)` 背后发生了什么？ → 涉及 体系结构(虚拟内存) + 内核(伙伴系统/slab) + 系统编程(内存管理API)
2. 一个HTTP请求从`write()`到网线经历了什么？ → 涉及 系统编程(文件I/O) + 内核(VFS/页缓存) + 网络(协议栈) + 性能(可观测性)
3. Docker容器内的`top`命令为什么和宿主机不同？ → 涉及 内核(进程管理/namespace/cgroups) + 容器(源码分析)

### 3.2 三层阅读法

| 层次 | 策略 | 时间占比 |
|:---|:---|:---|
| **第一遍：扫读** | 30分钟/章，跳过源码细节，只抓核心概念和数据流 | 30% |
| **第二遍：深读** | 跟着写代码/跑实验，每个概念都要有对应的源码行号 | 50% |
| **第三遍：复盘** | 用自己的语言写1000字总结，画出你理解的架构图 | 20% |

### 3.3 为什么你会感到痛苦（以及应对方法）

1. **概念密度过高** → 每章读完后强制用一句话概括核心思想，否则不进下一章
2. **源码追踪迷失** → 下载内核源码，用ctags/lxr辅助跳转，不要裸读
3. **成就感缺失** → 每攻克一个领域后，写一篇博客/做一个分享（费曼学习法）
4. **时间不够用** → 工作日每天1小时扫读，周末3小时深读+实验，节奏比强度重要

## 五、最终检验标准

当你完成这8个阶段后，你应该能：

1. **不用Google，画出一张完整的图**：从CPU通电 → BIOS → Bootloader → 内核启动 → init进程 → 你的程序运行 → malloc → 缺页中断 → TCP连接 → 数据发送 → 网卡DMA → 交换机 → 对端。
2. **排障时心中有数**：不是"搜索报错信息"，而是从系统层次推演可能原因。
3. **面试时碾压**：不是背面试题，而是用源码细节和实战经验说话。
4. **设计时有底气**：做任何技术决策时，能说出各个方案在内核/网络/性能三个维度的代价。
