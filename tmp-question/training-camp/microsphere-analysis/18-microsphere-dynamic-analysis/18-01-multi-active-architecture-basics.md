## 什么是多活架构

多活架构（Multi-Active Architecture）是指一个分布式系统在多个地理位置上同时提供读写服务，而不是传统的"主-备"模式——一个地方提供服务，其他地点冷备等待切换。

与之相对的是**主备架构**（Active-Standby）：

```
主备架构：
  ┌──────────┐                 ┌──────────┐
  │  Zone A  │ ← 全部流量       │  Zone B  │
  │ (Active) │                 │(Standby) │ ← 空转
  │   DB ────│──── 异步复制 ──→│   DB     │
  └──────────┘                 └──────────┘
  ✓ 简单
  ✗ 资源利用率 50%
  ✗ 切换有 downtime（分钟级）
  ✗ 备库延迟意味着切换后会丢数据
  ✗ 备库长期不加载流量，可能"假活"——实例正常但 SQL 执行结果不对

多活架构：
  ┌──────────┐                ┌──────────┐
  │  Zone A  │ ← 50% 流量     │  Zone B  │ ← 50% 流量
  │ (Active) │                │ (Active) │
  │   DB ────│─ 异步复制（双向）─│─── DB   │
  └──────────┘                └──────────┘
  ✓ 资源利用率 100%
  ✓ 切换理论上更快（流量重分发，无需拉起备库）
  ✓ 天然验证两套都活着
  ✗ 复杂度极高（数据冲突、一致性问题）
```

注：多活架构的 DB 间复制几乎总是**异步**的，极少使用同步复制。即使是同城双活，同步复制也会引入显著的写延迟（每个写入需等待跨 AZ 确认），且网络抖动时延会直接转化为写入延迟。后面会详细讨论这个 trade-off。

### 为什么需要多活

**1. 可用性目标提升：从单机房到多机房**

单机房故障是小概率事件，但云厂商的大规模故障历史上发生过多次（AWS US-EAST-1 宕机、GCP 东京故障、阿里云香港故障）。单机房部署意味着无论你的代码多好，机房光纤被挖断就是全站不可用。

注意：多活不等于可用性简单相乘（`1 - (1-0.9999)^2`），因为 Zone 间的故障不是独立事件——同 Region 的 AZ 共享电力上游和网络骨干，极端情况下可能同时故障。多活的实际可用性提升取决于 Zone 的**故障隔离程度**。跨 Region 的隔离程度 > 同城 AZ 间。

**2. 异地就近接入降低延迟**

用户在上海和用户在新疆，访问同一个北京机房的数据库，延迟差异巨大。多活架构可以让用户就近接入，提升全量用户的体验。

**3. 计划内维护不停机**

数据库版本升级、操作系统补丁、硬件更换——这些在单机房架构中都需要维护窗口。多活架构可以一个 zone 一个 zone 滚动维护。

**4. 监管合规要求**

某些行业（金融、医疗）要求数据必须存储在特定地域，同时要求跨地域容灾。多活架构满足两套要求。

## 多活的级别

多活不是 binary 的"要么多活要么不活"，而是不同层面、不同代价的多活。从接入层到数据库层，越往下共享的状态越多，多活的难度也越大。

### 第一级：接入层多活

```
用户 → DNS → SLB Zone A
            → SLB Zone B
```

用户流量通过 DNS/GSLB 分发到不同机房的入口网关。两台网关各自独立，不共享状态。

**难度**：低。DNS 和 SLB 天然支持多站点。但后端服务如果只部署在一个机房，网关多活没有意义。

**典型方案**：DNS GSLB、Anycast IP

### 第二级：无状态服务层多活

```
Zone A: Gateway → Service A → Service B
Zone B: Gateway → Service A → Service B
```

服务层本身是无状态的（状态在数据库或缓存中），所以多机房部署服务层本身就"自动多活"——只要数据库层支持。

**难度**：中。主要挑战是服务发现（Eureka/Nacos 需要跨机房集群）和 RPC 调用的 zone 优先路由（17-multiactive 解决的就是此处）。

**典型方案**：Eureka 多集群、Nacos 跨机房、Zone-prioritized LoadBalancer

### 第三级：配置层/控制层

```
Zone A: Nacos/etcd (集群)
Zone B: Nacos/etcd (集群)
         ↓
  所有服务共享同一套配置视图
```

这是常常被忽略的一层。多活架构需要统一的配置管理——ZoneContext 怎么同步、Zone 切换由谁决策、服务的配置变更怎么传播到所有实例。配置层本身也需要多活部署（否则它成为单点）。

18-dynamic 的 ZoneContext 集成属于这一层**在数据库领域的延伸**——它不解决配置的传播机制（由 Nacos/etcd 解决），而是解决"配置变化后，数据库层怎么响应"。

**难度**：中。主要挑战是配置的最终一致性、变更的原子性、以及多集群配置的同步延迟。

### 第四级：数据库层多活

```
Zone A: MySQL ↔ 异步复制 ↔ MySQL Zone B
        ↑                    ↑
      读写                 读写
```

这是多活架构中最难的一层，也是 18-dynamic 模块关注的领域。

**难度**：极高。详见下文。

注意：图中标注的是"异步复制"。虽然同城场景有半同步复制（semi-sync）可用，但 MySQL 本身没有"双向同步"的标准化方案。生产中的多活数据库层通常用以下方式之一：

1. **单元化（Unitization）**：业务层将数据按用户/租户分片，每个分片（单元）的写入只在一个 Zone 内完成，异步复制到其他 Zone 做只读。18-dynamic 的每个 `DynamicJdbcConfig` 本质上就是一个"单元"——它定义了一个独立的数据源 + ORM + 事务管理器组合，Zone 切换时整个单元的数据源被重建。
2. **第三方双向同步工具**：如 Tungsten Replicator、DRBD 等，不依赖 MySQL 原生复制。
3. **独立数据库 + 业务层合并**：每个 Zone 独立数据库，不互相同步，由业务层处理数据合并。

18-dynamic 的设计天然对齐方案 1（单元化）。每个 DynamicJdbcConfig 是一个数据库单元，ZoneContext 决定该单元当前使用哪个 zone 的配置。方案 2 和 3 不在本模块的关注范围内。

### 第五级：缓存层多活

```
Zone A: Redis (primary)   Zone B: Redis (replica)
Zone A: ←→ Zone B: Redis (双向同步 or 多主)
```

缓存层的多活方案高度依赖数据库层——如果数据库不是多活的，缓存多活没有意义（缓存数据源是单 Zone 的，缓存自身多活了但源数据没有）。

**难度**：高。写冲突、数据一致性、过期策略在跨机房场景下都有额外挑战。

**典型方案**：Redis CRDT、多主 Redis Cluster、各机房独立缓存 + 数据库兜底

### 第六级：消息层多活

```
Zone A: Kafka  → Consumer A
         ↓ (MirrorMaker)
Zone B: Kafka  → Consumer B
```

消息队列的多活通常需要跨机房复制 Topic，保证每个机房都能消费到全量消息。

**难度**：高。消息顺序、幂等消费、Exactly-Once 语义在跨机房场景下更难保证。

## 两种部署模型：单实例多 Zone vs 按 Zone 独立部署

在看具体的多活方案之前，先明确一个前提——微服务实例在多活架构中有两种部署方式：

### 模型 A：按 Zone 独立部署

```
Zone A: Service[实例 1, 实例 2, 实例 3]  →  DB Zone A
Zone B: Service[实例 4, 实例 5, 实例 6]  →  DB Zone B
```

每个 Zone 部署独立的微服务实例集群。实例只连接本 Zone 的数据库，不关心其他 Zone。Zone 切换通过 DNS/GSLB 将流量从 Zone A 的实例切到 Zone B 的实例。

**优点**：应用代码不需要感知多活，数据库连接配置是静态的。
**缺点**：资源利用率低（每个 Zone 都要预留足够的容量处理全量流量），Zone 切换时实例重启/预热有延迟。

### 模型 B：单实例多 Zone

```
Service[实例 1, 实例 2, 实例 3]  →  DB Zone A（当前）
                                 →  DB Zone B（切换后）
```

所有实例部署在同一个集群中（或跨 Zone 均匀分布），每个实例同时配置了多个 Zone 的数据库连接。Zone 切换时不需要切换实例，只需要在实例内部切换数据库连接。

**优点**：切换快（不需要启停实例），资源利用率高，支持更细粒度的路由（如请求级路由）。
**缺点**：应用代码需要感知多活，数据库连接配置是动态的，复杂度更高。

### 18-dynamic 的选择

18-dynamic 属于**模型 B**。它的核心假设就是：**一个微服务实例需要同时能连接多个 Zone 的数据库，并在 Zone 切换时在实例内部完成数据库切换**。这也是它为什么需要一个"动态 Spring 应用上下文"——因为数据库切换不仅仅是换一个 DataSource，还涉及 TransactionManager、MyBatis SqlSessionFactory、ShardingSphere 规则等一整套配置的热更新。

选择模型 B 的代价是复杂度，收益是切换速度和资源利用率。18-dynamic 试图通过子上下文隔离将复杂度封装在框架内部，让业务代码无感。

## Zone 与 Region

Zone（可用区）和 Region（地域）是云计算的两级抽象，多活架构设计必须理解这两个概念：

### Region（地域）

Region 是一个完全独立的地理区域，包含多个 AZ。

- 不同 Region 之间**完全隔离**（网络、电力、冷却）
- Region 间延迟：几十到几百毫秒
- Region 间的数据复制只能是异步的
- 每个 Region 有独立的 API endpoint

**例子**：AWS `us-east-1`（弗吉尼亚）、`cn-north-1`（北京）、`eu-west-1`（爱尔兰）

### Zone / AZ（可用区）

AZ 是 Region 内的一个或多个数据中心。

- 同 Region 的不同 AZ 通过**低延迟专线**连接（1-5ms）
- 不同 AZ 之间物理上隔离（独立的电力、网络、制冷）
- 同一个 AZ 的故障不会影响其他 AZ
- 同 Region 的 AZ 间可以做同步复制

**例子**：AWS `us-east-1a`、`us-east-1b`、`us-east-1c`

### 在数据库多活中的影响

```
Region A (北京)
  ├── AZ a ────┐
  │            │  同城专线 <2ms → 半同步复制可行
  ├── AZ b ────┘
  │
  │── 跨城专线 30ms → 必须异步复制
  │
Region B (上海)
  ├── AZ a
  └── AZ b
```

18-dynamic 的 `ha-datasource` 在概念上对应的是 Zone——每个 Zone 有自己的一套数据库配置。具体是"同城 AZ 级"还是"异地 Region 级"，完全取决于部署时怎么映射。

## 同城双活 vs 异地多活

这两个概念经常被混淆，它们的架构代价完全不同：

### 同城双活

```
同城双活：
           ┌─── Zone A (同城 AZ-1)
  城市 X ──┤
           └─── Zone B (同城 AZ-2)

  ───────────── 同城专线 (< 5ms) ─────────────
  
  特点：
  - 物理距离 < 50km
  - 专线延迟 < 5ms
  - 不跨运营商
  - 不跨法律区域
```

**优势**：
- 延迟极低（同城专线 1-3ms），半同步复制可行
- 不涉及法规合规问题
- 运维相对简单（同一套网络环境）

**劣势**：
- 无法防御城市级灾难（地震、洪水、全城停电）

**典型架构**：一个城市内两个 AZ，数据库用 MySQL Group Replication 或半同步复制，延迟 2-5ms。

注意：即使是同城半同步复制，**严格来说 RPO 也不等于 0**。半同步复制保证"事务提交时至少有一个备库已收到 binlog 事件"，但不保证"备库已应用该事件"。如果主库在备库应用前宕机，且该事务还未在备库可见，RPO > 0。要接近 RPO=0，需要用 Paxos/RAFT 共识协议（如 MySQL Group Replication 的 Single-Primary 模式、Galera、TiDB），但这三者的实现代价和写放大不可忽视。

### 异地多活

```
异地多活：
  城市 X ─── Zone A ────┐
                          ├── 专线/公网 (30-100ms)
  城市 Y ─── Zone B ────┘
  
  特点：
  - 物理距离 > 500km
  - 专线延迟 30-100ms
  - 可能跨运营商、跨法律区域
  - 网络故障概率高
```

**挑战**：

1. **延迟**：北京到上海专线延迟约 30ms，到广州约 50ms，国际链路更高。同步复制不可行（每次写操作要等 100ms 回包），必须用异步复制。

2. **数据冲突**：异步复制意味着同一行数据可能同时在两个机房被修改。必须设计冲突解决策略（最后写入者胜出、CRDT、业务层冲突合并）。

3. **脑裂**：专线中断时，两个机房都认为对方挂了，都切换为主。恢复后数据已经分叉，合并极端困难。

4. **事务**：跨机房的分布式事务（TCC/Saga）需要业务层配合实现回滚。

**典型方案**：业务层做单元化（Unitization）——每个用户固定归属一个"单元"，读写都在该单元内完成，单元间的数据交集最小化。数据库层不做跨机房强一致，只做异步复制。

### 两种模式的选型

| 因素 | 选同城双活 | 选异地多活 |
|------|-----------|-----------|
| RTO/RPO 要求 | RTO < 30s, RPO 接近 0 | RTO < 5min, RPO < 1min |
| 业务覆盖范围 | 只服务单一地区 | 全球/全国多地区 |
| 成本预算 | 中等（多一套机器） | 高（多两套 + 专线） |
| 一致性要求 | 强一致 | 最终一致可接受 |
| 合规要求 | 无地域限制 | 数据必须留本地 |



## 数据库层的多活挑战

这是整个多活架构中最难的一层，也是 18-dynamic 模块试图解决的核心问题。下面逐一展开每个挑战，并说明 18-dynamic 在这个挑战中的位置。

### 挑战 1：同步复制 vs 异步复制

数据库多活的核心矛盾：

```
同步复制：
  写入 Zone A ─→ 写入 Zone A 的 DB
                → 等待 Zone B 的 DB 确认
                → 返回客户端成功
  ✗ 延迟 = 网络 RTT + 双写时间
  ✗ 异地延迟 30-100ms，不可接受
  ✓ 数据零丢失

异步复制：
  写入 Zone A ─→ 写入 Zone A 的 DB
                → 立即返回客户端成功
                → 后台复制到 Zone B
  ✓ 延迟 = 本地单写时间
  ✗ 容灾时可能丢数据（复制延迟内的数据）
```

**trade-off**：同城可以做半同步（1-5ms 延迟，但 RPO 接近 0 而非严格 0），异地必须纯异步（RPO 肯定 > 0）。

**18-dynamic 的位置**：这个 trade-off 是数据库层面的，不是框架层面能解决的。18-dynamic 不试图改变复制方式，而是在"数据库已经部署好了，每个 Zone 有自己的数据库实例"的前提下，提供 Zone 感知的配置选择。不管你的复制是同步还是异步，18-dynamic 都能工作——它只关心"当前 Zone 的数据库配置是什么"。

### 挑战 2：写冲突

当两个 Zone 都允许写入时，同一行数据可能同时被修改：

```
T1: Zone A 更新 row.id=1 SET balance=100
T2: Zone B 更新 row.id=1 SET balance=50
T3: 异步复制后，两个 DB 看到不同值
```

解决策略：

| 策略 | 原理 | 代价 |
|------|------|------|
| 最后写入者胜出（LWW） | 用时间戳或版本号决定谁是最新的 | 丢失更新 |
| 业务层分区（单元化） | 每个用户的数据只在一个 Zone 写入 | 需要业务改造 |
| CRDT | 用无冲突数据类型合并 | 只支持特定数据结构 |
| 应用层合并 | 业务代码处理冲突 | 复杂度高，容易漏 |

**实际生产中，单元化是最常见的方案**——让每个用户的数据在逻辑上只属于一个 Zone，所有写操作路由到该 Zone。这样就不会有写冲突。

**18-dynamic 的位置**：18-dynamic 的 `ha-datasource` 本身就基于"单元化"假设——每个 DynamicJdbcConfig 是一个单元，Zone 切换时整个单元的数据库配置被替换。单元化是 18-dynamic 的前提，不是它的功能。如果你采用最后写入者胜出或 CRDT，18-dynamic 同样可以工作，因为它只管配置切换，不关心冲突解决策略。

### 挑战 3：事务

```
Zone A 执行事务 TX1
  1. UPDATE user SET balance = balance - 100 WHERE id = 1  → 成功
  2. INSERT INTO order_log (user_id, amount) VALUES (1, 100)  → 成功
  3. COMMIT  → 返回客户端"下单成功"
  4. 异步复制 TX1 的 binlog 到 Zone B（延迟 2s）
  
  第 3 步和第 4 步之间，Zone A 宕机：
  - 客户端收到了"下单成功"
  - Zone B 还没收到 TX1 的 binlog 事件
  - Zone B 切换为主 → 用户余额没扣、订单不存在
  → 数据不一致：客户端看到的成功在另一个 Zone 中不存在
```

这里的本质问题是：**客户端感知的成功 ≠ 数据在所有 Zone 中的持久化**。异步复制下，这个时间窗口始终存在。

解决方案：
- **避免跨 Zone 事务**：事务内的所有操作都在同一个 Zone 完成
- **TCC/Saga**：在事务的 prepare/confirm/cancel 各阶段嵌入跨 Zone 的协调逻辑
- **幂等 + 补偿**：接受最终不一致，用补偿作业修复

**18-dynamic 的位置**：Zone 切换时，18-dynamic 不等待活跃事务完成（这是它的局限 3）。这意味着在切换瞬间，可能有正在执行的事务被"遗弃"在旧上下文中。60s 延迟关闭给了事务一个缓冲窗口，但超过 60s 的事务仍会被中断。这是 18-dynamic 切换成本的一部分——如果你的业务有长时间事务，需要关注这个窗口。

### 挑战 4：主键冲突

两个 Zone 各自自增主键时，一定冲突：

```
Zone A: INSERT INTO user (id, name) VALUES (1, 'Alice')
Zone B: INSERT INTO user (id, name) VALUES (1, 'Bob')
```

解决方案：
- **全局唯一 ID**：Snowflake、Segment ID、UUID
- **分段自增**：Zone A 用奇数 ID，Zone B 用偶数 ID
- **应用层 ID 生成**：业务含义的 ID 天然不冲突

**18-dynamic 的位置**：主键冲突与 18-dynamic 无关。这是数据库设计层面的问题，无论你用不用 18-dynamic，只要做多活写入都需要解决。

### 挑战 5：数据初始化与全量同步

新加一个 Zone 时，需要从现有 Zone 全量同步数据，同时还要不停机接受新写入。

```
阶段 1：全量导出
  Zone A 导出全量数据 → 传输到 Zone B → Zone B 导入
阶段 2：增量追平
  Zone B 开始追阶段 1 期间产生的增量
  通过 binlog 订阅持续消费 Zone A 的变更
阶段 3：切换
  Zone B 完全追平后（复制延迟为零），开始接受流量
```

全量同步的复杂性不止于"一次性的数据搬运"：

1. **持续的增量同步**：全量导出只是第一步。之后需要建立持续的 binlog 订阅/复制通道，保证每个 DDL/DML 变更都能实时同步到新 Zone。这个通道需要监控复制延迟、处理网络闪断、重试失败的 binlog 事件。

2. **位点一致性**：全量导出的快照时间和增量订阅的起始位点必须对齐。如果位点对不准，全量数据和增量数据中间会有 gap 或 overlap。

3. **大事务跳过**：MySQL 的 binlog 是事务级别的，如果一个事务修改了全表（`UPDATE t SET c=1`），这个事务的 binlog 事件可能极大，导致复制通道堆积。

4. **DDL 兼容性**：增量同步期间如果 Zone A 执行了 DDL（ALTER TABLE），Zone B 的同步通道需要按正确的顺序执行这些 DDL。如果 DDL 顺序错了或执行时间不匹配，复制会中断。

5. **失败重试**：全量+增量同步可能持续数天甚至数周。期间任何一次网络中断、磁盘满、连接超时都可能导致同步中断，需要自动重试机制和断点续传。

## 故障转移策略

多活架构的故障转移分几个阶段，每个阶段的难度不同：

### 计划内切换（Planned Switchover）

```
场景：Zone A 要停机升级数据库
流程：
  1. 停止 Zone A 的新流量
  2. 等待 Zone A 的事务全部完成
  3. 等待 Zone A 的数据完全复制到 Zone B
  4. 确认 Zone B 数据完整
  5. 流量全部切到 Zone B
  6. Zone A 停机维护
  7. 维护完成后反向操作切回
```

**难度**：中。人为控制每个步骤，可以在任何时候中止回滚。

### 故障检测（Failure Detection）

这是自动故障转移的前提，也是 18-dynamic 没有实现的部分。

**需要回答的问题**：

1. **是数据库挂了还是网络挂了**？如果是网络分区，两个 Zone 都认为对方挂了，都切为主（脑裂），恢复后很难合并。
2. **是 MySQL 进程挂了还是机器挂了**？MySQL 挂了可以快速重启，机器挂了需要切换。
3. **连续失败几次才算故障**？一次网络抖动不算故障，连续 3 次/slow query 超时才算。
4. **谁来决策**？每个应用实例自己做决策 → 不一致。需要一个"仲裁者"——通常是 ZooKeeper/etcd 或独立的故障检测服务。

```
健康检查周期：
  ┌─────────────────┐
  │ 检测周期: 10s 一次 │
  │ 使用 SELECT 1   │
  │ 或连接池的验证   │
  └────────┬────────┘
           │ 连续失败 3 次
           ▼
  ┌─────────────────┐
  │ 标记为 DEGRADED  │
  │ 触发 failover    │
  └─────────────────┘
```

### 自动故障转移（Automated Failover）

```
故障检测触发后：
  ┌─────────────────────────────────────────────────┐
  │ 1. 确认 Zone A 确实不可用（防止误判）             │
  │    - 多个探测点同时检测                           │
  │    - 不同网络路径                                │
  ├─────────────────────────────────────────────────┤
  │ 2. 决定切换目标                                  │
  │    - 如果有备用 Zone：切换到备用 Zone              │
  │    - 如果是双活：所有流量切到健康 Zone             │
  ├─────────────────────────────────────────────────┤
  │ 3. 执行切换                                      │
  │    - Zone 级别：更新 DNS/GSLB                    │
  │    - 应用级别：更新 ZoneContext                   │
  │    - 数据库级别：执行 slave → master 提升          │
  ├─────────────────────────────────────────────────┤
  │ 4. 确认切换成功                                  │
  │    - 验证新 Zone 可正常读写                       │
  │    - 验证数据完整性                              │
  └─────────────────────────────────────────────────┘
```

### 故障恢复（Failback）

```
Zone A 恢复后：
  ┌─────────────────────────────────────────────────┐
  │ 1. Zone A 先以只读方式加入                        │
  │    - 从 Zone B 追增量数据                         │
  │    - 不接收写流量                                │
  ├─────────────────────────────────────────────────┤
  │ 2. 确认 Zone A 追平                              │
  │    - 检查复制延迟为零                            │
  │    - 做数据完整性校验                            │
  ├─────────────────────────────────────────────────┤
  │ 3. 逐渐回切                                      │
  │    - 先切 10% 的读流量到 Zone A                  │
  │    - 观察一段时间，确认没问题                     │
  │    - 逐步增加比例                                │
  ├─────────────────────────────────────────────────┤
  │ 4. 恢复双活                                      │
  │    - Zone A 恢复写入权限                          │
  │    - 回到正常双活状态                            │
  └─────────────────────────────────────────────────┘
```

**恢复比切换更危险**——很多系统在故障切换后正常运行，但在故障恢复回切时出问题。原因在于两种操作的前提假设不同：

- **切换时**：前提是"当前主库健康，数据是完整的"，所以切换的核心是验证新主库可用、更新路由
- **恢复时**：前提是"故障 Zone 刚恢复，它的数据可能落后了 N 小时的变更"，所以恢复时要先做数据一致性校验——但**校验的前提是假设数据已经不一致了**，而你怎么证明"不一致的范围有多大"是没有标准方法的

此外，恢复涉及流量逐步迁移（10% → 50% → 100%），每个阶段都要观察一段时间，耗时比切换长得多，暴露问题的概率也更高。

## 18-dynamic 的多活设计

回到 18-dynamic 模块本身，看看它的多活设计在真实的多活架构中处于什么位置。

### 它覆盖了什么

```
多活架构全栈：
  接入层：  DNS/GSLB  ← 不在本模块
  网关层：  Spring Cloud Gateway Zone 路由  ← 依赖 17-multiactive
  服务层：  Zone-prioritized LoadBalancer  ← 依赖 17-multiactive
  配置层：  Nacos/etcd 配置同步  ← 依赖外部设施
            ZoneContext 传播  ← 依赖 17-multiactive
  数据库层：
    配置管理：  DynamicJdbcConfig JSON 配置  ← ✅ 本模块
    Zone 感知： ZoneContext → ha-datasource 选择  ← ✅ 本模块
    动态切换：  DynamicDataSource 热替换  ← ✅ 本模块
    ORM 共存：  子上下文隔离 MyBatis/MP/ShardingSphere  ← ✅ 本模块
    故障检测、自动切换、故障恢复：  依赖外部系统触发 ZoneChangedEvent  ← ❌ 不在本模块
  缓存层：  Redis 多活  ← 不在本模块
  消息层：  Kafka MirrorMaker  ← 不在本模块
```

### 它的设计假设

1. **数据库层是多活的最后一公里**——前面的接入、服务、缓存都多活了，最后一层数据库也要跟上。18-dynamic 关注的就是这一层。
2. **一个进程可以同时为多个 Zone 服务**——微服务实例不需要按 Zone 独立部署，单个实例可以处理来自不同 Zone 的请求。这是"多活应用上下文"的前提。
3. **故障转移由外部系统驱动**——本模块仅监听 ZoneContextChangedEvent，不负责检测故障。检测由外部的健康检查系统完成。
4. **配置变更可热更新**——不需要重启，只需要更新配置文件中的 JSON，监听器就能感知并触发重建。

### 它的局限性

从多活架构的角度看，18-dynamic 的主要局限：

**局限 1：Zone 切换是重量级操作**

当前实现切换一个 Zone 需要：
1. 外部系统发布 ZoneContextChangedEvent
2. DynamicDataSource 等收到事件后，重建整个子上下文（Spring 容器 refresh）
3. 旧的子上下文 60s 后才关闭

整个过程秒级完成。对于同城双活（分钟级切换）来说可以接受，但对于请求级路由（每次请求可能来自不同 Zone）就不适用了。

**这是设计取舍，不是缺陷。** 18-dynamic 选择的方案是"完全隔离"——每次切换创建一个全新的 Spring 上下文，保证新上下文的配置与旧上下文完全独立。如果要做请求级路由，需要叠加一层 AbstractRoutingDataSource（如 Q3 所述），但那会失去"完全隔离"的收益。

**局限 2：没有故障检测**

18-dynamic 只能被动响应 Zone 变更，不能主动检测数据库故障。这意味着它需要依赖外部健康检查系统。如果外部系统没有及时检测到故障并更新 ZoneContext，所有请求会继续发给故障数据库。

**这是关注点分离，不是遗漏。** 故障检测是一个独立的问题域——它涉及健康检查、仲裁、防脑裂（一个应用实例不应该独自决定"数据库挂了"）。把这些逻辑放在 18-dynamic 内部会破坏"只做配置热更新"的单一职责。正确的架构是：独立的健康检查系统负责检测故障并更新 ZoneContext，18-dynamic 只负责响应 ZoneContext 的变化。

**局限 3：没有数据一致性保障**

Zone 切换时，18-dynamic 不等待活跃事务完成（对比 my-xhs 的 ConnectionWrapper 模式），也不验证新 Zone 的数据是否完整。如果新 Zone 的数据还没完全追平，会出现"切换成功但是数据不完整"的情况。

**这是设计范围的问题。** 18-dynamic 只有在"数据完整"的前提假设下才应该被触发切换。Zone 切换的决策者（外部健康检查系统）应该在发布 ZoneContextChangedEvent 之前确保数据一致性。如果把一致性验证放在 18-dynamic 内部，职责就重叠了。

**局限 4：不支持灰度切换**

故障恢复时，理想的策略是逐步切流量（先 10%，观察，再到 50%）。18-dynamic 的切换是全有或全无的——Zone 变了，所有请求都走新 Zone。

**同上，这是控制面的职责。** 灰度切换需要在 DNS/GSLB 层或网关层做流量权重控制，不是数据库配置层的责任。

### 它在真实生产中的位置

18-dynamic 更适合作为一个**配置管理+热更新基础层**，而不是一个完整的多活解决方案。在生产中使用时，需要在它的上层补充：

```
                        ┌ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐
                        │      健康检查 / 故障检测系统       │
                        │  (旁路系统，不阻断主数据路径)       │
                        │  检测到故障 → 更新 ZoneContext     │
                        └ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘
                                      │ (ZoneContextChangedEvent)
                                      ▼
┌─────────────────────────────────────────────────────────┐
│                    18-dynamic 模块                        │
│                                                         │
│  ╔═══════════════════════════════════════════════════════╗│
│  ║  配置管理：DynamicJdbcConfig JSON → Zone 感知选择    ║│
│  ║  (读取 ZoneContext → 选择 ha-datasource 对应 zone)  ║│
│  ╚═══════════════════════════════════════════════════════╝│
│                         │                                │
│                         ▼                                │
│  ╔═══════════════════════════════════════════════════════╗│
│  ║  DynamicDataSource：子上下文重建 + 原子切换 + 延迟关闭║│
│  ╚═══════════════════════════════════════════════════════╝│
│                         │                                │
│                         ▼                                │
│  ╔═══════════════════════════════════════════════════════╗│
│  ║  子上下文：HikariCP / ShardingSphere / MyBatis/MP   ║│
│  ╚═══════════════════════════════════════════════════════╝│
└─────────────────────────────────────────────────────────┘
```

### 与 17-multiactive 的分工

18-dynamic 和 17-multiactive 的分工是：

| 能力 | 属于哪个模块 |
|------|------------|
| Zone 概念定义（ZoneContext、ZoneId、Zone 优先级） | 17-multiactive-commons |
| Zone 变更事件发布（ZoneContextChangedEvent） | 17-multiactive-spring |
| Zone 感知的服务发现和负载均衡 | 17-multiactive-spring-cloud |
| Zone 感知的 DataSource 配置选择 | 18-dynamic |
| Zone 变更时的数据库重建 | 18-dynamic |

理解这个分工很重要——18-dynamic 不是"完整的多活框架"，而是 17-multiactive 的"数据库层补充"。17-multiactive 负责 Zone 的定义和传播，18-dynamic 负责让数据库层也加入这个 Zone 体系。

### 回到简历中的"多活架构能力"

在 18-dynamic 综合分析（`18-microsphere-dynamic-analysis.md`）的 Q1 中，我们指出简历中的"多活架构"是部分实现的。现在有了本文的背景，可以更精确地定位：

| 简历声称的能力 | 在多活架构中的位置 | 在本模块中的实现 |
|---------------|-------------------|-----------------|
| 同区域优先 | 配置层（Zone 感知的 DataSource 选择） | `DynamicJdbcConfig.getDataSourcePropertiesList()` 根据 ZoneContext 选择对应 zone 的数据库配置 |
| 故障转移 | 数据库层 + 配置层 | ❌ 依赖外部系统更新 ZoneContext，本模块被动响应 |
| 故障恢复 | 数据库层 + 配置层 | ❌ 同上，无自动回切 |
| 动态更新 | 配置层（热更新） | ✅ DynamicDataSource 事件驱动重建 |

18-dynamic 在多活架构中承担的角色是"配置层在数据库领域的延伸"——它理解 Zone 的概念，能根据 Zone 切换选择正确的数据库配置，并在配置变更时热更新 DataSource。但它不承担故障检测和切换决策的职责（这是多活架构中控制面的工作，通常由独立系统完成）。
