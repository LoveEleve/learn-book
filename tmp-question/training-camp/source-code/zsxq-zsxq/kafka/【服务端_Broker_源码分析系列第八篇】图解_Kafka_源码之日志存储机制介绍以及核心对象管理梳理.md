**02 日志存储机制**

kafka 最终的存储实现方案是底层基于「**日志文件**」的方式来保存生产者发送过来的消息数据。其中每条消息都有一个 「**offset**」值表示它在分区中的偏移量，它唯一确定了分区中的一条消息。

> 注意：这里的 offset 是逻辑值，而不是消息实际存放的物理地址。

![](https://article-images.zsxq.com/FrGsMdYv_IveCNwUbb_Jcl9uCb1t)

为了实现「**高性能**」，Kafka 在底层基于「**顺序追加写日志**」 + 「**稀疏哈希索引查询方式**」来支撑。

## **2.1 顺序追加写日志**

为了可以提高写入的性能，「**同一个分区**」中的消息是「**顺序追加写入**」的，这样就可以避免「**随机写入**」带来的性能问题。

我们都知道在 Kafka 中，消息是按主题 Topic 为基础单位归类的，各个 Topic 在逻辑上是独立的，每个 **Topic** 可以分为**多个分区**，而**每个分区**又会有**多个副本**。当一个分区的副本被选择为 「**Leader 副本**」且被划分到某个 Broker 上时，Kafka 就会在此 Broker 上为该分区建立相应的「**Log**」，所以「**生产者**」发送每条消息时会根据 「**分区规则**」被追加到指定的分区中的「**Log**」中，让「**消费者**」拉取后消费。

在 Kafka 中，消息存储一般都是「**海量**」的，**为了避免日志文件过大**，分区下的「**Log**」并不是直接对应于磁盘上的**一个日志文件**，而是对应磁盘上的**一个目录**「**由配置项 log.dirs 指定**」，而该目录的命名规则是 「**<topic\_name>+横杠+<partition\_id>**」，「**Log**」与「**分区**」之间的关系是一一对应的，**对应分区中的全部消息**都会存储在此目录下的日志文件中。

在这里，我之前画了一张图可以很形象的描述日志存储方式，如下图所示：

![](https://article-images.zsxq.com/FnDPoaG_9_LVjOlLMYsxj-t1zvVp)

 从上图可以看出来，Kafka 是基于「**主题**」+ 「**分区**」 + 「**副本**」+「**分段**」 + 「**索引**」的结构：

这里我们主要来说下，「**分段**」 + 「**索引**」。

在 Kafka 中，**为了避免日志文件过大导致数据定位效率低下**，「**分区**」将通过「**日志分段**」的方式将 「**Log**」 切分为多个 「**LogSegment 日志段**」，相当于一个巨型文件被平均分割为一些相对较小的文件，这样也便于消息的查找、维护和清理。这样在做历史数据清理的时候，直接删除旧的「**LogSegment 日志段**」文件就可以了。

「**LogSegment 日志段**」是一个逻辑上的概念，一个「**LogSegment 日志段**」包含磁盘上 3 个二进制格式的物理文件，一个「**日志文件 .log**」，一个「**位置索引文件 .index**」，一个 「**时间索引文件 .timeindex**」，其中日志文件用于记录消息，索引文件中保存了消息的索引。

随着消息的不断写入，日志段文件的数据量大小到达指定阈值时，就会创建新的日志文件和索引文件继续写入后续的消息和索引信息。

日志文件的文件名的命名规则是\[baseOffset\].log，「**baseOffset**」是日志文件中第一条消息的offset，默认为 00000000000000000000 。

## **2.2 稀疏哈希索引查询方式**

为了提高日志查询消息的效率，每个日志文件都会对应一个「**位置索引文件**」，它建立「**消息偏移量**」到「**物理位置**」的映射关系，这样更方便的定位消息所在物理文件的位置。

「**位置索引文件**」使用 「**稀疏哈希索引方式**」来维护数据，每次间隔特定大小「**1G**」的消息则记录一个「**消息索引**」，其内容为键值对 「**<消息批次最后一条消息偏移量，物理地址>**」的映射关系，如下图所示：

![](https://article-images.zsxq.com/FsmRpfy6l37q-eKJEGYnHAfttpIm)

这里需要注意的是：「**位置索引文件**」其实是使用了相对偏移量「**relativeOffset**」，每个位置索引文件都有一个 「**baseOffset**」，所以「**位置索引文件**」真正的偏移量为 「**baseOffset**」 + 「**relativeOffset**」。

如上图所示那样，00000000000012768089.index 「**位置索引文件**」的「**baseOffset**」为 12768089，要找 「**offset: 1115**」，需要先从「**位置索引文件**」中定位到第二个索引条目 「**offset: 1113, position: 1732**」，然后从「**日志文件**」中定位对应的物理地址位置。

## **3.2 LogManager 对象**

接下来，当日志消息请求被写入服务端后，**那么问题来了，底层是如何处理接收上来的日志批次的呢？**对应的管理类对象就是 「**LogManager**」，它是 Kafka 的日志管理组件。

主要功能包括 「**加载 Log**」、「**创建 Log**」、「**删除 Log**」、「**查询 Log**」以及 「**周期性任务**」。

其中周期性任务包括以下 4 个任务：

1.  **日志刷盘任务**：kafka-log-flusher。
2.  **日志保留任务**：log-retention。
3.  **日志检查点刷新任务**：kafka-recovery-point-checkpoint、kafka-log-start-offset-checkpoint。
4.  **日志清理任务**：kafka-delete-logs。

## **3.3 Log 对象**

接下来，日志数据被接收并写入服务端，被「**LogManager**」处理后，会「**创建 Log**」，也就是本篇的第二部分内容，知道了在 Kafka Broker 端存储的文件主要以「**日志段文件**」和「**日志索引文件**」为主，**那么问题来了**，「**日志段文件**」和「**日志索引文件**」是如何被管理的呢？「**Log**」日志对象是 Kafka 服务端源码最核心的部分，它是 「**LogSegment 日志段**」的容器，定义了很多管理日志段的操作。

其内部包含以下几种常见操作：

1.  **高水位管理**：对高水位概念的定义以及对高水位的各种操作，比如：设置高水位、读取高水位、更新高水位等。
2.  **日志段管理**：对日志段的增删改查操作，了解日志是如何对日志段进行管理的。
3.  **关键位移值管理**：主要针对 LEO、LSO 位移值的管理。
4.  **日志读写操作**：日志读写操作，这是 Kafka 消息中间件的基石。

## **3.4 LogSegment 对象**

接下来，日志被「**LogManager**」处理并写入到「**日志段文件**」后也就基本算完成了日志的存储过程，因为「**日志段文件**」是 Kafka 保存消息的最小载体。

对日志段源码研究是我们学习并吸收「**工业生产级高性能日志存储软件**」的核心设计理念以及精华所在。

其中包括「**消息日志文件**」、「**位移索引文件**」、「**时间戳索引文件**」、「**已终止事务文件**」等，这里我们会重点学一下 「**FileRecords**」类的实现，它是 Kafka 中底层如何保存消息的具体实现类。

最终，日志也会被写入到 「**位移索引文件**」、「**时间戳索引文件**」中，这势必会产生索引项，在这部分我们会学习 Kafka 底层是如何高效进行检索日志的，即 「**稀疏哈希索引**」是如何高效设计和管理的，最后会对比下这 2 种索引文件的区别。
