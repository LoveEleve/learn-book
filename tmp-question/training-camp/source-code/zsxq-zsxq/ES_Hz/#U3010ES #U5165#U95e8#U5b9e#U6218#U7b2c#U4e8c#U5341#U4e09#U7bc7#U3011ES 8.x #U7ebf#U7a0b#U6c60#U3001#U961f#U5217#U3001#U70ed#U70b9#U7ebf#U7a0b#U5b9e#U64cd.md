**02 ES 8.x 线程池&队列架构设计**

Elasticsearch 使用线程池（Thread pool ）来管理请求并优化集群中每个节点上的资源使用。

## **2.1 ES 8.x 线程池用途**

Elasticsearch中主要的线程池有：

1.  搜索线程池（search）：处理搜索请求。
2.  索引线程池（index）：处理索引文档的请求。
3.  写入线程池（write）：处理索引/删除/更新请求。
4.  查询线程池（get）：处理实时的GET请求。
5.  分析线程池（analyze）：处理分析请求。
6.  批量线程池（bulk）：处理批量操作。
7.  刷新线程池（refresh）：处理刷新操作，使文档可见。
8.  其他线程池如：merge（段合并）、snapshot（快照）等。

## **2.6 线程池&队列认知**

### **2.6.1 必要时设置 processors**

值得注意的是，线程池是根据 ES 在基础硬件上检测到的线程数（number of processors）设置的。如果检测失败，则应在 elasticsearch.yml 中显式设置硬件中可用的线程数。

特别是在一台宿主机配置多个 ES节点实例的情况下，若要修改其中一个节点线程池或队列大小，则要考虑配置 processors 参数。

elasticsearch.yml 中设置如下所示：

processors: 4

PS：Linux 查看线程数方法：

grep 'processor' /proc/cpuinfo | sort -u | wc -l

### **2.6.2 线程池关联队列设置**

大多数线程池具有与之关联的队列，以使 ES 可以将请求存储在内存中，同时等待资源变得可用来处理请求。

但是，队列通常具有有限的大小，如果超过该大小，ES 将拒绝该请求。

### **2.6.3 不要盲目修改队列大小**

有时你可能会增加队列的大小以防止请求被拒绝，但要结合资源实际进行修改，千万别盲目修改。

实际上，如果值设置的非常大，甚至可能适得其反。因为通过设置更大的队列大小，该节点将需要使用更多的内存来存储队列，这就意味着将剩下相对较少的内存来响应和管理实际请求。

此外，增加队列大小还会增加将操作响应保留在队列中的时间长度，从而导致客户端应用程序面临超时问题。

### **2.6.4 加强监控**

通常，唯一有需要增加队列大小的情况是：在请求数量激增导致无法在客户端管理此过程且资源使用率并未达到峰值。

## **03 ES 8.x 热点线程架构设计**

## **3.1 ES 热点线程是什么**

实战业务场景中，当我们遇到集群响应比平常慢且 CPU 使用率高时，我们需要做问题排查，找到根因集群才能恢复如丝般流畅。

### **4、hot\_threads支持的参数**

1.  ignore\_idle\_threads（可选，布尔值）
2.  如果为true，则会过滤掉已知的空闲线程（例如，在套接字选择中等待，或从空队列中获取任务）。默认为true。
3.  interval（可选，时间单位）执行热点线程的采样间隔。默认为500毫秒。
4.  snapshots（可选，整数）它是要获取的堆栈跟踪（在特定时间点嵌套的方法调用序列）数量。默认为10。![](images/FqxxYj06y4dpr6H6MdQjSqBCI_-T.png)
5.  threads（可选，整数）查看由type参数确定的信息，ElasticSearch将采用指定数量的最“热门”线程。
6.  最“热门”的线程，往往就是我们的问题所在。默认为3。也就是返回TOP 3 热点线程。![](images/FiGucjPmqRisGbEzUBn3wxyS7ZBQ.png)
7.  master\_timeout（可选，时间单位）指定等待连接到主节点的时间段。
8.  如果在超时到期之前未收到任何响应，则请求将失败并返回错误。
9.  默认为30秒。
10.  timeout（可选，时间单位）指定等待响应的时间段。
11.  如果在超时到期之前未收到任何响应，则请求将失败并返回错误。
12.  默认为30秒。
13.  type（可选，字符串）要采样的类型。默认为：cpu。
14.  可用的选项是：
15.  1）block ——线程阻塞状态的时间。
16.  2）cpu ——线程占据CPU时间。
17.  3）wait ——线程等待状态的时间。

### **7、hot\_threads API 执行原理**

与其他返回 JSON 结果的 API 不同，Hot Threads API返回格式化的文本，你可以在其中区分几个部分。

在看返回堆栈结果信息之前，先看一些有关Hot Threads API背后的逻辑原理知识。

1.  ES接收所有正在运行的线程，并收集有关每个线程所花费的 CPU 时间，特定线程被阻塞或处于等待状态的次数，被阻塞或处于等待状态的时间等各种信息。
2.  然后等待特定的时间间隔 interval（由时间间隔参数指定）后，ES 再次收集相同的信息，并根据运行的时间（降序）对热点线程进行排序。注意，上述时间是针对 type 参数指定的给定操作类型统计的。
3.  之后，由 ES分析前 N 个线程（其中 N 是由线程参数 threads 指定的线程数）。ES所做的是每隔几毫秒就会捕获线程堆栈跟踪的快照（快照数量由快照参数 snapshot 指定）。
4.  最终：对堆栈跟踪进行分组以可视化展示线程状态的变化，就是我们看到的执行API 返回的结果信息。

以上内容，再把 hot\_threads API 的相关参数串联起来，相信你会对 hot\_threads 有大致的了解。

### **3.4.1.2 reject 拒绝请求的原因**

如果 ES集群开始拒绝索引/写入（index）请求，则可能有多种原因。

1.  通常表明一个或多个节点无法跟上索引 / 删除 / 更新 / 批量请求的数量，从而导致在该节点上建立队列且队列逐渐累积。
2.  一旦索引队列超过队列的设置的最大值（如 elasticsearch.yml 定义的值或者默认值），则该节点将开始拒绝索引请求。
3.  排查方法：需要检查线程池的状态，以查明索引拒绝是否总是在同一节点上发生，还是分布在所有节点上。

GET /\_cat/thread\_pool?v

1.  如果 reject 仅发生在特定的数据节点上，那么您可能会遇到负载平衡或分片问题。
2.  如果 reject 与高 CPU 利用率相关联，那么通常这是 JVM 垃圾回收的结果，而 JVM 垃圾回收又是由配置或查询相关问题引起的。
3.  如果集群上有大量分片，则可能存在过度分片的问题。
4.  如果观察到节点上的队列拒绝，但监控发现 CPU 未达到饱和，则磁盘写入速度可能存在问题。

### **3.4.1.3 写入 bulk 值要递进步长调优**

不要妄图快速提高写入速度，一下调很大，很大势必会写入 reject。首先尝试一次索引 100 个文档，然后索引 200 个，再索引 400 个，依此类推...... 当索引写入速度（indexing rate）开始趋于平稳时，便知道已达到数据批量请求的最佳大小。

if \[ "$threads" -gt 0 \] 2>/dev/null; then

utilization=$((active \* 100 / threads))

else

utilization=0

fi

\# 根据状态添加表情符号

if \[ "$rejected" -gt 0 \]; then

prefix="🔴"

elif \[ "$queue" -gt 100 \]; then

prefix="🟡"

elif \[ "$utilization" -gt 80 \]; then

prefix="⚡"

else

prefix="✅"

fi

printf "%-20s %-6s %-6s %-8s %-9s\\n" \\

"${prefix} ${name}" "$active" "$queue" "$rejected" "${utilization}%"

done | head -15

echo ""

\# 2. 系统负载概览

echo "📈 系统负载概览"

echo "--------------------------------------------------------"

show\_system\_overview

echo ""

\# 3. 热点线程检测

echo "🔥 热点线程检测"

echo "--------------------------------------------------------"

show\_hot\_threads

echo ""

\# 4. 性能建议

echo "💡 性能建议"

echo "--------------------------------------------------------"

show\_performance\_tips

sleep 5

done

}

show\_system\_overview() {

\# 获取集群健康状态

local health\_status

health\_status=$(curl -s -u elastic:elastic -X GET "localhost:9200/\_cluster/health" 2>/dev/null)

if \[ $? -eq 0 \]; then

local status=$(echo "$health\_status" | grep -o '"status":"\[^"\]\*"' | cut -d'"' -f4)

local node\_count=$(echo "$health\_status" | grep -o '"number\_of\_nodes":\[0-9\]\*' | cut -d':' -f2)

local pending\_tasks=$(echo "$health\_status" | grep -o '"number\_of\_pending\_tasks":\[0-9\]\*' | cut -d':' -f2)

case $status in

"green") status\_icon="🟢" ;;

"yellow") status\_icon="🟡" ;;

"red") status\_icon="🔴" ;;

\*) status\_icon="⚪" ;;

esac

echo "集群状态: ${status\_icon} $status | 节点数: $node\_count | 待处理任务: ${pending\_tasks:-0}"

else

echo "❌ 无法获取集群状态"

fi

\# 获取关键线程池统计

local total\_active total\_queue total\_rejected

total\_active=$(echo "$thread\_pool\_data" | awk 'NR>1 {sum += $2} END {print sum}')

total\_queue=$(echo "$thread\_pool\_data" | awk 'NR>1 {sum += $3} END {print sum}')

total\_rejected=$(echo "$thread\_pool\_data" | awk 'NR>1 {sum += $4} END {print sum}')

echo "总活跃线程: $total\_active | 总队列任务: $total\_queue | 总拒绝任务: $total\_rejected"

}

show\_hot\_threads() {

local hot\_output

hot\_output=$(curl -s -u elastic:elastic -X GET "localhost:9200/\_nodes/hot\_threads?threads=3&interval=1s&type=cpu" 2>/dev/null)

if \[ $? -eq 0 \] && \[ -n "$hot\_output" \]; then

\# 提取热点线程信息

echo "$hot\_output" | grep -E "(\[0-9\]+\\.\[0-9\]+)%|thread.\*elasticsearch" | head -6 | while read -r line; do

if \[\[ "$line" =~ (\[0-9\]+\\.\[0-9\]+)% \]\]; then

cpu\_usage="${BASH\_REMATCH\[1\]}"

if (( $(echo "$cpu\_usage > 10.0" | bc -l 2>/dev/null) )); then

echo "🔴 $line"

elif (( $(echo "$cpu\_usage > 5.0" | bc -l 2>/dev/null) )); then

echo "🟡 $line"

else

echo "🟢 $line"

fi

else

echo " $line"

fi

done

else

echo "✅ 无显著热点线程"

fi

}

show\_performance\_tips() {

\# 基于当前状态的性能建议

high\_queue\_pools=$(echo "$thread\_pool\_data" | awk 'NR>1 && $3 > 100 {print $1}')

local high\_util\_pools

high\_util\_pools=$(echo "$thread\_pool\_data" | awk 'NR>1 && $5 > 0 && ($2 / $5) > 0.8 {print $1}')

if \[ -n "$high\_queue\_pools" \]; then

echo "⚠️ 队列积压: $high\_queue\_pools - 考虑增加队列大小"

fi

if \[ -n "$high\_util\_pools" \]; then

echo "⚡ 高利用率: $high\_util\_pools - 考虑增加线程数"

fi

if \[ -z "$high\_queue\_pools" \] && \[ -z "$high\_util\_pools" \]; then

echo "✅ 系统运行正常，无需立即优化"

fi

}
