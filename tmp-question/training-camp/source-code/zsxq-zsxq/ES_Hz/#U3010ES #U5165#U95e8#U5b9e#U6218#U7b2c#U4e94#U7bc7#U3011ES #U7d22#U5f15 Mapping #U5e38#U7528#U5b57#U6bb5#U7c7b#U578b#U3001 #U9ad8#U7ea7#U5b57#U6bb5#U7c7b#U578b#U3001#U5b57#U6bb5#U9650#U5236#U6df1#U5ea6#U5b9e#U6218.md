## **2.1 ES 索引 Mapping 简单回顾**

在正式实操之前，我们来回顾下 ES 索引 Mapping 相关概念和字段数据类型。

### **2.1.1 ES 索引 Mapping 概念**

Mapping 定义了 ES 索引中文档有哪些字段及其类型、这些字段是如何存储和索引的。每个文档都是一个字段的集合，每个字段都有自己的数据类型。

比如上篇我们定义的 sku 商品索引，其有 skuId、skuName、brand、category、price、vipPrice 等字段。所以 Mapping 的作用主要有：

1.  定义了索引中各个字段的名称和对应的类型。
2.  定义各个字段、倒排索引的相关设置。如使用某字段使用什么分词器等。

## **2.2 ES 索引 Mapping 常用字段类型实战**

### **2.2.1 字符串类型**

从 ES 7.x 之后的版本中，字符串类型只有 keyword 和 text 两种了，旧版本的 string 类型已不再支持。

![](images/FtPEbij2EVs4NczCscuSE2iZicBQ.png)

1.  keyword 单分词类型适合存储简短、结构化的字符串，比如商品 ID、品牌、分类等，其适合用于「**聚合**」、「**过滤**」、「**精确查询**」等。![](images/FrTXcTXpskv65OCYRi1M0AjnbNC2.png)
2.  text 多分词类型的字段适合存储全文本数据，比如商品名称、商品介绍、商品详情等。text 的类型数据将会被「**分词器**」进行分词，最终成为一个个「**词项**」存储在「**倒排索引**」中。不支持精确匹配：由于分词无法用 term 查询精确匹配原字符串（除非使用未分词的子字段），其默认的「**分词器**」为 standard，它主要用于需要「**分词检索/全文检索**」的场景，支持 match、match\_phrase 等查询，中文的分词器有「**ik\_smart**」、「**ik\_max\_word**」。不支持聚合和排序：如果需要，通常使用多字段（multi-fields）同时定义为 keyword。![](images/FrMG770gmnKUgymZQ9h1lkV9Z1nx.png)

> 这里需要注意的是：比如你分词用的分词器是 ik\_smart，那么查询时也要用 ik\_smart，不然会造成前后两个分词器进行分词的内容不一样，导致查询结果不正确的情况，对于新手来说，很容易犯这个错误，切记切记！

这里暂不安装中文分词器，后续篇章单独实操。

### **2.2.1 数值类型**

ES 中，数值类型分为 byte、short、integer、long、float、double、half\_float、scaled\_float、unsigned\_long。

![](images/Fg4RDUQ57RuIQvsFIJDk2QWOX5KT.png)

在满足需求的前提下，应当选择尽可能小的数据类型，除了可能会减少存储空间外，也会提高索引数据和检索数据的效率。

### **2.2.1.1 整数类型**

1.  Long 类型
2.  空间占用：64bit == 8字节
3.  范围区间：-2^63-2^63-1
4.  Unsigned Long 类型
5.  空间占用：64bit == 8字节
6.  范围区间：0~ 2^64-1
7.  Integer 类型
8.  空间占用：32bit == 4字节
9.  范围区间：-2^31-2^31-1
10.  short 类型
11.  空间占用：16bit == 2字节
12.  范围区间：-32768~32767
13.  Byte 类型
14.  空间占用：8bit == 1字节
15.  范围区间：-128~127

### **2.2.1.2 浮点数类型**

浮点数类型：

1.  double：双精度类型，长度很长，达到科学计数法。
2.  float：单精度类型。
3.  half\_float：是一种 16 位的半精度浮点数，限制为有限值。
4.  scaled\_float：缩放类型的浮点数，「**如果做聚合统计需求一定要用这个类型**」，背后基于 Long 类型实现，会出现精度问题。

注意：

1.  浮点类型精确统计会出现精确性问题。
2.  Java 底层实现问题。
3.  使用整数类型来避免精度问题。

### **2.3.4 嵌套类型**

在现实的应用场景中，关系型模型是普遍存在的，例如商品与商家的关系，用户和用户对商品评价的关系。在传统的关系型数据库领域，想要表达关系型模型是非常自然的，但在 ES 里要处理这个事情就并不那么简单了。

  
在 ES 中可以保存关系型模型数据的方式主要有以下两种：

1.  nested：在这种方式中，会将一对多的关系保存在同一个文档中。
2.  join（Parent / Child） ：通过维护文档的父子关系，将两个对象分离。

上述的这两种方式都可以描述一对多的关系，这里我们先来看下 nested 方式和优缺点和适用场景，父子关系比较鸡肋，不建议使用，这里就不展开了。

nested 类型是一种特别的 object 数据类型，其允许数组中的对象可以被「**单独索引**」，使它们可以被「**独立地检索**」。

下面我们先使用普通的 object 数组来保存商品与商家的一对多关系，我们看看会产生什么问题。创建 Mapping 索引，这里是静态 Mapping：

\# 创建 Mapping

PUT huazai\_ecshop\_sku\_seller\_index

{

"mappings": {

"properties": {

"skuId": {

"type": "integer"

},

"seller": {

"properties": {

"first\_name": {

"type": "keyword"

},

"last\_name": {

"type": "keyword"

}

}

}

}

}

}

![](images/FvxK6hCF6_WSeIkQmqjz5GD26ibB.png)

接着，写入一条数据：

\# 写入关系数据

PUT huazai\_ecshop\_sku\_seller\_index/\_doc/1

{

"skuId": 40021,

"seller": \[

{ "first\_name": "zhang", "last\_name": "san" },

{ "first\_name": "li", "last\_name": "si" }

\]

}

![](images/FsqRR4APlLy_CzpOoKN0XQXHuywp.png)

如上面的示例，我们创建了 huazai\_ecshop\_sku\_seller\_index 索引，其中 seller 字段是一个对象，包含了 first\_name 和 last\_name 两个属性。并且我们写入数据的时候，商品的商家有两个（描述了一对多的关系）：zhangsan 和 lisi。

下面我们来查询：

GET huazai\_ecshop\_sku\_seller\_index/\_search

{

"query": {

"bool": {

"must": \[

{ "term": { "seller.first\_name": "zhang" } },

{ "term": { "seller.last\_name": "si" } }

\]

}

}

}

  
![](images/FrLFSdFPg4_GWG7d1Yi77CI-Kit3.png)

  
如上查询，你会发现数据中是没有 zhangsi 这个商家的，但是这个查询却可以命中文档 1，跟我们预期的不一样。

为什么呢？因为 object 被扁平化处理后，其丢失了 first\_name 和 last\_name 之间的关系，变成了下面这样的关系：

{

"skuId": 40021,

"seller.first\_name": \["zhang", "li"\],

"seller.last\_name": \["san", "si"\]

}

对于这个扁平化数组，原先 first\_name 和 last\_name 间的对应关系已经不复存在了。所以我们的查询语句在 seller.first\_name 中匹配了 "zhang"，在 seller.last\_name 匹配了 "si"，自然而然就命中了文档 1。

那有什么办法可以维护这个关系吗？答案是使用 nested 数据类型。

「**使用 nested 数据类型可以使对象数组种地对象被单独索引**」，这样 first\_name 和 last\_name 间的对应关系就不会丢失了。

我们来修改一下 Mapping，把 seller 的类型定义为 nested：

DELETE huazai\_ecshop\_sku\_seller\_index

\# 创建 mapping, seller 类型为 nested

PUT huazai\_ecshop\_sku\_seller\_index

{

"mappings": {

"properties": {

"skuId": {

"type": "integer"

},

"seller": {

"type": "nested",

"properties": {

"first\_name": {

"type": "keyword"

},

"last\_name": {

"type": "keyword"

}

}

}

}

}

}

![](images/FgAWD_oZfadLo9GlSPun4psqHQi5.png)

如上，我们在 seller 中指定了这个对象的类型为 nested，在内部 nested 类型将数组中的每个对象索引为单独的隐藏文档，这样数组中的每个对象就可以被「**独立地检索**」了。

接着，写入一条数据：

PUT huazai\_ecshop\_sku\_seller\_index/\_doc/1

{

"skuId": 40021,

"seller": \[

{

"first\_name": "zhang",

"last\_name": "san"

},

{

"first\_name": "li",

"last\_name": "si"

}

\]

}

![](images/Fk0qfQbxdd_L7MBSuWIVX7oU-vg4.png)

"seller.first\_name": "li"

使用 nested 关键字指定一个 nested 对象的查询，使用 path 指定 nested 对象的名字。从上面的示例来看，nested 通过冗余的方式将对象和文档存储在一起，所以查询时的性能是很高的，但在需要更新对象信息的时候需要更新所有包含此对象的文档，例如某个商家的信息更改了，那么所有这个商家的商品文档都要更新。

因此，nested 适合「**查询频繁但是更新频率低**」的场景**。**

**2.3 ES 索引 Mapping 字段限制**

关于 ES 索引 Mapping 字段限制如下：

1.  索引字段数量限制
2.  映射爆炸限制
3.  索引字段长度与深度限制
4.  数据类型相关限制
5.  动态映射的潜在风险
6.  硬性资源限制

### **2.3.1 索引字段数量限制**

这是最直接、最常见的限制。Elasticsearch 并非不能处理大量字段，但字段过多会带来显著的开销。

1.  问题根源：
2.  内存开销：Lucene（ES 的底层引擎）的核心数据结构是“倒排索引”。每个字段都有自己的倒排索引、字典（Term Dictionary）和文档值（Doc Values）。这些结构都需要加载到内存（文件系统缓存）中以实现高效搜索和聚合。字段越多，内存消耗越大。
3.  性能下降：大量的字段会导致映射（Mapping）元数据变得非常庞大。在创建新文档、执行搜索或聚合时，处理这些元数据会增加 CPU 和内存的开销。
4.  熔断器风险：容易触发下一节要提到的“映射爆炸”熔断器。
5.  实际限制：
6.  没有绝对的硬性数字：官方从未规定一个确切的数字（如 1000 个字段）。性能拐点取决于你的硬件资源（特别是内存）、文档大小和查询复杂度。
7.  经验值：通常，建议将字段数量控制在 几百到一千 以内。一旦超过几千个，就需要非常小心地评估和优化。
8.  默认熔断器：ES 默认设置了一个索引最大字段数为 1000。这是一个软限制，旨在防止意外创建过多字段。

### **2.3.2 映射爆炸限制**

这是字段数量限制的延伸和强化，旨在防止一个恶意或错误的请求摧毁整个集群。

1.  问题场景：想象一个场景，你的索引启用了动态映射（"dynamic": true）。如果有一个包含大量随机键值对（例如，HTTP 请求头、随机生成的用户数据）的文档被写入，它会瞬间创建成百上千个新字段，耗尽节点内存，导致节点崩溃。
2.  相关设置：
3.  index.mapping.total\_fields.limit：单个索引中的最大字段数，默认 1000。
4.  index.mapping.depth.limit：字段的最大深度（防止过于复杂的嵌套 JSON），默认 20。
5.  index.mapping.nested\_fields.limit：嵌套类型（nested）字段的最大数量，默认 50。因为每个嵌套对象都被索引为一个独立的隐藏文档，开销很大。
6.  index.mapping.nested\_objects.limit：单个文档中所有嵌套类型字段所能包含的最大嵌套对象总数，默认 10000。
7.  index.mapping.field\_name\_length.limit：字段名称的最大长度限制，默认 Long.MAX\_VALUE（实际上非常长，但设置太长的名称不推荐）。
8.  index.mapping.dimension\_fields.limit：它是 Elasticsearch 7.13+ 版本引入的关键特性限制，专为 ​时间序列数据（如指标和日志）​​ 设计的。

![](images/Fs4anOhFVEM4u_i6nZUemheXbiDJ.png)

### **2.3.3 索引字段长度与深度限制**

1.  字段名长度：虽然限制很高，但过长的字段名（如 very\_long\_and\_descriptive\_field\_name\_that\_is\_self\_explanatory）会显著增加映射和传输数据的开销。建议使用简短、清晰的字段名。
2.  字段深度：指的是 JSON 结构的嵌套层级。

{

"level1": {

"level2": {

"level3": { // 深度为 3

"value": "data"

}

}

}

}

1.  过深的嵌套会让查询和聚合变得复杂且低效。默认深度限制为 20，通常足够了。

### **2.3.4 数据类型相关限制**

某些特定的数据类型有其自身的限制。

1.  keyword 类型：
2.  长度限制：ignore\_above 参数。默认情况下，超过 256 个 UTF-8 编码字节的字符串不会被索引（即无法被搜索或聚合），但原始数据仍然会存储在 \_source 中。

"ignore\_above": 512 // 可以自定义调整

}

1.  影响：这可以防止极其长的字符串（如文件内容、大段 Base64）被加入倒排索引，从而节省大量内存。
2.  text 类型：
3.  分析器限制：text 字段会被分词，分词后的词项（terms）数量受限于分析器（Analyzer）和原始文本长度。一个非常长的句子可能会产生成千上万个词项，增加索引大小。
4.  Term 长度限制：Lucene 内部对单个 Term 的长度也有限制（约 32KB）。

### **2.3.5 动态映射潜在风险**

这本身不是一个“限制”，但如果不加管理，它是导致触发上述所有限制的最主要原因。

1.  风险：默认的动态映射行为会自动为每个新出现的字段创建映射并推断其类型。这非常方便，但也非常危险，容易导致“映射污染”（Mapping Pollution）或“映射爆炸”（Mapping Explosion）。
2.  解决方案：
3.  显式映射：在创建索引时，为核心业务字段预定义好映射。这是最佳实践。
4.  严格控制动态映射：
5.  设置为 "dynamic": "false"：忽略未映射的新字段（不索引，但存储在 \_source 中）。
6.  设置为 "dynamic": "strict"：遇到未映射的新字段时，直接抛出异常，拒绝写入文档。这是最严格、最安全的方式。
7.  使用 flattened 数据类型：如果你确实需要存储大量不可预知的键值对（例如标签、HTTP 头、自定义属性），flattened 类型是完美的解决方案。它将整个子对象的所有值索引为一个“超级”字段，极大地节省内存并避免映射爆炸。

### **2.3.6 硬性资源限制**

最终，所有限制都归结为硬件的限制。

1.  堆内存：ES 节点的堆内存主要用于管理映射元数据、查询计算等。映射越大，可用堆内存就越少。
2.  文件系统缓存：Lucene 依赖文件系统缓存来高效访问索引数据。字段越多，索引文件越大，对文件系统缓存的需求就越高。如果缓存不足，搜索性能会急剧下降（产生磁盘 I/O）。

### **2.3.7 总结**

![](images/Fp4LVKxwppfngYFjj7pQ-oS5tufB.png)

1.  规划你的映射：像设计数据库表结构一样设计你的 ES 映射。这是最重要的第一步。
2.  禁用或严格管控动态映射：生产环境设置为 "dynamic": "strict"。
3.  善用 flattened 类型：处理未知的、稀疏的数据。
4.  监控字段数量：通过 GET /my\_index/\_mapping 定期查看，确保字段数在健康范围内。
5.  合理使用多字段：但注意，一个字段定义多个数据类型（如 text 和 keyword）也会增加字段计数。
