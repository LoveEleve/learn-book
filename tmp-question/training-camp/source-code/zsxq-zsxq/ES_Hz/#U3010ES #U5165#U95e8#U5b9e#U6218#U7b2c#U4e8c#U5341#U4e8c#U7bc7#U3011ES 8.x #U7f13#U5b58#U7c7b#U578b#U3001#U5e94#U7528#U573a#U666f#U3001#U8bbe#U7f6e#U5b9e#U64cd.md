## **2.1 节点级缓存**

### **2.1.1 PageCache 缓存**

操作系统级别的缓存，用于缓存磁盘上的数据。Elasticsearch 依赖于操作系统的页面缓存来快速访问索引文件。当节点重启时，页面缓存会丢失。

![](images/Fh4IR-vsgY2rmSNxPq01HLArn5AO.png)

### **2.1.1.1 应用场景**

1.  操作系统级别的文件缓存
2.  加速索引段、doc\_values 的读取操作、倒排索引的访问操作
3.  对搜索和聚合性能有重大影响

### **2.1.2 JVM 堆内存之字段数据缓存(FileData Cache)**

在字段上排序、聚合或者脚本访问字段值时，将字段数据加载到内存中。注意，字段数据缓存是针对分片级别的，并且构建成本很高，因此需要谨慎使用。默认text字段的字段数据缓存是关闭的，因为text字段通常经过分词，不适合直接用于排序和聚合。

![](images/FtdNKZ8VY0bzk9o9nKuxBMZRZjQ7.png)

### **2.1.2.1 应用场景**

1.  ✅ 必须使用场景：
2.  文本字段的排序（text field sorting）
3.  文本字段的聚合（terms aggregation on text）
4.  脚本中访问文本字段的分析结果
5.  对分析字段（analyzed text fields）进行聚合时必需
6.  ❌ 避免使用场景：
7.  高基数字段（如email、ID）：避免对唯一值过多的文本字段聚合
8.  大文本字段（如文章内容）：会导致内存爆炸
9.  内存受限的环境：必须设置合理的内存限制
10.  ​在高基数字段上深度分页​：性能极差

### **2.1.2.2 设置实操**

1.  默认不开启，需要在映射中显式设置"fielddata": true。
2.  建议使用keyword类型代替文本字段的fielddata，因为keyword类型使用doc values（正排索引，磁盘结构），更节省内存。
3.  字段数据缓存的大小默认是无限制的，但可以通过indices.fielddata.cache.size来设置节点级别的限制，例如：indices.fielddata.cache.size: 20%（堆内存的20%）。
4.  如果必须使用，可以设置缓存大小限制和断路器，超过会报错）。
5.  也可以通过映射设置"eager\_global\_ordinals": true来预加载全局序数，加快聚合速度。

我们先来修改 elasticsearch.yml：

### **2.1.4 节点查询缓存(Node Query Cache)**

缓存查询结果中每个分片的查询结果。主要针对Filter上下文查询，因为Filter查询的得分是固定的适合缓存。当相同的过滤条件再次出现时，可以直接使用缓存，避免重新计算。

> 注意，只有被频繁使用的Filter查询才会从缓存中受益。这里缓存的是查询阶段（query phase）的结果，即满足查询条件的文档ID集合（bitset）。主要用于频繁使用的查询条件，尤其是过滤查询（filter context），因为filter context的查询结果不计算相关性得分，可以缓存。

查询缓存（Query Cache）主要用于缓存查询结果，但并不是所有的查询都会使用查询缓存。关于ES查询缓存的要点：

1.  查询缓存只缓存在Filter上下文中使用的查询（例如：在bool查询的filter子句中的查询）。因为Filter上下文查询的结果是二元的（是否匹配），并且不计算相关性分数，因此可以缓存。
2.  查询缓存是节点级别的，每个节点有一个查询缓存，被该节点上的所有分片共享。
3.  默认情况下，查询缓存是开启的，但是每个查询默认并不使用缓存。你需要在查询时通过设置"cache": true来显式开启对某个查询的缓存。
4.  查询缓存使用LRU（最近最少使用）策略来淘汰缓存。
5.  如果索引的数据频繁更新，那么查询缓存的效率会很低，因为任何索引的更改都会使相关的缓存失效。

![](images/FnXsjnM4BeFtdd9R2_VYxL_71zyq.png)

### **2.1.4.1 应用场景**

1.  ✅ 适合场景：
2.  频繁的过滤条件（status=active, category=electronics）
3.  范围查询（date >= '2025-01-01'）
4.  权限过滤（user\_id = 123）
5.  ❌ 不适合场景：
6.  全文搜索（match query）
7.  评分查询（带有boost）
8.  数据频繁更新的索引

### **2.1.4.2 设置实操**

节点查询缓存大小默认是堆内存的10%，可以通过[indices.queries.cache.size](http://indices.queries.cache.size/)设置。例如，设置为堆内存的20%：indices.queries.cache.size: 20%。

修改 elasticsearch.yml配置：

\# elasticsearch.yml 配置

indices.queries.cache.size: 10% \# 默认堆内存的10%

indices.queries.cache.count: 10000 \# 缓存条目数

1.  默认开启，缓存大小默认为堆内存的10%。注意，这是一个节点级别的设置。
2.  可以通过索引设置 index.queries.cache.enabled 来控制单个索引的启用状态（true/false）。
3.  只有在过滤查询（如term、range、bool filter）时使用。
4.  每个段（segment）的缓存信息，段合并后缓存失效。

## **2.2 查询执行缓存**

### **2.2.1 分片请求缓存(Shard Request Cache）**

缓存整个分片的查询结果，包括聚合结果。但默认只缓存结果集较大的请求（如超过10%的文档被命中），并且只缓存那些不会立即过时的数据（如size:0的搜索请求）。当分片数据没有变化时，缓存可以重用。

> 注意，默认情况下，请求缓存是关闭的，因为它只缓存size:0的请求。

![](images/Fh-XtDnN8TX9oKSgdo-N9oMJLtK_.png)

###   
**2.2.1.1 应用场景**

1.  ✅ 适合场景：
2.  监控仪表板聚合查询
3.  报表生成（size: 0的查询）
4.  数据不频繁变化的索引
5.  实时性要求不高的统计
6.  ❌ 不适合场景：
7.  数据频繁更新的索引
8.  需要返回大量文档的查询
9.  实时搜索

### **2.2.1.2 设置实操**

全局默认值可以通过修改 elasticsearch.yml 配置：

\# elasticsearch.yml

indices.requests.cache.size: 3% \# 默认1%，可适当调大

indices.requests.cache.expire: null \# ES 8.x 不支持过期时间

### **2.2.2 聚合缓存(Aggregation Cache）**

### **2.2.2.1 应用场景**

ES 8.x 引入了聚合缓存，用于缓存聚合结果。当相同的聚合查询再次执行时，可以直接返回缓存结果。这对于重复的聚合查询非常有效。

### **2.2.2.2 设置实操**

全局默认值可以通过修改 elasticsearch.yml 配置：

1.  通过search.aggs.cache.enabled开启或关闭，默认是开启的。
2.  缓存大小通过search.aggs.cache.size设置，默认是堆内存的2%。

\# elasticsearch.yml

\# 聚合缓存

search.aggs.cache.enabled: true

search.aggs.cache.size: 5%

执行流程详细说明：

1.  阶段1：查询接收和解析
2.  ​客户端发送请求​：包含request\_cache=true参数的聚合查询
3.  ​协调节点解析​：解析查询DSL和缓存参数

5.  阶段2：缓存处理逻辑
6.  ​启用缓存路径​：
7.  数据节点检查请求缓存
8.  生成唯一缓存键（基于查询+聚合+分片版本）
9.  如果缓存命中，直接返回结果，大幅提升性能
10.  ​禁用缓存路径​：
11.  跳过缓存检查，直接执行查询
12.  适用于实时性要求高的场景
13.  阶段3：聚合计算执行（缓存未命中时）
14.  ​倒排索引扫描​：查找匹配的航班文档
15.  ​多聚合并行计算​：
16.  按航空公司分组统计
17.  计算平均票价、延误时间等指标
18.  执行复杂的桶脚本计算
19.  阶段4：缓存存储决策
20.  ​可缓存条件​：启用缓存且结果可缓存（无脚本、非实时等）
21.  ​缓存存储​：验证内存限制，必要时执行LRU清理
22.  ​跳过存储​：禁用缓存或结果不可缓存的情况
23.  阶段5：后台缓存维护
24.  ​内存监控​：持续监控缓存内存使用情况
25.  ​过期清理​：基于分片版本失效机制清理过期缓存
26.  ​统计更新​：维护命中率、内存使用等统计信息
