**02 ES 8.x 分页查询实战**

我们知道从 ES 索引中获取数据时分页是绕不开的操作，如果一下子从索引中获取「**过多数据**」可能会造成「**系统抖动**」、「**占用大量带宽**」等问题。

特别是进行「**全文搜索**」时只关心「**相关性最高**」的几条结果，从系统中拉取过多的数据等于浪费资源。

  
ES 官方提供了 3 种分页方式：

1.  from + size：这是最普通、最简单的分页方式，但是会产生「**深分页**」的问题。
2.  search after：解决了「**深分页**」的问题，但只能一页一页地往下翻，不支持跳转到指定页数。
3.  scroll API：会创建数据快照，无法检索新写入的数据，适合对结果集进行遍历的时候使用。

  
这 3 种方式的分页操作都有其优缺点，适合不同的场合使用。接下来学习这 3 种分页方式，在最后我们会介绍 ES 新引入的特性：Point In Time，看看如何使用 Point In Time + search after 的方式来代替 scroll API 进行大量数据的查询。

###   
**2.3.4.1 为什么会产生深分页？**

那什么是「**深分页**」和为什么会产生「**深分页**」的问题呢？

![](images/Fot_YVYu_fDKxHeyg7zz9qyLyHEH.png)  

如上图，ES 把数据保存到 3 个主分片中，当使用 from = 90000 和 size = 10000 进行分页的时候，ES 会先从每个分片中分别获取 10000个文档，然后把这 30000 个文档再汇聚到协调节点中进行排序，最后选出排序后的前 10000 个文档，返回第 90000 到 99999 的文档。

可以看到，当页数变大（发生了深分页）的时候，在每个分片中获取的数据就越多，消耗的资源就越多。并且如果分片越多，汇聚到协调节点的数据也越多，最终汇聚到协调节点的文档数为：shard\_amount \* (from + size)。

## **3.1 search after 方案**

使用 search after API 可以避免产生「**深分页**」的问题，不过 search after 不支持「**跳转到指定页数**」，只能一页页地往下翻。

使用 search after 接口分为两步：

1.  在 sort 中指定需要排序的字段，并且保证其值的唯一性（可以使用文档的 ID）。
2.  在下一次查询时，带上返回结果中最后一个文档的 sort 值进行访问。

### **3.1.1 查询核心目标**

下面示例查询的目标是：使用 Search After​ 技术实现的深度分页查询，目标是在大数据集中高效地进行分页浏览，避免传统 from/size分页的性能问题。

两次查询的关系：

1.  第一次查询：获取按 order\_date降序排列的前2条文档
2.  第二次查询：基于第一次查询最后一个文档的排序值，获取下一页的2条文档

\# 第一次调用 search after

POST kibana\_sample\_data\_ecommerce\_bigdata/\_search

{

"size": 2,

"query": { "match\_all": {} },

"sort": \[

{ "order\_date": "desc" }

\]

}

![](images/FmfmysVosIKXOs-1_kchrcsKHrSS.png)

如上示例，在第一次调用 search after 时指定了 sort 的值，并且 sort 中指定以 order\_date倒序排序。可以看到，第一次调用的返回结果中除了文档的信息外，还有 sort 相关的信息，在下一次调用的时候需要带上最后一个文档的 sort 值，示例中其值为：\[1762645536000\]。

下面的示例是第二次调用 search after 接口进行翻页操作：

\# 第二次调用 search after

POST kibana\_sample\_data\_ecommerce\_bigdata/\_search

{

"size": 2,

"query": {

"match\_all": {}

},

"search\_after": \[

1762645536000

\],

"sort": \[

{

"order\_date": "desc"

}

\]

}

![](images/Fkp5HzW9dDBn2hyo8pYJ2mNkQQTT.png)

如上示例，进行翻页操作的时候在 search after 字段中设置上一次返回结果中最后一个文档的 sort 值，并且保持 sort 的内容不变。

### **3.1.4 Search After 如何解决深分页**

那为啥 search after 不会产生深度分页的问题呢？其关键就是 sort 中指定的唯一排序值。

  
![](images/FlzkiDHRSgdElvl4aVed__B74-Ae.png)

资源消耗对比：

![](images/FvoZZ-PPuar-Lr2lnPoraOh31q87.png)

Search After 分页演进流程：

![](images/FpS8f9rscAfgJI_P10uYsh8HadKT.png)

如上图，因为有了「**唯一排序值**」做保证，所以每个分片只需要返回比 sort 中唯一值大的 size 个数据即可。例如，上一次的查询返回的最后一个文档的 sort 为 a，那么这一次查询只需要在分片 1、2、3 中返回 size 个排序比 a 大的文档，「**协调节点**」汇总这些数据进行「**排序**」后返回 size 个结果给客户端。

而 from + size 的方式因为没有「**唯一排序值**」，所以没法保证每个分片上的「**排序**」就是「**全局排序**」，必须把每个分片的 from + size 个数据汇总到协调节点进行排序处理，导致出现了「**深分页**」的问题。

因为 sort 的值是根据上一次请求结果来设置的 ，所以 search after 不支持跳转到指定的页数，甚至不能返回前一页，只能一页页往下翻。但我们可以结合「**缓存中间件**」，把每页返回的 sort 值缓存下来，即可实现往前翻页的功能。

### **3.2.5 Scroll 注意事项**

1.  资源消耗：Scroll会占用服务端资源，需要及时清理
2.  数据实时性：基于快照，不反映后续数据变更
3.  超时设置：根据数据量合理设置，避免过早超时或资源占用过长
4.  批次大小：过小增加请求次数，过大数据量传输压力大

## **3.3 Point In Time 方案**

最后，我们来看下 Point In Time 方案，Point In Time（PIT）是 「**ES 7.10 版本**」中引入的新特性，PIT 是一个「**轻量级**」的「**数据状态视图**」，用户可以利用这个视图反复查询某个索引，仿佛这个索引的数据集停留在某个时间点上。

也就是说，在创建 PIT 之后更新的数据是「**无法被检索**」到的。

当我们想要获取、统计以当前时间节点为准的数据而不考虑后续数据更新的时候，PIT 就显得非常有用了。使用 PIT 前需要显式使用 \_pit API 获取一个 PID ID。

### **3.3.1 查询核心目标**

三次查询的关系：

1.  PIT创建：建立20分钟有效期的数据快照上下文
2.  第一次Search After：基于PIT获取第一批2条文档
3.  第二次Search After：使用search\_after参数继续获取下一页数据

1.  第一个是我们用作排序的 order\_date 的值。

### **3.3.3 PIT & Scroll & Search After 对比**

![](images/Fgmbt-41kVR46VlgtSE2lmmfWg0i.png)

Search After + PIT 实现的功能似乎和 scroll API 类似，那它们间有啥区别呢？

1.  其实你会发现使用 scroll API 的时候，scroll 产生的上下文是与本次查询绑定的，很明显的一点就是，生成一个 scroll id 后，其他查询无法重用这个 id，scroll 的翻页也只能一直向下翻。
2.  而 PIT 可以允许用户在同一个固定数据集合上运行不同的查询，例如多个请求可以使用同一个 PIT 视图而互不影响。

### **3.2.6 PIT & Search After 注意事项**

使用限制：

1.  版本要求：Elasticsearch 7.10+ 版本完整支持
2.  资源管理：PIT会占用段引用，需要及时清理
3.  数据量：适合大数据集深度分页，小数据集用from/size即可
4.  排序要求：必须指定排序字段，且最好包含唯一字段

监控指标：

1.  PIT创建和删除频率
2.  Search After查询响应时间
3.  分页深度与性能关系
4.  内存和CPU使用情况

## **04 总结**

1.  from + size 是最普通、简单的分页方式，其支持在不同页面间随机跳转，但是会产生深分页的问题。默认的情况下可以支持 Top 10000 条数据内的分页场景，可以使用 max\_result\_window 进行调整，但不建议调得过大。
2.  search after：通过在 sort 中指定唯一排序值解决了深分页的问题，但导致其只能一页一页地往下翻，不支持跳转到指定页数。当然我们也介绍了可以使用缓存等手段实现向前翻页的功能。
3.  scroll API：会创建数据快照，无法检索新写入的数据，其适合遍历结果集的时候使用。scroll API 产生的快照与本次查询是绑定的，其他查询无法复用。
4.  最后介绍了 ES 在 7.10 中引入的特性：Point In Time（PIT），PIT 简单来说就是一个视图，多个查询可以复用一个 PIT，使得用户可以重复检索某个时间点的数据。在新版的 ES 官方文档中建议使用 PIT + search after 代替 scroll API，即使 scroll API 还可以使用。

综上，PIT + Search After组合提供了Elasticsearch中最优秀的深度分页解决方案，既有Scroll的数据一致性保证，又有Search After的实时性优势，是生产环境深度分页的首选方案。
