## **2.1 核心基础概念**

### **2.1.1 Suggest**

​目标​：处理用户输入的搜索词错误或提供替代/补充建议。简单来说，Suggester 会将输入的文本分解为 token，然后在索引里查找相似的 Term。

根据使用场景的不同，ES 提供了以下 4 种 Suggester：

  
![](images/FseG4c8FjnyEMYgzQkX7SkohsYxx.png)

1.  Term Suggester：基于单词的纠错补全，它使用编辑距离（Levenshtein Distance）算法为查询中的单个词提供相似词建议。例如将 filight 纠正为 flight。
2.  Phrase Suggester：基于短语的纠错补全，在 Term Suggester 基础上构建，用于对整个短语提供纠正建议。它会考虑短语中词项的上下文和词频，给出更自然的整体建议。例如将 filight to beijin 纠正为 flight to beijing。
3.  Completion Suggester：专为自动补全（Auto-Completion）​​ 设计，输入词语的前半部分自动补全单词。它并非用于纠正错误，而是提供前缀匹配。其底层依赖内存中的有限状态转换器（FST）​​ 数据结构，实现极速的查询响应。
4.  Context Suggester：基于上下文的补全提示，可以实现上下文感知推荐。

### **2.1.2 模糊查询 Fuzzy Query**

​目标​：在标准查询中容忍用户输入的拼写错误，确保「**搜错也能搜到**」。

​原理​：基于编辑距离，允许查询词项与目标词项之间存在指定数量的字符差异（增、删、改、换位）。例如，设置 fuzziness: "AUTO"，查询 kunming 可以匹配到 Kunming。

### **2.1.3 高亮显示 Highlighting**

​目标​：在返回的搜索结果中，明确标识出哪些文本片段与查询条件匹配，提升用户体验。

​原理​：从原始文档（\_source）或存储的字段中提取内容，定位匹配词元的位置，并用预定义的标签（如 <em>）包裹它们。

**2.4 Term Suggester 纠错补全实战**

Term Suggester 提供了基于单词的「**纠错**」、「**补全**」功能，其工作原理是基于「**编辑距离**」（edit distance）来运作的，编辑距离的核心思想是一个词需要改变多少个字符就可以和另一个词一致。所以如果一个词转化为原词所需要改动的字符数越少，它越有可能是最佳匹配。

例如，flaght 和 flight，为了把 flaght 转变为 flight 需要改变一个字符 'a'，所以其编辑距离为 1。

Term Suggester 会先将输入的文本切分为一个个单词 token，然后根据每个单词提供建议，所以其不会考虑输入文本间各个单词的关系。

Term Suggester API 提供了很多的参数：

![](images/Fu5J8OJ2czCP-nHHrMnaXFTjTUED.png)![](images/FgjE-ocxLQG71HwTUkfaAPcKpDbz.png)

比较常用的有以下几个：

1.  text：指定了需要产生建议的文本，一般是用户的输入内容，例子中是："kernel architture"。
2.  field：指定从文档的哪个字段中获取建议，上例中，我们从书名（name）字段中获取建议。
3.  suggest\_mode：设置建议的模式。其值有以下几个选项：
4.  missing：如果索引中存在就不进行建议，默认的选项。上例中使用的是此选项，所以可以看到返回的结果中 "kernel" 这个词是没有建议的。
5.  popular：推荐出现频率更高的词。
6.  always：不管是否存在，都进行建议。
7.  analyzer：指定分词器来对输入文本进行分词，默认与 field 指定的字段设置的分词器一致。
8.  size：为每个单词提供的最大建议数量。
9.  sort：建议结果排序的方式，有以下两个选项：
10.  score：先按相似性得分排序，然后按文档频率排序，最后按词项本身（字母顺序的等）排序。
11.  frequency：先按文档频率排序，然后按相似性得分排序，最后按词项本身排序。

3.  ​优化性能​：通过 size:0 不返回文档内容，track\_total\_hits 仅统计匹配总数，聚焦建议功能

## **2.5 Phrase Suggester 纠错补全实战**

Term Suggester 产生的建议是基于「**每个单词**」的，如果想要针对整个短语或者一句话做建议，Term Suggester 就有点无能为力了。

此时可以使用 Phrase Suggester API 获取与用户输入文本相似的内容。Phrase Suggester 在 Term Suggester 的基础上增加了一些额外的逻辑，因为是「**短语形式**」的建议，所以会考量多个 term 间的关系，比如「**相邻程度**」、「**词频**」等。

Phrase Suggester 可用的参数也比较多：

![](images/FpOPra44ZieX-AuLIMYpZdsaxWTb.png)![](images/FkPPYO6IZJUKXKgw_fKM3QBB5tTc.png)![](images/FiFK6dt9c3XwMrpKHa6dHx4JRjXh.png)![](images/Fmd0sFo1fet3Dav7_lC5lKlodP-A.png)

下面介绍几个用得比较多的参数选项：

1.  max\_error：指定最多可以拼写错误的词语的个数。
2.  confidence：其作用是用来控制返回结果条数的。如果用户输入的数据（短语）得分为 N，那么返回结果的得分需要大于 N \* confidence。confidence 默认值为 1.0。
3.  highlight：高亮被修改后的词语。

下面示例查询的目标是：

1.  ​短语级拼写纠错​：对输入短语 "Frankfurt am Main Airprot" 进行智能纠正
2.  ​高亮显示差异​：在返回的建议中用 <em> 标签标记突出显示被修改的部分
3.  ​容错搜索​：即使输入包含拼写错误（"Airprot"），仍能返回正确结果
4.  上下文感知​：基于整个短语的语义关系提供建议，而非单个单词

## **2.6 Completion Suggester 自动补全实战**

Completion Suggester 提供了「**自动补全**」的功能，其应用场景是用户每输入一个字符就需要返回匹配的结果给用户。

在「**并发量大**」、「**用户输入速度快**」的时候，对服务的吞吐量来说是个不小的挑战。所以 Completion Suggester 不能像上面的 Suggester API 那样简单通过「**倒排索引**」来实现，必须通过某些更高效的数据结构和算法才能满足需求。

Completion Suggester 在实现的时候会将 「**analyze**」后的数据进行编码，构建为「**FST**」并且和索引存放在一起。「**FST**」（finite-state transducer）是一种高效的前缀查询索引，由于「**FST**」天生为前缀查询而生，所以其非常适合实现自动补全的功能。

ES 会将整个「**FST**」加载到内存中，所以在使用「**FST**」进行前缀查询的时候效率是非常高效的。在使用 [Completion Suggester](http://completion%20suggester/) 前需要定义 [Mapping](http://mapping/)，对应的字段需要使用 ["type": "completion"](http://%22type%22:%20%22completion%22/)。

来看下该 suggester api 的 mapping，很简单只需要在原有基础上，新增一个字段来实现 suggest 即可。

## **2.7 Context Suggester 上下文感知实战**

[Context Suggester](http://context%20suggester/) 是 [Completion Suggester](http://completion%20suggester%20/) 的扩展，可以实现「**上下文感知推荐**」。

1.  Category：任意字符串的分类。
2.  Geo：地理位置信息。

19.  阶段五：结果聚合与返回
20.  ​分片结果聚合​：协调节点收集所有分片的结果
21.  ​全局排序​：对所有分片返回的结果进行全局排序
22.  ​数量限制​：应用 size:5 参数，只返回前 5 个结果
23.  ​响应构建​：构建最终的返回 JSON 结构

### **2.8.1 高亮匹配类型**

关于高亮匹配类型目前有 3 种，用来决定如何从文档中提取和匹配文本片段：

1.  plain：标准高亮器。将文本分解为单个词条，并基于查询中的每个词条进行高亮。适用场景：简单的 term 或 match 查  
    询。![](images/FlVmMvotTlAy50UpTNiHSiJLEBya.png)
2.  优点​：简单可靠，内存开销低。
3.  ​缺点​：对于复杂的布尔查询或短语查询，可能无法准确高亮所有相关部分。
4.  fvh (Fast Vector Highlighter)​：快速向量高亮器。需要字段映射中设置 "term\_vector": "with\_positions\_offsets"，性能更高，功能更丰富。适用场景：复杂查询、需要多字段匹配或需要突出显示短语。  
    ![](images/FkjjSSrY-JdHadOWEZ-QOMNJrrTy.png)
5.  ​优点​：精度高，支持复杂的多字段查询和短语高亮。
6.  ​缺点​：索引体积会增大（因为需要存储位置信息），写入性能略有下降。
7.  unified：统一高亮器。Elasticsearch 默认的高亮器，结合了 plain 和 fvh 的优点，无需特殊配置。适用场景：大多数场景，是目前的推荐选择。![](images/Fh95Qca5byZgp3NiRQBfyYdhJx30.png)
8.  优点​：无需特殊映射配置，兼具准确性和性能，支持所有查询类型。
9.  ​缺点​：在极其复杂的查询下，可能不如 fvh 精确。

2.  ​请求接收​：协调节点接收包含多字段高亮参数的搜索请求
3.  ​查询解析​：
4.  解析multi\_match查询，识别4个搜索关键字和4个目标字段
5.  解析各字段的高亮参数（不同的number\_of\_fragments设置）
6.  ​分片路由​：基于索引分片配置确定需要查询的所有相关分片
7.  ​请求分发​：向所有相关数据节点发送并行查询请求
8.  阶段二：文档匹配与评分（数据节点）
9.  ​多字段倒排索引查询​：在4个字段的倒排索引中查找匹配文档
10.  跨字段评分​：使用BM25算法计算每个匹配文档的综合相关性分值
11.  ​结果收集​：收集匹配文档ID和评分，按分值排序
12.  阶段三：多字段高亮处理（核心流程）
13.  ​多字段文本提取​：从匹配文档的\_source中提取4个字段的原始内容
14.  ​多字段片段生成​：为每个字段生成包含关键字的文本片段
15.  跨字段片段评分​：计算每个片段的相关性分值，考虑字段权重
16.  按字段排序和选择​：为每个字段选择限定数量的最高分片段
17.  阶段四：结果组装和返回
18.  ​多字段结果组装​：将各字段的高亮片段添加到文档结果中
19.  分片结果返回​：数据节点返回处理后的文档
20.  ​全局结果聚合​：协调节点聚合所有分片结果，按文档分值全局排序
21.  ​最终响应​：返回前5个最相关的文档给客户端
