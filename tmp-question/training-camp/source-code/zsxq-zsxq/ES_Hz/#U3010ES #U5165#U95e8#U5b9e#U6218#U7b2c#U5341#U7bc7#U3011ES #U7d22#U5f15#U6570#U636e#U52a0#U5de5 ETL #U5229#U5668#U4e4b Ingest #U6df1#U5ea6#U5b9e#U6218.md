## **02 ES 索引数据加工 ETL 利器介绍**

## **2.1 什么是 ES 索引数据加工之 Ingest**

ES Ingest​ 是一个强大而精巧的内置 ETL 工具，它通过 ​Pipeline​ 和 ​Processor​ 的模型，让用户能在数据写入阶段就完成清洗、转换、富化等一系列操作，最终将规整、有价值的数据直接存入索引，为后续的高效搜索和分析奠定了坚实的基础。它非常适合处理实时流式数据，是构建简洁、高效数据平台的重要利器。

Ingest 不是一个外部服务，而是 ES 集群内部的一个轻量级、低延迟的数据预处理层。它通常运行在协调节点（Coordinating Node）​​ 或专用的钻取节点（Ingest Node）​​ 上，这意味着您无需部署和维护像 Logstash 这样的额外服务来完成数据预处理。数据处理逻辑（Pipeline）的定义、执行和管理全部在 ES 集群内部完成，极大地简化了架构和运维复杂度。

1.  无外部依赖​：所有处理都在 ES 集群内完成，无需配置和维护额外服务。
2.  ​资源消耗低​：处理逻辑简单直接，通常只占用少量的 CPU 和内存资源。
3.  ​延迟极低​：在数据写入的同一网络往返中完成处理，延迟通常在毫秒级，非常适合实时数据流。

所谓 ETL 是 Extract（提取）、Transform（转换）、Load（加载）的缩写，是数据仓库领域的核心概念。

1.  Extract​：数据来自写入 ES 的请求。
2.  ​Transform​：在 Ingest Pipeline 中通过一系列处理器（Processor）完成转换。这正是它强大的地方。
3.  ​Load​：最终写入目标索引。

它实现了 ETL 的核心流程，但无需笨重的传统 ETL 工具，配置更灵活，延迟极低（毫秒级）。

### **2.2.1 数据写入/更新**

这是 Ingest 最基础和最常用的两大场景，覆盖了数据的全生命周期：

1.  ​数据写入 (insert)​​：这是最核心的场景。在数据被 index 或 create 操作写入之前，通过预定义的 Pipeline 自动完成清洗、转换、富化。
2.  例如，在写入日志数据前，自动提取 timestamp、解析 user\_agent、转换字段类型。
3.  ​数据更新 (update)​​：通过 Update By Query API 调用 Ingest Pipeline，对已存在于索引中的文档进行批量更新。
4.  例如，修复错误的数据格式、为历史数据添加新的衍生字段。

### **2.2.2 基于 enrich 策略构建大宽表索引**

这是 Ingest 非常强大的一个高级功能。通过 ​Enrich Processor，可以在写入主文档时，「**自动关联**」查询另一个已有的「**参考索引**」（如用户信息表、产品信息表），并将查询结果关联字段​整合到主文档中，从而构建一个包含大量关联信息的「**大宽表**」索引。

1.  ​优势​：避免了在查询时进行昂贵的关联查询（Join），以空间换时间，极大地提升了检索性能。
2.  ​场景​：在写入订单数据时，自动根据 user\_id 去“用户索引”中查询出用户的 level, region 等信息，并直接写入订单文档中。

由于篇幅问题，这部分的实战我们后续会单独展开。

### **2.2.3 共享处理数据加工**

Ingest Pipeline 一旦在集群中创建就成为一个全局共享的资源，这意味着：

1.  ​一致性​：不同的写入源（不同的应用程序、Logstash、Filebeat 等）都可以通过指定相同的 Pipeline 名称，来确保数据经过完全一致的处理逻辑，保证了数据规范性。
2.  ​可维护性​：数据处理逻辑（Pipeline 配置）只需在 ES 集群中维护一份。需要修改时，只需更新该 Pipeline，所有使用它的写入操作会自动生效，无需修改每个数据源的代码。

### **2.2.4 索引重建**

当您需要调整索引的映射（mapping）或分片策略时，重建索引是标准操作。Ingest Pipeline 在该过程中赋予了数据转换的能力，使得重建不仅是简单的拷贝，更是一次数据结构和内容的升级机会。

在使用 \_reindex API 将数据从一个索引迁移到另一个索引时可以指定 Pipeline，在写入新索引前对数据进行处理和改造。这常用于索引映射的版本升级或数据结构优化。

### **3.2.1 查看 Ingest-Pipeline**

GET \_ingest/pipeline

![](images/Fglq7v1WWvMOBCTbKoPl2iH82y0p.png)

可以看到获取的结果集就是 ES 集群中当前定义的所有 ​Ingest Pipeline 的配置清单，这个庞大的 JSON 对象包含了非常丰富的信息，是了解集群数据预处理能力的核心视图，这里简单的来介绍下，方便理解：

### **1、结构概览**

结果集是一个 JSON 对象，其最外层的每个 ​Key​ 都是一个 ​Pipeline 的名称。例如 synthetics-browser-1.3.0, logs@default-pipeline, traces-apm@pipeline 等。

每个 Pipeline 名称对应的 ​Value​ 是一个完整的 Pipeline 定义对象，包含了该管道的所有配置信息。

### **2、核心组成部分**

每一个 Pipeline 定义都包含以下几个核心部分：

1.  processors (处理器数组)​​：这是 Pipeline 的心脏。它定义了一个有序的处理器列表，数据会依次流经这些处理器并被加工。您会看到很多管道都大量使用了这个处理器。它的作用是调用另一个管道，实现了管道的模块化和嵌套组合。例如：

{ "pipeline": {

"name": "global@custom", // 调用名为 'global@custom' 的管道

"ignore\_missing\_pipeline": true // 如果指定的管道不存在，则忽略错误继续执行

}

}

1.  其他处理器​：如 set（设置字段）, script（执行脚本）, remove（删除字段）, geoip（IP地址解析）, user\_agent（解析UA）等。例如在 search-default-ingestion 中看到的 attachment, gsub, trim 等。
2.  \_meta (元数据)​：这部分描述了管道的管理属性。
3.  "managed": true：表示此管道是被托管的，通常由 Elasticsearch 本身、Fleet、Integrations 或 Elastic Agent 自动创建和管理。​谨慎手动修改这类管道，因为更新或升级后可能会被覆盖。
4.  "managed\_by": "fleet" / "managed\_by": "Search"：明确指出了该管道的管理方是谁（如 Fleet 服务器、Enterprise Search 服务等）。
5.  "package": { "name": "synthetics" }：指明了该管道属于哪个集成包（Integration Package）。
6.  "description"：提供了管道用途的人类可读描述。
7.  version (版本号)​​：管道的版本号。当管道被更新时，这个版本号会递增。这有助于追踪和管理配置的变更。
8.  ​description (描述)​​：管道的详细文本描述，说明其设计目的和功能。
9.  ​on\_failure (失败处理策略)​：（并非所有管道都有）它定义了当管道中的某个处理器执行失败时该怎么办。通常用于错误记录和清理，例如：

"on\_failure": \[

{

"append": {

"field": "\_ingestion\_errors",

"value": "Processor 'attachment' failed: {{ \_ingest.on\_failure\_message }}"

}

}

\]

### **3、结果集分类**

这个配置清单展示了 ES 不同功能模块创建的管道，可以分为以下几类：

1.  ​Synthetics（综合监控）相关管道​ (e.g., synthetics-browser-1.3.0, synthetics-http-1.3.0)
2.  ​用途​：处理来自 ​Heartbeat​ 等综合监控工具的数据。
3.  ​模式​：采用“责任链”模式，依次调用范围从广到窄的管道：
4.  global@custom -> synthetics@custom -> synthetics-synthetics.integration@custom -> synthetics-\[dataset\]@custom。
5.  ​设计理念​：提供了极大的灵活性。你可以在 global@custom 中定义所有数据通用的处理逻辑，在 synthetics-http@custom 中专门定义处理 HTTP 检查数据的逻辑。
6.  ​APM（应用性能监控）相关管道​ (e.g., traces-apm@default-pipeline, metrics-apm@app@default-pipeline, apm@pipeline)
7.  ​用途​：处理来自 ​APM Server​ 的链路追踪（traces）、指标（metrics）、日志（logs）数据。
8.  ​特点​：包含复杂的业务逻辑，如：
9.  ​路由 (reroute)​: 将数据路由到不同的数据集（dataset）。
10.  ​富化 (geoip, user\_agent)​: 添加地理位置和用户代理信息。
11.  ​脚本处理: 进行复杂的数据转换和计算。
12.  ​通用日志和指标管道​ (e.g., logs@default-pipeline, metrics-apm@app@default-pipeline)
13.  ​用途​：处理通用的日志和指标数据。
14.  ​常见操作​：确保 @timestamp 存在、调用用户自定义管道 (logs@custom)。
15.  ​Search 和 Enterprise Search 管道​ (e.g., search-default-ingestion, ent-search-generic-ingestion)
16.  ​用途​：在处理搜索引擎和企业搜索内容摄入时，用于文档内容的预处理。
17.  ​高级功能​：包括文本提取（attachment 处理器）、文本清理（gsub, trim）、错误处理等。
18.  ​Fleet 代理管道​ (e.g., .fleet\_final\_pipeline-1)
19.  ​用途​：这是由 ​Fleet​ 管理的 Elastic Agent 发送的所有数据的最终管道（final pipeline）​。
20.  ​核心任务​：添加安全相关信息、进行代理身份验证和验证（agent\_id\_status）、执行最终的数据清理。这是整个托管数据流的最后一道关卡。

### **4、总结与建议**

这个结果集展示了集群中一个强大而复杂的数据预处理生态系统。这些管道协同工作，在数据被索引之前自动完成了清洗、转换、富化、路由等大量繁重的工作。

1.  ​对于使用者​：不需要手动调用这些管道，当使用 ​Fleet​ 和 ​集成（Integrations）​​ 时，Elastic Agent 会自动为相应的数据流选择并应用正确的管道。这是 Elastic Stack ​​“开箱即用”​​ 体验的核心所在。
2.  ​对于开发者/运维​：理解这个清单有助于你：
3.  ​调试数据​：当数据不符合预期时，知道是哪个管道在处理它。
4.  ​自定义处理​：遵循 @custom 管道的设计模式，在不修改官方管道的前提下，添加你自己的处理逻辑。
5.  ​掌控全局​：了解数据在入库前经历了哪些变化。

## **4.1 IF 逻辑判断**

## **4.2 OnFailure 执行失败拦截**

PUT \_ingest/pipeline/kibana\_sample\_data\_ecommerce

{

"description": "ecommerce 数据加工 ingest",

"processors": \[

{

// 增加一个字段

"set": {

"field": "tag",

"value": "EUR\_order"

},

// 删除一个字段

"remove": {

"field": "email2",

"ignore\_failure": false, // 不忽略失败，执行 on\_failure

"on\_failure": \[{

"remove": {

"field": "email"

}

}\]

}

}

\]

}

执行 remove 处理器​：

1.  ​主要操作​：尝试删除字段 email2。
2.  ​错误处理​：由于 ignore\_failure 设置为 false，如果 email2 字段不存在，操作会失败。失败后，会触发 on\_failure 块。
3.  ​回退操作​：在 on\_failure 块中，另一个 remove 处理器会尝试删除字段 email。这意味着如果 email2 不存在，则删除 email 作为备选方案。

错误处理与容错机制​

1.  ​on\_failure 块：这是管道设计的强大功能。当处理器失败时（如字段不存在），可以执行备用操作。在当前管道中，如果删除 email2 失败，则尝试删除 email。
2.  ​ignore\_failure 参数​：设置为 false 时，失败会触发 on\_failure；如果设置为 true，则忽略失败并继续执行后续处理器。这提供了灵活的故障恢复策略。

## **4.5 Ingest 数据处理专用节点配置**

默认，所有的 ES 节点都具备 ingest 能力，需要人为去关闭并设置专职节点。也就是指导用户如何从默认所有节点都具备 Ingest 能力的集群中，配置出专用的 Ingest 数据处理节点。

### **4.5.1 专业 Ingest 节点的 ES 配置**

在一个名为 ingest-node-1 的节点上，其配置文件 elasticsearch.yml 应只包含 ingest 角色：

\# ingest-node-1 的 elasticsearch.yml 配置

\# - 角色设置为专用的 ingest 节点

node.roles: \[ ingest \]

\# - 通用配置

cluster.name: my-production-cluster

node.name: ingest-node-1

network.host: 192.168.1.20

discovery.seed\_hosts: \["master-node-1:9300"\]

cluster.initial\_master\_nodes: \["master-node-1"\]

![](images/FhF99mX7J8uNJgyAcApFjHVCu8Zw.png)

### **4.5.2 其他节点的 ES 配置（关闭 Ingest 能力）**

在这些节点的角色列表 node.roles 中，​不包含​ ingest 角色，即关闭了其默认的 Ingest 能力。

\# master-node-1 的配置 (主节点 + 数据节点)

node.roles: \[ master, data \] \# 注意：这里没有 'ingest'

\# data-node-1 的配置 (纯数据节点)

node.roles: \[ data \] \# 注意：这里没有 'ingest'

专用 Ingest 节点架构配置图​：

![](images/FiEJxRmQ_GaDeMoVo_CsJZrJDGOU.png)

这种架构的优势在于：​​

1.  ​资源隔离与性能​：
2.  ​专用 Ingst 节点​：专注于执行 Pipelines 中的处理器（如 grok、script、geoip），消耗 CPU 和内存。这可以防止繁重的数据处理操作影响数据节点的写入和查询性能。
3.  ​数据节点​：专注于数据的索引、搜索和存储，资源不会被数据处理任务抢占。
4.  ​弹性扩展​：
5.  当数据处理成为瓶颈时，您可以轻松地添加更多的 ingest 节点来水平扩展数据处理能力，而无需增加昂贵的数据节点。
6.  ​高可用性​：
7.  可以配置多个专用 Ingest 节点。客户端（如 Logstash、Filebeat）或应用程序可以将请求负载均衡到多个 Ingest 节点上，避免单点故障。

### **4.5.3 总结**

这里概括下 Elasticsearch 节点角色的配置哲学：「**默认全能，按需专用**」**​**。

1.  ​开发/测试环境​：使用默认配置（所有节点角色齐全）最简单。
2.  ​生产环境​：采用上述示例配置，​设置专职的 Ingest 节点，是提升集群稳定性、性能和扩展性的最佳实践。
