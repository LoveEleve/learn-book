**02 Script基础知识**

## **2.1 Script 概念**

ES Script 允许您在查询、聚合、更新文档等操作中，使用自定义的逻辑来计算字段值、修改文档内容或实现复杂的查询条件。目的是满足日益复杂的业务需求。

## **2.2 Script 脚本语言**

ES支持多种脚本语言，自ES 5.0版本以后主要推荐使用Painless脚本语言，因为它是专门为ES设计的，简单、安全且高效。

1.  高性能​： 直接编译为 Java 字节码，运行效率接近原生 Java。
2.  ​安全性​： 沙箱机制，通过白名单严格限制可访问的类和方法，杜绝危险操作。
3.  ​简单易用​： 语法类似 Java/JavaScript，学习成本低。

其他语言​： Expression、Mustache（模板语言）等，但功能和性能远不及 Painless，通常不推荐用于生产环境。

## **2.4 Script 脚本架构设计**

ES 的脚本模块设计精巧，核心目标是平衡灵活性、安全性和性能。

### **2.4.1 核心组件**

1.  脚本引擎​： 每种脚本语言（如 painless, expression）都有一个对应的脚本引擎实现。它负责将源代码编译成可执行对象。
2.  ​脚本缓存​： 这是性能的关键。为了避免每次执行都重新编译脚本，ES 使用一个 ​LRU（最近最少使用）缓存​ 来存储编译后的脚本对象。缓存键由脚本的源码（source）构成。
3.  ​沙箱安全模型​： 这是安全的关键。特别是对于 Painless 语言，它通过严格的白名单机制​ 来限制脚本可以访问的 Java 类、方法和字段。任何不在白名单上的操作都会被拒绝。
4.  ​脚本上下文​： 定义了脚本可以在哪里执行以及可以访问哪些数据。ES 为不同的用途定义了不同的上下文，例如：
5.  score上下文： 用于脚本查询，可以访问 doc值和 \_score。
6.  update上下文： 用于更新操作，可以访问 ctx.\_source。
7.  aggs上下文： 用于聚合。
8.  每个上下文允许的操作是不同的（例如，在 update上下文中才能修改 \_source）。

关键点说明：​​

1.  ​缓存优先​：流程的第一步就是检查缓存，这是性能优化的核心。
2.  ​编译与安全紧密耦合​：安全验证是编译过程中不可分割的一步，确保了“坏”的脚本在运行前就被拦截。
3.  ​清晰的失败路径​：安全验证失败会直接终止流程并返回错误。
4.  ​执行上下文绑定​：展示了执行阶段如何将运行时变量（如 params）和特定上下文的变量（如 doc或 ctx.\_source）注入到脚本中。

核心流程说明：

1.  解析与准备
2.  数据节点接收到包含脚本操作的请求（如 update\_by\_query）。
3.  节点解析请求体，识别出 script部分，包括 lang, source, params。
4.  根据 lang确定要使用的 ScriptEngine（例如 PainlessScriptEngine）。
5.  编译与缓存（最关键步骤）
6.  ​构建缓存键​： 系统使用脚本的源代码（source）来生成一个缓存键。​这就是为什么参数化脚本如此重要​：params的变化不会影响缓存键，因此 discount\_rate从 0.9 变为 0.8 时，脚本源码不变，可以命中缓存。
7.  ​缓存查找​： 在 LRU 编译缓存中查找该键。
8.  ​缓存命中​： 直接获取到之前已编译好的 CompiledScript对象，跳过后面的编译步骤，极大提升性能。
9.  ​缓存未命中​： 进入编译流程。
10.  ​词法分析 & 语法分析​： 将源代码解析成抽象语法树（AST）。
11.  ​安全验证​： ​这是沙箱安全的核心。编译器会遍历 AST，检查每一个表达式、每一个方法调用是否在允许的白名单内。例如，脚本中尝试执行 java.lang.System.exit(0)或访问文件系统，都会在这一步抛出异常，拒绝执行。
12.  ​代码生成​： 将验证通过的 AST 编译成 Java 字节码（对于 Painless）。
13.  ​缓存​： 将编译好的 CompiledScript对象存入 LRU 缓存，以备后续使用。
14.  执行
15.  ​创建执行上下文​： 根据操作类型（查询、更新、聚合）创建对应的 ScriptContext。这个上下文提供了脚本可以访问的变量（如 doc、\_source、params）。
16.  ​绑定参数​： 将运行时参数（params）和上下文变量绑定到脚本上。
17.  ​运行​： 脚本引擎（或 ScriptExecutor）执行编译后的字节码。对于 Painless，这通常是通过 Java 的动态语言 API 来调用生成的类和方法。
18.  ​资源限制​： ES 有防止脚本陷入无限循环的机制（通过 script.max\_compilation\_rate限制编译频率，通过断路器限制脚本执行时的内存使用）。
19.  返回结果
20.  脚本执行完毕后，将结果（例如，一个新计算的值、修改后的 \_source文档）返回给调用它的 ES 内部组件（如搜索模块、更新模块）。
21.  该组件再将最终结果整合到整个操作的响应中。

## **3.1.3 doc\_value 获取上下文**

doc\_values 本质上是一个序列化的列式存储，这个结构非常适合「**脚本**」、「**排序**」和 「**聚合**」等操作，ES 会为绝大多数字段类型都存储 doc\_values，为数不多的例外就是分词的类型，比如 text 就不会存储 doc\_values，也不支持设置 doc\_values 属性，关闭后无法使用「**脚本**」、「**排序**」和 「**聚合**」等操作来访问这个字段。

### **3.1.3.1 查询核心目标**

下面示例查询的目标是：​使用自定义脚本评分规则对航班数据进行动态排序。

具体实现：

1.  ​基础评分​：以 AvgTicketPrice（平均票价）作为基础分数。
2.  ​奖励机制​：对未取消的航班（Cancelled=false）额外增加10%的分数。
3.  ​安全防护​：通过字段存在性检查（containsKey）和空值检查（empty）避免脚本执行错误。

最终效果：​优先展示高票价且未取消的航班，结果中可见所有文档的 \_score都接近其 AvgTicketPrice值的1.1倍。

\# script doc\_value 获取上下文

GET kibana\_sample\_data\_flights/\_search

{

"size": 5,

"query": {

"script\_score": {

"query": {

"match\_all": {}

},

"script": {

"source": """

// 安全的 doc\_value 访问

double score = 1.0;

// 数值字段直接使用

if (doc.containsKey('AvgTicketPrice') && !doc\['AvgTicketPrice'\].empty) {

score = doc\['AvgTicketPrice'\].value;

}

// 布尔字段

if (doc.containsKey('Cancelled') && !doc\['Cancelled'\].empty) {

boolean cancelled = doc\['Cancelled'\].value;

if (!cancelled) {

score \*= 1.1;

}

}

return score;

"""

}

}

},

"\_source": \["AvgTicketPrice", "Cancelled", "Carrier"\]

}

## **3.1.4 \_source 获取上下文**

\_source 存储的是 ES 的原始文档，它会占用大量的存储空间，数据会压缩存储，读取时会有额外的解压缩开销，当你的业务场景「**不需要读取原始字段值**」时可以考虑关闭。

### **3.1.4.1 查询核心目标**

下面示例查询的目标是：​通过解析原始 JSON 文档（\_source）实现自定义评分逻辑。

与 doc\_values 方式的主要区别在于：

1.  ​原始数据访问​：直接操作存储的 JSON 文档而非列式存储
2.  ​灵活性优势​：可访问未定义 doc\_values 的字段
3.  ​计算逻辑​：
4.  基础分 = AvgTicketPrice（平均票价）
5.  未取消航班（Cancelled=false）额外获得 10% 加分
6.  ​安全机制​：通过 containsKey检查字段存在性

结果展示：所有文档的 \_score均为 AvgTicketPrice × 1.1（未取消航班），证明脚本正确访问了原始 JSON 数据。

\# script \_source 获取上下文

GET kibana\_sample\_data\_flights/\_search

{

"size": 5,

"query": {

"script\_score": {

"query": {

"match\_all": {}

},

"script": {

"source": """

// 安全的 source 访问

double score = 1.0;

// 直接访问原始 JSON 字段

if (params.\_source.containsKey('AvgTicketPrice')) {

score = params.\_source.AvgTicketPrice;

}

// 布尔字段处理

if (params.\_source.containsKey('Cancelled')) {

boolean cancelled = params.\_source.Cancelled;

if (!cancelled) {

score \*= 1.1;

}

}

return score;

"""

}

}

},

"\_source": \["AvgTicketPrice", "Cancelled", "Carrier"\]

}

13.  ​脚本执行与评分计算​：

15.  ​数据注入​：将解析后的 Map 结构注入到脚本的 params.\_source变量中
16.  ​字段存在性检查​：执行 params.\_source.containsKey('AvgTicketPrice')检查
17.  ​数值读取​：如果字段存在，读取 params.\_source.AvgTicketPrice值
18.  ​状态检查​：检查 params.\_source.Cancelled布尔值状态
19.  ​评分计算​：根据业务逻辑计算最终分数（未取消航班分数 ×1.1）
20.  ​分数返回​：脚本执行完毕，返回计算出的文档评分
21.  结果聚合阶段​：
22.  分片结果收集​：各数据节点完成本地评分后，返回 Top N 结果给协调节点
23.  ​全局排序​：协调节点对所有分片返回的结果进行全局合并排序

## **3.1.5 store 获取上下文**

它表示是否单独存储该字段的原始值，默认关闭（false），它与 \_source 是独立的，开启后会占用额外的存储空间。如果同时开启 \_source 和 store，就会将这个字段的原始内存保存 2 份，开启 store 属性的字段就会被单独存储，并且这些数据在磁盘上的存储是 「**不连续**」的，此时要读取多个字段就需要在磁盘上执行多次「**seek**」才能取回。

这时就需要权衡比较 \_source 和 store 的效率了，此时细心的老铁可能会有这样的疑问：「**既然 \_source 中已经存储了原始文档，那么为什么还需要额外的 store 属性呢？**」

1.  禁用 \_source 之后，可以指定 store 属性来单独保存某个或某几个字段。
2.  如果 \_source 中长文本，短文本共存时，当你只需要读取短文本时，如果使用 \_source 属性，ES 需要读取全部字段后返回其中的短文本，因此就会引入额外的开销，降低读取的效率，单独通过 store 保存短文本取出效率更高。
3.  设置 store 属性为 true，读取时不必在读取整个 source字段了。

## **3.3 Painess脚本基础与语法**

​在实战之前，先来看下 Painess 脚本的基础知识。

### **3.3.1 Painess脚本基础知识**

自ES 5.x 引入Painless，使得ES 拥有了安全、可靠、高性能脚本的解决方案。Painless是Elastic开发并做了专门的优化，相较之前的脚本更快、安全、易使用、可靠。

Painless脚本的目标是使编写脚本对用户来说无痛，特别是对于来自Java或Groovy环境的用户。它语法类似于Java，但更简单，并且是动态类型的（也支持静态类型）。

主要特点包括：

1.  ​强类型语言​：支持静态类型和动态类型（def关键字）
2.  Java语法兼容​：语法类似Java，支持大部分Java标准库
3.  高性能：直接编译成Java字节码运行。
4.  安全性：沙箱机制，限制对Java类的访问。
5.  易用性：语法简单，支持Java的部分语法。
6.  轻量级​：无需完整Java环境

主要用途包括：

1.  过滤脚本：根据复杂条件过滤文档。
2.  脚本化字段：动态计算和返回新字段。
3.  聚合脚本：在聚合中进行复杂的计算或动态分组。
4.  评分脚本：用于自定义搜索结果的评分逻辑。
