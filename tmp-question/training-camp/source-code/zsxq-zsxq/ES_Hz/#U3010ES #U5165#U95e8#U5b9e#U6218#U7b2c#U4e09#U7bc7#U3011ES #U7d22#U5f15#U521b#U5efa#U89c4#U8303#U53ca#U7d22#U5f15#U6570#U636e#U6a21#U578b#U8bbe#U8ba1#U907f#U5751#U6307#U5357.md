**02 ES 索引前置知识**

在正式进行实战 ES 索引创建之前，我们先来了解下 ES 索引的前置知识。

##   
**2.1 ES 索引基本概念**

索引指的是包含一堆有相似结构的文档数据（Document）。例如：商品索引、订单索引。在商品索引中我们可以存放成千上万的商品信息；在订单索引中我们可以存放成千上万的订单信息。

从这个角度上看，Index 和关系型数据库中的数据库类似。

  
![](images/FgXKg7eZ0ZeAP57VXwHPehBRIobd.png)

如图，Index 是一个逻辑的虚拟空间，在索引下面会有多个分片（至少一个分片），包括「**主分片**」和「**副本分片**」，分片是分布在各个节点上面，数据是存储在分片上。

当我们去创建索引的时候，它内部的元数据包含「**索引名称**」、「**分片数量**」、「**副本数量**」等默认信息。

##   
**2.2 ES 索引别名基本概念**

「**索引别名**」（alias）默认等同于「**索引名称**」，索引是一个逻辑的虚拟空间，「**索引别名**」则是在索引之上的又一层虚拟的「**空间**」。

###   
**2.2.1 ES 索引别名工作原理**

它允许我们在不更改查询代码的情况下，轻松地更改索引的映射或重新索引数据。别名的工作原理非常简单：它只是在 Elasticsearch 内部维护了一个从别名到索引名称的映射关系。当客户端向一个别名发起请求时，Elasticsearch 会自动将请求路由到该别名对应的索引上。

### **2.2.2 ES 索引别名应用场景**

1.  版本控制
2.  在 Elasticsearch 中，索引的映射和设置也可能随着需求的变化而发生变化。为了确保查询的正确性和一致性，我们可以使用别名来实现索引的版本控制。具体做法是：当索引的映射或设置发生更改时，我们创建一个新索引，并将其别名为旧索引的名称。这样查询代码可以继续使用旧索引名称，而实际上查询的是新索引。通过这种方式，我们可以实现无缝的版本切换，确保查询始终返回正确的结果。
3.  索引拆分
4.  随着数据的不断增长，单个索引可能会变得过大，导致查询性能下降。为了提高查询性能，我们可以考虑将大索引拆分为多个小索引。然而，拆分索引会带来一个问题：如何在查询时同时访问这些小索引？这时，别名就派上了用场。我们可以为每个小索引分配一个别名，然后使用一个统一的别名来引用这些小索引。这样，查询代码只需要使用统一的别名，就可以同时访问所有小索引，而无需知道底层索引的结构。
5.  滚动更新
6.  在一些需要定期更新索引的场景中，如日志分析、实时数据分析等，我们可以使用别名来实现滚动更新。具体做法是：创建一个新索引来存储最新数据，并将其别名为当前索引。随着时间的推移，我们可以逐渐将旧数据迁移到新索引中，并最终删除旧索引。通过这种方式，我们可以实现滚动更新，确保查询始终返回最新数据。同时，由于别名的存在，查询代码不需要做任何修改，就可以自动切换到新索引。

**2.3 ES 索引创建过程**

整个流程大致如下：

  
![](images/Fr8zTJ5wB3frgGFd0BJ5a2azC9Pm.png)

从这张图上可以看出，其流程分为三部分：「**协调节点流程**」、「**主节点流程**」、「**数据节点流程**」，我们分别来看下。

###   
**2.3.1 ES 协调节点流程**

客户端向 ES 节点发送创建索引请求，其处理流程如下：

1.  参数检查：对请求中的参数进行检查，检查参数是否合法，不合法的参数直接返回失败给客户端。
2.  数据预处理：
3.  如果请求指定了 pipeline 参数，则对数据进行预处理，数据预处理的节点为 Ingest Node。
4.  如果接受请求的节点不具有数据处理能力，则转发给其他能处理的节点。
5.  在 Ingest Node 上有定义好的处理数据的 Pipeline，Pipeline 中有一组定义好的 Processor，每个 Processor 分别具有不同的处理功能，ES 提供了一些内置的 Processor，如：split、join、set 、script 等，同时也支持通过插件的方式，实现自定义的 Processor。数据经过 Pipeline 处理完毕后继续进行下一步操作。
6.  自动创建索引：创建索引请求被发送到Master节点，由 Master 节点负责进行索引的创建，索引创建成功后，Master 节点会更新集群状态 clusterstate，更新完毕后将索引创建的情况返回给 Coordinate 节点，收到 Master 节点返回的所有创建索引的响应后，进入下一流程。
7.  请求预处理：
8.  检查参数、自动生成ID、处理 routing 等。
9.  获取集群状态信息，遍历所有请求，从集群状态中获取对应索引的元信息，检查mapping、routing、id信息，如果请求没有指定文档的id，则会生成一个 UUID 作为文档的id。
10.  检测集群状态：协调节点在开始处理时会检查集群状态，若集群异常则取消写入，如果Master节点不存在。
11.  路由算法及构建 shard 请求
12.  路由算法即根据请求的 routing 和文档id信息计算文档应该被索引到那个分片ID的过程。
13.  计算公式如下：[shard\_num = hash(\_routing) % num\_primary\_shards](http://shard_num%20=%20hash\(_routing\)%20%%20num_primary_shards)
14.  默认情况下，\_routing就是文档id，num\_primary\_shards 是主分片个数，所以从算法中即可以看出索引的主分片个数一旦指定便无法修改，因为文档利用主分片的个数来进行定位。
15.  当使用自定义 \_routing 或者id时，按照上面的公式计算，数据可能会大量聚集于某些分片，造成数据分布不均衡，所以ES提供了 routing\_partition\_size 参数，routing\_partition\_size 越大，数据的分布越均匀。
16.  分片的计算公式变为：[shard\_num = (hash(\_routing) + hash(\_id) % routing\_partition\_size) % num\_primary\_shards](http://shard_num%20=%20\(hash\(_routing\)%20+%20hash\(_id\)%20%%20routing_partition_size\)%20%%20num_primary_shards)，也就是说，\_routing 字段用于计算索引中的一组分片，然后使用\_id来选择该组内的分片。index.routing\_partition\_size 取值应具有大于1且小于 index.number\_of\_shards 的值。
17.  构建shard请求：将用户的 bulkRequest 重新组织为基于 shard 的请求列表。
18.  例如，原始用户请求可能有10个写操作，如果这些文档的主分片都属于同一个，则写请求被合并为1个。根据路由算法计算某文档属于哪个分片。遍历所有的用户请求，重新封装后添加到上述map结构。[Map<ShardId, List<BulkItemRequest>> requestsByShard = new HashMap<>()](http://Map<ShardId,%20List<BulkItemRequest>>%20requestsByShard%20=%20new%20HashMap<>\(\))；
19.  转发请求并等待响应：根据集群状态中的内容路由表确定主分片所在节点，转发请求并等待响应。遍历所有需要写的 shard，将位于某个 shard 的请求封装为 BulkShardRequest 类，调用 [TransportShardBulkAction#execute](http://transportshardbulkaction/#execute%20) 执行发送，在listener 中等待响应，每个响应也是以shard为单位的。如果某个 shard 的响应中部分 doc 写失败了，则将异常信息填充到Response 中，整体请求做成功处理。待收到所有响应后（无论成功还是失败的），回复给客户端。

### **2.3.2 ES 主节点流程**

![](images/Frk7X-3wki8cV_hWVpmDmY9CCDeU.png)

当主分片所在节点接受到请求后，节点开始进行本节点的文档写入，文档写入过程如下：

1.  文档写入时，不会直接写入到磁盘中，而是先将文档写入到 Index Buffer 内存空间中，到一定的时间，Index Buffer 会Refresh 把内存中的文档写入 Segment 中。当文档在 Index Buffer 中时，是无法被查询到的，这就是 ES 不是实时搜索，而是近实时搜索的原因。
2.  因为文档写入时，先写入到内存中，当文档落盘之前，节点出现故障重启、宕机等，会造成内存中的数据丢失，所以索引写入的同时会同步向 Transaction Log 写入操作内容。
3.  每隔固定的时间间隔 ES 会将 Index Buffer 中的文档写入到 Segment 中，这个写入的过程叫做 Refresh，Refresh 的时间可以通过 index.refresh\_interval，默认情况下为 1 秒。
4.  写入到Segment 中并不代表文档已经落盘，因为 Segment 写入磁盘的过程相对耗时，Refresh 时会先将 Segment 写入缓存，开放查询，也就是说当文档写入 Segment 后就可以被查询到。
5.  每次 refresh 的时候都会生成一个新的 segment，太多的 Segment 会占用过多的资源，而且每个搜索请求都会遍历所有的Segment，Segment 过多会导致搜索变慢，所以ES会定期合并 Segment，减少 Segment 的个数，并将 Segment 和并为一个大的 Segment；
6.  在操作 Segment时，会维护一个 Commit Point 文件，其中记录了所有 Segment 的信息；同时维护 .del 文件用于记录所有删除的 Segment 信息。单个倒排索引文件被称为 Segment。多个 Segment 汇总在一起，就是 Lucene 的索引，对应的就是ES中的 shard。
7.  Lucene 倒排索引由单词词典及倒排列表组成：单词词典：记录所有文档的单词，记录单词到倒排列表的关系，数据量比较大，一般采用B+树，哈希拉链法实现。倒排列表：记录单词对应的文档集合，由倒排索引项组成。倒排索引项结构如表所示：其中，文档ID：记录单词所在文档的ID；词频：记录单词在文档中出现的次数；位置：记录单词在文档中的位置；偏移：记录单词的开始位置，结束位置。
8.  每隔一定的时间（默认30分钟），ES会调用Flush操作，Flush 操作会调用 Refresh 将 Index Buffer 清空；然后调用 fsync将缓存中的 Segments 写入磁盘；随后清空 Transaction Log。同时当 Transaction Log 空间（默认512M）后也会触发 Flush 操作。

### **2.3.3 ES 数据节点流程**

当主分片完成索引操作后，会循环处理要写的所有副本分片，向副本分片所在的节点发送请求。副本分片执行和主分片一样的文档写入流程，然后返回写入结果给主分片节点。

主分片收到副本分片的响应后，会执行 finish() 操作，将收到的响应信息返回给 Coordinate 节点，告知 Coordinate节点文档写入分片成功、失败的情况；coordinate 节点收到响应后，将索引执行情况返回给客户端。当文档写入失败时，主分片节点会向 Master 节点返送 shardFieled 请求，因为主副本分片未同步，Master会更新集群的状态，将写失败的副本分片从 in-sync-allocation 中去除；同时在路由表中将该分片的状态改为 unassigned，即未分配状态。

## **3.2 ES 索引静态创建**

所谓静态创建，就是根据客观背景提前通过 API 创建好索引，提前做好索引数据分布和相应的设置。这是一种非常安全的模式，对于做运维监控的同学可能会有体会，比如我们的索引是按照日期自动滚动去创建。

如果你的集群上的索引很多，每天可能数千个，而且在某个时间点之后统一自动创建明天所有的索引，这个代价是很大的。

突然在你集群上集中创建上千个索引，会瞬间对集群的 master 节点造成很大的压力，需要消耗集群很大的资源，因为 maser 节点既要创建元数据，还要对数据进行分布，自动化任务的时候通常会遇到这个问题，所以尽量避免集中创建索引时，集群响应慢。

### **3.2.1 静态创建示例**

下面给出两种示例：

\# 删除索引

从上图得知：

1.  ​P (Primary Shard)​​ 是主分片​，负责存储索引的主要数据副本，所有写入操作都通过主分片，绿色实线框表示已正常分配并处于活动状态。
2.  ​R (Replica Shard)​ 是​副本分片​，主分片的完整拷贝，提供数据冗余​（防止数据丢失），提高读取性能​（支持并行查询），虚线框表示未分配状态。

在单节点 ES 集群中：

1.  主分片（P）会被分配，因为每个索引必须至少有一个主分片。
2.  副本分片（R）则不会被分配，因为「**副本分片**」不能与「**主分片**」分配在同一个节点上（这是为了保证高可用，如果主分片和副本分片在同一个节点，那么该节点挂掉，分片数据就都丢失了，失去了副本的意义）。因此在单节点集群中，副本分片会处于未分配状态（unassigned），用虚线表示。

所以，在我这个单节点的 ES 索引中：

1.  实线框的 p0-p3 是主分片，已经被分配到节点 8db0d1a58e99 上。
2.  虚线框的 r0-r3 是副本分片，它们没有被分配（unassigned），因为当前只有一个节点，无法分配副本（副本不能和主分片在同一节点）。

index.number\_of\_replicas: 0 # 关闭副本分片

\# 或在创建索引时指定

PUT /huazai-test-20250803

{

"settings": {

"number\_of\_shards": 4,

"number\_of\_replicas": 0

},

"mappings": {},

"aliases": {

"NAME": {}

}

## **04 ES 索引数据模型设计**

### **4.1 索引数据模型对比**

### **5.1.3 dynamic 属性引发的问题**

大概引发的问题有以下几种：

1.  字段数量不可控。
2.  误操作写入引入无关字段。
3.  集群性能杀手。

这里简单解释下：默认情况下，dynamic mapping 使得索引会根据写入的文档中新增的字段来增加 Mapping 中的字段，这样对于日志场景来说会产生大量的字段，而且混淆了写入误操作和查询操作就到导致检索语句中的查询语义字段设置为索引字段，那么如果字段大量激增，可能会带来什么后果呢？

由于索引字段的元数据信息会存储到集群的每一个节点上，当索引新增字段的时候，ES 必须为每个字段来更新集群中的状态，并且必须将集群里面的这些字段传递给所有的节点，对于大规模的集群来说，由于跨节点的集群状态传输是单线程的操作，因此需要更新的字段映射越多，完成更新所需的时间就越长，这种延迟通常会大大降低集群的性能，有时甚至导致整个集群宕机。

### **5.1.4 dynamic 属性问题解决方案**

从 ES 5.x 之后，ES 中的 Mapping 字段设置了一个上限参数：

index.mapping.total fields.limit: 1000

通常情况下，一个索引 Mapping 字段超过 100 个就是糟糕的设计，那么这种字段膨胀的问题如何解决呢？

这里我们提供两种解决方案：

1.  开启索引和 mapping 的 strict 严格模式。
2.  使用 Flattened 类型。

### **5.1.4.1 开启索引和 mapping 的严格模式**

1.  限制只有系统级别的索引可以自动创建。

## **5.2 ES Mapping 字段属性的填坑经验**

对于刚使用 ES 的同学来说，由于缺乏对 ES 技术栈的储备，从而埋下了很多坑。随着业务规模的扩大和系统数据规模的增长，出现各种各样的问题。

其中出现最多的问题就是建模过程中「**字段类型设置不合理**」，我们知道 ES 的字段属性大部分是不支持直接修改的，最后不得不通过「**重建索引的方式**」来解决， 而数据规模越大，重建索引的成本就越高。

###   
**5.2.1 ES Mapping 重要设置**

ES Mapping 的重要设置包括：

1.  \_source
2.  index
3.  enabled
4.  store
5.  doc\_values
6.  fielddata
7.  index\_option
8.  similarity

我们分别来看下。

### **5.2.1.1 \_source**

\_source 存储的是 ES 的原始文档，它会占用大量的存储空间，数据会压缩存储，读取时会有额外的解压缩开销，当你的业务场景「**不需要读取原始字段值**」时可以考虑关闭。

如果存储了 \_source 需要改变 mapping 结构的时候，由于存在原始数据，可以通过「**reindex**」操作来重建索引，但 TB 级别的索引很难通过「**reindex**」来重建。

那么为什么要存储原始文档呢？

因为 ES 使用「**倒排索引**」对文本进行搜索，而「**倒排索引**」是无法存储原始的输入文本，一旦文本交给 ES 之后，会经过「**分析器**」打散成单词进行处理。为了保证搜索的准确性，在打散的过程会去掉文本中的标点符号，统一文本的大小写，甚至对于英文中的发生变化的单词恢复成原型/词根，根据统一规整之后的单词建立「**倒排索引**」，经过如此一番处理之后，原始文本已经面目全非了，所以需要一个地方来存储原始文本信息以便在搜到这篇文档的时候能返回文档的原文，或者通过原始文档实现「**高亮显示**」或者基于原始文档进行「**reindex**」重建。

此时一定要存储原始文档吗？

其实是不一定的，如果只关心一篇文档「**是否存在**」而不关心文档的内容，也不需要做「**reindex**」，我们可以选择不保存 \_source 字段。在之前的实战经验中得出，对于大文本字段来说，不保存\_source 字段大约可以节省 30 %的磁盘空间。

但禁用 \_source 后也会带来一些后遗症：

1.  无法使用 update、update\_by\_query、reindex 等操作。
2.  无法高亮、返回原文。
3.  无法修改 mapping、升级到 ES 主版本等。

如果只是考虑「**存储空间**」，更建议通过设置更高级别的「**索引压缩存储方式**」来减少对磁盘空间的消耗，这时也可以大约可以节省 30 %的磁盘空间。

示例：

DELETE huazai-test-20250805

PUT huazai-test-20250805

{

"settings": {

"index.codec": "best\_compression"

}

}

### **5.2.1.2 index**

它表示是否加入「**倒排索引**」，默认开启（true），当关闭时就不会对该字段进行分词，也不会存储这个字段的「**倒排索引**」，所以关闭后无法对该字段进行「**全文搜索**」的。但是这个字段仍然会存储到 \_source 和 doc\_values 中，且可以用来「**排序**」和 「**聚合**」的。

###   
**5.2.1.3 enabled**

它类似 index 和 doc\_values 的总开关，默认开启（true）。关闭后字段只会存储到 \_source，index 和 doc\_values 中都不会被存储。

所以这个字段不可以被「**搜索**」、「**排序**」和 「**聚合**」，但是可以通过 \_source 获取到原始值。

###   
**5.2.1.4 store**

它表示是否单独存储该字段的原始值，默认关闭（false），它与 \_source 是独立的，开启后会占用额外的存储空间。如果同时开启 \_source 和 store，就会将这个字段的原始内存保存 2 份，开启 store 属性的字段就会被单独存储，并且这些数据在磁盘上的存储是 「**不连续**」的，此时要读取多个字段就需要在磁盘上执行多次「**seek**」才能取回。

这时就需要权衡比较 \_source 和 store 的效率了，此时细心的老铁可能会有这样的疑问：「**既然 \_source 中已经存储了原始文档，那么为什么还需要额外的 store 属性呢？**」

1.  禁用 \_source 之后，可以指定 store 属性来单独保存某个或某几个字段。
2.  如果 \_source 中长文本，短文本共存时，当你只需要读取短文本时，如果使用 \_source 属性，ES 需要读取全部字段后返回其中的短文本，因此就会引入额外的开销，降低读取的效率，单独通过 store 保存短文本取出效率更高。
3.  设置 store 属性为 true，读取时不必在读取整个 source字段了。

### **5.2.1.5 doc\_values**

它本质上是一个序列化的列式存储，这个结构非常适合「**脚本**」、「**排序**」和 「**聚合**」等操作，ES 会为绝大多数字段类型都存储 doc\_values，为数不多的例外就是分词的类型，比如 text 就不会存储 doc\_values，也不支持设置 doc\_values 属性，关闭后无法使用「**脚本**」、「**排序**」和 「**聚合**」等操作来访问这个字段。

###   
**5.2.1.6 fielddata**

它跟 doc\_values 一样，也是列式存储，默认为禁用，但是 id 字段除外。这个结构非常适合「**排序**」和 「**聚合**」等操作场景，需要注意的是「**fielddata**」 的构建和管理都是在 「**内存**」中。

加载「**fielddata**」是一个昂贵的过程，可能会带来索引读写的延时，一旦加载，它会常驻「**JVM 内存**」，可以使用 ES 提供的 API 来手动释放。

###   
**fielddata 管理**

\# 清理 fielddata 加载到 jvm 中的内存

POST /huazai-test-20250805/\_cache/clear?fielddata=true

\# 查看当前 ES 中 fielddata 内存占用情况

GET /\_stats/fielddata?fields=\*

GET /\_nodes/stats/indices/fielddata?fields=\*

GET /\_nodes/stats/indices/fielddata?level=indices&fields=\*

### **fielddata 内存限制**

这些设置都是针对「**节点级别**」的，我们可以来对 fielddata 的 JVM 堆内存限制，默认40%：

indices.breaker.fielddata.limit:40%

也可以设置各种查询聚合的 JVM 堆内存限制，默认 60%：

indices.breaker.request.limit:60%

另外还可以设置 总 JVM 堆内存限制，包括但不限于前两个，默认为当前节点的 95%

indices.breaker.total.limit:95%

如果 [indices.breaker.total.use\_real\_memory](http://indices.breaker.total.use_real_memory/) 设置为 false，此 [indices.breaker.total.limit](http://indices.breaker.total.limit/) 值默认是 75%。

> 注意：ES 7.x 前后版本默认值存在差异，实际场景中需要根据具体的业务场景来设置。

### **慎用 fielddata**

我们知道 JVM 堆内存的设置超过 32 G 就不会使用「**压缩指针**」了，为了提高系统的内存使用率，在生产部署 ES 时，我们的 JVM 配置一般小于 32G，当然也需要留出「**一半的内存**」给操作系统的 PageCache，由于使用 JVM 堆内存比较昂贵，所以默认会禁用字段的 「**fielddata**」属性，对于大文本/数据规模庞大的业务，不建议开启「**fielddata**」属性，推荐使用「**doc\_values**」。

对于数据量达到 TB 级别的索引，我们要慎重使用 「**fielddata**」，特别是 \_id 字段默认会开启「**fielddata**」，但是不会主动构建，如果不小心使用 \_id 字段来「**排序**」的话，就会将 \_id 字段的「**fielddata**」加载到 JVM 的堆内存中，对于低版本的 ES，可能会导致不断的 GC，最后节点直接 OOM。

所以在官方的文档中也提到：不建议使用 \_id 字段来排序，对于自定义 id 的场景，可以单独将业务的 ID 存储到某个字段，然后开启「**doc\_values**」来做排序使用。

> 注意：从 ES 8.x 版本开始，默认不再支持 \_id 排序。

### **5.2.1.7 index\_option**

它是用来配置「**倒排索引**」存储哪些信息的，其影响字段「**搜索**」、「**排序评分**」、「**高亮**」，主要包含 docs、freqs、positions、offsets 四个配置项。

这里我们需要了解「**倒排索引**」的组成：Term（单词）、Term Dictionary（单词词典）、Term Index（单词索引）、Posting List（倒排列表）。

1.  首先 Term 是字段是字段原文经过分词器处理后的一个个的单词，可以通过 GET \_analyze API 查看文本被分成了哪些 Term。
2.  Term Dictionary 是经过排序后的全部 Term 的集合，在 ES 中存储的文件后缀为 tim。
3.  Term Index 是 Term Dictionary 的索引，用来加速 term 查找速度。存储的是 term 的前缀与Term Dictionary 的 Block 之间的映射关系。它可以压缩存储且可以加载到内存。
4.  Term Index 也会存储到磁盘中，它的后缀为 tip 这样我们在内存的清理或者集群重启时快速在内存中构建 Term Index，在内存中的 Term Index 叫做 fst，它是一个带输出的有限状态机。值得关注的是 ES 从 7.3 版本开始，将 fst 由堆内存转到堆外内存（offheap），由操作系统的 PageCache 来管理。我们前面提到针对 JVM 堆内存设置在 32 G 以内情况才会开启「**压缩指针**」，所以堆内存是不可扩展的，7.3 的 offheap 是一个重要版本特性，早期的 JVM 堆内存占用最大的就是这个 fst，一般 1TB 的索引差不多会有 2TB 的 fst 内存占用。
5.  值得欣喜的是从 ES 7.7.0 版本开始将 \_id 字段开始移植到堆外内存（offheap）中，在选择版本时一定要多阅读对于版本的 release 文档。  
    
6.  Posting List(倒排列表)：记录 Term 对应的文档 ID 集合，设置 Term 在文档中的位置信息，存储文档的词频（Term frequency）和偏移量（offset）。

index\_option 的默认值有两种：

1.  被分析器分析的字符串字段比如 text 类型字段，使用 position 作为默认值。
2.  其他的字段比如 keyword，数值类型字段使用 docs 作为默认值。

如何查看指字段的倒排索引存储了哪些部分?

GET /huazai-test-20250805/\_termvectors/1?fields=fieldName

### **5.2.1.8 similarty**

它配置字段的文本评分算法或相似度，默认用的是BM25。只能对 text 和 keyword 类型配置，数值类型无法使用。

如果仅用于过滤和基于字段的「**排序**」、「**聚合**」排序，聚合可以将 **similarty** 设置为 bool 值。

### **5.2.2 ES Mapping 字段属性如何设置**

这里大概有 4 步：

1.  确定字段的数据类型。
2.  确定字段是否需要分词和高亮。
3.  确定字段是否需要排序和聚合分析。
4.  确定字段是否需要单独存储。

### **5.2.2.1 确定字段的数据类型**

1.  需要使用范围过滤或数值排序的的数值类型设置为数值。
2.  只进行 term 过滤的数值类型使用 keyword。
3.  如果数值类型字段存储的值是可枚举的，使用 keyword 压缩率更高。

### **5.2.2.2 确定字段是否需要分词和高亮**

1.  不需要分词的字段，index 属性可以设置为 false。
2.  字段不用于搜索也不用于排序，可以设置 enabled 为 false。
3.  考虑这字段使用的查询方式和高亮方式，设置 index\_option 为 offsets。

### **5.2.2.3 确定字段是否需要排序和聚合**

1.  不需要排序的 keyword 或数值类型，doc\_values 设置为 false。
2.  需要分词的字段也需要排序，不推荐开启 fielddata，可以增加一个 keyword 的子字段。

### **5.2.2.4 确定字段是否需要单独存储**

1.  不需要高亮和展示字段原始值，也不会重建索引和脚本操作可关闭字段的 \_source。
2.  长短字段共存，需单独取回的短字段可设置 store 为 true。
3.  避免使用 store 查询多个字段，因为 store 在磁盘上存储是不连续的， ES 在读取不同的 store 的值的时候，每个字段的读取都需要在磁盘上进行 seek 操作。
