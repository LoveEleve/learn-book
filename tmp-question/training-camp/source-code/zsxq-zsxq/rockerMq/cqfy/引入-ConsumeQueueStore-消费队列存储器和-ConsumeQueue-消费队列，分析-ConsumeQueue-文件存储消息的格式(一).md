剖析消费消息功能的实现原理  
  
在前面的章节，我们已经把 Broker 节点接收消息，处理消息，最终将消息落盘的全部功能都实现完毕了，整个功能的执行流程我也从头到尾为大家梳理了一遍，那这么看的话，消息队列框架存储消息的核心功能就算是实现完毕了，接下来就应该构建消费者客户端，然后实现消费者客户端消费消息的功能了。按照流程来说，接下来就应该这么做了。但是，目前我们还不能直接就去关注消费者客户端，因为在目前实现的消息队列框架存储消息的核心功能中，还存在一个巨大的缺陷等待我们修复。我这么说大家可能不太理解，毕竟我们实现消息存储功能时一切都是那么流畅，那么丝滑，各种性能优化的细节也都考虑周到了。既然是这样，那程序还存在什么问题呢？这个时候，我们就不能只关注消息存储的情况了。  
  
请大家想一想，我们为消息队列框架构建 Broker 模块的目的是什么？就目前实现的功能来说，Broker 存在的作用非常明显，那就是管理并存储生产者客户端生产的消息，尽管我们为消息队列框架引入了新的 Proxy 模块，但是 Proxy 模块仍然会把生产者生产的消息转发给 Broker 节点， 而 Broker 节点接收到消息后，就会把消息交给存储引擎去处理，不管是什么主题下的消息，这些消息都会被存储到本地的 CommitLog 文件夹的多个文件中 ，这个流程大家肯定都很熟悉了。很好，那现在新的问题就来了，不管是什么主题下的消息都会被存储到 CommitLog 文件夹的文件中，这就意味着一个本地文件中可能会存储了不同主题下的很多消息，比如说 CommitLog 文件夹中的第二个本地文件中存储了来自不同的五个主题下的消息，如果是这种情况的话，那如果我想从 CommitLog 文件夹中本地文件中查询某个主题下的消息时，该怎么查询呢？  
  
这时候其实我们就要关注 Broker 模块的第二个功能了，也就是为消费者客户端提供消费消息的功能。之前我们说 Broker 模块的核心功能是管理并且存储生产者生产的消息，没错，确实是这样，但这只是 Broker 模块核心功能的一部分，而另一部分核心功能就是要为消费者客户端提供消费消息的功能。当然，消息具体消费的逻辑肯定是用户在消费者客户端定义的，但是消费者客户端要想消费消息，肯定得访问存储了消息的 Broker 节点吧？比如说消费者客户端想消费 Test 主题下的所有消息，那消费者客户端肯定得访问 Broker 节点，到 Broker 节点内部查询 Test 主题下的所有消息，Broker 节点把该主题下的消息不断返回给消费者客户端，这样一来，消费者客户端得到了可以消费的消息，才能根据用户定义的逻辑正常消费消息。这个逻辑大家可以理解吧？  
  
那现在我们关心的就是消费者客户端怎么从 Broker 节点查询指定主题下的消息，刚才我们已经分析了，Broker 节点会把接收到的所有生产者消息都存储在 CommitLog 文件夹下的文件中，这也就意味着 CommitLog 文件夹中的某个文件中会存储多个主题下的消息，这样一来，从 CommitLog 文件夹中查询指定主题的消息似乎就有些困难了。按照常规思路， 如果一个文件中存储的都是同一主题的消息，那么当要查询指定主题的消息时，直接先判断哪些文件中存储的消息属于该主题之下，只要找到了对应的文件，或者说只要确定了这些本地文件对应的内存映射对象，那就可以直接操作对应的内存映射对象，得到该主题下的所有消息返回给消费者客户端 。如果要我为 Broker 节点实现查询指定主题下的消息的功能，那我就会按照刚才分析的常规思路来实现，我相信大家肯定也会选择这种方式。  
  
可现在我们面临的情况是，所有的消息都混杂在一起，存储在了 CommitLog 文件夹的多个本地文件中，如果要查询某些主题下的消息，并且不遗漏该主题下的任何一条消息，现在看来，似乎只能使用最笨拙的方法，也就是遍历 CommitLog 文件夹下的每一个文件，读取每一个文件中存储的每一条消息，判断遍历到的每一条消息是否属于对应主题，这个逻辑没问题吧？我们确实可以这么做，但这么做效率显然太低了，可能消费者客户端要消费的主题下只有一条消息，但是为了从 Broker 中查询这条消息，不得不遍历了 CommitLog 文件夹中的所有文件，这实在是非常愚蠢的做法，每一个有追求的程序员肯定都不屑在程序中使用这种方式查找指定主题下的消息。那么，为了改善这种情况，或者说为了提高程序查询执行主题消息的效率，我们可以怎么做呢？这个问题无法逃避，必须解决，只有解决了这个问题，消费者客户端才能更快地消费 Broker 节点存储的消息，也就是说， 为 Broker 节点实现一个完美的查询指定主题消息的功能，是实现消费者客户端消费消息的前提 。那这个完美的功能该怎么实现呢？  
  
也许大家现在还没什么头绪，不知道该怎从何处着手解决这个问题，但在我看来，解决这个问题的方式非常简单，那就是按照我们之前分析得那样： 要是能让一个本地文件中存储的都是同一主题的消息，那么当要查询指定主题的消息时，直接先判断哪些文件中存储的消息属于该主题之下，只要找到了对应的文件，或者说只要确定了这些本地文件对应的内存映射对象，那就可以直接操作对应的内存映射对象，得到该主题下的所有消息返回给消费者客户端 。这个逻辑大家可以理解吧？按照常规逻辑，就该这样来解决问题，但令我们头疼的地方也就在这里，CommitLog 文件夹中的本地文件并没有像我们希望的那样，只存储单一主题下的消息，那想到这里，我相信大家都会开始有意识的思考， 那有没有一种方法，可以让我们以主题信息为区别，把 CommitLog 文件夹中本地文件存储的消息区分开呢 ？比如说当 Broker 节点的消息存储引擎把每一条消息存储到本地文件时，我们能不能在程序中启动一个后台线程，这个后台线程所做的就是把存储到 CommitLog 文件夹中的每一条消息重新投放到对应主题的本地文件中呢？当然，这就意味着我们要先在程序内部为各个主题创建对应的本地文件，当 Broker 节点存储消息时，后台线程就可以判断每一条消息所属的主题信息，然后把消息重新投递到对应主题的本地文件中。如果能实现这个功能，那么要从 Broker 节点查询指定主题的消息时，就可以直接去对应主题的本地文件中查询了，对吧？大家可以品味品味这个逻辑。  
  
当然，我知道这个时候大家肯定会有一个疑问，把一条消息从 CommitLog 文件夹的本地文件中重新投递到另一个主题文件中，一条消息存储两份，这显然也太浪费本地硬盘空间了？而且这也就意味着同样的消息要被刷新到硬盘两次，除非你是有意对数据做更多的备份，否则这么做只会影响程序执行效率，聪明的程序员显然也不会这么做，不会为了解决一个棘手的问题而引入新的问题。这样分析下来，启动后台线程根据主题重新分发消息的方式似乎也行不通，那么我们应该怎么做呢？  
  
我想说的是，请大家先把这个问题放到一边，然后仔细想一想，如果我们不考虑主题信息，就只是单纯想从 CommitLog 文件夹中的本地文件中查询一条消息，这个时候应该怎么查找呢？这个功能应该怎么实现呢？或者说要查询消息的时候，必须知道什么关键信息呢？总不能凭空查找吧，你至少得让程序知道你想查询那条消息。 比如说你想从 CommitLog 文件夹的本地文件中查询消息，是不是必须提供这条消息在 CommitLog 文件夹中的全局偏移量和消息大小 ？ 知道了这条消息在 CommitLog 文件夹中的全局偏移量，就可以根据这个全局偏移量确定这条消息所在本地文件的索引，并且还可以确定这条消息在对应本地文件中的相对便宜量，而知道了相对偏移量，又知道了这条消息的大小，就可以直接操作本地文件对应的内存映射文件对象，直接获取这条消息了 。也许大家已经忘记之前实现的一些方法了，接下来就让我把相关方法展示一下。

接下来就让我为大家解释一下，之前我们已经分析过了，快速从 Broker 节点中查询指定主题下的消息的方式似乎只有一种： 那就是让一个本地文件中存储的都是同一主题的消息，那么当要查询指定主题的消息时，直接先判断哪些文件中存储的消息属于该主题之下，只要找到了对应的文件，或者说只要确定了这些本地文件对应的内存映射对象，那就可以直接操作对应的内存映射对象，得到该主题下的所有消息返回给消费者客户端 。为了实现这个功能，我们也提出了一种设想：那就是先在程序中为各个不同的主题创建对应的本地文件，然后在程序中启动一个后台线程，当 Broker 节点存储消息时，只要有消息被存储到了 CommitLog 文件夹中，确切地说，是被写入到了 CommitLog 文件夹中本地文件对应的内存缓冲区中，后台线程就可以判断每一条消息所属的主题信息，然后把消息重新投递到对应主题的本地文件中。这个逻辑想必大家都还记得。但这个功能的实现逻辑很快就被我们否决了，因为把相同的消息刷新到本地硬盘两次，这么做既浪费硬盘空间，也影响程序运行效率。我相信大家也都认同我的做法。  
  
但是，朋友们，现在情况有些不一样了，因为我们刚刚实现了一个新的功能，那就是根据消息在 CommitLog 文件夹中的全局偏移量和总大小，从 CommitLog 文件中查询指定消息的功能，也就是说， 只要知道了一条消息的全局偏移量和总大小，就能很快从 CommitLog 文件夹中定位并返回这条消息本身 。如果是这样的话， 那我们仍然可以启动一个后台线程重新分发 CommitLog 文件夹中的消息，只不过这次分发的时候不需要把消息全部内容分发出去，只要把每一条消息的全局偏移量和消息大小重新投放到所属主题的本地文件中不就行了吗 ？这样一来， 当消费者客户端从 Broker 节点查询某个主题下的所有消息时，直接到对应主题的本地文件中的到每一条消息的全局偏移量和大小，然后再根据这些信息到 CommitLog 文件夹中查询每一条消息的真正内容即可 。这种实现思路显然更加优秀，而且每一条消息存储到 CommitLog 文件夹中的本地文件时，这条消息在 CommitLog 文件夹中的全局偏移量已经确定了，这条消息的总大小也已经确定了，这么一来，不正好可以把消息的关键信息重放到对应主题的本地文件中吗？  
  
分析到这里，我相信每一位朋友们都意识到了，实际上在 RocketMq 源码中，消费者客户端到 Broker 节点消费消息的核心原理就是我们刚才分析的那样： 消费者客户端会先访问消息所属主题的对应文件，得到该主题下的每一条消息的关键信息，也就是消息在 CommitLog 文件中的全局偏移量和消息的大小，然后就可以根据每一条消息的关键信息到 CommitLog 文件夹中查询每一条消息的具体内容 。由此看来，我们之前认为把消息刷新到本地硬盘只是 Broker 节点存储消息的部分核心功能也是很有道理的， 存储消息的完整流程显然还应该包括消息重放，也就是在存储消息的时候，根据消息所属主题把消息重新投放到对应的主题文件中，并且消息重放的功能似乎比消息存储到 CommitLog 文件夹的功能更加重要 ，出现一点偏差都会导致消费者客户端无法从 Broker 节点消费消息，如果消息根本无法被消费，那存储它又有什么意义呢？  
  
好了，其他多余的内容我就不再展开分析了，毕竟现在还没有真正实现消费者客户端，我们现在最关心的应该是消息重放的功能如何实现。当然，这个功能的实现也可以拆分成几个阶段，之前我们已经分析了， 所谓消息重放其实就是在程序中启动一个后台线程，只要有消息被写入到 CommitLog 文件的内存映射缓冲区了，这个后台线程就可以解析 CommitLog 文件内存映射缓冲区中的每一条消息，得到每一条消息在 CommitLog 中的全局偏移量和消息总大小，然后把每一条消息的关键信息重访到对应主题的本地文件中即可 。这个逻辑我们已经重复了好几遍了，但现在要开始真正实现这个功能了，就必须得更仔细地对其进行分析，看看我们要从哪些方面入手。  
  
就比如说吧，要想根据主题信息实现消息重放功能，那肯定就得把主题对应的本地文件创建出来吧？本地文件创建完毕了，还得启动后台线程执行消息重放操作吧？那这个后台线程该怎么定义，怎么启动呢？当后台线程开始执行工作时，要怎么从 CommitLog 文件夹中解析出每一条消息的关键信息呢？而且在重放的时候还必须要保证重放消息的连续性，不能出现消息丢失的情况，更不能出现对同一条消息重复重放的情况，那这一点要怎么保障呢？你看，只是简单分析一下，就衍生出四个新的问题，这些问题可都关乎到代码的具体实现细节啊，由此可见，消息重放功能并不是那么容易就能实现的。当然，大家也没必要担心它的难度究竟有多高，接下来我会为大家仔细拆分，实现其中的每一个细节功能。  
  
引入 ConsumeQueue 消费队列和 ConsumeQueueStore 消费队列管理器  
  
首先我们来思考一下主题对应的本地文件该如何定义吧，这个本地文件可以说是消息重放功能的基础，否则要被重放的消息根本无法存储。当然，看到这里也许有朋友会觉得既然消息重放不需要把完整消息重新投放，只重新投放消息的关键信息，那为何不直接把这些信息缓存到内存中呢？我不这么做的原因很简单，这么做显然会占用更多的内存资源， 如果在程序中启用了内存读写分离功能，那么申请对外内存已经占用了一部分内存，现在把每一条消息的关键数据直接缓存到内存中，会导致内存资源非常紧张，甚至根本就不够用；第二就是老生常谈的问题了，不对数据执行持久化操作，那么被重放的消息一旦丢失，那么与其对应的在 CommitLog 文件夹中的消息就无法被消费者客户端消费了 。考虑到这两点，我们肯定要优先选择把数据持久化到本地的方式，也就是说，要给不同的主题创建本地文件。  
  
好了，明确了这一点之后，接下来我们就可以毫无顾虑地为主题创建对应的本地文件了。当然，其实这个本地文件很好创建，它就是一个文件啊，直接创建即可，直接调用 Java 的创建本地文件的方法即可；但是，我想说的是，创建文件只是一个开始，之后的操作最重要的，那之后要执行什么操作呢？很简单，把消息重访到对应主题的本地文件中，这就会涉及到数据刷新到本地硬盘的操作；而必要的时候，还需要从本地文件中读取数据，这就涉及到把数据加载到内存的操作。那看到本地文件数据的刷新和加载操作，我们肯定就会想到内存映射机制，毕竟我们之前刚刚为 CommitLog 文件夹中的本地文件实现了这个内存映射机制， 那现在要操作主题对应的本地文件了，我们同样也可以使用内存映射机制操纵这些本地文件，把数据刷新到本地文件、或者从本地文件中加载数据到 pagecache 中 。也就是说， 我们在为主题创建对应的本地文件时，只需要创建一个 DefaultMappedFile 对象即可，这样一来不仅会把本地文件创建完毕，而且还会把该文件映射到内存中 。这个逻辑大家可以理解吧？  
  
好了，为主题创建对应的本地文件的方式已经确定了，那接下来就可以把消息写入到本地文件中了。这个时候就有一个新的问题了，那就是消息写入文件的格式是什么呢？现在我们已经知道了，在消息重放的过程中，会把 CommitLog 文件夹中的每一条消息重放到该消息所属主题的本地文件中，并且只会存储每一条消息的关键信息，也就是消息的大小以及该消息在 CommitLog 文件夹中的全局偏移量。这就意味着存储到主题本地文件中的消息都是定长的，长度不会发生变化，如果我们就设置一个消息写入格式： 比如说使用 8 个字节存储消息在 CommitLog 文件夹中的全局偏移量，使用 4 个字节存储消息的总大小 ，这样一来， 每一条消息在主题本地文件中的大小就是固定的，也就是十二字节 。那当消费者客户端向主题文件中查询该主题下的所有消息时，就可以每次读取十二个字节，这样读取到的每一条重放消息都是完整的，然后解析消息得到这条消息的全局偏移量和大小，最后去 CommitLog 文件夹中查询消息的具体内容即可，这个逻辑可以理解吧？  
  
很好，现在要被重放的消息写入主题文件的格式也确定了，那我们就可以在程序中直接使用这种格式写入消息吗？本来是可以的，但是对照了 RocketMq 的源码之后，我发现我们不能真的这么做，消息写入的格式还需要稍微重构一下， 而重构的关键就是把消息的 tag、也就是二级标签信息补充完毕 。  
  
tag 标签大家应该都不陌生了吧？我们都知道，在有些情况下， 生产者客户端在生产消息的时候会给消息定义一个 tag 标签，以便消费者客户端在消费消息的时候可以根据要消费的消息的 tag 标签进一步过滤消息，只消费 tag 一样的消息 。那这个消息是怎么过滤的呢？在 RocketMq 源码中其实是这样的： 实际上 tag 标签信息也是重放消息的一部分，用 8 个字节存储 ，这样一来， 重放消息的总大小就成了 20 字节，而主题文件中的消息单元肯定也是 20 字节了，每 20 个字节就是一条完整消息 。 在消费者客户端到 Broker 节点查询消息时，会先去消息所属主题的文件中查找，查找的过程会对比每一条重放消息的 tag 信息，然后根据消息的 tag 对每一条消息执行过滤操作，tag 匹配的消息才会被保留下来。在这之后，消费者客户端就得到了要消费的主题下，与自己关注的 tag 信息一致的所有重放消息，接下来就可以使用过滤后得到的重放消息去 CommitLog 文件夹中查询每一条消息的具体内容了 。这就是源码中消费者客户端查询并获得消息的核心逻辑和流程，当然，这个过程中肯定还有很多其他的细节，但这些内容我就不展开讲解了，等后面为大家实现消费者客户端消费消息的功能时，大家就全部都明白了。总之，大家现在只要清楚 tag 标签信息也是重放消息的一部分就行了，这样分析下来，重放消息写入主题本地文件的格式就成了这样： 本条消息在 CommitLog 文件夹中的全局偏移量，这部分信息占用 8 字节；本条消息的总大小，这部分信息占用 4 字节；本条消息的 tag 标签，这部分信息占用 8 字节；这几个字节加起来总共是 20 字节，这就意味着每一条重放消息的大小为 20 字节，是定长的，这也就意味着主题文件中的消息单元就是 20 个字节 。那么消费者客户端到主题文件中查询消息时，只要每次读取 20 个字节，就可以每次读取到一条完整的消息，把所有消息都检查完毕。这个逻辑应该很好理解吧？  
  
很好，如果大家理解了以上的逻辑，那么现在 Broker 节点再执行消息存储操作时，要执行的整个流程就变成这样：只要 Broker 节点接收到了消息，有消息被写入到了 CommitLog 文件夹中，也就是本地文件对应的缓冲区中，这个时候消息重放后台线程就可以解析缓冲区中的每一条新消息，解析出消息的关键信息后，然后按照我们之前分析的格式对消息进行重放，使用内存映射机制把重放消息写入到主题文件对应的缓冲区中，最终刷新到本地硬盘中。这样一来， 随着重放消息不断写入主题文件文件，那一个文件写满了肯定就创建新的文件，这一点大家可以理解吧？那这就意味着一个主题下也许存在多个本地文件，那显然还需要对每个主题的多个本地文件进行管理，对吧 ？如果是这样的话，那肯定还是需要用到 MappedFileQueue 内存映射文件管理器。当然，就算要用到 MappedFileQueue 内存映射文件管理器，也肯定不能直接使用，而是需要对这个管理器做一层包装，就像 CommitLog 文件夹中存放着多个本地文件，在程序中使用了 CommitLog 对象来操作 CommitLog 文件夹，而 CommitLog 对象则持有了 MappedFileQueue 内存映射文件管理器； 现在我们要往主题文件中存储消息，而一个主题下可能存在多个本地文件，那么我们不妨就放照 CommitLog 文件夹那样，在程序中为主题文件定义一个对象，让这个对象操作主题文件，并且这个对象也要持有 MappedFileQueue 内存映射文件管理器管理众多内存映射文件 ，这个逻辑大家可以理解吧？  
  
很好，这个时候就可以引入一个新的类了，那就是 ConsumeQueue 类， 因为主题文件中的消息是被消费者客户端使用的，所以我就定义一个 ConsumeQueue 消费队列，这个消费队列就对应着一个主题，然后在消费队列中定义一个 MappedFileQueue 成员变量，而 MappedFileQueue 内存映射文件管理器就是用来创建并管理内存映射文件的；这样一来，消费队列就可以存储重放消息了，如果某个本地文件写满了，就可以使用 MappedFileQueue 创建新的本地文件 。这就是目前 ConsumeQueue 消费队列的简单定义，当然，为了让 ConsumeQueue 类稍微丰富一些，我还可以直接给它定义一个 putMessagePositionInfo() 方法，该方法就是用来把重放消息存放到本地文件中的，根据我们之前分析的消息重放格式，这个方法显然需要接收三个参数，第一个就是消息的全局偏移量，第二个就是消息总大小，第三就是消息的 tag 标签信息。这样分析下来，这个 ConsumeQueue 类就可以先定义成下面这样，请看下面代码块。
