在这一章我们要为生产者客户端实现生产消息的功能，所谓生产消息就是生产者客户端把消息发送给存储引擎的操作，这样一来，消费者客户端就可以去存储引擎消费这条消息了。看到这里，可能会有朋友终于忍不住提出疑问，我在前面的文章中已经不止一次提到存储引擎，不断重复生产者客户端会把消息发送给存储引擎这句话，那么存储引擎究竟是什么呢？生产者生产的消息不是应该发送给 Broker 节点吗？其实是这样的， 生产者客户端确实会把消息发送给 Broker 节点，Broker 节点接收到消息后并不会执行存储操作，而是会把消息交给 store 存储模块下的 DefaultMessageStore 默认存储引擎来存储 ，所以我才经常说生产者客户端会把生产的消息发送给存储引擎这句话。当然，刚才我们分析的是 RocketMq 5.0 之前版本的消息生产和存储流程，在 5.0 之后的版本中， 生产者客户端会先把生产出来的消息发送给 Proxy 服务端，Proxy 服务端会把消息转发给 Broker 节点，Broker 节点接收到消息后，会把消息交给 DefaultMessageStore 存储引擎存储 。在后面的版本代码中，我会为大家把这些功能全部实现，现在，先让我们看看生产者客户端怎么生产消息吧，以及怎么把消息发送给 Proxy 服务端。

引入 PublishingLoadBalancer 发布消息负载均衡器  
  
在文章开头我为大家分析了实现生产者发送消息功能的三个要点，第一个要点就是把消息定义出来，这个功能已经实现了，第二个要点消息是定义发送消息的方法，第三个要点能够选择消息被发送到的目标节点。现在第二个功能还没实现，我就要实现第三个功能，大家肯定有些奇怪。这其实没什么可奇怪的，因为在发送消息的过程中要选择目标节点，也就意味着第二个功能建立在第三个功能完成的基础上，那我们索性先把第三个功能实现了，再回过头实现第二个功能，这就岂不是更顺畅？  
  
第三个功能就是为消息选择目标节点，目标节点选择成功了，就可以把消息发送出去了。用专业术语来说， 我们一般把这个功能成为负载均衡功能 。生产者客户端向 Proxy 服务端查询了指定主题的路由信息后，肯定会接收到很多节点的信息， 而负载均衡要做的就是使用恰当的策略，在生产者客户端每次生产发送消息时，从这一堆路由信息中选择出合适的目标节点接收消息 。所以我们要专门为负载均衡功能定义一个负载均衡器，这个负载均衡器就可以在每次发送消息时，从所有可路由新的节点信息中选择合适的目标节点。那这个负载均衡器应该怎么定义呢？ 首先要考虑到的就是这个负载均衡器肯定要持有从 Proxy 服务端返回的主题路由信息，这个好办，我直接在负载均衡器中定义一个集合，用这个集合来存储所有路由信息就好了 。看到这里有些朋友可能会提出问题，复杂均衡器难道要持有所有主题的路由信息吗？如果持有所有主题的路由信息，那最好还是定义一个 Map，这样 key 代表主题信息，value 就是主题对应的全部路由信息。没错，我们确实可以这么做， 但我们也可以为每一个主题都定义一个负载均衡器，这样一来，负载均衡器就只存储对应主题的路由信息即可，RocketMq 源码中就是这么做的 。我们就把这个负载均衡器定义为 PublishingLoadBalancer 类吧，就目前的情况来说，这个 PublishingLoadBalancer 类可以暂时定义成下面这样，请看下面代码块。
