  
简单分析 Proxy 模块的作用  
  
当大家开始阅读这篇文章的时候，想必都已经看完我提供的第二版本代码了，应该也都清楚了 RocketMq 的 Namesrv 是如何构建的了。当然，目前我们构建的 Namesrv 仅仅算是初具规模，真正的核心功能还没有实现， 所谓核心功能就是 Namesrv 管理 RocketMq 中主题路由信息的功能 。如果我们真的把这个功能实现了，那么按照我们使用 RocketMq 框架的经验来看，我们肯定会按照以下流程执行各个操作，然后让 RocketMq 为我们的工作提供帮助：  
1 首先要启动 Namesrv、Broker 模块，Broker 就是用来存储生产者生产的消息。  
2 启动之后的 Broker 要将自己的信息注册到 Namesrv 上，这个时候 Broker 要注册的信息还很简单，无非就是 IP 地址端口号、Broker 所在集群名称和自己在集群中的名称这些信息。  
3 然后 Mq 的控制台、或者 Mq 内置的命令行模块就可以访问 Namesrv，从 Namesrv 中获得已经启动的 Broker 的信息，也就是获得对应的 Broker 的网络地址，接着 Mq 的控制台或者 Mq 内置的命令行模块就可以根据 Broker 的地址向对应的 Broker 发送创建 topic 主题的请求。  
4 Broker 模块在接收到创建 topic 主题的请求后，就会在自己内部把对应的主题创建出来，主题创建完毕之后，Broker 内部会保存一份，然后会再次向 Namesrv 注册自己的信息，与其说是注册，不如说是更新，这个时候 Broker 就会把自己内部的主题信息一起注册到 Namesrv 中。  
5 Namesrv 接收到 Broker 更新过来的主题信息后，会把主题信息保存在自己内部的主题路由信息管理器中。  
6 这个时候如果启动了生产者和消费者，那么生产者和消费者就可以直接访问 Namesrv，然后根据自己要订阅的 topic 的信息，从 Namesrv 中得到哪个 Broker 上存在对应的 topic 主题，当 Namesrv 把对应的 Broker 信息返回给生产者和消费者后，这个时候我们就可以说，生产者和消费者从 Namesrv 中获得了主题的路由信息。  
7 接下来生产者和消费者就可以根据自己得到的主题路由信息，访问对应的 Broker 了，生产者可以向 Broker 发送消息，消费者可以从 Broker 消费消息。一个完整的 RocketMq 的架构就搭建完毕了 。  
  
我相信如果大家在工作中都用过 RocketMq，那对上面的这些流程都会很熟悉，并且在读完上面的内容之后，我相信大家脑海里也会有一个清晰的 RocketMq 各个模块协同工作的流程图，我就不再文章中为大家展示了。总之， 在 RocketMq 中，Namesrv 模块掌管着最关键的信息，其他各个模块要不然就是把自己的信息注册到 Namesrv 模块，要不然就是从 Namesrv 模块获得信息，当然，Namesrv 的作用也仅限于此了，就是一个信息的中转站和管理器，其他什么职责也不用承担 。生产消息的是生产者，消费消息的是消费者，存储消息的是 Broker，生产者和消费者主要还是和 Broker 模块打交道，生产者和消费者从 Namesrv 获得对应的 Broker 信息，这样分析下来，我们也能清楚地知道， 在 RocketMq 中，真正发挥重要作用的模块有四个，那就是 Namesrv、Broker、生产者和消费者 ，并且在这四个模块中，Borker、生产者、消费者在处理信息的时候都要和 Namesrv 打交道，而在处理消息的过程中，生产者和消费者就要和 Broker 打交道了。这些都已经非常明显了，我就不再赘述了。  
  
当然，我在上面对 RocketMq 的模块解释了那么多，肯定有朋友觉得我很罗嗦，明明是很简单的内容，没必要浪费那么多文字。但我想对大家说的是，现在大家肯定已经清楚了 RocketMq 框架各个模块的作用，要想继续完善我们自己定义的 Mq 框架，那只需要按照之前分析的流程，按照 RocketMq 框架源码的模块为我们自己的 Mq 框架继续实现其他模块即可。 我们已经把自己的 Namesrv 模块的通信功能实现完毕了，接下来只需要接着实现 Namesrv 模块的主题信息管理功能，让 Broker 能注册信息，生产者、消费者都能从自己这里获得主题路由信息，这个时候我们就可以说我们自己定义的 Namesrv 模块已经实现完毕了 。但是，请大家先想一想，到目前为止，我们连 Broker 这个模块都还没定义呢，也就是说都还没有相关的 Broker 信息注册到 Namesrv 中呢，又怎么能知道 Namesrv 应该保存哪些信息呢？当然，有 RocketMq 源码在这里供我们参考，我们肯定都知道 Broker 应该向 Namesrv 注册什么信息，但回到我们自己定义的 Mq 框架中，我认为我们至少应该先实现一个简单的 Broker 模块，并且实现了 Broker 向 Namesrv 注册简单信息的功能，再回过头实现 Namesrv 管理信息的功能。所以，这样分析下来，接下来我们需要暂时转移一下目标，先把完善 Namesrv 的任务放一放，开始实现一个简单的 Broker 模块似乎成了我们的首要任务。  
  
如果我们仿照 RocketMq 5.0 之前的版本代码来实现我们自己的 Mq 框架，那我们接下来确实就应该先实现一个简单的 Broker 模块，但我们目前仿照的是 5.0 之后版本的 RocketMq 代码，在 5.0 之后的版本中，RocketMq 又增加了一个非常重要的模块，那就是 Proxy 模块，翻译过来就是代理模块。很多没用过 5.0 之后的 RocketMq 框架的朋友可能根本就没听过这个模块，更别提了解这个模块的作用了。所以接下来请允许我再次岔开一下话题，让我们先把注意力从即将实现的 Broker 模块移动到 RocketMq 5.0 新引入的 Proxy 模块上。  
  
请大家思考一下，如果我们以 5.0 版本之前的 RocketMq 源码为模板，在实现自己的 Mq 框架的过程中，我们肯定也会为自己的 Mq 框架定义 Namesrv、Broker、生产者客户端，消费者客户端，这些大家都没有异议吧？好了，当我们为自己的 Mq 框架实现了这些模块，启动程序之后，生产者和消费者要想顺利工作，那它们的客户端肯定要先访问 Namesrv，和 Namesrv 建立连接，从 Namesrv 获得自己订阅的主题的路由信息，也就得到了对应的 Broker 节点的信息，在这之后，生产者客户端和 Broker 节点建立连接，然后把消息发送给 Broker 节点，消费者也要和 Broker 节点建立连接，从 Broker 节点获取消息。这个过程大家肯定都很清楚了，但我想说的是，这个过程并不是一次性的，而是持久的，确切地说， 生产者和消费者的客户端和 Namesrv 以及 Broker 建立的连接会一直存在，只要程序还在运行，那我们就应该保证生产者和消费者的客户端和 Namesrv 以及 Broker 建立的连接不能中断 。原因很简单，随着生产规模的扩大，到某一刻我们总会为程序构建集群，Namesrv、Broker 这些模块都可能以集群的方式部署，既然是集群就意味着它们对外提供服务时存在动态变化，可能集群中的某个节点忽然宕机了，或者集群中忽然添加了一个新的节点。这些情况都有可能发生。  
  
既然集群中节点的数量可能发生动态变化，也就意味着对外提供的网络地址会发生动态变化，这就要求在使用 RocketMq 框架的过程中，生产者消费者一旦启动，和 Namesrv 以及对应的 Broker 建立连接之后，就要在内部维护这些连接，比如说使用 Map 成员变量存放已经建立连接的 Namesrv 和 Broker 的地址，并且在后台启动定时任务，定期对它们进行心跳检测，判断连接是否已断开。生产者总不能向已宕机的 Broker 节点发送消息吧？如果大家想阅读具体的代码，可以看看 RocketMq 5.0 之前的源码，直接阅读源码的 MQClientInstance 类的内容即可，更具体的内容我就不在文章中展开了。 由此可见，在旧版本的 RocketMq 源码中，为了程序能顺利运行下去，不管是生产者还是消费者，它们的客户端都会在内部维护大量的网络连接信息，集群中有任何一个节点发生变更了，都要立刻通知生产者和消费者的客户端更新内部信息 。  
  
当然，除了这些网络连接的信息，生产者和消费者客户端内部还会维护一些更重要的信息，比如说它们各自订阅的主题路由信息，这些信息非常重要，只有知道了这些信息，生产者才知道自己应该把消息发送给哪个 Broker，消费者知道自己应该去哪个 Broker 拉取消息。更重要的是，这些信息对客户端的负载均衡非常重要，如果生产者订阅的某个主题下有 4 个 Broker 可以发送消息，那当生产者客户端采用轮询方式发送消息时，就会按照顺序把消息平均分散到这 4 个 Broker 节点上。 由此可以看出，在旧版本 RocketMq 源码中，生产者客户端还需要在内部执行复杂均衡操作，如果内部存储的 Broker 节点信息发生变更了，那么负载均衡的对象也需要重新刷新 。  
  
分析了这些情况之后，大家应该也能意识到， 在旧版本的 RocketMq 的源码中，客户端和 Broker、Namesrv 在某种程度上来说是存在耦合的 。说得更确切一些，Broker、Namesrv 这些服务器对客户端来说都不是透明的，也许我这么说会让很多朋友感到奇怪，客户端肯定要知道 Broker、Namesrv 的信息啊，不然怎么访问它们呢？这些服务器本来就不该对客户端透明，但我想说的是，我希望生产者和消费者客户端尽可能简单点： 客户端不必再负责什么 RocketMq 框架内部的业务逻辑，客户端也不必再维护自己的消费进度信息，客户端只负责发送消息和获取消息，其他什么都不负责，也都不维护 。这样一来，更加简单的客户端在生产中可能会工作得更加稳定，除此之外，还能适应更多情况。  
  
我知道大家对这个所谓的"适应更多情况不"太理解，接下来就让我简单解释一下。当客户端负责很多业务逻辑的时候，它的内容显然就会丰富一些，代码量也许会多一些。而一个流行的框架往往会在多种编程语言开发的程序中发挥作用，也就是说 Java 开发的 RocketMq 框架的流行可能并不会局限在 Java 领域，也许 Python 也想使用 RocketMq 消息队列，那这个时候我们就可以为 Python 专门开发一个 RocketMq 的客户端，生产者和消费者客户端都要开发，然后再仿照 Broker 自己的 Remoting 协议，为 Python 客户端开发相应的通讯协议，之后就可以启动 Broker 节点，Python 客户端就可以和 Java 开发的 Broker 节点通信了。这个流程应该很清晰吧，而在这个流程中，真正耗费精力的显然就是开发 Python 版本的生产者、消费者客户端，Java 开发的生产者、消费者客户端中包含什么功能，Python 版本的客户端都要有。如果客户端的内容非常多，那么在为不同语言做适配的时候，比如 Python、Golang、Rust、C++、C#等等语言，这个时候就需要把相同逻辑的代码都重写一遍，显然这是非常麻烦的事情，如果遇到 RocketMq 通信协议升级，那么其他语言版本的客户端也要进行升级。这对 RocketMq 框架代码本身的维护和迭代来说，并不是一件好事。  
  
那该解决这种情况呢？也就是回到我刚才说的话那句，该怎么让 RocketMq 客户端适用更多情况呢？其实方法很简单，那就是尽量减少 RocketMq 客户端的功能，比如就像我刚才说的： 客户端不必再负责什么 RocketMq 框架内部的业务逻辑，客户端也不必再维护自己的消费进度信息，客户端只负责发送消息和获取消息，其他什么都不负责，也都不维护，RocketMq 客户端不再和 Namesrv 建立连接，也不再访问 Broker 。客户端内容越少，那么实现其他语言的 RocketMq 客户端就越省事，这个也可以理解吧？但这时候就有新的问题，如果 RocketMq 客户端不再和 Namesrv 建立连接，不再访问 Broker，那这个客户端还怎么发挥作用呢？它怎么知道消息要发送给谁，又从哪里获取消息呢？  
  
这个时候就轮到 Proxy 登场了，也就是 5.0 版本新引入的代理模块。这个 Proxy 代理模块启动之后会访问 Namesrv 模块，和 Namesrv 模块建立连接，并且会从 Namesrv 获取各个客户端要订阅的主题的路由信息，然后缓存在自己内部。RocketMq 生产者和消费者的客户端只和 Proxy 模块建立连接，也就是说 RocketMq 的客户端以后只访问 Proxy 模块，需要订阅某个主题下的路由信息了，那就给 Proxy 模块发送请求，让 Proxy 把路由信息返回给客户端；生产者需要向 Broker 发送消息了，那就把消息发送给 Proxy 模块，Proxy 会根据内部缓存的主题路由信息执行负载均衡，然后把消息发送给对应的 Broker 节点；消费者需要从 Broker 获取消息消费了，那就给 Proxy 模块发送对应的请求，Proxy 会从 Broker 获取消息，然后把消息返回给消费者客户端。 总而言之，之前客户端和 Namesrv、Broker 执行的交互操作，现在都交给 Proxy 来执行，客户端能通过 Proxy 得到它想要的一切，Proxy 作为客户端的代理和 Namesrv、Broker 进行通信 。这就是 5.0 版本引入的 Proxy 模块的作用之一。  
  
那就像这样真的引入了 Proxy 模块之后有什么具体的好处呢？好处就是客户端更简单了，并且和 Namesrv、Broker 信息解耦了，Broker 节点发生什么变更也不会影响到客户端，反正客户端只要能访问 Proxy 就行。除此之外，在位其他语言实现对应版本的 RocketMq 客户端时也更方便了，当然有一点我必须要补充， 那就是 RocketMq 5.0 之后版本客户端和 Proxy 使用 Grpc 框架建立网络连接和通信，这样一来有一个更大的好处，那就是不管要为什么语言实现对应的客户端，只要使用 protobuf 把网络传输的请求响应格式和处理请求的方法格式定义完毕，你就不必再为什么通信协议操心了，因为 Grpc 框架会帮你搞定底层通信的一切 。也就是说在为不同语言实现 RocketMq 客户端时，通信协议也都不用管了，那要实现的内容就只有客户端和 Proxy 模块的交互逻辑了，而这一部分内容非常少，这么操作下来，确实对 RocketMq 适配其他语言带来很大的好处。现在大家应该清楚 RocketMq 在 5.0 为什么要引入 Proxy 模块了吧？当然，我现在解释的仅仅是目前针对客户端实现带来的好处，至于存算分离这些内容，等进行到课程的第二部分内容再讲解吧。  
  
好了，现在我们也清楚了，在为 RocketMq 引入了 Proxy 模块之后，客户端就不再和 Namesrv、Broker 服务端进行通信了，而是使用 Grpc 的方式和 Proxy 模块进行通信，那么 Proxy 模块怎么和 Namesrv、Broker 节点通信呢？其实这也没什么好说的，答案非常简单， Proxy 仍然使用 Netty 构建的客户端和 Netty 构建的 Namesrv、Broker 服务端进行通信 ，也就是说在 RocketMq 框架内部，其各个模块仍然是使用 Remoting 协议进行通信，也就是说，使用的仍然是 Netty 构建的客户端和服务端进行通信；而生产者和消费者的客户端和 Proxy 模块则使用 Grpc 框架进行通信。当然，Proxy 模块也为旧版本的客户端做了适配，如果你使用了 5.0 之后的 RocketMq 框架，但是不想使用新生产者和消费者客户端工作，仍然想使用旧版本的客户端工作，那么在使用旧版本客户端的时候，就可以直接使用 Netty 构建的旧版本客户端和 Proxy 模块进行通信，这个时候客户端和 Proxy 模块使用的就是 Remoting 通信协议。当然，这也就意味着在 Proxy 模块内部有两个服务端，一个是 Grpc 框架构建的服务端，一个是 Netty 构建的服务端，这两个服务端使用的通信协议不同。这些内容我现在就不具体展开了，看了我提供的第三和第四版本代码之后，大家就全都清楚了。  
  
好了，写到这里我已经意识到我们已经离题很远了，别忘了，我们本来是要实现一个简单的 Broker 模块的的，但紧接着我们对 Proxy 模块展开讲解了很多内容。没错，我这么做不是因为别的，我就是要先实现一个简单的 Proxy 模块，然后再实现一个简单的 Broker 模块。至于我为什么要先实现一个简单的 Proxy 模块，原因也很简单， 因为 Proxy 有两种部署模式，一种是集群模式，另一种是 Local 本地模式，也就是说 Proxy 模块既可以部署成集群，也可以单机部署 。 当使用集群模式部署 Proxy 的时候，Proxy 和 Broker 节点需要部署在不同的服务器上，但使用单机模式部署 Proxy 的时候，Proxy 和 Broker 可以部署在同一台服务器上，并且会把 Broker 内嵌在 Proxy 中，在 Proxy 启动的过程中，会把 Broker 节点一起启动了 。现在我这么说大家肯定还很模糊，不清楚究竟是怎么回事，不用着急，大家可以先记住这两种模式，接下来我都会为大家实现。我提供给大家的代码就是用 Local 模式部署的 Proxy，既然是单机模式，Broker 节点会随着 Proxy 的启动而启动，那不如就先把 Proxy 实现了，然后再实现 Broker 模块，所以接下来就让我先为大家构建一个简单的 Proxy 模块吧。  
  
构建 Proxy 模块的 Netty 服务端  
  
好了，现在要构建一个简单的 Proxy 模块了，那么应该怎么构建呢？或者说从哪些方面开始构建呢？我首先能想到的就是 Proxy 模块要和生产者、消费者客户端进行通信，所以 Proxy 肯定要有服务端，以便接收客户端发送过来的消息；与此同时，Proxy 还要和 Namesrv、Broker 进行通信，所以 Proxy 模块也要有客户端，以便它把请求消息发送给 Namesrv、Broker。而通过我上一小节的分析，大家也都知道了，Proxy 内部实际上有两个服务端，一个是 Netty 构建的服务端，一个是 Grpc 构建的服务端，而我们之前已经使用 Netty 为 Namesrv 构建了服务端，趁着知识还没忘记，就继续运用那些知识为 Proxy 先构建 Netty 服务端吧。  
  
如果大家对 Namesrv 模块的启动流程还有印象，那大家肯定还记得我们在 Namesrv 模块中定义了一个 NamesrvStartup 启动器，只要调用该启动器的 start 方法，整个 Namesrv 模块就会成功启动了，当然，在启动的过程中肯定会执行解析命令行参数、初始化配置信息、初始化各个组件的操作，这些流程大家应该很清楚了，可以说是最常规的流程了。那现在我们要实现一个简单的 Proxy 模块，并且也要启动这个模块了，按照常规流程， 我们也可以为 Proxy 模块定义一个 ProxyStartup 启动器，然后调用该启动器的 start 方法启动 Proxy 模块 。
