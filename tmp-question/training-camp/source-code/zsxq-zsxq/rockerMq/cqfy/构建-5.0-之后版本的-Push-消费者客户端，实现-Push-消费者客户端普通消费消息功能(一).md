如果大家理解了上面的内容，很快就能意识到我们之前实现的 Pop 消费者客户端存在的问题，那就是这个消费者客户端在从 Broker 节点获取消息时，执行了 receive() 方法之后只能获取一批消息，如果还想获取更多消息，那看来执行再次执行 receive() 方法。也就是说， 似乎得在一个循环中不断执行 receive() 方法，Pop 消费者客户端才能不断从 Broker 节点获取消息消费 。而我们实现的 Pop 消费者客户端中显然并没有这样的循环操作，这也就意味着，如果用户在生产中用到了我们之前实现的 Pop 消费者客户端，还得自己手动定义循环，在循环中执行 receive() 方法，以便获得更多消息消费。对用户来说，这显然是个麻烦，因为用户要实现的操作不仅仅是一个循环，一旦定义了循环，就要考虑什么时候终止循环，考虑什么时候让线程休息，有时候这些操作比循环中要执行的操作更为重要，因为你不可能在程序中设置一个无法停止的死循环。那把这些额外的操作交给用户来实现，显然会对我们开发的消息队列框架的流行程度造成影响，甚至还会影响你这个程序员的名声。既然这样，那这些额外的工作索性就让我们包揽了吧。没错，看到这里，大家肯定意识到了， 在消息队列框架中，Pop 消费者模式应该只是一个底座，它会在核心功能中发挥作用，但肯定还有上层功能对它进行了包装 。换句话说， 我们之前实现的 Pop 消费者模式并不能当成真正的消费者客户端来使用，真正的消费者客户端虽然还没有被我们实现，但真正的消费者客户端内部一定用到了 Pop 消费模式从 Broker 节点获取消息 。我对这一点十分肯定。  
  
分析 Push 消费者客户端的重构思路  
  
也许大家还不明白我刚才的话是什么意思，那接下来就让我开门见山地跟大家解释一下， 我要在 Pop 消费模式上实现一个新的、真正的消费者客户端 。根据我们刚才的分析，一个消费者客户端要想不断从 Broker 节点获取消息，那么就得不断执行 receive() 方法，这也就意味着真正的消费者客户端要循环执行 receive() 方法，当然，消费消息的业务逻辑肯定还是用户自己定义。如果是这样的话，那对我们要实现的真正的消费者客户端来说，似乎只要在 Pop 消费模式上增加一个循环操作就可以开始工作了，这种设计思路应该没问题，不过这么做似乎有点粗暴。因为我们都很清楚，消费者客户端不可能一直从 Broker 节点获取消息，至少在两种情况中，消费者客户端不必执行 receive() 方法， 第一种就是消费者客户端能力不够，不足以消费更多消息了，之前获取的消息都没消费完，根本无力再消费更多的消息；第二种情况就是 Broker 节点已经没有消息可以让消费者客户端消费了 。这两点大家可以理解吧？考虑到这两种情况， 我认为把循环执行 receive() 方法的操作修正为定期执行 receive() 方法更加稳妥，也更可控。也就是说，我们可以给消费者客户端定义一个定时任务，然后在定时任务中定期执行 receive() 方法，而一旦判断消费者客户端无法消费更多的消息了，那么就暂缓到 Broker 节点获取新的消息 。这个逻辑也很容易理解吧？  
  
好了，如果大家理解了以上逻辑，那接下来的内容就很简单了，我们也不用实现什么复杂的功能，执行什么复杂的操作，只需要对一些旧功能修修改改即可，比如说，我们完全可以对旧的消费者客户端进行重构，正如当前小节标题展示的那样，我们可以对 Push 模式的消费者客户端进行重构。如果大家使用过 5.0 版本之前的 RocketMq 框架， 那么大家肯定就知道在使用 Push 模式的消费者客户端从 Broker 节点消费消息时，会使用独占策略消费消息，也就是同一个消费组中，每一个 Push 消费者客户端会被分配一个目标队列，当然，也可能会根据负载均衡机制分配多个队列，但各个消费者只会消费自己队列中的消息，客户端数量增加到一定程度之后对程序性能并没有什么帮助了，这种消费模式便会造成一些性能上的问题，因此我们引入了 Pop 消费模式。在 Pop 消费模式下，同一个消费组中的所有消费者客户端并不会独占消费队列，而是会从同一主题下的所有队列中获取消息消费，这种消费模式在某种程度上确实提高了消息被消费的效率 。这些内容大家应该还有印象吧？  
  
如果大家还记得以上内容，那接下来我们就可以这么做，我们可以给 Push 消费者客户端定义一个定时任务，在定时任务中定期执行 receive() 方法，从 Broker 节点获取消息消费，核心逻辑就是这么简单。那接下来我们就开始正式实现这个新的 Push 消费者客户端吧。

那实现了以上操作之后呢？之后我们要做什么呢？别忘了，PushConsumerImpl 类的 scanAssignments() 方法还未实现呢，该方法会在定时任务中被定期执行。想到这里，那程序接下来要执行的操作就很简单了，那就是在定时任务中定期从这些 Broker 主节点中获取消息，也就是从各个消费队列中获取可消费的消息，只要对目标节点执行 receive() 方法即可，这个可以理解吧？那这是不是就意味着要在 scanAssignments() 方法中对每一个消费队列的目标节点执行 receive() 方法呢？没错，确实应该执行这个操作，但是，在执行这些操作之前，还有一个非常重要的操作必须执行， 那就是要定期执行 queryAssignment() 方法，也就是说，要在 scanAssignments() 方法中执行 queryAssignment() 方法 ，大家可能对此有些疑惑，不明白为什么把 queryAssignment() 方法放在定时任务中定期执行，那就让我来给大家解释一下。  
  
其实原因很简单，既然 Push 消费者客户端要从获取到的所有消费队列中消费消息，这就意味着消费队列的信息都消费者客户端来说肯定是至关重要的。而我们都知道，在程序运行期间，是可以动态添加新的主节点，也就意味着会有新的 Broker 主节点信息注册到 Namesrv 中。既然是主节点，那 Push 消费者客户端显然也可以从该节点中获取消息，这时候答案就不言而喻了吧： 因为在程序运行过程中，Broker 主节点的信息可能会发生动态变化，这也就意味着 Push 消费者客户端从 Proxy 节点获取的可消费队列信息会动态变化，因此 Push 消费者客户端需要定期到 Proxy 节点获取最新的消费队列信息 。获取了这些信息之后，显然还要把这些信息缓存在本地，当然， 每次从 Proxy 节点获取了最新的消费队列信息后，还要和本地缓存的队列信息做对比，及时更新本地缓存的队列信息 。这样分析下来，这个 PushConsumerImpl 类就可以重构成下面这样，请看下面代码块。

引入 ProcessQueueImpl 本地队列对象  
  
现在，请大家先抛开同步队列信息到本地的操作，请大家思考一下，当 Push 消费者客户端从各个 Broker 主节点中获取了可消费的消息之后，会执行什么操作呢？这没得说，肯定是消费消息，那在消费消息之前呢？也许大家会有各种各样的想法，我对此的想法非常简单， 消费者客户端在开始消费消息之前，显然是要把获取到的消息缓存到本地。因为消费者客户端消费消息也需要时间呀，不可能一瞬间就把所有消息都消费完，那肯定是把获取到的消息缓存到本地，然后一条一条地消费即可 。这个逻辑大家可以理解吧？  
  
考虑到消费者客户端要把从 Broker 节点获取的所有消息都缓存到本地，这个时候就不得不关注消费者客户端的内存压力了，显然，消费者客户端不能无限缓存消息。这也就意味着我们应该给消费者客户端定义一些缓存消息的阈值，比如说消费者客户端最多只能缓存 1024 条消息，缓存消息数量达到阈值之后，消费者客户端就要暂缓到 Broker 节点获取消息，也就是暂缓执行 receive() 方法；或者我们还可以给 Push 消费者客户端设置可以缓存的消息字节总量，可以缓存的消息字节总量就算是 64 \* 1024 \* 1024，那消费者客户端缓存的消息字节总量超过了这个值，客户端也就要暂缓执行 receive() 方法。这些逻辑理解起来也很简单吧？  
  
当然，以上都是小意思，给程序定义各种各样的配置信息是最简单的操作了。那接下来让我思考一个稍微有一些深度的问题，我们已经明确了消费者客户端会把获得的消息缓存在本地，那么该怎以什么方式缓存呢？这个问题可能会让大家有些困惑，那我就把话说得再明白一些： 假如 Push 会从多个 Broker 主节点中获取消息，也就是从多个消费队列中获取消息，那么获取到的这些消息该怎么缓存呢？是把各个队列的消息都缓存到一起呢？还是各个队列缓存各自的消息呢 ？你当然可以把获取到的所有消息都缓存到一起，甚至可以专门定义为消费者客户端定义一个消息管理器，在消息管理器中判断消费者客户端的状态，消息数量是否达到阈值，以此决定是否继续获取新的消息，当然，消费者客户端自然也可以从消息管理器中获取每一条消息，依次消费。这么做完全可以。我并不想把编程思维局限在 RocketMq 这个消息队列框架中，实际上在我自己开发游戏的时候，我也倾向于为很多功能构建各种管理器，比如我会创建场景切换管理器，还会创建人物生成管理器，还有背包管理器以及一些全局管理器。总之，我会想尽各种方法让管理器管理某一个模块的功能，各个管理器持有彼此，协同工作。我认为这是一种很巧妙的编码方式，所以我们当然也可以在 Push 消费者客户端中定义一个消费管理器。  
  
但是，我们的程序完全是对源码的复刻，所以就不得不按照源码的方式来缓存消息。而源码中采取的方式和我们刚才分析的并不一样， 在源码中你会看到每一个消费队列缓存了各自从 Broker 主节点获取到的消息 。我能想到这句话同样会让大家感到困惑，那接下来就让我详细解释一下：在源码中， 当 Push 消费者客户端从 Proxy 节点获得多个消费队列信息之后，就会为每一个消费队列创建对应的本地队列 ，比如说 Push 消费者客户端从 Proxy 节点获取了 2 个消费队列信息，也就是两个 Broker 主节点信息，那么消费者客户端就会为这两个消费队列分别创建对应的本地队列，也就是 ProcessQueueImpl 对象，而每个 Broker 主节点的信息也都会封装在各自的本地队列中。这么做有一个绝佳的好处， 那就是一旦消费者客户端为每一个从 Proxy 节点获取的消费队列创建了对应的本地队列，那么从各个 Broker 主节点获取消息的操作就可以交给每一个本地队列来执行了，而获取到的消息也就可以直接缓存在各自的本地队列中，当然，客户端消费消息的时候就从各个本地队列中消费即可 。这样一来，就成了各个本地队列负责各自的工作，如果是顺序消息的话，那么接收到的消息仍然会按照顺序缓存在本地队列中，也不必担心消费者客户端消费出现问题。这些逻辑理解起来并不困难吧。如果大家理解了这些消息，那接下来我们就可以先把这个 ProcessQueueImpl 类定义出来，然后再实现之前没有实现的 syncProcessQueue() 方法。
