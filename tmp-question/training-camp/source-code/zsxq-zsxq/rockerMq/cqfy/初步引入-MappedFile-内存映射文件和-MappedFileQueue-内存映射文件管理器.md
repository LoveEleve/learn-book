剖析生产者消息的存储方式  
  
从很久之前，我们一起实现 Proxy 服务端接收生产者客户端生产的消息的功能时，我就跟大家提出过一种设想：那就是生产者客户端生产的消息，最终可能会被存放到对应的目标队列中。大家可能还记得这个过程，那就是当生产者客户端把一条生产消息发送给 Proxy 服务端后，Proxy 服务端会从消息中得到消息所属的主题信息，然后从内部缓存中得到该主题的所有可路由信息(如果是本地模式部署 Proxy 节点，那就会直接得到 Broker 节点，从 Broker 节点中得到主题的配置信息，然后得到可路由信息)，得到主题路由信息之后，就会对这些路由信息进行筛选，只保留 Broker 主从组中主节点的信息，然后为筛选之后的路由信息节点创建出对应权限的读写队列，也就是消息队列，每一个消息队列都包含所属 Broker 节点的网络地址。这一切操作执行完毕之后，Proxy 就会执行负载均衡操作，从该主题下的所有可路由写队列，也就是消息队列中选择一个目标队列，明确目标队列的队列 Id，因为队列中包含所属 Broker 节点的网络信息，所以 Proxy 服务端就可以直接把生产消息发送给目标队列所属的 Broker 节点。这些流程大家应该还有印象吧？毕竟都不是什么复杂的操作，我记得很清楚，就是在我为 Proxy 服务端实现了这些功能，并且把生产者客户端生产的消息从 Proxy 节点发送给目标队列所属的 Broker 节点之后，我跟大家简单解释了一句： 也许这些消息被发送给 Broker 节点之后，会存储到 Broker 节点内部的目标写队列中 。我当时就是这么说的。  
  
因为一直以来，从构建 Broker 模块，实现 Broker 节点创建主题信息功能时，我们脑海里就存在一种意识： 那就是 Broker 节点内部创建的每一个主题都有自己的配置信息，配置信息中定义了该主题的读写权限以及读写队列数量，而从表面意思上理解，写队列显然就是写入消息数据的队列，读队列显然就是读取消息数据的队列。因此，我们就可以大胆而又合理地认为，生产者客户端生产的消息，最终会存放到所属主题下的写队列中 。巧合得是，当 Proxy 服务端要把生产消息转发给 Broker 节点时，恰好为每一个可以路由信息的主 Broker 节点，为其内部的消息所属主题创建了读写队列，然后又使用负载均衡策略选择了具体的目标队列，队列 Id 也明确了，然后把消息发送给目标 Broker 节点，所以我们又进一步推测，发送给目标 Broker 节点的消息，最终会把消息存储在 Broker 节点内部对应的写队列中。这是我们之前分析的逻辑，看到这里我不知道大家有没有一个疑问，你看，我们已经在文章中多次提到写队列，可见写队列对于存储数据来说十分重要，那写队列究竟是什么呢？写队列究竟该怎么存储消息呢？  
  
也许大家会紧接着想到，我们之前不是已经实现写队列了吗？不就是消息队列 MessageQueue 类吗？就是下面代码块展示的内容，请看下面代码块。  
阅读了上面代码块之后的内容，大家可能会觉得，这个 MessageQueue 对象不是在 Proxy 节点中创建的吗？怎么能为 Broker 节点存储生产者的消息呢？接下来还是再让我罗嗦几句吧，按照现阶段编写的代码来推想，Proxy 节点可以从 Namesrv 中获取指定主题的路由信息，然后为每一个可路由的 Broker 节点信息创建消息队列，但是在真正的 Broker 节点中，也可以根据主题配置信息把对应的读写队列，也就是消息队列创建出来呀，对吧？Proxy 节点缓存的可路由的 Broker 节点的主题配置信息和真正的 Broker 节点的主题配置信息是一致的，所以这两者创建出来的消息队列也肯定都是一致的，因此目标 Broker 节点接收到消息后才能存储在与在 Proxy 服务端选中的目标队列 Id 相同的消息队列中。当然，这只是我们目前的推测，我们认为 MessageQueue 消息队列可以存储生产者生产的消息数据，所以才做出了这种猜想，但这种推测不一定是真的，因为在上面代码块中有一个最直观的，不容忽视的缺陷， 那就是在 MessageQueue 类中并没有真正用来存储消息数据的成员变量，常用的存储数据的容器也就那几种，无非就是集合、队列、数组等等数据结构，但在 MessageQueue 类中并没有定义这些数据结构，这似乎意味着 MessageQueue 类的对象根本就不能作为存储生产消息的容器 ，那这又是怎么回事呢？  
  
也许有朋友会下意识地思考，反正现在就差最后一步了，只要 MessageQueue 类的对象能够真正存储消息数据就行，那索性就重构一下 MessageQueue 类，在该类中定义一个很常规的数据结构成员变量用来存储消息不就行了？如果你决定开发自己的消息队列框架，那确实想怎么设计就怎么设计，但很遗憾，目前我们是在仿照 RocketMq 框架源码复刻一个消息队列框架，那么一切设计都要遵循 RocketMq 框架的源码。而我可以很负责任地告诉大家，在 RocketMq 框架源码中，MessageQueue 类的内容就是上面代码块展示的那样，再没有其余内容，也不需要重构了。所以分析到这里，我相信大家也都意识到了， 看来当 Broker 节点接收到 Proxy 发送过来的生产消息时，并不是把消息存储在消息队列中，我们以前的推想是错的 ，那意识到了这一点，我们肯定会更加困惑，Broker 节点究竟是怎么存储消息的呢？  
  
好了，啰里啰唆了一大堆，接下来终于该步入正题了。首相我想请大家思考一下，消息队列的本质是什么？或者说消息队列的核心功能是什么？我记得这个问题我们在本套课程的第一章就讨论过，也许大家对这个问题已经感到厌烦了，但现在我确实想抽时间再和大家讨论讨论，用最简洁的话来解释： 消息队列就是存储消息的队列，队列中存储的消息可以被随时取出来 。用稍微书面一点的话来解释： 消息队列其实就是一个生产者消费者模型，队列用来存储消息，生产者把生产的消息存放到队列中，消费者可以从队列中获取消息进行消费 。这个解释也很简单吧，总结下来就一句话： 一个能存能取的数据结构就可以被当成消费队列 。往小了说，集合、队列、数组都可以被当成消息队列，往大了说，Disiruptor 框架，Redis 数据库也可以被当成消息队列，只要是可以存储数据，又能够被读取数据的容器都可以看成消息队列。当然，如果考虑到消息队列的附加功能，那么消息队列框架就不会这么简单了。  
  
比如说你要为消息队列框架定义通信模块，为消息队列定义客户端和服务端，以便在生产环境中可以让生产者客户端生产消息，消费者客户端消费消息；而不可能所有的消费者都会消费同一种消息，因此你会引入主题这个机制，方便不同的消费者消费不同主题下的消息；程序开发是一个既严谨又灵活的工作，严谨体现在编写代码的过程中，而灵活则体现在框架的使用方式上，为了让用户更方便、更灵活地使用你开发的消息队列框架，于是你又要给消息队列框架添加顺序消息功能、延迟消息功能、事务消息等等功能；当然，在实现了诸多功能之后，你并没有忘记要回到消息队列最核心的功能，那就是消息的存储与消费功能。我不知道当大家在思考这个问题的时候会首先想到什么， 我首先想到的就是数据的安全问题，所谓数据安全就是数据的存储与备份 。按照我们之前的分析思路， 如果使用集合、队列、数组、或者是 Disiruptor 框架，Redis 充当消息队列，在这种情况下，生产者发送给消息队列的数据肯定是缓存在内存中，而缓存在内存中的数据显然容易丢失，为了防止出现这种情况，肯定需要对数据执行持久化操作。当然，为了进一步保证数据安全，我们还可以构建消息队列集群，对这些数据做备份 。当这些功能都实现了之后，一个消息队列框架才算初步成型了。  
  
很好，这些内容分析完毕之后，接下来让我们回到刚才展示的 MessageQueue 类，现在我们已经知道了 MessageQueue 类的对象并不能真的存储消息，它对于 Broker 节点存储生产消息应该派不上什么用场，而为了保证消息不会丢失，我们已经决定要对消息执行持久化操作， 也就是说要对 Broker 节点接收到的每一条生产消息都执行持久化操作，把消息持久化到本地文件中 。这样一来， 假如生产者一直生产消息，那么消息就都可以持久化到 Broker 节点的本地，当某个时间段启动了消费者客户端，消费者客户端到 Broker 节点消费消息时，就可以从 Broker 节点本地把消息加载到内存中，然后通过网络传输，把消息返回给消费者客户端消费 。这个逻辑大家应该可以理解吧？  
  
如果大家理解了以上逻辑，那么再回头讨论 Broker 节点如何存储生产者客户端生产的消息时，答案就已经非常明朗了， 那就是当 Broker 节点接收到生产消息时，就可以先把消息写入到缓存中，然后再寻找合适的时机把消息持久化到本地硬盘中 。这不就是非常常规的操作吗？大家可以回想一下在 SofaJraft 这个框架，确切地说是 Jraft 集群主节点接收到数据时是怎么存储的呢？肯定也是先写入缓存，然后再持久化到本地，对吧？在市面上流行的框架中，只要涉及到了数据存储，基本上都是按照这个流程来执行的。当这些内容完全铺展在大家面前之后，这个时候再回顾我们上一章引入的 DefaultMessageStore 消息存储引擎组件以及 CommitLog 类，大家也就能真的意识到这两个类的重要性了。  
  
在我们自己实现的消息队列框架中， DefaultMessageStore 消息存储引擎就是消息存储的入口，Broker 节点接收到生产消息后会把消息交给 DefaultMessageStore 消息存储引擎去处理，消息存储引擎接收到消息后就会把消息提交给 CommitLog 对象，CommitLog 对象就会把消息存储到 CommitLog 文件中 。这也就意味着 CommitLog 文件就是最终持久化消息的本地文件，不管 Broker 节点某个主题下配置了多少写队列，只要这个 Broker 节点接收到消息之后，就会把消息持久化到本地的 CommitLog 文件中 。当然，在持久化的过程中，显然会先把消息写入到缓存中，然后再寻找合适的时机持久化消息到本地，其中的细节以后我再为大家补充。总之，现在大家应该知道了， 我们为 Broker 节点定义了一个名为 CommitLog 的本地文件，这个文件会存储所有的生产消息，为了操作这个文件中的数据，我们又定义了一个 CommitLog 同名类，这个类的对象就会把消息存储到本地的 CommitLog 同名文件中 。  
  
当然，这么说有点不太准确，如果把 Broker 节点接收到的所有消息都存放到 CommitLog 这一个文件中，那这个文件存储的内容显然会越来越多，容量可能会从一开始的 1GB 逐渐增加到 100GB，这显然不是我们希望看到的情况，因为过于庞大的文件对数据的维护和管理是一种拖累。就比如说有些生产消息已经被消费者都消费完毕了，并且永远不会再被消费了，这就意味着这些数据需要从本地文件中删除，如果已经过期的数据和尚未被消费的数据都存储在同一个 100GB 大小的文件中，那处理过期数据显然非常麻烦，直接删除文件肯定会导致未被消费的数据也被删除了。因此，最简单的方式就是给存储生产消息的本地文件定义一个固定的容量，比如说本地文件最多只能存储 1GB 的数据，存满之后就可以创建新的文件继续存储消息数据。也就是说 Broker 节点内部可以有多个本地文件存储接收到的所有消息，并且这些消息会按照先后顺序存储到这些本地文件中，而所有存储消息的本地文件都可以存放到 CommitLog 文件夹中，这样一来，只要哪一个文件中的数据都过期了，直接删除这个文件即可。看到这里，大家应该也意识到了，实际上， 在 Broker 节点中，CommitLog 并不是一个文件，而是一个文件夹，这个文件夹中有多个存放了生产消息的本地文件，而 CommitLog 类的对象的责任并没有发生变化，仍然是把生产消息持久化到 CommitLog 文件夹中的本地文件中，并且是持久化到最新的本地文件中 。看到这里，大家应该彻底清楚了这个 CommitLog 类和 CommitLog 文件究竟是什么了吧？也清楚它们的作用了吧？当然，直到目前为止，我们仍然不清楚 CommitLog 对象究竟如何持久化消息，CommitLog 类如今仍是伪代码，但我们很快就会实现这些功能，大家不必心急。  
  
接下来，我有另外一个问题想和大家讨论，那就是经过上面一长串分析，我们终于明确了在 Broker 节点中消息是要持久化到本地，并且持久化到本地的操作是 CommitLog 对象负责的，所谓的 MessageQueue 消息队列根本就没有派上用场。源码中就是这么设计的，那看到这里我不禁要思考：既然在 Broker 节点存储消息时， MessageQueue 消息队列根本就没有派上用场，那么给主题定义配置信息，并且定义多个写队列数量的意义何在呢？比如说有一个 Broker 主节点创建了一个 Test 主题，然后给这个主题设置了读写权限，并且配置了 8 个写队列，当 Proxy 把生产消息路由给目标 Broker 节点时，会根据这个 Broker 节点的 8 个写队列来路由，但不管怎么路由，这 8 个写队列都属于同一个 Broker 节点，消息总是会被发送给这个 Broker 主节点，而 Broker 主节点接收到消息后，也没有把消息存储到目标队列中，不管选中的是哪个目标队列，只要消息被 Broker 节点接收了，就都被存储到 CommitLog 文件夹中的本地文件中。所以我真的不明白，为什么还要给 Broker 创建的主题定义多个写队列，因为就目前的情况来看，这些写队列并没有发挥一丁点作用，它们并没有分摊数据流量，不管数据有多少，最终还是存储到同一个 Broker 节点的本地文件中；它们也没有提高并发存储数据的效率；那它们究竟有什么作用呢？  
  
我相信很多朋友可能都会有以上哪些疑问，明明早就开始使用 MessageQueue 消息队列了，但是等真正存储消息的时候却发现消息队列根本没有派上用场。我想说的是，根据我阅读 RocketMq 源码的实际经验，如果某个主题的写队列只集中在一个 Broker 主节点上，比如说我们只构建了一个 Broker 集群组接收并存储消息，这个集群组的 Broker 主节点中有一个主题，主题配置了 8 个写队列，那这个时候这 8 个写队列肯定都集中在这个 Broker 主节点中；如果是这种情况，那么在 Broker 主节点存储消息的时候，这些写队列确实发挥不了多少作用，因为不管怎么路由，这些消息肯定都是存储到同一个 Broker 节点上。但是，如果说我们构建了多个 Broker 集群组，比如说有 a、b、c、d 这几个集群组，每个集群组的 Broker 主节点都创建了相同的主题，这时候请大家注意， 在 RocketMq 框架中，不同的 Broker 集群组可以创建相同的主题，但是主题的配置信息可以各不相同 。用户可以根据自己的需要使用控制台直接修改某个 Broker 节点中某个主题的配置信息，这个功能我们之前也实现了。如果有朋友已经忘了这个知识点，可以直接去 UpdateTopicSubCommand 类中回顾一下。  
  
好了，还是回到刚才的例子，在 a、b、c、d 这四个集群组的主节点中创建了一个 Test 主题，然后给这个 Test 主题定义了读写权限，并且定义了两个写队列，那在这种情况下，是不是意味着 a、b、c、d 这四个集群组各自的 Broker 主节点都拥有两个写队列？这样一来当 Proxy 就能根据可路由的 Broker 主节点的信息一共创建出 8 个可路由的写队列，而这 8 个写队列会平均分散在四个集群组的主节点上，那么 Proxy 路由生产消息的时候就可能把消息平均分散到各个 Broker 主节点中，这些消息队列也就起到了平摊数据流量的作用；当然，还有一种情况，可能各个服务器的配置并不相同，承受流量的能力也不相同，如果有哪个 Broker 主节点流量阈值高，那就可以给这个 Broker 节点的主题多定义几个写队列，哪个 Broker 主节点流量阈值低，就可以给这个 Broker 主节点的主题少定义几个写队列。如果我们总共就想为某个主题定义 8 个写队列，那么根据各个 Broker 集群组的主节点流量阈值的不同，我为这四个 Broker 主节点相同主题定义了 2、2、3、1 写队列配置，按照这个配置，显然集群 c 的主节点接收到的消息更多一些，集群 d 的主节点接收到的消息就少一些。这时候大家应该也明白了，在集群模式下，MessageQueue 消息队列才能真正发挥作用，当然，这其中肯定离不开负载均衡策略的配合。现在大家应该明白了 MessageQueue 消息队列的作用是什么了吧？那除此之外，消息队列还有什么其他的作用吗？也许有朋友会思考这个问题，这里我就先不展开讲解了，用不了多久，我们还会继续讨论这个话题。  
  
总之，到此为止大家应该稍微清楚一些了： MessageQueue 消息队列并没有真正的实体，确切地说消息队列并没有物理队列与其对应，它只是消息负载均衡中要用到的重要对象；Broker 节点真正存储存储消息的是 CommitLog 文件夹中的多个本地文件，CommitLog 对象负责把消息持久化到 CommitLog 文件夹中的最新创建的本地文件中 。大家可以再品味品味以上内容。  
  
剖析 CommitLog 对象处理数据的方式  
  
好了，生产者客户端生产的消息在 Broker 节点中的存储方式我们已经清楚了，这个方式十分常规，就是先写入到缓存中，然后再寻找合适的时机持久化到本地 CommitLog 文件夹的文件中。我们先不必考虑生产消息如何写入到缓存中，因为不管怎么设计，Broker 节点接收到的生产消息肯定是一堆已经序列化完毕的字节，要缓存这对字节非常简单，弄一个字节数组直接缓存不就完了？或者说就搞一个 ByteBuffer 对象，把接收到的所有消息都先缓存到 ByteBuffer 对象中，然后再寻找合适时机把 ByteBuffer 对象中的字节写入到本地文件中。这个可以理解吧？那现在问题就来了，既然最后要做的就是把字节数组中的字节写入到本地文件中，那该怎么写入呢？按照我们的编程经验，把一堆数据写入到本地文件中可以这么做，我把相关操作展示在下面代码块中了，请看下面代码块。

比如说有没有一种机制，在将数据写入到本地文件，或者从本地文件读取数据到内存时，不会涉及系统调用呢？只要不涉及系统调用，那么程序执行就不会有额外开销。当然，我也希望有一种机制，那就是在读取本地文件中的数据到内存时，可以尽量数据加载过程中的数据复制，也许可以直接将数据复制到用户态，或者直接复制到内核态，但是用户态可以访问，这样不就减少了数据复制的次数吗？更方便消费者客户端消费消息了。那究竟有没有这样的机制呢？巧得很，操作系统恰好为我们提供了一种机制可以解决以上的问题， 这个机制那就是内存映射 。我相信大家或多或少都听说过这个机制，但是并没有真正使用过，也没有什么机会使用，所以对这个内存映射机制也是一知半解。如果用稍微书面一些的语言来解释内存映射机制，那么可以解释成这样： 内存映射可以将硬盘上的文件直接映射到内存中，确切的说是将硬盘文件映射到用户进程的虚拟地址空间中，使程序能够像访问内存一样操作硬盘文件，也就是通过读写内存来实现硬盘文件的读写操作 。这就是内存映射机制的解释，当然，我知道这个解释对大家来说非常陌生，相当于什么也没解释，大家仍然不知道这个内存映射机制的具体作用是什么，也不知道内存映射机制的具体表现是什么，甚至大家可能连虚拟地址是什么都不太清楚。但我不准备继续往下讲解了，因为本篇文章的文字描述已经够多了，所以我不打算在这一章对内存映射机制展开详细讲解，对于这个机制目前我只想说两点：
