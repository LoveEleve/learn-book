  
完善 ConsumeQueue 消费队列和 ConsumeQueueStore 消费队列管理器  
  
我能想到的第一个问题就是，当消息被重放的时候，这些重放消息会被存储到 ConsumeQueue 消费队列的文件中，而这个过程会用到内存映射机制，但是除了内存映射机制，在之前实现消息存储到 CommitLog 文件夹的功能时，我们还实现了内存级别的读写分离功能，那现在问题来了， 在把重放消息写入到 ConsumeQueue 消费队列中时，可以启用内存级别的读写分离功能吗 ？  
  
在第一个问题之后，我又想到了第二个问题，那就是当重放消息都被写入到主题文件的缓冲区之后，该怎么刷新到本地硬盘中呢？根据之前存储消息到 CommitLog 文件夹功能的实现思路，我们已经知道了，只要缓冲区的消息要被刷新到本地硬盘，不管消息是粗放到对外内存缓冲区还是内存映射缓冲区，这些消息被刷新到本地时都要调用 DefaultMappedFile 内存映射文件对象的 flush() 方法，确切地说，是直接调用 MappedFileQueue 内存映射文件管理器的 flush() 方法。那么现在要把 ConsumeQueue 消费队列缓冲区中的数据刷新到本地持久化了，这个时候应该执行什么方法呢？因为 ConsumeQueue 对象持有了 MappedFileQueue 内存映射文件管理器，那这样一来， 是不是应该直接在 ConsumeQueue 对象内部调用 MappedFileQueue 内存映射文件管理器的 flush() 方法执行数据刷新操作呢 ？如果是这样的话，显然就应该给 ConsumeQueue 消费队列也定义一个 flush() 方法，但如果是这样的话，我们已经知道了，ConsumeQueue 消费队列会被 ConsumeQueueStore 消费队列管理器管理，那么 ConsumeQueueStore 消费队列管理器需要定义 flush() 方法吗？这是我想到的第二个问题。  
  
相比于前两个问题，第三个问题就更重要一些了，在目前的消息队列框架中，我们已经知道了，一个主题会对应一个 ConsumeQueue 消费队列对象，假如程序中存在多个主题，那么在 Broker 节点内部，就会为多个主题创建对应的 ConsumeQueue 消费队列对象。了解了这一点之后，我现在要提出的问题是： 在消息队列程序内部，一个指定的主题下可能会存在多个 ConsumeQueue 消费队列吗 ？我之所以提出这个问题，原因也很简单，因为很多时候，生产者生产的消息是没有顺序可言的，也不要求按照顺序生产消息，这就意味着消费者客户端消费消息的时候也不需要按照顺序消费，只需要尽快把消息消费完毕即可。如果是这样的话，那假如有多个消费者客户端同时到 Broker 节点消费消息，并且这些消费者客户端消费的都是同一个主题下的消息，比如说这个主题就是 TestTopic ， 而这个时候在 Broker 节点内部，这个 TestTopic 主题显然只对应着一个 ConsumeQueue 消费队列，这就意味着多个消费者客户端都要访问同一个 ConsumeQueue 消费队列，到这个队列中消费消息。这个逻辑大家可以理解吧？当然，这个逻辑本身肯定没什么问题，完全正确。我想说的是，在这个流程的基础上，可以对程序执行什么重构操作，以便提高多个消费者客户端消费消息的效率呢？  
  
我首先想到的就是既然有多个消费者客户端同时消费同一个主题下的消息，而现在只有一个 ConsumeQueue 消费队列可以被多个消费者客户端访问， 那为了提高程序执行效率，就可以为该主题，也就是 TestTopic 主题定义多个 ConsumeQueue 消费队列呀，当执行消息重放操作的时候，就可以把消息重放到这些队列中。这样一来，当多个消费者客户端消费消息的时候，不就可以消费多个消费队列中的消息了 ？这样不就提高程序执行效率了吗？  
  
大家可能不清楚这究竟是怎么回事，可能还有些疑问，就比如说，就算给某个主题提供了多个 ConsumeQueue 消费队列，多个消费者客户端可以共同消费这些队列中的消息，当然，一个客户端只能同时访问一个 ConsumeQueue 消费队列；这种方式虽然可以提高消息被消费的速度，但是当多个消费者客户端从各自访问的 ConsumeQueue 消费队列中消费了消息，最后还是要根据消息的关键信息到 CommitLog 文件夹中查询消息的真正内容，如果是这样的话，显然就是多个消费者客户端会同时访问 CommitLog 文件夹中的内容，那这种情况不会出现并发问题吗？实际上并不会，原因很简单， 因为只要被写入到 CommitLog 文件夹中的数据根本不会被修改，消息只是不断被追加到 CommitLog 文件夹中，在 CommitLog 文件夹中的数据只会越来越多，而原有的数据并不会被修改，消费者客户端到 CommitLog 文件夹中所做的也只是读取数据而已，所以就算出现并发读取数据的情况，也不会出现并发问题 。这个逻辑应该很容易理解吧？  
  
那这样分析下来之后，我想大家应该也认同了这个观点， 那就是确实可以给一个主题定义多个 ConsumeQueue 消费队列，只要不是顺序消费的场景，那么多个 ConsumeQueue 消费队列中的消息确实可以被多个消费者客户端同时消费 ，很好，那现在新的问题就来了， 怎么给一个主题定义多个 ConsumeQueue 消费队列呢？应该按照什么规则定义呢？而为一个主题定义了多个 ConsumeQueue 消费队列之后，那消息怎么被重放到主题下的多个 ConsumeQueue 消费队列中呢 ？  
  
当我终于提出以上几个问题之后，接下来的内容就变得简单了，而且接下来要实现得功能就会和之前 Proxy 节点中执行的某个操作联系起来了。实际上是这样的，大家应该还记得当生产者客户端生产了消息之后，会把消息发送给 Proxy 节点，而 Proxy 节点又会把消息转发给对应的 Broker 节点。在这个过程中，Proxy 节点执行了一个非常重要的操作，那就是根据消息所属的主题信息，得到了该主题下所有可以路由的消息队列，然后使用负载均衡功能选择了一个具体的目标队列，当这个队列被选出来之后，队列所属的 Broker 节点的网络地址也就确定了，而目标队列的队列 Id 也就确定了。这个流程大家应该都还有印象吧？假如我们给一个 Broker 节点创建了一个 TestTopic 主题，然后给这个主题定义配置信息时，定义了 8 个写队列和 8 个读队列，那么当 Proxy 节点为消息选择 TestTopic 主题的路由队列时，就有 8 个写队列可以选择，这不就是一个主题下有多个消息队列的情况吗？  
  
来到 Broker 节点内部，当存储 TestTopic 主题下的重放消息时，如果根据该主题的配置信息，也就是 8 个读队列数量，也为该主题定义 8 个 ConsumeQueue 消费队列对象，那这样一来，这个主题下不就拥有 8 个 ConsumeQueue 消费队列了吗？重放消息就可以被存放到该主题下的 8 个消费队列中了 。这个逻辑理解起来应该也不难吧？至于重放消息依据何种策略存放到这 8 个 ConsumeQueue 消费队列中，这就更简单了， 写队列 和读队列的队列 Id 是一一对应的 。就 比如说在 Proxy 节点选中了队列 Id 为 1 的目标队列，那么当 Broker 节点接收到消息后，在重放消息的时候，就可以根据消息信息中携带的目标队列 Id，查找对应 Id 的 ConsumeQueue 消费队列，如果 Broker 节点内部还没有创建对应 Id 的 ConsumeQueue 消费队列，那就创建 ConsumeQueue 对象，然后存储重放消息即可 。大家可以品味品味这个逻辑，总之，这样分析完毕之后， 我们也确实清楚了一个主题下是可以存在多个 ConsumeQueue 消费队列对象，并且每一个 ConsumeQueue 消费队列都拥有各自的队列 Id ，那这个时候，主题和 ConsumeQueue 消费队列的映射关系就要稍微改变一下了，就可以重构成下面这样，请看下面代码块。

上面图片只展示了 4 个队列文件夹，这一点可能会让大家觉得有些困惑，为什么少了 4 个队列文件夹呢？而且队列文件夹并不是从队列 1 开始的，这是因为 Proxy 节点在选中目标队列的时候有一个随机性，大家可以回顾一下之前的内容， 在 Proxy 节点刚开始轮询目标队列的时候有一个随机初始索引值，这样可以避免不同 Proxy 节点转发消息给 Broker 节点时在同一时间都被轮询到同一目标队列的情况出现，否则就会导致服务器压力骤增 。所以在刚开始可能并不会直接选择队列 Id 为 1 的目标队列来接收消息。而之所以缺少了 4 个队列， 是因为 Broker 节点并不会一开始就根据主题配置信息把某个主题下的所有消费队列文件夹都创建完毕，而是每接收到消息，根据消息携带的目标队列 Id 判断有没有为其创建对应的消费队列，如果没有，那这个时候才会真正创建消费对类对象，本地文件夹也才会被创建出来 。而在我为大家提供的第十五版本代码中，我测试的时候让生产者客户端发送了 4 次消息给 Broker 节点，Proxy 节点轮询了 4 次目标队列，所以 Broker 节点内部在接收到消息后就会把这 4 个队列 Id 对应的消费队列创建出来，因此大家才看到了本地存在的四个文件夹。大家在阅读第十五版本代码的过程中可以多让生产者客户端发送几次消息，看看本地队列文件夹会不会创建完整。好了，这些内容解释完毕之后，接下来就给大家展示一下队列文件夹中存放的本地文件，请看下面图片。
