请大家想一想，在我们构建一些集群时，尤其是构建数据库集群，什么 Mysql、Redis 数据库的时候，我们会采取主从模式构建集群，主节点可以读写数据，从节点负责数据备份，这个是很常见的操作吧？在数据流量平缓的时候，我们就会采取这种常规操作。但在另一种情况下，也就是流量非常大，并发压力非常高的时候，向数据库写入数据和读取数据的操作非常频繁，为了缓解主节点的压力，通常我们也可以对集群执行读写分离操作， 所谓读写分离，就是集群主节点负责写入数据，而从节点则负责读取数据，也就是说当用户想要从数据库获取数据，可以直接去从节点获取，这样一来，主节点就可以专注负责存储数据，而从节点专注负责读取数据，这就是典型的读写分离模式 。虽然这种模式有一定缺陷，比如说从节点更新数据不及时，导致用户读取到的数据可能不是最新的，但这种方式确实可以缓解主节点服务器压力。这种情况大家肯定都能理解吧？  
  
很好，如果大家都理解了这种情况，那再回到消息队列框架中，根据我们之前的分析，我们已经知道了，当 CommitLog 对象处理数据的时候，会先把数据写入到内存映射缓冲区，也就是 pagecache 中，而一旦我们为消息队列框架实现了消费者客户端，当消费者客户端从 Broker 节点消费消息的时候，也会从 pagecache 中获取消息，这个流程之前我们已经分析过了，大家应该都能理解。如果是这样的话，显然就是由 pagecache 负责数据的读写，那 pagecache 不就成了流量汇聚的焦点了吗？和刚才的数据库集群类比一下， 此刻 pagecache 就相当于集群主节点，负责数据的读写操作，如果 Broker 节点流量激增，消费者客户端频繁消费消息，生产者客户端频繁写入消息，那么 pagecache 的压力肯定很大 ，这个逻辑大家应该也能理解吧？如果大家也认同这种情况存在隐患，那么为了缓解 pagecache 的压力，我们可以怎么做呢？当然，我们完全可以对照数据库那样，对 pagecache 实现读写分离。但是，我们首先就会想到，根本就没有从节点啊？或者说 pagecache 又不是一个节点，怎么给它定义从节点呢？这很好办，其实根本就没有从节点，我们不需要什么从节点，我们需要的是什么？是多余的内存啊朋友！ 如果我们再为 pagecache 定义一块多余的内存，那就可以使用一块内存写入消息，一块内存读取消息了，对吧 ？这不就实现了读写分离吗？那现在问题来了， 就算我们多定义了一块内存，那么让谁负责写消息，谁负责读消息呢 ？接下来请听我仔细分析。  
  
是这样的朋友们，要讨论让哪一块内存负责写入消息，哪一块内存负责读取消息，首先我们得把额外的内存定义出来。pagecacha 是内核态的内存，我们肯定无法对其做任何改动，能使用它已经让我心怀感激了，既然内核态的内存我无法操作，那么我就操作用户态的内存，所以， 我的做法是直接申请一块堆外内存，也就是 DirectBuffer，让堆外内存帮助我们实现 pagecacha 的读写分离 。堆外内存的特点大家肯定都很清楚，如果 Java 堆内存要和本地硬盘进行 IO 操作，比如说要写入数据到本地，那么数据会先从堆内存复制到堆外内存，再从堆外内存复制到 pagecacha，然后再从 pagecacha 写入到本地； 如果直接让 JVM 使用堆外内存，把数据直接写入堆外内存缓冲区，那么把数据写入到本地的时候，就可以减少一次堆内存到堆外内存的复制 。除此之外， 堆外内存还有一个非常明显的有点，那就是它的释放不被 JVM 垃圾回收器管理，JVM 只是持有 DirectBuffer 引用，当 DirectBuffer 引用被 JVM 垃圾回收后，操作系统会帮我们处理堆外内存的释放，因此就算要释放一块特别大的堆外内存，也不会因为垃圾回收对 JVM 运行造成非常大的影响 。分析了这些内容之后，我做出了一个大胆的决定， 那就是让堆外内存负责写入数据，让 pagecacha 负责读取数据 。  
  
也许大家还是觉得有些模糊，那就让我再解释一下， 所谓让堆外内存写入数据，就是当 CommitLog 对象处理数据的时候，并不直接把数据追加到内存映射缓冲区中了，而是直接写入新申请的堆外内存，然后程序就可以直接返回了，就可以处理后面的数据。那这个时候肯定会有朋友疑惑，就算写入堆外内存了，这部分数据还是要落盘啊，只有落盘到本地，或者从堆外内存写入到对应的 pagecache 中，这部分数据才能在内存映射机制中发挥作用，才能使用内存映射机制被消费者客户端读取啊 。这就很好办了， 我们只需要定期对这部分堆外内存执行提交数据的操作，让堆外内存把数据定期提交到 pagecache 中 ，这样一来，这些数据就可以被刷新到本地，也可以被消费者客户端读取了呀。当然， 在执行定期提交堆外内存数据的时候，也可以等到堆外内存攒够了一批数据之后再执行提交数据操作，比如也可以判断积攒的消息是否达到了 4 个 4KB 页缓存大小，太频繁的提交操作会让系统频繁切换到内核态，影响程序性能，所以最好是批量提交数据，把一堆数据批量提交到 pagecache 中，以此减少系统切换开销 。这也是我选择让堆外内存负责写入数据的原因之一。  
  
当然，这么做肯定有缺陷，虽然这么做可以让堆外内存缓解 pagecache 的压力，做到了内存级别的读写分离，但是这就导致了最新的消息会被存放到堆外内存中，而不是实时到达 pagecache 或者是落盘到本地，以至于不能让消费者立刻消费消息。但这个问题也不大，因为通常来说，我们只会让生产者客户端对 Broker 节点发送新增的消息，并不会对 Broker 节点原有消息执行更新操作，所以消费者客户端肯定不会消息到错误消息，最多就是消费最新消息的时候有点延迟。这个过程我相信大家自己也能分析清楚。好了，分析到这里，接下来让我为大家总结一下： 只要在消息队列程序中启用了内存读写分离功能，那么 Broker 节点存储数据的时候就会把数据写入到堆外内存，并不会把数据追加到 pagecache 中，也就是说在写入数据的时候并没有使用内存映射机制；而当消费者客户端读取数据的时候，会从 pagecache 中获取，这个时候是在内存映射机制下执行的相关操作，也就是说，读取消息时使用了内存映射功能 。大家要理解这个过程。  
  
好了，刚才我们已经用一大堆文字分析清楚了内存级别的读写分离功能该如何实现，那么怎么用代码编写这个功能呢？编写代码就很简单了， 我已经定义好一个 TransientStorePool 类，翻译过来就是临时存储池的意思，我在这个类中定义了一个队列，队列用来存放多个 DirectBuffer 对象，当 TransientStorePool 对象被创建之后，就执行它内部的初始化方法，在初始化方法，也就是 init() 方法中，会预先申请多块堆外内存存储在内部队列中 。这样一来，当需要写入数据的时候就直接从 TransientStorePool 存储池中得到一块堆外内存写入数据，如果写满了就可以再从池中获取新的堆外内存继续写入数据，当然，堆外内存使用完毕之后还要归还给 TransientStorePool 存储池； 所以我还给 TransientStorePool 存储池定义了两个方法，一个是从内存池借出堆外内存的 borrowBuffer() 方法，另一个是归还堆外内存的 returnBuffer() 方法 。这样分析下来，这个 TransientStorePool 就可以定义成下面这样，请看下面代码块。

重构 DefaultMappedFile 类  
  
请大家想一想，在目前的程序中，操纵每一个本地文件的对象是什么？肯定是 DefaultMappedFile 对象，我们已经给 DefaultMappedFile 对象定义了内存映射缓冲区，用来追加消息到 pagecache 中，也给该对象定义了 flush() 方法，该方法可以把 pagecache 中的数据持久化到本地文件。现在突然搞出来一个读写分离，这就意味着写数据的时候数据不能直接追加到 DefaultMappedFile 对象的内存映射缓冲区了，而要写入到堆外内存中，既然 DefaultMappedFile 对象会操作本地文件， 那我直接再给 DefaultMappedFile 定义一个 ByteBuffer 成员变量，这个成员变量就是从 TransientStorePool 存储池中借来的堆外内存 。这样一来， 只要有消息到来，要追加消息的时候，那就判断程序是否开启了读写分离功能，如果开启了，就让 DefaultMappedFile 对象返回堆外内存缓冲区，把消息追加到堆外内存缓冲区中；如果没有开启读写分离功能，那就直接让 DefaultMappedFile 对象返回内存映射缓冲区，把消息追加到内存映射缓冲区中即可 。当然，如果开启了读写分离功能，那肯定就要考虑把堆外内存缓冲区的数据提交给 pagecache， 所以还要给 DefaultMappedFile 再定义一个提交对外内存缓冲区数据到 pagecache 的 commit() 方法 ，这个方法会被定期调用，提交数据到 pagecache 中，这个逻辑可以理解吧？当然，这样一来 DefaultMappedFile 对象刷新数据的方法也要重构了， 不能再使用内存映射缓冲区的 force() 方法刷新数据到硬盘，而应该使用文件通道的 force() 方法刷新数据到硬盘 ，这样分析下来，DefaultMappedFile 类就可以重构成下面这样，请看下面代码块。
