  
实现顺序消费消息功能  
  
谈到顺序消费消息，对大家来说，涌现脑海的第一个念头是什么呢？这不用说，肯定是要按照顺序一条一条消费消息，前一条消息没有消费完毕，那么消费者客户端就不能消费后面的消息。那怎么样就算是前一条消息被消费完毕了呢？这个也很简单，只要前一条消息被成功 ack 了，那就意味着前一条消息被消费完毕了。这样一来，其它的消费者客户端就可以消费后面的消息了。这个逻辑很好理解吧？  
  
好了，现在我们都清楚了消费者客户端从 Broker 节点获取消息时都是批量获取的，那在顺序消费消息的情况中，这个时候就变成了必须等待前一批被 Pop 出的消息被消费完毕了，也就是全部被 ack 了，在其之后的消息才能被消费者客户端继续消费。这个逻辑也很容易理解吧？  
  
我相信对大家来说，上面的内容理解起来肯定非常简单，因为这就是顺序消费消息功操作的本质，就算没有学过任何编程知识的朋友也能理解上面内容的意思。但话说回来，顺序消费消息并不是一个单一的功能，仅仅知道了消费者客户端怎么顺序消费消息还不够，消费者客户端只知道从消费队列中获取消息，等到前一批被消费的消息都 ack 完毕了，才能消费之后的消息，这么一来，消费者客户端就保证了消费消息的顺序性；但是，消息本身的顺序性该怎么保证呢？换句话说，已经储存到消费队列中的消息是不是按照顺序存储的呢？分析到这里，这一点就显得至关重要了。  
  
比如说现在有一个生产者客户端，这个生产者客户端都要向 Test 主题下发送生产消息，而主题下有 8 个写队列和读队列，这就意味着这个生产者生产的消息会按照设定的负载均衡策略分布在各个队列中。假如说这些消息最终分散存储在了 8 个消费队列中，当消息这样被存储的时候，就会造成一种情况：第 1、3、5 消息被存储到了 Id 为 1 的消费队列中，2、4、6 被存储到了 Id 为 2 的消费队列中， 而我们目前实现的是 Pop 模式的消费者客户端，该客户端并不会只消费某个指定队列中的消息，而是会在循环中消费这 8 个队列中的所有消息。并且每次消费的时候，会根据一个随机值得到要消费的消费队列的 Id 。也就是说，消费者客户端可能并不会直接从 Id 为 1 的消费队列中获取消息，如果从 Id 为 2 的队列中消费消息，那么就会首先消费第 2 条消息了，这显然就没有按照严格的顺序消费消息。就像下面代码块展示的这样，请看下面代码块。
