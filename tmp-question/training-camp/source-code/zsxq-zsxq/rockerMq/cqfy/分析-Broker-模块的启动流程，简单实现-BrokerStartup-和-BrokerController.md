前面两章我们已经为 Proxy 模块构建了 Netty 的服务端和 Grpc 服务端，这也就意味着这个 Proxy 模块已经可以启动了，如果消费者和生产者的客户端知道了 Proxy 服务端的网络地址，那么生产者和消费者客户端就可以直接和 Proxy 模块进行通信。当然，这个功能还要等等才能实现，到此为止，Proxy 模块就算是简单构建完毕了，那接下来我们应该做什么呢？这没的说，肯定就是实现一个简单的 Broker 模块，因为从实现了 Namesrv 模块之后，我们就打算构建 Broker 模块了， 只不过 RocketMq 5.0 版本引入了新的 Proxy 模块，并且如果使用 Local 本地模式启动了 Proxy 模块，那么就会把 Broker 内嵌在 Proxy 中部署，也就是说把 Broker 和 Proxy 部署在同一台服务器上，并且在 Proxy 模块启动的过程中，也会把 Broker 模块启动了 。为了在后面方面是实现源码中的这个功能，所以我们先构建了一个简单的 Proxy 模块，现在 Proxy 模块构建完毕了，那接下来肯定要回归主题，开始构建这个 Broker 模块，等 Broker 模块也构建完毕了，就可以让 Broker 模块和 Proxy 模块协同工作了。说了这么多，那这个 Broker 模块应该怎么构建呢？  
  
分析 Broker 模块的构建流程  
  
当我们开始构建 Broker 模块的时候，我们首先应该知道我们构建的这个 Broker 模块可以做什么，也就是说我们希望它能负责什么工作。按照前面章节的分析，我们已经知道了：  
1 这个 Broker 模块必须把自己的信息注册到 Namesrv 模块中，这样其他模块就可以从 Namesrv 模块中知道消息队列程序中的所有 Broker 节点的信息，这些信息包括 Broker 节点的自身信息以及内部包含的主题信息。  
2 Broker 模块还可以接收生产者客户端发送的消息，以及返回消费者客户端需要的消息，当然，这中间需要 Proxy 模块做一层代理。也就是说，生产者客户端和消费者客户端必须要发送响应的请求给 Proxy 模块，然后 Proxy 模块访问 Broker 节点，最终完成生产者和消费者客户端想要执行的操作。  
3 既然 Broker 节点内部有主题信息，而主题都是用户对 Broker 创建的，那 Broker 模块内部肯定要定义一个请求处理器，这个请求处理器可以接收创建主题信息请求，然后创建对应的主题信息 。  
以上就是我们目前已经能够确定的 Broker 模块的功能。  
  
那从这些信息中我们可以分析出什么呢？就比如说第一条信息吧，Broker 模块必须要把自己的信息注册到 Namesrv 中，这就意味着 Broker 模块肯定要和 Namesrv 模块进行通信，并且是主动通信，Namesrv 的服务端我们已经构建完毕了，是用 Netty 构建的，所以只要再给 Broker 模块构建一个客户端，并且是 Netty 构建的客户端，这样一来，Broker 模块就可以顺利和 Namesrv 模块进行通信了。这个可以理解吧？  
  
而 Broker 模块和 Namesrv 模块进行通信的目的，是想要把自己的信息注册到 Namesrv 中，而 Broker 的信息就包括当前节点的自身信息已经内部被创建的主题信息，主题信息并不是 Broker 节点自己能够控制的，开发者创建了什么主题，Broker 内部就会有什么主题，所以主题信息暂时不做考虑。那 Broker 节点的自身信息呢？这个是它自己的吧，这些信息都包括哪些呢？当前节点所在集群的名称，也就是 BrokerClusterName，当前节点的 BrokerName、BrokerId 等等，这些信息就是当前 Broker 节点自己的信息。当然，这些信息也是开发者事先定义好的，定义在 Broker 的配置文件中， 当 Broker 模块启动的时候，就可以加载并解析配置文件，把配置文件中的数据封装到 Broker 模块内部使用的配置文件对象中。如果我们把 Broker 模块内部使用的配置文件对象定义为 BrokerConfig，那么当根据用户定义的配置文件初始化了 BrokerConfig 配置文件对象之后，Broker 模块在运行过程中需要任何配置信息都可以直接从 BrokerConfig 配置对象中获取了 。就比如说我们可以在 Broker 模块的配置文件中定义以下信息，请看下面代码块。

那除了这些还能从刚才的第一点中分析出什么呢？也许大家并没有意识到，但是我已经看过源码了，我可以直接告诉大家， Broker 模块内部还需要一些定时器 ，至于是哪些定时器，请大家听我详细分析。请大家思考一下，既然Broker 模块在启动之后要把自己的信息注册到 Namesrv 模块中，这就意味着 Broker 模块需要知道 Namesrv 的网络地址， 如果程序中有多个 Namesrv 节点，也就是为了避免单点故障，给项目构建了一个 Namesrv 集群，这就意味着 Broker 需要知道所有 Namesrv 节点的网络地址，然后把自己的信息发送给所有的 Namesrv 节点 。原因很简单， Namesrv 集群是无状态集群，没有主节点和从节点之分，Broker 需要把自己的信息注册给 Namesrv 集群中的每一个节点，并且还要知道 Namesrv 集群中所有节点的网络地址，当 Broker 发现 Namesrv 集群中新添加了某个节点，或者某个节点宕机了，那 Broker 节点就要执行对应的操作，向新添加的 Namesrv 节点注册自己的信息，或者不再维护已经宕机的 Namesrv 节点的地址，这样就可以不再对该节点发送信息了 。这些逻辑应该可以理解吧？  
  
如果以上逻辑大家都理解了，那我们是不是可以反推一下，实际上 Namesrv 模块也要掌握与自己建立连接的每一个 Broker 节点的实时工作状态，判断该 Broker 节点是不是正常工作，还是说已经宕机了。 因为 Proxy 会代理生产者和消费者客户端从 Namesrv 模块中获取指定主题的路由信息，而这些路由信息就是可以对外正常工作的 Broker 节点的信息 ，如果某个 Broker 节点已经宕机了，但是 Namesrv 却把它返回给 Proxy 模块了，这显然会让程序运行出错。所以， Namesrv 模块需要掌握每一个注册到自己内部的 Broker 节点的工作状态，如果某个 Broker 节点已经宕机，那 Namesrv 就可以直接把维护的该 Broker 节点的信息移除 。  
  
这样分析下来，我们已经清楚了，对于 Broker 节点来说，Namesrv 集群中每一个 Namesrv 节点的网络地址可能会动态发生变化；而 Namesrv 需要实时获取每一个 Broker 节点的信息，维护与每一个 Broker 建立的连接。那我们就可以给 Broker 模块定义两个定时任务： 第一个定时任务就是用来定期刷新可用的 Namesrv 地址列表 ； 第二个定时任务就是用来定期向 Namesrv 模块发送心跳消息，维护网络连接。当 Namesrv 与 Broker 节点心跳检测失败时，Namesrv 就可以把对应的 Broker 节点信息移除了 。这两个定时任务的作用应该很好理解吧？  
  
当然，如果要多解释一句的话，那就是在给 Broker 模块定义第一个定时任务时，可以选择多种方式让 Broker 节点获得可用的最新 Namesrv 地址列表。 我们可以使用 DNS 的方式，通过解析用户事先定义在配置信息中的域名，来动态获得最新的可用的 Namesrv 地址列表 。 域名对应的 IP 地址可以被动态更新，那这个时候我们就可以在定时任务中定期解析域名对应的 IP 地址，这些 IP 地址就是最新的 Namesrv 地址列表 ，这样一来 Broker 不就能实时获得最新的可用的 Namesrv 地址列表吗？我把对应的代码展示在下面代码块中了，请看下面代码块。

好了朋友们，我对刚才提出的第一个要点已经分析得差不多了，接下来我们看看第二点能被我们分析出什么内容，也就是这一点： Broker 模块还可以接收生产者客户端发送的消息，以及返回消费者客户端需要的消息 。这一点分析起来其实就很简单了，既然 Broker 模块需要接收消息，这就意味着 Broker 模块需要一个服务端啊，并且还是 Netty 构建的服务端，因为在实现 Proxy 模块的时候我已经跟大家解释了，只有生产者和消费者客户端和 Proxy 模块通信的时候可以使用 Grpc 框架，RocketMq 的模块进行内部通信时，使用的仍然是 Remoting 协议，仍然是 Netty 构建的客户端和服务端。这个可以理解吧？当然了， 既然 Broker 内部需要定义 Netty 构建的客户端，并且还要处理客户端发送过来的请求，这就意味着 Broker 内部还得定义对应的请求处理器，处理客户端发送的各种请求 。具体要定义什么请求处理器可以先不必关心，大家只需要知道应该给 Broker 定义请求处理器即可。到此为止，第二个要点也分析完毕了。  
  
而第三点分析起来就更简单了，既然 Broker 模块能够根据请求在自己内部创建对应的主题，那仍然是需要一个对应的请求处理器而已，实现创建主题信息功能。这一点也很容易理解吧？  
  
到此为止，我就把最开始提出的和 Broker 模块功能相关的三个要点分析完毕了。这几个要点分析完毕之后，我相信大家对构建简单的 Broker 模块一定有了很清晰的思路，我自己也总结了一下，为 Broker 模块的构建总结了以下几个要点。  
1 首先用户要为 Broker 模块定义配置文件，Broker 的关键信息可以定义在配置文件中，在启动程序的时候，要把配置文件路径定义在命令行参数中，这样程序启动之后就可以根据配置文件路径加载对应的配置文件，初始化 BrokerConfig 配置信息对象。  
2 Namesrv 地址列表可以定义在 Broker 的配置文件中，也可以写在命令行中让程序自己解析，当然，还可以提供域名地址，让 Broker 根据域名解析 Namesrv 地址列表。  
3 Broker 运行之后应该启动 Netty 构建的服务端，把请求处理器注册到构建完毕的服务端中，也就是初始化网路通信组件。  
4 为 Broker 模块创建 Netty 构建的客户端对象。这个时候 Broker 模块已经可以收发消息了。  
5 为 Broker 定义两个定时任务，一个定时任务定期向 Namesrv 发送自己内部的信息，另一个定时任务定期更新可用的 Namesrv 地址集合。这一步其实就是初始化定时任务组件 。  
以上就是我总结的五个要点，我们只要遵循以上五个要点，就能实现一个非常简单的 Broker 模块。 接下来就让我们实现这个 Broker 模块吧。
