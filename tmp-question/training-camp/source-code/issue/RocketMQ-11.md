# RocketMQ-11. delay level、专用 Topic 和定时扫描怎样把消息重新投递出来

> 场景：上一篇已经知道延迟消息不是 Broker 睡一会再发，而是先被改写进 `SCHEDULE_TOPIC_XXXX` 这条延迟专用轨道里。接下来真正的问题才开始变具体：消息到了时间点以后，RocketMQ 到底是怎么把它重新拉回普通消息主链的？
>
> 本篇只回答一个问题：**delay level、专用 Topic 和定时扫描怎样把消息重新投递出来。** 这里不回头重讲“为什么要先改写成延迟形态”，而是聚焦 `parseDelayLevel() -> delayLevel2QueueId() -> DeliverDelayedMessageTimerTask -> messageTimeUp() -> putMessage() -> updateOffset()` 这条后台推进主链，解释延迟消息为什么本质上是一条“专用轨道上的顺序重投链”。

## 先把真正的困惑摆出来：为什么“到点重投”不能被理解成一次普通定时回调

理解了延迟消息必须先改写成特殊形态以后，很多人下一步又会自然滑向另一个过度简化的想法：那不就是 Broker 里有个定时器，到点以后把消息重新发一下吗？

这个直觉的问题在于，它把“到点重投”理解成了一次孤立 callback，却没看到 RocketMQ 真正要维护的是一条持续推进的后台主链。

因为延迟消息一旦进入 `SCHEDULE_TOPIC_XXXX`，后面要解决的不是单个消息“什么时候醒”，而是整条专用轨道上很多消息怎样有序地被推进：

- 不同 delay level 的消息怎么分桶；
- 每个 delay level 为什么要映射到一个专用 queue；
- 后台扫描任务是从哪里开始、扫到哪里结束；
- 某条消息到点以后，如何恢复原 topic/queue 语义；
- 重新投递成功之后，这个 delay level 的位点怎么继续向前推进。

这几个环节不是并列配置，而是一条有前后依赖的失败链：

- 没有 level 到 queue 的映射，就没有可独立推进的轨道；
- 没有专用 Topic，就没有隔离普通消费链的内部空间；
- 没有扫描任务，就没有从等待态走向到期态的推进者；
- 没有语义恢复，消息就回不到业务主链；
- 没有 offset 前移，轨道就会卡在旧位置，无法持续处理后续消息。

如果这些问题不先讲清楚，后面就很容易掉进几个典型误区。

第一个误区，是把 delay level 理解成单纯的时间配置，好像只是“10 秒”“1 分钟”“5 分钟”这样的参数表。实际上，在 RocketMQ 里，delay level 不只决定“等多久”，还决定消息会被放进哪一个延迟专用 queue，因此它同时是时间分桶键和扫描分片键。

第二个误区，是把定时扫描理解成“到点了就触发一下”。可真正的后台链路并不是被单个消息定时唤醒，而是顺着某个 delay queue 不断扫描、判断、转正、重投、再更新位点。它更像一条顺序推进的链，而不是一堆彼此独立的闹钟。

第三个误区，是觉得消息重新投递以后，任务就结束了。事实上，重新 put 成功之后，系统还必须推进这个 delay queue 的 offset，不然下一次扫描还会卡在旧位置，整条专用轨道就没法继续向前走。

所以这篇真正要回答的，不是“ScheduleMessageService 定时任务怎么写”，而是：**RocketMQ 如何把延迟消息重投这件事，组织成一条专用轨道上的顺序推进主链。**

可以先把这条主链压成一张图：

```text
parseDelayLevel()
  → delayLevelTable + delayLevel2QueueId()
    → SCHEDULE_TOPIC_XXXX 的各级专用队列
      → DeliverDelayedMessageTimerTask(level, offset)
        → lookMessageByOffset()
          → messageTimeUp() 恢复原消息语义
            → putMessage() 重新投递
              → updateOffset(level, nextOffset)
```

*关键设计（斜体）：* *RocketMQ 的延迟重投不是一个“单点定时器 callback”，而是一条以 delay level 和专用 queue 为骨架的后台推进主链：消息先按级别分桶，再被顺序扫描、转正重投，最后更新该级别的推进位点。*[模式: delay 分桶 + 专用轨道推进 + 到点转正]

## 第一层：没有 `delayLevel -> 专用 queue` 这层映射，主链会先在“不同延迟消息没有独立推进轨道”这里失败

延迟消息要能被稳定重投，第一步不是直接扫描消息，而是先把延迟等级组织成一套可推进的结构。

`parseDelayLevel()` 的真正意义，不只是把配置字符串解析成几个时间长度，而是建立一张 `delayLevelTable`：系统从此知道每个 delay level 对应的时间跨度是什么，又该被映射到哪一个专用 queue（`ScheduleMessageService.delayLevel2QueueId(level)=level-1`）。

这意味着 delay level 在 RocketMQ 里有双重角色：

- 它是“延迟多久”的时间语义；
- 它也是“这条消息进哪条专用轨道”的分片键。

如果没有这层映射，主链会先在哪坏掉？会坏在“所有不同延迟语义的消息都挤在一起，后台线程根本不知道该按什么粒度推进”这里。到那时，系统不是完全做不了延迟，而是失去了把延迟消息组织成多条独立推进轨道的能力。

所以 `parseDelayLevel()` 不该被看成配置读取函数，它在主链里真正回答的是：**延迟消息后续按什么维度被拆成多条可以独立扫描、独立推进的轨道。**

## 第二层：没有专用 Topic / queue，主链会先在“等待消息污染普通消费视图”这里失败

上一篇已经讲过，延迟消息不能以原始 topic/queue 直接暴露给普通 Consumer，否则会在“还没到时间就被普通主链看见”这里失败。到了这一篇，这个问题要再推进一层：专用 Topic / queue 的作用不只是隔离消费视图，它还决定了后台推进链怎么被组织起来。

因为 RocketMQ 不是在一堆普通消息里给某几条贴一个“晚点再发”标签，然后靠全局扫描找出来；它是先把这些消息整体送进 `SCHEDULE_TOPIC_XXXX` 及其各个 delay queue，让它们从一开始就进入一条独立但可重放、可定位、可推进的轨道。

这条专用轨道同时解决两个问题：

- 普通 Consumer 看不到还未到期的消息；
- `ScheduleMessageService` 有明确的 queue 和 offset，可以沿着固定空间推进，而不是在普通消息世界里全局筛选。

如果没有专用 Topic / queue，主链会先在哪坏掉？会坏在“等待消息既污染普通消费视图，又没有自己的扫描位点”这里。后面的定时扫描会退化成到处找特殊消息，既污染主链，也失去稳定进度。

所以专用 Topic / queue 在主链里的角色不是“存放特殊消息的临时筐子”，而是**延迟消息后台推进主链的物理轨道**。

## 第三层：`DeliverDelayedMessageTimerTask` 不是单条消息闹钟，而是专用轨道的顺序推进器

一旦 delay level 和专用 queue 都建立起来，后台主链才真正开始进入扫描阶段。这里最容易犯的错误，是把 `DeliverDelayedMessageTimerTask` 理解成“针对某条消息的定时任务”。

但 RocketMQ 真正做的不是给每条延迟消息都挂一个独立 timer，而是：针对每个 delay level，对应启动一条顺序推进的扫描任务。它带着 `(level, offset)` 这两个上下文，不断在该专用 queue 上往前走。

这说明什么？说明延迟消息的运行时模型不是“消息驱动定时器”，而是“专用轨道驱动扫描器”。系统关心的不是“某一条消息什么时候醒来”，而是“这条延迟轨道现在推进到哪个 offset，哪些消息已经到点，哪些还得继续留在轨道里”。

如果没有这种顺序扫描模型，主链会先在哪坏掉？会坏在“每条延迟消息都需要独立定时器状态，Broker 迟早要被大量分散定时器拖垮”这里。RocketMQ 正是用“轨道 + offset 推进”的方式，主动避免把自己实现成一个巨大的睡眠回调集合。

所以 `DeliverDelayedMessageTimerTask` 的关键身份，不是普通定时任务，而是**延迟专用轨道的推进器**。它的工作单位不是某一个孤立消息，而是某个 delay level 对应的队列位点。

## 第四层：`messageTimeUp()` 的真正作用，是把“延迟轨道上的消息”恢复成“普通消息主链上的消息”

当扫描任务沿着专用轨道往前走时，它真正的关键动作并不是“看到了这条消息”，而是“判断到点后怎样恢复它的原始业务身份”。这正是 `messageTimeUp()` 的核心价值。

因为 RocketMQ 之前为了防止消息过早消费，已经把它改写成了延迟专用形态。可如果到了时间点，只是简单地“再 put 一次”，而没有把原始 topic/queue 语义恢复回来，这条消息仍然只是内部延迟轨道上的消息，而不是真正回到了业务主链。

所以 `messageTimeUp()` 真正补的是“转正”这一步：它让消息从延迟专用身份恢复回业务原始身份。只有这样，后面的 `putMessage()` 才不是“继续往延迟系统里写”，而是“把它重新放回普通消息主链”。

如果没有这层恢复动作，主链会先在哪坏掉？会坏在“消息虽然到点了，却永远停留在内部延迟形态，回不到原 topic/queue 的业务世界”这里。它看似完成了定时扫描，实际上没有完成业务投递。

所以延迟消息真正难的不是“等多久”，而是“什么时候、怎样把它恢复回普通主链的语义”。

## 第五层：没有 `putMessage()` 和 `updateOffset()` 的双重收口，重投就不能持续推进

很多人看到“消息已经重新 put 回普通主链”时，会本能觉得整个流程到此就结束了。但对 RocketMQ 来说，这还少了最后一刀：**这条 delay queue 自己的推进位点有没有往前走。**

延迟重投有两个必须同时成立的结果：

1. 消息已经以普通 topic/queue 身份重新写回消息主链；
2. 原来那条延迟专用轨道已经承认自己处理到了下一个 offset。

前者靠 `putMessage()` 完成，后者靠 `updateOffset(level, nextOffset)` 完成。两者缺一不可。

如果只有 `putMessage()` 没有 offset 更新，会发生什么？主链会先坏在一个很隐蔽却很致命的地方：

- 重投的那条消息虽然已经成功回到普通主链；
- 但延迟轨道自己的扫描位点没动；
- 下一轮扫描还会从旧位置继续看；
- 结果是重复重投，或者整条轨道卡在旧位置。

如果只有 offset 更新、没有 `putMessage()`，则更直接：延迟轨道以为自己已经前进了，业务主链却根本没有收到转正后的普通消息。

所以 `putMessage()` 和 `updateOffset()` 本质上属于同一条重投主链的两段收口：一个完成“消息回到业务世界”，一个完成“延迟轨道继续向前”。

这说明 RocketMQ 维护的不是一堆“消息到点事件”，而是**每个 delay level 对应的一条可持续推进的轨道位点**。单条消息只是这条位点链上的一个被处理元素。

*关键设计（斜体）：* *RocketMQ 关心的不只是某条延迟消息有没有被重新投递，更关心“这条 delay 轨道是否能继续向前推进”；所以 `putMessage()` 和 `updateOffset()` 本质上属于同一条重投主链的两段收口。*[模式: 重投成功 + 轨道位点前移]

## 第六层：延迟消息不是独立子系统，而是普通主链上的“变形 -> 暂存 -> 转正 -> 回归”

把前面几层连起来，就会发现一个非常重要的事实：延迟消息从来不是 RocketMQ 之外的一套平行系统。

它和普通消息共享的是：

- 先落统一真相层；
- 仍然写 CommitLog；
- 仍然依赖 Broker 的宿主能力；
- 最终仍然要回到普通消息主链被消费。

它和普通消息不同的是：

- 中间会先被改写成延迟专用形态；
- 会沿着 `delayLevel -> 专用 queue -> 定时扫描` 这条后台轨道推进；
- 到点后再恢复原 topic/queue 并重新投递。

所以更准确的说法，不是“RocketMQ 有一个延迟消息子系统”，而是“RocketMQ 在普通消息主链中插入了一段可持久化、可推进、可回归的延迟轨道”。这也解释了为什么这篇必须放在普通主链、存储主链都讲清之后再写，因为它从头到尾都依赖那条主链，只是在中间拐了一段路。

## 收网：延迟消息真正做的，是沿专用轨道顺序推进，直到重新并回普通主链

如果把整篇压成一句话，RocketMQ 的延迟消息重投机制并不是“消息到点后触发一次 timer callback”，而是：先按 delay level 把消息分桶到专用 queue，再由后台扫描任务沿着这条队列顺序推进，到点后恢复原消息语义、重新 put 回普通主链，并同步推进延迟轨道自己的 offset。

```text
parseDelayLevel()
  → delayLevelTable + delayLevel2QueueId()
    → SCHEDULE_TOPIC_XXXX 的各级专用队列
      → DeliverDelayedMessageTimerTask(level, offset)
        → lookMessageByOffset()
          → messageTimeUp() 恢复原消息语义
            → putMessage() 重新投递
              → updateOffset(level, nextOffset)
```

到这里，主线只发生了三件事。

第一，delay level 不只是“延迟多久”的配置，它还是延迟专用轨道的分桶和分片键。

第二，专用 Topic/queue 不只是为了隔离普通 Consumer，还为后台扫描提供了明确的队列位点和推进空间。

第三，`DeliverDelayedMessageTimerTask`、`messageTimeUp()`、`putMessage()` 和 `updateOffset()` 共同维护的是延迟轨道推进，而不是一堆彼此独立的到点事件。

**本篇的一句话困惑**：delay level、专用 Topic 和定时扫描，到底是怎样把一条延迟消息重新投递出来的？

**本篇的一句话顿悟**：RocketMQ 不是给每条消息挂一个独立定时器，而是先按 delay level 把消息放进专用轨道，再由后台任务按队列和 offset 顺序推进，到点后恢复原 topic/queue 并重新投回普通消息主链，同时推进延迟轨道位点。**
