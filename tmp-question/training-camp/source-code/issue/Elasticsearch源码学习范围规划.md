## 二、知识域规划

### 🔴 核心域（6 个——搜索引擎内核）

| 编号 | 域 | 核心类 | 说明 |
|:---:|---|---|---|
| E-1 | **Index Engine—写入路径** | InternalEngine, Engine, Translog, IndexShard | **写入全链路**：`IndexRequest` → `TransportShardBulkAction` → `IndexShard.applyIndexOperationOnPrimary()` → `Engine.index(index)` 三件事：①写 `Translog.add(operation)`(WAL,顺序写磁盘) → ②写 Lucene `IndexWriter`(内存 buffer) → ③返回 `IndexResult(version, seqNo, translogLocation)`。**IndexingStrategy 计划-执行模式**(R2源码验证 InternalEngine L530+)：`planIndexingAsPrimary()` 决定 `indexIntoLucene`/`addStaleOpToLucene`/`useLuceneUpdateDocument` → `indexIntoLucene()` 执行实际 Lucene 写入。**append-only 优化**：`canOptimizeAddDocument()` 利用 autoGeneratedIdTimestamp 检测重试→直接用 `addDocument` 而非 `updateDocument`，跳过版本查找。**LiveVersionMap**：`versionMap.maybePutIndexUnderLock()` 内存版本映射，通过 `internalReaderManager` 的 refresh listener 更新。**并发**：`readLock.acquire()` 允许并发写入(read lock 语义——多 index 可并发，refresh/flush 序列化)。**refresh(默认1s)**：`Engine.refresh()` → `ReferenceManager.maybeRefresh()` → 打开新 `IndexReader`。**flush(默认30min或 translog 512MB)**：`InternalEngine.flush()` → ①refresh → ②Lucene `IndexWriter.commit()`(fsync) → ③`Translog.createNewTranslog()` 生成新 generation |
| E-2 | **Search 查询路径** | SearchService, QueryPhase, FetchPhase, DFSPhase | **两阶段查询**：① **QueryPhase**：协调节点 broadcast 到所有相关分片 → 各分片执行 Lucene `IndexSearcher.search()` → 返回 doc_id+score(不返回 _source) → ② **FetchPhase**：协调节点根据 doc_id 从分片拉取完整文档(`_source`/`stored_fields`/`highlight`)。**DFS(分布式词频)** 在三阶段查询中使用(先收集词频，再 Query，再 Fetch)。**Query 执行**：Lucene `IndexSearcher.search(Query, Collector)` → `BooleanQuery`(MUST/SHOULD/FILTER/MUST_NOT) → `TermQuery`/`MatchQuery`/`RangeQuery`/`PrefixQuery` 等各类 Query 重写为 `Weight.scorer()` → 迭代 doc_id 打分。**相关性评分**：BM25(TF-IDF 改进，`k1=1.2, b=0.75`)——词频饱和 + 文档长度归一化 |
| E-3 | **Translog—WAL 写入日志** | Translog, TranslogWriter, TranslogDeletionPolicy, Checkpoint | **双缓冲写入**：`TranslogWriter` 通过 `FileChannel.force(false)` 确保元数据写入(但数据可能延迟刷盘——ES 8.x 默认 `index.translog.durability=request`，每次请求 fsync)。**Checkpoint**：`translog.ckp` 文件记录 globalCheckpoint 和 minTranslogGeneration，崩溃恢复时通过 checkpoint 定位需要回放的操作。**Generation 轮转**：flush 时 `createNewTranslog()` 使当前 generation 封闭、只读，创建新 generation 继续写入——旧 generation 等待全部副本已同步后异步删除。**Peer Recovery**：恢复期间 `Translog.createSnapshot()` 创建 TranslogSnapshot，从 globalCheckpoint 位置开始迭代操作发送给恢复中的 replica |
| E-4 | **Cluster Routing—分片路由** | RoutingTable, IndexRoutingTable, ShardRouting, IndexShardRoutingTable | **RoutingTable 模型**(源码验证)：`version` 字段每次路由变更递增 → `ImmutableOpenMap<String, IndexRoutingTable>` 索引级路由。**ShardRouting** 含 `shardId/primary/replicaCurrentNodeId/state(INITIALIZING/STARTED/RELOCATING/UNASSIGNED)`。**分片分配算法**：`AllocationDeciders`(磁盘/副本/热/冷节点 等 10+ 个决策器) + `BalancedShardsAllocator` 平衡分片分布。**读路由**：`OperationRouting` 根据 `preference` 和 `routing` 参数选择目标分片——默认 round-robin 到任意副本。**写路由**：`routing=_id` 的 hash → target shard → 只发 Primary → Primary 复制到 Replicas |
| E-5 | **Shard Lifecycle—分片生命周期** | IndexShard, ReplicationGroup, IndexShardOperationPermits | **5 种状态**：`CREATED → RECOVERING → POST_RECOVERY → STARTED → CLOSED`。**IndexShard 核心组件**：①`Engine(InternalEngine)` — Lucene Engine ②`Translog` — WAL ③`Store` — 文件存储(Lucene IndexWriter) ④`ShardPath` — 磁盘目录。**ReplicationGroup**：维护 primary + replicas + inSyncAllocationIds(已同步副本集合) + trackedAllocationIds(跟踪中的副本)。**GlobalCheckpoint**：所有活跃副本中已确认完成的最小 seqNo → peer recovery 从此位置开始。**IndexShardOperationPermits**：信号量控制并发操作——写操作用 BLOCK 许可(阻塞等待)，读操作用 NON_BLOCK 许可(允许并发读) |
| E-6 | **SeqNo & 复制协议** | SequenceNumbers, ReplicationOperation, GlobalCheckpointSyncer | **seqNo 递增**：每次写入 Engine 分配递增的 `seqNo(sequence number)`，主副分片共享同一 seqNo 序列。**PrimaryTerms**：主分片每次当选获得新的 primaryTerm(递增数字)，防止老主在网络分区后继续写入。**GlobalCheckpoint 同步**：`GlobalCheckpointSyncer` 定期将 Primary 的 localCheckpoint 和已知副本的 globalCheckpoint 对比，广播 min(所有副本 localCheckpoint) 作为新 globalCheckpoint。**ReplicationOperation**：Primary 将操作(index/delete/noOp)序列发送给 replicas，replicas 按 seqNo 顺序逐个 apply → primary 收集各副本 ack → 当 `wait_for_active_shards` 个副本确认 → commit |

### 🟡 扩展域（5 个 — R2 新增 FieldData）

| 编号 | 域 | 核心类 | 说明 |
|:---:|---|---|---|
| E-7 | **Mapping—文档映射** | Mapping, DocumentMapper, MapperService | **Mapping 定义**：JSON Schema 定义字段类型(text/keyword/long/date/geo_point/nested/object)。**DocumentParser**：解析 JSON → 按 Mapping 提取字段值 → 构建 `ParsedDocument`(含 Lucene Document + docValues)。**DynamicMapping**：自动检测新字段类型并添加到 Mapping。**FieldMapper 体系**：`TextFieldMapper`(全文搜索)/`KeywordFieldMapper`(精确匹配+聚合)/`NumericFieldMapper`(数值范围)/`DateFieldMapper`(日期) — 每种映射指定 Lucene 索引方式(倒排索引/docValues/pointValues/termVectors) |
| E-8 | **Merge Policy—段合并** | MergeScheduler, MergePolicy, ElasticsearchConcurrentMergeScheduler | **Segment 碎片**：每次 refresh/commit 生成新 Segment → 随着写入积累产生数百个小 Segment → 查询需打开所有 Segment → 性能下降。**TieredMergePolicy**：按大小分层合并——将大小接近的小 Segment 合并为大 Segment，删除旧 Segment 标记为删除。**ElasticsearchConcurrentMergeScheduler**：限制合并线程数(maxThreadCount) + maxMergeCount，防止合并占用过多 IO 影响写入。**forceMerge(API)**：强制合并到指定 segment 数(如 to 1)，用于冷索引优化 |
| E-9 | **Bulk Processor—批量写入** | BulkProcessor, BulkRequest, BulkShardRequest | **Bulk API**：`{ "index":{...} }\n{"field":"value"}\n` 的 NDJSON 格式 → `TransportBulkAction` 预检 index/delete/create → 按 shard 分组(`BulkShardRequest`) → 每个 shard 内部 apply 多条操作 → Engine 内逐条执行。**批量优化**：①按 shard 聚合同一节点批操作 ②顺序执行非冲突操作(同一 doc 的多个操作需排序) ③`pipeline` 预处理器在 write 阶段前执行 |
| E-10 | **Cluster State—集群状态** | ClusterState, Metadata, CoordinationState, ClusterStatePublisher | **ClusterState 三层**：①`Metadata`(59 文件) — 索引元数据(IndexMetadata/Template/DataStream/Alias) + `RoutingTable` — 路由表 + `ClusterBlocks` — 集群级读写锁。**CoordinationState(R2 源码验证)**：Raft 风格 term-based 共识——`PersistedState`(持久化 currentTerm + lastAcceptedState) + `ElectionStrategy`(选举策略) + `VoteCollection`(join 投票收集) + `startedJoinSinceLastReboot/electionWon`(瞬态)。**两阶段发布**：Master 收到变更 → `CoordinationState` → `ClusterStatePublisher` publish 到所有节点 → 各节点 apply。**version 递增**(RoutingTable.withIncrementedVersion)：每次集群状态变更 version+1，节点通过 version 判断是否需要更新 |
| E-11 | **FieldData Cache** | IndexFieldData, GlobalOrdinalsBuilder, CircuitBreaker | **67 文件(R2 发现)**——聚合/排序性能核心。**DocValues**：列式存储(每字段单独存 byte[])，terms 聚合遍历所有文档。**加载**：`IndexFieldData.load()` 按 Segment 加载 → `SortedBinaryDocValues`(二分查找)。**GlobalOrdinals**：跨 Segment 去重编号——terms 聚合合并所有 Segment 词条。**CircuitBreaker**：`fielddata.breaker.limit` 限制单节点 fielddata 总内存(默认 JVM heap 40%)，超限抛 `CircuitBreakingException` 拒绝查询。**fielddata 历史**：ES 5.0+ 将聚合/排序迁移到 DocValues，但旧版本 fielddata 堆内存耗尽→OOM 是经典面试事故 |

## 五、关键架构关系

```
写入路径: IndexRequest → TransportShardBulkAction → IndexShard → Engine.index()
           ├─ Translog.add() (WAL 顺序写)
           └─ Lucene IndexWriter.addDocument() (内存 buffer)
              └─ ReplicationOperation → replicas

查询路径: SearchRequest → SearchService → QueryPhase (distributed)
           ├─ Lucene IndexSearcher.search(query, collector) → doc_ids + scores
           └─ FetchPhase → fetch _source/stored_fields from relevant shards

可见性: refresh() → IndexReader.reopen() → NRT (1s interval)
持久化: flush() → IndexWriter.commit() + new Translog generation (30min/512MB)

集群: ClusterState(versioned) → Metadata + RoutingTable
       Master 协调: CoordinationState(STARTED→COMMITTED→PUBLISHED)
```
