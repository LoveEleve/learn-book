# RocketMQ-7. Push、LitePull、Rebalance 为什么不是三套平行模型

> 场景：上一篇已经知道 Consumer 真正面对的是“队列责任 -> 拉回本地 -> ProcessQueue 承接 -> 位点推进”这条消费主链。但走到这里，读者通常会马上遇到另一个新的困惑：为什么 RocketMQ 里又冒出了 Push、LitePull、Rebalance 这些看起来彼此平行的消费者模型？它们到底是三套不同消费世界，还是同一条主链的不同入口姿势？
>
> 本篇只回答一个问题：**Push、LitePull、Rebalance 为什么不是三套平行模型。** 这里不展开 ConsumerGroup 协调协议全景，也不把文章写成 API 使用手册，而是先把“谁负责分配队列、谁驱动拉取、谁推进消费”这条共同主链理清，让后面真正写 ConsumerGroup / Rebalance 细节时不会再次丢主线。

## 先把真正的困惑摆出来：为什么看起来像三套消费者，背后却不该被写成三套故事

很多人在学 RocketMQ Consumer 的时候，会自然按类名或 API 入口把系统切成三块：

- PushConsumer 是一套模型；
- LitePullConsumer 是另一套模型；
- Rebalance 又像一个额外的组协调问题。

这种切法在使用层看起来很顺手，但一旦拿来理解源码，就很容易把主线拆碎。因为它会诱导你认为：Push、LitePull、Rebalance 各自有一套独立消费内核，只是恰好都叫 Consumer。

这恰恰是这里最该先纠正的错觉。对 RocketMQ 来说，消费主链本体并没有因为 API 入口不同就变成三套世界。真正没有变的是那条更底层的问题链：

1. 当前这个 Consumer 到底应该负责哪些 MessageQueue？
2. 这些队列里的消息，怎样从 Broker 拉回本地？
3. 拉回本地以后，怎样放进 ProcessQueue 这种责任平面？
4. 最后怎样由消费线程推进位点并处理失败？

Push、LitePull、Rebalance 看起来各自很大，其实都只是围绕这四个问题在不同层面切分职责。

最常见的几个失败直觉也都来自这里。

第一个失败直觉，是把 Push 理解成“Broker 主动把消息推给 Consumer”。一旦这样想，后面所有 `PullMessageService`、本地位点推进、ProcessQueue 的存在都会显得很奇怪。事实上，Push 的“推”主要是使用体验上的推，而不是消息物理传输语义上的推。

第二个失败直觉，是把 LitePull 理解成“完全另一套消费实现”。可它解决的主要是“谁来驱动拉取节奏”，不是重新发明一套新的消费主链。

第三个失败直觉，是把 Rebalance 当成外围协调协议，仿佛它只是 ConsumerGroup 才关心的元问题。实际上，没有 Rebalance 或别的责任划分机制，消费主链根本起不来：你连“当前这个 Consumer 到底该负责哪些队列”都回答不了。

所以这篇真正要回答的，不是 API 长什么样，而是：**消费主链在 RocketMQ 里到底是怎样被拆成“责任划分”和“入口姿势”两层的。**

可以先把这条关系压成一张图：

```text
ConsumerGroup 视角
  → RebalanceImpl 决定当前消费者负责哪些 MessageQueue
    → Push 模型：框架持续拉取并回调业务监听器
    → LitePull 模型：应用 poll/拉取，自己驱动消费节奏
      → 但两边都共享：队列责任 -> 拉取 -> ProcessQueue -> 位点推进
```

*关键设计（斜体）：* *Push、LitePull、Rebalance 的差别，不在于它们各自拥有独立消费内核，而在于“谁先决定队列责任、谁来驱动拉取、谁来推动消费节奏”；消费主链本体始终还是那条“责任队列 -> 拉取 -> 本地承接 -> 位点推进”链。*[模式: 同一消费主链 + 不同入口姿势]

## 第一层：没有 Rebalance，主链会先在“到底该由谁消费哪些队列”这里失败

上一篇已经说过，Consumer 这边的主链第一步不是读消息，而是先知道“哪些队列归我”。到了这一篇，这个问题要再往前推进一层：**谁来完成这种责任划分？**

答案就是 Rebalance。

如果没有 Rebalance 或任何等价的责任划分机制，Push 和 LitePull 都会在还没开始拉取之前先失败。因为它们虽然都知道 topic，甚至也都能拿到 Broker 端的消息视图，但它们根本还不知道：当前这个 Consumer 实例，究竟应该负责哪个 queue、又不该碰哪个 queue。

所以 Rebalance 不是消费主链外围的一层“组协议小知识”，而是消费主链的前提层。没有它，后面一切 Push、LitePull、ProcessQueue 都失去意义，因为你根本不知道这些本地状态该围绕哪些 queue 建立。

也就是说，Push 和 LitePull 不是站在 Rebalance 旁边的两条并列线，而是站在 Rebalance 之后才能成立的两种入口姿势。少了这条前提层，主链会最先坏在两个地方：

- 多个 Consumer 抢同一队列，位点推进互相覆盖；
- 某些队列根本没人负责，消息一直积压。

所以本篇虽然不展开 ConsumerGroup 的成员协议细节，但必须把这条边界钉死：**Rebalance 不是外围细节，而是 Push 和 LitePull 共同依赖的第一层主线。**

## 第二层：Push 不是“Broker 物理推送”，而是框架替你把拉取、承接和回调组织起来

很多人看到 `DefaultMQPushConsumer` 这个名字时，会自然脑补一种很经典的消息队列模型：Broker 主动把消息推过来，Consumer 被动接收。这个理解如果停留在使用层没太大问题，但一旦拿来理解源码，就会把整条主链彻底讲歪。

因为 RocketMQ 这里的 Push，更准确地说是**框架替你持续驱动拉取，并在消息到手后帮你组织消费回调**。它不是说 Broker 的消息物理传输方式变成了主动推送，而是说应用不必自己循环 poll、自己管节奏、自己把消息交给监听器，框架已经把这些步骤替你接住了。

这也意味着：Push 真正补的是一层**托管的消费节奏**。如果没有这层托管，主链会先在哪失败？不会先坏在“读不到消息”，而会坏在“应用得自己同时承担拉取、回调和推进三件事”这里。也就是说，本来应该由框架接住的一段消费运行时，会重新落回业务代码手里。

所以 Push 的价值不是“有一条不需要拉取的通道”，而是“在同一条消费主链上，框架替你托管了责任队列之后的节奏组织”。它背后仍然离不开：

- 先通过 Rebalance 拿到责任队列；
- 再由框架内部持续组织拉取；
- 再把拉回来的消息放进本地责任平面；
- 最后交给业务监听器，并继续处理位点推进。

如果把 Push 误解成“消息被直接推到业务回调里”，主链会先在“中间状态去哪了”这里失真：你会完全看不见 `PullMessageService`、`ProcessQueue` 和位点推进这些本来就存在的层。

## 第三层：LitePull 也不是另一套世界，它只是把节奏控制权交还给应用

和 Push 相对，LitePull 最容易被看成“另一种 Consumer 实现”，因为它暴露了 `poll()` 这种更像客户端自己拉的接口。这个感觉是对的，但它仍然不意味着底层主链换了一个世界。

LitePull 真正改变的，不是“有没有 Rebalance / Pull / ProcessQueue / 位点推进”，而是**谁来驱动这些动作的节奏**。在 Push 里，这个节奏更多由框架帮你组织；在 LitePull 里，应用自己来决定什么时候 poll、什么时候处理、什么时候推进自己的消费循环。

也就是说，LitePull 交还的是**节奏控制权**，不是重写底层主链。如果没有这层区分，主链会先在哪坏？会坏在读者把 LitePull 错看成“完全另一套消费实现”，于是后面再也看不出它和 Push 为什么还能共享 Rebalance、ProcessQueue 和位点推进这些共通结构。

所以这条链和 Push 的区别，更像是“框架驱动”和“应用驱动”的差别，而不是“消费主链结构完全不同”的差别。

## 第四层：`ProcessQueue` 之所以重要，正是因为 Push 和 LitePull 最终都要回到同一责任平面

如果 Rebalance 解决的是“队列归谁”，Push/LitePull 解决的是“谁驱动节奏”，那么 `ProcessQueue` 解决的仍然是上一篇已经立过的核心问题：**消息拉回本地以后，在哪里挂住自己的责任状态。**

这也是为什么本篇要刻意把 `ProcessQueue` 再拉回来讲一次。因为很多人会错误地觉得：一旦进入 Push / LitePull 模型差异，这种本地承接平面就不那么关键了。实际上恰恰相反——入口姿势越不同，越要先有一个相同的本地责任面，后面才谈得上统一推进。

Push 下，框架替你更积极地驱动拉取和消费；LitePull 下，应用自己来驱动这些节奏。但不管是谁驱动，拉回来的消息都不可能直接凭空完成消费和位点前移，它总要先落在某个“现在归我负责，但还没终结”的中间状态上。

如果没有 `ProcessQueue` 这种共同责任面，Push 和 LitePull 就真的会变成两套彼此难以对齐的世界：一个看起来像框架黑盒，一个看起来像 poll API 手册。正因为它们都共享同一个本地承接平面，RocketMQ 才能让两种入口姿势继续收束回同一条消费推进主链。

## 第五层：真正被分开的，不是消费主链，而是“谁先划责任、谁驱动节奏、谁暴露控制权”

走到这里，就可以把 Push、LitePull、Rebalance 的关系压得更清楚了。

它们并不是三套平行模型，各自有各自的消费内核。真正被分开的，其实只有三件事：

1. **谁先决定责任队列** —— 这由 Rebalance 解决；
2. **谁驱动拉取与消费节奏** —— Push 更偏框架驱动，LitePull 更偏应用驱动；
3. **谁承担业务回调与控制权** —— Push 更早把消息交给监听器，LitePull 则让应用显式管理 poll 结果和节奏。

但更底层的主链没有变：

- 先确定责任队列；
- 再从 Broker 拉回消息；
- 再放进本地责任平面；
- 最后再推进位点。

所以这篇最重要的结论，不是“Push 和 LitePull 有何区别”，而是：**它们共享同一条消费推进主链，只是在入口姿势和控制权边界上分工不同。**

*关键设计（斜体）：* *RocketMQ 真正分化的不是消费内核，而是消费入口姿势：Rebalance 先划责任，Push 再把“拉取 + 回调”托给框架，LitePull 则把更多节奏控制权交回应用；底层推进主链本身并没有因为入口不同而重写。*[模式: 责任先划分 + 入口姿势分化]

## 收网：Push、LitePull、Rebalance 的差别，不在于三套内核，而在于三种责任分工

如果把整篇压成一句话，Push、LitePull、Rebalance 最容易让人误会成三套平行模型，但它们真正分化的，不是消费主链本体，而是谁先划队列责任、谁来驱动拉取、谁来掌握消费节奏。

```text
ConsumerGroup 视角
  → RebalanceImpl 决定当前消费者负责哪些 MessageQueue
    → Push 模型：框架持续拉取并回调业务监听器
    → LitePull 模型：应用 poll/拉取，自己驱动消费节奏
      → 但两边都共享：队列责任 -> 拉取 -> ProcessQueue -> 位点推进
```

到这里，主线只发生了三件事。

第一，Rebalance 不是外围细节，而是消费主链的前提层；没有责任队列划分，后面的 Push 和 LitePull 都无从成立。

第二，Push 和 LitePull 不是两套消费世界，而是同一条消费推进主链上的两种入口姿势：一个更偏框架驱动，一个更偏应用驱动。

第三，`ProcessQueue` 和位点推进仍然是两边共享的本地责任平面与收口机制，这就是为什么入口不同不等于内核不同。

**本篇的一句话困惑**：Push、LitePull、Rebalance 为什么看起来像三套消费者模型，却又总在同一条消费主链里反复出现？

**本篇的一句话顿悟**：因为它们真正分开的不是消费内核，而是责任分配和入口姿势；RocketMQ 始终只有一条“队列责任 -> 拉取 -> 本地承接 -> 位点推进”的消费主链。**
