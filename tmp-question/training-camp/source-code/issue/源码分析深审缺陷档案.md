# 源码分析深审缺陷档案(通用)

> **定位**: 33 仓库知识规划共用的深审清单——每个项目写 KP/大纲后按此逐类自查
> **来源**: Arthas(10 轮深审)+ async-profiler(2 轮深审)的实证缺陷
> **用法**: 每完成一个域 → 按 #1~#12 逐类检测 → 修复 → 合格才进下一域;范围规划完成后先做一次"声明验证"

---

## A. 内容层缺陷

### #1 事实错误(类名/路径/数量/行号)

- **表现**: 引用的类名不存在、路径错误、数量不对、行号偏差
- **实证**: Arthas v1 规划 8 处(AgentLauncher 不存在/52 命令实为 49/MXBean 6 实为 8 等);monitor/line 的 @Name 行号写错
- **检测**: 每个 `File.java:行号` 引用必须 grep/sed 到源码行确认内容语义;数量类声明逐项数

### #2 API/实现路径编造

- **表现**: 凭"Java/C++ 常见模式"写实现方式,不读源码
- **实证**: Arthas 编造 issue 号 #196(全仓库不存在);async-profiler 编造 hooks.cpp="JVMTI 事件"(实测 pthread/dlopen 钩子)、objectSampler="instrument 插桩"(实测 JVMTI SampledObjectAlloc 回调)、ctimer="clock_gettime"(实测 timer_create)
- **检测**: 机制描述必须有源码行号支撑;issue 号必须在源码注释中溯源(`grep "issues/NNN"`)

### #3 文件名/目录名推断编造(高发)

- **表现**: 只看文件名就推断职责——**范围规划阶段的高危行为**
- **实证**: async-profiler 三连: hooks.cpp(200行)→"JVM 事件钩子";objectSampler.cpp→"instrument 插桩";ctimer→"clock_gettime"——全部推断失真
- **根因**: 范围规划基于文件盘点(文件名+行数),机制描述未经源码验证
- **检测**: 范围规划的每个"机制描述"必须抽查 grep;**写 KP 时全部重读,不许信范围规划的推断**

### #4 跨项目概念转移错误

- **表现**: 把已学项目的概念套到新项目(同为字节码增强/同为采样器)
- **实证**: async-profiler 的 objectSampler 被误套 Arthas 的"字节码插桩"概念;实际是 JVMTI 官方事件
- **检测**: 对比性描述(与 XX 同思路/同机制)必须验证对方项目真实对应关系

### #5 分类覆盖率不足(03 < 01)

- **表现**: KP 的 03 深度分类表没覆盖 01 提取表的全部机制
- **实证**: Arthas 初版 03 覆盖率 35-92%(7 域共缺 71 个);AP-1 缺 3、AP-2 缺 3
- **检测**: 脚本比对 01 表机制数 vs 03 分类行数;语义映射人工确认(措辞差异不算缺)

### #6 跨层不一致(KP 数不同步)

- **表现**: KP 扩充后,大纲头部/questions 头部/覆盖检查段落的数字没同步
- **实证**: Arthas 17 篇大纲头部 KP 数过期;7 份 questions 头部全部过期;覆盖检查段落 6 处过期
- **检测**: 脚本比对 KP 实际数 ↔ 大纲头部 ↔ questions 头部 ↔ 覆盖检查

## B. 结构层缺陷

### #7 文字锚(有函数名无行号)

- **表现**: 引用只写 `File.java` 或方法名,不给行号
- **实证**: 两个项目都出现;Arthas 修复 7 处
- **检测**: `rg -P '\.(java|cpp|h)(?!:\d)'`——排除 .jar/.so/示例文件名后必须为 0

### #8 篇节标注失效

- **表现**: questions 的"篇 X §Y"指向不存在的大纲章节
- **实证**: Arthas 166 标注首轮脚本 bug 修复后全有效;async-profiler 曾引用"篇 2 §5"(实为跨项目引用,误报)
- **检测**: 脚本提取"篇 X §Y"逐一核对大纲 `### N.` 章节;**注意区分跨项目引用(AR-1 篇 2 §5 合法)**

### #9 表格外行/格式不统一

- **表现**: 补充行落在表格外;标题 `?—` 缺空格;章节编号不连续;重复行
- **实证**: Arthas 10 篇标题空格、AR-3 Surface 补行在表格外、3 处重复行
- **检测**: 标题 regex `^# \d+\. .+ — .+`;章节编号连续性;表格结构检查

### #10 数字自洽

- **表现**: 关键数字(命令数/机制数/字段数)全文不一致
- **实证**: Arthas 9 组关键数字最终全自洽;需防脚本误报(162=行号/512=#1512 子串/8=18 子串)
- **检测**: 关键数字全文 grep 比对;可疑位置人工抽查

## C. 过程层教训

### #11 范围规划的推断不可信

- **实证**: 两个项目的范围规划机制描述都出现过编造(Arthas 8 处、async-profiler 3 处)
- **规则**: 范围规划可基于盘点(v1 允许推断),但必须标注"待验证";**KP 阶段逐文件深读,所有机制重新提取**;范围规划按深审结果滚动修订(v1→v1.1→v1.2)

### #12 "待确认"标记必须清零

- **实证**: Arthas/asprof.cpp 曾标"服务模式?"——KP 阶段深读后确认为 C API 导出
- **规则**: KP 完成时,范围规划/探索记录中的"?""待确认"必须全部清零或标注最终结论

### #13 一次一域,逐域深审(不可批量)

- **实证**: Arthas 初版批量完成 7 域,靠 10 轮深审弥补;async-profiler 改为一次一域
- **规则**: 每域 KP+大纲+questions 完成后,立即按 #1~#12 自查 → 通过 → 下一域

### #14 书稿代码块编造(写作期专属,高发)

- **表现**: 写文章时凭"记得的实现"贴伪代码/示意代码,不回到源码;大纲/规划文档里的行号直接抄,不重新 grep
- **实证**(openjdk-book 卷 2 第一篇,2026-08-11): ① `os.cpp:1744` 的 `initialize_initial_active_processor_count()` 凭记忆写 if/else 伪代码——真实实现是直接赋值 `active_processor_count()` 三行;② numa dlsym 行号照抄大纲 2890——实测在 3423 且是 `dlvsym` 版本化解析;③ "PER_CPU_SHARES 归一化"照抄 KP——实测 `cpu_shares()` 是 1024→-1("未设置"),归一化除法在 `active_processor_count()` 且受 `UseContainerCpuShares`(默认 false)控制;④ `CachedMetric` 位置照抄大纲(osContainer:78-92)——实测在 cgroupSubsystem_linux.hpp:213
- **根因**: ① 记忆冒充源码(即使"记得很清楚"的实现,落到 jdk11u 都可能不同——版本漂移);② 大纲/KP 是规划期产物,行号与描述未经写作期重验
- **规则**: 
  1. **每个代码块必须贴真实源码**(截取可省略模板/错误处理,但核心语句逐字)
  2. **大纲/KP 里的行号写作时一律重新 grep**,发现不符即修正文章并用真实行号
  3. **默认值/开关状态必须查 globals.hpp**(如 UseContainerCpuShares=false、PreferContainerQuotaForCPUCount=true)
  4. 自查命令: 文章里每个 `file:line` 逐个 `sed -n` 核对;每个代码块与源码 diff(截取部分允许)

### #15 大纲描述与源码漂移(写作期前置检查)

- **表现**: 规划期(KP/大纲)的机制描述与实际源码不符,直接照抄进文章
- **实证**(同 #14 案例): active_processor_count 的"三输入算法"(affinity/quota/shares)、cpu.shares 语义、CachedMetric 位置——KP 描述与 jdk11u 实际实现均有出入
- **根因**: KP 基于 2026-08-08 的提取,jdk11u 源码或理解演进;规划期置信度 High 不代表行号/细节精确
- **规则**: 写作时把 KP/大纲当"线索"而非"事实";机制描述以写作期 grep 结果为准;发现漂移 → 回填修正 KP/大纲(防下次再抄错)
