# 源码范围规划复盘方法论

> 目的：把一次框架源码规划中暴露出来的结构性问题沉淀为可复用方法，供后续分析 Netty 之外的框架时直接参考。  
> 适用对象：中大型基础设施框架、通信框架、RPC 框架、中间件、存储系统、容器与运行时。  
> 核心问题：如何避免“扫过很多文件，却没有建立正确的知识域”。

---

## 一、旧式范围规划最容易犯的错误

### 1. 用“类名出现”替代“机制闭环完成”

很多旧规划的问题，不是完全没扫到源码，而是把“这个类出现在列表里了”当成“这个主题已经被覆盖了”。

但类名出现，只能说明：
- 你见过这个类
- 它可能属于某个主题
- 它值得后续深入

它不能说明：
- 读者的困惑已经被回答
- 主题内部的状态机已经闭环
- 生命周期、线程边界、失败路径已经理清
- 这个类和其他机制的关系已经建立

所以后续规划不能只维护“类名清单”，还必须为每个候选主题补齐：
- 读者真实困惑是什么
- 入口在哪里
- 出口在哪里
- 中间状态如何变化
- 谁持有资源
- 谁处理异常
- 与其他主题如何交叉
- 能否单独写成一篇完整正文

只要这些问题没有闭环，主题就不能算“已规划”。

### 2. 直接按包、目录或模块切域

目录结构对阅读有帮助，但目录边界不等于知识边界。

大型框架里，大量关键机制天然跨包、跨模块分布。例如：
- 资源生命周期：可能横跨 buffer、transport、codec、handler
- 诊断能力：可能横跨 common、core、logging、buffer
- 背压链路：可能横跨网络层、缓冲层、协议层
- ThreadLocal/对象池：可能横跨并发包、工具包、核心运行时

如果直接按目录切域，常见结果是：
- 一个真正重要的机制被拆散到多个章节
- 每章都只讲自己那一小部分
- 读者最后还是拼不出完整运行图

因此，目录只能作为扫描起点，不能直接作为最终规划结构。

### 3. 把“运行时诊断能力”当成实现细节

很多规划会重视：
- 数据结构怎么分配
- 算法怎么执行
- 调度怎么运转

却低估：
- 泄漏怎么发现
- 错误怎么定位
- 日志如何解释
- 调试钩子如何工作
- 测试如何开启高强度检测

这是错误的。对于基础设施框架，诊断能力不是附属说明，而是核心运行时能力的一部分。

如果一个框架平时靠高性能工作，出问题时靠诊断机制救命，那么规划里就必须给诊断单独留出位置，而不是把它塞进备注或 FAQ。

### 4. 把“资源生命周期”拆成零散细节

很多旧规划会把以下内容零散地分散到不同章节里：
- retain / release
- close
- cancel
- fail promise
- handlerRemoved
- channelInactive
- destroy / recycle

但这些其实常常共同组成一件事：**资源所有权协议**。

也就是说，真正应该先回答的问题是：
- 对象现在归谁所有
- 什么时候发生转移
- 谁负责最终释放
- 异常发生时谁兜底
- 共享视图和聚合对象如何处理生命周期

如果没有先建立所有权总图，后面零散讲 release、close、fail，读者会一直陷入“这里为什么要释放”“那里为什么不能释放”的局部困惑里。

### 5. 把线程/调度问题和 I/O/缓冲问题混成一个主题

“谁在执行”与“数据如何流动”是两类不同问题。

例如：
- EventLoop / Scheduler 回答的是：谁执行、在哪个线程执行、任务何时被调度
- Buffer / Flush / Backpressure 回答的是：数据写到哪里、何时可写、何时真正发出、何时积压

旧规划常犯的错误是：
- 只要它们都在运行时发生，就统一收进一个“线程模型/核心流程”大章

这样做的结果是：
- 线程调度讲不深
- 出站背压讲不清
- flush 边界被冲淡
- 读者误以为可写性只是线程模型的附属细节

后续规划必须有意识地区分：
- 调度域
- 缓冲域
- 背压域
- 资源生命周期域

### 6. 把大模块简单标成“按需”，却没有复核中心性

很多人会根据名字或直觉判断：
- 这个是专项协议
- 这个不是主线
- 这个以后再看

问题在于，模块是否“按需”，不能只看名字。

应至少同时检查三类指标：
- 调用中心性：它被多少核心类依赖
- 上层复用度：多少上层框架依赖这条线
- 跨域连接数：它是否连接多个原本独立的机制域

只要一个模块同时满足：
- 调用密度高
- 上层复用高
- 机制桥接作用强

它就不该轻易被打成“按需”。

### 7. 只统计文件覆盖率，不统计机制覆盖率

“我扫了多少文件”只能说明输入规模，不能说明理解质量。

真正应该追踪的是五种覆盖：
- 模块覆盖
- 核心类覆盖
- 调用链覆盖
- 机制问题覆盖
- 失败路径覆盖

例如，对一个框架来说，必须能明确回答：
- 资源泄漏怎么定位
- 背压什么时候发生
- flush 为什么昂贵
- 对象什么时候失效
- 为什么某个异常会扩散到整条连接/整条请求链

如果这些问题没被回答，即使看了很多文件，也不能算完成了规划。

### 8. 忽略测试目录的设计证据

很多设计边界不是写在类注释里，而是写在测试里。

测试会直接暴露：
- 哪些行为被作者认为必须保证
- 哪些异常路径最容易出问题
- 哪些状态转换最值得锁死
- 哪些边界条件是公共 API 语义的一部分

因此，后续规划不能只扫 `src/main`。测试至少要承担三类职责：
- 用来发现真正的机制边界
- 用来验证你是否找对了知识域
- 用来给正文中的“为什么会这样”提供证据

### 9. 没有记录“排除理由”和“待复核边界”

很多旧规划只写：
- 按需
- 淘汰
- 不重要

但没有回答：
- 为什么排除
- 是暂时排除还是永久排除
- 后续什么条件下应该重新纳入

这会导致后续写作时出现两个问题：
- 历史判断被误读成永久结论
- 后来的扩展者不知道哪些边界其实已经讨论过

所以必须把范围之外的内容分层记录，例如：
- 当前主线
- 已探索但暂缓
- 平台特定
- 协议专项
- 构建/测试/工具
- 明确排除

### 10. 只做主干闭环，没有做“完整卷”补层

这是更隐蔽、也更容易在后期才暴露的问题。

很多规划在机制层面做得已经不错：
- 主干入口找到了
- 运行时闭环也立住了
- 失败路径和测试证据也补了

但最后形成的只是“主干卷”，而不是“完整卷”。

典型漏掉的内容包括：
- **规范层**：如 Servlet 规范、协议规范、契约边界
- **集成层**：如 Spring Boot / 上层框架如何装配和调用它
- **机制补深层**：如主干已经点到但未深挖的生命周期/类加载/资源隔离专题
- **生产层**：性能调优、安全运维、故障排查

问题在于，读者学一卷源码，往往并不只想知道“主干怎么跑”，还想知道：
- 它遵守什么规范
- 上层框架怎么接它
- 哪些机制值得继续深挖
- 真实生产里怎么调、怎么守、怎么查

如果这些层完全缺失，就会出现一种错觉：
- 主干篇数很少，看起来结构很紧
- 但整卷读完之后，读者还是会觉得“重要东西怎么没讲”

所以后续规划不能只问：
- 主干机制是否闭环

还要继续问：
- 这是不是一卷完整的源码书
- 是否缺规范层
- 是否缺集成层
- 是否缺机制补深层
- 是否缺生产与排障层

## 二、正确的范围规划应该怎么做

### 1. 先按模块扫描，再按机制重组

推荐顺序是：
1. 先扫目录和模块
2. 找核心入口类
3. 找状态核心类
4. 找资源/失败清理类
5. 找测试证据
6. 再把这些重组成“知识域”

也就是说：
- **扫描阶段**可以按目录
- **规划阶段**必须按机制

### 2. 每个知识域都要围绕真实困惑建立

一个合格的知识域，不是“这一包里有什么类”，而是“读者到底卡在哪个问题上”。

例如好的主题通常长这样：
- 对象所有权为什么会混乱
- 写缓冲何时触发背压
- 为什么 flush 不等于 write
- 为什么子 stream 可以映射成 child channel
- 为什么某些缓存要放在线程本地

这样的主题能直接转成正文标题，也能直接指导后续扫描与取证。

### 3. 为每个知识域建立五要素卡片

建议每个候选知识域都整理出以下五项：
- 读者问题
- 入口类
- 状态核心
- 失败路径
- 与其他域的连接点

这五项一旦不全，就说明该主题还没准备好进入写作阶段。

### 4. 强制补“失败路径”和“回收路径”

性能型框架里，最容易漏讲的就是失败路径。

规划时必须主动查：
- close / cancel / fail / cleanup / recycle / release / remove / shutdown
- exceptionCaught / handlerRemoved / channelInactive
- 测试里对应的 error / leak / overflow / not writable

如果不主动把这条线补进去，正文很容易写成“正常流程笔记”，无法支撑真实排障。

### 5. 把“桥接类”单独标出来

有一类类非常重要，但很容易被低估：**桥接类**。

它们负责把两个世界连起来，例如：
- 协议对象 -> 传输对象
- 上层 API -> 底层状态机
- 用户抽象 -> 内部资源模型
- 多路复用协议 -> 虚拟子通道

桥接类经常不是底层实现最多的类，但它们是理解整个框架如何“落地”的关键。

### 6. 在规划阶段就维护“可写正文”的优先级

范围规划不是文件清单，而是写作准备工作。

所以规划文件里最好同时维护：
- 哪些主题是核心域
- 哪些主题已经足够写正文
- 哪些主题还缺失败路径或测试证据
- 哪些主题只是后备候选

这样后续写作时，就不会再次回到无序扫描状态。

### 7. 在机制域之外，再补“卷级分层”

一卷完整的源码书，通常不只由机制主干构成。

主干机制域之外，至少还要检查是否需要补以下几层：

#### 1）主干层
回答：
- 系统怎么启动
- 请求/任务怎么进入
- 主执行链怎么跑
- 偏离正常路径时怎么收束

这是最核心的一层，也是最先应该收紧的一层。

#### 2）规范层
回答：
- 这套实现是在兑现哪些外部契约
- 哪些行为是规范要求
- 哪些行为是框架自己的实现取舍

如果缺这一层，读者很难分清“为什么实现必须长这样”。

#### 3）集成层
回答：
- 上层框架如何把它装起来
- 外部配置如何映射到内部结构
- 它在真实生态里怎么被使用

对于嵌入式框架、容器、存储、RPC 中间件，这一层往往不是可选项，而是落地语义的一部分。

#### 4）机制补深层
回答：
- 主干里已经点到、但值得独立深挖的专题
- 例如类加载、生命周期深挖、对象池、匹配规则、动态更新、资源隔离

这一层用于避免主干篇为了收主线而把重要机制压得过浅。

#### 5）生产层
回答：
- 性能调优怎么落
- 安全运维怎么守
- 故障排查怎么查

如果框架本身就是高频生产基础设施，这一层通常应该纳入完整卷，而不只是附录。

### 8. 嵌入式/集成型框架必须检查“上层装配桥”

有些框架本体分析完之后，看起来主干已经很完整，但真实使用者接触到的其实不是“裸框架”，而是被上层框架装起来之后的版本。

典型场景：
- Tomcat ↔ Spring Boot
- Netty ↔ Spring WebFlux / Gateway
- MyBatis ↔ Spring / Spring Boot
- RocketMQ 客户端 ↔ Spring Messaging 封装

对这些框架，范围规划时必须额外检查：
- 上层框架是怎么创建它的
- 配置是怎么映射进来的
- 生命周期是谁驱动的
- 使用者真正踩到的问题，是不是恰恰出在这个桥上

如果不补这层，就会出现一种常见断裂：
- 主干源码讲得很清楚
- 但读者仍然不知道“在自己的项目里，这玩意是怎么被真正装起来的”

## 三、建议的审计流程

以后分析任意框架时，可以直接复用下面这套审计流程：

### 第一步：目录扫描
- 扫所有主模块
- 记录目录结构
- 记录测试模块
- 初步划出核心模块与边缘模块

### 第二步：入口扫描
- 找启动入口
- 找运行时入口
- 找用户 API 入口
- 找资源创建入口

### 第三步：状态扫描
- 找状态机核心类
- 找生命周期核心类
- 找缓冲/队列/池化类
- 找线程/调度类

### 第四步：失败路径扫描
- 搜索 close / fail / cancel / cleanup / release / recycle
- 搜索异常包装与上抛路径
- 搜索测试中的异常断言

### 第五步：跨域桥扫描
- 找协议对象与传输对象桥
- 找用户 API 与内部状态桥
- 找 ThreadLocal / 对象池 / 缓存桥
- 找父子对象映射桥

### 第六步：重新编排知识域
- 不按目录列清单
- 按真实问题建立主题
- 对每个主题补齐五要素卡片
- 排出正文优先级

### 第七步：做卷级补洞
- 检查是否只有主干层，没有专题层
- 检查是否遗漏规范层
- 检查是否遗漏集成层
- 检查是否遗漏机制补深层
- 检查是否遗漏生产层
- 给出“主干先写”与“完整卷后补”的明确顺序

## 四、写作前的自检清单

在正式进入正文写作之前，至少要确认：

- 是否把“类名出现”误当成“主题完成”
- 是否有跨包机制被拆散
- 是否遗漏运行时诊断能力
- 是否遗漏资源所有权总图
- 是否把线程问题和 I/O 缓冲问题混在一起
- 是否把某个高中心性模块误判成按需
- 是否只统计了文件覆盖，没有统计机制覆盖
- 是否忽略了测试证据
- 是否记录了排除理由和待复核边界
- 是否只做了主干层，没有补完整卷专题层
- 是否遗漏上层装配桥（尤其是嵌入式/集成型框架）
- 是否遗漏生产性能 / 安全运维 / 故障排查等生产层

只要这里有 2-3 条没过，后续正文通常都会反复返工；如果主干层过了但卷级层没过，结果往往是“主线很清楚，但整卷明显不完整”。

## 五、最终原则

范围规划不是“把源码仓库列一遍”，而是：

- 找到真正的知识域
- 找到读者会卡住的问题
- 找到运行时最关键的状态与边界
- 找到异常和回收路径
- 为后续正文建立稳定的结构骨架
- 在主干闭环之外，补齐一卷源码书真正需要的规范、集成、机制补深与生产层

如果一份规划做完之后，仍然回答不了：
- 这套系统最容易出错的机制在哪
- 最难理解的边界在哪
- 最值得先写的正文是哪几篇
- 这一卷除了主干之外，还缺哪些专题层

那它就还不是一份合格的范围规划。
