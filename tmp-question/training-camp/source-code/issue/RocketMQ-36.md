# RocketMQ-36. TieredStore 为什么不是“把冷数据丢对象存储”——存储计算分离主链

> 场景：一听到 TieredStore，很多人第一反应就是：哦，就是把旧数据搬到对象存储里，给本地磁盘减压。这种理解抓到了一点表面现象，但远远不够。因为如果它只是“搬文件”，就不值得被 RocketMQ 5.x 单独提成重要架构能力。本篇要讲清的是：TieredStore 真正改变的，不只是冷数据放哪，而是 RocketMQ 原本紧耦合在 Broker 本地磁盘上的“存储与访问边界”被重新组织了。

## 先把真正的困惑摆出来：TieredStore 到底是在改“存储介质”，还是在改“系统边界”

如果只从运维角度看，TieredStore 很容易被理解成：

- 本地磁盘贵；
- 冷数据访问少；
- 把旧数据搬去远端对象存储；
- 节省成本。

这当然是它的一个直接收益，但如果只停在这层，就会看不见它真正带来的架构变化：**Broker 不再需要把“所有历史数据始终本地持有”当成默认前提。**

一旦这个前提被打破，随之变化的就不只是磁盘成本，还包括：

- 数据的热/冷边界如何组织；
- 读取路径如何分层；
- Broker 本地存储职责如何收缩；
- 可观测性和恢复路径又该如何重新理解。

*关键设计（斜体）：* *RocketMQ 5.x 的 TieredStore 不是简单的数据迁移工具，而是一次“本地热路径 + 远端冷路径”的显式分层：热数据仍由本地存储主链承载，冷数据则被放入远端分层存储，Broker 由此不必长期把所有历史数据都绑定在本地磁盘上。它改变的不只是数据放在哪里，而是存储与访问边界如何被拆层组织。*[模式: 本地热路径 + 远端冷路径 + 存储访问边界重划]

## 第一层：先承认原始模型——传统 RocketMQ 默认把存储和本地 Broker 绑得很紧

在没有 TieredStore 的传统心智里，RocketMQ 的主存储模型大致是：

- 消息顺序写入本地 `CommitLog`；
- 由本地 `ConsumeQueue` / `IndexFile` 等派生结构服务消费与查询；
- Broker 长期持有这套本地磁盘事实。

这套模型的优点很清楚：

- 热路径简单；
- 本地访问快；
- 主链围绕顺序写与本地索引展开。

但它也意味着一个默认前提：**历史数据和当前热数据都长期绑在 Broker 本地磁盘上。**

TieredStore 正是在挑战这个默认前提。

## 第二层：TieredStore 的核心不是“搬”，而是“分层”

如果只是把旧文件复制到别处，那叫归档；但 TieredStore 的关键不只是归档，而是把系统中的数据路径明确拆成两层：

- **热层**：仍由本地存储主链承载，服务最常见、最敏感的读写路径；
- **冷层**：把历史数据放到远端分层存储中，在需要时再按专门路径访问。

这意味着 RocketMQ 不再默认“所有访问都必须走本地磁盘”，而是开始承认：

- 有些数据要保证最低延迟；
- 有些数据更重要的是长期保存与可回读；
- 两者不一定必须共享同一套本地资源边界。

所以 TieredStore 的关键不在“存储介质变化”，而在“**访问分层被显式化**”。

## 第三层：为什么这会被称为“存储计算分离”而不是普通冷存储

“冷数据搬远端”只是结果；“存储计算分离”强调的是边界变化：

- Broker 负责的本地热路径可以更专注当前活跃流量；
- 历史数据存放不再与 Broker 本地算力/磁盘强绑定；
- 访问冷数据时，系统走的是另一套分层读取路径。

这意味着在架构上，RocketMQ 不再把“消息一直保存在本地节点上并由本地节点持续承担全部读取职责”当成唯一选择。

所以它不是给原有本地存储“外挂一个备份仓”，而是在承认：

> **消息系统也需要像数据系统一样，把热存储与冷存储、实时路径与历史路径拆开。**

## 第四层：TieredStore 并不否定 CommitLog，而是重新定义它的边界

这是最容易被误读的地方。

TieredStore 不是说 CommitLog 不重要了，更不是说 Broker 本地存储被替代了。相反，它仍然默认：

- 热写入主链在本地；
- 本地 `CommitLog` 仍然是当前活跃数据的主事实来源；
- 本地索引与消费结构依然服务核心热路径。

TieredStore 改变的是：**这条本地主链不必再无限承担全部历史数据的长期驻留责任。**

所以它对 CommitLog 的影响不是“推翻”，而是“**收缩边界**”：让本地主链更聚焦热数据，而把冷数据生命周期显式转移出去。

## 第五层：读取路径也随之变化——不是所有读取都该有同一成本

一旦存储分层成立，读取路径就不再天然同构：

- 热数据读取：优先走本地路径，延迟更低；
- 冷数据读取：通过分层存储路径回读，语义仍成立，但成本与时延模型不同。

这就是为什么 TieredStore 不是单纯“存储层小优化”，而是会改变整个系统对“读取成本”的理解：

- 不同时间层的数据，不再被假设具有同样的访问条件；
- 系统承认历史回读可以接受另一档成本；
- Broker 本地资源也因此有机会从历史负担中解放出来。

## 第六层：为什么它和 `DefaultMessageStore`、可观测性、恢复路径都有关

TieredStore 一旦进入系统，就不可能只影响“文件放哪”。

它会连带影响：

- `DefaultMessageStore` 的整体宿主边界理解；
- 哪些路径属于热存储，哪些路径属于冷存储；
- 监控系统需要分别观察本地热路径与远端冷路径；
- 恢复与回读时，哪些数据仍本地可得，哪些数据需要分层路径参与。

所以它和 `RocketMQ-28` 的存储总览、`RocketMQ-35` 的可观测性主线天然相连。

这也说明，TieredStore 不是“存储章节里的一个特殊 feature”，而是**存储边界重划**的一部分。

## 第七层：把 TieredStore 压成一句话，就是“Broker 不再长期背所有历史数据”

如果把它压缩成最短表达，可以这样理解：

- 传统模型：Broker 默认长期本地持有热数据 + 冷数据；
- TieredStore：Broker 本地更聚焦热数据，历史冷数据分层外提。

这就是它最根本的架构变化。

不是“对象存储更便宜”这么简单，而是：**RocketMQ 开始显式承认热/冷数据不应继续完全共享同一条本地主链。**

## 收网：TieredStore 不是冷数据搬家，而是存储与访问边界重划

把整篇压成一句话：RocketMQ 5.x 的 TieredStore 不是简单把冷数据搬去对象存储，而是把“本地热存储主链”与“远端冷分层存储路径”显式拆开，使 Broker 不再必须长期本地背负全部历史数据；CommitLog 和本地索引仍然服务热路径，但历史数据访问与长期保存开始拥有独立边界。这就是它之所以属于“存储计算分离”而不是普通归档的原因。

```text
传统 RocketMQ
  → 本地 CommitLog / ConsumeQueue / IndexFile
    → Broker 长期背热数据 + 冷数据

RocketMQ 5.x TieredStore
  → 本地热路径（当前活跃数据）
  → 远端冷路径（历史分层数据）
    → 存储与访问边界显式拆层
```

**本篇的一句话困惑**：TieredStore 为什么不能只理解成“把冷数据丢对象存储”？

**本篇的一句话顿悟**：因为它真正改变的不是存储介质本身，而是 RocketMQ 对热/冷数据、存储/访问路径、Broker 本地职责边界的组织方式；它是在显式拆开“本地热路径”和“远端冷路径”。**

## 本篇元数据：误解、证据与边界

### 至少要排除的误解

1. **“TieredStore = 冷数据备份。”** 它更关键的是显式分层热/冷路径。
2. **“有了 TieredStore，Broker 不再需要本地存储。”** 热写入主链仍然依赖本地存储。
3. **“这只是运维成本优化，不影响主链理解。”** 它会改变存储与访问边界的组织方式。
4. **“TieredStore 与可观测性、恢复路径无关。”** 分层以后，这些路径都要重新理解。
5. **“它只是给 CommitLog 换个存储位置。”** 它更像在收缩本地主链边界，而不是替代 CommitLog。
