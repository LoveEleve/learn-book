# 源码正文写作方法论

> 适用范围：本项目全部框架（Spring 生态 + 中间件）正文写作。
> 目标：把已经完成的域规划（pass1/pass2/completeness/outline/review）转成真正可读、可记、可迁移的技术文章。

## 一、正文不是大纲扩写

正文写作不是把：

- pass2 闭环
- completeness 问题
- outline 节点
- review 修正清单

按顺序拼起来。

正文要做的是：

1. 把“源码事实”重组为“读者理解路径”
2. 把“我读源码的顺序”改写成“读者最省力的顺序”
3. 把“代码片段”降级为证据，而不是骨架

一句话：

**先设计读者怎么懂，再决定源码怎么出场。**

## 二、正文写作的前置依赖

进入正文前，必须同时满足四类依赖：

### 1. 事实依赖

- 本域已有 `pass1-notes.md`
- 本域关键 `pass2-q*.md` 已闭环
- 本域已有 `completeness-questions.md`
- 本域已有 `outline.md`
- 本域已有 `review-notes.md`
- 所有关键锚点、默认值、数字、状态机都已重新 grep 验证

### 2. 机制依赖

- 本文依赖的前置域已经分析完成，或本篇能提供足够的小范围补前置
- 不允许把后置域结论当前置事实使用
- 跨框架对照只能作为 `COMPARE/NAV`，不能当主线依赖

### 3. 认知依赖

正文开写前，必须回答：

1. 读者此刻真正困惑什么？
2. 这篇的“一句话顿悟”是什么？
3. 读者最容易在哪个地方误解？
4. 哪些源码细节虽然正确，但现在讲会打断理解？

### 4. 叙事依赖

- 每篇必须能形成独立问题闭环
- 必须先有“问题 → 失败方案 → 设计 → 证据 → 回收”的结构
- 章节顺序不得按源码文件顺序机械铺开

## 三、三步分离流程

### 第一步：素材提取（机器友好）

产物来自现有规划文件：

- 机制链路
- 状态与时序
- 字段/常量/默认值
- 设计取舍
- 边界/失败路径
- 版本差异
- 源码锚点与测试/实验依据

注意：这些是**弹药**，不是正文骨架。

### 第二步：理解路径设计（写作前必须单独做）

每篇先产出一份“rewrite-plan”或同等规划，至少包含：

- 读者困惑
- 一句话顿悟
- 失败方案推演
- 章节顺序与每节要回答的问题
- 误解清单
- 证据清单
- 版本边界
- 字数预算

如果这一步没做，就不允许进入正文。

### 第三步：叙事写作（人味注入）

按理解路径写，不按源码目录写：

1. 事故/困惑开场
2. 直觉方案为什么不行
3. 角色、状态或数据流总图
4. 分层拆解实现
5. 用代码证明关键判断
6. 边界、代价、版本差异
7. 悬念回收与下一篇桥接

## 四、正文结构硬规则

### 1. 问题 → 挣扎 → 顿悟

每篇主线至少满足：

```text
困惑
  -> 朴素方案
  -> 失败原因
  -> 核心设计
  -> 分层拆解
  -> 收网总结
  -> 下篇钩子
```

### 2. 代码只能当证据

- 单段代码尽量不超过 30 行
- 先说“为什么现在要看它”，再给代码
- 代码后必须回答“它证明了什么”
- 删掉代码块后，文章主线仍应成立

### 3. 每层拆解四动作

每个核心机制层都要有：

- 动机
- 文字图/时序图/状态图
- 证据代码
- 路标（告诉读者现在走到哪里）

### 4. 失败方案是义务

每篇至少推演 1～2 个朴素方案，并明确：

- 它为什么直觉上合理
- 为什么不行
- 当前设计为什么必须绕一层

### 5. 构造时与运行时分离

- 构造篇只深讲初始化、注册、装配
- 运行时怎么使用，只做必要预告
- 运行时细节放后续专题

反过来也一样：运行时篇不要频繁跳回构造过程打断主线。

## 五、字数与反偷懒约束

- 重大机制篇/主链篇：正文原则上不少于 8000 字，目标 10000-15000 字
- 中等专题篇：5000-8000 字，但必须独立闭环
- 困惑开场建议 ≥ 600 字
- 失败方案推演建议 ≥ 1200 字
- 每个核心拆解层建议 ≥ 1500 字
- 误解澄清建议 ≥ 800 字
- 收网总结建议 ≥ 500 字

允许的扩容方式：

- 具体例子
- 失败方案
- 版本对比/方案对比
- 误解纠正
- 图的文字化描述

禁止的注水方式：

- 连续两句没有推进信息的重复总结
- 空洞排比
- 用“显然”“容易看出”掩盖没讲透
- 把一条结论拆成三遍不增加信息地重复

## 六、正文禁用词

正文主线出现以下词语时必须重写该节：

- 此处不再赘述
- 不再展开
- 类似地
- 同理
- 依此类推
- 篇幅所限
- 显然
- 容易看出
- 细节读者自行阅读源码

## 七、每篇必带的元数据

每篇正文除了正文本身，还必须同时产出：

1. 一句话困惑
2. 一句话顿悟
3. 一张总图（角色/箭头/时序）
4. 至少 3 条误解清单
5. 证据清单（关键结论分别由哪些 `file:line` 托底）
6. 版本/平台/实现边界清单
7. 前置依赖与后续桥接

## 八、正文写完后的深审流程

### 第一轮：事实审
- 类名、函数名、路径、数字、默认值、锚点、代码块真实性

### 第二轮：因果审
- 每个“因此/为了/保证/避免”是否有证据支撑
- 区分事实、推断和作者判断

### 第三轮：结构审
- 是否仍被源码文件顺序牵着走
- 是否有前向引用
- 是否有不能闭环的章节

### 第四轮：读者审
- 删码测试
- 陌生人测试
- 反向提纲测试

### 第五轮：边界审
- 并发、失败、资源释放、版本差异、未覆盖空间

### 第六轮：依赖审
- 前置依赖、后续桥接、跨域引用、知识脑图节点与边方向是否真实存在且方向正确

## 九、写作顺序规则

### 1. 全书顺序

正文顺序服从全局执行计划，而不是“哪个框架刚规划完就写哪个”。

### 2. 框架内顺序

同一框架正文顺序服从该框架 `outline/plan/handoff` 中已经确定的拓扑顺序。

### 3. 篇级顺序

篇与篇的顺序由读者理解依赖决定，不由源码文件顺序决定。

## 十、知识脑图要求

每篇正文同时要沉淀为脑图节点：

- 前置依赖（HARD/SOFT）
- 导航依赖（NAV）
- 对照关系（COMPARE）
- 消费关系（CONSUMES）
- 下一篇桥接（OUTBOUND）

正文里的桥接必须和脑图关系一致，不能正文这样写、脑图那样连。

## 十一、当前执行规则

- 先产出并确认这份正文方法论
- 再补“全局依赖关系图谱”
- 再按总执行计划确认第一篇该写哪个框架/域
- 之后每篇都必须先做篇级写作规划，再写正文
