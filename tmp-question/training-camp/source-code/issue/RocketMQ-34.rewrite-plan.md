# RocketMQ-34 重写规划

> 题目：为什么 RocketMQ 性能不如 Kafka——存储、路由、消费模型对照桥接篇
> 状态：桥接/对照篇。对应 `hz` 中“为什么性能不如 Kafka”主题，用前面已经拆过的两套主链对比出性能差异来源，避免落成口水结论。

## 1. 读者困惑
- RocketMQ 为什么常被说性能不如 Kafka？
- 是单纯实现差距，还是设计目标不同？
- 存储、路由、消费确认模型分别在哪些地方带来了额外开销？
- 为什么 RocketMQ 的功能语义更丰富时，吞吐对比就不能只看单次写入快慢？

## 2. 一句话顿悟
**RocketMQ 与 Kafka 的性能差异，不能简化成“谁代码写得更好”，而更应理解成两套不同取舍的结果：Kafka 极度偏向顺序追加、批量聚合与最短主链；RocketMQ 则在 Topic/Queue 路由、ConsumeQueue/IndexFile、事务/延迟/Pop 确认模型、接入层与多语义能力上承担了更多结构性成本。吞吐差异，本质上是“更短主链”与“更丰富语义”之间的架构取舍。**

## 3. 失败方案推演
- 把性能差异全归因于语言/实现优劣
- 只看 CommitLog vs LogSegment，不看消费/确认语义
- 忽略路由、索引、服务端确认模型引入的结构成本

## 4. 章节问题
- Kafka 为什么天然更接近极简高吞吐主链？
- RocketMQ 哪些能力会引入额外结构成本？
- 路由/消费/确认模型的差异怎么转化为性能差异？
- 为什么不能脱离业务语义只看裸吞吐？

## 5. 至少要排除的误解
- RocketMQ 慢只是实现差
- Kafka 快只是因为语言/团队更强
- 功能更丰富但性能还该无损持平
- 只看写入 benchmark 就能下结论
