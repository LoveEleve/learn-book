# RocketMQ-3. Producer send 以后，到底是谁决定发往哪个 Broker —— 路由发现与发送主链

> 场景：上一篇已经知道一条消息会经过 `Producer -> NameServer -> Broker -> CommitLog -> ConsumeQueue -> Consumer` 这条主链，但这时最容易被低估的一步其实发生在消息刚离开 Producer 的地方：业务代码手里明明只有一个 topic，为什么 RocketMQ 却总能把消息发到某个具体 Broker、某个具体队列，而且失败时还会避开某些节点？
>
> 本篇只回答一个问题：**Producer send 以后，到底是谁决定发往哪个 Broker。** 这里不进入 CommitLog 落盘、Consumer 拉取、顺序消息和事务消息细节，而是先把 `DefaultMQProducerImpl -> TopicPublishInfo -> selectOneMessageQueue() -> MQFaultStrategy -> sendKernelImpl() -> MQClientAPIImpl` 这条发送主链讲清，让后面存储和消费篇知道消息是如何先到达 Broker 的。

## 先把真正的困惑摆出来：Producer 手里只有 topic，为什么它却总能发往一个具体 Broker

从业务代码看，RocketMQ Producer 最像的只是一个“我给你 topic 和 body，你替我把消息发出去”的客户端。可这句话里其实藏着一个很大的空白：**发出去，到底是发给谁？**

业务侧通常只知道 topic，不知道这个 topic 当前分布在哪些 Broker 上、有多少可写队列、哪个 Broker 最近超时过、哪个队列最好暂时绕开，更不知道三种发送模式下最后该怎样收口。这意味着 Producer 并不是拿着消息就能直接调用一次“远程发送”完事。

这正是发送主链真正的第一道门槛。RocketMQ 在真正把字节发到网络上之前，必须先回答至少四个问题：

1. 这个 topic 现在对应哪些 Broker、哪些 MessageQueue？
2. Producer 端手里有没有这份路由视图，还是得补一次更新？
3. 即使队列列表已经有了，这次到底该挑哪一个？
4. 如果某个 Broker 刚刚失败、超时或表现很差，为什么不能继续无脑轮询它？

如果这几步没先讲清楚，后面“发送”很容易被误扁平化成一个错误直觉：Producer 只是做了一次 RPC。

最常见的几个失败方案其实都来自这个误扁平化。

第一个失败方案，是觉得 Producer 手里既然有 topic，那直接随机挑个 Broker 发就行。问题是 Producer 一开始并没有 Broker 目的地知识，它必须先把 topic 翻译成某个具体队列视图。

第二个失败方案，是觉得最准确的办法一定是“每次发送都实时去 NameServer 远程问一次路由”。这看起来最保险，实际上会把每次发送都拖进远程发现开销，发送主链会失去本地决策能力。

第三个失败方案，是觉得只要拿到了 topic 对应的队列列表，后面简单 round-robin 就够了。问题在于，Broker 的可写性不是静态的。某个 Broker 刚刚超时或故障时，如果还继续按静态轮询打过去，只会把失败放大。

第四个失败方案，是把 `SYNC / ASYNC / ONEWAY` 当成三条完全独立的主链。实际上，它们更像是**在“发给谁”这件事已经决定之后，发送结果如何收口**的三种模型，而不是三套从头到尾完全不同的路径。

所以这篇真正要回答的，不是“Producer API 怎么用”，而是：**从 topic 到 Broker/Queue 的目的地决策，RocketMQ 到底是怎样逐层完成的。**

可以先把这条主链压成一张图：

```text
业务 send(topic, msg)
  → 本地是否已有 TopicPublishInfo 路由视图
    → 不够时才去更新 NameServer 路由
      → TopicPublishInfo 持有可写队列视图
        → selectOneMessageQueue() + MQFaultStrategy
          → 选出当前 Broker / Queue
            → sendKernelImpl()
              → MQClientAPIImpl 远程调用 Broker
                → SYNC / ASYNC / ONEWAY 三种收口方式
```

*关键设计（斜体）：* *RocketMQ 的发送主链真正先解决的不是“怎么把字节发出去”，而是“当前这条消息应该发往哪个 Broker/Queue、失败时是否重选、重试时是否避开故障节点”；网络发送本身只是最后一跳，不是主链的全部。*[模式: 路由发现 + 本地决策 + 失败规避 + 发送收口]

## 第一层：没有本地路由视图，主链会先在“根本不知道往哪发”这里失败

发送主链的第一个关键对象不是 Netty 客户端，也不是发送请求包，而是 `TopicPublishInfo`。这正好说明 RocketMQ 的发送入口并不是“手里有 topic，直接开始发网络请求”，而是“先看本地有没有这个 topic 的可发布视图”。

这里要先立住一个最重要的边界：Producer 不是每次发送都实时向 NameServer 问路。更合理的做法，是先看本地是否已经缓存了当前 topic 的发布视图，不够时才去更新。也就是说，NameServer 在这条主链上首先是**路由来源**，而 `TopicPublishInfo` 则是 Producer 发送前真正握在手里的**本地路由视图**。

如果这一层缺席，主链不会晚点失败，而是会在最开始就失败：业务代码虽然知道 topic，但 Producer 根本还不知道有哪些 Broker/Queue 候选，更谈不上后面的“挑一个”“避开坏节点”“发出去”。

所以发送主链的第一道门，不是网络，不是重试，也不是发送模式，而是：**先拿到一张本地可用的路由地图。**

这一步如果没理解清楚，后面特别容易写散。因为一旦你误以为“每次发送都远程问路”，发送主链就会看起来像：send -> NameServer -> Broker。可 RocketMQ 真正的设计不是把 NameServer 放进每次发送的必经远程链路，而是尽量把“看路”变成 Producer 手边的一份可复用视图，再在必要时补一次刷新。

所以 `TopicPublishInfo` 不应该被记成“缓存对象”这种泛泛的名字，而应该被记成：**发送前的本地发布视图**。这是后面一切本地决策的前提。

## 第二层：有了候选集合还不够，主链会继续在“这次到底挑谁”这里卡住

即使 Producer 手里已经有了 `TopicPublishInfo`，这也还只是“知道有哪些可写队列”，并不等于已经决定“这次到底发给谁”。

这一步最容易被低估，因为它看起来很像一个小函数：不就是在一组 MessageQueue 里挑一个吗？可对消息主链来说，这恰恰是把“路由视图”变成“当前发送目的地”的关键动作。

为什么不能把这一步想成简单的静态轮询？因为队列视图只是一个候选集合，真正发送时还要解决另一层问题：**这一次具体挑哪一个目标，才算一次真正可执行的发送决策。**

也就是说，发送主链在这里第一次明显分成了两个层次：

- `TopicPublishInfo` 解决“有哪些候选”；
- `selectOneMessageQueue()` 解决“这次先挑谁”。

如果这第二层缺席，主链不会因为“完全没路由”而失败，而会卡在更细的一步：即使有一堆 Broker/Queue 候选，也不知道当前消息应该投到哪一个目的地。Producer 仍然不能真正开始发送。

这也是为什么后面顺序消息专题必须单独成篇：一旦发送不再是“任意队列都行”，而变成“同一个 key 必须稳定落到同一队列”，那么这一步就不再只是局部实现，而会直接变成业务语义的一部分。

所以在这一篇里，必须先把这条边界钉死：**本地路由视图 != 当前目标决策。** 这两层不分开，发送主链就会塌成一句“拿到路由后发出去”。

## 第三层：只会静态轮询还不够，主链还会在“明知某个 Broker 刚坏还继续打过去”这里失败

即使已经有了候选集合，也已经进入了“这次挑谁”的阶段，RocketMQ 仍然不能就此停止。因为还有一个更现实的失败场景：某个 Broker 刚刚超时、网络抖动，或者已经处在明显不健康状态，这时如果 Producer 还继续按静态 round-robin 轮询过去，会发生什么？

答案很直接：失败不会被吸收，反而会被放大。

Producer 在逻辑上“知道这台 Broker 还在候选集合里”，但从运行时事实看，它现在并不是一个好目的地。如果继续无脑轮询，结果就会是：

- 一次故障变成多次发送超时；
- 重试继续打到刚失败过的节点；
- 本来只是一小段抖动，被扩散成整批消息的发送不稳定。

这正是 `MQFaultStrategy` 必须被视为发送主链组成部分，而不是后置优化细节的原因。它回答的是一个非常主链的问题：**当队列视图还是对的，但某个 Broker 暂时不值得再碰时，Producer 如何在发送前就把它避开。**

注意，这不是“发出去以后失败了再补救”，而是“在发出去之前，先在候选视图里做一次运行时筛选”。所以发送主链在这里又多了一层：不是所有可写队列都等价，静态存在和当前可用之间，还差一层故障规避决策。

如果这一层缺席，发送主链会先在一个很尴尬的地方反复失败：Producer 明明已经知道有路由、也知道有队列，却还是会不断把消息投向一个刚刚超时过的目标。这样消息不是“发不出去”，而是“总能选到不该继续碰的对象”。

所以 `MQFaultStrategy` 的地位，必须和路由发现、队列选择放在一起理解：

- `TopicPublishInfo` 告诉你“有哪些候选”；
- `selectOneMessageQueue()` 告诉你“这次先挑谁”；
- `MQFaultStrategy` 告诉你“哪些候选虽然存在，但此刻不值得碰”。

*关键设计（斜体）：* *Producer 端的发送决策并不是“拿到队列列表后随便挑一个”，而是“候选视图 + 当前选择 + 故障规避”三层叠加；`MQFaultStrategy` 回答的是运行时可用性问题，不是锦上添花的性能优化。*[模式: 候选视图 + 目标选择 + 故障规避]

## 第四层：到了 `sendKernelImpl()`，主链真正回答的才不再是“发给谁”，而是“怎样收口”

只有到了这里，RocketMQ 才真正进入“把字节发出去”这一跳。也就是说，网络发送本身其实是整条主链里相对靠后的动作。

这点特别重要，因为它能打掉另一个常见误区：以为发送主链的核心就是一次 RPC。事实上，真正困难的不是 RPC 本身，而是 RPC 之前的目标决策。到了 `sendKernelImpl()` 和 `MQClientAPIImpl` 这层，Producer 已经基本知道：

- 这条消息发往哪个 Broker；
- 选中了哪个 MessageQueue；
- 当前是否应该避开某个故障节点；
- 如果失败了，重试大概该怎样处理。

所以 `sendKernelImpl()` 更像是“把本地已经完成的路由决策落成网络请求”，而不是独立地主导这条主链。

这也是为什么 `SYNC / ASYNC / ONEWAY` 最适合放在这里讲，而不是一开始就讲。因为这三种模式真正区分的，不是“消息发给谁”，而是“当目标已经决定之后，发送结果怎样收口”：

- `SYNC`：等结果返回再结束这次 send；
- `ASYNC`：把结果通过回调等方式异步收口；
- `ONEWAY`：只负责把消息送出，不等应答。

所以它们不是三条完全独立的发送主链，而是同一条“发给谁”决策已经完成之后的三种结果处理模型。

如果把它们过早前置，读者就很容易误以为 RocketMQ 的发送复杂度主要来自 API 模式差异；实际上，更前面的难点是：Producer 如何在本地完成一轮正确的目标决策。

## 第五层：为什么这篇必须先于 CommitLog——消息还没决定发往哪个 Broker，就根本还没到 Broker 侧世界

到这里，应该已经能看出这篇为什么必须在 CommitLog 之前。

CommitLog 回答的是“消息真正写到哪”，但在那之前，Producer 还必须先把两个问题解决掉：

1. 这条消息到底发往哪个 Broker；
2. 失败时是否应该换目标或重试。

如果这一步没先站稳，后面直接进入 CommitLog，会让读者自然误以为“消息一开始就在 Broker 侧”，而忽略了从 topic 到 Broker/Queue 的发送决策本身就是一条完整主链。

所以 CommitLog 并不是这条链的起点，而是它到达 Broker 宿主之后的下一层问题。先讲路由与发送，后讲落盘，顺序不是任意的，而是由读者理解依赖决定的。

## 收网：Producer 发送主链真正先决定的，不是“怎么发”，而是“发给谁”

如果把整篇压成一句话，RocketMQ Producer 发送主链真正先解决的，不是“怎么把消息发到网络里”，而是“当前这条消息到底应该发往哪个 Broker / Queue，以及失败时怎样避开坏目标”。

```text
业务 send(topic, msg)
  → 本地是否已有 TopicPublishInfo 路由视图
    → 不够时才去更新 NameServer 路由
      → TopicPublishInfo 持有可写队列视图
        → selectOneMessageQueue() + MQFaultStrategy
          → 选出当前 Broker / Queue
            → sendKernelImpl()
              → MQClientAPIImpl 远程调用 Broker
                → SYNC / ASYNC / ONEWAY 三种收口方式
```

到这里，主线只发生了三件事。

第一，Producer 手里只有 topic，不知道最终目的地，所以发送主链必须先建立一份本地路由视图，而不是上来就做 RPC。

第二，拿到 `TopicPublishInfo` 还不等于拿到目的地；真正的目标决策还要经过队列选择和故障规避。

第三，`sendKernelImpl()` / `MQClientAPIImpl` 只是把已经做完的本地决策真正变成网络发送，而 `SYNC / ASYNC / ONEWAY` 则只是这次发送的三种结果处理模型，不是三条独立主链。

**本篇的一句话困惑**：Producer send 以后，到底是谁决定把消息发往哪个 Broker？

**本篇的一句话顿悟**：不是一次简单 RPC，也不是 NameServer 每次替它远程裁决，而是 Producer 先靠 `TopicPublishInfo` 建立本地路由视图，再通过 `selectOneMessageQueue()` 和 `MQFaultStrategy` 在本地完成队列选择与故障规避，最后才由 `sendKernelImpl()` / `MQClientAPIImpl` 把这次决策发给 Broker。
