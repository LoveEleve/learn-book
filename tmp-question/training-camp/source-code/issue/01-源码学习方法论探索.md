## 一、问题定义

32 个仓库，数百万行代码。如果按"读完一个仓库再读下一个"的方式学，三年也学不完。如果按"只挑 microsphere 用到的部分学"，会变成功利主义学习——知识点碎片化，没有体系。

**核心矛盾**：全面 vs 深入、广度 vs 效率、系统性 vs 可执行性。

## 三、读源码的三个层次（框架性思考）

### 第一层：读代码
知道这个类有几个方法，每个方法做了什么。产出的文章就是"ClassLoader 有三个方法：a、b、c"。

**问题**：这是"源码翻译"——看起来代码引用准确、行号精确，但读者学不到任何可迁移的东西。

### 第二层：读设计
理解这个设计解决了什么问题，为什么用这个模式而不是另一个模式。
```
例：Spring 为什么用 BeanPostProcessor 而不是回调接口？
→ 因为后置处理器可以批量作用于所有 Bean，而回调接口要求每个 Bean 自己实现，侵入性更强。
```

### 第三层：读权衡
所有设计都是取舍。读到这一层才能真正理解"这个技术为什么长成现在这样"。
```
例：Spring 选择了高灵活性的代价是启动慢。
    Kafka 选择了高吞吐的代价是延迟抖动。
    Nacos 选择了 AP+CP 双模式的代价是复杂度翻倍。
```

**关键洞察**：第三层的上下文不在源码注释里，在源码之外——mailing list、JIRA issue、design doc、作者博客、git 提交历史。你在一头扎进单个仓库的几千个文件时，根本看不见"权衡"——因为这个设计的替代方案、被否决的原因、曾经踩过的坑，全都不在源码里。

## 四、第一性原理推导

> **核心洞察**：之前的方案（A/B/C/D）都在回答"先学什么"——这是一个内容排序问题。而第一性原理告诉你，真正的问题是"同一份源码需要被读几遍，每遍有什么不同的目的和深度"——这是一个认知层次问题。内容排序不重要，认知层级的递进才重要。

### 4.1 拆解到最基本元素

**源码 = 设计决策 × 实现细节**

实现细节是透明的——代码就在那里，grep 就能找到。但设计决策是不透明的——"为什么选方案 A 而不是方案 B"不在代码里。

所以真正的挑战是：**如何从透明的实现中，反向推导出不透明的设计决策？**

这不是一个"找资料"的问题，而是一个"提问能力"的问题。你面对一段代码时，能问出多深的问题，决定了你能学到多深。

### 4.2 "鸡生蛋还是蛋生鸡"的死锁

"提问能力"从哪来？你需要先有一些基础概念才能提出好问题——不知道 BeanPostProcessor 的话，永远看不懂 Spring 的扩展机制。但又需要先读代码才能建立基础概念。这是一个死锁。

**但这个死锁是假的**。因为不需要一次性理解所有东西——允许"暂时不理解但先记住"，在后续的学习中交叉验证。

### 4.3 自洽的三层循环

```
第一遍（扫轮廓）：建立"这是什么"的全局视图
    ↓  产出：模块职责地图（不要求深入理解，允许"标记不理解但重要"）
第二遍（盯关键点）：用"提问→提出假设→验证假设"循环逐个攻克
    ↓  产出：5-8 个独立的问题闭环（每个都是可独立阅读的小文章）
第三遍（收尾）：对核心模块产出深度文章，融合外部上下文
    ↓  产出：有观点的深度文章（含设计演变史）
```

**这三遍都在源码内部完成——不依赖外部素材。**

外部素材（mailing list / issue / blog）在前两遍都不需要——它们是第三遍的"加分项"，有则锦上添花，没有也不影响前两步。

### 4.4 三层循环 vs 已有方案的对比

| 维度 | 主题驱动(V1) | 层次递进(V2) | A-决策链 | B-包结构 | C-问题驱动 | **三层循环** |
|---|---|---|---|---|---|---|
| 完整性 | 碎片化 | 过于庞大 | 高 | 中 | 碎片化 | **每遍不同粒度，各自完整** |
| 可执行 | 容易但功利 | 容易迷失 | 需要调研 | 较容易 | 容易 | **每遍有明确终点** |
| 深度 | 浅 | 深 | 最深 | 中 | 中 | **深度逐遍递增** |
| 依赖外部素材 | 不依赖 | 不依赖 | 必须依赖 | 不依赖 | 不依赖 | **不依赖（第三遍可选）** |
| 死锁问题 | 无 | 有 | 无 | 有 | 无 | **解决：允许暂时不理解** |

### 4.5 三层循环的具体节奏（以 spring-core 为例）

**第一遍（扫轮廓）**：
- 打开 728 个文件的包结构
- 花 30 分钟画出"spring-core 职责地图"——core/io/type/annotation/env/aot 各管什么，之间怎么调用
- 标记 5-8 个"直觉上重要但暂时不理解"的点

**第二遍（盯关键点）**：
- 挑出一个标记点，做"提问→验证"循环
- 例："Spring 的 Ordered 接口为什么是用 int 而不是 enum 来实现优先级？"
- 这不需要外部资料，答案在源码里，且会影响你对 spring-beans/spring-context 中大量设计决策的理解
- 每个关键点独立闭环，可以任意顺序进行

**第三遍（收尾）**：
- 如果 spring-core 有 25 年的设计演变历史（确实有），可以深挖一个决策链产出深度文章
- 如果没有，第二遍的理解已经足够支撑继续读 spring-beans

### 4.6 三层循环 + 方案 D 的融合

方案 D（混合方案）可以和三层循环融合：

```
第一遍扫轮廓  → 用方案 B（包结构建骨架）——快速建立全局视图
第二遍盯关键点 → 用方案 C（问题驱动深入）——在关键环节做深度追踪
第三遍收尾    → 用方案 A（决策链学）——对重点模块产出深度文章
```

三层循环提供认知层级的递进框架（什么时候做什么），方案 A/B/C 提供具体的执行手段（怎么做）。

### 4.7 未解决的开放问题

本推导还需要和用户确认的：

1. **每一遍的"完成标准"是什么？** 扫轮廓到什么程度算"轮廓建立"了？
2. **三层循环是每个仓库独立跑，还是可以在不同仓库之间交叉？** 比如第三遍的深度文章，可能需要跨仓库的上下文（spring-core + spring-beans 的设计演变关系）
3. **MCP 索引在第一遍和第二遍中如何应用？** 第一遍用 search_graph 查调用关系辅助建骨架？第二遍用 trace_path 追踪数据流辅助验证假设？

## 五、待讨论的替代方案（历史记录）

### 方案 A：按决策链学（"故事驱动"）

**核心思路**：追踪一个具体的设计决策的完整演变史，在追踪过程中自然读完涉及的所有核心代码。

**例子**：
- "Netty 5 被放弃后又被重启，中间发生了什么？"——这个故事的线索不在 Netty 源码里，在 Netty 团队的博客、GitHub issue 讨论、邮件列表里。追踪完这个故事，你自然理解了 Netty 的线程模型为什么是现在这样、异步 I/O 框架在设计上的 3 个核心坑。
- "Spring 的 Bean 生命周期到底经历了多少次重构？"——从 1.0 到 6.2，每次重构解决了什么问题、引入了什么新问题。追踪完这个决策链，你自然读完了 spring-beans 的核心代码。

**优点**：
1. 产出的不是"又一个 XXX 源码分析系列"，而是带观点的、有原创判断的深度文章
2. 面试时不需要背八股文——当你讲得出"Netty 5 被放弃的 3 个核心原因"时，面试官知道你确实读过源码
3. 可迁移到任何框架

**难点**：
1. 决策链的起点需要大量背景调研——不是源码工具能帮你定位的
2. 不是每个仓库都有丰富的"决策故事"
3. 对基础有要求——如果完全不了解 Bean 生命周期，看"重构历程"也看不懂

### 方案 B：按代码结构学（"包结构驱动"）

**核心思路**：每个模块先探索顶层包结构，理解模块的"骨架"——它被分解成了哪些子问题、每部分的职责边界、各部分之间的调用关系，然后才深入每个包的实现细节。

**例子（spring-core）**：
```
spring-core 的包结构就是一个分层设计：
├── core/        ← 底层的通用抽象：Ordered、Priority、Converter
├── io/          ← 资源加载：Resource、InputStreamSource
├── type/        ← 类型系统：TypeDescriptor、TypeConverter
├── annotation/  ← 注解抽象：AnnotationAttributes、MergedAnnotations
├── env/         ← 环境抽象：PropertySource、Environment
└── aot/         ← AOT 编译支持：RuntimeHints、ReflectionHints
```

先理解了"这些包组成一个骨架"，再去看每个包的具体实现，就有了"这张图应该在哪个位置"的全局感。

**优点**：
1. 比"按文件逐读"效率高得多——先建骨架，再填充细节
2. 每个模块都有一个清晰的"入口地图"
3. 不容易迷失在细节里

**缺点**：
1. 包结构只能告诉你"这个模块包含了什么"，不能告诉你"为什么会这样设计"
2. 建骨架需要你已经有了一定的理解基础——纯新手看包名也看不懂"这个包是干什么的"

### 方案 C：按问题驱动学（"场景驱动"）

**核心思路**：从一个具体的场景/问题出发，追踪 Spring/中间件是如何解决这个问题的。

**例子**：
- "一个 HTTP 请求到达 Spring Boot 应用后，经历了什么？"——追踪 DispatcherServlet → HandlerMapping → HandlerAdapter → ViewResolver，自然读完 spring-webmvc。
- "Nacos 3.0 为什么从 HTTP 切到 gRPC？带来什么问题？"——追踪 gRPC 通信层的实现 + 连接管理 + 健康检查。

**优点**：
1. 最符合人类的认知方式——带着问题学，不是"先全部学完再验证"
2. 每个问题是一个独立的学习单元，可以独立完成

**缺点**：
1. 问题驱动容易"碎片化"——学到的知识点是散落的，没有体系
2. 需要一套"问题体系"来保证覆盖的完整性

### 方案 D：混合方案

把 A/B/C 组合使用：
1. **包结构建骨架**（方案 B）——快速建立模块的全局视图
2. **问题驱动深入**（方案 C）——在关键环节用问题驱动做深度追踪
3. **决策链收尾**（方案 A）——对重点模块，追踪设计演变史，产出有观点的深度文章

这样既有系统性（B 保证覆盖完整），又有深度（C 保证理解透彻），又有可迁移性（A 保证学到设计层面的东西）。

## 五、核心开放问题

1. **产出物的标准是什么？**——是"32 个仓库各写 N 篇文章"还是"产出多少篇有独立价值的深度文章"？这是两个完全不同的目标，会引导出完全不同的学习方法。

2. **"学完"的定义是什么？**——是"读完所有文件"还是"理解核心机制"还是"能独立设计类似的框架"？不同的定义对应不同的深度要求。

3. **MCP 索引 + AI 工具应该扮演什么角色？**——32 个仓库都有 MCP 索引，`search_graph` 可以查调用关系，`trace_path` 可以追踪数据流。这些工具是"辅助定位"还是"替代阅读"？

4. **起点在哪？**——是从 spring-core 开始（传统路线），还是从 microsphere-spring 开始（逆向学习），还是从某个具体的决策链开始（故事驱动）？

5. **节奏如何？**——是一个模块一个模块慢慢来，还是并行探索多模块寻找连接点？

## 六、用户已有的学习风格参考

从之前的项目中可以提炼出用户偏好的学习模式：

- **tomcat 系列**：按模块边界组织（1 篇 = 1 个知识领域），每篇不限字数，讲透为止。源码行号精确引用，面试点单独成块，4 轮 review 保证质量。
- **microsphere 分析**：D→C→A→B 滚动推进（读一块 → 写一块 → 测一块 → 收敛一块），不是先全部写完再验证。
- **拒绝过的事情**：功利主义学习（"只学 microsphere 用到的"被否决）、批量生成（"一次性搞定"被多次否决）、限制行数（"不要关注行数这种没有意义的东西"）。
