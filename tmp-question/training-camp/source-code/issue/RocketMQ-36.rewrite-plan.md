# RocketMQ-36 重写规划

> 题目：TieredStore 为什么不是“把冷数据丢对象存储”——存储计算分离主链
> 状态：5.x 能力篇。对应 `hz` 中 RocketMQ 5.x 分层存储 / 存储计算分离主题，承接 RocketMQ-28 存储总览与 RocketMQ-35 可观测性主线。

## 1. 读者困惑
- TieredStore 是不是只是把冷数据搬到远端存储？
- 为什么它会被说成“存储计算分离”的新思路？
- 它和 CommitLog/ConsumeQueue 的原有主链是什么关系？
- 它改变的是存储介质，还是整个读取/恢复/部署边界？

## 2. 一句话顿悟
**RocketMQ 5.x 的 TieredStore 不是简单把旧数据迁走，而是把“热路径上的本地存储”与“冷路径上的远端分层存储”显式拆成两层，使 Broker 不再必须把所有历史数据都长期绑定在本地磁盘上。它改变的不只是介质位置，而是存储与访问边界的组织方式。**

## 3. 失败方案推演
- 把 TieredStore 误解成对象存储备份
- 只看数据搬迁，不看读取路径和宿主边界变化
- 把它当成本地 CommitLog 的无损替代

## 4. 章节问题
- TieredStore 相比传统本地存储到底多了哪一层？
- 热/冷数据边界在 RocketMQ 里怎样体现？
- 它对 Broker 本地存储职责有什么重划？
- 它为什么属于“存储计算分离”而不是普通归档？

## 5. 至少要排除的误解
- TieredStore = 冷数据备份
- Broker 不再需要本地存储
- 远端分层存储只是运维策略，不影响主链理解
- TieredStore 与可观测性、恢复路径无关
