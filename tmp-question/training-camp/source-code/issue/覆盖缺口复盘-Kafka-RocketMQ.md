# 覆盖缺口复盘：为什么会出现 Kafka / RocketMQ 编号与主链缺口

## 1. 这次暴露的不是“少写两篇”，而是 coverage audit 失效

Kafka 与 RocketMQ 两轮都暴露出过类似问题：

- Kafka 一开始不是严格按最终总图顺序推进，而是沿“当前最值得深挖的点”不断插出新篇；
- RocketMQ 更明显，直接出现了 `RocketMQ-16`、`RocketMQ-17` 缺失，而后续篇号已经推进到 `RocketMQ-26`；
- 这说明问题不在单篇写作能力，而在 **编号推进、覆盖映射、主链收口** 三件事没有被绑定成一个硬流程。

也就是说，真正失效的是：**在写下一篇之前，没有先确认全局 coverage map 与编号连续性。**

## 2. Kafka 为什么也会“少”

Kafka 和 RocketMQ 的表象不完全一样，但根因相同。

### 2.1 Kafka 的“少”，更像先补深再补全

Kafka 没有像 RocketMQ 那样长期裸露 `16/17` 这种空号，但它同样出现过“主题覆盖先局部最优、后全局补齐”的问题：

- 最初先完成的是 12 域骨架；
- 后面不断补 `13~38` 的拆深篇时，推进方式是“哪个主题最值得拆，就先写哪个”；
- 再后面为了补 zsxq 覆盖，又快速增加了 `39~50` 的启动、Assignor、MetadataCache、CheckPoint、容量评估、消息排查、总索引等篇；
- 这导致 Kafka 曾经出现过一种“**总数够了，但不是先有完整 coverage map 再顺序推进**”的状态。

换句话说，Kafka 的问题不是“编号真缺了很多”，而是：

> **先按局部价值不断加篇，后按总图回补 coverage**。

这会带来两个后果：

1. 某些篇虽然有编号，但没有及时经过 deep review；
2. 某些主题虽然被提到过，但直到后期才补成独立篇。

### 2.2 RocketMQ 的“少”，是编号断层更直接

RocketMQ 比 Kafka 更明显，因为：

- 它一开始就不是“严格骨架域”驱动，而是“主链 + 若干专题”混合推进；
- 外部材料还分成 `hz` 原理专题 与 `cqfy` 手写实现 两套体系；
- 结果就是：在没有先做统一 coverage map 的情况下，篇号先往后走，导致 `RocketMQ-16/17` 直接缺位。

所以 Kafka 和 RocketMQ 的共同根因相同，但表现不同：

- **Kafka**：更像 coverage 顺序错位，先深挖、后补全；
- **RocketMQ**：更像编号连续性直接失守，先推进、后发现缺口。

## 3. 根因拆开看，其实是 4 个流程没绑死

### 3.1 没有“开新篇前先查 coverage map”

应该先问：

- 这个主题属于骨架主链、拆深篇还是桥接篇？
- 它在总图里的前置篇、后继篇是谁？
- 它是不是在补骨架缺口，还是在做局部深挖？

如果这些没先回答，就容易直接去写“当前最顺手的一篇”。

### 3.2 没有“编号连续性检查”闸门

应该在创建 `N+1` 前自动检查：

- `1..N` 是否连续；
- 有没有空号；
- 有没有只有 `rewrite-plan` 没有正文；
- 有没有正文有了但没元数据四节。

只要这个闸门不加，编号问题迟早会发生。

### 3.3 “被别篇提过”被误当成“已经覆盖”

这是最常见认知错觉。

比如：

- Kafka 的某些主题在总览篇里提过，但并不等于已经成为独立可复用主链篇；
- RocketMQ 的 NameServer/Broker 注册问题在启动、路由缓存等篇里碰到过，但不等于 NameServer 体系已完整覆盖。

所以必须区分：

- **被提到**
- **被解释**
- **被系统覆盖成独立篇**

这三件事完全不同。

### 3.4 每轮结束后没做“覆盖审计”

一次迭代完成后，应该强制做 audit：

- 编号是否连续；
- 每篇是否有 `rewrite-plan`；
- 每篇是否有元数据四节；
- 当前 coverage map 上还有没有骨架缺口；
- 拆深篇和桥接篇有没有反客为主，超过主链推进速度。

如果每轮不审，问题会越滚越晚暴露。

## 4. 以后要固定成 6 条硬规则

### 规则 1：任何系列，先画 coverage map，再允许写正文

最少分三层：

- 骨架主链
- 拆深篇
- 桥接篇

如果连这三层都没分，就不准开写下一篇。

### 规则 2：骨架没闭合前，拆深篇数量不能失控

允许先深挖，但要设上限。

建议硬规则：

> 骨架篇未闭合前，新增拆深篇不得连续超过 3 篇。

否则很容易进入“局部越写越深，全局越来越乱”。

### 规则 3：开新编号前，必须跑编号连续性检查

至少检查：

- 缺号
- 只有 plan 没正文
- 有正文没 plan
- 有正文没元数据四节

### 规则 4：主题“碰到过”不算覆盖，必须有独立篇才算

只有满足以下条件才算覆盖：

- 有独立篇名；
- 有独立 `rewrite-plan`；
- 有正文和元数据四节；
- 在总索引中能单独定位。

### 规则 5：桥接篇不能替代骨架篇

像“消息排查”“容量评估”“可靠性总串联”这种桥接篇，必须建立在对应骨架和拆深篇已经存在的前提下。

### 规则 6：每完成一轮，必须产出 coverage audit 结论

结论最少包含：

- 已完成骨架篇列表
- 已完成拆深篇列表
- 已完成桥接篇列表
- 缺口列表
- 建议下一批篇目顺序

## 5. 这次的直接修正动作

针对 RocketMQ / Kafka，后续推进必须改成：

1. 先对现有篇目做 coverage map；
2. 先补骨架缺口与编号断层；
3. 再继续拆深篇；
4. 最后再补桥接篇；
5. 每轮结束做 audit。

## 6. 一句话复盘

这次的问题不是“某两篇忘了写”，而是：

> **没有把 coverage map、编号连续性、骨架闭合、桥接边界 这四件事绑定成硬流程。**

Kafka 的问题表现为“先深挖、后补全”，RocketMQ 的问题表现为“编号断层更明显”；但本质上，都是 coverage audit 没有前置。
