# RocketMQ-12 重写规划

> 题目：消息过滤为什么不只是“消费者收到以后自己丢掉”
> 状态：本轮按单篇闭环执行；保留该 plan 作为后续二轮 consistency pass 工件
> 目标：把这一篇写成“RocketMQ 为什么要把过滤前移到 Broker 侧，而不是把所有消息都先送到 Consumer 再由业务丢弃”的横切专题，而不是 Tag/SQL92 语法说明文

## 1. 读者困惑

- 为什么消息过滤不能简单理解成“Consumer 收到以后自己 if 判断一下就丢掉”？
- Tag 过滤和 SQL92 过滤为什么不只是语法差别，而是执行位置和成本差别？
- 过滤为什么属于主链上的横切能力，而不是消费侧附属功能？
- `SelectorParser`、`SqlFilter`、`FilterFactory` 这些类到底在补哪一层缺口？

## 2. 一句话顿悟

**RocketMQ 把过滤放进 Broker 主链，不是为了做语法炫技，而是为了在消息真正离开 Broker 之前先剪掉不该下发给当前 Consumer 的数据；Tag/SQL92 的差异不只在表达能力，还在执行代价、匹配粒度和 Broker 侧过滤能力的边界。**

## 3. 总图

```text
Consumer 提交订阅表达式
  → Broker 解析过滤类型(Tag / SQL92)
    → 过滤逻辑挂在消息下发主链上
      → 能命中的消息才继续进入拉取/消费推进主链
        → 不能命中的消息留在 Broker 侧，不进入 Consumer 本地责任面
```

## 4. 关键边界

- 本篇只讲“为什么过滤要前移到 Broker 侧”及其主链意义，不展开全部消费组协议。
- 不把 Tag/SQL92 写成语法手册，而是围绕执行位置、能力和成本来讲。
- FilterServer/表达式解析只作为 Broker 侧过滤链的组成部分，不抢主链篇幅。
- 过滤在本篇是横切能力：作用在消息下发前，而不是消息消费后。

## 5. 本轮重写主线

1. 用“为什么不能先把消息全发给 Consumer 再由业务自己丢掉”开场。
2. 否定：过滤只是业务 if、Tag/SQL92 只是语法复杂度区别、Broker 不需要知道过滤条件。
3. 先讲过滤若后置到 Consumer，会在网络、堆积、本地责任面哪里先出问题。
4. 再讲 Broker 侧为什么必须提前知道订阅表达式。
5. 再讲 Tag/SQL92 的能力/代价分层。
6. 收网时明确：过滤是消费主链上的前置剪枝层，而不是后置清洗层。
