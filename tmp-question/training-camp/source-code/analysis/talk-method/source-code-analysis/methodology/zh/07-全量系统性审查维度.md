# 全量系统性审查维度

> 角色：AI 自约束操作规范。全部域的 Per-Article Outline 完成后必读。
> 先修：01-06 全部方法论文档
> 输入：全部域的 Per-Article Outline 文件（36-38 篇）
> 阅读顺序：01 → 02 → ... → 06 → 07（本文）。大纲阶段最终审查。

## 核心原则

**Per-domain 深审收敛于准确性，全量系统性审查收敛于完整性。** 单域审查在每篇内部验证"写的对吗？"，全量审查在跨域/跨卷层面验证"整体自洽吗？"。两个维度不可替代——单域全绿的整体可能在桥接/依赖/覆盖上支离破碎。

全量审查必须使用 **不同维度轮换**，每轮聚焦一个不可约简的检查面。同一维度连续多轮零发现 = 该维度审查收敛。

---

## 1. 五维度审查清单

执行全量审查时，逐维度使用本清单。每轮报告：维度名、发现数、修复数、是否收敛。

### 维度 1：叙事桥一致性 + 结构完整性

**检查**：
- 每域的 IN 桥正确承接前一域的 OUT 桥
- 每域的 OUT 桥指向正确的下一域（不跳域、不指向已讲域）
- 卷边界桥（前一卷末域 → 后一卷首域）有显式桥接
- 每域包含五个必需结构元素：概念依赖/先修、设计权衡、核心悬念、预估、叙事计划

**检测命令**：
```bash
# 提取全部域的桥
grep "→ 从\|→ 下一\|→ 卷" outlines/vol-0*/*.md

# 检查结构元素存在
grep -c "核心悬念\|设计权衡\|概念依赖\|预估\|叙事计划" <file>
```

### 维度 2：源码锚点密度

**检查**：每个大纲中精确源码锚点（`file:line` 格式）的数量。锚点密度直接衡量"这个大纲是基于源码写的还是凭记忆写的"。

- 🔴A 域：≥8 个锚点
- 🟡B 域：≥4 个锚点
- 🟡C 域：≥2 个锚点

**注意**：裸行号（如 `line 630` 缺文件名）不算锚点——必须包含文件名。

**检测命令**：
```bash
grep -c '\.cpp:\|\.hpp:\|\.java:' <file>
```

### 维度 3：前向引用 + 依赖正确性

**检查**：每域的概念依赖声明（`依赖：X + Y`）指向的域是否已在拓扑排序中讲过。

- 依赖的域必须序号 < 当前域
- 正文中"提及"未来域可接受；"声明为依赖"不可接受
- 跨越卷边界时额外检查：域 A 在 vol-03，不能声明依赖 vol-04 的域

**检测命令**：
```bash
# 提取全部域依赖声明
grep "依赖：\|先修：" outlines/vol-0*/*.md

# 交叉验证：每个依赖的拓扑序号是否 < 当前域序号
```

### 维度 4：线程 / 横切关注点覆盖矩阵

**检查**：选一个横切关注点（JVM 内部线程 / GC 屏障 / safepoint 检查点），追踪它在所有域中的出现。构建覆盖矩阵——哪些域提到了、哪些域应该提但没提。

- 线程覆盖例：Signal Dispatcher Thread 出现 0 次 → 缺漏
- 每个横切关注点覆盖 ≥1 个域

**流程**：
1. 选横切关注点（线程类型 / GC 屏障传播 / 信号处理链）
2. grep 全量大纲统计出现次数
3. 对照源码头文件确认"有哪些线程/屏障/信号处理点"
4. 构建"应有-实有"缺口表

### 维度 5：负面空间 + 开篇质量

**检查**：

**负面空间**: 对对比型域（域有明确的"不做某优化"的设计边界，如 C1 vs C2、G1 vs CMS），检查是否有"不做的事"的显式声明。表格式最佳——优化名 / 不做原因 / 对比域是否做。

**开篇质量**: 每域的"开篇场景"是否从一个具体的、读者可共鸣的情境出发——不是一个概念总结。好例："`System.gc()` 不会直接调 G1 的收集代码——它先经过 `CollectedHeap`"。差例："JVM 的 GC 框架很重要"。

**检测**：
```bash
# 负面空间检测
grep -c "不做\|故意不\|选择不做\|跳过" <file>

# 开篇质量检测（每域至少 3 个具体的场景化名词/动词）
head -20 <file> | grep -c "pthread\|jcmd\|jconsole\|OOM\|Spring\|Lambda\|线上"
```

## 2. 执行顺序与收敛判断

```
R1: 维度1 (桥+结构)       → 报告发现+修复
R2: 维度2 (锚点密度)       → 报告发现+修复  ← NEW
R3: 维度3 (前向引用)       → 报告发现+修复
R4: 维度4 (横切关注点)     → 报告发现+修复  ← NEW
R5: 维度5 (负面+开篇)      → 报告发现+修复  ← NEW

收敛信号：连续两轮零新发现，且使用不同维度 = 审查穷尽。
```

**禁止**：R5 零发现后再执行 R6（同维度）。维度穷尽后进入写作阶段——Pass 2/3。

## 3. 反模式

### 1. 用同一维度反复审查

```
错误：R1 桥 → 修完后 → R2 再查桥 → 零发现"
正确：R1 桥 → R2 锚点密度 → R3 前向引用 → 每轮新维度
```

### 2. 零发现 = "没细查"

```
错误：零发现后下意识想"应该还有问题，再查一轮"
正确：零发现 + 新维度 = 该维度确实是干净的。不是偷懒。
```

### 3. 标记缺口为"可接受"而不修复

```
错误：vol-03 OUT桥缺6个 → 标记 "方法论建立前完成，可接受"
正确：直接修复。1 行桥的修复成本极低，完整性收益高。
```

### 4. 横切关注点选得太窄

```
错误：只查 JVM 内部线程 → 10 条线程 × 36 领域 = 360 格太小 → 缺 1 格不说明问题
正确：线程覆盖率用 "线程 → 覆盖域" 稀疏矩阵看整体模式（非逐格计数）
```

### 5. 格式审查通过 ≠ 内容合格

```
错误：R1-R9 全部是格式维度（桥/结构/锚点/前向引用）→ 全部通过 → 宣称"完成"
正确：至少一轮切换到内容深度——用"反写测试"（只读大纲能否写文章）或"全视角提问"（7 身份追问）
```

### 6. 巨型域用普通拆分规则

```
错误：G1 GC 45692行 → Pre-Pass 3 说"强制拆 3-4 篇" → 仍是走马观花
正确：源码 >30000行 → 巨型域 → 一域一卷 → 拆 8-10 篇独立大纲
```

### 7. 大纲完成不执行全视角提问验证

```
错误：大纲深审通过→直接宣称完成→用户说"提问文档呢？"→才补做
正确：每个域大纲完成后自动执行 01-三层循环框架 §大纲完备性验证 → 产出提问文档
```

*全量审查完成后，不应再有新的审查轮——应直接进入大纲验收 → Pass 2/3 写作。*
