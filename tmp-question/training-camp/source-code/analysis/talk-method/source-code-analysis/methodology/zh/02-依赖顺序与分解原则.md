# 依赖顺序与分解原则

> 角色：AI 自约束操作规范。执行前必读。
> 先修：`01-三层循环框架.md`
> 阅读顺序：01 → 02（本文）→ 03 → 04 → 05 → 06。完整执行顺序见 01。

## 原则一：依赖顺序

### 1.1 基本规则

一个域几乎总是依赖多个其他域。**默认假设多依赖**。

```
反面：A 中提到 "B 将在后面讲解" → 读者不理解 B，无法理解 A
正面：所有依赖先分析透 → A 只引用已知内容
```

### 1.2 构建依赖图（强制，第一个域分析前完成）

对仓库中每个域，列出它依赖的**所有**域。格式：

```
Netty N-3 Pipeline 的依赖：
  依赖: N-2 (EventLoop — HeadContext 注册在 EventLoop 上)
        N-1 (ByteBuf — 数据通过 Pipeline 以 ByteBuf 形式流动)
  不依赖: N-4 (方向相反)
```

仓库中**所有**域都完成此列表后，才能开始分析。任何域依赖列表为【待补充】的，阻塞——不得开始。

**预分析轻扫**：构建依赖图前，对所有域做轻量扫描——`find src/main/java -type d` 看包结构，`grep '^public (class|interface)'` 看核心类声明，`grep -E '^import|^@'` 看顶层依赖。**这不是完整的第一遍**——不画继承树，不标记问题。只获取够判断域间依赖关系的信息。

### 1.3 拓扑排序

构建完依赖图后，按拓扑排序——所有被依赖的域必须排在被依赖它的域**之前**。零依赖的域排在最前面。

### 1.4 循环依赖

**检测**：如果 A 依赖 B 且 B 依赖 A，拓扑排序失败。

**策略（三轮化解）**：

1. **双方都做第零遍（上下文）+ 简略第一遍（仅继承树 + 元素分解）——跳过标记问题和测试文件阅读。** 建立双方的基本概念——够命名它们之间的接口边界。
2. **然后双方一起做第二遍（盯关键点）**——在同一轮深度分析中同时对两个域 grep 和读源码，交叉验证接口约定、共享假设和交互点
3. **然后各自回归判定方案（参考 04），如有 Pass 3 则完成**

原理：当概念互相依赖时，不可能完全学完一个再学另一个。先对双方做 Pass 0+简略 Pass 1，再交叉深入。

**循环依赖的常见例子**：
- Spring：`BeanPostProcessor` ↔ `BeanFactory`（BPP 修改 BF 创建的 Bean，BF 本身通过 BPP 创建）
- Netty：`Channel` ↔ `ChannelPipeline`（Channel 持有 Pipeline 引用，Pipeline 持有 Channel 引用）
- Kafka：`Producer` ↔ `RecordAccumulator` ↔ `Sender`（通过后台线程 + 批量队列形成循环）

## 原则二：组合/分解

**规则**：任何复杂的源码 = 基本代码的组合。分析策略是从分解到组合。

```
不要：直接分析 "Pipeline 的完整请求链路"
      → 迷失在 HeadContext → Handler → TailContext 复杂度中

应该：先回答 "Pipeline 由哪几个基本元素组成？"
      ① 双向链表（head → handler1 → handler2 → tail）
      ② 责任链模式（fireChannelRead → next.invoke()）
      ③ 线程安全（EventLoop 单线程保证）
      
      然后：三者如何组合 = Pipeline 的完整链路
```

**嵌入第一遍**：扫轮廓的产出中必须包含此问题：

> **"这个模块由哪几个基本元素组成？"**

这迫使从"庞然大物"变成"几个零件"，每个零件独立深入。

## 每个仓库分析前的检查清单

- [ ] 完整依赖图已构建（所有域映射完毕，无【待补充】）
- [ ] 循环依赖已识别并标记
- [ ] 循环依赖的三轮化解策略已记录
- [ ] 拓扑排序已验证（没有依赖出现在被依赖之后）
- [ ] 已确认：第一遍产出模板包含"基本元素分解"章节（见 01 原则二引用）
- [ ] 跨域引用策略已了解（见 06 了解引用格式和发现处理）
- [ ] Hub 候选已识别：被 ≥10 个其他域依赖的域（标记 Hub 升级，见 04 §Hub 升级）
