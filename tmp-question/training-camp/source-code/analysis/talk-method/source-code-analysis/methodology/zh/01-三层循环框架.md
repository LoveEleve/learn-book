# 三层循环框架

> 角色：AI 自约束操作规范。执行前必读。
> 先修：`progress/源码分析执行计划.md`
> 阅读顺序：01（本文）→ 02 → 03 → 04 → 05 → 06。执行：先走 02 的预分析检查单 → 每个域用 04 选定方案 → 按 01 的 Pass 0-3 执行 → 用 03 判断深度 → 用 05 分配工具 → 用 06 处理跨域引用。

## 操作模式：审查 vs 写作

本方法论支持两种不同操作模式。选错模式是根本性错误。

### 模式A：审查存量文章

**输入**：现有章节文本。**目标**：发现并修复真实内容问题——不准确的声明、深度不足、过时引用。

| Pass | 做什么 |
|------|--------|
| Pass 1 | 将现有章节分解为概念块。对具体声明的准确性、完整性或深度标出 ≥5 个问题。 |
| Pass 2 | **grep 验证关键声明**。按 methodology/03 测试深度：每条解释是否承载设计决策，还是只有"是什么"没有"为什么"？ |
| Pass 3 | **修复 Pass 2 发现的真实内容问题**——不准确的声明、缺失的深度、断裂的交叉引用。产出：改进后的现有章节。 |

**审查模式反模式**：
- 不做 Pass 2 源码验证，只加 前置依赖 + 设计权衡 节 → 格式审计，不是内容审查
- 从零重写整章 → 那是写作模式，不是审查模式
- 只做结构扫描后宣称"没问题" → 每篇都有深度缺口；没找到说明没找

### 模式B：写新文章

**输入**：仅有源码（无现有文本）。**目标**：按方法论结构创作原始章节。

| Pass | 做什么 |
|------|--------|
| Pass 0 | 读设计文档、issue、PR、release notes——碰源码前先建立上下文。 |
| Pass 1 | 扫描包结构、核心类声明、测试文件。建继承/调用图。标出 ≥5 个问题。 |
| Pass 2 | 每个问题深挖：假设 → grep 追踪 → 验证 → 结论。每个问题成一个循环笔记文件。 |
| Pass 3 | 将循环笔记合成文章：问题先行、依赖排序、概念递进、自然叙事。设计权衡融入文中，非附录。全文源码验证。 |

**写作模式反模式**：
- 在解释问题前先贴"0. 源码清单" → 代码先行，不是问题先行
- 使用 AI 模板格式（编号 § 节、✅❌ 符号、每段末尾"→ 细节：[链接]"）→ 自然叙事是目标

### 模式选择规则

任务是"REVIEW chXX" → 模式A。任务是"从零写 chXX" → 模式B。绝不混淆。

## 基本约束

1. **禁止编造**：任何函数名、常量值、数据结构描述，必须经过 `grep` 源码验证后才能写入产出物。不确定的东西标记 `[待验证]`，不得猜测。
2. **禁止跳步**：必须先完成第一遍的全部产出，才能进入第二遍。未完成第二遍至少 3 个闭环，不得进入第三遍（"闭环"定义见第二遍完成检查单）。
3. **禁止"后面讲"**：如果本域依赖其他域的类/接口，被依赖的必须先讲，不得写"将在后面讲解"。
4. **每个结论必须有源码位置**：格式 `file:line`。
5. **代码块必须可编译或显式标注**：每个代码块要么逐字来自源码（标注 `file:line`），要么显式标注 `[伪代码]`。不把伪代码当真实代码。
6. **数值声明必须 grep 验证**：每个数值常量（数量、大小、阈值、公式）必须经过 `grep` 源码验证。`cores/2` 写出来没 grep → 编造。实际：`availableProcessors() * 2` 受内存限制 (PooledByteBufAllocator.java:104-117)。
7. **类名 ≠ 行为**：不能仅凭类名推断其职责。`AdaptivePoolingAllocator` 被假设为"在 heap/direct 间选择"——实际是根据历史用量自适应调整池容量。读方法体，不只看类声明。
8. **外部 API 行为声明需验证**：对 JDK/NIO 行为的声明（如"SocketChannel.write()只接受 DirectBuffer"）必须对照 JDK 源码或文档验证——不能凭框架直觉推断。
9. **每个闭环笔记必须立即写文件**：完成一个问题的 grep→验证→结论循环后，立即写闭环笔记文件，再处理下一个。不等到所有问题完成再批量写——会导致遗漏文件（ByteBuf Q2/Q3 事件）。Pass 2 全部完成后：`find output-dir -type f | sort` 验证每个预期文件都存在。

### 自执行协议

**进行任何分析或审查前，输出本声明块。每项必须带证据数字——没有数字的声明毫无价值。**

```
## 已读声明 + 执行证据

- [x] 方法论/01 第一遍: N 个概念块分解完成
- [x] 方法论/01 第二遍: N 条源码声明 grep 验证，发现 N 处不准确/遗漏
- [x] 方法论/01 第三遍: N 个结构问题（缺失章节、过时图表）
- [x] 方法论/03 深度测试: N 条声明检查"为什么"vs"仅是什么"
- [x] 方法论/05 工具链: codegraph N 次查询，grep N 次验证
- [x] 源码路径: {path}
```

**执行后自审**

分析完成后，验证以下为真：
- [ ] grep-verified ≥3 条声明 → 否则 **Pass 2 未执行，重做**
- [ ] 至少发现 ONE 处内容不准确或遗漏 → 若零发现，**审查是格式扫描，不是内容审查**
- [ ] 至少使用了一种语义工具（codegraph/LSP）超越 grep → 否则 **违反方法论/05**
- [ ] 全部数值声明已对照源码检查 → 若 `cores/2` 写出未 grep 验证 → **编造**
- [ ] 全部基于类名的推断已对照实际方法体验证 → 若 `AdaptivePoolingAllocator` 描述未经读 `allocate()` 方法体 → **编造**
- [ ] ALL N 个闭环笔记都存在为文件 → `find output/ -name "pass2-q*.md" | wc -l` 匹配预期数量
- [ ] 概念覆盖审计：Pass 2 问题+闭环笔记对照该域已知特性面（测试文件名、Pass 1 公共 API 面、书籍 TOC）检查 → 无已知特性遗漏
- [ ] 全部代码示例运行时验证 → `register(selector, OP_READ)` 没设 attachment 后续 `key.attachment()` 返回 null（编译通过但运行时 NPE）
- [ ] 全部修复声明跨段同步 → 修了叙事层的 "NioEventLoop" 也要修 Pass 0 元数据层的同一声明（每次修复后 grep 全文确认）

**任一自审项未达标，分析不完整。不得在修正前呈报用户。**

**代码是设计的结果，不是设计的来源。先读设计类文档。**

```bash

Read README.md
```

无产出 — 纯吸收。先建立上下文，再碰实现代码。只在零文档/零 Issue/零 Release Note 时跳过此步（罕见）。

## 第二遍：盯关键点

### 对每个标记问题执行

```
1. 读问题的源码位置（Read 工具）
2. 提出假设："我认为这个机制是这样工作的：XXX"
3. 验证假设：
   - grep 追踪调用链（至少 2 层）
   - 读被调用方的关键方法体
   - 检查变量命名、注释、异常处理寻找设计意图
4. 判断代码类型（选一）：
   - Glue → 追问：它连接了什么接口？错误怎么处理？
   - Interface → 追问：契约完整吗？暴露了什么内部细节？
   - Implementation → 追问：状态的生命周期是什么？改变它有什么风险？
   - Algorithmic → 追问：数据结构是什么？时间复杂度？
5. 结论：假设被验证还是推翻？保留源码位置证据。
```

### 产出格式

```
## 闭环笔记：{问题}
假设：[一句话]
验证过程：
  - grep {pattern} → 找到 {file:line}，证实/推翻 XXX
  - Read {file:line} → 方法体中 XXX
  - 追踪到 {file:line} → XXX
代码类型：{Glue/Interface/Implementation/Algorithmic}
跨域关联：[如有] {域名} → {关联类型}
结论：[一句话，附源码位置]
```

### 完成检查

- [ ] 至少 3 个标记问题已完成闭环
- [ ] 每个闭环至少有 2 个源码位置证据
- [ ] 每个闭环都标注了代码类型
- [ ] 没有"我猜"——全部有源码佐证
- [ ] 如果发现新包/类 → **暂停，回第一遍补扫描**
- [ ] **文件存在检查**：`find output/ -name "pass2-q*.md" | wc -l` ≥ 标记问题数
- [ ] **概念覆盖审计**：Pass 2 闭环笔记覆盖了该域的全部特性面（已与测试文件名、Pass 1 公共 API 面、框架书籍 TOC 对照）
- [ ] **无类名推断**：每个行为声明来自读方法体，不是来自类名

### 已定义 → 回第一遍

当第二遍发现依赖的类不在第一遍的继承树中时，立即：
1. 回到第一遍补扫该包/类
2. 更新继承树
3. 添加新标记问题
4. 继续第二遍

### 时空溯源（仅 🔴 域）

对核心域，通过读早期版本来降维复杂度：

```bash
# 找到最早有语义意义的 tag
git tag --sort=version:refname | head -20
# Checkout 早期版本看骨架
git checkout <earliest-tag>
# 读简化版 — 没有向后兼容胶水代码，没有边界优化
```

早期版本剥离了多年累加的兼容层，暴露原始设计意图。仅用于 🔴 域（当前版本复杂度阻碍理解时）。

如果 checkout 了早期版本，用两个版本的对比视角重看第一遍的继承树和第二遍闭环笔记——早期版本是对比基线，不是当前版本分析的替代品。

## 出第三遍之前：大域文章拆分

**Pass 3 的产出模板假设一个域 = 一篇文章。对于大域（≥6 个闭环笔记），一篇文章不够——变成走马观花而非深度分析。**

### 何时拆分

统计 Pass 2 闭环笔记数（N）。若 N ≥ 6，域**必须**拆分为多篇文章。

### 怎么拆

```
1. 将闭环笔记按主题亲和性聚类为 M 组（每组 2-4 个笔记）
2. 每组 = 一篇文章：
   - 标题：有意义的子主题名
   - 笔记映射：覆盖哪些 Q#
   - 核心问题："这篇文章回答什么问题？"
3. 按概念依赖排序文章（基础 → 应用）
4. 呈报文章规划给用户确认再开始写
```

### 文章规划模板

```
## Pass 3 文章规划：{域名}

Pass 2 产出 {N} 个闭环笔记 → 拆分为 {M} 篇文章：

| # | 标题 | 覆盖 | 核心问题 |
|:--:|------|:--:|------|
| 上 | {标题} | Q1, Q2, ... | {一句话} |
| 中 | {标题} | Q4, Q5, ... | {一句话} |
| 下 | {标题} | Q3, Q6, ... | {一句话} |

每篇文章按 Pass 3 产出模板（§下方）执行。
这个规划合理吗？有没有遗漏？
```

### 反模式

```
错误: ByteBuf 有 9 个闭环笔记 → 挤成一篇文章 → 每个笔记只有 2 段话
正确: ByteBuf → 拆成 3 篇 → 每个笔记得到完整叙事

错误: 拆太细（M 太大）→ 每篇仍然浅薄
正确: 每篇 2-4 个笔记——足够厚又不至于深度崩塌
```

### 巨型域拆分（新增）— N ≥ 20 时上升为一域一卷

**触发条件**：Pass 2 闭环笔记 N ≥ 20，或源码行数 ≥ 30000，或文件数 ≥ 100。

**区别**：普通大域（6 ≤ N < 20）拆 2-5 篇，同一大纲文件内列出。巨型域（N ≥ 20）拆 **8-15 篇**——每篇有独立大纲文件，整个域占据 **一卷**的篇幅。

**例子**：
```
普通大域: ByteBuf (9 笔记) → 拆 3 篇, 同一大纲文件
巨型域:   G1 GC (30+ 笔记, 45692行/195文件) → 拆 8-10 篇, 每篇独立大纲, 占一整卷
巨型域:   C2 Compiler (30+ 笔记, 139595行/129文件) → 拆 8-10 篇, 每篇独立大纲, 占一整卷
巨型域:   JFR (20+ 笔记, 215文件) → 拆 6-8 篇, 每篇独立大纲
```

**巨型域文章规划模板**：
```
## 巨型域文章规划：{域名}

Pass 2 产出 {N} 个闭环笔记 → 源码 {L} 行 / {F} 文件 → 巨型域 → 拆 {M} 篇

| 篇 | 标题 | 覆盖笔记 | 核心问题 | 预估行数 |
|:--:|------|:--:|------|:--:|
| 1 | Region 模型 | Q1,Q2,Q5 | G1 怎么把堆切成 2048 块积木？ | 2000-3000 |
| 2 | GC 周期编排 | Q3,Q8 | 什么时候做 young、什么时候做 mixed？ | 2500-3500 |
...
| 10 | 调优与日志 | Q28,Q29,Q30 | gc.log 里的每一项是什么意思？ | 2000-3000 |

每篇独立大纲文件：{域名}/01-region-model.md 到 {域名}/10-tuning-logging.md
```

**反模式**：
```
错误: G1 GC 45692行 → Pre-Pass 3 声称"强制拆 3-4 篇" → 每篇 3000 字 → 仍然是走马观花
正确: N ≥ 20 → 上升为巨型域 → 拆 8-10 篇 → 每篇 2500-4000 行 → 真正深度覆盖

错误: 巨型域和普通大域共用同一个拆分模板 → 用"上中下"三篇命名
正确: 巨型域每篇独立大纲文件 → 有独立标题和清晰边界
```

## 每篇文章写作大纲

**在写任何文章之前，先产出一页大纲。呈报用户确认。** 大纲桥接"4个独立闭环笔记"和"一篇连贯叙事"的差距。没有大纲，Pass 3 步骤 2（"写出完整叙事"）是一个黑盒。

### 教学叙事设计（在大纲格式之前）

> 大纲不能只是技术清单——须指导 AI 写出读者能懂的教学文章。参照标准：《MySQL是怎样运行的》（作者小孩子4919）。

**技术清单 vs 教学叙事**:

| | 技术清单（错误） | 教学叙事（正确） |
|------|------|------|
| 标题 | "CodeBuffer + AbstractAssembler — 机器码的容器" | "从一条记录说起——InnoDB记录存储结构" / "盛放记录的大盒子——InnoDB数据页结构" |
| 结构 | 技术机制从上到下列举 | 从简单场景→逐步复杂→总结收束 |
| 语言 | 默认读者懂背景 | 从零构建认知 |
| 知识传递 | 回答"JVM 怎么做的" | 回答"你怎么理解 JVM 为什么这样做" |

**教学叙事设计包含五个要素**:

1. **读者处境分析** — 读者站在哪里？他已知道什么？这片会打开什么新视角？
2. **核心叙事线** — 用什么场景/故事串联所有 KP？**从简单→复杂→总结**，每步递增一步
3. **比喻锚点** — 每个 🔴 机制的日常类比——不是技术翻译，是认知桥梁
4. **每篇的"Aha Moment"** — 读者读完这篇后会突然明白什么？一句话
5. **What→Why→How 顺序** — 先建立直觉（"发生了什么现象"）→ 再解释原因（"为什么需要这个设计"）→ 最后展示实现（"源码怎么做的"）
6. **跨层知识嵌入** — 大纲必须标注每个机制依赖的外部知识层，指导 AI 在写作时嵌入解释：
   - **C++ 系统编程层**: JVM 是 C++ 程序——涉及 POSIX API（mmap/mprotect/pthread/sigaction/dlopen）、内存模型（volatile/atomic/memory_order）、模板元编程（SFINAE/type traits）。大纲中标注 `[C++: 概念]` 提示 AI 展开解释。
   - **Linux 内核层**: JVM 的行为由内核机制决定——虚拟内存（overcommit/THP/khugepaged）、信号处理（SIGSEGV 分发）、调度（CFS/nice）、cgroup（v1/v2 子系统）。大纲中标注 `[内核: 概念]` 提示 AI 解释内核行为。
   - **x86/CPU 硬件层**: 部分机制与 CPU 直接相关——TLB/cache line/page table walk/MESI protocol/LOCK prefix。大纲中标注 `[x86: 概念]` 提示 AI 简短解释硬件层。

**跨层嵌入规则**:

大纲层面（本步骤产出）:
- 每个 🔴 机制至少标注一个外部知识层，2-3 句概要——提示 AI "这里要讲什么背景知识"
- 标注格式: 在源码锚点后追加 `[C++: mmap 的 MAP_NORESERVE 语义]` / `[内核: vm.overcommit_memory 参数控制 overcommit]` / `[x86: TLB miss 代价 ~100 cycles]`

写作层面（Pass 3 执行，非本步骤）:
- 跨层知识必须**详细展开**——不是一句话带过。解释 POSIX API 的参数/返回值/错误码，必要时引用 `man 2 mmap` / `man 3 pthread_cond_wait` 验证
- Linux 内核行为必须解释因果链——"JVM 调了 mmap → 内核做了 page fault → overcommit_memory 决定是否分配 → 如果 OOM → OOM Killer 的行为"
- x86 硬件层必须给出数量级——"TLB miss ≈ 100 cycles (3 次 page table walk)，L1 cache hit = 4 cycles。大页面把 page table walk 从 4 层减到 3 层"
- **man 手册验证**: 对 POSIX API / 系统调用 / 内核参数的描述，必须根据 API 类型查阅正确的 man section:
  - `man 2` — 系统调用: mmap, mprotect, futex, sigaction, clone, sched_setaffinity
  - `man 3` — C 库函数: pthread_cond_wait, dlopen, sem_init, clock_gettime
  - `man 5` — 文件格式/配置: proc(5), cgroups(5), locale(5)
  - `man 7` — 概述/约定: signal(7), pthreads(7), cgroups(7), capabilities(7), overcommit(7)
  - 大纲中标注 `[man 2 mmap]` / `[man 7 signal]` 提示 AI 在写作时查阅对应 section
- 跨层知识不是独立章节——融入叙事流中，在源码分析需要时自然引入

**叙事线构建规则**:

- 开头是**具体场景**，不是抽象概念。例："你写了一个死循环递归，JVM 没 crash——为什么？"
- 每节回答**一个读者自然会问的问题**。上一节的答案引出下一节的问题。
- 结尾收束——回到开头场景，解释答案。

### 大纲格式

```
## 文章大纲：{文章标题}

### 概念依赖链
[这篇文章内的笔记之间谁依赖谁？必须先讲哪个？]

### 叙事顺序
1. 问题引入——这篇文章解决什么真实问题？
2. {第一个概念}——基础
3. {第二个概念}——建立在第一个之上
4. ...
   每个步骤之间的自然过渡句。

### 核心悬念
[读完这篇文章，读者能回答什么核心问题？]
[一句话。例："Java NIO 有 ByteBuffer，Netty 为什么重新发明了缓冲区？"]
```

## 大纲完备性验证：全视角提问

> 大纲写完后、宣称"完成"前，必须执行。用户不应每次提醒——这是强制步骤。

### 核心原则

**大纲的完备性不由"这篇大纲看起来全不全"判断——由"7 个身份的人分别读这篇大纲，能回答他们的问题吗"判断。**

如果某个身份的典型问题在大纲中没有对应机制 → 大纲不完备。

### 执行时机

在每个域的 Per-Article Outline 完成深审（R1+R2）后，立即执行全视角提问验证。

### 七身份

以下 7 个身份是针对 **JVM/编译器/GC 类域** 的标准身份集。对于其他域（如网络框架、数据库），应将身份调整为域相关的角色——身份的数量和类型不是固定的，但必须从多种视角覆盖。

| 身份 | 视角 | 典型追问 | 适用条件 |
|------|------|------|------|
| **开发者** | "我要改这部分的代码" | 数据结构的约束？并发协议？边界条件？ | 所有域 |
| **性能工程师** | "我怎么把它调好" | 参数效果？监控指标？经验法则？ | 有调优参数的域 |
| **架构师** | "为什么这样设计" | 为什么选 A 不选 B？tradeoff？ | 所有域 |
| **SRE/运维** | "线上出问题了" | 日志排查？crash 反推？降级决策？ | 生产可用的域 |
| **研究者** | "和替代方案对比" | vs 同类方案的边界？理论极限？不适用场景？ | 有多个实现的域 |
| **子系统开发者** | "上层/下层怎么配合" | 屏障注入？优化消除？回调接口？ | 有跨层交互的域 |
| **学生** | "我第一次看" | 为什么叫这个名字？最自然的 why？ | 所有域 |

### 执行步骤

```
1. 列出域的 8-10 个子主题（按自然聚类）
2. 对每个身份 × 每个子主题 → 出 2-5 个"该身份真正会问的"问题
3. 每个问题标注当前大纲中是否可以找到对应机制
   - ✅ 大纲有 → 标注对应段落
   - ⚠️ 大纲部分覆盖 → 标注缺失部分
   - ❌ 大纲无 → 标记为大纲不完备
4. 汇总 ❌ 和 ⚠️ 项 → 回大纲补全 → 再次验证
5. 全部 ✅ 后 → 将提问文档作为验证证据保留（`{域}-completeness-questions.md`）
6. 用户确认大纲时，一并呈报提问文档的覆盖统计（❌/⚠️/✅ 数量）
```

**注意**：补全缺口后的验证不需要用户介入——AI 自主补全→重新对照→直到全部 ✅。只有当 AI 反复补不齐某类问题时（如学生问题怎么都回答不好），才向用户求助。

### 产出格式

```
## 全视角提问验证：{域名}

| # | 身份 | 子主题 | 问题 | 大纲覆盖 |
|:--:|------|------|------|:--:|
| 1 | 开发者 | Region | 为什么 Region 大小必须是 2 的幂？ | ✅ 篇1-L3 |
| 2 | 架构师 | SATB | 为什么选 SATB 不选增量更新？ | ⚠️ 篇4 有机制无对比 |
| 3 | SRE | Full GC | gc log 中 To-space exhausted 怎么定位？ | ❌ 未覆盖 |

⚠️ 2 项部分覆盖，❌ 1 项缺失 → 回大纲补全。
```

### 数量基准

以下为**总问题数**（跨所有适用身份），不是每身份问题数。

| 域类型 | 源码行数 | 最少总问题数 | 最少身份数 | 验证粒度 |
|------|:--:|:--:|:--:|------|
| 普通域 | <10000 | 30 | 5 | 域级（一篇大纲 = 一次验证） |
| 大域 | 10000-30000 | 50 | 6 | 域级或篇级（≥3篇时逐篇验证） |
| 巨型域 | >30000 | 80 | 7 | **逐篇验证**（每篇大纲独立出题+验证） |

### 反模式

```

错误: 提问完就结束了，不逐题对照大纲
正确: 每道题标注大纲覆盖状态 → 汇总缺口 → 回补 → 再验证

错误: 用户每次都要提醒"出提问文档"
正确: 每个域大纲完成后自动产出提问文档
```
