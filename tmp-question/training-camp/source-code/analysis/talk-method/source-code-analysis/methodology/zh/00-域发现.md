# 域发现——如何找到要分析什么

> 角色：AI 自约束操作规范。分析任何新框架前必读。
> 先修：无（基础文档）
> 输入：框架源码目录 + 入口点类/方法
> 阅读顺序：00（本文）→ 01 → 02 → 03 → 04 → 05 → 06。

## 核心原则

**入口点是唯一人工指定的输入。** 其他一切自动推导。AI 读入口点，从入口向外展开执行流，发现框架依赖的核心子系统——那些子系统就是域。

---

## 1. 如何找到入口点

入口点是用户调用来启动框架的**门面/引导类**——创建初始对象、配置它们、启动执行。

```
找到入口点：
- 读 README.md 或 docs/ 找 "Getting Started" 示例
- 搜索返回框架对象或启动生命周期的 public 方法
  （构造函数、静态工厂方法、或实例方法）
- 找类名含 "Bootstrap"/"Starter"/"Main"/"Launcher"/"Factory"/"Application"/"Context"/"Engine" 的类
- 例子：
  Netty → ServerBootstrap.bind()  （带参实例方法）
  Spring → ApplicationContext.refresh()  （实例方法）
  Kafka → KafkaProducer.send() / KafkaConsumer.poll()  （实例方法）
  JVM → CreateJavaVM() 在 src/share/vm/prims/jni.cpp  （native 函数）
```

**输入格式**：`{入口点类}.{方法}()`

### 没有入口点的框架

库、中间件、嵌入式框架可能没有单一的用户可见入口点。此时：

```
1. 找使用最频繁的公开 API 类——用户最常交互的类
2. 读其构造函数或工厂方法看它创建什么
3. 仍不明确 → 问用户："你认为哪个类是入口点？"
```

入口点不必是"用户第一个接触的类"——只要它能创建/配置框架的核心对象即可。

---

## 2. 从入口点展开

从入口点追踪**它创建什么、配置什么、调用什么**。每个核心对象或子系统都是候选域。

### 执行流追踪

```
1. 读入口点方法体
2. 对每个创建的对象（new Xxx）：
   → 候选域：这个类做什么？
3. 对每个配置调用（setXxx、addXxx）：
   → 候选域：被配置的对象做什么？
4. 对每个方法调用（obj.doSomething()）：
   → 候选域：这个调用属于哪个子系统？
```

### 展开深度

**逐层展开**，不是一次到底：

```
Level 0：入口点（用户指定）
Level 1：入口点创建/配置/调用的对象
Level 2：Level 1 候选创建/配置/调用的对象
...
```

**停止条件**：展开到没有新候选为止。每层应比前层产生更少的新候选——某层零新候选时展开完成。不展开到实现细节（私有方法、内部辅助）——只沿公开/受保护边界。

### 候选域映射

每个候选映射到一个或多个源码包：

```
候选 → 包 → 设计决策测试 → 是域吗？
```

---

## 2.5 旁路发现——扫描独立子系统

入口展开（§2）只能找到**主执行路径**上的域。大型框架（JVM、Linux 内核、数据库引擎）还有**独立子系统**——它们不被主入口调用，而是自己启动、按需触发、或从独立进程运行。

### 何时扫描

以下情况扫描：
- 入口展开停止产生新候选，但
- 框架顶层有展开未访问的目录

### 如何扫描

```
1. ls 顶层源码目录
   JVM：src/hotspot/share/
   Netty：src/main/java/io/netty/
   内核：kernel/ mm/ fs/ net/

2. 对每个未被入口展开访问的顶层目录：
   → 检查：是否包含设计决策？
   → 例子：JVM 的 services/（JMX/JFR/SA）——不被 CreateJavaVM 调用

3. 标记为旁路候选
   → 应用 §3 设计决策测试
   → 应用 §3.5 基于信号的分类
```

### 旁路候选示例：JVM

```
入口展开发现（从 CreateJavaVM）：
  ✅ CodeCache、G1Heap、Metaspace、SymbolTable、解释器、JIT 编译、Safepoint

旁路扫描发现（不在 CreateJavaVM 路径上）：
  services/jmx       → JMX 管理服务            → [测试：设计决策？]
  jfr/               → JFR 记录引擎             → [测试：设计决策？]
  sa/                → Serviceability Agent     → [测试：设计决策？]
  signal/             → 信号处理                 → [测试：设计决策？]
  launcher/           → java 命令启动器          → [独立进程，非 JVM 内部]
```

### 旁路 vs 主路径

| 发现类型 | 来源 | 置信度 | 操作 |
|---------|------|--------|------|
| **主路径** | 入口展开 | 高（执行流验证） | 正常处理 |
| **旁路** | 目录扫描 | 中（非执行流验证） | 应用 §3 测试；通过 → 域；不确定 → `[TODO: verify]` |

旁路候选通过 §3 测试后，和其他域一样处理。唯一区别是来源不同——通过扫描而非执行流发现。

## 3. 设计决策测试 — 仅作过滤器

**本环节只判定一件事：该候选是否是域？** 是二元过滤器（是域/不是域），不是分类器（🔴/🟡）。分类由 §3.5 完成。

对每个候选，应用：

```
是域吗？
├── 包含任何设计决策？
│   ├── 否 → ✂️ 排除：纯工具、委托封装、废弃代码、测试基础设施
│   └── 是 → 是否仅是对单个已有机制的 thin wrapper？
│              ├── 是 → ✂️ 排除：未增加框架级决策
│              └── 否 → ✅ 域候选 → 进入 §3.5 分类
```

### 定量预检

在做出主观判断之前，先收集客观证据：

| 阈值 | 操作 |
|------|------|
| 包 ≥ **50 个源文件** | 必须先读 3-5 个关键类再决定——不能凭直觉排除 |
| 单类 ≥ **500 行** | 必须检查是否承载独立设计决策——大类通常有 |
| 包有**独立子包结构**（≥ 3 个子目录） | 不能仅当作"X 的一个实例"排除——检查是否有子域 |

### 域级 vs 代码级判定标准

| 层级 | 判定标准 | 应用于 | 用于 |
|------|---------|--------|------|
| **域级**（00，本文） | "该候选是域吗？"（二元 是/否） | 子系统/包 | 域发现 |
| **代码级**（03） | "这段代码是否承载设计决策？" | 单个方法/类 | 深度分析（Pass 2） |

🔴 vs 🟡 分类在 §3.5 用 3 信号完成，不在这里。

### 排除什么

- 纯工具类（PlatformDependent、StringUtil、ObjectUtil）
- 纯委托封装（没有增加设计决策）
- 废弃代码路径（标注 `[deprecated]`，跳过）
- 配置解析（除非有设计决策）
- 测试基础设施（Pass 1 已作为功能地图读过，不是域）

## 3.5 域分类 — 🔴 vs 🟡

**本环节是主分类器。** §3 决定了候选是否是一个域。本节决定每个域属于什么层级。

### 一级分类：定义特征测试

```
没有这个域，框架是否失去其定义特征？
├── 是 → 🔴 核心域 — 这就是 Netty 之所以是 Netty、Spring 之所以是 Spring
│         （EventLoop、ByteBuf、Pipeline、GC、BeanFactory、refresh()）
└── 否 → 🟡 支撑域 — 建立在核心机制之上，有独立的设计决策
          （Codec、Bootstrap、Promise/Future、@Transactional、@Scheduled）
```

**自检**：如果你的分类直觉是 80% 都是 🔴，说明你用错了标准。多数域应该是 🟡——🔴 保留给定义框架的那少数几个机制。

### 二级分类：三信号置信度

分配 🔴/🟡 之后，用 3 个信号验证置信度：

| 信号 | 衡量什么 | AI 如何使用 |
|------|---------|-----------|
| **面试频率** | 技术面试中被问到的频率 | 来自 AI 训练数据 |
| **生产频率** | 真实系统中被使用的频率 | 来自 AI 训练数据 |
| **框架依赖** | 框架内有多少其他域依赖它 | 来自 §4 依赖图 |

| 置信度 | 判定标准 | 操作 |
|--------|---------|------|
| **高** | 3 个信号全部与分类一致 | AI 独立判定 |
| **中** | 2 个一致 | AI 呈报并附理由；用户可调整 |
| **低** | ≤ 1 个一致或信号冲突 | AI 呈报给用户决定 |

### 定量打破僵局

当信号模糊或分类不确定时，用代码量作为**辅助判定**（非主要因素）：

| 信号 | 证据 |
|------|------|
| 域 ≥ **100 个源文件**或单类 ≥ **500 行** | 确认域有实质内容——未读 5 个关键类前不可降级 |
| 域 < **10 个源文件**且无类超过 **200 行** | 可能确实单薄——但仍检查是否有算法级决策（如 HashedWheelTimer 5 文件但时间轮算法是设计决策） |

### 分类流程

```
对每个通过 §3 的域候选：
  1. 应用定义特征测试 → 🔴 或 🟡
  2. 对 3 信号打分 → 分配 高/中/低 置信度
  3. 若低置信度 → 应用定量打破僵局 → 重新评估
  4. 产出：层级 + 置信度 + 理由
```

### 产出格式

```
### 核心域（🔴）
| 域 | 设计决策 | 面试 | 生产 | Hub | 置信度 |
|----|---------|:---:|:---:|:---:|:-----:|
| EventLoop | 单线程事件循环 | 高频 | 主流 | ✅ | 高 |

### 支撑域（🟡）
| 域 | 设计决策 | 面试 | 生产 | Hub | 置信度 |
|----|---------|:---:|:---:|:---:|:-----:|
| Codec | SPI 编解码 | 高频 | 主流 | ❌ | 中 |

置信度图例：
- 高 = 3/3 信号一致，AI 终判
- 中 = 2/3 一致，AI 呈报，用户可调
- 低 = ≤1/3 一致，需用户决定
```

## 4. 依赖图与拓扑排序

识别域之后，构建依赖图：

```
域 A → 依赖 → 域 B、C
域 B → 依赖 → 域 D
域 C → 依赖 → 域 D
域 D → （叶子 — 无依赖）
```

**规则**：
- `A 依赖 B` = 不理解 B 的机制，就无法理解 A 的行为或设计原因
- 这是机制层面依赖，不是包 import
- 环形依赖 → 应用三轮化解策略（来自 02 §1.4）

**拓扑排序**：叶子先 → Hub 其次 → 应用层最后。这成为教学顺序。

## 6. 执行步骤

### 第一步：入口点输入
从用户获取入口点：`{入口点类}.{方法}()`

### 第二步：Level-1+ 展开
读入口点方法体。对每个创建/配置/调用的对象，列为候选。然后递归展开：Level-1 → 读每个候选的关键类（每个候选 2-3 个）→ Level-2 候选 → 重复直到无新候选。

### 第三步：设计决策测试
对每个候选，检查：这个子系统承载设计决策吗？过滤掉胶水代码。

### 第四步：旁路扫描
入口展开停止产生新候选后，扫描未被展开访问的顶层源码目录。对每个目录应用 §3 测试。通过测试的旁路候选成为域，置信度为中（参见 §2.5）。

### 第五步：基于信号的分类
对全部存活的域（主路径 + 旁路），用 3 个信号（面试频率 + 生产频率 + 框架依赖）分类重要度。分配置信度（高/中/低）。

**置信度处理**：
- 高 → AI 独立判定，无需用户审查
- 中 → AI 呈报分类并附理由，用户在当前会话中未反对则继续
- 低 → AI 呈报给用户决定，等待确认后继续

**降级**：如果框架不在 AI 训练数据中（如内部/公司框架），面试/生产信号不可用 → 降级为仅用框架依赖信号。所有域标为中等置信度 → 用户全部审查。

### 第六步：依赖图
对所有存活的域，列出每个域的全部依赖。构建依赖图。

### 第七步：拓扑排序
按依赖排序——所有依赖出现在被依赖之前。

### 第八步：产出
按上述格式输出域清单、排除清单、教学顺序。

### 第九步：对照验证（强制）

**输出域清单后，必须对照已有知识源做验证。** 这防止 AI 系统性遗漏已知的重要域。

**流程**：

```
1. 读取该框架已有的执行计划/规划文档（若有）
   → 如 issue/Netty源码学习范围规划.md、issue/Spring源码学习范围规划.md

2. 从执行计划构建"基准域列表"：
   如 Netty：执行计划列出 ByteBuf/EventLoop/Pipeline/Codec/HTTP编解码/...

3. 对比：方法论产出 vs 基准：
   | 域 | 方法论 | 基准 | 状态 |
   |----|--------|----|------|
   | HTTP Codec | ✂️ 排除 | 🟡 | 差距——重新检查 |
   | handler扩展 | ✂️ 排除 | 🟡 | 差距——重新检查 |

4. 对每个差距（基准有，方法论缺）：
   → 重读该包的 3-5 个关键类
   → 重新应用 §3 过滤 + §3.5 分类
   → 结论：排除正确（附理由）或 新增域（之前遗漏）

5. 对每个多出的域（方法论有，基准无）：
   → 解释为什么方法论发现了它
   → 入口展开？旁路扫描？分类标准不同？

6. 在 00-domain-list.md 末尾输出覆盖率报告：
   ## 覆盖率报告
   | 来源 | 域数 | 覆盖率 |
   |------|:---:|:-----:|
   | 执行计划 | N | — |
   | 方法论/00 | M | M/N (XX%) |
   
   ### 差距分析
   | 域 | 方法论 | 基准 | 结论 |
   |----|--------|----|------|
   | X | ✂️ | 🟡 | 重检：[排除正确，因为...] / [新增：遗漏，因为...] |

7. 若覆盖率 < 80%：停止。方法论存在系统性问题。
   重新审查 §3 标准——是否对 🟡 过严？
8. 若覆盖率 > 100%（方法论产出更多域）：记录为什么方法论发现了额外域。
```

**为什么必须有这一步**：Netty 域发现花了 3 轮（9→10 域）才收敛。如果有对照验证步骤，执行计划的 12 个域在第一轮就能立即对比——差距在呈报用户之前就会被发现。这一步是"AI 随便猜一次"和"AI 系统验证"的分水岭。

## 7. 示例：Netty

### 入口点
`io.netty.bootstrap.ServerBootstrap.bind()`

### Level-1 展开

```
bind() → 需要 EventLoopGroup（线程模型子系统）
       → 需要 ChannelInitializer（管道初始化子系统）
       → 需要 Channel（I/O 抽象子系统）
```

### Level-2 展开

```
EventLoopGroup → NioEventLoopGroup → NioEventLoop
  → io.netty.channel.nio.* → 核心：事件循环线程模型

ChannelInitializer → ChannelPipeline → ChannelHandler
  → io.netty.channel.* → 核心：请求处理链

Channel → ByteBuf → ByteBufAllocator
  → io.netty.buffer.* → 核心：内存管理
```

### Level-3 展开

```
ByteBufAllocator → PooledByteBufAllocator → PoolArena
  → io.netty.buffer.* → 子域：内存池（设计决策：池化算法）
```

### 域清单

| 域 | 包 | 设计决策 | 依赖 |
|----|-----|---------|------|
| EventLoop | io.netty.channel | 单线程事件循环模型 | （叶子） |
| ByteBuf | io.netty.buffer | 引用计数 vs GC | （叶子） |
| Pipeline | io.netty.channel | 责任链 | ByteBuf |
| ChannelHandler | io.netty.channel | SPI 扩展机制 | Pipeline |
| 内存池 | io.netty.buffer | 池化分配算法 | ByteBuf |
| Codec | io.netty.handler.codec | SPI 编解码抽象 | ChannelHandler |
| SSLHandler | io.netty.handler.ssl | TLS 安全层 | ChannelHandler |
| ChunkedWriteHandler | io.netty.handler.stream | 分块传输 | ChannelHandler |

### 排除
| 类/包 | 原因 |
|-------|------|
| PlatformDependent | 纯工具类——无设计决策 |
| StringUtil | 纯工具——无设计决策 |
| IdleStateHandler | 定时器工具——机制简单 |

### 旁路扫描
Netty 无独立子系统——所有包都在 `bind()` 主执行路径上。旁路扫描产生零新候选。这对中间件框架很常见；大型框架（JVM、内核）通常有更多旁路发现。

## 8. 完成检查单

框架的域发现完成后：

- [ ] **入口点已记录**：用户指定或 AI 识别的入口点已记录
- [ ] **所有层级已展开**：展开持续到没有新候选为止
- [ ] **旁路扫描已完成**：顶层目录已扫描独立子系统
- [ ] **设计决策测试已应用**：每个候选（主路径 + 旁路）已评估设计决策
- [ ] **依赖已映射**：每个域有完整依赖列表
- [ ] **环形依赖已识别**：每对环形依赖记录三轮化解策略
- [ ] **拓扑排序已验证**：没有依赖出现在被依赖之后
- [ ] **排除清单已记录**：所有排除的类/包含原因
- [ ] **对照验证完成（第九步）**：域清单已与已有执行计划/基准对照。覆盖率报告已写。所有差距已解释。覆盖率 ≥ 80% 或系统性问题已解决。

## 9. 反模式

### 1. 把所有包当域

```
错误：find src/main/java -type d → 每个包都是域
正确：只有承载设计决策的包才是域。
      工具包、工具类、废弃包 → 排除。
```

### 2. 用使用频率当判定标准

```
错误："后端工程师用 Netty → 需要知道 EventLoop"
正确："EventLoop 承载了线程模型的设计决策"
      使用频率是知识规划的标准，不是源码分析的标准。
      源码分析问：代码承载设计决策吗？
```

### 3. 跳过内部子系统

```
错误："内存池是内部的——后端工程师不需要知道"
正确：内存池承载了池化算法的设计决策。
      源码分析是理解设计意图，不是使用便利性。
      内部机制中承载设计决策的就是域。
```

### 4. 不建依赖图就定教学顺序

```
错误："CFS 是 🔴，nice 值是 🟡 → 先讲 CFS"
正确：建依赖图 → 拓扑排序 → 教学顺序。
      重要性决定深度（04），依赖决定顺序。
```

### 5. 混淆域发现与方案选择

```
错误：产出包含每个域的"深度：A/B/C/D"
正确：域发现输出哪些域存在及其顺序。
      方案选择（A/B/C/D）由 04 按域判定。
```

### 6. 用代码量直觉代替 §3.5 信号分类

```
错误："这个包 200+ 文件 → 肯定重要 → 🟡"
      "这个包才 5 个文件 → 不重要 → ✂️ 排除"
正确：对每个候选跑完整 3 信号判定。
      代码量仅作为定量打破僵局的辅助数据点。
      小包可能承载算法级决策（HashedWheelTimer 5 文件，但时间轮是设计决策）。
案例：Netty 的 codec-http 有 262 文件。直觉说"这只是 Codec 实例"。
      但 §3.5 信号：面试高频（HTTP 粘包/拆包），生产主流。
      若 2/3 信号提示 + 定量打破僵局 ≥100 文件 → 🟡。
```

## 10. 域发现之后：知识规划 vs Per-Article Outline

域发现回答"该分析什么"——但**如何组织这些域的教学顺序**？对于纯源码项目（无书籍 TOC 参考），域发现完成后**不要直接跳到 Per-Article Outline**。应该先做知识规划：

```
域发现 (00)
  ↓
知识规划 (knowledge-planning/05 — 源码分析项目适用)
  01 逐源提取 — 从每个源文件提取机制
  02 聚合 — 跨文件去重，P1/P2/P3 分级
  03 深度分类 — 🔴/🟡/🟢 分类
  04 聚类 — 按概念依赖排序教学顺序
  ↓
方案选择 (04) + 书级规划 (01)
  ↓
Per-Article Outline (01 §Pass 3)
```

**为什么不能跳**：域发现给出的是一组"域"（如 G1 GC 是一个域），但域内部可能有 30+ 个子机制分布在 195 个文件中。不先做逐源提取→聚合→分类→聚类，就无法判断一个域该拆成多少篇文章、每篇覆盖什么——这就是为什么 G1 GC 45692 行源码只产出了 57 行大纲。

**什么时候需要知识规划**：
- 纯源码项目（无书籍 TOC）→ **必须**在域发现后做知识规划
- 有书籍 TOC 参考的项目 → 直接用书籍知识规划（knowledge-planning/01）
