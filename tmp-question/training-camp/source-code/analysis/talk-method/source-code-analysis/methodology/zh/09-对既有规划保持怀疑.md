# 对既有规划保持怀疑 — 开工前域重审规范

> 角色：AI 自约束操作规范。开始每个新阶段/新仓库的规划与执行前必读。
> 先修：`00-域发现.md`（域发现完整管线）、`00-域发现.md §第九步`（对照验证）
> 输入：既有规划（执行计划 / *-PLAN.md / HANDOFF 交接文档）+ 目标仓库源码
> 触发：任何一次"打开一个 PLAN 就开始干活"的时刻。

## 核心原则

**既有规划是"待验证假设"，不是权威事实。** 执行计划、PLAN 文档、交接文档都是人或 AI 在**未充分读码**（或上一轮对话）时产出的快照。它们可能来自未经验证的直觉、过时的版本、或纯粹的笔误。开工前必须以源码为唯一事实源，对既有规划跑一遍怀疑审计。

> 一句话：**先怀疑，后执行。任何一行规划文字在 grep 证据落地前都不可信。**

---

## 1. 为什么必须有这一步（实战实证）

### 1.1 Druid 阶段（HANDOFF-DRUID §四：40 处真实错误）

| 类型 | 错误 | 证据 |
|:--|:--|:--|
| 数字 | D-6 方言 "28 种" 实为 **29** | ls dialect 目录穷举 |
| 数字 | wall/spi "14 文件" 实为 **16** | 目录计数（漏 WallVisitorBase/Utils） |
| 默认值 | D-7 "三时机默认全 false" 实为 **testWhileIdle 默认 true** | grep DEFAULT_WHILE_IDLE |
| 机制 | D-5 CreateConnectionTask "指数退避" 实为**固定间隔 500ms** | 读方法体 |

### 1.2 MP 阶段（本阶段实证）

| 类型 | 错误 | 证据 |
|:--|:--|:--|
| 数字 | MP-1 "17 种内置方法" 实为 **18 方法类/12 默认注入** | ls injector/methods/ 穷举 |
| 数字 | MP-4 "5 个回调" 实为 **7**（6 回调+setProperties） | 读 InnerInterceptor 接口 |
| 依赖方向 | 执行计划排 MP 先于 MyBatis — 实为 **MP→M 单向依赖**（MP 源码 import org.apache.ibatis **474 处**；MyBatis 源码反向引用 com.baomidou **零命中**） | rg import 统计 |
| **域清单** | 执行计划 MyBatis 仅 5 域 — 遗漏 **scripting 动态 SQL（28 文件）**、**cache 缓存（19 文件）**、**builder 装配（23 文件）**，三者均通过设计决策测试 | 顶层包扫描对照 |

### 1.3 共性规律

1. **数字错误率 ~30-50%**：凡规划里出现数字（N 个实现/方法/回调/文件），验证前默认是错的
2. **域清单完整性错误率随仓库规模上升**：文件越多，遗漏越隐蔽（MyBatis 386 文件漏 3 个定义特征级包）
3. **执行顺序常混入教学序**：执行计划"MP 先于 M"反拓扑，且与阶段2"内核先"（Framework→Boot）自相矛盾——顺序必须用 00 §4 拓扑重跑
4. **依赖方向是隐式的**：规划不写依赖方向，只会说"前置 XX"。方向必须用 import 证据独立验证

## 2. 四类怀疑对象与验证方法

| # | 怀疑对象 | 验证方法 | 证据形式 |
|:--:|:--|:--|:--|
| 1 | **域清单完整性** | `find src -maxdepth N -type d` 顶层包扫描 → 与域清单对照 → **每个 ≥10 文件的未覆盖包**必须过 00 §3 设计决策测试（不能凭"没听过"跳过） | 包文件数 vs 域覆盖对照表 |
| 2 | **数字** | 目录/接口/常量穷举：`ls`、`grep -c`、`grep DEFAULT_*` | 穷举计数截图级证据 |
| 3 | **依赖方向** | `rg -c "^import <对方>"` 正向统计 + 反向 `rg -l "<我方包名>"` 确认零引用 | 正反双向 import 计数 |
| 4 | **执行顺序** | 00 §4 拓扑重跑：依赖图 → 叶子先 → 与规划顺序对照 | 重排前后顺序对照表 |

**定量预检（00 §3 强制）**：未覆盖包 ≥50 文件或单类 ≥500 行 → 必须先读 3-5 个关键类再决定排除；有独立子包结构（≥3 子目录）→ 检查子域。

## 3. 执行流程（每阶段开工前 15 分钟）

```
1. 读取既有规划（执行计划对应章节 / PLAN / HANDOFF 对应域）
2. 对规划中的每一项断言标注来源：{已 grep 验证} / {未验证}
3. 顶层包扫描，构建"包 ↔ 域"覆盖矩阵
4. 对每个未覆盖大包跑设计决策测试 → 新增域或排除（附理由）
5. 穷举验证全部数字断言
6. 用 import 证据验证依赖方向，重跑拓扑排序
7. 产出"怀疑审计表"（§4 格式）→ 写入新 PLAN 的"重审记录"节
8. 所有与既有规划的偏差：新增/修正/重排，逐条记录理由
9. 同步更新 HANDOFF（偏差历史累计）
```

**重要**：第 1 步结束后不要直接信任第 2-6 步的结论——重审本身也可能错。重审结论（新增域等）必须再过一遍 00 §3/§3.5（设计决策测试 + 三信号分类），且对照 00 §第九步覆盖率报告。

## 5. 反模式

### 1. "执行计划写的就是对的"

```
错误：打开执行计划 → 按 3.3/3.4 的域清单直接开工
正确：执行计划只是候选假设。MP 阶段已证明其数字 2 处错误、顺序反拓扑、
      MyBatis 域遗漏 3 个定义特征级包。
```

### 2. "交接文档是唯一入口，不会错"

```
错误：HANDOFF 说 X 就信 X
正确：HANDOFF-DRUID §四 自己记录了 40 处错误（PLAN 19 + 域 19 + 全量 2）。
      交接文档记录的是"已发现的错误"，不是"没有错误"。
```

### 3. "数字看起来合理"

```
错误：17 种内置方法 / 5 个回调 — 都很整齐，没细看
正确：17→18、5→7、28→29、14→16、6 实现→实际核对。整齐的数字更可疑。
```

### 4. "顺序是权威定的，可能有道理"

```
错误：执行计划 MP 先于 MyBatis → 可能有教学考虑 → 不深究
正确：顺序必须用 import 证据 + 拓扑重跑独立验证。教学序和拓扑序混排
      必须显式声明理由，否则按拓扑序。
```

### 5. 重审只对"新发现"负责，不复查"既有通过"部分

```
错误：只查我这次要动的域，其他域照旧
正确：每次重审对**全部**域断言重新过怀疑审计（本阶段教训：第一轮只
      review 了 MP-2 域内内容，直到用户追问才重审 M 域规划）。
```

### 6. 用"没听过/面试低频"替代设计决策测试

```
错误：MyBatis scripting 包没在面试题里见过 → 跳过
正确：00 §9 反模式 2/3：源码分析问"代码承载设计决策吗"，
      <if>/<foreach>/<where> 动态 SQL 是 MyBatis 定义特征，必须成域。
```

### 7. 机械执行历史格式规范，牺牲内容

```
错误：HANDOFF 里写了"密度标准 🔴 39-69 / 🟡 35-49 行" → 每个大纲都压到
      行数以内 → 反复压缩删内容 → 大纲质量受损 (M-7 从 74 行删到 58 行
      还在删, 内容被掏空)
正确：行号/格式类约定是"信息密度自查"的软参考，不是硬性压缩目标。
      内容完整 > 行数。任何历史规范在适用前必须问：
      ①它来自哪个阶段？②那个阶段的背景是否适用当前？③用户确认过吗？
      (实战教训: 密度标准源自 Druid 会话 HANDOFF, 未向用户确认即被
      当作不可置疑的权威执行, 违反本文件核心原则)
```

### 8. 用"合规范"替代"讲清楚"

```
错误："内容已经够了, 但行数超了, 再删点" — 删的是机制细节、边界、
      对照关系, 保留的是格式
正确：REVIEW 判断一篇大纲好不好, 标准是"读者能否靠它写出文章"——
      机制是否完整、数据流是否可追溯、边界是否交代。行数是结果不是目标。
      禁止以任何行号限制为由删除已验证的机制内容。
```

## 7. 适用范围

- **阶段级**：新仓库开工前（本规范主要场景）
- **域级**：每域开工前对 PLAN 中该域断言复查（重点：数字、行号、默认值）
- **跨阶段**：阶段收尾时对下一阶段规划的怀疑审计（本阶段教训源头——Druid 收尾时直接信任了执行计划的 M 域）
