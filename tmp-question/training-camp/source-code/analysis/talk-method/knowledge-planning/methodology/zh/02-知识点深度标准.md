# 知识点深度标准

> 角色：AI 自约束操作规范。为任何知识点编写内容前必读。
> 先修：`01-如何从TOC提取知识点.md`
> 阅读顺序：01 → 02（本文）→ 03 → 04。
> 注：本模型的深度标准与源码分析 03 不同——03 由"代码是否承载设计决策"驱动（代码视角），本模型由**学习者需求**驱动（读者视角）。两者服务于不同目的，互不冲突。

## 核心原则

**书籍提供主题边界，不提供内容。** TOC 告诉你覆盖什么。AI 生成内容。深度由知识点的实际重要程度决定——不是由书中说了多少来决定。

### 与 01 §3 优先级的关系

| 维度 | 01 §3（优先级） | 02 §2（重要程度） |
|------|---------------|-----------------|
| 衡量什么 | 多书共识信号 | 实际相关度 |
| 如何计算 | 书出现次数 / N | 面试频率 + 生产频率 + 被依赖数 |
| 决定什么 | 对此重要的置信度 | AI 应该写多深 |

**它们是两个独立维度：** Priority 1（3/3 书出现）的知识点可能是 🟢 低重要度。Priority 3（1/3 书出现）的知识点可能是 🔴 高重要度。分别判断。

## 1. 三层深度模型

| 层级 | 产出 | 例子：CFS 调度器 |
|------|------|-----------------|
| **表层** | 概念名 + 一句话定义 | "CFS 是 Linux 的完全公平调度器，用红黑树按 vruntime 排序进程" |
| **工作层** | 机制原理 + 行为解释 + 为什么这样设计 | vruntime 计算、nice 值映射、I/O 密集型如何自然获得优先、调度延迟设计 |
| **深层** | 工作层内容 + 关键架构组件 + 可选关键源码佐证 | 文字描述 sched_entity、cfs_rq、pick_next_task_fair() 组件及其关系 |

### 深层：必须 vs 可选

```
必须（结构组件）：
  - 列出关键数据结构及字段名和角色
  - 列出关键函数及入口/出口点
  - 描述组件间的流程（文字版架构图）
  - 格式：纯文字描述，非 C 语法

可选（源码佐证）：
  - struct 定义、函数签名、调用链摘录
  - 格式：来自内核源码或参考的实际代码块
  - 用途：结构证据，不是完整源码分析
  - 必须可 grep 验证。未验证的标注 [待验证]
```

## 2. 重要性分档

每个知识点分配重要性等级。深度由重要性决定，不是由书的篇幅决定。

| 重要性 | 判定 | 书籍角色 | AI 角色 | 深度 |
|--------|------|---------|---------|------|
| 🔴 高频/核心 | 面试频繁问到 且/或 生产环境常见 | 提供主题方向 | **详细写**——书不够就补 | 深层 |
| 🟡 常用/支撑 | ≥3 个其他知识点依赖它 且 偶尔遇到 | 提供主题方向 | 工作层解释 | 工作层 |
| 🟢 冷门/边缘 | 罕见场景、纯扩展知识 | 书提到了就提一句 | **1-2 句话**——仅定义 | 表层 |

### 判定三问

```
1. 面试频繁问到 或 生产环境常见？
   ├── 是 → 🔴，深层
   └── 否 → 继续

2. ≥3 个其他知识点依赖它 且 实际使用中偶尔遇到？
   ├── 是 → 🟡，工作层
   └── 否 → 继续

3. 书里提了吗？
   ├── 提了 → 🟢，表层（书里提了就跟 1-2 句话）
   └── 没提 → 默认不写。如属主题边界内且为 🔴 条目的支撑概念
             → 标记 [缺口：{概念}]，按 01 §5 第三步处理。不在此处补充——🔴 缺口将在 04 §4 合并阶段由 AI 补充。
```

### 判定来源

```
Q1（面试/生产频率）：
  - 参考常见面试资源（JavaGuide、小林coding、面试鸭）
  - 思考："≥50% 的后端工程师面试会问这个吗？"
  - 思考："后端工程师每月会在生产中遇到这个吗？"
  - 不确定 → 标记 [待验证：需用户确认重要度]

Q2（依赖数）：
  - 使用 03 §1 初步依赖扫描的产出（与 03 的粗粒度图是同一产物——共享，不在此独立构建）
  - "A 依赖 B" = 不理解 B 的机制，就无法理解 A 的行为或设计原因。
    依赖是机制层面（不是概念相关性）。只统计同一或相邻主题内的直接依赖。
  - **两阶段执行**：阶段1（本文）用粗粒度扫描——Q2 不确定时默认为"否"。
    阶段2（03 §2 完整依赖图建成后）必须**重跑 Q2** 修正可能被低估的 🟡 候选。
    重跑必须在写作前完成。
```

### 边界规则

- **下限**：面试+生产必备必须达到深层
- **上限**：🟢 条目仅限于表层（1-2 句话）
- **AI 补充**：🔴 条目书只给方向时，AI 必须扩展至深层。这是书范围内补充——主题来自 TOC，深度自生成。🔴 条目书完全没提 → 标记 `[缺口]`，不在此处编造——补充在 04 §4 合并阶段进行。
- **单书主题**：N=1 也可以有 🔴 条目——"频繁被问"不依赖"多少本书覆盖"

| 场景 | 操作 |
|------|------|
| 🔴，书仅给主题方向 | AI 基于外部知识写深层 |
| 🔴，书覆盖但深度不够 | AI 补充到深层 |
| 🔴，书完全没提 | 标记 `[缺口：{概念}]`，按 01 §5 第三步 |
| 🟡，书覆盖充足 | AI 写工作层（无需补充） |
| 🟡，书没覆盖，≥3 依赖 | AI 写工作层 |
| 🟢，TOC 提到 | 1-2 句话 |
| 🟢，TOC 没提 | 不写 |

## 3. 每层写作要求

### 表层（🟢）

```
必须：概念名 + 一句话定义
可选：来源（哪个版本/谁引入的）
禁止：机制解释、行为分析、源码片段

例子：
"O(1) 调度器是 CFS（2.6.23）之前 Linux 的调度器，使用优先级数组实现常数时间调度。"
```

### 工作层（🟡）

```
必须：机制如何工作 + 为什么这样设计
必须：不同场景下的行为（正常、边界、故障）
可选：替代方案对比、设计权衡
禁止：源码片段、内核结构体定义

例子：
"完全公平调度器（CFS）为每个任务分配虚拟运行时间（vruntime）。
vruntime 较小的任务优先运行。I/O 密集型任务自然地累积较少 vruntime，
从而隐式获得比 CPU 密集型任务更高的优先级。nice 值映射到一个权重，
该权重决定 vruntime 的增长速度——更高优先级（更低的 nice 值）
意味着更慢的 vruntime 增长和更多的 CPU 时间。"
```

### 深层（🔴）

```
必须：所有工作层内容
必须：关键架构组件（数据结构名+字段角色、函数签名+调用流程、
      文字版架构图）
可选：源码片段作为结构证据（结构体定义、函数调用链——
      从内核源码或官方文档 grep 验证）
禁止：逐行源码分析、实现细节、补丁级讨论

例子（关键架构组件，文字描述）：
"组件：
- sched_entity：每任务调度状态（vruntime、exec_start、load weight）
- cfs_rq：每 CPU 运行队列根（tasks_timeline：红黑树根，
  min_vruntime：防新任务饥饿，nr_running：活跃任务计数）
- pick_next_task_fair() → pick_next_entity() 选最左节点

流程：时钟中断 → update_curr() → resched → schedule()
→ pick_next_task_fair() → context_switch()

可选源码证据：
  struct sched_entity { u64 vruntime; struct load_weight load; ... }
  struct cfs_rq { struct rb_root_cached tasks_timeline; u64 min_vruntime; ... }
  （grep 验证自 kernel/sched/sched.h）"
```

## 4. 防编造规则（适用于所有写作层）

以下规则在任何 AI 写作时生效——不只是补充时。

1. **每个结构声明必须可独立验证。**
   - 内核结构：在内核源码中 `grep 'struct sched_entity'`
   - 函数签名：通过源码 grep 或外部参考确认函数存在
   - 调用链：验证链中每个函数存在
   - 源码不可访问时标注 `[待验证]`

2. **从 ≥2 个独立来源交叉验证结构声明**（内核源码 grep + 官方文档 + 可信在线参考）。仅 1 个来源时标注 `[待验证]`。

3. **TODO 标记家族** — 所有知识规划文档的统一标记：
   - `[TODO: verify]` — 不确定声明需验证（默认）
   - `[TODO: evaluate]` — 决策需评估（如：这是知识点吗？）
   - `[TODO: verify importance — needs user confirmation]` — 重要度不明
   - `[TODO: <动作>]` — 其他待办
   全部标记用 `[TODO: ...]` 前缀（en）或 `[待...]`（zh）。不得在此家族之外创建新标记格式。

4. **不自创算法或公式**——不知道确切公式时用概念性描述。

5. **补充是填补书范围内的缺口**——不是添加无关主题。

## 5. 产出格式

### 逐知识点深度决策

```
## 深度决策：{知识点名称}

01 优先级：P1/P2/P3（来自 01 §3）
重要性：🔴/🟡/🟢
理由：[根据判定三问写 1-2 句]
目标深度：表层 / 工作层 / 深层
书覆盖：充足（工作层及以上内容）/ 不足（表层或牵强）/ 仅主题方向（TOC 提到概念但无章节内容）/ TOC 提及（仅 TOC 条目，无正文）/ 未提及（零覆盖）

与 04 §1 覆盖等级映射：
- 充足 → 充足
- 不足 → 不足
- 仅主题方向 → 不足
- TOC 提及 → 不足
- 未提及 → 缺失
AI 补充：是 / 否
如需补充，补充范围：概念级（机制解释）/ 结构级（数据结构+调用流程）/ 全深层（满足 §3 深层全部要求）
```

### 主题深度汇总

```
## 深度汇总：{主题名}

| 知识点 | 01 优先级 | 重要程度 | 深度 | 补充 |
|--------|----------|---------|------|------|
| CFS调度 | P1 | 🔴 | 深层 | 全深层 |
| 实时调度 | P2 | 🟡 | 工作层 | 无 |
| O(1)调度器 | P2 | 🟢 | 表层 | 无 |
```

## 6. 完成检查单

主题内所有知识点分档完毕后：

- [ ] **每个知识点已分档**：🔴/🟡/🟢 已分配，含理由
- [ ] **01 优先级已记录**：来自 01 §3 跨书聚合的 P1/P2/P3
- [ ] **下限已满足**：所有面试+生产必备知识达到深层
- [ ] **上限已遵守**：🟢 条目仅限于表层（1-2 句话）
- [ ] **AI 补充范围已定义**：每个需 AI 补充的知识点列出了补充范围
- [ ] **缺口已标记**：🔴 条目书完全没覆盖的标记 `[缺口]`，不编造
- [ ] **无自创声明**：补充时所有结构声明可验证，且尽量从 ≥2 来源交叉验证
- [ ] **不确定性标记一致**：所有不确定声明使用 `[TODO: verify]`（en）/ `[待验证]`（zh）
- [ ] **深度决策已记录**：逐知识点决策表和主题汇总表均已完成
- [ ] **待用户确认**：用户确认重要性分档后再开始写内容

## 7. 反模式

### 1. 书的篇幅决定深度

```
错误："这书有 50 页讲进程调度 → 深层"
正确：实际重要程度决定深度。2 页的 🔴 主题需要 AI 扩展。50 页的 🟢 主题只有 1-2 句话。
```

### 2. 所有知识点一样深

```
错误：每个提取出的知识点都写到工作层
正确：🔴 深层，🟡 工作层，🟢 表层——深度匹配重要性
```

### 3. 补充变成源码分析

```
错误："CFS 深层 → 读内核源码 → 逐行解释 enqueue_entity()"
正确：深层 = 工作层内容 + 架构组件（结构体/函数名、调用流程、架构图）
      + 可选源码片段作为结构证据。不追踪实现体内部。
```

### 4. 跳过面试/生产必备

```
错误："书没详细讲调度延迟 → 跳过"
正确：🔴 条目不管书说什么，AI 必须详细覆盖
```

### 5. 混淆 01 优先级与 02 重要程度

```
错误："P1（3 本书都出现）→ 一定是 🔴 深层"
正确：P1 = 多书共识信号。🔴 = 实际重要程度。独立判断，分别评估。
```

### 6. 知识点讲解中出现"后面会讲"

```
错误："CFS 使用 nice 值（nice 值将在 §进程优先级 中讲解）"
      — 前向引用一个还没讲的概念
正确：如果 CFS 依赖理解 nice 值，必须先讲 nice 值。
      引用已经讲过的概念（"见 §进程优先级——前文已讲"）是正确的——
      拓扑排序的全部意义就是让后讲的知识点可以引用先讲的概念。
```

知识点必须遵循拓扑顺序——和源码分析 02 一样。任何复杂概念 = 基础概念组合。A 依赖 B → 先讲 B，再讲 A。绝不写前向引用（"后面会讲"）到未学的概念。后向引用（引用已讲概念）不仅允许，而且是被期待的。
