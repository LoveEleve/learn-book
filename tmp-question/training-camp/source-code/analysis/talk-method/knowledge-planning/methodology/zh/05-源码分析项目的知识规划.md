# 源码分析项目的知识规划

> 角色：AI 自约束操作规范。对纯源码项目（无 TOC 书籍参考）进行知识规划前必读。
> 先修：knowledge-planning/01~04（TOC 提取流程）
> 输入：源码仓库的文件/包结构
> 阅读顺序：01 → 02 → 03 → 04 → 05（本文）。仅在"无书籍 TOC 参考"模式下使用。

## 核心原则

源码分析项目的知识规划与书籍知识规划使用**相同的方法论管道**（提取→聚合→分类→聚类），但"原材料"不同：

| | 书籍知识规划 | 源码知识规划 |
|------|------|------|
| 原材料 | 书籍 TOC（章/节/小节） | 源文件/包结构 |
| 提取单位 | 每个 Section → 一个知识点 | 每个源文件/类 → 一个机制 |
| 聚合信号 | 几本书提到了同一个概念 | 几个源文件引用了同一个机制 |
| 分类基准 | 后端工程师需要理解什么 | JVM/框架开发者需要理解什么 |
| 聚类基准 | 概念依赖链 | 拓扑排序（A 依赖 B → B 先讲） |

## 1. 提取 — 从源码提取知识点

### 1.1 提取单位

从源码仓库提取知识点时，以**包**为第一级粒度、**核心类/文件**为第二级粒度。

```
包扫描 → 列出所有子包 → 每子包识别核心类 → 每核心类 = 1-N 个机制
```

### 1.2 产出格式

```markdown
## 01 提取 — 逐源映射

### 包: hotspot/share/gc/g1/ (195文件)

| Source File | Inferred Knowledge Point | Confidence |
|------------|------------------------|------------|
| heapRegion.hpp:191 | HeapRegion — G1 的堆分配基本单元 | High |
| heapRegion.hpp:191 | Region 四种角色: Eden/Survivor/Old/Humongous | High |
| heapRegionRemSet.hpp | RSet — 跨 Region 引用索引 | High |
| g1ConcurrentMark.hpp | SATB 并发标记算法 | High |
| g1Policy.hpp | GC 周期编排与预测模型 | Medium |
```

### 1.3 置信度

| 置信度 | 含义 | 例 |
|------|------|------|
| High | 从类声明/方法体直接读取 | `class HeapRegion` → 机制明确 |
| Medium | 从类名推断但未读方法体验证 | `class G1Policy` → 编排逻辑待验证 |
| Low | 从类名猜测，需后续读源码确认 | `class G1MMUTracker` → 可能属于监控子系统 |

### 1.4 什么算"一个机制"

**算机制**（对应书籍知识规划的"算知识点"）:
- 一个独立的数据结构设计（如 `HeapRegion` 的布局）
- 一个算法实现（如 SATB 并发标记）
- 一个跨组件交互协议（如 JIT → GC barrier 的注入协议）

**不算机制**:
- getter/setter/toString — 纯数据访问
- 纯工具类（如 `GrowableArray` — 基础设施，不承载域级设计决策）
- 构建配置（如 `globals.hpp` 中的 flag 声明 — 属于 Arguments 域）

## 2. 聚合 — 跨文件去重

与书籍知识规划的多书交叉验证不同，源码知识规划的聚合基于**文件引用频率**。

```markdown
## 01 聚合 — 跨文件汇总

| KP | 出现文件 | P-Level |
|----|---------|---------|
| RSet 三级存储 | heapRegionRemSet.hpp, g1RemSet.cpp, g1RemSetSummary.cpp | P1 |
| SATB 并发标记 | g1ConcurrentMark.hpp, g1SATBCardTableModRefBS.cpp, ptrQueue.hpp | P1 |
| Humongous 回收 | g1CollectedHeap.cpp:1448, heapRegion.hpp | P2 |
```

**聚合规则**:

| 出现文件数 | 层级 | 
|----------|:--:|
| ≥5 个文件引用 | P1 — 全系统共识 |
| 2-4 个文件引用 | P2 — 局部重要 |
| 1 个文件独有 | P3 — 评估是否为独立知识点 |

## 3. 深度分类 — 🔴🟡🟢

与书籍知识规划使用相同的分类标准（03-分析深度标准），但判断基准从"后端工程师"调整为"JVM/框架开发者"。

```markdown
## 02 深度分类

### 🔴 Deep (承载核心设计决策)

| KP | 为什么🔴 |
|----|---------|
| SATB 并发标记 | 算法选择（SATB vs Incremental Update）— 设计决策 |
| RSet 三级存储 | 数据结构选择（sparse→fine→coarse）— 设计决策 |

### 🟡 Working (有设计决策但非核心)

| KP | 说明 |
|----|------|
| GC 周期编排 | 预测模型很重要但不是 G1 独有 |

### 🟢 Surface (机制性了解即可)

| KP | 放在哪 |
|----|-------|
| MMUTracker | 调优章节作为子主题 |
```

## 4. 聚类 — 教学顺序

```markdown
## 03 聚类

### Cluster A: Region 模型 (6 KP)
Region 类型/布局/commit/BlockOffsetTable — 最底层，无前置依赖

### Cluster B: Young GC (5 KP)  
依赖 A (Region)，不依赖标记 — 先讲简单的 STW 收集

### Cluster C: 并发标记 (8 KP)
SATB/barrier/concurrent marking/remark — 依赖 A+B

### Cluster D: RSet + Refinement (6 KP)
依赖 A+C — 标记后才知道哪些 card 需要记录

### Cluster E: Mixed GC + Full GC (7 KP)
依赖 A+B+C+D — 聚合全部知识

### 教学顺序: A → B → C → D → E
```

## 5. 与 Per-Article Outline 的关系

知识规划（01→02→03→04）是 **Per-Article Outline 的前置步骤**。

```
正确流程: 01提取 → 02聚合 → 03分类 → 04聚类 → Per-Article Outline
错误流程: 直接写 Per-Article Outline（跳过提取/聚合/分类/聚类）
```

知识规划回答了"有哪些知识点、该怎么分类、该怎么排序"——Per-Article Outline 基于这些答案写出"每篇讲什么"。

## 6. 多维分析维度 — 超越纯源码分析的三个视角

源码提取(§1-§4)覆盖了"实现层"——但某些项目需要额外的分析维度来决定域划分和内容深度：

### 6.1 项目类型前置判断

在开始知识规划之前，先判断项目类型：

| 项目类型 | 示例 | 核心分析维度 |
|------|------|------|
| **纯框架** | Netty | 源码提取(§1-§4) + 设计意图 |
| **规范参考实现** | Tomcat(Servlet规范) | 源码提取 + **规范对应表** + 设计模式 |
| **中间件** | RocketMQ | 源码提取 + 架构分层 + 协议设计 |

**规范参考实现**的项目（如 Tomcat 实现 Jakarta Servlet 规范），源码架构是**规范驱动的**——域划分必须反映"规范接口 → 实现类"的映射。

### 6.2 规范/标准维度

如果项目是某个规范的参考实现，知识规划的每个域必须标注：

```
→ 实现规范: ServletContext / ServletConfig / ServletContainerInitializer
```

产出格式——规范-实现对照表（含规范版本）：

| 规范接口 (规范版本) | 实现类 | 所属域 |
|------|------|:--:|
| `jakarta.servlet.Servlet` (1.0) | StandardWrapperValve.invoke() | T-3 |
| `jakarta.servlet.FilterChain` (2.3) | ApplicationFilterChain.doFilter() | T-3 |
| `jakarta.servlet.ServletContainerInitializer` (3.0) | ContextConfig | T-1 |

**规范版本标注规则**: 每个规范接口标注其首次引入的 Servlet 版本，帮助读者理解"这个机制是基础版的还是后来加的"。Tomcat 10.1 对应 Jakarta Servlet 6.0 — 涵盖了 1.0→6.0 的所有接口。

**判断标准**: 检查项目中是否存在独立规范定义的接口包（如 `jakarta.servlet.*`），以及是否有对应的 `org.apache.*` 实现。

### 6.3 设计模式维度

知识规划的"关键设计"列应显式标注使用的 GoF 模式，让读者理解"为什么这样组织"而不只是"怎么实现"：

| 模式 | 在哪 | 标注格式 |
|------|------|------|
| Chain of Responsibility | Pipeline-Valve + FilterChain 双链嵌套 | `[模式: Chain of Responsibility]` |
| Template Method | ContainerBase.startInternal/stopInternal | `[模式: Template Method]` |
| Adapter | CoyoteAdapter (coyote.Request→HttpServletRequest) | `[模式: Adapter]` |

### 6.4 架构维度

逐源提取只能看到"局部实现"——架构维度补充"全局设计的意图"：

- **控制流方向**: 谁调谁？（Tomcat 的"规范调用户" vs Netty 的"框架调用户"——反转的控制流影响架构理解）
- **分层意图**: 每层解决什么问题？层间用什么接口通信？
- **生命周期拓扑**: 组件启动/停止的顺序关系（如 DAG 依赖启动）

### 6.5 维度适用性

不是所有维度适用于所有项目：

| 维度 | 规范参考实现 | 纯框架 | 中间件 |
|------|:--:|:--:|:--:|
| 规范对应 | ✅ 必须 | — | 可选 |
| 设计模式 | ✅ | ✅ | ✅ |
| 架构意图 | ✅ | ✅ | ✅ |

## 7. 域审核前置 — 继承上一个 AI 的范围规划前必读

从一个 AI 交接的源码分析项目时，它的"范围规划"（域发现）不能直接作为知识规划的输入——必须先审核。

### 7.1 审核清单

1. **域过载检查**: 一个域是否塞了过多机制？（指标：域内核心类 > 10 个且行数 > 5000 → 考虑拆分）
2. **子机制遗漏**: 域描述中"一句话带过"的机制是否值得独立？（用 `wc -l` 验证机制规模）
3. **淘汰清单验证**: 排除的功能模块是否确实不需要？（判断标准：Spring Boot 生态系统是否通过其他组件替代）
4. **规范缺口检查**（仅规范参考实现）: 规范层定义的接口是否全部有对应的实现域？

### 7.2 域数量控制原则

- **6-8 域**: 学习型分析（理解核心链路即可）
- **10+ 域**: 全量框架分析（面向掌握者）

**禁止**因"发现缺失的子机制"而过度增加域——子机制可能在现有域中已作为重点覆盖（验证方法：读域描述的源码行数+核心类列表）。

### 7.3 审核后的行动

审核结果可能是：
- **无改动**: 原范围规划合理 → 直接进入 §1 逐源提取
- **微调**: 砍掉被生态替代的域（如 Tomcat Session → Spring Session Redis 替代）→ 调整域数量
- **维度补充**: 在不增加域数量的前提下，在知识规划中增加规范/模式/架构标注

## 8. 淘汰机制处理 — 场景/数据流必须以当代生态方式为主

### 8.1 原则

源码分析的文章中，**场景句(场景:)和数据流(数据流:)不能以淘汰的配置方式为读者默认体验**。必须以该框架在当代生态系统中的实际使用方式为主——淘汰的机制只能作为"备选方案"附带提及。

### 8.2 典型场景

**Tomcat/Servlet 容器类项目**:

| 淘汰方式 | 当代方式 | 规则 |
|------|------|------|
| `server.xml` `<Connector>` 配置 | Spring Boot `server.port=8080` / `TomcatServletWebServerFactory` 程序化配置 | 当代方式为主体，`server.xml` 仅作为"独立部署中..."附带 |
| `web.xml` `<servlet>`/`<filter>` 声明 | `@WebServlet`/`@WebFilter` 注解 / Spring Boot 自动配置扫描 | 注解为当代方式，`web.xml` 作为"传统部署中..."附带 |
| `server.xml` `<Valve>` 配置 | `WebServerFactoryCustomizer` → `engine.getPipeline().addValve()` | 程序化 API 为主体 |

**检测方法**: `grep -rn 'server\.xml\|web\.xml' outlines/` → 所有引用必须是为辅形式（"独立部署中..."、"传统部署中..."），不能作为主场景句。

### 8.3 判断标准

一个机制是否"过时"，不是看它是否还存在于源码中（源码可能保留大量历史兼容代码），而是看**在当前生态中，主流使用方式是否已迁移到替代方案**。判断流程:

1. 该机制的配置方式: 当代项目（Spring Boot 2.x+/Quarkus/Micronaut）用什么方式？
2. 如果当代方式与历史方式不同 → 大纲中以当代方式为主场景
3. 历史方式仅作为"理解底层原理"的附注提及，不作为第一次阅读的场景入口

### 8.4 为什么重要

读者对源码分析的场景句有强烈的"当下感"——如果第一句是 `server.xml` 配置，现代开发者会判断"这是老东西/不学了"。当代方式为主的场景句能**立刻让读者将源码分析与自己的日常开发体验关联**，显著提升学习动机和留存率。

**不良示例**: "`server.xml` 里配了 `<Connector port="8080" protocol="HTTP/1.1">`"
**正确示例**: "Spring Boot `server.port=8080` — 背后 `TomcatServletWebServerFactory` 如何创建 Connector？独立部署中 `server.xml` 同样通过反射找到 `Http11NioProtocol`"
