# 如何从 TOC 提取知识点

> 角色：AI 自约束操作规范。从任何书籍提取知识点前必读。
> 先修：无（基础文档）
> 输入：一本或多本书的 TOC（仅目录大纲，无正文内容）
> 注：主题分组由用户提供或预先指定后开始提取。本文仅处理单主题内的提取。
> 阅读顺序：01（本文）→ 02 → 03 → 04。执行：用户提供主题分组 → 01 提取 → 02 深度分类 → 03 聚类+排序 → 04 合并 → 写作。

## 核心约束

1. **只从 TOC 推断**——不得编造目录中没有的概念、算法或细节。目录只到第 2 层（章→节），就只提取到第 2 层。不猜测小节内容"应该"是什么。
2. **标注不确定性**——每个无法从 TOC 标题文字直接确认的推断知识点，必须标注 `[待验证]`。高置信度提取不需要此标记。
3. **知识点优先**——组织原则是"后端工程师必须理解什么"，不是"这本书包含什么"，也不是"面试问什么"。
4. **禁止编造**——绝不自创 TOC 不支撑的概念、公式或主张。

## 1. 按 TOC 粒度选择提取策略

| TOC 层级 | 例子 | 能提取什么 | 不能提取什么 |
|---------|------|-----------|------------|
| 1 级（仅章） | 第3章："进程调度" | 单个宽泛知识点 | 任何子分解（无节细节） |
| 2 级（章→节） | 第3章 → 3.1 CFS / 3.2 实时 / 3.3 抢占 | 知识点粗粒度列表 | CFS 内部的 vruntime 计算逻辑 |
| 3 级（章→节→小节） | 3.1 CFS → 3.1.1 调度实体 → 3.1.2 vruntime | 知识点的子分解 | 具体算法细节 |
| 4 级+（更深小节） | 3.1.1.1 调度平均 vs 调度实体 | 细粒度子知识点 | 实现级代码细节 |
| 泛化节标题 | "数据结构和算法" | **零**——太泛，不提取 | — |

**规则**：TOC 提供到第几层，就提取到第几层。不根据书名或声誉猜测更深内容。4 级以上 TOC 少见但可提取——提供细粒度知识点分解，但仍不提供实现细节。

## 2. 什么算"一个知识点"

### 算知识点

- 一个后端工程师不懂就无法工作的概念（如：不懂虚拟内存就无法理解 mmap）
- 一个影响系统行为的机制（如：CFS 调度器的 vruntime 如何影响 CPU 分配）
- 一个跨组件交互的契约（如：内核态/用户态切换时保存哪些寄存器）

### 不算知识点

- 纯命令/工具用法（如："grep 的 -r 参数"——这是 man page，不是知识）
- 纯历史（如："Linux 0.01 的调度器只有 100 行"——有趣但非必要）
- 过于具体的硬件细节（如："Intel CPU 的 L1 缓存是 32KB"——硬件手册，不是知识）

### 与 §3 优先级的关系

§2 判断**是否**为知识点（逐知识点的质量判断）。§3 判断其在多书主题中的**优先级等级**（逐知识点的共识信号）。两者用途不同，不冲突：

- 如果知识点通过 §2 但仅出现在 1 本书 → 仍然是知识点，但优先级 3（孤立）
- 如果知识点出现在 3 本书但未通过 §2（如 3 个 TOC 都提到"grep -r 参数"）→ 仍然不是知识点
- §3 的优先级等级绝不覆盖 §2 的是/否判断

## 3. 多书交叉验证——TOC 共识信号

多本书共享类似章节主题但子节结构不同——这不是重复，是**信号**：

```
书A：3.1 CFS / 3.2 实时调度 / 3.3 多核调度
书B：2.1 调度策略 / 2.2 上下文切换 / 2.3 抢占
书C：4.1 CFS / 4.2 调度实体 / 4.3 vruntime 计算

3书都有：CFS → 高优先级（一定是核心知识点）
2书都有：实时调度 → 中优先级
仅1书有：vruntime 计算 → 评估后端工程师是否需要
```

**通用规则**：

| 包含该知识点的书籍数 | 优先级 |
|---------------------|--------|
| 大多数书（>N/2） | **优先级1 — 共识** |
| 少数书（>1 但非大多数） | **优先级2 — 强信号** |
| 恰好 1（仅一本书有） | **优先级3 — 孤立** [待评估：后端工程师需要吗？] |

单书主题（N=1）：所有知识点均为优先级1——无法做交叉验证。在聚合输出中注明：`[N=1 — 共识信号不可用]`。

**多书交叉验证不是去重——是行业共识对"什么重要"的投票。**

## 4. 产出格式

### 单书提取

```
## 知识点提取：{书名}

### 章节映射
| 原书章节 | 推断知识点 | 置信度 |
|---------|----------|--------|
| 第3章 进程调度 | CFS调度策略 | 高（3.1 明确提到"完全公平调度"） |
| 第3章 进程调度 | 调度器数据结构 | 中（3.5 节标题含糊，待读正文确认） |
| 第3章 进程调度 | 上下文切换机制 | 高（3.3 节标题明确写"上下文切换"） |
```

### 主题聚合（一个主题下所有书提取完毕后）

```
## 主题：{主题名} — 跨书知识点聚合

分析书籍数：{N}

### 优先级1 — 共识（大多数书，>N/2）
- CFS调度策略（书A §3.1、书B §2.1、书C §4.1）

### 优先级2 — 强信号（少数书，>1 但非大多数）
- 实时调度（书A §3.2、书C §4.2）

### 优先级3 — 孤立（仅 1 本书出现）
- vruntime 计算 [待评估：后端工程师需要吗？]（书C §4.3）
```

### 置信度等级

| 等级 | 判定标准 |
|------|---------|
| **高** | TOC 标题明确命名该概念，无需消歧 |
| **中** | TOC 标题暗示该概念，但措辞含糊或使用通用术语 |
| **低** | 与 TOC 标题仅模糊相关；概念从上下文推断而非显式标题 |

置信度仅由 **TOC 标题特征**决定——显式名称匹配、标题具体性、概念到标题的距离。不使用 AI "感觉不确定"作为判断标准。在两级之间犹豫时，选低的那一级。

## 5. 执行步骤

### 第一步：单书提取
1. 从头到尾阅读 TOC
2. 对每个章节，用 §2 标准识别候选知识点
3. 按 §4 标准分配置信度
4. 输出单书提取表

### 第二步：多书聚合（每个主题）
1. 收集该主题下所有单书提取表
2. 按知识点名称分组（归一化同义词："Context Switch" = "上下文切换" = "Process Switch"）
3. 统计各知识点在不同书中出现的次数
4. 按 §3 规则分配优先级等级
5. 输出主题聚合表

### 第三步：缺口分析
1. 对比提取的知识点与预期主题范围（从主题名推断："进程管理"、"内存管理"等）
2. 标记明显缺失的知识点：`[缺口：{概念} 本主题中无书覆盖——需外部来源或重新评估主题范围]`

---

## 6. 完成检查单

主题内所有书籍的知识点提取完毕后：

- [ ] **所有书已提取**：主题内每本书都有单书提取表
- [ ] **无编造**：每个提取的知识点可追溯到 TOC 标题
- [ ] **不确定性已标注**：所有中、低置信度条目标注 `[待验证]`
- [ ] **优先级已分配**：跨书聚合完成，含共识投票优先级
- [ ] **缺口已标记**：任何缺失的预期知识点标记 `[缺口：...]`
- [ ] **单书主题已注明**：如 N=1，标注"共识信号不可用"
- [ ] **同义词已归一**：同一概念跨书使用同一个标准名称
- [ ] **待用户审查**：全部产出按 §4 模板格式化

---

## 7. 反模式

### 1. 直接抄目录

```
错误："第1章 → 知识点1，第2章 → 知识点2"
正确：章节标题是输入，不是产出。将每章分解为面向后端工程师的子知识点。
```

### 2. 根据书名声誉猜测

```
错误："这是《Linux内核深度剖析》，所以一定详细讲了内存屏障"
正确：目录没有内存屏障，就不提取。标记缺口："[缺口：本主题暂无书籍覆盖内存屏障]"
```

### 3. 面试题导向提取

```
错误："CFS → 'CFS和O(1)调度器有什么区别？' → 提取为问答对"
正确："CFS调度策略"——这是知识点。面试题是掌握知识后的自然产物。
```

### 4. 全部标"高"置信度

```
错误：所有行标"高"，因为标题"听起来是对的"
正确：只在标题文字零歧义时标"高"。在两级之间犹豫时选低的那一级。
```

### 5. 跨书同义词漂移

```
错误：书A提取为"Context Switch"，书B为"上下文切换"，书C为"Process Context Switching"
正确：跨书使用同一个统一的英文标准名称。如有必要，在括号中注明原始标题措辞。
```
