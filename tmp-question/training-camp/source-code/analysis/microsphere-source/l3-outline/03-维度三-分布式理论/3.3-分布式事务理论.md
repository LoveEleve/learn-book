## 1. 问题定义：为什么本地事务不够

本地事务（ACID——1.3/2.5 已述）**保证单库**。跨库/跨服务时：订单库提交了、库存库失败了——**没有"全局事务管理器"来保证整体原子性**——这就是分布式事务问题的本质（2.5 交叉）。

三种主流方案：**2PC**（强一致——锁的代价）/ **TCC**（业务级补偿——无锁）/ **SAGA**（长事务补偿链——最终一致）。

---

## 2. 2PC：两阶段提交（理论——[过时→Seata AT]）

### 五角色（stage-2-15 KP-02）

```
TM（事务管理器——协调者）
  ├── 每个 RM（资源管理器——数据库/队列——阶段一/二的执行者）
  ├── AS（应用服务器——托管基础设施）
  ├── TA（事务应用——发起事务的业务）
  └── CRM（通信资源管理器——事务上下文传播）
```

### 两阶段（实验 `TwoPhaseTest` 验证）

```
阶段一 Prepare：TM 问所有 RM"能提交吗"（RM 锁资源——prepare:xxx）
阶段二 Decide：全票 Yes → COMMIT（commit:xxx）；任一 No → 全部 ABORT（abort:xxx）
```

### 理论性质（为什么过时）

1. **阻塞问题**：阶段一后资源锁住直到全局决定——**长锁**（高并发不可接受）
2. **协调者单点**：TM 挂了 → 参与者卡在"已准备"状态（等决定）
3. **要求 RM 支持 XA**：数据库/队列要支持 XA 协议（选型限制）

**结论**：2PC 理论正确（全票提交/任一否决回滚——实验验证），但**阻塞 + 单点 + 选型限制**让它不适合互联网高并发——**Seata AT 模式**是它的改良（UNDO 日志 + 同事务提交立即释放锁——2.5 详述）。

## 3. TCC：业务级两阶段（理论）

### 历史（stage-2-18 KP-01——重要）

**Pat Helland 2007**《Life beyond Distributed Transactions》提出（原名 Tentative-Confirmation-Cancellation）→ **Atomikos** 正式化（注册 TCC 商标）→ 阿里程立 2008 引入国内——**TCC 是"2PC 的补偿变体"**：Try（预留）/Confirm（提交）/Cancel（回滚）用**业务逻辑**实现，避免 2PC 锁资源。

### 为什么能避免锁

2PC 锁"数据库行"（RM 层面）；TCC 锁"业务资源"（业务自己控制——库存冻结/账户预留）——**锁粒度从数据库到业务，由业务决定锁多久**（这是 TCC 的核心理论价值）。

**与 2PC 的精确映射**（"补偿变体"的具体含义）：**Try = Prepare（预留）/ Confirm = Commit（确认）/ Cancel = Abort（回滚）**——三方法就是两阶段的业务化改写——只是"锁什么、锁多久"从数据库协议交给了业务代码。

### 三问题（所有 TCC 实现的必答题——2.5 实验验证）

幂等（重复 Try/Confirm/Cancel 只生效一次）/ 空回滚（Cancel 先到）/ 防悬挂（Confirm 先到）——**理论要求：任何乱序到达都不能造成错误状态**。

## 4. SAGA：长事务补偿链（理论）

### 本质

长流程（订单 → 支付 → 库存 → 物流——2.5 的可靠事件是其实现）——**没有全局锁**，每步提交后记录补偿操作——失败时**反向执行补偿链**（第 N 步失败 → 补偿 N-1...1）。

### 两种编排

| 编排 | 机制 | 实现 |
|------|------|------|
| 编排式（Orchestration） | 中央协调器调各步 + 补偿 | Seata SAGA |
|  choreography（编排式/事件式） | 各步发事件触发下一步（无中心） | **可靠事件/Outbox**（2.5——"SAGA 的事件驱动版"） |

**对比 TCC**：TCC 是"业务两阶段"（Try 预留），SAGA 是"长事务补偿链"（每步提交后补）——**SAGA 无锁但补偿复杂度随链长增长**。

**补偿的可靠性**（SAGA 的隐藏代价）：补偿操作**必须幂等 + 可重试**——补偿本身也可能失败（网络/宕机）——"补偿的补偿"靠重试 + 幂等兜底（2.5 的 Outbox 重试/事件幂等是 SAGA 补偿链的实现面）。

> 可跳过（进阶级）：**3PC**（三阶段提交——为解 2PC 阻塞的理论尝试：协调者故障时参与者可主动中止——但引入新的活锁问题——**实践中极少用**——知道存在即可，工程答案还是 Seata AT）。

## 5. 理论对照表（选型的理论依据）

| | 2PC | TCC | SAGA |
|---|-----|-----|------|
| 一致性 | 强（全票） | 强（业务两阶段） | **最终一致** |
| 锁 | **数据库长锁** | 业务预留（可控） | **无锁** |
| 侵入 | RM 支持 XA | 业务三方法 | 业务补偿方法 |
| 适合 | 传统企业（[过时→AT]） | 预留资源（库存/账户） | 长流程（订单履约链） |
| 理论代价 | 阻塞/单点 | 三问题 | 补偿链复杂度 |

**选型第一问（与 3.1 呼应）**：业务要哪种一致性？——要强一致 → TCC/AT；能最终一致 → SAGA/Outbox——**"一致性级别先定，方案后选"**。**TCC/SAGA 就是 3.1 的 BASE（最终一致）在事务域的工程实现**——"软状态 + 最终收敛"的落地。

## 本章小结

**知识本体**：分布式事务 = 本地事务的边界外推——**2PC**（五角色 + 两阶段 + 阻塞/单点/选型三代价——实验验证）+ **TCC**（2PC 补偿变体——业务锁粒度 + 三问题 + 历史）+ **SAGA**（长事务补偿链——编排 vs 事件式——Outbox 是其事件版）+ 理论对照表（一致性/锁/侵入/代价）。

**实验验证**：2PC 全票提交 / 任一否决全回滚（2 断言——spec-tx 的 TwoPhaseTest）+ TCC 三问题 / Outbox（2.5 章节 4 断言）。

**my-xhs 判定**：TCC 理论已用（TccFenceService——三问题的落地实证——2.5）/ SAGA 型已用（异步链路——Outbox 场景）/ 2PC 不该用（阻塞代价——单库场景不需要）。
