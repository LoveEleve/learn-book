# 19. 共识算法：让多节点"说同一个答案"

> 配套实验：`sca-lab/custom-java-infra/spec-consensus`（3 个断言——Raft 核心机制模拟）
> 定位：**共识理论 → 工程实现 → 训练营运用**三段式（Paxos/Raft/ZAB + SOFAJRaft/ZK/Nacos）
> 课程来源：stage-2-02、stage-2-03、stage-2-04、stage-2-05、stage-2-06、stage-2-07、stage-2-08、stage-2-11（8 篇主属）+ 本地源码锚点（sofa-jraft/zookeeper/nacos）
> 前置：3.1 章节（CAP——CP 系统的理论基础）

多个节点对同一个问题**必须给出同一个答案**（不能你说是 A 我说是 B）——这就是**共识**。Zookeeper 选 Leader、Nacos 配置一致、SOFAJRaft 日志复制——全是共识算法的运用。这一章按"理论 → 实现 → 运用"三段讲透：Paxos（理论先驱）→ Raft（工程标准）→ ZAB（ZK 的原子广播）→ 工程实现 → Nacos 的运用。

---

## 1. 共识问题与状态机复制（stage-2-03 KP-02）

**为什么需要共识**：多副本系统要保证"所有副本按相同顺序执行相同命令"（**状态机复制**——State Machine Replication）——执行序列一致，状态才一致。**共识 = 让所有节点对"命令序列"达成一致**——这是复制日志（SOFAJRaft/Kafka/ZK 数据）的共同底座。

---

## 2. Paxos：理论先驱（stage-2-02）

| 要素 | 内容 |
|------|------|
| 角色 | Proposer（提）/Acceptor（审）/Learner（学） |
| **仲裁** | 多数派（Quorum——过半）——两个多数派必有交集（安全性的根基） |
| 提议编号 | 全局唯一递增（约束：编号大的提议优先） |
| 属性 | 安全性（不选出冲突值）+ 活性（最终选出） |

**历史与演进**：Paxos 由 Lamport 提出（教堂比喻论文——出了名地难读）——理论正确但工程实现难——**Raft 就是 Multi-Paxos 的工程简化**（"Paxos 是理论，Raft 是工程"——Raft 论文明确说自己是 Paxos 的重新设计）。

---

## 3. Raft：工程标准（stage-2-03——主讲）

### 三子问题（KP-03）

Raft 把共识拆成三个独立子问题（工程化的关键）：

```
① 领导者选举（Leader Election）
② 日志复制（Log Replication）
③ 安全性（Safety）
```

### 选举（KP-05——实验 `electionNeedsMajority` 验证）

**任期（Term）**：每次选举任期 +1；节点投票给"任期更新且日志更新"的候选者；**候选者得多数票当选**——实验：3 节点全活 → 当选；剩 1 台 → 选不出（不可用——CP 的正确表现）。

### 日志复制与提交（KP-06/07——实验 `logReplicationCommitsOnMajority` 验证）

```
Leader 追加命令到本地日志
  → 复制给所有节点（AppendEntries）
  → 多数派确认 → 提交（committed——状态机执行）
```

**日志匹配属性**（KP-07）：两条日志在相同 index 的 term 相同 → 之前的所有条目也相同（索引传递性——冲突时 Leader 强制覆盖）。

**关键属性**（stage-2-03 KP-04）：**选举安全性**（任一任期最多一个 Leader——多数派互斥保证）+ **Leader 追加原则**（Leader 从不删除/覆盖自己的日志——冲突只改副本）+ **状态机安全**（提交顺序一致——多数派提交的日志必然已在 Leader 日志里）。

**多数派容错**（实验 `majorityTolerance` 验证）：3 节点容 1 故障——**2 台挂 → 不可用**（< 多数派——CP 的可用性边界——与 3.1 的 CAP 对照）。

## 4. ZAB：ZK 的原子广播（stage-2-04 + 2-11）

ZAB（ZooKeeper Atomic Broadcast）与 Raft 同代（更早）——核心差异：

| | Raft | ZAB |
|---|------|-----|
| 目标 | 状态机复制（通用） | **主备原子广播**（数据一致性） |
| 主序属性 | — | **事务按 Leader 提议顺序全序交付** |
| 恢复 | 日志重放 | **高效恢复**（历史提议 + 快照——事务标识 zxid） |
| 三阶段 | 选举/复制/安全 | 发现/同步/广播（三阶段消息——stage-2-04 KP-06） |

**前缀交付 + 幂等**（KP-03）：状态变更按提交前缀顺序交付（不跳号）+ 重复交付幂等——"广播的顺序一致性"。

> 可跳过（进阶级）：**流水线**（stage-2-04 KP-04——ZAB 允许多个未完成提议并行推进——吞吐的关键——对比单提议串行）；SOFAJRaft 功能特性（stage-2-05 KP-02——多副本/故障转移/线性一致性读——"读优化"是 Raft 的进阶）。

**ZK 实现**（stage-2-11）：`QuorumPeer`（仲裁参与方——服务器状态/选票 Vote 结构——源码锚点）+ Leader 选举（变更投票规则——比较 zxid + sid）+ 请求处理器链（PrepRequest→Proposal→Commit——三阶段落地）。

## 5. 工程实现对照（SOFAJRaft——stage-2-05/06）

| 组件 | 职责（源码锚点：jraft-core Node/NodeImpl） |
|------|------|
| `Node` | 共识节点门面（选举/复制/状态机触达） |
| 日志存储 | 复制日志持久化（`LogStorage`——实验的 log 列表的工程版） |
| Meta 存储 | 任期/投票持久化（重启不丢） |
| 快照存储 | 日志压缩（长日志 → 状态快照——恢复加速） |
| 状态机 | 提交命令的执行者（`StateMachine`——apply 回调） |
| RPC 服务端 | 节点间通讯（选举/复制消息） |

**Closure/Status/Task**（stage-2-06 KP-02）：异步回调模型（Raft 的"请求-回调"——命令提交后回调执行结果）——**异步是共识实现的标准形态**（对比同步等待）。

## 6. 运用：Nacos 的 CP/AP（stage-2-07/08）

### Nacos 内核：一致性协议抽象（KP-04/05）

`ConsistencyProtocol` 接口（源码锚点：nacos core 的 `ConsistencyProtocol`）——**协议可插拔**：`JRaftProtocol`（CP 实现——配置一致）+ Distro（AP 实现——服务注册）。**"双协议"的代码落地**（3.1 的 CAP 选型在这里变成接口实现）。

### Distro 协议（KP-01~07——AP 面）

| 环节 | 机制 |
|------|------|
| 设计思想 | 去中心化（无 Leader——每个节点可写）+ 异步复制 |
| 写操作 | 本地写 + 异步同步到其他节点（最终一致） |
| 读操作 | 本地读（可能旧——AP 语义） |
| 数据校验 | 定期校验（对账——修复漏同步） |
| 初始化 | 启动时全量拉取 |

**Raft（CP）vs Distro（AP）对照**：Raft 多数派提交（强一致——写要等多数）；Distro 本地写异步复制（最终一致——写快但有滞后窗口）——**同一 Nacos 内两种一致性并存**（注册 AP + 配置 CP——3.1 的教科书落地）。
