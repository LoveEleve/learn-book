# 18. CAP 与 BASE：分布式系统的"选型第一问"

> 配套实验：`sca-lab/custom-java-infra/spec-theory`（3 个断言——CAP 分区模拟）
> 定位：**理论基座**——贯穿全部分布式主题的判定框架（每个分布式问题的"选型第一问"）；PACELC 非缺口（stage-2-01 KP-02 已覆盖——总览 [缺口] 标注修正）
> 课程来源：stage-2-01（7 KP 主属）+ 源码 08（最终一致）+ 训练营实践锚点（ZK/Nacos/MySQL 复制）
> 前置：分布式基础概念

设计任何分布式系统，第一个要回答的问题：**"网络分区了怎么办？"** CAP 定理说：不可能三全其美，必须先做取舍。这一章把 CAP/BASE/PACELC/一致性模型讲透——后面所有章节（注册中心 AP/CP、配置 CP、复制最终一致）都是这套理论的落地。

---

## 1. CAP 定理（Brewer 定理——stage-2-01 KP-01）

三个性质：

| | 含义 |
|---|------|
| **C**（Consistency） | 所有节点访问同一份**最新**数据 |
| **A**（Availability） | 每次请求都能得到**非错**响应（不保证最新） |
| **P**（Partition tolerance） | 网络分区（通信超时）下的继续运作 |

**核心论断**：网络分区**不可避免**（P 是现实不是选择）——分区发生时，必须在 C 和 A 之间二选一：**取消操作**（保一致——CP）或**继续操作**（保可用——AP）。

**实验验证**（`partitionCpRejectsWrite`/`partitionApAcceptsWrite`）：两节点 + 分区开关——CP 模式分区时**拒绝写入**（一致性优先）；AP 模式分区时**接受写入**（可用性优先——副本不一致——恢复后需冲突解决）。

> **关键澄清（面试必答）**：CAP 的一致性 ≠ ACID 事务的一致性——两者语义截然不同（CAP 是"多副本最新数据"，ACID 是"单事务原子性"）。

> 可跳过（进阶级——stage-2-01 KP-03）：**CAP 历史**——Brewer 2000 年 PODC 演讲提出（直觉命题）→ **Gilbert/Lynch 2002 年形式化证明**（严格定理）——"讲出来的是猜想，被证明的才是定理"。

---

## 2. "三取二"的误导 + PACELC（stage-2-01 KP-02）

**"CAP 就是三选二"是误导**：无分区时 C、A 可同时满足——CAP 的取舍**只在分区时刻发生**（"分区时必须二选一"，不是"平时必须三选二"）。

**PACELC 是补全**（Brewer 团队后来提出）：

```
P（分区）→ 在 A/C 间选
A（无分区/正常）→ 在 L（延迟）/C（一致性）间选
```

**PACELC 的实践意义**（实验 `pacelcTradeoffWithoutPartition` 验证）：无分区时也在取舍——**同步复制**（强一致但延迟高——写要等副本 ack——Raft 的**多数派写入**就是"同步"的共识版，3.2 章节）vs **异步复制**（延迟低但副本可能滞后——最终一致——2.1 的传播延迟/2.6 的 MySQL 主从都是 PACELC 的 L-C 权衡）。

## 3. CAP 选型落地（stage-2-01 KP-04——训练营实践锚点）

| 系统 | 取舍 | 理由 |
|------|------|------|
| Zookeeper | **CP** | 协调服务要强一致（2.1 的临时节点语义依赖） |
| Nacos 注册 | **AP**（Distro） | 注册中心挂了服务也要能查 |
| Nacos 配置 | **CP**（JRaft） | 配置不能乱（2.2） |
| Eureka | AP | 历史（2.1 已述——纯 AP 单协议） |
| MySQL 主从 | 最终一致 | 异步复制（PACELC 的 L-C 权衡——2.6） |

**"注册要 AP、配置要 CP"**是 Nacos 双协议的设计动机——CAP 理论的教科书落地（2.1/2.2 章节的收束）。

## 4. BASE 与最终一致性（stage-2-01 KP-05/06）

**BASE**（CAP 中 A/C 的工程折中）：

| 要素 | 含义 |
|------|------|
| **B**asic Availability | 基本可用（部分功能降级，整体可用） |
| **S**oft state | 软状态（副本可暂时不一致） |
| **E**ventually consistent | 最终一致（无新写入后，副本最终收敛） |

**最终一致性**：AP 系统的承诺——"不是立即一致，而是**最终**一致"。达成路径：**复制**（2.6 的 MySQL 主从/Binlog、2.8 的跨区复制）+ **冲突解决**（last-write-wins/版本号——2.10 的事件可重投幂等）。

**两个工程含义**：①**"最终"没有时间上界**——"最终一致"不承诺 1 秒还是 10 分钟（无界——业务要能容忍不确定的滞后窗口）②**脑裂风险**——分区期间两端都可能变成"主"（双主/双持锁——2.8 多活反模式的 Split-Brain 是 CAP 分区的直接后果——理论到工程的映射）。

**BASE vs ACID**：BASE 是 ACID 的工程对立面——ACID 追求"强一致 + 隔离"，BASE 接受"最终一致 + 降级可用"——**选 ACID 还是 BASE 取决于业务能否容忍滞后窗口**。

> 可跳过（进阶级）：**一致性模型谱系**（stage-2-01 KP-07）——强一致（线性一致性——CP）/因果一致/读己之写/最终一致——**越往右性能越好、实现越简单**——"选型先定一致性级别"。

---

## 5. 复制三陷阱（源码 08 交叉——最终一致的坑）

最终一致不是免费的——复制链路三个陷阱（源码 08 问题域）：**复制延迟**（副本滞后窗口——2.1 传播延迟）、**复制冲突**（双写冲突——版本/合并策略）、**复制丢失**（网络/顺序问题丢更新）。**"最终一致"的前提是复制链路正确**——这也是 2.8 的 Binlog 脏窗口（Canal 切换消费位点丢/重）的理论根源。

## 本章小结

**知识本体**：CAP 定理（C/A/P + 分区必然性 + 分区时二选一）+ **"三取二"误导**（取舍只在分区时刻）+ **PACELC**（无分区时也在 L/C 间权衡——同步 vs 异步复制）+ CAP 选型落地（ZK CP/Nacos 双协议/MySQL 最终一致）+ **BASE**（基本可用/软状态/最终一致）+ 一致性模型谱系 + 复制三陷阱。

**实验验证**：分区 CP 拒写 / 分区 AP 接受写（不一致窗口）/ PACELC 同步 vs 异步复制（3 断言）。

**my-xhs 判定**：CAP 理论已用（Nacos 双协议——注册 AP + 配置 CP 实证——2.1/2.2）/ 最终一致已用（MySQL 主从——2.6）/ PACELC 已用（异步复制——延迟优先——2.1 传播延迟的实证）。
