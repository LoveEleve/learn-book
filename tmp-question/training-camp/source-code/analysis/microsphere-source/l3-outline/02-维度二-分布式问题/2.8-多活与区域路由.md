# 15. 多活与区域路由：让系统"换个机房也能活"

> 配套实验：`sca-lab/custom-java-infra/spec-zone`（3 个断言）
> 定位：**训练营收束主题**（13 篇主属 + 源码 06/07）——上篇讲 Zone 机制（区域路由），下篇讲存储与 JDBC 多活；理论基座（多活六级/部署模型）在 3.4 章节
> 课程来源：stage-4-02~08/13/16~19/22 + 源码 06（Zone）+ 源码 07（动态数据源联动）
> 前置：2.1（服务发现）、2.3（LB Zone 感知）、2.6（存储）

**多活**：一个机房挂了，流量切到另一个机房，系统继续服务。**区域路由**：请求优先路由到本机房（同 zone）的实例——延迟低 + 故障隔离。这一章是训练营的收束主题：上面所有章节（发现/LB/网关/存储）在多活场景的最终形态。上篇讲 Zone 机制，下篇讲存储与 JDBC 多活。

---

# 上篇：Zone 机制（区域路由的核心）

## 1. 从多活六级说起（3.4 交叉——一句版）

多活六级（接入层→无状态服务层→配置层→数据库层→缓存层→消息层）+ 两种部署模型（按 Zone 独立部署 vs 单实例多 Zone）——**训练营的部署模型 = 单实例多 Zone**（一个实例内按 zone 切换数据源——理论细节在 3.4 章节）。

## 2. Zone 自动发现：两段式 SPI（源码 06 一章）

**"我现在在哪个 zone？"**——不能用配置文件写死（换机房就错），要自动发现。源码 06 的两段式 SPI（实验 `twoStageLocatorSpi` 验证）：

```
Locator.supports(context)  → 认领（"这个来源我认识"）
Locator.locate(context)    → 定位（"从这拿 zone"）
```

多实现（云元数据探测/AWS 家族/环境变量/系统属性）按优先级尝试，**首个认领者生效；无认领 → DEFAULT 兜底**（保守——不会因未知来源挂掉）。stage-4-07 KP-01/02 的 ZoneLocator 抽象 + 内建实现（优先级）同构。

## 3. ZoneContext：全局状态（源码 06 二章）

**核心设计**：zone 是**全局可变状态**——所有组件（LB/Filter/数据源）读同一个值。源码 06 的做法（实验 `zoneContextGlobalStateWithConservativeDefault` 验证）：

- **全局单例**（静态——非 Spring 可达）
- **保守默认值**（未配置 → DEFAULT——不会因未知 zone 挂掉）
- **双事件桥接**（JavaBeans 属性变更 → Spring 事件——ZoneContextChangedEvent——配置/探测变化驱动全局更新）

my-xhs 的 `ZoneContext`（zone 包实证——`DEFAULT_ZONE` 常量族 + 全局状态）就是这套机制的整体移植（handover 实证：逐字段对应）。

> 可跳过（进阶级）：stage-4-08 的 AZLocator 加餐——Zone 组件事件监听器族（zone 变化的监听面）+ **Zone 元信息上报**（实例注册时把 zone 写进注册中心）+ 自动装配两方案（双通道装配——4.3 交叉）。

## 4. 区域优先路由：三重保护（源码 06 三章）

路由决策的完整保护链（stage-4-07 KP-03/04 + 源码 06 三章）：

1. **ZonePreferenceFilter**（实验 `zonePreferenceFilter` 验证）：同 zone 可用实例优先 → 同 zone 无可用 → 跨区兜底（所有可用）→ 全不可用 → 空
2. **可用性检查**：只路由到可用实例（`available` 标记——健康检查联动）
3. **LB 侧 Supplier**（ZonePreferenceServiceInstanceListSupplier——2.3 章节的 Zone 感知——my-xhs zone/loadbalancer 包实证）

**设计要点**：同 zone 可用性不足时**兜底跨区**（不因区域故障全断）——"区域优先但不是区域死锁"。

## 5. 注册元数据闭环（源码 06 四章）

**注册时带 zone 元数据**（2.1 章节）→ **消费者解析元数据**（实例的 zone 从哪来）→ **路由决策**（Filter/Supplier 消费）——"注册元数据 → 区域感知"的完整闭环。stage-4-05/06 的多注册中心（CompositeDiscoveryClient——2.1 的 Union 模式）+ 跨域认证隔离（KP-04）。

**客户端按需订阅**（stage-4-04——现代发现的优化核心）：全量订阅的问题（每个客户端订阅全部服务 = 带宽/内存浪费）→ **按需订阅**（只订阅自己调用的服务——Nacos 的按需订阅/SCG 按需——"发现从全量广播进化到按需拉取"——2.1 的发现模式在现代的演进）。

**Dubbo 多活**（stage-4-13）：Dubbo Router SPI 区域路由（自定义 Router 实现按 zone 选实例——Dubbo 扩展点面——4.3 交叉）+ 动态配置实时更新（路由规则热更新——2.2 交叉）。

## 6. 事件驱动重建：03→06→07 传播链（源码 07 1.3）

**配置/Zone 变化 → 数据源重建**——跨仓库事件链的终点（handover 关键链路）：

```
03 PropertySourcesChangedEvent（配置变化）
  → 06 ZoneContextChangedEvent（zone 变化——双事件桥接）
  → 07 DynamicJdbcConfigChangedEvent（数据源配置变化）
  → DynamicDataSource 重建（只重建含 ha-datasource 的单元——zone 切换联动）
```

**这是"配置变化 → 全链路联动"的完整实证**——2.2/2.10 章节的事件化在这里收束。

## 7. my-xhs 移植实证（已用 10 KP）

zone 包整体移植（代码实证）：`ZoneContext`（全局单例）/`ZoneResolver`+`ServiceInstanceZoneResolver`（两段式定位）/`ZonePreferenceFilter`（区域优先）/`ZonePreferenceServiceInstanceListSupplier`（LB 集成）/`ZoneContextAutoConfiguration`+`ZoneProperties`（自动装配）/`redis/interceptor`（RedisMethodInterceptor——命令拦截移植——2.6 交叉）。**真实差距（该用没用 5 KP）**：多源 SPI 定位/组合定位器/云元数据探测（Nacos 声明式替代——单 zone 场景够用）。

## 多活反模式与工程陷阱（stage-4 梳理 §六——缺陷家族素材）

1. **伪多活**：只做了入口切流，底层 MySQL/Redis 仍单机房——故障时数据层不可用
2. **死亡三角量化**：CAP 三选二 × RTT——跨洲延迟必然舍弃强一致，不存在"全球强一致多活"
3. **跨区锁 Split-Brain**：Redisson RLock 在 Redis Cluster Multi-AZ 下可能双持锁（2.6 交叉——除非所有节点同一 CP 组）
4. **自我保护误读**：保护模式返回旧数据 ≠ 系统故障——区分"发现降级"和"系统故障"
5. **Binlog 脏窗口**：Canal 切换消费位点瞬间丢/重数据——配幂等消费 + Checkpoint
6. **全局 ID 冲突**：Snowflake workerId 跨区分配冲突——用 Leaf-Segment/CosId 号段
7. **监控区分主动切流 vs 被动降级**：主动 = 静默切换，被动 = P0 告警——告警策略完全不同
8. **Chaos 5 级递进**：单服务 → 单 AZ → 跨 AZ 网络 → 全 AZ 摘除 → 恢复演练——每级验证自动切换与自动恢复

**教学定位**：多活不是"方案堆叠"——反模式清单是上线前的检查表（缺陷家族总表收束处）。

## 本章小结

**知识本体**：多活 = **Zone 机制**（两段式发现 → ZoneContext 全局态 → 区域优先三重保护 → 注册元数据闭环 → 事件驱动重建）+ **存储多活**（MySQL Binlog/MGR、JDBC Multi-Host、Redis 事件化复制 + 2025 现代方案）+ **动态数据源两架构**。

**实验验证**：ZoneContext 保守默认 / 两段式定位兜底 / 区域优先过滤（3 断言）。

**my-xhs 判定**：Zone 机制**已用（整体移植——10 KP 实证）**/ 预建池切换已用 / Nacos Distro 现代方案已用（注册面）/ **云元数据探测该用没用**（单 zone 场景）/ **跨区复制该用没用**（差距 TOP④）/ 事件传播链该用没用（原生监听直连——无传播层，简化合理）。
