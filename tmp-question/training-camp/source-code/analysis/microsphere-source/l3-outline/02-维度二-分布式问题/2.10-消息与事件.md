# 17. 消息与事件：让系统"互相通知"

> 配套实验：`sca-lab/custom-java-infra/spec-event`（3 个断言，Spring 事件 + 分发器实测）
> 定位：**事件化模式家族主落位**（11/14 仓库）——事件三要素 + 分发机制 + 本地 vs 分布式 + 传播链收束
> 课程来源：stage-3-14/16（2 篇主属）+ 源码 02（事件分发器）+ 源码 03（事件拦截链）+ 源码 10（RedisCommandEvent）
> 前置：2.5（Outbox——事件的一个应用）、2.8（事件传播链）

**事件驱动**：A 发生了某件事，B 想知道——不是 A 调 B（耦合），而是 A 发"事件"，B 订阅"事件"（解耦）。这是微服务解耦的核心机制（11/14 个 microsphere 仓库用它——**事件化是生态第二大模式家族**）。这一章把事件讲透：三要素、分发机制、本地 vs 分布式、以及训练营的传播链收束。

---

## 1. 事件驱动三要素（stage-3-14 KP-01）

| 要素 | 干什么 |
|------|--------|
| **事件**（Event） | 数据载体（"发生了什么"——订单创建/配置变更/Zone 变化） |
| **发布者**（Publisher） | 发事件（不关心谁听） |
| **监听器**（Listener） | 收事件（不关心谁发） |

**解耦的本质**：发布者不认识监听器——中间靠**事件分发器**（把事件送到该听的人手里）。

---

## 2. 分发机制：类型键缓存 + 继承匹配（实验实证）

事件分发器的两个核心语义（源码 02 5.1——实验 `dispatcherTypeKeyAndInheritanceMatching` 验证）：

1. **类型键缓存**：监听器按事件类型注册（`Map<事件类, 监听器列表>`——类型即键）
2. **继承匹配**：发布子类事件 → 沿类型链向上命中所有监听器（`OrderCreatedEvent` 命中 created + order + event 三个监听器）

```java
// spec-event EventDispatcher（核心语义）
while (type != null && type != Object.class) {      // 沿类型链向上
    listeners.get(type)?.forEach(l -> l.accept(event));  // 命中即分发
    type = type.getSuperclass();
}
```

**Spring 的实现**：`ApplicationEvent`（事件基类——spring-context 实证）+ `ApplicationEventMulticaster`（多播器——继承匹配同款语义）+ `@EventListener`（实验 `springEventListener` 验证）。**时序铁律**（静默失效家族 P1——2.9 详述）：`@EventListener` 在自动配置早期注册 → **早期事件永不触发**——**事件系统要回答"谁在什么时候注册"**（启动缓冲-转移模式——2.9 交叉）。

**本地事件两形态**（stage-3-16 KP-01）：①**同步**（默认——发布者线程直接调监听器——简单但阻塞发布路径）②**异步**（`@Async` + 事件——线程池执行——**发布者不被监听器拖慢**）。配套两个使用点：**监听顺序**（多个监听器用 `@Order` 控制执行顺序）——**"先本地后分布式"里，本地也分同步/异步两档**（事务事件 + 异步监听是"不阻塞主路径"的组合）。

## 3. 事务事件：事件与事务绑定（实验实证）

**经典问题**：事务里发了事件，但事务后来回滚了——监听器已经处理了不该处理的事。

`@TransactionalEventListener` 解决（实验 `transactionalEventListenerAfterCommit` 验证）：**事件挂到事务上**——`AFTER_COMMIT`（提交后才触发）/`AFTER_ROLLBACK`（回滚才触发）/`BEFORE_COMMIT`——**回滚事务的事件不会在提交阶段执行**。

```
事务内 publishEvent → 事务提交 → AFTER_COMMIT 监听器执行
                  → 事务回滚 → AFTER_ROLLBACK 监听器执行（AFTER_COMMIT 不执行）
```

**应用场景**：订单创建成功（提交）后才发"通知服务"事件——**避免"通知了但订单没建成"**。

## 4. 本地事件 vs 分布式事件（stage-3-14 KP-02）

| | 本地事件（JVM 内） | 分布式事件（跨服务） |
|---|---|---|
| 载体 | Spring 事件/EventBus | **MQ**（Kafka/RocketMQ） |
| 语义 | 同步/异步线程 | 网络传输 + 持久化 + 重投 |
| 可靠性 | 进程内（进程挂了就丢） | **MQ 持久化**（可靠投递——2.5 的 Outbox 用 MQ） |
| 顺序 | 同线程保证 | 分区有序（Kafka） |

**选型一句话**：同服务内解耦用本地事件；跨服务通知用 MQ——**"先本地后分布式"是演进路径**（stage-3-14 核心命题）。

**分布式事件结构**（stage-3-14 KP-05）：事件 ID（幂等——2.5 交叉）+ 类型 + 时间戳 + payload——**事件本身要可重投**（消费端幂等是分布式事件的另一半）。

## 6. 事件传播链收束（03→06→07——2.8 详述的链路）

```
03 PropertySourcesChangedEvent（配置变化）
  → 06 ZoneContextChangedEvent（zone 变化）
  → 07 DynamicJdbcConfigChangedEvent（数据源配置）
  → DynamicDataSource 重建
```

**这条链是事件化家族的教学收束案例**：三仓库三个事件、三种职责（配置/区域/存储），靠事件解耦串联——**每个环节只认识相邻事件，不认识整条链**（事件化的价值放大版）。

**注册中心事件与心跳**（stage-3-14 KP-04 交叉）：注册中心的心跳/状态变化也事件化（2.9 的注册四态事件——注册可观测面）。

## 7. Kafka 高可用（stage-3-16 KP-05——消息载体）

Kafka 集群高可用要点：**分区副本**（leader/follower——故障自动切换）+ **ISR**（同步副本集合——一致性）+ 持久化；消费模型 = **消费者组**（一个组内分区分摊消费、组间广播——"事件广播 vs 竞争消费"的消息面语义）。**消息面不是本章重点**（训练营未设独立消息章节——消息原理在官方源码锚点：kafka/rocketmq——2.5 的事务消息交叉）。
