# 11. 服务容错：不让一个坏服务拖垮全局

> 配套实验：`sca-lab/custom-java-infra/spec-sentinel`（4 个断言，Sentinel 本地实测）
> 定位：容错四模式（时间无关）+ 现代载体（Sentinel）+ 框架整合（装饰器）+ 动态变更 + 差距 TOP②
> 课程来源：stage-1-07/08/09/10（4 篇主属）+ 源码 14（六适配器/三模式）+ 源码 11（binder 交叉）
> 前置：2.1（服务发现）、2.3（负载均衡）

你调的下游服务挂了、慢了、被流量打爆了——**你的服务怎么办？** 等它超时？你的线程也一起被拖死，然后你的调用方也被你拖死——**雪崩**。服务容错就是防雪崩的一整套手段。这一章讲：容错四模式、现代载体（Sentinel，含实测）、怎么接入三个框架、规则怎么动态变、以及训练营识别的真实差距。

---

## 1. 容错四模式（stage-1-08 KP-01~04）

| 模式 | 干什么 | 一句话 |
|------|--------|--------|
| **熔断** | 下游故障率超阈值 → 直接短路（快速失败） | "下游不行了就别再试了" |
| **降级** | 故障时走兜底方案（缓存/默认值/关功能） | "主路不通走辅路" |
| **限流** | 超过自身处理能力 → 拒绝多余请求 | "门口限号，别挤爆" |
| **隔离** | 每个下游独立线程池/信号量 | "一个桶漏了不淹别的桶"（舱壁） |
| 重试（补充） | 短暂故障重试（带退避） | "一次不行再来一次，但别打鸡血"——**风险：非幂等操作重试 = 重复执行**（下游已执行但响应丢失——扣款重试两次？）——重试必须配幂等（2.5 事务章节交叉） |

**防雪崩的核心逻辑**：下游慢 → 熔断兜底（快速失败）→ 上游线程不被拖死 → 雪崩链条被切断。

## 2. 现代载体：Sentinel（实测验证）

**历史对照（过时→现代）**：**Hystrix**（Netflix——服务容错的先行者——**已停止维护/过时**）→ **Sentinel**（阿里——限流熔断一体 + 控制台 + 规则热更新）vs **Resilience4j**（轻量函数式——stage-1 的对比对象）。**"Sentinel 替代 Hystrix 是容错域的现代替代映射"**（stage-1 梳理实证——训练营的对比主线）。

### 资源埋点：一切规则作用的对象

Sentinel 的模型：**资源（Resource）**——你保护的一段代码（`SphU.entry("pay")`，`SphU.java:84` 实证）——所有规则（限流/熔断）都挂在资源上：

```java
Entry entry = SphU.entry("pay");   // 进入保护
try {
    return doPay();                // 被保护的代码
} finally {
    entry.exit();                  // 必须 exit（漏了会造成指标错乱——实验代码的 try/finally 保证）
}
```

### 限流（实验实证）

`FlowRule` 按 QPS 阈值（实验 `flowRuleBlocksOverThreshold`）：QPS 阈值 1 → 第 1 次放行、短时间内第 2 次抛 `BlockException`。

### 熔断（实验实证）

`DegradeRule` 异常比例策略（实验 `exceptionRatioOpensCircuitBreaker`）：异常比例 > 50% → 熔断器打开 → 后续请求**快速失败**（不再真调下游）。

**熔断三态状态机**：`CLOSED（关闭，正常）→ OPEN（打开，快速失败）→ HALF_OPEN（半开，试探）→ 恢复或再打开`——**半开是关键**：熔断持续 `timeWindow` 秒后放一个试探请求，成功 → 恢复 CLOSED（下游好了）；失败 → 回到 OPEN（还没好，继续等）。没有半开，熔断后永远不会自动恢复。

> **使用坑（实验踩出）**：DegradeRule 必须设置 `timeWindow`（熔断持续时间秒）——`isValidRule` 校验不通过会静默拒绝规则（规则加载了但实际没生效——**静默失效**！排查熔断不生效先查这个）。

### 三模式（outline 14 核心——别漏）

Sentinel 的规则分三族（源码 14 三模式实证）：
1. **流量控制**（`FlowRule`）——QPS/并发线程数阈值（实验验证）
2. **熔断降级**（`DegradeRule`）——异常比例/慢调用比例/异常数（实验验证）
3. **系统自适应保护**（`SystemRule`）——CPU 利用率/系统负载超阈值 → 全局入口限流（"系统快不行了，自动少接客"）

> 可跳过（进阶级）：**SentinelTemplate 模板 API**（outline 14 一章——execute 重载族）——把 entry/exit 封装成模板方法，业务代码免手写 try/finally（对比实验代码的手写版）；JMX MBean 仓库（运行期开关插件——2.9 JMX 交叉）。

> 可跳过（进阶级）：**资源命名基数控制**（outline 14 3.2）——资源名太细（每个订单 ID 一个资源）会撑爆规则存储与指标（**高基数问题**，与 my-xhs ApiMetricsFilter 的 URI 归一化同源——2.9 交叉）；源码 14 的四重条件装配（框架可用+开关+类存在+Web 栈）归属 4.2 章节。

### 规则热更新（实验实证——动态变更）

`FlowRuleManager.loadRules()` 重新加载 → **立刻生效**（实验 `ruleHotUpdateTakesEffectImmediately`：阈值 1 → 阻塞；阈值调 100 → 立刻放行）——这是"容错规则动态变更"的机制底座（配置中心推送 → 规则热更新 → 服务不重启，与 2.2 章节联动）。

## 3. 整合三框架：装饰器模式（stage-1-09）

容错不能只保护"业务代码块"——要保护**对下游的每一次调用**。整合方式：**装饰器/拦截器**（stage-1-09 KP-02 实证）：

| 框架 | 接入点 | 机制 |
|------|--------|------|
| OpenFeign | Feign 拦截器 | 每个 Feign 调用包上容错 |
| MyBatis | Executor 拦截器 | SQL 执行点挂容错 |
| Spring Redis | Redis 连接拦截 | Redis 调用挂容错 |

**这是源码 14 的六适配器统一模式**（核心资产）：每个框架一个适配器（MyBatis ExecutorFilter/Druid 过滤/Redis 拦截/P6Spy/Web HandlerMethodInterceptor/Hibernate）——**统一实现 Sentinel 插件接口，各自挂到框架扩展点**（12/13/10/11 仓库扩展点 = 14 的挂载点——跨仓库组合实证——**装饰器/适配器模式本体在 4.6 章节主落位，这里是容错域实例**）。my-xhs 的 `SentinelBulkheadConfig` 就是舱壁隔离的落地（Feign 调用独立线程池 + 规则 dataId 走 Nacos 动态下发）。

## 4. 动态变更：规则不用重启（stage-1-10）

容错规则**必须能动态变**（突发流量时临时调限流阈值——重启就晚了）。机制链（stage-1-10 KP-01~05）：

```
配置中心推送（Nacos）
  → EnvironmentChangeEvent（配置变化事件）
  → @RefreshScope / ConfigurationPropertiesRebinder（重新绑定）
  → 规则加载（FlowRuleManager.loadRules——实验验证的立刻生效）
```

my-xhs 实证：Sentinel 规则走 Nacos 下发（dataId 实证）+ @RefreshScope 2 处（2.2 章节的共享机制）。动态变更还能作用于**日志级别**（stage-1-10 KP-07——logback 的 scan 机制/配置中心下发——线上临时开 DEBUG 排查不用重启）和 **Tomcat 组件参数**（stage-1-10 KP-06——线程池大小动态调整——容器层也能热改）。

## 5. 差距 TOP②：SQL/Redis 命令级限流（官方空白）

**这是训练营识别的最有价值的自主实现差距**（handover §七 核心差距②）：

| 层面 | 官方 Sentinel | 差距 |
|------|--------------|------|
| Web 层 | ✅ 适配器齐全 | — |
| **SQL 层** | ❌ 无命令级限流 | 慢 SQL/热点 SQL 的精确限流——官方空白 |
| **Redis 层** | ❌ 无命令级限流 | 热点 key 的精确保护——官方空白 |

**自主实现思路**：源码 10（redis 命令拦截 SPI）+ 源码 12（ExecutorFilter）扩展点就是挂载点——**把"命令级"变成 Sentinel 资源**（每条 SQL/每个 Redis 命令 = 一个资源 → 挂限流规则）——这正是六适配器模式的延伸（官方没有 → 自己实现，进 my-xhs 差距清单）。

## 本章小结

**知识本体**：容错四模式（熔断/降级/限流/隔离 + 重试——防雪崩链条）+ Sentinel 模型（资源埋点/限流/熔断/规则热更新）+ 框架整合（装饰器/六适配器统一模式）+ 动态变更（配置中心 → 规则热更新）+ **差距 TOP②（SQL/Redis 命令级限流——官方空白）**。
