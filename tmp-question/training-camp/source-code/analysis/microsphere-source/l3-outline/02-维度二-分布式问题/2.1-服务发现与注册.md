# 08. 服务发现与注册：服务之间怎么互相找到

> 配套实验：`sca-lab/custom-java-infra/spec-discovery`（4 个断言，内存注册中心实测）
> 定位：**模式本体（时间无关）+ 现代载体（Nacos 主讲）**——注册中心原理不绑具体实现；Eureka 历史对照降级为可跳过
> 课程来源：stage-3-07/08（模式知识）+ stage-3-24（Dubbo xDS）+ stage-2-09/10/12（ZK）+ stage-4-09（CloudNative）+ 源码 05（多注册语义）
> 前置：写过微服务、用过 HTTP 调用

微服务 A 要调用微服务 B。问题来了：**B 在哪？** 它的 IP 会变（容器重建）、副本会多（3 个实例）、还要知道哪个实例健康。A 的配置写死 B 的地址？写死就失去了微服务的意义。

**服务发现**解决的就是这个问题：一个"注册中心"记录"谁在提供服务"（注册表），服务实例上线时登记自己，下线时注销；调用方去查"B 现在有几个健康实例"。

这一章讲注册中心的模式本体（不绑具体实现）+ 现代载体（Nacos）+ 对照载体（ZK Curator）+ 客户端抽象。学完你会发现：Eureka、Nacos、ZK、Consul——全是同一套模式的变体。

---

## 1. 注册中心要解决什么：五类操作 + 租约机制

### 五类操作（服务发现的完整生命周期）

任何一个注册中心，本质就是提供这五类操作（stage-2-12 KP-02 实证）：

| 操作 | 谁发起 | 干什么 |
|------|--------|--------|
| **注册** | 服务实例 | "我上线了，IP:端口，能力：order-service" |
| **注销** | 服务实例 | "我下线了"（优雅停机） |
| **查询** | 调用方 | "order-service 现在有几个实例？" |
| **更新** | 服务实例 | "我的元数据变了"（版本/权重/zone） |
| **监听** | 调用方 | "order-service 变了通知我"（订阅推送） |

实验 `DiscoverySpecTest.fiveOperations` 把这五类操作全跑了一遍（内存注册中心实现）。

### 注册-心跳-摘除（租约机制——时间无关模式）

服务实例可能**突然死亡**（进程崩溃、网络断开）——来不及注销。注册中心怎么知道"它死了"？答案是**租约（Lease）**：实例注册后**周期性心跳**（"我还活着"），注册中心检查"上次心跳超过阈值 → 摘除"。

```
注册 → 周期性心跳（续约）→ 心跳超时 → 摘除
```

实验 `DiscoverySpecTest.heartbeatLeaseAndExpiryEviction` 验证了完整机制：持续心跳 → 不被摘除；停止心跳（500ms 超时）→ 被摘除。**这是 Eureka/Nacos 共用的模式**（Eureka 的 30s 心跳/90s 超时；Nacos 的**心跳三件套**——`DEFAULT_HEART_BEAT_INTERVAL=5s`/`DEFAULT_HEART_BEAT_TIMEOUT=15s`/`DEFAULT_IP_DELETE_TIMEOUT=30s`（api/common/Constants.java:189/:185/:187 实证——**注意：15s 是心跳超时，30s 是 IP 删除超时——别混**）——数值不同，模式相同）。

### 客户端两种模式 + 三个必知概念（stage-3-07 KP-03~06）

**客户端拿实例列表有两种模式**：①**拉取（pull）**——周期性全量/增量拉取 + 本地缓存（Eureka 经典做法）②**订阅推送（push）**——注册中心变化主动推（Nacos 长轮询/订阅）。生产常见混合：**拉取建缓存 + 订阅做增量更新**。

三个必知概念：
- **传播延迟**：从"实例注册/注销"到"所有调用方看到"有时间差（拉取周期/推送延迟）——**刚下线的服务还会被调用一会儿**是正常的，不是 bug（靠客户端重试兜底）
- **优雅停机**：实例下线前先主动注销再停止——把"被调用到死实例"的窗口缩到最小（对比进程被杀直接断线等超时摘除）
- **实例状态**：UP/DOWN/OUT_OF_SERVICE——健康检查标记实例状态，不只是"在不在"（配合负载均衡只选 UP 实例）

## 2. 模式一：租约式注册（Nacos——现代载体主讲）

### Nacos 的使用：客户端三行

```java
NamingService naming = NamingFactory.createNamingService("127.0.0.1:8848");  // 注册中心地址
naming.registerInstance("order-service", "10.0.0.1", 8080);   // 注册（NamingService.java:46 实证）
List<Instance> instances = naming.getAllInstances("order-service");  // 查询
```

**注册后的机制链**（Nacos 源码实证）：
- **注册** → 服务端登记实例 + **健康检查**（主动探测 + 客户端心跳）
- **查询** → 调用方拿到实例列表（可带权重/zone 元数据）
- **变更** → **长轮询推送**（客户端订阅服务，实例变化立即通知——比轮询省流量）

### 为什么 Nacos 是"双协议"（现代选型核心）

注册中心要同时解决两个一致性诉求：

| 诉求 | 场景 | 协议 |
|------|------|------|
| **CP**（强一致） | 配置管理——配置不能乱 | **JRaft**（Raft 实现） |
| **AP**（高可用） | 服务注册——注册中心挂了服务也要能查 | **Distro**（去中心化 + gRPC 长连接同步） |

**一个组件两种协议**——这是 Nacos 替代 Eureka（纯 AP）+ ZK（纯 CP）的核心理由：服务注册要 AP（高可用优先），配置要 CP（一致性优先），Nacos 一套搞定（stage-2 完整梳理"为什么选 X"实证）。Eureka 只有 AP 且已进入维护模式（Spring Cloud 2020 起移除）——**真正过时的是 Eureka，不是"注册中心"这个模式**。

> 可跳过（历史对照）：Eureka 的注册/心跳/拉取/自我保护机制（stage-3-07 KP-02~06）——模式与 Nacos 相同（租约 + 缓存 + 自我保护）；**自我保护**（"宁可保留旧数据不摘除"——网络分区时防止误杀）是个好概念，Nacos 也有（健康保护阈值——P2-6 运维核对项）。Eureka Server 的集群复制/双部署模式（stage-3-08）同属历史实现——其**注册四态事件**（注册可观测性）归属 2.9 可观测章节。

## 3. 模式二：临时节点注册（ZK Curator——活跃技术对照）

### 先澄清：ZK 没过时

ZooKeeper 是**活跃技术**——Kafka/HBase/Dubbo 都依赖它（curator 5.8.0 活跃维护实证）。过时的只是"ZK 当注册中心用"这一**选型场景**（训练营课程结论：该场景 → Nacos）——**不能把场景选型变化说成技术过时**（04 方法论：精确过时判定）。

### ZK 的注册中心模式：临时节点

ZK 的数据模型天然适合做注册中心（stage-2-09 KP-03/04）：

- **服务注册 = 创建临时节点**：`/services/order-service/10.0.0.1:8080`
- **临时节点语义**：会话断开**自动消失**（不需要心跳摘除——**连接即租约**）
- **服务查询 = 列子节点**
- **变更监听 = Watch**（节点变化通知）

**模式对照**：

| | 租约式（Nacos/Eureka） | 临时节点式（ZK） |
|---|---|---|
| "还活着"的证明 | 应用层心跳续约 | 底层会话保活（连接即租约） |
| 摘除机制 | 心跳超时判断 | 会话超时自动删节点 |
| 依赖 | 需要健康检查逻辑 | 依赖会话机制（写路径经 Leader——CP） |
| 一致性 | AP（Nacos Distro） | CP（ZAB 强一致） |

Curator 的 `ServiceDiscovery`（`curator-x-discovery`——stage-2-12 KP-03 实证）把这套封装成五类操作 API。**Dubbo 3 也支持注册到 ZK**——活跃使用场景实证。

> 可跳过（ZK 基础设施）：临时节点的"会话"语义依赖 ZK 的通讯与会话机制（stage-2-10——Jute 序列化/传输层/客户端连接——会话超时决定临时节点何时消失）——ZK 作为协调服务的主载体在共识章节（3.2）详述。**顺序节点**（stage-2-09 KP-05——`create -s` 带序号）是分布式锁的基础（2.6 章节）；客户端选实例的 `ProviderStrategy`（stage-2-12 KP-04——ROUND_ROBIN/RANDOM 等）是"选哪个实例"的策略——负载均衡章节（2.3）详谈。

## 4. 客户端抽象：DiscoveryClient（应用层不绑注册中心）

调用方不该直接调 Nacos/ZK 的 API——Spring Cloud 给了一个统一抽象 `DiscoveryClient`（spring-cloud-commons `DiscoveryClient.java:32` 实证）：

```java
public interface DiscoveryClient extends Ordered {
    List<ServiceInstance> getInstances(String serviceId);   // 查实例
    List<String> getServices();                              // 列服务
}
```

**任何注册中心（Nacos/Eureka/ZK/Consul）都实现这个接口**——应用层代码只依赖接口，换注册中心不改业务代码。实验 `discoveryClientAbstraction` 验证了这套抽象（我们的内存注册中心实现了它）。

**注册元数据**（源码 06 四章交叉）：实例注册时携带元数据（zone/版本/权重）——消费者解析实例元数据做路由决策（Zone 元数据闭环——多活章节 2.8 详谈，这是"区域感知"的注册侧基础）。

**源码 05 的多注册语义**（交叉）：microsphere 的注册中心封装支持**多注册中心**（同一实例同时注册到 Nacos + Eureka + ZK——`短路`：任何一个成功即成功 vs `全量`：全部成功才算成功——两种语义的取舍）。**Union 模式**：跨注册中心的合并发现——多活章节（2.8）详谈。

## 5. 现代选型与演进方向（一句话版）

| 组件 | 定位 | 现状 |
|------|------|------|
| Nacos | 注册 + 配置一体（CP/AP 双协议） | **现代默认**（my-xhs 部署实证——compose nacos 服务） |
| ZK | 协调基础设施（临时节点模式仍活跃） | Kafka/HBase/Dubbo 依赖 |
| Eureka | 历史教材（模式知识保留） | 维护模式 → Nacos |
| **平台化** | K8s API Server/etcd/Istio xDS 承担注册发现 | **云原生方向**（stage-4-09——业务零自建，1.7 章节已述） |

**Dubbo 的演进**（stage-3-24 交叉）：Dubbo 服务发现从自研注册中心 → **xDS 协议**（Istio 的注册发现标准——`xDS API` 总览 KP-01）——"注册中心平台化"在 RPC 层的落地（双注册/Mess 重构）。xDS 家族里 **RDS（路由发现）/LDS（监听发现）** 与网关路由同构（stage-3-24 KP-02：RDS 对应 SCG 路由表——网关章节 2.7 交叉）。

**my-xhs 落地点**：Nacos 部署实证（compose——端口 18848 实证）+ Spring Cloud Alibaba 注册（注册中心由框架托管）；**判定精确化**：部署侧实证完整，业务服务接入配置（server-addr）未直接命中——列为 P2-6 核对项（健康保护阈值/存储后端 Derby vs MySQL 同项）。

**服务端结构一句话**（Nacos 源码实证）：服务端 = 注册表存储（ServiceManager）+ 客户端操作面（ClientOperationService——gRPC 注册/注销/订阅）+ 租约/推送管理——"注册表 + 租约 + 复制/推送"是所有注册中心服务端的同构三件。

## 本章小结

**知识本体**：服务发现 = 注册中心五类操作（注册/注销/查询/更新/监听）+ 两种实现模式（租约式心跳摘除 vs 临时节点会话即租约）+ 客户端抽象（DiscoveryClient）+ 一致性选型（AP 注册/CP 配置 → Nacos 双协议）+ 平台化演进（K8s/xDS）。

**实验验证**：五类操作 / 心跳续约与超时摘除 / 租约机制 / DiscoveryClient 抽象（4 断言）。

**my-xhs 判定**：Nacos 已用（部署实证）/ DiscoveryClient 抽象已用（框架托管）/ ZK 模式该用没用（无 ZK 依赖——知识对照价值）/ Eureka 不该用（过时）。
