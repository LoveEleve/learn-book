# 13. 锁、缓存与存储：数据层的一整套功夫

> 配套实验：`sca-lab/custom-java-infra/spec-storage`（4 个断言）
> 定位：缓存三兄弟 + 分布式锁 + 读写分离/分片 + 数据源增强 + **差距 TOP③④**
> 课程来源：stage-2-25/26/27/28 + stage-3-11/12（6 篇主属）+ 源码 10/12/13/07
> 前置：1.3 章节（JDBC/DataSource）、2.5 章节（事务）

数据层是分布式系统最"接地气"的部分：缓存怎么防三兄弟、分布式锁怎么加、数据怎么读写分离/分片、数据源怎么被增强。这一章把数据层的一整套功夫串起来——每块都有实验验证和 my-xhs 实证。

## 1. 缓存三兄弟：穿透/击穿/雪崩（实验实证）

| 问题 | 现象 | 解法 |
|------|------|------|
| **穿透** | 查不存在的 key → 每次打 DB | **空值缓存**（不存在也缓存，短 TTL）——实验验证 |
| **击穿** | 热点 key 过期 → 并发重建打爆 DB | **互斥重建**（一个线程去 DB，其余等待）——实验验证 |
| **雪崩** | 一批 key 同时过期 → 集体打 DB | **过期时间加随机抖动**——实验验证 |

实验 `cachePenetrationNullCaching`/`cacheBreakdownMutexRebuild`/`cacheAvalancheJitteredExpiry` 分别验证了三个解法。

**多级缓存**（stage-2-27 KP-07）：本地缓存（Caffeine/Guava——最快）+ 分布式缓存（Redis）+ DB——**命中率优先本地，一致性兜底 Redis**。

**淘汰策略**（stage-2-27 KP-08——面试点）：LRU（最近最少用——历史数据锁死缓存问题）→ LFU（最不常用——偶发热点被冷落）→ **Caffeine 的 W-TinyLFU**（LRU+LFU 混合 + Count-Min Sketch 近似统计——近最优命中率，stage-2 梳理的技术理由实证——2.2 章节的选型对照）。

## 2. 分布式锁（Redisson 家族——stage-2-28）

### 为什么需要分布式锁

单体用 `synchronized`/`ReentrantLock`（JVM 内有效）；多实例场景锁必须**跨进程**——Redis 的 `SET key value NX EX ttl`（原子加锁 + 过期）是最简单形态。实验 `setNxDistributedLock` 验证了核心语义：加锁（NX 原子）/ **防误删**（解锁校验持有者——A 不能解 B 的锁）/ 过期自动释放。

### Redisson 的锁家族（my-xhs 21 文件实证）

| 锁 | 场景 |
|----|------|
| `RLock` | 基本互斥（可重入——`RedissonLock` 的 Lua 实现，源码实证 `tryLockInnerAsync`） |
| 读写锁 | 读读并发/读写互斥 |
| 信号量/`Semaphore` | 限并发（stage-2-28 KP-05） |
| `RateLimiter` | 限流（stage-2-28 KP-03） |

> 可跳过（进阶级）：**锁的坑**——过期时间太短（业务没做完锁没了）/ 太长（死等）——看门狗续期机制（watchdog）；跨区场景的 Split-Brain 双持锁风险（2.8 多活章节——Redisson 在 Redis Cluster Multi-AZ 下的陷阱）。

**分布式 Session**（stage-2-28 KP-06/07）：多实例登录态共享——Spring Session + Redis（session 从 JVM 内存搬到 Redis——`Spring Session` 分布式 Session）。

**幂等性服务**（stage-2-28 KP-08）：分布式场景的重复提交防护——幂等键（请求方生成）+ Redis 去重/唯一约束——"同一个请求处理多次结果一样"（与 2.5 的重试幂等交叉——重试、消息、幂等键三件套）。

## 3. 存储层扩展：读写分离与分库分表

### 读写分离（stage-2-25）

**主从复制**（MySQL 主写从读——Binlog 同步）→ **数据源路由**（读走从库、写走主库）——（stage-2-25 KP-06——**Redis 读写分离**数据源：主写从读同样适用）：

```
@Transactional(readOnly = true) → 路由到从库（my-xhs ReadWriteRoutingDataSource 实证）
普通/写事务 → 路由到主库
```

my-xhs 的 `ReadWriteRoutingDataSource` 基于 Spring `AbstractRoutingDataSource`（`determineCurrentLookupKey` 实证——`@Transactional(readOnly=true)` 自动路由——1.3 章节的 DataSource 装饰器实战）。

### 分库分表（stage-2-26 + stage-3-12 KP-07）

**ShardingSphere**（现代载体）：SQL 解析引擎自动识别读写（零侵入——stage-2 完整梳理的技术理由实证）+ 分片路由。**挂载点**（stage-2-26 KP-01——JDBC Driver 扩展面）：JDBC 形态 = **DataSource 装饰器**（应用内）；Proxy 形态 = 独立代理服务（应用零改造但多一跳）。两种形态：**JDBC**（应用内数据源代理）/ **Proxy**（独立代理服务）。规则 API + 模式存储仓库（stage-2-26 KP-06~08——Memory/Standalone/Cluster 三模式）。

**读写分离 vs 分库分表**（stage-2-25 KP-08）：读写分离 = 副本水平扩展（读）；分库分表 = 数据垂直/水平拆分（容量）——两回事，常组合。

## 5. 动态数据源两架构（差距 TOP③——核心对照）

动态切换数据源（多活/多环境场景）有两种根本不同的架构（源码 07 三章——**本仓库最大对照价值**）：

| | **子上下文重建**（microsphere） | **预建池切换**（my-xhs） |
|---|---|---|
| 机制 | 配置变更 → 重建整个 Spring 子上下文 → 新 DataSource | **按 zone 预建连接池** → `switchDataSource(zone)` 换 Map 里的池 |
| 切换成本 | 重（容器重建） | **轻（Map 查找）** |
| 隔离 | 彻底（独立 Bean 生命周期） | 池级 |
| 在途连接 | 延迟关闭旧上下文 | **activeConnectionCount + 30s 等待**（安全切换） |
| 场景 | 多单元复杂配置 | **单库 HA（my-xhs 场景足够）** |

**差距 TOP③**：子上下文多单元隔离（07——单数据源场景 my-xhs 可接受；若未来多单元复杂配置 → 07 架构为差距项）。

## 7. MySQL 高可用（stage-3-11）

| 方案 | 机制 |
|------|------|
| 主从复制 | Binlog 异步复制（读扩展） |
| **MGR**（组复制） | **分布式状态机复制**（Paxos 类共识——组成员/故障检测自动切换——3.2 共识交叉） |
| 高可用选型 | 主从 + MGR + 中间件（MHA/Orchestrator——`[缺口]`） |

**ORM 选型**（stage-3-12 KP-06——主要内容②）：MyBatis（精确 SQL 控制——现代默认，stage-3 梳理 JPA→MyBatis-Plus 映射）vs JPA（生产力/约定映射——训练营定为"不要"）——`[过时→MyBatis-Plus]`（精确 SQL 控制是电商场景的正解）。

Binlog 消费（stage-3-11 KP-03）是 Canal 等同步工具的底座（2.8 存储多活交叉）。**数据备份**（stage-3-11 KP-02——全量备份 + 增量（Binlog）——备份策略是数据安全的最后防线，my-xhs P3-13 规划项）。

> **分布式 ID（骨架 §9.6 [N=1] 交叉注记）**：**雪花 ID（Snowflake）**——时间戳 + 机器位 + 序列号（趋势递增 + 无中心化）——训练营仅 1 篇提及（stage-3 梳理），不设独立主题；**2.8 多活的全局 ID 冲突反模式**（跨区 workerId 分配冲突——Leaf-Segment/CosId 号段替代）在此交叉。**my-xhs 实证（三合一）**：`my-xhs-common/id/IdGeneratorUtil.java:13`——"三合一：**雪花 + 号段 + Redis 自增**"（:16 雪花 ID 用于订单/笔记/评论——18 位趋势递增本地生成）+ `SegmentIdGenerator.java`（号段生成器——**号段替代正是多活全局 ID 冲突的解法**——2.8 交叉实证）。
