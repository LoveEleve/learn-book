# 12. 分布式事务：跨库跨服务怎么保证"全成或全不成"

> 配套实验：`sca-lab/custom-java-infra/spec-tx`（**模块共 6 个断言**——TxSpecTest 4（本文）+ TwoPhaseTest 2（3.3 理论章节），H2 + Spring tx 实测）
> 定位：事务实践全链路（本地事务 → 分布式三思路 → Seata 现代载体）；**理论本体（2PC/TCC/SAGA）在 3.3 章节提炼**——本章讲怎么用
> 课程来源：stage-2-13~20（8 篇主属——训练营最大主题之一）
> 前置：1.3 章节（JDBC 事务——autoCommit/隔离级别/Savepoint）

1.3 讲过一个库内的事务（`setAutoCommit(false)` + commit/rollback——ACID 由数据库保证）。这一章的问题升级：**订单服务写订单库 + 扣库存服务写库存库——两个库怎么保证"全成或全不成"？** 本地事务管不了别人的库——这就是分布式事务。这一章讲：Spring 事务抽象（你在代码里写的东西）、分布式事务三种思路（2PC/可靠事件/TCC）、现代载体（Seata AT/TCC）、怎么选。

## 1. 你在代码里写的：Spring 事务抽象（stage-2-14/16）

### @Transactional 的语义

```java
@Transactional(rollbackFor = Exception.class)   // my-xhs 23 处实证——为什么必须写 rollbackFor？
public void transfer() { 扣钱(); 加钱(); }
```

**坑（实验实测）**：Spring 默认只对 `RuntimeException`/`Error` 回滚——**检查异常（Exception 子类）默认不回滚**！所以生产惯例 `rollbackFor = Exception.class`（my-xhs 23 处实证——惯例不是随便写的）。

**传播行为**（`Propagation`——面试必考）：`REQUIRED`（默认——加入已有事务）/`REQUIRES_NEW`（新开事务挂起外层——典型场景：**审计日志**——外层回滚不影响已记的日志）/`NESTED`（嵌套保存点）。实验 `requiredPropagationOuterRollsBack` 验证了核心语义：内层抛异常 → **外层整体回滚**（同事务）。

**@Transactional 属性族**（对应 `TransactionDefinition`——stage-2-16 KP-06）：隔离级别（`isolation`——默认跟随数据库，1.3 章节的四级）/ **超时**（`timeout`——超时强制回滚——my-xhs 实证 `timeout = 10`）/ **只读**（`readOnly = true`——只读事务的优化提示——my-xhs 实证 3 处）。

### 实现的三件套（stage-2-16 KP-01~05）

`PlatformTransactionManager`（抽象）→ `DataSourceTransactionManager`（JDBC 实现）→ `TransactionTemplate`（编程式）。你写的 `@Transactional` 是 AOP 拦截器包装这三件套（事务拦截器——stage-2-14 KP-05/06）。

## 2. 思路一：2PC/XA——教科书方案（过时→Seata）

### 机制

两阶段提交（理论本体见 3.3 章节）：**阶段一 Prepare**（各库"我准备好了，能提交"——资源锁住）→ **阶段二 Commit/Abort**（全票通过才提交）。

JTA/XA 是 Java 的 2PC 标准（stage-2-15 KP-01~06：五角色——TM/各库 RM + 事务接口）。

### 为什么过时（stage-2 完整梳理实证）

1. **阶段一锁资源直到提交**——高并发下锁持有时间太长（整个二阶段）
2. **要求数据库支持 XA 协议**——限制选型
3. 协调者单点（TM 挂了大家都卡住）

**结论**：XA 的"长锁"在互联网高并发下不可接受 → 被 Seata AT 取代（见 §5）。

## 3. 思路二：可靠事件/Outbox——最终一致（实验实证）

### 核心思想

不追求"强一致"——**先保证本地成功，再保证事件最终送达**（最终一致，BASE）。机制（stage-2-17 KP-01~03）：

```
业务 INSERT + 事件表 INSERT（本地事务表）—— 同一本地事务（原子！）
    ↓ 事务提交后
异步发送事件到 MQ
    ↓ 发送失败
事件表状态 FAILED → 重试任务 → 重新发送
    ↓ 消费端
幂等消费（同一个事件只处理一次）
```

**关键保证**：业务写和事件写在同一本地事务——"业务成功但事件没写"这种状态不存在（`OutboxStateMachine` 实验验证了状态流转 PENDING → FAILED → 重试 → SENT）。

**Transaction Outbox vs 本地消息表**（stage-2-17 KP-05）：同一个模式的两个名字（Outbox 是微服务时代的叫法）。

**消费端幂等**（stage-2-17 KP-06——必须）：MQ 会重复投递——消费端按事件 ID 去重（**实现：事件表唯一索引 + 已处理标记**——幂等消费是可靠事件的另一半）。

> 可跳过（进阶级）：**事务消息**（RocketMQ Half/Commit——发送"半消息"→ 本地事务成功才 commit——MQ 自带的 Outbox，省掉事件表；消息在 MQ 里待定，本地事务失败 → rollback 半消息）。

## 4. 思路三：TCC——业务级两阶段（实验实证）

### 机制

TCC 把"业务操作"分成三步（理论本体 3.3）：

```
Try（预留）→ Confirm（确认——真正生效）
         ↘ Cancel（取消——释放预留）
```

典型场景：库存扣减 = Try 冻结库存 → Confirm 扣减 / Cancel 解冻。**对比 2PC：锁的是"业务资源"不是"数据库行"**——业务自己控制锁粒度（stage-2-18 KP-01~03）。

### 三问题（所有 TCC 实现的必答题——实验验证）

| 问题 | 意思 | 实验 |
|------|------|------|
| **幂等** | 重复 Try/Confirm/Cancel 只生效一次 | tryPhase 重复调用返回已有状态 |
| **空回滚** | Cancel 先到（Try 没发生）→ 不能算失败 | cancel 未 Try 分支记录空回滚 |
| **防悬挂** | Confirm/Cancel 先到（Try 未完成）→ 不能成功 | confirm 未 Try 分支拒绝 |

my-xhs 的 `TccFenceService`（common/tcc 实证）就是这三问题的落地（Seata TCC fence 同款）。

### 实现家族

Hmily（stage-2-18 KP-04~06——事务处理器/执行器）→ 现代统一到 **Seata TCC 模式**（stage-2-20——`@TwoPhaseBusinessAction` 注解 + `TccActionInterceptor` 拦截器）。

## 5. Seata：现代载体（AT 模式——零侵入）

### AT 模式（stage-2-19 KP-01~06）：2PC 的改良

```
阶段一：业务 SQL + UNDO 日志 —— 同一本地事务提交（锁立刻释放！）
阶段二：全部成功 → 异步删 UNDO 日志
        有失败 → 用 UNDO 日志反向补偿（回滚）
```

**对比 XA 的关键差异（stage-2 完整梳理实证）**：AT 一阶段业务 SQL + UNDO 日志**在同一本地事务提交，立即释放锁**——锁持有时间从"整个二阶段"变成"一次提交"——高并发可接受。代价：需要**全局锁**（防脏写）+ 反向补偿的正确性（UNDO 日志组件——`AbstractUndoLogManager` 实证）。

**三角色**（stage-2-19 术语——Seata 架构核心）：`TC`（事务协调者——Seata Server，管全局事务状态机）/`TM`（事务管理器——业务侧，开/提交/回滚全局事务——`@GlobalTransactional` 背后）/`RM`（资源管理器——数据源代理，管分支事务 + UNDO 日志）。

组件（seata 源码实证）：`GlobalTransactionScanner`（扫描 @GlobalTransactional——TM 侧）/`DataSourceProxy`（数据源代理——RM 侧：SQL 拦截 + UNDO 记录）/`BranchType`（AT/TCC/XA/SAGA 分支类型）。

### 三种模式选型（stage-2-19 KP-02）

| 模式 | 侵入 | 场景 |
|------|------|------|
| **AT** | 零侵入（代理数据源） | 一般业务（默认） |
| **TCC** | 业务改造（三方法） | 需预留资源（库存/账户冻结） |
| SAGA | 无锁（长事务） | 长流程（订单履约链） |

## 6. 选型对照（本章收束）

| 方案 | 一致性 | 侵入 | 场景 | 现状 |
|------|--------|------|------|------|
| 本地事务 | 强 | 低 | 单库 | 默认 |
| 2PC/XA | 强 | 高（XA 库） | 传统企业 | [过时→Seata AT] |
| **可靠事件/Outbox** | 最终 | 低（事件表） | 跨服务异步链路 | **微服务默认**（配合 MQ） |
| **TCC** | 最终 | 中（三方法） | 预留资源场景 | Seata TCC / 自研（my-xhs TccFenceService） |
| **Seata AT** | 强（带全局锁） | **零侵入** | 需要强一致的跨库事务 | **现代默认** |

**一句话**：能最终一致就 Outbox（异步）；要强一致且零改造就 Seata AT；要预留资源就 TCC——**先想清楚业务到底需要哪种一致性**。

## 本章小结

**知识本体**：Spring 事务抽象（rollbackFor 坑/传播行为/三件套）+ 分布式三思路（2PC 长锁过时 / Outbox 最终一致 / TCC 业务级两阶段 + 三问题）+ Seata（AT 改良 2PC——UNDO 日志 + 全局锁 / TCC / 选型）。

**实验验证**：rollbackFor 回滚语义 / REQUIRED 传播整体回滚 / Outbox 状态机 / TCC 三问题（4 断言）。

**my-xhs 判定**：本地事务已用（19 文件 + rollbackFor 惯例实证）/ **TCC 已用**（TccFenceService——防悬挂落地实证）/ Seata AT 该用没用（当前单库场景不需要；多库强一致场景为差距）/ Outbox 该用没用（异步链路场景——事件驱动面 2.10 交叉）。
