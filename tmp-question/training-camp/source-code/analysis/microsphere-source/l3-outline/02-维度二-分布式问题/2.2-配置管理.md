# 09. 配置管理：配置从哪来、怎么变、怎么生效

> 配套实验：`sca-lab/custom-java-infra/spec-config`（3 个断言，spring-boot Binder 实测）
> 定位：配置中心的本质 + 客户端抽象 + 热更新三种粒度（核心对照）+ 选型
> 课程来源：stage-2-23/24 + stage-3-25/26/27（5 篇主属）+ 源码 08（三件套）+ 源码 04（Binder）+ 源码 03（@PropertySource 增强）
> 前置：用过 application.yml、知道 Spring Environment

你的配置住在 `application.yml` 里。改一个值 → 重启服务 → 生效。单体时代没问题，微服务时代是灾难：**几十个服务各改各的重启，还容易改漏**。配置中心解决三件事：**配置集中存放**（一个地方管所有服务的配置）、**动态变更**（改配置不用重启）、**版本与审计**（谁改的、改了什么）。

这一章讲：配置中心的本质、客户端怎么拿到配置（Environment 抽象）、@PropertySource 的四个坑、**热更新的三种粒度**（本章核心）、选型。

---

## 1. 配置中心的本质：五件事

一个配置中心（stage-2-23 KP-01~10）本质做五件事：

| 事 | 说明 |
|----|------|
| **存储** | 配置放哪（数据库/etcd——**KV 模型 + 环境/命名空间隔离 + 版本**） |
| **获取** | 客户端怎么读（HTTP API/长轮询/推送） |
| **变更事件** | 配置变了怎么通知（推送/轮询/长轮询——stage-3-25 KP-06 变更事件要素） |
| **集群部署** | 高可用（多节点 + 一致性） |
| **Open API** | 管理面（Web 控制台/**审计/版本回滚**——配置错了能一键回滚到上个版本） |

**配置中心 vs 注册中心（stage-2-23 KP-09——面试爱问）**：注册中心要 **AP**（高可用优先——注册中心挂了服务也要能查）；**配置要 CP**（强一致——配置不能乱，一个服务看到新配置另一个看到旧配置会造成混乱）。这就是 Nacos 做双协议的原因（2.1 章节详述）。

## 2. 客户端怎么拿到配置：Environment 抽象

### Spring 的答案：PropertySource 链

Spring 把"所有配置来源"抽象成一条**有序的 `PropertySource` 链**（环境变量 → 系统属性 → application.yml → ...）——后面的覆盖前面的。配置中心客户端的本质就是：**把自己的 PropertySource 插进这条链**（stage-2-24 KP-03/05 + stage-3-27 KP-03）：

```
PropertySource 链（前面的优先级高）
  env vars → system props → config-center（Nacos 推送的源）→ application.yml
```

代码读 `@Value("${app.threads}")` 时，Spring 沿链找第一个命中的——**配置中心源的插入位置决定覆盖关系**。

### 客户端三实现路径（stage-3-27 KP-01）

| 路径 | 存储 | 实时性 |
|------|------|--------|
| 文件系统 | 本地文件 | 静态（改要重启/重读） |
| Zookeeper | ZK 节点 | **Watch 推送** |
| etcd | etcd KV | **Watch 推送** |

三路径共享同一个 `PropertySource Loader` 抽象——**换存储 = 换 Loader**（插件式）。动态配置的实时性由存储的 Watch 机制决定。

**客户端订阅 API**（stage-2-24 KP-09/10 交叉）：Nacos 的 `Listener`（addListener 订阅 dataId——变更回调）、Apollo 的 `ConfigChangeListener`/`ConfigChangeEvent`（发布面带变更明细：key/oldValue/newValue）——"订阅变更"是配置客户端的事件面（与 2.10 事件化章节交叉；源码 08 的 `PropertySourcesChangedEvent` 就是把它桥接进 Spring 事件体系）。

**客户端核心机制三件**（stage-3-27 KP-02）：①**本地缓存**（配置拉下来存本地——每次读走缓存不快连配置中心）②**变更推送**（长轮询/Watch——缓存同步更新）③**容错降级**（配置中心挂了 → 用本地缓存继续跑——**"配置中心故障 ≠ 应用故障"**，这是配置客户端最重要的容错设计）。`Environment` 的层次（stage-2-24 KP-03）：`Environment` 接口（`PropertyResolver.getProperty` 解析 + 占位符 `\${key}` 展开）持有一条 `PropertySources` 链——**读配置 = 沿链查找 + 占位符解析**两步。

## 3. @PropertySource 的四个坑（配置客户端设计的动机）

Spring 自带的 `@PropertySource` 只能加载**静态本地文件**——它的四个缺陷（stage-3-26 KP-05 实证）就是配置中心存在的动机：

| 缺陷 | 说明 |
|------|------|
| ① 无法注解扩展 | `value()` 必填，自定义注解无法 @AliasFor 默认 |
| ② 不自动刷新 | 静态加载，动态配置缺失 |
| ③ 不支持顺序 | 绝对顺序/相对顺序都不支持 |
| ④ 无法元注解复用 | Spring 内部 `processPropertySource` 处理，用户无法注解层介入 |

**microsphere-spring-config 的解法**（stage-3-26 KP-06 + 源码 08）：`@PropertySource` 增强版 + `AnnotatedPropertySourceLoader` 层次——**注解驱动 + Loader 插件化**（换配置源 = 换 Loader）；源码 08 的**注解化三件套**（@EnableConfigurationSource 家族）+ **双模式**（Loader vs Registrar）把"动态/多源/有序"补全——**四缺陷 = 配置中心整合的动机**。

## 4. 热更新：三种粒度（本章核心对照）

配置变更后"怎么生效"有三种粒度——**这是 2.2 最重要的知识**：

| 粒度 | 机制 | 代表 | 成本/隔离 |
|------|------|------|------|
| **属性级** | 配置值变更 → 重新绑定/重新读取 | 源码 08（Apollo 克隆替换——新配置对象替换旧对象）、`@RefreshScope` | 轻量；只换值 |
| **Bean 级** | 配置变更 → 重建整个 Bean（子上下文） | 源码 07（DynamicDataSource 重建）、**源码 05（Feign 组件注册表 + 可刷新装饰器——配置变 → 装饰器换底，组件引用不变）** | 重；隔离彻底 |
| **池级** | 预建多个池 → 按配置切换 | **my-xhs（DynamicDataSource 预建池切换）** | 快；池级隔离 |

**绑定细节两个**：①**类型转换**——Binder 绑定时字符串自动转目标类型（"16" → int 16，实验断言）——底层是 ConversionService（1.6 章节对照）；②**绑定监听**（源码 04 三章）——Binder 提供绑定监听 + 属性变更事件化（配置一变 → 事件发出 → 监听者联动）——热更新的"事件"骨架。

**事件链起点**（源码 03 三章交叉）：`PropertySourcesChangedEvent`——配置源变化事件——这是 03→06→07 三仓事件传播链的起点（多活章节 2.8 详述：配置变化 → Zone 变化 → 数据源重建）。

**实验验证属性级**（`ConfigSpecTest.environmentChangeTriggersRebind`）：环境属性源变更 → 重新 `Binder` 绑定 → 拿到新值——属性级热更新的最小模型。`@RefreshScope`（spring-cloud-context 实证，my-xhs 2 处使用）把"重新绑定"接到 Bean 生命周期上。

**粒度选型**：配置只影响一个值 → 属性级；配置影响 Bean 的组装结构 → Bean 级；配置是"选哪个资源"（数据源/连接池）→ 池级。**层次越深越重，但隔离越彻底**——这是 07 仓库 vs my-xhs 的架构对照核心（2.6 章节展开）。

## 5. 选型：Nacos vs etcd vs Apollo

| 组件 | 定位 | 特点 |
|------|------|------|
| **Nacos** | 注册 + 配置一体 | 双协议（AP 注册 + CP 配置）、长轮询推送、**健康保护阈值**（stage-3-25 KP-03——保护模式下返回旧数据 ≠ 系统不可用）；**领域模型三元组**（stage-3-25 KP-05——`namespace/group/dataId`：命名空间隔离环境、分组隔离业务、dataId 定位单个配置） |
| etcd | KV 存储（K8s 的底座） | 强一致（Raft 集群——3 节点起步/Leader 选举，共识章节 3.2 详述）、Watch 推送；无 Web 控制台（配置管理要自建） |
| Consul | 注册 + 配置（Go） | 竞品矩阵一员（stage-3-26 KP-01）——场景与 Nacos 重叠，国内生态 Nacos 更主流 |
| Apollo | 纯配置中心 | 配置管理面最强（灰度/审计/多环境）；需独立部署 |

**my-xhs 实证**：Nacos 配置已用——`shared-configs`（my-xhs-common.yaml，application.yml:70 实证）+ **Nacos 存储后端 = MySQL**（`nacos_config` 库实证——P2-6 的 Derby vs MySQL 核对项已有答案：MySQL）+ `@RefreshScope` 2 处。差距：配置变更 → 热生效的链路核对（P2-4）。

## 本章小结

**知识本体**：配置中心五件事（存储/获取/变更事件/集群/Open API）+ **配置要 CP**（vs 注册 AP）+ PropertySource 链抽象（配置中心 = 往链里插源）+ 三实现路径（文件/ZK/etcd——换存储换 Loader）+ **@PropertySource 四缺陷**（配置中心动机）+ **热更新三粒度**（属性/Bean/池——核心）+ 选型（Nacos/etcd/Apollo）。

**实验验证**：Binder 绑定 / 环境变更重绑定（属性级热更新）/ 约定推断（3 断言）。

**my-xhs 判定**：Nacos 配置已用（shared-configs + MySQL 存储实证）/ @RefreshScope 已用（2 处）/ 属性级热更新已用（Binder——框架托管）/ Bean 级重建该用没用（单数据源场景不必要——07 对照）/ 热生效链路待核（P2-4）。
