# 14. 服务网关：流量入口的一整套功夫

> 配套实验：`sca-lab/custom-java-infra/spec-gateway`（4 个断言）
> 定位：网关架构（路由三要素/Filter 链）+ 动态路由 + **端点粒度路由（差距 TOP①）** + RPC 网关 + Mesh + 多活网关
> 课程来源：stage-1-19/20 + stage-3-19/20/21/22 + stage-4-14/15（8 篇主属）+ 源码 09
> 前置：2.1（服务发现）、2.3（负载均衡——网关内部用 LB）

所有请求先进网关——**网关是整个系统的流量入口**。它做路由（去哪）、Filter（鉴权/限流/日志）、聚合、协议转换。这一章把网关的一整套功夫讲透：SCG 的路由三要素、动态路由、源码 09 的端点粒度路由（差距 TOP①）、RPC 网关、Mesh（网关的进化）、多活网关。

---

## 1. 路由三要素：Route/Predicate/Filter（SCG 核心模型）

SCG 的路由 = 三件事（stage-1-19/20 KP-01~03 实证 + `Route.java`/`GatewayFilterChain.java` 源码锚点）：

```java
Route（id + 匹配条件 + 目标 URI + 过滤器列表）
  ├─ Predicate：匹配条件（Path/Header/Query...——"这个请求归我管吗"）
  ├─ 目标 URI：转发到哪（lb://order-service——2.3 的负载均衡接入点）
  └─ Filter：处理链（鉴权/限流/改写/日志——"经过时做点什么"）
```

实验 `routeThreeElements` 验证了三要素 + 匹配（`/api/order/**` → order-route）。

**安全：网关是鉴权的天然位置**（stage-1-19 KP-07——所有请求必经入口——统一鉴权/签名校验放网关，业务服务专注业务——my-xhs 的 `GatewayAuthFilter`/`HmacSignatureFilter` 实证）。

**执行过程**（stage-1-20 KP-06）：`RoutePredicateHandlerMapping`（路由定位——哪个 Route 管这个请求）→ `GatewayFilterChain`（过滤器链）→ 转发。实验 `filterChainExecutionOrder` 验证了链序：**全局 Filter（request-id/trace）→ 路由 Filter（auth/metrics）→ 转发**。

## 2. 动态路由：路由可以不改代码地变

### 为什么必须动态

路由规则是基础设施——加服务/换权重/灰度切流都不能重启网关（重启 = 全体流量中断）。

### 机制（stage-3-19 KP-05 + stage-4-14 KP-04）

```
配置中心（Nacos 路由配置）
  → EnvironmentChangeEvent / 数据源变更
  → RefreshRoutesEvent（SCG 源码 RefreshRoutesEvent.java:27 实证——路由刷新事件）
  → RouteDefinitionRouteLocator 重新加载 → 新路由生效
```

**RouteLocator 体系**（stage-1-20 KP-01/04）：`RouteDefinitionLocator`（路由定义从哪来——yml/数据库/Nacos）→ `RouteDefinitionRouteLocator`（定义 → 可用路由）→ 路由缓存。**换路由来源 = 换 Locator 实现**（与 2.2 配置的 Loader 插件式同构）。

my-xhs 实证：灰度路由通过 **Nacos 实例元数据**（`gray-tag=gray` 标记——GrayRouteFilter 实证）+ 流量染色（TrafficColoringFilter——压测流量染色联动）+ 动态路由方案（自定义 RouteLocator——注释实证）。

## 3. 端点粒度路由（源码 09——差距 TOP①）

### 官方现状：服务粒度

SCG 路由到**服务**（`lb://order-service`）——服务内的方法级路由是服务自己的事。**官方没有端点粒度路由**。

### 源码 09 的 we://（差距 TOP① 的机制本体）

microsphere 的 `we://` 协议把路由粒度从"服务"下沉到"**端点**"（`we://order-service#createOrder`——路由直接到方法的端点元数据）。实验 `weEndpointRouting` 验证了机制：URI 重写链（端点目标 + 路径拼接）。

配套（源码 09 实证）：端点排除过滤（`/actuator` 不对外——实验 `endpointExclusion`）、metadata 协议链路（端点元数据从哪来——**协议隐患三连（G11/G12/G3）**：**G11 无分片**（metadata 超注册中心长度限制）/ **G12 无版本号**（`Kind.valueOf` 解析抛错——升级静默破坏）/ **G3 字段脱节**（context-path 发布不消费）——**协议设计的三个反面教训**）、Filter 链缓存 + 事件重建（性能 + 热更新）。

**端点元数据从哪来——跨仓库能力消费链**：源码 03 的 `WebEndpointMapping`（端点映射元数据——十字段模型）→ **09 we:// 路由是它的消费端**（端点元数据驱动路由——handover 关键链路：03 WebEndpointMapping → 09 we:// 路由）。stage-3-19 的 Actuator Mappings Endpoint 聚合也是同一思路（端点 = 可路由的原子单元）。

> 可跳过（缺陷家族）：G1-G15 缺陷清单（**15/15 全部源码证实**——心跳禁用断链根源/`globalFilters` 反射读私有字段/协议隐患三连（G11 无分片/G12 无版本号/G3 字段脱节）/G15 静默 200——可观测章节的静默失效家族成员）。

**自主实现思路**（差距 TOP①）：端点元数据 → 注册中心/配置中心 → 网关加载端点级路由表（we:// 目标 + 重写链）——my-xhs 差距清单 P 项。

## 5. RPC 网关（stage-3-20）

HTTP 网关之外的形态：**RPC 网关**——把 HTTP 请求转成 RPC 调用：

| 能力 | 说明 |
|------|------|
| Dubbo 泛化调用 | 网关不依赖 API jar——按服务名+方法名反射调用（泛化引用） |
| gRPC 网关 | HTTP/2 协议转换（1.7 章节的 gRPC 底座） |
| HTTP/2 + SSL | ALPN/TLS（1.7 章节——my-xhs P2-2 差距项） |

**网关的本质不变**：路由 + Filter + 协议转换——只是目标从"HTTP 服务"换成"RPC 服务"。**自动探测 Dubbo 上游**（stage-4-15 KP-04）：RPC 网关从注册中心自动发现上游服务（路由表自动生成——注册中心驱动的路由自动化，与 2.1 的服务发现联动）。

## 6. Mesh：网关的进化（stage-3-21/22）

**Service Mesh 演进五阶段**（stage-3-21 KP-01）：库内嵌（客户端 SDK）→ 独立库 → 代理 → Sidecar → Mesh——**"治理能力从代码里搬出来"**。

| | 网关 | Mesh |
|---|------|------|
| 位置 | 集中入口（南北流量） | **每服务旁路 Sidecar（东西流量）** |
| 能力 | 路由/限流/鉴权 | + 全链路治理（重试/超时/加密/观测） |
| 侵入 | 零（入口统一） | 零（Sidecar 透明代理） |

**Mesh 定义四面**（stage-3-21 KP-02——连接/安全/策略/可观测——四功能面）：连接（服务互通治理）、安全（mTLS 加密）、策略（限流/路由）、可观测（指标/日志/追踪）。

**Istio 流量管理**（stage-3-21 KP-04）：VirtualService/DestinationRule（xDS 下发——2.1 的 xDS 交叉）——"网关的路由能力下沉到每个 Sidecar"。可观测三面（指标/日志/追踪——2.9）+ Kiali（拓扑可视化——stage-3-22）。

**现代对应**（stage-3 梳理实证）：**Istio 1.x + Cilium Service Mesh**（eBPF 数据面——兴起中）+ **Dubbo 3.x Proxyless Mesh**（无 Sidecar——应用直接连控制面——Dubbo 生态的 Mesh 路径——4.3 交叉）——**"Sidecar 不是唯一形态，Proxyless 是纯 Java 生态的现实选择"**。

> 可跳过（进阶级，网关 Actuator 面——stage-3 网关域）：**Actuator Endpoints 架构**——统一注解 `@Endpoint`（合并 JMX 和 Web 双通道）+ **读操作（非敏感）vs 写操作（敏感）** 分级 + 暴露控制（`management.web.exposure.include/exclude` + 高版本默认仅最低权限 + `enabled-by-default` 默认 false）——**"端点暴露面是安全边界"**（2.9 的可观测消费端 × 本文的暴露控制端）。

> 可跳过：Mesh 引入是 P3 规划项（my-xhs 差距 P3-4——流量治理诉求触发时评估）；Istio vs 网关不是二选一——**入口网关 + 内部 Mesh 是现代组合**。

## 7. 多活网关（stage-4-14/15）

多活场景网关的三个关键（2.8 详述机制，本章讲网关侧）：

## 本章小结

**知识本体**：网关 = 路由三要素（Route/Predicate/Filter）+ 动态路由（RefreshRoutesEvent/RouteLocator 插件式）+ **端点粒度路由（we://——差距 TOP①）** + 可观测性能 + RPC 网关（泛化调用）+ **Mesh 演进**（Sidecar——治理出代码）+ 多活网关（双栈/AZ Locator）。

**实验验证**：路由三要素 / Filter 链序 / we:// 端点路由 / 端点排除（4 断言）。

**my-xhs 判定**：SCG 已用（starter + 5 个网关 Filter 实证：鉴权/灰度/流量染色/版本/签名）/ 动态路由已用（Nacos 元数据 + RouteLocator 方案）/ **端点粒度路由该用没用（差距 TOP①——自主实现）** / Mesh 该用没用（P3 规划）/ 压测基线缺失（P1-2）。
