> 课程来源：stage-1-11、stage-1-12（监控指标/动态权重 LB）+ stage-4-10、stage-4-11、stage-4-12（多活 LB/SCLB/四客户端）+ 源码 05 3.1（平滑加权）+ 源码 06 3.2（Zone Supplier）

2.1 讲"服务在哪"（注册中心给候选实例列表）。这一章讲"选哪个"：**order-service 有 3 个实例，每次调用选谁？** 这就是负载均衡——客户端侧（调用方自己选）还是服务端侧（网关/LB 代理选），微服务时代**客户端负载均衡是主流**（调用方直接从注册中心拿列表自己选，少一跳）。

---

## 1. 负载均衡的本质

**选实例 = 列表 + 策略**：候选实例来自注册中心（2.1），策略决定"选谁"。策略演进三阶段：

```
轮询（RoundRobin）→ 加权轮询 → 平滑加权轮询 + 动态权重
  均匀         带权（笨重）   平滑（经典）+ 感知性能（现代）
```

---

## 2. 算法：平滑加权轮询（面试手撕题）

### 为什么需要"平滑"

加权轮询的朴素实现有个问题：权重 2:1 时可能连续选 A、A、B——**权重大的被连续选中，流量突发堆积**。**平滑加权轮询**（Nginx 算法，源码 05 3.1 实证）解决：每轮 `current += weight`，选最大者，选中后 `current -= total`——**权重比例正确 + 不会连续选中**。

实验 `smoothWeightedDistributionFollowsWeightRatio` + `smoothnessNoConsecutiveStarvation` 验证了这两点：权重 2:1 → 分布 2:1，且 A 最多连续出现 2 次。

```java
// spec-loadbalancer SmoothWeightedRoundRobin（核心三行）
i.current += i.weight;      // ① 每轮累加
best.current -= total;      // ② 选中者减总量（平滑的关键）
```

## 3. 动态权重：负载跟着性能走

### 场景

三个实例性能不一样（一台机器老、CPU 高）——固定权重不公平。**动态权重**：用监控指标（CPU 利用率/响应时间）实时调整权重——**快的实例多接流量，慢的少接**（stage-1-11/12 核心命题）。

**WeightedResponseTimeRule 思路**（实验 `dynamicWeightFromResponseTime`）：响应时间反比 → 权重（10ms 的实例权重远大于 1000ms 的）→ 分布跟着性能走。

**指标从哪来**：JMX（CPU 利用率——`OperatingSystemMXBean.getSystemLoadAverage`，stage-1-11 KP-02/03 实证）→ 定期上报 → LB 调整权重。这是"监控 → 决策 → 动作"闭环在 LB 上的落地（完整监控体系——Prometheus/Grafana——在 2.9 可观测章节）。

> 历史对照（可跳过）：Ribbon 内置 `WeightedResponseTimeRule`——但 Ribbon 已过时（Spring Cloud 2020 起移除）；**Spring Cloud LoadBalancer 没有现成实现**——"手写 WeightedResponseTimeRule"是 stage-1 梳理明确的空白填补。**sca-lab 落地实证（gateway-lab）**：`WeightedResponseTimeGatewayFilter`——`weight = 1/(avgMs+1)`（响应时间反比）+ **RingBuffer 滑动窗口**（最近 10 次求平均）+ 冷启动退化均匀分布（无历史数据不偏见）+ 设计决策（order > 10150 必须在 LoadBalancer 之后——避免选择被覆盖）——**"动态权重"从课程概念到可运行代码的完整落地**。

## 4. 区域感知：Zone 优先（多活交叉）

### 场景

实例分布在不同机房（zone-a/zone-b）。**同机房调用**延迟最低——LB 应该优先选本 zone 实例（跨区兜底）。这就是多活的"区域优先路由"（2.8 详述——本章讲 LB 侧机制）。

实验 `zonePreferenceFiltersInstances` 验证了简化模型（`ZoneFilter`）：本 zone 有实例 → 只留本 zone；没有 → 跨区兜底。

**框架实现**：SCLB 的 `ZonePreferenceServiceInstanceListSupplier`（spring-cloud-commons 实证）——**"实例列表供应商"链式组合**：`DiscoveryClient 供应商 → Zone 过滤供应商 → 缓存供应商 → LB 算法消费**——每个环节一个 Supplier，可插拔组合（源码 06 3.2 的 Supplier 装饰链同构）。

## 5. 框架抽象：SCLB 的接口体系

### 两个核心接口

```java
// spring-cloud-commons ServiceInstanceListSupplier.java:33（实证）
public interface ServiceInstanceListSupplier extends Supplier<Flux<List<ServiceInstance>>> {
    // 提供"候选实例列表"（可链式组合：发现 → 过滤 → 缓存）
}

public interface ReactiveLoadBalancer<T> {
    Mono<Response<T>> choose(Request<T> request);   // 从列表里"选一个"
}
```

**列表和选择分离**——想换算法换 `ReactiveLoadBalancer` 实现，想换列表处理加 Supplier 链。my-xhs 的 `LeastConnectionsLoadBalancer` 就是扩展 `ReactiveLoadBalancer` 实现"最少连接"算法（注释实证：替代默认轮询）。

**列表的动态更新**（stage-4-10 KP-02 ServerList 体系）：候选列表不是静态的——注册中心实例变更 → 列表缓存刷新（定时拉取 + 变更监听双通道）。**"LB 选实例"永远基于一个会变化的快照**——刷新延迟窗口内可能选到已下线实例（2.1 的传播延迟在这里显现，靠客户端重试兜底）。

### 默认装配与算法切换（stage-4-11 KP-02）

SCLB 默认装配 = 轮询（`RoundRobinLoadBalancer`）——**换算法两种方式**：①配置（`spring.cloud.loadbalancer` 属性 + 启用候选类）②编程（自定义 `ReactiveLoadBalancer` Bean——my-xhs 走的就是这条路，`LoadBalancerClients#defaultConfiguration` 注册）。

### 子上下文（stage-4-10 KP-03——NamedContextFactory）

每个服务的 LB 配置**独立**——`LoadBalancerClientFactory`（NamedContextFactory 子上下文：**每个 serviceId 一个独立子上下文**，互不干扰）。my-xhs 注释实证：`LoadBalancerClients#defaultConfiguration()` 注册 → 每个 serviceId 独立 LeastConnectionsLoadBalancer。**这是"每服务独立配置"的 Spring 标准做法**（Feign 上下文同构——4.5 章节）。

## 6. 四个客户端怎么用（stage-4-12）

| 客户端 | 接入 LB 的方式 | 说明 |
|--------|--------------|------|
| RestTemplate | `@LoadBalanced` 注解 | 拦截器注入 LB |
| OpenFeign | 内置 | 声明式 + LB |
| WebClient | `@LoadBalanced`/自定义 | 响应式 + `ExchangeFilterFunction` |
| HTTP Interface | 复用上述 | Spring 6 声明式（1.7 章节） |

**"声明即负载均衡"**——四客户端统一模式：要么注解要么内置，调用方代码里看不到 LB 逻辑（stage-4-12 核心命题）。

## 7. my-xhs 实证：三个自研 LB

| 自研 | 算法 | 场景 |
|------|------|------|
| `LeastConnectionsLoadBalancer` | 最少连接 | 默认策略（替代轮询） |
| `ImConsistentHashLoadBalancer` | **一致哈希** | IM 粘性会话（同一用户固定同一实例）——**为什么不是取模**：实例增减时哈希环只影响相邻节点（最小迁移），取模会全量重映射（面试点） |
| `ZoneLoadBalancerConfiguration` | **Zone 感知** | 区域优先（多活——2.8 详述） |

**差距（P1-1 规划项）**：`GrayLoadBalancer`（灰度实例过滤——打标后按标记路由）注释"需后续实现"——打标已实现、实例过滤未实现（my-xhs-优化规划 P1-1）。

## 本章小结

**知识本体**：LB = 列表 + 策略——算法（轮询→加权→**平滑加权**）/ 动态权重（监控指标驱动——WeightedResponseTimeRule 思路）/ 区域感知（Zone 优先——Supplier 链式组合）/ 框架抽象（列表与选择分离 + 每服务子上下文）/ 四客户端统一接入。

**实验验证**：平滑加权分布 + 平滑性 / 动态权重 / Zone 过滤（4 断言）。

**my-xhs 判定**：LB 抽象已用（3 个自研：最少连接/一致哈希/Zone）/ 动态权重该用没用（无指标驱动权重——潜在 P2）/ 灰度 LB 未实现（P1-1 差距）。
