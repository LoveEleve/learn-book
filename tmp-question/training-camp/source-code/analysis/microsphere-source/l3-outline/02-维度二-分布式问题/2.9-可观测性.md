# 16. 可观测性：指标、追踪、日志三支柱

> 配套实验：`sca-lab/custom-java-infra/spec-observability`（4 个断言，Micrometer 实测）
> 定位：三支柱（指标/追踪/日志）+ 采集模式（Pull/Push）+ 规范锚点（W3C/OTel）+ **静默失效家族**（源码 11）
> 课程来源：stage-1-13、stage-1-14、stage-1-15、stage-1-16、stage-1-17、stage-1-18 + stage-3-29/30（8 篇主属）+ 源码 11 + 源码 05（注册四态事件）
> 前置：2.1/2.2（注册/配置的可观测面）

系统出问题时你怎么知道？——**指标**（慢了？多了？）、**追踪**（一次请求经过了哪些服务？）、**日志**（具体报了什么错？）。这就是可观测性三支柱（Observability）。这一章讲三支柱怎么用、指标怎么采集（Pull/Push）、规范长什么样、以及**静默失效家族**（训练营最有价值的反面教材）。

## 1. 指标：四种类型 + 采集模式

### 四种指标类型（stage-1-13 KP-01/02——实验全部实测）

| 类型 | 语义 | 典型指标 | 实验 |
|------|------|---------|------|
| **Counter** | 单调递增 | 请求数/错误数（吞吐） | increment 语义验证 |
| **Timer** | 耗时分布 | 响应时间（延迟——p99 的基础） | count/累计/max 验证 |
| **Gauge** | 当前值（可升可降） | 队列深度/连接数（存量） | set 语义验证 |
| Summary/Histogram | 分布桶 | 百分位（p95/p99） | 内建 |

**选型一句话**：数"发生了多少次"用 Counter；测"花了多久"用 Timer；看"现在有多少"用 Gauge——**别用 Gauge 数累计值（会丢）**。

**聚合语义**（stage-1-13 KP-03——面试点）：Counter 跨实例**可加总**（各实例计数求和 = 总量）；Gauge 跨实例**不可加总**（"队列深度"三实例各 5 不是 15——是取最大/平均）——聚合查询要按类型选算子。

**基数控制**：指标标签越细越危险（`uri` 标签带路径变量 = 基数爆炸——my-xhs `ApiMetricsFilter` 归一化 `/api/note/123` → `/api/note/{id}`——2.4 高基数同源问题的可观测面）。

### Pull vs Push（stage-1-15/16——两种采集哲学）

| | Pull（拉取） | Push（推送） |
|---|---|---|
| 机制 | Prometheus 定期 scrape 应用端点（`/actuator/prometheus`） | 应用主动推（Pushgateway/InfluxDB） |
| 优点 | 谁在采集可见/存活即发现 | 批处理/短生命周期任务适用 |
| 缺点 | 应用必须可被访问 | 推送目标挂了丢数据 |
| 现代 | **默认**（K8s 服务发现——Prometheus 自动发现） | 补充（批任务） |

实验 `prometheusExportTextFormat` 验证了 Pull 的文本格式（指标名 + 标签 + 值——Prometheus 标准）。**混合模式**（stage-1-16 KP-06）：长任务 Pull + 批任务 Push。

> **规范锚点（骨架 §9.5 补充——三支柱的现代标准面）**：①**OpenMetrics**——Prometheus 文本格式的开放标准（指标名 + 标签 + 时间戳 + 单位——`/actuator/prometheus` 的现代格式锚点——micrometer-prometheus 直接输出）；②**SLF4J 门面**——日志三支柱的"写一遍到处用"（1.1 章节的 JDK 门面对照 + 源码 02 5.2 的复刻实证）；③**ECS 结构化日志**——Elastic Common Schema（字段统一——`LogstashEncoder` 输出 ECS 兼容字段——my-xhs 实证——见 §3）。**统一方向：OpenTelemetry/OTLP 是三支柱的现代标准答案**（[缺口：外部补源]——骨架 §9.4 标注）。

### 框架：Micrometer（门面——写一遍到处用）

Micrometer = 指标门面（写代码时无关后端——Prometheus/Influx/JMX 随意换）。my-xhs 36 个文件用 MeterRegistry/Counter/Timer（实证）+ `ApiMetricsFilter`（每个请求记耗时——URI 归一化控制基数——2.4 的高基数同源问题）。

### 自定义 MeterBinder：cgroup 与系统指标（源码 11 3.1——KP-1003）

> 可跳过（进阶级）：**Micrometer 官方之外的 binder 扩展**——微球给"系统面"写自定义指标（`microsphere-observability/microsphere-micrometer/instrument/binder/system/` 三件）：

**① CGroupMemoryMetrics**（容器内存感知——你部署在 K8s 时 JVM 看不到容器内存限制）：**直读 cgroup 文件系统**（`/sys/fs/cgroup/memory/` 下的 memory.stat/memory.usage_in_bytes 等——cgroup v1）→ 指标化两族：**5 个字节型**（`cgroup.memory.usage_in_bytes`/max_usage/memsw.usage/memsw.max_usage/limit_in_bytes）+ **11 个 memory.stat 细分**（cache/rss/swap/active_anon/inactive_anon/active_file/inactive_file/unevictable/hierarchical_memory_limit 等）——**"JVM 之外的系统内存"补全**（对比 5.2 的 JVM 内存 10 项——**容器视角 vs JVM 视角**）。

**② 容器探测条件**（`@ConditionalOnResource("file:///sys/fs/cgroup/")`——:22 实证——**cgroup 文件存在才装配**——4.2 条件注解在指标面）：K8s 环境自动生效、裸机自动跳过——**"条件装配做环境感知"**。

**③ 系统指标族**：SystemMemoryMetrics（系统内存）/NetworkStatisticsMetrics（网络统计）+ JMX MBean 指标化（MBeanAttributeMeterBinder——5.2 的 JMX 面联动）+ SentinelMetrics（2.4 对接）+ MicrometerJdbcEventListener（P6Spy——5.4 的 JDBC 面）。

> 可跳过（进阶级，反模式——11 仓 4.2 死代码清单）：**"设计文档式代码"**——`MBeanAttributeMeterBinder` **接口骨架无实现**（:39）+ `CompositeFilter` TODO（:36）+ `I18nLogger` **只完成 trace() 其余空方法**——**"接口先行但实现没写"的代码 = 用代码当设计文档**。**教训**：①接口定义 ≠ 功能可用（README 里没写的功能默认没有）；②**空实现方法**（I18nLogger 的 trace 之外全空）是**隐藏的坑**——调用方以为有日志实际静默丢弃（静默失效家族变体——G15 同族）；③**写代码先写实现，接口先行必须配 TODO 清单**。**识别法**：接口/抽象类方法多但实现类方法空 → 查 TODO/空体——"设计文档式代码"一眼认出。

**my-xhs 判定**：**该用没用**——my-xhs 用官方 actuator + micrometer 指标（36 文件），**自定义系统/cgroup binder 未用**（K8s 部署后容器内存指标为差距——outline 11 标注"CGroup 指标可借鉴"）；JMX/Sentinel/JDBC binder 同理（官方/生态覆盖评估）。

## 2. 追踪：一次请求的完整路径

### 核心模型（stage-1-17 KP-01/02）

**Trace（一整条请求链）+ Span（链上的每一跳）**——每个服务在请求头上拿 `traceId`（同一个），自己的调用生成子 Span（spanId）。

**Trace ID 上下文传递**（stage-1-17 KP-03——关键）：HTTP 头带 traceId（**W3C Trace Context 标准——`traceparent` 头**——1.1 章节实证；历史 B3/Zipkin 头——`X-B3-TraceId`——已过时）→ 服务间传递 → 日志里也带（MDC）→ 全链路可关联。

**my-xhs 实证（trace 透传三面）**：`TraceIdConfig`（HTTP）+ `FeignTraceInterceptorConfig`（Feign 调用）+ `MqTraceHelper`（MQ 消息）——**透传的完整面**（+ MdcAwareExecutorService——异步线程池 MDC 透传——2.4 交叉）。

### 埋点演进（stage-1-17/18）

应用层埋点（侵入）→ 框架自动埋点（Sleuth/Filter）→ **字节码/Agent 层自动埋点**（Instrument——SkyWalking——零侵入，1.7 章节已述机制）。

> 可跳过（进阶级）：**埋点位置**（stage-1-17 KP-06——TraceValve vs TracingFilter）——Tomcat Valve（容器级——请求进容器的更早位置）vs Servlet Filter（应用级）——容器层埋点能覆盖更广但侵入容器；应用层埋点灵活但覆盖面有限。现代链路：**Micrometer Tracing（Observation API——统一 metrics+tracing+logging——`@Observed` 注解替代 Sleuth 的 `@NewSpan`——stage-1 现代替代映射实证）+ W3C 传播**；SkyWalking 是生产主力（字节码增强 + 拓扑发现）；**OpenTelemetry（OTel）是统一标准方向**（[缺口：外部补源——2.9 现代锚点标注]）。

## 3. 日志：ELK 平台（stage-3-29）

**ELK 架构**：应用（logback + `LogstashEncoder`——my-xhs 实证）→ Logstash（采集/转换）→ **Kafka（缓冲削峰——异步传输）** → ES（存储/检索——节点角色：master/data/ingest）→ Kibana（可视化）。

```
应用 → Logstash → Kafka（削峰）→ ES → Kibana
```

**关键设计**：①**异步化传输**（日志不打崩应用——AsyncAppender）②**Kafka 缓冲**（Logstash 处理不过来时积压不丢——削峰）③**日志生命周期**（保留策略——ILM 清理——my-xhs P2-3 差距项）。

## 4. 监控平台（stage-3-30）

**VictoriaMetrics**（VM）：Prometheus 兼容的时序数据库——**无缝迁移**（PromQL 兼容）+ 集群部署 + 性能更优。选型：数据量大/保留期长 → VM（my-xhs P3-2 规划项）；标准场景 Prometheus 够用。OpenTSDB 整合（历史——`[过时→VM]`）。

**Grafana 面板与告警**（stage-1-15 KP-05）：可视化面板（my-xhs 的 Prometheus + Grafana 部署实证）+ **告警规则**（my-xhs `alert_rules/myxhs_rules.yml` 实证——hikaricp_connections 等指标告警）——"主动切流 vs 被动降级"的告警策略区分（2.8 多活反模式第 7 条交叉）。

## 5. 静默失效家族（源码 11——教学金矿）

**"系统没报错，但功能不对"**——可观测性的反面教材（源码 11 + handover 缺陷家族）：

| 模式 | 现象 | 教训 |
|------|------|------|
| **P1 时序** | `@EventListener` 在自动配置早期注册 → **事件永不触发**（启动缓冲 InMemoryAppender——早期日志丢失） | 事件注册有"时序铁律"——早期事件要缓冲后转移（源码 11 的缓冲-转移模式） |
| **P2 语义** | `@ConditionalOnBean(name=...)` vs `value=...` 混用 → 条件静默不匹配（1.6 章节详述） | API 语义细节 |
| **G15 无日志** | 网关未命中端点静默 200（源码 09） | 失败必须可观测——"没日志的失败 = 事故伏笔" |

**可观测的第一性**：**每个失败都要有日志/指标**——这是全章的核心结论（静默 = 最贵的 bug）。
