# 04. Bean Validation：用注解声明"参数不能乱来"

> 配套实验：`sca-lab/custom-java-infra/spec-validation`（5 个断言，Hibernate Validator 实测）
> 定位：**规范的使用层面**——注解声明式校验怎么用、坑在哪。校验器内部实现不在本章
> 课程来源：stage-1-03（主属）+ stage-1-04（交叉）| 前置：写过 REST 接口、用过 @Valid

写接口最常见的三句废话代码：

```java
if (userName == null || userName.trim().isEmpty()) { throw ... }
if (userName.length() < 2 || userName.length() > 20) { throw ... }
if (!phone.matches("^1[3-9]\\d{9}$")) { throw ... }
```

每个接口都要写一遍，换个人风格还不一样。**Bean Validation 规范（JSR-380）解决这个**：把校验规则声明成注解挂在字段上，校验器统一执行：

```java
@NotBlank(message = "用户名不能为空")
@Size(min = 2, max = 20, message = "用户名长度 2-20")
private String username;
```

这一章讲：核心注解、级联/分组/自定义三个进阶、和 Spring 怎么配合。my-xhs 有 55 个文件在用这套东西——它是 Java 后端的事实标准。

---

## 1. 核心用法：注解声明

### 常用约束（my-xhs 真实使用画像）

| 注解 | 意思 | my-xhs 用量 |
|------|------|:--:|
| `@NotNull` | 不能是 null | 54 |
| `@Size` | 长度范围 | 28 |
| `@Min`/`@Max` | 数值范围 | 25/16 |
| `@NotBlank` | 非 null 且非空白（字符串） | 23 |
| `@Positive` | 必须正数 | 13 |
| `@Pattern` | 正则匹配 | 6 |
| `@FutureOrPresent`/`@Past` | 时间校验 | 2/1 |

**空值语义（面试爱问）**：`@NotBlank`/`@Size`/`@Min` 这类"值约束"遇到 null 是**放行**的——null 交给 `@NotNull` 管。"为空 vs 值不合法"是两个职责，别混。

**三个"空"注解的区别——三空辨析（高频面试题）**：
- `@NotNull`：只要不是 null（空字符串/空集合都算"非 null"——所以它管不住"空"）
- `@NotEmpty`：非 null 且非空（字符串长度>0 / 集合元素>0）
- `@NotBlank`：非 null 且非空白（去空格后还有字符——字符串专用）

### 使用三步

```java
// ① 字段挂注解
public class UserRequest {
    @NotBlank(message = "用户名不能为空")   // message 就是报错文案
    private String username;
}

// ② 构建校验器（Hibernate Validator 是参考实现）
Validator validator = Validation.buildDefaultValidatorFactory().getValidator();

// ③ 校验 → 拿到违规集合
Set<ConstraintViolation<UserRequest>> violations = validator.validate(user);
violations.forEach(v -> System.out.println(v.getPropertyPath() + ": " + v.getMessage()));
```

实验 `ValidationSpecTest.basicConstraints` 验证了三条违规同时报出（长度/年龄/手机号——每个违规一条消息，不是"第一个错误就停"）。

## 2. 三个进阶：级联、分组、自定义

### 级联：嵌套对象也要校验

请求对象里套着对象（`user.address.city`）——字段上加 `@Valid`，嵌套对象就跟着校验。实验 `cascadeValidationWithValid` 验证了：address 的 city 为空时违规被报出。

### 分组：同一个字段，不同场景不同规则

创建用户要校验手机号，更新用户不校验——用"组"：

```java
public interface Create { }
public interface Update { }

@Pattern(regexp = "^1[3-9]\\d{9}$", groups = Create.class, message = "手机号格式不正确")
private String phone;
```

调用时指定组：`validator.validate(user, UserRequest.Create.class)`——**只跑该组的约束**。实验 `groupValidation` 验证了分组隔离（Create 组报手机号、Update 组不报）。

> **踩坑（实验实测）**：级联校验时**组照样过滤**——嵌套对象的约束如果没挂到当前组，就不会触发。挂约束时别忘组。

### 自定义约束：内置不够用就自己造

两件套：注解（`@Constraint(validatedBy = ...)`）+ 实现（`ConstraintValidator`）：

```java
@Constraint(validatedBy = ChinesePhoneValidator.class)   // 注解：声明用哪个校验器
public @interface ChinesePhone {
    String message() default "手机号格式不正确";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class ChinesePhoneValidator implements ConstraintValidator<ChinesePhone, String> {
    public boolean isValid(String value, ConstraintValidatorContext context) {
        return value == null || value.matches("^1[3-9]\\d{9}$");  // null 放行（由 @NotNull 管空）
    }
}
```

实验 `customConstraint` 验证了自定义约束生效。

> 可跳过（进阶级）：
- **快速失败 vs 全量收集**：默认是"全量收集"（一次报出所有违规——实验 basicConstraints 就是三条一起报）；Hibernate Validator 可开 failFast（遇到第一个就停）——批量导入场景用全量，接口校验用默认即可
- **方法级校验**：类上 `@Validated` + 方法参数注解——校验失败抛的是 `ConstraintViolationException`（注意和 MVC 的 `MethodArgumentNotValidException` 是两个异常）
- **类级约束**：字段/方法不够用时（如"开始时间必须早于结束时间"的交叉字段）——用 `@AssertTrue` 挂在 getter 上或 `@ScriptAssert` 类级脚本校验
- **校验器线程安全**：`Validator` 实例是线程安全的，可全局共享（别每次校验都新建——性能面）
- **可重复注解**：同一字段多套规则用 `@Size.List({...})` 组合（@Email 这类常用内置约束也值得扫一眼 my-xhs 画像——它没用到是因为手机号场景多）

①**消息国际化**——`message` 可以引用 `ValidationMessages.properties` 里的键（`message = "{phone.invalid}"`），多语言文案集中管理。②（Expression Language，EL）依赖**——Hibernate Validator 处理消息插值需要 EL 实现（如 Tomcat EL，实验 pom 里的 jakarta.el）——依赖缺失时启动会报错，这是引入校验器最常见的坑。③**依赖隔离**——Hibernate Validator 与 Netty/Hibernate/JBoss Common Logger 等框架存在类冲突历史（logger 类名碰撞），引入时要留意（stage-1-03 KP-05 实证）。

## 3. 与 Spring 的配合

### MVC 自动校验

Spring Boot 里不用手动调 `validator.validate()`——Controller 参数上加 `@Valid`（或类上 `@Validated`），框架自动校验，失败抛异常：

```java
@PostMapping("/users")
public void create(@Valid @RequestBody UserRequest request) { ... }
```

Spring 的适配是 `LocalValidatorFactoryBean`（`spring-context` 的 `validation/beanvalidation` 包实证——还有 `OptionalValidatorFactoryBean`/`MethodValidationPostProcessor`/`SpringValidatorAdapter`）。**校验失败不直接返回 400**——抛 `MethodArgumentNotValidException`，由你的统一异常处理（`@RestControllerAdvice` + `@ExceptionHandler`）翻译成统一响应格式（stage-1-03 KP-06——my-xhs 的 `GlobalExceptionHandler` 实证）。

### 一个历史包袱：命名空间迁移

老项目里看到 `javax.validation`（Spring Boot 2.x 时代），现在是 `jakarta.validation`（Boot 3.x，Java EE 9 改名）——**只换包名，机制没变**（第 1.2 章 Servlet 讲过同样的事）。

## 本章小结

**知识本体**：Bean Validation = 注解声明式校验——常用约束 + 空值语义（null 放行） + 级联（@Valid）+ 分组（场景差异化）+ 自定义（两件套）+ Spring 集成（@Valid 自动校验 + 统一异常翻译）。

**my-xhs 判定**：**已用**（55 个文件实证——@NotNull 54/@Size 28/@Min 25 等真实画像；`@Valid` + `GlobalExceptionHandler` 统一处理）。

**一句话选型**：新接口一律声明式校验，别写手写 if——**"不推荐 Spring WebMVC 自定义扩展，推荐 Bean Validation 标准扩展"**（stage-1-03 KP-05 结论）。

> **排除注记（骨架 §9.4 决策）**：**JPA 不设主题**——训练营以 MyBatis 为主（JPA 仅 stage-3-12 一提——ORM 面归 2.6 交叉）；本维度规范面覆盖 Validation/JDBC/Bean 等，JPA 规范不在范围内（用户明确决策）。
