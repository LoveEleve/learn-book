# 01. Java SE 规范：JDK 没给怎么办

> 配套实验：`sca-lab/custom-java-infra`（30 个断言，`mvn clean test` 全绿）
> 前置：Java 基础 + 用过 Spring
> 课程交叉：stage-3-32/33（Java 版本与语言演进，主属 5.2 章节）
> 配套实验模块：`spec-jdk`（SPI/资源束/Base64/空注解/日志）+ `spec-apt`（编译期三阶段闭环）

有个老项目叫 confucius-commons，36 个文件，每个文件都在回答同一个问题：**"JDK 没给怎么办？"**

JDK 6 的时代没有 `java.util.Base64`，没有 `ServiceLoader.stream()`，properties 文件中文会乱码。于是它手写编码、手写 Base64、手写 SPI 加载器。

然后有意思的事发生了：**JDK 后来把这些手写实现全收了**。每个手写类都对应一条"JDK 演进吃掉框架模式"的轨迹。留下来的不是代码，是规范——这些规范到今天还在用。这一章讲六个这样的故事：SPI、资源束、Base64、空注解、编译期注解、日志。每个故事都配了实验，能跑。

---

## 1. SPI：框架怎么"不认识你的实现"也能用上它

### 场景

你写了一个接口 `Serializer`。你想让任何人往 classpath 里丢一个自己的实现，你的框架**一行代码不改**就能发现它、用它。怎么做到？

"直接 new"不行——你编译时不知道实现类叫什么。"扫描所有类"不行——太慢。Java 的答案很朴素：**接口的全限定名当文件名，放在 `META-INF/services/` 目录下，文件里写实现类的全限定名**：

```
# src/main/resources/META-INF/services/你的接口全名
com.example.MySerializer
```

框架拿接口名字去读这个文件，找到实现类，加载。

**配置即发现，文件即注册表。** 这就是 SPI（Service Provider Interface）。

### 使用三步走

```java
public interface Greeter { String greet(String name); }   // ① 定义接口

// ② 实现 + 在 META-INF/services/ 下注册（文件名 = 接口全名）

// ③ 加载
ServiceLoader<Greeter> loader = ServiceLoader.load(Greeter.class);
for (Greeter g : loader) {          // 遍历 = 按文件里的书写顺序实例化
    System.out.println(g.greet("world"));
}
```

实验 `SpiTest.orderFollowsConfigurationFile` 验证了一个关键语义：**加载顺序 = 配置文件书写顺序**（文件里谁在前谁先被返回），不是排序、不是"最优"。要"选最优"得自己加排序（microsphere 加了个 `Prioritized` 接口干这事）。

### 三个必须知道的语义

1. **实现类必须无参构造**——SPI 加载不了有参构造的实现（框架没法猜参数）。
2. **"没实现"怎么处理是你的事**——confucius 的选择是直接抛异常（fail-fast：生态里 SPI 是强契约，没有实现就是装配错了，早炸好）。如果你写的是"可选扩展"，该返回空列表。
3. **JDK 9+ 推荐 `stream()`**：拿到"提供者"再决定要不要实例化（懒加载）。

### 你其实每天都在用 SPI

Spring 的"自动配置"就是 SPI 的改版（`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，由 `SpringFactoriesLoader` 加载）。**理解 JDK 的原始 SPI，Spring 的"魔法"就没了魔法**。my-xhs 一个 ServiceLoader 都没写——但每个 Spring Boot 项目启动时，驱动加载（JDBC 章节）、自动配置发现，全走这个机制。

## 2. ResourceBundle：中文乱码的故事

### 场景

你的项目要支持中英文。按惯例，文案放在 `messages.properties` 里，代码用 `ResourceBundle.getBundle("messages", Locale.CHINA)` 取——**按 locale 自动选文件**（`messages_zh_CN.properties` / `messages_en.properties`）。

JDK 6 时代有个坑：properties 文件默认按 **ISO-8859-1**（拉丁字符集）读——**中文全变乱码**。confucius 的解法是扩展 `ResourceBundle.Control`（规范留给你的"干预点"），重写"怎么读文件"这一步，指定 UTF-8。

**然后 JDK 自己把这个问题解决了**：JDK 9 起 properties 默认按 UTF-8 读。实验 `ResourceBundleTest.defaultLoadingIsUtf8SinceJdk9` 直接验证：今天什么都不做，中文就正确。

**这个故事的意义**：confucius 当年写的 Control 扩展类现在还在、还能用——但已经没用了。**框架解决的标准问题，最终由 JDK 标准化吸收**——这是本章反复出现的主题。

> 可跳过（排查用）：如果你要干预资源加载（不是编码问题，比如加密的 properties），JDK 9+ 的官方扩展点是 `ResourceBundleControlProvider`（SPI 方式注册）。`Control` 类本身没弃用（JDK 17 实测）——但"凭印象说弃用"是写技术文档的大忌，要查源码。

## 3. Base64：一个编码的故事

### 场景

要把二进制数据转成纯文本传输（比如签名、图片转文本），用 Base64。JDK 8 之前没有官方实现——confucius 直接把一段现成代码复制进自己的项目：

```java
@author Josh Bloch      // 文件头写着原作者
@see java.util.prefs.Preferences
```

**文件头就是"移植识别"的证据**：这段代码是 JDK 1.4 起 `Preferences` 内部藏着的 Base64（它自己要用，但 JDK 8 前没公开），作者 Josh Bloch 是 JDK 的大神。confucius 复制了过来（还保留了作者署名——识别移植就靠看文件头的版权注释）。

### 现在：用官方的

```java
String s = Base64.getEncoder().encodeToString(data);   // 标准版
Base64.getUrlEncoder().withoutPadding()...             // URL 安全版（+ / 换成 - _）
Base64.getMimeEncoder()...                             // MIME 版（76 字符换行）
```

实验 `Base64Test` 做了一件事：**手写一份 Base64（面试手撕题级别），然后和官方实现逐字对照**——编码结果必须一致。算法本身值得亲手写一遍（3 字节 → 4 字符，不够补 `=`），但生产永远用官方。

my-xhs 有 3 处 `java.util.Base64`（网关签名、验证码、AI 服务）——全部官方 API，零自研。**手写版本被官方替代，留下来的只有 RFC 的规范本体。**

## 4. 空注解：一个从未进 JDK 的规范

### 场景

你想表达"这个参数不能为空"——Java 里没有内置的 `@Nonnull`。有个叫 **JSR-305** 的规范提议过它，但**从未进入 JDK**（第三方，后来停维护）。不是过时，是从没生效过。

### 但它留下了一个好设计：TypeQualifierNickname

JSR-305 有个"注解组合"机制：用 `@TypeQualifierNickname` 给注解起"昵称"，新注解自动继承被组合注解的语义。microsphere 用它做了双契约：

```java
@javax.annotation.Nonnull       // 组合"必须非空"
@TypeQualifierNickname
public @interface Nonnull { }    // 昵称：非空

@javax.annotation.Nonnull(when = When.MAYBE)   // 同一源头，加条件
@TypeQualifierNickname
public @interface Nullable { }   // 昵称：可空
```

**一个源头，两种契约**。实验 `NullableTest` 验证了组合语义（`@SpecNonNull` 上能反射读到 `@Nonnull(when=ALWAYS)`），还发现了一个真实细节：**昵称标记本身不保留到运行期**（编译期约定，静态分析器用）——用 `getAnnotation` 查昵称标记会得到 null，不是没组合，是它根本不保留。

### 来源识别的教训

microsphere 里还有一对 `@ThreadSafe/@NotThreadSafe`，看着像 JSR-305——**看文件头**：

```
Copyright (c) 2005 Brian Goetz
Official home: http://www.jcip.net
```

Brian Goetz，**《Java Concurrency in Practice》（JCIP）作者**——这是 JCIP 书附带的注解，跟 JSR-305 没关系。**来源断言必须查文件头**，这是移植识别的基本功。

**移植来源三实证**（源码 02 九章——版权头识别法作为系统方法）：①**Base64**——作者头 `@author Josh Bloch`（上文）；②**ThreadSafe 注解**——`Copyright (c) 2005 Brian Goetz`（JCIP——上文）；③**JSON 库**——`Copyright (C) 2010 The Android Open Source Project`（JSON.java:2 实证——**Android OpenJDK 移植**）。**方法**：写"是 XX 移植"前必须查 header——版权头是识别来源的唯一实证手段（没有版权头 = 存疑）。

> 现在怎么写：JSpecify（标准方向，还没落地）或 Spring 的 `org.springframework.lang.Nullable`。my-xhs 一个空注解没用——Spring 生态里不需要自造。

## 5. 注解 + 编译期：一个"选型"的故事

### 场景：配置怎么变成对象

Spring 的做法：`@ConfigurationProperties` 标注的类，**运行期**启动时扫描、反射绑定——字段名 `server.port` 对应配置 `server.port`，**靠约定猜**。

microsphere 选了另一条路：**编译期**就把配置声明变成元数据。它的注解叫 `ConfigurationProperty`（六要素全显式，不猜——name/type/defaultValue/required/description/source），实验里复刻成了 `@ConfigProperty`：

```java
@ConfigProperty(name = "app.threads", type = Integer.class,
                defaultValue = "8", required = true, description = "线程数")
public int threads;
```

然后一个"三阶段闭环"：

```
阶段一 注解声明（上面的 @ConfigProperty）
阶段二 编译期：一个"注解处理器"在编译时把注解变成 JSON 文件（javac 自动调用）
阶段三 运行期：读那个 JSON，得到配置对象
```

实验 `spec-apt` 模块把这条链完整跑通了（`AaptThreeStageLoopTest` 断言编译期生成的 JSON 与注解声明完全一致）。

### 取舍：两种哲学

| | 编译期（microsphere） | 运行期（Spring） |
|---|---|---|
| 类型安全 | 编译时就定 | 运行期反射 |
| 启动速度 | 快（无反射扫描） | 有反射成本 |
| 灵活性 | 改声明要重新编译 | 灵活 |
| 复杂度 | 要自建 APT 工具链 | 框架内置 |

没有谁对谁错——**学这个闭环是理解一切"编译期魔法"的地基**：Lombok（生成 getter）、MapStruct（生成映射代码）、Spring AOT——全是"注解 + 编译期处理"。

### 两个实验踩出来的坑（写注解处理器的必知）

1. **处理器里不能读注解的 Class 类型属性**——编译期"Class 对象"还不存在，直接读会抛异常（`MirroredTypeException`）。要从字段的类型（TypeMirror）取。
2. **处理器靠 SPI 注册**（`META-INF/services/javax.annotation.processing.Processor`）——`@SupportedAnnotationTypes` 只是声明"我管哪些注解"，不注册的话 javac 根本不会调用你。输出文件靠 `Filer`（编译期写文件的官方工具）——实验的 JSON 就是它写的。

> 可跳过（进阶级，写完整 APT 工具链再看）：microsphere 还给这条链配了三样东西——编译期产物的文件约定（`ResourceConstants` 定义的 `META-INF/microsphere/configuration-properties.json` 路径）、16 个语言模型工具文件（`lang-model`，Element/TypeMirror 的工具化 + `JSONElementVisitor` 把注解元素转 JSON）、库作者用的元注解三件（`@Since`（模块+版本双属性）/`@Experimental`/`@Immutable`）。知道存在即可。

## 6. 打日志与管理：JDK 的日志门面与 JMX

> 可跳过（进阶级）：**JMX** 是 JDK 的管理监控标准（`java.management` 模块）——`ClassLoadingMXBean` 这类平台 MBean 能读已加载类数等，`setVerbose(true)` 等价运行时开 `-verbose:class`。现在业务代码几乎不直接写 JMX（Arthas/Prometheus 替你消费了），知道"JMX 是平台标准、MBean 是对象模型"即可。

### 打日志：JDK 自己的日志门面

### 场景

你的库想打日志，但不想强绑 logback 还是 log4j——**打给"门面"，底层随意换**。SLF4J 是事实标准，但它不是 JDK 的。JDK 9 起（JEP 264）JDK 有了自己的：

```java
Logger log = System.getLogger("com.example.MyClass");
log.log(Level.INFO, "你好");
```

结构就两样东西：`System.Logger`（门面接口，打日志的 API）+ `System.LoggerFinder`（SPI 钩子，日志框架实现它就被自动桥接）。**JDK 自己演示了一遍"门面 + SPI"**（第一节的活学活用）。顺带澄清一个容易混的点：JDK 早先还有个完整的日志框架 **JUL**（`java.util.logging`）——JUL 是框架，System.Logger 是门面，两者不同（JUL 太笨重，生产没人用）。

> 用法细节：高并发路径先 `log.isLoggable(Level.DEBUG)` 再拼字符串——避免白干活。

**现在怎么写**：my-xhs 走 SLF4J/logback（生态最广）。`System.Logger` 适合"库作者不想引依赖"的场景。

## 本章小结

六个故事，一条共同的轨迹：

| 手写/封装 | 规范本体 | JDK/生态最终形态 |
|---|---|---|
| SPI 加载器 | SPI | `ServiceLoader.stream()` + SpringFactoriesLoader |
| 编码 Control | ResourceBundle | **UTF-8 默认（JDK 9 吸收问题）** |
| 手写 Base64 | RFC 2045/4648 | `java.util.Base64` |
| JSR-305 昵称 | 空注解语义 | JSpecify / Spring Nullable |
| 自研注解元模型 | 注解处理（APT） | Spring `@ConfigurationProperties` |
| 日志门面复刻 | 日志门面 | `System.Logger` + `LoggerFinder` |

**每一条都是同一件事：JDK 把框架的手写实现标准化，框架代码失去存在理由。** 所以学这些"旧"代码，学的不是代码——是代码背后的规范本体，和"JDK 演进吃掉框架模式"的观察方法。

判断一个技术该不该学，看它是"规范/机制"还是"实现"：规范永远值得学，实现要看有没有被官方替代。**判定"不该用"不丢人，知道为什么不该用才是知识。**
