# 02. Servlet：你的请求是怎么到达你写的 Controller 的

> 配套实验：`sca-lab/custom-java-infra/spec-servlet`（3 个断言，内嵌 Tomcat 实测）
> 前置：会写 Spring Boot 的 @RestController 就行

你在浏览器敲一个网址，回车。请求先到一个叫 **Tomcat** 的程序，然后一路被分发，最后到你写的 `@RestController` 方法里，跑完再一路返回来。这中间"请求怎么走、组件什么时候创建、谁负责转发"——全由 **Servlet 规范**规定。你天天用 Spring Boot，但 Boot 只是住在 Servlet 容器（Tomcat）里的一个房客。

这一章跟着一个请求走一遍，把 Servlet 规范讲明白。

---

## 1. 起点：你的项目里其实住着两个世界

```
Tomcat（Servlet 容器：管 HTTP、管连接、管线程）
  └─ Spring（你的代码：DispatcherServlet 住在 Tomcat 里）
```

`DispatcherServlet` 你其实天天在用——Spring MVC 的所有请求都先进它。而它本身就是一个 `Servlet`（规范里的组件类型），由 Tomcat 管理生命周期。**两级容器模型**：Tomcat 管"HTTP 和线程"，Spring 管"你的 Bean"。

> 课程交叉：stage-3-09（HTTP 架构升级，主属本篇）+ stage-1-07/21（Tomcat 容错/性能，主属 2.4/5.1 章节）

规范从 Servlet 2.3 一路演进到 6.0，三个里程碑（记住这三个就够了）：

| 版本 | 里程碑 | 一句话 |
|------|------|--------|
| 3.0 | **异步** | 长任务不再占着线程干等（第 5 节） |
| 3.1 | **非阻塞 IO** | 读写数据也不阻塞线程（`ReadListener`/`WriteListener`） |
| 4.0 | **HTTP/2** | 协议层提速（多路复用） |

还有个事别搞混：Servlet 5.0 起包名从 `javax.servlet` 换成 `jakarta.servlet`——**只是换了个名字，机制没变**（Java EE 被 Eclipse 接管后改名 Jakarta EE）。看到 `jakarta.servlet` 别慌。

## 2. Servlet 的一生：谁创建它、谁销毁它

### 生命周期：容器说了算

一个 Servlet 组件（包括你的 DispatcherServlet）**不是 new 出来的，是 Tomcat 按契约管的**：

```
容器启动 → init()（只调一次，做初始化）
每次请求 → service()（处理请求）
容器关闭 → destroy()（做清理）
```

实验 `ServletSpecTest.lifecycleInitThenService` 验证了这个顺序：第一次请求到达前，`init` 一定已经跑过。

**使用启示**：初始化逻辑放 `init`，不要放构造函数——构造函数跑的时候 Tomcat 还没把环境准备好（拿不到配置）。

### 并发模型：一个实例服务所有请求

**关键认知（单实例多线程模型）**：一个 Servlet 只有一个实例（Tomcat 只 new 一次），**所有请求并发地调用它**。所以 Servlet 里的字段必须是"只读的或线程安全的"——有状态的字段就是并发 bug 温床。这也是为什么 Spring 的 Bean 默认要求无状态。

## 3. 请求怎么被认领：注册与映射

### 怎么告诉 Tomcat"这个 URL 交给谁"

三种方式（历史演进）：

| 方式 | 写法 | 现在还用吗 |
|------|------|-----------|
| web.xml | `<servlet>` + `<servlet-mapping>` | 老项目（WAR 部署） |
| 注解 | `@WebServlet("/hello")` | 有限支持（Boot 里要 `@ServletComponentScan` 扫到才生效） |
| **编程** | `ctx.addServlet("hello", servlet).addMapping("/hello")` | **现代默认（Boot 内部就是这么干的）** |

> 可跳过（进阶级）：Boot 的编程注册体系叫 `RegistrationBean` 族（ServletRegistrationBean/FilterRegistrationBean）；传统 WAR 外置部署（`SpringBootServletInitializer`）已过时——现代默认嵌入式 + Docker。

Spring Boot 里你写的 `@RestController` 最终都被编程注册成"DispatcherServlet 上的路由"。

### URL 匹配规则（面试爱问）

`addMapping("/hello")` 里的模式有优先级：

| 模式 | 例子 | 优先级 |
|------|------|:--:|
| 精确 | `/hello` | 最高 |
| 前缀 | `/api/*` | 中 |
| 后缀 | `*.do` | 低 |
| 默认 | `/`（兜底） | 最低 |

请求按"最长前缀"匹配——`/api/order/1` 命中的是 `/api/*` 而不是 `/`。

### 一个容易踩的坑：注册时机

编程注册不是"随便什么时候都能调"——Tomcat 源码里有一个硬性检查：**只能在容器启动的过程中注册**（技术上是 STARTING_PREP 阶段），启动之前或之后调 `addServlet` 都会报错。正确的编程注册入口是实现一个 `ServletContainerInitializer`（容器启动时回调它）：

```java
// spec-servlet .../DemoInitializer.java（实验）
public class DemoInitializer implements ServletContainerInitializer {
    @Override
    public void onStartup(Set<Class<?>> c, ServletContext ctx) {
        ctx.addServlet("hello", new HelloServlet()).addMapping("/hello");
    }
}
```

这条"SCI → Spring 的 SpringServletContainerInitializer → Boot 初始化"的链路，就是 Boot 启动时注册一切的方式。

## 4. 请求的关卡：Filter 链

### Filter 是干嘛的

Filter = 请求的"关卡"——在请求到达 Servlet 之前、响应返回之后，拦截处理。典型用途：登录校验、日志、编码、指标采集（my-xhs 的 `ApiMetricsFilter` 就是这么干的：给每个请求记耗时指标）。

### 洋葱模型

多个 Filter 按注册顺序串成一条链，请求进出各过一遍：

```
请求 → FilterA.doFilter → FilterB.doFilter → Servlet → 响应反向返回
```

实验 `ServletSpecTest.filterChainFollowsRegistrationOrder` 验证了这个进出顺序（先进后出，洋葱一样）。

**一个容易踩的坑（实验实测）**：Servlet 3.0 起请求可以"异步"（下一节），但**异步请求经过的每个 Filter 都必须声明支持异步**（`asyncSupported`），漏一个就报 500 错误。

> 可跳过（排查用）：Filter 可以指定只在某些"分发类型"触发（DispatcherType：REQUEST/FORWARD/ERROR...）——`EnumSet.of(DispatcherType.REQUEST)` 只拦外部请求。

---

## 5. 长任务怎么办：异步释放线程

### 问题：请求线程被"占着干等"

同步模式：**一个请求占着一个容器线程，直到响应写完**。如果接口里有慢操作（查慢数据库、长轮询、等外部服务），这个线程就一直干等——Tomcat 的线程池就 200 个线程，全被干等占住，新的请求就排队。

### 异步：startAsync 释放线程

Servlet 3.0 的解法：请求线程说"我不等了"，把活儿交给业务线程池，自己立即回线程池接新请求：

```java
AsyncContext async = req.startAsync();   // 请求线程释放，回容器线程池
BIZ_POOL.submit(() -> {                   // 业务线程池干活
    // 长任务...
    resp.getWriter().write("done");
    async.complete();                     // 通知容器：响应写完了
});
```

实验 `ServletSpecTest.asyncReleasesContainerThread` 验证了这点：响应的内容里，处理请求的线程名（`http-nio-...`，容器线程）和干活的线程名（`pool-...`，业务线程）**不是同一个**——请求线程确实被释放了。配套的 `AsyncListener` 有四个回调（完成/超时/出错/再次异步）——超时处理就写在这里。

**核心认知**：异步是"释放容器线程"（吞吐提升），**不是"让单次请求更快"**。

> Spring 里对应的三形态（知道即可）：`Callable`（简单包装）/ `DeferredResult`（事件驱动）/ `CompletionStage`（链式）。my-xhs 的异步化还配套了 `MdcAwareExecutorService`（把 traceId 传给业务线程——否则日志链路断裂）。

---

## 6. Tomcat 的线程池：先扩线程再排队

JDK 的线程池（ThreadPoolExecutor）习惯是：核心线程 → 排队 → 满了再扩线程。**Tomcat 反着来：先扩线程，再排队**（Tomcat 源码 TaskQueue 实证）——避免任务在队列里干等。这解释了为什么 `server.tomcat.threads.max` 这个配置直接影响并发上限。

> 一条经验：调大 `threads.max` = 更多并发线程；`accept-count` = 排队的长度。限流也靠这里：限制线程池大小 + 连接数（`setMaxConnections`）双手段。

## 7. 性能升级三路径（HTTP 篇）

| 路径 | 解决什么 | 现代形态 |
|------|---------|---------|
| ① 异步（Servlet 3.0） | 线程干等 | `CompletableFuture`/`DeferredResult` |
| ② 非阻塞（Servlet 3.1） | IO 读写阻塞线程 | **Reactive 栈（WebFlux/Netty）** |
| ③ HTTP/2（Servlet 4.0） | 协议开销 | 多路复用（无需改代码） |

my-xhs 现状：HTTP/2 已启用（各服务 `application.yml` 的 `http2.enabled: true` 配置实证）；网关层已用 WebFlux（非阻塞）；业务层是阻塞 Tomcat 栈（混合架构，合理）——**最大差距是没有压测基线数据**（改完没对比，等于没改）。

---

## 本章小结：一次请求的旅程回顾

```
浏览器 → Tomcat（容器）
  → Filter 链（关卡：校验/日志/指标）
  → 按 URL 匹配找到 Servlet（DispatcherServlet → 你的 Controller）
  → 响应反向穿过 Filter 链返回
容器管理一切生命周期：Servlet 一个实例服务所有请求（字段要无状态）
长任务用异步释放线程；线程池先扩线程再排队；性能升级三路径（异步/非阻塞/HTTP2）
```

**my-xhs 落地点**：Filter 已用（3 个 OncePerRequestFilter：指标/网关信任/MCP 认证）/ 异步已用（17 个文件 + MDC 透传）/ HTTP2 已用 / 差距 = 压测基线 + 控制器层异步出口。
