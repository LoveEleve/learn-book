## 1. K8s 声明式模型：告诉系统"想要什么"，不是"做什么"

### 场景

传统部署：你写脚本"创建 3 个副本、等待、检查健康、失败重来"——**指令式**（每一步都你指挥）。K8s 反着来：你只写"我要 3 个副本"（**声明式**），系统自己持续保证"实际状态 = 期望状态"。

### 核心概念（stage-4-09 实证）

- **对象 = 目标性记录**：创建即告知期望状态，系统持续确保存在
- **spec + status**：`spec`（你设的期望）/`status`（系统更新的现状）——**控制回路持续收敛两者**（Deployment 3 副本案例）
- **必须字段**：`apiVersion`（API 版本）/`kind`（对象类别）/`metadata`（name/UID/namespace）
- **名称 vs ID**：名称（同类唯一）/UID（集群唯一）/标签注解（非唯一属性）
- **命名空间**：一个物理集群上的多个"虚拟集群"
- **三管理方式**：指令式命令 / 指令式对象配置 / **声明式对象配置**（kubectl 自动检测——目标是它）

**平台化注册中心（stage-4-09 核心命题）**：云原生时代注册发现"平台化"——K8s API Server/etcd/Istio xDS 承担注册发现，业务零自建（对比 Eureka/Nacos 的应用层自建——"注册中心的平台化演进"主线，多活章节详谈）。

**一句话**：**"不是编排是控制回路"**——期望状态声明 + 持续收敛（与 stage-3-22 的 Istio 控制回路同源）。

## 2. Spring 6 HTTP Interface：声明式 HTTP 客户端

### 场景

HTTP 客户端写了四代：RestTemplate（命令式）→ OpenFeign（声明式，但依赖第三方）→ WebClient（响应式）→ **HTTP Interface（Spring 6 官方声明式，2022）**。核心思路和 OpenFeign 一样：**接口 + 注解 = 客户端**：

```java
@HttpExchange("/api/users")              // 类级：公共前缀
public interface UserApi {
    @GetExchange("/{id}")
    String getUser(String id);           // 方法级：GET /api/users/{id}
}
```

运行时 `HttpServiceProxyFactory` 把接口变成代理（实验 `httpInterfaceIsDeclarativeClient` 验证注解契约 + 构建机制）。**意义**：接口既是客户端契约也是服务端契约（"契约共享"）；不用 Feign 也能享受声明式（Spring 原生）。

> 可跳过：`@HttpExchange(method="POST")` 等完整注解族 + 与 WebClient/Feign 的选型对照（stage-4-12 KP-05——多活章节详谈负载均衡化）。

## 3. Reactive Streams：响应式的"底层协议"

### 场景

Reactive（WebFlux/Reactor）号称解决高并发——它的底层规范是 **Reactive Streams**（2015，Netflix/Pivotal/Red Hat 共同制定），核心解决**背压**：慢的消费者不会被快的生产者淹没。

### 四接口（stage-3-17 KP-04——🔴 核心）

```java
Publisher<T>     // 数据源（发什么）
Subscriber<T>    // 消费者（收什么）
Subscription     // 纽带：request(n) 背压（消费者声明"我一次能要多少"）
Processor<T,R>   // 中间站（既是 Subscriber 又是 Publisher）
```

**JDK 9 起把这套规范收进了 JDK**——`java.util.concurrent.Flow`（`Flow.java:193/218/270/301` 实证——四接口一字不差）+ `SubmissionPublisher` 现成实现。实验 `flowApiIsJdkReactiveStreams` 验证了背压：发布 10 个元素，订阅者 `request(3)` 后只收到 3 个就 cancel——**消费速率 = 请求数量**。

**Reactor（Mono/Flux）就是在这套规范上加糖**——学 Reactive 之前先懂四接口 + 背压，后面全是语法糖。

## 4. Instrument：Java 的"字节码手术"规范

### 场景

链路追踪从"应用层埋点"升级成"字节码层自动埋点"——不改业务代码，靠 **Instrument（java.lang.instrument）** 在类加载时改写字节码（stage-1-18 核心命题）。

**三件套**：
- **premain**：启动时 `-javaagent:xxx.jar`——JVM 启动前挂 agent（改类加载前的字节码）
- **agentmain**：运行时挂载（`VirtualMachine.loadAgent`——attach 机制，第一章 JMX/Attach 讲过）
- **ClassFileTransformer**：真正的"手术刀"——`transform()` 回调里改字节码

**埋点演进链（stage-1-18 核心命题）**：链路追踪的埋点方式三代演进——①应用层手写埋点（侵入）→ ②**JDK 动态代理**（接口代理，侵入小）→ ③**字节码增强**（CGLIB/ASM/Byte Buddy——不改代码改类）→ ④**Agent 层**（Instrument 挂载——零侵入，SkyWalking 方案）。**动态代理 vs 字节码增强**的边界：代理只能拦接口/方法，字节码能改任意类——这是所有"增强框架"（MyBatis 插件/CGLIB 代理）的分水岭。

**使用认知**：业务代码几乎不写 Instrument——**但 SkyWalking/Arthas 的底层全是它**（stage-1-18 用 SkyWalking 重构实证）。知道"字节码增强从哪来"即可。

> 可跳过：**RSocket**（stage-3-17 提及）——响应式的"传输协议"（背压语义贯穿到网络层，对比 HTTP 请求-响应模型）——分布式事件/长连接场景，训练营未深入，[缺口：外部补源]。

## 5. gRPC/Triple：RPC 协议的现代底座（stage-3-10 交叉）

三个设计事实（stage-3-10 实证）：

1. **HTTP/2 是 RPC 的共同底座**：gRPC/Triple 都选 HTTP/2（多路复用/流控）——和 Servlet 4.0 的 HTTP/2 升级是**同一底层演进**（1.2 章节衔接）
2. **开放协议 vs 私有协议**：私有协议（性能）vs 开放协议（互通）——云原生时代天平倒向开放（Triple/gRPC 都基于 HTTP/2 + Protobuf 生态）
3. **治理元数据进协议头**：version/group/traceId 放 header——网关/路由/追踪基础设施直接识别（对比 Dubbo2 的 Body/Attachments 冗余）——"治理数据协议化"的设计趋势
4. **穿透性**：Triple 的 metadata/payload 分离让网关/Service Mesh **不参与业务解析**也能转发（性能与治理的分层——对比 Dubbo2 网关要解析 Body）

> 可跳过：`@HttpExchange` 与 gRPC 的选型（REST 语义 vs 强类型 RPC）；stage-3-10 的协议设计取舍四性。

## 6. HTTP 协议族：性能演进（§9.4 决策落地）

| 版本 | 核心改进 | 状态 |
|------|---------|------|
| HTTP/1.1 | 持久连接/管道 | 存量主流 |
| HTTP/2 | 多路复用/头部压缩/二进制帧 | **现代默认**（Servlet 4.0+，1.2 章节衔接） |
| HTTP/3 | QUIC（UDP 底座）/0-RTT/队头阻塞根治 | 演进中 |

使用认知：HTTP/2 需要 **ALPN 协商 + TLS**（`http2.enabled=true` 没配 `server.ssl` 就不生效——my-xhs 差距项 P2-2）；HTTP/3 走 UDP（QUIC），当前主要内网/边缘场景。协议面选择影响网关和 RPC（gRPC 直接要求 HTTP/2）。

## 7. Web Service（SOAP）：过气的第一代标准（stage-4-01 交叉）

SOA 时代的 Web Service 三要素（stage-4-01 KP-03）：**XML Schema**（数据模型）/ **UDDI**（服务发现）/ **SOAP**（通讯协议，走 HTTP/Email）。**过时**——被 REST（JAX-RS）与 gRPC 取代，但"服务总线 = 注册中心+路由+调用+发现"的 SOA 思想留下来了（看微服务架构全是它的影子）。

> 可跳过：OpenAPI/Swagger（REST API 契约——`@OpenAPIDefinition` 文档生成，REST 工程标配）——训练营未涉及，标注 [缺口：外部补源]；JAX-RS（Spring MVC 的规范对标物——@Path 对应 @RequestMapping，知道存在即可）。

## 本章小结

**知识本体**：云原生与协议规范聚合——K8s 声明式（spec/status/控制回路）、HTTP Interface（声明式客户端）、Reactive Streams 四接口 + 背压（JDK Flow API 已吸收）、Instrument（premain/agentmain/Transformer）、gRPC/Triple（HTTP/2 底座 + 治理元数据协议化）、Web Service（过时）。

**my-xhs 判定**：HTTP/2 已用（协议面）/ WebClient+WebFlux 已用（Reactive 面）/ HTTP Interface 该用没用（Spring 6 官方声明式——网关/微服务间调用值得评估）/ **K8s 部分已用（部署模板实证——2026-08-15 核实：`k8s/` 8 个模板文件 configmap/deployment/hpa/ingress/namespace/service——声明式部署就绪，未上真集群为演进项）**/ gRPC 该用没用（评估中——stage-3-10 差距项）/ Instrument 不该用（SkyWalking 覆盖——机制必须懂）。
