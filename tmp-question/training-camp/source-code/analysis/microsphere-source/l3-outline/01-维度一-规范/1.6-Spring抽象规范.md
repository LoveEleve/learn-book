# 06. Spring 抽象规范：框架的"契约"长什么样

> 配套实验：`sca-lab/custom-java-infra/spec-spring`（**模块共 7 个断言**——SpringSpecTest 4（本文）+ SpringExtensionTest 3（4.5 章节），spring-context 实测）
> 定位：**契约面**——Spring 的抽象规范（注解组合/条件装配/生命周期/生态适配）怎么用、坑在哪；"扩展点怎么实现"在工程问题卷 4.5 章节（一体两面：这里讲契约，那里讲扩展）
> 课程交叉：stage-1-23/24（脚手架里的自动装配/条件注解元模型）、stage-4-08（Spring 生命周期）

Spring 不只是一个框架，是一套**契约**——"Bean 的生命周期由谁管"、"注解怎么组合"、"装配怎么开关"，全有规范。你用 Spring 写了三年代码，但很少意识到自己一直在遵守这些契约。这一章把四个最重要的契约讲明白：**注解组合（@AliasFor）、条件装配（@ConditionalOnXxx）、生命周期时序、生态适配纪律**。

---

## 1. 注解组合：@AliasFor（怎么造"增强版"注解）

### 场景

你不想让调用方写 Spring 官方的 `@EnableCaching`，你想造自己的 `@EnableFeature`——**把官方注解的属性"透传"（属性透传）出来，换自己的名字**。@AliasFor 就是干这个的（`AliasFor.java:181` 实证）：

```java
@Retention(RetentionPolicy.RUNTIME)
public @interface EnableFeature {
    @AliasFor(attribute = "scanPackage")   // 别名：value 和 scanPackage 是同一个东西
    String value() default "";

    String scanPackage() default "";
}
```

**契约语义**：解析时 `value` 和 `scanPackage` 合并成一个值——调用方写哪个都行，Spring 保证两者一致（实验 `aliasForMergesAttributes` 断言：写 `value`，解析后 `scanPackage` 也是它）。

两种用法：
- **注解内别名**（上面——同一个注解的两个属性互指）
- **跨注解组合**：`@AliasFor(annotation = Xxx.class)`——自己的注解组合官方注解并透传属性（microsphere 的 `@EnableTTLCaching` 就是这么做的：把官方注解的属性全透传出来，KP-217）

> 可跳过（进阶级）：microsphere 有个更激进的方案 `@OverrideAnnotationAttributes`——**策略化覆盖**（strategy SPI 可插拔，:89）vs 官方固定合并。官方够用，自造版本是为了教学。

**使用判断**：my-xhs 0 处 @AliasFor（官方注解够用）——但**读框架源码时这是必懂语法**（Spring 内部到处是它）。

## 2. 条件装配：@ConditionalOnXxx 家族（装配的"开关"）

### 场景

同一个 jar，装上 Redis 才装配 Redis 相关 Bean、有 Web 环境才装配 Web 相关 Bean——**装配按"条件"开关**。这是 Boot 自动配置的核心契约（my-xhs 42 个文件在用——@ConditionalOnProperty 20/@ConditionalOnClass 15/@ConditionalOnWebApplication 12/@ConditionalOnBean 8/@ConditionalOnMissingBean 3 的真实画像）。

### 三个机制（契约的核心）

1. **类名探测**：`@ConditionalOnClass("com.mysql.cj.jdbc.Driver")`——按**类名**判断，不需要编译期依赖（可选依赖不引入就跳过——microsphere 的 @ConditionalOnWebFluxAvailable 就是这个思路）
2. **属性匹配**：`@ConditionalOnProperty(prefix="app", name="enabled", havingValue="true")`——配置开关
3. **matchIfMissing**：条件不满足时是"通过"还是"拒绝"——默认拒绝（保守），`matchIfMissing=true` 表示"没配置就当开启"（这是隐式默认值的来源）

### 自造一个条件注解（三件套）

```java
@Conditional(OnPropertyPresentCondition.class)   // ① 注解挂 Condition
public @interface ConditionalOnPropertyPresent {
    String name();
}

class OnPropertyPresentCondition implements Condition {   // ② Condition 实现
    public boolean matches(ConditionContext ctx, AnnotatedTypeMetadata meta) {
        // ③ 评估：环境里属性存在即匹配
        String value = ctx.getEnvironment().getProperty((String) meta.getAnnotationAttributes(
                ConditionalOnPropertyPresent.class.getName()).get("name"));
        return value != null && !value.isEmpty();
    }
}
```

实验 `customConditionalEvaluates` 断言：属性存在 → Bean 注册；属性缺失 → 不注册。**这是 microsphere `@ConditionalOnPropertyPrefix`（前缀匹配——官方是精确名匹配，差异在"前缀 vs 精确名"，KP-301）和 sentinel 四重条件（框架可用 + 开关 + 类存在 + Web 栈，KP-1303）的底层机制**——全仓库的条件注解都是这三件套。

> 可跳过（进阶级）：
- **@ConditionalOnBean vs @ConditionalOnMissingBean 互补**：一个是"有才装配"、一个是"没有才装配"（my-xhs 画像 8/3 实证）——`@ConditionalOnMissingBean` 是"给用户覆盖机会"的标准写法（用户自己定义 → 框架的自动配置让位）
- **havingValue 语义**：`@ConditionalOnProperty(havingValue="true")` 是精确值匹配；`matchIfMissing=true` 表示"没配置就算通过"（隐式默认值）
- **@Profile vs @ConditionalOnProperty**：Profile 是"环境选择"（dev/prod 整体切换），@ConditionalOnProperty 是"特性开关"（细粒度）——别混用
- **自动配置排序**：`@AutoConfigureAfter/@AutoConfigureBefore` 定义自动配置的执行顺序（14 仓四重条件的配套——依赖方排后面）
- **条件评估报告**：启动参数 `-Ddebug`（或 debug 日志）可打印 `ConditionEvaluationReport`——"哪个条件为什么没通过"的诊断利器（04 仓启动诊断）
- **陷阱**（11 仓库实证）：`@ConditionalOnBean(name=...)` 的 name 是 Bean 名、value 是类——**语义不同，别混**；`@EventListener` 在自动配置早期注册可能永不触发（时序问题——可观测章节的静默失效家族）。

## 3. BeanFactory 生命周期契约（一句话版）

Bean 的一生由容器管：`BeanFactory` 注册定义 → 实例化 → 属性填充 → 初始化回调 → 就绪 → 销毁。这套时序是**契约**（`AbstractApplicationContext.refresh()` 的 12 步），Spring 的一切扩展点（BeanPostProcessor/InitializingBean/ApplicationListener）都挂在这条时序上。

**本章只立契约**：扩展点怎么挂、每个钩子什么时候被调——工程问题卷 4.5 章节（microsphere-spring 的注入点/事件拦截/Environment 双钩）就是在这条时序上做文章的。

## 4. 生态适配纪律 + JSR-330 对照

### 生态适配纪律（microsphere 的最佳实践）

microsphere 进 Spring 生态时有一条纪律：**"进 Spring 用 Spring 的"**——SPI 用 `SpringFactoriesLoader`（spring.factories，不用 JDK ServiceLoader）、排序用 `Ordered`（不用自家 Prioritized）、注解组合用 `@AliasFor`（不用自造）——**同一作者在两个生态做同一件事，选对生态的标准件**（03 仓一章 KP-202/206/217 实证）。

### JSR-330 对照（§9.4 决策的落地）

Spring 的 `@Autowired` 对标规范 `jakarta.inject` 的 `@Inject`（JSR-330）——Spring 6 原生支持：

| | Spring 专有 | JSR-330 规范 |
|---|---|---|
| 注入 | `@Autowired` | `@Inject` |
| 限定 | `@Qualifier` | `@Named` |

实验 `jakartaInjectIsSupported` 断言：`@Inject @Named` 与 `@Autowired` 在 Spring 里都可用。**教学意义**：`@Inject` 是"可移植标准"（换容器不用改代码），`@Autowired` 是 Spring 增强（required=false 等）——**写框架/库用规范，写应用随框架**。my-xhs 全 `@Autowired`（0 处 jakarta.inject——Spring 专有够用，判定正确）。

## 本章小结

**知识本体**：Spring 抽象规范 = 四个契约——注解组合（@AliasFor：注解内别名/跨注解透传）、条件装配（@ConditionalOnXxx：类名探测 + 属性匹配 + matchIfMissing + Condition 三件套）、生命周期时序（refresh 12 步——扩展点挂载时序）、生态适配（进 Spring 用 Spring 的标准件 + JSR-330 @Inject/@Autowired 对照）。

**my-xhs 判定**：条件注解**已用**（42 文件画像实证）；@AliasFor **该用没用**（参考级——造自定义 EnableXxx 时值得用）；jakarta.inject **不该用**（@Autowired 够用——写应用随框架）。

**与 4.5 的分工**：契约在这里（怎么用/语义/坑），扩展点实现（注入点解析/事件拦截/BeanFactory 三时点）在工程问题卷 4.5。
