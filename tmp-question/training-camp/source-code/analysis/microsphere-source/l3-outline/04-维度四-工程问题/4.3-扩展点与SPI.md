# 24. 扩展点与 SPI：让框架"不认识实现也能扩展"

> 配套实验：`spec-spi`（3 个断言——选优/懒缓存/门控）+ `spec-jdk`（SPI 加载——1.1 章节）
> 定位：**SPI 注册中心模式家族（1）主落位**（10/14 仓库——生态核心 DNA）——四件套（加载/排序/缓存/兜底）完整教学
> 来源：源码 02 一章（SPI+Prioritized 选优）+ 03 一章（生态选择）+ 07 二章（4 SPI 管道——最完整）+ 06（双通道）+ 14（插件 SPI）+ stage-2-21/stage-3-23（RPC 微内核/Dubbo）
> 前置：1.1 章节（SPI 规范本体——ServiceLoader 机制）

1.1 讲了 JDK 的 SPI 机制（ServiceLoader）。这一章讲**工程化的 SPI**：怎么把"加载"升级成"注册中心"（选优/缓存/门控）——microsphere 生态 10/14 个仓库用同一套模式（**生态核心 DNA**）。学完这套四件套，microsphere 的"魔法"就没了魔法。

---

## 1. 四件套：加载/排序/缓存/兜底（核心命题）

SPI 从"能加载"到"能选优"的四件套（02 仓"SPI + Prioritized 选优"三处实证：convert/io/metadata 同构）：

```
① 加载（loadServicesList——SPI 发现全部实现）
② 排序（Prioritized/COMPARATOR——按优先级）
③ 缓存（懒加载 + 字段缓存——首次加载后续复用）
④ 兜底（supports 门控——无匹配跳过；空列表处理）
```

实验 `prioritizedSelection`/`lazyCaching`/`supportsGating` 分别验证了①②③④。

**与 1.1 的对照**：confucius 版"无缓存每次重载" → microsphere 版加缓存层（`servicesCache` + `microsphere.service-loader.cached` 系统属性开关——02 1.1）——**同一主题两代实现的演进实证**（1.1 章节的 confucius ServiceLoaderUtils → 本仓库的完整注册中心）。

> 可跳过（进阶级）：**双键缓存 + 懒过滤**（02 1.3——Converters 专用——`Entry<Class,Class>` 双键缓存 + 未命中时按 `accept` 懒过滤再缓存——"启动分组 + 懒补充"双层策略）——**任何"类型对→处理器"映射场景的通用模式**（my-xhs 的自定义协议转换/扩展层可参考——2.1 章节的 my-xhs SPI 化适配器该用没用项）。

## 2. 生态选择：进 Spring 用 Spring 的（03 一章）

| 生态 | 用哪个 SPI | 排序 | 理由 |
|------|-----------|------|------|
| 纯 JDK（microsphere-java） | `ServiceLoader` | `Prioritized`（自研） | 无框架依赖 |
| Spring 生态（microsphere-spring） | `SpringFactoriesLoader` | `Ordered`（官方） | **进 Spring 用 Spring 的** |

**生态适配纪律**：同一作者在两个生态做同一件事，选对生态的标准件（03 一章 KP-202/206）——"不该用自家 JDK 版在 Spring 里造轮子"（4.3 的核心纪律）。

## 3. 4 SPI × 6 模块管道（07 二章——最完整案例）

### 五步管道

每个数据库单元经 5 步处理（07 二章——"模块化装配"的完整形态）：

```
注解处理器 → PostProcessor → Validator → dynamic 分支 → Synthesizer（属性源）→ Registrar（注册）
```

### 模块化：新模块 = 接口 + spring.factories

6 个模块（datasource/transaction/sharding-sphere/mybatis/mybatis-plus/ha）**按需实现**——四族 SPI（PostProcessor/Validator/Synthesizer/Registrar——**四 Aware 统一基座同构**）+ **懒加载**（loadFactories 四族 + 字段缓存 :218-246——四件套的③）+ **supports 门控**（无配置即跳过——四件套的④）。

> 可跳过（进阶级）：**泛型反射取配置类型**（07 2.1 的 `ConfigurationCapable`——`resolveActualTypeArgumentClass`）——**1.1 章节 APT 陷阱的运行时版本**（编译期用 TypeMirror、运行时用泛型反射取类型实参——同一问题的两域解法）。

### 缺陷（R2——缺陷家族成员）

**dynamic 分支原地清空 config 字段**（:112-119——破坏性副作用——重建时从环境重读有补救）——"看起来在做分支，实际改了共享状态"——**管道处理里的副作用要警惕**（与 2.8 的 R1 忙等/3.1 的语义缺陷同族）。

## 4. 双通道装配 + 插件 SPI（06 + 14）

**双通道装配**（06 ZoneAutoConfiguration）：`loadFactories`（SPI 通道）+ **Bean 收集**（容器通道）——两条路都能进 ZoneLocator（"既有 SPI 自动发现，又能被用户 Bean 覆盖"）。

**插件 + 扩展点双实现**（14 一章——Sentinel 适配器）：每个适配器 `extends AbstractSentinelPlugin implements {框架扩展点}`——**"统一插件接口 + 各框架扩展点"的桥接**（12/13/10/11 的扩展点 = 14 的挂载点——跨仓库组合实证——2.4 章节已述）。

## 5. RPC 微内核与 Dubbo（stage-2-21/3-23——课程侧）

**RPC 微内核**（stage-2-21）：RPC 框架的"内核 + 插件"架构（网络/IO/序列化/协议可替换——微内核 = SPI 的架构级应用——2.1 章节的 xDS 也在 RPC 面）。

**Dubbo 架构**（stage-3-23）：**分层架构**（接口/配置/集群/注册中心/协议/序列化层）+ **三大中心**（注册/配置/元数据中心——2.1 交叉）+ **SPI 扩展与内建实现**（KP-06——Dubbo 的 ExtensionLoader 是 SPI 注册中心的工业级实例——自定义 Filter/Router 就是加一个 SPI 文件）。

> 可跳过（进阶级）：**Dubbo 2.x → 3.x 演进**（stage-3-23 KP-05——2.x 不足 → 3.x 的 IoC 演进 + **Triple 协议**（1.7 章节）+ **Proxyless Mesh**（3.1 章节 xDS 面））；RPC 序列化映射（stage-2-21——Hessian [过时→Protobuf/Kryo]——2.5 章节的 stage-2 梳理映射表）。

## 本章小结

**知识本体**：SPI 四件套（**加载/排序/缓存/兜底**——实验）+ 生态选择纪律（进 Spring 用 Spring 的）+ **4 SPI × 6 模块管道**（五步管道 + 模块化 + supports 门控 + R2 副作用缺陷）+ 双通道装配 + 插件/扩展点双实现 + RPC 微内核/Dubbo ExtensionLoader。
