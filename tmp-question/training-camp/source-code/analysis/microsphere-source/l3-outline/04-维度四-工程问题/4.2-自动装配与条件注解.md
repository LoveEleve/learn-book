# 23. 自动装配与条件注解：装配的"开关与流水线"

> 配套实验：`spec-autoconfig`（3 个断言——三阶段 + 三源去重）+ `spec-spring`（自定义 @Conditional——1.6 章节）
> 定位：**条件注解模式家族（3）主落位**——条件注解家族 + AutoConfiguration 三阶段 + 三源装配；契约面在 1.6 章节（本章讲实现与坑）
> 来源：源码 04（前缀条件）+ 14（四重条件）+ 07（三阶段/三件套）+ 13（三源装配）+ 10/12（@Enable 族）
> 前置：1.6 章节（@ConditionalOnXxx 契约）

Spring Boot 的"魔法"：**jar 一放，Bean 自动就位**。底层是两件事：**条件注解**（开关——"这个 Bean 该不该装配"）+ **自动配置流水线**（三阶段——"装配什么、按什么顺序"）。这一章把这两件事讲透——条件注解家族、四重条件组合、三阶段流水线、三源装配（含一个真实缺陷）。

## 1. 条件注解家族（my-xhs 42 文件实证画像）

my-xhs 的真实使用分布（42 文件）：

| 注解 | 次数 | 语义 |
|------|:--:|------|
| `@ConditionalOnProperty` | 20 | 配置开关（1.6 契约） |
| `@ConditionalOnClass` | 15 | 类存在探测（可选依赖） |
| `@ConditionalOnWebApplication` | 12 | Web 栈探测 |
| `@ConditionalOnBean`/`@ConditionalOnMissingBean` | 8/3 | Bean 存在性（互补） |

**microsphere 的补全**（04 一章）：官方没有的**前缀条件**（`@ConditionalOnPropertyPrefix`——按前缀 startsWith 匹配——vs 官方精确名匹配——差异在"前缀 vs 精确名"）+ Web 栈条件（WebFlux/WebMVC 探测——1.6 已述）。

**四重条件组合**（14 2.2——跨仓库条件消费）：框架可用 + 类存在 + 开关 + Web 栈——**条件可以叠加成"装配的完整前置"**（Sentinel 适配器只在"Sentinel 在 + 框架在 + 开关开 + 环境对"时才装配）。

> **陷阱引用**（1.6 已详述）：`@ConditionalOnBean(name=...)` 的 name 是 Bean 名、value 是类——混用静默不匹配（11 的 P2——静默失效家族）。

> 可跳过（进阶级）：**自动配置排序**（`@AutoConfigureAfter/@AutoConfigureBefore`——14 2.2 的四重条件配套——依赖方排后面）+ **条件评估报告**（04 2.3——`-Ddebug` 打印"哪个条件为什么没通过"——启动诊断——1.6 已述）。

## 2. AutoConfiguration 三阶段（07 7.4——流水线）

自动配置不是"直接注册"——是**三阶段流水线**（实验 `threeStagesParseFilterImport` 验证）：

```
① 解析（parse）：读取候选配置类（**spring.factories（Boot 2）→ AutoConfiguration.imports（Boot 3——1.1 章节）的类名列表**——解析来源的演进）
② 过滤（filter）：排除列表（exclude）+ 条件评估（@ConditionalOnXxx——不满足的剔除）
③ 导入（import）：去重后注册 Bean 定义
```

**对应 Spring 的三个扩展点**（07 3.3——Import 三件套）：`AutoConfigurationImportSelector`（解析+选择）/`AutoConfigurationImportFilter`（过滤）/`AutoConfigurationImportListener`（监听——生命周期钩子）——**"三阶段 × 三扩展点"是自动配置的完整控制面**。

> 可跳过（进阶级）：ClassLoader 作用域缓存（07 3.3——按 ClassLoader 缓存自动配置结果——性能）+ 按前缀取类名（模块级隔离——父上下文排除来源）+ DisposableBean 清理。

## 3. 三源装配 + P2 缺陷（13 二章——真实教训）

### 三源装配

`@EnableAlibabaDruid` 的装配来源**三个**（三源扫描——实验 `threeSourceAssemblyDeduplicates` 验证合并去重）：

```
① BeanFactory（自身注册的 Filter Bean）
② SpringFactories（spring.factories 声明的）
③ JavaServiceProvider（JDK SPI——02 仓库的 SPI 体系应用）
```

### P2 缺陷（switch fallthrough——缺陷家族成员）

**源码实证**：三个 case 全无 break（:69-78）→ 默认 sources 下 **BPP 注册两次**——**下游同名去重（allowBeanDefinitionOverriding=false 跳过 + warn）才无害**——git 81b8043b 引入未修复——测试未断言注册次数未捕获。

**三个教训**（直接适用 my-xhs）：
1. **switch 必加 break**（fallthrough 是 C 系最经典的坑）
2. **"下游幂等掩盖缺陷"模式**——缺陷依赖下游容错才无害（这里靠 BeanDefinitionOverriding 去重兜底）——**上游 bug 被下游容错掩盖 = 隐患**（跨仓库同族缺陷）
3. **测试要断言副作用次数**（"注册了几次"——不只看"有没有"）

## 4. @Enable 族（10 四章 + 12 2.1）

**@Enable 对称三件**（10 的 `@EnableRedisConfiguration/Context/Interceptor`——对称命名 + 条件族 + registrar 三件）：**@EnableXxx = 装配的入口注解**（用户侧）+ 内部条件装配（框架侧）。12 的**双 Enable**（两个入口注解共存——`@EnableExecutorFilter` 族）。

**my-xhs 实证**：`RedisInterceptorAutoConfiguration`（对应物——@Enable 族在现代 Spring 的等价形态）。

> 可跳过（进阶级）：**动态连接**（10 四章的 `DynamicRedisConnectionFactory`——配置变更时连接工厂动态重建——热更新面与 2.2 联动）；07 7.4 的**配置系统全链路**（JSON → POJO → PostProcessor 链 → Synthesizer 链 → Environment——四 SPI 管道——4.3 章节详述）。
