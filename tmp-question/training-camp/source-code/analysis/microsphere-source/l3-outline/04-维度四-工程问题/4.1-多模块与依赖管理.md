# 22. 多模块与依赖管理：工程的地基

> 配套实证：`custom-java-infra` 自身（19 模块——本文结论的活例子）+ my-xhs（22 模块 + BOM）
> 定位：**工程构建面**——Maven 的继承/聚合/BOM/作用域 + 业务工程模板（bom 仓已移出决策——handover——轻量讲）
> 课程来源：stage-1-01（8 KP）+ stage-1-02（8 KP）
> 前置：写过 Maven 项目

多模块工程的三个基础问题：**父 POM 怎么管子模块**（继承 vs 聚合）、**版本怎么统一**（BOM）、**依赖怎么隔离**（作用域/仲裁）。这一章把工程地基讲透——你在看的所有仓库（microsphere 14 仓、my-xhs 22 模块）都踩在这上面。

---

## 0. Maven 是什么（stage-1-01 KP-01——一句话）

**生命周期 + 约定优于配置**：`validate → compile → test → package → install → deploy` 六阶段（每个阶段自动依赖前序）+ "约定优于配置"（src/main/java 等标准目录——不用配置就按约定找）。**理解生命周期 = 理解 `mvn install` 为什么先编译再测试再打包**（本仓库的 19 模块聚合构建就是生命周期 + 模块依赖的执行序）。

---

## 1. Maven 双胞胎：继承 vs 聚合（stage-1-01 KP-02~04）

| | 继承（parent） | 聚合（modules） |
|---|---|---|
| 关系 | 子 POM 认父 POM（`<parent>`） | 父 POM 列子模块（`<modules>`） |
| 作用 | 继承配置（版本/插件/属性） | 一键构建（`mvn install` 全家桶） |
| 方向 | 配置下传 | 构建上收 |

**通常合体**：一个父 POM 既是 parent（继承）又是聚合根（modules）——**microsphere 14 仓、my-xhs 22 模块、custom-java-infra 19 模块都是这个模式**（实证：本仓库根 pom 的 `<modules>` 列表就是聚合）——**一句话记忆："继承管配置，聚合管构建"**。

---

## 2. 依赖管理：BOM（统一版本的核心——stage-1-01 KP-06/07）

**问题**：20 个模块各自写 `spring-boot:3.3.5`——升级版本要改 20 处。

**BOM 解法**（`dependencyManagement`）：父 POM 集中声明版本，子模块**只写坐标不写版本**：

```xml
<!-- 父 POM：版本集中管理 -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot</artifactId>
      <version>3.3.5</version>   <!-- 只在这里改 -->
    </dependency>
  </dependencies>
</dependencyManagement>
```

**my-xhs 实证**：`my-xhs-bom` 模块（dependencyManagement + `${project.version}` 内部版本统一——22 模块引用）——**BOM 是微服务工程的版本治理标准**（Spring 自己的 `spring-boot-dependencies` 也是 BOM——生态对照）。

**依赖仲裁**（KP-06）：传递依赖冲突时 Maven 的规则（就近原则 + 先声明优先）——**BOM 的出现让仲裁不再靠运气**（版本显式声明）。

> 可跳过（进阶级）：**传递依赖排除**（`<exclusions>`）——A 依赖 B，B 传递依赖了 C 但你不想用 C（版本冲突/多余）——排除后显式声明自己的 C 版本——**依赖治理的最后手段**（能用 BOM 管住的不用 exclusions）。

## 3. 依赖作用域（stage-1-01 KP-08）

| 作用域 | 什么时候在 | 典型 |
|--------|-----------|------|
| compile | 编译+运行 | 业务依赖 |
| provided | 编译（运行由容器给） | Servlet API（Tomcat 提供） |
| runtime | 运行（编译不需要） | JDBC 驱动 |
| test | 测试 | JUnit（本仓库 19 个模块的 junit 都是 test） |

**作用域是"依赖不泄漏"的手段**：`provided` 防容器依赖重复、`test` 防测试依赖进生产——**写依赖前先想作用域**。

---

## 4. Build Profiles（stage-1-01 KP-05）

**按环境切换构建**（dev/prod 配置差异）：

```xml
<profiles>
  <profile>
    <id>prod</id>
    <properties><env>prod</env></properties>
  </profile>
</profiles>
```

`mvn package -P prod`——**构建期环境隔离**（运行期环境隔离是 2.2 配置章节的事——两回事）。

---

## 5. 业务工程模板（stage-1-02）

**模块化设计**（KP-01/02）：Spring 模块化（按能力分模块——web/service/mapper）→ 业务工程按领域分模块（my-xhs：user/content/order/product/cart...——22 模块实证）——**标准化项目结构**（KP-03——统一包名/分层约定）。

**兼容性矩阵**（KP-06——关键）：Spring Cloud / Spring Boot / Spring Cloud Alibaba 的版本搭配是**锁定的**（2025.0.2 ↔ 3.3.x ↔ 2025.0.0.0——sca-lab 根 pom 实证）——**版本矩阵不匹配 = 起不来的项目**（最常见的工程事故）。

**插件排除间接依赖**（KP-07）：Spring Boot 插件的可执行 jar 打包——排除重复/冲突的间接依赖（构建期治理）。

**工程模板与脚手架**（stage-1-02 KP-08 + stage-1 梳理的 scaffold-lab）：标准化工程模板 = 一次性生成（包名/分层/依赖基线全套）——Spring Initializr 是官方生成器，scaffold-lab 是训练营的定制化模板实践（"生成出来的工程直接能跑"——工程化效率的来源）。
