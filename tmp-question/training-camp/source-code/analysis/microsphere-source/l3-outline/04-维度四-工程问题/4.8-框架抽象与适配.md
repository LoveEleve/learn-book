# 29. 框架抽象与适配：不写两遍代码的艺术

> 配套实验：`spec-bridge`（8 个断言——双栈/桥接/签名解析/特性开关）
> 定位：**模式家族 7（框架抽象+桥接）主落位**——"自研抽象 + 框架适配器"的完整方法论；课程主属 stage-2-22（RPC 生态整合——ServiceRegistry 接口抽象）
> 来源：源码 09 四章（双栈）+ 11 二章（Filter 抽象/Log4j2 桥接）+ 12 1.2（Interceptor 桥接）+ 08 二/三章（自研 vs SDK 选型）+ 04 四章（Boot3 兼容层/Actuator 化）+ 05 1.2/五章（响应式桥/特性开关/子上下文规格）+ 课程 stage-2-22（服务注册接口抽象）
> 前置：4.6 章节（桥接家族在 12 的实例）、4.3（SPI——框架无关的加载机制）、4.5（Spring 扩展点）

你在做微服务框架，想让自己的能力**既能在 WebFlux 上用、也能在 WebMVC 上用**——两套 API、两套模型。最笨的做法是写两遍；框架的做法是：**写一遍抽象，写两个适配器**。

这一章讲"框架抽象与适配"的完整方法论：双栈实现、Filter 桥接、拦截器签名解析、自研 vs 官方 SDK 的选型框架、版本兼容层、特性开关——每个都是"不写两遍代码"的具体手法。

## 1. 双栈实现：同一能力，两套框架（09 四章）

### 场景

微球网关要在 **WebFlux（响应式）和 WebMVC（传统 Servlet）** 双栈下提供"端点映射路由"能力。两栈的 API 完全不同：WebFlux 是 `GlobalFilter`（响应式流），WebMVC 是 `HandlerFilterFunction`（函数式端点）。

**答案不是写两遍**——是**同一能力接口 + 两个栈各自适配**：

```
同一能力（端点映射路由）
  ├── WebFlux 适配：实现 GlobalFilter（响应式管道拦截）
  └── WebMVC 适配：实现 HandlerFilterFunction（函数式端点过滤）
      （官方 SCG Server MVC SPI——WebEndpointMappingHandlerFilterFunction:83 实证）
```

微球的做法（09 4.1）：**webflux `GlobalFilter` vs webmvc `HandlerSupplier/HandlerFilterFunction`**——同一个路由过滤语义，在双栈各实现一次适配器，能力本体只写一遍。WebMVC 侧还要把 `excludes`（排除路径）翻译成 `RequestMappingInfo` 集合（:178——MVC 端点匹配模型——**"配置模型 → 栈本地模型"的翻译层**）。

**对照**：为什么双栈适配有价值？**用户的技术栈定了，你的能力要跟着适配**——适配器隔离"能力"与"框架"，换框架不动能力。my-xhs **不该用**（官方 SCG 是 WebFlux 单栈，无需双栈——没有这个需求就不制造这个抽象）。

实验 `sameCapability_dualStackImplementations` 验证：同一端点处理能力在两个"栈"实现下行为一致；`webfluxFilter_vs_webmvcInterceptor_sameSemantics` 验证双栈拦截语义等价。

**同族：响应式 ↔ 阻塞桥**（05 1.2——模式家族 7 实例）——`ReactiveDiscoveryClientAdapter` 把响应式的 Flux 服务发现结果**转成阻塞 List**（Flux → toList :88-89——响应式注册中心被 MVC 消费）：**跨"栈"适配的另一形态**——不是双实现，而是"数据流模型转换"（响应式拉取、阻塞消费）。my-xhs **该用没用**（暂无响应式↔阻塞混合场景——全阻塞栈）。

## 2. 框架无关抽象 + Filter 桥接（11 二章）

### 场景

你想让日志过滤能力**不依赖具体日志框架**——今天用 Log4j2、明天可能换 logback、后天可能 JDK 自带。怎么办？写一个**框架无关的 Filter 抽象**，再给每个目标框架写**桥接适配器**：

```
框架无关 Filter 族（Filter/AbstractFilter/CompositeFilter/LoggingNameFilter）
  └── Log4j2FilterAdapter（微球 Filter → Log4j2 Filter 的桥）
```

**这就是适配器模式（Adapter）**：把自家接口翻译成目标框架的接口。`CompositeFilter` 组合过滤（AND 语义——实验 `compositeFilter_shortCircuitsOnFirstReject` 验证短路），`Log4j2FilterAdapter` 委托转发（实验 `frameworkAgnosticFilter_bridgedToLog4j2` 验证桥接后语义不变）。

**要点**：框架无关层**只定义语义**（过滤什么），桥接层**只做翻译**（怎么融入目标框架）——职责分离，换框架只换桥。

**my-xhs 判定**：**不该用**——my-xhs 日志是 logback 直用（`logback filter` 原生覆盖——logback 自己的 Filter 体系就够用，不需要自造抽象）。**但"框架无关抽象 + 桥"是库作者的核心技能**：写通用库/中间件时，抽象层不绑框架、桥接层可插拔——4.3 的 SPI 就是"桥"的加载机制。

## 3. 服务注册接口抽象：可替换底层的教学本体（stage-2-22）

### 场景

你的 RPC 框架要支持**多注册中心**——今天用 ZK、明天换 SOFAJRaft、后天接 dubbo 生态。每个底层的 API 完全不同。怎么做到**换底层不动业务代码**？

**答案是服务注册接口抽象**（stage-2-22 的核心命题——课程主属落位）：`ServiceRegistry` 接口把注册/注销/查询收敛成五个标准操作：

```
ServiceRegistry（接口抽象——业务只依赖它）
  ├── initialize(config)            初始化
  ├── register(serviceInstance)     注册
  ├── deregister(serviceInstance)   注销
  ├── getServiceInstances(name)     查询
  └── close()                       关闭
  ├── 实现 1：ZK（参考 Spring Cloud ZK）
  └── 实现 2：SOFAJRaft（FSM + RpcProcessor + 副本同步内建）
```

**这是"框架抽象"最朴素的形态**：**接口定契约，实现可替换**——业务代码只看到五个方法，换底层 = 换一个实现类（配合 4.3 的 SPI/工厂加载）。

### 工业对照：dubbo ServiceDiscovery

dubbo 的服务发现接口是工业级版本（stage-2-22 KP-08 源码实证）：`ServiceDiscovery` 接口（register:36/unregister:40/getInstances:49）+ `AbstractServiceDiscovery` 抽象基座（:65——doRegister/doUnregister:365 **抽象方法留给子类**）——**"接口契约 + 抽象基座固化通用流程 + 子类最小实现"**（4.6 模板方法模式的 RPC 实例）。

### 关联：RPC 全链路聚合线

stage-2-22 是 **RPC 聚合线**的一环（骨架 §3.x）：stage-2-21（4.3 SPI 微内核）→ **本环节（4.8 生态整合）**→ stage-3-10（4.4 架构升级）→ stage-3-23（4.3 Dubbo 架构）→ stage-3-24（2.1 xDS 发现）→ stage-4-13（2.8 多活）。**服务注册抽象是所有 RPC 框架的地基**——dubbo/Feign/Spring Cloud 各自的 ServiceRegistry/ServiceDiscovery 都是这个模式的实例。

**my-xhs 判定**：**已用（Nacos 接管）**——my-xhs 的注册发现是 Nacos 声明式（`spring-cloud-starter-alibaba-nacos-discovery`——pom:52 实证），接口抽象由 Spring Cloud DiscoveryClient 提供（2.1 章节）——**不需要自造 ServiceRegistry**；**接口抽象的知识本体必懂**：看懂任何注册中心的接入层（DiscoveryClient/ZK Client/dubbo Registry）都是"接口 + 可替换实现"。

## 4. 双体系适配：Interceptor 签名解析（12 1.2）

### 场景

你在微球 MyBatis 增强里实现了自己的 `ExecutorFilter` 体系，但**用户习惯用 MyBatis 原生 Interceptor**——两套拦截体系并存，互不兼容。怎么让用户的 Interceptor 在自家过滤链里生效？

**答案是签名解析 + 适配器**：`InterceptorsExecutorFilterAdapter`（MyBatis Interceptor ↔ ExecutorFilter 双向桥接）。核心是 **@Intercepts 签名解析**（`signatureMap`——MyBatis 3.5.x 在 Plugin.java:67，旧版在 Plugins.java：**类名随版本迁移的实证**——读源码先看版本）：

```java
@Intercepts({
    @Signature(type = StatementHandler.class, method = "prepare", args = {}),
    @Signature(type = ResultSetHandler.class, method = "handle", args = {})
})
```

`getSignatureMap` 从注解**解析出"目标类型 + 方法 + 参数"三元组**，映射成拦截方法表——**声明式告诉框架"我拦谁"**（实验 `interceptsSignature_isParsedToMethodMap` 验证：2 个 @Signature → 2 个方法键）。签名指向不存在的方法**必须 fail-fast**（实验 `brokenSignature_failsFast`——Plugin.java:71 无 @Intercepts 抛 PluginException 同族）——**声明错误早炸好过运行时静默**。

**两个体系互通的本质**：拦截语义（前置/后置/短路）是通的，差的是**注册与分发机制**——适配器把"MyBatis 的声明式签名"翻译成"自家链的显式传递"（4.6 的显式 Chain vs 隐式 Plugin 对照）。

**my-xhs 判定**：**该用没用**——my-xhs 用 MyBatis-Plus 拦截器体系（MP 覆盖，无需自造）；**签名解析 + fail-fast 是写拦截器框架的必懂机制**（面试点：@Intercepts 怎么工作）。

## 5. 自研 vs 官方 SDK：选型决策框架（08 三章）

### 场景

配置中心客户端——直接用 Nacos 官方 SDK？还是自己写个 OpenAPI 客户端？微球选了后者（`OpenApiTemplateClient`——io.microsphere.nacos.client.common 包，零官方依赖）。**这不是拍脑袋**——08 3.2 沉淀了一个**选型决策框架**：

| 维度 | 官方 SDK | 自研（微球 OpenAPI） |
|------|---------|---------------------|
| 连接模型 | gRPC 长连接 | HTTP 短连接（OpenAPI 直连） |
| 推送 | 双向流（服务端主动推） | 长轮询（客户端拉） |
| 故障转移 | 有（连接管理/重连） | 无（自管） |
| 依赖 | ~10MB（SDK + 传输层） | ≈0（HTTP 客户端内置） |
| 版本适配 | 自动（跟随官方） | 手动（OpenAPI 接口自己维护） |

**决策逻辑**：**"轻量可控" vs "兼容维护"**——自研省依赖、可控、但版本演进自己扛（OpenAPI 变了自己改）；官方 SDK 省心、但有 10MB 依赖、升级跟随官方节奏。微球的取舍：作为**教学库**，自研 OpenAPI 客户端演示"最小可用"，且配了 **JVM 关闭钩子清理**（ConfigListenerManager:94 `addShutdownHook`——静态缓存 + 关闭时销毁——4.7 关闭钩子章节的实例）。

**my-xhs 判定**：**该用没用（官方已覆盖）**——my-xhs-analytics pom:52/:58 用官方 Nacos Starter（discovery + config 双 Starter 实证）；**决策框架本身是知识本体**：接任何基础设施（注册中心/配置中心/消息），先过一遍这张维度表——**"默认用官方"和"默认自研"都是懒惰，决策才是架构师**。

> 可跳过（进阶级，缺陷家族交叉）：自研还有**工程质量代价**——08 历史自研客户端被证实 4 个缺陷（D1 HashMap 并发缓存/D2 单 dataId 限制/D3 强转风险/D4 `Hashtable.contains` 查值非查键——"不覆盖"防御无效）——**"自研省依赖，但要自己扛并发/语义/边界"**。这些缺陷家族条目 3.3 章节（分布式事务理论）交叉汇总，此处提名字即可。**同仓拼写缺陷（家族第 4/5 例）**：`NacosPorpertySource`（Porperty——**注解类名拼错**——测试也拼错——**错误固化**）+ `configCientCache`（Cient——缺 p）——**API 稳定约束**（StacKTrace/Pattens/FILER 同族——4.6/4.5/4.7 已述）。

## 6. 版本兼容层：同名同包重实现（04 4.3）

### 场景

你还在 Boot 2 项目，但想用 Boot 3 的新 API（`BootstrapContext`——启动期按类型取值的服务注册表）。怎么办？

**微球的答案：`package org.springframework.boot` 同名同包重实现**（microsphere-spring-boot-compatible 模块）——**在自己的代码里把 Boot 3 的类名/包名原样实现一遍**（BootstrapContext.java:34 interface + 五方法完整契约 get/getOrElse/getOrElseSupply/getOrElseThrow/isRegistered :56/:67/:81/:90 实证）：

```java
package org.springframework.boot;   // 同名同包！

public interface BootstrapContext {
    <T> T getOrElse(Class<T> type, T other);
    <T> T getOrElseSupply(Class<T> type, Supplier<T> other);
    <T> T getOrElseThrow(Class<T> type, Supplier<? extends X> exceptionSupplier) throws X;
    <T> boolean isRegistered(Class<T> type);
}
```

**原理**：Java 类加载按"**包名 + 类名**"区分——同名同包即"就是那个类"，业务代码 import 不变、编译不变，只是运行时走的是你的实现。**这是版本迁移兼容的激进策略**：代码先动、框架后升——等升级 Boot 3 后删掉兼容层，官方类接管（标注 [过时→Boot 3.2 官方]）。

**边界（必须知道）**：同名同包重实现是**危险操作**——类加载冲突（两个同名类在 classpath 时行为未定义）、与官方版本共存会互相污染。**适用前提**：你是**框架维护者**（控制 classpath）；**不适用**：应用开发者（直接升级或依赖版本兼容库）。

**my-xhs 判定**：**该用没用**——my-xhs 是 Boot 3 已迁移（无 Boot 2 项目，无此需求）；**知识本体**：理解"同名同包"机制能解释很多诡异问题（类被谁加载、SPI 被谁覆盖——4.7 类加载章节联动）。

> 可跳过（进阶级，04 四章配套）：兼容层还包含 **Actuator 化**——把内部工具暴露成 Actuator 端点（`/actuator/artifacts` 构件探测、`/actuator/configMetadata` 配置元数据——04 4.1：**"内部工具 → 运维端点"的生产化路径**）——2.9 章节（可观测性）的指标面是消费端，这里讲的是**端点生产端**。

## 7. 特性开关：功能门控（05 5.1）

### 场景

你的框架能力越来越多（zone 路由/灰度/调试端点），想让用户**按配置启停**——不用的功能不装配。Spring Cloud 没内建特性开关，微球自己做了 **Features 特性门控**（05 5.1）：

**`@ConditionalOnFeaturesAvailable`/`@ConditionalOnFeaturesEnabled`**（条件注解）+ `FeaturesProperties`（配置载体）+ `NamedFeatureComparator`（按 order 排序——NamedFeatureComparator.java:32 实证）——**功能门控（Feature Toggle）模式**：配置声明哪些特性开，条件注解按特性集合决定装配。

实验 `featureToggle_enabledByConfiguredNames` 验证按配置启停；`featureToggle_sortedByOrder` 验证特性按 order 稳定执行（同名 Comparator 语义）。

**与 4.2 条件注解的关系**：特性开关 = **条件注解的应用层**——@ConditionalOnXxx 是"类/属性存在"的条件，特性开关是"业务功能级"的门控（4.2 的机制面 + 本文的功能面）。

**my-xhs 判定**：**该用没用**——my-xhs 的灰度/功能开关是 Nacos 配置 + 代码 if（散落）；**特性开关集中化**（配置 + 条件注解 + 排序）可参考——2.8 的灰度路由场景直接受益。

## 本章小结

**知识本体**：框架抽象与适配的完整工具箱——**双栈实现**（同一能力 + 两套框架适配器——实验）+ **Filter 桥接**（框架无关抽象 + Log4j2 适配器——实验）+ **服务注册接口抽象**（ServiceRegistry 五操作 + dubbo 工业对照——课程主属 stage-2-22）+ **双体系适配**（Interceptor 签名解析 + fail-fast——实验）+ **选型决策框架**（自研 vs 官方 SDK 五维表 + D1-D4 工程质量代价）+ **版本兼容层**（同名同包重实现——五方法契约）+ **特性开关**（功能门控 + 排序——实验）+ **子上下文规格定制**（可跳过）+ **响应式↔阻塞桥**（Flux→List）。

**一条主线**：**"抽象层写一遍，适配层写 N 遍"**——能力本体不绑框架（Filter/双栈/拦截语义/服务注册），适配器负责翻译（桥接/签名解析/双栈适配/数据流转换），选型决策决定哪些该抽象、哪些直接用官方。

**实验验证**：spec-bridge 8 个断言全绿（双栈 2/桥接 2/签名解析 2/特性开关 2）。

**my-xhs 判定**：双栈/Filter 抽象/兼容层**不该用**（单栈 + 官方覆盖）/ 服务注册已用（Nacos + DiscoveryClient 接管）/ 签名解析该用没用（MP 覆盖）/ 特性开关该用没用（灰度集中化——2.8 受益）/ 官方 SDK 已用（Nacos Starter——选型框架知识本体）/ 子上下文该用没用（官方 NamedContextFactory 覆盖）。
