# 28. 工具与基础库：JDK 演进吃掉框架模式

> 配套实验：`spec-tools`（11 个断言——类加载/调用者/进程/泛型/集合/版本/转换）
> 定位：**模式家族 9（反射读私有字段）主落位** + 过时替代图谱 + 序列化族谱汇总（Base64 → 转换方向族 → 定长）
> 来源：源码 01 一~三章（类加载/反射/进程）+ 02 三/四/七/八章（泛型/集合/版本/转换）+ 06 五章（常量/工具）+ 01 六章（替代图谱）+ 10 三章（定长序列化）
> 前置：1.1 章节（SPI/规范本体——工具库的姊妹篇）

有个老工具库叫 confucius-commons，36 个文件，每个文件都在替 JDK 6 补位：JDK 没给 `Base64`、没给 `Path`、没给 `ProcessHandle`，它就手写。然后在接下来的十年里，**JDK 把它的实现一个接一个全收编了**——今天打开这个库，36 个文件几乎个个都有原生替代品，全库变成一份"JDK 演进吃掉框架模式"的死亡档案。

这一章把这些工具按**知识本体**分组讲：类加载、反射与模块、进程、泛型模型、集合、版本、转换——每个都配实验。学它的价值不在代码（代码全该删），在它触发的 **JDK 内部机制**：这些机制到今天还是排查线上问题、读懂框架源码的底层语言。

## 1. 类加载：框架魔法的血管

### 场景

你的应用内存泄漏，怀疑有类被反复加载。怎么知道"某个类到底加载没加载"？JDK 有这个能力——但**它是 `protected` 的**：`ClassLoader.findLoadedClass(String)`（JDK17 ClassLoader.java:1282），唯一 Java 侧入口是反射。

confucius 就是这么干的：沿 `getParent()` **ClassLoader 继承链**逐个加载器反射调用 `findLoadedClass`（类可能由任一父加载器加载——这就是双亲委派的名字由来：子加载器先问父），底层是 native 的 `findLoadedClass0`（ClassLoader.java:1288）。

### 三个更底层的事实

1. **每个 ClassLoader 都有一张"已加载类注册表"**：私有字段 `classes`（JDK17 是 `ArrayList<Class<?>>`，ClassLoader.java:311）。confucius 直接反射读它拿全量快照——**这个字段在 JDK11 还是 `Vector`，JDK17 改成 `ArrayList`，改型一次**（版本脆弱性实证：反射 JDK 内部 = 拿命赌它不改名）。
2. **类代码来源能定位**：`Class.forName(...).getProtectionDomain().getCodeSource().getLocation()`——回答"这个类到底来自哪个 jar"（类冲突排查神器）。bootstrap 类没有 ProtectionDomain，要走 classpath 兜底。
3. **`--add-opens` 是今天的门槛**：JDK9 起模块默认封装，上述反射 `setAccessible(true)` 直接抛 `InaccessibleObjectException`（AccessibleObject.java:221 实证）——必须 `--add-opens java.base/java.lang` 放行。**生产没人会为诊断加这个参数**——所以这套工具今天全用 Arthas（`sc`/`dump` 命令）替代。

实验 `parentDelegation_requestsGoToParentFirst` 验证了双亲委派（自定义加载器加载 `String`，落点是 bootstrap——顶层无加载器）；`codeSourceLocatesClassOrigin` 验证了类来源定位。

> 可跳过（排查用）：类加载还有个"诊断视角"——`ClassLoadingMXBean`（标准 JMX）能读已加载/卸载计数、运行时开关 verbose（等价 `-verbose:class`）。业务代码几乎不碰 JMX，Arthas/Prometheus 替你消费了。同类还有三个 confucius 的历史封装：`ResourceType` 枚举（`com.foo.Bar` → `com/foo/Bar.class` 资源名归一化）、`ClassLoader.getResources()` 多加载器联合查找（JDK 原生沿继承链返回全部）、`SimpleClassScanner` 全量扫描链 + **JAR/目录双模式类发现**（isDirectory 递归 / JarFile 遍历双分派——启动全扫现代是性能陷阱——Spring `ClassPathScanningCandidateComponentProvider` + `JarFile.stream()` 是正解）、运行时 classpath 解析（`RuntimeMXBean.getClassPath()` 按分隔符切分——JDK9+ 直接读 `java.class.path` 系统属性即可，bootstrap path 已恒空）。知道名字即可。

**my-xhs 判定**：**不该用**——类冲突排查用 `jar tf`/Arthas；my-xhs 无反射读 ClassLoader 场景。**但"双亲委派 + 类来源定位 + 模块封装"是读懂 Spring 扫描/SPI/热部署的底层语言，知识本体必须掌握。**

## 2. 反射与模块系统：JPMS 是分水岭

### 场景

你的工具库要"找调用者"（谁调用了当前方法）——日志归属、权限判断都要它。JDK 6 时代的答案是 `sun.reflect.Reflection.getCallerClass(int)`，一个内部 API。**JDK 9 模块化后它躲进 `jdk.internal.reflect`**（JDK17 Class.java:77 import 实证——`getCallerClass` 还在，但 java.base 内部专属，外部代码碰不到），confucius 的调用路径从此是死代码。三代演进：

| 方案 | 机制 | 结局 |
|------|------|------|
| `sun.reflect.Reflection` | 反射调内部静态方法 | **JDK9 藏进 `jdk.internal.reflect`**——外部死代码 |
| `getStackTrace()` 遍历 | 全栈生成再找偏移 | 慢（每次生成全栈）+ 帧偏移是魔法数 |
| **`StackWalker`**（JDK9+） | 官方 API，按需遍历栈帧 | **正解**——`getCallerClass()`（StackWalker.java:595）一行搞定 |

实验 `callerClassName_viaStackWalker` 验证了 `StackWalker.getCallerClass()` 返回真正的调用者类。

### 模块化三件套（排查反射问题的必备知识）

1. **`--add-opens` vs `--add-exports`**：exports 管"编译期可读 + 运行期可读"（Module.java:865），opens 管"运行期深层反射"（Module.java:903/912）——**区别在作用面：exports 管"看得见"，opens 管"摸得着"**。反射 `setAccessible` 失败要的是 `--add-opens`。
2. **`InaccessibleObjectException`**：JDK9+ 反射越界的标准报错——不是权限问题，是**模块设计问题**（java.base 就是不 opens 给你）。
3. **`Unsafe` 的历史地位**：JDK9 前拿反射读 `Unsafe.theUnsafe`（`AccessController.doPrivileged` + 反射）是标准做法；JDK17 它在 `jdk.unsupported` 模块，官方明示 unsupported；**替代品 `VarHandle`**（类型安全、内存语义安全）——"JDK 把后门收编成正规军"的实证。

### 反射工具的两个工程细节（02 三章）

1. **banned-methods 配置化禁用名单**（MethodUtils :104-113）：`microsphere.reflect.banned-methods` 系统属性声明"哪些方法反射时不碰"（如 `java.lang.String#substring()`）——**排除框架反射遍历时的干扰方法**。Spring 用 `findAllMethods` + 过滤器，microsphere 是配置化名单——"运行时可调的反射白名单"是个少见的工程思路。
2. **`--add-opens` 友好错误提示**（AccessibleObjectUtils :200-204）：反射失败时**解析异常消息自动提取包名**，拼出完整的 `--add-opens java.base/xxx` 命令给开发者（JDK9+ 的 `trySetAccessible()` 返回 false 而非抛异常时，这个提示是唯一线索）——**开发体验设计**：把 JDK 的报错翻译成人话。§9 的 my-xhs 反射案例如果失败，这个提示能直接告诉你怎么放行。

**my-xhs 判定**：**不该用**——my-xhs 无 `StackWalker`/`Unsafe` 场景（反射读私有字段另有 3 处实证，见 §9）。**但"模块化反射规则"是排查一切"反射突然失败"问题的必备知识。**

## 3. 进程：JDK 原生 API 的补位史

> 可跳过（历史对照）：这一节的代码全过时，但"演进路径"是 JDK 原生 API 设计的活教材。

### 进程号：三级深挖到一行 API

confucius 取 PID 的路径极端到教科书级别：**反射读 `RuntimeMXBean` 私有字段 `jvm`，再反射调它的私有方法 `getProcessId()`**——两级深挖，依赖 `sun.management.RuntimeImpl` 内部实现类，任何 JDK 内部调整都炸。降级方案是解析 `runtimeMXBean.getName()`（格式 `pid@host`）。

**JDK 9 的正解**：`ProcessHandle.current().pid()`（ProcessHandle.java:135）——一行。实验 `processPid_twoSourcesAgree` 验证两条路径结果一致。

### 进程执行超时：轮询 vs 原生

confucius 手写超时循环：轮询 `exitValue()`（未结束抛 `IllegalThreadStateException`）+ `sleep` + `destroy()` 回收。两个坑：**忙等轮询空转 CPU**、`endTime` 初始值 -1 导致首次判定失真。**现代正解**：`process.waitFor(timeout, TimeUnit)` + `destroyForcibly()`——原生支持，无轮询。

### Attach：Java Agent 的底层

`VirtualMachine.attach(pid)` → 操作 → finally `detach()`——**attach 是理解 Java Agent/Arthas 的底层前置**。JDK9 起它归入 `jdk.attach` 模块（attach API 本身 JDK6 已有，模块化是 9+）。注意 agent 两条加载路径：`premain`（启动时 `-javaagent`，不走 attach）vs `agentmain`（运行时 `VirtualMachine.loadAgent` 附加——**Arthas 走的就是这条**）。4.7 交叉 stage-1-18（Instrument 追踪链路重构——agent 应用实例）。

**my-xhs 判定**：进程面**已用 1 处**——`OnlineRouteService.java:40` 用 `ProcessHandle.current().pid()` 拼实例唯一 ID（线上实证）；进程执行/attach **不该用**（诊断用 Arthas 覆盖）。交叉：01 三章主落位本文，性能面 5.2 章节（JVM 诊断）。

## 4. 泛型模型：Type 五形态

### 场景

你写了个 `BaseDao<T>`，子类 `UserDao extends BaseDao<User>`——运行时怎么知道"T 就是 User"？**泛型擦除后反射拿不到实参？错了——`getGenericSuperclass()` 能拿到**。JDK 的 `java.lang.reflect.Type` 有 5 种形态（Kind 枚举实证——JavaType:213-216）：

| 形态 | 例子 |
|------|------|
| `Class` | `String.class` |
| `ParameterizedType` | `List<String>` |
| `TypeVariable` | `T` |
| `WildcardType` | `? extends Number` |
| `GenericArrayType` | `T[]` |

microsphere 把 5 形态封装成 `JavaType` 模型（懒解析缓存 + 常用实例预置），配套 `TypeUtils.resolveActualTypeArgument`（:448/:476）解析实参——**convert 包泛型推断的地基**（泛型 DAO/泛型转换器都靠它）。

**深潜：递归解析怎么防环**——属性解析（BeanUtils :449-459）递归展开字段类型，但**没有 visited 集**，靠**深度预算**截断：`resolvedDepth.incrementAndGet() >= maxResolvedDepth` 即停（:454），配类型白名单（primitive/simple 直接返回 :488-489）。对照：Jackson/Spring 用对象标识防环，microsphere 用深度预算——**性能与完整性的权衡**。自循环类型（`Node` 的字段是 `Node`）没有它就会无限递归。

实验 `genericTypeArgument_isResolvedFromSuperclass` 复刻了解析链：`getGenericSuperclass()` → `ParameterizedType` → `getActualTypeArguments()[0]` → `User.class`；`wildcardUpperBound_isExposedByTypeApi` 验证了 `? extends Number` 的上界读取。

**现代对照**：Spring `ResolvableType`（spring-core:87）功能更全（含 AnnotatedType）——`ResolvableType.forClass(...)` + `GenericTypeResolver.resolveTypeArgument`（GenericTypeResolver.java:112）。**自研封装 = 重复造轮子；机制 = 必懂**（Spring 的 `ResolvableType`、MyBatis 的泛型 Mapper 推断全踩在这条链上）。

**my-xhs 判定**：**不该用**——Spring `GenericTypeResolver`/`ResolvableType` 已覆盖；my-xhs 无自研泛型工具。**实参解析机制必懂**（读框架源码的钥匙）。

## 5. 集合工具：JDK 补位的最后战场

### 不可变工厂的诞生（JDK 9 之前的手工活）

JDK 9 前没有 `List.of()`。microsphere 的 `Lists.ofList` 用 **MethodHandle 运行期探测**：`findPublicStatic` 探测 JDK9 的 `List.of` 是否存在（方法不存在返回 NOT_FOUND 哨兵——MethodHandlesLookupUtils:66/:115——探测失败返回 null 而非抛错）——存在则 `invokeExact` 调用，不存在降级 `Arrays.asList`。**探测-降级双保险**是跨 JDK 版本兼容的标准手法。它还用了 JDK9 前经典的**重载轰炸**手法（`of` 方法 9 重载，按元素个数 0-8 逐个定义，避免 varargs 数组分配——Sets/Maps 按 arity 缓存多个 MethodHandle）。今天 JDK9 起步，`List.of`/`Set.of`/`Map.of` 原生（不可变实现 `List12`/`ListN`，ImmutableCollections.java:546/653）——探测代码本身也被收编了。

实验 `listOf_isImmutable` 验证 `List.of()` 不可变（add 抛异常）。

### 两个值得学的集合细节

1. **LRU 一行实现**：`LinkedHashMap` 的 `accessOrder=true` 参数（构造第三个参数）——按访问序排序，配 `removeEldestEntry` 就是 LRU 缓存。microsphere 的 `MapUtils` 参数化了它（:655）。实验 `lruMap_evictsLeastRecentlyUsed` 验证：访问 `a` 后再插入触发淘汰，被淘汰的是最久未访问的 `b`。
2. **equals 的集合语义陷阱**：JDK 的 `List.equals(Set)` 恒 false（类型不同即不等）——但"集合语义相等"（元素集相等）在 `CollectionUtils.equals` 里用**同引用/双空/长度/containsAll 四判**（:411-430）——**空 List 与空 Set 语义相等**（测试实证 CollectionUtilsTest:196-198）。**陷阱**：containsAll 在重复元素场景不精确（`{a,a,b}` vs `{a,b,b}` 长度和 containsAll 都过但语义不等——multiset 边缘缺陷）。

### 教科书 bug：组合谓词的 XOR 陷阱（confucius KP-14——4.6 交叉落位）

confucius 的 `FilterOperator` 用枚举实现 AND/OR/XOR 组合过滤（JDK8 前无 `Predicate.and/or`）。**XOR 实现藏了一个教科书级 bug**（FilterOperator.java:60）：

```java
XOR {
    public <T> boolean accept(T o, Filter<T>... filters) {
        int length = Array.getLength(filters);
        if (length == 0)
            return true;            // ① 空数组返回 true——XOR 恒等元应为 false
        boolean success = true;     // ② 初始值 true——这是 bug 根源
        for (Filter<T> f : filters) {
            success ^= f.accept(o); // ③ ^= 是"组合操作"，但初始值决定语义
        }
        return success;
    }
}
```

**`success = true` 初始值让 XOR 变成了 XNOR**：单 filter 时 `true ^ f` = `!f`（取反！），双 filter 时 `true ^ f1 ^ f2` = `f1 == f2`（同或）——**"看起来在做 XOR，实际做 XNOR"**。正确应初始化 `false`（"奇数个 true"才是 XOR）。同类坑还有 `&=`/`|=` **非短路**（先全算再归并——`Predicate.and` 用 `&&` 短路）。

**测试教训**：这个 bug 上线多年没被发现——因为测试只覆盖单 filter 的 AND/OR（FilterUtilsTest），XOR 与多 filter 组合**从未被测过**。**"没测过的分支 = 不存在"**。

**现在怎么写**：`Predicate.and/or/negate` 原生短路组合（本 bug 的现代替代）。

> 可跳过（进阶级）：同类"看起来对≠真的对"案例——`FileUtils` 相对路径用 `contains` 子串匹配当路径边界（`/data/workspace` 误匹配 `/data/workspace2`，FileUtils:36）；`SimpleJarEntryScanner` 用 `startsWith` 前缀匹配（`META-INF/` 误匹配 `META-INF2/`，:117）——**路径/包边界必须用 Path 语义或分隔符判定，不能偷懒用子串**。现代替代 `Path.relativize`。
>
> 可跳过（进阶级）：**confucius 的正面教材**（值得学的好设计）——①`FilterUtils` 三保险：**拷贝 → iterator.remove → 不可变返回**（FilterUtils:58-68——先拷贝再删，副作用隔离；返回 unmodifiableList 防外部修改——"别人动不了你的集合"）；②`JarUtils` 协议白名单校验（JarUtils:68-71——只认 `jar:`/`file:` 协议，拒绝 http 等——**防任意协议加载**）；③`ProcessManager.remove(key, value)`（:32——带值匹配的删除，防止误删同 key 新进程——并发防误删细节）；④`CustomizedThreadFactory` 线程命名（02 七章——:40 implements ThreadFactory + 名称前缀/daemon/优先级/栈大小 :61-63——my-xhs 排查线程问题时"看得见名字"的工程细节）。

> 可跳过（进阶级）：`FIXED_LOAD_FACTOR=1.0f` 防扩容（已知容量时预分配满，避免 resize 抖动——MapUtils:66）；空/单例/不可变/委托/适配器五家族（02 四章）——**DelegatingWrapper 解包协议**（`unwrap/isWrapperFor` 默认方法——JDBC Wrapper 模式的移植）值得记住名字，my-xhs 数据源包装层有同类需求。

**my-xhs 判定**：**已用**——`List.of`/`Map.of` 等不可变工厂 **220+ 处**、`LinkedHashMap` 保序场景大量使用（如 LikeService:249）；LRU **不该用**——**不是"没想到用"，是决策过不用**：CounterService.java:26-33 注释实证"为什么不用 Caffeine 本地缓存"（计数高频变更 + 多实例一致性：实例 A 失效只清自己的缓存、实例 B 仍返回旧值；Redis GET <1ms 不值得引入分布式一致性问题）——本地 LRU 缓存被 Redis 服务端淘汰策略替代（RedisMultiSourceConfig.java:13 allkeys-lru）。这个"决策文档"本身就是要学的模式：**缓存工具的选择不是性能最优，是架构一致。**

## 6. 版本与兼容：SemVer 和它的 DSL

### SemVer：别用字符串比较版本

"1.10.0" 和 "1.9.0" 用字符串比较是 `"1.10.0" < "1.9.0"`——**错**。逐段数值比较才是语义化版本（SemVer）的规则：major/minor/patch 三段分别 `compareTo`。microsphere 的 `Version`（02 :91-791）实现了完整的 `Comparable<Version>`。

实验 `semVer_comparesNumericNotLexical` 直接对比了两种比较的差异。

### Compatible DSL：声明式版本分支

`Compatible.of(Class).on(">=", "2.0").call()`——版本满足才执行回调，**Operator 枚举实现 `BiPredicate`**（EQ/LT/LE/GT/GE + null 安全比较）。这是 Spring 都没有的独特设计：多版本兼容场景（第三方 SDK 适配）把 `if (version >= 2.0)` 手写分支 DSL 化。实验 `whenAtLeast_conditionalExecution` 验证：不满足条件的回调不执行。

### 从类反查构件（ArtifactDetector）

类 → classpath URL → Artifact（artifactId/version）——Maven 版本从 `pom.properties` 解析；配合 `BannedArtifact` 黑名单（`META-INF/banned-artifacts`——与 §2 的 banned-methods 同家族）。依赖冲突诊断利器——现代替代是 Maven `dependency:tree`（构建期）。

> 可跳过（进阶级）：**URL 协议扩展**（02 七章）——`URL.setURLStreamHandlerFactory` 全局只能设一次（**单例限制**），microsphere 的 `CompositeURLStreamHandlerFactory`（net 包，六件套：组合工厂顺序委派 :75-80 + SPI 加载 + 子协议连接工厂）解决"一个工厂不够用"。**对照：扩展 JDK URL 协议 vs 用 Spring `Resource` 抽象**——Spring 选择了协议无关的抽象（`classpath:`/`file:` 前缀），比动 JDK 内部更稳。my-xhs **不该用**（Spring Resource 覆盖）——但"**单例限制 → 组合工厂**"是通用设计手法（任何"全局只能设一次"的扩展点都能用）。

**my-xhs 判定**：**该用没用**——版本兼容判断无场景（单版本部署）；SemVer 比较若遇到"按版本分支"场景（如第三方 SDK 适配）可参考 `Compatible` DSL；**"字符串比较版本是错的"是面试高频题，必须会**。

## 7. 关闭钩子管理：停机的工程化

### 场景

你的服务要优雅停机：先停接收新请求 → 等存量请求处理完 → 刷盘内存数据 → 关连接池。**停机是"最后一次能全局干预的窗口"**（与 4.5 启动扩展呼应）——但 JDK 的 `Runtime.addShutdownHook` 有个问题：**每个钩子一个线程，钩子多了不可控**（阻塞的钩子拖着 JVM 不退出；无限注册无上限）。

### microsphere 的方案：专用线程 + 容量配置

`ShutdownHookUtils`（02 七章）三个设计：

1. **专用线程**：所有回调注册到一个 `ShutdownHookCallbacksThread`（ShutdownHookCallbacksThread:40 extends Thread）——**单线程串行执行，顺序可控**。
2. **容量配置化**：`microsphere.shutdown-hook.callbacks-capacity` 系统属性 + 默认 512（:86-96）——**防止无限注册**。
3. **幂等注册**：`registerShutdownHook()` 先用自家线程过滤器查是否已挂过 JDK 钩子（:112/:139——`SHUTDOWN_HOOK_CALLBACKS_THREAD_FILTER` 按类名识别），已挂则跳过——**防重复注册**（静态块 `:120-122` 类加载即注册，不是懒）。

### my-xhs 的实证（已用，但走了另一条路）

my-xhs 的停机是 **Spring 生态标准做法**（GracefulShutdownListener.java——监听 `ContextClosedEvent`）：Nacos 下线 → sleep 10s 等服务列表传播 → `getBeansOfType(GracefulShutdownHook.class)` 逐个调 `onShutdown()`（:112——**失败隔离**：单个钩子异常不影响其他）→ @PreDestroy → 关连接池。对比：

| | microsphere ShutdownHookUtils | my-xhs Spring 版 |
|---|---|---|
| 触发源 | JDK shutdown hook | `ContextClosedEvent`（Spring 容器事件） |
| 钩子收集 | 系统属性容量注册 | **Bean 收集**（接口实现即自动注册——4.3 SPI 模式） |
| 顺序 | 单线程串行 | Bean 迭代顺序 |
| 失败隔离 | — | **逐钩子 try-catch**（:109-118） |

**my-xhs 判定**：**已用（Spring 等价物）**——`GracefulShutdownHook` 接口 + `GracefulShutdownListener`（停机全流程注释是教科书级：`server.shutdown=graceful` + timeout + Nacos 下线 + 钩子链）；microsphere 的"容量限制"思路**该用没用**（my-xhs 无钩子上限——钩子多了的防御可补）；JDK 裸 `addShutdownHook` **不该用**（Spring 事件覆盖）。

## 8. 常量与工具组织：从常量接口到 @ConfigurationProperties

### 场景

多活模块有一组配置属性（`zone.enabled`/`zone.preference.enabled`/`zone.preference.upstream.disabled-zone`）——**前缀分层属性族**（06 ZoneConstants:15-241）。JDK 9 前没有接口私有方法，共享常量最省事的方式是**常量接口**（`interface ZoneConstants`，:15——经典反模式）。它是经典反模式：接口暴露 API 面、无封装、实现类被污染——就是过时替代图谱的末条（§11 表格 #17）。

**现代正解是 `@ConfigurationProperties`**：注解类 + 嵌套结构代替常量前缀拼接（my-xhs 实证——`ZoneProperties.java` 四层嵌套结构 :17-35 与微球常量前缀逐层对应——**微球常量接口 → Boot 标准绑定**的完整演进）。

### 两个知识细节

1. **拼写错误的 API 稳定性**（缺陷家族）：`ZoneConstants` 里的 `PREFERENCE_FILER`（:108——FILER 应为 FILTER）——**常量/方法名一旦发布就是契约**，微球拼错后全生态只能沿用（StacKTrace/Pattens 同族——4.6/4.5 已述）。
2. **按名取 Bean 的替代**：`ZoneUtils` 里 `getBean(Class)` 之类的手工取 Bean 工具——Spring 注入即可，自研工具是冗余（06 :313 判定实证）。

**my-xhs 判定**：**已用（现代化改写）**——`ZoneConstants` 移植 + `ZoneProperties`（@ConfigurationProperties 嵌套替代常量接口——2.8 章节实证）；`ZoneUtils` 型工具**不该用**（Spring 注入覆盖）。

## 9. 反射读私有字段：模式家族 9（脆弱性家族）

> 定位：**模式家族 9 主落位**——跨仓库 5 处实证的脆弱模式：反射读 JDK/框架私有字段（或栈帧探测），框架一升级就静默失败。

### 三个案例，同一个教训

| 仓库 | 读什么 | 风险 |
|------|--------|------|
| 09 G8 | SCG `FilteringWebHandler` 私有字段 `globalFilters`（CachingFilteringWebHandler.java:122 `getFieldValue(this, "globalFilters")`） | SCG 升级静默失败——缓存构建逻辑全断 |
| 12 P1 | MyBatis `CachingExecutor.delegate` 私有字段（Executors.java:64 `getFieldValue(cachingExecutor, "delegate")`） | 二级缓存短路时拦截器失效——**语义隐藏边界**（CachingExecutor :102-107 同族） |
| 01 | JDK `ClassLoader.classes` 字段（11→17 Vector→ArrayList 改型） | **JDK 已改型一次**——版本脆弱性实证 |
| 02 | 调用者类解析：`getStackTrace()` 遍历 + 帧偏移魔法数（StackTraceUtils:44/:64——注释自承"每加一层调用都要 +1"） | 帧偏移随 JVM/代码结构漂移——脆弱魔法数（confucius KP-28 同族） |
| 14 | Sentinel `ContextUtil.resetContextMap` 内部方法（SentinelUtils:51 MethodHandle 反射） | Sentinel 升级静默失效 |

**规律**：反射读框架私有字段 = 把"内部实现"当 API——框架没承诺，改了不通知，你的逻辑静默失效（无编译错、无运行时报错，只是行为悄悄变了）。

### my-xhs 的真实教训（3 处实证）

my-xhs 生产代码（src/main）里有 **3 处反射读私有字段**：

- `RocketMQHealthIndicator.java:89-90`——反射读 `RocketMQTemplate.producer`（健康检查需要触达 producer 状态）——**真·该用没用**：官方 `getProducer()` 就摆在那（RocketMQTemplate.java:75 实证），反射纯属省事路径，RocketMQ 升级即静默失效
- `ShadowTableInterceptor.java:90-91`——反射写 MyBatis `BoundSql.sql`（影子表 SQL 重写）——**可接受的业界惯例**：`BoundSql` 只有 `getSql()` 没有 setter（BoundSql.java:52 实证），改写只能反射（ShardingSphere 同款）；风险仍在升级，但手段无替代
- `InterceptingRedisConnectionInvocationHandler.java:70`——`setAccessible` 包装代理调用（代理场景的标准操作，风险低）

**判定**：**已用但分三档**——①有官方入口却走反射（RocketMQ）= **必须整改**（改 `getProducer()`，一行）；②官方无 setter 的业界惯例（BoundSql）= **保留但要 fail-fast**（反射失败显式报错，别静默）；③代理包装的标准操作 = 无风险。**核心纪律：反射不是不能用，是必须把"失败"暴露出来**——微球 G8 的教训恰恰是"反射失败没人知道"。

## 10. 转换方向族 + 序列化族谱

### 转换四方向族（02 八章）

52 个转换器按方向归 4 族——**每族一个模板模式**：

| 族 | 模板 | 实例 |
|----|------|------|
| 字符串族 | `StringConverter<T>`（String 枢纽标记）+ 单例 | String→Enum/Duration/InputStream 17 个 |
| 集合族 | **继承树**（`StringToIterableConverter` 基座 → Collection → List/Set/Queue/Deque 13 变体）+ **MultiValueConverter 双类型 accept**（源 + 集合类型双匹配） | 分隔字符串转集合 |
| 数值族 | 统一模板 | Number→X 7 个 |
| Object 族 | 宽入口 + Optional 特殊实现 + Map↔Properties | 特殊类型 |

**设计要点**：集合族用**继承树而非 13 个独立类**——模板方法模式的转换器版（4.6 交叉）。

### 序列化族谱（4.7 汇总——跨主题聚合线）

**一条线看懂序列化演进**：手写 → JDK 收编 → 框架抽象 → 框架内置。每个环节的"知识本体"（编码规则/边界校验）独立成立，**实现全部被替代**。

**my-xhs 判定**：**不该用**——Spring 转换体系（`Converter`/`ConversionService`）+ Jackson 全覆盖（RedisConfig.java:119-140 实证）；**该用没用**——定长自校验模式（协议设计防损坏数据的思路——my-xhs 与外部系统交互若做自定义编码可参考，性能面见 5.3 章节交叉）。
