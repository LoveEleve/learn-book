## 1. 连接池的本质：复用昂贵的连接

### 场景

数据库连接**创建极贵**（TCP 握手 + 认证 + 会话建立——毫秒级）。每次查询都新建连接 = 把时间花在连接上。连接池的答案：**连接复用**——池里常驻 N 条连接，用完归还，需要再借。

**连接生命周期**（07 7.1 知识本体）：**创建 → 验证 → 借用 → 归还 → 关闭**。

**DataSource 契约**（1.3 章节的 JDBC 规范）：`getConnection()` 是应用唯一入口——**连接池 = DataSource 的实现**（应用无感知——1.3 的驱动注册机制联动）。

## 2. HikariCP 的核心：ConcurrentBag（07 7.1——性能面）

### 为什么 Hikari 快？——ConcurrentBag 设计

HikariCP 的**高性能核心**是 `ConcurrentBag`（ConcurrentBag.java:73——`handoffQueue` 实证）——连接容器的三个设计：

1. **ThreadLocal 优先**（:45——"ThreadLocal lists can be stolen"——**线程本地借还零锁**）：借用时先看自己的 ThreadLocal 列表——**无锁复用**（归还时放回，下次同一线程直接拿）。
2. **handoff 队列兜底**（:73 `SynchronousQueue`——**"被偷"机制**）：ThreadLocal 没有时从 handoff 队列取——**跨线程借用**（"stolen" 语义实证）。
3. **借出不删除**（:49-52——"borrowed objects are not removed"——**借用标记而非移除**）：借用 = 标记状态，不离开集合——**减少 GC 压力**；归还 = `requite`（放回 ThreadLocal）——**"requite"是 ConcurrentBag 的归还语义词**。

实验 `concurrentBag_borrowRequiteReusesConnections` 验证：归还后借用**复用同一连接**（created 不增长——复用语义）；`concurrentBag_handoffQueue_stealsWhenSharedEmpty` 验证：共享列表空时从 handoff 取（**ThreadLocal steal 语义模拟**）。

**对照**：传统池的获取路径有**显式锁**（DruidDataSource.java:204/:234/:267——`lock.lock()/unlock()` 实证——借还都要拿锁）；Hikari 的 ThreadLocal + handoff = **绝大多数借用无锁**——**"少锁"是 Hikari 快的第一原因**（Druid 也有后续优化，但 Hikari 把"无锁优先"做到设计核心）。

## 3. Hikari 参数族：五个关键旋钮（07 7.1——:372-404）

### 参数与默认值

| 参数 | 默认值 | 含义 | 调优要点 |
|------|--------|------|---------|
| `minimumIdle` | 与 max 相同 | **最小空闲连接**（池常驻下限） | 预热：突发前先备好 |
| `maximumPoolSize` | 10 | **最大连接数**（并发上限） | **不是越大越好**（DB 侧也有连接上限） |
| `connectionTimeout` | **30s**（HikariConfig.java:50） | **借不到连接的等待超时** | 池满时的"卡死"就是它在等 |
| `idleTimeout` | **10min**（:53） | 空闲连接存活（**仅在 minIdle < maxPoolSize 时生效**——README:198 官方语义） | 空转资源回收 |
| `maxLifetime` | **30min**（:54） | **连接最大寿命**（到期强制回收） | **必须小于数据库侧超时**（防"僵尸连接"） |
| `keepaliveTime` | **2min**（README:209——主动保活） | **定期"ping"空闲连接防 DB 超时踢** | 与 maxLifetime 配合（防僵尸的主动解法） |

**两个隐藏语义**（官方 README 实证——面试点）：①**idleTimeout 的生效前提**——"only applies when minimumIdle is defined to be less than maximumPoolSize"（README:198 逐字）——**默认池（minIdle=maxPoolSize=10）下 idleTimeout 完全失效**——想让空闲回收生效，必须显式设 minIdle < maxPoolSize；②**idleTimeout 的 ±30s 抖动**——"maximum variation of +30 seconds"（README:199-201）——**不是精确到点回收**（避免同一时刻批量回收——mass-extinction 防护）。

**三个黄金规则**（07 7.1 经验值 + Hikari 官方）：①**maxLifetime < 数据库连接超时**（如 MySQL wait_timeout——官方原文："should be several seconds shorter than any database or infrastructure imposed connection time limit"——README:221-222 逐字实证——否则数据库先断，应用还在用"死连接"）；②**connectionTimeout 不能太短**（突发时误杀）也不能太长（卡死无感知）；③**keepaliveTime 主动保活**（默认 2min——定期 isValid() "ping"空闲连接——**"僵尸连接"的主动预防**）。

**池满即卡死的真相**：`connectionTimeout` 到期抛 `SQLTransientConnectionException`——**"连接池满"不是内存问题，是等待超时问题**——监控看 active/max 比率（§5）。

实验 `poolParams_experienceValues` 验证 my-xhs 参数族的语义（30s/10min/30min 的对应关系）。

## 4. my-xhs 实证：读写分离双池差异化

my-xhs 的读写分离用 **Hikari 双池**（ReadWriteRoutingDataSourceConfig.java 实证）：

| 池 | 配置 | 行号 |
|----|------|------|
| **写库（master）** | `setMinimumIdle(5)` / **`setMaximumPoolSize(20)`** / idleTimeout 30s / maxLifetime 30min / connectionTimeout 10s | :38-42 |
| **读库（slave）** | `setMinimumIdle(5)` / **`setMaximumPoolSize(10)`** / 同上 | :57-59 |

**双池差异化的理由**（知识本体）：**写库压力大于读库**（写一条影响多行 + 事务），**读库可加从库水平扩展**——**max 按角色分配**（20/10）而非一刀切（与 5.1 的 Tomcat 差异化线程数同构——**"参数是角色特征函数"**）。**隐藏细节**：my-xhs 设 minIdle=5 < maxPoolSize——**恰好满足 idleTimeout 生效前提**（§3 的"只在 minIdle < maxPoolSize 时生效"）——**配置自洽**（想用 idleTimeout 回收就必须显式拉开 min 与 max）。

**配套：驱动自动推导**（07 5.1——DataSource 配置的工程面）：`DatabaseDriver.fromJdbcUrl(url)`（Boot 官方——DatabaseDriver.java:308 实证——**从 JDBC URL 推导驱动枚举**——`jdbc:mysql://...` → MYSQL）+ `setPropertyIfAbsent` 统一填充（**缺省才补——不覆盖显式配置**）——**"显式配置优先 + 缺省推导"是配置填充的原则**（2.2 配置章节联动）。my-xhs 用 Boot 官方能力共享（07 5.1 实证——已用）。

**my-xhs 判定**：**已用（完整实证）**——五参数族全配（minIdle/max/idleTimeout/maxLifetime/connectionTimeout——:36-42/:55-60）+ **读写分离双池**（2.6 章节的机制面）；**监控面**：`hikaricp.connections.acquire/usage/creation` 指标已开（my-xhs-user application.yml:129-131——2.9 可观测性交叉）。

## 5. 连接池接入 Actuator：DataSourcePoolMetadata（13 三章）

### 自定义连接池怎么进监控

Spring Boot 的池指标通过 **`DataSourcePoolMetadata` SPI**（13 3.1——DruidDataSourcePoolMetadata:48 实证）——**任何连接池实现这个 SPI 就自动获得 Actuator 指标**：

```
DataSourcePoolMetadata（SPI——Boot 定义的"池描述"契约）
  ├── getUsage()    — 使用率（active/max）
  ├── getActive()   — 活跃连接数
  ├── getIdle()     — 空闲连接数
  ├── getMax()      — 最大连接数
  └── getMin()      — 最小空闲数
```

**"自定义连接池接入 Actuator 的标准路径"**（13 3.1 实证）——Hikari 自带实现（`HikariPoolMXBean`——**MXBean 版池指标**——5.2 的 JMX 面联动），Druid 需要自实现（微球写了 `DruidDataSourcePoolMetadata`）。

实验 `poolMetrics_usageActiveOverMax` 验证 getUsage 语义（2/20=10%——**监控里的"池健康"= usage 接近 100% 时告警**）。

**my-xhs 判定**：**已用（Hikari + Boot 官方池指标——同机制实证）**——13 3.1 标注"已用——Hikari + Boot 官方池指标（同机制）"；Druid 的自实现路径是**备选知识**（换池时要知道"新池要自己实现 PoolMetadata 才能进监控"）。

**SQL 级可观测**（13 四章——交叉）：**SQL AST 解析**——`SQLUtils.parseStatements(sql, dbType)`（SQLUtils.java:661 + 微球 AbstractStatementFilter.java:255 实证——**每条 SQL 解析成 AST 生成资源名——SQL 级可观测键**）——**连接池指标（池健康）+ SQL 级指标（语句性能）**是数据库可观测的两层：前者看"池容量"，后者看"语句慢在哪"（慢 SQL 定位——2.9 交叉）。**P2 教训（复用优先）**：13-mybatis 复用静态工具 vs 14-druid 手写 switch（fallthrough bug）——**"自写替代已有工具前先查"（复用优先原则）**。

## 6. 连接池的工程坑（缺陷家族联动）

> 可跳过（进阶级）：连接池的三个经典坑——**①maxLifetime 未配 < DB 超时**：数据库（MySQL `wait_timeout` 默认 28800s=8h——MySQL 官方文档默认值）先断空闲连接，应用拿到"死连接"——**查询突然失败 + 重启才好**（"僵尸连接"模式——排查要点：看 maxLifetime vs wait_timeout）；**②连接泄漏**：`getConnection()` 后忘 `close()`（finally 缺失）——**active 只增不减 → 池耗尽**（监控 active=max 恒久 = 泄漏实证——与 5.2 线程池泄漏同模式）；**③池大小拍脑袋**：max=1000 以为"更快"——**DB 侧连接数爆炸**（每连接 = DB 进程内存）——**"池大小是 DB 资源的函数"**。**"池健康三看"**（排障模板）：active/max 比率（容量）/ usage（压力）/ wait 次数（connectionTimeout 命中——2.9 交叉）。

## 7. 缓存性能面（交叉——2.6 的缓存三兄弟 + 5.2 JVM 面）

> 可跳过（进阶级）：缓存的性能面与连接池的对照——**①缓存是"读的池"**：连接池池化连接，缓存池化数据——**都是"复用昂贵资源"**（连接/计算）；**②缓存淘汰 = 连接回收**：LRU/LFU（2.6 的 W-TinyLFU）对应 idleTimeout/maxLifetime——**"生命周期管理"是两者的共同本体**；**③本地缓存 vs 连接池的内存面**：Caffeine（2.6）对应 Hikari（本文）——**都在 JVM 堆内（5.2 的 heap 项）**——**"数据层性能 = 连接池（本文）+ 缓存（2.6）+ GC（5.2）三面联动"**。
