# 32. 网络与 IO：Reactive 的本质与真相

> 配套实验：`spec-reactive`（4 个断言——Reactive Streams 四接口/背压/演进推导）
> 定位：**Reactive 异步服务的完整认知**——"不是更快，是更省线程"的本质 + Reactive Streams 规范 + 演进推导
> 来源：课程 stage-3-17（Reactive 异步服务——8 KP 全覆盖）+ 源码 02 八章/10 三章（序列化族谱性能面交叉——5.3 交叉）
> 前置：5.1 章节（WebFlux 双栈——本节的深化）、1.7（Reactive Streams 规范锚点）

5.1 讲了 WebFlux vs WebMVC 的线程模型；这一章讲 **Reactive 的本质**——它到底是什么、规范怎么定义、什么时候该用。最反直觉的真相：**"Reactive 不是更快，是更省线程"**（stage-3-17 的认知纠偏核心）——学完这一章，你能回答"为什么我重构了 WebFlux 却没变快"。

## 1. 认知纠偏：Reactive 的三大误解（KP-01）

### 场景

你听说"Reactive 能提升性能"，把服务重构成 WebFlux——结果 Gatling 压测**没变快甚至稍差**。为什么？

**三大误解**（docs 开篇）：①"Reactive 是异步非阻塞编程"——**半对**（是特征不是收益）；②"Reactive 能够提升程序性能"——**错**；③"Reactive 解决传统编程模型困境"——**部分**。

**官方真相**（Spring 官方原文）："**Reactive and non-blocking generally do not make applications run faster**"——收益是"**以少量固定线程和更少内存扩展（scale with a small, fixed number of threads and less memory）**，负载下更可预测地扩展"。

**JHipster 报告**（第三方实证）：MySQL/Mongo 应用 **"无速度提升（Gatling 结果甚至稍差）"** + 编码调试更复杂——**"WebFlux 尚未证明明显优于 MVC"**（2018 时点）。

**结论**：**省线程 ≠ 更快**——Reactive 收益在"**高连接/慢 IO 场景的资源效率**"（需要 latency + 混合慢不可预测网络 IO 时差异 dramatic）——**不是银弹**。**"Reactive 化之前先问：你的瓶颈是线程还是 CPU/DB？"**

## 2. 演进推导：阻塞→并行→异步→Reactive（KP-02）

### 为什么需要 Reactive——从 6 秒到 3 秒的推导

docs 用 DataLoader 系列逐步推导：

| 阶段 | 方式 | 耗时 | 问题 |
|------|------|------|------|
| ① 串行 | 逐个 load | 1+2+3=**6s** | 阻塞模式即串行执行 |
| ② 并行 | CompletionService 三任务 | max(1,2,3)=**3s** | **并行是资源换时间**（加线程引竞争） |
| ③ Future 阻塞 | 逐一 `future.get()` | **退回 6s** | 强等待从并行退回串行 |
| ④ CompletableFuture | `runAsync().thenRun().whenComplete()` | 链式 3s | 无依赖并行 + 有依赖链式 |
| ⑤ Reactive | + 背压/流式/组合 | 可预测扩展 | 解决"组合与背压" |

**核心洞察**：并行能解决"无依赖"（CompletionService），CompletableFuture 解决"有依赖链式"（thenCompose），**Reactive 补上最后一块——"背压 + 流式"**（消费速度控制生产速度）。**实验是毫秒级模拟（100/150/200ms）**——验证的是"串行总和（450）> 并行最大值（200）"的本质，docs 的 6s→3s 是同一比例关系。

实验 `evolution_serialSlowerThanParallel` 验证串行 vs 并行；`evolution_completableFutureChainsDependentSteps` 验证链式组合。

## 3. Reactive 的定义：多源共识（KP-03）

> 可跳过（进阶级）：Reactive 没有单一权威定义——**六源共识**（Manifesto/维基/Spring/ReactiveX/Reactor/@andrestaltz）抓共性：

**Reactive Manifesto 四性**：**Responsive（响应）/ Resilient（韧性）/ Elastic（弹性）/ Message Driven（消息驱动）**——系统设计宣言。**维基**：**声明式编程范式——数据流（data streams）+ 传播变化（propagation of change）**（技术连接：Java 8 Stream/Observable-Observer）。**Spring**：**reacting to change（响应变化）+ 非阻塞**（技术连接：Servlet 3.1 ReadListener/WriteListener）。**ReactiveX**：观察者模式扩展——数据/事件序列 + **操作符组合** + 屏蔽并发细节。**Reactor**：观察者/响应流/迭代器三模式 + **推（push）vs 拉（pull）**（Iterable 拉 vs Observable 推对照：next()↔onNext()/异常↔onError/结束↔onComplete）。**@andrestaltz**："异步数据流编程"——事件总线就是流。

**共性小结**：编程模型（响应式/函数式 vs 命令式）+ 设计模式（**Observer 推**）+ 数据结构（流/序列/事件）+ 并发模式（非阻塞同步/异步）——**"推 vs 拉"是 Reactive 的核心范式转换（订阅式数据消费）**。

## 4. Reactive Streams 规范：四接口 + 背压（KP-04）

### 规范本体（JDK 已内建——Flow API）

Reactive Streams 是跨语言规范，JDK9 把它内建为 **`java.util.concurrent.Flow`**（Flow.java:193/:218/:270/:301 实证——四接口 JDK 化）：

| 接口 | 职责 |
|------|------|
| `Publisher<T>` | 发布者——`subscribe(Subscriber)` |
| `Subscriber<T>` | 订阅者——`onSubscribe/onNext/onError/onComplete` 四回调 |
| `Subscription` | 信号控制——**`request(long n)` / `cancel()`** |
| `Processor<T,R>` | 两者合体（转换器） |

### 背压：request(n) 是核心信号

**背压机制**：下游在无边界流水线上消费不及上游生产时 → **传播 `request(n)` 信号限制需求（Demand）**——**"强制非阻塞背压"**（mandatory non-blocking backpressure——避免无界缓冲/内存爆炸）。

实验 `backpressure_requestN_limitsDelivery` 验证：`request(2)` 只交付 2 个——**下游控制上游速率**；追加 request(3) 再交付 3 个——**按需拉取**。实验 `backpressure_preventsUnboundedBuffering` 验证：慢消费者只 request(1)——**无界缓冲被避免**。

**对照**：**request(n) 背压 vs 无界队列**——资源可控 vs 内存爆炸——**背压是响应式流的核心价值**（订单处理场景用背压控制流量——削峰/防压垮——docs 主要内容②）。

## 5. Reactor 三核心：Mono/Flux/Scheduler（KP-05）

| 核心 | 类比 | 用途 |
|------|------|------|
| **Mono**（0-1） | 非阻塞 Optional | 点对点（单结果） |
| **Flux**（0-N） | 非阻塞 Stream | 发布者/订阅者（序列） |
| **Scheduler**（线程池选择） | 见下表 | 决定任务在哪跑 |

**Scheduler 四线程池**（docs 参数实证——选错线程池 = 资源失控）：

| Scheduler | 机制 | 适用 |
|-----------|------|------|
| `immediate()` | 当前线程 | 调试/同步上下文 |
| `single()` | 单线程（ScheduledThreadPoolExecutor core 1） | 串行任务 |
| `elastic()` | **无限制线程 + 60s 空闲回收** | **IO 阻塞任务**（弹性） |
| `parallel()` | **处理器数量线程 + 60s 空闲** | **CPU 密集**（并行） |

**关键取舍**：**elastic（无界）vs parallel（核数）**——IO 阻塞任务用 elastic（等 IO 不占 CPU）、CPU 密集用 parallel（线程数=核数）——**用反了：CPU 任务进 elastic = 线程失控**（5.2 案例二的内存面）。

> 可跳过（进阶级）：Flux 生成三件（docs 实战）——`Flux.generate`（**同步一对一 + SynchronousSink**——程序化同步发射）、`Flux.create`（异步多值——桥接回调 API）、`Flux.handle`（条件发射示例）。生产编码用它们做"业务数据 → 响应式流"的桥。

## 6. WebFlux 编程模型与使用场景（KP-06/07）

### 并发模型（官方表述）

**MVC**："假设应用可能阻塞（如远程调用）→ 容器用**大线程池**吸收阻塞" vs **WebFlux**："假设不阻塞 → 小固定线程池（event loop workers）"——**这是"更省线程"的官方表述**（5.1 的深化）。

**编程模型两形态**：注解驱动（与 MVC **API 表面相同**——@Controller/@RequestMapping——**运行时不同**）+ 函数式端点（RouterFunction——5.1 已述）。**核心组件**：`HttpHandler`（最低层契约——`Mono<Void> handle(ServerHttpRequest, ServerHttpResponse)`）+ WebHandler API 链。**动机——去 Servlet 化**：Servlet 3.1 非阻塞 API 与同步契约（Filter/getParameter）割裂 → 新通用 API（Netty 为默认运行时）。

> 可跳过（进阶级，网络栈定位）：**Netty**（WebFlux 默认运行时——骨架 §八 锚点）——**事件循环（EventLoop）模型**：少量线程处理海量连接（NIO 多路复用）——**5.1 §4 的"事件循环"就是 Netty 的 EventLoop**；reactive 栈的底层 = 应用层（WebFlux/RSocket）+ 传输层（Netty EventLoop）+ 协议层（HTTP/2、WebSocket——2.7 交叉）。**理解"Netty 一个线程服务 N 个连接"是理解 Reactive 省线程的物理基础**。

**最大陷阱**：**阻塞代码进 WebFlux**——JDBC/同步 IO 会阻塞事件循环线程（5.1 的"不使用 JDBC"纪律——my-xhs 网关注释实证）。

### 使用场景（何时该选）

**官方条件**："需要一些延迟，包括**混合慢且不可预测的网络 IO**——Reactive 开始显优势，差异 dramatic"。**反面**：JHipster 的 MySQL/Mongo 阻塞 DB 场景**无提升甚至稍差**——**阻塞数据层抵消收益**。

**选型判据**：①高并发连接（网关/入口）→ 选；②慢/不可预测 IO 混合（聚合调用/流式）→ 选；③CPU 密集/DB 密集 → 不选。

**my-xhs 判定**：**已用（混合实证）**——gateway（入口/聚合/IO 密集）已 WebFlux（GatewayApplication.java:12 注释 + starter-gateway 依赖实证——**正符合选型判据①**）；user/order（DB 密集 WebMVC）**未重构**（docs 的"用户服务 WebFlux 重构"在 my-xhs 未做——**符合判据③：DB 阻塞栈收益有限**）。**"按层选型而非运动"——gateway Reactive + 业务 DB 阻塞 WebMVC 是 my-xhs 的架构决策实证**。

## 7. RSocket：服务间响应式传输（KP-08）

> 可跳过（进阶级）：RSocket——**二进制协议**（TCP/WebSocket 传输）+ **四交互模型**（Request-Response/Request-Stream/**Channel 双向流**/Fire-and-Forget）+ **背压内建**（Reactive Streams 语义贯穿——request(n) 在服务间生效）。**docs 意图**："基于 RSocket 实现服务端 Reactive 化，利用背压重构订单处理"——**订单服务间调用（阻塞 HTTP）→ RSocket（响应式背压）**：削峰（下游 request(n) 限速）。

**选型矩阵**（服务间传输）：**RSocket（背压交互——趋势衰退）vs gRPC（HTTP/2 生态 + Triple——2.7/4.4 交叉——现代流式主选）vs Feign（HTTP 阻塞——现状）**——现代服务间调用主流仍 HTTP/gRPC，**"RSocket 衰退 → gRPC Triple"是 stage-3 现代替代映射的实证结论**——**背压思想留下来（Reactive Streams 规范），传输协议选生态（gRPC）**。

**my-xhs 判定**：**该用没用（现状合理）**——my-xhs 未用 RSocket（grep 无依赖实证）；订单为 WebMVC + **CompletableFuture 异步**（OrderService.java:478-479 `runAsync` + **自定义 MDC 线程池**——O2 修复注释"替代 CompletableFuture.runAsync 的 commonPool 丢 traceId"——**my-xhs 异步的工程化实证**）；**背压重构订单未落地**——但注意：my-xhs 已用 CompletableFuture + 自定义线程池解决了"丢 traceId"问题——**先解决可观测性，再谈背压**（2.9 交叉）。

## 8. 网络与 IO 的源码面（02 六章/八章 + 10 三章——序列化族谱交叉）

> 可跳过（进阶级，序列化聚合线的性能面 + IO 工具面——4.7 汇总族谱交叉）：

**① 定长序列化**（10 三章——AbstractSerializer 模板 + 长度前缀复合编码）在 **IO 密集场景的性能价值**：长度前缀使接收方**预分配/流式解析**（省内存）；转换方向族（02 八章）的**字符串枢纽**设计在**网络边界**（反序列化入口）的性能意义——**序列化/反序列化是网络 IO 的 CPU 面**（5.1 的 Body 缓存节联动）。

**② FastByteArray 流**（02 六章——`FastByteArrayOutputStream`——"a fast, non-thread-safe implementation of ByteArrayOutputStream" :29 实证——**无 synchronized 的字节流（非线程安全——单线程专用）**）：`ByteArrayOutputStream` 自带 synchronized（线程安全但**每次写都加锁**）——单线程 IO 场景**锁是纯开销**，去掉 synchronized 的版本更快（**性能取舍：线程安全 vs 单线程快**）。IO 工具面 2.10 章节（事件）交叉。

**③ FileWatchService**（02 六章——StandardFileWatchService:69 封装 JDK7 `WatchService`——文件/目录变更监听）：**JDK WatchService 是文件系统事件监听**（native 事件，非轮询）——配置热更新的 IO 面（2.2 配置章节的文件监听场景）。

**性能面结论**：协议设计（定长/长度前缀）决定网络边界的内存与 CPU 效率——4.7 的知识本体在 IO 面的落地。

## 本章小结

**知识本体**：Reactive 的完整认知——**真相**（不是更快，是省线程/可预测扩展——JHipster 反面实证）+ **演进**（串行→并行→CompletableFuture→Reactive——组合与背压——实验）+ **规范**（Reactive Streams 四接口——JDK Flow API + 背压 request(n)——实验）+ **Reactor**（Mono/Flux/Scheduler 四线程池——elastic vs parallel 取舍）+ **WebFlux**（并发模型/使用场景判据/阻塞陷阱）+ **RSocket**（四交互模型/服务间背压——可跳过）+ **网络与 IO 源码面**（定长/长度前缀 + FastByteArray 流 + FileWatchService——交叉）。

**一条主线**：**"先纠偏（不是更快），再学规范（四接口/背压），后定选型（判据三问）"**——**Reactive 是工具不是信仰**：瓶颈在线程（网关/聚合/慢 IO）用它，瓶颈在 DB/CPU 用它没收益。

**实验验证**：spec-reactive 4 个断言全绿（背压 2/演进 2）。

**my-xhs 判定**：网关 WebFlux 已用（判据①实证）/ 业务 WebMVC 未重构（判据③合理）/ 订单 CompletableFuture + 自定义线程池已用（可观测性优先）/ RSocket 该用没用（现状合理）/ 序列化性能面该用没用（自定义协议场景）。
