## 1. JFR：JDK 内建的生产级诊断器（stage-3-04）

### 场景

生产事故发生了，现场已经过去——怎么**事后还原**？传统方式是堆转储/线程 dump（快照，只有瞬间）。JFR 的答案是：**一直在录**——低开销环形缓冲，事件持续写入，出事后 dump 出**事故前的时间线**（"黑盒记录仪"）。

**JFR（Java Flight Recorder）三个特点**：①**低开销**（官方设计目标 <1% 性能影响——生产常驻）；②**黑盒环形缓冲**（旧事件滚动淘汰——保现场又限磁盘）；③**三用途**（性能分析/故障诊断/容量规划）。

### 激活方式（重要演进——过时处理）

**商业时代（JDK8-10）**：`-XX:+UnlockCommercialFeatures -XX:+FlightRecorder`——**要付费解锁**。**JDK11 起开源（JEP 328）**——解锁参数**已移除**，直接可用：

```
# 启动时录制（已知要录的场景——含启动期事件）
java -XX:StartFlightRecording=duration=60s,filename=myrecording.jfr MyApp

# 运行中动态启用（生产首选——事故现场后补录、零重启）
jcmd <pid> JFR.start duration=60s filename=myrecording.jfr
jcmd <pid> JFR.check      # 查看录制状态
jcmd <pid> JFR.stop       # 停止
jcmd <pid> JFR.dump       # 导出

# 退出兜底（进程退出自动保存）
-XX:FlightRecorderOptions=defaultrecording=true,dumponexit=true
```

**jcmd 动态启用是生产首选**（DCmdStart.java:55/:400 源码实证——jcmd JFR.start 语法）——**事故发生后补录，零重启**；`dumponexit` 兜底进程退出场景。**安全注意**：录制文件含命令行/环境变量机密——按堆转储级别保管。

### 录制配置（环形缓冲理念）

`maxsize`（大小 k/m/g）+ `maxage`（年龄 s/m/h/d）**双限任一达限即删**；`delay`（等 JVM 预热再录）；`compress=true`（ZIP 压缩——费 CPU 注意）；触发器（JMC 规则——堆 >100MB 自动录）。**"大小/年龄双限"就是环形缓冲的实现**——保现场又限磁盘。

### 事件模型：3 类事件 + 阈值过滤（stage-3-04 KP-02）

JFR 的数据单元是**事件**（名称/时间戳/payload/线程/堆栈/持续时间），分 3 类：**①持续时间事件**（耗时发生、完成时记录——**可设阈值只记超阈值的**——对短事件设阈值省开销）；**②即时事件**（立即发生立即记录）；**③样本事件**（固定间隔采样——可配采样频率）。**开销控制的核心 = 阈值过滤**：JFR 数据量大，**只记录需要的事件类型 + 阈值过滤**（CPU 采样 1s、锁 10ms——按场景配，阈值太高漏细节、太低开销大）。

**架构分工**（KP-03）：**JFR 运行时**（JVM 内记录引擎）+ **代理**（控制缓冲区/磁盘 IO/MBean）+ **生产者**（向缓冲区插数据：JVM/Java 应用/第三方）+ **JMC**（GUI 启动/停止/查看——飞行记录器插件）。**对比第三方工具**（async-profiler）：JFR 深度集成（看得见 GC/编译内部事件——无侵入），async-profiler 采样视角不同、可观测栈可组合。

### JFR API：业务自定义事件（把应用层打进 JVM 时间线）

```java
@Label("订单创建")
class OrderEvent extends jdk.jfr.Event {
    @Label("订单ID")
    long orderId;
    @Label("金额")
    String amount;
}
// 使用
OrderEvent event = new OrderEvent();
event.begin();
// ...业务逻辑...
event.end();
event.commit();   // 与 JVM 事件同窗分析
```

**关键模式 `shouldCommit()`**（Event.java:80/:144 源码实证）：**提交前先问"这次会不会被记录"**——不会就跳过昂贵的数据收集（**"收集数据可能昂贵"**）。**静态事件（继承 Event）快且可工具识别，优先于动态定义**（EventFactory 运行时定义——性能低）。

**三工具分工**（stage-3-04 KP-07）：**JMeter**（压测——主动制造负载）/ **JFR**（运行时录制——被动观察 JVM 内部）/ **JMH**（微基准——精确测量单点性能）。**"压测发现问题、JFR 定位原因、JMH 验证假设"**。

**my-xhs 判定**：**该用没用**——my-xhs 未启用 JFR（stage-3-04 实证）；**建议**：JVM 参数常驻录制（低开销）+ jcmd 动态启用兜底事故现场——**诊断工具是"事后补不了"的，必须提前部署**。

## 2. 生产 JVM 故障：三种典型形态（stage-3-18）

### 案例一：线程池泄漏——大量 WAITING 线程

**事故现象**：应用有大量 `ThreadPoolExecutor` 对象 + jstack 见大量 **WAITING 线程**（未命名——排障障碍）。

**成因**：`Executors.newFixedThreadPool(1)`（Executors.java:92——`ThreadPoolExecutor(1,1,0L,MILLISECONDS,LinkedBlockingQueue)`）在**方法内创建、不 shutdown** → **keepAliveTime=0 且 `allowCoreThreadTimeOut` 默认 false**（ThreadPoolExecutor:526 实证——core 线程永不超时回收）→ **core 线程永久等待 → Thread.State.WAITING**——方法每调一次漏一个池，泄漏积累。

**结构链**：`ThreadPoolExecutor → workers(HashSet<Worker>) → Worker → Thread`。

**解法（docs 明确答案）**：①排查并及时关闭；②**单例共享**（docs 划掉了"设置 Keep-Alive=60s"——**共享优于调参，调参治标**）。**"线程池单例 + 生命周期管理"是纪律**（实验 `leakedPool_keepsWaitingThreads_unlikeShared` 演示泄漏前兆）。

### 案例二：线程失控与 OOM Kill 死亡螺旋

**事故现象**：`SimpleAsyncTaskExecutor`（**非池化——每任务一个无界线程**）+ `@Async` 误用 + **无熔断** → 线程失控 → **OOM Kill → 重启 → 再失控**（死亡螺旋）。

**成因链**：非池化线程池**无界**（创建即线程，无上限）+ @Async 每个调用都开线程 + 无熔断（服务挂了照调）→ **"失控的循环"**。

**my-xhs 正确对照**：my-xhs 的异步是**池化**（线程池共享 + 命名——排障第一线索）。**"线程名是排障第一线索"**（stage-3-18 KP-02——未命名线程 = 排障障碍）。

### 案例三：线程池拒绝策略（docs 空节发散）

线程池满 + 队列满 → **拒绝**。四种策略：`AbortPolicy`（默认——抛异常）/`CallerRunsPolicy`（**调用者线程执行**——天然背压）/`DiscardPolicy`/`DiscardOldestPolicy`（静默丢弃——**生产慎用**：失败不可见）。**"拒绝"是线程池的最后防线**——配合监控（拒绝计数——2.9 可观测性交叉）。

**诊断工具链**（stage-3-18 KP-02）：`jstack` 抓多份时间点快照 → fastthread.io 在线分析（线程状态分布）→ 定位可疑线程。**快照看状态分布，Arthas 在线看栈详情**。

### 内存全景：JVM 进程的 10 项分布（stage-3-18 KP-05/06——案例一核心）

**事故现象**：top 显示进程占 600MB，但 JVM 内部算出来只有 319MB——**"600M 之谜"**。答案：**JVM 进程内存 ≠ 堆**——10 项分布：

| 内存项 | 限制 | 排障要点 |
|--------|------|---------|
| **heap** | -Xmx | 唯一被 -Xmx 限制的 |
| **class**（元空间） | MaxMetaspaceSize/CompressedClassSpaceSize | 类加载泄漏 |
| **thread**（线程栈） | -Xss/线程数（**总大小无限制**） | **线程失控的内存面**（§2 案例二联动） |
| **code**（JIT 代码） | ReservedCodeCacheSize | 动态生成类/代理多 |
| **gc**（GC 结构） | **G1 最多堆 10% 额外、ZGC 15-20%——不受限** | GC 选型的隐藏成本 |
| compiler/internal/symbol | 常量池（StringTableSize） | — |
| **Native Memory Tracking** | 采集本身开销 | 排查用的"尺子" |
| Arena Chunk | — | 分配器细节 |

**工具**：`-XX:NativeMemoryTracking=summary` 启动 + `jcmd pid VM.native_memory summary`——**committed = 实际使用**。

**保留/提交模型**（KP-06——核心认知）：OS 内存两阶段——**保留（reserve：预留连续虚拟地址）→ 提交（commit：映射物理内存）**——**`-Xmx` 只是保留上限，实际占用看 committed**。**top 的 RSS（进程视角）≠ JVM 的 committed（JVM 视角）**——差值排查面：线程数（-Xss×线程数）/元空间/GC 结构（G1 堆 10%）/DirectBuffer。

**排障实证**（docs）：`arthas vmtool --action forceGc` 强制 Full GC **不能减少进程内存占用**——**内存不在堆内**（堆外/线程栈/GC 结构嫌疑）——**"看内存占用看 committed 不是 -Xmx"**。实验 `directBuffer_outOfHeap_notCountedInHeapLimit` 验证：64MB DirectBuffer 分配后**堆占用几乎不变**（堆外——但增加进程 RSS——NMT 才能看清）；`threadStack_memoryNotBoundedByXmx` 验证线程栈不受 -Xmx 约束。

**my-xhs 判定**：**已用（实证）**——my-xhs 异步是池化 + 命名（`@Async` 配自定义线程池）；**该用没用**——JFR/线程 dump 的常规演练未沉淀 + **NMT 未启用**（-XX:NativeMemoryTracking=summary——600M 之谜这类排障需要它）；**知识本体**：三大事故模式（泄漏/失控/拒绝）+ **内存 10 项分布**是排障模板——**"先识别模式，再定位代码"**。

### 强封装与反射受限（JEP 396/403——4.7 章节的根源）

JDK9 起模块封装，**JDK16（JEP 396）+ JDK17（JEP 403）强封装 JDK 内部**：`sun.misc.Unsafe` 等内部 API **默认不可反射访问**（`trySetAccessible()` 返回 false——实验 `strongEncapsulation_blocksJdkInternals` 验证：`ClassLoader.classes` 字段反射受限 + `sun.reflect.Reflection` 已不可见）。**"反射读 JDK 内部"从"后门"变成"非法"**——4.7 的演进替代图谱就是这条主线的展开。

### 对生态的影响

现代 Java 演进直接决定框架写法：模块化 → 反射受限 → **框架必须提供显式扩展点**（4.3 SPI）/Record/Sealed → 数据模型范式（my-xhs 的 DTO 实践）/虚拟线程 → **线程池模型再思考**（5.1 对照——虚拟线程是"每请求一线程"的轻量版，阻塞模型下不再怕线程耗尽）。

**my-xhs 判定**：**已用（JDK17 LTS 标准栈）**——var 使用实证（stage-3-33 核对：6 文件）、G1+MaxGCPauseMillis（start-all.sh:30-34）、Record/Sealed 待扩展；**迁移评估**：21 的**虚拟线程**是**高价值迁移点**（高并发演进——stage-3-33 KP-08 实证决策待定）。

## 4. Native 三路径：从 JIT 到 AOT（stage-3-28/31/32）

### 背景：JIT vs AOT

**JIT（Just-In-Time）**：运行期热点编译——启动慢（预热）+ 运行快（**Graal JIT——用 Java 写的 JIT 编译器**——4.4 章节的 GC 演进主线衔接）。**AOT（Ahead-Of-Time）**：编译期原生镜像——**启动快 + 内存小 + 无反射动态性**。GraalVM 生态（stage-3-28）：高性能 JDK + **Truffle 语言实现框架**（polyglot 互操作——JVM 上跑多语言）+ Native Image。

### 三路径全景（stage-3-32 KP-03 Native 组收官）

| 路径 | 本质 | 现状 |
|------|------|------|
| **GraalVM Native Image**（stage-3-28） | AOT 编译成原生可执行文件 | 启动毫秒级/内存小/**Metadata 配置繁琐**（reflect-config/resource-config/proxy-config——**反射/代理/资源的"清单化"**） |
| **Spring Native**（stage-3-31） | Spring AOT 处理（**编译期应用分析**——静态化 Bean 定义/条件评估） | 解决"Spring 动态性 vs Native 静态性"矛盾 |
| **Java Native**（stage-3-32） | Project Leyden（AOT 演进方向——官方路线） | 进行中——JDK 官方吸收 AOT |

### 关键矛盾：动态性 vs 静态性

**Native 的代价是失去"运行期魔法"**：反射/动态代理/动态类加载在原生镜像里**都不存在**——所以必须**Metadata 清单化**（**把运行期会反射的类/方法/代理提前声明**）。**Spring AOT 处理**（Spring Native——编译期分析应用：Bean 定义/条件评估/代理接口——**把 Spring 的"运行期魔法"翻译成编译期事实**）。

**动态代理两形态**（stage-3-31 KP-02）：**JDK 动态代理**（接口代理——反射调用）vs **字节码动态代理**（类代理——CGLIB/ASM 生成子类）——**Native 下两形态都需要 proxy-config 声明**（5.1 的静态/动态代理对照在 Native 面）。

**现代 Java 对 Native 的回应**：**JDK 官方吸收 AOT 方向**（Project Leyden）——**"Native 是方向，但 Metadata 成本是门槛"**（stage-3-32）。

**my-xhs 判定**：**不该用（现状）**——my-xhs 是 JDK17 标准栈（stage-3-32 KP-04 实证——无 Spring Native）；**知识本体**：Native 三路径的**取舍地图**（启动/内存收益 vs Metadata/动态性成本）——评估任何"Native 化"项目的决策框架。

## 本章小结

**知识本体**：JVM 的完整图景——**诊断**（JFR——黑盒环形缓冲/**3 类事件 + 阈值过滤**/jcmd 动态启用/shouldCommit/三工具分工——实验）+ **故障**（三案例：线程池泄漏/线程失控 OOM 螺旋/拒绝策略 + **内存 10 项分布 + 保留/提交模型**——实验）+ **演进**（Java 9-21 语言/API/JVM 三主线 + 强封装 JEP 396/403——实验）+ **Native 三路径**（JIT vs AOT/GraalVM/Spring AOT/Leyden——Metadata 成本）+ **演进归组替代表**（JVM 机制面 × JDK 替代——01 六章主落位 + MethodHandle 探测）。
