# 30. 容器与服务端：性能优化的第一战场

> 配套实验：`spec-container`（5 个断言——Tomcat 并发/静态 vs 动态代理/Filter 链缓存/双栈模型）
> 定位：**维度五开篇**——"进程外（容器）→ 进程内（JVM）→ 框架层（装配/代理）"的性能优化三面之首
> 来源：课程 stage-3-05（服务容器调优）+ stage-1-21（Spring Web 性能）+ stage-1-22（Spring Cloud 性能）+ stage-3-13（Reactive 栈）+ 源码 09 二章（Filter 链缓存）
> 前置：2.7 章节（网关——Filter 链的消费面）、4.6（代理模式）、1.2（Servlet 生命周期）

你的服务上线后性能差，第一反应调什么？**不是代码，是容器**——Tomcat 线程池、请求队列、连接参数，这些**进程外**的参数往往比业务代码优化见效更快（TPS 立涨）。这就是"容器调优"的定位：**性能优化的第一战场**。

这一章讲容器与服务端的完整优化面：Tomcat 并发参数（进程外）、静态代理 vs 动态代理（框架层）、Filter 链缓存（框架层）、WebMVC vs WebFlux（架构层）——从外到内、从易到难。

## 1. Tomcat 并发参数：线程池与队列的平衡（stage-3-05）

### 场景

请求打进来了，Tomcat 怎么安排？**线程池（threads）+ 等待队列（accept-count）+ 连接数（max-connections）**三件套：

```
请求 → max-connections（连接上限）
  → 有空闲线程？→ 直接处理
  → 线程满？→ 进 accept-count 队列等待
  → 队列也满？→ 拒绝（connection refused）
```

**核心参数**（Tomcat 默认/经验值）：

| 参数 | 含义 | 默认 | 影响 |
|------|------|------|------|
| `threads.max`（源码 `maxThreads`——AbstractEndpoint.java:794 默认 200） | 最大工作线程数 | 200 | **并发上限**——超了就排队 |
| `threads.min-spare` | 最小空闲线程 | 10 | **预热**——突发前先备好 |
| `accept-count` | 等待队列长度 | 100 | **兜底**——线程满时排队的容量 |
| `max-connections` | 最大连接数 | 8192 | 连接层上限（与线程数解耦——连接可多于线程，排队等线程） |
| `connection-timeout` | 连接超时 | 60s | 防慢客户端占资源 |
| `keep-alive-timeout`/`max-keep-alive-requests` | 长连接保持 | 5s/100 | **HTTP/1.1 复用**——减少 TCP 建连开销 |

**关键理解**：**线程数 ≠ 连接数**——连接可以多（8192），但处理线程有限（200）——多出来的连接**进队列等待**，不是拒绝（实验 `tomcatQueue_absorbsBurstBeyondThreads` 验证：300 突发，200 线程 + 队列兜底，不直接拒绝）。**"队列兜底"就是 Tomcat 的背压**：宁可排队，不可丢弃。

> **调优优先级实证**（stage-3-05 KP-08 测试数据解读——5 组三变量组合）：Tomcat 线程 200→500 **+9%**、Hikari 池 8→80 **+19%**、G1→ZGC **+427%**——**GC 选型是最大变量，线程数/连接池是小幅增益**。**口径警示**：Shopizer 单机小数据、TPS 定义未注明——结论方向可参考（ZGC 低延迟场景吞吐优势），绝对值不可比较。**优先序：先选对 GC/框架（架构级），再微调线程/池（参数级）**。

### my-xhs 的差异化实证（三特征分类）

my-xhs 的 Tomcat 配置不是一刀切（gateway application.yml:8-9 注释实证）：

```
Tomcat 线程数按服务特性差异化：网关(入口,IO密集)=300, 库存(锁竞争)=100, 支付(等回调)=100, 其他=150
```

**分类逻辑**（知识本体）：**IO 密集（网关）→ 线程多**（等网络响应不占 CPU，线程可多开）；**锁竞争（库存）→ 线程少**（线程多了全在抢锁，反而降吞吐）；**回调等待（支付）→ 线程少**（等第三方回调是纯等待）。**线程数是"工作负载特征"的函数，不是越大越好**。

**my-xhs 判定**：**已用（实证）**——gateway `max: 300/min-spare: 30/accept-count: 100/max-connections: 8192/keep-alive 参数全配`（my-xhs-gateway application.yml:1-13）；user `max: 150/min-spare: 15`（差异化）；JVM 侧 G1 + `MaxGCPauseMillis=200`（start-all.sh:30-34——G1 选型实证，5.2 章节详述）。**配置本身是决策文档**——"为什么网关 300、库存 100"比数字更重要。

## 2. 静态代理 vs 动态代理：性能与灵活性的取舍（stage-1-21）

### 场景

Spring AOP 的 `@Transactional`/`@Cacheable`/自定义注解，靠的是**动态代理**（运行期生成代理类）。动态代理的开销：**代理创建 + 方法调用走反射**。对高频 Web 接口，能不能**不用代理就完成拦截**？

**答案是 WebMVC 的 `HandlerInterceptor`（静态代理）**——微球的思路（stage-1-21 KP-05）：**用 WebMVC 机制替代部分 AOP**。

| | AOP 动态代理 | WebMVC HandlerInterceptor（静态） |
|---|---|---|
| 生成时机 | 运行期动态生成代理类 | 编译期就定了（Servlet 规范标准组件） |
| 调用开销 | 反射调用（Method.invoke） | 直接方法调用 |
| 可调试性 | 代理栈难读 | 显式、可断点 |
| 适用面 | 任意 Bean（事务/缓存/切面） | Web 请求链（HandlerMethod 级） |
| 结论 | 通用但重 | **Web 场景够用且轻** |

微球的实现：`MethodHandlerInterceptor`（仅处理 HandlerMethod）+ `DelegatingMethodHandlerInterceptor`（委派门面——按 HandlerMethod 关联的 Method 查找对应拦截器）+ `AnnotatedMethodHandlerInterceptor`（按方法注解拦截）。

实验 `staticProxy_vs_dynamicProxy_sameResult` 验证两种代理业务结果一致（差异只在开销与调试性）；`dynamicProxy_interfaceOnly` 验证 JDK 动态代理只能代理接口（类代理需 CGLIB/字节码）。

**同族：Web 组件优化**（stage-1-21 KP-06/07）——①**减少非必需 AOP 代理**：用 WebMVC 机制（拦截器/事件）替代不必要的 AOP（`HandlerMethodArgumentsResolvedEvent`——参数解析后事件，参数列表存 ServletRequest 上下文复用）；②**Body 序列化缓存**：`StoringRequestBodyArgumentAdvice`（微球 webmvc 包——RequestBodyAdviceAdapter.java:17 抽象适配器 + 缓存请求体）——**序列化/反序列化是资源消耗操作**，请求/响应 Body 缓存减少重复计算。

**对照**：事务/缓存这种"任意方法级"的拦截，AOP 无可替代（4.5 章节的 BPP/切面）——Spring 的 `TransactionInterceptor`（spring-tx:55 implements MethodInterceptor）和 `CacheInterceptor`（spring-context:46/:50 invoke 织入）就是动态代理的典型实例；但 **Web 请求链的拦截（鉴权/日志/限流）用 HandlerInterceptor 就够了**——**先问"拦截的粒度"再选机制**。

**my-xhs 判定**：**已用（混合）**——my-xhs 既有 AOP（事务——CommentService.java:77/:221 `@Transactional(rollbackFor)` 实证）、也有 WebMVC/Servlet 拦截器（鉴权——`GatewayAuthTrustFilter extends OncePerRequestFilter` 实证——Servlet Filter 非 AOP）；**静态代理优先的思路可借鉴**：新拦截需求先评估"能否用容器级机制（Filter/Interceptor）实现"，不行才上 AOP。

## 3. Filter 链缓存：高并发网关的性能开关（源码 09 二章）

### 场景

网关每个请求都要**重新组装 GlobalFilter 链**——从路由表查 filters、排序、构建链对象。高并发下这是**每次请求的重复计算**。微球的优化：**链构建一次，缓存复用**（09 二章）：

**`CachingFilteringWebHandler`**（覆写官方 `FilteringWebHandler`）：`ConcurrentHashMap<routeId, GatewayFilter[]>` 缓存**每个路由的 Filter 链**（:66）+ `@EventListener(RefreshRoutesResultEvent)` **路由变更才重建**（:79-80——事件驱动失效——2.10 的事件化模式）+ `BeanDefinitionRegistryPostProcessor` **Bean 定义级替换官方 Bean**（:39——4.5 的扩展点机制）。

```
请求 → routeId → 缓存命中？→ 直接用缓存的链（O(1)）
                → 未命中 → 构建链 → 缓存 → 后续复用
                → 路由变更事件 → 缓存重建（失效再构建）
```

实验 `filterChainCache_buildsOnce_andRebuildsOnEvent` 验证：同 routeId 只构建一次（buildCount=1），事件触发才重建。

**三个坑（缺陷家族——必看）**：**G7** 空链吞请求（DefaultGatewayFilterChain:58 empty()——缓存未建立窗口无响应——**"缓存未就绪=无服务"**）；**G8** 反射读私有字段（:122——4.7 §9 详述）；**G9** dispose 阻塞（:89-93——Redis 路由仓库消费不完整）。

**my-xhs 判定**：**已用（实证——2026-08-15 核实）**——my-xhs 网关**已实现 Filter 链缓存**（`my-xhs-gateway/handler/CachingFilteringWebHandler.java:36` `ConcurrentHashMap` + `:58` `computeIfAbsent` 构建一次 + `:71-73` `@EventListener(RefreshRoutesResultEvent)` 路由变更重建——**与源码 09 模式同构，且规避了 G8 坑**：直接继承/重写官方逻辑而非反射读私有字段）；**"缓存 + 事件重建"是通用模式**（任何"组装开销大 + 变更低频"的资源都适用——2.2 热更新三种粒度的框架层变体）。

## 4. WebMVC vs WebFlux：阻塞与响应式（stage-3-13）

### 场景

Spring Web 两栈之争：**WebMVC（Servlet 阻塞）vs WebFlux（Reactive 非阻塞）**。核心认知（stage-3-13 的命题）：**"Reactive 不是更快，是更省线程"**。

| | WebMVC（阻塞） | WebFlux（响应式） |
|---|---|---|
| 线程模型 | **每请求一线程**（线程池有限——耗尽即拒绝） | **事件循环**（少量线程处理海量请求） |
| 处理模式 | 阻塞式（等 IO 就占线程） | 事件流（onSubscribe/onNext/onComplete——不占线程） |
| 适用 | 传统业务（数据库/同步调用多） | 高并发 IO 密集（网关/代理） |
| 背压 | 队列兜底（拒绝/等待） | **背压机制**（消费速度控制生产速度） |
| 上手 | 简单（同步思维） | 陡（Reactive 思维 + 调试难） |

实验 `servletStack_threadsLimited_reactiveStack_noThreadPerRequest` 验证核心差异：Servlet 栈单线程被慢请求占用后第二个请求**直接拒绝**（503）；Reactive 栈的事件流处理**不占线程**。

**WebFlux 的处理链**（stage-3-13 KP-03 源码实证）：`WebHandler`（基础链接口——WebHandler.java:35）→ `DispatcherHandler`（WebFlux 前端控制器——**Reactive 版的 DispatcherServlet**，DispatcherHandler.java:72 implements WebHandler + :142 handle 全异步）→ 控制器返回 Publisher（**Reactor**：Mono/Flux 响应式流）→ 背压传播 → Netty 事件循环写回。**阻塞调用（JDBC/同步 IO）会阻塞事件循环线程**——WebFlux 中阻塞操作必须换线程池或用响应式驱动（my-xhs 网关注释"不使用 JDBC"即此纪律）。

**第二形态：函数式端点**（stage-3-13 KP-04——**两栈共有**）：`RouterFunction`（路由表：谓词 → 处理器）替代注解映射——**webflux 版（RouterFunction.java:36）+ webmvc 版（RouterFunction.java:35）都有**——函数式端点是注解之外的统一第二形态（`HandlerFunction` 处理请求返回 Mono/Flux）。**注解 vs 函数式**：声明式分散 vs 组合式集中（`RouterFunctions.route().GET()...`）——网关/API 组合场景友好（SCG 的 RouteLocator 即函数式风格）。

**关键认知**：**WebFlux 适合"IO 密集 + 少量计算"的网关/代理层**（等下游响应不占线程）；**业务服务（大量 DB/缓存同步调用）用 WebMVC 更简单**——**"响应式不是银弹，是省线程的武器"**（stage-3-13 KP-01）。

**my-xhs 判定**：**已用（混合实证）**——gateway 是 **WebFlux**（GatewayApplication.java:12 注释"基于 WebFlux 的响应式网关，不使用传统 WebMVC 和 JDBC"实证——网关入口高并发 IO 密集用响应式）；**业务服务全部 WebMVC**（user/cart 等——DB 同步调用为主）。**"网关响应式 + 业务阻塞"是 my-xhs 的架构决策实证**——两栈各取所长。

## 5. Spring Cloud 层优化：RefreshScope 与 Feign（stage-1-22）

> 可跳过（进阶级）：Spring Cloud 的容器级优化面——**①@RefreshScope 的坑**（自定义 Scope → AOP 代理 → 方法调用反射开销 + 仅 destroy 不重新 initialize——配置 Bean 场景远不如 `ConfigurationPropertiesRebinder`，stage-1-22 KP-01/03——2.2 配置章节的热更新对照）；**②Feign 序列化/传输优化**（`SpringEncoder`（HttpMessageConverter 适配——Feign 序列化扩展点）→ Jackson 替代 FastJSON；`feign.Client` SPI 换底层 HTTP 客户端（OkHttp3/HttpComponents）——4.8 的"接口+可替换实现"在 Feign 的实例 + 消息压缩 + 超时合理设置，stage-1-22 KP-04/05）；**③负载均衡计算消耗**（Ribbon 的 ServerListUpdater 非远程获取、无 zone 不用 ZoneAwareLoadBalancer——**Ribbon 已过时**，现代 Spring Cloud LoadBalancer 更简单——2.3 章节交叉，stage-1-22 KP-06）；**④失效 Bootstrap 上下文**（`spring.cloud.bootstrap.enabled=false`——Bootstrap 基于 `BootstrapApplicationListener`（BootstrapApplicationListener.java:77 监听 ApplicationEnvironmentPreparedEvent）创建独立 bootstrapServiceContext——**弊端**：事件多上下文重复传播 + 配置优先级过高难排查 + 增加启动时间——新版本默认失效，stage-1-22 KP-07）；**⑤System Properties 读取优化**（Spring Environment 的 systemProperties 源（StandardEnvironment.java:61）——底层 Hashtable 同步有并发消耗——可在 ApplicationEnvironmentPreparedEvent 阶段替换该 PropertySource 避免锁阻塞，stage-1-22 KP-08）。知道方向即可，细节在 2.2/2.3/4.8 章节交叉。

## 本章小结

**知识本体**：容器与服务端的优化工具箱——**Tomcat 并发三件套**（线程池/队列/连接——"队列兜底 = 背压"）+ **调优优先级实证**（GC 选型是最大变量 +427%，线程/池是小幅增益）+ **静态 vs 动态代理**（WebMVC HandlerInterceptor 替代 AOP + Body 序列化缓存/Web 组件优化）+ **Filter 链缓存**（构建一次 + 事件重建——G7/G8/G9 三坑）+ **双栈选型**（WebMVC 阻塞 vs WebFlux 省线程 + DispatcherHandler 处理链 + 函数式端点）+ **Spring Cloud 层**（RefreshScope 坑/Feign 优化/Bootstrap 失效/System Properties——可跳过）。

**优化顺序方法论**（stage-3-05 KP-01）：**进程外（Tomcat 参数——见效最快）→ 框架层（代理/缓存——TCO 高）→ 架构层（双栈——根本性但成本高）**——**先调容器，再调代码，最后才是重构架构**。

**实验验证**：spec-container 5 个断言全绿（Tomcat 队列 1/代理 2/Filter 缓存 1/双栈 1）。

**my-xhs 判定**：Tomcat 差异化已用（三特征分类实证）/ 双栈混合已用（网关 WebFlux + 业务 WebMVC）/ 静态代理思路已用（AOP + Web Filter 混合）/ **Filter 链缓存已用**（CachingFilteringWebHandler 实证——2026-08-15 核实）/ RefreshScope 该用没用（Rebinder 替代）/ lab：performance-lab 关联（JMH + 虚拟线程面）。
