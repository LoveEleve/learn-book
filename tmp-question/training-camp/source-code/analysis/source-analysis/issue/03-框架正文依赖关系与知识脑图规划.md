# 框架正文依赖关系与知识脑图规划

> 目标：把 Spring 生态 32/33 个仓库、阶段与域之间的前置依赖、复用关系、对照关系和正文写作顺序统一起来，为后续知识脑图提供稳定输入。
> 说明：这里记录的是“正文理解依赖”，不是简单 import 图；源码 import 图只作为验证证据之一。

## 一、依赖边类型

### HARD

没有前置概念就无法理解当前正文主线，必须先完成前置域，或在当前篇补齐最小前置。

### SOFT

当前篇可局部解释，但前置域能显著降低认知成本；可作为双链，不阻塞正文。

### NAV

只做导航，不提前使用后置域结论；常用于篇末 OUT 桥和未来框架。

### COMPARE

两个框架/域存在设计对照，但没有正文先后依赖。

### CONSUMES

当前框架消费另一个框架输出的 API、协议、配置或运行时能力；不等于必须读完对方全部源码。

## 二、全局正文执行阶段

根据 `issue/源码分析执行计划.md`，正文写作阶段仍按依赖优先，而不是按“最近规划完成”排序：

```text
阶段 1 基础 I/O
  Netty → Tomcat

阶段 2 核心容器
  Spring Framework → Spring Boot

阶段 3 数据与存储
  HikariCP → Druid → MyBatis/MyBatis-Plus → Redis → Redisson → Elasticsearch

阶段 4 消息与事务
  RocketMQ → Kafka → ZooKeeper → Seata → Curator → SofaJRaft

阶段 5 RPC 与治理
  Feign → Dubbo → gRPC → Spring Cloud Commons/Gateway/OpenFeign
  → Spring Cloud Alibaba → Nacos → Sentinel

阶段 6 可观测与运维
  Micrometer → Micrometer Tracing → SkyWalking → XXL-Job → Arthas → ShardingSphere
```

重要约束：

- 已规划完成不代表可以跳过前置阶段直接写
- 其他 AI 正在进行的框架不接手、不并行、不修改
- 若阶段内拓扑与原始计划冲突，以已验证的框架 handoff/plan 为准
- 每次切换框架前，先做冲突审计和状态审计

## 三、已验证的主要跨框架依赖

### 阶段 1/2 基座

- `Netty` `CONSUMES` `Tomcat/其他网络适配器`：网络传输与事件模型作为外围能力
- `Spring Framework` `HARD` `Spring Boot`：Boot 自动装配建立在 Spring 容器/环境/Bean 生命周期上
- `Spring Framework` `COMPARE` `Netty/Tomcat`：容器抽象与网络容器实现对照

### 数据与存储

- `HikariCP` `CONSUMES` `Spring Boot` DataSource 自动配置
- `Druid` `COMPARE` `HikariCP`：连接池并发/维护/监控设计对照
- `MyBatis-Plus` `CONSUMES` `MyBatis`：MP 依赖 MyBatis 执行/映射内核
- `MyBatis` `CONSUMES` `HikariCP/Druid`：Executor/JDBC 运行时消费 DataSource
- `Redisson` `CONSUMES` `Redis` 协议/数据结构/命令能力
- `Elasticsearch` `COMPARE` `Redis/Kafka`：分布式索引/日志/持久化路径对照

### 消息与一致性

- `Kafka` `COMPARE` `RocketMQ`：日志、复制、消费组、事务/消息语义对照
- `ZooKeeper` `HARD` `Curator`：Curator 封装 ZK session/watch/node 协议
- `SofaJRaft` `COMPARE` `ZooKeeper`：Raft 与 ZAB 一致性/选举/复制对照
- `Seata` `CONSUMES` `SofaJRaft`：当 Seata 的 RAFT 会话/协调实现接入 SofaJRaft 时建立消费边
- `Seata` `CONSUMES` `RocketMQ`：消息事务/异步提交对照需以实际模块使用为证

### RPC 与治理

- `Feign` `CONSUMES` `Spring Framework` HTTP/编码抽象
- `Spring Cloud Commons` `CONSUMES` `Spring Framework` 容器/环境/事件/负载均衡抽象
- `Spring Cloud Gateway` `CONSUMES` `Spring Cloud Commons` discovery/load-balancer 能力
- `Spring Cloud OpenFeign` `CONSUMES` `Feign` + `Spring Cloud Commons`
- `Dubbo` `COMPARE` `Feign/gRPC`：代理/协议/集群容错对照
- `gRPC` `COMPARE` `Netty`：HTTP/2 transport 与 channel/event loop 对照
- `Spring Cloud Alibaba` `CONSUMES` `Nacos`：服务注册/配置中心；`CONSUMES` `Sentinel`：流控/熔断/网关治理
- `Nacos` `COMPARE` `ZooKeeper`：命名/配置/一致性/健康检查对照
- `Sentinel` `CONSUMES` `Spring Cloud Alibaba` 适配层；`Sentinel` 与 Gateway/Dubbo/gRPC 建立适配器对照边

### 可观测与运维

- `Micrometer Tracing` `CONSUMES` `Micrometer` observation/meter 生态
- `SkyWalking` `COMPARE` `Micrometer/Micrometer Tracing`：agent/instrumentation/trace pipeline 对照
- `Arthas` `CONSUMES` `JVM/OpenJDK` 诊断接口；与 SkyWalking 建观察方式对照
- `async-profiler` `CONSUMES` `JVM/OpenJDK` runtime/JVMTI/perf 能力；与 Arthas 建采样 vs 插桩对照
- `XXL-Job` `COMPARE` `Spring` 任务/执行器生命周期，不建立 Spring 硬前置，除非具体集成篇需要
- `ShardingSphere` `CONSUMES` `MyBatis/JDBC` 语义与数据源能力；与读写分离/加密/分片插件形成域内图

## 四、域内依赖表达规则

每个框架的 `PLAN`/`outline` 应声明：

```yaml
id: sentinel.s5-node-statistic
hard_prerequisites:
  - sentinel.s2-entry
soft_prerequisites:
  - sentinel.s1-slotchain-spi
consumes:
  - sentinel.s2-entry.Entry.exit
outbound:
  - sentinel.s3-flow
compare:
  - spring-cloud-alibaba.A-6
status: planned|draft|reviewed|published
```

- `hard_prerequisites` 必须位于当前正文之前
- `outbound` 只能是已规划/已存在的目标，不提前借用其未验证结论
- `compare` 不改变正文执行顺序
- `consumes` 必须写清消费的是接口、协议、配置还是运行时行为

## 五、知识脑图节点模型

### 节点

```text
id: <framework>.<domain>.<article>
title: <article title>
framework: <framework>
stage: <stage>
status: outline|draft|reviewed|published
source_version: <version>
```

### 边

```text
from: <node id>
to: <node id>
type: HARD|SOFT|NAV|COMPARE|CONSUMES
reason: <reader dependency or design relationship>
evidence: <plan/handoff/source/test reference>
```

## 六、正文开写前的全局检查

- [ ] 当前框架没有其他 AI 进行中产物
- [ ] 当前阶段顺序已在执行计划中确认
- [ ] 前置框架的规划/正文状态真实可查
- [ ] 当前域的硬前置已经 reviewed
- [ ] 本篇没有把后置域当作事实前提
- [ ] 横向对照已标为 COMPARE，而非硬依赖
- [ ] 每个 OUT 桥都指向真实节点
- [ ] 新发现依赖会回填框架 plan 和全局图谱
- [ ] 依赖图没有未解释的环
- [ ] 文章完成后更新节点状态与证据

## 七、当前状态口径

- `Sentinel`：域规划已收束，正文尚未开始
- `XXL-Job`：域规划已收束，正文尚未开始
- `ShardingSphere`：域规划已收束，正文尚未开始
- `SkyWalking`：存在其他 AI 进行中产物，不接手、不并行
- `Micrometer/Micrometer Tracing`：已有阶段级规划与闭环
- `Arthas/async-profiler`：已有知识规划，属于其他既有工作流边界

正文阶段的下一动作必须由执行计划和冲突审计共同决定，不能由“哪个目录刚刚更新”决定。
