# 框架源码正文写作方法论

> 适用范围：Spring 生态及其 32/33 个框架的源码分析正文。
> 当前阶段：框架域规划已逐步收束，正文写作尚未统一启动。

## 一、正文写作不是大纲扩写

已有的范围规划、Pass1、Pass2、completeness、outline、review-notes 是事实与结构准备，不应直接拼成正文。

正文必须把：

```text
源码事实 → 读者困惑 → 失败方案 → 设计取舍 → 实现证据 → 可迁移结论
```

组织成完整文章，而不是按包目录或函数调用顺序翻译源码。

## 二、正文前置依赖

### 事实依赖

- 当前框架的域规划已经完成
- 目标域有 Pass1/Pass2/completeness/outline/review 产物
- 关键类名、方法名、默认值、数字和行号已经重新验证
- 代码块来源可以回到当前源码版本
- 已知版本差异和未验证边界已记录

### 机制依赖

- 当前域的硬前置域已经完成规划或正文
- 当前正文不把后置域的未验证结论当作前提
- 复用域必须明确复用什么：接口、协议、数据结构、生命周期或设计模式
- 跨框架引用必须标记为对照或消费关系，不自动升级为硬依赖

### 认知依赖

写作前必须明确：

1. 读者真正卡在哪里
2. 本篇的一句话顿悟是什么
3. 哪些概念必须先建立
4. 哪些代码细节会打断主线
5. 读者读完后能解释什么生产现象或设计取舍

## 三、三步正文流程

### 第一步：素材提取

从域规划产物中提取事实卡片：

- 入口与出口
- 调用链
- 状态机/线程/时序
- 关键字段与常量
- 失败路径
- 并发与资源生命周期
- 版本演进
- 测试/实验/日志证据

事实卡片是证据库，不是文章目录。

### 第二步：理解路径设计

每篇正文写作前单独产出篇级规划，至少包括：

- 一句话困惑
- 一句话顿悟
- 硬/软/导航前置依赖
- 失败方案推演
- 章节理解顺序
- 误解清单
- 证据清单
- 版本边界
- 下一篇桥接
- 目标字数

没有篇级理解路径，不进入正文。

### 第三步：叙事写作

正文按以下主线推进：

```text
问题/场景
  → 直觉方案
  → 方案失败
  → 核心设计
  → 角色/数据流/状态机
  → 源码证据
  → 边界与代价
  → 悬念回收
  → 下一篇桥接
```

## 四、单篇文章硬规则

### 1. 先角色和问题，再类名和字段

每节优先回答：

- 谁在什么场景下行动
- 它想解决什么问题
- 为什么简单方案不够
- 当前设计承担了什么代价

### 2. 代码只能当证据

- 代码块必须来自当前源码
- 行号写作时重新 grep/sed
- 单段代码尽量不超过 30 行
- 删除无关模板、日志和样板
- 代码前说明观察目的，代码后说明证明结论
- 删除所有代码后，文章主线仍然成立

### 3. 每个机制都回答四问

1. 谁在什么场景下触发？
2. 一步一步做了什么？
3. 缺席或失败会怎样？
4. 为什么不选更简单的方案？

### 4. 必须包含失败方案

每篇至少推演一个直觉但不可行的方案；核心机制篇建议至少两个，并说明失败原因和当前设计的取舍。

### 5. 构造与运行时分离

- 构造/装配篇深讲注册、初始化、SPI、Bean/模块创建
- 运行时篇深讲请求/任务/消息/事务执行
- 只通过必要桥接连接两者，不来回跳跃打断主线

## 五、文章长度和反偷懒

- 主链/枢纽/核心机制篇：原则上不少于 8000 字，目标 10000-15000 字
- 中型专题篇：通常 5000-8000 字，但必须独立闭环
- 字数不足时只能用真实场景、失败方案、版本对比、误解纠正、时序图和数据流图扩展
- 禁止用重复总结、空洞排比、源码清单充字数

## 六、正文禁用词

正文主线出现以下表达时必须复查并优先重写：

- 此处不再赘述
- 不再展开
- 类似地
- 同理
- 依此类推
- 篇幅所限
- 显然
- 容易看出
- 细节读者自行阅读源码

## 七、篇级交付物

每篇正文必须同时保留：

1. 一句话困惑
2. 一句话顿悟
3. 文字总图/时序图/状态图
4. 至少三条误解清单
5. 关键证据清单（`file:line`）
6. 版本、平台和实现边界
7. 硬/软/NAV 前置依赖
8. 下一篇 OUTBOUND 桥接

## 八、六轮深审

### 第一轮：事实审

核对类名、路径、方法、数字、默认值、版本、代码块和行号。

### 第二轮：因果审

逐句检查“为了、因此、保证、避免、所以”等因果表达是否有源码或测试依据；区分源码事实、推断和观点。

### 第三轮：结构审

检查是否按读者理解路径组织，是否仍被源码文件顺序牵引，是否存在无法闭环的章节或前向引用。

### 第四轮：读者审

执行删码测试、陌生人测试、反向提纲测试：只看文字和标题也应能复述主线。

### 第五轮：边界审

检查异常、失败、并发、线程、资源释放、重试、超时、版本差异和未覆盖面。

### 第六轮：依赖审

检查前置关系、跨框架关系、篇末桥接和知识脑图边方向；发现新硬依赖时暂停写作，先回填规划。

只有多轮 review 不再产生新的高风险问题，文章才算收敛。

## 九、全局写作顺序

- 正文写作服从 `issue/源码分析执行计划.md` 的阶段顺序与已验证拓扑
- 不因为某个框架刚完成规划就跳过更早的阶段
- 不接手其他 AI 正在进行的框架
- 框架内按其 Plan/Handoff 的域顺序
- 域内按篇级 HARD 依赖排序
- SOFT/NAV 关系可以通过局部解释或导航链接解决，不得阻塞整个阶段

## 十、知识脑图同步

每篇正文完成后同步脑图节点和边：

```text
节点：框架/域/文章
边：HARD | SOFT | NAV | COMPARE | CONSUMES
证据：源码、测试、规划或交接文档
```

正文中的“前置依赖”和脑图中的 HARD 边必须一致；篇末提到的后续框架默认只能是 NAV，不能自动变成硬前置。

## 十一、当前启动顺序

1. 先完成本方法论与全局依赖图谱
2. 复核总执行计划和所有框架占用状态
3. 选择最早、未被其他 AI 占用、且规划已收束的框架/域
4. 为第一篇产出篇级写作规划
5. 逐篇写作、逐篇六轮深审
