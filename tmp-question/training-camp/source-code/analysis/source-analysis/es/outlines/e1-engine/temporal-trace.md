## 三个核心设计变迁

### 1. 单 versionMap → LiveVersionMap 双 map

```
v0.90: ConcurrentMap<String, VersionValue> versionMap (InternalEngine.java:182) — 单 map, refresh 时无切换
v8.12: Maps(current, old) 双 map (LiveVersionMap.java:125-169) — refresh 前建 transition, afterRefresh 清 old
```
- 设计原因: 单 map 在 refresh 期间无法安全清理 (读可能正用); 双 map 让"已 refresh 的键"进 old, 新写进 current, 无锁读靠 volatile 引用
- 代价: 内存多一倍 (old 存活一个 refresh 周期)

### 2. 内联判断 → IndexingStrategy 计划-执行 (v8 前)

```
v0.90: index() 内直接 versionMap.get → 冲突判断 → 写 (单一大方法)
v8.12: indexingStrategyForOperation (InternalEngine.java:1305) → planIndexingAsPrimary (InternalEngine.java:1314) 产出纯数据计划
       → 执行段 (InternalEngine.java:1169-1225) 按 plan 分派 addDocs/updateDocs/addStaleDocs
```
- 设计原因: 计划与执行分离让主/副分片共用决策逻辑, 便于测试 (计划可独立单测), 且 append-only 优化需要"计划时知道是否可跳过版本查找"

### 3. 无幂等 → autoGeneratedIdTimestamp 重试去重

```
v0.90: 网络重试可能重复索引 (无幂等机制)
v8.12: canOptimizeAddDocument (InternalEngine.java:1059) + maxUnsafeAutoIdTimestamp 水位 — 重试文档降级 updateDocument
```
- 设计原因: 客户端重试是常态 (超时重发), 无幂等 = 重复文档; 时间戳建立 happens-before (注释 L1143-1173)

## 对照 Redis 持久化演进

- Redis: RDB (rdb.c:95 全量快照) + AOF (增量日志) — 双轨共存至今
- ES: Lucene commit (段快照) + translog (未提交增量) — 同样双轨, 但 translog 在 commit 后可删 (E-3 交付)
- 结论: "快照+日志"是持久化通用范式, 差异在日志生命周期 (Redis 全量保留 vs ES 提交即弃)
