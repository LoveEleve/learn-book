**读者处境**: 你调 `client.index(...)` 返回 201。中间发生了什么? 面试官问 "ES 写入流程" — 你能说出 internal 阶段 (计划) 和 indexIntoLucene (执行) 吗? 问 "append-only 优化是什么?" 你答 "直接 addDocument 不用 updateDocument" — 但为什么安全? 这篇是写入路径的完整答案。

### 1. 问题引入 — index() 的锁与两阶段

场景: 1000 并发写同一索引, 同一文档 id 被两个线程同时写 — 谁会赢?
- 三级锁 (InternalEngine.java:1134-1141): readLock (全文档并发) → versionMap.acquireLock(uid) (同文档串行) → throttle (全局限速)
- 两阶段: `indexingStrategyForOperation` (InternalEngine.java:1305) 计划 → 执行段按 plan 分派 (InternalEngine.java:1169-1225)

### 2. 计划阶段 — planIndexingAsPrimary 五分支

场景: 计划器怎么决定"追加/更新/跳过/失败"?
- 入口分派 (InternalEngine.java:1305-1313): PRIMARY → planIndexingAsPrimary; 其他 origin → planIndexingAsNonPrimary (InternalEngine.java:1269)
- 五分支 (InternalEngine.java:1314-1383):
  ① optimizedAppendOnly (InternalEngine.java:1325): 可 append + 未索引过 → 直接加
  ② skipDueToVersionConflict ×3 (InternalEngine.java:1349,1360,1367): ifSeqNo 不匹配 / primaryTerm 不匹配 / version 冲突
  ③ failAsTooManyDocs (InternalEngine.java:1323,1371): 内存文档数超限
  ④ processNormally (InternalEngine.java:1373): 常规版本更新 — `index.versionType().updateVersion(currentVersion, index.version())` (L1375): INTERNAL 类型 version+1, 递增逻辑在 VersionType 抽象 (VersionType.java:251)
- 计划产物: IndexingStrategy 纯数据载体 (InternalEngine.java:1483-1530): 6 字段 + 静态工厂

### 3. 执行阶段 — indexIntoLucene 三分派

场景: 计划好了, 怎么落 Lucene?
- 执行入口 (InternalEngine.java:1169): plan 决定 indexIntoLucene / addStaleOpToLucene / useLuceneUpdateDocument
- indexIntoLucene (InternalEngine.java:1384-1430): updateSeqID (InternalEngine.java:1389) → 三分派:
  - addStaleDocs 定义 (InternalEngine.java:1472): 过期操作直接加 (recovery 场景)
  - updateDocs 定义 (InternalEngine.java:1584): 版本更新
  - addDocs 定义 (InternalEngine.java:1463): 追加 (append-only 优化路径, "document does not exists, we can optimize for create")
- 失败处理 (InternalEngine.java:1404-1430): 主分片文档失败 → IndexResult(FAILURE) (InternalEngine.java:1428); 其他 → tragic (篇 3 展开)
- translog.add (InternalEngine.java:1221): 先日志后索引 (E-3 衔接)

### 4. append-only 优化 — 为什么安全

场景: 为什么能跳过版本查找直接 addDocument?
- canOptimizeAddDocument (InternalEngine.java:1059-1090): autoGeneratedIdTimestamp != UNSET + origin 判定
- **幂等水位** (注释 L1143-1173): maxUnsafeAutoIdTimestamp — "doc A ts=10 isRetry=false; doc B ts=9; 断线重发 A' ts=10 isRetry=true → maxUnsafe=10 → 后续 A/B 都走 updateDocument"
- mayHaveBeenIndexedBefore (InternalEngine.java:1090 附近): 时间戳 < 水位 → 降级
- 设计权衡: 追加性能 (跳过版本查找) vs 幂等正确性 (时间戳建立 happens-before)

### 5. 收束 — 与复制写入的衔接

- 主分片: generateSeqNoForOperationOnPrimary (InternalEngine.java:1105) 生成 seqNo → 复制到副本 (E-6 展开)
- 副本/恢复: planIndexingAsNonPrimary (InternalEngine.java:1269) 复用传入 seqNo, 无版本冲突检查 (副本不决策)
- 引出: 篇 2 (NRT 可见性) — 篇 3 (版本管理 LiveVersionMap)

### 核心悬念
"同一个文档并发写 1000 次, ES 怎么保证不丢?" — 计划阶段在 uid 锁内解析版本, 执行阶段原子落盘, append-only 优化用时间戳水位防重试重复。
