## Q1: IndexingStrategy 为什么是"计划-执行"两阶段?

## Q2: append-only 优化 (canOptimizeAddDocument) 怎么防重试重复?

假设: autoGeneratedIdTimestamp 时间戳 + maxUnsafeAutoIdTimestamp 水位 — 重试的文档时间戳 ≤ 水位时降级为 updateDocument。

验证过程:
- Read canOptimizeAddDocument (InternalEngine.java:1059-1090): 仅当 autoGeneratedIdTimestamp != UNSET 且 origin 在 PRIMARY/REPLICA/PEER_RECOVERY/LOCAL_TRANSLOG_RECOVERY 时 true
- Read index() 内注释 (InternalEngine.java:1143-1173): 完整解释 — "doc A has autoGeneratedIdTimestamp = 10, isRetry = false; doc B = 9... 断线重发 A' → maxUnsafeAutoIdTimestamp=10 → 后续 A/B 都走 updateDocument" — **用时间戳建立 happens-before, 防止网络重试造成重复文档**
- mayHaveBeenIndexedBefore (InternalEngine.java:1090 附近) 检查 maxUnsafeAutoIdTimestamp
- 执行: optimizedAppendOnly (InternalEngine.java:1325) → indexIntoLucene 走 addDocs 定义 (InternalEngine.java:1463, "document does not exists, we can optimize for create")

代码类型: Algorithmic (幂等去重)

结论: **autoGeneratedIdTimestamp 是客户端生成的单调时间戳, maxUnsafeAutoIdTimestamp 记录已见过的最大值; 重试文档 (isRetry=true) 时间戳 ≤ 水位 → 降级 updateDocument 防重复; 这是"无版本检查的追加优化"与"幂等重试"的平衡**。InternalEngine.java:1059-1090 + L1143-1173

## Q3: LiveVersionMap 双 map 切换怎么保证并发正确?

假设: Maps(current, old) 双 map — refresh 前建 transition (新 current + 旧 current 变 old), 读写查 current+old, afterRefresh 后清 old — 无锁读依赖 volatile Maps 引用。

验证过程:
- Read Maps 类 (LiveVersionMap.java:120-175): current/old 双 VersionLookup (InternalEngine.java:126-127); needsSafeAccess 继承 (InternalEngine.java:133-139)
- buildTransitionMap (InternalEngine.java:146-152): **beforeRefresh 时建新 current, 旧 current 变 old** — "Builds a new map for the refresh transition"
- invalidateOldMap (InternalEngine.java:165-169): **afterRefresh 时 old 清空** (archive.afterRefresh(old)) — "maintains the current"
- 并发安全: 注释 (InternalEngine.java:120-122) "we don't need to maintain a happens before relationship across doc IDs... volatile read of the Maps reference"
- tombstones (InternalEngine.java:211) 删除标记独立 map; unsafeKeysMap (InternalEngine.java:216) 断言用

代码类型: Implementation (读写锁分离 + volatile)

结论: **双 map 是"refresh 期间读写不阻塞"的关键: 写进新 current (并发安全 map), 旧 current 降级为 old 供未 refresh 的读; afterRefresh 原子切换 Maps 引用 (volatile) 并归档 old — 读路径无锁, 靠 volatile 引用发布**。LiveVersionMap.java:146-169

## Q4: NRT 可见性 — realtime get vs searcher

假设: realtime get 查 LiveVersionMap + translog (不查 Lucene), 非 realtime 查 searcher — refresh 是"不可见 → 可见"的开关。

验证过程:
- Read get (InternalEngine.java:827-845): realtime → realtimeGetUnderLock(..., true) (InternalEngine.java:837)
- Read realtimeGetUnderLock (InternalEngine.java:865-905): 先查 versionMap (L869-871, "we need to lock here to access the version map to do this truly in RT") → 有值且非删除 → 检查版本冲突 → 从 translog 读 (InternalEngine.java:916) → 兜底 getFromSearcher (InternalEngine.java:923-924)

- refresh (InternalEngine.java:2022-2060): internal/external 双 ReaderManager, maybeRefresh 打开新段 reader

代码类型: Implementation (两级可见性)

结论: **NRT 三级可见性: ① realtime get → LiveVersionMap+translog (写后立即可见, 代价单文档查询) ② refresh (1s) → Lucene 段 reader 更新 (搜索可见) ③ flush → commit 落盘 (持久化); 面试标准答案 "ES 写入 1s 后可搜, 立即可 get"**。InternalEngine.java:865-924 + L2022
