# S-12 事务自动配置 — 自动启用 + 管理器装配

> 依赖 s29-s33 (复用) + S-10 | 🟡 Working | 6 KP | [模式: 条件自动启用 + 定制器]

**读者处境**: 没写 @EnableTransactionManagement 也能用 @Transactional?事务管理器谁建的?怎么统一定制?

### 1. 自动启用 — 不用写 @EnableTransactionManagement

场景: 引了 JDBC 相关依赖, @Transactional 就能用 — 因为 TransactionAutoConfiguration 自动启用了声明式事务。

源码路径:
- `TransactionAutoConfiguration.java:45,47` — **条件**: @AutoConfiguration(L45) + @ConditionalOnClass(PlatformTransactionManager)(L46 — 事务管理器类在 classpath)
- `TransactionAutoConfiguration.java:70,74` — **自动启用**: @ConditionalOnMissingBean(AbstractTransactionManagementConfiguration)(L70 — **用户没显式配置事务管理**) → @EnableTransactionManagement(proxyTargetClass)(L74) — 导入 s29 的 TransactionInterceptor 等

关键设计: **Why 自动 @EnableTransactionManagement？** 引依赖即有事务, 无需额外注解 — 条件 @ConditionalOnMissingBean 保证用户显式 @EnableTransactionManagement(或自定义配置)时自动装配让位(避免重复启用)。事务**机制**(代理/拦截器链)是 s29-s33, 本域只讲"自动启用"。[模式: 条件自动启用]

数据流: 有 spring-tx(DataSource 依赖带入) → TransactionAutoConfiguration 激活 → 容器无 AbstractTransactionManagementConfiguration → L74 @EnableTransactionManagement → 导入 s29 的事务基础设施(TransactionInterceptor/Advisor)→ @Transactional 生效。用户显式 @EnableTransactionManagement → 条件不匹配 → 跳过。

### 2. 事务管理器自动创建

场景: DataSourceTransactionManager 谁建的?为什么有时是 JdbcTransactionManager?

源码路径:
- `DataSourceTransactionManagerAutoConfiguration.java:49,53` — **条件**: @AutoConfiguration(L49) + @ConditionalOnClass({DataSource, JdbcTemplate, TransactionManager})(L51 — 数据源+JDBC 在 classpath)
- `DataSourceTransactionManagerAutoConfiguration.java:60,61,70` — **创建**: transactionManager L61(@ConditionalOnMissingBean(TransactionManager) — 用户自定义管理器优先) → createTransactionManager L70: 按环境条件选 **JdbcTransactionManager**(新, 6.x 增强版)或 DataSourceTransactionManager — 都基于 S-10 的 DataSource

关键设计: **Why JdbcTransactionManager 条件？** 事务管理器需要 DataSource — 若存在 JdbcTemplate 场景, JdbcTransactionManager 提供增强(更精确的异常翻译); 否则 DataSourceTransactionManager 兜底。**Why @ConditionalOnMissingBean？** 用户自定义事务管理器(如 JTA/多数据源)优先。[模式: 条件装配 + 用户优先]

数据流: 有 DataSource(S-10)→ DataSourceTransactionManagerAutoConfiguration 激活 → 容器无 TransactionManager → createTransactionManager: 条件满足 → JdbcTransactionManager(dataSource) 或 DataSourceTransactionManager(dataSource) → TransactionManager bean → 注入 s29 的 TransactionInterceptor。用户 @Bean DataSourceTransactionManager(自定义) → 跳过自动装配。

### 3. 定制器与边界

场景: 怎么统一定制所有事务管理器(超时/回滚规则)?与 s29-s33 的边界?

源码路径:
- `TransactionManagerCustomizers.java` — **定制器**: 收集容器全部 `PlatformTransactionManagerCustomizer` beans → 应用到每个事务管理器 — 统一的横切定制点
- `TransactionProperties.java` — **属性**: spring.transaction.* (默认超时/回滚规则) — S-5 绑定
- 边界: 事务**机制**(传播行为/失效场景/异常翻译)在 s29-s33 — 本域只讲"自动装配: 启用/创建/定制"

关键设计: **Why Customizers？** 自动装配创建的事务管理器要允许横切定制(如统一超时)而不改每个装配类 — Customizer 模式(Boot 通用); 与 S-8 的 ServletWebServerFactoryCustomizer 同构。**Why 与 s29-s33 边界？** 06 §2.5: 机制引用, 装配展开。[模式: 定制器 + 边界声明]

数据流: 用户 @Bean PlatformTransactionManagerCustomizer(统一超时) → TransactionManagerCustomizers 收集 → DataSourceTransactionManagerAutoConfiguration 创建事务管理器时应用 → 所有自动装配的事务管理器带统一超时。spring.transaction.default-timeout → TransactionProperties → 默认值。

→ 引出 S-13: 缓存自动配置 — 事务旁的另一横切: CacheAutoConfiguration 条件与 CacheManager 多实现选择(s19 @Cacheable 机制复用)。
