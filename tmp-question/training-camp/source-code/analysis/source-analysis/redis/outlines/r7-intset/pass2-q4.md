# 闭环笔记 q4: 升而不降 — 删除为什么不缩编码

## 假设
intset 编码只会升级不会降级: 删除大量元素后即使全剩小值, encoding 保持大宽度 — 设计决策 (降级成本 > 收益)。

## 验证过程
- intsetRemove (intset.c:236-253): 二分 → MoveTail 覆盖 → `intsetResize(is, len-1)` — **只缩元素数, 不缩编码宽度**; 无任何"检查是否可降级"逻辑
- 隐含: 一旦加入过 int64 值 (如 2^63), 之后即使删除它, 集合永远 8B/元素
- 降级成本分析 (为什么不做): 降级 = 逐元素搬移 (同升级 O(n)) + **必须验证所有剩余值在新编码值域内** (O(n) 扫描) — 每次删除都检查成本高; 且删除后可能又插入大值 (乒乓)
- 对照: 这是"单向升级"策略 — 与 Redis 的 listpack→dict 转换 (单向) 同哲学: **小→大转换便宜且少见, 大→小转换需要全量验证且可能回弹**
- 实际影响: 极端场景 (一次性超大值后删除) 浪费空间 — 接受 (SREM 后重建 set 可恢复)

## 代码类型
Algorithmic (策略决策) — 显式不做

## 跨域关联
- R-27 (t_set 删除) → 消费面
- R-19 (listpack→dict 单向) → 同哲学
- R-25 (hash 转换单向) → 同族

## 结论
升而不降: 降级需全量值域验证 (O(n)) + 可能回弹 (乒乓), 收益低; 单向升级与 Redis 的编码转换哲学一致。代价: 一次性大值后空间浪费 — 业务可通过重建恢复。
