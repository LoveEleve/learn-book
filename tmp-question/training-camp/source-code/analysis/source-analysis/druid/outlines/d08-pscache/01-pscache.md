### 1. 缓存结构 — 零手写 LRU

场景: 缓存放哪?容量满了淘汰谁?被淘汰的物理 statement 谁关?

源码路径:
- `PreparedStatementPool.java:185,189` — **LRU**: `LRUCache extends LinkedHashMap<PreparedStatementKey, PreparedStatementHolder>`(L185): `super(maxSize, 0.75f, true)`(L189, **accessOrder=true 按访问序**)
- `PreparedStatementPool.java:192,193,196` — **淘汰**: `removeEldestEntry`(L192): `size() > maxPoolPreparedStatementPerConnectionSize`(L193)→`closeRemovedStatement(eldest)`(L196) — **put 后触发, 淘汰队首(最久未用)并关物理 statement**
- `DruidAbstractDataSource.java:118` — **容量**: `maxPoolPreparedStatementPerConnectionSize = 10`(L118) — per-connection 上限
- `DruidConnectionHolder.java:317` — **归属**: `getStatementPool()`(L317) 懒建, 挂 holder — per-connection 独立

关键设计: **Why 继承 LinkedHashMap？**(闭环 q1): accessOrder=true 让 get/put 自动挪队尾, removeEldestEntry 每次 put 后判定 — 20 行封装拿到完整 LRU+资源释放; 淘汰细节: **in-use 条目跳过物理关闭**(等归还再关, L163-165), Oracle 缓存条目先退出。[模式: LRU 缓存]

数据流: 首次 prepareStatement → holder.getStatementPool()(317, 懒建) → put 超容量 → removeEldestEntry(192) → closeRemovedStatement(196) 关最旧 statement。

### 2. 借还路径 — 命中 / 未命中 / 归还三分支

场景: prepareStatement 和 close 分别怎么和缓存交互?同一条能被并发用吗?

源码路径:
- `DruidPooledConnection.java:355,359,364` — **借出**: `prepareStatement(sql)`(L355): `new PreparedStatementKey(sql, getCatalog(), MethodType.M1)`(L359)→`getStatementPool().get(key)`(L364)
- `PreparedStatementPool.java:58,62` — **命中保护**: `isInUse() && !sharePreparedStatements` → null(L58-60, **in-use 不共享**); 否则 `incrementHitCount`(L62)
- `DruidPooledConnection.java:369` — **未命中**: `new PreparedStatementHolder(key, conn.prepareStatement(sql))`(L369)
- `DruidPooledConnection.java:138,173,186,190` — **归还三分支**: `closePoolableStatement`(L138): clearParameters/clearBatch(L163-180)→①`pooled && poolPreparedStatements && exceptionCount==0` → `put`(L173); ②异常过 → `remove`(L186); ③否则物理 `closeInternal`(L190)

关键设计: **Why exceptionCount==0 才入池？**(闭环 q3): 执行异常过的 statement 可能坏(连接级故障/游标残留) — 入池会污染下次复用, 剔除最安全。**Why in-use 保护？** 同一物理 statement 的参数是共享状态, 两线程同时 setString 会串数据 — 默认不共享, `sharePreparedStatements: true` 显式放开。[模式: 缓存卫生协议]

数据流: prepareStatement(355) → get(key)(364) → 命中且非 in-use: 复用+hitCount; in-use 不共享: 当未命中 → 未命中: 物理新建(369) → 用完 close(153) → closePoolableStatement(138) → 干净: put(173) / 异常: remove(186) / 不缓存: 物理关(190)。

### 3. 键与方言 — 全参数键 + Oracle 让位

场景: 什么决定两次 prepareStatement 是"同一条"?Oracle 驱动也有缓存怎么办?

源码路径:
- `DruidPooledPreparedStatement.java:910,911,916,919` — **键**: `PreparedStatementKey`(L910): `sql+catalog+methodType`(L911-914)+`resultSetType/Concurrency/Holdability`(L916-918)+`autoGeneratedKeys/columnIndexes/columnNames`(L919-921) — 全参 equals/hashCode(L982+)
- `PreparedStatementPool.java:82,89` — **Oracle**: `put()`(L82): Oracle+useOracleImplicitCache → `enterImplicitCache`(L89-94), 命中 `exitImplicitCacheToActive`(L64-66); **自适应预取**(闭环 q4): `fetchRowPeak` 驱动 rowPrefetch — ≤1→2/>默认→默认/否则 peak+1(DruidPooledPreparedStatement:516-527)
- `PreparedStatementPool.java:63,68` — **统计**: `incrementCachedPreparedStatementHitCount`(L63)/`MissCount`(L68)

关键设计: **Why 全参数键？**(闭环 q2): `prepareStatement(sql, TYPE_SCROLL_SENSITIVE)` 与默认形态是不同物理 statement — 键少一维就可能把 scroll 形态复用到默认场景; 全参 equals 保证"命中即物理兼容"。**Why Oracle 让位？** 驱动自带 statement 缓存, Druid 重复持有会双缓存冲突 — 进出隐式缓存最小侵入适配。[模式: 键对象 + 驱动适配]

数据流: 复用判定: key 全字段 equals(982) → 命中计数(63)/未命中(68) → Oracle: put 进隐式缓存(89), get 转活跃(64) → 其他库: Druid 自己持有。

→ 引出 D-6: SQL Parser 体系 — PSCache 要求 SQL 字符串完全一致才命中, 参数化合并是另一条复用路径 (导航指针)。
