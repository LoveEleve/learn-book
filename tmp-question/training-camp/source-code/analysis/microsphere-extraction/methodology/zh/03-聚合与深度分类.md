# 聚合与深度分类

> 角色：AI 自约束操作规范。课程或源码逐篇/逐文件提取完成后，做聚合和深度/优先级/维度分类前必读。
> 先修：`01-训练营课程提取.md` / `02-源码逐文件提取.md`
> 输入：单主体（课程或源码）的提取结果
> 阅读顺序：00 → 01/02 → 03（本文）→ 04 → 05 → 06 → 07。

## 核心原则

01/02 提取出的是"单元 → 知识点"的扁平映射。本节做三件事：
1. **聚合**：跨单元去重——同一个机制被多个单元引用，归并成一个知识点
2. **维度**：为每个知识点分配**更高层次的维度标签**（规范/分布式问题/分布式理论/工程问题/性能优化）
3. **分类**：为每个知识点分配**深度**（🔴/🟡/🟢）和**优先级**（P1/P2/P3）+ **过时状态**（见 04）

---

## 1. 五维框架（维度标签）

每个知识点打一个**维度标签**。维度是"学习的认知单位"，决定最终如何聚类和教学。这是与"按仓库组织"的本质区别——**总大纲按维度组织，而非按仓库**。

### 1.1 五个维度

| 维度 | 标签 | 覆盖内容 | 例子 |
|------|------|---------|------|
| **规范** | `[规范]` | 当下活跃的规范与标准 | Servlet/JDBC/JMS/CDI/Bean Validation/SPI/ClassLoader/MicroProfile/Spring 抽象 |
| **分布式问题** | `[分布式问题]` | 分布式系统要解决的问题 | 服务发现/配置管理/负载均衡/容错/分布式事务/分布式锁/网关/多活/可观测/消息 |
| **分布式理论** | `[分布式理论]` | 分布式系统理论 | CAP/BASE/PACELC/Paxos/Raft/ZAB/2PC/TCC/SAGA/共识 |
| **工程问题** | `[工程问题]` | 软件工程与框架设计 | 多模块/BOM/自动装配/条件注解/扩展点/SPI/三层架构/依赖管理 |
| **性能优化** | `[性能优化]` | 性能调优 | 容器(Tomcat/Netty)/JVM/网络IO/数据库/缓存/线程模型 |

> **规范维度只列当下活跃的规范。** deprecated 的规范(如 JTA,Java EE 8 起已标记废弃)不列入此维度——它们交由 `04-过时内容处理` 处理:规范过时 → 提取底层"时间无关的模式"(如 JTA 底层的 XA/两阶段提交 → `[分布式理论]`/`[分布式问题]`),并映射现代替代(JTA → Jakarta Transactions / Seata)。

### 1.2 维度分配规则

- 每个知识点**至少一个维度**，可多个（如"基于 Raft 的服务注册"= 分布式理论 + 分布式问题）
- 维度是**主分类**，决定最终总大纲的组织（07）

### 1.3 维度与源码/课程的映射

```
规范     → 一个实现类实现了哪个规范接口（如 implements Servlet、extends JDBC Driver）
分布式问题 → 这个机制解决了哪个分布式问题（如服务发现、配置刷新）
分布式理论 → 基于哪个理论（如 Raft、CAP）
工程问题 → 框架设计/扩展机制（如 BeanPostProcessor、SPI 加载）
性能优化 → 线程模型/缓存/池化（如 Netty EventLoop、连接池）
```

## 2. 聚合 — 跨单元去重

### 2.1 聚合规则

多个单元引用同一个机制 → 归并为一个知识点。

```markdown
## 03 聚合 — 跨单元汇总：{仓库名/阶段}

| KP | 维度 | 出现单元 | 优先级 |
|----|------|---------|--------|
| {知识点} | [分布式问题] | {文件A}, {文件B} | P1 |
```

### 2.2 优先级规则（P1/P2/P3）

| 出现单元数 | 优先级 |
|-----------|:--:|
| ≥5 个单元引用 | P1 — 共识（核心机制） |
| 2-4 个单元引用 | P2 — 局部重要 |
| 1 个单元独有 | P3 — 评估是否为独立知识点 |

**跨仓库聚合**：提取完多个仓库后，同一知识点出现在多个仓库 → 行业共识信号。

### 2.3 优先级 vs 维度/规范权威性

P1/P2/P3 基于**出现单元数**。但要注意：**一个规范知识点可能只在少数单元出现却极其重要**（如 Servlet 规范）。此时：
- 优先级低（P3，出现少）但深度高（🔴，规范权威）
- 深度由 §3 判定，不因出现少而降低

## 3. 深度分类 — 🔴/🟡/🟢

### 3.1 判断基准

本框架面向**训练营学员/后端工程师**的学习需求。判断基准：**学习者需要理解到什么程度**。

### 3.2 三层深度模型

| 层级 | 产出 |
|------|------|
| **表层（🟢）** | 概念名 + 一句话定义 |
| **工作层（🟡）** | 机制原理 + 行为 + 为什么这样设计 |
| **深层（🔴）** | 工作层内容 + 关键架构组件 + 可选源码佐证 |

### 3.3 深度判定（含维度与规范对比）

```
1. 面试频繁 或 生产常见？→ 🔴 深层
2. ≥3 个知识点依赖它 且 偶尔遇到？→ 🟡 工作层
3. 属于规范/理论维度且是规范权威？→ 🔴（规范/理论维度提升深度）
4. 仅提取到？→ 🟢 表层（1-2 句）
```

**规范/理论维度加权**：`[规范]` 和 `[分布式理论]` 维度的知识点，因承载标准/理论，通常值得更深。尤其当它是"microsphere 实现 vs 规范本身"的对比时 → 🔴。

### 3.4 深度 vs 优先级 vs 维度 vs 过时

四个**独立维度**，分别判定：
- **优先级** P1/P2/P3 = 出现单元数（共识信号）
- **深度** 🔴/🟡/🟢 = 学习者需求 + 规范/理论加权
- **维度** = 认知单位
- **过时状态** = 有效/过时→替代/时间无关（04）

## 6. 反模式

### 1. 混淆优先级、深度、维度、过时

```
错误：P1（多单元出现）→ 一定是 🔴 深层 + 不分维度
正确：四者独立判定。P1 是共识，🔴 是需求，维度是认知单位，过时是时效。
```

### 2. 忽略规范/理论加权

```
错误：Servlet 规范只在一个文件出现 → P3 → 🟢 表层
正确：Servlet 规范是 [规范] 维度、规范权威 → 🔴 深层，即使出现少
```

### 3. 全部标🔴或全部标🟢

```
错误：所有知识点一样深
正确：深度匹配重要性，🔴 少数，🟢 多数
```
