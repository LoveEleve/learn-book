# 过时内容处理

> 角色：AI 自约束操作规范。对训练营课程或 microsphere 生态中可能过时的内容做处理前必读。
> 先修：`01-训练营课程提取.md` / `02-源码逐文件提取.md`
> 输入：提取到的知识点（可能过时）
> 阅读顺序：00 → 01/02 → 03 → 04（本文）→ 05 → 06 → 07。

## 核心原则

**"工具会过时，模式不会。"** （源自 cloud-native/_archive 的洞察）

- 训练营原始技术栈（stage-1：Spring Boot 2.7.4 + Spring Cloud 2021 + Netflix OSS + Dubbo 2.7.8；stage-2：SOFAJRaft 1.3.12 等）**大部分已过时**。
- 过时的是**具体工具/版本**，不过时的是**底层设计模式、规范、理论**。
- **技术基准：JDK11 / JDK17。** 训练营代码多基于此区间，过时判断与源码验证都以 JDK11/JDK17 为准（而非"2025 最新栈"）。必要时拉取 JDK11/JDK17 源码验证（源码放 `/data/workspace/source-code/code/spring/` 下，参照已有的 `openjdk11u` 与 `openjdk-book`）。
- 提取的目标：**从过时的工具中提炼"时间无关的模式/规范/理论"**，并按 JDK11/JDK17 基准判断有效/过时。

---

## 1. 三级过时状态

每个知识点分配一个过时状态：

| 状态 | 标记 | 含义 | 处理 |
|------|------|------|------|
| **有效** | `[有效]` | 在 JDK11/JDK17 基准下仍适用 | 正常提取 |
| **过时 → 现代替代** | `[过时→{现代替代}]` | 具体工具/版本已过时 | 提取底层模式 + 映射替代 |
| **时间无关模式** | `[时间无关模式]` | 设计模式/规范/理论，不绑定工具 | 正常提取，无需映射 |

### 判断标准

```
1. 这是"具体工具/版本"还是"模式/规范/理论"？
   ├── 模式/规范/理论 → [时间无关模式]，正常提取
   └── 具体工具/版本 → 继续
2. 该工具/版本在 JDK11/JDK17 基准下是否仍适用？
   ├── 是 → [有效]
   └── 否 → [过时→{现代替代}]
```

### 源码验证（JDK11/JDK17）

涉及 JDK 机制（ClassLoader/Unsafe/反射/GC/并发）的断言，**必须用 JDK11/JDK17 源码验证**：
- JDK11 源码：`/data/workspace/source-code/openjdk11u/`
- JDK17 源码：拉到 `/data/workspace/source-code/code/spring/`（参照 openjdk11u 布局）
- 参考：`/data/workspace/source-code/openjdk-book/`（格物致知 OpenJDK 源码分析）
- 验证不了标 `[待验证]`

以下是训练营原始栈 → 现代对应（按 JDK11/JDK17 基准）的参考映射（提取时用到）：

|-------------|---------|--------------|

## 3. 处理规则

### 3.1 过时工具 → 提取底层模式

```
错误："Eureka 的 PeerAwareInstanceRegistry 会定期同步"（只讲过时工具）
正确："服务注册中心通过多节点对等复制保证高可用（模式），
       Eureka 用 P2P 复制实现（2021），Nacos 用 Distro（2025）——模式不变"
```

### 3.2 规范/理论 → 保留（时间无关）

```
Servlet 规范、JDBC 规范、CAP 定理、Raft 算法 → [时间无关模式]，正常提取
```

### 3.2.1 区分"机制" vs "命名空间/版本迁移"（重要）

**规范"机制"时间无关，但"命名空间迁移"是真实过时点，不能一刀切标"时间无关"。**

```
错误：Bean Validation 机制不变 → 标 [时间无关模式]
正确：Bean Validation 机制不变 → [时间无关模式]；
      但 javax.validation → jakarta.validation 命名空间迁移是真实过时点
      → 标 [过时→Jakarta Validation]，并注明"机制不变，命名空间迁移"
```

**判断方法**：涉及规范时，区分两个层面：
1. **机制/理论**（@Valid 声明式校验思想）→ `[时间无关模式]`
2. **命名空间/API 包名/版本迁移**（javax→jakarta，EE9 分界）→ `[过时→{现代对应}]`

**反例（本文档实际决策）**：
- Bean Validation：机制时间无关，但 `javax.validation→jakarta.validation` 标 `[过时→Jakarta Validation]`（已用 biz-project 的 `javax.validation` 实证）
- JTA：规范过时→Jakarta Transactions；底层 XA/2PC 模式时间无关（见 §2 映射表）

### 3.2.2 docs 举例的"技术选项"要用实际工程验证过时

**docs 提到的技术选项（如 FastJSON）可能已过时，需用实际工程验证，不能只标 `[待验证]`。**

```
错误：docs 提到 FastJSON 优化 → 标 [待验证:是否过时]
正确：FastJSON 有 CVE 安全漏洞 + biz-project 实际用 Jackson
      → 明确标 [过时→Jackson]，并注明"docs举例 vs 实际工程"
```

**判断方法**：docs 举例某个第三方库/工具时，检查：
1. 该工具是否有已知过时/安全风险（如 FastJSON CVE）
2. 实际工程（biz-project/microsphere）用的是不是它
3. 结论 → 明确标 `[过时→{现代替代}]` 或 `[有效]`，不要停在"待验证"

### 3.3 版本绑定 → 标注现代对应

```
"Spring Boot 2.7 的自动装配" → "[过时→Spring Boot 3.x] 自动装配机制"
```

### 3.4 JDK 机制 → 用 JDK11/JDK17 源码验证

涉及 JDK 机制（ClassLoader/Unsafe/反射/GC/并发）的断言，用 JDK11/JDK17 源码验证：
- JDK11：`/data/workspace/source-code/openjdk11u/`
- JDK17：拉到 `/data/workspace/source-code/code/spring/`
- 参考：`/data/workspace/source-code/openjdk-book/`
- 验证不了标 `[待验证]`
