# 源码逐文件提取

> 角色：AI 自约束操作规范。对 microsphere 生态每个仓库做逐文件知识点提取前必读。
> 先修：`00-项目清单与依赖.md`
> 输入：单个 microsphere 仓库的源码目录
> 阅读顺序：00 → 02（本文）→ 03 → 04 → 05 → 06 → 07。

## 核心原则

**提取单位是"文件/类"，不是"包"或"域"。** 逐文件扫描，对每个文件判断它承载什么知识点。这是与 talk-method 域驱动分析的本质区别——本框架要**穷尽所有文件**，不遗漏任何承载知识的文件。

**穷尽性优先**：宁可多提取、标注低置信度，也不遗漏。这是本框架存在的意义——之前的梳理"不齐全"就是因为按主题组织时漏掉了文件。

---

## 1. 提取前准备

### 1.1 建 MCP 索引

每个仓库提取前必须先建 codebase-memory 索引。**以 cloud-native-code 版本为准**（更全，00 §2.1 已确认）：

```
index_repository(
  repo_path = /data/workspace/java-training-camp/cloud-native-code/{share|stage-4|projects|stage-3}/{仓库名},
  mode = full
)
```

**索引项目名格式**：`data-workspace-java-training-camp-cloud-native-code-{share|stage-4|projects|stage-3}-{仓库名}`

> 注意：
> - **以 cloud-native-code 为准**（00 已确认两处为同一 git remote 副本，cloud-native-code 更全）
> - 个别仓库只存在于 source-code/code/microsphere（如 confucius-commons），用其对应路径建索引
> - 旧路径索引（如 `data-workspace-source-code-code-microsphere-*`、`data-workspace-java-training-camp-cloud-native-code-share-*`）可能对应过时版本，以实际提取的仓库路径为准重建

### 1.2 读仓库上下文

```
Read README.md / docs/*.md      ← 了解仓库定位
find src/main/java -type d      ← 包结构
cat pom.xml                     ← 依赖、版本、模块
find src/test/java -type d      ← 测试当行为文档
```

### 1.3 确定文件清单

```
find src/main/java -name "*.java" | sort
```

对每个文件准备提取。**所有文件都过一遍**，不跳过。工具类、测试类也过（判断是否承载知识）。

## 2. 提取单位：一个文件 = 1-N 个知识点

### 2.1 判断标准

对每个文件，问"这个文件承载什么知识点？"。参考 talk-method 的"设计决策测试"精神，但放宽——本框架连纯工具类也提取（作为 🟢 表层知识点）。

| 文件类型 | 提取方式 | 例子 |
|---------|---------|------|
| 核心机制类 | 每个关键类 = 1-N 个机制知识点 | SPI 加载器、事件分发器 |
| 工具类 | 1 个工具类知识点（🟢 表层） | StringUtil、ObjectUtil |
| 配置类 | 1 个配置知识点（🔴/🟡 看复杂度） | AutoConfiguration、Properties 类 |
| 注解类 | 1 个注解知识点（🟢 表层） | @EnableXxx、@ConditionalOnXxx |
| 常量类 | 1 个常量知识点（🟢 表层） | 常量定义、Key 前缀 |
| 测试类 | **不作为独立知识点**，但**必须扫描**——读测试当行为文档，验证机制理解；如测试暴露了生产代码未体现的行为/边界，转为该机制的佐证说明 | — |

> **测试类与穷尽性**：穷尽性指"所有生产文件都有知识点映射"。测试类不产生独立知识点，但**必须逐个扫描**（读断言/用例），用于：①验证机制理解；②发现生产代码未显式说明的行为与边界。扫描结果并入对应机制知识点的"测试佐证"。

### 2.2 什么算"一个知识点"

**算知识点**：
- 一个独立的数据结构设计（如 `ZoneContext` 单例、`EventDispatcher` 分层）
- 一个算法/机制实现（如 SPI 优先级排序、双层代理）
- 一个跨组件交互协议（如 BeanPostProcessor 的扩展点、事件监听链）
- 一个设计模式的具体应用（如工厂模式、装饰器、模板方法）

**不算知识点**：
- getter/setter/toString（纯数据访问）
- 单纯的继承实现（无新增决策）
- 纯构建配置（pom.xml 的依赖声明）

### 2.3 置信度

| 置信度 | 判定标准 |
|--------|---------|
| **高** | 从类声明/方法体直接读取，机制明确 |
| **中** | 从类名推断但未读方法体验证 |
| **低** | 从类名猜测，需后续读源码确认 |

在两级之间犹豫时选低的那一级。

## 3. 逐文件映射表产出格式

每个文件产出一行（或多个知识点行）：

```markdown
## 02 提取 — 逐文件映射：{仓库名}

### 包: {包路径}

| Source File | 推断知识点 | 维度 | 置信度 | 说明 |
|------------|-----------|------|--------|------|
| {文件}.java:行号 | {知识点} | {规范/分布式问题/分布式理论/工程问题/性能优化} | High/Medium/Low | {一句话说明它承载什么} |
| {文件}.java | {知识点2} | {维度} | Medium | {另一机制} |
```

> 维度标签在提取时打上（03 §1 详述），供聚类和总大纲按维度组织。
> 过时状态在 04 处理后补标。

## 4. 执行步骤

### 第一步：建索引
`index_repository` 建 MCP 索引。

### 第二步：读上下文
读 README、包结构、pom.xml、测试目录。

### 第三步：逐文件扫描（分批）

遍历所有 `.java` 文件，对每个文件用 §2 标准判断知识点，产出映射表。

**分批纪律（质量铁律）**：
- **禁止一次读完全部文件再一起写**——上下文超载会稀释质量。
- 每批读 **≤10 个文件** → 即时提取该批的知识点 → 再读下一批。
- 每完成一个**包**（或一个子模块）后，可停下来让用户 review 该包。
- 大型仓库（如 microsphere-java 776 文件、shopizer 1210 文件）必须拆成多个会话/批次推进，禁止一次性扫完。

### 第四步：辅助验证
对中等/低置信度的知识点，用 MCP 辅助验证：
- `search_graph`（查类/方法）
- `get_code_snippet`（读源码片段）
- `trace_path`（追踪调用链）

### 第五步：产出映射表
输出完整逐文件映射表。**必须覆盖所有文件**——这是"齐全"的保证。

### 第六步：单元确认门
当前仓库提取完成后，**停下来交给用户 review**，用户确认后才进入下一个仓库。禁止批量连续提取多个仓库。

## 5. 完成检查单

- [ ] **MCP 索引已建**：当前仓库已 `index_repository`
- [ ] **上下文已读**：README、包结构、pom.xml、测试已读
- [ ] **所有文件已覆盖**：`find src/main/java -name "*.java"` 的每个文件都有映射
- [ ] **测试已扫描**：测试类已扫描（读断言/用例验证机制），未遗漏生产行为边界
- [ ] **置信度已标注**：每个知识点有 High/Medium/Low
- [ ] **知识判断已应用**：非知识点的文件已说明理由（工具类→🟢）
- [ ] **分批已完成**：文件按批（≤10/批）读 + 提取，无一次性全量扫描
- [ ] **已交用户 review**：本仓库提取完成后已停下来，用户确认后才进入下一仓库
- [ ] **待用户审查**：映射表已输出，供用户检查是否遗漏

## 6. 反模式

### 1. 按包跳过文件

```
错误：这个包是工具包，跳过
正确：工具类也提取为 🟢 表层知识点。穷尽性是本框架的核心。
```

### 2. 按主题组织代替逐文件

```
错误：先想"这个仓库讲什么主题"，再按主题找文件
正确：先逐文件扫描，再在 02 聚合时按主题归组。逐文件是手段，聚合是结果。
```

### 3. 只提取"重要"文件

```
错误：只提取核心机制类，工具/配置/注解跳过
正确：所有文件都提取。配置类和注解类也是知识点（可能 🟡/🟢）。
```

### 4. 不看测试

```
错误：测试不是生产代码，跳过
正确：测试当行为文档，验证对机制的理解。测试类本身不是知识点，但帮助判断。
```

### 5. 批量一次性扫描全部文件

```
错误：一次性读完全部 776 个文件 → 一次性写完整份映射表
     （上下文超载 → 编造、重复、深度稀释 → 质量崩塌）
正确：分批读（≤10 文件/批）→ 即时提取该批 → 再下一批。
     每仓库完成后停下交用户 review，确认后再做下一仓库。
```

### 6. 批量连续提取多个仓库

```
错误：一口气把 36 个仓库全提取完再一次性交差
正确：一次只做 1 个仓库，完成后停下 review，用户确认后下一仓库。
     禁止未经确认连续推进多个仓库。
```
