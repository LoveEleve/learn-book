# 需求转换与自主实现视角

> 角色：AI 自约束操作规范。**贯穿所有提取**。小马哥的课程/源码**只是参考**，不是知识本体。知识本体是"需求 + 自主实现方案"。
> 先修：`00-项目清单与依赖.md`
> 输入：小马哥课程 docs + microsphere 源码
> 阅读顺序：00 → 08（本文）→ 01/02 → 03 → 04 → 05 → 06 → 07。

## 核心原则

**最重要的视角转换：从"分析小马哥做了什么" 转为 "小马哥是参考，我若实现会怎么做"。**

```
旧视角：小马哥实现了 X → 我分析 X 的源码
新视角：小马哥想解决什么问题 → 转成需求 →
        如果我来实现会怎么做（自主设计）→ 对照小马哥源码看参考价值
```

小马哥的课程/源码**降级为"参考实现"**，不再是知识本体。提取时每个知识点都要标注：
1. **它解决了什么需求**（需求）
2. **如果我自己实现会怎么做**（自主实现方案）
3. **小马哥/源码怎么做的**（参考实现）
4. **两者差异 + 我的取舍**（对比）

### 架构师视角补全（防"井底之蛙"）

**docs 是压缩的笔记，小马哥的视频/背景/权衡大多没有落到 docs。** 若只转述 docs 字面内容，会成为"井底之蛙"——只看到文档，看不到主题在真实架构中的完整认知。

**每篇必须强制补全（不只转述 docs）**：站在技术专家/架构师高度，回答 docs 没写但主题该讲的：

1. **完整认知**：这个主题在真实生产/架构中，完整应该讲什么（跳出 docs 骨架）
2. **关键决策/权衡**：为什么这样设计，替代方案是什么，取舍
3. **常见坑/反模式**：生产环境踩过的坑、易错点
4. **生态位置**：这个主题在整套架构中的位置，与前后置主题的关系

> **docs 内容越少，补全越重要。** 有些 docs 只有标题/配置骨架（如"Resilience4j 基础"23 行、"Prometheus 配置"56 行）——这些篇目更要把主题发散到架构师完整认知，而不是只复述那几行。

## 1. 提取的三个层次（每个知识点都要过）

对每个知识点（来自课程 docs 或 microsphere 源码），都从三个层次看待：

| 层次 | 问题 | 来源 |
|------|------|------|
| **需求层** | 这个解决什么生产问题？ | 从问题出发，不是从代码出发 |
| **自主实现层** | 如果我来实现，会怎么设计？用什么方案？ | 你的设计能力（核心产出） |
| **参考实现层** | 小马哥/源码怎么做的？ | 参考，用于对照 |

### 1.1 需求层（先想清楚"为什么"）

从"生产问题"反推需求，不是从代码目录出发：

```
问题：多环境部署时配置管理混乱
→ 需求：需要一个统一的配置抽象，支持多数据源（文件/Nacos/Apollo/etcd/ZK）
→ 这就对应 microsphere-configuration 要解决的
```

### 1.2 自主实现层（核心产出，先于看源码）

在对照小马哥源码**之前**，先自主设计：

```
需求：统一配置抽象
我的设计：定义 Configuration 接口 → 各数据源适配器 → SPI 加载 → @PropertySource 扩展
我选 Spring 的 PropertySource 机制 + 自定义注解元模型
```

> **先自主设计，再看源码**。这是"如果让你来实现你会怎么做"的核心。自主设计是知识本体，源码只是对照。

### 1.3 参考实现层（对照）

小马哥/源码怎么做的？与我的设计对比，看差异和取舍。

### 1.3.1 参考实现的选择：按主流性/生态适用性，不按训练营标题

**参考实现不应照搬训练营/文档的标题（如"基于 Resilience4j"），而应选"当前主流 + 生态适用"的技术。**

```
错误：docs 标题是"基于 Resilience4j" → 参考实现就写 Resilience4j
正确：需求是"Web 服务容错" →
      自主实现：我设计超时/重试/熔断/限流/降级
      参考实现：国内主流 Sentinel（有本地源码可验证）
               + Resilience4j（国外主流，docs 提到，无源码）
      → 主流性决定参考实现，而非标题
```

**判定规则**：
1. **主流性**：该技术在当前技术栈（尤其国内 Java 生态）是否主流？如国内容错主流是 **Sentinel**，Resilience4j 非主流
2. **生态适用性**：本地/生态是否有源码可验证（有源码优先）——`code/spring/sentinel` 有源码，resilience4j 无
3. **标题只是线索，不是决定**：训练营标题可能过时/非主流，参考实现选"你实际会用/业界主流"的

**参考实现来源（优先级）**：
1. `code/spring/` 下的官方框架源码（sentinel/spring-framework/spring-boot/netty/seata...——有源码优先）
2. 小马哥的 biz-project / microsphere 代码
3. docs 描述（无源码时的经验参考）

**反例（本文档实际决策）**：
- 第 8 节"基于 Resilience4j" → 需求是"Web 服务容错"，参考实现**以 Sentinel 为主**（国内主流 + 有源码），Resilience4j 为对照（docs 标题，非主流）
- 印证：`master-integration-plan.md` 已写"resilience4j 国内用 Sentinel 为主，不需要第二个熔断库"

## 2. 为什么这是核心

- **可迁移**：自主设计能力是可迁移的，记住"某个框架怎么做"不可迁移
- **对抗"只读源码"**：读源码产出的是"源码翻译"；自主设计产出的是"可复用的工程能力"
- **贴合 REQ 思路**：HANDOVER 强调"把模块当生产级需求做，可写简历"——正是这个视角


## 5. 反模式

### 1. 只翻译源码

```
错误：小马哥的 EventDispatcher 有 A/B/C 三个类，分别做...
正确：需求是"事件解耦"→ 我若实现会选同步/异步/并行分发方案 → 小马哥用三种 dispatcher → 对比
```

### 2. 源码当知识本体

```
错误：把 microsphere-xxx 的源码当作要记住的知识
正确：源码是参考实现。知识本体是"需求 + 自主实现 + 取舍"
```

### 3. 看源码前就丧失自主性

```
错误：先看源码，然后照着源码"复述"
正确：先自主设计，再看源码对照。自主设计在源码之前。
```

### 4. 现状核对吞没知识本体（B2 模式边界——2026-08-12 沉淀）

> **教训来源**：stage-4 01 篇"跨区域多活"曾因 my-xhs 单机无诉求只标"决策待定"，主题知识只剩一句话——用户质疑"你就没规划吗"后补 §七 完整规划（六步设计/业界参考/分阶段路径）。

```
错误：my-xhs 未用/未触发 → KP 只写"现状说明：无诉求，决策待定"——主题知识只剩一句话
正确：B2 现状核对的"决策待定/现状说明"只描述案例载体（my-xhs）的落地状态；
知识本体（需求/自主实现/参考实现/对比取舍/触发条件/分阶段路径）必须独立于案例载体完整落位——
my-xhs 未用 ≠ 该主题知识可一句话带过
判据：知识本体 KP（🔴/🟡）中出现"现状"字样 = 违规；现状只允许出现在独立的"现状核对"节
正例：stage-3 23 篇"范式学习与工程选型分离"——知识本体（分层/三中心/微内核）完整 + 现状核对独立
```
