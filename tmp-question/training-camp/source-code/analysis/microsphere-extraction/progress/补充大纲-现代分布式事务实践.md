| 主题 | 核心解决 | 现代定位 |
|------|---------|---------|
| A. Transaction Outbox（事务发件箱） | 本地事务与消息发布的原子性 | 云原生"避免强一致分布式事务"的主流实现 |

**两者关系**：Outbox 是"保证业务变更与事件发布原子"的模式；CDC 是"读取数据库变更日志(如 binlog) 并转为事件"的机制。**Outbox + CDC = 完整的事件驱动事务实践链路**（本地事务写 outbox 表 → CDC 读取 → 发消息）。

# 主题 A：Transaction Outbox（事务发件箱）模式

## A1. 问题背景（为什么需要 Outbox）
- 微服务跨服务数据一致性的痛点：一个本地事务里"改数据库 + 发 MQ 消息"如何保证原子？
  - 先发消息再提交事务 → 事务回滚但消息已发（脏消息）
  - 先提交事务再发消息 → 事务成功但消息发送失败（丢消息）
- 传统方案对比与局限：
  - **2PC/XA**：强一致但阻塞、协调者单点（第 15 节）
  - **Seata AT**：阿里系主流但性能/侵入性权衡（第 19/20 节）
- **Outbox 的核心思想**：不再追求"数据库+消息"的强一致，而是"本地事务原子写业务+outbox 表"，再异步可靠地发消息 → **最终一致**

## A2. 核心概念
- **Outbox 表**：与业务数据同库的一张"待发布事件"表（事务发件箱）
- **原子性来源**：业务操作 + 写 outbox 表在**同一个本地数据库事务**中 → 要么都成功要么都失败
- **与"本地消息表"的关系**：
  - 本地消息表（第 17 节 docs 覆盖）= 业务库里的消息表，应用主动读表发消息
  - Outbox = 本地消息表的**规范化命名与最佳实践**（专用 outbox 表、单一职责、幂等）
  - 二者本质同一思想：**同库写业务+事件表，异步投递**
- **at-least-once 投递**：消息可能重复，消费端必须幂等

## A3. 工作原理（完整流程）
1. **步骤 1（本地事务）**：业务操作（如创建订单）+ 插入 outbox 记录（事件类型/负载/状态）→ **同一事务提交**
2. **步骤 2（事件发布）**：通过**轮询** 或 **CDC** 读取 outbox 表中待发布记录
3. **步骤 3（发消息）**：把事件负载发布到 MQ（Kafka/RocketMQ 等）
4. **步骤 4（确认）**：标记 outbox 记录已发布/删除（防止重复发布）
- **保证**：事件发布是"尽力而为 + 重试"，最终至少投递一次

## A4. 关键技术点
- **同库原子性**：业务表 + outbox 表必须同一数据源/同一事务（否则失去意义）
- **幂等消费**：消费端用业务 ID 去重（at-least-once 的配套）
- **事件重试/死信**：发布失败重试、超时进入死信队列
- **有序性**：同一业务实体的事件需有序（outbox 表排序 + 单分区消费）
- **清理策略**：已发布记录定期清理，防 outbox 表膨胀
- **事务边界**：outbox 写入必须在业务事务内；发布可在事务外异步

## A5. 变体与演进（重点）
- **经典 Outbox（应用轮询）**：应用起定时任务/后台线程轮询 outbox 表 → 发消息。简单但轮询延迟、DB 压力
- **Outbox + CDC（Debezium/Canal）**：用 CDC 从 binlog 实时读 outbox 表 → 发消息。**无轮询、近实时、低侵入**（见主题 B）
- **对比**：轮询(简单/有延迟) vs CDC(实时/需引入 CDC 组件)

## A6. 参考实现与生态
- 手动实现：outbox 表 + 定时任务（教学）
- 框架/库：Debezium outbox event router、Canal、Mallorca、RocketMQ 事务消息（类似思想）、DTM 本地消息表
- 参考代码结构（伪代码）：业务 Service → 同事务写 outbox → EventPublisher 轮询/CDC 触发发布

## A7. 优缺点与权衡
- **优点**：无需分布式事务、无强一致阻塞、可靠最终一致、实现相对简单、可扩展（配合消息）
- **缺点**：最终一致（非实时强一致）、需幂等、事件可能有延迟、outbox 表维护成本
- **权衡**：一致性与实时性 → 最终一致换取高可用/性能

## A8. 适用场景
- 订单/支付/积分等跨服务事件联动（不需要强一致读的场景）
- 需要可靠事件发布的微服务
- 与 Saga 配合（事件驱动 Saga 的落地基础）

# 主题 B：事件驱动 + CDC（Debezium / Canal）

## B1. 问题背景（为什么需要事件驱动 + CDC）
- 微服务数据解耦：服务间通过事件而非直接 RPC 依赖
- 数据同步痛点：双写数据库(业务库+缓存/索引/搜索)不一致、定时任务同步延迟
- **事件驱动架构**：服务发布领域事件，其他服务订阅响应 → 松耦合、可扩展
- **CDC 的价值**：直接读数据库**变更日志**（binlog/redo log），把数据库变更变成事件流 → 无需应用改动即可捕获数据变化

## B2. 事件驱动架构基础
- **事件(Event) vs 命令(Command)**：事件是"已发生的事实"，命令是"请求执行"
- **事件源/事件总线**：MQ(Kafka/RocketMQ) 作为事件流载体
- **事件驱动 vs 请求驱动**：请求驱动紧耦合同步；事件驱动异步松耦合
- **核心组件**：Producer(事件发布) / Broker(消息) / Consumer(订阅消费) / Schema 治理

## B3. CDC（Change Data Capture）概念
- **什么是 CDC**：变更数据捕获——捕获数据库的插入/更新/删除并转为结构化事件
- **原理**：订阅数据库**日志**（MySQL binlog、PostgreSQL WAL），解析并转发
- **与 Outbox 的关系**：CDC 可以读取 outbox 表（Outbox+CDC 组合），也可以直接读业务表变更
- **两种 CDC 风格**：基于日志(Log-based，主流) vs 基于轮询/快照

## B4. 主流 CDC 框架对比
- **Debezium**（Red Hat，开源，Java）
  - 基于 Kafka Connect 生态
  - 支持 MySQL/PostgreSQL/MongoDB/Oracle 等
  - 组件：Debezium Server / Connector / Engine
  - 内置 **Outbox Event Router**（直接对接 Outbox 模式）
- **Canal**（阿里巴巴，开源，Java）
  - 专注 MySQL binlog
  - 架构：Canal Server(解析 binlog) → Client(消费) → Adapter(对接 MQ/ES)
- **对比**：
  | 维度 | Debezium | Canal |
  |------|----------|-------|
  | 数据库支持 | 多种 | 主 MySQL |
  | 生态 | Kafka Connect 强 | 阿里系 MQ 适配 |
  | Outbox 支持 | 内置 Outbox Router | 需自建 |
  | 部署 | Server/Connector | Server/Client/Adapter |
  - **国内现状**：Canal 在阿里系常见；Debezium 国际主流

## B5. 架构与实现机制
- **Debezium 架构**：Connector 启动(快照 Snapshot) → 持续流式(Streaming)读 binlog → 解析为 SourceRecord → 发送 Kafka；Schema 变更处理
- **Canal 架构**：Canal Server 伪装成 MySQL 从库请求 binlog → 解析 → Client 消费；Adapter 可对接 RocketMQ/Kafka/ES
- **binlog 读取机制**：MySQL 主从复制原理（Canal 伪装 slave）；日志位置(offset)管理实现断点续传
- **关键实现**：offset 持久化（不重不漏，at-least-once）、幂等消费

## B6. 与 MQ/事件流集成
- Debezium → Kafka：SourceRecord → Kafka Topic（每表一 topic）
- 事件流进一步处理：Kafka Streams/消费者做业务处理、投递到下游服务
- 与事件驱动闭环：数据库变更 → 事件 → 下游服务响应 → 状态更新

## B7. 应用场景
- **数据同步**：业务库 → 缓存(Redis)/搜索(ES)/数仓，替代双写
- **缓存一致性**：缓存失效/更新基于 binlog 事件
- **搜索/索引同步**：ES 索引随业务表变更更新
- **事件溯源 / CQRS**：事件作为事实来源，读写分离
- **Outbox 落地**：Outbox+CDC 发消息（主题 A 的组合）
- **实时数仓**：binlog → 消息 → 实时计算

## B8. 优缺点与权衡
- **优点**：无侵入(不改应用)、实时、可靠(at-least-once)、解耦、可扩展
- **缺点**：binlog 延迟、运维复杂度(CDC 组件)、Schema 演进管理、幂等处理、日志格式版本
- **权衡**：实时性 vs 复杂性；at-least-once 需幂等

## B9. 现代实践组合（两主题合流）
- **完整链路**：本地事务写业务+Outbox → CDC(Debezium/Canal) 读 Outbox → 发 MQ → 下游消费(幂等) → 最终一致
- 对比 Seata AT/TCC/SAGA：Outbox+事件驱动是"无侵入、最终一致"取向；Seata AT 是"AT 无侵入但需代理"取向；按业务一致性与技术栈选型
- **决策建议**：能避免强一致就用 Outbox+事件驱动；必须强一致读才考虑 Seata/分布式事务
