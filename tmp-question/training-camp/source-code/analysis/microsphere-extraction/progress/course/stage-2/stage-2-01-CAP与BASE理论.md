## 二、知识点提取（三层次：需求 / 自主实现 / 参考实现）

### KP-01 CAP 定理（Brewer 定理）定义
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]`（理论，不绑工具） | **置信度**：High
- **前置**：分布式基础、CAP 术语
- **来源**：docs §CAP 理论
- **需求**：理解分布式系统"不可能同时满足 一致性/可用性/分区容错"的根本约束
- **自主实现**：设计分布式系统前先判断：网络分区不可避免，必须在 C 和 A 间取舍
- **参考实现**（docs）：CAP 定理（Brewer 定理）——分布式计算系统不可能同时满足三点：
  - **一致性(C)**：所有节点访问同一份最新数据副本
  - **可用性(A)**：每次请求都能获非错响应（不保证最新）
  - **分区容错(P)**：分区=通信时限，系统不能在时限内达成一致即发生分区，须在 C/A 间选择
  - 分区时二选一：**取消操作**(降可用保一致) 或 **继续操作**(保可用冒不一致)
- **对比取舍**：**关键**——CAP 的一致性 ≠ ACID 事务的一致性（docs 强调），两者语义截然不同
- **测试佐证**：本地源码验证方向（zookeeper=CP、nacos=AP/CP，见 KP-04）

### KP-02 "三取二"的误导 + PACELC 定理
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-01
- **来源**：docs §CAP 历史（Brewer 澄清 + PACELC）
- **需求**：纠正"CAP=三取二"的常见误读，理解无分区时还有另一重权衡
- **自主实现**：设计系统时不要盲目"三选二"——只在**分区存在**时才牺牲 C 或 A；无分区时二者可兼得
- **参考实现**（docs）：
  - **Brewer 2012 澄清**：系统设计者只需在**分区存在**时牺牲一致性或可用性；多数系统中分区罕见；存在分区管理和恢复技术
  - **PACELC 定理（2010）**：以 CAP 为基础——若发生分区(P)，在可用性(A)和一致性(C)间权衡；否则(E)，在延迟(L)和一致性(C)间权衡
- **对比取舍**：**PACELC 补全 CAP 盲区**——CAP 只讲分区时的 C/A 权衡，PACELC 增加无分区时 延迟/一致性 权衡，更贴近真实设计决策

### KP-05 BASE 理论（基本可用/软状态/最终一致）
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-01（CAP 一致性=强一致）
- **来源**：docs §BASE 理论
- **需求**：CAP 无法满足强一致时，用"最终一致"达成高可用
- **自主实现**：设计允许最终一致的系统，用 BASE 语义替代 ACID
- **参考实现**（docs）：eBay Dan Pritchett 大规模实践总结，CAP 延伸——无法做强一致(Strong Consistency)时，用适合方式达**最终一致性(Eventual Consistency)**；BASE 三要素：
  - **Basically Available(基本可用)**：读写尽可能可用（用集群所有节点），但可能不一致
  - **Soft state(软状态)**：无一致性保证，一段时间后仅概率知道状态（未收敛）
  - **Eventually consistent(最终一致)**：写入后系统运行足够久，读取返回相同值
  - 来源：《企业IT架构转型之道》6.3 事务与柔性事务
- **对比取舍**：**BASE vs ACID**——BASE 服务提供最终一致而非 ACID 强保证；最终一致性是**活性保证**（读取最终返回相同值），**不保证安全性**（收敛前可返回任意值）

### KP-06 最终一致性（Eventual Consistency）
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-05、Happens-before（docs 提到）
- **来源**：docs §最终一致性
- **需求**：理解最终一致性是高可用分布式系统的基础一致性模型
- **自主实现**：用乐观复制实现最终一致，理解其强弱边界
- **参考实现**（docs）：最终一致性=分布式计算用于高可用的**一致性模型**——非正式保证：对某数据项无新更新时，最终所有访问返回上次更新值；又称**乐观复制**，广泛部署，源于早期移动计算；已收敛系统=实现复制收敛；是**很弱的保证**（更强模型如线性化最终微不足道地一致）
- **对比取舍**：**弱保证**——最终一致只是活性保证（最终读到相同值），收敛前可能返回任何值；Happens-before 是理解其顺序的基础概念

### KP-07 一致性模型（Consistency Model）谱系
- **维度**：`[分布式理论]` | **权重**：`[支撑]` | **深度**：🟡 | **优先级**：P2 | **过时**：`[时间无关模式]` | **置信度**：Medium
- **前置**：KP-01、KP-06
- **来源**：docs §一致性模型（仅 wiki 参考链接，无正文）——**docs 骨架节，架构师发散补全（08 §2）**
- **需求**：理解"一致性不是二元的"，而是一族从强到弱的模型谱系
- **自主实现**：把 CAP 的"强一致"和 BASE 的"最终一致"放到统一谱系上定位
- **参考实现**（docs 只有 wiki 链接 + 架构师发散）：一致性模型谱系（从强到弱）：
  - **线性化(Linearizability)**：最强，操作按实时序原子化，读写即时一致（CAP 的 C 即此端）
  - **顺序一致性(Sequential)**：所有操作按某全局序，但允许非实时序
  - **因果一致性(Causal)**：有因果关系的操作有序，无因果可乱序
  - **最终一致性(Eventual)**：最弱，收敛前可任意值（BASE 即此端，见 KP-06）
- **对比取舍**：**一致性 = 谱系而非二元**——CAP 的 C(线性化) 与 BASE(最终一致) 是谱系两端；中间还有顺序/因果一致；设计时按业务选择谱系位置
- **测试佐证**：`[待验证]` 本地源码中具体一致性模型实现（如 Raft 线性化，见第 3 节）

## 五、本节小结（三层次视角）

**需求**：理解分布式系统的根本权衡——CAP（一致性/可用性/分区容错）不可能三者兼得，及 BASE（最终一致）作为高可用方案。

**自主实现核心**：若我设计——
1. 先判断分区不可避免 → 在 C/A 间取舍，不盲目"三取二"
2. 用 PACELC 补全：无分区时权衡 延迟/一致性
3. 强一致需求选 CP（ZK/Nacos-CP），高可用选 AP（Nacos-AP）
4. 无法强一致时用 BASE 最终一致 + 乐观复制
5. 用一致性模型谱系定位业务所需的一致强度（线性化→最终一致）

**参考实现**：CAP/BASE 是理论（时间无关）；技术选型用本地源码（zookeeper CP、nacos AP/CP）验证。

**对比取舍**：知识本体是"**分布式一致性权衡理论**"。核心洞察：**CAP 三分不可兼得(分区时 C/A 二选一)、PACELC 补延迟权衡、BASE=最终一致替代强一致、一致性模型谱系(线性化→最终一致)**。CAP 一致性 ≠ ACID 一致性。为后续事务/共识/容错篇奠基。

## 六、架构师视角补全（防井底之蛙）

> **来源标注**：本节大部分为架构师发散；docs 理论较全，补全聚焦"CAP/BASE 在真实架构中的应用判断"。

### 完整认知：CAP/BASE 在真实架构中完整该讲什么

docs 覆盖了 CAP 定义/历史/PACELC/BASE/最终一致。作为架构师，这个主题完整还该包含：

1. **CAP 是"分区时"的定理，不是"任何时候"**：无分区时 C/A 可兼得（Brewer 2012 澄清）——很多面试/架构讨论误把 CAP 当"常态三选二"，这是最大的误读
2. **实际系统大多运行在无分区态**：设计目标应是"分区时优雅降级 + 无分区时性能最优"，而非"永久牺牲一个"——分区检测与恢复是工程关键
3. **一致性不是二元的**：从强到弱有一致性谱系——线性化 > 顺序一致 > 因果一致 > 最终一致；CAP 的 C 是"强一致/线性化"这一端，BASE 是另一端
4. **CAP 一致性 ≠ 事务一致性**：CAP 的 C 关于"副本间的最新值"，ACID 的 C 关于"约束的完整保持"——语义混淆是常见坑
5. **技术选型看业务**：注册中心/配置中心/数据库按 CAP 定位选择——ZK(CP 强一致)、Eureka(AP 高可用，过时)、Nacos(AP/CP 双模)、etcd(CP)；数据层：RDBMS(CP)、NoSQL(BASE)
6. **BASE 的工程代价**：最终一致需要**补偿/对账/幂等/版本协调**机制兜底——"最终一致"不是"放任不一致"，而是"接受短暂不一致 + 事后收敛"（衔接 stage-2 事务篇的补偿/可靠事件/ TCC）
7. **PACELC 是更实用的决策框架**：真实系统 99% 时间无分区，此时"延迟 vs 一致性"的权衡（如异步复制 vs 同步复制、缓存一致性）比 CAP 的 C/A 更常被用到

### 关键决策与权衡

| 决策 | 权衡 |
|------|------|
| 分区时 C vs A | 取消操作(保一致降可用) vs 继续操作(保可用冒不一致) |
| 无分区时 L vs C (PACELC) | 同步复制(强一致高延迟) vs 异步复制(低延迟弱一致) |
| CP vs AP 注册中心 | 强一致(ZK) vs 高可用(Eureka/Nacos-AP) |
| 强一致 vs 最终一致 | ACID/BASE 二选一，看业务容忍度 |
| 最终一致的代价 | 需补偿/幂等/对账机制兜底 |

### 常见坑/反模式

1. **"三取二"误读**：以为系统可以任意时刻只保两个——错，只在分区时取舍
2. **混淆 CAP/ACID 的一致性**：把 CAP 的副本一致当成事务一致
3. **以为最终一致=放任不管**：缺补偿/幂等/对账机制，数据永不收敛
4. **把 CAP 当常态**：无分区时也牺牲 C/A，浪费性能和一致性
5. **选型一刀切**：不看业务就选 CP 或 AP——应看一致性/可用性需求

### 生态位置

- **分布式理论维度**：CAP/BASE 是**总大纲理论维度的基石**——后续 PACELC、共识(Paxos/Raft/ZAB)、事务(2PC/TCC/SAGA)、一致性问题全部以此为基
- **衔接**：第 2 节(Paxos) 起的共识算法、第 13-20 节(事务) 的补偿/可靠事件/TCC、第 27-28 节(缓存一致性)
- **与源码提取的关系**：CP/AP 选型用 zookeeper(CP)/nacos(AP) 源码验证；理论本身时间无关

**架构师视角结论**：本篇不只是背 CAP 定义，而是"**分布式一致性权衡的系统决策框架**"——CAP(分区时 C/A)、PACELC(无分区时 L/C)、BASE(最终一致替代强一致)、一致性谱系(线性化→最终一致)；它是整个分布式问题维度的理论源头。
