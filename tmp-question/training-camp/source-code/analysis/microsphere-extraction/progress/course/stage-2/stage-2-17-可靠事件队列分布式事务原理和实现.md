## 六、架构师视角补全（防井底之蛙）

> **来源标注**：docs 主为环境准备 + 参考资源（骨架节），方案机制大部分为架构师发散 + RocketMQ 源码验证；补全重要（08 §2）。

### 完整认知：可靠事件队列/本地消息表在真实架构中完整该讲什么

docs 覆盖了环境准备 + 参考资源。作为架构师，这个主题完整还该包含：

1. **本地消息表是"避免强一致分布式事务"的核心方案**：本地事务写业务+消息表，异步投递——最终一致、无 2PC 阻塞、无侵入；是云原生主流(对比 2PC/Seata)
2. **同库原子性是关键**：业务表+消息表必须同库同事务，否则失去意义(跨库需分布式)
3. **演进到 Transaction Outbox + CDC**：本地消息表 → Outbox(规范化) → Outbox+Debezium/Canal(近实时捕获)——现代最佳实践（详见补充大纲）
4. **RocketMQ 事务消息 = 工业内建版本**：半消息 + 事务回查，Broker 管理，应用免自建消息表——阿里系主流
5. **at-least-once + 幂等**：可靠投递可能重复，消费幂等是标配
6. **与 2PC/TCC/Saga 选型**：最终一致(消息表) vs 强一致(TCC) vs 补偿(Saga)——按业务需求选
7. **可靠投递的工程细节**：消息表清理、重试、死信、顺序性

### 关键决策与权衡

| 决策 | 权衡 |
|------|------|
| 本地消息表 vs 2PC | 最终一致简单；2PC 强一致阻塞 |
| 本地消息表 vs RocketMQ 事务消息 | 自建可控；MQ 内建免维护 |
| 自建消息表 vs Outbox+CDC | 手动扫描；CDC 近实时 |
| 最终一致 vs 强一致 | 可用性/简单 vs 一致性 |
| 幂等设计 | at-least-once 需幂等 |

### 常见坑/反模式

1. **消息表与业务不同库**：跨库失去同事务原子性
2. **不幂等消费**：at-least-once 重复处理——需按业务ID去重
3. **消息表无限增长**：不清理已投递消息——定期清理
4. **投递失败不重试**：可靠投递需重试/死信机制
5. **强一致需求用消息表**：需要实时强一致读的场景不适合最终一致

### 生态位置

- **分布式问题维度**：可靠事件/本地消息表是**"避免强一致"的主流方案**——承接 BASE(第 1 节)、对比 2PC(第 15 节)、为 TCC(第 18 节)/Seata(第 19/20 节)对照、衔接补充大纲(Outbox/CDC)
- **衔接**：BASE(第 1 节) → JTA/XA(第 15 节) → 事务整合(第 16 节) → 本地消息表(本篇) → TCC(第 18 节) → Seata(19/20) → 补充大纲(Outbox/CDC 现代实践)
- **与源码提取的关系**：rocketmq(事务消息) 是核心源码

**架构师视角结论**：本篇不只是背 tx_messages 表，而是"**理解最终一致分布式事务的核心方案**"——本地消息表(本地事务+异步投递+幂等)、RocketMQ 事务消息(半消息+回查)、演进到 Outbox+CDC 事件驱动；这是现代分布式事务"避免强一致"的主流实践，也是你关心的 Outbox 的起点。
