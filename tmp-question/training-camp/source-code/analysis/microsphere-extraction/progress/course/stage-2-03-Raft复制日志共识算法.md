### KP-02 什么是共识 + 状态机复制背景
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：状态机复制
- **来源**：docs §什么是共识 / §状态复制机
- **需求**：理解共识在复制状态机中的地位——让多服务器日志一致
- **自主实现**：若我设计——每服务器有状态机+日志，共识算法保证各日志命令一致，状态机按序执行
- **参考实现**（docs）：共识=多服务器就数值达成一致，决定**最终**；多数服务器可用即进展（5 台容 2 故障）；复制状态机：每服务器一个状态机+日志，客户端看到单个可靠状态机；共识模块保证日志同序同命令；实例：GFS/HDFS/RAMCloud(领导选举)、Chubby/Zookeeper

### KP-03 Raft 三子问题（领导选举/日志复制/安全）
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-01
- **来源**：docs §Raft 共识算法
- **需求**：把共识分解为独立子问题，各自清晰解决
- **自主实现**：先选一个**领导人**，让其完全负责管理复制日志
- **参考实现**（docs）：Raft 先选一个**有区别的领导者**，其完全负责管理复制日志；分解为三独立子问题：
  - **领导选举**：现有领导失败时选新领导
  - **日志复制**：领导接受客户端条目并复制到集群，强迫其他日志同意自己
  - **安全**：状态机安全属性——若某服务器已把某日志条目应用到状态机，没有其他服务器可对相同索引应用不同命令
- **对比取舍**：**强领导简化管理**——领导决定日志位置、单向传输数据；三子问题独立使 Raft 易理解

### KP-04 算法关键属性（服务器状态/任期/RPC）
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-03
- **来源**：docs §算法关键属性 / §Raft 基础
- **需求**：定义服务器状态、任期逻辑时钟、RPC 三种类型
- **自主实现**：若我设计——服务器三状态 + 任期单调时钟 + 两种基础 RPC
- **参考实现**（docs）：
  - **服务器状态**：Leader / Follower / Candidate 三态；正常操作仅一个 Leader，其余 Follower（被动响应）；Candidate 用于选举
  - **任期**：把时间划为任意长度任期，连续整数编号；每任期以选举开始；最多一个领导者/任期；任期=**逻辑时钟**，检测陈旧信息；每服务器存当前任期单调递增，通信时交换
  - **RPC**：两种基础——RequestVote(候选人在选举期)、AppendEntries(领导人复制日志+心跳)；第三种传输快照
  - **服务器规则（docs 图 3，图片化内容补全）**：
    - **所有服务器**：若 RPC 请求/响应任期 > 当前任期，更新当前任期回 Follower；若自己任期过期则拒绝
    - **Follower**：响应 Candidate 的 RequestVote、Leader 的 AppendEntries；若选举超时未收 AppendEntries 则变 Candidate
    - **Candidate**：当选后先为自己投票、并发 RequestVote；若得多数票变 Leader；若收到合法 AppendEntries(任期≥自己)则回 Follower；选举超时则重开选举
    - **Leader**：定期发心跳(空 AppendEntries)；若收到更高任期请求则回 Follower；决定何时提交日志条目
- **对比取舍**：**任期逻辑时钟**是 Raft 防陈旧信息的关键（替换 Paxos 的复杂编号）；服务器规则约束各状态行为，是实现 Raft 的明确规范

### KP-05 领导者选举（Leader Election）
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-04
- **来源**：docs §领导者选举
- **需求**：领导失败时快速选新领导，避免分裂投票
- **自主实现**：若我设计——Follower 超时未收心跳 → 变 Candidate → 拉票
- **参考实现**（docs）：心跳机制触发选举——Follower 超过**选举超时**未收通信 → 增任期变 Candidate，为自己投票 + 并行发 RequestVote；三种结局：
  - **赢选举**：收到大多数同任期投票（多数规则保最多一名赢家）
  - **另一个服务器确立为领导**：收到合法 AppendEntries 则回 Follower
  - **无赢家**：分裂投票 → 增任期重新选举
  - **随机选举超时**(150-300ms) 防分裂投票——多数情况仅一服务器超时即赢
- **对比取舍**：**随机超时替代排名系统**——作者试过排名系统有微妙可用性问题，随机重试更明显易懂
- **测试佐证**：`sofa-jraft` 的 Leader 选举实现 `[待验证]` 具体类

### KP-06 日志复制（Log Replication）
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-03
- **来源**：docs §日志复制
- **需求**：让领导接受的命令复制到各服务器日志，且保持一致
- **自主实现**：若我设计——领导加条目到日志，并行 AppendEntries 复制；安全时提交并应用到状态机
- **参考实现**（docs）：领导把命令作为新条目加入日志，并行 AppendEntries 复制；被多数服务器复制即**提交(committed)**并应用到状态机返回客户端；日志条目含**命令+任期+索引**；慢/崩追随者无限重试直到追齐
- **对比取舍**：**提交=多数复制**；日志条目的任期号用于检测不一致，索引标识位置

### KP-07 日志匹配属性（Log Matching）
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-06
- **来源**：docs §日志复制（日志匹配属性）
- **需求**：保证各服务器日志高度一致（安全性组成部分）
- **自主实现**：若我设计——同索引同任期→同命令；同索引同任期→前面条目全相同
- **参考实现**（docs）：两个属性：
  - 两日志同索引+同任期 → 存相同命令
  - 同索引+同任期 → 前面所有条目相同
  - 由"领导任期最多创建某索引一个条目 + 日志条目位置不变 + 一致性检查"保证
- **对比取舍**：**一致性检查**——AppendEntries 带前一条目索引/任期，追随者找不到则拒绝 → 领导降低 nextIndex 重试直到对齐

### KP-08 日志不一致恢复（nextIndex 机制）
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🟡 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-07
- **来源**：docs §日志复制（不一致处理）
- **需求**：领导崩溃后追随者日志可能不一致，需自动收敛
- **自主实现**：若我设计——领导强迫追随者覆盖冲突条目，直到日志一致
- **参考实现**（docs）：领导为每追随者维护 **nextIndex**；不一致时 AppendEntries 一致性检查失败 → 减 nextIndex 重试 → 最终对齐，删除冲突条目并补领导条目；领导者**从不覆盖/删除自己日志条目**(Leader Append-Only)；可优化：拒绝时返回冲突任期和首索引，批量跳过
- **对比取舍**：**自动收敛**——领导正常操作即靠一致性检查失败驱动日志趋同，无需特殊恢复动作

### KP-09 安全性（选举限制 + 从前条目提交）
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-05/06/08
- **来源**：docs §安全性
- **需求**：保证各状态机以同序执行完全相同命令
- **自主实现**：若我设计——限制谁能当领导（须含所有已提交条目）+ 精确化提交规则
- **参考实现**（docs）：
  - **选举限制**：候选人须联系多数才能当选 → 其日志至少与多数中最新的一样新，故含所有已提交条目；RequestVote 比较最后条目的索引+任期
  - **从前条目提交**：**只通过计算副本来提交当前任期的条目**；前任期条目靠日志匹配属性间接提交（保留原任期号，Raft 更保守但易推理）
  - **安全性论证（docs §安全性论证，矛盾证明简述）**：假设领导者完整性属性不成立——任期 T 的 leaderT 提交了某条目，但未来某任期 U>T 的 leaderU 不存该条目。leaderU 获多数投票、leaderT 复制到多数 → 必有一"选民"同时接受过 leaderT 条目并投票给 leaderU。该选民投票时仍存该条目(领导不删、追随者仅删冲突)；leaderU 日志须与选民一样新 → 矛盾(若同尾条目则 leaderU 须含选民所有条目；否则 leaderU 任期> T 且其创建者须含该提交条目)。故 >T 的所有领导必含 T 的已提交条目。由领导者完整性 + 日志匹配，可证状态机安全属性成立。
- **对比取舍**：**领导者完整性属性**——新领导必含前任期所有已提交条目；据此证明状态机安全属性成立（图 9 矛盾论证：借"选民"同时接触旧条目的关键角色）

### KP-10 跟随者/候选者崩溃 + 时机与可用性
- **维度**：`[分布式理论]` | **权重**：`[支撑]` | **深度**：🟡 | **优先级**：P2 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-05/06
- **来源**：docs §跟随者和候选者奔溃 + §时机和可用性
- **需求**：理解崩溃处理与时间要求对可用性的影响
- **自主实现**：无（机制理解）
- **参考实现**（docs）：
  - **跟随者/候选者崩溃**：无限重跑 RPC；Raft RPC 幂等，重复无害（如忽略已存在条目）
  - **时机**：安全性不依赖时间，但**可用性依赖**；要求 `broadcastTime ≪ electionTimeout ≪ MTBF`（广播时间≪选举超时≪平均故障间隔），选举超时随机(10-500ms)
- **对比取舍**：**安全不靠时间、可用性靠时间**——满足时间不等式才能稳定选领导；这是 Raft 的重要工程约束

### KP-11 集群成员变更（联合共识）
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：KP-09
- **来源**：docs §集群成员变更
- **需求**：不停机安全变更集群成员（增删服务器）
- **自主实现**：若我设计——两阶段切换避免分裂成两个多数
- **参考实现**（docs）：直接切换不安全（可能分裂成两个独立多数）；Raft 用**联合共识(Cold,new)**两阶段过渡：
  - 日志条目复制到两种配置所有服务器
  - 任一配置服务器可当领导
  - 选举/提交要求**新旧各占多数**
  - 配置存为特殊日志条目；三个问题：新服务器先无投票权追赶、领导不在新配置则下台、被移除服务器可能捣乱(忽略其 RequestVote)
- **对比取舍**：**联合共识保安全**——过渡期 Cold 或 Cnew 都不能单方面决定；不停机服务

## 五、本节小结（三层次视角）

**需求**：提供一种**易于理解**的复制日志共识算法，等价 Paxos 但更适合实际系统。

**自主实现核心**：若我设计——
1. 选一个**强领导**完全管理复制日志，分解为 选举/日志复制/安全 三子问题
2. 服务器三状态 + 任期逻辑时钟 + 两种基础 RPC
3. 随机超时选举防分裂；多数投票保唯一领导
4. 日志复制 + 提交(多数) + 日志匹配属性 + nextIndex 恢复不一致
5. 选举限制 + 从前条目提交保安全
6. 联合共识成员变更 + 快照日志压缩

## 六、架构师视角补全（防井底之蛙）

> **来源标注**：docs 理论详实（Raft 论文摘要级），补全聚焦"Raft 工程化与对比"。

### 完整认知：Raft 在真实架构中完整该讲什么

docs 覆盖了选举/日志复制/安全/成员变更/快照。作为架构师，这个主题完整还该包含：

1. **Raft 是"可理解的 Paxos"**：解决 Paxos 难懂/难实现的痛点——分解子问题 + 状态空间缩减；实际系统（etcd/K8s/SOFAJRaft/Consul/TiKV）都用 Raft
2. **强领导模型的代价与收益**：收益=日志单向流、管理简单；代价=领导成为热点/单点（性能瓶颈），需读多写少场景
3. **提交/一致性理解**：提交=多数复制；Raft 只提交当前任期条目(保守)；日志匹配属性是安全的支柱
4. **工程实现要点**：选举超时随机(避免活锁)、心跳、快照、成员变更、WAL(写前日志)+持久化——理论之外的大量工程细节
5. **Raft vs Paxos vs ZAB vs SOFAJRaft**：Raft 强调可理解；Paxos 理论优雅；ZAB 面向 ZK 原子广播；SOFAJRaft 是 Raft 的 Java 工业实现（第 5-6 节）
6. **实际一致性应用**：etcd/Raft、ZK/ZAB、SOFAJRaft——一致性地基；本节的选举/复制模式在 Nacos 配置一致性、注册中心可复现
7. **时机约束的现实性**：broadcastTime≪electionTimeout≪MTBF 是可用性前提——数据中心网络通常满足，跨地域/慢网络需调参

### 关键决策与权衡

| 决策 | 权衡 |
|------|------|
| 强领导 vs 无领导 | 强领导简化但成热点；无领导复杂但负载均衡 |
| 随机超时 vs 排名选举 | 随机简单防分裂；排名曾有可用性角落问题 |
| 提交当前任期 vs 前任期 | Raft 保守只提交当前任期(易推理)；前任期靠间接提交 |
| 联合共识 vs 一次性切换 | 联合共识保安全不停机；一次性切换有分裂风险 |
| 快照 vs 全量日志 | 快照省空间/回放；需传输快照状态 |

### 常见坑/反模式

1. **选举超时太小**：频繁选举/领导抖动——不满足 broadcastTime≪electionTimeout
2. **忽略持久化**：日志/任期不落盘，崩溃后破坏安全
3. **直接切配置**：成员变更一次性切换，可能分裂成两个多数——用联合共识
4. **日志无限增长**：不压缩，回放越来越慢——用快照
5. **把安全当活性能保证**：Raft 保安全(不返回错误结果)，进展依赖多数可用+时机

### 生态位置

- **分布式理论维度**：Raft 是**共识算法工程化主流**——承接 Paxos(第 2 节)思想，为第 4 节 ZAB、第 5-6 节 SOFAJRaft 铺垫；与 CAP(第 1 节)一致性问题衔接
- **衔接**：Paxos → Raft(可理解实现) → ZAB(ZK) → SOFAJRaft(工业 Java 实现) → Nacos 等应用
- **与源码提取的关系**：sofa-jraft 是 Raft 的直接实现，第 5-6 节将逐文件提取

**架构师视角结论**：本篇不只是背 Raft 选举/复制，而是"**理解现代一致性系统为什么都用 Raft**"——它用强领导+任期+分解子问题换取可理解性，同时保性能等价 Paxos；是 etcd/K8s/SOFAJRaft 的地基，也是理解一切复制日志系统的人门。
