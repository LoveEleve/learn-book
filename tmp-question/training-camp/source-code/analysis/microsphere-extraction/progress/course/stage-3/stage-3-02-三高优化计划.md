### KP-06 性能指标（TPS/QPS/RT + 排队理论）
- **维度**：`[性能优化]` | **权重**：`[核心]` | **深度**：🟡 | **优先级**：P2 | **过时**：`[有效]` | **置信度**：High
- **前置**：并发/队列概念
- **来源**：docs §性能指标（TPS/QPS/RT 3 节）
- **需求**：统一指标口径——调优流程第①步"建立数值"的度量对象
- **自主实现**：若我设计——TPS 看事务吞吐、QPS 看请求到达率、RT 拆服务时间+等待时间
- **参考实现**（docs）：**TPS**——每秒事务数（DB 场景指数据库事务，复杂事务用 TPM）；**QPS**——每秒查询/请求（请求-响应系统称 RPS 更准确）；**RT（响应时间）**——服务时间（完成工作所需，随负载变化小）+ **等待时间**（排队等待，0→服务时间的数倍）+ 传输时间（传播/错误/带宽）；**排队理论核心结论**——设备从 0→100% 繁忙时平均等待时间**非线性增长**（接近满负载时 RT 急剧恶化）
- **对比取舍**：**RT 三成分拆解**——服务时间恒定、等待时间随利用率非线性爆炸——这是"高水位系统为何突然变慢"的理论根源
- **测试佐证**：docs §性能指标；衔接 my-xhs 网关 `RateLimitFilter`（限流即控制等待时间的手段）

### KP-07 JIT 编译与自适应优化（HotSpot 分层编译/去优化）
- **维度**：`[性能优化]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P2 | **过时**：`[有效]` | **置信度**：High
- **前置**：JVM 执行模型
- **来源**：docs §JIT 编译 + §自适应优化 + JDK11/17 源码验证
- **需求**：理解 Java"解释→JIT→自适应"的性能演进机制
- **自主实现**：若我设计——热点检测 + 分层编译（C1 启动快/C2 峰值高）+ 激进优化可去优化回退
- **参考实现**（docs + 源码验证）：**历史**——Java 1.0 解释执行（比 C 慢 10-20 倍）→ Java 1.1 JIT（10 倍提速）→ 1.2 HotSpot（热点检测）→ 1.3 默认；**机制**——JVM 分析"热点"频繁执行路径 → 优化 → 低开销高性能；**自适应优化**——按执行 profile 动态重编译、权衡解释/JIT、可**去优化（deoptimize）**回安全路径；**分层编译**（docs §Java 7）——C1 客户端编译器（启动快）+ C2 服务端（长期运行峰值），两者可同时使用（JDK7+，Da Vinci 项目产物）；**动态语言支持**（docs §Java 7）——invokedynamic（JSR 292，达芬奇机器原型）为动态语言提供 JVM 级调用指令；**JDK11/17 验证**——`globals.hpp` `product_pd(bool, TieredCompilation)`（平台相关默认，实际默认开启）；JIT 机制在 JDK11/17 仍为 C1/C2 分层 + Graal JIT（`-XX:+UseJVMCICompiler` 可选）
- **对比取舍**：**激进优化 + 去优化回退**——性能收益 vs 安全兜底（HotSpot 的核心设计：激进但不破）
- **测试佐证**：openjdk11u + jdk17 `src/hotspot/share/runtime/globals.hpp`（TieredCompilation 声明）+ docs §JIT/自适应/Java 7

- **自主实现**：若我设计——默认 G1（可预测暂停）+ 超低延迟场景 ZGC/Shenandoah
- **参考实现**（docs + 源码验证 + 实例）：**历史**——1.0/1.1 标记-清除（堆分段）→ 1.2 分代收集器（碎片整理更好）→ Java 7 引入 G1（"垃圾优先"，可预测暂停）→ **JDK9+ G1 默认**（JEP 248）→ **CMS 已移除**（JDK14，JEP 363）→ ZGC（JEP 333，JDK11 实验，JDK15 正式）/ Shenandoah（JEP 189，JDK12）→ **JDK11 源码验证**——`gcConfig.cpp:100-105` `select_gc_ergonomically()`（**server-class 机器**时 `FLAG_SET_ERGO_IF_DEFAULT(bool, UseG1GC, true)`，G1 默认）；**my-xhs 实例**——`start-all.sh:16-20` 显式 `-XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:MaxMetaspaceSize=256m`（目标导向调优：给 G1 设暂停目标而非无脑堆大小；BASE 512m / GW 256m / HEAVY 1024m 分档，ANALYTICS 额外 `-Dmanagement.admin-token`）+ SkyWalking agent

### 完整认知：三高优化的完整方法论该讲什么

docs 覆盖了流程/测试/指标/JVM 机制。作为架构师，完整还该包含：

1. **优化清单 = stage-3 目录**（docs 前言明确）：服务进程→注册中心→服务调用→数据库→分布式事件→API 网关→分布式缓存→分布式锁→分布式文件系统→配置中心→监控平台——**这就是后续 05-33 篇的教学路线图**，本篇是它的"元方法"
2. **瓶颈分析的现代手段**（架构师发散）：docs 只提"采样证明"，现代是 **JFR 飞行记录 + async-profiler 火焰图 + Arthas 在线诊断**——18 节（JVM 故障）展开；"CPU 高""GC 频繁"各有对应工具链
3. **排队理论的工程推论**（docs 明确 + 发散）：RT 非线性爆炸 → 系统应**保持低利用率运行（≤70%）**、用**限流/削峰**（my-xhs `RateLimitFilter`、Sentinel）控制等待时间——不是"越高越好"
4. **GC 选型是延迟目标驱动的**（docs 明确 + 实例）：my-xhs `-XX:MaxGCPauseMillis=200`——先定暂停目标再选 GC（G1），超低延迟（<10ms）才上 ZGC/Shenandoah；**Metaspace 256m 限制**防元空间泄漏
5. **压测是团队纪律不是一次性活动**（架构师发散）：CI 回归基准（test-2 全链路）+ 发布前压力测试——docs 6 步循环的工程化落地
6. **"过时"不是"失效"**（04 处理）：CDS→AppCDS、split 验证→StackMapTable、CMS→G1/ZGC——**机制思想时间无关，实现形态随 JDK 换代**；提取时应记机制不记版本

### 关键决策与权衡

| 决策 | 权衡 |
|------|------|
| 测量驱动 vs 直觉 | 采样证明防错；慢（需先建基线） |
| 采样 vs 插桩 profiler | 低开销近似；精确但拖慢 |
| 四类测试分工 | 各测一个维度；全做成本高（按阶段选） |
| GC：G1 vs ZGC/Shenandoah | G1 默认均衡；超低延迟牺牲吞吐/复杂度 |
| 分层编译 C1+C2 | 启动快+峰值高；编译开销/内存 |
| 激进优化+去优化 | 性能 vs 安全回退（HotSpot 设计核心） |

### 常见坑/反模式

1. **不测就改**（docs 明确警告）：猜测瓶颈是最大反模式——"猜测往往错误，且猜测本身成为瓶颈"
2. **指标口径混乱**：TPS 不含工具/场景/时长（Shopizer 案例警示）——不可复现的压测数字无意义
3. **堆越大人越好**：无暂停目标乱调堆大小（my-xhs 反例示范：G1+MaxGCPauseMillis 目标导向）
4. **忘记回滚闸**：6 步第⑥步是质量闸——"改完更差就回滚"在发布流程中要留预案
5. **只看均值**：RT 排队理论非线性——要看 **P99/P95 尾部延迟**，均值会掩盖等待时间爆炸
6. **过时版本照搬**：CMS 参数（-XX:+UseConcMarkSweepGC）在 JDK14+ 直接**启动失败**（已移除）——生产环境升级要清理
