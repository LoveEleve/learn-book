- **自主实现**：若我设计——先理解 K8s 管什么（容器化工作负载声明式管理）与不管什么（不构建应用/不提供中间件/不要求日志方案）
- **参考实现**（docs 清单 + 发散）：**定位（docs）**——可移植可扩展开源平台，管理容器化工作负载，促进**声明式配置和自动化**；2014 Google 开源（希腊语"舵手"）；**9 大能力（docs）**——服务发现和负载均衡（DNS/IP + 负载均衡分发）/存储编排/自动部署和回滚（受控速率改期望状态）/自动装箱计算（CPU/内存请求）/自我修复（重启失败容器、健康检查、就绪前不通告）/密钥与配置管理（不重建镜像更新）；**7 个"不提供"（docs 关键边界）**——不部署源码/不构建应用（CI/CD 是组织的）/不提供应用级中间件（消息/DB/缓存——可运行其上）/不要求日志监控告警方案/不提供配置语言系统/不采用机器配置系统/**"不仅仅是一个编排系统"**——**编排=执行已定义工作流（A→B→C）；K8s=独立的可组合控制过程，连续驱动当前状态→期望状态（如何从 A 到 C 无关紧要）**（docs 明确——声明式控制回路）
- **对比取舍**：**编排（预定义流程）vs 声明式（期望状态驱动）**——集中控制 vs 控制回路——**K8s 的核心范式**（与 21 篇 Mesh 的"能力外置"呼应：平台层承担）

## 七、架构师视角补全（防井底之蛙）

### 完整认知：K8s 与 Istio 的完整认知该讲什么

docs 覆盖 K8s 基础与示例链接。完整还该包含：

1. **K8s 是 Mesh 的"土壤"**（docs + 21 篇衔接）：Sidecar 注入/Envoy 调度/控制平面协调——**没有 K8s 的声明式调度，Mesh 的"零侵入"无法实现**（21 篇 Stage ⑤ 的运行前提）
2. **"声明式控制回路"是平台范式**（docs 明确 + 发散）：编排（A→B→C 预定义）vs 声明式（期望状态 → 连续驱动）——**与注册中心的"自愈"（07 篇心跳驱逐）、网关的"配置驱动"（19 篇）同构思想**——平台层的共同范式
3. **能力边界是"平台 vs 业务"的分层**（docs 7 不提供 + 发散）：K8s 不提供中间件/日志方案——**业务设施（Nacos/MQ/Prometheus）跑在 K8s 上而非 K8s 内建**（my-xhs：compose 编排的 Nacos/RocketMQ/SkyWalking——03 篇）——**分层清晰是架构健康的标志**
4. **etcd 的"一致高可用 + 备份计划"**（docs 明确 + 衔接）：K8s 状态存 etcd（强一致——stage-2 01 CP）——**26 节 etcd 配置中心同一技术**；"需要备份计划"（docs）——基础设施的关键数据面
5. **Kiali 的价值是"拓扑化"**（docs ② + 发散）：服务网格的可观测最终形态 = **依赖拓扑图**（谁调用谁/版本分布/延迟）——my-xhs 的 SkyWalking 拓扑（03 篇）是应用层等价物——**Mesh 引入后 Kiali 是自然升级**
6. **部署形态的演进路径**（发散）：Docker Compose（my-xhs 当前——03 篇）→ K8s 模板（已准备——本篇）→ K8s + Mesh（演进项）——**三步走的渐进路径**

### 关键决策与权衡

| 决策 | 权衡 |
|------|------|
| 编排 vs 声明式 | 预定义流程 vs 期望状态驱动（K8s 范式） |
| etcd（CP 强一致）vs 注册中心（AP） | 平台状态 vs 业务发现（stage-2 01） |
| CRI 多运行时 vs 绑定 | 开放 vs 锁定 |
| Kiali（Mesh 拓扑）vs SkyWalking（应用拓扑） | 零负担 vs 埋点 |
| Compose vs K8s | 简单 vs 平台能力（my-xhs 渐进） |
