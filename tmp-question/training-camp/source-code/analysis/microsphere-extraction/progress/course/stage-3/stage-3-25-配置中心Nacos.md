- **自主实现**：若我设计——健康实例比例低于阈值 → 返回全部实例（含不健康）——**宁损失流量不压垮健康实例**

### 完整认知：Nacos 配置中心的完整认知该讲什么

docs 覆盖概念与架构。完整还该包含：

1. **"三元组是配置组织的空间"**（docs 模型 + 发散）：Namespace（租户/环境）→ Group（分类）→ Data ID（具体配置）——**三维定位任何一条配置**；my-xhs 用 namespace: my-xhs 单环境——**多环境应 namespace 隔离**（docs"常用场景"）
2. **快照是客户端容灾的第一道防线**（docs 明确 + 发散）：本地快照（无过期概念——Git 类比）——**Server 全挂配置照常**（07 篇"客户端缓存兜底"同哲学——注册表与配置双快照）；**与 07 篇 ServiceCache/FailoverReactor 同构**
3. **健康保护阈值与自保护是"保命机制"**（docs + 07 篇对照）：Nacos（返回不健康实例）vs Eureka（停止驱逐）——**同思想：宁可给旧数据不雪崩**（stage-2 01 CAP 的 AP 落地）
4. **配置事件六要素 = 可审计的变更模型**（docs + 发散）：内容/ID/时间/类型/字符集/版本——**支撑版本回滚/金丝雀/更新状态跟踪**（docs 动态配置特性）——配置治理的基础
5. **双部署模式的选型**（docs ①② + 发散）：Raft CP（内建共识——配置强一致）+ DB 外置（复用 MySQL 高可用）——**"一致性要求 × 运维现状"决定**；压测稳定性（docs 意图）是选型验证手段（02 篇方法）
6. **模块化组件面与 SPI**（docs 29 组件 + 发散）：插件机制（可分可合）——**与 23 篇 Dubbo SPI 同思想**（生态可扩展的框架设计）

### 关键决策与权衡

| 决策 | 权衡 |
|------|------|
| 注册+配置一体 vs 分离 | 一致部署 vs 职责分离 |
| 三元组组织 vs 单 Key | 多维隔离 vs 简单 |
| 快照容灾 vs 无快照 | Server 挂可用 vs 数据过期风险 |
| 健康保护阈值 vs 严格过滤 | 防雪崩 vs 精确（宁旧不崩） |
| Raft CP vs DB 外置 | 内建共识 vs 复用 MySQL 高可用 |
| 合并 vs 分离部署 | 一进程 vs 独立扩缩 |

### 常见坑/反模式

1. **不设健康保护阈值**：不健康实例过滤 → 健康实例被压垮雪崩（docs 明确）
2. **命名空间不用**：全部配置 public——环境/租户混淆（docs 常用场景）
3. **快照过期误解**：快照无过期概念——本地旧配置长期可用（docs 明确）
4. **配置无版本管理**：无法回滚——版本/时间要素必带（docs 六要素）
5. **忽略压测**：集群/DB 模型上线前压测稳定性（docs ①②意图——02 篇方法）
6. **Data ID 命名随意**：全局唯一性靠命名约定（docs 类 Java 包规则）
