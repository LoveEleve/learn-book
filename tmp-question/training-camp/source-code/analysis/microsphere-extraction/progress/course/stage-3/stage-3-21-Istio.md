- **维度**：`[分布式问题]` | **权重**：`[核心]` | **深度**：🟡 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High

- **自主实现**：若我设计——网关=入口（南北向），Mesh=全网格（东西向）——能力重叠但作用域不同
- **参考实现**（docs 同异 + 发散 + my-xhs 对照）：**相同点（docs）**——功能类似（路由/限流/熔断/可观测——19/20 篇网关能力）；**不同点（docs 图 + 发散）**——**网关：入口级（南北向——外部流量 → 服务）**；**Mesh：全网格（东西向——服务间所有流量）**——每个实例旁有代理（KP-01 Stage ⑤）；**能力形态（发散）**——网关是"单点横切"，Mesh 是"全网旁路"；**my-xhs 对照**——my-xhs 的网关过滤器（灰度/染色/限流——03 篇）承担了 Mesh 流量控制的部分能力（入口级），服务间流量（Feign——06 篇）无代理——**能力覆盖：入口有、网内无**
- **对比取舍**：**网关（入口治理）vs Mesh（全网治理）**——部署简单 vs 覆盖完整——**演进路径：先网关后 Mesh**（docs 五阶段 ③→⑤）
- **测试佐证**：docs §同异（图）+ my-xhs（网关 7 过滤器 03 篇）

- **参考实现**（docs + my-xhs 对照）：**Istio 定位（docs）**——完全开源服务网格/透明一层/平台（集成日志遥测策略）/保护连接监控统一方法；**为什么用（docs）**——大厂背书（Google、IBM）/轻松构建/功能丰富；**流量管理（docs）**——路由规则控制流量 API 调用；简化服务级别属性（**熔断器、超时、重试**）；**A/B 测试、金丝雀发布、基于流量百分比切分的分阶段发布**；开箱即用故障恢复；**机制（docs 明确）**——**data plane 流量都经由 Envoy 代理**（网格内服务收发全过 Envoy）→ 控制网格流量**无需服务任何更改**；**my-xhs 对照（灰度现状实证）**——`GrayRouteFilter.java:15`（X-Gray-Tag Header 路由灰度实例）+ `:47`（灰度比例由上游 CDN/前端按百分比设置 X-Gray-Tag——**非网关内权重切分**）——**docs 的"版本/流量分配"在 my-xhs 是 header 灰度（可控但非百分比切分）**

## 七、架构师视角补全（防井底之蛙）

> **来源标注**：docs 为 Istio 官方文档转写（定义/指标示例精确）；实战/发展空节；my-xhs 实证；"docs 明确内容"vs"架构师发散"如下。

### 完整认知：服务网格的完整认知该讲什么

docs 覆盖演进与能力。完整还该包含：

1. **"应用无感知"是 Mesh 的终极价值**（docs 定义 + 发散）：能力（流量/策略/安全/可观测）全在 Sidecar——**应用代码零侵入**；对比框架内实现（网关过滤器/埋点——my-xhs）——**演进 = 能力不断外置**（KP-01 五阶段主线）
2. **Mesh 与网关是互补不是替代**（docs 同异 + 发散）：网关管南北向（入口），Mesh 管东西向（网内）——**现代架构两者并存**（Istio 也有 Ingress Gateway 管入口）；my-xhs 无 Mesh 时网关承担部分网内能力（灰度）
3. **流量管理是 Mesh 的核心卖点**（docs ② + 发散）：金丝雀/百分比切分/镜像——**发布策略的基建化**；对比 my-xhs 的 header 灰度（需上游协作）——**"灰度 LB 未实现"正是 Mesh 价值的位置**（docs 的"无需服务更改"vs my-xhs 的"需 header 约定"）
4. **黄金四标识是服务监控的通用框架**（docs ③ + 发散）：延迟/流量/错误/饱和——**与 02 篇性能方法论/03 篇面板同构**——Mesh 指标（istio_requests_total 全标签）让"任两维度交叉分析"成为可能（源×版本×响应码）
5. **可观测"零负担"的代价**（docs ③ + 发散）：Envoy 默认只采一小部分指标（docs 明确——CPU 开销权衡）——**自动化的另一面是配置复杂度**（采样率/指标扩展）
6. **开源选型五查**（docs + 发散）：Istio 的"大厂背书"正是五查第①④条的体现——**基础设施选型的风险前置**

### 关键决策与权衡

| 决策 | 权衡 |
|------|------|
| 代码内→库→代理→Sidecar→Mesh | 能力外置化（侵入→透明） |
| 网关（南北向）vs Mesh（东西向） | 入口治理 vs 全网旁路（互补并存） |
| Envoy 全流量代理 vs 网关 header 灰度 | 零侵入 vs 应用协作（my-xhs TODO 位置） |
| 自动指标 vs 应用埋点 | 零负担 vs CPU/配置权衡（默认少采） |
| 上 Mesh vs 网关+应用层 | 全覆盖 vs 轻量可控（my-xhs 现状） |

### 常见坑/反模式

1. **灰度"看起来做了"**：header 路由了但 LB 未实现（my-xhs GrayRouteFilter:43 TODO——"看起来在做≠真的实现"）
2. **灰度依赖上游约定**：header 由 CDN/前端设置——网关内不可控（百分比切分缺失）
3. **Mesh 与网关混为一谈**：入口治理 ≠ 全网治理（docs 同异）
4. **全量指标采集**：Envoy 全采 CPU 开销爆炸——默认少采+按需扩展（docs 明确）
5. **采样率不控制**：追踪数据量失控——采样率必配（docs）
6. **选型不看社区/协议**：五查缺失（docs 风险评估）
7. **Mesh 误当银弹**：无网内流量控制诉求也上 Mesh——复杂度白增（KP-08 评估）
