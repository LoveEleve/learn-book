## 二、知识点提取（三层次：需求 / 自主实现 / 参考实现）

### KP-01 Maven 定义与目标
- **维度**：`[工程问题]` | **深度**：🟢 | **优先级**：P2 | **过时**：`[时间无关模式]`
- **前置**：无（最基础）
- **需求**：统一、标准化的 Java 项目构建与依赖管理
- **自主实现**：若自研构建系统，核心是"声明式 POM(项目结构描述) + 生命周期(阶段化执行) + 仓库(依赖共享)"
- **参考实现**：Maven 用 POM(XML)描述项目，目标=简化构建+统一构建系统+高质量项目信息+最佳实践
- **对比取舍**：Maven 是事实标准；Gradle 更灵活但更复杂。训练营基线用 Maven

**基础补充（你画像：Maven 薄弱区）**：
- Maven 解决"Java 项目怎么构建/管理依赖"的痛点。以前用 Ant(每项目手写构建脚本)，Maven 用**约定优于配置**——默认源码在 `src/main/java`、测试在 `src/test/java`、构建产物在 `target/`
- **POM**(Project Object Model) 是项目的"身份证"XML，描述：坐标(artifactId/version)、依赖、插件、模块
- 构建是**生命周期**概念：`validate → compile → test → package → verify → install → deploy`，一条 `mvn install` 走完整条链
- 依赖从**远程仓库**(Maven Central)下载到本地 `~/.m2/repository`，一处下载全局复用

### KP-02 项目继承（Inheritance）
- **维度**：`[工程问题]` | **深度**：🟡 | **优先级**：P1 | **过时**：`[时间无关模式]`
- **需求**：多个模块共享相同配置，避免重复
- **自主实现**：抽取公共配置到父 POM，子模块声明 `<parent>` 继承
- **参考实现**：合并的元素含 dependencies/developers/plugin lists/plugin executions/plugin configuration/resources
- **对比取舍**：继承解决"共享配置"，但不能自动知道子模块

### KP-03 项目聚合（Aggregation）
- **维度**：`[工程问题]` | **深度**：🟡 | **优先级**：P1 | **过时**：`[时间无关模式]`
- **需求**：一次构建多个相关模块
- **自主实现**：父 POM 声明 `<modules>` 列出子模块目录，父 packaging=pom
- **参考实现**：父 POM 指定模块目录；对父执行命令会递归到子模块
- **对比取舍**：聚合解决"一起构建"；继承解决"共享配置"——**两者常同时使用**（microsphere-java 正是这样）

### KP-04 继承 vs 聚合（核心辨析）
- **维度**：`[工程问题]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]`
- **前置**：KP-02 项目继承、KP-03 项目聚合
- **需求**：理解 Maven 多模块的两种组织维度
- **自主实现**：继承=纵向(父子共享配置)；聚合=横向(父管理一批模块)。同时用需三条规则：子指父 / 父 packaging=pom / 父列模块
- **参考实现**：microsphere-java 根 POM 同时是聚合器(`<modules>` 8 个)+ 被 parent 模块继承——两者并用
- **对比取舍**：这是工程化最常混淆的点。本质：继承是"配置复用"，聚合是"构建编排"
- **测试佐证**：microsphere-java 根 pom.xml `<modules>` 列出 parent/dependencies/annotations/core/jdk-tools/test/lang-model/annotation-processor 8 个模块

**基础补充（你画像：Maven 薄弱区）**：
- 用类比理解：**继承**像"类继承"——子类(子模块)自动获得父类(父POM)的公共字段和方法(依赖、插件、属性)，解决**配置去重**
- **聚合**像"一个总文件夹打包管理多个子项目"——父 POM 只是"指挥者"，`<modules>` 列出子模块，`mvn` 对父执行命令会**递归到每个子模块**，解决**一键构建**
- 二者可叠加：一个根 POM 既当父(被继承)又当聚合器(列模块)——**microsphere-java 就是典型**，你读它根 pom.xml 就能看到 `<modules>` 和 `<parent>` 同时存在
- **packaging=pom**：父/聚合 POM 不产出 jar，只是容器，所以 packaging 必须是 `pom`

### KP-05 构建配置 Build Profiles
- **维度**：`[工程问题]` | **深度**：🟡 | **优先级**：P2 | **过时**：`[时间无关模式]`
- **需求**：同一工程在不同环境(dev/test/prod)需要不同参数
- **自主实现**：用 Profile 在构建时修改 POM，为不同目标环境提供参数

### KP-06 可传递依赖与依赖仲裁（Dependency Mediation）
- **维度**：`[工程问题]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]`
- **前置**：Maven 可传递依赖机制（KP-06 之前需理解依赖如何传递）
- **需求**：多模块依赖树中版本冲突时选哪个
- **自主实现**：若我实现，会按"最近定义优先"选版本；显式声明可覆盖
- **参考实现**：Maven 选"最接近的定义"；同深度时第一个声明获胜
- **对比取舍**：仲裁规则是 Maven 依赖冲突的根源，需深刻理解(见 KP-12 冲突场景)
- **待验证**：不同构建工具(Gradle 冲突解决策略)可能不同

### KP-07 依赖管理 Dependency Management
- **维度**：`[工程问题]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]`
- **需求**：统一控制传递依赖/未指定版本依赖的版本
- **自主实现**：在 `dependencyManagement` 声明版本，子模块只需声明 artifactId 不用版本
- **参考实现**：`dependencyManagement` 控制引用时用的版本；是 BOM 的基础机制
- **对比取舍**：这是"版本集中管理"的核心，BOM(见 KP-11)基于它

### KP-08 依赖作用域 Dependency Scope（6 种）
- **维度**：`[工程问题]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]`
- **需求**：控制依赖在哪些阶段可用 + 可传递性
- **自主实现**：若设计作用域，关键是"何时在类路径 + 是否传递"
- **参考实现**：
  - `compile`：默认，全阶段可用，传递
  - `provided`：编译/测试可用，运行时由容器提供，**不传递**（如 Servlet API）
  - `runtime`：编译不需要，执行需要
  - `test`：仅测试，不传递
  - `system`：类似 provided，显式提供 JAR
  - `import`：仅 dependencyManagement 的 pom 类型，导入 BOM
- **对比取舍**：6 种作用域决定可传递性矩阵，是依赖管理的核心概念
- **待验证**：可用 JDK11/17 或 Maven 文档进一步验证可传递矩阵

**基础补充（你画像：Maven 薄弱区）**：
- 作用域本质回答两个问题：**①这个依赖在编译/测试/运行哪个阶段进 classpath？②它会不会传给下游模块？**
- 最常用就 4 个，先记这三个场景：
  - **compile(默认)**：编译+运行都要，且会传给下游。绝大多数依赖用它
  - **provided**：编译时要，但**运行时由容器提供**，且**不传给下游**。最典型：`Servlet API`——你写代码编译要它，但运行时 Tomcat 已经带了，所以不能打包进去也不能传给下游
  - **test**：只在写测试时用（JUnit/Mockito），编译运行都不进
- **可传递** = 你的模块 A 依赖 B，A 的下游(依赖 A 的人)会不会"顺便"也拿到 B。compile 会，provided/test 不会
- 一句话记法：**provided 是"运行时别人给"（容器/JDK），test 是"只有我测试用"，compile 是"默认啥都要"**

### KP-09 依赖排除与可选依赖
- **维度**：`[工程问题]` | **深度**：🟡 | **优先级**：P2 | **过时**：`[时间无关模式]`
- **需求**：控制传递依赖，避免引入不需要/冲突的库
- **自主实现**：`<exclusion>` 排除传递依赖；`<optional>` 标记可选(默认排除)
- **参考实现**：exclusion 显式排除；optional 标记为默认排除(如 Z optional 时 X<-Y，不自动带 Z)
- **对比取舍**：optional 是"默认排除"，调用方可按需显式添加

### KP-10 多模块层次与基础框架工程结构
- **维度**：`[工程问题]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]`
- **需求**：企业级 Java 应用如何组织模块
- **自主实现**：三层结构——**基础设施**(Spring/Tomcat/MQ/Redis/RPC/Search/BigData/Job) + **业务共享模块**(部署近/远端、分类交易/会员/物流/风控) + **业务应用**(聚焦业务领域)
- **参考实现**：小马哥给出三层划分 + 建模(领域模型)/模块(独立/低耦合/高内聚/避免循环依赖)/实现(jar/war/ear/树形依赖)
- **对比取舍**：这是企业工程的顶层设计观。基础设施 vs 业务共享 vs 业务应用三层职责分离

### KP-12 依赖冲突场景与解决

## 六、架构师视角补全（防井底之蛙）

### 完整认知：Maven 多模块工程化在真实架构中完整该讲什么

docs 只覆盖了 Maven 的"机制面"（继承/聚合/仲裁/作用域/BOM）。作为架构师，这个主题完整还该包含：

1. **依赖治理的完整方案**：不只是 BOM，还有 `dependencyManagement` 分层、`enforcer` 插件强制约束（禁止传递依赖冲突/统一版本）、`maven-dependency-plugin` 分析依赖树
2. **工程模板的整体观**：不只是"怎么搭"，而是"**标准约定**"——一个团队/企业统一的模块划分、命名、版本策略约定（这是第 2 节"业务工程模板定制"的前置）
3. **构建性能与可复现性**：`maven.repo.local` 本地仓库、多模块增量构建（`-pl/-am`）、`-T` 并行构建
4. **发布与 CI/CD 衔接**：SNAPSHOT→RELEASE 发布流、`mvn deploy` 到私服（Nexus）、与 Jenkins/GitHub Actions 集成
5. **与容器化/新构建工具的演进**：Gradle、Bazel、Maven 4 的变化；FAT JAR 在容器化后的意义变化

### 关键决策与权衡

| 决策 | 权衡 |
|------|------|
| 继承 vs 聚合 | 继承=配置复用(纵向)、聚合=构建编排(横向)，**通常同时用**（根 POM 兼做两者） |
| BOM 集中管理 vs 各自声明 | BOM 统一版本(一致)但升级不灵活；各自声明灵活但易版本冲突 |
| SNAPSHOT vs RELEASE | SNAPSHOT 更新快但不稳定；RELEASE 稳定但升级慢 |
| 按需复制 API vs 依赖整个 Artifact | 复制 API 降低依赖爆炸(Dubbo 复制 netty、Spring 复制 ASM)，但要维护复制代码 |

### 常见坑/反模式

1. **依赖冲突(版本地狱)**：传递依赖版本仲裁导致实际生效版本与预期不符——用 `mvn dependency:tree` 排查，exclude 或显式声明解决
2. **误用 provided/test 作用域**：把运行时需要的依赖标 provided，导致运行时 ClassNotFound
3. **BOM 版本漂移**：子模块忘了跟随 BOM，各自声明不同版本
4. **直接把 DataSource 等强转成具体类型**（HikariDataSource）：被包装后 instanceof 不成立，要用 unwrap（第 14 节展开）
5. **循环依赖**：模块间 A→B→A，破坏构建——分层 + 依赖倒置解决
