### KP-04 多活概念体系（Source-Replica/同城灾备/同城多活/异地多活）【docs 声明主题——正文发散】
- **维度**：`[分布式理论]` | **权重**：`[核心]` | **深度**：🔴 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：Medium
- **前置**：stage-2 01（CAP）
- **来源**：docs 头部"主要内容"声明（Source-Repica 架构、同城灾备、同城多活、异地多活）——**正文无文字**（图/直播载体）+ 架构师发散
- **需求**：**多活概念体系是本篇核心命题**——docs 声明四个概念但正文缺失：Source-Replica、同城灾备、同城多活、异地多活
- **自主实现**：若我设计——按"**故障面 × 恢复目标**"组织认知：①**Source-Replica（主从）**——一主一从/多从，主故障→从接管（复制机制：binlog/GTID——stage-3 11）②**同城灾备**——同城双机房，主备切换（备份不承载流量）③**同城多活**——同城双机房均承载流量（数据同步：同城专线低延迟）④**异地多活**——跨地域多中心均承载流量（数据冲突/同步延迟是核心难题——饿了么案例）
- **参考实现**（docs 声明 + 发散 + 案例）：**概念定义（发散——docs 正文缺失 `[待验证：docs 图示具体定义]`）**——**Source-Replica（主从复制）**：源→副本单向复制（MySQL 主从——stage-3 11 实证），**故障转移（failover）**需人工/哨兵介入；**灾备（Disaster Recovery）**：备而不活（备用中心不承载流量，恢复靠切换——RTO 分钟~小时级）；**多活（Active-Active）**：多中心均承载流量（**无流量冷备**——切换时流量可立即落在活中心）；**同城 vs 异地（发散）**——同城（专线 RTT <5ms：同步复制可行）/异地（公网 RTT 几十 ms：必须异步+冲突处理）；**衡量指标（发散）**——**RTO（恢复时间目标）/ RPO（恢复点目标——数据丢失容忍）**：灾备 RPO 分钟级/多活 RPO 趋零；**业界实践（发散）**——饿了么异地多活（docs 案例二——单元化路由）、AWS DR 白皮书（docs 案例一——KP-05）、支付宝单元化（LDC——异地多活的国内标杆）
- **对比取舍**：**灾备（备而不活：成本低 RTO 高）vs 多活（全活：成本高 RTO 低）**——RTO/RPO 需求决定形态；**同城（同步复制）vs 异地（异步+冲突）**——延迟预算决定复制策略——**多活不是灾备的别名，是"全部中心可用"的形态**
- **测试佐证**：docs 头部声明（多活四概念）+ stage-2 01（CAP 理论）+ stage-3 11（主从复制机制）+ 案例链接（AWS/饿了么——外部参考）

## 七、跨区域多活完整规划（知识框架——独立于 my-xhs 现状）

> **定位**：my-xhs 单机无多活 ≠ 无知识规划。本节是"跨区域多活该怎么做"的**完整知识框架**（需求 → 自主实现 → 参考实现 → 分阶段路径）——独立于案例载体（08 SOP：知识本体不因现状不需要而缺失）；后续篇（02-04 注册中心面/10-12 负载均衡/14-15 网关/16-17 MySQL/18-19 Redis/22 动态 JDBC）按此框架填细节。

### 7.1 需求层（触发条件——什么业务才做）

| 触发条件 | 说明 |
|---------|------|
| RTO/RPO 诉求 | 灾备分钟~小时级 / 多活趋零（KP-04 衡量尺——银行核心 RPO=0） |
| 合规/监管 | 金融"两地三中心"（监管强制） |
| 营收影响面 | 故障损失 > 多活成本（大促/核心链路不可用损失测算） |
| 地理就近 | 全球/全国业务（用户就近接入——延迟而非容灾驱动） |

### 7.2 自主实现层（六步设计——若我实现）

1. **区域拓扑**：Region（地理）→ AZ（故障域）两级切分（02 篇 KP-05 机制）；同城（专线 RTT<5ms——同步复制可行）vs 异地（>30ms——必须异步）
2. **数据面分流**：按数据性质选一致性——注册元数据（AP——客户端缓存兜底，02-04 篇）、配置（CP——Raft，03 篇）、业务数据（MySQL 异地复制 16-17 / Redis 异地 18-19 / 消息跨区）
3. **流量路由**：DNS/GSLB 就近解析 + 网关路由（14-15 篇）+ 客户端区域感知（04 篇 KP-05）——就近优先 + 故障转移
4. **冲突处理**：**单元化（按用户/业务分片——Set）** = 异地多活的冲突解法（各单元只写自己分片，跨单元异步/最终一致——阿里 LDC/饿了么同思路，KP-05）；双向同步+冲突解决（时间戳/版本）工程上罕见且危险
5. **故障转移**：区域级切换（健康探测 → DNS TTL 调整 → 数据回切）——**RTO 由切换自动化程度决定**（手工切换=小时级；自动化=秒~分钟级）
6. **演练常态化**：故障演练/混沌工程（大促前演练——行业文化；结营篇阿里云事故的教训面）

### 7.3 参考实现层（业界实践——主流性选择）

- **AWS Multi-Region**（docs 01 案例一）：DR 策略阶梯（Backup & Restore → Pilot Light → Warm Standby → Multi-site Active/Active——KP-05）
- **阿里单元化 LDC**（逻辑数据中心）：Set 化分片 + 异地单元化单活——国内异地多活标杆
- **饿了么异地多活**（docs 01 案例二）：单元化路由实践（KP-05）
- **两地三中心**（金融行业标准）：同城双活 + 异地灾备——监管驱动形态
- **注册中心面**：区域隔离（02 篇）+ 双模（03 篇）+ 客户端区域感知/按需订阅（04 篇）——**本篇规划框架下已提取**
- **数据面**：MySQL 多活（16-17 篇——docs 顺序待提取）、Redis 多活（18-19 篇待提取）

### 7.4 对比取舍

| 决策 | 权衡 |
|------|------|
| 同城多活 vs 异地多活 | 延迟预算（同步复制可行）vs 故障域覆盖（必须异步+冲突） |
| 单元化（异地单活） vs 全量多活（异地全活） | 冲突处理复杂度 vs 全地域读写能力 |
| 同步复制 vs 异步复制 | 数据零丢失（RPO=0）vs 延迟/可用性 |
| 异地灾备 vs 异地多活 | 成本低/RTO 高 vs 成本高/RTO 低 |

### 7.5 分阶段路径（触发条件驱动——my-xhs 生产化时按此演进）

```
阶段 0：单机房高可用（主从/哨兵——my-xhs 现有：Source-Replica ✅）
   ↓ 触发：RTO 诉求出现
阶段 1：同城灾备（备份 + 恢复演练——RPO 分钟级）
   ↓ 触发：同城延迟预算（专线）
阶段 2：同城双活（同步复制——多中心承载流量）
   ↓ 触发：异地覆盖诉求（合规/营收）
阶段 3：异地单元化（用户分片 + 异步 + 路由——RTO 秒级）
```
每阶段配套：注册中心集群化（02/03 篇差距项）→ 按需订阅（04 篇）→ 数据面多活（16-19 篇）→ 可观测/演练（stage-3 三件套）。

**本节结论**：跨区域多活是**完整的知识域与工程规划**（六步设计 + 业界参考 + 分阶段路径）——my-xhs 单机不触发**只是现状**（B2 核对），知识规划在 01 篇立框架、后续专篇填细节。

### 完整认知：多活架构基础的完整认知该讲什么

docs 是图驱动的开场课。完整还该包含：

1. **"多活是容灾的最高形态，不是唯一形态"**（发散）：容灾阶梯——**备份（Backup）→ 灾备（Standby）→ 多活（Active-Active）**；先想清楚 **RTO/RPO 预算**再选形态（银行核心 RPO=0 必须多活/同步复制；内容网站 RPO 分钟级可接受灾备）——**成本与恢复目标的正比关系**
2. **"Source-Replica 是所有容灾的地基"**（发散 + stage-3 11）：主从复制（binlog/GTID）贯穿全部形态——灾备是"备中心不活"，多活是"副本也能写"——**复制机制本身不产生多活，多活要在复制之上解决双向一致**
3. **"同城 vs 异地的分界线是物理定律"**（发散）：光速延迟——同城专线 RTT 亚毫秒~几毫秒（同步复制可行），异地公网 RTT 30-100ms（**异步复制 + 冲突处理是唯一选择**）——**为什么异地多活难：不是网络，是冲突**
4. **"单元化是异地多活的路由解法"**（发散）：按用户/业务分片（Set/单元），每个单元在同城对可用、异地单活——**"异地多活"工程上常退化为"异地单元化单活"**（支付宝 LDC/饿了么单元化）；docs 案例二（饿了么）即此路线
5. **"多活的适用边界"**（发散）：多活是**高成本工程**（数据中心/专线/冲突处理/路由）——**绝大多数业务用不到**；触发条件：故障影响面（营收/合规）> 多活成本时才值得——**my-xhs 单机是合理的教学形态**（KP-06）
6. **"演进五阶段与多活的定位"**（docs 标题 + 发散）：docs 把多活列为演进终点——**更准确的定位**：多活是**部署形态维度**（与拆分粒度正交——单体也能多活，微服务也能单机房）；小马哥 stage-4 主题 = "多活架构"，01 篇是概念基座，02 篇起进入 Eureka/负载均衡/网关/MySQL/Redis 的具体多活实现

### 关键决策与权衡

| 决策 | 权衡 |
|------|------|
| 备份 vs 灾备 vs 多活 | 成本递增，RTO/RPO 递减（恢复目标驱动） |
| 同城 vs 异地 | 专线延迟预算（同步复制 vs 异步+冲突） |
| 灾备（备不活） vs 多活（全活） | 切换成本 vs 流量即达 |
| 单元化（异地单活） vs 全量多活（异地全活） | 冲突处理复杂度 vs 全地域读写能力 |
| Source-Replica（主从） vs 多活（双向） | 单向复制简单 vs 双向一致复杂 |

### 常见坑/反模式

1. **把灾备当多活**：备中心不承载流量 = 灾备（切换有时间窗），不是多活——**"多活"的字面陷阱**
2. **多活先行不评估 RTO/RPO**：没有恢复目标就上多活 = 为不需要的指标付全价
3. **异地直接同步复制**：跨地域延迟下同步复制 = 每次写等 100ms——**必须异步**
4. **忽略数据冲突**：多活最难的不是"多中心部署"而是"多中心写同一份数据"——单元化/分片是正道
5. **Source-Replica 误当高可用终点**：主从复制只是复制，主故障切换（哨兵/人工）才是可用性动作（stage-3 11 交叉）
