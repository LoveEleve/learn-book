> **来源标注**：docs 为极短篇（19 行）——头部声明 2 路线 + 3 交叉引用 + 1 链接；知识本体 = 声明 + 架构师发散 + 已提取篇交叉；"docs 明确内容"vs"架构师发散"如下。

### 完整认知：优化 Eureka Server 多活的完整认知该讲什么

docs 只有两行声明。完整还该包含：

1. **"注册中心同步协议是路线谱系（AP 双线 + CP 面）"**（发散 + stage-3-08）：**AP 面**——P2P 全复制（Eureka 原生）→ JGroup 组播（2016 前后探索——网络层扩散）→ **TCP 增量同步（Distro——现代主流）**；**CP 面**——Raft 共识（独立维度——docs 路线②）；docs 路线①（JGroup）已是历史探索（stage-3-08 标注过时方向），**本篇真正价值在路线②（Raft/CP 面）**
2. **"AP/CP 双模是 Nacos 的差异化设计"**（docs 路线② + Nacos 实证）：Eureka 纯 AP（注册场景好但元数据弱一致）、ZK/etcd 纯 CP（一致但分区不可用）、**Nacos 双模（按数据性质分流——注册 AP/配置 CP）**——docs"增加 CP 模型"的改造思路与 Nacos 设计殊途同归；**行业整体是分化态**（AP vs CP 二分），**双模（AP 主面 + CP 辅面）是 Nacos 独有答案**
3. **"改造 vs 换组件"的工程判断**（发散）：docs 思路是"给 Eureka 打补丁"（JRAFT 集成）——**现实工程更常见"换组件"**（Nacos 内建双模）——**改造成本 vs 迁移成本的决策**；D3 纪律正是此判断（不搞 Eureka——Nacos 现成）
4. **"强一致的注册中心要付出什么"**（发散）：Raft 多数派（3 节点可用、写需多数确认）——**CP 面可用性下降**（n/2+1 才可用——stage-2 02 交叉）——**双模的价值 = 把 CP 成本只付给需要强一致的元数据**（配置/持久服务），注册流量走 AP 免于多数派开销
5. **"单实例阶段无模型之争"**（发散）：my-xhs 单 Nacos——AP/CP 之分在**多副本时才有意义**（单节点既强一致也高可用）——**双模设计是"多活规模"的决策，教学阶段不触发**（03 篇现状合理）

### 关键决策与权衡

| 决策 | 权衡 |
|------|------|
| P2P 复制 vs JGroup 广播 vs Raft 共识 | 简单性 → 扩散效率 → 强一致（复杂度递增） |
| 纯 AP vs 双模 vs 纯 CP | 注册可用性 vs 元数据一致（按数据分流） |
| 改造 Eureka（JRAFT 集成） vs 换 Nacos | 存量兼容 vs 内建双模（迁移成本） |
| CP 面多数派 | 强一致 vs 可用性（n/2+1 阈值） |

### 常见坑/反模式

1. **注册中心全 CP**：注册流量走多数派 = 无谓开销 + 分区不可用（注册场景 AP 足矣）
2. **元数据无强一致**：配置/持久服务弱一致 = 脑裂/丢数据（CP 面该付的成本）
3. **改造存量组件**：给 Eureka 集成 Raft 的复杂度 vs 换 Nacos 的迁移成本——先算账
4. **双模混为一谈**：AP/CP 是**按数据性质分流**，不是"一个集群两个协议都走"
5. **单实例讨论模型**：单节点无 AP/CP 之分（多活规模才触发）
