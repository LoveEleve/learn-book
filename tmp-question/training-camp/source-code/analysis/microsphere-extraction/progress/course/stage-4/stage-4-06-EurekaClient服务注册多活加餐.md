### KP-01 多注册中心类型组合（同构 vs 异构——docs 唯一内容）
- **维度**：`[分布式问题]` | **权重**：`[核心]` | **深度**：🟡 | **优先级**：P1 | **过时**：`[时间无关模式]` | **置信度**：High
- **前置**：05 篇（多注册机制）
- **来源**：docs §Spring Cloud 实现多服务注册（docs:16-22——两行分类照录）
- **需求**：**多注册中心的两种组合形态**——docs 明确：**相同类型**（2 Nacos 或 2 Eureka——docs:19）+ **不同类型**（Eureka + Nacos / Eureka + Nacos + Consul——docs:22）
- **自主实现**：若我设计——多注册组合按"组件同构性"分类：同构（同产品多集群——协议一致）/异构（多产品混合——协议/能力差异）
- **参考实现**（docs 两行照录 + 发散）：**docs 分类（照录）**——①**相同类型**：2 Nacos 或 2 Eureka（同产品多集群/多环境）②**不同类型**：Eureka+Nacos（双注册）或 Eureka+Nacos+Consul（三注册）；**同构 vs 异构的工程含义（发散）**——**同构多注册**：同一产品多集群（多机房各一套 Nacos/Eureka）——协议一致、合并机制简单（05 篇拦截器/Composite 通用）；**异构多注册**：不同产品并存——**协议/元数据/健康语义差异**（Eureka 心跳租约 vs Nacos 临时实例 vs Consul Raft）——**合并靠 Spring Cloud DiscoveryClient 统一抽象**（04 篇 KP-02——接口屏蔽差异）+ **元数据兼容问题**（各注册中心元数据模型不同——灰度标记/权重等语义不互通）
- **对比取舍**：**同构（简单合并）vs 异构（抽象统一）**——协议一致 vs 能力差异——**异构多注册是 DiscoveryClient 抽象存在的意义**（Spring Cloud 统一接口的价值场景）
- **机制/说明**：类型组合决定了合并实现的复杂度——同构=纯合并（结果并集）；异构=抽象层兼容（每个注册中心一个 DiscoveryClient 实现——spring-cloud-commons 的 SPI 生态：EurekaDiscoveryClient/NacosDiscoveryClient 都是同一接口的实现——**stage-3 07 NacosDiscoveryClient 实证**）；**同构多注册的 Nacos 内建形态（源码实证——D3）**——Nacos 客户端**单实例多 serverList**（`NacosNamingService.java:57/76-77` + `NamingServerListManager.java:44/96/102` 轮询切换——05 篇 KP-01 已补）——**"2 Nacos"同构组合在 Nacos 生态 = 客户端配置多 server 或集群形态，无需多 DiscoveryClient**——**docs 的"组合分类"在 Nacos 是配置面/集群面而非客户端组合面**

### 完整认知：多注册中心的完整认知该讲什么

docs 只有两行分类。完整还该包含：

1. **"多注册的类型组合 = 诉求的镜像"**（docs 分类 + 发散）：**同构**（2 Nacos/2 Eureka）——多机房/多环境的同产品部署（跨域诉求）；**异构**（Eureka+Nacos(+Consul)）——**迁移过渡期**（换注册中心期间双注册并存——架构师推断场景，docs 未提用途）或**多云/多技术栈并存**——**组合形态暴露了业务诉求**（隔离/迁移/多云）
2. **"异构多注册是 DiscoveryClient 抽象的存在意义"**（发散 + stage-3 07）：Spring Cloud 的 DiscoveryClient 统一接口 + SPI 实现（EurekaDiscoveryClient/NacosDiscoveryClient/ConsulDiscoveryClient）——**正是为异构注册中心准备的**（04/05 篇机制：Composite 组合 + 拦截器合并）；没有抽象层，异构合并无法实现——**抽象的价值在异构场景兑现**
3. **"注册中心间无内建同步"**（发散——注册侧 docs 为 TODO，双写为推断）：多注册的注册/发现是**客户端双写双读**（注册双发 + 发现合并）——各注册中心独立维护（与 02 篇"区域间不交流"同哲学：**注册中心各自为政，客户端负责合并**）——**一致性靠客户端，不靠注册中心间协议**
4. **"迁移过渡是双注册最常见场景"**（发散）：注册中心替换（Eureka→Nacos/Consul 等）的标准操作 = **双注册并存 → 验证 → 移除一方**——docs"Eureka+Nacos"组合的工程定位；**退出机制**（移除一方）是过渡期必做的收尾（否则长期双注册成本）
5. **"多注册不是高可用的免费午餐"**（发散）：多注册 ≠ 注册中心高可用（那是集群化——02/03 篇）；多注册是**跨域可见性**手段——**两者区分**：集群化（同产品内高可用）+ 多注册（跨产品/跨域可见）
6. **"my-xhs 单注册的合理性"**（发散）：单 Nacos 单实例是教学形态——多注册的触发条件（跨域/迁移）未出现——**学机制、看触发、不照搬**（08 SOP 核心视角）

### 关键决策与权衡

| 决策 | 权衡 |
|------|------|
| 同构 vs 异构多注册 | 协议一致简单 vs 抽象统一（按诉求选） |
| 客户端双写双读 vs 服务端同步 | 简单可靠 vs 中心化复杂（注册中心间无内建同步） |
| 迁移过渡双注册 | 平滑迁移 vs 双份维护成本（需退出机制） |
| 多注册 vs 集群化 | 跨域可见 vs 同产品高可用（两者不同目的） |

### 常见坑/反模式

1. **异构组合当同构处理**：协议/元数据差异未抽象——合并后元数据语义错乱（灰度标记/权重不互通）
2. **双注册无退出机制**：迁移过渡期拖成长期双维护（成本翻倍）
3. **多注册当高可用**：多注册解决跨域可见性，不是注册中心高可用（高可用靠集群化——02/03 篇）
4. **docs 重复声明重复提取**：加餐与 05 篇头部声明相同——交叉引用不重提（06 纪律——本篇实践）
5. **单注册场景过度设计**：无跨域/迁移诉求时谈多注册 = 复杂度白增（触发条件判据）
