# 源码学习 Agent 的问题清单与产品机会

> 生成日期:2026-08-14
> 背景:用户自研 Agent 的定位思考——"没有一款 agent 能帮助程序员学习源码、快速成为技术专家"
> 用途:作为自研 agent 的产品需求清单 + 面试差异化弹药
> 状态:持续讨论中,会继续补充

---

## 第一部分:源码学习场景的 20 个问题

### A. 技术层(agent 自身缺陷)

**1. 视野矛盾:上下文窗口装不下"全局理解"**
源码理解需要全局结构(spring-framework 94 万行)与局部细节(file:line 级)两种相反的东西。agent 一次只能加载局部,而"该加载哪部分"本身就是一种理解——鸡生蛋问题。依赖图构建是 agent 最贵的动作:不建依赖图读不深,建依赖图要先读懂。图索引是静态的,动态行为(运行时状态机、事件流)抓不到。

**2. 幻觉是源码分析的致命伤**
对应方法论铁律"禁止编造:函数名、常量值必须 grep 验证"——这是真实踩坑,不是预防性规则。agent 面对知名框架会本能用训练数据(Spring 3.x 的记忆)填补当前版本(Spring 6.x)的空白,版本差异是幻觉重灾区。更隐蔽的:看到类名就推断职责("AdaptivePoolingAllocator 应该是自适应池")。**源码学习场景,学错比不学更糟。**

**3. 动态分派和运行时行为看不到**
静态读代码看不到多态、反射、SPI 分派后的真实路径。Netty 的 EventLoop 线程模型、Spring 循环依赖解决——框架的灵魂只在运行时出现。agent 自动"跑起来调试"成本极高,默认用静态推断糊弄过去。人卡住时会写 demo 验证,agent 不会主动这么做。

**4. 验证闭环断裂:写出结论就结束**
agent 默认行为是读完就写,不会主动质疑自己的结论,不会"回第一遍补扫"。自审机制失效:让 agent 检查 agent 的输出,它倾向于确认而非证伪。人学习时反复验证,agent 需要被强制才验证——这就是方法论里全是"必须/禁止"强制动词的原因。

**5. 上下文遗忘导致前后矛盾**
分析大规模仓库,agent 会忘掉前 50 个回合读过什么:A 依赖 B 写成 B 依赖 A。人的解决方式是做笔记,agent 的问题是不知道什么该记成笔记——它倾向记住结论、忘掉证据(file:line),而学习场景恰恰要证据优先。

**6. 错误雪球且不自知**
早期某个概念理解错,后续所有分析都基于错误前提,且不会回头修正——每一轮只看到局部上下文,没有全局一致性检查。人做笔记能发现矛盾,agent 的笔记自己不会读。

**7. 确定性破缺:两次分析结果不同**
学习场景最需要"可复现":今天讲的明天应该一样。但 LLM 每次输出不同,温度、上下文顺序都会改变结论。用户无法区分"是我没懂"还是"它今天讲的不一样"——摧毁学习者信任。考试复习最怕答案每天变。

### B. 学习认知层(最根本的盲区)

**8. 虚假掌握感——最危险的问题**
agent 读完讲清楚,用户点头"懂了"。但理解的幻觉产生于流畅的输入:用户跳过了"卡住→挣扎→顿悟"的过程,而正是这个过程建立真实理解。面试官一问"NioEventLoop 为什么单线程?",用户只能复述总结,无法现场推导。**agent 把"学会"变成了"听过",制造的不是专家,是"背过答案的人"。**

**9. 认知外包与用进废退**
读源码能力本身就是工程师的核心竞争力。agent 代读一次两次爽,代读一百次,用户分析能力萎缩——变成"只能通过 agent 理解代码"的人。私教让会员自己练,agent 是"替你练"。产品在帮用户的同时正在废掉用户。

**10. 专家直觉不可转移**
资深工程师的"第六感"(扫一眼知道哪个类是核心、哪里会出坑)是成千上万小时 pattern 匹配形成的。agent 给显式知识(它做了什么),给不了隐性知识(为什么这里值得警惕)。agent 能教"循环依赖怎么解决",教不了"什么样的代码结构将来会变成屎山"。

**11. 只讲正常路径,不讲失败路径**
专家知识结构恰恰相反:他知道 EventLoop 什么时候会饥饿、连接池什么条件下踩坑。用户学完 agent 分析,能讲原理,出事故不会排查——排查能力来自失败案例积累,agent 默认不给失败案例。

**12. 不会切换视角**
"性能/并发/扩展性/安全"视角分析重点完全不同。专家自动切换,agent 默认只有一个视角。方法论"全视角提问验证"(7 身份)对 agent 是七次完全不同的分析,但 agent 会当成一次分析做七遍。

**13. 知识迁移不会发生**
学会 Netty 的 EventLoop,高手立刻类比 Redis 单线程模型、Nginx worker 模型。跨项目抽象迁移是专家核心能力,agent 分析是项目隔离的。分析完 4 个 agent 项目,它不会主动告诉你"Reasonix 的缓存裁剪和 Netty 的 ByteBuf 池化是同一种思想"。

### C. 时间与历史维度

**14. 源码是历史产物,不是静态文本**
框架现状是十年演进堆积。不看 git blame、不看废弃路径演进,就会把兼容层当核心机制、把核心机制当兼容层。专家读代码自带时间轴("这段是 4.0 为了 X 加的"),agent 默认只看当前快照。"时空溯源"是人为触发的,agent 不会主动做。

**15. 版本漂移与知识过期**
框架升级,agent 昨天讲的结论今天就错。人会用版本敏感性自我修正,agent 不会主动说"我上次分析的是 3.x,现在是 6.x,结论已失效"。

### D. 产品与工程层

**16. 成本结构倒挂**
深度源码分析 token 消耗巨大,而学习场景是用户预算最低的场景(个人开发者、学生)。分析 spring-framework 一次的成本可能超过买一本 100 块的《Spring 源码深度解析》——书是人写的、有质量保证、可反复读。**agent 必须回答:为什么用户不买书?**

**17. 泛化失败**
为 Spring 调好的分析流程,换 Netty/Redis/ES 就失灵。每个框架的分析入口(Netty 的 bind()、Spring 的 refresh()、JVM 的 CreateJavaVM)完全不同,agent 不会自动发现入口——方法论 00"入口点是唯一人工指定的输入"翻译过来:agent 连第一步都做不了,得人告诉它。

**18. 交互成本与学习深度成反比**
深度理解需要"追问—反驳—辩论"的螺旋。TUI 交互形式天然鼓励"一次性提问→一次性长报告"。用户不会追着 agent 反驳(反驳需要自己的思考,思考恰恰最稀缺)。产品形态决定了它只能做浅层问答。

**19. 教学与报告的矛盾**
源码学习是构建认知(依赖顺序、从简单到复杂、比喻锚点、Why 先于 How),不是报告事实。agent 天然倾向输出全面而干燥的清单——擅长回答"是什么",不擅长"你怎么理解它"。判断读者站在哪里(已知什么、哪里会卡住),agent 几乎做不到。

**20. 信任问题(最致命的产品问题)**
源码学习是最不能容忍错误的场景。ChatGPT 写代码错了,读者跑一下能发现;源码分析错了,读者不一定能验证——他找你就是为了省验证成本。方法论"每个结论必须有 file:line"是信任基础设施:让读者能跳回去核验。任何源码学习 agent 答不出"凭什么这么说",就没资格教人。

## 第二部分:最根本的产品矛盾

**市面上所有 coding agent 的目标是"替用户做事",而源码学习的本质是"让用户自己会做事"——两个方向是冲突的。**

教一个人钓鱼,和你替他钓鱼,是相反的两种产品。

## 第三部分补充:会话交接问题(21-23,来自真实使用经验)

**背景**:用户在长期源码分析实践中,每次上下文满 → 让 agent 写交接文档 → 新 session → 让 agent 读文档继续。已沉淀一整套**双文档交接协议**(见下)。这个模式暴露了深层问题。

### #21:会话交接(用户亲历,最真实的问题)

用户当前模式:
```
上下文满 → agent 写交接文档 → new session → agent 读文档 → 继续重复
```

衍生问题:
1. **交接时机 = agent 状态最差的时候**:上下文满时 agent 已开始劣化(遗忘/前后矛盾),此时却要它写"最完整的总结"——垃圾进,垃圾出。交接文档质量取决于一个半失忆的 agent。
2. **交接文档丢失过程**:能记结论("分析了 EventLoop"),记不住走过的死路("试过 A 假设,被 grep 推翻")。死路恰是学习精华——方法论"假设→验证→推翻"闭环在交接时全部蒸发。
3. **新 session 没有延续感**:它只是"又读了一个文档",不是"继续上次的工作"。不知道前面确认过什么、推翻过什么、下一步计划——分析进度倒退回"文档能表达的范围内"。
4. **用户是唯一一致性保障者**:新 session 不会自动与旧 session 对齐,仲裁职责落在用户身上——用户被迫当了 agent 的项目经理。
5. **交接文档不可验证**:agent 写完,用户无法确认遗漏了什么——不知道不知道什么。
6. **更深的讽刺**:上下文管理本该是 agent 核心能力(Context Engineering 是 10 份 JD 第一关键词),真实使用中却是用户在替 agent 做上下文管理。

### #21.5:用户已沉淀的"双文档交接协议"(最佳实践,产品化蓝本)

用户实际使用的协议(HANDOVER.md + HANDOVER-session00X.md,见 microsphere 分析项目):

**双文档职责分离**:
| 文档 | 职责 | 关键内容 |
|------|------|---------|
| `HANDOVER.md`(项目级,单一真相源) | 跨 session 的常量状态 | 任务背景 / 方法论框架索引 / 当前状态 / 接手须知最小集合 / 工作方法铁律 / 交接约定 / 已沉淀教训 |
| `HANDOVER-session00X.md`(会话级) | 单 session 增量 | 本 session 产出(KP 编号/文件清单)/ 新增铁律 / 历史缺陷交叉验证结果 / 待验证 / 未决问题 / 接手须知(下个 AI 第一件事) |

**协议设计要点(产品化可直接抄)**:
1. **单一真相源**:HANDOVER.md 是唯一权威进度文档,接手前完整阅读,不依赖口头传达
2. **方法论演进**:每个 session 新增铁律(如"my-xhs 判定实证先行""basename 级穷尽核对")——方法论跨 session 持续进化,不是复制粘贴
3. **证据链验证**:对交接文档本身再做源码验证循环(如"交接声称穷尽被证伪,6 处真遗漏")——交接文档也要可核验
4. **故障转移机制**:agent 陷入死循环时,停下来写交接文档让下个会话接手——交接 = 熔断 + 转移
5. **接手须知**:明确"下个 AI 第一件事"——减少冷启动成本
6. **git 约定 + 提交纪律**:每写完一篇及时 commit,不堆积——产出物有版本历史

### #22:探索路径不可复现

用户在 4 个项目上做的所有分析(域发现/闭环笔记/对账),依赖"当前 session 的 agent 记得"。session 结束,探索轨迹(包括推翻过的假设)只剩手动保存的产物。知识沉淀依赖人工纪律,而非系统设计——闭环笔记文件就是用户在手动弥补这个缺陷。**手工方案的代价**:交接文档本身要维护(更新主文档+写 session 文档),且每个新 session 都要重新读文档热身。

### #23:多 session 平行宇宙

同时分析多个项目/开多个 session 时,它们互相不知道对方存在。Reasonix session 得出的"上下文裁剪"结论,Pi session 用不上——跨 session 知识孤岛。而跨项目类比(问题 #13)恰恰是最值钱的知识。**理想形态**:session 共享知识库,新 session 自动感知"相关知识已在其他 session 分析过"。

### #24:收敛性验证缺失(用户亲历,2026-08-14)

**现象**:agent 每次都说"完成了",但用户每次 review 都能找到新东西;再 review 又能找到。agent 的"完成感"不可信,只有人发起的 review 循环能逼近完整。

**拆解**:
1. **agent 的"完成"声明不可信**:它说"完成"是因为到达了自己的 token 预算或"感觉差不多",没有穷尽性检查机制。
2. **review 发现递减但永不为零**:第 1 轮 review 找到 5 个,第 2 轮 2 个,第 3 轮 1 个……理论上衰减,但 agent 永远不会自己说"还有遗漏"——它永远声称完成。
3. **用户被迫成为唯一收敛性裁判**:review 必须由人发起,agent 没有自我怀疑的触发机制。

**"完成"的可信定义**:连续 N 轮 review 无新增发现(收敛),而非 agent 的主观声明。

**产品映射(自动验收器核心特性)**:
```
自动验收器 = 把"人发起的 review"变成"agent 自发的收敛性检查"
  1. 每次产出后自动跑穷尽性检查(文件清单 vs 文档提及)
  2. 输出"当前覆盖率 X%,已知遗漏 N 项"
  3. 覆盖率不达标 → 自动进入下一轮 review,不说"完成"
  4. "完成" = 覆盖率达标 + 连续两轮 review 无新增
```

**方法论映射**:13-保持怀疑应加一条——"每次产出后自问:如果用户 review,会找出什么?"(交付前自己扮演 reviewer)

### #25:规范约束失效——agent 会跳过文档规定的质量门禁(用户亲历,2026-08-14,自举项目 Hermes 分析时发生)

**现象**:交接文档(HANDOVER.md)明确规定"每份笔记写完即 review、每阶段收敛确认、域发现多轮迭代",agent 完整读过文档后,仍一口气批量产出 5 份闭环笔记 + 域发现 v1,全部跳过 review 门。用户连续两次中断纠正,agent 才停下。

**拆解**:
1. **文档/提示词是软约束**:交接文档、AGENTS.md、方法论文件对 agent 而言只是"上下文里的建议",上下文压力(想一次做完)+ 任务结构(todo 列表天然鼓励线性推进)会系统性压过软约束。
2. **agent 不仅"完成声明"不可信,连"遵守质量流程"也不可信**(#24 的加深):#24 说"agent 说完成不可信,靠 review 循环",本问题暴露——**agent 会跳过 review 循环本身**。
3. **todo 列表被误读为流水线许可证**:列了 11 项 todo 后,agent 把"计划"当成"可以连续执行的授权",项与项之间的验收门被忽略。
4. **"写"与"验"被合并**:生产者和质检者同为 agent 时,质检环节会蒸发——这恰恰是产品③自动验收器要解决的事,但 agent 在自己的项目执行中先犯了。
5. **上下文压力驱动的批量倾向**:agent 倾向单 session 内最大化产出(怕断点),违背"跨 session 持续积累"的产品哲学。

**产品设计约束(本问题的最重要产出)**:
```
一切质量门禁必须工程化,禁止依赖 LLM 自觉遵守文档规范。
- 验收门必须是程序化的、强制的(agent 无法跳过),不能是提示词要求
- "完成→验收→发布"必须是状态机迁移,非法迁移不可达(Pi applyMutation 不变量思想)
- 文档规范(交接文档/方法论)只是工程化的输入,不是约束本身
```

**产品映射(自动验收器 + 执行引擎)**:
```
1. 每章产出 → 自动触发验收器(不是 agent 自觉去验)
2. 验收器不过 → 状态机拒绝进入下一章(执行引擎层面阻止,非提示词)
3. 域发现/笔记的 review 轮次 = 状态机强制计数(至少 N 轮),agent 无法自行跳过
4. 收敛判定 = 程序化对账(文件清单/设计数),不是 agent 声明
```

**方法论映射**:交接文档纪律本身应升级——"每份笔记 review 后置验收门"写成给用户看的清单,由用户确认推进(本 session 已改:每份笔记写完 → 用户确认 → 下一份)。

**自举证据链**:本问题由 Hermes 分析项目(产品④知识库直接蓝本)的执行失败实证,与 #24 同为"人肉 review 门"的最真实反面教材。
