## 一、最终目标(修正)

**做出一个"源码学习 Agent"——输入"帮我分析 JVM 源码",对齐后自主跑完,产出一本好书。**

面试只是顺带:做出来的东西本身就是作品、简历、谈资。方法论是工程规范,不是面试工具。

```
核心目标: 做出来(能跑、能产出书级作品)
支撑手段: 方法论(工程规范,防编造/防跑偏)
副产品:   面试弹药(作品 + 第一手失败案例 + 架构理解)
```

---

## 二、为什么是这个产品(动机回顾)

1. **没有任何一款 agent 能帮程序员学源码成为专家** — 市场空白
2. **现有 agent 全是"人肉驱动"**:必须人坐在电脑前,输入→等→评估→再输入
3. **用户亲历的 23 个问题** → 每个问题都是产品需求
4. **用户已手工验证过全部关键机制**:G0 盘问(对齐)/ 铁律(契约)/ review 门(验收)/ 交接文档(知识库)——**做的是工程化,不是发明**

## 二.5 产品定位澄清(重要)

**产品 = 通用的源码学习 Agent,不是"agent 分析器"。**

- 分析对象:任意源码——JVM、Redis、Netty、Docker、Spring、agent 框架……一切
- 4 个 agent 项目(Pi/Reasonix/Hermes/OpenCode)只是**第一批自举样本**(碰巧是 agent 领域):
  - 用途 1:打磨方法论流程(域发现/完备性/验收机制)——练手验证
  - 用途 2:沉淀 agent 领域骨架(骨架库的第一份)
  - 用途 3:给自研 agent 抄架构(产品设计蓝本)
  - **不是产品对象本身**
- 第一个实战目标:**OpenJDK**(用户已在写 OpenJDK 书,机制跑通后直接用它验证闭环)

---

## 三、产品定义

### 3.1 一句话

> 源码学习 Agent:对源码进行"对齐 → 执行 → 验收"的自主分析引擎,产出书级学习作品。

### 3.2 用户场景(目标体验)

```
用户: "帮我分析 JVM 源码"(废话级输入)
  ↓
对齐: agent 引导 6 维盘问(带推荐+科普,初学者也能答)
  ↓ 产出规格书
执行: agent 自主一直跑(解决 7 卡点,无需人在场)
  ↓
验收: 每章自动对照规格书,不过就自修
  ↓
交付: 一本写给目标读者的书(跨 session 连贯)
```

### 3.3 核心矛盾(产品哲学)

**现有 coding agent 替用户做事;源码学习 agent 让用户会做事。** 这个矛盾决定了产品形态:
- 输出不是"答案",是"可核验的知识结构"(file:line 证据链)
- 交互不是"代读",是"引导用户思考"(费曼测试、留白)
- 不是一次性 demo,是**跨 session 持续积累的作品生产线**

## 四、产品架构(四组件)

```
┌────────────────────────────────────────────────────────────┐
│                     源码学习 Agent                           │
├──────────────┬──────────────┬──────────────┬───────────────┤
│  ① 对齐模块   │  ② 执行契约  │  ③ 自动验收器 │  ④ 书级知识库  │
├──────────────┼──────────────┼──────────────┼───────────────┤
│ 引导式 6 维   │ 规格书 schema │ 章节对照检查  │ 跨 session 记忆 │
│ 盘问(三档提问)│ = 执行许可证   │ = 自动化 review│ = 交接协议工程化│
└──────────────┴──────────────┴──────────────┴───────────────┘
```

### 组件① 对齐模块(核心设计,6 维 × 三档提问)

**6 维**:对象与版本 / 目标 / 深度分层 / 学习者画像 / 边界排除 / 产出形式

**三档提问(D12)**:
| 档位 | 谁答 | 示例 |
|------|------|------|
| A 档 | agent 自查,不出现 | 版本、入口点、源码位置(README/build) |
| B 档 | 推荐 + 证据 + 确认 | 平台→Linux(生产 99%);深度→按画像 |
| C 档 | 用户决策(给选项) | 目标:写书/面试/自用;时间约束 |

**对齐 = 科普 + 确认,不是收集答案**。初学者不知道怎么学 → agent 的每个推荐都是教学点。
⚠ 不逼用户指定入口点(D13:agent 自发现)、不空手问(D14:问必带推荐)。

### 组件② 执行契约(规格书 = "敢一直跑"的许可证)

解决 7 卡点中的:完成判据 / 权限预授权 / 意图漂移锚点 / 边界约束

```
规格书内容(对齐产物):
├── 对象/版本/入口点(agent 自查)
├── 目标与学习者画像(写书给初学者)
├── 深度分层(🔴 A 全深度 / 🟡 B 标准 / D 扫描)
├── 域清单 + 排除清单(不碰 Windows 分支——D10 Linux 基准)
├── 章节计划(概念依赖拓扑序)
├── 验收标准(每章:覆盖哪些 KP / 写给谁 / 深度要求)
└── 边界权限(禁止:删文件/推送/改配置)
```

### 组件③ 自动验收器(把 review 门从人肉变程序)

原方法论每篇 review 门是人工;产品把它程序化:
- 章节完成 → 对照规格书检查(覆盖的 KP?深度?读者对象?)
- 失败模式检测:指令偏移(跑题)/ 上下文遗忘(前后矛盾)/ 编造(无 file:line)
- 不过 → agent 自修 → 再验;连续失败 → 停下问人(降级回交互)

### 组件④ 书级知识库(把交接文档工程化)

用户手工协议(HANDOVER.md + session00X.md)结构化:
- 大纲层:章节计划、概念依赖(永不进上下文,始终在磁盘)
- 结论层:每章结论 + file:line 证据(跨 session 不丢)
- 坑位层:待验证项、未决问题、失败模式记录
- 新 session 加载 = 读知识库,不是"又读一个文档"

## 五、技术路线

### 5.1 为什么是纯工程(MVP 无需新模型能力)

| 组件 | 用户已验证的对应物 | 工程化手段 |
|------|------------------|-----------|
| 对齐模块 | G0 盘问 + Q1-Q5 + 9 前置知识 SOP | 提示词模板 + 6 维 schema |
| 执行契约 | 方法论铁律 | 结构化文档 schema |
| 自动验收器 | 每篇检查单 + 覆盖审计 | 检查脚本(结构化产出对比) |
| 书级知识库 | HANDOVER 交接协议 | 文件/DB 结构化存储 |

### 5.2 落地约束

- **Linux 唯一基准**(D10):系统编程面(沙箱/pty/进程)只做 Linux
- **平台标签检查**(D11):文件名后缀/go:build/ifdef 先确认
- **理论层检查**(D15):持久层/并发层/协调层必须检查是否引入理论模式
- **正确性问题检查**(D16):状态管理/存储域必须回答"如何保证正确性"
- 参考架构:Pi(agent loop 分层)、Reasonix(长跑/checkpoint)、Hermes(跨 session 记忆)、OpenCode(权限/验收)

### 5.3 当前可用的工具

- codebase-memory MCP:4 项目知识图谱已建(理解 agent 架构用)
- 原方法论:分析 OpenJDK11 等目标源码的规范
- 4 项目源码:直接参考其 agent loop/上下文/记忆实现

### 5.4 正确性理论基础(2026-08-14 新增)— 从 Pi 源码分析中提炼

**背景**:Pi 的持久层/状态层揭示了"如何证明正确"的工程实践(Fencing Token、状态机不变量、契约测试)。这些直接转化为产品④(知识库)和③(验收器)的理论支柱。

**支柱 1:事件溯源可重放性(产品④知识库的理论基础)**

```
命题:同一份知识库日志(JSONL/追加写),任何时间重放 → 得到相同状态
理论:事件溯源(Event Sourcing)+ 日志全序(seq)+ 确定性(纯函数式状态归约)
Pi 证据:
- session-sequences.ts:单调 seq 全序
- state.ts applyMutation:状态归约是纯函数(输入 mutation → 新状态)
- session.ts:42 assertJsonSerializable:写入前验证
- 恢复语义:findOpenOperations 0/1/2 三态(崩溃后从日志重建)
```

**产品用法**:
- 书级知识库 = 追加写事件日志(章节开始/结论落库/验收结果/压缩摘要)
- 中断恢复 = 重放日志到 lastSeq(不依赖内存状态)
- **跨 session 延续 = 同一日志继续追加**(解决 #21 会话交接:交接不是写文档,是日志本身就是交接)
- 可验证性 = "重放即真相"(解决 #24 收敛性:验收时重放日志检查状态一致)

**支柱 2:契约检查(产品③验收器的理论基础)**

```
命题:产出物必须满足规格书定义的契约,不满足则不合格
理论:契约式设计(Design by Contract)——前置条件/后置条件/不变量
Pi 证据:
- conformance.ts(1016 行):多后端共享行为规范
  "rejects duplicate ids without changing state"(失败时状态不变)
  "rejects invalid queries before empty reads"(验证顺序)
- SessionErrorCode:稳定错误契约
```

**产品用法**:
- 章节规格书 = 契约(覆盖 KP/深度/读者对象/证据链要求)
- 自动验收器 = 契约检查器(conformance 测试)
- 验收失败 = 明确的"为什么失败 + 怎么改"(Pi 的 edit 错误消息哲学)
- 多产出形态(书/大纲/笔记)共享同一验收契约

**支柱 3:状态机不变量(产品执行引擎的理论基础)**

```
命题:非法状态不可达——每个变更验证不变量后才允许
Pi 证据:state.ts applyMutation(seq 连续/id 唯一/lane 存在)
产品用法:
- 分析状态机:对齐中/执行中/验收中/已完成 的合法迁移表
- 每个迁移验证不变量(如"验收中不能有新结论写入")
```

**支柱 4:质量门禁工程化(2026-08-14 新增,问题 #25 实证)**

```
命题:一切质量门禁必须程序化强制,禁止依赖 LLM 自觉遵守文档规范
实证:交接文档明确要求"每份笔记 review 后推进",agent 读过文档仍批量跳过
    (Hermes 分析自举项目发生,用户两次中断纠正)
拆解:
- 文档/提示词 = 软约束,上下文压力会系统性压过它
- agent 不仅"完成声明"不可信(#24),"遵守质量流程"也不可信——会跳过 review 门本身
- 生产者和质检者同为 agent 时,质检环节蒸发

产品用法:
- 验收门 = 状态机迁移的强制前置(验收器不过,执行引擎拒绝进入下一章)
- review 轮次 = 状态机强制计数(至少 N 轮),agent 无法自行跳过
- 收敛判定 = 程序化对账(文件清单/设计数),非 agent 声明
- 文档规范(交接/方法论)是工程化的输入,不是约束本身
```

**可讨论的进一步方向(不纳入 MVP)**:
- 性质测试(Property-based):随机章节验证"重放一致性"
- 模型检查(TLA+/Alloy):分析状态机的死锁/坏状态证明
- 这些是"锦上添花",MVP 阶段用 支柱 1+2 即可(支柱 4 与 支柱 2 同实现面:验收器即程序化门禁)

## 六、方法论线(降为工程规范,支撑产品)

原 16 条决策(D1-D16)不变,但定位改变:
- **目的**:保证产品产出的书"不编造、不跑偏、深度够"——是产品的质量保障系统

### D15:理论层检查(2026-08-14 新增)

**背景**:review Pi 时用户追问"有没有数学/分布式理论",挖出 hidden 理论层(Fencing Token/Lease/Event Sourcing/2PC 恢复/状态机不变量),这些在域发现中被归为"存储实现细节"漏掉了。

**规则**:分析任何域的**持久层/并发层/协调层**时,强制检查是否引入理论模式:
```
□ 分布式:租约(Lease)/栅栏令牌(Fencing Token)/共识/两阶段提交(2PC)/CAP
□ 数据:事件溯源(Event Sourcing)/日志全序/快照隔离/乐观并发(CAS)
□ 状态:有限状态机(FSM)/不变量(invariant)检查/非法迁移保护
□ 正确性:契约测试(conformance)/断言(assert)/恢复语义定理
□ 算法:复杂度分析/数据结构选择
```

**检查方法**:
- 文件命名:含 lease/lock/sequence/fence/conformance/invariant/validate/assert 的文件
- 并发声明:AGENTS.md/README 中"多进程/多 session/并发"声明 → 必有协调机制
- 恢复逻辑:崩溃恢复/中断恢复 → 必有状态机判定(0/1/2 三态类)

**产出**:发现的每个理论模式单独记录(理论名 + 实现位置 + 对应哪个经典问题)。

### D16:正确性问题检查(2026-08-14 新增)

**背景**:Pi 的 session.ts 有 `assertJsonSerializable`(运行时断言)、state.ts 有 `applyMutation` 不变量验证、conformance.ts 有 1016 行契约测试——"如何证明正确"的工程实践。

**规则**:分析状态管理/存储域时,强制回答"**这个系统如何保证正确性**":
```
□ 运行时断言:关键数据结构的合法性检查(assertJsonSerializable)
□ 状态机不变量:每个变更是否验证不变量(seq 连续/id 唯一/lane 存在)
□ 契约测试:是否有 conformance/契约测试套件(多后端共享行为规范)
□ 失败语义:错误码/错误类型是否有稳定契约(SessionErrorCode)
```

**产出**:每个正确性机制记录"它防止哪类 bug"。

### D17:参考架构落地性检查(2026-08-14 新增)

**背景**:Pi 参考架构 v3 review 发现——源码覆盖度(v2 检查"设计有没有漏抄")和产品落地性(v3 检查"蓝图本身能不能落地")是**两种不同的 review**。v3 找到 5 个产品设计层遗漏(规格书三合一/验收-执行交互/元验收/全书检索/对齐中断处理),这些不是源码遗漏,是"蓝图缺设计决策"。

**规则**:产出**参考架构/设计蓝图类文档**后,除核对设计覆盖外,必须回答 5 个落地性问题:
```
1. 数据怎么流动:同一份数据(spec)是否被多处消费且不漂移?(三合一原则)
2. 时机怎么定:关键动作(验收/压缩)的触发时机是否有明确决策?(每章 vs 每轮)
3. 失败怎么循环:失败后如何回到主循环?(steer 回注 → LLM 修正 → 重验)
4. 大库怎么查:规模增长后的检索路径?(全书级 FTS5,不靠内存)
5. 系统怎么自证:检查器本身是否被检查?(元验收——验收器的契约测试)
```

**产出**:每个落地性问题在设计蓝图中有明确答案,缺失则标记 [设计缺口]。

**反模式**:
- 只核对"设计 A/B/C 抄到了吗",不追问"数据流/时机/失败循环/大库/自证" → 蓝图看起来全,落地时卡壳
- **用法**:写进对齐模块(盘问模板)、执行契约(铁律)、验收器(检查单)
- 分析 4 个开源 Agent 项目 = 给产品抄架构,不是面试准备

### D18:穷尽性检查 = 文件体量排序核对,禁止按目录感觉(2026-08-14 新增)

**背景**:Pi 域发现 v1-v6 声称 59 域收敛,实为**假收敛**——Hermes 深度 review 被用户逼出"文件体量排序 + 覆盖核对"方法(Hermes 27→80 域)后,用同法复测 Pi,当场发现 4 个 load-bearing 遗漏:interactive-mode.ts(6,436 行,**项目最大文件**,6 轮 review 都没进视野)、reducer.ts(事件溯源损坏检测核心)、extensions/runner.ts、event-bus。v7/v8 复测后 Pi 59→85 域。

**规则**:域发现的穷尽性检查必须程序化,禁止"按目录感觉扫描":
```
1. 文件体量排序:find + wc -l,排除 test/examples/vendor,取 top N(项目规模定 N)
2. 逐一核对:每个 top N 文件 grep 域发现文档,无覆盖 → 必须解释(遗漏/排除理由)
3. 理论层双位置:理论发现(q7 Fencing Token)必须同时记录"理论名 + 实现文件"
   ——D15 的"实现位置"要求在域发现层强制执行(writer-leases.ts/session-sequences.ts)
4. 收敛判定:top N 全部核对 + 子目录全部扫描后才可声明收敛,不是"新增数为零"
```

**产出**:域发现文档含"体量排序核对表"(top N 文件 × 覆盖状态)。

**反模式**:
- "感觉扫完了" → 假收敛(Pi 59 域的教训,interactive-mode 6,436 行漏 6 轮)
- 理论层发现不追实现 → 域发现写"有 Fencing Token",实际实现文件未知

**实证案例(2026-08-14 完整链 — 三项目共证"感觉收敛"不可信)**:

| 项目 | 语言 | 原始声明(agent 自觉) | 最终(体量排序+逐目录核对) | 增长 | 用户追问轮次 |
|------|------|:--:|:--:|:--:|:--:|
| Hermes | Python 4,138 文件 | 27 域 | **80 域** | +53 | 5 次 |
| Reasonix | Go 966 文件 | 41 域 | **101 域** | +60 | 2 次 |
| Pi | TS 561 文件 | 59 域 | **126 域** | +67 | 3 次 |

**每次"感觉到底"都被证伪的记录**:
- Pi v14 称"收官确认无新域" → v15-v19 每轮都有真发现(agent 门面/双层循环截断处理/tui 分片缓冲/server 连接状态机/测试契约)
- Hermes v9 称"所有大文件层面已打开" → v10 发现 auxiliary_client(10,432 行)/cli.py(19,269 行)从未打开
- **规律:换层面必有发现**(agent 核心 → 子目录 → 测试契约 → 排除清单复核 → 工程工具),直到程序化覆盖核对(文件清单 × 层面清单)全部通过

**最终结论**:
1. **agent 的"探索完毕"声明永远不可信**(#24 在域发现层面的铁证)
2. **穷尽性 = 文件体量排序 + 逐目录核对 + 排除清单复核** 三重程序化检查,与"新增数为零"无关
3. **排除清单也要复核**(Pi tui 原生层曾排除,stdin-buffer 分片缓冲/undo-stack 快照实为通用设计)
4. **跨项目通用模式 = 机制在三项目独立出现**(租约/验收器/执行引擎/遥测/搜索/工具延迟加载 6 组定论)
