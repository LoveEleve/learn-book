## 1. 引言：编译器知道的比你多

S7Ch07 教你找热点——找到 hottest function 后你手动重写它。但如果编译器能自动帮你优化呢？`-O2` 已经做到了——自动内联、死代码消除、循环展开。但编译器的视野被**编译单元（TU）边界**限制着——它看不到 `foo.c` 里的函数调用 `bar.c` 里的函数时的内联机会。

LTO 和 PGO 突破了这个边界。

---

## 2. `-O0` 到 `-O3`——编译器到底做了什么

| 级别 | 含义 | 适用 | 典型的优化 |
|---|---|---|---|
| `-O0` | 不优化 | **调试**——保证源码行与指令一对一 | 无 |
| `-Og` | 优化但不干扰调试 | 开发期调试 | 无变量被消除、无语句被重排 |
| `-O1` | 保守优化 | 增量构建 | 死代码消除、常量传播、简单的寄存器分配 |
| `-O2` | **标准优化** | **生产默认** | `-O1` + 内联、循环优化、指令调度、自动向量化（不改变代码语义） |
| `-O3` | 激进优化 | 性能关键——可能变慢 | `-O2` + 函数克隆（`-fipa-cp-clone`）、循环展开、预测公共子表达式 |
| `-Os` | 优化体积 | 嵌入式 | `-O2` 中不增大体积的优化子集——省 ROM/磁盘 |
| `-Ofast` | `-O3` + 数学宽松 | 数值计算（允许不严格遵守 IEEE 754） | `-ffast-math`—— 假设 NaN/Inf 不发生、代数恒等成立 |

**关键**：`-O2` 是生产默认——它在编译时间、调试能力、运行时性能之间取得平衡。`-O3` 不保证比 `-O2` 快——函数克隆可能膨胀代码→I-cache miss 增加→反而变慢。

## 3. LTO（Link-Time Optimization）——跨 TU 优化

### 3.1 问题：编译器的视野被 TU 边界限制

```c
// foo.c
int add(int a, int b) { return a + b; }

// bar.c
extern int add(int a, int b);
int main() { return add(1, 2); }  // 编译器在这里看到的是 call add 而非 return 3
```

传统编译：每个 `.c` 独立编译。编译器编译 `bar.c` 时不知道 `add` 的实现——它只能生成 `call add`。LTO 改变了这一限制。

### 3.2 LTO 的实现原理

```bash
# LTO——在链接阶段也保留 GIMPLE IR
gcc -flto -O2 foo.c -c -o foo.o     # foo.o 中是 GIMPLE IR（非机器码） + 机器码
gcc -flto -O2 bar.c -c -o bar.o
gcc -flto -O2 foo.o bar.o -o prog   # 链接时用 GIMPLE IR 做跨 TU 优化
```

**LTO 做了什么**：链接器读到 GIMPLE IR → 整个程序展开为完整的 GIMPLE 调用图 → 内联 `add` 跨越 TU 边界 → `main` 变成了 `return 3`——这只有一个 TU 时做不到。

### 3.3 LTO 的代价

- 编译时间延长 2-5x（保留 IR 并处理整个程序）
- 链接时间延长（跨 TU 优化遍历完整的调用图）
- `.o` 文件变大（包含 IR + 机器码两种格式）

## 4. PGO（Profile-Guided Optimization）——基于运行时数据的优化

### 4.1 两步流程

```bash
# Step 1：Instrument——编译插��版本 + 用代表性训练数据运行
gcc -fprofile-generate -O2 myapp.c -o myapp_instrumented
./myapp_instrumented < training_data.txt   # 运行训练负载——生成 .gcda 文件

# Step 2：Use——基于 profile 数据重新优化
gcc -fprofile-use -O2 myapp.c -o myapp_optimized
./myapp_optimized < real_data.txt
```

### 4.2 PGO 的核心优化

| 优化 | 基于 profile 的什么数据 |
|---|---|
| 分支预测偏置 | 统计哪个分支更常被执行（`if (error) ` vs `if (normal) `）——将 common case 放在无跳转路径 |
| 内联决策 | 统计函数被调用的频率——小函数被频繁调→强制内联，大函数被频繁调→不值得内联（代码膨胀） |
| 函数重排 | 热门函数放在一起→ I-cache locality 改善 |
| 基本块重排 | cold code（如错误处理）远离 hot code——减少指令缓存占用 |

### 4.3 PGO 的陷阱

- **训练数据必须代表性**——用轻负载跑 PGO 优化为轻负载→重负载反而变慢
- **函数签名的 ABI 变化**——新函数的调用约定可能被改变——**不要交叉链接** instrument 和 optimized 版本的 `.o`

## 5. 优化陷阱——编译器"优化"掉 UB

### 5.1 有符号整数溢出

```c
int safe_add(int a, int b) {
    if (a + b < a) return INT_MAX;  // 溢出检查
    return a + b;
}
```

`-O2` 下编译器推理：`a + b < a` → 无溢出时不可能（数学上 b 必须是负数）。如果溢出→那是 UB → 编译器可以假设它不溢出。所以 `a + b < a` 永远为假 → 删除整个 `if` 分支。你的溢出检查**被优化掉了**。

### 5.2 死代码消除——删掉你只用来调试的代码

```c
int x = do_something();
printf("debug: x=%d\n", x);
```

在 `-O2` 下 `do_something` 如果没有其他使用者（`x` 被后序覆盖了），编译器可能直接不调用它——`printf` 是输出函数不会被删，但 `do_something()` 的调用可能被优化掉。

### 5.3 如何避免优化陷阱

1. **不要依赖 UB**——使用 `__builtin_add_overflow`（GCC/Clang）或有符号→无符号转换（检查 wrapping）
2. **`volatile` 阻止优化**——在 需调试的场景中可以阻止死代码消除
3. **`-Og` 进行调试**——如果有优化但不想被优化干扰

## 6. 总结

| 概念 | 核心知识 |
|---|---|
| `-O2` | 生产默认——安全优化，不改变语义 |
| `-O3` | 可能更慢——函数克隆爆炸 I-cache |
| LTO | 链接时使用 GIMPLE IR——跨 TU 内联+死代码消除 |
| PGO | 两步编译——基于运行时训练数据优化分支预测+内联+排布 |
| UB 陷阱 | `-O2` 会利用 UB 删除检查——不溢出检查有符号整数 |
| PGO 陷阱 | 训练数据必须代表性——profile 误导编译器做错误决策 |

**核心观点**：编译优化不是"开启就行"——它改变了程序的语义边界。`-O2` 假设你的代码没有 UB，并在假设下推理——消除"不可能"的代码路径。技术专家不是"知道 `-O2` 更快"，而是"知道 `-O2` 会利用 UB 消除你的安全检查——如果你的检查依赖于有符号溢出是可见的，这个假设本身就不成立"。

## 面试题

**Q1：`-O2` 和 `-O3` 的区别——编译器各做了哪些优化？**

`-O3` added: 函数克隆、循环展开、预测公共子表达式。函数克隆可能导致代码膨胀——如果 I-cache miss 多于改进的指令效果→程序反而变慢。这是为什么生产默认是 `-O2` 的核心原因。回答时提一个具体例子比笼统地列优化名更强。

**追问**："什么场景下 `-O3` 反而更慢？"——微基准没问题，大系统的 I-cache 压力是真实瓶颈。

**Q2：PGO 为什么需要两步？为什么不能用静态分析替代？**

编译器静态分析无法预知运行时分支频率——`if (error) ` 和 `if (normal) ` 在源码中的出现顺序与运行时无关。PGO 的运行时数据是唯一的真实反馈。追问："为什么不直接用 perf 数据然后手动改代码？"——perf 告诉你函数级热点，PGO 优化的是指令级（分支偏置、cache line placement）——手工做不到的精度。
