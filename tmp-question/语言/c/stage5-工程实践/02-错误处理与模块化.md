## 1. 引言：C 没有异常——这是自由，也是责任

Java 用 `try-catch-finally`——编译器保证异常一定被捕获或向上传播。C 用返回码——编译器不检查你是否忘了判断 `malloc` 返回 NULL。

一个技术专家面对的不是"哪种更好"的问题，而是"如何在 C 的限制下构建健壮的错误处理系统"——这个问题 Linux 内核用 30 年回答了三套模式：`goto cleanup`、`cleanup` attribute 和 `errno`。本章讲解这三种模式的完整实现、各自陷阱和选择标准。

## 2. 返回码 + `errno`

### 2.1 标准模式

```c
int fd = open("data.txt", O_RDONLY);
if (fd < 0) {
    fprintf(stderr, "open failed: %s\n", strerror_r(errno, buf, sizeof(buf))  // 线程安全);
    return -1;
}

// 或者直接输出：
perror("open");  // 输出 "open: No such file or directory"
```

**`errno` 的本质**：在 glibc 中 `errno` 定义为 `(*__errno_location())`——每次访问 `errno` 实际是调用 `__errno_location()` 返回当前线程 TLS（Thread-Local Storage，线程局部存储）中 errno 变量的地址。这就是为什么多线程下每个线程有自己独立的 `errno`——其底层通过 `pthread_key` 或 `__thread` 实现线程局部性。只有在函数返回错误指示时才有效——成功时 `errno` 的值未定义。

**`strerror` vs `strerror_r`（线程安全）**：`strerror_r(errno, buf, sizeof(buf))  // 线程安全` 返回指向全局静态缓冲区的指针——多线程下该缓冲区可被**另一个线程的 strerror 调用覆盖**。生产代码用 `strerror_r(errno, buf, sizeof(buf))`——将错误字符串写入调用者提供的缓冲区。

### 2.2 `errno` 的陷阱

**陷阱 1：不检查返回值就检查 errno**

```c
int fd = open("data.txt", O_RDONLY);
if (errno != 0) {  // 错误！成功时 errno 的值未定义
    // open 成功，但 errno 可能是前一次失败的残留值
}
```

**正确做法**：先检查返回值，再用 `errno` 获取错误细节。

**陷阱 2：两次调用之间 errno 被覆盖**

```c
int fd = open("data.txt", O_RDONLY);
if (fd < 0) {
    close(other_fd);  // 可能覆盖 errno！
    fprintf(stderr, "open failed: %s\n", strerror_r(errno, buf, sizeof(buf))  // 线程安全);  // 错误信息不准确
}
```

**正确做法**：保存 `errno` 在可能覆盖它的调用之前。

```c
int saved_errno = errno;
close(other_fd);
fprintf(stderr, "open failed: %s\n", strerror(saved_errno));
```

### 2.3 错误日志的定位——`__FILE__` 与 `__LINE__`

```c
#define LOG_ERROR(fmt, ...) \
    fprintf(stderr, "[%s:%d] " fmt "\n", __FILE__, __LINE__, ##__VA_ARGS__)

if (fd < 0) {
    char ebuf[256];
    strerror_r(errno, ebuf, sizeof(ebuf));
    LOG_ERROR("open failed: %s", ebuf);
    return -1;
}
// 输出：[module.c:42] open failed: No such file or directory
```

### 2.4 assert——调试期的防御性编程

```c
#include <assert.h>
assert(p != NULL);  // 条件为假 → 输出 _FILE_:_LINE_ + 条件表达式 → abort
// Release 编译：gcc -DNDEBUG → assert 被预处理器完全移除——零运行时开销
```

**策略**：`assert` 在开发/测试中捕捉"不可能发生"的 bug；`-DNDEBUG` 在生产中消除其开销。不能用 `assert` 检查用户输入或可恢复的错误——`assert` 失败直接 `abort()`，不适合生产环境优雅降级。

### 2.5 宏简化——减少样板代码

```c
#define CHECK(expr, action) do { \
    if ((expr) < 0) { perror(#expr); action; } \
} while(0)

CHECK(fd = open("data.txt", O_RDONLY), return -1);
CHECK(n = read(fd, buf, sizeof(buf)), { close(fd); return -1; });
```

## 3. `goto cleanup`——Linux 内核的核心模式

### 3.1 为什么 goto 在 C 中是好的

**争议**：Dijkstra 1968 年的 "Goto Considered Harmful" 主要反对**无条件跳转**造成意大利面条代码。在 C 中，`goto` 用于**统一错误路径**——所有错误跳转到同一个 `cleanup` 标签，按逆序释放已分配的资源。这与 Dijkstra 反对的无条件跳转是不同的用途。

### 3.2 完整实现

```c
int do_work(const char *path) {
    int ret = -1;
    int fd = -1;
    char *buf = NULL;
    struct stat *st = NULL;

    fd = open(path, O_RDONLY);
    if (fd < 0) { perror("open"); goto cleanup; }

    st = malloc(sizeof(*st));
    if (!st) { perror("malloc st"); goto cleanup; }

    if (fstat(fd, st) < 0) { perror("fstat"); goto cleanup; }

    buf = malloc(st->st_size);
    if (!buf) { perror("malloc buf"); goto cleanup; }

    if (read(fd, buf, st->st_size) < 0) { perror("read"); goto cleanup; }

    process(buf, st->st_size);
    ret = 0;  // 成功——仅在这里设置

cleanup:
    if (fd >= 0) close(fd);    // 逆序释放——最后分配的最先释放
    free(st);
    free(buf);
    return ret;
}
```

**关键原则**：
1. **资源初始化用无效值**（`fd = -1`, `buf = NULL`）——cleanup 时检查是否已分配
2. **逆序释放**——最后分配的（buf）最先释放，最早分配的（fd）最后释放
3. **所有错误路径 goto 同一个 cleanup 标签**——不是每个错误有自己的 cleanup
4. **成功时 ret = 0 只在正常路径设置**——cleanup 不设 errno，由调用者检查返回值

### 3.3 生产案例——Linux 内核中的 `goto cleanup`

Linux 内核的 `do_execveat_common()` 用了 50+ 行的 goto cleanup 链：

```c
retval = bprm_execve(bprm, fd, filename, flags);
if (retval < 0)
    goto out;

// ... 正常路径 ...

out:
    // 逆序释放：
    if (bprm->mm) acct_arg_size(bprm, 0);
    // ...
    if (bprm->cred) abort_creds(bprm->cred);
    // ...
    free_bprm(bprm);
    // ...
    if (filename) __putname(filename);
    // ...
    putname(filename);
    return retval;
```

## 4. `cleanup` attribute——C 的 RAII

### 4.1 GCC/Clang `__attribute__((cleanup(fn)))`

```c
// 声明——变量离开作用域时自动调用 cleanup_fn
#define auto_free __attribute__((cleanup(free_ptr)))

static void free_ptr(void *p) { free(*(void **)p); }

void process(void) {
    auto_free char *buf = malloc(1024);
    if (!buf) return;

    // 使用 buf...

    // 无论通过 return、goto 或函数结束离开——buf 被自动 free
}
```

### 4.2 对比三种错误处理

| 方案 | 代码量 | 安全度 | 可移植性 | 适用 |
|---|---|---|---|---|
| 返回码+手动清理 | 高——每个资源单独 free | 低——容易漏 | ✅ 所有 C | 简单场景 |
| `goto cleanup` | 中——cleanup 标签一次 | 中——需 discipline | ✅ 所有 C | **标准选择**——Linux 内核 |
| `cleanup` attribute | 低——自动释放 | 高——编译器保证 | ❌ GCC/Clang only | 中型函数 |

**选择原则**：
- 简单场景（≤2 个资源）→ 返回码就够了
- 中等场景（3-5 个资源）→ `goto cleanup`
- 复杂场景或需要绝对安全 → `cleanup` attribute（仅 GCC/Clang，用条件编译提供 `goto cleanup` 作为回退）

## 5. setjmp/longjmp——跨栈帧的非局部跳转

### 5.1 基本用法

`setjmp/longjmp` 是 C 标准库的第四种错误处理——绕过正常的函数返回路径，直接从深层调用栈跳回浅层调用栈：

```c
#include <setjmp.h>

jmp_buf env;

void deep_function(void) {
    longjmp(env, 1);  // 不返回——直接跳回 setjmp 的位置
}

int main() {
    if (setjmp(env) == 0) {
        // 初始调用——setjmp 返回 0
        deep_function();  // 被 deep_function 中的 longjmp 中断
    } else {
        // longjmp 返回——setjmp 返回非零值（longjmp 的第二个参数）
        printf("Recovered from error\n");
    }
    return 0;
}
```

**为什么不在一般代码中使用**：
- `longjmp` 不执行栈展开——所有在 setjmp 和 longjmp 之间创建的**栈变量、malloc 分配的内存、打开的 fd 都不会被自动释放**
- 寄存器中的变量值被恢复为 setjmp 时刻的快照——已修改的局部变量值丢失
- 线程不安全——不能在不同线程间跳转
- 与 C++ 异常不同——没有析构调用

**唯一合法用途**：`try-catch` 级别的错误恢复框架中（Lua、libpng 的内部实现用它做非局部错误返回）。在应用层代码中应避免——用 `goto cleanup` 代替。

## 6. 模块化——头文件设计与 API 隐藏

### 5.1 公共接口 vs 内部实现

```c
// foo.h —— 公共头文件
#ifndef FOO_H
#define FOO_H

typedef struct foo foo_t;

foo_t *foo_create(int init_val);
int    foo_process(foo_t *f, const void *data, size_t len);
void   foo_destroy(foo_t *f);

#endif
```

```c
// foo_internal.h —— 本模块内可见
#include "foo.h"

struct foo {
    int   val;
    char *buf;
    // ... 本模块的 struct 定义——其他模块看不到
};
```

**`foo_internal.h` 的使用场景**：
- `foo.c` 的实现需要访问 struct 成员——include `foo_internal.h`
- `foo_test.c` 的单元测试需要访问内部状态——include `foo_internal.h`
- 外部模块只依赖公共 API——只 include `foo.h`

### 5.2 符号可见性控制

```c
// GCC/Clang:
#define PUBLIC  __attribute__((visibility("default")))
#define HIDDEN  __attribute__((visibility("hidden")))

PUBLIC  int foo_process(foo_t *f, const void *data, size_t len);
HIDDEN  static int internal_helper(void);  // 本模块内调用，不导出
```

**默认可见性**：GCC 默认所有非 `static` 函数导出。加上 `-fvisibility=hidden` 改为默认隐藏——只有显式标注 `PUBLIC` 的函数导出。这减少了符号冲突和库的体积。

### 6.3 头文件的循环依赖与解决

```c
// a.h — 包含 b.h
#include "b.h"

// b.h — 包含 a.h（循环！）
#include "a.h"   // a.h 的 include guard 防止无限递归，但语义无效
```

**解决方案**——前向声明 + 在 .c 中 include：

```c
// a.h
typedef struct b_t b_t;   // 前向声明——不需要知道 b_t 的成员
void foo(b_t *b);          // 用指针参数不需要完整类型

// a.c
#include "a.h"
#include "b.h"             // 这里才需要完整类型
void foo(b_t *b) { /* 可以访问 b->member */ }
```

**检测原则**：如果 `a.h` 只需要指向 `b` 的**指针**——前向声明就够了。如果需要 `sizeof(b)` 或访问 `b` 的成员——需要 `#include "b.h"`。

### 6.4 静态函数——编译器层面的封装

```c
// 模块内部 helper——不应该在头文件中声明
static int validate_input(const char *data, size_t len) {
    return len > 0 && data != NULL;
}
```

`static` 函数只在本 TU（Translation Unit）可见——链接器看不到这些符号，是 C 最底层的"封装墙"。

### 5.4 完整的模块示例

```c
// module.h
#ifndef MODULE_H
#define MODULE_H

typedef struct module module_t;

module_t *module_create(const char *name);
int       module_run(module_t *m);
void      module_destroy(module_t *m);

#endif
```

```c
// module.c
#include "module.h"
#include <stdlib.h>
#include <string.h>

struct module {
    char   *name;
    int     state;
};

static int validate_name(const char *name) {
    return name && strlen(name) > 0;
}

module_t *module_create(const char *name) {
    if (!validate_name(name)) return NULL;
    module_t *m = calloc(1, sizeof(*m));
    if (!m) return NULL;
    m->name = strdup(name);
    if (!m->name) { free(m); return NULL; }
    return m;
}

void module_destroy(module_t *m) {
    if (!m) return;
    free(m->name);
    free(m);
}
```

## 7. 总结

| 概念 | 核心知识 |
|---|---|
| `errno` | 只在返回值指示错误时有效——成功时值未定义 |
| `perror/strerror` | 将 errno 转为人类可读的错误字符串 |
| `goto cleanup` | Linux 内核的标准错误处理——统一释放点 + 逆序释放 |
| `cleanup` attribute | C 的 RAII 等价——GCC/Clang 扩展 |
| 公共/内部头文件 | `foo.h`（公共 API）vs `foo_internal.h`（模块内部可见） |
| `static` 函数 | TU 级封装——链接器不可见 |
| 符号可见性 | `-fvisibility=hidden` + 显式 `PUBLIC`——减少符号冲突 |

**核心观点**：C 的错误处理不是"缺少异常"——这是刻意的取舍。`goto cleanup` 是 30 年 Linux 内核开发的最佳实践——不是丑陋，是线性、清晰、可证明的安全。技术专家不是"知道 goto 不好"，而是"知道为什么 Linux 内核用 goto cleanup 替代了 C++ 的异常处理——因为 goto 在 C 中是唯一能安全释放多个资源而不产生意大利面条代码的方式"。

## 面试题

**Q1：goto 在 C 中为什么是好的？Dijkstra 不是反对 goto 吗？**

Dijkstra 1968 年的 "Goto Considered Harmful" 反对的是**无条件跳转**造成的意大利面条代码。C 的 `goto cleanup` 用于**统一错误路径**——所有错误跳入同一个 cleanup 标签，按 LIFO 逆序释放资源。这不是无条件跳转——这是**线性的、可证明安全的结构化错误处理**。Linux 内核 3000 万行 C 代码全部用这个模式。

**追问**："为什么不直接用 C++ 异常？"——Linux 内核不能链接 libstdc++，且异常的栈展开在持有 spinlock 时可能导致死锁。`goto cleanup` 是内核唯一安全的选择。

**Q2：errno 是线程安全的吗？为什么？**

是——glibc 中 errno 定义为 `(*__errno_location())`，每次访问 errno 实际调用函数返回当前线程 TLS 中 errno 的地址。底层用 `pthread_key` 或 `__thread` 实现。追问："`strerror(errno)` 是线程安全的吗？"——不是！strerror 返回全局静态缓冲区指针，多线程会被覆盖。生产代码必须用 `strerror_r`。
