## 1. 引言：C 测试为什么比 Java 难？

> **Stage5 主线**：Stage5 的目标是"把 C 代码工程化"——S5Ch01 教你写可维护的 C（OOP），S5Ch02 教你处理错误（goto cleanup），本章教你**验证代码正确性**（测试）和**组织项目**（构建）。测试不是"写完了再补"——是"写代码的同时写测试"。

Java 用 JUnit——`@Test` 注解一行，Maven 自动跑，覆盖率自动生成。C 没有注解、没有反射、没有统一的测试框架——你需要手动组织测试、手动编译测试二进制、手动运行、手动统计覆盖率。

但这是一种自由——你可以选择完全不同的测试策略：Unity（单头文件，极小）vs cmocka（支持 mock）vs Criterion（现代风格）。本章从极简的 Unity 开始，再到完整的 CMake 构建系统——教你把 C 项目从"能编译"提升到"可测试、可构建、可 CI"。

## 2. Unity——单头文件的极简测试框架

### 2.1 入门

```bash
# 下载 Unity（一个 .c + 一个 .h，约 800 行）
wget https://raw.githubusercontent.com/ThrowTheSwitch/Unity/master/src/unity.c
wget https://raw.githubusercontent.com/ThrowTheSwitch/Unity/master/src/unity.h
```

```c
// test_stack.c
#include "unity.h"
#include "stack.h"   // 你要测试的模块

void setUp(void)   { /* 每个测试前调用 */ }
void tearDown(void) { /* 每个测试后调用 */ }

void test_stack_push_pop(void) {
    stack_t *s = stack_create();
    TEST_ASSERT_NOT_NULL(s);

    stack_push(s, 42);
    TEST_ASSERT_EQUAL(42, stack_pop(s));

    stack_destroy(s);
}

void test_stack_empty_pop(void) {
    stack_t *s = stack_create();
    // 空栈 pop 应该返回什么？这取决于你的设计——测试定义行为
    stack_pop(s);
    stack_destroy(s);
}

int main(void) {
    UNITY_BEGIN();
    RUN_TEST(test_stack_push_pop);
    RUN_TEST(test_stack_empty_pop);
    return UNITY_END();
}
```

编译和运行：

```bash
gcc -Wall unity.c test_stack.c stack.c -o test_stack && ./test_stack
# 输出：test_stack.c:15:test_stack_push_pop:PASS
#       test_stack.c:22:test_stack_empty_pop:PASS
```

### 2.2 Unity 的核心断言

| 断言 | 用途 |
|---|---|
| `TEST_ASSERT(expr)` | 基本——`expr` 为真 |
| `TEST_ASSERT_EQUAL(expected, actual)` | 整型比较 |
| `TEST_ASSERT_EQUAL_STRING(expected, actual)` | 字符串比较 |
| `TEST_ASSERT_NOT_NULL(ptr)` | 指针不为空 |
| `TEST_ASSERT_NULL(ptr)` | 指针为空 |
| `TEST_ASSERT_FLOAT_WITHIN(delta, expected, actual)` | 浮点数近似比较 |

### 2.3 测试 double-free 和 UAF——ASan 集成

```bash
# 编译时链接 AddressSanitizer
gcc -g -fsanitize=address unity.c test_stack.c stack.c -o test_asan
./test_asan
# ASan 会在运行时检测 UAF、double-free、栈溢出——测试框架做不到
```

### 2.4 测试策略——不只是"测通"

**边界值分析——栈的四个关键时刻**：

```c
void test_stack_boundaries(void) {
    stack_t *s = stack_create();
    // 边界 1：空栈 pop 的返回值定义
    TEST_ASSERT_EQUAL(-1, stack_pop(s));

    // 边界 2：溢出——push 超过初始容量
    for (int i = 0; i < 100; i++) stack_push(s, i);
    TEST_ASSERT_EQUAL(99, stack_pop(s));

    // 边界 3：NULL 输入
    TEST_ASSERT_EQUAL(-1, stack_pop(NULL));

    stack_destroy(s);
}
```

**测试 malloc 返回 NULL（面试高频）**：用 `LD_PRELOAD` 劫持 `malloc` 让它返回 NULL：

```c
// mock_malloc.c — 编译为 .so
#include <stdlib.h>
void *malloc(size_t size) { return NULL; }
// gcc -shared -fPIC mock_malloc.c -o mock_malloc.so
// LD_PRELOAD=./mock_malloc.so ./test_stack
// 验证 stack_create() 正确处理 malloc 失败
```

**mock 函数调用的三种技术**：

| 技术 | 原理 | 适用 |
|---|---|---|
| LD_PRELOAD | 动态链接器查找优先级——先加载 mock.so | 集成测试，多数场景 |
| `-Wl,--wrap=symbol` | 链接器自动将 `malloc` 的调用重定向到 `__wrap_malloc` | 链接时 mock |
| weak symbol | 定义弱符号 `__attribute__((weak))` 的函数——强符号版本优先 | 编译时可选依赖 |

**与 S5Ch01/S5Ch02 的交叉验证**：

- S5Ch01 的 `circle_create` 返回 `NULL` 的处理——用 `TEST_ASSERT_NULL(circle_create(-1.0))` 验证
- S5Ch02 的 `goto cleanup` four principles——用 ASan 验证每次资源都被释放

### 2.5 覆盖率——gcov/lcov

```bash
gcc -fprofile-arcs -ftest-coverage test_stack.c stack.c -o test_stack
./test_stack
gcov stack.c                          # 生成 stack.c.gcov
# 或用 lcov 生成 HTML 报告
lcov --capture --directory . --output-file coverage.info
genhtml coverage.info --output-directory coverage_html
```

## 3. 测试框架对比

| 框架 | 文件 | 特色 | 适用 |
|---|---|---|---|
| **Unity** | 2 文件（~800 行） | 极简，零依赖，可嵌入项目 | 小项目，嵌入式，学习 |
| **cmocka** | 标准安装 | 支持 mock（可以模拟函数调用） | 需要测试函数间交互 |
| **Criterion** | 标准安装 | 现代风格——测试自动注册（不用写 main），fork 子进程隔离 | 大中型项目 |
| **Check** | 标准安装 | fork 隔离——每个测试独立进程 | 稳定性要求高的项目 |

**为什么 C 测试框架需要 fork 隔离**：C 的测试没有异常捕获——一个 SIGSEGV 杀掉整个进程。Check/Criterion 在每个测试前 fork 一个子进程——子进程崩溃不影响测试运行器收集结果。

## 4. C 构建系统——从 Make 到 CMake

### 4.1 为什么 C 需要专门的构建工具

Java 用 Maven——类路径固定，编译命令单一。C 的构建复杂得多：
- 多个源码文件 + 多个头文件目录
- 静态库(.a) 和共享库(.so) 的链接顺序敏感
- 跨平台（Linux Clang vs macOS GCC vs Windows MSVC）条件编译
- Debug/Release 两套编译选项

**历史演进**：**Make**(1976)——最早，语法复杂，手写规则。**autotools**(1991)——解决平台检测，但配置慢且过度工程化。**CMake**(2000)——生成器模型（生成 Make/Ninja/MSBuild），跨平台抽象层，2010s 后成为 C 社区事实标准。

### 4.2 CMake 的核心概念——不是语法

```cmake
add_library(mylib STATIC foo.c)  # 这背后是：ar rcs libmylib.a foo.o
target_include_directories(mylib PUBLIC include)  # 对应 gcc -Iinclude
target_link_libraries(myapp PRIVATE mylib)        # 对应 gcc -lmylib
```

CMake 不是"另一种 Make"——它是**构建描述语言**。你描述"项目由什么组成、依赖什么"，CMake 生成平台特定的构建文件。

```cmake
cmake_minimum_required(VERSION 3.10)
project(myapp C)

set(CMAKE_C_STANDARD 11)
set(CMAKE_C_FLAGS "${CMAKE_C_FLAGS} -Wall -Wextra -Wpedantic")

add_executable(myapp main.c foo.c bar.c)
```

### 4.3 多目标——可执行文件 + 库

```cmake
# 静态库
add_library(mylib STATIC foo.c bar.c)

# 共享库
add_library(mylib_shared SHARED foo.c bar.c)

# 可执行文件（链接静态库）
add_executable(myapp main.c)
target_link_libraries(myapp mylib)
```

### 4.4 集成测试

```cmake
# 通过 ExternalProject 或直接包含源码
add_library(unity STATIC unity.c)

# 每个模块一个测试可执行文件
add_executable(test_stack test_stack.c stack.c)
target_link_libraries(test_stack unity)

# 注册测试——make test 或 ctest
enable_testing()
add_test(NAME test_stack COMMAND test_stack)
```

### 4.5 Debug vs Release 配置

```cmake
# Debug——无优化 + ASan
set(CMAKE_C_FLAGS_DEBUG "-O0 -g -fsanitize=address")

# Release——优化 + 去符号
set(CMAKE_C_FLAGS_RELEASE "-O2 -DNDEBUG -s")

# 构建：
mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Debug && make
```

### 4.6 检测编译器特性——检测编译器特性

```cmake
include(CheckCCompilerFlag)
check_c_compiler_flag("-fstack-protector-strong" HAS_STACK_PROTECTOR)
if(HAS_STACK_PROTECTOR)
    target_compile_options(myapp PRIVATE -fstack-protector-strong)
endif()
```

### 4.7 编译加速——ccache

```bash
ccache gcc -c foo.c  # 首次编译——cache the object
ccache gcc -c foo.c  # 第二次——hit! 0ms
```

CMake 集成：`cmake -DCMAKE_C_COMPILER_LAUNCHER=ccache`。CI 平台中可节约 50-80% 的重复编译时间。

## 5. 生产 CI 集成

```yaml
# .github/workflows/c-ci.yml
name: C CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: sudo apt install -y build-essential cmake
      - run: mkdir build && cd build && cmake .. -DCMAKE_BUILD_TYPE=Debug && make
      - run: cd build && ctest --output-on-failure
      - run: cd build && make test_asan && ./test_asan
```

## 6. 总结

| 概念 | 核心知识 |
|---|---|
| Unity | 单头文件极简框架——嵌入项目、零依赖 |
| CMake | 事实标准的跨平台构建——多目标、Debug/Release、集成测试 |
| ASan | 测试 DOUBLE FREE/UAF/栈溢出——`-fsanitize=address` |
| fork 隔离 | Criterion/Check——防止 SIGSEGV 杀掉测试运行器 |
| CI 集成 | GitHub Actions——编译 + ctest + ASan 全自动 |

**核心观点**：C 的测试不是"写了就行"——as_ptr_stack 的 SEGV 会杀掉你的测试运行器。技术专家不是"知道 Unity 怎么用"，而是"知道为什么 C 的测试框架需要 fork 隔离——因为 C 没有异常，一个 SIGSEGV 就等于末日，唯一保护测试运行器的方法是把每个测试放在独立的子进程中"。

## 面试题

**Q1：gcov/lcov 的覆盖率是插桩还是采样？覆盖率 100% 代表没有 bug 吗？**

gcov 是**编译时插桩**——`-fprofile-arcs -ftest-coverage` 为每个基本块插入计数器。覆盖率 100% 不代表无 bug——它只证明**每行代码被执行过**，不证明：
- 每行的所有分支组合都被覆盖（MC/DC 覆盖率才查这个）
- 边界值被测试过（等价类/边界值分析）
- 异步时序/并发竞争被触发

**追问**："ASan 检测越界但为什么漏了未初始化读？"——ASan 的影子内存机制只为**可访问性**（分配/释放状态）分配影子位，不跟踪每个字节是否被初始化。Valgrind memcheck 的核心差异正在于此。

**Q2：gcov 和生产性能 profiling 的区别？**

gcov 统计**代码覆盖率**——哪些行被执行过，目的是找出未被测试覆盖的死代码。perf 统计**CPU 热点**——哪些函数消耗了最多 CPU 时间，目的是优化性能瓶颈。两者互补——gcov 找出"没跑到的代码"，perf 找出"跑得最慢的代码"。
