# 时间与定时器

> **对应 Layer**：Layer 4（OS 接口补充—时间子系统），stage4 补遗第 1 篇  
> **主线标准**：C11/C17 + Linux 系统调用（POSIX）

---

## 1. 引言：为什么时间会"跳"？

2016 年闰秒事件——全世界 NTP 服务器同时将系统时钟回退 1 秒。所有依赖 `gettimeofday` 做超时判断的 C 服务程序在这一刻陷入死循环或提前触发超时。Google 在 2011 年就预见了这个问题——他们的 "Leap Smear" 方案将闰秒分摊到 24 小时中平滑过渡，而不用突然跳变。

但大多数服务没有 Google 的 Luck。Redis 2.8 版本有一个已知的 bug：系统时间回退导致 `server.mstime` 减小，`aeProcessEvents` 的超时计算为负值→select/epoll 的 timeout 参数为负→死循环 100% CPU。修复很简单——用 `CLOCK_MONOTONIC` 替代 `gettimeofday`。

这个故事教会每一个 C 系统编程工程师：**你不只是在写 C——你在写的东西会跑在真实的 Linux 内核上，内核有自己的时间子系统，它的行为受 NTP 守护进程、系统管理员、闰秒和虚拟化环境的影响。**

## 2. `gettimeofday` vs `clock_gettime`——两条时间线

### 2.1 两种时间的根本区别

```c
#include <sys/time.h>
#include <time.h>

// 墙钟（wall-clock）——告诉你"现在几点"
struct timeval tv;
gettimeofday(&tv, NULL);
printf("Realtime: %ld.%06ld\n", tv.tv_sec, tv.tv_usec);
// 输出：1719763200.123456——系统管理员可以用 date -s 改、NTP 可以跳

// 单调钟（monotonic clock）——告诉你"启动后过了多久"
struct timespec ts;
clock_gettime(CLOCK_MONOTONIC, &ts);
printf("Monotonic: %ld.%09ld\n", ts.tv_sec, ts.tv_nsec);
// 输出：82345.678901234——从开机开始计数，只向前走，从不后退
```

| 属性 | `gettimeofday` / `CLOCK_REALTIME` | `CLOCK_MONOTONIC` |
|---|---|---|
| 含义 | 墙上时钟——"现在是几点" | 单调递增计数器——"启动后过了多久" |
| 受 NTP 步进影响？ | 是（>500ms 跳变） | **否** — 步进不影响 MONOTONIC |
| 受 NTP 微调（slewing）影响？ | 是（频率微调 ±500ppm） | **是！** — `adjtimex` 调整时钟频率会影响 MONOTONIC 的走时速率 |
| 受系统管理员影响？ | 是（`date -s` 直接改） | 否 |
| 受闰秒影响？ | 是（回退或重复） | 否 |
| 受虚拟机暂停影响？ | 是 | 否（不含虚拟机暂停的时间） |
| 适用场景 | 对人类的日志时间戳 | **所有超时/延时/性能测量** |
| 精度 | 微秒 | 纳秒 |
| 系统调用 | `gettimeofday` | `clock_gettime` |

### 2.2 内核实现——两条时间线的物理来源

**`CLOCK_REALTIME`**：内核维护 `tk_core.timekeeper.xtime_sec`（从 epoch 开始的秒数）+ `xtime_nsec`（纳秒偏移）。NTP 守护进程通过 `adjtimex()` 系统调用修改这个值。

**`CLOCK_MONOTONIC`**：内核在读取时通过 `tkr_mono.base + (cycles * mult) >> shift` **实时计算** monotonic 秒数（而非存在一个独立的 `ktime_sec` 字段中）。NTP 步进不改变 `tkr_mono.base`，但频率微调（slewing）会改变 `mult` 参数——这就是 **MONOTONIC 的速率受 NTP 微调影响** 的原因。`CLOCK_MONOTONIC_RAW` 用未调频的原始硬件计数器，完全不受 NTP 任何影响。

在 C 代码中，`gettimeofday()` 调用底层的 `do_gettimeofday() → ktime_get_real_ts64()`。`clock_gettime(CLOCK_MONOTONIC)` 调用 `ktime_get_ts64()`。两条线在内核中是完全分离的。

### 2.3 生产事故——时间跳变的真实代价

**Redis 2.8 时间回退 bug**：

```
场景：系统管理员用 date -s 将时间回退 1 小时

Redis 事件循环：
  last_time = gettimeofday()   → 14:00:00
  ... 管理员改时间 ...
  now = gettimeofday()         → 13:00:01

  // Redis aeProcessEvents()
  int timeout_ms = next_timer_ms - now_ms;  // now_ms 变小了！
  timeout_ms = 1000 - (-3599000) = 3599000  // 变成正数——1 小时超时！
  // 或者如果刚好没有定时器：timeout_ms = -1 → select(-1) → 死循环 100% CPU
```

**Java GC 日志时间混乱**（类似原理）：`System.currentTimeMillis()` 依赖 `gettimeofday`——NTP 步进时，GC 日志显示"一个 GC 暂停花了 -500ms"——实际上 GC 花了 200ms，但时钟后退了 700ms。

**修复方案**：所有超时相关的代码检查：是否用了 `CLOCK_MONOTONIC`？如果用了 `gettimeofday`，改掉。

### 2.4 其他时钟类型

| 时钟 | 含义 | 用途 |
|---|---|---|
| `CLOCK_MONOTONIC_RAW` | 原始硬件计数器——**连 NTP 频率微调也不受** | 性能基准测试——时间间隔不受 NTP slewing 影响，比普通 MONOTONIC 更适合测量代码耗时 |
| `CLOCK_MONOTONIC_COARSE` | 低精度 MONOTONIC——通过 **vDSO** 在用户态读取 | 高吞吐量计数器——<20ns 延迟（零系统调用） |
| `CLOCK_PROCESS_CPUTIME_ID` | 当前进程的 CPU 时间（用户+系统） | 分析 CPU 使用量 |
| `CLOCK_THREAD_CPUTIME_ID` | 当前线程的 CPU 时间 | 分析单个线程 |
| `CLOCK_BOOTTIME` | 同 MONOTONIC 但包含系统挂起时间 | 需要计算真实 wall-time 间隔 |

## 3. `nanosleep`——精确延时

### 3.1 基本用法

```c
#include <time.h>

struct timespec req = { .tv_sec = 0, .tv_nsec = 500000000 };  // 500ms
struct timespec rem;

int ret = nanosleep(&req, &rem);

if (ret == -1 && errno == EINTR) {
    // 被信号中断——剩余时间在 rem 中
    // 继续休眠剩余时间
    nanosleep(&rem, NULL);
}
```

**为什么 `nanosleep` 替代了 `usleep`**：`usleep` 在 POSIX.1-2008 中被标记为废弃——它没有信号中断恢复机制。`nanosleep` 的第二个参数 `rem` 保存了被中断时剩余的休眠时间。

### 3.2 `clock_nanosleep`——绝对时间定时

`nanosleep` 使用**相对时间**——你告诉内核"从现在开始睡 500ms"。如果多次 `nanosleep` 之间有处理逻辑，累积误差逐渐增长：

```c
// 错误——累积漂移
struct timespec ts = { .tv_sec = 0, .tv_nsec = 500000000 };
while (running) {
    do_work();          // 可能耗时 1-10ms
    nanosleep(&ts, NULL);  // 又等 500ms——实际周期 = 501-510ms
}

// 正确——`clock_nanosleep` + TIMER_ABSTIME
clock_gettime(CLOCK_MONOTONIC, &ts);
while (running) {
    do_work();
    ts.tv_nsec += 500000000;  // 按绝对时间提前 500ms
    if (ts.tv_nsec >= 1000000000) { ts.tv_sec++; ts.tv_nsec -= 1000000000; }
    clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &ts, NULL);
    // 无论 do_work 耗时多少，下一个唤醒时间总是间隔 500ms
}
```

**内核实现**：`clock_nanosleep` → `hrtimer_nanosleep`。`TIMER_ABSTIME` 模式直接设置到期时间——`hrtimer_start(timer, expires, HRTIMER_MODE_ABS)`。这是所有精确周期定时器的标准机制。

### 3.3 vDSO——用户态时间读取

高并发服务（每请求读一次时间）下，`clock_gettime` 是热点路径。glibc 通过 **vDSO**（virtual Dynamic Shared Object，虚拟动态共享对象）对 `CLOCK_MONOTONIC_COARSE` / `CLOCK_REALTIME_COARSE` 实现**用户态**读取——零系统调用，~20ns vs ~200ns 完整 syscall。内核将时间信息写入 vDSO 页面，用户态直接读内存即获取时间戳。代价：精度降为 tick 级（~1ms）。

### 3.4 内核实现

`nanosleep()` → `hrtimer_nanosleep()` 将当前任务加入高精度定时器队列。`schedule()` 让出 CPU。当定时器到期→中断→唤醒→`nanosleep` 返回。

**为什么不是精确的纳秒**：`nanosleep` 只是"至少休眠 N 纳秒"——调度器可能在定时器到期后几微秒到几毫秒才重新唤醒线程。如果需���精确延时，需要实时调度策略（`SCHED_FIFO`）。

### 3.3 实验——测量 nanosleep 的实际精度

```bash
cat > nanosleep_accuracy.c << 'EOF'
#include <stdio.h>
#include <time.h>

int main() {
    struct timespec start, end, req = { .tv_sec = 0, .tv_nsec = 1000000 };  // 1ms
    for (int i = 0; i < 1000; i++) {
        clock_gettime(CLOCK_MONOTONIC, &start);
        nanosleep(&req, NULL);
        clock_gettime(CLOCK_MONOTONIC, &end);
        long elapsed = (end.tv_sec - start.tv_sec) * 1000000000L +
                       (end.tv_nsec - start.tv_nsec);
        printf("%ld ns (requested 1000000)\n", elapsed);
    }
    return 0;
}
EOF
gcc -O2 nanosleep_accuracy.c -o nanosleep_accuracy && ./nanosleep_accuracy | head -20
# 典型输出：1000500 ns ← 实际休眠超过请求时间 500ns（调度器唤醒延迟）
```

## 4. POSIX 定时器——任务定时触发

### 4.1 基本用法

```c
#include <signal.h>
#include <time.h>

void timer_handler(int sig) {
    static int count = 0;
    printf("Timer tick %d\n", ++count);
}

int main() {
    signal(SIGUSR1, timer_handler);

    struct sigevent sev = {
        .sigev_notify = SIGEV_SIGNAL,
        .sigev_signo  = SIGUSR1
    };

    timer_t timerid;
    timer_create(CLOCK_MONOTONIC, &sev, &timerid);

    struct itimerspec its = {
        .it_value    = { .tv_sec = 1 },           // 首次 1 秒后
        .it_interval = { .tv_sec = 0, .tv_nsec = 500000000 }  // 之后每 500ms
    };
    timer_settime(timerid, 0, &its, NULL);

    pause();  // 等信号
    timer_delete(timerid);
    return 0;
}
```

**`timer_create` 的优势**：替代老旧的 `alarm()`（只能设秒级、只有一个定时器、用 `SIGALRM`）。POSIX 定时器可以有多个、纳秒精度、任意信号。

### 4.2 `timerfd`——epoll 集成的首选

**POSIX 定时器用信号通知——在 Reactor 模型中不方便。`timerfd` 将定时器变为 fd**——可以在 epoll loop 中统一处理：

```c
#include <sys/timerfd.h>

int tfd = timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK);

struct itimerspec its = {
    .it_value    = { .tv_sec = 1 },
    .it_interval = { .tv_sec = 5 }   // 之后每 5 秒触发一次
};
timerfd_settime(tfd, 0, &its, NULL);

// 加入 epoll
struct epoll_event ev = { .events = EPOLLIN, .data.fd = tfd };
epoll_ctl(epfd, EPOLL_CTL_ADD, tfd, &ev);

// epoll_wait 返回时
uint64_t expirations;
read(tfd, &expirations, sizeof(expirations));  // 读取定时器触发次数——清空事件
// 如果定时器触发了 3 次才被处理，expirations = 3
```

**为什么 `timerfd` 比 `timer_create`+信号更适合 Reactor 模型**：
- 定时器事件和其他 fd（socket/pipe）在同一个 epoll loop 中统一处理——不需要异步信号中断
- `read(tfd)` 返回触发次数——不会因为处理慢而丢失触发

### 4.3 生产案例——Redis 的定时器实现

Redis 用 `aeCreateTimeEvent()` 创建定时任务——内部是一个链表，按到期时间排序。每次事件循环时检查第一个定时器是否到期。Redis 的内部时间 `server.mstime` 在 Redis 6.0+ 中基于 `clock_gettime(CLOCK_MONOTONIC)`。

---

**定时器精度的深层原因**：
- **`CONFIG_HZ`**：内核 tick 频率——100/250/1000Hz。低 HZ → 调度延迟更大，定时器到期与唤醒之间的延迟更长
- **`CONFIG_HIGH_RES_TIMERS`**：高精度定时器（hrtimer）——绕过 tick，直接编程 LAPIC/HPET 硬件定时器。如果未启用→定时器精度降至 tick 级（~1-10ms）
- **timer slack**：`prctl(PR_SET_TIMERSLACK)`——内核故意将多个定时器到期时间对齐以减少唤醒次数。默认 50µs。实时应用应设 0
- **C-states**：深度休眠时 LAPIC timer 停止→唤醒延迟可达 100µs-1ms。实时系统用 `idle=poll` 或 CPU isolation 解决
- **虚拟化 steal time**：hypervisor 暂停 vCPU→`CLOCK_MONOTONIC` 不计入暂停时间→定时器可能在 vCPU 返回后立即到期

## 6. 面试题

### 面试题：CLOCK_MONOTONIC 与时间跳变

**面试官**：服务端超时判断为什么必须用 `clock_gettime(CLOCK_MONOTONIC)` 而不是 `gettimeofday`？

**回答**：`gettimeofday` 读的是墙上时钟（CLOCK_REALTIME）——系统管理员 `date -s`、NTP 步进（>500ms 跳变）、闰秒都可能导致时间回退。如果一个超时计算 = 到期时间 - 当前时间，当前时间突然回退 1 小时→负超时→epoll_wait 负 timeout→死循环 100% CPU（Redis 2.8 bug）。`CLOCK_MONOTONIC` 从开机开始单调递增，只向前不走——不受任何上述事件影响。所有超时/延时/性能测量必须用它。

**追问 1（面试官）**：那 `CLOCK_MONOTONIC` 有没有可能"变慢"或"变快"？

**追问 1 回答**：NTP 频率微调（slewing，±500ppm）会改变 monotonic 的走时速率。`CLOCK_MONOTONIC_RAW` 连 NTP 微调也不受——用原始硬件计数器（TSC 或架构定时器）。性能基准测试应选 MONOTONIC_RAW 消除所有外部干扰。`CLOCK_BOOTTIME` 额外包含系统挂起时间——需要计算真实 wall-time 间隔时使用。

**追问 2（面试官）**：`timerfd` 和 `timer_create` + 信号的区别？为什么 Reactor 模型用 timerfd？

**追问 2 回答**：timerfd 把定时器变成 fd——可加入 epoll 统一等事件。信号在 Reactor 模型中不方便——发送异步信号中断任何代码→不能安全做任何事（printf/malloc/加锁都不行）。timerfd 触发后 epoll_wait 返回 tfd→read(tfd) 读触发次数→在正常事件循环中处理，完全同步。"一次事件循环里同时处理 socket 和 timer"是 Reactor 的哲学。

## 总结

| 概念 | 核心知识 |
|---|---|
| `CLOCK_MONOTONIC` | 所有超时的基础——不受 NTP/系统管理员/闰秒影响 |
| `gettimeofday` 的陷阱 | NTP 步进→时间回退→负超时→死循环（Redis 2.8 bug） |
| 内核两条时间线 | `xtime_sec`（REAL）vs `ktime_sec`（MONOTONIC）—完全独立 |
| `CLOCK_MONOTONIC_RAW` | 连 NTP 微调也不受——性能基准测试用 |
| `clock_nanosleep` + `TIMER_ABSTIME` | 绝对时间定时——无累积漂移——精确定时循环的标准方案 |
| `nanosleep` + EINTR | 被信号中断→`rem` 保存剩余时间→继续休眠 |
| `timerfd` | 定时器变 fd——epoll 集成的首选 |
| Redis 时间实现 | `aeCreateTimeEvent` + 内部 `server.mstime`—基于 MONOTONIC |

**核心观点**：时间不是简单的"读一个值"——在 Linux 中，不同时钟有根本不同的行为。`gettimeofday` 不是 `CLOCK_REALTIME` 的简化版——它是不安全的替代。技术专家不是"知道 clock_gettime 怎么用"，而是"知道 NTP 步进会导致你的定时器提前或延迟触发，并且知道如何用 CLOCK_MONOTONIC 防止这个 bug 进入生产代码"。
