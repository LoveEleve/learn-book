## Part A：目录操作

### A.1 `opendir`/`readdir`——遍历目录

```c
#include <dirent.h>
#include <stdio.h>

DIR *d = opendir("/tmp");
if (!d) { perror("opendir"); return -1; }

struct dirent *entry;
while ((entry = readdir(d)) != NULL) {
    // 跳过 "." 和 ".."
    if (entry->d_name[0] == '.') continue;

    switch (entry->d_type) {
        case DT_REG:  printf("File: %s\n", entry->d_name); break;
        case DT_DIR:  printf("Dir : %s\n", entry->d_name); break;
        case DT_LNK:  printf("Link: %s\n", entry->d_name); break;
        case DT_FIFO: printf("FIFO: %s\n", entry->d_name); break;
    }
}
closedir(d);
```

**`d_type` 的可靠性**：`DT_REG`/`DT_DIR` 等依赖于底层文件系统是否在 `readdir` 时提供类型信息。ext4/xfs 全都提供，但 NFS 可能写 `DT_UNKNOWN`。如果需要保证正确，调用 `stat(entry->d_name)` 代替。

### A.2 `scandir`——过滤+排序的组合

```c
#include <dirent.h>

// 过滤器——只保留 .log 文件
int filter_log(const struct dirent *e) {
    const char *name = e->d_name;
    size_t len = strlen(name);
    return len > 4 && strcmp(name + len - 4, ".log") == 0;
}

struct dirent **namelist;
int n = scandir("/var/log", &namelist, filter_log, alphasort);
for (int i = 0; i < n; i++) {
    printf("  %s\n", namelist[i]->d_name);
    free(namelist[i]);   // scandir 分配的内存——调用者负责释放
}
free(namelist);
```

**`scandir` 的陷阱**：`namelist` 中的每一项 `namelist[i]` 和被 `namelist` 指向的数组都由 `scandir` 分配（内部调用 `malloc`）。调用者必须释放每一项和数组本身——忘记释放弃 `scandir` 的内存是常见的内存泄漏源头。

### A.3 `nftw`——递归遍历

```c
#include <ftw.h>

int callback(const char *path, const struct stat *sb, int flag, struct FTW *ftw) {
    printf("%-3s %s\n",
        flag == FTW_D ? "[D]" :
        flag == FTW_F ? "[F]" : "[?]", path);
    return 0;  // 返回 0 继续，非 0 停止
}

nftw("/tmp", callback, 10, FTW_PHYS);  // 最多 10 个 fd 同时打开
```

### A.4 生产案例——Nginx 配置目录遍历

Nginx 的 `ngx_conf_walk_directory()` 遍历 `/etc/nginx/conf.d/` 目录，按文件名排序加载所有 `.conf` 文件。核心逻辑：

```c
// Nginx 简化版配置加载
DIR *d = opendir("/etc/nginx/conf.d");
struct dirent *entry;
while ((entry = readdir(d)) != NULL) {
    if (ngx_strstr(entry->d_name, ".conf") != NULL) {
        ngx_conf_parse(entry->d_name);  // 解析配置文件
    }
}
closedir(d);
```

## Part B：用户/组/权限

### B.1 UID/EUID 的区别

```c
#include <unistd.h>
#include <stdio.h>

uid_t uid  = getuid();    // 实际用户 ID——启动进程的用户
uid_t euid = geteuid();   // 有效用户 ID——用于权限检查

printf("Real UID=%d, Effective UID=%d\n", uid, euid);
// 普通程序：uid == euid
// setuid 程序：uid != euid（euid 是文件所有者的 UID）
```

**`setuid` 程序**：当可执行文件的 `setuid` 位被设置时，内核将进程的 euid 设为文件所有者的 UID——即使用户 A 启动了该程序，程序以文件所有者（通常是 root）的身份运行。`passwd` 命令是经典的 setuid 程序——普通用户可以改自己的密码，但改密码需要写 `/etc/shadow`（仅 root 可写）。

### B.2 root 降权——Nginx 的主从模型

```c
// Nginx 启动时：
// 1. master 进程以 root 身份执行 bind(80)、读取证书
// 2. 创建 worker 后立即降权

if (geteuid() == 0) {
    // 降权到 nobody 用户
    if (setgid(65534) != 0) { perror("setgid"); exit(1); }
    if (setuid(65534) != 0) { perror("setuid"); exit(1); }
    // 现在这个进程不再是 root —— 即使被注入也无法改系统文件
}

// 验证降权成功
if (setuid(0) == 0) {
    fprintf(stderr, "DANGER: can still become root!\n");
}
if (seteuid(0) == 0) {
    fprintf(stderr, "DANGER: effective uid is still root!\n");
}
```

**为什么降权后不能重新提权**：`setuid()` 对非 root 进程只允许设为自己的 uid、euid 或 saved-suid。一旦 worker 降权到 nobody，就无法再回到 root——这是 Nginx 安全的基石。

### B.3 Linux Capabilities——root 权限细分

传统 Unix 中 root 是"全权"——有 CAP_SYS_ADMIN 就意味着可以加载内核模块、挂载文件系统、修改内核参数。`capabilities` 将 root 的巨大权限拆分为细粒度的小权限。

**capabilities 的 5 个集合**：

| 集合 | 含义 | exec 后变化 |
|---|---|---|
| **Permitted** | 进程**可以**拥有的能力（上限） | 受 pI + file permitted 的 AND 限制 |
| **Inheritable** | 可通过 exec 传递给子进程的能力 | 保留（受 Ambient 影响）|
| **Effective** | 当前**正在使用**的能力 | 非 root 通常清空 |
| **Bounding** | 进程**绝对不能**拥有的能力（上限上限） | 不增加，只减少 |
| **Ambient** | 非 root 进程 exec 后保留的能力（Linux 4.3+） | 帮助非 root 进程在 exec 后保留能力 |

```c
#include <sys/capability.h>

cap_t caps = cap_get_proc();  // 获取当前进程的能力集

cap_flag_value_t val;
cap_get_flag(caps, CAP_NET_BIND_SERVICE, CAP_PERMITTED, &val);
printf("Bind to port <1024: %s\n", val ? "Yes" : "No");

// 检查是否可以做原始套接字
cap_get_flag(caps, CAP_NET_RAW, CAP_EFFECTIVE, &val);
printf("Raw socket: %s\n", val ? "Yes" : "No");

cap_free(caps);
```

**生产案例**：给 Nginx 二进制设置 `cap_net_bind_service=ep` 允许 worker（nobody）绑定 80 端口——而不需要给整个过程 root 权限。

### B.5 0022

```c
mode_t old = umask(0027);  // 所有者 rwx，组 r-x，其他人无权限
// 新建文件的权限 = 创建时请求的权限 & ~umask
int fd = open("new.txt", O_CREAT | O_WRONLY, 0666);
// 实际权限 = 0666 & ~0027 = 0640（rw-r-----）

// 目录不同——umask 可能去掉 x 权限导致无法 cd 进入
mkdir("newdir", 0777);
// 实际权限 = 0777 & ~0027 = 0750——组有 r-x，可 cd 进入
// 如果 umask 是 0033：0777 & ~0033 = 0744——组只有 r--，**不能 cd**
umask(old);  // 恢复原值

**线程安全**：glibc 的 umask 是线程安全的（内部用信号保护），但修改 umask 是全局操作——影响同一进程中所有线程的新文件创建。  // 所有者 rwx，组 r-x，其他人无权限
// 新建文件的权限 = 创建时请求的权限 & ~umask
int fd = open("new.txt", O_CREAT | O_WRONLY, 0666);
// 实际权限 = 0666 & ~0027 = 0640（rw-r-----）
umask(old);  // 恢复原值
```

## 面试题

**面试官**：Nginx master/worker 的权限模型——为什么 master 是 root，worker 是 nobody？降权后为什么不能再提权？

**回答**：master 需要 root 才能 bind 特权端口（<1024）、读证书文件（`/etc/ssl/` 仅 root 可读）、切换 worker 用户。worker 只做 I/O 处理——不需要任何特权。如果 worker 被攻击者注入，它只能以 nobody 权限瘫痪自己——不能修改系统文件、不能 bind 新端口、不能读其他用户的数据。`setuid(nobody_uid)` 后不能提权是因为内核记录了一个 saved-suid——非 root 进程只能设 uid 为 real uid、effective uid 或 saved-suid。worker 的三者都被改为 nobody 后，回不到 root。

**追问 1（面试官）**：capabilities 怎么代替全权 root？给一个 Nginx 用 capabilities 绑定 80 端口的例子。

**追问 1 回答**：`setcap cap_net_bind_service=ep /usr/sbin/nginx`——将 CAP_NET_BIND_SERVICE 的能力加入 Nginx 二进制的 Permitted 和 Effective 集合。Nginx 启动后，即使用 nobody 身份运行，仍可在有效能力集中有 NET_BIND_SERVICE→可以 bind 80 端口。不需要整个进程跑 root——能力粒度为"我只给你绑端口的权限，不给其他 root 权限"。

**追问 2（面试官）**：setuid 程序的安全陷阱——为什么不能在 setuid 程序里用 `system()` 或 `popen()`？

**追问 2 回答**：`system("ls")` 内部调用 `/bin/sh -c "ls"`——shell 忽略 setuid，以 real UID 执行命令（不是 effective UID）。setuid 程序启动者的 real UID 是普通用户→`system` 里执行"`/bin/sh -c \"rm -rf /tmp/*\"`"只在 /tmp 下操作——合理。但如果环境变量 PATH 被攻击者修改——`/tmp/evil/ls` 被先找到→以 root 权限执行攻击者代码。且 system 之前没有有效的 fd 隔离——继承的 fd 可能导致泄漏。

## 总结

| 概念 | 核心知识 |
|---|---|
| `opendir/readdir` | 标准目录遍历——`d_type` 在 NFS 上可能为 `DT_UNKNOWN` |
| `scandir` | 过滤+排序——调用者负责释放每一项和数组 |
| `nftw` | 递归遍历——Nginx 用它加载配置目录 |
| `getuid` vs `geteuid` | 实际 UID vs 有效 UID——setuid 程序用 euid 做权限检查 |
| Nginx 降权 | master(root)→worker(nobody)——`setuid(65534)` 不���逆转 |
| capabilities | root 权限细分——`CAP_NET_BIND_SERVICE` 替代全权 root |
| `umask` | 文件创建权限掩码——`new_perm = mode & ~umask` |
