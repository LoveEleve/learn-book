## 1. 引言：错误处理的两条路

### 1.1 C 的返回码——错误容易"被忘掉"

C 里处理错误靠返回码：

```cpp
int divide(int a, int b, int* result) {
    if (b == 0) return -1;  // 错误——除零
    *result = a / b;
    return 0;               // 正确
}

// 调用方必须检查每一个返回码
int result;
if (divide(10, 0, &result) != 0) {
    // 处理错误
}
```

这有两个致命缺陷：(1) **调用方可以忘记检查**——`divide(10, 2, &result);` 没检查返回码，可能用了未初始化的 result；(2) **正常逻辑和错误处理混在一起**——每两行正常代码就要穿插一个 `if (ret < 0) { goto cleanup; }`，读代码的人被错误处理打断思路。

### 1.2 C++ 的异常——正常逻辑和错误处理分离

C++ 异常给你另一种思路：**正常代码走主路径，错误自动"跳"到专门的 `catch` 块**：

```cpp
#include <iostream>
#include <stdexcept>

int divide(int a, int b) {
    if (b == 0) throw std::runtime_error("division by zero");
    return a / b;
}

int main() {
    try {
        int result = divide(10, 0);
        std::cout << result;  // 不会执行——异常跳过了
    } catch (const std::runtime_error& e) {
        std::cout << "Error: " << e.what() << '\n';
    } catch (...) {
        std::cout << "Unknown error\n";  // 兜底——捕获任何东西
    }
}
```

核心区别——C 的返回码是"调用方可以忽略的建议"，C++ 异常是**你不处理就接着往上抛**——最终程序终止。异常让错误处理"强制化"了。

**但异常引入了新问题——你的资源在异常穿过时会被正确释放吗？**

```cpp
void bad_function() {
    int* p = new int(42);    // 裸指针
    risky_call();             // 可能抛异常
    delete p;                 // 如果抛了——这行不执行——泄漏！
}
```

本章教两件事：基本语法，以及怎么让你的代码在异常发生时"保持正确"——即异常安全。

## 2. `try`/`catch`/`throw`——异常的基本语法

### 2.1 抛出和捕获

```cpp
#include <iostream>
#include <stdexcept>

void validate_age(int age) {
    if (age < 0)   throw std::invalid_argument("age cannot be negative");
    if (age > 150) throw std::out_of_range("age too large");
}

int main() {
    try {
        validate_age(-5);
    } catch (const std::invalid_argument& e) {
        std::cout << "Bad input: " << e.what() << '\n';
    } catch (const std::out_of_range& e) {
        std::cout << "Out of range: " << e.what() << '\n';
    } catch (const std::exception& e) {
        std::cout << "Some error: " << e.what() << '\n';  // 兜底
    }
}
```

- **`throw`**：可以抛任何类型（int/string/自定义类/标准异常子类）。生产代码建议抛 `std::exception` 的子类。
- **`catch`**：按类型匹配——从上到下逐个试，第一个匹配的被选中。子类的 `catch` 放在父类前面——`std::invalid_argument` 是 `std::exception` 的子类，如果 `catch (std::exception&)` 放前面，它什么都能接住。
- **`catch (...)`**：兜底捕获任何东西——但你拿不到异常对象本身，不知道具体是什么。

### 2.2 标准异常层次

C++ 标准库的异常体系：

```
std::exception
├── std::logic_error       （程序逻辑错误——应该避免）
│   ├── std::invalid_argument
│   ├── std::out_of_range
│   └── std::length_error
├── std::runtime_error     （运行时错误——无法预测）
│   ├── std::overflow_error
│   ├── std::underflow_error
│   └── std::system_error
└── std::bad_alloc         （new 失败）
```

- `logic_error`——程序 bug，应该修复代码而不是 `catch` 它
- `runtime_error`——外部因素，如文件不存在、网络断开，应该 `catch` 并处理
- `bad_alloc`——`new` 分配失败时抛出。C++11 的 `new (std::nothrow)` 返回 `nullptr` 而不抛异常

### 2.3 异常和返回码的选择

| | 异常 | 返回码 |
|---|---|---|
| 调用方可忽略 | 不能——不处理就 `terminate` | 可以——忘了检查就静默出错 |
| 性能 | 抛异常慢（栈展开 + RTTI），正常路径快 | 每次调用都要检查返回码 |
| 代码可读性 | 正常逻辑和错误处理分离 | 交织在一起 |
| 适用场景 | 不经常发生的错误 | 高频错误（如 EOF、not found） |

**原则**：异常用于"不应该发生"的错误（除零、无效参数、构造失败）。预期的可恢复错误（文件不存在、键找不到）可以考虑返回码或 `std::optional`（C++17）。

## 3. 栈展开——异常穿过你的代码时发生了什么

### 3.1 异常冒泡的过程中谁在清理

当异常从 `throw` 点向上冒泡，每经过一个函数帧，该帧的**局部对象**被析构：

```cpp
#include <iostream>
#include <memory>

struct Tracker {
    const char* name;
    Tracker(const char* n) : name(n) { std::cout << name << " created\n"; }
    ~Tracker()                   { std::cout << name << " destroyed\n"; }
};

void inner() {
    Tracker t("inner");    // 局部对象
    throw std::runtime_error("oops!");
    // t 被栈展开析构←编译器自动生成
}

void outer() {
    Tracker t("outer");    // 局部对象
    inner();               // 异常从这里冒出
    // t 也被栈展开析构
}

int main() {
    try {
        outer();
    } catch (const std::runtime_error&) {
        std::cout << "caught!\n";
    }
}
```

**输出**：
```
outer created
inner created
inner destroyed    ← 栈展开：inner 帧中 t 被析构
outer destroyed    ← 栈展开：outer 帧中 t 被析构
caught!
```

栈展开按照"构造的逆序"逐个析构局部对象——这是 C++ RAII 的核心机制。

### 3.2 栈展开不释放什么——裸指针和裸资源

栈展开只析构**完整的 C++ 对象**。裸指针（`int*`）也是"对象"（8 字节），但它的析构函数什么也不做——不释放它指向的内存：

```cpp
void leaky() {
    int* p = new int(42);       // 🔴 裸指针——栈展开不释放它指向的 int
    throw std::runtime_error("leak!");
    // p 本身（8 字节的指针变量）被"析构"——就是什么都不做
    // p 指向的 int 还留在堆上→泄漏
}
```

非 RAII 包装的资源都一样——裸指针、裸文件句柄（`FILE*`）、裸锁（`pthread_mutex_t*`）——栈展开**都不会自动释放**。

### 3.3 正确姿势——所有资源都用 RAII 对象管理

```cpp
void safe() {
    auto p = std::unique_ptr<int>(new int(42));  // ✓ RAII 管理堆内存
    risky_call();                                 // 即使抛异常
    // p 的析构函数释放 int——RAII 正常工作
}

void safe_file() {
    std::ifstream f("data.txt");  // ✓ RAII 管理文件——析构函数 fclose
    read_all(f);
    // 即使 read_all 抛异常——f 的析构函数关闭文件
}
```

**核心规则**：异常安全的代码 = 所有资源都用 RAII 对象管理。这呼应了 Stage1 Ch04 的 RAII——异常安全是 RAII 最重要、最不可替代的使用场景。没有异常安全的需求，RAII 只是"语法方便"；有了异常安全的需求，RAII 变成**必须**。

## 4. 异常安全的三个保证级别

### 4.1 三级安全保证

每个函数在异常发生时提供的保证分为三级：

| 级别 | 承诺 | STL 例子 |
|---|---|---|
| **基本保证（basic）** | 不泄漏资源、对象状态有效（但值可能变了） | `std::copy` 从输入迭代器复制失败→目标序列部分元素已被写入，但所有元素仍是有效状态 |
| **强保证（strong）** | "要么全做，要么全不做"——状态回滚 | `vector::push_back` 抛异常（扩容失败或元素构造失败）→vector 回到操作前的状态——"insertion has no effects" |
| **不抛保证（nothrow）** | 承诺不抛异常 | `swap` / 移动构造 / 析构函数 |

三级是递增的——不抛 ≥ 强 ≥ 基本。

### 4.2 基本保证——不泄漏但可能"变样"

基本保证是最低要求——不泄漏资源、对象仍能安全使用，但不保证数据完全不变：

```cpp
// 基本保证示例——for_each 遍历到一半 Lambda 抛异常
std::vector<int> v = {1, 2, 3, 4, 5};
int modified = 0;
try {
    std::for_each(v.begin(), v.end(), [&](int& x) {
        if (++modified > 3) throw std::runtime_error("stop");
        x *= 2;  // 前 3 个元素已被翻倍→[2,4,6,4,5]
    });
} catch (...) {
    // v = [2, 4, 6, 4, 5]——前 3 个元素变了，后 2 个保持原样
    // 但 v 仍然是有效的 vector——这是"基本保证"
}
```

任何一个声称"异常安全"的 C++ 函数都应该至少满足基本保证。如果连这都做不到——异常后对象变成"已破坏状态"（如野指针、数据不一致）→不应该出现在生产代码里。

### 4.3 强保证——copy-and-swap 模式

强保证的实现模式——在临时副本上做所有危险操作，成功后再用不抛的 `swap` 换进来：

```cpp
#include <string>
#include <utility>

class Widget {
    std::string name;
    int value;
public:
    // 强保证——如果抛异常，对象完全不变
    void update(const std::string& new_name, int new_value) {
        // Step 1：在临时副本上做所有可能失败的事
        std::string temp_name = new_name;  // 可能抛 bad_alloc（string 拷贝分配内存）
        int temp_value = new_value;        // 不抛（int 赋值不抛）

        // Step 2：全部成功——用不抛的 swap 换进来
        name.swap(temp_name);              // string::swap 不抛——只交换内部指针
        std::swap(value, temp_value);      // int swap 不抛

        // Step 3：temp_name 和 temp_value 在离开作用域时被析构——不影响 Widget 的状态
    }
    // 隐式的强保证实现：如果 temp_name = new_name 抛了→name 和 value 都没被修改→对象不变
};
```

**为什么 `swap` 必须不抛**：如果 `swap` 抛异常——临时副本的干净数据没换进来，旧数据已被破坏→既不能满足强保证，也不能满足基本保证。

`std::swap` 在 C++11 中通过移动语义实现不抛——只交换内部指针，不分配内存。这就是 Ch03 移动语义在异常安全领地的兑现——没有移动构造的 `noexcept` 保证，`swap` 就不是不抛的，copy-and-swap 这个最优雅的异常安全模式就不存在。

### 4.4 不抛保证——`noexcept`

不抛保证是最强的——调用方**确信**不会收到异常。哪些函数应该不抛：

| 函数类型 | 为什么 | 例子 |
|---|---|---|
| 析构函数 | 如果析构抛异常且栈正在展开→`std::terminate` | `~File()` 吞掉 fclose 错误 |
| 移动构造 | `vector` 扩容时用它判断走移动还是拷贝 | `Widget(Widget&&) noexcept` |
| `swap` | copy-and-swap 的核心操作必须不抛 | `std::swap` |
| `delete` | 释放资源不应失败 | `operator delete` |

## 5. `noexcept`——C++11 的承诺机制

### 5.1 语法和含义

```cpp
// 承诺不抛异常
void swap(Widget& a, Widget& b) noexcept {
    // 内部只交换指针——不分配内存
}

// 条件 noexcept——仅当条件是 true 时才承诺不抛
template <typename T>
void my_swap(T& a, T& b) noexcept(noexcept(T(std::move(a)))) {
    T tmp = std::move(a);
    a = std::move(b);
    b = std::move(tmp);
}
```

`noexcept(T(std::move(a)))` —— `noexcept` 操作符在编译时检查表达式是否可能抛异常——如果 T 的移动构造标记了 `noexcept`，这个 `noexcept` 返回 `true`；否则返回 `false`。

### 5.2 `noexcept` 为什么影响性能

`vector` 扩容时的关键决策——用移动还是拷贝：

```cpp
// vector 扩容的内部逻辑（简化，C++11 实际用 std::move_if_noexcept + 标签分发）
// 如果 T 的移动构造是 noexcept → move_if_noexcept 返回 T&& → 走移动
// 如果 T 的移动构造不是 noexcept → move_if_noexcept 返回 const T& → 走拷贝
```

如果 `T` 的移动构造被标记为 `noexcept` —— `vector` 扩容时用移动（O(1) 交换指针）。如果没标记 `noexcept` —— `vector` 不敢用移动（万一移动到一半抛异常，旧 buffer 和新 buffer 都可能损坏）→退化为拷贝（O(n) 深拷贝每个元素）。

这就是 Stage1 Ch03 讲的 **"移动构造必须 noexcept"** 的终极原因——不是代码写错了，是不加 `noexcept` 你的移动构造函数等于没写（`vector` 不敢用）。

### 5.3 析构函数默认是 `noexcept`

C++11 起，析构函数隐式标记为 `noexcept(true)`。如果你需要析构函数能抛异常（极少见），必须显式声明 `noexcept(false)`：

```cpp
struct NormalDtor {
    ~NormalDtor() { /* 不能抛——编译器在背后加了 noexcept(true) */ }
};

struct DangerDtor {
    ~DangerDtor() noexcept(false) {  // 你明确要求"可以抛"
        throw std::runtime_error("bad");
    }
};
```

**为什么**：如果析构函数抛异常且栈已经在展开中（另一个异常正在传播）→ 两个异常同时存在 → C++ 标准要求 `std::terminate()` → 程序直接终止，没有 catch 的机会。

## 6. 构造和析构中的异常——边界情况

### 6.1 构造函数抛异常——对象从未"活过"

```cpp
class BadWidget {
    int* p1;
    int* p2;
public:
    BadWidget() : p1(new int(1)), p2(new int(2)) {
        throw std::runtime_error("construction failed");
        // 异常后——p1 分配了但 BadWidget 对象从未构造完成
        // 析构函数不跑！p1 泄漏！
    }
    ~BadWidget() { delete p1; delete p2; }
};

// BadWidget w;  // 构造失败——w 从未存在——析构不跑——p1 泄漏
```

**规则**：构造函数抛异常→对象从未"活过"→析构函数不跑。但**已构造的成员**（`p1` 是已构造的 `int*`）会被析构——只是 `int*` 的析构函数不释放 `*p1`。

**解决——用 RAII 成员替代裸指针**：

```cpp
class GoodWidget {
    std::unique_ptr<int> p1;
    std::unique_ptr<int> p2;
public:
    GoodWidget() : p1(new int(1)),
                   p2(new int(2)) {
        throw std::runtime_error("construction failed");
        // 异常后——p1 是已构造的 unique_ptr→它的析构函数被调→释放 int
        // p2 是已构造的 unique_ptr→同样被释放
        // 零泄漏！
    }
};
```

**关键**——已构造的成员变量（`unique_ptr<int> p1`）的析构函数会被调用，释放 `p1` 指向的 `int`。但如果 `p1` 是裸指针，它的析构函数只释放 8 字节的指针变量本身，不释放它指向的内存。

### 6.2 析构函数抛异常——双重灾难

```cpp
struct Bad {
    ~Bad() noexcept(false) {
        throw std::runtime_error("dtor threw!");
    }
};

int main() {
    try {
        Bad b;
        throw std::runtime_error("original");  // 第一个异常
        // b 的析构函数在栈展开时被调→throw→第二个异常！
    } catch (...) {
        // 永远不会执行——std::terminate() 已经终止了进程
    }
}
```

**输出**：`terminate called after throwing an instance of 'std::runtime_error'` → SIGABRT。

**铁律**：析构函数永远不抛异常。如果析构调用的函数可能失败（`fclose`、`pthread_mutex_unlock`）——在析构函数里 `try-catch(...)` 吞掉，记录日志：

```cpp
class SafeFile {
    FILE* f;
public:
    ~SafeFile() {
        try {
            if (f && fclose(f) != 0) {
                // 记录日志——但不能抛
            }
        } catch (...) {
            // 吞掉一切——析构函数不能传播异常
        }
    }
};
```

## 7. 可运行错误实验

### 实验 1：裸指针在异常中泄漏

```cpp
#include <iostream>
#include <stdexcept>

void leaky() {
    int* p = new int(42);       // 🔴 裸指针
    std::cout << "allocated: " << *p << '\n';
    throw std::runtime_error("oops!");  // 异常！delete p 不执行！
    delete p;                    // 永远不到这里
}

int main() {
    try {
        leaky();
    } catch (const std::exception& e) {
        std::cout << "caught: " << e.what() << '\n';
    }
    return 0;
}
```

**编译运行**：`g++ -std=c++11 leak.cpp -o leak && ./leak`
**valgrind 验证**：`valgrind --leak-check=full ./leak` → "4 bytes in 1 blocks are definitely lost"

**修复**：把 `int* p = new int(42);` 改为 `auto p = std::unique_ptr<int>(new int(42));`，重新编译——valgrind 无泄漏。

### 实验 2：析构函数抛异常 → std::terminate

```cpp
#include <iostream>
#include <stdexcept>

struct BadDtor {
    ~BadDtor() noexcept(false) {  // 显式允许析构抛异常
        throw std::runtime_error("dtor threw!");
    }
};

struct Container {
    BadDtor b;
    ~Container() { /* b 的析构在这里被调 */ }
};

int main() {
    try {
        Container c;
        throw std::runtime_error("original");  // 第一个异常
        // c 析构→b 析构→throw→第二个异常→std::terminate()
    } catch (...) {
        std::cout << "never reached\n";
    }
    return 0;
}
```

**运行**：`g++ -std=c++11 terminate.cpp && ./a.out`
**输出**：`terminate called after throwing an instance of 'std::runtime_error'` → SIGABRT

### 实验 3：构造函数中裸指针泄漏 vs RAII 安全

```cpp
#include <iostream>
#include <memory>
#include <stdexcept>

int leak_count = 0;

struct Raw {
    int* p;
    Raw() : p(new int(42)) {
        leak_count++;
        throw std::runtime_error("fail");
    }
    ~Raw() { delete p; leak_count--; }  // 不会被调！
};

struct Safe {
    std::unique_ptr<int> p;
    Safe() : p(std::unique_ptr<int>(new int(42))) {
        throw std::runtime_error("fail");
    }
    // unique_ptr 的析构被调→释放 int——安全
};

int main() {
    try { Raw r; } catch (...) {}
    std::cout << "Raw leak_count: " << leak_count << '\n';  // 1——泄漏了！

    try { Safe s; } catch (...) {}
    std::cout << "Safe: no leak (unique_ptr auto-cleaned)\n";
    return 0;
}
```

**输出**：`Raw leak_count: 1`（裸指针泄漏），Safe 无泄漏。

## 8. 面试题

### 面试题 1：异常安全的三个级别

**面试官**：C++ 的异常安全有哪三个级别？各给一个 STL 例子。

**回答**：(1) 基本保证——对象状态有效但值可能变了。`vector::push_back` 扩容失败→vector 仍是有效对象，但 capacity 可能已变化。(2) 强保证——"要么全做要么全不做"。`vector::insert` 失败→vector 回到插入前的状态，就像操作没发生过。(3) 不抛保证——承诺不抛异常。`swap`、移动构造、析构函数。三个级别递增——不抛 ≥ 强 ≥ 基本。

**追问（面试官）**：怎么把基本保证升级为强保证？给一个实现模式。

**追问回答**："copy-and-swap"模式——(1) 在临时副本上做所有可能失败的操作（拷贝构造、内存分配）；(2) 全部成功→用不抛的 `swap` 把临时副本换进来；(3) 任何一步失败→临时副本被析构，原对象未受任何影响。核心要求——`swap` 必须不抛（`noexcept`）。C++11 的移动语义实现了不抛的 `swap`（只交换内部指针），让 copy-and-swap 成为可用的模式。

### 面试题 2：`noexcept` 的用途

**面试官**：`noexcept` 解决什么问题？不加 `noexcept` 有什么后果？

**回答**：(1) **文档化承诺**——告诉调用方"这个函数不抛异常"；(2) **编译器优化**——`noexcept` 函数调用处编译器可以省略栈展开的代码；(3) **`vector` 扩容决策**——`vector` 用 `noexcept(移动构造)` 判断是否能用移动：移动构造标记 `noexcept` → 扩容用移动（快）；没标记 → 扩容用拷贝（安全但慢）。这就是 Stage1 Ch03 移动构造必须 `noexcept` 的原因——不加等于移动语义"白写"。

**追问（面试官）**：析构函数默认是 `noexcept` 吗？如果在析构函数里强制抛异常会发生什么？

**追问回答**：C++11 起析构函数默认 `noexcept(true)`。如果强制抛异常——情况分两种：(1) 没有其他异常在传播→异常照常传播；(2) 栈已经在展开中（另一个异常正在传播）→两个异常同时存在→`std::terminate()`→程序直接终止。这就是"析构函数绝不要抛异常"的根源——不是因为不能抛，是因为碰到"双重异常"直接杀进程，catch 的机会都没有。

### 面试题 3：构造函数中的异常安全

**面试官**：构造函数中抛异常后，已构造的成员会被析构吗？已 `new` 的裸指针呢？

**回答**：已构造的成员（如 `string name`）**会被析构**——它们是已完整创建的对象，编译器按构造逆序调它们的析构函数。已 `new` 的裸指针成员 (`int* p`)**不会被释放**——`p` 是已构造的成员会被析构，但 `int*` 的析构函数只释放指针本身（8 字节），不释放它指向的内存。解决方案——用 `unique_ptr` / RAII 类型的成员——即使构造函数抛异常，这些成员的析构函数会释放它们持有的资源。

**追问（面试官）**：构造函数里抛了异常——析构函数会跑吗？

**追问回答**：不会。对象从未"活过"（构造未完成），C++ 标准规定不调析构函数。所以构造函数必须自己处理已分配资源的清理——最容易的方式是用 RAII 成员（`unique_ptr`/`string`/`vector`），让编译器自动处理成员析构，不需要手动写清理代码。

## 9. 本章小结

| 概念 | 核心理解 |
|---|---|
| 栈展开 | 异常从 throw 到 catch 过程中，自动析构局部 RAII 对象 |
| RAII + 异常 | 所有资源用 RAII 管理——异常安全=RAII 的终极用途 |
| 基本保证 | 不泄漏——对象仍有效，但值可能变化（`push_back`） |
| 强保证 | copy-and-swap——"要么全做要么全不做"（`insert`） |
| 不抛保证 | `noexcept`——移动构造/析构函数/swap |
| `noexcept` 操作符 | 编译时检查表达式是否可能抛异常 |
| 构造+异常 | 已构造的 RAII 成员被析构；裸指针成员不被释放 |
| 析构+异常 | 永远不抛——双重异常→`std::terminate` |

**本章没讲但后续章节会讲**：`std::exception_ptr` / `std::nested_exception`（异常嵌套传播——C++11 进阶）、`std::expected`（C++23——类型化错误处理替代异常）、异常的性能开销（平台特定，参考手册即可）。
