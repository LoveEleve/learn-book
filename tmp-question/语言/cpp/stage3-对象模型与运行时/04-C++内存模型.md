> **前置依赖**：读者已完成 C 语言阶段的内存模型（store buffer / MESI / x86 lock 前缀 / ARM LDREX-STREX），**理解 `memory_order_relaxed`/`acquire`/`release`/`seq_cst` 的语义和硬件实现**。本章不重讲这些——只讲 C++11 在 C11 基础上的封装和差异。
> **主线版本**：C++11

## 1. 引言：你已经会了——C++ 只是换了一种写法

C 阶段你已经深刻理解了原子操作和内存序——你知道 store buffer 为什么让 relaxed 不够用、知道 x86 的 lock 前缀和 ARM 的 LDREX/STREX、知道 memory order 的四种等级。

C++11 的 `std::atomic<T>` 不是"重新发明原子操作"——C++ 和 C11 委员会协调设计了**完全相同**的内存模型（第 29 页标准，逐字对齐）。C++ 只是把它包装成了模板类、成员函数、操作符重载的形式。

本章不是从头学内存模型——是把你的 C11 知识"翻译"成 C++11。读完只需要记住三个差异：(1) `atomic_int` → `std::atomic<int>`；(2) `atomic_fetch_add` → `fetch_add`；(3) `memory_order_relaxed` → `std::memory_order_relaxed`。

## 2. `std::atomic<T>`——模板化的原子操作

### 2.1 从 C11 到 C++11 — 一行代码的迁移

```cpp
// C11 写法（你已经会的）：
#include <stdatomic.h>
atomic_int counter = 0;
atomic_fetch_add(&counter, 1);
atomic_store(&counter, 0);
int v = atomic_load(&counter);

// C++11 写法——完全等价的语义，只是换成了模板 + 成员函数：
#include <atomic>
std::atomic<int> counter{0};
counter.fetch_add(1);
counter.store(0);
int v = counter.load();
```

**为什么 C++ 用模板而不是 `typedef`**：因为 C++ 的模板可以接受任何满足要求的类型——`atomic<int>`、`atomic<long>`、`atomic<Foo*>`——一份模板代码覆盖所有。C11 必须为每个类型单独定义 `atomic_int`/`atomic_long`/`atomic_llong`……

### 2.2 成员函数 vs 操作符

C++ 的 `std::atomic<T>` 支持操作符重载——让原子变量看起来像普通变量：

```cpp
std::atomic<int> counter{0};

// 操作符——等价于 fetch_add(1, std::memory_order_seq_cst)
counter++;       // 默认 seq_cst
counter--;       // 默认 seq_cst
counter += 5;    // 默认 seq_cst

// 显式指定内存序——成员函数版本
counter.fetch_add(1, std::memory_order_relaxed);
counter.fetch_sub(1, std::memory_order_release);
counter.store(42, std::memory_order_relaxed);

// CAS——compare_exchange_strong / compare_exchange_weak
int expected = 0;
if (counter.compare_exchange_strong(expected, 42)) {
    // 交换成功——counter 从 0 变成 42
} else {
    // 交换失败——expected 被更新为 counter 的当前值
}
```

**`compare_exchange_strong` vs `weak`**：`strong` 只有值不匹配时才失败。`weak` 可能"虚假失败"（spurious failure）——即使值匹配也可能返回 false。`weak` 在某些平台（ARM LDREX/STREX）上效率更高→用在循环里：`while (!counter.compare_exchange_weak(expected, new_val));`。`strong` 适合单次 CAS 判断。

### 2.3 哪些类型可以用 `std::atomic<T>` 

```cpp
#include <atomic>

// ✓ 整数类型——有完整的算术操作
std::atomic<int>         ai{0};  // fetch_add, fetch_sub, fetch_and, fetch_or, fetch_xor
std::atomic<long>        al{0};
std::atomic<size_t>      az{0};

// ✓ 指针类型——有 fetch_add（等同于 p += n）
int arr[10];
std::atomic<int*>        ap{arr};
ap.fetch_add(1);  // 指向 arr[1]

// ✓ trivially-copyable 类型——但只有 load/store/exchange/CAS，无算术操作
struct Point { int x, y; };
std::atomic<Point>       apt{};  // 需要 sizeof(Point) ≤ 16 + 编译器支持

// ✗ 非 trivially-copyable 类型——编译器报错或退化为锁实现
// std::atomic<std::string> as;  // string 有 non-trivial 构造函数/析构
```

**`is_lock_free()`** ——运行时检查当前类型在这个平台上是否真的是无锁实现：

```cpp
std::atomic<Point> apt;
if (apt.is_lock_free()) {
    // x86_64：16 字节以内用 CMPXCHG16B——无锁
    // 超过 16 字节——用内部互斥锁实现（仍是原子操作，只是用了锁）
}
```

### 2.4 特殊成员函数——不能拷贝

```cpp
std::atomic<int> a{0};
// std::atomic<int> b = a;     // ✗ 编译错误——拷贝构造被删除
// std::atomic<int> b(a);      // ✗ 同上
// a = 5;                       // ✓ 赋值——不是拷贝赋值，是 store(5, seq_cst)
// int v = a;                   // ✓ 隐式转换——load(seq_cst)
```

**为什么**：拷贝和赋值的语义不明确——是拷贝原子变量的当前值（应该用 `load`）还是拷贝原子对象本身（被禁止）？标准直接删掉了拷贝构造和拷贝赋值——强制用 `load`/`store` 明确表达意图。

## 3. C++ 内存序——与 C11 的一一对照

### 3.1 对照表

| C++11 内存序 | C11 等价 | 语义 | x86 典型开销 |
|---|---|---|---|
| `std::memory_order_relaxed` | `memory_order_relaxed` | 只保证原子性，无顺序约束 | 原子指令 |
| `std::memory_order_acquire` | `memory_order_acquire` | 后续读写不重排到此操作之前 | `mov`（x86 免费） |
| `std::memory_order_release` | `memory_order_release` | 前面读写不重排到此操作之后 | `mov`（x86 免费） |
| `std::memory_order_acq_rel` | `memory_order_acq_rel` | RMW 操作——同时 acquire + release | `lock` 前缀 |
| `std::memory_order_seq_cst` | `memory_order_seq_cst` | 全局单一全序（**C/C++ 默认**） | `xchg` 或 `mfence` |
| `std::memory_order_consume` | `memory_order_consume` | 依赖序（大多数编译器降级为 acquire） | 同 acquire |

**和 C11 完全一样**——C 和 C++ 委员会在第 29 页标准上逐字对齐了内存模型。唯一区别——C++ 用 `std::memory_order` 枚举，C 用 `memory_order` 枚举。名字不同，值相同。

### 3.2 默认是 `seq_cst` ——最安全也最慢

```cpp
std::atomic<int> a{0};
a.store(5);   // 等价于 a.store(5, std::memory_order_seq_cst)
int v = a;    // 等价于 a.load(std::memory_order_seq_cst)

// seq_cst 的代价——x86 需要 xchg 或 mfence（~33 cycles）
// relaxed 的代价——x86 仅需 mov（~1 cycle）
// 差距——对于热路径上的原子变量，选对内存序能提升 30x 性能
```

**什么时候降级**：

| 场景 | 选什么 | 原因 |
|---|---|---|
| 仅计数，不用于同步 | `relaxed` | `shared_ptr` 引用计数增减——你只关心归零时刻 |
| 发布数据给另一个线程 | `release` + `acquire` | writer 用 release store → reader 用 acquire load |
| 不确定就别降 | `seq_cst` | 正确性优先——错了调试极其困难 |

## 4. C++ 内存模型的关键差异

虽然基本语义和 C11 一样，C++ 有几个独特的点值得注意。

### 4.1 `std::atomic` 和普通变量可以混用——但不要这样做

C11 的 `_Atomic int` 和普通 `int` 是不同类型——编译时就能区分。C++ 的 `std::atomic<int>` 和 `int` 也是不同类型——但**同一块内存可以同时被 `int*` 和 `atomic<int>*` 访问**，编译器不阻止：

```cpp
#include <iostream>
#include <thread>
#include <atomic>

int shared = 0;                    // 普通变量
std::atomic<bool> ready{false};   // 原子变量

void writer() {
    shared = 42;                   // 普通写——不是原子的
    ready.store(true);             // 原子写
}

void reader() {
    while (!ready.load());         // 原子读——等到 ready=true
    std::cout << shared << '\n';   // 🔴 数据竞争！shared 可能还是 0！
    // shared=42 和 ready.store(true) 之间没有 happens-before
}
```

**问题**：`shared = 42` 不是原子的。即使 writer 已经执行了 `ready.store(true)` —— reader 看到 `ready=true` 不代表看到 `shared=42`。在不同的硬件线程上，这两个写操作可能以不同顺序到达内存。

**修复——加 release/acquire**：

```cpp
void writer() {
    shared = 42;
    ready.store(true, std::memory_order_release);  // 释放——之前的所有写入对之后的 acquire 可见
}

void reader() {
    while (!ready.load(std::memory_order_acquire));  // 获取——能看到 release 前的所有写入
    std::cout << shared << '\n';  // ✓ 保证看到 42
}
```

这就是内存序的实战用法——relaxed 不够，需要 release+acquire 建立 happens-before 关系。

### 4.2 `std::atomic_flag`——最轻量的原子布尔值

```cpp
#include <atomic>

std::atomic_flag lock = ATOMIC_FLAG_INIT;  // C++11 初始化方式

// 自旋获取锁
while (lock.test_and_set(std::memory_order_acquire))
    ;  // 自旋等待

// 临界区
// ...

// 释放锁
lock.clear(std::memory_order_release);
```

- **保证在所有平台上都是 lock-free**——等同于 C11 的 `atomic_flag`。
- **只有 `test_and_set` 和 `clear` 两个操作**——不提供 `load`/`store`。
- C 里有完全等价的 `atomic_flag`——成员函数语法是唯一的区别。

### 4.3 `shared_ptr` 引用计数用的内存序——降级带来真实收益

`std::shared_ptr` 的控制块里有两个计数器——强引用计数和弱引用计数。它们的增减**不需要 seq_cst**：

```cpp
// shared_ptr 内部实现（简化）
template <typename T>
class shared_ptr {
    control_block* ctrl;
public:
    shared_ptr(const shared_ptr& rhs) : ctrl(rhs.ctrl) {
        ctrl->strong_count.fetch_add(1, std::memory_order_relaxed);  // 只计数，不需要顺序
    }

    ~shared_ptr() {
        if (ctrl->strong_count.fetch_sub(1, std::memory_order_acq_rel) == 1) {
            // 最后一个——acq_rel 已提供 acquire 语义，能看到其他线程对对象的所有修改
            delete ctrl->ptr;
            // 弱引用计数为 0 时释放控制块
            if (ctrl->weak_count.fetch_sub(1, std::memory_order_relaxed) == 1)
                delete ctrl;
        }
    }
};
```

**为什么增减用 relaxed**：你只关心"引用计数什么时候归零"，不关心"和谁的 store 有什么 happens-before 关系"。每次拷贝/析构 `shared_ptr` 时，relaxed 比 seq_cst 省一个 mfence（x86 上 ~33 cycles）。对于一个频繁拷贝 `shared_ptr` 的程序——这可能是显著的性能收益。

**为什么归零时必须用 acq_rel**：`fetch_sub` 返回减 1 之前的值。如果减之前是 1——说明这是最后一个 `shared_ptr`。此时需要 acquire 语义——保证看到其他线程对对象的所有修改。释放对象之前，所有写入必须可见。

**弱引用计数**：增减用 relaxed——不需要顺序。`weak_ptr::lock()` 尝试提升为 `shared_ptr` 时需要 CAS + acquire——如果提升成功，需要看对象的状态。

### 4.4 C++ `volatile` vs `std::atomic`——最常见的误解

C++ 的 `volatile` ≠ 多线程同步。这和 Java 完全不同：

```cpp
volatile int v = 0;           // C++ volatile——告诉编译器"每次读都从内存读，不要优化掉"
std::atomic<int> a{0};        // C++ atomic——真正的多线程原子操作

void thread1() {
    v = 42;                    // 🔴 没有原子性——其他线程可能读到"半个" v
    a = 42;                    // ✓ 原子写——其他线程看到完整的 42
}
```

| | `volatile` | `std::atomic` |
|---|---|---|
| 原子性 | 无 | 有——RMW 操作不可分割 |
| 可见性 | 无——没有 happens-before | 有——配合 memory order 建立同步 |
| 编译优化 | 阻止对该变量的优化 | 阻止重排 + 配合 memory order |
| 用途 | MMIO / 信号处理 / setjmp | 多线程同步 |
| Java 等价 | N/A（Java volatile 有 happens-before） | `AtomicInteger` 等 |

**C++ `volatile` 的三个合法场景**（和 C 完全一样）：(1) 内存映射 I/O（硬件寄存器地址）；(2) 信号处理器中修改的全局变量 `volatile sig_atomic_t`；(3) `setjmp`/`longjmp` 之间的局部变量。多线程同步——不在这三个场景内——必须用 `std::atomic`。

## 5. 从 C11 无锁数据结构到 C++ 的迁移

C 阶段你写过 MPSC 队列和 Treiber 栈。C++ 版本怎么写——只需把 `_Atomic` 换成 `std::atomic<T>`：

```cpp
// C 版本（你已经会的）：
struct mpsc_node { void* data; _Atomic(struct mpsc_node*) next; };
struct mpsc_queue {
    _Atomic(struct mpsc_node*) head;
    struct mpsc_node* tail;  // 消费者独占——不需要原子
};

// C++ 版本——模板化 + 类型安全：
#include <atomic>

template <typename T>
class MpscQueue {
    struct Node {
        T data;
        std::atomic<Node*> next;  // _Atomic(Node*) → std::atomic<Node*>
    };
    std::atomic<Node*> head;
    Node* tail;                    // 消费者独占——同一个原则

public:
    void enqueue(T value) {
        Node* node = new Node{value, nullptr};
        Node* prev = head.exchange(node, std::memory_order_acq_rel);
        if (prev) {                                        // 初次 enqueue 时 prev 为 nullptr——不用写 next
            prev->next.store(node, std::memory_order_release);
        } else {
            tail = node;                                   // 空队列——tail 直接指向第一个节点
        }
    }

    T dequeue() {
        Node* result = tail;
        // ... 和 C 版本相同的 CAS 循环
        return result->data;
    }
};
```

**核心原则没变**——内存序的选择、happens-before 关系、哪个操作是哪个线程独占的——全和 C 版本一样。C++ 只是给了类型安全和模板化。

## 6. 可运行错误实验

### 实验：atomic 和普通变量混用的数据竞争

```cpp
#include <iostream>
#include <thread>
#include <atomic>

int shared = 0;                     // 普通变量——没有原子保护
std::atomic<bool> ready{false};    // 原子变量——但用了默认 seq_cst

void writer() {
    shared = 42;                    // 🔴 普通写入——没有原子性
    ready.store(true);              // 原子存储——默认 seq_cst
}

void reader() {
    while (!ready.load());          // 原子加载——等到 ready=true
    std::cout << shared << '\n';    // 🔴 数据竞争！可能输出 0 而不是 42
}

int main() {
    for (int i = 0; i < 10; i++) {
        shared = 0;
        ready = false;
        std::thread t1(writer), t2(reader);
        t1.join(); t2.join();
        std::cout << "---\n";
    }
    return 0;
}
```

**编译运行**：`g++ -std=c++11 -pthread race.cpp -o race && ./race`

即使 `ready` 是 `atomic<bool>` 且用了默认 `seq_cst` —— `shared = 42` 仍然是普通写，没有 happens-before 关系。x86 上大概率看到 42（强内存模型），但 ARM 上会反复看到 0。

**修复**：writer 用 `std::memory_order_release`，reader 用 `std::memory_order_acquire`——建立 happens-before。

```cpp
ready.store(true, std::memory_order_release);    // writer
ready.load(std::memory_order_acquire);            // reader
```

重新编译运行——ARM 上也稳定输出 42。

## 7. 面试题

### 面试题 1：C11 vs C++11 原子操作

**面试官**：C11 的 `atomic_fetch_add(&counter, 1, memory_order_relaxed)` 在 C++11 里怎么写？有什么不同？

**回答**：C++11——`counter.fetch_add(1, std::memory_order_relaxed);`。核心区别：(1) C++ 是模板类——`std::atomic<T>` 一份代码覆盖所有类型，C11 必须 `atomic_int`/`atomic_long` 逐个定义；(2) C++ 支持操作符重载——`counter++` 等价于 `fetch_add(1, seq_cst)`；(3) C++ 内存序枚举在 `std::memory_order` 命名层——加了个 `std::` 前缀；(4) C++ 的 `operator=` 是 `store(seq_cst)`，不是拷贝构造——拷贝构造被删除了。

**追问（面试官）**：`std::atomic<double>` 能用吗？`std::atomic<std::string>` 呢？

**追问回答**：`atomic<double>` —— `load`/`store`/`exchange`/`CAS` 可用，但 `fetch_add` 等算术操作不提供（C++20 才有 `atomic<float>` 的扩展）。`atomic<string>` ——不能用（`string` 不是 trivially-copyable），编译器报错或有退化的锁实现（`is_lock_free()` 返回 false）。要原子操作 string→用 `mutex` 保护，或存 `atomic<string*>`（原子操作指针）。

### 面试题 2：`shared_ptr` 为什么用 relaxed？

**面试官**：`shared_ptr` 的引用计数操作为什么用 `memory_order_relaxed` 而不是默认的 `seq_cst`？

**回答**：强引用计数的增减不需要顺序保证——你只关心"离归零还有多远"，不关心"和谁的 store 有什么 happens-before 关系"。当计数从 1 降到 0 时——最后一个 `shared_ptr` 析构时需要 acquire 语义保证看到对象的所有修改。relaxed 比 seq_cst 省一个 mfence（x86 ~33 cycles），高频 `shared_ptr` 拷贝场景下收益明显。

**追问（面试官）**：那弱引用计数（`weak_ptr`）呢？也是 relaxed 吗？

**追问回答**：弱引用计数的增减是 relaxed——不需要顺序保证。但 `wp.lock()`（尝试提升为 `shared_ptr`）需要 `compare_exchange_strong` + `memory_order_acquire`——如果提升成功，需要 acquire 语义看到对象状态。如果提升失败（对象已释放）→不需要任何顺序保证。

### 面试题 3：C++ `volatile` vs `std::atomic`

**面试官**：C++ 的 `volatile` 和 `std::atomic` 的区别？为什么不能用 `volatile` 做线程同步？

**回答**：C++ `volatile` 和 C 完全一样——告诉编译器"不要优化掉这个变量的读写"——**没有**原子性、**没有** happens-before、**没有** 多线程同步语义。`std::atomic` 提供真正的多线程同步——原子 RMW、memory order 控制 happens-before。Java 的 `volatile` 有 happens-before——但 C++ 没有。这是最容易跨语言混淆的点——面试官特别喜欢用这个考察候选人是否深入理解内存模型。

**追问（面试官）**：那 C++ 的 `volatile` 到底用在哪？

**追问回答**：和 C 一样的三个场景——(1) MMIO：硬件寄存器地址，每次读取可能改变硬件状态→编译器不能优化掉重复读；(2) 信号处理器中修改的全局变量 `volatile sig_atomic_t`——`sig_atomic_t` 保证在信号和主程序之间原子可读；(3) `setjmp`/`longjmp` 之间的局部变量——防止 longjmp 后变量被恢复到旧值。多线程同步——不在这三个场景内——必须用 `std::atomic` 或 `std::mutex`。

## 8. Stage3 回顾 + 全书预告

### 8.1 本章小结

| 概念 | 核心理解 |
|---|---|
| `std::atomic<T>` | C11 `atomic_T` 的 C++ 模板封装——成员函数 + 操作符重载 |
| 内存序 | 和 C11 完全相同——`std::memory_order_` 前缀是唯一区别 |
| `is_lock_free()` | 运行时检查——大 struct 可能用内部锁 |
| relaxed 计数 | `shared_ptr` 引用计数增减不需要顺序——省 mfence |
| release+acquire | atomic 通知普通变量——建立 happens-before |
| `volatile` ≠ 原子 | 只阻止优化，不做多线程同步 |

### 8.2 Stage3 四章回顾

```
Ch01 继承与多态    → 编译时多态（模板）到运行时多态（虚函数/vtable）
Ch02 多重继承      → MI 的内存代价——vptr 飘移、vbptr 间接、菱形数据重复
Ch03 异常安全      → 异常让 RAII 成为必需品——构造/析构的边界条件
Ch04 C++ 内存模型  → C11 原子知识向 C++ 的迁移——同一套标准、不同语法
```

**Stage3 核心主线**：C++ 的运行时机制——虚函数表、多继承对象布局、异常栈展开、内存模型。这些不是日常代码里能看到的——但每个资深 C++ 程序员都必须理解。理解了这些，你就不是在"用 C++"，你是在"理解编译器为你的代码做了什么"。
