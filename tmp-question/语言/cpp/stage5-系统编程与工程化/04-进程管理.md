## 1. 引言：C 的进程管理最容易犯的两个错

C 里 `fork` + `exec` 的模式很强大——但不能更繁琐了：

```cpp
// C 的模式——fork 后两个进程各自处理、父进程必须 waitpid
pid_t pid = fork();
if (pid < 0) { perror("fork"); return -1; }

if (pid == 0) {
    // 子进程
    execlp("ls", "ls", "-l", NULL);
    perror("exec");  // exec 失败才到这里
    _exit(1);        // 必须 _exit——不能用 exit！
} else {
    // 父进程
    int status;
    waitpid(pid, &status, 0);  // 忘了这行→子进程变僵尸
}
```

两个最容易忘的陷阱：(1) 父进程忘了 `waitpid` → 子进程变僵尸；(2) 子进程 `exec` 失败后用 `exit` 而不是 `_exit` → 父进程的 `atexit` 回调被错误触发。C++ 可以把这个过程包装成 RAII——`fork` 后自动管理子进程生命周期。

## 2. `Subprocess`——RAII 管理的子进程

### 2.1 最简封装——构造 fork、析构 wait

```cpp
#include <unistd.h>
#include <sys/wait.h>
#include <stdexcept>
#include <string>

class Subprocess {
    pid_t pid_ = -1;

public:
    // 构造——fork
    Subprocess() {
        pid_ = fork();
        if (pid_ < 0) throw std::runtime_error("fork failed");
    }

    // 析构——如果父进程，自动 wait
    ~Subprocess() {
        if (pid_ > 0) {           // 父进程
            int status;
            waitpid(pid_, &status, 0);
        }
    }

    // 我是子进程？
    bool is_child() const { return pid_ == 0; }

    // 执行新程序——只在子进程调用
    void exec(const char* path, char* const argv[]) {
        if (pid_ != 0) throw std::logic_error("exec() only valid in child");
        execvp(path, argv);
        throw std::runtime_error(std::string("exec failed: ") + path);
        // 如果到了这里——exec 失败
    }

    Subprocess(const Subprocess&) = delete;
    Subprocess& operator=(const Subprocess&) = delete;
};
```

### 2.2 使用——三行替代 C 的十五行

```cpp
#include <iostream>

int main() {
    Subprocess proc;

    if (proc.is_child()) {
        // 子进程——执行 ls
        char* const args[] = { (char*)"ls", (char*)"-l", NULL };
        proc.exec("ls", args);
        // 不会到这里——exec 替换了进程镜像
    } else {
        // 父进程——继续自己的事
        std::cout << "Parent: waiting for child...\n";
    }
    // proc 析构自动 waitpid——零手动清理
    return 0;
}
```

**关键设计**：`Subprocess` 的析构函数只在父进程（`pid_ > 0`）做 `waitpid`。子进程（`pid_ == 0`）析构什么都不做——因为子进程的镜像已经被 `exec` 替换了（或者失败后 `_exit` 了）。

## 3. 管道通信——RAII 管理 pipe 文件描述符

### 3.1 父→子单向通信

```cpp
#include <unistd.h>
#include <stdexcept>

class Pipe {
    int fds_[2] = {-1, -1};  // fds_[0]=读端, fds_[1]=写端

public:
    Pipe() {
        if (pipe(fds_) < 0) throw std::runtime_error("pipe failed");
    }

    ~Pipe() {
        if (fds_[0] >= 0) close(fds_[0]);
        if (fds_[1] >= 0) close(fds_[1]);
    }

    int read_fd()  const { return fds_[0]; }
    int write_fd() const { return fds_[1]; }

    // 关闭某一端——通常是 fork 后
    void close_read()  { if (fds_[0] >= 0) { close(fds_[0]); fds_[0] = -1; } }
    void close_write() { if (fds_[1] >= 0) { close(fds_[1]); fds_[1] = -1; } }

    Pipe(const Pipe&) = delete;
    Pipe& operator=(const Pipe&) = delete;
};
```

### 3.2 fork + pipe——父进程向子进程发数据

```cpp
#include <iostream>
#include <string>
#include <vector>

int main() {
    Pipe p;
    Subprocess proc;

    if (proc.is_child()) {
        // 子进程——不需要写端
        p.close_write();

        // 从读端读取父进程发来的数据
        int result;
        ssize_t n = read(p.read_fd(), &result, sizeof(result));
        if (n == sizeof(result)) {
            std::cout << "Child received: " << result << '\n';
        }
    } else {
        // 父进程——不需要读端
        p.close_read();

        // 计算数据...
        int data = 42 * 2;
        write(p.write_fd(), &data, sizeof(data));
        // 父进程析构——pipe 写端 close→子进程 read 返回 EOF
    }
    return 0;
}
```

**核心原则**：fork 后，父和子各有一份 pipe fd 的副本。父不需要读→ `close_read()`；子不需要写→ `close_write()`。不关掉多余端口的后果——子进程的 `read` 永远不会返回 EOF（因为怎么都有一个进程持有写端——可能是自己忘了关的）。

## 4. 重定向——把子进程的输出导入 pipe

### 4.1 标准输出重定向

更实用的场景——父进程启动子进程（如 `grep`），读取子进程的输出：

```cpp
#include <unistd.h>
#include <sys/wait.h>
#include <iostream>
#include <vector>
#include <cstdio>

std::string run_and_capture(const std::vector<std::string>& cmd) {
    Pipe p;
    pid_t pid = fork();

    if (pid == 0) {
        // 子进程——重定向 stdout 到 pipe 写端
        p.close_read();                       // 子进程不需要读 pipe
        dup2(p.write_fd(), STDOUT_FILENO);    // 把 stdout 重定向到 pipe 写端
        p.close_write();                      // dup2 后原来的 fd 不需要了

        // 构造 argv
        std::vector<char*> args;
        for (auto& s : cmd) args.push_back(const_cast<char*>(s.c_str()));
        args.push_back(nullptr);

        execvp(args[0], args.data());
        perror("exec"); _exit(1);             // exec 失败
    }

    // 父进程——读取子进程输出
    p.close_write();                          // 父进程不需要写 pipe
    std::string result;
    char buf[256];
    ssize_t n;
    while ((n = read(p.read_fd(), buf, sizeof(buf))) > 0) {
        result.append(buf, n);
    }

    int status;
    waitpid(pid, &status, 0);
    return result;
}

int main() {
    auto output = run_and_capture({"ls", "-l"});
    std::cout << "captured:\n" << output;
    return 0;
}
```

**`dup2(write_fd, STDOUT_FILENO)` 做了什么**：把文件描述符 `1`（stdout）重定向到 pipe 的写端。之后子进程里所有的 `printf`/`std::cout` 输出都流入 pipe——父进程从 pipe 读端取。

## 5. `fork` + `exec` 的 RAII 总结——一个完整的子进程执行器

### 5.1 封装——构造时 fork + 析构时自动 wait

```cpp
class ForkExec {
    pid_t pid_ = -1;
    Pipe  stdout_pipe_;
    std::string output_;

public:
    ForkExec(const std::vector<std::string>& cmd) {
        pid_ = fork();
        if (pid_ < 0) throw std::runtime_error("fork failed");

        if (pid_ == 0) {
            // 子进程——重定向 stdout 后 exec
            stdout_pipe_.close_read();
            dup2(stdout_pipe_.write_fd(), STDOUT_FILENO);
            stdout_pipe_.close_write();

            std::vector<char*> args;
            for (auto& s : cmd) args.push_back(const_cast<char*>(s.c_str()));
            args.push_back(nullptr);
            execvp(args[0], args.data());
            perror("exec"); _exit(1);
        } else {
            // 父进程——关闭写端，等待读
            stdout_pipe_.close_write();
        }
    }

    // 获取子进程的 stdout 输出
    const std::string& output() {
        if (pid_ > 0 && output_.empty()) {
            char buf[256]; ssize_t n;
            while ((n = read(stdout_pipe_.read_fd(), buf, sizeof(buf))) > 0) {
                output_.append(buf, n);
            }
        }
        return output_;
    }

    // 等待子进程结束
    int wait() {
        if (pid_ > 0) {
            int status;
            waitpid(pid_, &status, 0);
            pid_ = -1;
            return WEXITSTATUS(status);
        }
        return -1;
    }

    ~ForkExec() {
        if (pid_ > 0) wait();  // 自动 wait——不僵尸
    }
};
```

### 5.2 使用——一行启动、一行获取结果

```cpp
int main() {
    ForkExec ls({"ls", "-l", "/tmp"});
    std::cout << ls.output();  // 自动读取子进程 stdout
    // ForkExec 析构——自动 wait
    return 0;
}
```

## 6. 可运行实验

### 实验：fork 后忘 waitpid → 僵尸进程

```cpp
#include <unistd.h>
#include <sys/wait.h>
#include <iostream>
#include <cstdlib>

int main() {
    pid_t pid = fork();
    if (pid == 0) {
        std::cout << "Child exiting...\n";
        _exit(0);                     // 子进程立即退出
    }

    // 父进程故意不 wait——睡眠 10 秒
    std::cout << "Parent: child pid=" << pid << " (check 'ps aux | grep Z')\n";
    sleep(10);                        // 这 10 秒内子进程是僵尸！
    // 忘了 waitpid！

    // 修复——加上这行
    int status;
    waitpid(pid, &status, 0);         // 收了尸体——不再是僵尸
    std::cout << "Parent exiting\n";
    return 0;
}
```

**编译运行**：`g++ -std=c++11 zombie.cpp -o zombie && ./zombie`。另开终端 `ps aux | grep Z`——前 10 秒看到一个 `<defunct>` 进程。

## 7. 面试题

### 面试题 1：fork 后子进程 exec 失败怎么办

**面试官**：子进程里 `exec` 失败了——应该用 `exit` 还是 `_exit`？为什么？

**回答**：必须用 `_exit` 而不是 `exit`。`exit` 会调用 `atexit` 注册的回调函数——这些回调是父进程注册的（如清理临时文件）。子进程如果 `exit`——父进程的临时文件被清理了、父进程的缓冲区被 flush 了——但父进程还在运行——结果不可预测。`_exit` 直接终止进程，不调任何 `atexit` 回调。

**追问（面试官）**：fork 后父进程忘了 `waitpid` 会怎样？

**追问回答**：子进程退出后变成僵尸（zombie）——内核保留它的 PID 和退出状态在进程表中，直到父进程调 `waitpid` 收了尸体。如果父进程是一个长期运行的服务（如 Web 服务器），僵尸进程积累→PID 耗尽→无法创建新进程。RAII 的 `Subprocess` 在析构时自动 `waitpid`——消除这个隐患。

### 面试题 2：pipe 通信

**面试官**：fork 后 pipe 的每一端在父进程和子进程中都存在一份副本——为什么要关掉不用的端？

**回答**：pipe 的 `read` 在**所有持有写端 fd 的进程都关闭后**才返回 EOF。如果子进程需要读父进程的数据——子进程关掉自己的写端副本（否则即使父进程关了写端、子进程的写端仍然开着→read 永远不会返回 EOF→死等）。同理——父进程如果不关掉自己的读端——永远不知道子进程什么时候读完了数据。

**追问（面试官）**：`dup2(write_fd, STDOUT_FILENO)` 做了什么？

**追问回答**：把文件描述符 `STDOUT_FILENO`（=1）变成 `write_fd` 的副本——之后所有写到 stdout 的内容都流向 pipe。`dup2` 之前需要先关掉 pipe 的不需要端（`close_read()`），`dup2` 之后原来的 `write_fd` 也不需要了（`close_write()` 关掉多余的 fd）。

### 面试题 3：RAII 子进程管理

**面试官**：设计一个 RAII 封装 `fork`+`exec` 的类——哪些是必须的？

**回答**：(1) 构造时 `fork`——如果失败抛异常；如果成功，记录 pid。(2) 析构时——如果 `pid_ > 0`（父进程），自动 `waitpid`——绝不让子进程变僵尸。(3) 禁止拷贝——两个对象管理同一个子进程没有意义。(4) `exec()` 方法——只在 `is_child()` 为 true 时调用，失败用 `_exit` 不是 `exit`。(5) 管道通信——pipe fd 用 RAII 包装，fork 后及时关掉不需要的端。

## 8. 本章小结

| 概念 | C 的做法 | C++ 的做法 | 核心收益 |
|---|---|---|---|
| `fork` | 手动 `fork` + 手动 `waitpid` | `Subprocess` RAII | 析构自动 wait——零僵尸 |
| `exec` 失败 | `exit` 误调 atexit 回调 | `_exit`——直接用 | 不破坏父进程状态 |
| pipe 通信 | 手动 `pipe` + `close` 各端 | `Pipe` RAII + fork 后关多余端 | 保证 read 正常返回 EOF |
| stdout 重定向 | `dup2` + 手动 close | 封装在 `ForkExec` 里 | 一行启动、一行获取输出 |
| 僵尸进程 | 忘了 waitpid→累积→PID 耗尽 | RAII 析构自动收尸 | 彻底杜绝僵尸 |
