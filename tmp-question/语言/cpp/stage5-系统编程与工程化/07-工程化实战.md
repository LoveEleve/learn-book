## 1. 引言：写好代码 ≠ 写好项目

前 22 章教你怎么写**正确且快的** C++ 代码。本章的视角不同——怎么把这些代码组织成一个可维护、可测试、可持续构建的**工程**：

```cpp
// 你的代码再正确，如果：
// - 每次改代码都要手动敲 g++ 命令
// - 没有测试——改了代码不知道有没有破
// - 没有静态分析——错误要到运行时才暴露
// - 没有 CI——新同事 clone 下来跑不起来
// 那这个"正确的代码"在生产环境中活不下去
```

## 2. Modern CMake——目标体系替代变量堆砌

### 2.1 问题——传统 CMake 的坑

传统 CMake 用**全局变量**控制编译——改一个地方可能影响整个项目：

```cmake
# 传统 CMake——不推荐
add_definitions(-Wall -O2)           # 影响所有目标——包括不该影响的
include_directories(./include)        # 全局包含路径——耦合混乱
add_executable(myapp main.cpp utils.cpp)  # 源文件逐个列出
```

改 `include_directories` 会影响所有目标——把内部路径暴露给了不相关的外部目标。Modern CMake 用 **target** 体系——每个库/可执行文件是一个独立的目标，有自己的编译选项和包含路径。

### 2.2 Modern CMake——target 体系

```cmake
cmake_minimum_required(VERSION 3.16)
project(MyApp VERSION 1.0 LANGUAGES CXX)

# 设定 C++11 标准——跨平台统一
set(CMAKE_CXX_STANDARD 11)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# 静态库——有自己的源文件和包含路径
add_library(utils STATIC
    src/utils.cpp
    src/parser.cpp
)
target_include_directories(utils PUBLIC include)  # PUBLIC——使用 utils 的目标也能访问

# 可执行文件——依赖 utils
add_executable(myapp src/main.cpp)
target_link_libraries(myapp PRIVATE utils)  # PRIVATE——只有 myapp 能用

# 安装规则
install(TARGETS myapp DESTINATION bin)
```

### 2.3 `PUBLIC`/`PRIVATE`/`INTERFACE`——依赖传播

| 关键字 | 含义 | 场景 |
|---|---|---|
| `PUBLIC` | 目标的依赖和头文件都暴露给使用者 | 公共库——头文件和符号都对外 |
| `PRIVATE` | 目标的依赖不暴露 | 可执行文件——它的依赖是它自己的 |
| `INTERFACE` | 只有头文件，没有编译产物 | 纯头文件库 |

```cmake
# utils 是 PUBLIC——依赖 utils 的目标自动获得 utils 的 include 路径
target_include_directories(utils PUBLIC include)

# 如果改成 PRIVATE——myapp 编译时找不到 utils/include 下的头文件
```

### 2.4 平台差异的编译选项

```cmake
# 跨平台编译选项——用 generator expression
target_compile_options(utils PRIVATE
    $<$<CXX_COMPILER_ID:GNU>:-Wall -Wextra -Werror>
    $<$<CXX_COMPILER_ID:MSVC>:/W4 /WX>
)

# Debug vs Release——用 CMAKE_BUILD_TYPE
# -DCMAKE_BUILD_TYPE=Debug  → 无优化 + 调试符号
# -DCMAKE_BUILD_TYPE=Release → -O3 + 无调试符号
# CMakeLists 里不强制设置——构建时指定
```

## 3. Google Test——单元测试

### 3.1 最简单的测试

```cpp
#include <gtest/gtest.h>

int add(int a, int b) { return a + b; }

TEST(MathTest, AddPositive) {      // 测试名 + 测试用例名
    EXPECT_EQ(add(2, 3), 5);       // 断言——相等
}

TEST(MathTest, AddNegative) {
    EXPECT_EQ(add(-1, -2), -3);
}

TEST(MathTest, AddZero) {
    EXPECT_EQ(add(0, 0), 0);
}
```

### 3.2 `EXPECT_EQ` vs `ASSERT_EQ`

```cpp
// EXPECT——失败后继续执行（可以一次看到多个失败）
TEST(CalcTest, MultipleChecks) {
    EXPECT_EQ(add(1, 1), 2);
    EXPECT_EQ(add(2, 2), 4);       // 即使第一个失败——第二个也执行
    EXPECT_EQ(add(3, 3), 6);
}

// ASSERT——失败后停止（后续检查无意义时用）
TEST(CalcTest, OrderDependent) {
    ASSERT_TRUE(init_database());   // 初始化失败——后面都没意义了
    EXPECT_EQ(get_value("key"), 42);
}
```

### 3.3 测试夹具——SetUp/TearDown

```cpp
class CalcTest : public ::testing::Test {
protected:
    void SetUp() override {    // 每个测试用例运行前
        db = new Database("test.db");
    }
    void TearDown() override { // 每个测试用例运行后
        delete db;
    }
    Database* db;
};

TEST_F(CalcTest, InsertAndQuery) {   // TEST_F——使用夹具
    db->insert("key", 42);
    EXPECT_EQ(db->query("key"), 42);
}

TEST_F(CalcTest, EmptyQuery) {
    EXPECT_THROW(db->query("missing"), std::out_of_range);
}
```

### 3.4 CMake 集成

```cmake
# 查找或拉取 GTest
find_package(GTest REQUIRED)

add_executable(tests
    tests/test_utils.cpp
    tests/test_parser.cpp
)
target_link_libraries(tests PRIVATE utils GTest::gtest GTest::gtest_main)

# 注册到 CTest——make test 跑所有测试
enable_testing()
add_test(NAME AllTests COMMAND tests)
```

## 4. clang-tidy——静态分析

### 4.1 检查什么

```bash
# 在项目根目录——用 compile_commands.json 知道每个文件怎么编译的
cmake -DCMAKE_EXPORT_COMPILE_COMMANDS=ON ..
clang-tidy src/main.cpp -checks='modernize-*,performance-*,readability-*'
```

**三类最有价值的检查**：

| 检查 | 做什么 | 例子 |
|---|---|---|
| `modernize-*` | 把老 C++ 写法换成现代写法 | `NULL` → `nullptr`、手写循环 → `for (auto& x : v)` |
| `performance-*` | 发现性能问题 | `std::string` 按值传参 → 改为 `const std::string&` |
| `readability-*` | 发现可读性问题 | `else` 前面 `return` 提示多余、函数过长 |

### 4.2 CI 集成

```yaml
# .github/workflows/ci.yml
- name: clang-tidy
  run: |
    cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
    find src -name '*.cpp' -exec clang-tidy {} -p build \;
```

## 5. GitHub Actions CI——持续构建

### 5.1 完整模板

```yaml
# .github/workflows/ci.yml
name: CI

on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
    - uses: actions/checkout@v4

    - name: Configure
      run: cmake -B build -DCMAKE_BUILD_TYPE=Release

    - name: Build
      run: cmake --build build

    - name: Test
      run: cd build && ctest --output-on-failure

    - name: Lint
      run: |
        cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
        find src -name '*.cpp' -exec clang-tidy {} -p build \;
```

### 5.2 为什么 Test 和 Lint 分开

- **Test**——验证逻辑正确——编译 + 跑测试
- **Lint**——验证代码质量——不编译、不跑测试，只看代码
- 分开的好处——测试通过但 lint 失败→提醒开发者修改；测试失败→必须修改才能合并

## 6. 面试题

### 面试题 1：Modern CMake vs 传统 CMake

**面试官**：Modern CMake 和传统 CMake 的核心区别？`PUBLIC`/`PRIVATE`/`INTERFACE` 有什么区别？

**回答**：传统 CMake 用全局变量（`include_directories`、`add_definitions`）——所有目标共享配置，改一个影响全部。Modern CMake 用 target 体系——每个库/可执行文件是独立的目标，有自己的编译选项和包含路径。`PUBLIC`——目标的包含路径和依赖都暴露给使用者（公共库）；`PRIVATE`——只给自己用（可执行文件的内部依赖）；`INTERFACE`——只有头文件，没有编译产物（纯头文件库）。

**追问（面试官）**：`add_definitions(-Wall)` 和 `target_compile_options` 的区别？

**追问回答**：`add_definitions` 影响**所有**在此之后定义的目标——包括你不想影响的。`target_compile_options` 只影响指定目标——`utils` 库的 `-Wall` 不影响 `myapp` 可执行文件。加 `-Werror` 时特别明显——全局加会让第三方库的警告也变成编译错误，目标级别可以只对你自己的代码严格。

### 面试题 2：Google Test 的 ASSERT vs EXPECT

**面试官**：`ASSERT_*` 和 `EXPECT_*` 的区别？什么时候用哪个？

**回答**：`ASSERT_*` ——失败后**停止**当前测试——后续检查无意义时使用（如初始化失败、指针为空后解引用）。`EXPECT_*` ——失败后**继续**当前测试——一次运行看到多个失败时使用（如多个独立断言）。`ASSERT_TRUE(init())` 之后 `EXPECT_EQ(get(), 42)`——初始化失败就停止，否则继续检查。

**追问（面试官）**：测试夹具（Fixture）的 SetUp/TearDown 为什么用 TEST_F 而不是 TEST？

**追问回答**：`TEST`——独立测试用例，每个用例独立运行，不共享状态。`TEST_F`——绑定到夹具类，每个用例运行前调用 `SetUp()`、运行后调用 `TearDown()`——保证每个测试有全新的环境。不用 TEST_F 的共享静态数据会导致测试间相互影响——第一个测试写入的数据影响第二个测试的读取。

### 面试题 3：CI 的价值

**面试官**：为什么需要 CI？本地编译通过不就行了吗？

**回答**：(1) 本地编译通过≠其他机器通过——本地用的 GCC 12，CI 用 GCC 11/Clang/MSVC——编译器差异可能暴露问题。(2) 本地有缓存/旧产物——CI 从干净环境构建，发现"为什么我在本地能编过但别人不能"的问题。(3) 强制测试——本地忘了跑测试→CI 必须跑——防呆。(4) 可重现的构建环境——`Dockerfile`/`ubuntu-latest` 是固定的——"在我机器上能跑"变成"在 CI 上能跑，所以能部署"。

## 7. 本章小结 + Stage5 全书回顾

### 7.1 本章小结

| 工具 | 做什么 | 替代什么 |
|---|---|---|
| Modern CMake | target 体系——每个目标独立配置 | 传统 `add_definitions` + `include_directories` |
| Google Test | 单元测试——`TEST`/`TEST_F`/`EXPECT`/`ASSERT` | 手写 `assert` 和 `printf` 调试 |
| clang-tidy | 静态分析——自动发现代码问题 | 人工 code review 找低级错误 |
| GitHub Actions CI | 持续构建——每次 push 自动编译+测试 | 手动"在本地编一下试试" |

### 7.2 Stage5 回顾 + 全书收尾

**Stage5 七章回顾**：

```
Ch01 C++11 并发         → thread/mutex/condvar/async——RAII 包装 C pthread
Ch02 RAII 文件 I/O       → fstream/iostream/stringstream——替代 C FILE*
Ch03 内存映射与共享内存   → mmap RAII/共享内存/Arena 内存池
Ch04 进程管理            → Subprocess/Pipe/ForkExec RAII——杜绝僵尸
Ch05 信号与 Socket       → Fd/Socket/SignalHandler RAII——一行关闭所有资源
Ch06 跨语言 FFI          → extern "C"/wrapper/ABI 可见性
Ch07 工程化实战          → CMake/GTest/clang-tidy/CI——从"能编过"到"可维护"
```

**全书 23 章完成**。

**核心主线**：C 的每一个手动管理资源的地方——文件/内存/进程/线程/锁/socket——C++ 都用 RAII 消灭了。你不再需要"记得关文件""记得 waitpid""记得 unlock"——编译器帮你记住。这就是 C++ 工程化的价值——把资源管理从"程序员的责任"变成"语言的责任"。
