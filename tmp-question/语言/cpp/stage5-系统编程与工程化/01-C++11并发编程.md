## 1. 引言：从 C 的 pthread 到 C++ 的 RAII

C 阶段你已经精通 pthread——能用 `pthread_create`/`pthread_mutex_lock`/`pthread_cond_wait` 写线程池。C++11 不是"重新讲一遍并发"——是**把 C 的并发原语用 RAII 重新包装**：

| C 里最容易犯的错 | C++11 怎么消灭它 |
|---|---|
| `pthread_mutex_lock` 后忘记 `unlock`（异常路径） | `lock_guard` ——离开作用域自动 unlock |
| `pthread_create` 后忘记 `join`/`detach`→zombie | `thread` 析构时调用 `terminate`——强迫你了结 |
| 用 `void*` 传参数和返回值 | 类型安全的模板——`thread(worker, 42)` + `future<int>` |

C 的并发思维没变——mutex/condvar/futex 的底层机制一模一样。C++11 只是给了更安全、更简洁的语法。

## 2. `std::thread`——RAII 管理的线程

### 2.1 创建和了结

```cpp
#include <thread>
#include <iostream>

void worker(int id) {
    std::cout << "Thread " << id << " running\n";
}

int main() {
    std::thread t1(worker, 1);   // 创建——参数直接传给 worker
    std::thread t2(worker, 2);

    t1.join();                    // 等待完成
    t2.join();
    // 如果忘了 join——t1 析构时调用 std::terminate()！
    return 0;
}
```

**`std::thread` 必须被"了结"**——要么 `join()`（等待完成），要么 `detach()`（分离不等待）。析构时如果既没 join 也没 detach→`std::terminate()` 直接终止进程。

**和 pthread 的对比**：`pthread_create` 不 join→子线程变僵尸（资源泄漏，悄无声息）。`std::thread` 不 join→进程直接死。C++ 的哲学是"未定义行为应该是显式崩溃，不是静默泄漏"。

### 2.2 传参——类型安全替代 `void*`

```cpp
// C：用 void* 传参——运行时强制转换
// pthread_create(&t, NULL, worker, (void*)&data);  // 类型不安全

// C++11：模板直接传任意类型参数
std::thread t([](int a, double b) {
    std::cout << a << ", " << b;
}, 42, 3.14);  // 编译时检查类型—传错立即编译错误
```

## 3. `std::mutex` + `std::lock_guard`——自动释放锁

### 3.1 最简单的互斥保护

```cpp
#include <mutex>

std::mutex mtx;
int counter = 0;

void increment() {
    std::lock_guard<std::mutex> lock(mtx);  // 构造——lock
    counter++;                                // 临界区
}  // lock 析构——自动 unlock——即使抛异常也释放！
```

**C 的对比**：

```cpp
// C：手动配对——容易忘 unlock（尤其是异常路径上）
pthread_mutex_lock(&mtx);
counter++;
if (error) return -1;  // 🔴 忘了 unlock——死锁！
pthread_mutex_unlock(&mtx);

// C++11：lock_guard——自动释放
{
    std::lock_guard<std::mutex> lock(mtx);
    counter++;
    if (error) return -1;  // ✓ lock_guard 析构自动 unlock
}
```

### 3.2 `lock_guard` vs `unique_lock`

| | `lock_guard` | `unique_lock` |
|---|---|---|
| 构造 lock / 析构 unlock | ✅ | ✅ |
| 可移动 | ❌ | ✅——可转移所有权 |
| 可延迟 lock | ❌ | ✅——`unique_lock lk(mtx, defer_lock)` |
| 可手动 unlock | ❌ | ✅ |
| 配合 condvar | ❌——wait 需要临时 unlock | ✅ |
| 开销 | 最小 | 略大——多一个 bool 标志 |

**原则**：默认用 `lock_guard`——只在需要 `unique_lock` 的功能时（condvar、延迟 lock、手动 unlock）才换。

### 3.3 `std::recursive_mutex`——同一线程允许多次 lock

```cpp
std::mutex mtx;           // 同一线程两次 lock→死锁
std::recursive_mutex rm;  // 同一线程允许多次 lock（内部计数器）

void recursive(int n) {
    std::lock_guard<std::recursive_mutex> lock(rm);
    if (n > 0) recursive(n - 1);  // ✓ 递归调用重新 lock 同一个 mutex——OK
}
```

## 4. `std::condition_variable`——和 C 一样逻辑

### 4.1 生产者-消费者

```cpp
#include <mutex>
#include <condition_variable>
#include <queue>

std::mutex mtx;
std::condition_variable cv;
std::queue<int> queue;
bool done = false;

void consumer() {
    std::unique_lock<std::mutex> lock(mtx);  // 必须是 unique_lock
    cv.wait(lock, [] { return !queue.empty() || done; });  // 等价于 while(!pred()) cv.wait(lock);
    // queue 非空或 done→消费
    while (!queue.empty()) {
        int val = queue.front(); queue.pop();
        lock.unlock();         // 消费数据时不持锁
        process(val);
        lock.lock();
    }
}

void producer() {
    {
        std::lock_guard<std::mutex> lock(mtx);
        queue.push(42);
    }
    cv.notify_one();  // 通知一个等待者（notify_all 通知全部）
}
```

### 4.2 为什么是 `while` 不是 `if`

```cpp
// 🔴 错误——用 if 检查条件
cv.wait(lock);  // 被唤醒
if (queue.empty()) { /* ... */ }  // 假唤醒→条件可能没变！

// ✓ 正确——用 while 重新检查
cv.wait(lock, [] { return !queue.empty(); });
// 等价于 while (!queue.empty()) { cv.wait(lock); }
```

POSIX 允许 `pthread_cond_wait` **假唤醒**（spurious wakeup）——在没有通知的情况下返回。C++ 继承了这份行为。`while` 确保唤醒后重新检查条件——`if` 可能"一觉醒来条件又变了"。

### 4.3 为什么 condvar 只能配 `unique_lock`

`cv.wait(lock)` 内部流程——(1) 原子释放锁 + 进入等待队列；(2) 被唤醒时重新获取锁。如果不先释放锁→生产者永远拿不到锁→死锁。`lock_guard` 不支持手动 unlock——`unique_lock` 支持。

## 5. `std::async` / `std::future`——异步任务的更高层抽象

### 5.1 启动异步任务

```cpp
#include <future>
#include <iostream>

int compute_heavy(int n) {
    int result = 0;
    for (int i = 0; i < n; i++) result += i;
    return result;
}

int main() {
    // async——自动管理线程 + 返回值
    std::future<int> result = std::async(std::launch::async, compute_heavy, 1000);

    // ... 干点别的 ...

    int value = result.get();  // 阻塞直到 compute_heavy 完成
    std::cout << value << '\n';
    return 0;
}
```

**`std::launch::async` vs `std::launch::deferred`**：
- `async`——启动新线程立即执行
- `deferred`——惰性求值。调用方第一次 `get()` 时才在当前线程执行

### 5.2 `promise` / `future` 配对

```cpp
#include <future>
#include <thread>

void producer(std::promise<int> p) {
    // 计算结果...
    p.set_value(42);  // 生产者端——存入结果
}

int main() {
    std::promise<int> prom;
    std::future<int> fut = prom.get_future();  // 从 promise 获取 future

    std::thread t(producer, std::move(prom));  // promise 转移给线程
    t.detach();

    int result = fut.get();  // 阻塞直到 producer 调用 set_value
    std::cout << result << '\n';  // 42
    return 0;
}
```

`promise` 是生产者端（`set_value`）、`future` 是消费者端（`get`）——比 C 的 `pthread_create` + `void*` 安全得多——类型安全 + 自动同步。

### 5.3 `future::get()` 只能调用一次

```cpp
auto f = std::async(compute);
int a = f.get();  // ✓ 第一次——获取结果
int b = f.get();  // 🔴 第二次——UB！future 已失效
```

`get()` 消耗 future——调用后 future 变成无效状态。需要多次读取→用 `std::shared_future`（允许多次 `get()`）。

## 6. `std::atomic<T>` 在并发中的位置 + 同步速查

C++ 内存模型已在 Stage3 Ch04 详讲。这里只做"并发场景下什么时候用什么"的速查：

| 同步方式 | 适用场景 | 开销 |
|---|---|---|
| `atomic<T>` + relaxed | 计数器/统计——不需要 happens-before | 仅原子指令 |
| `atomic<T>` + acquire/release | flag 通知——生产者-消费者配对 | x86 免费 / ARM DMB |
| `mutex` + `lock_guard` | 互斥访问共享资源——临界区 | 无竞争时纯用户态 (futex) |
| `condition_variable` | 等待条件成立——生产者-消费者 | futex + 可能的上下文切换 |
| `async`/`future` | 一次性异步任务——需要返回值 | 线程创建 + future 开销 |

**选择原则**：能用 `atomic` 不用 `mutex`、能用 `lock_guard` 不手写 `lock/unlock`、能用 `async` 不手写 `thread`。

**死锁检测工具**：
```bash
# TSan——编译时插桩，运行时检测（~2-5x 开销）
g++ -std=c++11 -g -fsanitize=thread program.cpp -o program
./program  # 检测数据竞争和锁顺序反转

# helgrind——valgrind 工具，模拟执行（~20-50x 开销，更全面）
valgrind --tool=helgrind ./program
```

## 7. 面试题

### 面试题 1：`lock_guard` vs `unique_lock`

**面试官**：`lock_guard` 和 `unique_lock` 的区别？什么时候必须用 `unique_lock`？

**回答**：`lock_guard` ——最简单的 RAII 锁包装，构造 lock、析构 unlock，无额外功能。`unique_lock` ——可延迟 lock（`defer_lock`）、可手动 unlock、可移动所有权。必须用 `unique_lock` 的场景——配合 `condition_variable`（`wait` 操作需要临时 unlock+重新 lock）、需要手动 `unlock` 再 `lock` 的灵活场景。默认用 `lock_guard`——只有需要 `unique_lock` 功能时才换。

**追问（面试官）**：`condition_variable::wait` 的参数为什么必须是 `unique_lock` 而不是 `lock_guard`？

**追问回答**：`wait` 的操作流程是——先原子释放锁、进入等待队列、被唤醒后重新获取锁。释放锁和重新获取锁需要一个支持 **手动 unlock + 手动 lock** 的锁类型。`lock_guard` 不支持手动操作——只有构造 lock、析构 unlock。`unique_lock` 提供完整的 `lock()`/`unlock()` 方法，满足 `wait` 的需要。

### 面试题 2：`async` vs `thread`

**面试官**：`std::async` 和 `std::thread` 的区别？什么时候用哪个？

**回答**：`thread` ——手动创建线程、手动 join/detach、需要自己管理返回结果（通过共享变量或 promise）。`async` ——自动管理线程生命周期、通过 `future` 返回结果、异常会自动传播到 `get()` 调用点。`async` 适用于"需要返回值的一次性异步任务"——`future<int> f = async(task); int x = f.get();`。`thread` 适用于长期运行的服务线程或需要精确控制的场景。

**追问（面试官）**：`std::future::get()` 有什么限制？

**追问回答**：只能调用一次——`get()` 会消耗 future，调用后 future 变成无效状态。重复 `get()` 是 UB。如果需要多次读取结果→用 `std::shared_future`（允许多次 `get()`，每次返回同样的值）。`shared_future` 的创建——`auto sf = fut.share();` 或 `std::shared_future<T> sf(std::move(fut));`。

### 面试题 3：条件变量的 while 和假唤醒

**面试官**：为什么 `condition_variable::wait` 条件检查要用 `while` 而不是 `if`？

**回答**：POSIX 允许 `pthread_cond_wait` **假唤醒**（spurious wakeup）——没有收到通知也能返回。如果 `if` 检查条件→假唤醒后继续执行→条件可能不成立→逻辑错误。`while` 确保每次唤醒后都重新检查条件——"一觉醒来再看看条件是不是真的满足了"。这是 C++ 继承 POSIX 的行为——和 C 阶段的条件变量使用完全一致。

**追问（面试官）**：`notify_one` 和 `notify_all` 怎么选？

**追问回答**：`notify_one` ——唤醒一个等待者。适用场景——每次只生产一个任务、消费者处理完一个再取下一个（如任务队列）。`notify_all` ——唤醒所有等待者。适用场景——状态变更后所有等待者都需要重新检查（如 shutdown 标记、配置变更）。如果不确定用哪个→`notify_all` 更安全——代价是多唤醒几个线程，它们重新检查条件发现没工作后又回去睡。

## 8. 本章小结

| 概念 | 核心理解 | 替代 C |
|---|---|---|
| `std::thread` | 必须 join/detach——否则析构 terminate | `pthread_create` + 手动 join |
| `lock_guard` | RAII 自动 unlock——**异常安全** | 手写 lock/unlock（易忘） |
| `unique_lock` | 延迟 lock / 手动 unlock / condvar 绑定 | — |
| `condition_variable` | `wait(lock, pred)` —— while 防假唤醒 | `pthread_cond_wait` |
| `async` / `future` | 自动线程 + 返回值——类型安全 | `pthread_create` + `void*` |
| `promise` / `future` | 生产者-消费者配对——`set_value` ↔ `get` | 手动传结果 |
