## 1. 引言：拷贝太慢了——能不能直接"偷"？

Ch02 教了你深拷贝——`Buffer b2 = b1;` 分配新内存、逐字节复制 `b1` 的数据。这保证了两份完全独立的数据——安全。但不总是高效。

看这个场景：

```cpp
Buffer make_buffer() {
    Buffer b("hello world");     // 构造 Buffer——分配内存、拷贝 "hello world"
    return b;                     // 🔴 返回——触发一次深拷贝！
}
Buffer b2 = make_buffer();       // 🔴 又触发一次深拷贝！
```

`make_buffer()` 内部的 `b` 是局部变量——函数返回后就销毁了。**没人再会用它**。但编译器不知道这一点——它老老实实地把 `b` 的数据深拷贝给 `b2`，然后析构 `b`（释放刚拷贝完的数据）。你分配了两份内存、做了两次拷贝——其中一次完全浪费。

这就是移动语义的核心：**你可以区分"我不再需要这个对象"和"我还要继续用它"**——前者走移动（"偷"资源、零拷贝），后者走拷贝（保持独立、保持安全）。

本章教你三件事：
1. 什么时候拷贝、什么时候移动——编译器怎么自动判断
2. `std::move` 不是"移动"，而是"我允许你被移动"——误会最多的地方
3. 移动让 Ch02 的 Rule of Three 升级为 Rule of Five

## 2. 左值与右值——编译器怎么知道"这个快死了"

### 2.1 左值和右值的通俗定义

移动的前提是"我知道这个对象快死了，可以偷"。编译器怎么知道？——通过**左值**和**右值**的区别：

| 概念 | 一句话 | 例子 |
|---|---|---|
| **左值（lvalue）** | 能取地址的、有名字的 | `int x = 5;` — `x` 是左值 |
| **右值（rvalue）** | 临时的、不能取地址的 | `5`、`x + y`、`make_buffer()` 返回值 |
| **左值引用** `T&` | 绑定左值 | `int &r = x;` ✓ / `int &r = 5;` ✗ |
| **右值引用** `T&&` | 绑定右值 | `int &&r = 5;` ✓ / `int &&r = x;` ✗ |

亲手试一下——编译下面这行：

```cpp
int &r = 5;   // ✗ 编译错误——左值引用不能绑定右值
```

再试：

```cpp
int &&r = 5;  // ✓ 右值引用可以绑定右值
```

**右值引用的核心理解**：右值引用 `T&&` 可以绑定到一个"临时的、即将销毁的值"——这就是"移动"的前提。你绑定到一个快死的东西上，就可以放心地把它的资源转移到别处——反正它马上毁灭了。

### 2.2 编译器什么时候选移动

当你用一个右值初始化一个对象时——编译器自动选择移动构造而不是拷贝构造。因为右值就是"临时的、没人会再用的值"——移动它安全+高效：

```cpp
Buffer b = make_buffer();   // make_buffer() 返回的是右值→编译器选移动构造
Buffer b = Buffer("hello"); // Buffer("hello") 是临时对象（右值）→选移动构造
```

当你用一个左值初始化时——编译器选拷贝构造。因为左值是"有名字的、还可能被后续代码使用的"——拷贝它安全：

```cpp
Buffer a("hello");
Buffer b = a;               // a 是左值→选拷贝构造——a 还要继续用
```

## 3. 移动构造函数与移动赋值——怎么写

### 3.1 从 Ch02 的 Buffer 出发

Ch02 的 Buffer 有拷贝构造（深拷贝）。现在加上移动构造——"偷"资源：

```cpp
class Buffer {
    char *data;
    size_t size;
public:
    Buffer(const char *src) : size(strlen(src) + 1), data(new char[size]) {
        memcpy(data, src, size);
    }

    // Ch02 教的——拷贝构造：深拷贝数据
    Buffer(const Buffer &other) : size(other.size), data(new char[size]) {
        memcpy(data, other.data, size);          // 逐字节复制——O(n)
    }

    // 🆕 移动构造——"偷"资源而不是拷贝
    Buffer(Buffer &&other) noexcept              // 注意 1：参数是 &&（右值引用）
        : data(other.data), size(other.size) {   // 注意 2：初始化列表直接"偷"指针
        other.data = nullptr;                     // 把源对象的 data 清空
        other.size = 0;                           // 防止源对象析构时释放我们偷来的 data
    }

    ~Buffer() { delete[] data; }
};
```

**移动构造和拷贝构造的关键区别**：
- 拷贝构造的参数是 `const T&`（左值引用）——"我要读你的数据，不动你"
- 移动构造的参数是 `T&&`（右值引用）——"我知道你快死了，你的资源给我"

**移动构造做了什么**：把源对象的 `data` 指针直接拷过来——不分配新内存、不拷贝数据。然后把源对象的 `data` 设为 `nullptr`——防止源对象析构时释放我们偷走的内存。O(1) 完成——和拷贝构造的 O(n) 天差地别。

### 3.2 为什么必须标记 `noexcept`

你刚刚看到移动构造标记了 `noexcept`——这不是可选优化，是**强制性要求**。原因：`std::vector` 扩容时需要移动已有元素：

- 如果移动构造有 `noexcept` → vector 用移动（快、安全——移动不会失败）
- 如果移动构造没有 `noexcept` → vector 不敢用移动——因为移动中途抛异常时数据已经"被偷"无法回滚——退化为拷贝

这意味着：**你的移动构造不加 `noexcept`，`vector<Buffer>` 扩容时走的是拷贝——白写了移动构造。** 移动构造、移动赋值、`swap`——永远标记 `noexcept`。

### 3.3 移动赋值——`a = std::move(b)`

和移动构造类似——对象已经"活着"，用另一个对象的资源替换自己的：

```cpp
Buffer& operator=(Buffer &&other) noexcept {
    if (this != &other) {
        delete[] data;           // 释放自己的旧资源
        data = other.data;       // 偷对方的资源
        size = other.size;
        other.data = nullptr;    // 清空源对象
        other.size = 0;
    }
    return *this;
}
```

## 4. `std::move`——不是"移动"，是"我允许你被移动"

### 4.1 `std::move` 只做类型转换，不生成任何代码

这是 C++ 世界最常见的误解之一——`std::move` 不"移动"任何东西：

```cpp
Buffer b1("hello");
Buffer b2 = std::move(b1);   // std::move 做了什么？只是类型转换——把 b1（左值）转成右值引用
// 真正"移动"的是 Buffer 的移动构造函数——它在 b2 的位置读取 b1 的 data 指针、清空 b1.data
```

`std::move` 等价于 `static_cast<T&&>(x)`——纯编译时类型转换，零运行时开销。它不生成任何机器码。起名叫 `move` 是命名失误——更准确的名字是 `std::enable_move` 或 `std::rvalue_cast`。

**那真正的"移动"在哪里？** 在移动构造函数里（§3）——它才真正做了"偷 data 指针、清空源对象"的工作。`std::move` 只是"允许"这段代码被调用——把参数从左值标记为右值，让编译器选择移动构造而不是拷贝构造。

### 4.2 `std::move` 之后——源对象变成"空壳"

```cpp
Buffer b1("hello");
Buffer b2 = std::move(b1);

// b2.data = 指向 "hello" 的内存 ← 从 b1 偷来的
// b1.data = nullptr              ← 被清空了
// b1 不能再被使用！它是一个"空壳"——调用 c_str() 返回 nullptr
```

**什么可以 move**：
- 临时对象（编译器自动选移动——不用写 `std::move`）
- 局部变量返回（编译器自动——见 §5 RVO）
- 你确实不再需要的变量（手动 `std::move`）

**什么不该 move**：
- 还有用的变量——move 之后它是空壳，再用是 bug

**"move 后误用"的真实 bug 场景**：

```cpp
Buffer b1("hello");
Buffer b2 = std::move(b1);   // b1 的 data 被偷走

// 后续代码不小心又用了 b1——
size_t len = strlen(b1.c_str());  // 🔴 b1.c_str() 返回 nullptr → strlen(nullptr) → SIGSEGV！
// 如果 c_str() 没有空指针检查（大多数 C API 没有），直接崩溃
```

**C++ 标准怎么说**：移动之后的源对象处于 **"有效但未指定状态"**（valid but unspecified）。你可以安全地析构它、可以给它赋值（`b1 = Buffer("new")`）、可以调用没有前置条件的函数（如 `clear()`）。但你不应该依赖它的具体值——比如假设 `data` 还是原来的内容、假设 `size` 还是原来的值。这和"空指针"不同——这是"值不确定"。

### 4.3 `return std::move(local_var)` 是坏习惯

```cpp
Buffer bad() {
    Buffer b("hello");
    return std::move(b);   // 🔴 坏习惯——阻止 RVO
}

Buffer good() {
    Buffer b("hello");
    return b;               // ✓ 让编译器决定
}
```

为什么？编译器对 `return b;` 可以做**RVO**（返回值优化）——直接把 `b` 构造在调用方的栈上，零拷贝零移动。`return std::move(b);` 强制返回右值引用→编译器不能用 RVO→多一次移动构造。**原则**：永远不要对 `return` 写 `std::move`——让编译器自动决定。

## 5. Rule of Five + RVO——类设计的完整版

### 5.1 从 Rule of Three 到 Rule of Five

Ch02 教了 Rule of Three——如果你需要自定义析构/拷贝构造/拷贝赋值中的任何一个，三个都必须自定义。C++11 多了两个：

| 函数 | Ch02 讲的 | 本章加的 |
|---|---|---|
| 析构函数 | ✅ | |
| 拷贝构造函数 | ✅ | |
| 拷贝赋值 | ✅ | |
| **移动构造函数** | | 🆕 |
| **移动赋值** | | 🆕 |

Rule of Five 的完整逻辑：如果你管理了资源（堆内存、文件、锁），你需要控制这个资源在**五种操作**中的行为——出生（构造）、拷贝（深拷贝）、移动（偷资源）、赋值（释放旧+拷贝新/偷新）、死亡（析构释放）。

### 5.2 Rule of Five→Rule of Zero

和 Ch02 说的 Rule of Zero 呼应——如果你的类成员全部是"自己管理自己"的标准库类型（`std::string`、`std::vector`、`std::unique_ptr`），编译器自动生成的五个函数完全正确。**Rule of Five 本身就是不推荐的使用场景**——用裸指针管理资源，这个场景在现代 C++ 用智能指针替代（Ch04）。

### 5.3 RVO/NRVO——编译器绕开移动

编译器有一种优化比移动更快——**完全不产生临时对象**。C++ 里实际有两种返回值优化：

**RVO（Return Value Optimization）**——返回**无名临时对象**时，编译器直接在调用方位置构造：

```cpp
Buffer make() {
    return Buffer("hello");   // 🔑 返回无名临时对象——RVO
}
Buffer b = make();   // 编译器在 b 的位置直接构造 Buffer("hello")——零拷贝零移动
```

**NRVO（Named Return Value Optimization）**——返回**有名字的局部变量**时，编译器可以优化（但不保证在所有情况下都生效）：

```cpp
Buffer make() {
    Buffer b("hello");         // 有名字的局部变量
    return b;                  // NRVO——编译器可能在 b 的位置直接构造结果对象
}
```

**RVO 比 NRVO 更可靠**——C++17 强制要求 RVO（返回无名临时对象），但 NRVO 仍然是"尽力而为"的优化。如果函数有多个 return 语句返回不同变量→NRVO 失效→退化为移动（有移动构造）或拷贝（无移动构造）。

RVO 在 C++17 是强制要求——C++11 不强制但所有主流编译器都做了。**怎么验证 RVO 是否生效**：给类加打印构造/拷贝/移动日志——编译运行看看输出——如果只看到 "default ctor" 没有 "MOVE ctor"，优化生效了。用 `g++ -fno-elide-constructors` 关闭所有返回优化对比。

## 6. 可运行实验

### 实验 1：`std::move` 之后再使用源对象

```cpp
#include <iostream>
#include <cstring>

class Buffer {
    char *data;
    size_t size;
public:
    Buffer(const char *src) : size(strlen(src) + 1), data(new char[size]) {
        memcpy(data, src, size);
    }
    Buffer(Buffer &&other) noexcept : data(other.data), size(other.size) {
        other.data = nullptr;
        other.size = 0;
    }
    ~Buffer() { delete[] data; }
    const char *c_str() const { return data ? data : "(stolen)"; }
};

int main() {
    Buffer b1("hello");
    Buffer b2(std::move(b1));       // b1 的 data 被偷走

    std::cout << "b2: " << b2.c_str() << "\n";   // "hello"
    std::cout << "b1: " << b1.c_str() << "\n";   // "(stolen)" — 空壳
    return 0;
}
```

**编译运行**：`g++ -std=c++11 move_test.cpp && ./a.out`

### 实验 2：`return std::move` 阻止 RVO

```cpp
#include <iostream>

struct Foo {
    Foo()           { std::cout << "  default ctor\n"; }
    Foo(const Foo&) { std::cout << "  COPY ctor\n"; }
    Foo(Foo&&)      { std::cout << "  MOVE ctor\n"; }
};

Foo make_good() { Foo f; return f; }        // RVO 生效——零输出
Foo make_bad()  { Foo f; return std::move(f); } // 强制 move——多一次 MOVE

int main() {
    std::cout << "Good:\n";
    Foo g = make_good();
    std::cout << "\nBad:\n";
    Foo b = make_bad();
    return 0;
}
```

**编译运行**：`g++ -std=c++11 rvo.cpp && ./a.out`——`make_good` 零输出（RVO），`make_bad` 多一次 MOVE ctor。

## 7. 面试题

### 面试题 1：移动构造 vs 拷贝构造

**面试官**：什么时候会调用移动构造函数而不是拷贝构造函数？移动构造做了什么？

**回答**：当初始化的源头是右值（临时对象、`std::move` 转换后的左值）时调用移动构造。移动构造"偷"源对象的资源（把 `data` 指针拷过来）而不是分配新内存拷贝数据——O(1) vs O(n)。源对象被置为"空壳"（`data = nullptr`），防止析构时重复释放。关键标志——参数 `T&&` + `noexcept`。

**追问（面试官）**：为什么移动构造必须标记 `noexcept`？不标记有什么后果？

**追问回答**：`std::vector` 扩容时检查移动构造是否是 `noexcept`——是就用移动，不是就用拷贝（因为移动失败无法回滚：旧对象已被偷、新对象构造失败→数据永久丢失）。不加 `noexcept` → `vector<Buffer>` 扩容走拷贝→性能白给。所以：移动构造、移动赋值、`swap`——永远 `noexcept`。

### 面试题 2：std::move 的真相

**面试官**：`std::move` 做了什么？为什么叫"move"但其实不移动任何东西？

**回答**：`std::move` 是纯类型转换——`static_cast<T&&>(x)`——把左值转成右值引用。零运行时开销。它不"移动"数据——只是告诉编译器"把这个值当右值处理，触发移动构造"。真正的移动在移动构造函数里。更准确的名字是 `std::enable_move`。

**追问（面试官）**：`return std::move(local_var);` 是好习惯还是坏习惯？

**追问回答**：坏习惯——阻止 RVO。编译器本来可以把 `local_var` 直接在调用方构造（零拷贝零移动），但 `std::move` 强制右值引用→编译器不能用 RVO→多一次移动。原则：`return local_var;` 让编译器决定。

### 面试题 3：Rule of Five→Rule of Zero

**面试官**：Ch02 的 Rule of Three 在 C++11 变成了 Rule of Five——多了哪两个？为什么需要？

**回答**：多了移动构造函数和移动赋值运算符。如果类管理堆内存，移动避免深拷贝——大型 Buffer 从 O(n) 降到 O(1)。Rule of Five 的逻辑：管理资源 → 控制出生（构造）/拷贝/移动/死亡（析构）五种操作。

**追问（面试官）**：什么时候 Rule of Five 可以简化为 Rule of Zero？

**追问回答**：类成员全部是标准库类型（`std::string`/`std::vector`/`std::unique_ptr`）时——编译器自动生成的五个函数完全正确。Rule of Zero——用标准库类型替代裸指针，让编译器替你管理——这对应 Ch04 的智能指针。
