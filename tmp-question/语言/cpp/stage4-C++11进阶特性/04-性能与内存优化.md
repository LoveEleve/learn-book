## 1. 引言：正确的代码 ≠ 快的代码

前 15 章教了你怎么写出**正确**的 C++ 代码——类/RAII/智能指针/模板/STL/虚函数/异常安全。本章的视角不同——同样正确的代码，性能可以差 10 倍：

```cpp
// 这两行功能完全一样——但速度不同
v.push_back(std::string(5, 'x'));  // 临时构造 → 移动 → 析构——三步
v.emplace_back(5, 'x');             // 原地构造——一步

// 这两行也功能完全一样——但 vector 扩容时的代价不同
struct FastMove { FastMove(FastMove&&) noexcept {} };       // ✓ 扩容用移动
struct SlowMove { SlowMove(SlowMove&&) {} };                 // ✗ 扩容用拷贝
```

优化不是"加 `-O3` 编译"——是理解每一行代码在 CPU 缓存、内存分配、编译器优化层面的代价。本章教你用工具量化性能——`perf` 告诉你热点在哪、benchmark 告诉你改完之后快了多少、编译选项告诉你多快才算"够快"。

## 2. `emplace` 系列——零拷贝构造

### 2.1 `emplace_back` vs `push_back`

```cpp
#include <vector>
#include <string>

std::vector<std::string> v;

// push_back——三步走：
// (1) std::string(5, 'x') → 临时对象构造
// (2) 移动到 vector 内部
// (3) 临时对象析构
v.push_back(std::string(5, 'x'));

// emplace_back——一步到位：
// 把参数 (5, 'x') 原样转发给 vector 内部的 string 构造函数
// 在 vector 的内存上直接构造——零拷贝、零移动
v.emplace_back(5, 'x');
```

**性能差异**：`push_back` 对 `string` 这种有堆内存的类型——临时对象的构造（一次 `new`）、移动（指针交换，零 `new`）、临时对象的析构（一次 `delete`）。`emplace_back` 只有一次 `new`——省了 `new`+`delete` 各一次。

### 2.2 什么时候 `emplace` 有收益

| 对象类型 | push_back | emplace_back | 收益 |
|---|---|---|---|
| `int` / 指针 | 一次拷贝 / 移动 | 同上 | **无——大小一样** |
| `string` / `vector` | 临时构造+移动+析构 | 原地构造一次 | **大——省了一次内存分配** |
| 有 RAII 的自定义类型 | 同上 | 同上 | 取决于构造代价 |

### 2.3 `push_back` 传右值 vs `emplace_back` 传构造参数

```cpp
// 场景 1：push_back 传右值——和 emplace_back 一样快（都是移动）
std::string s = "hello world, this is a long string";
v.push_back(std::move(s));       // 移动构造进 vector
v.emplace_back(std::move(s));    // 同样——移动构造进 vector
// 这俩性能等价——都是移动

// 场景 2：emplace_back 直接传构造参数——真正省掉临时对象
v.push_back(std::string(5, 'x')); // 临时 string → 移动 → 析构
v.emplace_back(5, 'x');           // 原地构造——省掉临时对象
// emplace 只有在"传构造参数"时才比 push_back 快
```

**核心规则**：`emplace_back` 的优化来自**跳过临时对象**。如果你传的是一个现成对象→和 `push_back` 一样。如果你传的是构造参数→省掉一次构造。

## 3. `noexcept` 的性能兑现——Vector 扩容的真实收益

### 3.1 Benchmark——亲眼看到差距

```cpp
#include <vector>
#include <chrono>
#include <iostream>

struct NoExcept {
    char data[256];                          // 256 字节——足够大
    NoExcept() {}
    NoExcept(NoExcept&&) noexcept {}         // ✓ noexcept
};

struct Throwing {
    char data[256];
    Throwing() {}
    Throwing(Throwing&&) {}                  // ✗ 没有 noexcept
};

template<typename T>
double bench() {
    std::vector<T> v;
    auto start = std::chrono::steady_clock::now();
    for (int i = 0; i < 100000; i++) {
        v.push_back(T{});  // 触发多次扩容
    }
    auto end = std::chrono::steady_clock::now();
    return std::chrono::duration_cast<std::chrono::milliseconds>(end - start).count();
}

int main() {
    std::cout << "noexcept: " << bench<NoExcept>() << " ms\n";
    std::cout << "throwing: " << bench<Throwing>() << " ms\n";
    // 预期：noexcept 快 3-5 倍——扩容用移动（O(1) 交换指针）vs 拷贝（O(n) 逐元素拷贝）
    return 0;
}
```

**编译运行**：`g++ -std=c++11 -O2 noexcept_bench.cpp -o bench && ./bench`

### 3.2 为什么会这样

`vector` 扩容时调用 `std::move_if_noexcept`——如果移动构造标记了 `noexcept`：返回 `T&&`（走移动，O(1) 指针交换）。如果没标记 `noexcept`：返回 `const T&`（走拷贝，O(n) 逐元素深拷贝）。

**为什么 `vector` 不信任没有 `noexcept` 的移动**：移动到一半如果抛异常——新的 buffer 部分填充了新对象、旧的 buffer 已经释放了部分——无法回滚。`vector` 的强异常安全保证要求"要么全做、要么全不做"——拷贝可以做到（失败时旧 buffer 完好）、移动保证不了——除非你标记 `noexcept`。

### 3.3 编译时检查

```cpp
#include <type_traits>

// 编译时验证——如果你的移动构造没标记 noexcept，这里直接编译报错
static_assert(std::is_nothrow_move_constructible<NoExcept>::value,
              "NoExcept must have noexcept move constructor");
```

## 4. 内存优化——缓存、对齐与分配器

### 4.1 AoS vs SoA——缓存友好的数据结构

```cpp
// AoS（Array of Structs）——每个对象的字段连续，适合逐对象遍历
struct Particle {
    float x, y, z;     // 12 字节
    float vx, vy, vz;  // 12 字节
};
std::vector<Particle> particles;  // 所有粒子连续存储

// 遍历所有粒子的位置——缓存友好（24 字节连续读入 cache line）
for (auto& p : particles) {
    p.x += p.vx;
    p.y += p.vy;
    p.z += p.vz;
}

// SoA（Struct of Arrays）——同一字段排列在一起，适合同字段批量运算
struct ParticleSystem {
    std::vector<float> x, y, z;  // 三个独立分配
    std::vector<float> vx, vy, vz;
};

// 所有粒子的 x 坐标做运算——缓存不友好 SoA、缓存友好 AoS？
// 错误——这是依赖于"访问什么"而不是数据结构本身
```

**选择原则**：

| 访问模式 | 选 | 原因 |
|---|---|---|
| 遍历每个对象的多个字段 | AoS | 一个对象的数据在同一个 cache line 里 |
| 对"所有对象的同一个字段"做运算 | SoA | 只加载你需要的字段——不浪费 cache 加载不用的字段 |
| 不确定？ | AoS | 默认——更像你自然建模的方式 |

### 4.2 False Sharing——两个线程互相拖慢

两个线程写不同的变量——但因为它们在同一个 cache line 里而互相拖慢：

```cpp
#include <thread>
#include <atomic>

// 🔴 False sharing——两个计数器在同一个 64 字节 cache line 里
struct Counters {
    std::atomic<int> produced{0};  // 线程 A 写
    std::atomic<int> consumed{0};  // 线程 B 写
};
// A 写 produced → CPU A 的 cache line 变成 "modified"
// → 向 CPU B 发 invalidate → B 的 cache line 被标记为无效
// → B 写 consumed → 需重新加载整个 cache line → A 的又失效了...
// 两个完全不相关的变量互相拖慢——每次写入都触发跨核可见性同步

// ✓ 对齐隔离——每个变量独占一个 cache line
struct alignas(64) CountersFixed {
    std::atomic<int> produced{0};
    char pad1[60];  // padding——填满 64 字节
    std::atomic<int> consumed{0};
    char pad2[60];
};
// 或 C++17 的 std::hardware_destructive_interference_size——自动获取平台 cache line 大小
```

### 4.3 内存池——批量分配减少系统调用

每次 `new` 可能触发系统调用（`mmap`/`brk`）。内存池预分配一大块→切给你→释放时整块 `delete`：

```cpp
// 默认分配——每个对象一次 malloc → N 个对象 N 次系统调用
for (int i = 0; i < 10000; i++) {
    auto* p = new Particle();  // 每次可能走 mmap
    // ... 使用 p ...
    delete p;                   // 每次可能走 munmap
}

// 内存池——预分配 10000 个对象空间→O(1) 从池中取
// 不在标准库中——需要自己写或用第三方库
// 但理解这个概念就够了——大部分场景默认分配器已经够好
```

## 5. 用 `perf` 找热点——不要猜，要量

### 5.1 完整工作流

```bash
# Step 1：编译——保留调试符号（-g）+ frame pointer（perf 需要）
g++ -std=c++11 -O2 -g -fno-omit-frame-pointer program.cpp -o program

# Step 2：采样——perf 记录每 1000 个 CPU 周期程序在哪
perf record -g ./program

# Step 3：看报告——哪个函数花了最多 CPU 时间
perf report
```

`perf report` 输出每个函数的 CPU 占比——你不需要猜"这里可能慢"，它直接告诉你热点在哪。如果 `quicksort` 占了 80% CPU→要么优化排序算法、要么想办法少排序。

### 5.2 cache miss 和分支预测

```bash
# cache miss 分析——如果 cache miss 率 > 5-10%，数据结构可能不友好缓存
perf stat -e cache-misses,cache-references ./program

# 分支预测——高分支 miss 暗示 if 条件不够可预测 → 考虑查表或位运算
perf stat -e branch-misses,branches ./program
```

## 6. 编译优化——`-O2` vs `-O3` 的实际影响

### 6.1 优化级别

| 级别 | 做了什么 | 适用 | 注意事项 |
|---|---|---|---|
| `-O0` | 无优化 | 开发/调试 | 代码直译——无内联 |
| `-O1` | 基础优化 | 调试点性能 | 内联简单函数 |
| `-O2` | **生产标准** | 绝大多数场景 | 速度与体积平衡——不展开太大的内联 |
| `-O3` | 激进优化 | 计算密集型 | 积极内联+向量化——可能增大二进制 |

### 6.2 `-O2` 是生产默认

`-O2` 包含了最重要的优化——inline、常量传播、死代码消除、循环优化——不疯狂展开内联导致代码膨胀。`-O3` 更激进的内联可能让二进制体积暴涨 20-50% → instruction cache miss 增加 → 不测不知道是快了还是慢了。

**唯一判断方法——benchmark**。拿到 `-O2` 和你候选方案的实测数据，选最快的。

### 6.3 `-march=native` 的陷阱

`-march=native` 让编译器利用你当前 CPU 的所有指令集（SSE/AVX/AVX-512）——生成的二进制在别的 CPU 上可能 `SIGILL`（非法指令）：

```bash
# 开发机：Intel Core i9（有 AVX-512）
g++ -O2 -march=native program.cpp -o program   # 生成 AVX-512 指令

# 部署到云上（AMD EPYC，无 AVX-512）
./program   # 💀 SIGILL——非法指令！
```

生产环境 CI 应该用目标部署平台的最低 CPU 指令集编译——或 `-march=x86-64-v2` 指定最低要求。

## 8. 面试题

### 面试题 1：`emplace_back` vs `push_back`

**面试官**：`emplace_back` 和 `push_back` 的区别？为什么 `emplace_back` 更快？

**回答**：`push_back`——先构造临时对象→拷贝/移动到容器→临时对象析构（三步）。`emplace_back`——把构造参数原地转发给容器→在容器内部一次构造完成（一步）。省了临时对象的构造和析构。对大对象（有堆内存分配的类型如 `string`/`vector`）收益最大——每次省一次 `new`+`delete`。

**追问（面试官）**：`push_back` 传右值和 `emplace_back` 有什么区别？

**追问回答**：`v.push_back(std::move(obj))` ——移动进容器（一次移动构造）。`v.emplace_back(std::move(obj))` ——用移动构造在原地构造。两者在这个场景下**性能等价**——都是移动。`emplace_back` 只有传**构造参数**（如 `v.emplace_back(5, 'x')`）才比 `push_back(string(5, 'x'))` 有优势——省了一次临时对象。核心规则——`emplace` 的优势来自跳过临时对象，不是来自"emplace 本身比 push 快"。

### 面试题 2：缓存优化

**面试官**：什么是 false sharing？怎么用 C++11 解决？

**回答**：两个线程写不同变量——但它们在同一个 cache line 里（64 字节）。当一个线程写入→该 cache line 被标记为"dirty"→另一个 CPU 的 cache line 被 invalidate→下次读写需要重新加载。两个不相关的变量互相拖慢——每次写入都触发跨核缓存一致性同步。C++11 解决——`struct alignas(64) { ... }` 让变量独占一个 cache line，或 C++17 的 `hardware_destructive_interference_size` 自动获取平台 cache line 大小。

**追问（面试官）**：AoS 和 SoA 的区别？什么时候用哪种？

**追问回答**：AoS（Array of Structs）——`struct Particle {float x,y,z;}; vector<Particle>` ——遍历一个对象的多个字段缓存友好（对象数据在同一个 cache line 里）。SoA（Struct of Arrays）——`struct Particles {vector<float> x,y,z;};` ——对所有对象的同一个字段做运算时缓存友好（只加载你需要的字段，不浪费 cache）。粒子物理——逐粒子更新位置+速度→AoS。矩阵乘法——逐分量运算→SoA。

### 面试题 3：编译器优化级别的选择

**面试官**：`-O2` 和 `-O3` 的区别？为什么生产代码用 `-O2` 而不是 `-O3`？

**回答**：`-O2` ——标准优化（内联/常量传播/死代码消除/循环优化），速度与体积平衡。`-O3` ——更激进的内联、向量化、循环展开——但可能让二进制体积暴涨 20-50%→I-cache miss 增加→有时比 `-O2` 慢。加上更长的编译时间 + 更难的调试（优化太激进导致 debug 信息不准）。生产默认 `-O2`，`-O3` 只在 benchmark 证明收益时对特定文件启用。

**追问（面试官）**：`-march=native` 有什么风险？

**追问回答**：编译器利用当前 CPU 的所有指令集——包括 AVX-512 等扩展指令。生成的二进制在 CI 机器上跑快——但部署到老 CPU 或不同云实例类型上→缺少对应指令→`SIGILL` 直接崩溃。生产环境 CI 应该用目标部署平台的最低 CPU 指令集编译——或 `-march=x86-64-v2` 指定最低要求。

### 9.1 本章小结

| 概念 | 核心理解 |
|---|---|
| `emplace_back` | 跳过临时对象——只传构造参数时才比 push_back 快 |

| `perf` | 编译→采样→看报告→改代码→再测——闭路优化工作流 |
| `-O2` vs `-O3` | `-O2` 生产标准——`-O3` 不一定更快（代码膨胀→I-cache miss） |
